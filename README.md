# IT 단어 학습 목업

🟡 개발 중 · UI/UX 프로토타입 단계

Obsidian `IT단어장` vault 를 읽어서 모바일에서 공부하기 좋게 보여주는 학습 웹앱의 목업이다.
지금 단계의 목표는 기능 완성이 아니라 **디자인과 화면 흐름을 눈으로 확인하고 승인받는 것**이다.

## 실행

```bash
cd apps/development/it-roadmap
python3 -m http.server 8000
# http://localhost:8000 을 브라우저에서 연다
```

`index.html` 을 더블클릭해서 `file://` 로 열어도 동작한다. 외부 프레임워크도 빌드 단계도 없다.

모바일 화면을 기준으로 만들었으므로, 데스크톱 브라우저라면 개발자 도구의 기기 모드에서
iPhone 크기(390 x 844)로 보는 것을 권한다.

## 무엇이 되는가

- 홈에서 "지금 뭘 하면 되는지" 한 화면에 제시
- 단어장 6개 / 단어 36개 (vault 에서 실제로 추출한 내용)
- 검색, 상태 필터, 이전/다음 단어 이동
- 단어 상세에서 progressive disclosure 로 깊이 조절
- 학습 완료 처리, 퀴즈 3종, 즉시 피드백과 해설, 결과 요약
- 틀린 단어가 복습 대기열로 넘어가는 학습 루프
- 진도 화면(전체/공부한/통과/복습 필요, 연속 학습일, 단어장별 진행률, 기록)
- 밝은 화면 / 어두운 화면, 시스템 설정 따름 + 수동 전환
- 상태는 `localStorage` 에 남아서 껐다 켜도 이어진다

로그인도 서버도 데이터베이스도 없다. 목업 단계에서는 필요하지 않다.

## 데이터

원본은 다음 경로이며, **읽기만 하고 수정하지 않는다**.

```
~/Library/Mobile Documents/iCloud~md~obsidian/Documents/IT단어장
```

`tools/obsidian_adapter.py` 가 Markdown 을 읽어 `data/vocabulary.js` 를 만든다.

```bash
# 목업용 큐레이션 세트 (단어장 6개 x 6단어)
python3 tools/obsidian_adapter.py --out data/vocabulary.js

# vault 전체 (단어장 15개, 단어 242개)
python3 tools/obsidian_adapter.py --all --out data/vocabulary.js

# 어떤 단어가 잡히는지만 확인
python3 tools/obsidian_adapter.py --dry-run
```

목업에는 일부러 36개만 넣었다. 전체 방향을 보는 데는 그걸로 충분하고,
단어가 많아졌을 때의 탐색(검색/필터)도 이 정도면 확인된다.
전체로 바꾸려면 `--all` 로 다시 만들면 되고, UI 는 손댈 필요가 없다.

어댑터가 vault 에서 뽑아내는 것:

| 원본 | 앱에서 쓰이는 곳 |
|---|---|
| `# 용어 (읽는 법)` | 표제어, 원어 표기 |
| `## 📝 정의` 첫 문장 | 한 줄 뜻 (항상 보이는 자리) |
| 나머지 본문 | 상세 설명 |
| `### 하위 절` | 접이식 섹션 |
| `## ⚠️ 해결하는 문제` | "왜 필요한가" |
| `## ⚙️ 작동 원리` | "어떻게 작동하나" |
| `## 📊 비교`, `## 💡 실제 사례` 등 | 각 접이식 섹션 |
| `## 🔗 관련 용어` 의 `[[링크]]` | 관련 개념, 퀴즈 출제 근거 |
| 폴더 이름 | 단어장 분류 |

노트마다 제목 표기가 조금씩 달라서(`## 💡 HTTP 메서드` 처럼 용어명이 낀 제목),
매핑에 없는 제목은 버리지 않고 원문 제목 그대로 살린다. 다만 어느 학습 단계인지는
제목의 단어로 추측해서 읽는 순서를 맞춘다. 왜 -> 어떻게 -> 개념 -> 비교 -> 사례 순이다.

## 조사한 것과 거기서 가져온 것

디자인을 상상해서 만들지 않았다. 아래를 먼저 확인하고 각각에서 하나씩 가져왔다.

**Apple Human Interface Guidelines (탭 바)**
탭은 3~5개를 쓰고, 화면을 옮겨 다녀도 탭 바는 계속 보여야 한다.
다만 모달성 화면에서는 감춰도 된다.
→ 목적지를 4개로 고정했다. 그리고 읽기 화면과 퀴즈 진행 화면에서만 탭 바를 감춘다.
그 두 화면은 하나의 일에 집중하는 자리이기 때문이다.

**Material Design 3 (내비게이션 바)**
하단 내비게이션은 3~5개, 최상위 목적지 전용이다.
→ 하위 내비게이션을 탭 바에 밀어 넣지 않았다. 단어장 안의 필터는 화면 안의 칩으로 뒀다.

**Anki (학습 상태 모델)**
카드를 New / Learning / Review 로 나누고, 덱 화면에서 오늘 할 양을 숫자로 먼저 보여준다.
→ 상태를 5개로 정리했다. 안 봄 / 읽는 중 / 학습 완료 / 퀴즈 통과 / 복습 필요.
이 다섯 개가 앱 전체에서 같은 이름, 같은 색, 같은 아이콘으로 쓰인다.
그리고 홈에서 "오늘 뭘 할지"를 목록이 아니라 행동 하나로 제시한다.

**Quizlet Learn (적응형 출제)**
틀린 항목을 더 자주 물어보는 방식으로 학습을 개인화한다.
→ 퀴즈에서 틀리면 그 자리에서 복습 대기열로 넘어간다. 별도 조작이 필요 없다.
홈과 탭 바의 배지가 그 숫자를 계속 보여준다.

**Readwise Reader (긴 글 읽기)**
긴 글을 읽을 때는 액션이 많은 하단 바를 감추고 읽기 진행률만 남긴다.
→ 단어 상세에서 탭 바를 감추고, 화면 최상단에 2px 짜리 읽기 진행선을 뒀다.
하단에는 지금 필요한 액션 하나와 이전/다음만 남겼다.

**Nielsen Norman Group (progressive disclosure)**
처음에는 자주 쓰는 것만 보이고, 나머지는 요청할 때 연다.
단계는 2단계까지만 만든다. 3단계 이상이면 사용성이 떨어진다.
버튼 이름은 열었을 때 뭐가 나오는지 알 수 있어야 한다.
→ 항상 보이는 것은 표제어와 한 줄 뜻과 짧은 본문까지다.
그 아래는 "왜 필요한가", "어떻게 작동하나" 처럼 내용을 말하는 이름으로 접어뒀다.
"더보기" 같은 이름은 쓰지 않았고, 3단계는 만들지 않았다.

**Notion / NotebookLM 계열의 인상**
UI 가 콘텐츠보다 눈에 띄지 않는다.
→ 브랜드 색을 따로 두지 않았다. 가장 진한 잉크색이 곧 주요 버튼 색이다.
색은 학습 상태를 말할 때만 쓴다.

## 여기서 뽑은 디자인 원칙 6가지

1. **3초 안에 다음 할 일이 보인다.** 홈은 통계판이 아니라 "다음 단어 하나 + 시작 버튼"이다.
2. **한 화면에 다 넣지 않는다.** 항상 보이는 것과 눌러서 여는 것을 나눈다. 2단계까지만.
3. **학습 루프가 버튼에 드러난다.** 상세 화면의 주 버튼이 상태에 따라 바뀐다.
   학습 완료 -> 퀴즈로 확인하기 -> 복습 목록에 넣기. 읽고 끝나지 않게 한다.
4. **색만으로 뜻을 전달하지 않는다.** 상태는 색 + 아이콘 + 글자를 항상 같이 쓴다.
5. **UI 가 콘텐츠보다 튀지 않는다.** 그라디언트, 유리 효과, 큰 그림자, 큰 아이콘을 쓰지 않는다.
6. **게임처럼 만들지 않는다.** 연속 학습일은 보여주되 불꽃도 레벨도 트로피도 없다.
   학습 관리 도구의 인상을 유지한다.

```
 ├── 오늘의 단어 + 시작 버튼
 ├── 복습 대기 알림 (있을 때만)
 ├── 공부 중인 단어장
 └── 최근에 본 단어

단어장                       무엇을 공부할 수 있는가
 └── 단어 목록               검색 / 상태 필터
      └── 단어 상세          집중해서 읽는 자리 (탭 바 숨김)
           ├── 표제어 + 한 줄 뜻     항상 보임
           ├── 접이식 섹션 최대 5개   눌러서 열기
           ├── 관련 개념             눌러서 열기
           └── 하단 고정 액션        상태에 따라 라벨이 바뀜

퀴즈                        정말 이해했는가
 ├── 범위 고르기 (복습 / 학습 완료 / 단어장별)
 ├── 문제 -> 답 선택 -> 즉시 피드백과 해설 -> 다음
 └── 결과: 점수, 복습으로 넘긴 단어, 통과한 단어

진도                        어디까지 왔는가
 ├── 전체 / 공부한 / 통과 / 복습 필요
 ├── 최근 7일과 연속 학습일
 ├── 단어장별 진행률
 └── 학습 기록
```

## 퀴즈를 어떻게 냈는가

암기가 아니라 이해를 확인하는 게 목적이라 세 종류를 섞는다.

1. **설명에서 용어 찾기** 뜻을 읽고 이름을 떠올릴 수 있는가
2. **용어의 뜻 고르기** 이름을 보고 뜻을 고를 수 있는가
3. **같이 쓰이는 개념** 노트의 `관련 용어` 를 정답으로 쓴다

내용을 몰라도 맞힐 수 있는 길을 막는 데 신경을 썼다.

- 오답은 **같은 단어장 안에서** 뽑는다. 전혀 다른 분야에서 뽑으면 소거법으로 풀린다.
- 지문에서 정답 용어를 지운다. 노트마다 제목은 영문인데 본문은 한글 이름을 쓰는 경우가 있어서
  (`# Load Balancer` 인데 본문은 "로드 밸런서는"), 용어명 필드가 아니라 문장의 앞머리를 찾아 지운다.
- 보기 길이를 맞춘다. 정답만 유난히 길면 읽지 않고도 고를 수 있다.
  길이가 비슷한 오답을 골라서, 가장 긴 보기가 정답인 비율을 23~26%로 맞췄다 (무작위면 25%).
- 보기에는 마크다운을 렌더하지 않는다. 굵은 글씨가 한 보기에만 남으면 그것도 힌트가 된다.

## 확인한 것

브라우저(390 x 844)에서 실제로 열어 화면마다 확인했고,
헤드리스 하네스로 전 화면 렌더와 퀴즈 한 판을 자동으로 돌려서 검증했다.

- 화면 6종 전부 렌더, 단어 36개 상세 전부 렌더, 오류 없음
- 퀴즈 흐름: 범위 선택 -> 문제 -> 피드백 -> 결과 -> 복습 반영까지 연결
- 지문에 정답이 노출되지 않음
- 상태 전이: 안 봄 -> 읽는 중 -> 학습 완료 -> 퀴즈 통과 -> 복습
- 원본 Markdown 은 한 글자도 바뀌지 않았다 (어댑터는 읽기 전용)
