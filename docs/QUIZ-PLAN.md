2026-08-16 작성.

## 지금 얼마나 작은가 (실측)

```
단어 229편 · 12권
퀴즈 문제 유형 3개 — 전부 "한 줄 뜻" 과 "관련 용어" 에서만 만든다
단어 하나당 문제 하나 (세 유형 중 무작위로 하나만 고른다)
```

**단어를 다 읽어도 한 판에 8문제.** 권 하나가 34편인데도 8문제다.
그리고 한 단어는 늘 한 가지 형식으로만 나온다.

## 무엇을 더할 것인가

### 원칙 — 문제 수를 늘리는 게 목적이 아니다

억지로 문제를 찍어내면 "아는데 틀리는" 문제가 생기고, 그건 학습을 망친다.
**답의 근거가 노트 안에 있는 것만** 문제로 만든다. 지금 세 유형이 지키는 규칙이고
새 유형도 똑같이 지킨다.

오답 선택지는 **같은 단어장 안에서** 뽑는다. 다른 분야에서 뽑으면 내용을 몰라도
소거법으로 맞힐 수 있어 이해를 확인하지 못한다. (기존 규칙 유지)

### 새 문제 유형 6개

| 유형 | 무엇을 묻나 | 재료 | 만들 수 있는 양 |
|---|---|---|---|
| `MYTH` 오해 판별 | 이 말이 맞나 틀리나 (O/X) | 흔한 오해 | **687** |
| `MYTH_PICK` 틀린 것 고르기 | 넷 중 틀린 진술 하나 | 흔한 오해 + 정정문 | 229 |
| `ANALOGY` 비유에서 용어 | 이 비유는 어떤 개념인가 | 비유 | 229 |
| `FIGURE` 그림이 답하는 질문 | 이 그림은 무엇을 설명하나 | 대표 도해 | 229 |
| `ORDER` 흐름 순서 | 네 마디를 순서대로 | 흐름 도해 | 205 |
| `CASE` 사례에서 용어 | 이 상황은 어떤 개념인가 | 실제 사례 | 229 |

합치면 **약 1,800문항**이 나온다. 지금은 229편에서 229문항이다.

### 구조도 함께 고친다

1. **단어 하나에 문제 하나** 제한을 푼다. 지금 `buildFor` 는 만들 수 있는 문제 중
   하나만 고르고 나머지를 버린다. 한 단어를 여러 각도로 물을 수 있어야
   "외웠는지" 가 아니라 "이해했는지" 가 확인된다.
2. **한 판 길이를 고를 수 있게 한다.** 8문제 고정 대신 짧게(8) · 보통(15) · 길게(30).
   범위가 34편인데 8문제만 나오는 건 범위를 고른 의미가 없다.
3. **유형이 고르게 섞이게 한다.** 지금은 무작위라 한 판이 같은 유형으로 쏠릴 수 있다.
4. **회상 화면에 저자의 질문을 쓴다.** `js/recall.js` 는 지금 단어만 보여주고
   "떠올랐나" 를 묻는다. 저자가 쓴 확인 질문 687개가 있으니 그걸 묻는 게 낫다.
   이건 `docs/TERM-TEMPLATE.md` 말미에 적힌 미해결 TODO 이기도 하다.

## 데이터 계약 (먼저 정한다)

새 유형은 Markdown 을 다시 파싱하면 안 된다. 화면 쪽에서 파싱하면 렌더러와
갈라지고, 노트 형식이 바뀔 때마다 조용히 깨진다. **`tools/build.py` 가 구조로 굽는다.**

`data/terms/<권>.js` 의 단어마다 다음을 더한다.

```js
"myths": [                          // 흔한 오해. 지금은 sections 안의 Markdown 이다
  { "wrong": "DNS 가 사이트에 연결해준다",
    "right": "아니다. IP 주소를 알려주고 거기서 끝난다." }
],
"cases": [                          // 💡 실제 사례. "**라벨** — 설명" 을 갈라 담는다
  { "label": "무중단 배포", "note": "새 서버를 띄우고 A 레코드만 바꾸면…" }
],
"dia": {                            // 대표 도해를 구조로. figure(원문)는 그대로 둔다
  "shape": "흐름",                   // 흐름 | 대조 | 층
  "title": "주소창에 google.com 을 치면 무슨 일이 일어나나",
  "rows": [ { "who": "브라우저", "what": "캐시에 있나? 있으면 여기서 끝난다" } ],
  "sum": "다섯 번을 물어 찾아가는 길이지만, 열에 아홉은 첫 줄에서 끝난다"
}
```

`analogy` · `check` 는 이미 실려 있다. `check` 는 `[{q, at}]` 형태다.

**기존 필드를 하나도 바꾸지 않는다.** 더하기만 한다. 단어 id 도 그대로다.

## 문제 객체 계약 (기존 형태를 유지한다)

`js/quiz-screens.js` 가 이미 아는 형태를 그대로 쓴다. 새 유형이라고 새 모양을
만들지 않는다 — 화면이 유형마다 다르게 그려야 하면 유형을 늘릴 때마다 화면도 늘어난다.

```js
{
  kind: KINDS.MYTH,        // 유형 이름
  termId: "net--dns",
  prompt: "다음 설명은 맞을까요?",
  quote: "DNS 가 사이트에 연결해준다",   // 없으면 null
  options: [ { id, sourceId, text, correct } ],
  explain: "아니다. IP 주소를 알려주고 거기서 끝난다."
}
```

`ORDER`(순서 세우기)만은 보기 넷 중 하나를 고르는 형태로 만든다 —
**끌어다 놓기를 넣지 않는다.** 390px 화면에서 드래그는 스크롤과 싸우고,
그걸 피하려면 화면 장치가 늘어난다. 대신 "네 마디를 바르게 늘어놓은 것은?" 으로
낸다. 보기 하나가 정답 순서, 셋은 두 마디를 맞바꾼 것이다.

## 병렬 작업 배분 (파일이 겹치지 않는다)

| 갈래 | 파일 | 할 일 |
|---|---|---|
| **A** | `tools/build.py` | 위 데이터 계약 세 필드(`myths` · `cases` · `dia`)를 굽는다 |
| **B** | `js/quiz.js` | 새 유형 6개 + 단어당 여러 문제 + 유형 고르게 섞기 |
| **C** | `js/quiz-screens.js` + `css/app.css` | 한 판 길이 고르기, 범위별 실제 문항 수, 새 유형 렌더 |

네 갈래가 같은 계약을 본다. B 는 A 가 굽기 전에도 짤 수 있다 — 계약이 정해져 있으니.
합류 뒤 `python3 tools/build.py` 로 한 번에 굽고 확인한다.

## 검증

- `python3 tools/build.py` → **단어 229개 유지**, id 한 글자도 안 달라짐
- `python3 tools/check_template.py content/` → 실패 0건 유지
- 문항 수 실측 — 유형별로 몇 개가 실제로 만들어지는지 세어 계획의 숫자와 대조
- 헤드리스로 한 판 끝까지 풀어 오류 0건
- **오답 검사** — 만들어진 문제 표본에서 (1) 정답이 보기에 정확히 하나인지
  (2) 보기가 서로 중복되지 않는지 (3) 오답이 우연히 정답이 되지 않는지

## 하지 않을 것

- 게임 장치(연속 정답, 배지, 순위). 단어장이지 게임이 아니다.
- 끌어다 놓기 정렬. 390px 에서 스크롤과 싸운다.
- 서술형 채점. 저자의 확인 질문은 회상(스스로 답하고 확인)으로 쓰고,
  기계가 맞다 틀리다 판정하지 않는다.
