# 이행 기록 — 제품관리 (18편)

대상: A/B Testing · Agile · Backlog · CAC LTV · Funnel · GTM · KPI · MVP ·
North Star Metric · OKR · PMF · Persona · Product Roadmap · Retention ·
Scrum · Sprint · User Story · Wireframe

검사 결과: **18편 실패 0건 · 경고 0건** (`--strict` 로도 0건)

## 1. 확인 질문에 "→ 답이 있는 자리" 달기 (18편 전부)

18편 모두 화살표가 하나도 없던 상태였다. **답이 실제로 그 섹션에 있는지 하나씩 열어
확인하고** 달았다. 질문 셋이 서로 다른 섹션을 겨누게 맞췄고, 끝의 물음표는 본보기
두 편(DNS·HTTP)과 같게 뗐다.

| 노트 | 겨눈 자리 셋 |
|---|---|
| A/B Testing | 작동 원리 · 흔한 오해 · 실제 사례 |
| Agile | 해결하는 문제 · 그림 · 흔한 오해 |
| Backlog | 해결하는 문제 · 흔한 오해 · 작동 원리 |
| CAC LTV | 해결하는 문제 · 흔한 오해 · 작동 원리 |
| Funnel | 실제 사례 · 흔한 오해 · 작동 원리 |
| GTM | 해결하는 문제 · 작동 원리 · 그림 |
| KPI | 해결하는 문제 · 흔한 오해 · 작동 원리 |
| MVP | 실제 사례 · 흔한 오해 · 해결하는 문제 |
| North Star Metric | 실제 사례 · 작동 원리 · 흔한 오해 |
| OKR | 흔한 오해 · 해결하는 문제 · 작동 원리 |
| PMF | 해결하는 문제 · 작동 원리 · 비교 |
| Persona | 해결하는 문제 · 작동 원리 · 흔한 오해 |
| Product Roadmap | 해결하는 문제 · 흔한 오해 · 작동 원리 |
| Retention | 해결하는 문제 · 실제 사례 · 작동 원리 |
| Scrum | 실제 사례 · 그림 · 흔한 오해 |
| Sprint | 작동 원리 · 실제 사례 · 해결하는 문제 |
| User Story | 흔한 오해 · 해결하는 문제 · 작동 원리 |
| Wireframe | 해결하는 문제 · 흔한 오해 · 주의사항 |

### 답이 없거나 한 자리로 몰려 질문을 바꾼 것 (4건)

- **KPI** — "사용자 만족도를 높인다가 KPI가 될 수 없는 이유는"
  답(SMART 다섯 가지)은 작동 원리에만 있는데, 셋째 질문("하루 5만 명, 한 달 20만 명이면
  DAU/MAU는")의 답도 같은 자리다. 셋을 두 자리로 몰지 않으려고
  **"'사용자 경험을 개선한다'를 목표로 걸면 석 달 뒤 회고에서 무슨 일이 벌어지나
  → 해결하는 문제"** 로 바꿨다. 해결하는 문제 첫 문단의 "각자 기억나는 장면을 근거로
  잘됐다거나 아쉬웠다고 말하게 된다" 가 그대로 답이다. 숫자 앵커가 든 DAU/MAU 질문을
  살리는 쪽을 골랐다.
- **Agile** — "2주마다 돌아가는 것을 내놓아야 하는 이유가 무엇인가"
  답이 첫 질문과 같은 해결하는 문제 문단이었다.
  **"시연에서 쓰는 사람이 한 말은 그다음에 어디로 가나 → 그림"** 으로 바꿨다.
  그림의 `@ 계획 :: 들은 말을 다음 바퀴 목록에 넣고 다시 돈다` 가 답이다.
- **Product Roadmap** — "한 분기에 스무 개가 적힌 로드맵은 무엇을 잃나"
  답(흔한 오해 셋째 줄)이 둘째 질문과 같은 자리다.
  **"새 요청 두 개 중 무엇을 먼저 할지 근거를 대려면 무엇을 견주어 보나 → 작동 원리"** 로
  바꿨다. 작동 원리의 "효과가 얼마나 있는지와 품이 얼마나 드는지" 와 RICE 문단이 답이다.
- **Product Roadmap** — "로드맵의 **어느 부분**이 이 상황을 정리하나"
  노트가 로드맵의 '부분' 을 나눠 적은 적이 없어서, 그대로 두면 답이 없는 질문이 된다.
  같은 상황을 유지한 채 **"로드맵이 이 자리에서 하는 일은 무엇인가 → 해결하는 문제"** 로
  물음만 고쳤다. 해결하는 문제 둘째 문단이 답이다.

## 2. 흐름의 `<` 감사 — `<` 가 있던 17편 **전부** 바뀌었다

이 권에서 가장 크게 걸린 자리다. 제품관리 도해에는 **요청과 응답이 없다.**
사람이 밟는 절차이거나 한 바퀴 도는 주기라서, "누가 누구에게 답을 주는가" 를 물으면
17편 어디서도 대답이 안 나왔다. `<` 앞에 앱이 "여기서부터 돌아오는 길" 을 새기므로
그대로 뒀으면 열일곱 장이 같은 거짓말을 하고 있었을 것이다.

### `@` 로 바꾼 것 — 처음으로 돌아가 다시 하는 순환 (6편)

- **Agile** `< 계획 :: 들은 말을 다음 바퀴 목록에 넣는다`
  → 마디 이름이 첫 마디(계획)와 같다. 응답이 아니라 **한 바퀴**다.
  `@ 계획 :: 들은 말을 다음 바퀴 목록에 넣고 다시 돈다`
- **Scrum** `< 계획 :: 받은 의견을 목록에 넣고 다음 주기를 연다` → 같은 이유로 `@`.
- **OKR** `< 다음 분기 :: 왜 못 갔는지 보고 목표를 다시 적는다` → 분기마다 처음으로 돌아간다. `@`.
- **MVP** `< 다음 판 :: 맞았으면 늘리고 틀렸으면 방향을 튼다` → 만들고 재고 배우기를 다시 돈다. `@`.
- **Wireframe** `< 고치기 :: 지우고 다시 그린다` → 싸게 지우고 다시 그리는 것이 이 단어의 핵심이다. `@`.
- **Sprint** `< 회고 :: 일하는 방식에서 고칠 것을 정한다`
  → 회고는 되돌아오는 길이 아니라 **주기 안의 한 걸음**이라 표지를 떼고,
  대신 `@ 다음 바퀴 :: 고칠 점을 안고 같은 기간을 다시 돈다` 를 마지막 줄에 뒀다.
  Scrum 쪽과 달리 마지막 마디가 첫 마디 이름을 다시 부르지 않아 순환이 사라지던 자리다.
  실제 사례의 "격주 금요일에 보여주고 다음 주 월요일에 다음 주기를 시작한다" 가 근거다.

### 표지를 뗀 것 — 조건을 만족해 빠져나오는 마지막 마디 (11편)

A/B Testing(검정→판단) · Backlog(선정→완료) · CAC LTV(이탈→판단) ·
Funnel(결제 시작→구매 완료) · GTM(가격→출시) · KPI(측정→판단) ·
North Star Metric(평가→결정) · Persona(쓰기→판단) · Product Roadmap(우선순위→공유) ·
Retention(30일 후→곡선) · User Story(대화→인수 기준).

전부 **앞으로 나아가 끝나는 걸음**이지 누가 답을 되돌려주는 자리가 아니다.
특히 Funnel 은 방향이 한쪽뿐인 깔때기라 되돌아오는 길을 그리면 그림이 개념을 뒤집는다.

**PMF 만 처음부터 `<` 가 없었다.**

## 3. 대조 감사 — 바꾼 것 없음

18편의 `||` 대조를 왼쪽 칸부터 읽었다. 전부 "있고 없고" 꼴이고 **왼쪽에 장점이 한 줄도
없다** (실험 없이 / 한 번에 / 목록 없이 / 안 볼 때 / 전체 수치만 / GTM 없이 / KPI 없이 /
완성 후 출시 / 지표 없이 / 숫자 없이 / PMF 이전 / 페르소나 없이 / 로드맵 없이 /
가입자 수만 / 한 번에 만들면 / 기간 없이 / 기술로 적으면 / 디자인부터 하면).
`|=|` 로 바꿀 자리가 없어 하나도 쓰지 않았다.

User Story 의 `기술로 적으면 || 스토리로 적으면` 만 잠깐 멈춰 봤다. 왼쪽의
"구현 방법 :: 이미 정해져 있음" 이 확실성으로 읽힐 여지가 있지만, 이 노트는 그것을
"팀이 더 나은 방법을 고를 여지가 사라진다" 는 손해로만 다루고 우열 없는 비교는
📊 비교 표(User Story / Use Case / Requirement)가 따로 맡고 있어 그대로 뒀다.

## 4. 그림 자리 감사 — PMF 한 편을 맞바꿨다

18편 모두 "그림만 보고 정의 첫 문장을 복원할 수 있는가" 로 봤다.

- **PMF** 🖼️ 자리에 `흐름: PMF 에 닿았는지 어떤 순서로 확인하나` 가 있었다.
  제목부터가 **확인 절차**고, 정의 첫 문장("제품이 시장의 필요와 맞아떨어진 **상태**")이
  아니라 재는 방법을 복원한다.
  → 절차는 ⚙️ 작동 원리로 내렸다. 그 아래 세 문단(션 엘리스 테스트 · 리텐션 곡선 ·
  NPS와 유기적 성장)이 이 흐름의 마지막 두 마디를 그대로 풀어 쓰고 있어 자리가 맞는다.
  → 대신 ⚠️ 해결하는 문제에 있던 대조를 **그림 자리로 올렸다**.
  `PMF 이전 || PMF 이후` — 가입 100명 중 5명이 남느냐 80명이 남느냐, 광고를 끄면
  끊기느냐 입소문이 남느냐. 이쪽이 "맞아떨어진 상태" 를 2초에 보여준다.
  제목은 자리에 맞춰 `대조: 제품이 시장에 맞아떨어지면 무엇이 달라지나` 로 고쳤다.
  ⚠️ 해결하는 문제는 원래 있던 문단 둘로 남았다(도해 없이). 규약상 그 자리는 대조
  도해 하나가 권고지만, 그림 자리에 절차를 두는 쪽이 더 비싼 손해라고 봤다.
- 나머지 17편은 통과했다. 만드는 순서를 그린 편(Persona · Wireframe · Product Roadmap)도
  마디 안에 개념의 형태가 들어 있어 정의가 복원된다 — Persona 는 `= 여러 명에게서 나온
  것을 한 사람의 얼굴로 줄여둔 것이다`, Wireframe 은 `자리 잡기 :: 회색 상자로 크기와
  위치만 배치한다` 가 정의 첫 문장 그 자체다.

## 5. 층 반증 테스트 — 2편에서 층이 아니었다

- **Sprint** ⚙️ 작동 원리 `층: 스프린트에서 무엇을 고정하고 무엇을 움직이나`
  (기간 / 목표 / 범위)
  `= ` 줄이 **"셋 중 하나는"** 이라는 집합어로 시작했고, 기간과 목표를 맞바꿔도
  그림이 안 틀린다(둘 다 "고정" 쪽이라 위아래에 뜻이 없다). 축이 없는 세 낱말 나열이었다.
  → **본문 문단으로 되돌렸다.** "기간과 목표와 범위 셋을 놓고 무엇을 고정할지 먼저
  정한다 … 셋 중 하나는 움직여야 하니 남는 것은 범위다." 사실은 도해에 있던 것 그대로고,
  확인 질문 1번("기간과 범위 중 무엇을 움직이나 → 작동 원리")의 답도 이 문단이 받는다.
- **Persona** ⚙️ 작동 원리 `층: 페르소나에 무엇이 적혀야 쓸모가 있나`
  (인용구 / 고충과 목표 / 행동 / 인구통계)
  아래 두 경계는 단단한데(인구통계를 행동 위로 올리면 `= 아래만 있으면 명단이고` 가
  깨진다) **맨 위 둘은 맞바꿔도 안 틀린다.** 인용구는 고충과 목표의 근거지 그보다
  윗칸이 아니다. 노트 자신도 정리에서 "무엇 때문에 쓰고 어디서 막히는지가 적혀 있어야
  결정을 가른다" 고 고충 쪽을 맨 위에 놓는다.
  → 두 칸을 **한 칸으로 묶었다**: `고충과 목표 :: 왜 쓰는지, 어디서 막히는지.
  실제로 한 말을 근거로 붙인다`. 층은 셋이 되고 모든 이웃이 맞바꾸면 틀린다.

### 살아남은 층

- **Backlog**(제품 백로그 → 꺼낼 후보 → 스프린트 백로그): 범위와 확정도 축.
- **CAC LTV**(3배 이상 → 1~3배 → 1배 미만): 배수의 눈금. 순서를 흔들면 판정이 뒤집힌다.
- **GTM**(TAM → SAM → SOM): 담김 관계. 맞바꾸면 큰 것이 작은 것 안에 들어간다.
- **MVP**(핵심 가치 → 쓸 만한 최소 → 편의 → 치장): 잘라도 되는 정도 축.
- **North Star Metric**(북극성 → 입력 지표 → 팀의 일): `= 아래를 움직여야 위가 움직인다`.
- **OKR**(회사 → 팀 → 개인): `= 위층의 KR 이 아래층의 Objective 가 된다`.
- **Retention**(첫 화면 → 첫 성공 → 재방문 이유 → 습관): 관여의 깊이 축.
  이름에 시간말이 없고 맞바꾸면 `= 아래 단계는 위 단계를 통과한 사람에게만 생긴다` 가
  깨져서 층으로 남겼다.
- **Scrum**(제품 백로그 → 스프린트 백로그 → 작업): 담김 관계.
- **User Story**(에픽 → 스토리 → 작업): 크기 축.
- **Wireframe**(저해상도 → 중해상도 → 고해상도): 정확도와 고치는 값 축.

**Backlog 의 층 이름 하나를 고쳤다.** `다음 주기 후보` → `꺼낼 후보`.
검사기가 "층 이름이 순서를 가리킨다" 고 경고하던 자리인데, 뜻으로 보면 시간이 아니라
"정제가 끝나 바로 꺼낼 수 있는 것" 이라 오탐이었다. 다만 이름에 '다음' 이 있는 한
읽는 사람도 시간으로 넘겨짚을 수 있어, 뜻을 그대로 두고 이름만 줄였다.

## 6. 선행 용어 — 4곳을 반 구절로 풀었다

- **A/B Testing** 주의사항의 `세그먼트`
  → `세그먼트(사용자를 조건별로 갈라 본 집단)`. 이 노트가 설명한 적 없는 말이고
  관련 용어에도 없다.
- **Backlog** 주의사항의 `P0` → `P0(가장 급한 등급)`.
- **OKR** 해결하는 문제의 `NPS 70점` → `NPS(추천 의향 점수) 70점`.
  KR 예시로 세 번 나오는데 무엇을 재는 숫자인지가 노트 안에 없었다.
- **Agile** 흔한 오해의 `선언문` → `애자일 선언문`.
  앞뒤에 어떤 선언문인지 나오지 않아 이름 없는 문서를 가리키고 있었다.

`[[링크]]` 를 새로 건 곳은 없다. 이 권의 노트끼리는 이미 관련 용어로 촘촘히 이어져 있고
(Agile↔Scrum↔Sprint↔Backlog↔User Story), 관련 용어 칸이 3~5개 상한에 차 있어
새 링크를 넣으면 있던 관계를 빼야 했다.

- 배정 밖 파일, tools/ · js/ · css/ · docs/: 읽기만 했다.
