## 1. 확인 질문에 "→ 답이 있는 자리" 달기 (20편 전부)

20편 모두 화살표가 없었다. 전편에 달았고, **화살표 뒤 섹션을 실제로 열어
거기에 답이 있는지 하나씩 확인했다.** 질문 셋이 서로 다른 섹션을 겨누게 맞췄고,
끝의 물음표는 본보기(DNS·HTTP)와 같게 뗐다.

### 답이 노트에 없어 질문을 바꾼 것 (5건)

- **API Gateway** — "서비스가 세 개뿐일 때도 게이트웨이가 이득일까? 왜 그런가"
  **답이 노트 어디에도 없다.** 몇 개부터 이득인지는 이 노트가 다루지 않는다.
  억지로 짚지 않고 **"서비스 스무 곳에 토큰 검증 코드를 따로 두면 왜 구멍이 생기나
  → 해결하는 문제"** 로 바꿨다. 해결하는 문제의 "토큰 검증 로직이 스무 벌 생기고,
  그중 한 곳만 업데이트를 놓쳐도 구멍이 된다" 가 그대로 답이다.
- **API** — "주소를 정확히 알고 보냈는데 요청이 거절된다면 무엇이 빠졌나"
  답(키)은 흔한 오해에 있는데 첫 질문이 이미 흔한 오해를 겨눴다. 셋이 두 자리로 몰린다.
  **"같은 `/users/123` 주소로 보낸 두 요청이 서로 다른 일을 한다. 무엇이 그것을 정하나
  → 작동 원리"** 로 바꿨다. 작동 원리의 "같은 주소에 메서드만 바꿔 보내면 다른 일이
  일어난다" 가 답이다.
- **Auto Scaling** — "CPU 를 기준으로 대수를 늘렸는데 응답이 그대로라면"
  답(병목)이 흔한 오해에 있는데 첫 질문도 흔한 오해였다.
  **"지표가 아직 높은데도 서버를 곧바로 더 안 띄우는 구간이 있다. 왜 그런가
  → 작동 원리"** 로 바꿨다. 작동 원리의 "서버를 하나 추가한 뒤에는 잠시 판단을 멈춘다"
  가 답이다.
- **Caching** — "캐시를 붙였는데 오히려 느려졌다면 어떤 데이터를 넣은 것인가"
  답이 흔한 오해에 있는데 첫 질문도 흔한 오해였다.
  **"서버를 두 대로 늘렸더니 같은 값을 물어도 서버마다 다르게 답한다. 캐시를 어디에
  둔 것인가 → 작동 원리"** 로 바꿨다. 작동 원리 층의 "앱 메모리 :: 서버마다 따로 갖는다"
  와 "분산 캐시 :: 여러 앱이 같은 값을 본다" 가 답이다.
- **Latency** — "사용자는 느리다고 하는데 평균은 정상이라면" 과 "서버 사양을 올렸는데"
  둘 다 흔한 오해가 답이었다. 앞의 것을 **작동 원리**로 옮겼다 — "회선을 오가는 시간은
  거리가 정하고, 처리 시간은 코드와 서버가 정하고… 어느 조각이 큰지 모르면 엉뚱한 곳을
  고치게 된다" 가 더 직접적인 답이다.

내용을 새로 채운 곳은 없다. 다섯 건 모두 **질문을 바꾸는 쪽**을 골랐고,
바꾼 질문의 답은 전부 그 노트에 이미 있던 문장이다.

## 2. 흐름의 `<` 감사

"누가 누구에게 답을 주는가" 를 물어 판정했다. 검사기 경고는 단순 문자열 검사라
따르지 않고 뜻으로 봤다.

### `@` 로 바꾸고 마지막 줄에 둔 것 (4편)

- **Auto Scaling** — `< 감시 :: 다시 지켜본다` → `@`. 아무도 답을 주지 않는다.
  감시 → 기준 초과 → 증설 → 감시로 도는 순환이다.
- **Caching** — `< 앱 :: 두 번째 요청은 캐시에서 끝난다` → `@ 다음 요청 :: 처음부터 다시.
  이번엔 캐시에서 끝난다`. 응답이 돌아오는 게 아니라 **두 번째 요청이 처음부터 다시**
  도는 것이다. 그림 제목("두 번째로 부르면")이 이미 순환을 말하고 있었다.
- **Circuit Breaker** — `< 차단기 :: 성공하면 닫고, 또 실패하면 다시 연다` → `@`.
  닫힘으로 돌아가 실패를 다시 세기 시작한다. 템플릿이 순환의 예로 든 개념이다.
- **Pipeline** — `< 재실행 :: 실패한 단계부터만 다시 돌린다` → `@`.
  되돌아가 다시 흘려보내는 것이지 응답이 오는 게 아니다.

### 표지를 뗀 것 (4편)

- **API 외부 공개** — `< 외부 사용자 :: 이제 주소만 알면 부를 수 있다`.
  공개 준비가 끝났다는 결론이다. 돌아오는 것이 없다.
- **Consistent Hashing** — `< 결과 :: 배치가 그대로면 같은 키는 늘 같은 곳으로`.
  탐색이 끝나 빠져나오는 자리다.
- **LangGraph** — `< 실행 :: 시작 값을 넣으면 끝 노드까지 흘러간다`. 끝까지 흘러가는
  마디다. 대신 이 노트에서 **진짜 순환은 따로 있어서** `@ 되돌림 :: 답이 부족하면 앞
  노드로 돌아가 한 바퀴 더` 를 마지막 줄에 붙였다. 되돌아가는 길이 없으면 그림이
  "그래프니까 순서가 한 줄" 이라는 이 노트의 흔한 오해 2번을 그대로 심는다.
  근거는 작동 원리("뒤쪽이 있어서 앞 노드로 되돌아가는 흐름을 만들 수 있고")와
  실제 사례("찾은 게 부족하면 검색 노드로 되돌린다")에 이미 있던 사실이다.
- **Message Queue** — `< 사용자 :: 가입 완료 화면을 즉시 본다` 가 **가운데**에 있었다.
  앱은 첫 `<` 앞에 "여기서부터 돌아오는 길" 을 새기는데, 그 뒤로 메일 워커 두 마디가
  앞으로 더 간다. 응답이 돌아오는 것은 맞지만 그 표지가 그림을 거짓말하게 만들어 뗐다.

### 여럿이 동시에 받는 자리를 한 마디로 묶은 것 (2편)

템플릿이 든 `구독자A / 구독자B / 구독자C` 예와 같은 자리다. 마디를 나누면 1·2·3
번호가 붙어 **없는 순서가 생긴다.** Pub/Sub 은 "순서가 없다" 가 개념의 절반이라
그림이 개념과 반대되는 말을 하고 있었다.

- **Event-Driven Architecture** — 결제/재고/알림 세 마디 → `구독자들 :: 결제·재고·알림이
  저마다 꺼내 간다. 순서도 없고 서로 모른다` + `각자 처리 :: 한 곳이 느리거나 죽어도
  나머지는 그대로 간다`. 마지막 마디의 `<` 도 함께 뗐다(돌아오는 것이 없다).
- **Pub-Sub** — 재고/배송/알림 세 마디 → `구독자들 :: 재고·배송·알림이 저마다 받는다.
  순서도 없고 서로 모른다` + `새 구독자 :: 나중에 붙어도 주제만 구독하면 끝난다`.

### 자리를 옮겨 진짜 응답으로 만든 것 (1편)

- **Service Discovery** — `< 주문 :: 받은 주소로 호출한다` 는 주문이 **나가는** 마디였다.
  응답을 주는 쪽은 그 앞의 레지스트리다. 두 마디를 묶어
  `< 레지스트리 :: 살아 있는 주소를 돌려준다. 주문은 그리로 부른다` 로 바꿨다.

### 그대로 둔 `<` (8편)

API · API Gateway · Bedrock · Latency · Load Balancing · Rate Limiting ·
Sharding · tRPC · Monolith vs Microservices — 전부 "받은 쪽이 부른 쪽에 응답을
되돌려준다" 가 성립한다.

**Rate Limiting 의 경고는 알고 남겼다.** `< 사용자 :: 얼마 뒤 다시 오라는 안내를 받는다`
에서 "다시" 는 `Retry-After` 안내문의 일부이지 순환이 아니다. 제한기가 사용자에게
`429` 를 돌려주는 **응답**이 맞아서 `<` 를 지켰다. 검사기의 오탐이다.

## 3. 대조 감사 — ✕ 칸 자기검사

왼쪽 칸을 한 줄씩 읽고 장점이 섞였는지 봤다. **20편 중 19편은 "있고 없고" 대조**라
(캐시 없이 / 제한 없이 / 큐 없이 / 주소를 박아두면 …) 왼쪽이 실제로 나쁜 상태다.
그대로 뒀다.

- **Monolith vs Microservices** — 그림 자리에 새로 세운 대조만 `|=|` 로 썼다(4번 참고).
  해결하는 문제의 `모놀리스 || 마이크로서비스` 는 **"결제에만 트래픽이 몰리면"** 이라는
  좁은 물음 아래 왼쪽이 실제로 나쁜 상태라 `||` 를 지켰다. 균형은 비교 표와
  흔한 오해 1번("나중에 나온 것이지 더 나은 것이 아니다")이 맡는다.
- **Event-Driven Architecture** 의 `받는 쪽 목록 :: 부르는 쪽이 앎 || 알 필요 없음` 을
  가장 오래 봤다. "안다" 가 장점처럼 읽힐 수 있지만 물음("서비스 하나를 새로 붙이면
  무엇을 고쳐야 하나") 아래에서는 결합 비용이다. 추적이 쉽다는 반대편 장점은
  비교 표와 정리가 이미 정직하게 적고 있다. `||` 유지.

## 4. 그림 자리 감사 — 1편을 바꿨다

판정법("그림만 보고 정의 첫 문장을 복원할 수 있는가")을 20편에 다 걸었다.

- **Monolith vs Microservices** — 정의는 "기능을 **한 덩어리로 둘지 쪼갤지**의 차이다"
  인데, 그림 자리에는 **마이크로서비스 쪽만** 그린 흐름이 있었다. 한쪽만 보고는
  "둘지 쪼갤지의 차이" 가 복원되지 않는다. `vs` 노트의 형태는 대조다.
  - 🖼️ 그림 ← `대조: 기능을 한 덩어리로 둘 때와 쪼갤 때는 무엇이 다른가` (`|=|`).
    네 줄 모두 이미 노트에 있던 사실이다 — 코드와 DB(정의), 함수 호출/네트워크 통신
    (해결하는 문제 문단과 옛 그림의 `=`), 배포·초기 운영 비용(비교 표).
    `=` 줄은 정리의 "어느 쪽이 옳은 게 아니라" 를 그대로 옮겼다.
  - ⚙️ 작동 원리 ← 옛 흐름을 그대로 옮겼다. 나뉜 서비스가 실제로 어떻게 도는지는
    작동 원리의 자리다. 접이식 칸 수는 그대로 6이다.

나머지 19편은 그림만 보고 정의 첫 문장이 복원된다. 손대지 않았다.

## 5. 층 반증 테스트 — 3편에서 층을 걷어냈다

이웃한 두 층을 맞바꿔 보고 그림이 틀리는지 봤다.

- **Load Balancing** ⚙️ — `층: 어느 서버로 보낼지 무엇을 보고 정하나`
  (순서대로 / 연결 수 / 가중치 / 주소 해시, `= 아래로 갈수록 상태를 더 많이 보고 판단한다`).
  **가중치는 고정 설정이라 연결 수보다 상태를 더 보지 않는다.** 둘을 맞바꿔도 그림이
  안 틀리고, 주소 해시는 아예 다른 축(요청한 사람)이다. 순서에 뜻이 없으니 층이 아니라
  나열이었다. **본문 불릿으로 되돌렸다.** 네 규칙과 설명은 한 글자도 안 버렸다.
- **Service Discovery** ⚙️ — `층: 서비스 디스커버리는 무엇으로 이뤄지나`
  (등록 / 헬스체크 / 조회 / 해지). 제목이 "무엇으로 이뤄지나" 인 시점에서 겹겹의
  구조가 아니라 구성 목록이다. 조회와 헬스체크를 맞바꿔도 아무것도 안 틀린다.
  **본문 불릿으로 되돌렸고**, `=` 줄("명단이 실제와 어긋나면 없느니만 못하다")은
  문장으로 남겼다. 확인 질문 2번이 이 자리를 겨누므로 답은 그대로 있다.
- **Circuit Breaker** ⚙️ — `층: 차단기는 어떤 상태를 오가나` (닫힘 / 열림 / 반열림).
  **상태 전이는 층이 아니다.** 움직이는 것을 정지한 구조로 그리고 있었다.
  이 노트의 순환은 이미 🖼️ 그림 자리의 흐름이 `@` 로 담고 있어서(2번 참고)
  같은 순환을 두 번 그리는 대신 **본문 불릿으로 되돌렸다.**

### 그대로 둔 층 (4편)

- **Caching** ⚙️ — CPU 캐시 / 앱 메모리 / 분산 캐시 / DB. 맞바꾸면 틀린다. 진짜 층.
- **Latency** ⚙️ — 브라우저 캐시 / 가까운 거점 / 원본 서버 / 데이터베이스. 진짜 층.
- **API 외부 공개** ⚙️ — 터널링 / 클라우드 / 도메인 / 관문. 아래로 갈수록 준비가
  늘어나는 축이 실재하고, 앞의 것이 있어야 뒤의 것이 성립한다. 유지.
- **tRPC** ⚙️ — 프로시저 / 라우터 / 타입. 라우터가 프로시저를 담고 타입이 라우터에서
  나온다. 맞바꾸면 말이 안 된다. 진짜 층.

## 6. 선행 용어

노트 밖에서 배워야 하는 말을 도해 마디와 본문에서 훑었다. **고칠 곳이 없었다.**

- 반 구절로 이미 풀려 있던 것 — 미스(Caching), 폴백(Circuit Breaker), 가상 노드
  (Consistent Hashing), 핫스팟(Sharding), 프로듀서·컨슈머·데드레터 큐(Message Queue),
  RPC·프로시저·라우터(tRPC), 브로커(Event-Driven Architecture), ngrok·레지스트리,
  `429`·`Retry-After`(Rate Limiting).
- `[[링크]]` + 🔗 관련 용어에 이미 올라와 있던 것 — REST·JSON(API), Load Balancer
  (API Gateway), Message Queue(Pub-Sub), API Gateway·DNS(API 외부 공개) 등.

억지로 링크를 더 걸지 않았다. 관련 용어 칸이 이미 3~5개로 차 있고, 더 넣으면
관계 설명이 얇아진다.

## 남긴 경고 하나

```
△ Rate Limiting.md — 🖼️ 그림으로 보기 도해1: 응답 줄에 '다시' 가 있다
   — < 사용자 :: 얼마 뒤 다시 오라는 안내를 받는다
```

위 2번에 적은 대로 오탐이다. 제한기가 `429` 와 함께 "얼마 뒤 다시 오라" 를 **돌려주는**
응답 마디이고, "다시" 는 그 안내문의 말이지 그림이 도는 표시가 아니다.
`@` 로 바꾸면 요청량 제한이 순환하는 장치처럼 보인다.
