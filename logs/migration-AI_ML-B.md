## 1. 확인 질문에 "→ 답이 있는 자리" 달기 (13편 전편)

39개 질문 전부에 화살표를 달았다. 다는 것으로 끝내지 않고 **가리킨 섹션을 열어 답이 실재하는지 확인**했다.
질문 셋이 같은 섹션을 겨눈 경우가 3편에서 나왔고, 그때는 답이 실제로 있는 다른 섹션으로 질문을 옮기거나 질문을 바꿨다.

### 답이 한 자리에 몰려 있어 질문을 바꾼 것 — 이번 이행의 수확

| 노트 | 원래 질문 | 무엇이 문제였나 | 어떻게 했나 |
|---|---|---|---|
| **LLM** | 같은 질문에 매번 다른 답이 나오는 이유는? | 답이 작동 원리 마지막 문단에만 있는데 1번 질문("대화가 길어지면 앞을 잊는 이유")도 같은 자리라 셋 중 둘이 겹쳤다 | **"답이 길어질수록 다 나오는 데 시간이 더 걸리는 이유는 → 그림"** 으로 교체. 그림이 "한 조각씩 이어 붙인다" 를 그대로 보여준다 |
| **Token** | 문맥 창 8,000토큰은 무엇과 무엇을 합쳐서 8,000인가? | 답이 작동 원리에만 있어 1번("한국어가 비싼 이유")과 겹쳤고, 되묻기에 가까웠다 | **"짧게 물었는데 답이 길게 오면 요금이 왜 더 나오나 → 흔한 오해"** 로 교체. 흔한 오해 3번 "입력만 돈이 든다 — 출력도 토큰으로 센다" 가 답이다 |
| **Text-to-SQL** | 조회만 하는 기능인데도 읽기 전용 계정으로 돌리는 이유는? | 답이 흔한 오해 3번에 있는데 2번 질문도 흔한 오해를 가리켜 겹쳤다 | 질문은 그대로 두고 **실제 사례**를 겨누게 했다. "읽기 전용 통로 — 어떤 쿼리가 나와도 데이터가 바뀌지 않게 한다" 가 같은 답이다 |
| **Routing** | 처리자가 넷인데 하나만 답하게 만드는 것은 어디가 하는 일인가? | 답은 해결하는 문제에 있지만 "라우팅이 뭐냐" 를 되묻는 꼴이었다 | **"처리자 셋이 한 질문에 저마다 답하면 사용자에게 무엇이 문제인가 → 해결하는 문제"** 로 상황 질문으로 바꿨다. "세 개의 답이 한꺼번에 나와서 어느 것을 봐야 할지 알 수 없다" 가 답이다 |

**노트에 없는 답을 채워 넣은 자리는 없다.** 네 건 모두 이미 있는 사실 쪽으로 질문을 옮기는 방향으로 풀었다.

## 2. 흐름의 `<` 감사

"누가 누구에게 답을 주는가" 를 물어 판정했다. 검사기 경고(문자열 검사)는 참고만 하고 뜻으로 판단했다.

### `<` → `@` (처음으로 돌아가 다시 하는 순환)

- **LLM** `< 사용자 :: 끝 신호가 나올 때까지 반복한 결과를 본다` 앞에 `모델 :: 고른 것을 뒤에 붙이고 다시 처음부터 예측` 이 직선 마디로 펴져 있었다.
  → 그 마디를 없애고 마지막 줄에 `@ 다시 예측으로 :: 고른 토큰을 뒤에 붙이고 한 조각 더` 를 놓았다. `<` 는 "끝 신호가 나오면 이어 붙인 문장을 받는다" 로 고쳐 **진짜 응답이 돌아오는 줄**로 만들었다.
  이 노트의 정의가 "한 조각씩 이어 붙인다" 인데 순환이 직선이면 그림이 정의를 부정한다.
- **Prompt** `LLM :: 고른 토큰을 뒤에 붙이고 다시 고른다` 가 같은 문제였다.
  → `@ 다시 고르기 :: 고른 토큰을 뒤에 붙이고 한 조각 더`. `<` 는 `< 사람 :: 멈출 자리까지 이어 붙인 답을 받는다` 로 바꿨다(첫 마디가 `사람` 이라 돌아오는 자리가 맞다).
- **Transformer** `< 다음 층 :: 같은 일을 여러 겹 반복해 결과를 낸다` — 아무것도 안 돌아온다. 어텐션으로 되돌아가 겹을 쌓는 것이다.
  → `@ 다시 어텐션으로 :: 같은 일을 여러 겹 쌓아 결과를 낸다`
- **ReAct** 는 아래 5번과 함께 다뤘다. 그림 자체가 순환인데 `< 답변` 으로 끝나 있었다.
  → `@ 다시 생각으로 :: 다 모였으면 답하고, 아니면 한 바퀴 더`. 두 번째 바퀴를 직선으로 펴 그리던 마디 둘(`생각 :: 다 모였다고 판단`, `행동 :: 답을 내놓기로 정한다`)을 지우고 첫 마디에 `사용자` 를 넣었다.
  `= 생각과 행동과 관찰이 한 바퀴고, 필요한 만큼 돈다` 가 이제 그림과 맞는다.

### `<` → 표지 없는 보통 마디 (아무것도 안 돌아온다)

- **Reranking** `< LLM :: 남은 3건만 읽고 답을 만든다` — 순위 → LLM 은 계속 앞으로 가는 방향이다.
- **Routing** `< 처리자 :: 그 하나만 실행되어 답을 만든다` — 라우터가 넘긴 것이지 되받은 게 아니다.
- **Token** `< 요금 :: 넣은 토큰 수 + 나온 토큰 수로 계산된다` — "요금" 은 응답이 아니다.

### 고친 표현 하나

- **Prompt Engineering** `< 모델 :: 좁아진 범위 안에서 답을 고른다` → `< 모델 :: 좁아진 범위 안에서 골라 답을 돌려준다`.
  마디 자체는 응답이 맞지만 "고른다" 로 끝나면 돌아오는 그림이 안 보였다.

### 그대로 둔 `<` (진짜 응답이 돌아온다)

Orchestrator(`사용자 :: 어느 Agent 가 답했는지는 모른 채 받는다`) · RAG(`사용자 :: 출처가 붙은 답을 받는다`) · Semantic Search(`결과 :: 가까운 순으로 위에서 몇 개만 돌려준다`) · Text-to-SQL(`답 :: 표나 문장으로 바꿔 보여준다`) · Vector DB(`결과 :: 가장 가까운 셋을 돌려준다`).

## 3. 대조 감사 — ✕ 칸 자기검사

`||` 왼쪽 칸에 장점이 한 줄이라도 있으면 `|=|` 로 바꿨다.

### `||` → `|=|`

- **Vector DB** `일반 DB || 벡터 DB` — 왼쪽 `정확도 :: 완벽` 이 명백한 장점이다.
  이 노트의 흔한 오해 2번이 "일반 데이터베이스를 대체한다 — 주문 내역처럼 정확히 일치하는 조회는 여전히 관계형이 맞다" 인데, 그림이 2초 만에 그 오해를 심고 있었다. `= 전부 재는 대신 대부분 맞는 답을 훨씬 빨리 주는 쪽을 고른 것이다` 라는 결론 자체가 거래(trade-off)라 `|=|` 가 맞다.
- **Token** `글자 단위 || 토큰 단위` — 왼쪽에 장점이 **둘**이었다. `목록 크기 :: 작다`, `처음 보는 말 :: 처리된다`.
  본문도 "글자 단위로 쪼개면 그 문제는 없지만 목록이 너무 길어진다" 라고 쓰고 있다. `= 글자는 너무 잘고 단어는 너무 많아서 그 사이를 고른 것이다` 가 우열이 아니라 위치 선택이다.
- **LLM** `규칙 기반 || LLM` — 왼쪽 `답의 근거 :: 규칙을 짚을 수 있다` 가 장점이다.
  `= 사람이 규칙을 다 못 적는 문제를 풀었고, 대신 왜 그렇게 답했는지를 잃었다` — 결론 줄이 이미 거래라고 말하고 있었다.

### 그대로 둔 `||` (왼쪽이 실제로 나쁜 상태다)

Orchestrator(조율 없이) · Prompt Engineering(막연한 요청) · Prompt(조건 없이) · RAG(RAG 없이) · ReAct(그냥 LLM) · Reranking(리랭킹 없이) · Routing(라우터 없이) · Text-to-SQL(사람에게 부탁) · Transformer(한 낱말씩).

**판단이 갈린 하나 — Semantic Search** `낱말 검색 || 의미 검색` 은 그대로 뒀다.
이 노트의 흔한 오해 2번이 "의미 검색이 낱말 검색보다 항상 낫다" 라서 `|=|` 를 검토했지만, **대조 세 줄(동의어 · 말 바꿔 묻기 · 오타) 어디에도 왼쪽 장점이 없다.** 셋 다 글자 맞추기가 실패하는 자리이고 그게 ⚠️ 해결하는 문제가 보여야 할 것이다. 낱말 검색의 장점(속도 · 드는 것)은 📊 비교 표에 이미 따로 서 있다.

## 4. 그림 자리 감사

13편 모두 **그림만 보고 정의 첫 문장이 복원되는지** 확인했다. ⚙️ 작동 원리로 내려보낼 절차 그림은 없었다.
13편 전부 대표 그림이 `흐름` 이지만, 이 갈래는 단어 자체가 "무엇이 어떤 순서로 오가는가" 인 것들이라(LLM · RAG · ReAct · Routing · Reranking …) 형태가 곧 순서다. 억지로 모양을 바꾸지 않았다.

Prompt Engineering 만 한 번 더 봤다. 그림이 "프롬프트를 고쳐 쓰는 절차" 라 절차 그림으로 보일 수 있는데, 이 단어의 정의 자체가 "원하는 답이 나오도록 질문을 설계하는 기술" 이라 **절차가 곧 개념의 형태**다. 그대로 뒀다.

## 5. 층 반증 테스트

이웃 둘을 맞바꿔 그림이 틀리는지 봤다. 층 도해가 있던 10편 중 **5편이 층이 아니었다.**

### 흐름으로 다시 그린 것 (시간 순서였다)

- **RAG** `층: 문서가 답이 되기까지 무엇을 거치나` — 제목도 `= ` 줄("앞의 세 **단계**는 미리")도 시간을 말하고 있었다.
  → `흐름: 문서 한 장이 답의 근거가 되기까지 무엇을 거치나`. 🖼️ 그림은 질의 시점 흐름이고 이쪽은 색인 시점 흐름이라 겹치지 않는다.
- **Vector DB** `층: 벡터 하나가 검색되기까지 무엇을 거치나` — 같은 이유.
  → `흐름: 넣어둔 문서가 골라져 나오기까지 무엇을 거치나`

### 본문으로 되돌린 것

- **Orchestrator** `층: Orchestrator 안은 무엇으로 나뉘어 있나` — 의도 분류 → 라우터 → Agent 풀 → 응답 통합은 **요청이 지나가는 순서**이고, 같은 네 마디가 같은 순서로 🖼️ 그림(흐름)에 이미 있었다. 층으로 한 번 더 그리면 접이식을 열어도 새로 아는 것이 없다.
  → 표로 되돌리고 `= ` 줄의 결론("분류가 틀리면 뒤가 아무리 좋아도 엉뚱한 답이 나온다")은 본문 굵은 글씨로 남겼다. 1번 질문의 답이 이 문장이라 반드시 살려야 했다.
- **ReAct** `층: 한 바퀴는 무엇으로 이루어져 있나` — Thought → Action → Observation 은 **한 바퀴 도는 시간**이다. 상태가 아니라 순환이고, 2번 항목에서 🖼️ 그림을 `@` 순환으로 고치면서 이 층은 그림의 복사본이 됐다.
  → 표로 되돌리고 `= 판단을 글로 남기므로 어디서 어긋났는지 되짚을 수 있다` 는 본문 문단에 합쳤다.
- **Text-to-SQL** `층: 정확한 SQL 이 나오려면 무엇이 필요한가` — 순서에 뜻이 없는 **준비물 목록**이다. 관계와 용어를 맞바꿔도 그림이 안 틀린다.
  `= 모델은 모르는 것을 지어낸다. 미리 알려준 만큼만 맞는다` 는 위아래 관계가 아니라 넷 전부에 똑같이 걸리는 말이라, 문서가 경고한 집합어 `= ` 줄과 같은 꼴이다.
  → 본문 불릿으로 되돌렸다.

### 대조로 바꾼 것

- **Prompt** `층: 프롬프트에는 무엇을 얹을 수 있나` — `= 위쪽은 대화 내내 남고 아래쪽은 이번 한 번에만 쓰인다` 가 4단 기울기처럼 말하지만 실제로는 **둘로 나뉘는 이분법**이다. 지시 · 예시 · 맥락 셋은 전부 "이번 한 번" 이라 자기들끼리 맞바꿔도 그림이 안 틀린다.
  → `대조: 시스템 프롬프트와 나머지는 무엇이 다른가` / `시스템 |=| 지시·예시·맥락` 으로 세웠다(우열이 없으니 `|=|`). 네 자리 설명은 본문 문단으로 옮겨 하나도 잃지 않았다.
  3번 질문("시스템 프롬프트에 적은 말투가 다음 질문에도 남아 있는 이유")의 답이 `남는 기간 :: 대화 내내 || 이번 한 번` 한 줄로 더 또렷해졌다.

### 그대로 둔 층 (축이 진짜다)

- **LLM** `층: 답변 하나가 어떤 재료로 만들어지나` — 시스템 지시 / 대화 기록 / 이번 질문 / 문맥 창 밖. 축은 "얼마나 오래 실려 있나" 이고 넷이 동시에 존재한다. 이웃을 맞바꾸면 프롬프트가 틀린 그림이 된다.
- **Prompt Engineering** `층: 프롬프트에 무엇부터 얹나` — `= 위쪽만으로 되면 아래를 붙일 이유가 없다` 라는 **덧대기 사다리**다. 조건과 예시를 맞바꾸면 순서가 틀린다.
- **Routing** `층: 어느 처리자인지 무엇으로 가리나` — 규칙 → 분류 모델 → 의미 유사도 → 모름. `= 위쪽일수록 싸고 확실하고, 아래로 갈수록 넓게 잡는다` 는 진짜 폴백 사다리다.
- **Semantic Search** `층: 유사도 점수는 어디에서 갈리나` — 0.7 위 / 0.5~0.7 / 0.5 아래. 눈금 자체가 축이다.
- **Token** `층: 같은 뜻을 쓰는 데 토큰이 얼마나 드나` — 영어 → 한글 → 코드. 축은 "얼마나 잘 묶여 있나" 이고 `= ` 줄이 그 기울기에서 결론을 뽑는다.
- **Transformer** `층: Transformer 한 겹은 무엇으로 이루어져 있나` 는 **뺐다.** 셀프 어텐션과 멀티 헤드는 위아래가 아니라 같은 일의 갈래라 맞바꿔도 안 틀리고, 나머지는 🖼️ 그림(흐름)에 이미 있다.
  → 표로 되돌리고 `= 이 한 겹을 여러 번 쌓아 올린 것이 모델의 깊이다` 는 본문 한 줄로 남겼다.

## 6. 선행 용어

노트 밖에서 배워야 하는 말은 대체로 이미 반 구절로 풀려 있거나 🔗 관련 용어에 올라 있었다. 새로 푼 것은 하나다.

- **RAG** 🖼️ 그림 `검색기 :: 질문을 벡터로 바꾼다` → `검색기 :: 질문을 벡터(뜻을 담은 숫자 목록)로 바꾼다`
  그림의 첫 마디부터 "벡터" 가 나오는데 이 노트 어디에도 벡터가 무엇인지 없었다. 다음 마디가 `벡터 DB` 라 이름을 지우면 안 되고, 반 구절이 맞았다.

확인만 하고 그대로 둔 것 — Reranking `Cross-Encoder`(본문에서 정의) · Transformer `RNN`(첫 문단에서 "앞에서부터 한 낱말씩 읽던" 으로 풀림) · Prompt / Prompt Engineering `Zero-shot · Few-shot · Chain-of-Thought`(전부 본문에서 정의 + 관련 용어) · Orchestrator `폴백`(본문 정의 + `[[Fallback]]`) · LLM `문맥 창`(작동 원리 첫 문장에서 풀림) · Vector DB `근사 최근접 이웃 검색`(본문 정의).
