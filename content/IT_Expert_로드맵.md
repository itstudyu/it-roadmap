# 🗺️ IT Expert 로드맵 — 아키텍처 설계 & 개발

> **목표**: 시스템을 직접 설계하고, 개발 방향을 결정하고, 기술 의사결정을 할 수 있는 IT Expert
> **기간**: 약 18~24개월 (현업 병행 기준)
> **접근법**: 단어 암기 → 개념 연결 → 직접 구현 → 설계 적용

---

## 🧭 전체 구조

```
Phase 1 (0-3개월)    : 컴퓨터가 어떻게 작동하는지 이해
Phase 2 (3-6개월)    : 인터넷과 웹이 어떻게 작동하는지 이해
Phase 3 (6-12개월)   : 백엔드 개발 + 데이터베이스
Phase 4 (12-18개월)  : 인프라 + 클라우드 + 보안
Phase 5 (18-24개월)  : 아키텍처 설계 + 시스템 설계
```

---

## 📗 Phase 1: 컴퓨터 과학 기초 (0~3개월)

> "컴퓨터가 무엇인지 이해해야 소프트웨어를 이해할 수 있다"

### 공부할 단어장 용어

| 용어                                 | 왜 중요한가                 |
| ---------------------------------- | ---------------------- |
| [[OS]]                             | 모든 소프트웨어가 위에서 돌아가는 기반  |

### 학습 방법

1. **용어를 읽는다** → IT단어장에서 해당 파일 정독
2. **남에게 설명해본다** → "CPU는 ~~한 것이다" 한 문장으로 표현
3. **연결한다** → "CPU가 느리면 Process가 느려지고, 그러면 Thread도..."
4. **비유를 기억한다** → 각 파일의 비유 섹션 활용

### 이 단계 끝에 할 수 있어야 할 것
- "왜 멀티스레드가 빠른지" 설명 가능
- "메모리 부족 오류가 왜 발생하는지" 설명 가능
- 코드의 성능을 Big O로 개략적으로 판단 가능

### 이 단계 끝에 할 수 있어야 할 것

- 서버가 내부망/외부망에 어떻게 배치되는지 이해

### 시스템 설계 연습 (가장 중요!)

아키텍처 설계 능력은 **실제로 설계해봐야** 생긴다. 아래 시나리오를 직접 설계해볼 것:

**레벨 1: 단순 서비스**
- 블로그 서비스 설계: 사용자, 게시글, 댓글
- 고려 사항: DB 스키마, API 설계, 인증

**레벨 2: 트래픽이 많은 서비스**
- URL 단축 서비스 (bit.ly) 설계
- 고려 사항: 대규모 읽기, 캐싱 전략, 데이터 분산

**레벨 3: 실시간 서비스**
- 채팅 시스템 설계
- 고려 사항: WebSocket, 메시지 저장, 읽음 처리

**레벨 4: 글로벌 서비스**
- 넷플릭스/유튜브 같은 미디어 스트리밍 설계
- 고려 사항: CDN, Region 분산, 인코딩 파이프라인

### 이 단계 끝에 할 수 있어야 할 것
- 요구사항을 받아 시스템 아키텍처 다이어그램 그리기 가능
- 각 기술 선택의 이유를 트레이드오프로 설명 가능
- 확장성, 가용성, 보안을 동시에 고려한 설계 가능

## 🎯 효과적인 학습 방법

### 1. 파인만 기법 (Feynman Technique) — 가장 중요
```
단계 1: IT단어장에서 개념을 읽는다
단계 2: 노트를 덮고, 초등학생에게 설명하듯 적어본다
단계 3: 설명 못한 부분을 다시 읽는다
단계 4: 비유를 만들어낸다

→ 설명할 수 없으면 아직 모르는 것이다
```

### 2. 개념 연결하기
각 용어를 독립적으로 보지 말고 연결해서 볼 것:

```
예시: 사용자가 웹사이트에 로그인하는 과정
URL 입력 → DNS → HTTP → HTTPS/SSL → 서버 → API → JWT 발급
→ 이후 요청마다 JWT → RBAC으로 권한 확인 → DB Query(Index 활용)
→ Redis 캐시 확인 → 응답
```

### 3. 직접 만들어보기 (Build to Learn)
```
읽기만 하면 20% 기억
직접 만들면 80% 기억

로드맵별 프로젝트:
Phase 1-2: 간단한 HTTP 서버 만들기
Phase 3: 로그인 + CRUD API 만들기
Phase 4: AWS에 배포 + CI/CD 구축
Phase 5: 실제 서비스 아키텍처 설계 문서 작성
```

### 4. 기술 선택 시 항상 "왜?"를 물어보기
```
❌ "Redis를 쓴다"
✅ "조회가 많고 변경이 적은 데이터라서, DB 부하를 줄이기 위해 Redis 캐시를 앞단에 배치한다"

이 습관이 아키텍트와 단순 개발자를 가른다
```

### 5. 트레이드오프 사고
모든 기술 선택에는 트레이드오프가 있다:

| 선택 | 장점 | 단점 |
|------|------|------|
| Monolith | 단순함, 빠른 개발 | 확장 어려움, 기술 스택 제한 |
| Microservices | 독립 확장, 기술 다양성 | 복잡성, 네트워크 비용 |
| SQL DB | ACID, 강한 일관성 | 수평 확장 어려움 |
| NoSQL DB | 수평 확장, 유연한 스키마 | 약한 일관성 |
| 서버리스 | 비용 효율, 자동 확장 | 콜드 스타트, 긴 실행 불가 |
