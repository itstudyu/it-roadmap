# Binary Search (이진 탐색)

## 📝 정의

Binary Search 는 정렬된 목록의 가운데를 보고 **반을 버리는** 찾기다.

이름의 binary 는 둘을 뜻한다. 한 번 볼 때마다 남은 구간을 둘로 쪼개기 때문이고, Python 의 `bisect` 모듈 이름도 그 "둘로 나눈다" 는 동작에서 그대로 왔다.

### 비유
사전 찾기. 아무 데나 펼쳐 보고 찾는 낱말이 그보다 앞이면 뒤쪽 절반은 아예 넘겨보지 않는다.

### 예
1부터 100 사이 숫자를 정해두고 업다운으로 맞히는 놀이가 이것이다. 50부터 부르는 사람이 늘 먼저 맞힌다.

## 🖼️ 그림으로 보기

```도해
흐름: 정렬된 목록에서 하나를 찾을 때 왜 절반씩 버리나
남은 구간 :: 처음에는 목록 전체가 후보다
가운데 :: 그 구간의 가운데 값 하나를 본다
견주기 :: 찾는 값이 그보다 큰지 작은지 본다
버리기 :: 있을 수 없는 쪽 절반을 지운다
@ 다시 가운데로 :: 구간이 한 칸이 될 때까지 되풀이한다
= 한 번 볼 때마다 후보가 반으로 준다. 100만 개도 스무 번이면 끝난다
```

## ⚠️ 해결하는 문제

```도해
대조: 100만 개에서 하나를 찾을 때 무엇이 달라지나
앞에서 끝까지 || 이진 탐색
볼 횟수 :: 100만 번까지 || 스무 번
목록이 두 배면 :: 볼 횟수도 두 배 || 한 번만 더
못 찾았을 때 :: 없다는 것만 || 넣을 자리를 안다
= 정렬해 두었다면 100만 개짜리도 스무 번에 좁혀진다
```

앞에서부터 하나씩 견주면 목록이 커지는 만큼 그대로 느려진다. 100만 개면 100만 번까지 봐야 하고, 200만 개가 되면 그 두 배다.

반씩 버리면 늘어나는 쪽이 바뀐다. 한 번 볼 때마다 후보가 절반이 되니 100만 개는 스무 번, 목록이 두 배가 되어도 볼 횟수는 딱 한 번 늘어난다. 5만 배쯤 되는 차이를 정렬해 두었다는 전제 하나로 사는 것이다.

## ⚙️ 작동 원리

이진 탐색이 실제로 돌려주는 것은 "있다/없다" 가 아니라 **자리**다. Python 의 `bisect` 는 정렬을 유지하려면 어디에 끼워야 하는지를 돌려주고, 그 값이 이미 있을 때 왼쪽에 넣을 자리와 오른쪽에 넣을 자리가 함수로 갈려 있다. Go 의 `sort.Search` 는 조건이 처음으로 참이 되는 가장 작은 자리를 돌려주고, 그런 자리가 없으면 길이 n 을 돌려준다 — 못 찾았다는 뜻으로 -1 을 쓰지 않는다고 문서가 따로 밝혀 뒀다.

그래서 **찾던 값이 정말 있었는지는 한 번 더 봐야 안다.** Go 문서는 받은 자리의 값이 찾던 값과 같은지 따로 견주라고 예시까지 들어 적어 뒀다. Python 문서도 이 함수들이 같은지를 아예 묻지 않고 오직 "작은가" 만 묻는다고 밝힌다. `slices.BinarySearch` 처럼 자리와 함께 찾았는지를 참·거짓으로 돌려주는 것도 있다.

없을 때 돌아오는 자리가 버려지는 값이 아니라는 점도 중요하다. 그 자리가 곧 "정렬을 깨지 않고 넣을 수 있는 자리" 라서, 끼워 넣는 함수도 이 찾기를 먼저 돌린 다음 그 자리에 넣는다.

## 💡 실제 사례

- **점수를 등급으로 바꾸기** — 60·70·80·90 을 늘어놓고 점수가 그 사이 어디에 끼는지 물으면 등급이 나온다. Python 문서가 이 모듈의 예로 그대로 드는 것이다.
- **정렬을 유지하며 끼워 넣기** — 새 값이 들어갈 자리를 이진 탐색으로 찾고 그 자리에 넣는다. `insort` 가 이 두 걸음을 하나로 묶은 것이다.
- **이 값 이하로 가장 큰 것** — 값 하나를 정확히 집는 일이 아니라 구간을 묻는 일이다. Python 문서는 이런 물음을 이진 탐색의 몫으로 두고, 특정 값을 집는 데는 딕셔너리가 낫다고 적어 뒀다.

## 🚫 흔한 오해

- **정렬 안 된 목록에서도 쓸 수 있다** — 못 쓴다. Go 문서는 슬라이스가 오름차순으로 정렬돼 있어야 한다고 못 박는다. 절반을 버리는 근거 자체가 순서이기 때문이다.
- **찾았다는 뜻의 번호가 돌아온다** — 돌아오는 것은 자리다. 그 자리의 값이 찾던 값인지는 따로 견줘야 하고, 없을 때 -1 이 오는 것도 아니다.
- **찾기는 이진 탐색이 제일 빠르다** — 값 하나를 정확히 집는 일이라면 딕셔너리가 더 빠르다고 Python 문서가 직접 적어 뒀다. 이진 탐색이 맞는 자리는 구간을 묻는 쪽이다.

## 🚨 주의사항

- **정렬 비용을 같이 세라.** 한 번 찾으려고 정렬부터 하면 남는 것이 없다. `bisect` 문서가 이 모듈의 쓸모를 "넣을 때마다 다시 정렬하지 않고 정렬 상태를 유지하는 것" 이라고 적은 이유다.
- **끼워 넣기는 O(log n) 이 아니다.** 자리를 찾는 걸음은 O(log n) 인데 실제로 밀어 넣는 걸음이 O(n) 이라, Python 문서는 `insort` 를 O(n) 으로 못 박는다.
- **내림차순이면 조건을 뒤집는다.** Go 문서는 내림차순으로 정렬된 데이터를 찾을 때 `>=` 대신 `<=` 를 쓰라고 한다. 정렬 방향과 조건이 어긋나면 답이 성립하지 않는다.

## 📝 정리

이진 탐색은 정렬된 구간의 가운데를 보고 절반을 버리는 찾기다. 한 번 볼 때마다 후보가 반으로 줄어서 100만 개도 스무 번이면 좁혀지지만, 그 값은 목록이 정렬돼 있다는 전제를 치르고 사는 것이다. 돌려주는 것도 "있다" 가 아니라 자리라서, 있었는지는 한 번 더 견줘야 안다.

## ❓ 이해했는지

- 정렬해 두지 않은 목록에 이진 탐색을 쓸 수 없는 이유는 → 흔한 오해
- 자리를 받고도 그 자리의 값을 한 번 더 견주는 이유는 → 작동 원리
- 목록이 100만 개에서 200만 개로 늘면 볼 횟수는 얼마나 늘어나나 → 해결하는 문제
