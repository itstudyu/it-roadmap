# Linked List (연결 리스트)

## 📝 정의

Linked List 는 **값마다 다음 값의 자리를 들고 있는 자료구조**다.

Go 표준 라이브러리의 `container/list` 는 자기 소개를 "이 패키지는 이중 연결 리스트를 구현한다" 한 줄로 한다. 마디(Element) 하나가 `Next` 와 `Prev` 를 갖고 각각 다음 마디와 이전 마디를 돌려주기 때문에, 목록을 훑는 코드가 `for e := l.Front(); e != nil; e = e.Next()` 다. 다음 마디는 지금 마디에게 물어봐야 안다.

### 이름
Linked :: 손을 이어 잡은
List :: 죽 늘어놓은 것
= 붙여 읽으면 "손을 이어 잡고 늘어선 목록". 번호가 아니라 손이 순서를 만든다

### 비유
기차. 칸마다 옆 칸으로만 문이 나 있어서, 셋째 칸에 가려면 첫 칸에서부터 걸어 들어가야 한다.

### 예
음악 앱에서 다음 곡 버튼만으로 옮겨 다닐 때, 열 곡 뒤로 가려면 열 번을 눌러야 한다.

### 직접
폰 음악 앱에서 열 곡 뒤의 노래로 가 보라. 다음 곡 버튼만 쓰면 열 번을 눌러야 하고, 목록을 펼치면 그 줄을 곧장 짚는다.

## 🖼️ 그림으로 보기

```도해
대조: 배열과 연결 리스트는 무엇이 다른가
배열 |=| 연결 리스트
한 칸에 든 것 :: 값만 있다 || 값과 다음 자리
셋째 값 꺼내기 :: 자리를 계산 || 앞에서 세 번
맨 앞에 끼우기 :: 뒤를 다 민다 || 손만 바꿔 잡는다
= 배열은 자리를 계산해 곧장 가고, 연결 리스트는 손을 잡고 따라간다
```

## ⚠️ 해결하는 문제

```도해
대조: 맨 앞에서 넣고 빼기를 되풀이하면 어떻게 되나
배열로 || 연결로
한 번 비용 :: 뒤를 다 옮긴다 || 자리 하나만 고침
백만 개일 때 :: 백만 번 이동 || 그대로 한 번
개수가 늘면 :: 같이 느려진다 || 영향이 없다
= 앞뒤가 자주 드나드는 자리에서는 미는 일 자체를 없애는 게 답이다
```

맨 앞에서 넣고 빼는 일이 잦은 대기열을 [[Array]] 로 두면, 한 번 꺼낼 때마다 뒤에 있는 값 전부가 한 칸씩 앞으로 옮겨져야 한다. 파이썬 문서는 리스트가 `pop(0)` 과 `insert(0, v)` 에서 **O(n) 의 메모리 이동 비용**을 낸다고 적는다. 백만 개가 든 대기열이면 한 번 꺼낼 때마다 백만 번에 가까운 이동이 딸려 오고, 개수가 늘면 그만큼 더 딸려 온다.

연결된 구조에는 미는 일이 아예 없다. 같은 문서는 양끝 큐(deque)가 양쪽 끝에서 넣고 빼기를 **어느 쪽이든 대략 O(1)** 로 한다고 적는다. Go 의 `container/list` 도 `PushFront` 로 맨 앞에 마디 하나를 끼워 넣고 `Remove` 로 그 마디를 떼어낸다. 떼어낸 자리의 앞뒤 마디가 서로 손을 다시 잡으면 그걸로 끝이다.

## ⚙️ 작동 원리

한 방향만 들고 있는 것과 양쪽을 다 들고 있는 것이 다르다. Go 의 마디는 `Next` 와 `Prev` 를 둘 다 가진 **이중 연결**이라 앞뒤로 오갈 수 있고, 다음 자리만 들고 있으면 뒤로는 못 간다. 대신 마디마다 자리를 하나 더 기억해야 하니 한 칸이 그만큼 무거워진다.

꺼내는 값은 어디를 꺼내느냐로 갈린다. 파이썬 문서는 양끝 큐의 색인 접근이 "양쪽 끝에서는 O(1) 이지만 가운데로 갈수록 O(n) 으로 느려진다" 고 적고, 그러고는 곧바로 "빠른 임의 접근이 필요하면 리스트를 쓰라" 고 못 박는다. 앞의 O(n) 은 값을 옮기느라 드는 것이고 이쪽의 O(n) 은 손을 잡고 따라가느라 드는 것이다.

넣기가 싼 것도 조건이 붙는다. Go 의 `InsertBefore` 는 표시(mark)로 넘긴 마디 **바로 앞에** 새 마디를 넣는데, 그 mark 를 어디서 얻었느냐가 값을 정한다. 이미 손에 들고 있었다면 끼우는 일만 남지만, 앞에서부터 찾아왔다면 그 찾기가 이미 O(n) 이다.

## 📊 비교: 어느 일이 싸고 어느 일이 비싼가

| 하는 일 | 배열 | 연결 리스트 |
|---|---|---|
| 번호로 꺼내기 | 자리를 계산해 한 번 | 앞에서부터 짚어 간다 |
| 맨 앞에 넣고 빼기 | 뒤쪽 값 전부를 옮긴다 | 자리 하나만 고친다 |
| 자리를 아는 곳에 끼우기 | 뒤쪽 값 전부를 옮긴다 | 손만 바꿔 잡는다 |
| 한 칸이 차지하는 것 | 값 하나 | 값과 다음 자리 |

## 💡 실제 사례

- **양끝 대기열** — 앞뒤에서 넣고 빼는 일이 잦은 큐는 미는 비용이 없는 쪽으로 만든다. 파이썬의 `deque` 가 그 자리에 있다.
- **해시 충돌 처리** — [[Hash Table]] 의 한 칸에 여러 열쇠가 몰릴 때, 그 칸에 마디를 이어 붙여 늘리는 방식(체이닝)이 이 모양을 쓴다.
- **앞뒤로만 오가는 목록** — 다음 곡과 이전 곡으로 움직이는 재생 목록처럼, 번호로 뛰어들 일이 없고 옆으로만 가는 목록에 맞는다.

## 🚫 흔한 오해

- **연결 리스트가 배열보다 빠르다** — 넣고 빼는 자리만 그렇다. 셋째 값을 달라고 하면 배열은 자리를 계산해 한 번에 가고, 연결 리스트는 앞에서부터 세 번을 짚어 간다.
- **연결 리스트에 넣는 일은 언제나 O(1) 이다** — 끼울 자리를 이미 손에 들고 있을 때만 그렇다. `InsertBefore` 가 표시 마디를 요구하는 이유가 이것이고, 그 마디를 찾아가는 데 O(n) 이 들 수 있다.
- **파이썬의 `list` 가 연결 리스트다** — 이름만 리스트다. 문서가 `insert(0, v)` 에 O(n) 의 메모리 이동이 든다고 적는 것이 값을 미는 구조라는 증거다.

## 📝 정리

**"칸마다 다음 칸을 손에 쥔 그 줄"** 이라고 읽으면 된다. 손만 바꿔 잡으면 되니 넣고 빼는 데 미는 일이 없고, 대신 몇 번째 값을 달라는 요구에는 앞에서부터 짚어 가야 한다. 어느 쪽이 낫다가 아니라, 자주 하는 일이 꺼내기인지 끼우기인지로 갈린다.

## 🧒 열 살에게

기차 칸에는 옆 칸으로 가는 문만 있지? 그래서 셋째 칸에 가려면 첫 칸부터 걸어 들어가야 해. 대신 새 칸을 가운데 끼워 넣을 때는 앞뒤 칸의 고리만 바꿔 걸면 끝이라, 다른 칸은 하나도 옮기지 않아도 돼.

## ❓ 이해했는지

- 백만 개가 든 대기열의 맨 앞을 계속 꺼내는데 배열로 두면 무엇이 문제인가 → 해결하는 문제
- 연결 리스트에서 셋째 값을 꺼내는 일이 배열보다 오래 걸리는 이유는 → 작동 원리
- 이름이 리스트인 파이썬의 `list` 를 연결 리스트로 여기면 무엇을 잘못 예상하게 되나 → 흔한 오해
