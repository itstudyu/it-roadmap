# Character Encoding (문자 인코딩)

## 📝 정의

문자 인코딩은 **글자를 바이트로 바꿔 적는 약속**이다.

일이 두 층으로 갈려 있다. 유니코드가 세상의 모든 문자에 번호를 하나씩 매기고(지금 십오만 자가 넘는다), UTF-8 같은 인코딩 방식이 **그 번호를 바이트로 옮긴다.** 유니코드 컨소시엄은 이 옮기는 규칙을 "모든 유니코드 번호를 고유한 바이트 열로 대응시키는 알고리즘" 이라고 정의한다.

### 이름
Character :: 글자 한 자
Encoding :: 정한 꼴로 옮겨 적기
= 붙여 읽으면 "글자를 정한 꼴로 옮겨 적기". 무슨 꼴로 적었는지가 곧 그 약속의 이름이다

### 비유
글자마다 번호를 매겨 둔 명단과, 그 번호를 종이에 적는 필기법이 따로 있는 셈이다.

### 예
보낸 문서를 상대가 열었더니 한글이 전부 물음표와 낯선 기호로 바뀌어 있다는 연락을 받는 그 순간이다.

### 직접
아무 웹페이지에서 "페이지 소스 보기" 를 열고 맨 위의 `charset` 을 찾아 보라. 그 문서가 어떤 약속으로 적혔는지 스스로 밝혀 둔 자리다.

## 🖼️ 그림으로 보기

```도해
층: 사람이 보는 '한' 은 파일 안에서 무엇이 되나
글자 :: 사람이 보고 읽는 '한'
번호 :: 유니코드가 정해 둔 `U+D55C`
바이트 :: UTF-8 이 적은 세 바이트 `ED 95 9C`
= 글자와 바이트 사이에 번호가 한 층 끼어 있고, 인코딩은 아래 두 층을 잇는 약속이다
```

## ⚠️ 해결하는 문제

```도해
대조: 글자마다 정해진 번호가 없으면 어떻게 되나
약속이 저마다면 || 번호가 하나면
같은 바이트 :: 다른 글자가 된다 || 같은 글자가 된다
한글 문서 :: 뜻 없는 기호가 된다 || 그대로 열린다
여러 언어 :: 한 파일에 못 담는다 || 한 파일에 다 담긴다
= 모든 문자에 번호를 하나씩 매겨 두면, 남는 문제는 그 번호를 어떻게 적을지다
```

파일에 남는 것은 바이트뿐이고, 바이트는 자기가 어떤 글자였는지 말해주지 않는다. 같은 바이트 묶음을 다른 약속으로 읽으면 다른 글자가 나온다. 한글이 뜻 모를 기호로 뒤틀려 보이는 일은 대개 이것이다 — 적은 약속과 읽는 약속이 다른 것.

유니코드는 **번호를 통일해서** 아래 절반을 해결했다. "현대와 고대를 포함해 세상의 모든 표기 체계의 문자를 담는다"는 것이 유니코드 컨소시엄의 설명이다. 위 절반, 곧 그 번호를 바이트로 어떻게 적을지가 UTF-8·UTF-16 의 몫이다.

## ⚙️ 작동 원리

```도해
층: 번호가 커지면 바이트는 몇 개까지 늘어나나
1바이트 :: `U+0000`~`U+007F`. 영문·숫자·기호
2바이트 :: `U+0080`~`U+07FF`. 유럽·중동 문자
3바이트 :: `U+0800`~`U+FFFF`. 한글·한자·일본어
4바이트 :: `U+10000`~`U+10FFFF`. 이모지 등 나머지
= 번호가 클수록 바이트가 늘어난다. 한글은 세 번째 칸이라 한 글자에 세 바이트다
```

UTF-8 은 번호 크기에 따라 한 글자를 1~4바이트로 적는다. 한글 낱글자가 모인 칸은 `U+AC00`~`U+D7AF` 이니 셋째 줄에 들어가고, 그래서 한글은 한 글자에 세 바이트다.

첫 줄이 이 방식의 값을 만든다. 옛 ASCII 문자는 원래 값 그대로 한 바이트에 들어가고, 그 값을 가진 바이트는 ASCII 문자 말고 다른 것일 수 없다. 그래서 영문과 기호만 든 파일은 UTF-8 로 적어도 옛 도구가 한 글자도 어긋나지 않게 읽는다.

## 📊 비교: UTF-8 vs UTF-16

| | UTF-8 | UTF-16 |
|---|---|---|
| **영문 한 글자** | 1바이트 | 2바이트 |
| **한글 한 글자** | 3바이트 | 2바이트 |
| **옛 ASCII 파일** | 바이트가 그대로 | 전부 달라진다 |
| **나머지 문자** | 4바이트까지 늘린다 | 두 칸을 이어 붙인다 |

한글만 든 문서는 UTF-8 이 UTF-16 보다 **1.5배쯤 크다.** 영문 비중이 조금이라도 있으면 이 차이는 줄어들고, 태그와 기호가 많은 문서에서는 뒤집힌다.

## 💡 실제 사례

- **글자가 뒤틀린 파일** — 보낸 쪽이 어떤 약속으로 적었는지 밝히지 않으면, 읽는 쪽은 자기 약속으로 해석해서 엉뚱한 글자를 낸다.
- **글자 수와 바이트 수가 어긋난 입력 칸** — 한글 열 자는 UTF-8 로 서른 바이트다. 길이를 바이트로 재는 칸은 한글을 셋 중 하나만큼만 받는다.
- **영문만 든 설정 파일** — UTF-8 바이트가 옛 ASCII 와 한 글자도 다르지 않아서, 인코딩을 모르는 옛 도구도 그대로 읽는다.

## 🚫 흔한 오해

- **UTF-8 이 곧 유니코드다** — 유니코드는 글자마다 번호를 정한 표준이고, UTF-8 은 그 번호를 바이트로 옮기는 방식 하나다. 같은 번호를 UTF-16 으로 적으면 바이트가 달라진다.
- **한 글자는 한 바이트다** — 영문·숫자만 그렇다. 한글은 세 바이트, 이모지는 네 바이트다. 그래서 바이트 수로 글자 수를 세면 틀린다.
- **UTF-8 이 항상 낫다** — 한글이나 한자만 담는 문서라면 UTF-16 이 글자당 두 바이트라 오히려 작다. UTF-8 이 이긴 자리는 크기가 아니라 옛 ASCII 와 어긋나지 않는다는 점이다.

## 📝 정리

**"글자를 바이트로 옮겨 적는 그 약속"** 이라고 읽으면 된다. 유니코드가 글자마다 번호를 정하고, UTF-8 같은 인코딩이 그 번호를 몇 바이트로 어떻게 적을지 정한다. 글자가 깨지는 것은 대개 적은 약속과 읽는 약속이 다를 때다.

## 🧒 열 살에게

반 아이들한테 번호를 하나씩 매겨 두면 "3번" 이라고만 해도 누군지 알지? 온 세상 글자에도 그렇게 번호가 하나씩 붙어 있는데, 그 번호를 종이에 적는 방법은 여러 가지야. 적을 때 쓴 방법과 읽을 때 쓴 방법이 다르면 엉뚱한 글자가 튀어나와.

- 한글만 든 문서를 UTF-16 으로 적으면 더 작아지는 이유는 → 비교
