# Race Condition (경쟁 상태)

## 📝 정의

Race Condition 은 **누가 먼저 닿는지**에 따라 결과가 달라지는 버그다.

이름의 '경쟁' 은 둘 이상의 흐름이 같은 코드 지점에 누가 먼저 닿는지를 두고 벌이는 달리기에서 왔다. .NET 문서는 멀티스레딩이 처리량과 응답성을 해결해주는 대신 새 문제 둘을 들여온다고 적는다 — 교착 상태와 경쟁 상태다.

### 이름
Race :: 누가 먼저 닿나
Condition :: 그런 상황
= 붙여 읽으면 "먼저 닿는 쪽이 이기는 상황". 이름이 곧 버그의 원인이다

### 비유
둘이 같은 칠판에 적힌 숫자를 각자 읽고 1 을 더해 적으면, 두 번 더했는데 1 만 올라간다.

### 예
결제 버튼을 급하게 두 번 눌렀더니 같은 주문이 두 건 들어가 있던 일이 있다.

### 직접
같은 글 파일을 편집기 두 개로 열어 서로 다르게 고친 뒤 둘 다 저장해 보라. 나중에 저장한 쪽만 남는다.

## 🖼️ 그림으로 보기

```도해
흐름: 두 흐름이 같은 값을 하나씩 올렸는데 왜 1 만 올라가나
흐름A :: 값 5 를 읽어 손에 든다
흐름B :: 끼어들어 같은 5 를 읽는다
흐름B :: 6 으로 만들어 적고 끝난다
흐름A :: 아까 읽은 5 로 6 을 적는다
= 두 번 올렸는데 6 이다. 어느 쪽이 먼저 닿았는지가 결과를 바꾼다
```

## ⚠️ 해결하는 문제

```도해
대조: 공유하는 값에 순서를 정해주면 무엇이 달라지나
순서 없이 || 순서를 정하면
두 번 올리면 :: 하나가 사라진다 || 둘 다 남는다
같은 입력 :: 실행마다 다르다 || 언제나 같다
버그 찾기 :: 될 때만 재현된다 || 애초에 안 난다
= 값이 틀리는 게 아니라 순서가 안 정해진 것이 문제다
```

경쟁 상태가 무서운 이유는 틀린 값이 나온다는 데 있지 않다. **대개는 잘 돌아간다**는 데 있다. .NET 문서는 같은 프로그램을 여러 번 돌리면 서로 다른 결과가 나오고 어떤 한 번의 결과도 미리 알 수 없다고 적는다. 그러니 한 번 잘 돌아간 것은 다음에도 잘 돌아간다는 증거가 못 된다.

고치는 방법은 값을 검사하는 것이 아니라 **순서를 정해주는 것**이다. 같은 값을 만지는 구간에 한 번에 하나만 들어가게 하거나, 읽고 더하고 쓰는 세 걸음을 쪼갤 수 없는 한 걸음으로 합친다. .NET 문서가 단순한 값 갱신에 `lock` 보다 `Interlocked.Increment` 를 권하는 것이 후자다.

## ⚙️ 작동 원리

한 줄로 쓴 코드가 한 걸음은 아니다. 값을 하나 올리는 일은 값을 읽어 오고, 1 을 더하고, 다시 써 넣는 세 걸음으로 쪼개진다. .NET 문서는 값을 읽어 더한 흐름이 중간에 선점될 수 있고, 끼어든 흐름이 세 걸음을 다 끝낸 뒤 먼저 있던 흐름이 자기 값을 써 넣으면 그동안 값이 바뀐 사실을 무시한 채 덮어쓴다고 설명한다.

그래서 문서는 코드 한 줄을 쓸 때마다 이렇게 물으라고 한다 — 이 줄을(또는 이 줄을 이루는 기계 명령 하나하나를) 실행하기 전에 흐름이 선점되고 다른 흐름이 앞질러 갔다면 무슨 일이 벌어지나.

공유하는 것이 메모리만은 아니다. 임시 파일 이름을 먼저 만들고 나중에 그 이름으로 파일을 여는 방식은, 그 사이에 다른 프로세스가 같은 이름으로 파일을 만들어 버릴 수 있다. Python 문서는 이 방식을 보안 구멍이라 부르고, 이름을 받아 든 다음 무언가 하려 할 때쯤이면 누군가 먼저 손을 썼을 수 있다고 적는다. **확인한 시점과 쓰는 시점이 벌어지면 그 틈이 곧 경쟁 상태다.**

## 💡 실제 사례

- **인스턴스 개수 세기** — 객체를 만들 때마다 올리는 공용 카운터는 읽고·더하고·쓰는 세 걸음이라, 중간에 끼어들면 한 번이 조용히 사라진다.
- **임시 파일 이름** — 이름을 만든 뒤 파일을 여는 두 걸음 사이에 다른 프로세스가 끼어든다. 스레드를 하나도 안 쓴 프로그램에서도 경쟁 상태가 나는 자리다.
- **동기화 코드 안** — 여러 흐름의 순서를 맞추려고 쓴 코드 자체에서도 경쟁 상태가 생긴다고 .NET 문서가 따로 경고한다.

## 🚫 흔한 오해

- **테스트가 통과했으니 괜찮다** — 같은 코드가 실행마다 다른 결과를 낸다. 어떤 한 번의 결과도 미리 알 수 없으니, 백 번 통과한 것은 백한 번째를 보장하지 않는다.
- **`count++` 은 한 줄이니까 한 번에 끝난다** — 읽고, 더하고, 쓰는 세 걸음이다. 그 사이 어디서든 다른 흐름이 끼어들 수 있다.
- **잠금을 촘촘히 걸수록 안전해진다** — .NET 문서는 되도록 동기화가 필요 없게 설계하라고 먼저 말한다. 불필요한 동기화는 성능을 깎고 교착과 경쟁 상태의 가능성을 오히려 만든다.

## 🚨 주의사항

- **두 걸음을 한 걸음으로 합치는 쪽이 확실하다** — 이름을 만든 뒤 파일을 여는 대신 만들면서 여는 함수를 쓰라는 것이 Python 문서의 답이다. 잠금을 덧대는 것보다 틈 자체를 없애는 편이 낫다.
- **단순한 값 갱신에는 잠금보다 원자 연산** — .NET 문서는 간단한 상태 변경에 `lock` 대신 `Interlocked` 를 쓰라고 권한다. 다툼이 없을 때는 잠금 접두사 하나만 실행되어 더 빠르다.
- **없애는 대신 견디는 선택도 있다** — 문서는 경우에 따라 경쟁 상태를 없애기보다 그것을 견디도록 알고리즘을 손보는 편이 나을 수도 있다고 적었다. 무조건 잠그는 것이 정답은 아니다.

## 📝 정리

**"먼저 닿는 쪽이 이기는 그 상황"** 이라고 읽으면 된다. 값이 틀린 것이 아니라 순서를 아무도 정해주지 않은 것이 문제이고, 그래서 같은 코드가 실행마다 다른 답을 낸다. 한 번 잘 돌아간 것은 다음에도 잘 돌아간다는 증거가 못 된다.

## 🧒 열 살에게

칠판에 5 라고 적혀 있는데 너랑 친구가 동시에 그걸 보고 각자 6 을 적으면 어떻게 될까? 둘이 한 번씩 올렸는데 칠판에는 6 만 남아. 한 번이 조용히 사라진 거야 — 누가 먼저 봤느냐에 따라 답이 달라지거든.
