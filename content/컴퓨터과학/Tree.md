# Tree (트리)

## 📝 정의

Tree 는 **한 뿌리에서 아래로 갈라져 내려가는 구조**다.

WHATWG 의 DOM 표준은 이 모양만 따로 떼어 규정한다. 트리에 참여하는 객체는 "널이거나 객체 하나" 인 부모와 "순서 있는 객체들의 집합" 인 자식을 가진다. 어떤 객체의 뿌리는 부모가 널이면 자기 자신이고 아니면 자기 부모의 뿌리다 — 위로는 하나로 모이고 아래로는 여럿으로 갈라진다는 말을 표준은 이렇게 적는다.

### 이름
= 말 그대로 "나무" 다. 다만 뿌리를 맨 위에 두고 거꾸로 세워 그린 나무다

### 비유
책의 목차. 부 안에 장이, 장 안에 절이 들어 있어서 어느 절에서 시작해도 위로 올라가면 부 하나로 모인다.

### 예
쇼핑몰에서 카테고리를 누를수록 갈래가 좁아지다 결국 상품 하나에 닿는다.

### 직접
컴퓨터 폴더 창의 왼쪽 목록에서 화살표를 눌러 펼쳐 보라. 폴더 안에 폴더가 갈라져 내려가고, 거슬러 올라가면 한 곳으로 모인다.

## 🖼️ 그림으로 보기

```도해
층: 트리는 위에서 아래로 어떻게 갈라지나
뿌리 :: 부모가 없는 단 하나. 여기서 시작한다
중간 마디 :: 위로는 부모 하나, 아래로는 자식 여럿
잎 :: 자식이 없는 끝. 여기서 갈래가 멈춘다
= 위로는 하나로 모이고 아래로는 갈라진다. 그래서 어느 잎이든 올라가는 길이 하나다
```

## ⚠️ 해결하는 문제

```도해
대조: 정렬해 둔 백만 개에서 하나를 찾으면 어떻게 되나
한 줄로 훑기 || 트리로 내려가기
한 번 볼 때 :: 하나를 지운다 || 절반을 지운다
백만 개 :: 평균 50만 번 || 20번쯤
100배로 늘면 :: 시간도 100배 || 7번쯤 더
= 한 번에 절반을 버릴 수 있으면 백만 개도 스무 번이면 닿는다
```

값을 한 줄로 늘어놓고 하나를 찾으면 앞에서부터 견주는 수밖에 없다. 백만 개면 평균 오십만 번이고, 개수가 백 배로 늘면 걸리는 시간도 백 배가 된다.

트리는 마디마다 갈 방향을 하나만 고르게 한다. 한 마디를 지날 때 안 고른 갈래가 통째로 후보에서 빠지므로 남은 후보가 매번 절반이 된다. 백만은 스무 번쯤 반으로 접으면 하나가 되고, 거기서 개수가 백 배로 늘어도 일곱 번쯤 더 접으면 된다. 닷넷 문서는 이진 탐색 트리로 만든 `SortedDictionary` 의 조회를 O(log n) 이라고 적고, 정렬되지 않은 데이터를 넣고 빼는 일도 같은 O(log n) 이라고 적는다.

## ⚙️ 작동 원리

절반을 버릴 수 있는 건 마디마다 **어디로 갈지 정해 주는 규칙**이 있을 때다. 규칙이 없으면 트리는 그냥 갈라진 그림이고, 값 하나를 찾으려면 모든 갈래를 다 내려가 봐야 한다.

파이썬 `heapq` 문서가 그 규칙을 가장 짧게 보여준다. 최소 힙은 "모든 부모 마디가 자기 자식들보다 작거나 같은 이진 트리" 이고, 그래서 "가장 작은 원소가 늘 뿌리" 다. 부모와 자식 사이의 규칙 한 줄이 꼭대기만 봐도 최솟값을 알게 만든다.

같은 문서는 이 트리를 **리스트 하나에 담는다.** `heap[k]` 의 자식이 `heap[2*k+1]` 과 `heap[2*k+2]` 다. 마디를 잇는 손이 따로 없어도 번호 계산으로 부모와 자식을 오간다 — 트리는 값들 사이의 관계이지 저장 방식이 아니다.

드는 비용은 뿌리에서 잎까지 내려가는 길의 길이가 정한다. 같은 문서는 뿌리에 놓인 값을 규칙이 맞을 때까지 아래로 내려보내는 일이 "트리에 든 전체 개수에 대해 명백히 로그" 라고 적는다. 층이 하나 늘 때마다 담을 수 있는 개수가 곱절이 되니, 개수가 곱절이 되어도 길이는 한 칸만 늘어난다.

## 📊 비교: 트리의 갈래들

| 갈래 | 마디들이 지키는 규칙 | 그래서 잘하는 일 |
|---|---|---|
| 이진 탐색 트리 | 정렬 기준으로 둘로 갈라 담는다 | 정렬된 채로 찾고 넣기. O(log n) |
| 힙 | 부모가 자식보다 작거나 같다 | 가장 작은 것 하나만 꺼내기 |
| 문서 트리(DOM) | 부모 하나에 순서 있는 자식들 | 화면에 그릴 문서의 구조 담기 |

한 마디를 둘이 아니라 더 여러 갈래로 갈라 놓은 갈래도 있다. PostgreSQL 문서가 색인에 쓰는 표준 btree 를 "여러 갈래로 갈라지는 균형 트리(multi-way balanced tree)" 라고 적는 그것이고, 이 앱에서는 [[B-Tree]] 로 따로 다룬다.

## 💡 실제 사례

- **파일 시스템** — 폴더 안에 폴더를 담고 경로를 따라 내려간다. 어느 파일이든 부모를 거슬러 올라가면 뿌리 하나로 모인다.
- **웹 문서** — 브라우저는 HTML 을 마디의 트리로 들고 있다. DOM 표준이 그 트리의 부모·자식·형제와 훑는 순서(tree order)까지 규정한다.
- **DB 색인** — 정렬해 둔 열쇠를 트리로 담아, 백만 행이 든 표에서도 몇 층만 내려가 원하는 행에 닿는다.

## 🚫 흔한 오해

- **트리에 담으면 언제나 O(log n) 이다** — 마디마다 자식이 하나뿐이게 자란 트리는 뿌리에서 잎까지의 길이가 개수와 같아져서 한 줄을 훑는 것과 다르지 않다. 절반을 버릴 수 있는 건 갈래가 고르게 갈라져 있을 때이고, PostgreSQL 문서가 색인의 btree 를 굳이 "균형(balanced) 트리" 라고 적는 이유가 이것이다.
- **한 마디가 부모를 여럿 가질 수도 있다** — DOM 표준은 부모를 "널이거나 객체 하나" 로 못 박는다. 부모가 둘이 되면 위로 올라가는 길이 하나가 아니어서, 트리라서 얻던 성질이 전부 사라진다.
- **찾는 일이면 트리가 낫다** — 열쇠 하나로 콕 집어 꺼내는 일은 해시 테이블이 평균 계산 한 번이다. 트리가 이기는 자리는 순서와 범위를 함께 다뤄야 할 때다.

## 📝 정리

**"뿌리 하나에서 갈라져 내려가는 모양"** 이라고 읽으면 된다. 마디마다 갈 방향을 정해 주는 규칙이 붙으면 한 번 볼 때마다 남은 후보의 절반이 사라져서 백만 개도 스무 번이면 닿는다. 대신 갈래가 한쪽으로 치우치면 그 이득이 그대로 없어진다.

## 🧒 열 살에게

두꺼운 책 맨 앞의 목차를 보면 부 안에 장이 있고 장 안에 절이 있지? 아무 절이나 골라 위로 거슬러 올라가면 결국 한 군데로 모여. 그래서 찾을 때는 거꾸로, 위에서 갈래 하나만 고르면 나머지 갈래는 통째로 안 봐도 돼.

## ❓ 이해했는지

- 백만 개에서 스무 번 만에 찾을 수 있다는 말의 근거가 무엇인가 → 해결하는 문제
- 트리에 담았는데도 찾기가 한 줄만큼 느려지는 경우는 언제인가 → 흔한 오해
- 가장 작은 값 하나만 계속 꺼내야 하는 일에는 어느 갈래가 맞나 → 비교
