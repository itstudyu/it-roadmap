# RAG (Retrieval-Augmented Generation)

## 📝 정의

RAG는 **LLM에게 교과서를 찾아주는 시스템**입니다. LLM 혼자서는 최신 정보나 회사별 정보를 모르지만, RAG가 관련 문서를 찾아주면 정확한 답변을 할 수 있습니다.

### 핵심 개념

- **무엇인가?**: 검색(Retrieval) + LLM 생성(Generation)의 결합
- **왜 필요한가?**: LLM의 지식 한계와 환각(Hallucination)을 해결하기 위해
- **어떻게 작동하나?**: 질문 → 관련 문서 검색 → LLM에 전달 → 답변 생성

## 🤔 왜 RAG가 필요한가?

### LLM 단독 사용의 문제

**1. 최신 정보 모름**:
```
사용자: "2024년 육아휴직 개정 내용은?"
LLM 단독: "2023년까지만 알아요..." ❌
→ 학습 데이터가 낡음!

RAG 사용: [2024년 문서 검색]
→ "2024년 3월 개정: 기간 2년→3년" ✅
```

**2. 회사별 정보 모름**:
```
사용자: "우리 회사 육아휴직 규정은?"
LLM 단독: "일반적으로는..." ❌
→ A회사 규정을 모름!

RAG 사용: [A회사 취업규칙 검색]
→ "A회사는 최대 2년입니다" ✅
```

**3. Hallucination (환각)**:
```
사용자: "제40조 내용은?"
LLM 단독: "제40조는 퇴직금..." ❌
→ 없는 조항을 지어냄!

RAG 사용: [문서 검색 → 없음]
→ "문서에 제40조가 없습니다" ✅
```

## 📊 RAG 작동 원리

### 전체 흐름


### 단계별 설명

**1단계: 질문 이해**
```
"육아휴직은 몇 년?"
→ 벡터로 변환: [0.3, 0.5, 0.7, ...]
(의미를 숫자로 표현)
```

**2단계: 유사 문서 검색**
```
Vector DB에서 유사한 문서 찾기:
제32조 (육아휴직): 유사도 0.89 ✅
제30조 (연차휴가): 유사도 0.43
제33조 (경조사): 유사도 0.38

→ Top-3 선택
```

**3단계: LLM에게 전달**
```
LLM에게:
"다음 문서를 참고해서 답변하세요:
제32조: 육아휴직 기간은 최대 2년..."

질문: "육아휴직은 몇 년?"
```

**4단계: 답변 생성**
```
LLM: "제32조에 따르면,
      육아휴직 기간은 최대 2년입니다."

→ 출처와 함께 정확한 답변!
```

## 💡 일상적 비유로 이해하기

### RAG = 시험에 교과서 들고 가기

**LLM 단독 (교과서 없이 시험)**:
```
학생: 기억에만 의존
→ 2023년에 공부한 내용만 앎
→ 가끔 기억 착각
→ 회사별 규정은 모름

점수: 60점
```

**RAG (교과서 보면서 시험)**:
```
학생: 책 찾아보면서 답변
→ 최신 개정판도 확인 가능
→ 정확한 조항 찾아서 인용
→ 출처도 명시

점수: 95점
```

### RAG의 장점

| 기능 | LLM 단독 | RAG |
|------|----------|-----|
| 최신 정보 | ❌ (학습 시점까지) | ✅ (문서 업데이트하면 즉시) |
| 회사별 정보 | ❌ (모름) | ✅ (문서에 있으면 찾음) |
| Hallucination | ⚠️ (자주 발생) | ✅ (문서 기반으로 방어) |
| 출처 제공 | ❌ | ✅ (어느 조항인지 명시) |
| 비용 | 낮음 | 중간 (Vector DB 필요) |

## 🎯 P3 시스템의 RAG

### P3 RAG 파이프라인

```도해
흐름: RAG, 무슨 순서로 오가나
사용자 :: 육아휴직은?
Chatbot :: 유사 문서 검색
Vector DB :: 제32조 (0.89), 제30조 (0.43)
Chatbot :: 질문 + 문서들
LLM :: 제32조에 따르면 최대 2년...
Chatbot :: 답변 + 출처
```

### P3에서 RAG가 중요한 이유

```
1. 취업규칙 = 회사마다 다름
   → LLM 학습 데이터에 없음
   → RAG 필수!

2. 규정 자주 변경
   → 매번 Fine-tuning 불가능 (비용 ↑)
   → RAG로 문서만 업데이트 (비용 ↓)

3. 법적 정확성 필요
   → Hallucination 절대 안 됨
   → RAG로 출처 명시
```


## 🔧 RAG 최적화

### 1. Chunking (문서 분할)

```
❌ 나쁜 예: 전체 문서를 한 덩어리로
→ 검색 정확도 낮음

✅ 좋은 예: 조항별로 분할
제30조 → 하나의 청크
제32조 → 하나의 청크
→ 검색 정확도 높음
```

### 2. Hybrid Search

```
Vector Search (의미 검색) 70%
+
Keyword Search (키워드 매칭) 30%
=
더 정확한 검색
```

### 3. Reranking

```
1차 검색: Vector DB → Top-10
2차 정렬: Cross-Encoder로 재평가
→ Top-3 최종 선택

정확도: 85% → 95% 향상
```

### 4. Caching

```
같은 질문 반복 시:
→ Vector DB 검색 생략
→ 캐시에서 바로 가져오기
→ 속도: 0.5초 → 0.005초 (100배)
→ 비용: 70% 절감
```

## 🚨 주의사항

### 1. Chunk 크기

```
너무 작으면: 문맥 손실
→ "최대 2년" (무엇이 2년?)

너무 크면: 검색 정확도 하락
→ 여러 주제 섞임

P3 권장: 조항별 분할
→ 제32조 = 1개 청크
```

### 2. 임계값 설정

```
유사도 0.3 이하:
→ "관련 정보를 찾지 못했습니다"
→ Hallucination 방지

유사도 0.7 이상:
→ "제32조에 따르면..."
→ 높은 신뢰도
```

### 3. 비용 관리

```
Vector DB: $50~500/월
LLM 호출: $1,000~3,000/월

절감 방법:
1. 캐싱 (70%)
2. Batch 처리 (20%)
3. Threshold로 LLM 호출 줄이기 (30%)

→ 총 $500/월까지 가능
```

## 📝 정리

**RAG 핵심 3줄 요약**:
```
1. LLM에게 교과서(문서)를 찾아주는 시스템
2. 최신 정보 + 회사별 정보 + Hallucination 방지
3. 비용 효율적이고 업데이트 쉬움

→ P3 같은 기업 AI에 필수!
```

**비유로 기억하기**:
```
LLM 단독 = 기억에만 의존하는 시험
→ 60점

RAG = 교과서 보면서 시험
→ 95점

P3 = RAG + 캐싱 + 최적화
→ 99점 + 빠름 + 저렴
```

**RAG 공식**:
```
RAG = 검색(Retrieval) + LLM(Generation)

검색: Vector DB에서 관련 문서 찾기
생성: LLM이 문서 기반으로 답변

결과 = 정확도 ↑ + 최신성 ↑ + 비용 ↓
```
