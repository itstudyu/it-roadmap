# RAG (Retrieval-Augmented Generation)

## 📝 정의

RAG는 **답하기 전에 관련 문서를 찾아 같이 넣어주는 방식**이다.

모델은 학습한 것만 안다. 우리 회사 규정이나 어제 올라온 문서는 모른다. 질문이 오면 먼저 그 문서를 찾아서 질문과 함께 넣어주면, 모델은 그 내용을 보고 답한다.

### 비유
개방형 시험. 외운 것만으로 답하게 하면 틀리거나 지어내지만, 교재를 펴놓고 답하게 하면 근거를 짚어 답한다.

## 🖼️ 그림으로 보기

```도해
흐름: 사내 규정을 물으면 무슨 일이 일어나나
사용자 :: "연차는 며칠인가요" 라고 묻는다
검색기 :: 질문을 벡터로 바꾼다
벡터 DB :: 뜻이 가까운 문서 조각 세 개를 꺼낸다
조립 :: 찾은 조각 + 원래 질문을 하나로 묶는다
모델 :: 그 묶음만 보고 답을 만든다
< 사용자 :: 출처가 붙은 답을 받는다
= 모델을 다시 학습시키지 않고도 새 지식을 쓰게 만드는 방법이다
```

## ⚠️ 해결하는 문제

```도해
대조: 사내 문서를 모델에 물으려면 어떻게 하나
RAG 없이 || RAG 로
새 문서 반영 :: 재학습 필요 || 넣으면 바로
출처 :: 알 수 없다 || 문서를 짚어준다
비용 :: 학습 비용이 크다 || 검색 비용만
= 지식을 모델 안에 넣지 않고 밖에 두는 것이 이 방식의 요점이다
```

모델을 우리 데이터로 다시 학습시키는 방법도 있지만 비싸고 오래 걸린다. 문서가 하나 바뀔 때마다 다시 학습할 수는 없다.

RAG는 지식을 모델 밖에 둔다. 문서가 바뀌면 저장소만 갱신하면 되고, 답에 어느 문서를 봤는지 붙일 수 있어서 사람이 확인할 수 있다. [[Hallucination]]이 줄어드는 것도 지어낼 필요가 없어지기 때문이다.

## ⚙️ 작동 원리

준비 단계와 응답 단계가 나뉜다.

```도해
층: 문서가 답이 되기까지 무엇을 거치나
쪼개기 :: 긴 문서를 문단 단위로 자른다
임베딩 :: 조각마다 뜻을 벡터로 만든다
저장 :: 벡터 DB 에 넣어둔다
검색 :: 질문 벡터와 가까운 조각을 꺼낸다
= 앞의 세 단계는 미리, 마지막 하나만 질문할 때 한다
```

쪼개는 크기가 품질을 크게 좌우한다. 너무 크면 관계없는 내용이 섞여 들어오고, 너무 작으면 문맥이 끊겨서 무슨 말인지 알 수 없게 된다.

## 📊 비교: 일반 LLM vs RAG vs Fine-tuning

| | 일반 LLM | RAG | Fine-tuning |
|---|---|---|---|
| 지식 출처 | 학습 데이터 | 바깥 문서 | 재학습 데이터 |
| 최신 정보 | 안 된다 | 문서만 고치면 된다 | 다시 학습해야 한다 |
| 출처 표시 | 못 한다 | 조각까지 댄다 | 못 한다 |
| 바꾸는 비용 | 바꿀 수 없다 | 낮다 | 높다 |

## 💡 실제 사례

- **사내 문서 검색** 규정, 매뉴얼, 회의록을 넣어두고 자연어로 묻는다.
- **고객 문의 응대** 제품 문서를 근거로 답하고 링크를 함께 준다.
- **코드베이스 질문** 저장소를 쪼개 넣어두면 "이 함수 어디서 쓰나"를 물을 수 있다.

## 🚫 흔한 오해

- **RAG를 붙이면 환각이 사라진다** — 줄어들 뿐이다. 검색이 엉뚱한 문서를 가져오면 그 엉뚱한 문서를 근거로 그럴듯하게 지어낸다.
- **문서를 다 넣으면 된다** — 문맥 창에 한계가 있어서 다 넣을 수 없다. 무엇을 골라 넣느냐가 이 방식의 전부다.
- **검색이 키워드로 이뤄진다** — 뜻으로 찾는다. "연차"라고 물어도 "휴가 규정" 문서가 나오는 것이 이 방식의 장점이자, 엉뚱한 문서를 가져오는 이유다.

## 🚨 주의사항

- **검색 품질이 답의 상한이다.** 모델을 바꾸기 전에 무엇을 가져왔는지부터 본다. 나쁜 답의 대부분은 나쁜 검색에서 나온다.
- **권한을 검색 단계에서 거른다.** 문서를 다 넣어두면 권한 없는 사용자에게도 내용이 나갈 수 있다.

## 📝 정리

RAG는 답하기 전에 관련 문서를 찾아 함께 넣어주는 방식이다. 지식을 모델 밖에 두어 갱신과 출처 표시가 쉬워지고, 대신 검색 품질이 답의 품질을 정한다.
