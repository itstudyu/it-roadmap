# Prompt Caching (프롬프트 캐싱)

## 📝 정의

Prompt Caching은 **매번 같은 앞부분을 다시 계산하지 않고 재사용하는 것**이다.

모델은 매번 프롬프트를 처음부터 끝까지 읽는다. 그런데 실제 서비스에서 앞쪽은 거의 안 바뀐다 — 규정 문서, 예시 몇 개, 도구 정의는 부를 때마다 똑같이 실린다. 그 앞부분을 읽어들인 상태로 저장해 두었다가 다음 요청에서 이어 쓰는 것이 이 장치다. 두 곳의 공식 문서가 같은 말로 적는다. Anthropic 문서는 "프롬프트의 특정 앞자락에서 이어서 시작하게 해 준다" 고 쓰고, OpenAI 문서는 "프롬프트의 앞자락이 정확히 일치할 때만 캐시가 걸린다" 고 쓴다.

### 이름
Prompt :: 모델에 건네는 말
Caching :: 해 둔 것을 남겨 둠
= 붙여 읽으면 "건넨 말을 남겨 두고 다시 쓰기". 남는 것은 답이 아니라 읽어들인 앞부분이다

### 비유
매일 같은 교과서를 펴는 수업. 읽은 데까지 책갈피가 꽂혀 있어서, 오늘은 그 뒤부터 읽으면 된다.

### 예
계약서를 통째로 붙여 넣고 질문만 바꿔 가며 열 번 물어볼 때다. 계약서는 열 번 다 똑같다.

## 🖼️ 그림으로 보기

```도해
흐름: 같은 앞부분을 다시 보내면 무슨 일이 일어나나
요청 :: 지시문·문서·질문을 통째로 다시 보낸다
맞춰 보기 :: 앞에서부터 저장해 둔 것과 대조한다
같은 데까지 :: 계산을 건너뛰고 그대로 가져온다
어긋난 뒤 :: 여기서부터만 새로 읽는다
< 응답 :: 꺼내 쓴 양과 새로 넣은 양을 함께 알려준다
= 앞에서부터 똑같은 만큼만 아낀다. 한 글자라도 다르면 거기서부터 다시다
```

## ⚠️ 해결하는 문제

```도해
대조: 앞부분이 길어지면 무엇이 달라지나
캐시 없이 || 캐시로
같은 지시문 :: 부를 때마다 다시 || 한 번만 읽는다
값 :: 전부 제값 || 읽기는 십분의 일
기다림 :: 앞부분만큼 늦다 || 뒷부분만큼만
= 되풀이되는 앞부분이 길수록 아끼는 몫이 커진다
```

앞에 붙이는 것이 길어질수록 값과 기다림이 같이 늘어난다. 규정 문서 스무 장을 붙여 놓고 한 줄짜리 질문을 던지면, 매번 스무 장을 다시 읽히고 그만큼을 매번 낸다. 질문을 열 번 하면 스무 장을 열 번 읽는다.

캐싱은 **안 바뀌는 앞부분과 바뀌는 뒷부분을 갈라 놓는다.** 앞부분은 한 번만 읽히고, 그다음부터는 저장분에서 꺼내 쓴다. 두 곳 문서가 모두 꺼내 쓴 몫을 원래 입력값의 십분의 일로 계산한다고 적는다. 그래서 앞부분이 길수록, 그리고 같은 앞부분을 자주 부를수록 이득이 커진다.

## 🧱 구성

```도해
층: 요청의 어느 칸을 고치면 어디까지 무효가 되나
도구 정의 :: 맨 앞에 실린다. 여기를 고치면 아래가 전부 무효
지시문 :: 도구가 그대로여도 여기를 고치면 아래가 무효
주고받은 말 :: 위가 그대로면 앞에서부터 같은 데까지는 살아 있다
= 위를 건드리면 아래가 통째로 날아간다. 그래서 안 바뀌는 것을 위에 둔다
```

## ⚙️ 작동 원리

**손으로 잡는 손잡이는 셋이다.** 첫째는 어디까지를 저장할지 정하는 표시다. Anthropic 문서는 자주 바뀌는 정도가 다른 구간을 따로 저장하도록 표시 지점을 최대 네 곳까지 둘 수 있다고 적는다. 표시를 뒤로 밀수록 저장되는 앞부분이 길어지고, 그만큼 그 뒤가 조금만 바뀌어도 다시 읽힐 것이 늘어난다. OpenAI 쪽은 이 표시가 아예 없다 — 길이 조건만 넘으면 자동으로 걸린다.

둘째는 수명이다. Anthropic 문서는 기본 수명을 5분으로 적고, 그것이 짧으면 1시간짜리를 고를 수 있다고 적는다. 대신 1시간짜리는 처음 넣을 때 값이 더 든다. 이 값을 올리면 뜸하게 오는 대화도 살아남고, 대신 한 번 부르고 마는 요청에서는 넣어 둔 값만 나간다. OpenAI 쪽은 고를 것이 없고, 앞자락을 다시 쓸 때마다 수명이 갱신된다.

셋째는 길이다. 두 곳 다 하한이 있다 — 모델마다 다르고, 흔한 값이 천 토큰이다. 그보다 짧으면 **표시를 해 두어도 그냥 캐시 없이 처리되고 오류도 나지 않는다.** 그래서 "표시했는데 왜 그대로지" 가 여기서 자주 나온다. 걸렸는지는 응답의 사용량에서 확인한다. 새로 넣은 양과 꺼내 쓴 양이 따로 세어져 돌아온다.

## 💡 실제 사례

- **긴 지시문을 매번 보내는 상담 도우미** — 규정 문서와 예시가 앞에 그대로 실린다. 두 번째 질문부터는 그 앞부분을 다시 읽지 않는다.
- **도구를 여럿 붙인 에이전트** — 도구 정의는 요청의 맨 앞에 실리고, 한 바퀴 돌 때마다 똑같이 다시 실린다. 표시해 두면 그 몫을 한 번만 낸다.
- **문서 하나를 놓고 여러 번 묻기** — 계약서를 앞에 붙이고 질문만 바꾼다. 계약서는 저장분에서 나오고 질문만 새로 읽힌다.

## 🚫 흔한 오해

- **캐시를 켜면 무조건 싸진다** — 처음 넣을 때는 오히려 값이 더 든다. 수명 안에 다시 안 부르면 손해다. 자주 되풀이되는 앞부분에만 값을 한다.
- **비슷하면 걸린다** — Anthropic 문서는 앞자락이 100% 똑같아야 한다고 적는다. 지시문 맨 앞에 오늘 날짜 한 줄을 넣는 순간 그 뒤가 전부 다시 읽힌다.
- **남이 같은 지시문을 쓰면 내 캐시를 가져다 쓴다** — 아니다. 두 곳 문서 모두 조직이 다르면 프롬프트가 글자 하나까지 똑같아도 저장분을 나눠 쓰지 않는다고 못 박는다. 아끼는 몫은 내가 만든 저장분에서만 나온다.

## 🚨 주의사항

- **바뀌는 것을 앞에 두지 마라.** OpenAI 문서는 지시문과 예시처럼 안 바뀌는 것을 앞에, 사용자마다 다른 것을 뒤에 두라고 적는다. 앞줄의 시각 하나가 뒤 전부를 무효로 만든다.
- **도구 목록을 함부로 흔들지 마라.** 도구 정의가 바뀌면 그 아래가 통째로 무효다. 도구를 하나 늘린 것만으로 절약이 사라진다.
- **짧으면 아무 일도 안 일어난다.** 하한 미만은 조용히 캐시 없이 처리된다. 안 걸린 것을 알려주지 않으므로 사용량을 직접 봐야 한다.

## 📝 정리

**"앞부분을 다시 안 읽게 해 두는 그 표시"** 라고 읽으면 된다. 앞에서부터 한 글자도 안 틀린 만큼만 걸리므로, 안 바뀌는 것을 앞에 몰아 두는 것이 사실상 전부다. 걸렸는지 아닌지는 짐작하지 말고 응답에 딸려 오는 사용량으로 확인한다.

## 🧒 열 살에게

선생님이 매일 같은 책을 펴서 앞쪽 스무 장을 처음부터 다시 읽어 주면 지루하겠지? 그래서 읽은 데까지 책갈피를 꽂아 둬. 다음 시간에는 책갈피 뒤부터만 읽으니까 훨씬 빨리 오늘 이야기에 닿아.

## ❓ 이해했는지

- 지시문 맨 앞줄에 오늘 날짜를 적어 두면 왜 아끼는 것이 없어지나 → 주의사항
- 앞부분은 그대로인데 도구를 하나 늘렸다. 어디까지 다시 읽히나 → 구성
- 표시를 해 뒀는데 값이 그대로 나온다. 무엇을 먼저 의심하나 → 작동 원리

## 🔗 관련 용어

- [[Prompt]] — 캐시가 걸리는 대상 그 자체
- [[Token]] — 새로 넣은 양과 꺼내 쓴 양을 세는 단위
- [[Context Window]] — 앞부분을 길게 붙일수록 이 한도와 같이 봐야 한다
- [[Cache]] — 같은 것을 두 번 계산하지 않는다는 원리의 원형
- [[Agent Memory]] — 이쪽은 수명이 짧고, 저쪽은 대화가 끝나도 남는다
