# Text-to-SQL

## 📝 정의

Text-to-SQL은 **말로 물으면 SQL을 만들어주는 기술**이다.

DB에 있는 것을 보려면 SQL을 써야 하는데, 그걸 쓸 줄 아는 사람은 조직에서 소수다. 질문을 그대로 받아 쿼리로 옮겨주면 그 사이에 있던 사람이 빠진다.

### 비유
말이 안 통하는 손님 대신 주문을 옮겨주는 통역. 말은 통하지만 주방에 무엇이 있는지는 통역이 알고 있어야 한다.

## 🖼️ 그림으로 보기

```도해
흐름: "지난달 매출 얼마야" 가 어떻게 답이 되나
질문 :: 사람이 평소 쓰는 말로 묻는다
스키마 :: 어떤 표에 어떤 칸이 있는지 같이 넘긴다
LLM :: 그 정보를 보고 SQL 문장을 만든다
검사 :: 읽기만 하는 쿼리인지 확인하고 통과시킨다
DB :: 실행해서 행을 돌려준다
< 답 :: 표나 문장으로 바꿔 보여준다
= 사람은 SQL 을 안 쓰지만 DB 가 받는 것은 여전히 SQL 이다
```

## ⚠️ 해결하는 문제

```도해
대조: SQL 을 모르는 사람이 숫자를 보려면 어떻게 되나
사람에게 부탁 || 말로 물어서
걸리는 시간 :: 며칠씩 기다림 || 바로 나온다
질문 바꾸기 :: 다시 부탁한다 || 다시 물으면 끝
개발자 :: 조회 요청에 묶임 || 다른 일을 한다
= 숫자를 궁금해하는 사람과 SQL 을 쓰는 사람을 떼어놓는 것이다
```

"지난달 신규 가입자 몇 명이야" 같은 질문은 매주 나온다. 물어볼 곳이 사람뿐이면 요청이 쌓여 며칠이 걸리고, 답을 받고 나서 조건 하나를 바꾸고 싶으면 처음부터 다시 부탁해야 한다.

Text-to-SQL은 그 왕복을 없앤다. 궁금한 사람이 직접 묻고 바로 다시 물을 수 있으므로, 조건을 바꿔가며 확인하는 일이 사람 손을 거치지 않는다.

## ⚙️ 작동 원리

모델은 DB를 들여다보지 못한다. 질문과 함께 넘겨준 것만 보고 문장을 만든다. 정확한 SQL 이 나오려면 이만큼을 같이 넘겨야 한다.

- **스키마** — 표 이름과 칸 이름, 자료형
- **관계** — 어느 칸이 어느 표와 이어지는지
- **용어** — "매출"이 어느 칸을 뜻하는지 적어둔 것
- **예시 질문** — 이런 질문에는 이런 쿼리라는 견본

모델은 모르는 것을 지어내므로 미리 알려준 만큼만 맞는다. 표 이름이나 칸 이름을 안 알려주면 그럴듯한 이름을 지어내고, 그 쿼리는 실행 단계에서 깨진다.

만들어진 쿼리를 바로 실행하지 않는 것도 중요하다. 읽기 전용 계정으로 돌리고, `DELETE`나 `DROP`, `UPDATE` 같은 것이 섞여 있으면 실행 전에 막는다.

## 💡 실제 사례

- **사내 데이터 조회** — 자주 나오는 질문을 담당자에게 부탁하지 않고 직접 물어본다.
- **읽기 전용 통로** — 조회 권한만 있는 계정으로 실행해서 어떤 쿼리가 나와도 데이터가 바뀌지 않게 한다.
- **쿼리 같이 보여주기** — 결과만 주지 않고 만들어진 SQL을 함께 띄워 무엇을 센 숫자인지 확인하게 한다.

## 🚫 흔한 오해

- **말로 물으면 알아서 찾아준다** — 모델이 아는 것은 넘겨준 스키마뿐이다. 표와 칸 이름, "매출"이 어느 칸인지를 안 알려주면 있을 법한 이름을 지어내 틀린 쿼리를 만든다.
- **결과가 나왔으면 맞는 것이다** — 문법이 맞는 SQL과 의도에 맞는 SQL은 다르다. 조건이 하나 빠져도 쿼리는 잘 돌고 숫자만 틀리게 나온다.
- **읽기만 하는 기능이라 위험하지 않다** — 만들어지는 문장이 항상 읽기라는 보장이 없다. 읽기 전용 계정으로 돌리고 실행 전에 걸러야 그 말이 성립한다.

## 🚨 주의사항

- **스키마를 통째로 넘기지 않는다.** 표가 많으면 넘길 것을 골라야 하고, 민감한 칸은 애초에 안 보이게 한다.
- **결과를 그대로 보고서에 옮기지 않는다.** 어떤 쿼리로 나온 숫자인지 확인하지 않으면 틀린 수를 근거로 결정하게 된다.

## 📝 정리

Text-to-SQL은 질문과 스키마를 받아 SQL을 만들어주는 기술이다. 모델은 알려준 만큼만 알기 때문에 스키마와 용어를 얼마나 잘 넘겨주느냐가 정확도를 정하고, 만들어진 쿼리는 실행 전에 한 번 걸러야 한다.
