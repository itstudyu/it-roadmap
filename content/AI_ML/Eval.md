# Eval (평가)

## 📝 정의

Eval은 **모델의 답을 미리 정한 기준으로 채점하는 시험**이다.

프롬프트를 고치고 "좋아진 것 같다" 로 넘어가면, 무엇이 대신 나빠졌는지는 아무도 모른다. 성공 기준을 숫자로 먼저 적고 그 숫자를 재는 시험지를 만들어 두는 것이 이 자리다. OpenAI 문서가 특히 꼽는 때가 모델을 바꾸거나 새로 써 볼 때다.

### 이름
Evaluation :: 값을 매겨 재기
= Eval 은 Evaluation 을 줄인 말이다. "잘하나" 를 느낌이 아니라 매번 같은 방식으로 잰 값으로 바꾼다

### 비유
정답지를 붙여 둔 받아쓰기 시험지. 고칠 때마다 같은 것을 다시 풀려 몇 개 맞았는지를 센다.

### 예
프롬프트를 한 줄 고치고 예시 서너 개만 눈으로 확인한 뒤 넘어간 적이 있다면, 그 서너 개가 이미 아주 작은 시험지다.

### 직접
쓰는 챗봇에 같은 질문을 다섯 번 넣어 보라. 답이 얼마나 갈리는지가 그 작업의 일관성 점수다.

## 🖼️ 그림으로 보기

```도해
흐름: 고친 프롬프트가 나아졌는지 어떻게 아나
시험 문항 :: 입력과 정답을 짝지어 미리 모아 둔다
모델 :: 문항마다 답을 만든다
채점기 :: 정한 기준으로 답마다 점수를 매긴다
점수 :: 전체 통과율 한 숫자로 모인다
@ 다시 고치기 :: 오르면 남기고 내리면 되돌린다
= 느낌 대신 같은 시험지를 매번 다시 풀려서, 고친 것이 나아졌는지를 숫자로 본다
```

## ⚠️ 해결하는 문제

```도해
대조: 고친 프롬프트를 눈으로만 보면 무엇이 안 보이나
평가 없이 || 평가로
판단 근거 :: 예시 서너 개 || 문항 수백 개
고친 뒤 :: 깨진 걸 모른다 || 내려간 게 뜬다
모델 교체 :: 감으로 정한다 || 같은 시험 재실행
= 좋아진 느낌과 실제로 좋아진 것을 가르는 자리다
```

프롬프트 한 줄을 고치면 좋아지는 항목과 나빠지는 항목이 같이 생긴다. 눈으로 보는 예시는 대개 잘 되는 쪽만 몇 개라, 나빠진 쪽은 배포한 뒤에야 사용자가 발견한다.

성공 기준을 먼저 못 박으면 이 사각지대가 줄어든다. "안전한 답" 이 아니라 "만 번 중 걸리는 것이 0.1% 미만" 처럼 적어 두면, 다음에 고쳤을 때 그 숫자가 올랐는지 내렸는지가 바로 보인다. 애매한 주제도 이렇게 숫자로 옮길 수 있다는 것이 Anthropic 문서가 드는 예다.

## ⚙️ 작동 원리

```도해
층: 채점을 누구에게 맡길수록 무엇이 달라지나
글자 맞추기 :: 정답이 하나면 여기서 끝난다. 가장 싸고 안 흔들린다
코드 채점 :: 형식·범위·금지어처럼 규칙으로 적히는 것
다른 모델 :: 말투나 공감처럼 규칙으로 못 적는 것을 1에서 5로 매긴다
사람 채점 :: 가장 정확하지만 문항 수가 곧 사람 시간이다
= 아래로 갈수록 잴 수 있는 것이 넓어지고, 값과 흔들림이 같이 커진다
```

손잡이가 셋이다. 첫째는 문항 수다. 문항을 늘리면 한 문항이 우연히 맞고 틀리는 흔들림이 묻히고, 어제 점수와 오늘 점수의 차이를 믿을 수 있게 된다. Anthropic 문서는 손으로 정성껏 채점한 적은 문항보다 신호가 조금 흐려도 자동 채점한 많은 문항이 낫다고 적는다.

둘째는 채점기 종류다. 분류처럼 정답이 딱 떨어지면 글자 맞추기로 충분하고, 같은 질문을 다르게 물었을 때 답이 비슷한지는 문장을 벡터(뜻을 담은 숫자 목록)로 바꿔 각도를 재고, 말투나 공감처럼 규칙으로 못 적는 것은 다른 모델에게 1에서 5로 매기게 한다. 채점기를 아래로 내릴수록 잴 수 있는 것이 넓어지고 값과 흔들림이 함께 커진다.

셋째는 어려운 문항의 비율이다. 문서가 첫 원칙으로 드는 것이 실제로 들어오는 입력을 그대로 본뜨라는 것이고, 반어법·아주 긴 입력·사람도 판단이 갈리는 것 같은 가장자리를 일부러 섞어 두라고 적는다. 쉬운 문항만 모으면 통과율은 오르는데 배포하면 그대로 깨진다.

## 📊 비교: 재는 방식 세 갈래

| 갈래 | 무엇을 보나 | 언제 쓰나 |
|---|---|---|
| **metric** | 대개 정답과 견줘 성능을 잰다 | 시험지에 정답이 붙어 있을 때 |
| **comparison** | 두 모델 이상의 답이 갈리는지를 잰다 | 어느 쪽을 쓸지 정할 때 |
| **measurement** | 데이터와 모델 예측 자체를 들여다본다 | 시험지가 한쪽으로 쏠렸는지 볼 때 |

순위표 점수 하나만 보면 둘째와 셋째가 통째로 빠진다. 같은 점수라도 두 모델이 틀리는 문항이 다르면 고르는 이유가 달라진다.

## 💡 실제 사례

- **모델 교체 전후** — 같은 시험지를 새 모델에 한 번 더 돌려 어떤 항목이 내려갔는지 본다.
- **프롬프트 손보기** — 한 줄 고칠 때마다 통과율을 재고, 내려가면 되돌린다.
- **여러 잣대로 한꺼번에** — 정확도만이 아니라 응답 시간·비용·위험 문구 비율을 같은 표에 놓고 본다.

## 🚫 흔한 오해

- **점수가 높으면 잘 되고 있는 것이다** — 시험지가 실제 들어오는 입력과 다르면 점수만 오른다. 첫 원칙이 실제 분포를 그대로 본뜨라는 것인 이유다.
- **채점은 다른 모델에게 맡기는 게 제일 낫다** — 말투처럼 규칙으로 못 적는 것에는 맞지만, 정답이 딱 떨어지는 분류에는 글자 맞추기가 더 싸고 덜 흔들린다.
- **사람이 직접 채점해야 믿을 만하다** — 문서는 반대로 적는다. 신호가 조금 흐려도 자동 채점으로 문항 수를 늘리는 쪽을 먼저 하라는 것이다.

## 📝 정리

**"고친 것이 나아졌는지 재는 같은 시험지"** 라고 읽으면 된다. 성공 기준을 숫자로 먼저 적고, 실제 입력을 본뜬 문항을 모으고, 채점을 되도록 자동으로 돌린다. 모델을 바꾸거나 올릴 때 이 시험지가 없으면 나빠진 자리를 사용자가 먼저 발견한다.

## 🧒 열 살에게

공부하는 방법을 바꿨을 때 진짜 나아졌는지 어떻게 알아? 똑같은 문제지를 다시 풀어 보고 몇 개 더 맞았는지 세면 되지. 그래서 방법을 바꿀 때마다 그 문제지를 꺼내는 거야.

## ❓ 이해했는지

- 예시 서너 개만 눈으로 보고 넘어가면 무엇을 놓치나 → 해결하는 문제
- 문항을 늘리는 쪽과 한 문항을 정성껏 채점하는 쪽 중 무엇을 먼저 하나 → 작동 원리
- 정답이 딱 떨어지는 분류에 다른 모델을 채점기로 세우면 무엇이 손해인가 → 흔한 오해
