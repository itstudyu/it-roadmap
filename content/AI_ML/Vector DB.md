# Vector DB (벡터 데이터베이스)

## 📝 정의

Vector DB는 **벡터를 저장하고 가까운 것을 빠르게 찾아주는 저장소**다.

임베딩으로 만든 숫자 목록을 수백만 개 넣어두고, 질문 벡터가 들어오면 그와 가장 가까운 것들을 골라준다. 일반 데이터베이스가 값이 같은 것을 찾는다면 이쪽은 값이 비슷한 것을 찾는다.

### 비유
도서관의 주제별 배가. 제목이 정확히 기억나지 않아도 관련 서가로 가면 비슷한 책들이 모여 있다. 청구기호가 정확히 일치해야 찾을 수 있는 방식과 다르다.

### 예
쇼핑 앱에서 물건 사진을 찍어 올리면 비슷하게 생긴 상품들이 줄줄이 뜨는 그 검색이다.

## 🖼️ 그림으로 보기

```도해
흐름: 백만 개 중에서 가까운 셋을 어떻게 찾나
질문 :: 벡터 하나가 들어온다
색인 :: 미리 만들어둔 이웃 지도를 탄다
색인 :: 가까운 후보 구역으로 건너뛴다
색인 :: 그 안에서만 실제 거리를 잰다
< 결과 :: 가장 가까운 셋을 돌려준다
= 백만 개를 다 재지 않는 대신 정확도를 조금 내주는 거래다
```

## ⚠️ 해결하는 문제

```도해
대조: 백만 개 벡터에서 가까운 것을 어떻게 찾나
일반 DB |=| 벡터 DB
검색 방식 :: 전부 하나씩 계산 || 색인으로 건너뛴다
소요 시간 :: 수 초 || 수십 밀리초
정확도 :: 완벽 || 거의 정확
= 전부 재는 대신 대부분 맞는 답을 훨씬 빨리 주는 쪽을 고른 것이다
```

벡터 검색은 원래 무거운 작업이다. 백만 개가 있으면 백만 번 거리를 계산해야 한다. 관계형 데이터베이스에 벡터를 넣고 매번 전부 계산하면 검색 하나에 수 초가 걸린다.

벡터 DB는 이웃 관계를 미리 지도로 만들어둔다. 검색할 때 그 지도를 따라 후보 구역까지 건너뛰고 그 안에서만 실제로 계산한다. 완벽한 답을 포기하는 대신 속도를 얻는 방식이라 근사 최근접 이웃 검색이라고 부른다.

## 🧱 구성

```도해
층: 벡터 DB 안에는 무엇이 쌓여 있나
색인 :: 이웃 지도. 어디부터 뒤질지 정한다
벡터 :: 뜻을 숫자로 바꿔 놓은 목록
원본 조각 :: 검색에 걸렸을 때 실제로 꺼내 주는 글
= 색인은 벡터 위에 얹혀 있고, 벡터는 원본 조각을 가리키는 표일 뿐이다
```

## ⚙️ 작동 원리

```도해
흐름: 넣어둔 문서가 골라져 나오기까지 무엇을 거치나
임베딩 :: 문서를 벡터로 만든다
색인 :: 이웃 관계를 미리 계산해 지도를 만든다
검색 :: 질문이 오면 지도를 타고 후보를 좁힌다
필터 :: 부서나 권한 같은 조건으로 거른다
= 색인을 만드는 시간이 들지만 그 뒤로는 검색이 싸진다
```

메타데이터 필터가 실무에서 중요하다. 벡터로 가까운 것을 찾되 "이 사용자가 볼 수 있는 문서"로 한정하지 않으면 권한 없는 내용이 검색된다.

## 💡 실제 사례

- **RAG 저장소** — 사내 문서를 조각내 넣어두고 질문과 가까운 조각을 꺼낸다.
- **이미지 검색** — 사진을 벡터로 넣어두면 비슷한 사진을 찾을 수 있다.
- **중복 문의 묶기** — 표현이 다른 같은 문의를 벡터 거리로 묶어 한 번에 처리한다.

## 🚫 흔한 오해

- **벡터 DB가 항상 정확한 답을 준다** — 근사 검색이라 가장 가까운 것을 놓칠 수 있다. 정확도와 속도를 설정으로 조절한다.
- **일반 데이터베이스를 대체한다** — 대체하지 않는다. 주문 내역처럼 정확히 일치하는 조회는 여전히 관계형이 맞다.
- **넣기만 하면 검색이 좋아진다** — 검색 품질은 임베딩 모델과 문서를 어떻게 잘랐는지가 정한다. 저장소는 빠르게 찾아줄 뿐이다.

## 🚨 주의사항

- **권한 필터를 벡터 검색에 같이 건다.** 나중에 거르면 이미 본 문서가 나간 뒤다.
- **모델을 바꾸면 전부 다시 넣어야 한다.** 좌표계가 달라져서 옛 벡터와 새 벡터를 비교할 수 없다.

## 📝 정리

Vector DB는 벡터를 저장하고 가까운 것을 빠르게 찾아주는 저장소다. 완벽한 답 대신 속도를 택한 구조이고, 검색 품질 자체는 임베딩과 문서 자르기가 정한다.
