# Vector DB (벡터 데이터베이스)

## 📝 정의

Vector DB는 **Embedding 벡터를 저장하고 의미로 검색하는 특수 데이터베이스**입니다. 마치 똑똑한 도서관 사서처럼, 정확한 제목을 몰라도 "의미"만으로 관련 문서를 찾아줍니다.

### 핵심 개념

- **무엇인가?**: 고차원 벡터(768차원)를 저장하고 유사도로 검색하는 DB
- **왜 필요한가?**: 수백만 개의 벡터에서 0.01초 안에 비슷한 의미 찾기
- **어떻게 작동하나?**: ANN (근사 최근접 이웃) 알고리즘으로 빠른 검색

## 🤔 왜 Vector DB가 필요한가?

### 일반 DB의 한계

**문제 1: 유사도 검색 불가능**
```
PostgreSQL 같은 일반 DB:
SELECT * FROM documents
WHERE title = '육아휴직'  ✅ 정확한 매칭만 가능

SELECT * FROM documents
WHERE title 의미가_비슷한 '아이 키우기'  ❌ 불가능!

→ 정확한 단어만 찾음, 의미 검색 안 됨
```

**문제 2: 벡터 검색이 너무 느림**
```
100만 개 문서에서 유사 벡터 찾기:

일반 DB (전체 스캔):
→ 모든 벡터와 하나씩 비교
→ 100만 번 계산
→ 10초 이상 ❌

필요한 속도:
→ 0.1초 이내
→ 실시간 검색
```

**문제 3: 메모리 낭비**
```
100만 문서 × 768차원 = 7억 개 숫자
→ 약 3GB 메모리 필요
→ 전부 메모리에 로드 불가능
```

### Vector DB의 해결

```
핵심: 똑똑한 인덱싱 (ANN)

전체 스캔 X
→ "대충 비슷한" 벡터만 확인 (ANN)
→ 정확도 95% + 속도 1000배 ✅

100만 개 벡터에서 검색:
→ 0.01초 (초고속) ✅
→ 메모리 효율적 (압축 저장) ✅
→ 수평 확장 가능 (수억 개까지) ✅
```

## 📊 작동 원리

### ANN (Approximate Nearest Neighbor)


### 전체 스캔 vs ANN

```
전체 스캔 (일반 DB):
100만 개 전부 확인
→ 1,000,000번 계산
→ 10초 ❌

ANN (Vector DB):
1. 클러스터링으로 1,000개 후보 선택
2. 1,000개만 정확히 계산
→ 1,000번 계산 (1000배 빠름)
→ 0.01초 ✅
→ 정확도: 95% (충분히 높음)
```

## 💡 일상적 비유로 이해하기

### Vector DB = 똑똑한 도서관 사서

**일반 DB (카드 목록)**:
```
사용자: "육아휴직 책 있어요?"
사서: [카드 목록 뒤적] "육아휴직" 제목 검색
→ 정확히 "육아휴직"이라는 제목만 찾음
→ "양육휴가"라는 비슷한 책은 못 찾음 ❌
```

**Vector DB (의미 기반 도서관)**:
```
사용자: "아이 키우기 위한 휴가 책 있어요?"
사서: "아, 육아휴직 관련이시군요!"
→ 의미를 이해하고 관련 책 모두 찾아줌
→ "육아휴직", "양육휴가", "출산휴가" 모두 추천 ✅

게다가 100만 권 중에서도 0.01초 만에 찾아줌!
```

### RAG 파이프라인의 핵심

```도해
흐름: Vector DB, 무슨 순서로 오가나

사용자 :: 육아휴직은 몇 년?

Chatbot :: 유사 문서 검색
Vector DB :: Top-3 (0.01초)
Chatbot :: 질문 + 문서 전달
LLM :: 제32조에 따르면 2년...
```

### P3의 Vector DB 선택

```
개발 환경: ChromaDB
→ 무료, 로컬 실행
→ 설치 쉬움 (pip install chromadb)
→ 1만 개 문서까지 충분

프로덕션: Pinecone
→ 관리형 서비스 (Managed)
→ 속도 빠름 (0.01초)
→ 자동 스케일링
→ 비용: $70/월

대안: Elasticsearch
→ 키워드 + 벡터 검색 (Hybrid)
→ 기존 시스템과 통합 쉬움
→ 비용: $50~200/월
```

### P3 실제 사례

```
취업규칙: 10,000개 조항 저장

검색 예시:
"아이 키우려고 쉬고 싶은데요"

Vector DB 검색 결과 (0.01초):
1. 제32조 (육아휴직) - 유사도 0.89 ✅
2. 제30조 (연차휴가) - 유사도 0.43
3. 제31조 (병가) - 유사도 0.38

→ Top-3를 LLM에 전달
→ LLM이 제32조 기반으로 답변 생성
```

## 🚀 Vector DB 최적화

### 1. 인덱스 알고리즘 선택

```
Flat (전체 스캔):
→ 정확도: 100%
→ 속도: 느림
→ 사용: < 1만 벡터

IVF (클러스터 기반):
→ 정확도: 95%
→ 속도: 빠름
→ 사용: 1만~100만 벡터

HNSW (그래프 기반):
→ 정확도: 98%
→ 속도: 매우 빠름
→ 메모리: 많음
→ 사용: 고속 검색 필요

P3 권장: HNSW
→ 속도 중요, 메모리 충분
```

### 2. 메타데이터 필터링

```
문제: 여러 회사 문서 섞여있을 때

해결: 메타데이터로 필터링
→ "A회사" 문서만 검색
→ "B회사" 문서는 제외

예시:
질문: "육아휴직은?"
필터: company="A회사"

→ A회사 문서만 검색
→ B회사 규정은 안 나옴
```

### 3. 캐싱

```
같은 질문 반복:
→ Vector DB 검색 생략
→ 캐시에서 바로 가져오기

속도: 0.01초 → 0.0001초 (100배)
비용: 70% 절감
```

## 🚨 주의사항

### 1. 차원 수 일치 필수

```
Vector DB 생성 시: 768차원 지정
→ 이후 모든 벡터는 768차원이어야 함

다른 차원 벡터 삽입 시:
→ 에러 발생! ❌

해결:
→ 항상 같은 Embedding 모델 사용
→ ko-sroberta: 768차원
→ OpenAI 3-small: 1536차원
```

### 2. ANN은 근사치

```
ANN = Approximate (대략)
→ 정확도 95~98%
→ 2~5%는 놓칠 수 있음

대부분의 경우 문제없음:
→ Top-10 중 1개 정도만 달라짐
→ RAG 검색에는 충분히 정확

완벽한 검색 필요 시:
→ Flat 인덱스 사용 (느리지만 100% 정확)
```

### 3. 비용 관리

```
Pinecone 비용:
→ 벡터 개수 + 쿼리 수
→ 100만 벡터: $70/월
→ 쿼리는 무제한

절감 방법:
1. ChromaDB 로컬 사용 (개발)
2. 캐싱으로 쿼리 줄이기
3. 불필요한 벡터 삭제
```

## 📝 정리

**Vector DB 핵심 3줄**:
```
1. Embedding 벡터를 저장하고 의미로 검색
2. 수백만 개 중에서 0.01초 안에 검색 (ANN)
3. RAG의 필수 인프라 = 똑똑한 도서관 사서

→ Vector DB 없으면 RAG 불가능!
```

**비유로 기억하기**:
```
일반 DB = 도서관 카드 목록
→ "육아휴직" 제목으로만 검색
→ 정확한 단어 필요

Vector DB = 똑똑한 사서
→ "아이 키우기" 의미로 검색
→ "육아휴직" 관련 모두 찾아줌
→ 100만 권 중에서도 0.01초!
```

**Vector DB 공식**:
```
Embedding + 빠른 검색 = Vector DB

일반 DB:
→ 정확한 매칭 (=)
→ WHERE title = '육아휴직'

Vector DB:
→ 유사도 검색 (≈)
→ WHERE 의미_비슷함('아이 키우기')
→ Cosine Similarity > 0.7
```

**P3 시스템 선택**:
```
개발: ChromaDB (무료, 로컬, 쉬움)
프로덕션: Pinecone (빠름, Managed)

선택 기준:
- < 1만 문서: ChromaDB
- 1만~100만: Pinecone
- Hybrid 필요: Elasticsearch
- 대규모: Milvus

핵심 = RAG의 성능은 Vector DB가 결정!
```

**RAG 파이프라인**:
```
1. 문서 Embedding → Vector DB 저장 (준비)
2. 질문 Embedding → 유사 문서 검색 (0.01초)
3. Top-3 문서 → LLM 전달
4. 정확한 답변 생성

Vector DB가 빠를수록:
→ 사용자 응답 속도 빠름
→ 더 많은 문서 검색 가능
→ RAG 품질 향상
```
