# UDP (User Datagram Protocol)

## 📝 정의

UDP는 인터넷 프로토콜 스위트의 전송 계층 프로토콜로, 두 컴퓨터 간에 빠르게 데이터를 보내기 위한 비연결 프로토콜입니다. TCP와 달리 사전 연결 설정이 없으며, 받는 쪽이 준비되었는지 확인하지 않고 바로 데이터를 보냅니다. UDP는 패킷 손실이나 순서 뒤바뀜을 처리하지 않으므로, 신뢰성보다 속도를 우선시하는 애플리케이션에 적합합니다.

UDP의 가장 큰 장점은 간단한 구조와 빠른 속도입니다. 연결 설정과 종료의 오버헤드가 없고, 각 패킷(데이터그램)을 독립적으로 처리하므로 지연이 최소화됩니다. 또한 UDP는 브로드캐스트와 멀티캐스트를 지원하므로, 한 송신자가 여러 수신자에게 동시에 데이터를 보낼 수 있습니다. 이러한 특성으로 인해 실시간 스트리밍, 온라인 게임, VoIP 등에서 선호됩니다.

> **한 줄 요약**: 신뢰성을 포기하고 속도를 극대화한 빠르고 경량의 비연결형 통신 프로토콜

> **비유**: 🔵일방적 방송 - 시청자가 준비되었는지 확인하지 않고 방송을 송출하는 것처럼, 수신자의 상태를 확인하지 않고 데이터를 보냄 / 🟡편지 없는 택배 - 택배 기사가 수신자 확인 없이 물품을 놓고 가듯이, 도착 확인 없이 빠르게 데이터를 전송함

## 🎯 핵심 개념

### 1. 비연결형 통신 (Connectionless)
UDP는 통신 전에 연결 설정 과정이 없습니다. 클라이언트가 언제든지 데이터를 보낼 수 있으며, 수신자가 준비되었는지 확인할 필요가 없습니다. 이로 인해 3-way handshake와 같은 연결 설정 오버헤드가 전혀 없으므로 매우 빠릅니다. 각 데이터그램은 독립적으로 처리되며, 송신자와 수신자 간의 상태 정보를 유지할 필요가 없습니다.

### 2. 손실 허용 (Loss Tolerance)
UDP는 패킷이 손실되어도 재전송하지 않습니다. 송신자는 패킷을 보낸 후 응답을 기다리지 않으므로, 패킷이 도착했는지 확인할 수 없습니다. 네트워크 혼잡이나 라우터 오류로 인해 패킷이 버려질 수 있지만, UDP는 이를 처리하지 않습니다. 따라서 일부 데이터 손실이 허용되는 실시간 애플리케이션에 적합합니다.

### 3. 순서 미보장 (No Ordering Guarantee)
UDP는 여러 패킷을 보낼 때 도착 순서를 보장하지 않습니다. 다양한 네트워크 경로를 통해 전송된 패킷들이 다른 순서로 도착할 수 있습니다. 애플리케이션이 패킷 순서를 보장해야 한다면, 애플리케이션 계층에서 순서 정렬을 처리해야 합니다. UDP는 각 데이터그램을 독립적으로 취급하므로 순서 추적 메커니즘이 없습니다.

### 4. 브로드캐스트/멀티캐스트 지원
UDP는 한 송신자가 여러 수신자에게 동시에 데이터를 보낼 수 있습니다. 브로드캐스트는 로컬 네트워크의 모든 호스트에 데이터를 보내고, 멀티캐스트는 특정 그룹에 속한 호스트들에게만 데이터를 보냅니다. TCP는 일대일 연결만 가능하지만, UDP의 이러한 능력은 네트워크 효율성을 크게 높입니다.

### 5. 최소한의 오버헤드
UDP의 헤더는 단 8바이트로 매우 간단합니다. TCP의 20-60바이트 헤더와 비교하면 훨씬 작습니다. 또한 연결 상태 관리, 버퍼 관리, 흐름 제어 등의 복잡한 메커니즘이 없으므로, 구현이 간단하고 시스템 자원 사용량이 적습니다. 이러한 특성으로 인해 UDP는 낮은 지연 시간을 제공합니다.

## ⚠️ 해결하는 문제

### 문제 1: 높은 지연 시간
TCP의 연결 설정, 흐름 제어, 패킷 재전송 등으로 인해 지연이 발생합니다. UDP는 이러한 모든 과정을 생략하므로 매우 빠릅니다. 특히 실시간 애플리케이션에서는 몇 밀리초의 지연도 문제가 될 수 있는데, UDP는 이를 해결합니다. 온라인 게임에서 플레이어의 움직임이 즉시 반영되려면 UDP의 낮은 지연 시간이 필수적입니다.

### 문제 2: 네트워크 혼잡 시 적응성
TCP는 네트워크 혼잡을 감지하면 자동으로 송신 속도를 줄입니다. 이는 신뢰성을 높이지만 지연을 증가시킵니다. UDP는 네트워크 상태에 관계없이 일정한 속도로 데이터를 보내므로, 실시간 스트리밍처럼 일정한 비트레이트가 필요한 애플리케이션에 적합합니다. 애플리케이션이 필요에 따라 품질을 조절할 수 있습니다.

### 문제 3: 일대다 통신의 비효율성
TCP는 일대일 연결만 지원하므로, 한 서버에서 많은 클라이언트에게 같은 데이터를 보내려면 각 클라이언트마다 별도의 연결을 만들어야 합니다. UDP의 브로드캐스트와 멀티캐스트는 한 번의 전송으로 여러 수신자에게 데이터를 보낼 수 있습니다. 이는 네트워크 대역폭을 효율적으로 사용하며, 특히 라이브 스트리밍이나 네트워크 게임 등에서 큰 이점이 됩니다.

### 문제 4: 가벼운 프로토콜의 필요성
제한된 리소스를 가진 장치(임베디드 시스템, IoT 기기, 휴대폰)에서는 TCP의 복잡한 상태 관리가 부담이 될 수 있습니다. UDP는 최소한의 오버헤드로 작동하므로, 저전력 장치에서도 효율적으로 통신할 수 있습니다. 또한 DNS, SNMP 등 간단한 요청-응답 패턴의 프로토콜도 UDP를 기반으로 설계됩니다.

## ⚙️ 작동 원리

UDP의 작동은 매우 간단합니다. 애플리케이션이 전송할 데이터를 UDP에 제공하면, UDP는 최소한의 헤더 정보(출발지 포트, 목적지 포트, 길이, 체크섬)를 붙여 IP 계층에 전달합니다. IP 계층은 이를 물리 계층을 통해 네트워크로 보냅니다. UDP는 패킷이 정확히 도착했는지 확인하지 않으므로, 송신 작업은 매우 빠르게 완료됩니다.

수신자 쪽에서는 네트워크로부터 UDP 데이터그램이 도착하면, UDP 헤더의 포트 번호를 확인하여 해당하는 애플리케이션에 데이터를 전달합니다. 체크섬 검증에 실패하면 데이터그램을 조용히 버립니다(silent drop). UDP는 송신자에게 이를 알리지 않으며, 애플리케이션도 자신의 데이터가 도착했는지 알 수 없습니다.

만약 애플리케이션이 수신자의 응답이 필요하다면, 애플리케이션 계층에서 별도의 확인 메커니즘을 구현해야 합니다. 예를 들어, DNS 클라이언트는 서버로부터 응답을 받지 못하면 일정 시간 후에 요청을 다시 보냅니다. UDP 자체는 이를 처리하지 않습니다.

UDP의 또 다른 특징은 각 애플리케이션이 독립적으로 작동한다는 것입니다. 한 애플리케이션의 문제가 다른 애플리케이션에 영향을 주지 않습니다. 또한 UDP는 흐름 제어나 혼잡 제어를 수행하지 않으므로, 애플리케이션이 네트워크 상황에 따라 전송 속도를 자체적으로 관리해야 합니다.

## 📊 비교

| 항목 | UDP | TCP |
|------|-----|-----|
| **연결 방식** | 비연결형 (Connectionless) | 연결 지향 (Connection-oriented) |
| **신뢰성** | 낮음 (손실 허용) | 높음 (모든 패킷 보장) |
| **속도** | 빠름 (오버헤드 적음) | 느림 (오버헤드 많음) |
| **순서 보장** | 아니오 (순서 미보장) | 예 (일련번호 사용) |
| **흐름 제어** | 없음 | 있음 (윈도우 기반) |
| **혼잡 제어** | 없음 | 있음 (속도 조절) |
| **일대다 통신** | 가능 (브로드캐스트/멀티캐스트) | 불가능 (일대일만) |
| **사용 예** | 게임, 스트리밍, DNS, VoIP | HTTP, 이메일, FTP, SSH |

## ✅ 장단점

### 장점
- **빠른 속도**: 연결 설정과 상태 관리 오버헤드가 없어 TCP보다 훨씬 빠릅니다.
- **낮은 지연 시간**: 최소한의 처리로 인해 지연이 최소화되므로 실시간 애플리케이션에 적합합니다.
- **간단한 구현**: 프로토콜의 구조가 간단하므로 구현과 디버깅이 쉽습니다.
- **효율적인 브로드캐스트/멀티캐스트**: 한 번의 전송으로 여러 수신자에게 데이터를 보낼 수 있습니다.
- **리소스 효율성**: 상태 관리와 버퍼링이 최소한이므로 시스템 자원을 적게 사용합니다.
- **일정한 비트레이트**: 흐름 제어와 혼잡 제어가 없어 일정한 속도로 데이터를 보낼 수 있습니다.

### 단점
- **신뢰성 부족**: 패킷 손실이 발생해도 재전송하지 않으므로 데이터 손실이 가능합니다.
- **순서 미보장**: 패킷이 순서대로 도착하지 않을 수 있으므로 애플리케이션에서 순서 정렬을 처리해야 합니다.
- **애플리케이션의 책임 증가**: 신뢰성과 순서 보장을 원한다면 애플리케이션에서 구현해야 합니다.
- **혼잡 제어 부재**: 네트워크 혼잡에 대응하지 않으므로 과도한 트래픽을 발생시킬 수 있습니다.
- **받는 쪽 상태 불명**: 수신자가 준비되었는지 확인할 수 없으므로 예상치 못한 동작이 발생할 수 있습니다.
- **디버깅의 어려움**: 패킷 손실이 간헐적으로 발생할 수 있어 재현하기 어렵습니다.

## 💡 실제 사례

실시간 영상 통화(Zoom, Skype, Google Meet)는 UDP를 주로 사용합니다. 비디오 통화에서 완벽한 품질의 모든 프레임을 수신하는 것보다 낮은 지연 시간으로 실시간 상호작용이 가능한 것이 더 중요합니다. 일부 프레임이 손실되어도 시청자는 자연스러운 대화를 유지할 수 있습니다.

온라인 게임(League of Legends, Fortnite, Counter-Strike 등)도 UDP를 사용합니다. 플레이어의 위치, 움직임, 행동이 즉시 다른 플레이어들에게 반영되어야 하므로 낮은 지연 시간이 필수적입니다. 일부 업데이트가 손실되어도 다음 업데이트로 보정되므로 문제가 되지 않습니다.

DNS(Domain Name System) 조회도 UDP를 사용합니다. 클라이언트가 DNS 서버에 도메인명을 물으면, 서버는 IP 주소를 응답합니다. 단순한 요청-응답 패턴이므로 UDP의 빠른 속도가 유리합니다. 응답이 없으면 클라이언트가 다시 요청합니다.

스트리밍 서비스(YouTube, Netflix, 라이브 방송)는 UDP 기반의 RTP(Realtime Transport Protocol)를 사용합니다. 실시간으로 수백만 명에게 같은 콘텐츠를 보낼 때, 멀티캐스트를 지원하는 UDP의 효율성이 중요합니다. 또한 네트워크 대역폭이 부족할 때 일부 프레임을 건너뛰어 스트리밍을 계속할 수 있습니다.

## 🔗 관련 용어

- **TCP**: UDP와 비교되는 프로토콜로, 신뢰성은 높지만 느림
- **IP**: UDP가 동작하는 기반이 되는 네트워크 계층 프로토콜
- **OSI 7계층**: UDP는 전송 계층(4계층)에 위치
- **포트(Port)**: UDP에서 애플리케이션을 구분하기 위해 사용
- **데이터그램(Datagram)**: UDP의 데이터 단위
- **RTP**: UDP 위에서 작동하는 실시간 통신 프로토콜
- **DNS**: UDP를 사용하는 대표적인 프로토콜
