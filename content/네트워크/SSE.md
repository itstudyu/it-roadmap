# SSE (Server-Sent Events)

## 📝 정의

SSE는 **서버가 클라이언트로 계속 밀어 보내는 단방향 연결**이다.

브라우저가 연결을 한 번 열어두면 서버는 그 연결을 끊지 않고 잡고 있다가, 보낼 것이 생길 때마다 그리로 내보낸다. 보통의 HTTP 요청이 응답 하나를 주고 끝나는 것과 다른 지점이 여기다.

### 비유
라디오. 주파수를 한 번 맞춰두면 방송국이 보낼 때마다 들리고, 듣는 쪽에서 말을 걸 수는 없다.

### 예
새로고침하지 않았는데 알림 숫자가 혼자 늘어나는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 알림 하나가 화면에 뜨기까지 무엇을 거치나
브라우저 :: /events 로 연결을 한 번 연다
서버 :: 응답을 끝내지 않고 연결을 잡아둔다
서버 :: 보낼 것이 생기면 그 연결로 내보낸다
브라우저 :: 받은 것을 이벤트로 처리한다
@ 브라우저 :: 끊기면 알아서 다시 연결해 이어받는다
= 물어보러 가는 대신 열어두고 기다리는 방식이다
```

## ⚠️ 해결하는 문제

```도해
대조: 새 알림이 있는지 계속 물어보면 어떻게 되나
폴링으로 || SSE 로
요청 수 :: 주기마다 계속 || 연결 한 번
알림 지연 :: 다음 주기까지 || 생기면 바로
응답 내용 :: 대부분 빈손 || 있을 때만 옴
= 물어보는 쪽에서 보내는 쪽으로 주도권을 옮긴 것이다
```

새 알림이 있는지 몇 초마다 물어보는 방식은 알림이 없을 때도 요청을 만든다. 사용자가 늘어나면 대부분 빈손으로 돌아오는 요청이 초당 수백 개씩 쌓인다.

동시에 알림은 늦게 도착한다. 알림이 생긴 시점과 다음 질문 사이의 간격만큼 밀리기 때문이다. 주기를 줄이면 지연은 줄지만 요청 수는 그만큼 늘어난다. SSE는 연결을 열어두는 것으로 이 맞바꿈에서 빠져나온다.

## ⚙️ 작동 원리

브라우저는 평범한 GET 요청을 보내되 이벤트 스트림을 받겠다고 알린다. 서버는 `Content-Type: text/event-stream`으로 답하고 응답을 끝내지 않는다. 그 뒤로는 정해진 형식의 줄을 써 보내면 브라우저 쪽에서 이벤트로 뜬다.

```
event: notification
id: 42
data: {"message": "새 알림"}

: 이 줄은 주석이다. 살아 있다고 알리는 데 쓴다
```

`event`는 이벤트 종류라서 종류별로 다른 처리를 붙일 수 있고, `id`는 마지막으로 받은 지점을 표시한다. 연결이 끊기면 브라우저가 알아서 다시 열고, 이때 마지막 `id`를 함께 보낸다. 서버는 그 뒤부터 이어 보내면 되므로 끊긴 사이의 이벤트를 흘리지 않는다.

오래 조용하면 중간 장비가 연결을 정리해버린다. 그래서 보낼 게 없어도 주기적으로 주석 한 줄을 흘려보내 연결을 유지한다.

## 📊 비교: SSE와 WebSocket과 폴링

| | SSE | WebSocket | 폴링 |
|---|---|---|---|
| 방향 | 서버에서 클라이언트로 | 양쪽 | 클라이언트가 물어봄 |
| 바탕 | HTTP | 별도 프로토콜 | HTTP |
| 재연결 | 브라우저가 자동으로 | 직접 만들어야 | 다음 요청이 곧 재시도 |
| 서버 부하 | 낮다 | 낮다 | 높다 |
| 어울리는 곳 | 알림, 피드, 로그 | 채팅, 게임 | 가끔 확인하면 되는 것 |

## 💡 실제 사례

- **알림 배지** — 새 알림이 생기는 순간 숫자가 바뀐다. 안 생기면 아무것도 오가지 않는다.
- **대시보드** — 값이 바뀔 때만 서버가 내보내서 열려 있는 화면들이 같은 시점으로 맞춰진다.
- **로그 보기** — 서버 로그가 쌓이는 대로 브라우저 화면에 이어 붙는다.

## 🚫 흔한 오해

- **SSE 로 클라이언트도 서버에 보낼 수 있다** — 보낼 수 없다. 보낼 일이 있으면 평범한 HTTP 요청을 따로 보내야 하고, 그래서 채팅처럼 양쪽이 오가는 데는 잘 안 맞는다.
- **연결이 끊기면 직접 다시 열어야 한다** — 브라우저가 알아서 다시 연다. 마지막으로 받은 번호까지 같이 보내주므로 서버는 그 뒤부터 이어 보내면 된다.
- **SSE 는 WebSocket 이 나오기 전의 방식이다** — 세대가 아니라 방향이 다르다. 한쪽으로만 흐르면 SSE가 간단하고, 양쪽이 오가야 하면 WebSocket이다.

## 🚨 주의사항

- **한 도메인에 열 수 있는 연결 수에 한계가 있다.** 화면마다 스트림을 따로 열면 나중에 연 것이 막힌다. 하나로 합치고 이벤트 종류로 나누는 편이 낫다.
- **연결을 잡아둔다는 것은 서버 쪽 자원도 잡아둔다는 뜻이다.** 화면을 닫거나 탭이 뒤로 갔을 때 정리하지 않으면 죽은 연결이 쌓인다.

## 📝 정리

SSE는 서버가 열린 HTTP 연결로 데이터를 계속 내보내는 단방향 방식이다. 재연결과 이어받기를 브라우저가 맡아주기 때문에 직접 만들 것이 적다. 클라이언트에서 보낼 길은 없으므로 오가는 통신이 필요하면 다른 것을 써야 한다.

## ❓ 이해했는지

- 채팅에 SSE만 쓰기 어려운 이유는 → 흔한 오해
- 연결이 잠깐 끊겼다가 다시 붙었을 때 그 사이 이벤트를 놓치지 않으려면 무엇이 필요한가 → 작동 원리
- 화면마다 스트림을 따로 열면 무엇이 문제가 되나 → 주의사항
