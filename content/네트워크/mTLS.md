# mTLS (Mutual TLS)

## 📝 정의

mTLS 는 **양쪽이 서로 인증서를 내보이는 TLS**다.

앞에 붙은 m 하나가 이 단어의 전부다 — mutual, 서로. RFC 8446 은 TLS 를 두고 "서버 쪽은 항상 인증되고, 클라이언트 쪽은 선택적으로 인증된다"고 적어두었다. 그 선택 항목을 켠 것이 mTLS 다.

### 이름
Mutual :: 서로, 양쪽 다
Transport :: 실어 나르는 일
Layer :: 그 층
Security :: 안전하게 지킴
= 붙여 읽으면 "실어 나르는 층을 서로 확인하며 지킴". 앞에 붙은 m 하나가 한쪽을 양쪽으로 바꾼다

### 비유
출입증을 서로 확인하는 문 — 경비가 방문객 증을 보는 것으로 끝나지 않고 방문객도 경비의 증을 확인한다.

### 예
회사에서 지급한 노트북으로만 사내 시스템이 열리는 일이 있다. 기기에 심어둔 증을 서버가 확인하기 때문이다.

## 🖼️ 그림으로 보기

```도해
대조: 서버만 증명하는 TLS 와 mTLS 는 무엇이 다른가
보통 TLS |=| mTLS
증을 내는 쪽 :: 서버만 || 서버와 부른 쪽
서버가 아는 것 :: 상대를 모른다 || 누구인지 안다
붙는 자리 :: 누구나 접속 || 증 받은 것만
= 서버만 증명하던 문을, 양쪽이 증명하는 문으로 바꾼 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 내부망이라 믿고 서로 확인하지 않으면 어떻게 되나
망만 믿을 때 || 서로 증명할 때
부른 쪽 :: 누군지 모른다 || 인증서로 밝힌다
침입한 뒤 :: 다 부를 수 있다 || 증이 없어 막힌다
권한 주기 :: IP 로 어림한다 || 신원으로 준다
= 같은 망에 있다는 것은 신원이 아니다. 신원은 증명해야 생긴다
```

서버가 자기만 증명하는 보통의 [[SSL_TLS]] 는 공개 웹에 맞는 모양이다. 아무나 오는 손님에게 증을 요구할 수는 없으니, 손님이 서버를 확인하는 것으로 충분하다.

서비스끼리 부르는 자리에서는 사정이 뒤집힌다. 부르는 쪽이 사람이 아니라 정해진 몇 개의 서비스이고, 받는 쪽은 그중 누가 불렀는지 알아야 권한을 정할 수 있다. 그런데 "같은 망 안에서 왔다"는 것은 신원이 아니다. Google Cloud 문서가 [[Zero Trust]] 를 설명하며 못 박는 대목이 이것이다 — 망 안에서 온 트래픽이든 밖에서 온 트래픽이든 모두 위험한 것으로 본다. mTLS 는 부른 쪽에도 인증서를 요구해서, 확인된 신원 위에서 권한을 주게 만든다.

## ⚙️ 작동 원리

```도해
흐름: mTLS 손잡기에서 부르는 쪽은 무엇을 더 하나
서버 :: 자기 인증서를 보내며 "네 것도 내라" 고 청한다
부른 쪽 :: 받은 인증서로 서버가 맞는지 먼저 본다
부른 쪽 :: 자기 인증서를 내고 개인 키로 손잡기에 서명한다
서버 :: 신뢰 사슬과 그 서명을 검사한다
< 서버 :: 맞으면 연결을 열고, 아니면 끊는다
= 청하는 한 마디가 붙으면 아래 두 마디가 생긴다. 그게 mTLS 다
```

갈림길은 서버가 인증서를 청하느냐 한 곳이다. RFC 8446 은 이 메시지를 두고 "클라이언트 인증이 필요 없으면 생략된다"고 적는다. 청하면 부른 쪽은 인증서와 함께 서명 하나를 더 보내는데, 그것은 **인증서에 실린 공개 키에 대응하는 개인 키로 손잡기 전체에 한 서명**이다. 그래서 남의 인증서를 그대로 베껴 붙여도 통과하지 못한다 — 개인 키를 쥔 쪽만 그 서명을 만들 수 있다.

검사하는 쪽은 신뢰 앵커(루트 인증서)를 담은 저장소를 두고, 받은 인증서에서 그 앵커까지 사슬이 이어지는지 본다. 검사에 실패했을 때 무엇을 할지는 **고르는 값**이다. 연결을 끊을 수도 있고, 통과시키되 실패 사유를 헤더에 적어 뒤로 넘길 수도 있다.

## 💡 실제 사례

- **서비스 간 호출** — 같은 클러스터 안이라도 부르는 쪽이 인증서로 자기를 밝히고, 받는 쪽은 확인된 신원으로 권한을 정한다.
- **인증서 자동 발급** — 서비스 메시에서는 관리 계층이 서비스마다 인증서를 자동으로 발급해, 사람이 나눠주지 않아도 서로 인증할 수 있게 한다.
- **앞단에서 걸러내기** — 로드 밸런서가 클라이언트 인증서를 먼저 검사하고, 어긋나면 연결을 끊거나 사유를 헤더에 실어 뒤로 넘긴다.

## 🚫 흔한 오해

- **HTTPS 가 걸려 있으면 이미 양쪽을 확인한 것이다** — 보통 TLS 가 확인하는 것은 서버 쪽이다. 부른 쪽 확인은 켜야 생기는 선택 항목이고, 안 켜면 서버는 상대가 누구인지 모른다.
- **mTLS 를 통과했으니 그 요청은 허용된 요청이다** — 확인된 것은 신원까지다. 그 신원이 무엇을 할 수 있는지는 인가에서 따로 정해야 한다.
- **내부 통신은 전부 mTLS 로 바꾸는 게 낫다** — 관리할 인증서가 양쪽으로 늘어난다. 자동으로 발급하고 갈아 끼우는 장치가 없으면, 만료 하나가 그 경로를 통째로 멈춰 세운다.

## 🚨 주의사항

- **갱신을 사람 손에 맡기지 않는다.** 양쪽이 인증서를 쓰니 만료 지점이 두 배가 되고, 하나만 지나도 그 호출이 막힌다.
- **검사에 실패했을 때 무엇을 할지 먼저 정한다.** 끊을 것인지 사유만 붙여 넘길 것인지는 설정으로 고르는 값이라, 잘못 고르면 검사를 켜둔 채로 아무나 들어온다.

## 📝 정리

**"양쪽이 서로 증을 내보이는 그 문"** 이라고 읽으면 된다. 같은 망에 있다는 사실 대신 양쪽이 인증서로 신원을 밝히므로, 받는 쪽은 누가 불렀는지 확인하고 그 신원 위에서 권한을 줄 수 있다. 대신 관리할 인증서가 양쪽으로 늘어난다.

## 🧒 열 살에게

문 앞에서 한쪽만 이름표를 보이고 다른 쪽은 그냥 지나가면, 문은 방금 들어온 게 누군지 몰라. 그래서 둘 다 이름표를 꺼내 보이기로 한 거야. 그래야 문이 "아, 너구나" 하고 알아보고, 이름표 없는 애는 아예 못 들어와.

## ❓ 이해했는지

- HTTPS 로 붙었는데도 서버가 부른 쪽을 모르는 이유는 → 흔한 오해
- 남의 인증서를 그대로 베껴 붙여도 통과하지 못하는 이유는 → 작동 원리
- 방화벽으로 감싼 내부망에서까지 서로 증명하게 만드는 이유는 → 해결하는 문제

## 🔗 관련 용어

- [[SSL_TLS]] — 서버 쪽만 증명하는 기본형. mTLS 는 그 선택 항목을 켠 것이다
- [[인증서]] — 양쪽이 서로 내보이는 그 문서
- [[CA]] — 그 인증서에 서명해 신뢰 사슬의 뿌리가 되는 기관
- [[Zero Trust]] — 망 안이라고 믿지 않는다는 원칙. mTLS 가 그것을 실행하는 수단
