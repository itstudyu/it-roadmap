# Long Polling (롱 폴링)

## 📝 정의

Long Polling 은 **서버가 답할 것이 생길 때까지 요청을 붙잡아 두는** 방식이다.

HTTP 는 요청이 없으면 서버가 먼저 말을 걸 수 없게 되어 있다. 그래서 요청을 미리 하나 보내 두고 서버가 그것을 붙잡고 있게 만들었다. 2011년 RFC 6202 는 'Comet' 이라 불리던 이런 우회로 가운데 가장 흔한 둘로 롱 폴링과 HTTP 스트리밍을 꼽으면서, 이것이 HTTP 의 원래 뜻을 늘려 쓴 것임을 문서 스스로 인정한다.

### 비유
콜센터 대기음. 끊고 다시 걸어 묻는 대신 통화를 붙들고 있다가, 상담원이 오면 그 통화로 바로 듣는다.

## 🖼️ 그림으로 보기

```도해
흐름: 서버는 어떻게 요청을 붙잡아 두고 있다가 답하나
브라우저 :: 새 소식을 달라고 요청 하나를 보낸다
서버 :: 줄 것이 없다. 응답을 끝내지 않고 붙잡아 둔다
새 소식 :: 그 사이 새 메시지가 서버에 도착한다
< 서버 :: 붙잡아 둔 요청에 `200 OK` 로 그것을 담아 답한다
@ 브라우저 :: 받자마자 다음 요청을 새로 보낸다
= 답할 것이 생길 때까지 요청을 붙잡아 두는 것이 롱 폴링이다
```

## ⚠️ 해결하는 문제

```도해
대조: 새 소식이 있는지 몇 초마다 물어보면 무엇이 나쁜가
짧은 폴링 || 롱 폴링
빈 응답 :: 대부분이 빈손 || 소식 있을 때만
소식 지연 :: 다음 차례까지 || 생기면 바로
지연 줄이기 :: 요청 수가 늘어난다 || 그대로다
= 자주 물으면 낭비고 드물게 물으면 늦다. 그 맞바꿈에서 빠져나온다
```

표준 HTTP 에서 서버는 클라이언트에게 먼저 연결을 걸 수도, 묻지 않은 응답을 보낼 수도 없다. 그래서 새 소식을 빨리 알려면 클라이언트가 주기적으로 물어보는 수밖에 없었다. 그런데 물어봤을 때 줄 것이 없으면 그 왕복은 통째로 낭비고, 소식은 다음 질문 차례까지 서버에 갇혀 있으니 응답도 늦다. 주기를 어디에 두든 낭비와 지연 중 하나는 커진다.

롱 폴링은 그 맞바꿈에서 빠져나온다. 서버가 **사건이나 대기 만료 때만 답하기로** 하면, 어느 시점에도 서버는 답할 수 있는 요청 하나를 붙잡고 있는 상태가 된다. 소식이 생기는 순간 그 요청에 답하면 되니 낭비도 지연도 함께 줄어든다.

## ⚙️ 작동 원리

새 프로토콜은 없다. 브라우저가 보내는 것은 평범한 요청이고 서버는 그 응답을 미룰 뿐이다. 답할 때도 보통의 `200 OK` 이고, 본문에 그동안 생긴 사건이나 상태를 담는다.

그래서 이 방식의 핵심 설정값은 **대기 시간 하나**다. 길게 잡을수록 헛된 왕복이 줄지만 너무 길면 서버가 `408 Request Timeout` 을, 중간 프록시가 `504 Gateway Timeout` 을 먼저 던진다. RFC 6202 가 적어둔 브라우저 기본 대기 시간은 300초인데, 사이에 놓인 프록시와 서버들은 그만큼 기다려주지 않는다. 120초까지 성공한 실험이 있지만 30초가 안전한 값으로 통한다.

응답이 나가고 다음 요청이 도착하기까지의 **틈**도 이 방식의 성질이다. 그 틈에 생긴 소식은 서버가 들고 있다가 다음 요청에 얹어야 한다. 평균 지연은 편도 한 번에 가깝지만 최악은 편도 세 번(응답 → 다음 요청 → 응답)을 넘는다.

캐시는 끈다. 중간 장비에게 이것이 롱 폴링이라고 알릴 방법이 없어서 보통 요청으로 취급되고, 그러면 캐시된 옛 응답이 돌아올 수 있다. `Cache-Control: no-cache` 를 붙이는 것이 관례다.

## 📊 비교: 짧은 폴링에서 WebSocket 까지

| 방식 | 요청 하나가 어떻게 끝나나 | 서버가 먼저 보내려면 |
|---|---|---|
| **짧은 폴링** | 곧바로 답한다. 없으면 빈손 | 다음 질문을 기다린다 |
| **롱 폴링** | 사건이나 대기 만료 때 답한다 | 붙잡아 둔 요청에 답한다 |
| **HTTP 스트리밍** | 끝내지 않고 계속 밀어 보낸다 | 열린 응답에 이어 쓴다 |
| **WebSocket** | HTTP 로 시작해 갈아탄다 | 아무 때나 프레임을 던진다 |

가운데 둘이 RFC 6202 가 다루는 두 갈래다. [[SSE]] 는 그중 스트리밍 쪽을 `text/event-stream` 형식으로 규격화한 것이고, [[WebSocket]] 은 HTTP 연결을 갈아타서 만드는 별도 프로토콜이라 아예 다른 줄에 선다.

## 💡 실제 사례

- **알림 배지** — 서버가 요청을 붙잡고 있다가 새 알림이 생기는 순간 그 요청에 답한다. 다음 질문 차례를 기다리지 않는다.
- **소식이 몰릴 때** — 응답과 다음 요청 사이에 여러 건이 쌓이면 한 응답에 묶어 내보낼 수 있다. 건당 부담이 그만큼 줄어든다.
- **프록시가 많은 망** — 오가는 것이 완결된 요청과 응답뿐이라 중간 장비가 손대지 않고 그대로 통과시킨다.

## 🚫 흔한 오해

- **롱 폴링은 서버가 먼저 말을 거는 것이다** — 먼저 걸 수 없다. 클라이언트가 미리 보내둔 요청에 늦게 답하는 것이고, 그 답을 보낸 순간 서버는 다시 말할 통로를 잃는다.
- **롱 폴링은 특별한 프로토콜이다** — 보통의 HTTP 요청 하나다. 서버가 응답 시점을 미룰 뿐이고 답할 때는 평범한 `200 OK` 다.
- **실시간이면 롱 폴링이 짧은 폴링보다 언제나 낫다** — 사람 수만큼 요청을 열어 둔 채 붙잡고 있어야 한다. 게이트웨이나 프록시가 동시에 붙들 수 있는 요청 수에서 먼저 막히고, 브라우저가 한 도메인에 여는 연결 여섯 개 중 하나도 계속 물고 있다.

## 🚨 주의사항

- **브라우저가 한 도메인에 여는 연결은 여섯 개쯤이다.** 롱 폴 하나가 그중 하나를 계속 물고 있어서, 탭과 프레임마다 따로 열면 금방 바닥난다. 게다가 보통 요청이 롱 폴 뒤에 줄을 서면 롱 폴이 끝날 때까지 같이 밀린다. 창 전체에서 롱 폴 하나만 쓰는 것이 권고다.
- **요청을 붙잡는 것은 자원을 붙잡는 것이다.** 클라이언트 하나마다 TCP 연결과 HTTP 요청이 함께 열려 있어야 한다. 연결 쪽은 대개 가볍지만 요청에 붙는 자원이 커서 게이트웨이·프록시·서버가 동시 요청 수에서 먼저 한계를 만난다.
- **앞단이 뒤쪽 연결을 나눠 쓰면 굶는다.** 리버스 프록시 중에는 서버로 가는 연결을 열 몇 개만 두고 모든 클라이언트가 나눠 쓰게 하는 것이 있다. 거기에 롱 폴이 실리면 그 몇 개를 다 차지해서, 롱 폴이든 보통 요청이든 나머지가 멈춰 선다.
- **소식이 짧으면 오가는 양의 대부분이 헤더다.** 요청도 응답도 완결된 HTTP 메시지라서 헤더 한 벌이 매번 따라붙는다.

## 📝 정리

롱 폴링은 서버가 답할 것이 생길 때까지 요청을 붙잡아 두는 우회로다. HTTP 가 요청 없이는 답할 수 없게 되어 있어서, 요청을 미리 보내 두는 것으로 그 제약을 비켜 갔다. 응답 하나마다 요청을 새로 보내야 하고 사람 수만큼 요청을 열어 둬야 해서, SSE 와 WebSocket 이 생긴 뒤로는 그것들을 쓸 수 없는 자리에 남았다.

## 🔗 관련 용어

- [[HTTP]] — 요청이 없으면 답할 수 없다는 규칙. 롱 폴링이 비켜 가려는 대상이다
- [[SSE]] — 응답을 끝내지 않고 계속 내려보내는 쪽. 롱 폴링의 다음 세대다
- [[WebSocket]] — 갈아타서 양쪽이 오가게 만든 쪽. 역시 다음 세대다
- [[TCP]] — 요청을 붙잡아 둔다는 것이 실제로 붙잡고 있는 연결
- [[Reverse Proxy]] — 붙잡아 둔 요청 때문에 앞단 연결이 굶는 자리
