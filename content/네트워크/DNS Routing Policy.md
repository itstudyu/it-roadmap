# DNS Routing Policy (이름 조회 응답 정책)

## 📝 정의

DNS Routing Policy는 **같은 이름을 물어도 묻는 쪽에 따라 다른 주소를 주는 규칙**이다.

이름 하나에 주소 하나라는 그림은 오래전에 깨졌다. Route 53 은 여덟 가지, Azure Traffic Manager 는 여섯 가지 방식을 두고 있고, 어느 것을 고르느냐가 곧 "우리 이용자를 어느 리전으로 보낼 것인가" 를 정한다.

### 이름
DNS :: 이름을 주소로
Routing :: 어디로 보낼지
Policy :: 정해 둔 규칙
= 붙여 읽으면 "이름을 물어 왔을 때 어디로 보낼지 정해 둔 규칙"

### 비유
같은 대표 번호를 눌러도 서울에서 걸면 서울 지점이, 부산에서 걸면 부산 지점이 받는 콜센터.

### 예
해외에서 늘 쓰던 사이트를 열었더니 언어도 화면도 통째로 달라져 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 같은 이름을 물었는데 왜 사람마다 다른 주소를 받나
묻는 쪽 :: 서울에서 이름 하나를 묻는다
응답 서버 :: 답하기 전에 누가 물었는지부터 본다
정책표 :: 지역·무게·살았나 중 무엇으로 고를지 적혀 있다
고른 답 :: 규칙에 맞는 주소 하나를 뽑는다
< 묻는 쪽 :: 서울 주소를 받는다. 부산에서 물으면 다른 답이 온다
= 이름은 하나인데 답은 여럿이고, 무엇을 보고 고를지가 곧 규칙이다
```

## ⚠️ 해결하는 문제

```도해
대조: 이름 하나에 답이 하나뿐이면 무엇이 곤란해지나
답이 하나면 || 규칙을 두면
먼 나라 이용자 :: 지구 반대편까지 || 가까운 쪽으로
한 곳이 죽으면 :: 죽은 주소를 준다 || 살아 있는 곳만
새 버전 시험 :: 전부 아니면 전무 || 열에 하나만
= 이름은 하나로 두고, 누구에게 무엇을 줄지만 규칙으로 가른다
```

여러 리전에 같은 것을 띄워 놓아도 이름이 한 주소만 가리키면 그 노력은 절반이 버려진다. 유럽 이용자가 서울까지 왕복하고, 서울이 죽어도 이름은 계속 죽은 곳을 가리킨다. 새 버전을 일부에게만 보여 보려 해도 방법이 없다.

응답 정책은 답하는 자리에 판단을 하나 끼워 넣어 이 셋을 한꺼번에 푼다. 이름은 그대로 두고 **누가 물었는가**만 보는 것이라, 앱을 고치지 않고도 사람을 갈라 보낼 수 있다. 다만 이 판단은 답이 한 번 나가는 순간까지만 유효하다 — 그 뒤는 캐시가 물고 있다.

## ⚙️ 작동 원리

지연으로 고르는 방식이 가장 오해가 잦다. AWS 문서는 이 값이 "이용자와 데이터센터 사이의 실제 통신을 두고 오랫동안 모은 지연 자료" 라고 못 박는다. 거리를 재는 것이 아니라 왕복 시간을 재고, 그 값은 인터넷 경로가 바뀌면 함께 바뀌어서 이번 주에 오리건으로 가던 런던 이용자가 다음 주에는 싱가포르로 갈 수 있다. Azure 도 같은 방식을 쓰는데, 그쪽은 IP 대역과 데이터센터 사이의 왕복 시간을 적어 둔 "인터넷 지연 표" 를 두고 그 표를 계속 갱신한다고 적는다.

누가 물었는지를 아는 방법에도 한계가 있다. 응답 서버에 실제로 도착하는 것은 이용자의 주소가 아니라 이용자가 쓰는 해석기의 주소다. 문서들은 이것을 "이용자의 위치를 가늠하기에 충분히 쓸 만한 대리 값" 이라고 표현한다. EDNS0 확장을 지원하는 해석기만 이용자 주소의 앞부분을 함께 보내 주고, 그때는 그 값까지 참고한다.

살았는지 죽었는지는 헬스체크가 맡는다. Cloud DNS 는 활성 묶음이 전부 죽었을 때만 예비 묶음의 주소를 내보내고, Route 53 은 다중값 방식에서 건강한 것 중 최대 여덟 개를 무작위로 골라 준다. 다만 헬스체크가 A·AAAA 처럼 주소를 담은 레코드에만 붙는다는 제약이 있다.

## 📊 비교: 무엇을 보고 고르나

| 방식 | 무엇을 보나 | 언제 쓰나 |
|---|---|---|
| **단순** | 아무것도 안 본다 | 답이 하나뿐일 때 |
| **장애 대체** | 주 쪽이 살았나 | 평소엔 주, 죽으면 예비 |
| **지역** | 물어 온 나라·주 | 규정·언어를 나라별로 가를 때 |
| **지연** | 리전까지의 왕복 시간 | 여러 리전에 같은 것을 띄웠을 때 |
| **가중치** | 미리 정한 비율 | 새 쪽에 열에 하나만 보낼 때 |
| **다중값** | 건강한 것 여럿 | 이용자 쪽에서 다시 시도하게 할 때 |

## 💡 실제 사례

- **여러 리전 운영** — Route 53 의 지연 레코드를 서울과 버지니아에 하나씩 만들어 두면, 물어 온 쪽에서 왕복이 짧은 리전의 주소가 나간다.
- **조금씩 옮기기** — Azure Traffic Manager 의 가중치 방식으로 새 쪽에 1, 옛 쪽에 99 를 걸어 두고, 지표가 멀쩡하면 무게를 올려 결국 전부를 옮긴다.
- **나라 밖으로 못 내보내는 자료** — Cloud DNS 의 지역 정책으로 그 나라에서 온 물음만 그 나라 안의 것으로 보내고, 나머지는 본진으로 보낸다.

## 🚫 흔한 오해

- **가장 가까운 리전으로 보내 준다** — 재는 것은 거리가 아니라 왕복 시간이고, 그 값은 인터넷 사정에 따라 바뀐다. 같은 도시에 리전이 있어도 실제 지연은 크게 다를 수 있다고 문서가 직접 경고한다.
- **규칙을 바꾸면 곧바로 반영된다** — 한 번 나간 답은 중간 해석기에 TTL 동안 남는다. Cloud DNS 문서는 이 때문에 "쏠림이 정확하지 않을 수 있다" 고 적고, Azure 는 이용자나 해석기 수가 적으면 무게대로 안 나뉜다고 적는다.
- **묻는 사람의 위치를 정확히 안다** — 대개 보이는 것은 이용자가 아니라 그가 쓰는 해석기의 주소다. 회사 안에서 다들 같은 해석기를 쓰면 전원이 한 곳으로 몰려 보인다.

## 📝 정리

**"이름 하나에 답을 여럿 두고 골라 주는 규칙"** 이라고 읽으면 된다. 무엇을 보고 고르는지가 방식의 이름이 되고, 지연으로 고를 때 재는 것은 거리가 아니라 왕복 시간이다. 어느 방식을 쓰든 답이 나간 뒤에는 캐시가 물고 있으므로 바꾼 규칙은 TTL 만큼 늦게 듣는다.
