# Reverse Proxy (리버스 프록시)

## 📝 정의

Reverse Proxy는 **서버 앞에 서서 요청을 대신 받는 중개 서버**다.

클라이언트는 이 앞단의 주소만 알고 뒤에 서버가 몇 대 있는지는 모른다. 암호 풀기, 캐시, 분배를 앞단 한 곳에서 처리한다.

### 비유
대형 병원의 접수실. 환자는 접수실에만 말하면 되고 어느 과 몇 번 방으로 갈지는 접수실이 정한다.

### 예
점검 중이라는 같은 안내 화면만 계속 뜨는 사이트가 있다. 뒤쪽 서버 대신 앞단이 그 화면을 내주고 있는 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 요청 하나가 리버스 프록시를 지나며 무엇을 겪나
클라이언트 :: example.com 으로 HTTPS 요청을 보낸다
프록시 :: HTTPS 를 풀어 평문 요청으로 만든다
프록시 :: 캐시에 있으면 여기서 바로 돌려준다
프록시 :: 없으면 뒤쪽 서버 중 한 대를 고른다
앱 서버 :: 요청을 처리해 응답을 만든다
< 프록시 :: 압축하고 다시 암호화해 돌려준다
= 클라이언트는 앞단의 IP 하나만 알고 뒤는 끝내 모른다
```

## ⚠️ 해결하는 문제

```도해
대조: 서버를 인터넷에 그대로 열면 어떻게 되나
프록시 없이 || 프록시를 두면
서버 IP :: 밖에 드러난다 || 앞단만 보인다
서버 늘리기 :: 주소가 늘어난다 || 뒤에 붙이면 끝
인증서 :: 서버마다 설치 || 앞단 한 곳에
= 밖에서 보이는 문을 하나로 줄이는 것이다
```

서버를 인터넷에 직접 붙이면 그 IP 가 그대로 드러난다. 포트를 훑거나 응답 헤더에 적힌 소프트웨어 버전을 보고 그 버전의 알려진 구멍을 찌를 수 있다. 사용자가 늘어 서버를 한 대 더 놓으면 밖에서 보이는 주소가 하나 더 생기고, 인증서도 서버 수만큼 깔아야 한다.

리버스 프록시는 밖에서 보이는 문을 하나로 줄인다. 뒤에 몇 대를 붙이든 사용자가 쓰는 주소는 그대로고 인증서도 앞단에만 있으면 된다. 뒤쪽 한 대를 목록에서 빼고 나머지로만 받게 할 수 있어서 서비스를 세우지 않고 배포할 수도 있다.

## 🧱 구성

```도해
층: 요청은 어디까지 안으로 들어오나
인터넷 :: 누구나 닿을 수 있는 바깥
리버스 프록시 :: 공인 IP 를 가진 유일한 문
앱 서버 :: 사설 IP 만 있다. 밖에서 직접 못 닿는다
DB :: 앱 서버만 붙는다. 가장 안쪽
= 안으로 갈수록 닿을 수 있는 곳이 줄어든다
```

## ⚙️ 작동 원리

HTTPS 연결은 앞단에서 끊는다. 암호를 풀고 다시 거는 일은 CPU 를 많이 먹는데, 이걸 앞단이 전담하면 뒤쪽 서버는 자기 일에만 쓴다. 이것을 SSL 종료라고 부른다.

캐시에 있는 응답은 뒤까지 가지 않고 앞단에서 끝난다. 남은 요청은 정해둔 규칙에 따라 뒤쪽 서버에 나눠 준다. 돌려줄 때는 압축해서 내보내 오가는 양을 줄인다.

## 📊 비교: Reverse Proxy vs Forward Proxy

| | Reverse Proxy | Forward Proxy |
|---|---|---|
| 서 있는 자리 | 서버 앞 | 클라이언트 앞 |
| 감추는 것 | 서버의 IP | 클라이언트의 IP |
| 누가 두나 | 서비스 운영자 | 회사나 학교 |
| 주로 하는 일 | 분배, SSL 종료, 캐시 | 접근 제어, 캐시 |

## 💡 실제 사례

- **웹 서비스 앞단** — Nginx 나 HAProxy 를 세워 뒤쪽 앱 서버 여러 대에 요청을 나눠 준다.
- **마이크로서비스** — 경로를 보고 어느 서비스로 보낼지 앞단에서 갈라준다.
- **무중단 배포** — 한 대를 목록에서 빼고 고친 뒤 다시 넣는 식으로 서비스를 세우지 않고 올린다.

## 🚫 흔한 오해

- **리버스 프록시는 로드 밸런서와 같은 말이다** — 나눠 주는 일은 겹치지만 리버스 프록시는 SSL 종료와 캐시와 경로 갈라주기까지 맡는다. 나누는 일만 하는 장치는 따로 있다.
- **프록시니까 내 IP 를 숨겨준다** — 감추는 쪽이 반대다. 감춰지는 건 뒤에 있는 서버이고, 클라이언트를 감추는 건 Forward Proxy 다.
- **앞에 하나 세우면 더 안전해진다** — 그 하나가 죽으면 뒤가 다 멀쩡해도 전부 안 된다. 앞단 자체를 여러 대로 두지 않으면 무너질 지점을 하나 만든 셈이다.

## 🚨 주의사항

- **앞단을 한 대만 두지 않는다.** 뒤쪽을 아무리 늘려도 앞단이 죽으면 서비스가 통째로 멈춘다.
- **어느 뒷단이 받았는지 로그에 남긴다.** 요청이 나뉘어 가므로 이걸 안 적어두면 문제가 난 서버를 찾을 수 없다.

## 📝 정리

Reverse Proxy는 서버 앞에 서서 요청을 대신 받고 뒤로 넘기는 중개 서버다. 밖에서 보이는 문을 하나로 줄여 서버 IP 를 감추고, SSL 종료와 캐시와 분배를 앞단 한 곳에 몰아둔다. 몰아둔 만큼 그 한 곳이 죽었을 때의 여파도 같이 커진다.

## ❓ 이해했는지

- 뒤에 앱 서버를 두 대 더 붙여도 사용자가 쓰는 주소가 그대로인 이유는 → 해결하는 문제
- 앱 서버는 사설 IP 만 갖고 있는데 밖에서 접속이 되는 이유는 → 구성
- 앞단을 한 대만 두면 무엇이 위험해지나 → 주의사항
