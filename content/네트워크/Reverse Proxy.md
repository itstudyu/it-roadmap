# Reverse Proxy

## 📝 정의

리버스 프록시(Reverse Proxy)는 서버 앞에 위치하면서 클라이언트의 요청을 받아 내부의 여러 서버로 전달하는 중개 서버입니다. Forward Proxy와 달리 클라이언트 입장에서는 실제 서버가 어디에 있는지 알 수 없으며, 오직 리버스 프록시와만 통신합니다. 리버스 프록시는 요청을 받은 후 내부 서버의 위치를 클라이언트에게 숨기면서, 서버의 실제 IP 주소와 구조를 보호합니다.

리버스 프록시가 등장한 이유는 웹 서비스의 규모가 커지면서 단일 서버로는 많은 사용자 요청을 처리할 수 없게 되었기 때문입니다. 또한 서버의 위치를 클라이언트로부터 숨겨야 보안 침해의 위험을 줄일 수 있습니다. 로드 밸런싱, SSL 암호화, 캐싱 등 다양한 기능을 한 곳에서 처리할 수 있어서, 큰 규모의 웹 서비스에서 필수적인 기술이 되었습니다.

### 한 줄 요약
> 서버 앞에서 클라이언트 요청을 받아 내부 서버로 전달하고 응답을 반환하는 중개자

### 비유
- 🔵 **비유 1**: 대형 병원의 접수실처럼, 환자들은 병원의 접수실(리버스 프록시)에만 가서 증상을 말하면, 접수실에서 적절한 과의 의사(내부 서버)에게 환자를 배정합니다. 환자는 병원 내부 구조를 모르지만, 효율적으로 진료를 받을 수 있습니다.
- 🟡 **비유 2**: 콜센터의 교환원처럼, 고객이 콜센터 번호(리버스 프록시)로 전화하면, 교환원이 통화 내용에 따라 적절한 부서(내부 서버)로 연결합니다. 고객은 각 부서의 직통 번호를 몰라도 됩니다.

## 🎯 핵심 개념

### 1. 서버 보호 및 익명성
리버스 프록시는 서버들의 실제 IP 주소를 클라이언트로부터 숨깁니다. 클라이언트는 리버스 프록시의 IP만 알 수 있고, 뒤에 있는 실제 서버의 위치나 개수를 알 수 없습니다. 이는 해킹 공격을 어렵게 만들고, 서버 인프라의 구조를 비밀로 유지할 수 있게 합니다. DDoS 공격이나 포트 스캔 같은 공격으로부터 내부 서버를 보호하는 중요한 방어선 역할을 합니다.

### 2. 로드 밸런싱
리버스 프록시는 들어오는 요청을 여러 개의 내부 서버에 분산시킬 수 있습니다. 예를 들어, 100명의 사용자 요청이 들어오면, 리버스 프록시가 Round Robin 방식으로 5개의 서버에 각각 20개씩 분배합니다. 이를 통해 단일 서버의 과부하를 방지하고, 전체 시스템의 성능을 향상시킵니다. 동시에 특정 서버의 성능이 떨어지면 자동으로 해당 서버로의 요청을 줄이는 지능형 로드 밸런싱도 가능합니다.

### 3. SSL 종료 (SSL Termination)
리버스 프록시는 클라이언트와의 HTTPS 연결을 담당하고, 내부 서버와의 통신은 HTTP로 처리할 수 있습니다. 이를 SSL 종료라고 합니다. 암호화와 복호화는 CPU를 많이 사용하는데, 이 작업을 리버스 프록시에서 전담함으로써 실제 서버는 비즈니스 로직에만 집중할 수 있습니다. 또한 SSL 인증서를 리버스 프록시에만 설치하면 되므로, 관리가 단순해집니다.

### 4. 캐싱 및 압축
리버스 프록시는 서버의 응답을 캐시해둘 수 있습니다. 자주 요청되는 정적 콘텐츠(이미지, CSS, JavaScript)는 원본 서버에서 매번 불러올 필요 없이 캐시된 버전을 바로 반환할 수 있습니다. 또한 응답을 Gzip으로 압축하여 클라이언트에 전송함으로써 네트워크 대역폭을 절약할 수 있습니다.

## ⚠️ 해결하는 문제

### 문제 1: 단일 서버의 성능 한계
웹 서비스가 성장하면서 단일 서버로는 많은 사용자의 동시 요청을 처리할 수 없게 됩니다. 서버가 모든 요청을 처리하려다 보면 응답이 느려지거나 다운될 수 있습니다. 기존에는 더 비싼 서버로 업그레이드하는 수직 확장(Scale Up)만 가능했고, 비용이 많이 들었습니다. 리버스 프록시는 요청을 여러 저사양 서버에 분산시켜, 더 많은 사용자를 처리할 수 있게 합니다. 이를 수평 확장(Scale Out)이라 하며, 비용 효율적입니다.

### 문제 2: 서버의 보안 위험성
클라이언트가 서버의 실제 IP 주소를 알면, 직접 공격할 수 있습니다. 포트 스캔, DDoS 공격, 취약점 공격 등이 직접 서버를 대상으로 이루어질 수 있습니다. 또한 서버의 응답 헤더에서 서버 소프트웨어 정보(예: Apache 2.4.41)가 노출되면, 해당 버전의 알려진 취약점을 악용할 수 있습니다. 리버스 프록시가 클라이언트 요청을 받으면, 해당 정보를 수정하여 전달하거나, 악의적인 요청을 사전에 차단할 수 있습니다. 결과적으로 내부 서버의 보안이 크게 강화됩니다.

### 문제 3: 복잡한 서버 관리 및 유지보수
대규모 웹 서비스는 여러 종류의 서버(웹 서버, API 서버, 데이터베이스 등)를 운영합니다. 각 서버의 업데이트나 재시작이 필요할 때, 서비스 중단 없이 처리하기가 어렵습니다. 또한 SSL 인증서를 모든 서버에 설치하고 관리해야 합니다. 리버스 프록시가 중앙에서 요청 흐름을 제어하면, 특정 서버를 일시적으로 제외하고 다른 서버로만 요청을 처리할 수 있습니다. 무중단 배포(Zero-downtime deployment)가 가능해집니다.

## ⚙️ 작동 원리

### 단계별 과정

1. **요청 도착**: 클라이언트가 www.example.com으로 HTTPS 요청을 보냅니다. 실제로는 Reverse Proxy의 IP(203.0.113.1)로 연결됩니다.

2. **SSL 종료**: 리버스 프록시가 HTTPS 핸드셰이크를 처리하고, 클라이언트의 요청을 복호화합니다. 이제 리버스 프록시는 평문(Plain text) 요청을 가지고 있습니다.

3. **캐시 확인**: 리버스 프록시는 요청에 해당하는 응답이 캐시에 저장되어 있는지 확인합니다. 정적 콘텐츠나 자주 요청되는 페이지는 여기서 즉시 반환될 수 있습니다.

4. **로드 밸런싱**: 캐시에 없으면, 리버스 프록시는 설정된 로드 밸런싱 알고리즘에 따라 여러 내부 서버 중 하나를 선택합니다. 예를 들어, Round Robin 방식이면 첫 번째 요청은 App Server 1로, 두 번째는 App Server 2로 보냅니다.

5. **내부 서버 처리**: 선택된 App Server가 요청을 처리합니다. 필요하면 데이터베이스에 접근합니다.

6. **응답 수신**: App Server의 응답을 리버스 프록시가 받습니다. 필요에 따라 응답을 캐시에 저장합니다.

7. **응답 처리 및 반환**: 리버스 프록시는 응답을 Gzip으로 압축하고, SSL/TLS로 암호화한 후 클라이언트에게 보냅니다.

```도해
흐름: Reverse Proxy, 무슨 순서로 오가나
클라이언트 :: HTTPS 요청 (GET /api/users)
Reverse Proxy :: SSL 종료, 복호화
Reverse Proxy :: 압축 및 암호화 후 응답
Reverse Proxy :: 응답 압축
Reverse Proxy :: 압축 및 암호화 후 응답
```

## ✅ 장점과 단점

### 장점

- **서버 보안 강화**: 내부 서버의 실제 IP와 구조를 외부로부터 숨겨서, 직접 공격으로부터 보호합니다.
- **로드 밸런싱**: 여러 서버에 요청을 분산시켜 높은 처리량(throughput)을 달성하고, 서비스의 고가용성을 보장합니다.
- **SSL 종료**: 암호화/복호화 작업을 리버스 프록시에서 처리하여, 실제 서버의 CPU 부하를 줄입니다.
- **캐싱**: 정적 콘텐츠를 캐시하여 응답 시간을 단축하고, 내부 서버의 부하를 감소시킵니다.
- **무중단 배포**: 특정 서버를 제외하고 요청을 처리하여, 서비스 중단 없이 업데이트할 수 있습니다.
- **응답 압축**: 응답을 압축하여 네트워크 대역폭을 절약합니다.
- **간단한 URL 정책**: 여러 내부 서버를 하나의 도메인으로 제공할 수 있습니다.

### 단점

- **단일 장애점(Single Point of Failure)**: 리버스 프록시 자체가 다운되면 모든 사용자가 서비스를 받을 수 없습니다. (다만 리버스 프록시를 여러 개 구성하면 이를 해결할 수 있습니다)
- **추가 네트워크 지연**: 요청이 리버스 프록시를 거쳐야 하므로 약간의 지연이 발생합니다.
- **설정 복잡성**: 로드 밸런싱 알고리즘, 헬스 체크, 세션 관리 등 다양한 설정이 필요합니다.
- **디버깅 어려움**: 요청이 어떤 내부 서버로 분배되었는지 추적하기 어려울 수 있습니다.
- **비용**: 리버스 프록시 소프트웨어(Nginx, HAProxy) 또는 로드 밸런서 하드웨어 구입 비용이 발생합니다.
- **메모리 사용량 증가**: 캐싱과 요청 버퍼링으로 인해 리버스 프록시의 메모리 사용량이 증가합니다.

## 💡 실제 사용 사례

**대규모 웹 서비스**: Netflix, Airbnb, GitHub 같은 대규모 웹 서비스는 Nginx나 HAProxy를 사용해 Reverse Proxy를 구성합니다. 수백 개의 내부 서버에 요청을 분산시키고, SSL 암호화를 한 곳에서 처리합니다. 동시에 자주 요청되는 콘텐츠를 캐시하여 응답 속도를 높입니다. 이러한 구성을 통해 일초에 수백만 개의 요청을 안정적으로 처리할 수 있습니다.

**마이크로서비스 아키텍처**: 현대적인 애플리케이션은 여러 마이크로서비스로 구성되어 있습니다. Reverse Proxy가 클라이언트 요청을 받아 각 마이크로서비스로 라우팅합니다. 또한 API Gateway 역할을 하여 인증, 속도 제한, 로깅 등을 중앙에서 처리합니다. 이를 통해 각 마이크로서비스는 자신의 비즈니스 로직에만 집중할 수 있습니다.

**CDN (Content Delivery Network)**: CDN 서비스는 Reverse Proxy의 원리를 활용합니다. 사용자의 요청을 가장 가까운 지리적 위치의 서버로 분배하고, 자주 접근하는 콘텐츠를 캐시합니다. 이를 통해 전 세계의 사용자가 빠른 속도로 콘텐츠에 접근할 수 있습니다.

**무중단 배포**: 전자상거래 플랫폼이나 금융 서비스는 24시간 365일 운영되어야 합니다. Reverse Proxy를 사용하면 일부 서버를 선택적으로 제외하고 나머지 서버로만 요청을 처리합니다. 제외된 서버에서 소프트웨어를 업데이트하고 테스트한 후 다시 서비스에 포함시킵니다. 이런 식으로 서비스 중단 없이 지속적으로 배포할 수 있습니다.

## 🔗 관련 용어

- **[[Proxy]]**: 클라이언트 앞에 위치하는 Forward Proxy로, 리버스 프록시와 반대 방향에 위치합니다.
- **[[Load Balancer]]**: 리버스 프록시와 유사하게 요청을 여러 서버에 분산시키는 기술입니다.
- **[[Gateway]]**: 리버스 프록시보다 더 광범위한 네트워크 관리 기능을 제공합니다.
- **[[VPN]]**: 암호화된 통신 채널을 제공하는 기술로, 리버스 프록시와는 다른 목적을 가집니다.
- **[[Firewall]]**: 네트워크 트래픽을 필터링하는 보안 장치로, 리버스 프록시 앞에 배치됩니다.
- **API Gateway**: 마이크로서비스 아키텍처에서 API 요청을 라우팅하는 중개자 역할을 합니다.
- **SSL/TLS 인증서**: 리버스 프록시에서 HTTPS 암호화를 위해 필수적입니다.
