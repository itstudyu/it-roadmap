# Server Name Indication (서버 이름 표시)

## 📝 정의

SNI는 **TLS 인사 첫 마디에 접속할 이름을 적어 보내는 칸**이다.

순서 때문에 생긴 칸이다. 자물쇠를 걸려면 서버가 인증서를 먼저 내밀어야 하는데, 어느 사이트의 인증서를 내밀지는 접속하려는 이름을 알아야 정해진다. 그런데 이름을 담은 `Host` 헤더는 자물쇠가 다 걸린 뒤에야 온다. 그래서 인사 첫 마디인 `ClientHello` 안에 이름 한 칸을 만들어 미리 적어 보낸다. RFC 6066 이 정한 확장 0번이고, 그 뒤로 통로가 아무리 잠겨도 이 칸만은 오래도록 평문으로 남았다.

### 이름
Server :: 접속할 그쪽
Name :: 사이트 이름
Indication :: 미리 알려 줌
= 붙여 읽으면 "접속할 곳의 이름을 미리 알려 주는 것". 인증서를 고르려면 이 한 마디가 먼저 있어야 한다

### 비유
공동 현관 인터폰. 문이 하나뿐이라 누구를 찾아왔는지 먼저 말해야 그 집이 문을 열어 준다.

### 예
주소창의 자물쇠를 눌러 인증서를 봤는데 전혀 다른 사이트 이름이 떠 있던 그 순간이다.

### 직접
주소창 자물쇠를 눌러 인증서의 "Subject Alternative Name" 목록을 보라. 그 목록 중 어느 것을 꺼낼지가 이 칸으로 정해진다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 주소에 사이트가 여럿인데 어느 인증서가 나오나
클라이언트 :: `ClientHello` 를 평문으로 먼저 보낸다
이름 칸 :: 그 안의 `server_name` 확장에 접속할 이름을 적는다
서버 :: 그 이름에 맞는 인증서를 골라 든다
< 서버 :: 모르는 이름이면 `unrecognized_name` 으로 끊는다
= 이름을 먼저 말해야 인증서를 고를 수 있다. 그래서 이 칸은 잠기기 전에 나간다
```

## ⚠️ 해결하는 문제

```도해
대조: 이 칸이 비면 무엇이 어긋나나
이름을 안 대면 || 이름을 대면
인증서 :: 기본 것만 나온다 || 이름에 맞는 것
한 주소에 :: 사이트 하나뿐 || 사이트 여럿
브라우저 :: 이름 불일치 경고 || 조용히 열린다
= 인증서를 고르는 단서가 이 한 칸이다. 비면 고를 방법이 없다
```

nginx 문서가 이 문제를 그대로 적어 두었다. `listen 443 ssl` 인 서버 블록을 둘 두고 `server_name` 만 달리하면, 브라우저는 요청한 이름과 상관없이 첫 블록의 인증서를 받는다. "SSL 연결은 브라우저가 HTTP 요청을 보내기 전에 맺어지고, nginx 는 요청된 서버 이름을 모른다" 는 것이 그 이유다.

그래서 예전에는 HTTPS 사이트마다 IP 주소를 하나씩 사야 했다. 이 칸이 생기면서 주소 하나에 사이트 수백 개를 얹을 수 있게 되었고, 공유 호스팅과 CDN 이 지금 모습이 된 것도 여기서 출발한다.

## ⚙️ 작동 원리

이 칸에는 클라이언트가 이해한 그대로의 완전한 도메인 이름을 ASCII 로 적는다. 끝에 점은 붙이지 않고, 국제화 도메인은 A-label 로 바꿔 적는다. 한 가지 못이 박혀 있다 — RFC 6066 은 "리터럴 IPv4·IPv6 주소는 `HostName` 에 넣을 수 없다" 고 정한다. 그래서 IP 주소를 직접 쳐서 접속하면 이 칸이 아예 비고, 서버는 기본 인증서를 내밀 수밖에 없다. 앞단 장비가 IP 만 아는 뒷단으로 다시 연결할 때 인증서 검증이 어긋나는 사고가 대개 여기서 나온다.

모르는 이름을 받은 서버는 둘 중 하나를 한다. `unrecognized_name(112)` 치명 경고로 인사를 끊거나, 아무 일 없다는 듯 그냥 진행하거나. 경고 수준으로 보내는 것은 권하지 않는데, 클라이언트마다 반응이 제각각이기 때문이다.

핵심은 이 칸이 **잠기기 전에** 나간다는 점이다. 인증서를 고르는 데 쓰려면 그럴 수밖에 없다. TLS 1.3 에서 인사의 뒷부분이 잠기게 된 뒤에도 이 칸만은 평문으로 남았다. 2026년 3월에 나온 RFC 9849 는 그것을 두고 "어느 연결이 어느 도메인을 향하는지 흘리는 이 평문 칸이 TLS 1.3 에 암호화되지 않은 채 남은 것 중 아마도 가장 민감하다" 고 적고, 첫 마디 자체를 서버 공개키로 감싸 그 칸까지 가리는 방식을 정했다. 그것이 Encrypted Client Hello 다.

## 💡 실제 사례

- **한 주소에 사이트 수십 개** — nginx 에서 `listen 443 ssl` 블록을 여러 개 두고 `server_name` 으로 가른다. 이 칸이 없으면 전부 첫 블록의 인증서를 받는다. `nginx -V` 출력에 `TLS SNI support enabled` 가 있어야 동작한다.
- **인증서가 엉뚱할 때** — `openssl s_client -connect example.com:443 -servername example.com` 으로 이름을 붙여 보고, `-servername` 을 뺐을 때와 견주면 어느 쪽 설정이 문제인지 한 번에 갈린다.
- **앞단이 뒷단으로 다시 붙을 때** — Azure Application Gateway 문서는 뒷단 주소가 IP 뿐이면 RFC 6066 에 따라 이 칸을 세우지 않는다고 적는다. 그러면 뒷단은 기본 인증서를 내밀고 이름이 안 맞아 상태 검사가 통째로 실패한다. 앞단 뒤에서 인증서가 어긋나는 사고는 대개 여기다.

## 🚫 흔한 오해

- **https 면 어디에 접속하는지도 안 보인다** — 인사 첫 마디의 이 칸은 평문이다. 접속 대상은 그대로 보이고, 가려지는 것은 그 뒤에 오가는 내용이다.
- **`Host` 헤더가 있으니 이 칸은 없어도 된다** — 순서가 반대다. `Host` 는 자물쇠가 걸린 뒤에 오는 HTTP 헤더고, 인증서는 걸리기 전에 골라야 한다.
- **IP 주소로 접속해도 이 칸은 채워진다** — RFC 6066 이 리터럴 IP 주소를 넣지 못하게 못박았다. IP 로 붙으면 칸이 비고 기본 인증서가 나온다.

## 📝 정리

**"인증서를 고르라고 먼저 대는 이름"** 이라고 읽으면 된다. 자물쇠를 걸기 전에 나가야 쓸모가 있는 칸이라 평문일 수밖에 없고, 그래서 주소 하나에 사이트를 여럿 얹는 일과 접속 대상이 밖에서 보이는 일이 같은 뿌리에서 나온다. 인증서가 엉뚱하게 나오면 이 칸부터 본다.

## 🧒 열 살에게

아파트 공동 현관에는 문이 하나뿐이라 누구를 찾아왔는지 먼저 말해야 그 집이 열어 주지? 그런데 그 말은 문이 열리기 전에 하는 거라, 옆에 서 있는 사람도 네가 누구를 찾는지 다 들어.

## ❓ 이해했는지

- 자물쇠가 걸린 뒤에 오는 `Host` 헤더로는 왜 인증서를 못 고르나 → 작동 원리
- 인증서가 엉뚱한 사이트 것으로 나올 때 무엇을 쳐 보면 갈리나 → 실제 사례
- https 인데도 어느 사이트에 접속하는지 중간에서 보이는 까닭은 무엇인가 → 흔한 오해
