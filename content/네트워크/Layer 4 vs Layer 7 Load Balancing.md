# Layer 4 vs Layer 7 Load Balancing (4계층과 7계층 부하 분산)

## 📝 정의

4계층은 주소와 포트만 보고 나누고, 7계층은 **내용까지 열어 보고 나눈다**.

같은 "부하 분산기" 라는 말이 두 개의 다른 물건을 가리킨다. AWS 의 NLB 와 ALB, Azure 의 Load Balancer 와 Application Gateway, Google 의 통과형과 프록시형이 각각 이 두 쪽에 서 있다.

### 이름
Layer 4 :: 주소와 포트까지
Layer 7 :: 내용까지
Load Balancing :: 짐 고르게 나누기
= 어느 층까지 열어 보고 나눌지로 갈라 놓은 이름이다

### 비유
경기장 입구의 두 가지 검표 — 표의 구역 숫자만 보고 문으로 밀어 넣으면 빠르고, 표를 읽고 무엇이 필요한지 물어 자리까지 안내하면 느리지만 알맞게 간다.

### 예
결제 쪽만 유독 느려서 그 경로로 오는 것만 따로 떼어 다른 무리로 보내 봤던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
대조: 어디까지 열어 보고 나누는가
4계층 |=| 7계층
보는 것 :: 주소와 포트 || 경로와 머리말까지
연결 :: 손님과 끝단이 직접 || 가운데가 끊고 다시
손대기 :: 그대로 흘려보낸다 || 고쳐서 보낸다
= 아래 층은 열지 않고 흘리고, 위 층은 열어 보고 고른다
```

## ⚠️ 해결하는 문제

```도해
대조: 겉봉만 보고 나누면 무엇을 못 하나
겉만 보면 || 열어 보면
경로별 나눔 :: 못 한다 || 경로마다 딴 곳
잠금 풀기 :: 끝단이 다 한다 || 앞에서 한 번에
같은 손님 :: 누군지 모른다 || 쪽지로 알아본다
= 열어 보는 값을 내는 대신, 앞에서 할 수 있는 일이 늘어난다
```

주소와 포트만 보면 "이 손님을 어느 기계로" 까지는 정할 수 있어도 "`/api` 로 시작하는 것만 저쪽으로" 는 정할 수 없다. 겉에 붙은 주소와 포트에는 그런 것이 안 적혀 있기 때문이다. 잠금을 푸는 일도 끝단이 저마다 해야 하니 증명서가 기계 수만큼 흩어진다.

7계층은 연결을 앞에서 한 번 끊고 자기가 새로 맺는다. Azure 문서는 이것을 "끊는 부하 분산기" 라 부르고, 손님이 끝단과 직접 맺는 쪽을 "통과 부하 분산기" 라 부른다. 끊는 순간 내용이 보이므로 경로로 가르고, 증명서를 한 곳에 모으고, 방화벽 규칙을 여기서 걸 수 있다. 대신 그 열어 보는 일이 지연과 값으로 붙는다.

## ⚙️ 작동 원리

통과형은 받은 것을 손대지 않고 흘린다. Google 문서는 "출발지와 목적지 주소, 규약, 포트가 바뀌지 않은 채로 뒷단에 도착한다" 고 적는다. 그래서 뒷단 기록에 손님의 진짜 주소가 그대로 찍히고, 답이 분산기를 거치지 않고 곧장 손님에게 돌아가는 방식까지 쓸 수 있다. 열어 볼 필요가 없으니 TCP·UDP 는 물론 그 밖의 규약도 그대로 지나간다.

프록시형은 두 개의 연결을 잇는 가운데 사람이다. 손님과 하나, 뒷단과 하나를 따로 맺어 놓고 내용을 옮겨 나른다. 그래서 뒷단이 보는 출발지는 손님이 아니라 분산기이고, 진짜 주소를 알려 주려면 머리말(`X-Forwarded-For`)에 따로 실어 보내야 한다. 대신 이 자리에서 경로별 가름, 잠금 풀기, 요청 검사, 쪽지로 손님 붙이기가 전부 가능해진다.

한쪽만 고르는 것이 아니라 겹쳐 쓰는 배치가 흔하다. 바깥에는 7계층을 두어 검사와 잠금을 맡기고, 그 뒤 사설 망 안에서는 4계층으로 빠르게 흘리는 식이다.

## 📊 비교: 어느 쪽을 언제 고르나

| | 4계층 | 7계층 |
|---|---|---|
| **받는 것** | TCP·UDP 등 규약 대부분 | HTTP 계열만 |
| **나누는 기준** | 주소·포트 | 도메인·경로·머리말 |
| **손님 주소** | 그대로 보인다 | 머리말로 넘겨야 보인다 |
| **잠금 풀기** | 끝단이 한다 | 앞에서 한 번에 |
| **요청 검사** | 못 한다 | 방화벽 규칙을 건다 |
| **대표 이름** | NLB · Azure Load Balancer | ALB · Application Gateway |

## 💡 실제 사례

- **한 도메인 여러 갈래** — `/api` 로 오는 것만 API 무리로, 나머지는 웹 무리로 보낸다. ALB·Application Gateway 같은 7계층만 할 수 있는 일이다.
- **게임과 이름 조회** — HTTP 가 아닌 것을 나눌 때는 열어 볼 수가 없으니 NLB·Azure Load Balancer 같은 4계층을 쓴다.
- **증명서 한 곳 모으기** — Application Gateway 가 앞에서 잠금을 풀면 증명서를 기계마다 깔지 않고 한 곳에서만 갈아 끼운다. Azure 문서가 이 떠넘기기를 따로 이름 붙여 권한다.

## 🚫 흔한 오해

- **7계층이 4계층보다 좋은 것이다** — 열어 보는 만큼 지연과 값이 붙고, 애초에 HTTP 가 아닌 것은 열어 볼 수도 없다. 그냥 흘려보내면 되는 것에 굳이 열어 볼 이유가 없다.
- **7계층을 쓰면 끝단이 손님의 진짜 주소를 본다** — 가운데가 연결을 끊고 새로 맺으므로 끝단에 찍히는 것은 분산기의 주소다. 진짜 주소는 머리말에 실어 따로 넘겨야 한다.
- **부하 분산기는 다 같은 물건이다** — 이름은 하나인데 받는 규약도, 나누는 기준도, 손님 주소가 보이는지도 두 쪽이 다르다. 고르기 전에 "HTTP 인가" 부터 물어야 한다.

## 📝 정리

**"겉에 적힌 것만 보느냐, 속까지 읽고 고르느냐의 차이"** 라고 읽으면 된다. 열어 보면 경로별 가름·잠금 풀기·요청 검사가 열리는 대신 지연과 값이 붙고 끝단은 손님의 진짜 주소를 잃는다. 그래서 바깥은 7계층, 안쪽은 4계층으로 겹쳐 쓰는 배치가 흔하다.

## 🧒 열 살에게

경기장 문 앞에서 표에 적힌 숫자만 슥 보고 저쪽 문으로 가라고 하면 줄이 아주 빨리 줄지? 표를 하나하나 읽고 무엇이 필요한지 물어서 자리까지 데려다주면 훨씬 잘 맞는 자리에 앉는데 그만큼 느려. 그래서 어디까지 보고 나눌지를 먼저 정해 두는 거야.

## ❓ 이해했는지

- 같은 이름 아래에서 특정 경로로 오는 것만 다른 무리로 보내려면 어느 쪽이 필요한가 → 그림
- 뒷단 기록에 손님 주소 대신 분산기 주소가 찍히는 이유는 무엇인가 → 흔한 오해
- 게임이나 이름 조회처럼 HTTP 가 아닌 것을 나눌 때 어느 쪽을 쓰나 → 비교
