# SNMP (단순 망 관리 프로토콜)

## 📝 정의

SNMP는 **장비의 값마다 번호를 매겨 두고 그 번호로 묻는 약속**이다.

값 하나하나에 붙는 번호를 OID 라 하고, 그 번호와 뜻을 적어 둔 목록이 MIB 다. 장비가 무엇인지 몰라도 번호만 알면 값을 꺼낼 수 있게 만든 것이 이 약속의 요점이다. 판이 셋인데(v1 · v2c · v3) 실무에서 갈리는 지점은 늘 같다 — 비밀번호에 해당하는 것이 평문으로 실려 가느냐다.

### 이름
Simple :: 간단하게
Network :: 서로 이어진 장비
Management :: 살피고 손대기
Protocol :: 약속
= 붙여 읽으면 "이어진 장비를 간단히 살피는 약속". 간단한 쪽은 묻는 방식이지 다루는 값이 아니다

### 비유
아파트 계량기 검침. 집집마다 정해진 자리에 눈금이 달려 있어서, 검침원은 문을 안 열고도 번호만 대고 눈금을 적어 간다.

### 예
스위치 포트가 몇 퍼센트 차 있는지 보여주는 그 그래프는, 대개 30초마다 이 방식으로 눈금을 읽어 와 그린 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 그래프의 점 하나는 어떻게 장비에서 실려 오나
관리자 :: `GetRequest` 에 OID 를 담아 161번으로 보낸다
장비 :: MIB 에서 그 번호에 해당하는 값을 찾는다
< 장비 :: `Response` 에 번호와 값을 짝지어 되돌려준다
관리자 :: 30초 뒤 같은 번호를 한 번 더 묻는다
@ 다시 묻기로 :: 두 값의 차이가 그래프의 기울기가 된다
= 장비가 말해 주는 게 아니라, 정해진 번호를 되풀이해 묻는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 장비마다 보는 법이 다르면 무엇이 곤란해지나
제각각이면 || SNMP 로
새 장비 :: 볼 도구를 새로 짠다 || 번호만 알면 된다
백 대 보기 :: 백 번 붙어야 한다 || 한 곳에서 긁는다
값의 뜻 :: 문서를 뒤진다 || MIB 에 적혀 있다
= 값을 꺼내는 방식을 표준으로 못 박아서, 도구가 장비를 몰라도 되게 만든 것이다
```

장비를 만드는 곳은 수십 군데인데 보는 사람은 한 명이다. 제조사마다 다른 명령으로 값을 꺼내야 하면 감시 도구는 장비를 하나 들일 때마다 다시 짜야 하고, 그 도구를 못 짜는 동안은 그 장비만 어둠 속에 있다.

SNMP 는 "값에 번호를 붙이고 그 번호로 묻는다" 는 방식 하나만 표준으로 고정했다. 그러면 도구는 번호를 던지는 일만 알면 되고, 장비가 무엇을 아는지는 MIB 라는 목록이 알려준다. 도구와 장비가 서로를 몰라도 되는 이유가 여기 있다.

## 🧱 구성

```도해
층: SNMP 한 대는 무엇으로 되어 있나
응용 :: 묻는 쪽 · 답하는 쪽 · 알림 보내는 쪽
디스패처 :: 들어온 메시지가 몇 판인지 보고 넘긴다
메시지 처리 :: v1 · v2c · v3 마다 다른 봉투를 푼다
보안 :: v3 에서 서명과 감추기를 맡는다
접근 제어 :: 이 번호를 이 사람이 봐도 되는지 따진다
= 위는 무엇을 묻는가이고, 아래로 갈수록 봉투를 뜯고 자격을 따지는 일이다
```

## ⚙️ 작동 원리

묻는 방식이 셋이다. `GetRequest` 는 번호를 대고 그 값 하나를 가져온다. `GetNextRequest` 는 "이 번호 다음 것" 을 가져와서, 무엇이 있는지 모르는 표를 처음부터 끝까지 훑을 때 쓴다. `GetBulkRequest` 는 그 훑기를 한 번에 몇 줄씩 가져오게 만든 것으로, `non-repeaters` 와 `max-repetitions` 로 몇 개를 한꺼번에 받을지 정한다. 값을 바꾸는 `SetRequest` 도 있지만 실무에서는 대개 막아 둔다.

반대 방향도 있다. 장비가 먼저 말을 거는 `SNMPv2-Trap` 은 162번으로 날아오고, 받았다는 확인이 없다. 확인을 받고 싶으면 `InformRequest` 를 쓴다. 실려 가는 바닥은 UDP 라, 트랩이 도중에 사라져도 보낸 쪽도 받을 쪽도 그 사실을 모른다. "알림이 안 왔으니 괜찮다" 가 성립하지 않는 이유가 이것이다.

크기 제약도 실무에 걸린다. 어떤 구현이든 484바이트짜리 메시지는 받을 수 있어야 하고 권고치가 1472바이트다. 표를 통째로 훑을 때 `max-repetitions` 를 크게 잡으면 답이 이 크기를 넘겨 잘려 돌아온다.

## 💡 실제 사례

- **포트 대역폭 그래프** — 오간 바이트를 세는 카운터를 30초 간격으로 두 번 읽고 그 차이를 시간으로 나눈다. 그래서 그래프의 점 하나는 늘 두 번의 물음으로 만들어진다.
- **온도·전원 감시** — 값이 기준을 넘으면 장비가 먼저 162번으로 트랩을 던진다. 다음 물음까지 30초를 기다리지 않으려고 이 길을 따로 둔 것이다.
- **살아 있는 장비 훑기** — `sysDescr` 과 `sysUpTime` 을 대역 전체에 던져 무엇이 몇 대 켜져 있는지, 언제 재부팅됐는지를 목록으로 만든다.

## 🚫 흔한 오해

- **커뮤니티 문자열이 비밀번호다** — v1 과 v2c 의 커뮤니티는 그냥 평문으로 실려 간다. 그 구간을 떠서 열면 `public` 이 글자 그대로 보인다. 비밀을 지키는 것은 v3 부터다.
- **알림이 안 왔으니 장비는 멀쩡하다** — 트랩은 UDP 로 던져지고 확인 응답이 없다. 장비가 죽어서 못 보냈는지, 보냈는데 없어졌는지, 정말 아무 일이 없었는지가 구분되지 않는다.
- **감시는 SNMP 로 통일하면 된다** — 앱 안에서 벌어지는 일은 MIB 에 번호가 없다. 주문이 몇 건 실패했는지 같은 값은 장비 눈금이 아니라 앱이 직접 내보내야 한다.

## 📝 정리

**"번호를 대고 눈금을 읽어 오는 그 약속"** 이라고 읽으면 된다. 값마다 번호를 붙이고 그 번호로 묻게 만든 덕에, 감시 도구는 장비가 무엇인지 몰라도 값을 꺼낼 수 있다. 대신 실려 가는 바닥이 UDP 라서 답도 알림도 조용히 사라질 수 있고, v2c 까지는 비밀번호에 해당하는 것이 평문이다.

## 🧒 열 살에게

집집마다 물을 얼마나 썼는지 재는 눈금이 밖에 달려 있지? 검침하는 아저씨는 문을 안 두드리고 정해진 자리의 눈금만 적어 가. 그리고 지난달에 적은 숫자랑 비교해야 이번 달에 물을 많이 썼는지 알 수 있어.

## ❓ 이해했는지

- 30초마다 값을 한 번씩 읽을 뿐인데 그래프에는 속도가 그려지는 이유는 무엇인가 → 작동 원리
- 감시 도구를 장비마다 새로 짜지 않아도 되는 이유는 무엇인가 → 해결하는 문제
- 사설 망 안에서만 열어 두라고 하는 말이 왜 나오나 → 흔한 오해

## 🔗 관련 용어

- [[UDP]] — 물음과 답과 알림이 실려 가는 바닥. 잃어버려도 다시 안 보낸다
- [[Metric]] — 같은 일을 장비 눈금이 아니라 앱 안쪽에서 하는 요즘 방식
- [[IPFIX]] — 같은 장비에서 눈금 대신 오간 흐름을 내보내는 쪽
- [[Prometheus]] — 주기적으로 긁어 가는 방식을 그대로 물려받은 도구
- [[Alerting]] — 트랩이 결국 닿으려 하는 자리
