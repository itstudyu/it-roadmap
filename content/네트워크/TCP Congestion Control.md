# TCP Congestion Control (티시피 혼잡 제어)

## 📝 정의

혼잡 제어는 **길이 막히는지 보아 가며 보내는 양을 스스로 줄이는 규칙**이다.

길이 얼마나 넓은지 알려주는 사람은 아무도 없다. 그래서 보내는 쪽은 조금씩 늘려 보다가 조각이 사라지면 막혔다고 판단하고 뒤로 물러선다. RFC 5681 이 정한 네 가지 동작 — 느린 시작, 혼잡 회피, 빠른 재전송, 빠른 회복 — 이 그 물러섬과 되올림의 규칙이다.

### 이름
TCP :: 차례를 지켜 나르는 약속
Congestion :: 길 막힘
Control :: 조절
= 붙여 읽으면 "길 막힘 조절". 받는 쪽 사정이 아니라 길 사정을 보고 줄인다는 뜻이다

### 비유
좁은 골목에 차를 밀어 넣을 때, 한 대라도 못 지나가면 속도를 절반으로 줄였다가 잘 빠지면 조금씩 다시 올리는 운전과 같다.

### 예
파일 하나를 받는데 속도가 확 올랐다가 뚝 떨어지고 다시 서서히 오르는, 그 톱니 모양 그래프가 이것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 번에 보낼 양은 어떻게 정해지나
느린 시작 :: 왕복마다 창을 두 배로 키운다
문턱 넘음 :: 문턱(ssthresh)을 넘으면 왕복당 한 칸씩
손실 감지 :: 같은 번호의 ACK 가 셋 오면 잃은 것으로 본다
창 반토막 :: 문턱을 절반으로 내리고 창도 줄인다
@ 되올리기 :: 줄인 자리에서 다시 조금씩 올린다
= 정해진 속도가 없다. 올려 보다 막히면 반으로 접는 톱니가 곧 속도다
```

## ⚠️ 해결하는 문제

```도해
대조: 아무도 안 줄이면 무슨 일이 벌어지나
제어 없이 || 혼잡 제어로
막힌 길 :: 그대로 밀어 넣는다 || 보내는 양을 줄인다
버려진 조각 :: 재전송이 또 막는다 || 손실이 줄어든다
여럿이 쓸 때 :: 센 쪽이 다 먹는다 || 비슷하게 나눠 쓴다
= 길에는 임자가 없다. 보내는 쪽이 스스로 접어야 다 같이 산다
```

길이 막혔을 때 가장 나쁜 반응은 "안 갔으니 다시 보내자" 다. 버려진 조각을 다시 보내면 이미 꽉 찬 길에 짐이 더 쌓이고, 그래서 더 많이 버려지고, 그래서 더 많이 재전송된다. 실제로 흐르는 양이 오히려 떨어지는 이 악순환을 막는 장치가 이것이다.

핵심은 **줄이는 주체가 길이 아니라 보내는 쪽**이라는 데 있다. 라우터는 짐을 버릴 뿐 아무에게도 통보하지 않는다. 보내는 쪽이 "답이 안 온다 = 길이 막혔다" 로 읽고 스스로 접는 것이 전부고, 인터넷 위의 모든 TCP 가 같은 규칙으로 접기 때문에 공유된 길이 무너지지 않는다.

## ⚙️ 작동 원리

보내는 쪽이 들고 있는 창은 둘이다. 하나는 받는 쪽이 "여기까지 받을 자리가 있다" 고 알려주는 **rwnd**, 다른 하나는 보내는 쪽이 혼자 짐작해서 정하는 **cwnd** 다. 실제로 한 번에 나가는 양은 **둘 중 작은 쪽**이다. 흐름 제어와 혼잡 제어가 다른 것이라는 말이 이 한 줄이다.

cwnd 를 키우는 규칙은 문턱값(ssthresh)을 기준으로 갈린다. RFC 5681 은 이렇게 적는다.

- cwnd < ssthresh 이면 느린 시작 — ACK 하나마다 `cwnd += min(N, SMSS)`, 왕복마다 대략 두 배
- cwnd > ssthresh 이면 혼잡 회피 — ACK 하나마다 `cwnd += SMSS*SMSS/cwnd`, 왕복당 대략 한 조각

줄이는 규칙도 두 가지다. 같은 번호의 ACK 가 세 번 겹쳐 오면 타임아웃을 기다리지 않고 그 조각만 즉시 다시 보내고(빠른 재전송) 문턱을 `ssthresh = max(FlightSize / 2, 2*SMSS)` 로 접는다. 타임아웃까지 갔다면 훨씬 심각한 신호라서 창을 바닥까지 내리고 느린 시작부터 다시 한다.

어느 알고리즘이 이 규칙을 실제로 실행하는지는 커널 설정이다. `sysctl net.ipv4.tcp_congestion_control` 이 지금 쓰는 것을, `sysctl net.ipv4.tcp_available_congestion_control` 이 고를 수 있는 것을 보여준다. 리눅스 커널 문서는 **reno 는 언제나 등록되어 있다**고만 못 박고, 기본값은 커널 빌드 설정에 달렸다고 적는다. 지금 이 연결의 창과 재전송 수는 `ss -ti` 로 본다.

## 📊 비교: 느린 시작과 혼잡 회피는 무엇이 다른가

| | 느린 시작 | 혼잡 회피 |
|---|---|---|
| **언제** | cwnd < ssthresh | cwnd > ssthresh |
| **키우는 식** | `cwnd += min(N, SMSS)` | `cwnd += SMSS*SMSS/cwnd` |
| **왕복당 결과** | 대략 두 배 | 대략 한 조각 |
| **성격** | 길 폭을 빠르게 더듬는다 | 찾은 폭 근처에서 살살 민다 |

## 💡 실제 사례

- **먼 지역에서만 느린 다운로드** — 창이 65,535바이트이고 왕복이 30ms 면 한 연결의 상한은 약 17Mbps 다. 회선이 1Gbps 라도 그렇다. 대역폭이 아니라 왕복 시간이 잡고 있는 것이다.
- **손실 0.1%에 속도가 반토막** — 조각 하나를 잃을 때마다 창이 절반으로 접히고, 다시 올리는 데 왕복이 수십 번 든다. 회선은 멀쩡한데 속도만 안 나오는 전형적인 모습이다.
- **짧은 연결을 계속 새로 맺는 서비스** — 새 연결은 언제나 느린 시작부터다. 몇 십 KB 를 보내고 끊으면 창이 커지기도 전에 끝나서, 회선의 절반도 못 쓴다.

## 🚫 흔한 오해

- **속도가 안 나오면 회선을 늘리면 된다** — 창과 왕복 시간이 상한을 정하고 있으면 회선을 열 배로 늘려도 한 연결의 속도는 그대로다. 늘려야 할 것이 창인지 회선인지부터 갈라야 한다.
- **혼잡 제어와 흐름 제어는 같은 말이다** — 흐름 제어는 받는 쪽이 벅찬지를 보는 것(rwnd)이고, 혼잡 제어는 길이 막혔는지를 보는 것(cwnd)이다. 나가는 양은 둘 중 작은 쪽이라, 엉뚱한 쪽을 붙잡고 있으면 아무리 고쳐도 안 변한다.
- **알고리즘을 바꾸면 늘 빨라진다** — 알고리즘은 같은 신호를 다르게 읽을 뿐 없는 폭을 만들지 못한다. 손실이 거의 없는 길에서는 바꿔도 차이가 안 나고, 어떤 것은 같은 길을 쓰는 옆 연결의 몫을 가져올 뿐이다.

## 🚨 주의사항

- **재전송 수부터 봐라.** `ss -ti` 의 `retrans` 와 `netstat -s` 의 재전송 통계가 0에 가까우면 범인은 혼잡 제어가 아니다.
- **한 연결로 잰 속도는 회선 속도가 아니다.** 창이 상한을 잡고 있으므로, 회선을 재려면 연결을 여러 개 동시에 써야 한다.
- **버퍼가 크다고 좋은 것이 아니다.** 중간 장비가 짐을 잔뜩 쌓아 두면 손실 대신 지연이 늘어서, 보내는 쪽은 길이 막힌 줄도 모른 채 계속 밀어 넣는다.

## 📝 정리

**"막히면 반으로 접고 괜찮으면 조금씩 올리는 그 습관"** 이라고 읽으면 된다. 속도는 회선이 정해 주는 값이 아니라 보내는 쪽이 더듬어 찾는 값이고, 그래서 왕복 시간이 길거나 손실이 있으면 회선이 넓어도 안 빨라진다.

## 🧒 열 살에게

좁은 골목에 차를 들여보낼 때 잘 빠져나가면 조금씩 더 보내고, 한 대라도 못 지나가면 얼른 절반으로 줄이지? 골목이 얼마나 넓은지 아무도 안 알려주니까 보내 보면서 알아내는 수밖에 없어. 다들 그렇게 눈치를 봐야 골목이 아주 막혀 버리지 않아.

## ❓ 이해했는지

- 회선을 열 배로 늘렸는데 한 파일 받는 속도가 그대로다. 왜인가 → 흔한 오해
- 같은 번호의 ACK 가 셋 오면 보내는 쪽은 무엇을 하나 → 그림
- 짧은 연결을 계속 새로 맺으면 왜 전속력이 안 나오나 → 실제 사례
