# HTTP/3

## 📝 정의

HTTP/3 은 **TCP 를 버리고 QUIC 위로 옮긴 HTTP**다.

[[QUIC]] 은 UDP 위에 새로 얹은 전송 프로토콜이다. 스트림 여러 개를 각자 독립으로 나르고, TLS 1.3 을 자기 손잡기 안에 품는다. 2022년 RFC 9114 가 정한 HTTP/3 은 [[HTTP/2]] 의 설계를 거의 그대로 물려받으면서, 스트림의 수명과 흐름 제어를 QUIC 에 넘겨버렸다.

### 비유
짐과 주소는 그대로 두고 운송회사만 바꾼 것으로, 새 회사는 상자 하나가 늦어도 나머지를 먼저 내려준다.

### 예
지하철에서 신호가 오락가락할 때 페이지가 통째로 멈추지 않고 이미지 한 장만 늦게 채워지는 쪽이 이것이다.

### 직접
브라우저 개발자 도구 네트워크 탭의 '프로토콜' 열을 켜고 구글이나 유튜브를 열어 보라. `h3` 이라고 적힌 줄이 이 판으로 오간 것이다.

## 🖼️ 그림으로 보기

```도해
층: HTTP/3 은 무엇 위에 올라타 있나
HTTP/3 :: 메서드·상태 코드는 그대로. 스트림마다 프레임을 얹는다
QUIC :: 스트림을 각자 독립으로 나르고 TLS 1.3 을 품는다
UDP :: 순서도 재전송도 없는 최소한의 배달만 한다
IP :: 조각에 주소를 붙여 길을 고른다
= TCP 가 있던 자리를 QUIC 이 대신한다. 그래서 그 아래가 UDP 다
```

## ⚠️ 해결하는 문제

```도해
대조: 바탕을 TCP 에서 QUIC 으로 바꾸면 무엇이 달라지나
TCP 위에서 || QUIC 위에서
조각 하나 잃으면 :: 전부 멈춘다 || 그 흐름만 멈춘다
순서 맞추기 :: 연결 전체가 한 줄 || 흐름마다 한 줄
연결 맺기 :: 손잡기 두 번 || 한 번에 합친다
= 멈춤을 연결 전체가 나눠 쓰던 것을, 흐름 하나에 가둔 것이다
```

HTTP/2 는 앱 층의 줄서기를 없앴지만 그 아래는 손대지 않았다. RFC 9114 는 그 한계를 이렇게 적었다 — HTTP/2 의 병렬성이 TCP 의 손실 복구에는 보이지 않기 때문에, 조각 하나가 사라지거나 순서가 뒤바뀌면 그 조각과 아무 상관없는 거래까지 전부 멈춰 선다.

QUIC 은 신뢰성을 **스트림 단위로** 제공하고 혼잡 제어는 연결 전체로 한다. 그래서 잃은 조각은 그 스트림만 멈춰 세우고 나머지는 계속 내려온다. 여기에 TLS 손잡기를 전송 계층 안으로 끌어들여, 연결을 맺는 동안 주고받아야 하는 메시지 수도 줄였다.

## ⚙️ 작동 원리

HTTP/3 은 HTTP/2 의 프레임 구조를 스트림마다 그대로 쓴다. 다만 QUIC 이 이미 하는 일은 넘겼다.

| HTTP/2 에서는 | HTTP/3 에서는 |
|---|---|
| 스트림과 흐름 제어를 직접 다뤘다 | QUIC 에 맡긴다 |
| 헤더 압축이 HPACK 이었다 | QPACK 으로 갈았다 |
| TLS 를 TCP 위에 따로 얹었다 | QUIC 안에 들어 있다 |

HPACK 을 버린 이유가 이 프로토콜의 성격을 잘 보여준다. HPACK 은 압축한 헤더가 **순서대로 도착한다**는 것을 전제로 하는데, QUIC 은 그걸 보장하지 않는다. 그래서 QPACK 은 표를 고치는 일과 그 표를 참조하는 일을 갈라 따로 보낸다.

찾아가는 방법도 다르다. 클라이언트는 이 서버가 HTTP/3 을 하는지 미리 모른다. 서버가 `Alt-Svc: h3=":50781"` 같은 응답 헤더로 알려주고, 그걸 본 클라이언트가 그 UDP 주소로 QUIC 연결을 연다. 손잡기에서 `h3` 이라는 이름표를 골라 이 프로토콜을 쓰겠다고 밝힌다.

## 💡 실제 사례

- **모바일에서 신호가 오락가락할 때** — 조각을 잃어도 그 스트림만 멈춘다. 다른 요청의 응답은 계속 내려온다.
- **처음 접속이 짧아진다** — TLS 손잡기가 QUIC 손잡기 안에 들어 있어서, 데이터를 보내기 전에 주고받아야 할 메시지 수가 줄어든다.
- **서버가 `Alt-Svc` 로 알린다** — 브라우저는 먼저 HTTP/1.1 이나 HTTP/2 로 붙었다가, 이 헤더를 보고 다음부터 HTTP/3 로 옮겨 간다.

## 🚫 흔한 오해

- **UDP 를 쓰니까 데이터가 사라져도 그냥 넘어간다** — 사라진 것을 되찾는 일을 QUIC 이 한다. RFC 9114 는 HTTP/3 이 QUIC 에 기대어 "믿을 수 있고 스트림마다 순서가 맞는 전달" 을 받는다고 적었다.
- **HTTP/3 을 켜면 항상 빨라진다** — UDP 가 막힌 망에서는 QUIC 연결이 아예 안 열려서 HTTP/2 로 되돌아가야 한다. HTTP/3 이 되찾아 주는 것은 조각을 잃거나 순서가 뒤바뀔 때의 멈춤이라, 그런 일이 없는 망에서는 되찾을 것도 없다.
- **HTTP/3 은 완전히 새로운 웹 규칙이다** — 메서드·상태 코드·헤더 같은 HTTP 의 뜻은 그대로다. RFC 9114 가 정한 것은 그 뜻을 QUIC 위에 어떻게 얹느냐뿐이다.

## 🚨 주의사항

- **UDP 가 막히면 못 붙는다.** 중간에서 UDP 를 막아두면 QUIC 연결이 실패한다. RFC 9114 도 이럴 때는 TCP 기반 HTTP 로 다시 붙어야 한다고 적었다.
- **포트가 고정이 아니다.** 서버는 아무 UDP 포트로도 HTTP/3 을 낼 수 있다. 클라이언트는 `Alt-Svc` 가 알려준 포트로 간다.
- **HTTP/2 확장이 그대로 오지는 않는다.** QUIC 이 흡수해버린 HTTP/2 기능이 있어서, RFC 9114 는 확장을 옮기는 방법을 따로 적어두었다.

## 📝 정리

**"짐은 그대로 두고 운송회사만 바꾼 그 판"** 이라고 읽으면 된다. 스트림마다 손실 복구를 따로 하니 조각 하나를 잃어도 그 스트림만 멈추고, TLS 를 품은 손잡기 덕에 연결을 맺는 값도 줄었다. 대신 UDP 가 막힌 자리에서는 연결 자체가 열리지 않아 HTTP/2 로 돌아갈 길이 필요하다.

## 🧒 열 살에게

이삿짐은 그대로인데 옮겨 주는 회사만 바꿨다고 해 봐. 예전 회사는 상자 하나가 늦으면 트럭을 세우고 다 같이 기다렸는데, 새 회사는 늦은 상자만 빼놓고 나머지를 먼저 집에 들여놔 줘. 그래서 신호가 흔들려도 화면이 통째로 멈추지 않고 그림 한 장만 늦게 채워져.

## ❓ 이해했는지

- UDP 위에 올렸는데도 데이터가 안 사라지는 이유는 → 흔한 오해
- HTTP/3 이 HPACK 을 버리고 QPACK 으로 간 까닭은 → 작동 원리
- 브라우저는 이 서버가 HTTP/3 을 한다는 걸 어떻게 아나 → 실제 사례

## 🔗 관련 용어

- [[HTTP/2]] — 설계를 물려주고 못 푼 문제까지 넘긴 앞 판
- [[UDP]] — QUIC 이 올라탄 바탕. 순서도 재전송도 없는 쪽
- [[TCP]] — HTTP/3 이 비운 자리. 여기서 오던 줄서기가 문제였다
- [[QUIC]] — HTTP/3 이 올라탄 전송 프로토콜. TLS 1.3 을 품고 스트림을 따로 나른다
- [[Packet]] — 하나 잃었을 때 무엇까지 멈추느냐가 이 단어의 요점
