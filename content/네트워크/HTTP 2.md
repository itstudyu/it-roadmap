# HTTP/2

## 📝 정의

HTTP/2 는 **한 연결에 여러 요청을 겹쳐 보내는 HTTP**다.

2022년 RFC 9113 이 지금의 규격이다(그전의 RFC 7540 을 대체했다). HTTP/1.0 은 한 TCP 연결에 요청 하나만 띄울 수 있었고, HTTP/1.1 이 요청을 연달아 보내는 방법을 붙였지만 앱 층의 줄서기가 그대로 남았다. 그래서 브라우저는 연결을 여러 개 열어 버텼다.

### 비유
번호표를 받아 앉아 기다리는 은행 창구처럼, 오래 걸리는 사람 뒤에 줄이 막히지 않고 먼저 끝난 순서로 나간다.

### 예
이미지가 많은 페이지가 위에서부터 한 장씩 차례로 뜨지 않고 여기저기서 한꺼번에 채워지는 그 모습이다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 연결로 요청 셋을 보내면 그 안에서 무슨 일이 일어나나
브라우저 :: 요청마다 번호(스트림)를 붙인다
한 연결 :: 여러 번호의 조각이 섞여 나간다
서버 :: 번호별로 모아 요청 셋으로 되돌린다
< 서버 :: 준비된 것부터 번호를 달아 보낸다
< 브라우저 :: 번호로 갈라 어느 요청의 답인지 안다
= 연결은 하나인데, 그 안의 요청과 응답은 서로를 기다리지 않는다
```

## ⚠️ 해결하는 문제

```도해
대조: 페이지 하나에 요청이 수십 개일 때 무엇이 걸리나
HTTP/1.1 || HTTP/2
한 연결에 :: 요청 하나씩 || 여러 개를 겹쳐
느린 응답 :: 뒤가 다 막힌다 || 다른 것부터 온다
연결 수 :: 도메인마다 6개 || 하나로 충분하다
= 연결을 여러 개 열어 버티던 것을 한 연결 안의 여러 흐름으로 바꿨다
```

HTTP/1.1 에는 요청을 연달아 보내는 방법(파이프라이닝)이 있었지만 기본으로 켜지지 않았다. 응답이 요청받은 순서대로 돌아와야 하는 설계라서, 앞 요청 하나가 오래 걸리면 뒤가 전부 밀렸다. 중간의 프록시가 이걸 제대로 다루지 못하는 경우도 많았다.

그래서 브라우저는 한 도메인에 연결을 여러 개 열었다. 예전에는 2~3개, 지금은 6개가 흔하다. 연결마다 손잡기 값을 다시 내야 하고 혼잡 제어도 따로 굴러가니, 병렬을 얻는 값이 비쌌다. HTTP/2 는 요청마다 번호를 붙여 **한 연결 안에서 겹쳐 보내는** 방식으로 이 값을 없앴다.

## ⚙️ 작동 원리

HTTP/2 는 HTTP 의 뜻을 바꾸지 않는다. 메서드·상태 코드·URI·헤더 필드는 그대로고, 바뀐 것은 그것을 어떤 모양으로 실어 보내는가다.

| 무엇 | 하는 일 |
|---|---|
| 프레임 | 전송의 기본 단위. `HEADERS` 와 `DATA` 가 요청·응답의 몸통이다 |
| 스트림 | 요청·응답 한 쌍이 갖는 번호. 서로 거의 독립이다 |
| HPACK | 되풀이되는 헤더 필드를 표로 압축한다 |
| 흐름 제어 | 받는 쪽이 소화할 만큼만 보내게 막는다 |
| 우선순위 | 급한 것을 먼저 보내달라고 알린다 |

스트림이 서로 거의 독립이라, 요청 하나가 막히거나 멈춰도 다른 스트림은 진행한다. 한 연결에서 동시에 열 수 있는 스트림 수는 서버가 정해 알려주는데, RFC 9113 은 병렬성을 괜히 깎지 않도록 이 값을 **100 보다 작게 두지 말라**고 권한다.

헤더 압축이 버는 것도 작지 않다. HTTP 헤더는 요청마다 거의 같은 내용을 되풀이하는데, RFC 9113 은 압축 덕에 **요청 여럿을 [[Packet]] 하나에 담을 수도 있다**고 적었다. 새 연결에서 TCP 혼잡 창이 금방 차버리던 문제가 여기서 줄어든다.

## 💡 실제 사례

- **이미지가 많은 페이지** — 요청 수십 개가 한 연결 안에서 겹쳐 나간다. 연결을 새로 맺는 값을 그만큼 안 낸다.
- **도메인 쪼개기를 되돌린다** — HTTP/1.1 때는 연결 수 한계를 피하려고 정적 파일을 여러 하위 도메인에 흩었다. HTTP/2 에서는 그게 오히려 성능에 해로워서 되돌린다.
- **응답이 도착 순서를 지키지 않는다** — 서버가 먼저 준비된 것부터 보내고, 브라우저는 스트림 번호로 어느 요청의 답인지 가른다.

## 🚫 흔한 오해

- **HTTP/2 는 HTTP 와 다른 프로토콜이다** — 메서드·상태 코드·URI·헤더 필드는 하나도 안 바뀌었다. 같은 뜻을 다른 모양으로 실어 보내는 것뿐이라 기존 앱은 고칠 게 없다.
- **HTTP/2 로 바꾸면 항상 빨라진다** — 없어진 건 앱 층의 줄서기뿐이다. RFC 9113 이 서두에 직접 적어둔 대로 TCP 층의 줄서기는 그대로여서, 조각 하나를 잃으면 그 연결에 실린 스트림이 전부 함께 멈춘다. 손실이 잦은 망에서는 한 연결에 다 모아둔 것이 오히려 약점이 된다.
- **서버 푸시로 미리 보내면 빨라진다** — 실제로는 구현이 까다로웠고 주요 브라우저 엔진에서 대부분 걷어냈다. `rel="preload"` 와 `103 Early Hints` 가 그 자리를 대신한다.

## 🚨 주의사항

- **TCP 층의 줄서기는 남는다.** RFC 9113 이 이 프로토콜로 풀지 못한다고 못 박아 둔 자리다. 그걸 겨눈 것이 [[HTTP/3]] 다.
- **도메인 쪼개기는 되돌려라.** 하위 도메인에 흩어두면 연결이 다시 갈라져서 한 연결에 모으려는 설계와 어긋난다.
- **우선순위 신호는 갈아탔다.** RFC 9113 은 RFC 7540 의 우선순위 방식을 폐기했다. 옛 방식에 맞춰둔 설정은 다시 봐야 한다.

## 📝 정리

HTTP/2 는 HTTP 의 뜻을 그대로 두고 실어 보내는 모양만 바꾼 개정이다. 요청마다 번호를 붙여 한 연결 안에서 겹쳐 보내니 연결을 여러 개 열어 병렬을 만들던 일이 필요 없어졌다. 다만 바탕이 여전히 TCP 라서, 조각 하나를 잃으면 그 연결이 함께 멈추는 문제는 남았다.

## ❓ 이해했는지

- 브라우저가 한 도메인에 연결을 여섯 개씩 열던 이유는 → 해결하는 문제
- 서버가 응답 순서를 바꿔 보내도 브라우저가 안 헷갈리는 이유는 → 그림
- HTTP/2 인데도 조각 하나가 사라지면 전부 멈추는 이유는 → 흔한 오해

## 🔗 관련 용어

- [[HTTP]] — HTTP/2 가 모양만 바꿔 실어 보내는 그 규칙
- [[HTTP/3]] — HTTP/2 가 못 푼 TCP 층 줄서기를 QUIC 로 푼 다음 판
- [[TCP]] — HTTP/2 가 올라타는 바탕. 여기서 오는 한계가 그대로 남는다
- [[Packet]] — 하나 잃으면 그 연결의 스트림이 다 멈춘다고 할 때의 그 조각
