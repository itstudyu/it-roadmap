# Dedicated Cloud Interconnect (전용 회선 연결)

## 📝 정의

Dedicated Cloud Interconnect는 **회사 망과 클라우드를 전용 회선으로 잇는 것**이다.

온프레미스와 클라우드를 잇는 길은 셋이다 — 그냥 인터넷, 인터넷 위에 잠금을 씌운 VPN, 그리고 남의 망을 아예 안 지나는 전용 회선. 이 편은 셋째 길이고, 사업자마다 이름이 다르다(Dedicated Interconnect · Direct Connect · ExpressRoute).

### 이름
Dedicated :: 그 회사 전용
Cloud :: 클라우드
Interconnect :: 서로 맞대어 잇기
= 붙여 읽으면 "그 회사만 쓰는 선으로 클라우드와 맞대어 잇기"

### 비유
공장과 창고 사이에만 낸 사설 도로 — 시내가 아무리 막혀도 그 길만은 늘 같은 시간이 걸린다.

### 예
본사에 쌓인 수십 테라를 옮기려는데 인터넷으로 보내면 몇 주가 걸린다고 계산이 나온 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 회사 망과 클라우드는 어디서 어떻게 맞닿나
회사 장비 :: 우리 쪽 라우터를 만남 시설 안에 둔다
만남 시설 :: 두 회사의 장비가 같은 건물에 들어가 있다
교차 연결 :: 두 장비 사이를 광케이블 한 가닥으로 잇는다
길 나눔 :: 서로의 길 목록을 BGP 로 주고받는다
사내 망 :: 사설 주소 그대로 오간다. 인터넷을 안 지난다
= 인터넷을 빌려 타는 게 아니라, 두 망이 한 건물에서 선으로 맞닿는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 인터넷으로만 이으면 무엇이 아쉬운가
인터넷 너머로 || 전용 회선으로
지연 :: 날마다 들쭉날쭉 || 거의 일정하다
굵기 :: 남는 만큼만 쓴다 || 산 만큼 보장된다
지나는 곳 :: 남의 망을 거친다 || 두 망만 지난다
= 값을 더 내고 사는 것은 속도가 아니라 "늘 같음" 이다
```

인터넷은 굵기도 지연도 아무도 약속해 주지 않는다. 평소엔 멀쩡하다가 저녁마다 느려지고, 어느 날은 경로가 바뀌어 왕복이 두 배가 된다. 온프레미스 데이터베이스를 클라우드 앱이 붙들고 쓰는 구조라면 이 흔들림이 그대로 응답 시간의 흔들림이 된다.

전용 회선은 남의 망을 안 지나게 만들어 이 흔들림을 걷어낸다. 세 사업자의 문서가 하나같이 같은 말을 쓴다 — Google 은 "공용 인터넷을 지나지 않는 직접 물리 연결", AWS 는 "네트워크 경로에서 인터넷 사업자를 건너뛴다", Microsoft 는 "공용 인터넷을 지나지 않기 때문에 더 나은 신뢰성과 일정한 지연" 이라고 적는다. 값은 대개 포트를 붙들고 있는 시간과 나가는 양으로 매겨진다.

## 📊 비교: 온프레미스를 클라우드에 잇는 세 갈래

| | 인터넷 | VPN | 전용 회선 |
|---|---|---|---|
| **지나는 곳** | 남의 망 여럿 | 남의 망 여럿 | 두 망만 |
| **지연** | 그날그날 다르다 | 인터넷 + 잠금 비용 | 거의 일정 |
| **굵기** | 보장 없음 | 터널 하나만큼 | 산 만큼 보장 |
| **잠금** | 앱이 알아서 | 기본으로 걸린다 | **기본은 안 걸린다** |
| **값** | 나가는 양 | 나가는 양 + 게이트웨이 | 포트 시간 + 나가는 양 |
| **깔리는 시간** | 즉시 | 수십 분 | 수 주 |

## 💡 실제 사례

- **대량 이전** — 창고에 쌓인 자료를 클라우드로 옮길 때, 굵은 회선을 잠깐 사서 몇 주 걸릴 일을 며칠로 줄인다.
- **반반 구조** — 데이터베이스는 사내에 두고 앱만 클라우드에 두는 동안, 둘 사이를 이 회선으로 잇고 응답 시간의 흔들림을 없앤다.
- **규정 대응** — 자료가 공용 인터넷을 지나면 안 된다는 요구가 있을 때, 물리적으로 안 지나게 만드는 유일한 답이 이것이다.

## ⚙️ 작동 원리

굵기는 회선의 종류와 그 위에 붙이는 몫으로 두 번 나뉜다. Google 은 10Gbps · 100Gbps · 400Gbps 회선을 최대 여덟 가닥까지 묶게 하고, 그 위에 50Mbps 부터 50Gbps 까지의 몫을 잘라 쓰게 한다. Azure 는 회선 자체를 50Mbps 부터 10Gbps 까지 골라 사게 한다. 회선의 종류는 만든 뒤에 못 바꾸므로 처음 고르는 자리가 중요하다.

약속받는 가동률은 회선 개수가 정한다. Google 문서는 99.99% 를 받으려면 두 도시에 걸쳐 최소 네 가닥, 99.9% 는 같은 도시 안의 서로 다른 구역에 최소 두 가닥이 필요하다고 적는다. Azure 도 회선 하나마다 두 대의 경계 라우터에 각각 붙는 이중 연결을 요구하고, 최대 회복력은 서로 다른 두 곳에 회선 둘을 두는 것이라고 적는다. 한 가닥만 사면 아무리 굵어도 가장 높은 약속은 못 받는다.

길은 BGP 로 주고받는다. 회사 라우터와 클라우드 쪽 라우터가 서로 "우리 쪽에는 이런 대역이 있다" 고 알려 주고, 그 목록대로 오간다. 그래서 양쪽 주소 대역이 겹치면 곤란해진다.

## 🚫 흔한 오해

- **전용선을 깔았으니 오가는 내용은 저절로 잠긴다** — 아니다. Google 문서는 Interconnect 가 기본으로 암호화되지 않는다고 적고, 필요하면 그 위에 다시 VPN 을 얹으라고 안내한다. 남이 못 지나는 길인 것과 내용이 잠긴 것은 다른 이야기다.
- **전용선이 인터넷보다 무조건 빠르다** — 빨라지는 것은 대개 흔들림이지 최고 속도가 아니다. 같은 도시 안에서라면 인터넷 왕복도 이미 충분히 짧고, 그때 전용선이 주는 값어치는 "늘 같은 시간" 쪽이다.
- **VPN 이면 충분한데 굳이 살 이유가 없다** — VPN 은 터널 하나가 낼 수 있는 굵기에 한계가 있고 잠그고 푸는 값이 지연으로 붙는다. 사내와 클라우드 사이가 늘 굵게 오가는 구조라면 이 한계가 먼저 온다.

## 📝 정리

**"인터넷을 안 지나고 두 망을 선으로 맞댄 길"** 이라고 읽으면 된다. 돈을 더 내고 사는 것은 최고 속도가 아니라 늘 같은 지연과 보장된 굵기이며, 가장 높은 가동률은 회선을 여러 곳에 여러 가닥 두었을 때만 받는다. 길이 사설이라고 내용까지 잠기는 것은 아니어서 잠금은 따로 얹어야 한다.

## 🧒 열 살에게

학교랑 집 사이에 우리만 다니는 길을 하나 새로 깔았다고 해 봐. 큰길이 아무리 막혀도 그 길은 늘 똑같은 시간에 도착하지만, 길을 까는 값은 우리가 다 내야 하고 깔리는 데 몇 주가 걸려. 그리고 남이 못 다니는 길이라는 거지, 들고 가는 가방이 잠긴다는 뜻은 아니야.
