# MTU (최대 전송 단위)

## 📝 정의

MTU 는 **한 번에 실어 보낼 수 있는 조각의 최대 크기**다.

이더넷의 1500바이트는 표준이 정한 값이라기보다 전 세계 장비가 그렇게 맞춰 온 사실상의 기본값이다. Azure 문서도 "Azure VM 의 기본 MTU 이자 전 세계 대부분 장비의 기본 설정" 이라고 같은 값을 적는다. 이 선을 넘긴 조각은 쪼개지거나, 쪼갤 수 없으면 버려진다.

### 이름
Maximum :: 가장 큰
Transmission :: 실어 보내기
Unit :: 한 덩어리
= 붙여 읽으면 "한 번에 실어 보낼 가장 큰 덩어리". 그 선을 넘으면 쪼개지거나 사라진다

### 비유
엘리베이터 문 크기와 같다. 아무리 급한 짐이라도 문보다 크면 나눠 싣거나 계단으로 돌아가는 수밖에 없다.

### 예
사내망에서는 잘 되던 파일 전송이 VPN 만 켜면 중간에 멈춰 버리는 그 증상이 대개 이것이다.

### 직접
터미널에서 `ping -c1 -M do -s 1472 1.1.1.1` 을 쳐 보라(맥은 `ping -c1 -D -s 1472`). 답이 오면 그 길은 1500 을 통과한다는 뜻이다.

## 🖼️ 그림으로 보기

```도해
층: 한 조각에 실을 수 있는 크기는 어디서 깎이나
이더넷 프레임 :: 1522바이트 — 머리 14 + 태그 4 + 꼬리 4 포함
IP 조각 :: 1500바이트 — 이 선이 MTU 다
TCP 내용 :: 1460바이트 — 헤더 40을 뺀 MSS
터널 안 :: 1350바이트 안팎 — 터널 헤더가 또 먹는다
= 겉을 감쌀수록 진짜 내용이 들어갈 자리는 줄어든다. MTU 는 그 둘째 칸의 선이다
```

## ⚠️ 해결하는 문제

```도해
대조: 길마다 문 크기가 다르면 무엇이 문제인가
크기를 모르면 || 크기를 맞추면
큰 조각 :: 중간에서 버려진다 || 애초에 안 만든다
쪼개짐 :: 하나 잃으면 다 잃음 || 쪼갤 일이 없다
증상 :: 되다 말다 한다 || 크기와 무관해진다
= 길마다 문 크기가 다르다. 가장 좁은 문에 맞춰야 짐이 끝까지 간다
```

한 조각을 쪼개면 비용이 두 번 든다. 쪼개는 쪽도 붙이는 쪽도 CPU 와 메모리를 쓰고, 조각 중 하나만 잃어도 원래 짐 전체를 다시 보내야 한다. Azure 문서는 여기에 더해 가속 네트워킹이 쪼개진 조각을 처리하지 못하고 느린 경로로 떨어진다는 것, 순서가 뒤바뀐 조각은 아예 버린다는 것을 적는다.

그래서 실제 운영에서 MTU 는 "성능을 올리는 손잡이" 가 아니라 **장애의 원인을 가르는 값**으로 쓰인다. 작은 것은 되는데 큰 것만 안 되면 거의 항상 여기다.

## ⚙️ 작동 원리

경로 위 가장 좁은 구간의 MTU 를 경로 MTU 라 부르고, 그 값은 협상으로 정하지 않는다. 한 번 부딪혀 보고 알아낸다.

```도해
흐름: 경로에서 가장 좁은 곳을 어떻게 알아내나
보내는 쪽 :: DF 비트를 세워 1500 으로 보낸다
좁은 구간 :: 못 지나간다. 쪼갤 수도 없다
그 라우터 :: ICMP Type 3 Code 4 를 되돌린다
< 보내는 쪽 :: 그 안에 적힌 다음 구간 크기로 낮춘다
= 경로 MTU 는 합의된 값이 아니라, 튕겨 보고 알아낸 값이다
```

RFC 1191 은 이 되돌아오는 메시지에 **다음 구간의 MTU 를 숫자로 적어 보내라**고 정했다. 그 숫자가 0 이면 옛 장비라는 뜻이고, 그때는 576 까지 낮추고 DF 를 포기하라고 적는다. IPv6 에서는 중간 장비가 아예 쪼갤 수 없어서, 대신 `ICMPv6 Packet Too Big (Type 2)` 이 같은 일을 한다.

문제는 이 메시지가 자주 막힌다는 것이다. 방화벽이 ICMP 를 통째로 버리면 보내는 쪽은 낮춰야 한다는 사실을 영영 모르고 같은 크기를 계속 재전송한다. 이것이 **MTU 블랙홀**이고, 리눅스는 이를 대비해 `net.ipv4.tcp_mtu_probing` 으로 ICMP 없이 크기를 더듬어 내려가는 길을 열어 둔다. 다만 기본값은 꺼짐(0)이라, 블랙홀이 의심되면 1(ICMP 블랙홀을 감지하면 켠다)이나 2(항상 켠다)로 직접 올려야 한다.

손에 쥘 명령은 넷이다.

- `ip link show eth0` — 이 장비에 걸린 MTU
- `tracepath 1.1.1.1` — 구간별로 `pmtu` 가 어디서 꺾이는지
- `ping -M do -s <크기>` — 그 크기가 통과하는지 (28 을 더한 값이 실제 조각 크기다)
- `iptables -t mangle -A FORWARD -p tcp --syn -j TCPMSS --clamp-mss-to-pmtu` — 악수 때 MSS 를 경로에 맞춰 낮춰 준다

## 📊 비교: 어디서 어떤 값을 쓰나

| 자리 | MTU | 근거 |
|---|---|---|
| **보통 이더넷** | 1500 | 전 세계 장비의 기본값 |
| **AWS 사설 가상 인터페이스** | 9001 | 점보 프레임. 프레임으로는 9023바이트 |
| **AWS 트랜싯 가상 인터페이스** | 8500 | 같은 전용선이라도 여기는 8500 |
| **AWS 인터넷 게이트웨이** | 1500 | 밖으로 나가면 점보는 못 쓴다 |
| **Azure IPsec 터널** | 1400 | MSS 는 1350 으로 물리라고 권고 |

## 💡 실제 사례

- **SSH 는 붙는데 화면이 안 넘어간다** — 로그인 인사 같은 작은 조각은 통과하고 화면을 채우는 큰 조각만 사라진다. 블랙홀의 교과서적인 모습이다.
- **VPN 만 켜면 특정 사이트가 안 열린다** — 터널 헤더가 붙어 1500 을 넘긴 조각이 중간에서 버려진다. 터널 장비에서 MSS 를 1350 으로 물려 고친다.
- **점보 프레임을 켰더니 사내는 빨라지고 밖은 죽었다** — 같은 길에 9001 과 1500 이 섞이면 넘는 쪽이 쪼개지거나 버려진다. AWS 문서도 인터넷으로 나가는 트래픽에는 1500 을 권한다.

## 🚫 흔한 오해

- **큰 조각은 알아서 쪼개진다** — DF 비트가 서 있으면 라우터는 쪼개지 않고 버린다. TCP 는 경로 MTU 를 알아내려고 그 비트를 늘 세워 두므로, 기본 상태가 곧 "쪼개지 말고 버려라" 다.
- **MTU 를 키우면 항상 빨라진다** — 경로 어딘가가 1500 이면 큰 조각은 쪼개지거나 버려져서 오히려 느려진다. Azure 문서가 VM 의 MTU 를 올리지 말라고 명시하는 이유다.
- **연결만 되면 크기는 문제가 아니다** — 악수에 쓰는 조각은 작아서 언제나 통과한다. 문제는 큰 내용이 흐르기 시작하는 그다음부터 생긴다.

## 🚨 주의사항

- **ICMP 를 통째로 막지 마라.** Type 3 Code 4(IPv6 는 Type 2)를 막으면 경로 MTU 를 알아낼 방법이 사라지고, 증상은 "가끔 멈춤" 으로만 나타난다.
- **링크의 양쪽을 같이 바꿔라.** 한쪽만 9001 로 올리면 그 차이만큼이 조용히 버려진다.
- **터널을 쓰면 MSS 를 물려라.** 경로 MTU 탐색이 막힌 환경에서는 MSS 클램핑이 유일하게 확실한 수단이다.

## 📝 정리

**"한 번에 실을 수 있는 짐 크기의 상한"** 이라고 읽으면 된다. 작은 것은 되는데 큰 것만 안 되면 여기부터 의심하고, 실제 경로의 가장 좁은 문은 `tracepath` 와 `ping -M do` 로 직접 찾아낸다.

## 🧒 열 살에게

엘리베이터 문보다 큰 짐은 아무리 밀어도 안 들어가지? 그래서 짐을 나눠 싣거나, 가는 길 중에 문이 제일 작은 곳에 미리 맞춰서 싸야 해. 어디가 제일 좁은지 모르고 그냥 보내면 잘 가다가 짐이 사라진 것처럼 뚝 멈춰.

## ❓ 이해했는지

- 작은 접속은 되는데 큰 파일만 멈추는 일은 왜 생기나 → 실제 사례
- ICMP 를 전부 막아 놓으면 어떤 일이 벌어지나 → 작동 원리
- 사내에서 점보 프레임을 켠 서버가 밖으로 나갈 때 왜 위험한가 → 흔한 오해
