# Gateway

## 📝 정의

게이트웨이(Gateway)는 서로 다른 네트워크를 연결하는 진입점 또는 출입구 역할을 하는 네트워크 장치 또는 소프트웨어입니다. 게이트웨이는 두 네트워크 간에 데이터를 주고받을 때 프로토콜, 데이터 형식, 통신 규약의 차이를 변환하여 호환성을 맞춥니다. 예를 들어, 회사 내부 네트워크(LAN)와 인터넷(WAN) 간의 통신을 담당하는 것이 게이트웨이입니다.

게이트웨이가 필요해진 이유는 모든 네트워크가 동일한 규약으로 동작하지 않기 때문입니다. 회사 내부 네트워크는 특정한 방식으로 설계되었고, 인터넷은 다른 방식으로 동작합니다. 또한 마이크로서비스 아키텍처에서는 많은 API 서버들이 다양한 프로토콜로 통신하므로, 이들 사이를 조율하는 중앙 게이트웨이가 필요합니다. 모던 IT 환경에서 게이트웨이는 보안, 인증, 라우팅, 트래픽 제어 등 많은 역할을 담당합니다.

### 한 줄 요약
> 서로 다른 네트워크 간의 통신을 중개하고 프로토콜을 변환하는 진입점

### 비유
- 🔵 **비유 1**: 국경의 국제공항처럼, 게이트웨이는 두 나라 사이의 이동을 담당합니다. 여행자(데이터)는 공항에서 여권을 검사받고(인증), 짐을 검사받은 후(보안 검사), 목적지 나라의 규칙에 따라 변환되어(프로토콜 변환) 들어갑니다.
- 🟡 **비유 2**: 번역관처럼, 게이트웨이는 한국어를 영어로, 영어를 일본어로 번역하는 중개자입니다. 일방적인 번역이 아니라, 양쪽 의도를 정확하게 전달하면서 변환합니다.

## 🎯 핵심 개념

### 1. 프로토콜 변환 (Protocol Translation)
게이트웨이의 가장 기본적인 기능은 서로 다른 프로토콜을 변환하는 것입니다. 예를 들어, 회사 내부 네트워크에서 사용하는 IPX/SPX 프로토콜을 인터넷의 TCP/IP 프로토콜로 변환합니다. 또는 레거시 시스템의 HTTP 요청을 최신 시스템의 gRPC로 변환합니다. 클라이언트와 서버가 다른 언어를 사용하더라도, 게이트웨이가 중간에서 통역하면 두 시스템이 완벽하게 통신할 수 있습니다.

### 2. 네트워크 라우팅 (Network Routing)
게이트웨이는 데이터 패킷의 목적지를 결정하고, 최적의 경로를 찾아 전달합니다. 라우팅 테이블을 참고하여 들어온 패킷을 어느 네트워크로 보낼지 결정합니다. 예를 들어, 패킷의 목적지가 192.168.1.0/24 네트워크이면 게이트웨이는 그 네트워크 방향으로 패킷을 전달합니다. 또는 목적지를 찾을 수 없으면 기본 경로(Default Route)로 패킷을 보냅니다.

### 3. API 게이트웨이의 역할
마이크로서비스 아키텍처에서 API 게이트웨이는 모든 클라이언트 요청의 진입점입니다. 클라이언트는 여러 백엔드 서비스에 직접 요청하지 않고, API 게이트웨이에 요청합니다. API 게이트웨이는 요청을 적절한 마이크로서비스로 라우팅합니다. 동시에 인증, 속도 제한, 로깅, 요청 변환 등을 중앙에서 처리하므로, 각 마이크로서비스는 자신의 비즈니스 로직에만 집중할 수 있습니다.

### 4. 보안 및 접근 제어
게이트웨이는 네트워크의 진입점이므로, 모든 외부 요청을 검사합니다. 불인가된 접근을 차단하고, 인증이 필요한 요청은 인증을 요구합니다. 또한 악의적인 요청 패턴을 감지하고 차단할 수 있습니다. DDoS 공격이 들어오면 게이트웨이에서 이를 필터링하여, 뒤의 내부 시스템이 영향을 받지 않도록 합니다.

## ⚠️ 해결하는 문제

### 문제 1: 이질적인 네트워크 간의 호환성 문제
회사가 여러 번에 걸쳐 인수합병(M&A)을 겪으면, 다양한 네트워크 시스템이 섞여 있게 됩니다. A 회사는 레거시 IPX/SPX 프로토콜을 사용하고, B 회사는 최신 TCP/IP를 사용할 수 있습니다. 이 두 네트워크를 직접 연결할 수 없으므로, 중간에 프로토콜을 변환하는 게이트웨이가 필요합니다. 게이트웨이가 없으면 두 네트워크의 통신이 불가능하여, 회사 통합 자체가 불가능합니다.

### 문제 2: 마이크로서비스 환경의 복잡성
최근의 크고 복잡한 애플리케이션은 수십 개 이상의 마이크로서비스로 구성됩니다. 클라이언트가 직접 각 마이크로서비스에 접근하려면, 모든 서비스의 위치, 포트, 프로토콜을 알아야 합니다. 서비스가 추가되거나 이동할 때마다 클라이언트 코드를 수정해야 합니다. API 게이트웨이를 사용하면 클라이언트는 게이트웨이의 주소만 알면 되고, 게이트웨이가 내부 라우팅을 담당합니다. 또한 인증, 속도 제한 같은 공통 기능을 게이트웨이에서 중앙 집중식으로 관리할 수 있습니다.

### 문제 3: 분산된 시스템의 인증 및 권한 관리
마이크로서비스 환경에서 각 서비스가 독립적으로 인증을 처리하면, 설정이 복잡하고 일관성이 떨어집니다. API 게이트웨이에서 모든 인증을 담당하면, 한 곳에서 사용자 토큰을 검증하고, 권한을 확인할 수 있습니다. JWT(JSON Web Token) 토큰을 확인하고, 만료된 토큰을 거절합니다. 각 마이크로서비스는 이미 검증된 사용자 정보를 받으므로, 중복된 인증 로직을 작성할 필요가 없습니다.

## ⚙️ 작동 원리

### 단계별 과정

1. **요청 도착**: 클라이언트가 게이트웨이의 주소로 요청을 보냅니다. 예를 들어, "api.example.com/users"로 GET 요청을 보냅니다.

2. **인증 확인**: 게이트웨이는 요청 헤더의 인증 토큰을 확인합니다. 토큰이 없거나 유효하지 않으면 401 Unauthorized를 반환합니다.

3. **속도 제한 확인**: 같은 사용자로부터 짧은 시간에 많은 요청이 들어오는지 확인합니다. 제한을 초과하면 429 Too Many Requests를 반환합니다.

4. **요청 경로 분석**: 요청의 URL 경로를 분석합니다. "/users"는 User Service로, "/orders"는 Order Service로 보내져야 합니다.

5. **요청 변환**: 필요하면 요청 형식을 변환합니다. 예를 들어, gRPC 요청을 REST API로 변환합니다.

6. **적절한 서비스로 라우팅**: 분석한 경로에 따라 요청을 해당 마이크로서비스로 보냅니다. 게이트웨이는 로드 밸런싱을 사용하여 여러 인스턴스에 분산시킬 수도 있습니다.

7. **서비스 응답 수신**: 마이크로서비스가 응답을 보냅니다.

8. **응답 변환**: 필요하면 응답 형식을 변환합니다.

9. **응답 반환**: 최종 응답을 클라이언트에게 보냅니다.

10. **로깅**: 모든 요청과 응답을 기록합니다. 나중에 성능 분석, 문제 추적, 보안 감시에 사용됩니다.

```도해
흐름: Gateway, 무슨 순서로 오가나
클라이언트 :: GET /api/users Authorization: Bea…
Gateway :: 요청 검사 (포맷, 경로 등)
Gateway :: 토큰 검증 Bearer TOKEN
인증서비스 :: 검증 결과 User ID: 123
Gateway :: 속도 제한 확인 User 123: 10req/min
Gateway :: 라우팅 결정 /api/users -> UserService
Gateway :: 요청 전달 GET /users (User ID: 123)
UserService :: JSON 응답 [ {user data} ]
Gateway :: 응답 검증 로깅
Gateway :: 응답 반환
```

## ✅ 장점과 단점

### 장점

- **시스템 간 호환성**: 서로 다른 프로토콜과 데이터 형식을 변환하여, 이질적인 시스템 간 통신을 가능하게 합니다.
- **중앙 집중식 관리**: 인증, 로깅, 속도 제한 등을 한 곳에서 관리할 수 있어, 각 마이크로서비스가 중복 로직을 작성할 필요가 없습니다.
- **유연한 라우팅**: 요청의 내용에 따라 동적으로 라우팅 규칙을 변경할 수 있습니다.
- **보안 강화**: 게이트웨이에서 악의적인 요청을 필터링하여, 뒤의 내부 시스템을 보호합니다.
- **확장성**: 마이크로서비스를 추가하거나 제거할 때, 클라이언트 코드 수정 없이 게이트웨이 설정만 변경하면 됩니다.
- **성능 최적화**: 캐싱, 압축, 연결 재사용 등으로 성능을 최적화할 수 있습니다.
- **버전 관리**: API 버전 관리를 게이트웨이에서 처리할 수 있습니다. v1, v2 API를 동시에 지원할 수 있습니다.

### 단점

- **성능 병목**: 모든 요청이 게이트웨이를 거쳐야 하므로, 게이트웨이의 성능이 전체 시스템을 제한합니다.
- **단일 장애점**: 게이트웨이가 다운되면 전체 시스템이 마비됩니다. (고가용성 구성이 필수)
- **복잡한 설정**: 라우팅 규칙, 프로토콜 변환, 인증 정책 등 많은 설정이 필요합니다.
- **디버깅 어려움**: 요청이 게이트웨이를 거쳐가므로, 문제 발생 시 원인을 파악하기 어려울 수 있습니다.
- **레이턴시 증가**: 프로토콜 변환, 인증 확인 등으로 인한 지연이 누적됩니다.
- **상태 관리**: 게이트웨이가 많은 상태(세션, 연결 정보)를 유지해야 하므로, 메모리 사용량이 증가합니다.
- **비용**: 엔터프라이즈급 API 게이트웨이(Kong, AWS API Gateway)의 라이선스 비용이 클 수 있습니다.

## 💡 실제 사용 사례

**API 게이트웨이**: Netflix, Uber, Airbnb 같은 대규모 서비스는 API 게이트웨이를 사용합니다. 클라이언트는 게이트웨이의 api.netflix.com으로 모든 요청을 보냅니다. 게이트웨이가 수십 개의 내부 마이크로서비스로 라우팅합니다. 동시에 인증, 속도 제한, 로깅을 중앙에서 처리합니다.

**엔터프라이즈 네트워크 통합**: 여러 회사가 합병될 때, 각 회사의 레거시 시스템이 다를 수 있습니다. 게이트웨이를 사용하면 이들 시스템을 연결할 수 있습니다. 레거시 IPX 네트워크와 최신 TCP/IP 네트워크를 게이트웨이로 연결합니다.

**클라우드 멀티테넌시**: 클라우드 서비스 제공자는 게이트웨이를 사용하여 여러 고객의 요청을 분리하고 라우팅합니다. 고객 A의 요청은 고객 A의 리소스로만 라우팅되도록 보장합니다. 또한 고객별 속도 제한, 가격 책정을 게이트웨이에서 관리합니다.

**레거시 시스템 마이그레이션**: 회사가 레거시 시스템을 최신 마이크로서비스로 마이그레이션할 때, 게이트웨이를 사용하여 점진적으로 전환합니다. 일부 요청은 여전히 레거시 시스템으로 보내고, 일부는 새로운 시스템으로 보냅니다. 게이트웨이가 두 시스템 간의 호환성을 관리합니다.

## 🔗 관련 용어

- **[[Proxy]]**: 클라이언트 앞에 위치하는 중개자로, 게이트웨이와 유사한 역할을 합니다.
- **[[Reverse Proxy]]**: 서버 앞에 위치하는 중개자로, API 게이트웨이와 유사합니다.
- **[[Load Balancer]]**: 요청을 여러 서버에 분산시키는 기술로, 게이트웨이가 로드 밸런싱 기능을 포함할 수 있습니다.
- **[[Firewall]]**: 네트워크 보안을 담당하는 기술로, 게이트웨이와 함께 사용됩니다.
- **[[VPN]]**: 암호화된 터널을 제공하는 기술로, 게이트웨이는 보안만 담당합니다.
- **API Gateway**: 마이크로서비스 아키텍처에서 사용하는 특화된 게이트웨이입니다.
- **Service Mesh**: 게이트웨이의 고급 기능으로, 마이크로서비스 간의 통신을 관리합니다.
- **Router**: 네트워크 패킷을 라우팅하는 장치로, 게이트웨이는 라우터의 고급 기능을 포함합니다.
- **Proxy Pattern**: 게이트웨이의 기본이 되는 디자인 패턴입니다.
