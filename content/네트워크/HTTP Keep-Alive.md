# HTTP Keep-Alive (연결 유지)

## 📝 정의

Keep-Alive 는 **한 번 맺은 연결을 끊지 않고 다음 요청에 다시 쓰는 것**이다.

HTTP/1.0 은 요청 하나에 연결 하나였다. RFC 9112 는 HTTP/1.1 부터 유지가 **기본값**이라고 못 박고, 오히려 끊고 싶으면 `Connection: close` 를 적으라고 정한다. 그래서 이 이름은 기능의 이름이라기보다 옛 방식과 구분하려고 남은 이름에 가깝다.

### 이름
HTTP :: 웹에서 주고받는 약속
Keep :: 계속 두다
Alive :: 살아 있게
= 붙여 읽으면 "살려 둔다". 볼일이 끝나도 문을 닫지 않고 다음 볼일까지 열어 둔다

### 비유
가게에 갈 때마다 문을 열고 닫는 대신, 살 것이 더 있으면 문을 열어 둔 채로 드나드는 것과 같다.

### 예
사이트 하나를 여는 데 이미지와 스크립트 수십 개가 필요한데, 그때마다 연결을 새로 맺지는 않는다.

### 직접
크롬에서 F12 를 눌러 Network 를 열고 두 번째 이후 요청의 Timing 을 보라. `Initial connection` 이 비어 있으면 앞 연결을 그대로 쓴 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 연결 위에서 요청은 어떻게 이어지나
악수 :: 세 번 오가고 연결이 열린다
첫 요청 :: 보내고 응답을 받는다
그대로 둠 :: 끊지 않고 잠깐 놀린다
다음 요청 :: 같은 연결에 그대로 실린다
시간 초과 :: 정해진 시간 동안 조용하면 닫는다
= 요청마다 새로 여는 게 아니라, 한 번 연 문을 시간이 다할 때까지 돌려 쓴다
```

## ⚠️ 해결하는 문제

```도해
대조: 요청마다 연결을 새로 맺으면 무엇이 달라지나
매번 새로 || 살려 두고 다시
왕복 :: 요청마다 악수부터 || 첫 번만 악수한다
속도 :: 늘 느린 시작 || 창이 커진 채로 간다
포트 :: 금방 바닥난다 || 몇 개로 버틴다
= 연결을 살려 두면 악수 값과 느린 시작 값을 두 번째부터 안 낸다
```

새 연결 하나에는 눈에 안 보이는 값이 둘 붙는다. 3방향 악수에 왕복 한 번, TLS 까지 붙으면 왕복이 더 붙는다. 그리고 새 연결은 언제나 혼잡 창이 가장 작은 상태에서 시작하므로, 짧게 쓰고 끊으면 회선 폭을 쓰기도 전에 끝난다.

MDN 은 브라우저가 도메인마다 여는 병렬 연결이 예전에는 2~3개였다가 지금은 보통 **여섯 개**라고 적는다. 그 여섯 개를 살려 두고 수십 개의 파일을 실어 나르는 것과, 파일 수십 개마다 악수를 다시 하는 것의 차이가 이 절에서 말하는 전부다.

## ⚙️ 작동 원리

살려 두는 쪽은 언제까지 살려 둘지를 정해야 한다. 아무도 안 쓰는 연결도 자리를 차지하기 때문이다. 서버는 그 약속을 응답에 적어 보낼 수 있다.

```
Connection: keep-alive
Keep-Alive: timeout=5, max=200
```

MDN 은 `timeout` 을 "쉬는 연결을 닫지 않고 두는 초" 로, `max` 를 "이 연결로 받을 최대 요청 수" 로 정의한다. 다만 이것은 권고고, 실제로 닫는 시점은 양쪽이 각자 정한다.

nginx 의 기본값이 그 실물이다. `keepalive_timeout 75s`(쉬는 연결을 75초까지), `keepalive_requests 1000`(한 연결로 1000개까지), `keepalive_time 1h`(연결 하나의 총 수명 1시간). 연결마다 메모리를 붙들기 때문에 주기적으로 닫아 주는 것이라고 문서가 이유까지 적어 둔다.

- `curl -v --http1.1 https://example.com` — 응답의 `Connection` 과 `Keep-Alive` 머리표를 눈으로 본다
- `ss -tn state established '( dport = :443 )'` — 지금 살아 있는 연결이 몇 개인지
- `nginx -T | grep keepalive` — 실제로 적용된 값이 무엇인지

## 📊 비교: nginx 는 무엇을 어떻게 잡아 두나

| 설정 | 무엇을 정하나 | 기본값 |
|---|---|---|
| **keepalive_timeout** | 조용한 연결을 얼마나 살려 두나 | 75초 |
| **keepalive_requests** | 한 연결로 몇 개까지 처리하나 | 1000개 |
| **keepalive_time** | 연결 하나의 총 수명 | 1시간 |

## 💡 실제 사례

- **이미지가 많은 페이지** — 브라우저가 도메인당 여섯 개쯤을 살려 두고 그 위로 수십 장을 흘린다. 매번 새로 맺으면 그만큼의 왕복이 그대로 대기 시간이 된다.
- **프록시 뒤에서 간헐적으로 뜨는 502** — 앞단이 살려 둔 연결을 뒷단이 먼저 닫으면, 그 연결에 실어 보낸 요청이 허공에서 끊긴다. 뒷단의 유지 시간을 앞단보다 길게 잡아야 사라진다.
- **로드밸런서 뒤의 쏠림** — 연결을 오래 살려 두면 그 연결이 붙은 서버로만 계속 간다. 서버를 늘려도 새 서버로 안 가는 이유가 이것이고, `keepalive_time` 같은 총 수명 상한이 그래서 있다.

## 🚫 흔한 오해

- **`Connection: keep-alive` 를 보내야 유지된다** — HTTP/1.1 은 안 적어도 유지가 기본이다. 그 머리표는 HTTP/1.0 상대를 위한 잔재고, HTTP/2 와 HTTP/3 에서는 연결 전용 머리표라서 아예 금지다.
- **오래 살려 둘수록 좋다** — 쉬는 연결도 메모리와 자리를 붙든다. 동시 접속이 많은 서버에서 시간을 길게 잡으면 아무 일도 안 하는 연결이 한도를 다 먹는다.
- **연결이 살아 있는지는 보내 보면 안다** — 상대가 이미 닫은 연결에 실은 요청은 그대로 실패한다. 그래서 재시도는 같은 것을 여러 번 해도 되는 요청에만 안전하다.

## 🚨 주의사항

- **앞단보다 뒷단을 길게 잡아라.** 뒤집히면 502 가 재현 안 되는 빈도로 뜬다.
- **TCP 의 keepalive 와 다른 것이다.** 커널의 `net.ipv4.tcp_keepalive_time` 은 기본 2시간이고, 이건 죽은 상대를 알아내려고 빈 조각을 찔러 보는 장치다. 여기서 말하는 것은 연결을 재사용하는 쪽이다.
- **HTTP/2 를 쓰면 볼 자리가 다르다.** 연결 하나에 흐름을 여럿 태우므로, 손잡이는 이 설정이 아니라 동시 흐름 수 쪽에 있다.

## 📝 정리

**"볼일이 끝나도 문을 닫지 않는 그 습관"** 이라고 읽으면 된다. 두 번째 요청부터 악수 값과 느린 시작 값을 안 내는 대신, 쉬는 연결이 자리를 붙든다. 앞단과 뒷단의 유지 시간이 뒤집히지 않게 두는 것이 실제 운영에서 제일 자주 문제가 된다.

## 🧒 열 살에게

가게에서 물건 하나 살 때마다 문을 열고 닫고, 또 열고 닫으면 힘들지? 그래서 살 게 더 있으면 문을 잠깐 열어 둔 채로 계속 드나들어. 대신 한참 아무도 안 드나들면 문을 닫아 버려.

## ❓ 이해했는지

- 앞단과 뒷단의 유지 시간이 뒤집히면 왜 502 가 뜨나 → 실제 사례
- HTTP/2 응답에 이 머리표를 넣으면 어떻게 되나 → 흔한 오해
- 커널의 tcp_keepalive_time 을 늘리면 이 문제가 풀리나 → 주의사항
