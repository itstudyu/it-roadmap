# URL (Uniform Resource Locator)

## 📝 정의

URL(Uniform Resource Locator)은 인터넷 상의 자원(웹 페이지, 이미지, 비디오, 파일 등)의 위치를 나타내는 표준화된 주소 체계입니다. 웹 브라우저가 서버에 접근하기 위해 필요한 모든 정보를 포함하며, 전 세계 모든 웹 사이트가 고유한 URL을 통해 식별됩니다. URL은 프로토콜, 도메인, 포트, 경로, 쿼리 문자열, 프래그먼트로 구성되어 있으며, 각 부분은 서로 다른 역할을 수행합니다.

URL의 역사는 1994년 Tim Berners-Lee가 웹 브라우징의 표준화를 위해 정의했습니다. 이전에는 자원에 접근하기 위한 일관된 방식이 없었지만, URL의 등장으로 전 세계 누구든 동일한 형식으로 웹 자원에 접근할 수 있게 되었습니다. 현대의 인터넷은 URL 없이는 작동할 수 없으며, 이는 웹의 기초를 이루는 핵심 개념입니다.

> **한 줄 요약**: URL은 인터넷 자원의 주소를 나타내는 표준화된 문자열로, 브라우저가 서버의 특정 자원에 접근하기 위한 정확한 위치 정보를 제공합니다.

**비유 1**: URL은 마치 우체국 배송 주소와 같습니다. 나라(프로토콜), 도시(도메인), 건물번호(포트), 아파트 호수(경로), 특정 물건(쿼리)을 모두 명시해야 편지가 정확하게 배송되듯이, URL도 모든 요소가 명확해야 브라우저가 정확한 자원에 접근할 수 있습니다.

**비유 2**: URL은 도서관의 책 위치 시스템과 유사합니다. 도서관 이름(도메인), 층(포트), 섹션(경로), 책 번호(쿼리)를 알면 원하는 책을 찾을 수 있듯이, URL의 각 구성요소를 알면 웹상의 자원을 정확히 찾을 수 있습니다.

## 🎯 핵심 개념

### 1. URL의 기본 구조

URL의 표준 형식은 `scheme://host:port/path?query#fragment`입니다. 각 부분은 선택적이거나 필수적이지만, 모두 함께 작동하여 자원의 완전한 주소를 형성합니다. **Scheme**은 사용할 프로토콜(http, https, ftp 등)을 지정하며, **Host**는 서버의 도메인 이름이나 IP 주소입니다. **Port**는 서버의 특정 포트 번호(기본값: http는 80, https는 443)를 나타내고, **Path**는 서버 내에서의 자원 위치입니다. **Query String**은 검색어나 필터 조건 같은 추가 정보를 전달하며, **Fragment**는 페이지 내 특정 섹션으로의 이동을 지정합니다.

예시: `https://www.example.com:443/search?q=programming&sort=recent#results`
- Scheme: https
- Host: www.example.com
- Port: 443
- Path: /search
- Query: q=programming&sort=recent
- Fragment: results

### 2. URI, URL, URN의 관계

URI(Uniform Resource Identifier)는 자원을 식별하는 가장 넓은 개념입니다. URI는 URL과 URN을 포함하는 상위 카테고리입니다. **URL(Uniform Resource Locator)**는 자원의 **위치**를 나타내며(How to access), **URN(Uniform Resource Name)**은 자원의 **이름**을 나타냅니다(What it is). 즉, URL은 "서버의 어느 경로에 있는가?"를 답하고, URN은 "이것이 무엇인가?"를 답합니다.

실제 예시로 보면, ISBN(International Standard Book Number)은 URN의 예입니다. ISBN:978-0-596-00712-6은 책을 식별하지만 책의 위치는 알려주지 않습니다. 반면 URL은 http://www.amazon.com/book/978-0-596-00712-6 형태로 책의 위치를 정확히 명시합니다. 현재 웹에서는 URL이 주로 사용되며, URN은 아직 충분히 보급되지 않았습니다.

### 3. URL 인코딩 (Percent Encoding)

URL에는 공백이나 특수문자를 직접 포함할 수 없으므로, 이러한 문자들을 퍼센트 인코딩(%HH 형식)으로 변환해야 합니다. 예를 들어 공백은 %20, 한글 문자 '가'는 %EA%B0%80으로 인코딩됩니다. 이는 URL이 ASCII 문자만 허용하는 표준이기 때문입니다. 모던 브라우저는 자동으로 이를 처리하지만, API 호출이나 링크 전송 시 수동으로 인코딩해야 할 경우가 많습니다.

## ⚠️ 해결하는 문제

### 문제 1: 웹 자원의 표준화된 위치 표현

**문제**: 인터넷 초기에는 각 서버가 고유한 방식으로 자원에 접근하도록 했기 때문에, 사용자가 다양한 서버의 자원에 접근하기 매우 어려웠습니다. 같은 형식의 이미지도 각 서버마다 다른 경로와 방식으로 접근해야 했습니다.

**해결 방법**: URL은 모든 웹 자원에 적용할 수 있는 표준화된 형식을 제공합니다. 프로토콜, 호스트, 경로의 통일된 구조로 인해, 사용자와 프로그래머는 직관적으로 자원에 접근할 수 있습니다. 이를 통해 웹은 진정한 의미의 '전 지구적 정보 네트워크'가 될 수 있었습니다.

### 문제 2: 동적 데이터 전달

**문제**: 정적 페이지만으로는 개인화된 정보, 검색 결과, 필터링된 데이터 등을 전달할 수 없습니다. 사용자가 선택한 옵션이나 검색어를 서버에 전달할 방법이 필요합니다.

**해결 방법**: Query String은 URL에 포함된 파라미터를 통해 동적 데이터를 서버로 전달합니다. 예를 들어, `?sort=price&filter=category`처럼 여러 파라미터를 추가할 수 있고, GET 메서드로 전달되므로 간단하고 직관적입니다. REST API 설계의 기반이 되었으며, 현대 웹 애플리케이션의 필수 요소입니다.

## ⚙️ 작동 원리

### 1단계: URL 입력 및 파싱
사용자가 브라우저의 주소창에 URL을 입력하면, 브라우저는 URL 문자열을 파싱하여 각 구성 요소를 분리합니다. 유효한 형식인지 검증하고, 특수문자가 포함되어 있으면 URL 인코딩을 수행합니다.

### 2단계: DNS 조회
Host(도메인명)를 IP 주소로 변환하기 위해 DNS 서버에 쿼리를 보냅니다. DNS 조회 결과는 캐시되므로, 반복된 방문 시 더 빠르게 처리됩니다. 만약 도메인이 존재하지 않으면 오류 메시지를 표시합니다.

### 3단계: 연결 및 요청 전송
브라우저가 해당 IP의 Port로 TCP 연결을 시도합니다. HTTPS인 경우 TLS 핸드셰이크를 거쳐 안전한 연결을 설정합니다. 그 후 HTTP 요청(GET 메서드로 Path를 요청)을 서버로 전송합니다.

### 4단계: 서버 처리 및 응답
웹 서버가 Path에 해당하는 자원을 찾아 HTTP 응답(상태 코드 + 자원 데이터)을 반환합니다. 자원이 없으면 404 에러를 반환합니다.

### 5단계: 브라우저 렌더링
브라우저가 응답받은 자원(HTML, CSS, JavaScript 등)을 처리하여 페이지를 렌더링합니다. Fragment가 포함된 경우 해당 섹션으로 스크롤 이동합니다.

## ✅ 장단점

### 장점

1. **표준화된 형식**: 모든 웹 자원이 동일한 형식으로 표현되므로, 사용자와 개발자가 직관적으로 자원에 접근할 수 있습니다.

2. **간단하고 명확**: URL의 구조가 명확하여 사람이 읽기 쉽고, 도메인명으로 자원의 정체를 쉽게 파악할 수 있습니다.

3. **세계적 상호호환성**: HTTP/HTTPS라는 표준 프로토콜을 사용하므로, 모든 웹 브라우저와 서버가 동일하게 처리할 수 있습니다.

4. **동적 데이터 전달**: Query String을 통해 파라미터를 간단하게 전달할 수 있어, REST API 설계의 기반이 됩니다.

5. **SEO 최적화**: URL 구조가 명확하면 검색 엔진이 페이지를 더 잘 이해하고 인덱싱할 수 있습니다.

### 단점

1. **길이 제한**: 브라우저마다 URL 길이 제한이 있어(일반적으로 2000자), 복잡한 쿼리 파라미터가 많으면 문제가 발생할 수 있습니다.

2. **보안 취약성**: Query String의 파라미터가 URL에 노출되므로, 민감한 정보(비밀번호, 개인정보)를 GET 파라미터로 전달하면 위험합니다.

3. **대소문자 구분**: URL은 대소문자를 구분하므로, 사용자 실수로 인한 404 에러가 발생할 수 있습니다(도메인명 제외).

4. **특수문자 인코딩**: 한글이나 특수문자를 사용할 때 URL 인코딩이 필요하여, 가독성이 떨어질 수 있습니다.

5. **상태 유지 불가**: URL만으로는 사용자 세션 상태를 유지할 수 없어, 쿠키나 세션 저장소가 필요합니다.

## 💡 실제 사례

### 사례 1: 검색 엔진의 URL 파라미터 활용
Google 검색 결과: `https://www.google.com/search?q=python+programming&num=10&start=0`
- `q=python+programming`: 검색어 (공백은 +로 인코딩)
- `num=10`: 페이지당 결과 개수
- `start=0`: 페이지 번호 (0 = 첫 페이지)

이처럼 검색 조건을 URL 파라미터로 표현하므로, 검색 결과를 북마크하거나 다른 사람에게 공유할 수 있습니다.

### 사례 2: REST API URL 설계
전자상거래 API: `https://api.example.com/products?category=electronics&sort=price&limit=20`
- 자원: products (상품)
- 필터: category=electronics (전자제품)
- 정렬: sort=price (가격순)
- 제한: limit=20 (20개 항목)

REST API는 URL의 Path와 Query String을 활용하여 직관적인 인터페이스를 제공합니다. 같은 자원을 다양한 파라미터로 요청할 수 있어 유연성이 높습니다.

### 사례 3: 앵커 링크(Fragment)를 통한 페이지 내 네비게이션
문서 URL: `https://example.com/guide#installation`
- Fragment `#installation`은 페이지가 로드된 후 `<h2 id="installation">` 요소로 자동 스크롤합니다.

이를 통해 긴 문서에서 사용자를 특정 섹션으로 직접 안내할 수 있습니다.

## 🔗 관련 용어

- **HTTP / HTTPS**: URL에서 사용하는 프로토콜
- **Domain Name**: URL의 Host 부분
- **Query String**: URL의 파라미터 전달 방식
- **REST API**: URL을 기반으로 설계되는 API 스타일
- **DNS (Domain Name System)**: 도메인명을 IP 주소로 변환하는 시스템
- **URI / URN**: URL과 함께 자원 식별을 논의할 때 나오는 개념
- **URL Encoding**: 특수문자를 URL에 포함시키기 위한 인코딩 방식
- **Port**: URL에서 지정하는 서버의 접속 포트
