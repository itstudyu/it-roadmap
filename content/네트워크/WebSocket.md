# WebSocket (웹소켓)

## 📝 정의

WebSocket은 **한 번 연결하면 양쪽이 계속 주고받는 통로**다.

HTTP 는 물어야 답이 오지만 WebSocket 은 서버가 먼저 말을 걸 수 있다. 연결은 HTTP 요청으로 시작해서 도중에 갈아탄다.

### 비유
전화 통화. 한 번 걸어 두면 끊을 때까지 양쪽이 아무 때나 말할 수 있다.

## 🖼️ 그림으로 보기

```도해
흐름: 브라우저와 서버는 어떻게 계속 이어진 채로 있나
브라우저 :: HTTP 요청에 갈아타자는 헤더를 붙여 보낸다
서버 :: 101 로 답하며 프로토콜을 바꾼다
연결 :: 그대로 열린 채 남는다. 다시 맺지 않는다
브라우저 :: 보낼 게 생기면 프레임 하나를 던진다
서버 :: 서버 쪽에서도 먼저 프레임을 보낸다
어느 쪽 :: 닫자는 프레임을 보내면 거기서 끝난다
= 요청 없이도 서버가 먼저 말을 거는 것이 HTTP 와의 차이다
```

## ⚠️ 해결하는 문제

```도해
대조: 새 메시지가 왔는지 1초마다 물어보면 어떻게 되나
폴링으로 || WebSocket 으로
빈 응답 :: 대부분이 빈손 || 있을 때만 온다
헤더 :: 매번 1KB 가까이 || 프레임 몇 바이트
지연 :: 최대 1초 기다림 || 생기는 즉시
= 계속 물어보는 대신 오갈 것이 있을 때만 흐르게 바꾼다
```

HTTP 는 클라이언트가 물어야 답이 온다. 그래서 새 메시지가 왔는지 알려면 1초마다 물어보는 수밖에 없었다. 사용자 천 명이면 초당 천 번의 요청이 들어오고 그중 대부분은 새 게 없다는 답만 받는다. 요청마다 헤더가 1KB 가까이 붙으니 오가는 양도 그만큼 는다.

WebSocket 은 연결을 한 번 열고 그대로 둔다. 새 게 생겼을 때만 프레임이 흐르고 그 프레임의 헤더는 몇 바이트 수준이다. 서버가 먼저 보낼 수 있으니 다음 물어볼 때까지 기다리는 시간도 없어진다.

## ⚙️ 작동 원리

```도해
층: WebSocket 은 어느 자리에 얹혀 있나
내 코드 :: send 를 부르고 onmessage 를 기다린다
WebSocket :: 보낼 것을 프레임으로 감싸고 받은 걸 푼다
TCP :: 순서와 빠짐없음을 챙기는 아래층
= 웹 요청과 같은 연결 위에 서고 오가는 방식만 다르다
```

시작은 평범한 HTTP 요청이다. `Upgrade: websocket` 헤더를 붙여 보내면 서버가 `101 Switching Protocols` 로 답하고, 그 순간부터 같은 연결 위에서 WebSocket 프레임이 오간다. 포트를 새로 열지 않으니 쓰던 웹 서버 주소를 그대로 쓴다.

오가는 단위는 프레임이다. 글자를 담는 텍스트 프레임과 파일 같은 걸 담는 바이너리 프레임이 있고, 살아 있는지 확인하는 핑과 퐁 프레임이 따로 있다. 닫을 때도 닫자는 프레임을 보낸다.

## 📊 비교: WebSocket vs SSE vs Long Polling

| | WebSocket | SSE | Long Polling |
|---|---|---|---|
| 방향 | 양쪽 다 | 서버에서만 | 서버에서만 |
| 바탕 | 갈아타서 `ws://` | HTTP 그대로 | HTTP 그대로 |
| 끊겼을 때 | 직접 다시 붙인다 | 브라우저가 알아서 | 직접 다시 붙인다 |
| 맞는 자리 | 채팅, 게임, 협업 | 알림, 피드, 로그 | 가벼운 갱신 |

## 💡 실제 사례

- **채팅** — 한 명이 보낸 글을 서버가 접속 중인 나머지 모두에게 그대로 밀어준다.
- **협업 편집** — 다른 사람이 친 글자와 커서 위치가 기다림 없이 화면에 반영된다.
- **실시간 시세** — 관심 종목을 구독해 두면 값이 바뀔 때마다 서버가 먼저 보낸다.

## 🚫 흔한 오해

- **WebSocket 은 HTTP 를 대신하는 것이다** — 시작은 HTTP 요청이다. 갈아타자는 헤더를 붙여 보내고 서버가 101 로 답해야 열린다.
- **연결만 열어두면 계속 살아 있다** — 중간의 프록시나 방화벽이 조용한 연결을 끊는다. 핑을 주기적으로 보내고 끊기면 다시 붙는 코드를 직접 넣어야 한다.
- **실시간이면 무조건 WebSocket 이다** — 서버가 내려보내기만 하는 자리는 SSE 가 더 간단하다. 끊겼을 때 다시 붙는 것도 브라우저가 알아서 한다.

## 🚨 주의사항

- **끊기면 스스로 다시 붙지 않는다.** 다시 붙는 로직과 그동안 못 보낸 것을 담아 둘 자리를 같이 만들어야 한다.
- **채널마다 연결을 새로 열지 않는다.** 연결 하나를 열고 그 안에서 구독을 나누는 편이 낫다.

## 📝 정리

WebSocket은 HTTP 요청으로 시작해 갈아탄 뒤 그대로 열어두는 통로다. 서버가 먼저 말을 걸 수 있어서 새 게 있는지 계속 물어보던 폴링을 없앤다. 대신 끊겼을 때 다시 붙는 일과 살아 있는지 확인하는 일을 직접 챙겨야 한다.

## ❓ 이해했는지

- 폴링으로 채팅을 만들면 서버가 받는 요청 대부분은 어떤 답을 내놓게 되나 → 해결하는 문제
- 새 포트를 열지 않았는데 WebSocket 연결이 맺어지는 이유는 → 작동 원리
- 알림만 내려보내면 되는 화면에 SSE 를 고르는 이유는 → 흔한 오해
