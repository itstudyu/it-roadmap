# Domain (도메인)

## 📝 정의

Domain은 **기억하기 어려운 IP 주소를 사람이 이해하기 쉬운 이름으로 표현한 것**입니다. 예를 들어 142.250.207.46이라는 IP 주소를 google.com이라는 도메인으로 표현합니다. 도메인은 DNS를 통해 해당 IP 주소로 변환되어 실제 네트워크 통신이 일어납니다.

도메인 시스템은 1983년에 Paul Mockapetris에 의해 DNS와 함께 개발되었습니다. 초기 인터넷 사용자들은 모두 IP 주소를 외워서 입력해야 했지만, 도메인 시스템의 등장으로 웹사이트에 기억하기 쉬운 이름을 붙일 수 있게 되었습니다. 이는 인터넷의 대중화에 가장 중요한 요소 중 하나였습니다. 오늘날 인터넷 상에는 약 3억 개 이상의 등록된 도메인이 있습니다.

### 한 줄 요약
> 도메인은 IP 주소를 사람이 기억하기 쉬운 이름으로 표현한 웹사이트 주소입니다.

### 비유
- 🔵 **비유 1**: 사람의 이름과 주민등록번호와 같습니다. 주민등록번호는 개인을 유일하게 식별하지만 외우기 어렵고(IP), 이름은 더 쉽게 기억할 수 있습니다(도메인). 통신할 때는 실제로 주민등록번호가 사용되지만, 사람들은 이름으로 소통합니다.
- 🟡 **비유 2**: 회사의 전화번호와 회사명과 같습니다. 회사마다 번호가 있어서 전화를 연결하지만(IP), 사람들은 회사명으로 회사를 부르고 기억합니다(도메인). 전화 연결은 번호로 하지만, 회사명으로 검색하고 공유합니다.

## 🎯 핵심 개념

### 1. 계층적 도메인 구조

도메인은 점(.)으로 구분된 계층 구조를 가집니다. 오른쪽에서부터 가장 일반적인 것부터 가장 구체적인 것 순서로 배열됩니다. 최상위 계층은 최상위 도메인(TLD, Top-Level Domain)으로, .com, .org, .kr 같은 전체 카테고리입니다. 그 다음 계층은 두 번째 수준 도메인(Second-Level Domain)으로, google.com에서 google 부분입니다. 그 다음부터는 서브도메인으로, mail.google.com에서 mail이 서브도메인입니다. 이러한 계층 구조 덕분에 DNS는 효율적으로 도메인을 관리할 수 있습니다. 각 수준의 DNS 서버가 자신의 하위 도메인을 관리하므로, 중앙집중식 관리가 필요 없습니다. 또한 새로운 도메인을 추가할 때마다 전체 시스템을 변경할 필요가 없습니다.

### 2. 도메인 레지스트리와 레지스트라

도메인 관리 체계는 두 개의 주요 역할로 나뉩니다. 레지스트리(Registry)는 특정 TLD의 모든 도메인 등록 정보를 관리하는 중앙 기관입니다. 예를 들어 VeriSign은 .com과 .net의 레지스트리이고, Korea Internet & Security Agency(KISA)는 .kr의 레지스트리입니다. 레지스트라(Registrar)는 최종 사용자로부터 도메인 등록 신청을 받는 중개 업체입니다. GoDaddy, Namecheap, 카페24 같은 회사들이 대표적입니다. 사용자가 GoDaddy에서 example.com을 등록하면, GoDaddy는 .com 레지스트리에 그 정보를 등록합니다. 이러한 분업 시스템으로 인해 규모가 다양한 업체들이 도메인 등록 서비스를 제공할 수 있습니다.

### 3. 도메인 등록과 ICANN

ICANN(Internet Corporation for Assigned Names and Numbers)은 도메인 체계의 최상위 조직입니다. ICANN은 TLD를 정의하고, 각 TLD의 레지스트리를 승인하며, 도메인 시스템의 안정성과 보안을 관리합니다. 도메인을 등록하려면 먼저 사용 가능한 도메인인지 확인하고, 선택한 레지스트라에 신청합니다. 레지스트라는 ICANN의 규정에 따라 도메인의 WHOIS 정보(소유자 정보)를 수집하고, 이를 레지스트리에 등록합니다. 등록 후 도메인 소유자는 DNS 설정을 통해 도메인을 자신의 웹 서버 IP 주소와 연결합니다. 도메인의 소유권은 연간 갱신을 통해 유지되어야 하며, 갱신하지 않으면 도메인은 만료되어 누군가 다시 등록할 수 있게 됩니다.

### 4. 서브도메인과 와일드카드 DNS

서브도메인은 기존 도메인 앞에 추가되는 부분입니다. 예를 들어 google.com의 서브도메인에는 mail.google.com, drive.google.com, photos.google.com 등이 있습니다. 서브도메인은 독립적으로 DNS 레코드를 가지며, 각각 다른 IP 주소를 가리킬 수 있습니다. 서브도메인을 추가할 때는 새로운 도메인을 등록할 필요 없이, 단지 DNS 설정을 추가하면 됩니다. 와일드카드 DNS는 *.example.com 같은 패턴으로 설정되어, example.com의 모든 서브도메인을 같은 IP로 지칭할 수 있습니다. 예를 들어 cdn.example.com, storage.example.com, api.example.com 등이 모두 같은 서버를 가리키도록 할 수 있습니다. 이러한 유연성으로 인해 여러 서브도메인을 효율적으로 관리할 수 있습니다.

## ⚠️ 해결하는 문제

### 문제 1: 사용자가 IP 주소를 기억하고 입력해야 하는 부담

인터넷 초창기에는 모든 사용자가 142.250.207.46 같은 IP 주소를 직접 입력하여 웹사이트에 접속해야 했습니다. 이는 매우 불편했고, 사용자들이 여러 IP 주소를 외워야 했습니다. 숫자 조합은 외우기 어렵고, 실수하기 쉬우며, IP 주소가 변경되면 새로운 주소를 다시 외워야 합니다.

도메인은 이 문제를 완벽하게 해결합니다. google.com이라는 단순하고 기억하기 쉬운 이름을 사용하여 접속할 수 있으므로, 사용자는 숫자를 외울 필요가 없습니다. 또한 도메인은 서비스의 정체성을 표현하므로, 사용자가 어떤 서비스에 접속하는지도 쉽게 알 수 있습니다.

### 문제 2: 서버 IP 주소 변경 시 사용자 혼란

서버를 이전하거나 업그레이드할 때 IP 주소가 변경되어야 할 수 있습니다. 만약 사용자들이 모두 IP 주소로 접속한다면, 모든 사용자에게 새로운 IP 주소를 공지하고, 북마크를 변경하도록 안내해야 합니다. 이는 대규모 사용자 베이스를 가진 서비스에서는 거의 불가능합니다.

도메인은 이 문제를 투명하게 해결합니다. 도메인 자체는 변경 없이 유지하고, DNS 레코드만 새로운 IP 주소로 업데이트합니다. 사용자는 여전히 google.com으로 접속하지만, 자동으로 새로운 서버에 연결됩니다. 도메인 변경 없이도 인프라를 완전히 재구성할 수 있습니다.

### 문제 3: 브랜드 정체성 확립의 어려움

IP 주소로는 서비스의 정체성을 나타낼 수 없습니다. 142.250.207.46이 구글인지 알리바바인지 아마존인지 전혀 알 수 없습니다. 사용자는 서비스를 IP 주소로 기억하고 공유할 수 없습니다.

도메인은 서비스의 정체성을 강력하게 표현합니다. google.com, amazon.com, facebook.com이라는 도메인은 각 회사의 브랜드를 대표하며, 사용자가 쉽게 기억하고 공유할 수 있습니다. 도메인은 마케팅, 신뢰도, 브랜드 구축에 핵심적인 역할을 합니다.

```도해
SLD (2단계 도메인) goo… :: 2번째 수준
서브도메인 (3단계) mail… :: 3번째 수준
예시: mail.google.c… :: 전체 예시
```

## ✅ 장점과 단점

### 장점

- **사용자 친화적**: 기억하기 쉬운 이름으로 서비스 접속 가능
- **브랜드 가치**: 도메인명 자체가 브랜드의 일부가 되며 신뢰도 구축
- **유연한 변경**: 서버 IP 변경 시 도메인은 유지하고 DNS만 변경
- **마케팅 효과**: 도메인을 통해 서비스를 홍보하고 공유하기 쉬움
- **글로벌 확장**: 도메인으로 여러 국가와 지역에 동시 서비스 가능
- **다중 호스팅**: 같은 도메인으로 여러 서버에 분산 배치 가능 (로드밸런싱)
- **이메일 통합**: 도메인으로 전문 이메일 주소(예: info@company.com) 운영

### 단점

- **비용**: 도메인 등록 및 갱신 비용 필요
- **갱신 의무**: 주기적으로 갱신해야 하며, 갱신하지 않으면 타인이 등록 가능
- **DNS 의존성**: DNS 조회 실패 시 접속 불가능
- **도메인 대기 시간**: DNS 조회로 인한 약간의 지연 (ms 단위)
- **도메인 고갈**: 인기 있는 도메인은 이미 등록되어 있을 수 있음
- **스팸과 피싱**: 도메인이 도용되거나 피싱 사이트에 악용될 수 있음
- **DNS 스푸핑**: 잘못된 IP로 도메인이 변조될 수 있음 (DNSSEC로 개선 중)
- **관리 복잡성**: 여러 서브도메인 관리 시 DNS 레코드 관리가 복잡할 수 있음

## 💡 실제 사용 사례

스타트업이 새로운 웹 서비스를 런칭할 때, 먼저 startup.com 같은 도메인을 등록합니다. 초기에는 저비용 웹 호스팅 서비스의 서버 IP에 도메인을 연결합니다. 사용자가 startup.com으로 접속하면, DNS가 이를 웹 호스팅 서버의 IP로 변환합니다. 비즈니스가 성장하면서 자체 서버를 구축하게 되면, DNS 레코드만 새로운 서버의 IP로 변경합니다. 사용자는 여전히 startup.com으로 접속하지만, 자동으로 새로운 서버에 연결됩니다. 도메인을 바꾸거나 사용자에게 새로운 주소를 공지할 필요가 없습니다. 나중에 여러 데이터센터로 확장할 때도, CDN을 통해 여러 지역의 서버를 같은 도메인으로 관리할 수 있습니다.

또 다른 사례로, 대규모 기업의 브랜드 운영이 있습니다. Google은 google.com이라는 핵심 도메인 외에도 여러 서브도메인을 운영합니다. mail.google.com (Gmail), drive.google.com (Google Drive), scholar.google.com (Google Scholar) 등이 모두 같은 google.com 브랜드 아래에서 다양한 서비스를 제공합니다. 각 서브도메인은 별도의 서버에서 실행되지만, 모두 google.com 브랜드의 일부로 인식됩니다. 또한 google.kr, google.com.br, google.co.in 같은 지역별 도메인을 통해 각 국가의 사용자에게 지역화된 서비스를 제공합니다.

## 🔗 관련 용어

- **DNS**: 도메인을 IP 주소로 변환하는 시스템
- **URL**: 프로토콜, 도메인, 경로를 포함하는 웹 리소스 주소 (예: https://example.com/path)
- **IP Address**: 도메인이 가리키는 실제 네트워크 주소
- **ICANN**: 도메인 체계를 관리하는 최상위 국제 기구
- **TLD (Top-Level Domain)**: .com, .org, .kr 같은 최상위 도메인
- **WHOIS**: 도메인 소유자 정보를 조회하는 서비스
- **SSL/HTTPS**: 도메인 보안 연결을 위한 암호화 프로토콜
- **CDN**: 도메인으로 여러 지역의 서버에 분산 배치
