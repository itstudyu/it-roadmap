# WebRTC (웹 실시간 통신)

## 📝 정의

WebRTC는 **브라우저끼리 직접 소리와 화면을 흘리는 규격**이다.

빠진 것이 하나 있는데, 그게 이 규격의 성격을 말해 준다. 두 브라우저가 서로를 처음 찾게 해 주는 통로는 규격이 정하지 않았다. 사양서도 "신호 규약이라 부르는 제어 메시지 교환은 명시되지 않은 수단으로 제공되는 통로 위에서 이뤄진다" 고만 적는다. 무엇을 쓰든 만드는 사람 몫이라는 뜻이다.

### 이름
Web :: 브라우저에서
Real-Time :: 늦지 않게 바로
Communication :: 주고받기
= 붙여 읽으면 "브라우저에서 늦지 않게 주고받기". 앱을 안 깔아도 된다는 게 Web 쪽의 뜻이다

### 비유
전화기를 새로 사지 않고 이미 손에 있는 물건으로 통화하는 것. 무엇을 설치하라고 하지 않고 주소 하나만 열게 한다.

### 예
회의 링크를 눌렀더니 아무것도 안 깔고 브라우저에서 바로 카메라가 켜지는 그 경험이 이것이다.

### 직접
통화 중에 주소창에 `chrome://webrtc-internals` 를 열어 보라. 어떤 길이 후보로 올라왔고 무엇이 골라졌는지 그대로 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 두 브라우저는 어떻게 서로에게 닿나
신호 통로 :: 규격 밖이다. 무엇을 쓸지 내가 정한다
제안·응답 :: SDP 로 형식과 주소 후보를 주고받는다

미디어 :: 고른 길로 소리와 화면이 곧장 흐른다
= 서버는 짝만 지어 주고 빠진다. 통화 자체는 두 쪽이 직접 흘린다
```

## ⚠️ 해결하는 문제

```도해
대조: 실시간 통화를 웹에서 하려면 예전엔 무엇이 필요했나
규격이 없으면 || WebRTC 로
시작 :: 앱을 깔아야 한다 || 링크만 누른다
경로 :: 서버를 꼭 한 번 || 되면 직접 간다
호환 :: 만든 곳끼리만 || 브라우저끼리
= 앱 없이, 되도록 남을 거치지 않고 흘리도록 브라우저에 못 박아 둔 것이다
```

실시간 통화는 오래 있었지만 늘 전용 프로그램을 깔아야 했다. 만든 곳마다 방식이 달라서 같은 것을 깐 사람끼리만 통화가 됐고, 소리와 화면은 대개 그 회사 서버를 한 번 거쳤다. 거치는 만큼 늦어지고, 사람이 늘수록 그 서버의 대역폭 요금이 그대로 늘었다.

WebRTC 는 그 기능을 브라우저 안에 규격으로 박아 넣었다. 그러면 깔 것이 없어지고, 브라우저를 만든 곳이 달라도 통한다. 그리고 되는 상황이라면 두 기기가 서로 직접 흘리므로 중간을 한 번 덜 거친다. 대신 서로를 찾아 주는 첫 인사만은 여전히 누군가 만들어야 한다.

## ⚙️ 작동 원리

부르는 순서가 정해져 있다. 거는 쪽이 `createOffer()` 로 제안을 만들고 `setLocalDescription()` 으로 자기에게 적용한 뒤, 그 내용을 내가 만든 신호 통로로 상대에게 보낸다. 받는 쪽은 `setRemoteDescription()` 으로 그것을 받아들이고 `createAnswer()` 로 답을 만들어 되돌린다. 이 사이 상태는 `"stable"` 에서 `"have-local-offer"` 나 `"have-remote-offer"` 로 갔다가 다시 `"stable"` 로 돌아온다.

주소 후보는 따로 흐른다. 브라우저가 후보를 하나 찾을 때마다 `icecandidate` 사건이 뜨고, 그것도 신호 통로로 상대에게 보낸다. 제안을 다 만들 때까지 기다렸다가 한꺼번에 보내지 않고 나오는 대로 보내기 때문에, 연결이 눈에 띄게 빨라진다.

붙었는지는 두 상태값으로 본다. `iceConnectionState` 는 `"new"` `"checking"` `"connected"` `"completed"` `"failed"` `"disconnected"` `"closed"` 를 오가고, 전체 상태인 `connectionState` 는 `"new"` `"connecting"` `"connected"` `"disconnected"` `"failed"` `"closed"` 다. 통화가 안 붙었다는 신고를 받으면 이 값이 어디서 멈췄는지가 첫 단서다. `"checking"` 에서 멈추면 후보는 모았는데 되는 짝이 없다는 뜻이다.

## 💡 실제 사례

- **설치 없는 화상 회의** — 링크를 열면 브라우저가 카메라를 잡고 신호 통로로 제안을 주고받은 뒤 직접 길을 튼다.
- **소리·화면이 아닌 것도 같은 길로** — `RTCDataChannel` 로 파일이나 화면 좌표 같은 임의의 것을 보낸다. 게임이나 공동 편집이 이 통로를 쓴다.
- **사람이 늘 때 터지는 지점** — 각자가 모두와 직접 이으면 짝의 수가 사람 수의 제곱으로 는다. 그래서 일정 인원부터는 중간에서 섞어 주는 서버를 둔다.

## 🚫 흔한 오해

- **WebRTC 는 서버가 필요 없다** — 서로를 찾게 해 주는 신호 통로가 있어야 시작되고, 밖에서 본 주소를 알려줄 서버도 있어야 한다. 규격이 안 정한 것은 신호 통로뿐이지 없어도 된다는 뜻이 아니다.
- **붙었으면 언제나 직접 간다** — 상대마다 번호를 바꾸는 문지기 뒤에서는 중계 서버를 거친다. 화면상 똑같이 통화 중이지만 그 구간은 대역폭 요금이 그대로 나온다.
- **회의도 전부 이걸로 하면 된다** — 사람이 늘면 짝이 제곱으로 늘어 각자의 기기가 먼저 못 버틴다. 몇 명을 넘어가면 중간 서버를 두는 쪽이 정석이다.

## 📝 정리

**"브라우저끼리 직접 흘리게 해 주는 그 규격"** 이라고 읽으면 된다. 깔 것을 없애고 되도록 중간을 거치지 않게 만든 대신, 서로를 처음 찾게 해 주는 통로는 규격이 비워 두고 만드는 사람에게 맡겼다. 안 붙는다는 신고를 받으면 상태값이 어디서 멈췄는지부터 본다.

## 🧒 열 살에게

멀리 있는 친구랑 얼굴 보고 이야기하려면, 처음엔 누가 서로의 집이 어디인지 한 번 알려 줘야 하지? 그렇게 한 번만 알려 주면 그다음부터는 둘이 곧장 오가며 이야기해. 매번 가운데 사람을 거치면 말이 늦게 닿고, 그 사람도 하루 종일 붙잡혀 있어야 하거든.

## ❓ 이해했는지

- 규격이 비워 둔 탓에 만드는 사람이 직접 마련해야 하는 것은 무엇인가 → 작동 원리
- 직접 이어졌다는데도 중계 요금이 나오는 일이 왜 생기나 → 흔한 오해
- 통화 내용이 도중에 그대로 들여다보이지 않는 이유는 무엇인가 → 구성
