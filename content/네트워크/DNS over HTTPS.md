# DNS over HTTPS (암호화된 이름 조회)

## 📝 정의

DNS over HTTPS는 **이름 조회를 HTTPS 요청 한 통으로 감싼 것**이다.

묻는 내용은 하나도 안 바뀐다. 예전 그대로의 DNS 질의 한 덩어리를 그대로 만들어서, 53번 포트로 맨몸으로 내보내는 대신 443번 위의 잠긴 통로에 실어 보낸다. RFC 8484 는 이때 쓸 형식을 `application/dns-message` 라는 미디어 타입 하나로 못박았고, 최소 권고 판을 HTTP/2 로 잡았다. 줄여서 DoH 라고 부른다.

### 이름
DNS :: 이름을 묻는 일
over :: ~에 실어서
HTTPS :: 잠긴 웹 통로
= 붙여 읽으면 "이름 묻는 일을 잠긴 웹 통로에 실은 것". 묻는 말은 그대로고 실어 나르는 길만 바뀐다

### 비유
편의점에서 찾는 물건을 큰 소리로 묻느냐 점원에게만 들리게 귓속말로 묻느냐의 차이다 — 점원은 여전히 다 알지만 줄 선 사람들은 모른다.

### 예
회사나 학교 와이파이에서 특정 사이트만 안 열리던 그 경험이다. 대개 이름을 묻는 단계에서 걸러진 것이다.

### 직접
크롬 주소창에 `chrome://settings/security` 를 열어 보라. "보안 DNS 사용" 항목이 지금 이 기기의 조회를 어디로 보낼지 정하는 자리다.

## 🖼️ 그림으로 보기

```도해
흐름: 이름 하나를 물으면 실제로 무엇이 나가나
클라이언트 :: 예전 그대로의 DNS 질의를 만든다
감싸기 :: `GET ...?dns=<base64url>` 또는 POST 본문에 싣는다
헤더 :: `accept: application/dns-message` 를 붙인다
전송 :: 443번 위 HTTP/2 로 나간다. 겉은 평범한 웹 통행이다
< DoH 서버 :: 같은 형식으로 답하고, `Age` 만큼 TTL 을 깎아 준다
= 묻는 말은 그대로다. 그 한 통을 HTTPS 요청으로 감싼 것이 전부다
```

## ⚠️ 해결하는 문제

```도해
대조: 같은 물음이 어떤 모습으로 나가나
평문 조회 || DoH
포트 :: 53/UDP 로 혼자 || 443/TCP 로 섞여
겉모습 :: 조회라고 티 난다 || 웹 통행과 똑같다
읽는 쪽 :: 중간의 누구나 || 받는 그곳만
바꿔치기 :: 중간에서 가능 || 통로가 잠겨 어렵다
= 물음의 내용이 아니라 물음이 실려 가는 길이 바뀐 것이다
```

평문 조회는 봉투 없는 엽서다. 같은 와이파이에 붙은 사람, 통신망을 운영하는 쪽, 중간의 어느 장비든 무엇을 물었는지 그대로 읽는다. 읽는 데서 그치지 않는다 — 먼저 도착한 답이 이기므로, 읽을 수 있는 자리에 있는 쪽은 가짜 답을 먼저 밀어 넣을 수도 있다.

DoH 는 그 한 통을 HTTPS 요청으로 감싼다. 통로가 잠기므로 중간에서는 읽지도 바꾸지도 못하고, 겉모습이 평범한 웹 통행과 같아져서 조회만 골라 끊기도 어려워진다. 대신 통로 끝에서 받는 그곳은 여전히 전부 안다 — 감춰지는 대상이 사라진 게 아니라 옮겨 간 것이다.

## ⚙️ 작동 원리

DoH 클라이언트는 어디로 물을지를 URI 템플릿 하나로 받아 둔다. RFC 8484 는 그 설정과 갱신을 이 규격 밖에서 하도록 했고, "밖에서 발견했다는 이유만으로 다른 주소를 써서는 안 된다" 고 못박았다. 조회처가 응답 한 줄로 조용히 갈아치워지는 일을 막는 조항이다.

보내는 방법은 둘이고 서버는 둘 다 반드시 구현해야 한다. GET 은 질의를 base64url 로 바꿔 `dns` 라는 이름의 값으로 붙이는데, 이때 패딩 문자는 붙이지 않는다. 주소가 곧 질의라서 HTTP 캐시에 그대로 얹힌다. POST 는 질의를 본문에 그대로 싣는다. 인코딩을 안 하니 대체로 더 작다.

캐시가 두 겹이 되는 것이 이 규격의 까다로운 지점이다. DNS 에는 TTL 이 있고 HTTP 에는 신선도 수명이 따로 있다. RFC 8484 는 응답의 신선도 수명이 답 구역 안 가장 작은 TTL 보다 크면 안 된다고 정했고, 클라이언트는 `Age` 응답 헤더 값을 빼고 남은 만큼을 실제 TTL 로 세야 한다. 이 계산을 빼먹으면 이미 만료된 주소를 한참 더 붙들고 있게 된다.

## 💡 실제 사례

- **조회처가 회사 이름으로 정해진다** — 윈도우 서버가 기본으로 아는 목록은 Cloudflare(1.1.1.1)·Google(8.8.8.8)·Quad9(9.9.9.9) 셋뿐이고, 그 밖의 곳은 `Add-DnsClientDohServerAddress` 로 주소와 템플릿을 직접 등록해야 고를 수 있다. 켜는 순간 내 조회를 보는 쪽이 통신망 운영자에서 이 셋 중 하나로 바뀐다.
- **사내 차단이 안 먹는다** — 53번 포트를 막아 둔 조직에서 브라우저가 DoH 를 켜면 그 차단이 통째로 비껴간다. 그래서 관리 환경에서는 정책으로 끈다. 윈도우 그룹 정책의 "Prohibit DoH" 가 그 자리다.
- **도메인에 가입한 컴퓨터에는 켜지 마라** — 마이크로소프트 문서가 "Require DoH" 를 두고 그렇게 못박는다. 액티브 디렉터리가 이름 조회에 크게 기대는데 정작 윈도우 서버의 DNS 서버 쪽은 DoH 질의를 받지 못해서, 반드시 잠긴 통로로만 물으라고 걸면 사내 이름 풀이가 통째로 멈춘다.

## 🚫 흔한 오해

- **켜면 아무도 내가 어디 접속하는지 모른다** — 통로 끝에서 받는 그곳은 전부 안다. 가려지는 건 중간 구간뿐이고, 보는 주체가 통신망 운영자에서 그 조회처로 바뀐 것이다.
- **이걸 켜면 가짜 답도 막힌다** — 통로는 잠기지만 그 끝이 준 답이 진짜인지는 별개 문제다. 답 자체의 진위는 DNSSEC 가 본다.
- **접속하려는 사이트 이름도 같이 가려진다** — 아니다. 조회가 끝나면 바로 이어지는 TLS 인사에서 SNI 칸에 같은 이름이 평문으로 또 나간다.

## 📝 정리

**"이름 묻는 소리를 잠긴 통로에 넣은 것"** 이라고 읽으면 된다. 물음의 내용은 그대로고 실려 가는 길만 바뀌므로, 중간에서 읽거나 바꾸는 일은 막히지만 통로 끝에서 받는 곳은 여전히 전부 본다. 가림막이 사라진 게 아니라 누구를 믿을지의 문제로 옮겨 간 것이다.

## 🧒 열 살에게

편의점에서 찾는 물건을 큰 소리로 물으면 줄 선 사람들이 다 듣지? 점원한테만 들리게 귓속말로 물으면 남들은 못 듣는데, 점원은 여전히 네가 뭘 찾는지 다 알아.

## 🔗 관련 용어

- [[DNS]] — 감싸는 대상. 안에 든 질의는 이쪽 형식 그대로다
- [[HTTPS]] — 조회를 실어 나르는 통로 그 자체
- [[DNSSEC]] — 통로가 아니라 답 자체의 진위를 보는 쪽
- [[Server Name Indication]] — 조회를 가려도 그다음 인사에서 이름이 또 새는 자리
- [[HTTP/2]] — 규격이 최소로 권고한 판. 한 연결에 조회 여러 개를 겹쳐 보낸다
