# DDD (Domain-Driven Design)

## 📝 정의

DDD는 **업무 영역을 모델로 삼아 시스템 경계를 긋는 설계법**이다.

서비스 경계를 어디에 그을지 정하는 기계적인 절차는 없다. Microsoft 의 아키텍처 문서는 이 일을 마이크로서비스의 가장 큰 난제 중 하나로 적고, 자료 접근이나 메시징 같은 가로층이 아니라 업무 능력을 축으로 나누라고 말한다. DDD 는 그 축을 어디서 찾는지에 대한 답이다.

### 이름
Domain :: 업무가 도는 영역
Driven :: 그쪽이 이끄는
Design :: 설계
= 붙여 읽으면 "업무 영역이 이끄는 설계". 기술이 아니라 업무가 경계를 정한다는 뜻이다

### 비유
교실 팻말. 같은 "당번" 이라는 말도 1학년 교실과 6학년 교실에서 하는 일이 달라서, 어느 교실 이야기인지부터 정해야 말이 통한다.

### 예
"주문" 이라는 낱말 하나를 두고 영업팀과 물류팀이 30분째 서로 다른 이야기를 하고 있던 그 회의다.

### 직접
지금 팀의 회의록에서 같은 낱말이 두 가지 뜻으로 쓰인 자리를 하나만 찾아보라. 거기가 경계선이 지나가는 자리다.

## 🖼️ 그림으로 보기

```도해
층: 업무를 어디까지 좁혀야 서비스 하나가 나오나
도메인 :: 회사가 하는 일 전체. 배송업이면 배송에 관한 전부
하위 도메인 :: 핵심·지원·일반으로 갈린다. 어디에 힘을 쓸지 여기서 갈린다
경계 컨텍스트 :: 한 모델과 한 낱말 뜻이 통하는 범위
도메인 모델 :: 그 범위 안의 개체와 규칙. 서비스 하나의 속이 된다
= 큰 업무를 뜻이 안 엇갈리는 범위까지 좁히면, 그 범위 하나가 서비스 하나가 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 시스템을 기술로 나누면 무엇이 어긋나나
기술로 나누면 || 업무로 나누면
나누는 축 :: 화면·로직·저장 || 배송·정산·계정
같은 낱말 :: 팀마다 다른 뜻 || 경계 안에서 한 뜻
기능 하나 추가 :: 세 층을 다 고친다 || 한 곳만 고친다
= 업무가 경계를 정해야 한 가지 일이 한 자리에 모인다
```

경계를 대충 그으면 서비스 사이에 숨은 의존이 생기고, 서로 꽉 물려서 따로 배포할 수 없게 된다. Microsoft 문서는 그 상태를 "구조 없는 설계" 라고 부른다. 겉으로는 서비스가 여럿인데 하나를 고치면 나머지도 같이 고쳐야 하니, 쪼갠 값은 못 받고 쪼갠 대가만 치른다.

낱말 뜻이 갈리는 것도 같은 뿌리다. 정비 쪽이 말하는 "드론" 은 정비 이력과 주행거리와 모델 번호를 안고 있고, 배차 쪽이 말하는 "드론" 은 지금 비었는지와 도착 예정 시각뿐이다. 하나의 모델로 둘을 다 담으면 모델은 부풀고, 고칠 때마다 두 팀이 합의해야 한다. DDD 는 같은 사물을 **경계마다 다른 모델로** 두는 것을 허락해서 이 매듭을 푼다.

## ⚙️ 작동 원리

```도해
흐름: 업무에서 서비스 경계를 어떻게 끌어내나
업무 분석 :: 하는 일을 다 늘어놓고 서로 어떻게 얽히는지 그린다
경계 컨텍스트 :: 한 모델이 통하는 범위로 자른다. 낱말 뜻은 그 안에서만 하나다
전술 패턴 :: 그 안에 개체·애그리게이트·도메인 서비스를 놓는다
서비스 식별 :: 그 결과를 서비스 하나하나로 옮긴다
@ 다시 분석으로 :: 경계는 고정이 아니다. 업무가 자라면 다시 긋는다
= 서비스를 먼저 정하고 업무를 끼우는 게 아니라, 업무를 갈라 두면 서비스가 따라 나온다
```

DDD 는 전략과 전술 두 단계로 나뉜다. 전략 단계에서 큰 구조를 정하고, 전술 단계에서 개체·애그리게이트·도메인 서비스 같은 패턴으로 모델 속을 채운다. 앞의 둘이 위 그림의 처음 두 마디이고, 이 순서를 뒤집으면 코드 패턴만 남고 경계는 안 생긴다.

업무를 늘어놓을 때 하위 도메인은 셋으로 갈린다. **핵심**은 경쟁력이 걸린 곳이라 직접 정성껏 만들고, **지원**은 업무에 필요하지만 남과 다를 것이 없는 곳이고, **일반**은 업계가 이미 푼 문제라 기성품을 쓴다. 계정 관리나 콜센터가 대개 일반에 들어간다. 이 분류가 곧 어디에 사람을 넣을지의 답이다.

경계 컨텍스트끼리 만나는 자리는 컨텍스트 맵으로 적어 둔다. 위쪽이 주는 것에 아래쪽이 기대고 둘이 계약을 맞추는 관계, 위쪽이 잘 정의된 창구를 공통 형식으로 열어 두는 관계, 아래쪽이 번역 층을 세워 자기 모델을 지키는 관계, 아예 안 엮고 각자 가는 관계가 있다. 낡은 시스템과 붙을 때 번역 층을 끼우는 이유는 그쪽 자료 모양이 이쪽 모델로 새어 들어오기 때문이다.

## 📊 비교: 언제 이 설계를 들이나

```도해
대조: 어떤 업무에서 이 설계가 값을 하나
들일 만한 곳 |=| 다시 따져 볼 곳
업무 복잡도 :: 규칙이 얽혀 있다 || 화면과 저장뿐
물어볼 사람 :: 업무 전문가 있다 || 팀 안에 없다
기존 모듈 경계 :: 업무를 따라 나 있다 || 층으로 얽혀 있다
= 얽힌 업무와 물어볼 사람, 이미 난 경계가 있을 때 값을 한다
```

AWS 문서는 하위 도메인으로 쪼개는 방식의 단점을 둘로 적는다. 서비스가 너무 많아져서 찾고 잇는 일이 어려워지는 것, 그리고 업무 하위 도메인을 알아내는 일 자체가 업무 전체를 깊이 알아야 가능하다는 것. 뒤의 것이 더 무섭다 — 물어볼 사람이 없으면 경계는 추측으로 그어지고, 추측으로 그은 경계는 반드시 다시 긋게 된다.

반대로 잘 들어맞는 자리도 분명하다. AWS 문서는 이 방식이 **모듈 사이 경계가 이미 업무를 따라 나 있는 기존 시스템**에 알맞다고 적는다. 그런 경우에는 코드를 크게 다시 쓰지 않고 모듈을 다시 묶기만 해도 서비스가 나온다.

## 💡 실제 사례

- **모놀리스 쪼개기** — 모듈 경계가 이미 업무를 따라 나 있으면 크게 다시 쓰지 않고 그대로 떼어내 서비스로 만든다.
- **어디에 힘을 쓸지 고르기** — 핵심 하위 도메인만 직접 만들고, 계정이나 콜센터 같은 일반 영역은 기성품으로 덮는다.
- **낡은 시스템과 붙는 자리** — 그쪽 자료 모양이 새 모델로 새어 들어오지 않게 사이에 번역 층을 하나 끼운다.

## 🚫 흔한 오해

- **DDD 를 하면 어떤 프로젝트든 좋아진다** — 공짜로 얻는 것이 아니다. AWS 문서는 하위 도메인을 알아내는 일 자체가 업무 전체를 깊이 알아야 가능하다고 적는다.
- **DDD 는 개체와 애그리게이트 같은 코드 패턴이다** — 그건 전술 쪽 절반이다. 먼저 오는 것은 업무를 갈라 경계를 긋는 전략 쪽이고, 그걸 건너뛰면 이름만 DDD 인 코드가 남는다.
- **경계 컨텍스트는 한 번 정하면 끝이다** — Microsoft 문서는 경계 평가를 계속 이어지는 일로 적는다. 앱이 자라면 서비스 하나를 여럿으로 다시 가르게 된다.

## 🚨 주의사항

- **팀 구조가 경계를 정하게 두지 마라.** 시스템은 만드는 조직의 소통 구조를 닮는다. 그대로 두면 조직도가 아키텍처가 되므로, 업무 분석으로 경계를 먼저 긋고 팀을 거기에 맞춘다.
- **한 팀이 서로 무관한 경계를 여럿 안고 있거나, 한 경계를 여러 팀이 나눠 맡고 있으면** 경계와 팀 배치 중 하나가 틀린 것이다. Microsoft 문서는 그럴 때 둘 다 다시 보라고 적는다.
- **너무 잘게 자르지 마라.** 서비스가 많아질수록 서로 찾고 잇는 비용이 는다. 잘게 자른 값이 그 비용을 넘는지 매번 따진다.

## 📝 정리

**"낱말 뜻이 하나로 통하는 범위까지 업무를 좁히는 일"** 이라고 읽으면 된다. 그 범위가 경계 컨텍스트이고, 경계 하나가 대체로 서비스 하나가 된다. 경계는 한 번 긋고 끝나는 선이 아니라 업무가 자라면 다시 긋는 선이다.

## 🧒 열 살에게

학교에서 "당번" 이라고만 하면 누구 얘긴지 모르지? 1학년 교실 당번이랑 6학년 교실 당번이 하는 일이 다르니까. 그래서 일을 나눌 때는 어느 교실 이야기인지부터 정하고, 그 교실 안에서만 통하는 말로 적어 두는 거야.

## ❓ 이해했는지

- 같은 "고객" 이라는 말이 팀마다 다른 뜻으로 쓰이면 무엇이 잘못되나 → 해결하는 문제
- 하위 도메인을 핵심·지원·일반으로 갈라 놓으면 무엇을 정할 수 있나 → 작동 원리
- 서비스를 너무 잘게 잘랐을 때 새로 생기는 문제는 무엇인가 → 주의사항
