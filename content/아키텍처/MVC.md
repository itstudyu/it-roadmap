# MVC (Model View Controller)

## 📝 정의

MVC는 **앱을 모델·뷰·컨트롤러 셋으로 가르는 짜임새**다.

가르는 목적은 하나다. 화면 쪽 로직은 자주 바뀌고 업무 규칙은 덜 바뀌는데, 둘이 한 덩어리에 있으면 화면을 손볼 때마다 업무 규칙이 든 코드를 고치게 되고 그때마다 다시 시험해야 한다.

### 이름
Model :: 자료와 업무 규칙
View :: 보여 주는 쪽
Controller :: 입력 받아 고르는 쪽
= 붙여 읽으면 "자료·보여주기·고르기". 이름이 곧 세 덩어리의 목록이다

### 비유
학교 급식실. 조리실이 음식을 만들고, 배식대가 담아 내놓고, 당번이 줄을 세워 누가 언제 받을지 정한다.

### 예
장보기 목록 앱에서 담기 단추를 누르면 목록이 바뀌고 화면이 다시 그려지는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 단추 하나를 누르면 셋 중 누가 먼저 움직이나
사용자 :: 단추를 누른다
컨트롤러 :: 그 입력이 닿는 첫 자리. 무엇을 할지 고른다
모델 :: 자료를 바꾸고 업무 규칙을 따진다
뷰 :: 컨트롤러가 고른 화면이 바뀐 자료를 그린다
< 사용자 :: 새로 그려진 화면을 본다
= 입력은 컨트롤러로 들어가 모델을 거쳐 뷰로 나온다. 모델은 나머지 둘을 모른다
```

## ⚠️ 해결하는 문제

```도해
대조: 화면과 업무 규칙을 한 덩어리로 두면 무엇이 터지나
안 가르면 || 셋으로 가르면
단추 색만 바꿔도 :: 규칙까지 다시 본다 || 뷰만 고친다
시험 :: 화면을 띄워야 || 모델만 돌린다
나눠 맡기 :: 한 파일에서 겹친다 || 셋으로 갈린다
= 자주 바뀌는 화면과 덜 바뀌는 규칙을 갈라 둔 것이다
```

Microsoft 문서는 이유를 이렇게 적는다. 화면 로직은 업무 로직보다 자주 바뀐다. 둘이 한 객체에 섞여 있으면 화면을 조금 바꿀 때마다 업무 로직이 든 객체를 고쳐야 하고, 그래서 오류가 끼어들고 업무 로직을 매번 다시 시험하게 된다.

방향이 한쪽으로만 나 있는 것도 이 절의 답이다. 뷰와 컨트롤러는 모델에 기대지만 모델은 뷰와 컨트롤러를 모른다. 그래서 모델은 화면 없이 따로 만들고 따로 시험할 수 있다. 하나만 하는 조각이 짜고 고치고 시험하기 쉬우니, 앱이 복잡해져도 감당이 된다.

## ⚙️ 작동 원리

들어온 주소가 먼저 컨트롤러의 동작 하나로 이어진다. 그 동작은 입력을 꺼내 형식이 맞는지 보고, 맞으면 모델을 부른다. 모델은 업무 규칙을 따져 자료를 바꾸고 결과를 돌려준다. 컨트롤러는 그 결과를 보고 어느 뷰를 쓸지 고른 뒤 뷰가 그릴 자료를 넘긴다. 뷰는 넘겨받은 자료로 화면을 만들어 낸다.

화면 고르기가 모델이 아니라 컨트롤러의 몫인 것이 이 순서의 요점이다. 같은 동작이라도 저장에 성공하면 목록으로, 규칙에 걸리면 입력 화면으로 돌아가야 한다. 그 갈림을 모델에 넣는 순간 모델이 화면 이름을 알게 되고, 화면 없이 규칙만 시험하던 이득이 거기서 끝난다.

방향은 한쪽으로만 나 있다. 컨트롤러와 뷰는 모델을 부르지만 모델은 그 둘을 부르지 않고, 뷰는 넘겨받은 자료를 읽기만 하고 바꾸지 않는다. 자료가 바뀌었으면 그것은 이미 모델 안에서 끝난 일이고, 뷰는 바뀐 결과를 받아 다시 그릴 뿐이다.

## 📊 비교: 셋으로 가르는 것만으로 어디까지 가나

```도해
대조: 셋으로 가르는 것만으로 언제까지 버티나
폴더 셋으로 |=| 층까지 가를 때
프로젝트 크기 :: 작고 단순하다 || 커지고 얽힌다
업무 규칙 자리 :: 모델 폴더에 || 안쪽 프로젝트에
드는 값 :: 지금이 싸다 || 나중이 싸다
= 셋으로 가르는 것은 화면 쪽 정리다. 커지면 층을 한 번 더 갈라야 한다
```

작은 앱은 프로젝트 하나에 모델·뷰·컨트롤러 폴더를 두는 것만으로 충분하다. Microsoft 문서도 한 덩어리로 올리는 이 방식이 사내용이나 규모가 작은 공개 앱에 아주 잘 맞는다고 적는다.

문제는 자랄 때 온다. 같은 문서는 프로젝트가 커지면 화면 관심사가 여러 폴더로 흩어지고, 업무 규칙이 모델 폴더와 서비스 폴더 사이에 널리고, 어느 폴더가 어느 폴더에 기대야 하는지 알 길이 없어진다고 적는다. 그 상태를 스파게티 코드로 가는 길이라 부른다. 그때 필요한 것은 MVC 를 더 잘 지키는 것이 아니라 **층을 한 번 더 가르는 것**이다.

## 💡 실제 사례

- **주소 하나 처리하기** — 들어온 주소가 컨트롤러의 동작 하나로 이어지고, 그 동작이 모델을 부른 뒤 어떤 뷰를 쓸지 고른다.
- **화면 개편** — 같은 모델 위에 뷰 파일만 갈아 끼우면 새 화면이 올라간다. 규칙은 손대지 않는다.
- **같은 규칙 두 얼굴** — 같은 모델을 두고 사람이 볼 화면과 기계가 읽을 응답을 나란히 낸다. 컨트롤러가 어느 쪽으로 낼지만 고른다.

## 🚫 흔한 오해

- **폴더를 셋으로 나눠 두면 그 자체로 잘 정리된 구조다** — Microsoft 문서는 규모가 커지면 화면 관심사가 여러 폴더로 흩어지고 업무 규칙이 모델과 서비스 사이에 널려 스파게티 코드로 간다고 적는다. 셋으로 가르는 것은 시작이지 끝이 아니다.
- **컨트롤러가 화면을 그린다** — 아니다. 컨트롤러는 어느 뷰를 쓸지 고르고 필요한 자료를 넘길 뿐이다. 그리는 일은 뷰가 한다.
- **모델은 자료를 담는 그릇이다** — 모델은 앱의 상태와 업무 규칙을 함께 담는다. 규칙을 컨트롤러에 두면 컨트롤러가 부풀고, 그러면 갈라 둔 값이 사라진다.

## 🚨 주의사항

- **컨트롤러를 두껍게 만들지 마라.** Microsoft 문서는 컨트롤러가 책임을 너무 많이 지지 않게 하고, 업무 규칙은 도메인 모델 쪽으로 밀어내라고 적는다.
- **뷰에 로직을 넣지 마라.** 같은 문서는 뷰 안의 로직을 최소로 두고 그마저도 보여주는 일에 관한 것만 남기라고 적는다. 뷰에서 계산이 길어지면 그건 모델이 할 일이다.
- **방향이 뒤집히지 않게 지켜라.** 모델이 뷰나 컨트롤러를 알기 시작하면 화면 없이 규칙만 시험할 수 없게 된다. 갈라 둔 이득이 거기서 끝난다.

## 📝 정리

**"입력·규칙·화면을 셋으로 갈라 둔 그 짜임새"** 라고 읽으면 된다. 뷰와 컨트롤러는 모델을 알지만 모델은 둘을 모르고, 그 한 방향 덕에 규칙만 따로 시험된다. 앱이 커져 폴더 셋으로 감당이 안 되면 MVC 를 조이는 게 아니라 층을 한 번 더 가른다.

## 🧒 열 살에게

급식실을 떠올려 봐. 조리실은 음식을 만들고, 배식대는 그걸 담아 내놓고, 당번은 줄을 세워 누가 언제 받을지 정하지? 담는 접시를 바꾼다고 조리법까지 다시 쓰지는 않잖아.
