# Retry & Exponential Backoff (재시도와 지수 백오프)

## 📝 정의

이 짝은 **실패한 호출을 점점 길게 기다렸다 다시 거는 규칙**이다.

클라우드에서 나는 실패의 상당수는 잠깐 났다 스스로 낫는 것들이다 — 순간 끊긴 연결, 잠시 바쁜 상대, 요청량을 넘겨 돌아온 거절. 애저 문서는 이런 실패를 "일시적 결함" 이라 부르고, 적당히 기다렸다 같은 일을 다시 하면 대개 성공한다고 적는다.

### 이름
Retry :: 다시 걸기
Exponential :: 갑절씩 커지는
Backoff :: 물러나 기다리기
= 붙여 읽으면 "물러나 기다리는 시간을 갑절씩 늘리며 다시 걸기". 이름이 곧 규칙이다

### 비유
통화 중인 친구에게 1분 뒤, 2분 뒤, 4분 뒤로 간격을 늘려 가며 다시 거는 일.

### 예
"일시적인 오류입니다. 다시 시도해 주세요" 를 눌렀더니 두 번째에는 그냥 되던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 호출이 실패했을 때 언제 다시 거나
호출 :: 상대를 부른다. 실패가 돌아온다
판정 :: 잠깐 나는 실패인가, 오래 갈 실패인가
대기 :: 1초, 2초, 4초로 기다림을 갑절씩 늘린다
흔들기 :: 거기에 무작위를 섞어 시각을 흩는다
@ 다시 호출로 :: 성공하면 끝, 정해둔 횟수를 넘기면 실패로 답한다
= 다시 거는 것만으로는 모자라고, 언제 거느냐를 같이 정해야 한다
```

## ⚠️ 해결하는 문제

```도해
대조: 실패하자마자 곧바로 다시 걸면 어떻게 되나
간격 없이 || 갑절씩 늘려서
바쁜 상대 :: 부하가 더 얹힌다 || 숨 돌릴 틈이 난다
재시도 물결 :: 다 같은 시각에 || 시각이 흩어진다
회복 :: 더 늦어진다 || 대개 스스로 푼다
= 다시 거는 일이 상대를 죽이지 않게 하는 것이 이 규칙의 절반이다
```

잠깐 나는 실패를 그대로 사용자에게 내보내면 멀쩡한 요청이 실패로 끝난다. 그래서 다시 건다. 문제는 다시 거는 방식이다. 애저 문서는 간격이 거의 없고 횟수만 많은 재시도가 한계에 걸려 있는 상대를 더 나쁘게 만든다고 적는다. 실패한 호출들이 하나같이 같은 간격으로 다시 걸리면, 그 다시 걸기가 같은 시각에 몰려 물결이 된다.

지수 백오프는 기다림을 갑절씩 늘려 부하를 흩고, 무작위(지터)는 시각을 흩는다. 구글 SRE 책은 "재시도를 잡을 때는 **언제나** 무작위를 섞은 지수 백오프를 쓰라" 고 적는다. 지터가 없으면 작은 흔들림 하나가 재시도 물결을 같은 시각에 정렬시키고, 그 물결이 스스로를 키운다.

## ⚙️ 작동 원리

기다림을 어떻게 늘릴지는 그림이 말했다. 남은 것은 셋이다 — 무엇을 다시 걸지, 두 번 걸려도 괜찮은지, 어디까지 걸지.

**무엇을 다시 걸지**가 먼저다. 요청량 초과 거절이나 순간 끊김은 다시 걸 값어치가 있지만, 업무 규칙이 틀려서 난 오류는 백 번 걸어도 같은 답이 온다. AWS 문서는 원인을 알 수 있는 오래 갈 고장이면 재시도 대신 서킷 브레이커로 빨리 실패하는 편이 낫다고 적는다.

**멱등한가**가 그다음이다. 상대가 요청을 제대로 처리하고 응답만 못 보냈을 수 있다. 그때 다시 건 요청은 같은 일을 두 번 하게 만든다. 애저 문서와 AWS 문서가 모두 같은 말을 한다 — 재시도를 걸 연산은 멱등해야 하고, 아니면 부분 갱신이 상태를 망가뜨린다.

**어디까지 걸지**는 호출 하나가 아니라 프로세스 단위로 조인다. 구글 SRE 책은 프로세스마다 재시도 예산을 두라고 적는다. 분당 60번까지만 다시 걸게 하고 예산을 넘기면 다시 걸지 않고 곧바로 실패로 답하는 식이다. 예산이 없으면 재시도는 부하가 커질수록 같이 커진다.

## 🚨 주의사항

- **한 층에서만 건다.** 계층마다 재시도를 걸면 곱해진다. 아래층은 빨리 실패하고 그 이유를 위로 올려서, 정책은 한 층에서만 정하게 둔다.
- **기다림이 길어지는 값을 치른다.** 갑절씩 늘린 만큼 답을 받는 시각도 뒤로 밀린다. AWS 문서는 백오프가 최종 사용자의 대기 시간을 늘린다고 적는다.
- **잦은 재시도는 규모 문제의 신호다.** 상대가 늘 바쁘다면 재시도를 늘릴 게 아니라 상대를 늘려야 한다.

## 💡 실제 사례

- **요청량 초과 거절** — 429 가 돌아오면 곧바로 다시 걸지 않고 간격을 늘려 가며 다시 건다. 상대가 스스로를 지키려고 거절한 것이기 때문이다.
- **워크플로 설정** — 재시도 세 번에 배수 1.5 로 잡으면 3초, 4.5초, 6.75초 뒤에 다시 걸고 그래도 실패하면 그 일을 실패로 끝낸다.
- **재시도 예산** — 한 프로세스에서 분당 60번까지만 다시 걸게 하고, 예산을 넘기면 다시 걸지 않고 곧바로 실패로 답한다.

## 🚫 흔한 오해

- **일단 재시도를 넣으면 안정성이 올라간다** — 잠깐 나는 실패에만 그렇다. 오래 갈 고장이나 업무 규칙이 틀려서 난 오류에 다시 걸면 시간과 자원만 쓰고 같은 답을 받는다.
- **재시도는 계층마다 넣어 두면 든든하다** — 겹치면 곱해진다. 구글 SRE 책은 층마다 네 번씩 세 겹이면 사용자의 한 번 누름이 맨 아래에서 64번의 시도가 된다고 적는다.
- **어디서든 다시 걸어 보는 편이 낫다** — 사람이 화면 앞에서 기다리는 자리에서는 짧게 몇 번만 걸고 빨리 실패하는 편이 낫다. 기다리는 동안 화면은 멈춰 있다.

## 📝 정리

**"다시 걸되 갈수록 늦게, 남과 다른 시각에"** 라고 읽으면 된다. 잠깐 나는 실패만 골라 다시 걸고, 기다림을 갑절씩 늘려 상대에게 숨 돌릴 틈을 주고, 무작위를 섞어 다시 걸기가 한 시각에 몰리지 않게 한다. 층마다 겹쳐 걸지 않는 것과 멱등한 연산에만 거는 것, 이 둘을 안 지키면 재시도는 고장을 키우는 쪽이 된다.

## 🧒 열 살에게

친구한테 전화했는데 통화 중이면 바로 또 걸지는 않지? 1분 있다가, 그래도 안 되면 2분, 그다음엔 4분, 이렇게 점점 더 오래 기다렸다 걸어. 다들 똑같이 1분 뒤에 걸면 또 한꺼번에 몰리니까 저마다 조금씩 다르게 기다리는 거야.

## ❓ 이해했는지

- 재시도를 계층마다 넣으면 왜 상황이 더 나빠지나 → 흔한 오해
- 기다리는 시간에 무작위를 안 섞으면 무슨 일이 생기나 → 해결하는 문제
- 응답만 못 받은 요청을 다시 걸기 전에 무엇을 확인해야 하나 → 작동 원리

## 🔗 관련 용어

- [[Circuit Breaker]] — 다시 걸어도 안 되는 상대를 아예 그만 부르는 장치. 재시도와 짝으로 쓴다
- [[Idempotency Key]] — 두 번 걸려도 한 번만 처리되게 만드는 열쇠
- [[Rate Limiting]] — 상대가 요청량을 자를 때 돌아오는 그 거절이 재시도의 대표적인 신호다
- [[Back Pressure]] — 상대가 느릴 때는 다시 거는 대신 보내는 속도를 늦춘다
- [[Latency]] — 기다림을 늘리면 성공률은 오르고 이쪽은 길어진다
