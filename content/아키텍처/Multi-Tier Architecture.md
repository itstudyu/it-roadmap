# Multi-Tier Architecture (여러 층 구조)

## 📝 정의

Multi-Tier Architecture 는 **앱을 화면·처리·저장 층으로 갈라 두는 짜임**이다.

애저 아키텍처 센터는 이 짜임을 두 낱말로 갈라 설명한다. 계층(layer)은 책임을 나누는 선이고, 티어(tier)는 실제로 다른 기계에서 도는 경계다. AWS 백서는 가장 흔한 꼴로 세 층을 든다 — 사람이 직접 만지는 화면 층(presentation), 누른 것을 규칙대로 처리하는 논리 층(logic), 결과를 남기는 저장 층(data).

### 이름
Multi :: 여럿
Tier :: 따로 놓인 한 켜
Architecture :: 짜임새
= 붙여 읽으면 "여러 켜로 짠 구조". 켜와 켜 사이의 선이 곧 기계와 기계 사이의 선이다

### 비유
음식점의 홀·주방·창고 — 손님은 홀에서만 말하고, 창고에는 주방을 거쳐야만 닿는다.

### 예
로그인 화면은 멀쩡히 뜨는데 누르면 "잠시 후 다시 시도해 주세요" 만 나오던 날, 앞 층은 살아 있고 뒤 층이 죽은 것이다.

## 🖼️ 그림으로 보기

```도해
층: 여러 층 구조는 무엇을 무엇 위에 올린 것인가
화면 층 :: 사람이 직접 보고 누르는 자리
처리 층 :: 누른 것을 규칙에 맞게 처리한다
저장 층 :: 결과를 오래 남겨 두는 자리
= 위는 사람에 가깝고 아래는 자료에 가깝다. 위층은 아래층을 부르지만 그 반대는 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 층을 안 가르면 무엇이 달라지나
한 덩어리 || 층으로 갈라
바꿀 때 :: 전부 다시 올린다 || 그 층만 손댄다
늘릴 때 :: 통째로 늘린다 || 붐비는 층만
막을 때 :: 다 같은 자리다 || 층마다 막는다
= 층은 기능을 나누는 선이 아니라, 따로 바꾸고 따로 늘리고 따로 막는 경계다
```

한 덩어리로 두면 화면 글자 하나를 고쳐도 저장까지 통째로 다시 올려야 한다. 화면만 붐비는 날에도 전부를 함께 늘려야 하고, 바깥에서 들어온 것이 곧바로 저장까지 닿는다. 셋이 다른 요구를 갖는데 경계가 하나뿐이라서 생기는 일이다.

층을 가르면 이 셋이 각각 제 경계를 얻는다. 애저 문서는 티어마다 제 서브넷에 두고 서브넷을 보안 경계로 쓰라고 적고, 저장 층은 처리 층에서 온 것만 받게 하라고 적는다. AWS 백서도 이 짜임의 값어치를 "따로 개발하고 따로 관리하고 따로 늘릴 수 있게 하는 틀" 로 적는다. **층은 기능의 분류가 아니라 경계의 개수다.**

## ⚙️ 작동 원리

```도해
대조: 위층이 아래층을 건너뛰어 불러도 되나
닫힌 층 |=| 열린 층
부를 수 있는 곳 :: 바로 아래만 || 아래 아무 층
갈아 끼우기 :: 한 층씩 안전 || 얽힌 데가 는다
거쳐 가는 값 :: 전달만 하는 층 || 없다
= 닫으면 의존이 줄고 거쳐 가는 값이 늘고, 열면 그 반대다
```

계층과 티어는 다른 축이다. 한 티어에 여러 계층을 올려도 되고, 계층마다 티어를 따로 둬도 된다. 티어로 가르면 확장성과 회복력이 오르는 대신 그 사이가 망이라 지연이 붙는다 — 애저 문서가 티어를 나눌 때 반드시 함께 적는 맞바꿈이다.

부르는 규칙에도 두 갈래가 있다. 닫힌 계층은 바로 아래 계층만 부를 수 있고, 열린 계층은 아래 아무 층이나 부를 수 있다. 닫으면 의존이 정리되는 대신 받은 것을 그대로 넘기기만 하는 층이 생기고, 열면 그 헛걸음은 없어지지만 얽힌 데가 늘어 나중에 한 층을 갈아 끼우기 어려워진다. 티어끼리도 같은 갈래가 있다 — 이웃을 하나씩 거치는 엄격한 쪽과 건너뛸 수 있는 느슨한 쪽이다.

곧바로 부르는 대신 메시지 줄을 사이에 두면 층 사이가 느슨해진다. 애저 문서가 이 짜임의 모범 사례에 "티어를 떼어 놓으려면 비동기 메시징을 쓰라" 를 올려 두는 이유가 이것이다.

## 📊 비교: 계층과 티어는 무엇이 다른가

| | 계층 (layer) | 티어 (tier) |
|---|---|---|
| **무엇을 가르나** | 책임 | 기계 |
| **어디서 갈리나** | 코드 안 | 망 위 |
| **가르면 드는 값** | 없다 | 부를 때마다 지연 |
| **가르면 얻는 것** | 의존이 정리된다 | 따로 늘리고 따로 막는다 |

## 💡 실제 사례

- **서브넷으로 층 가르기** — 층마다 다른 서브넷에 두고 저장 층은 처리 층에서 온 것만 받게 막는다. 층 경계가 곧 방화벽 경계가 된다.
- **붐비는 층만 늘리기** — 화면 층 앞에 부하 분산기를 두고 그 층만 여러 대로 불린다. 저장 층은 그대로 둔다.
- **옛 앱 그대로 옮기기** — 이미 층으로 갈라진 사내 앱은 손을 거의 안 대고 클라우드로 옮길 수 있다. 애저 문서가 이 짜임을 권하는 대표 상황이다.

## 🚫 흔한 오해

- **층을 나눴으니 마이크로서비스다** — 아니다. 층으로 갈라도 배포는 여전히 한 덩어리인 경우가 많고, 애저 문서는 이 짜임의 약점으로 기능을 따로 배포하지 못하는 점을 든다.
- **층은 많을수록 좋다** — 받은 것을 그대로 아래로 넘기기만 하는 층은 지연과 코드만 늘린다. 애저 문서가 이 짜임의 첫 번째 함정으로 적는 것이 바로 그런 중간 층이다.
- **계층과 티어는 같은 말이다** — 계층은 코드 안의 책임 경계고 티어는 다른 기계라는 경계다. 한 기계에 세 계층을 다 올리면 계층은 셋인데 티어는 하나다.

## 📝 정리

**"화면·처리·저장을 따로 세운 켜"** 라고 읽으면 된다. 켜를 가르는 값은 부를 때마다 붙는 지연이고, 얻는 것은 따로 바꾸고 따로 늘리고 따로 막을 수 있는 경계다. 그러니 층을 하나 더 세울 때는 그 층이 무슨 경계를 새로 주는지부터 물어야 한다.

## 🧒 열 살에게

음식점에 가면 손님은 홀에만 있고, 요리는 주방에서 하고, 재료는 창고에 쌓아 두지? 이렇게 갈라 두면 홀만 넓히거나 주방만 고칠 수 있고, 손님이 창고에 함부로 들어가는 일도 없어. 다 한방에 몰아 두면 의자 하나 옮기려 해도 가게 문을 통째로 닫아야 해.
