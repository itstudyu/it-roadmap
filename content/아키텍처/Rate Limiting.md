# Rate Limiting (요청량 제한)

## 📝 정의

Rate Limiting은 **정해진 시간 안에 부를 수 있는 횟수를 막는 것**이다.

한 사용자가 1분에 60번까지만 부를 수 있게 정해두면, 61번째부터는 처리하지 않고 거절한다. 서버를 지키는 가장 싸고 확실한 방법이다.

### 비유
놀이공원의 1인당 탑승 제한. 한 사람이 계속 타면 뒤에 선 사람들이 영원히 못 탄다. 제한은 특정인을 막으려는 게 아니라 줄이 돌아가게 하려는 것이다.

### 예
인증번호 재전송 단추가 잠긴 채 60초를 세고 있는 그 화면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 한도를 넘은 요청은 어떻게 처리되나
사용자 :: 1분 사이에 61번째 요청을 보낸다
제한기 :: 이 사용자의 이번 분 횟수를 센다
제한기 :: 60을 넘었다
제한기 :: `429 Too Many Requests` 로 거절한다
< 사용자 :: 얼마 뒤 다시 오라는 안내를 받는다
= 서버가 무너지는 대신 요청 하나가 거절되는 쪽을 고르는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 제한이 없으면 무슨 일이 생기나
제한 없이 || 제한으로
한 사용자 폭주 :: 전체가 느려진다 || 그 사람만 막힌다
비밀번호 대입 :: 무한정 시도 || 몇 번 뒤 차단
서버 비용 :: 예측 불가 || 상한이 생긴다
= 최악의 사용자 한 명이 전체 품질을 정하지 못하게 만든다
```

공개된 API에는 반드시 잘못 쓰는 쪽이 생긴다. 반복문 안에서 실수로 초당 수천 번 부르는 경우가 대부분이고, 일부러 부하를 거는 경우도 있다. 제한이 없으면 그 한 명 때문에 나머지 전원이 느려진다.

보안 측면도 크다. 로그인 요청에 제한이 없으면 비밀번호를 무한정 대입할 수 있다. 다섯 번으로 막으면 그 공격 자체가 성립하지 않는다.

## ⚙️ 작동 원리

세는 방식이 몇 가지 있다.

| 방식 | 어떻게 세나 | 특징 |
|---|---|---|
| 고정 창 | 1분 단위로 끊어서 센다 | 단순하지만 경계에서 두 배가 몰린다 |
| 슬라이딩 창 | 지금부터 1분 전까지를 센다 | 고르지만 계산이 무겁다 |
| 토큰 버킷 | 토큰을 채워두고 쓸 때마다 뺀다 | 순간적인 몰림을 허용한다 |

거절할 때는 `429` 상태 코드와 함께 `Retry-After` 헤더로 언제 다시 오면 되는지 알려준다. 그래야 클라이언트가 무작정 재시도하지 않는다.

## 💡 실제 사례

- **공개 API 등급** — 무료는 시간당 100번, 유료는 10,000번처럼 요금제와 묶는다.
- **로그인 보호** — 같은 계정에 실패가 다섯 번 쌓이면 잠시 막는다.
- **문자 인증 발송** — 한 번호에 하루 몇 건으로 제한한다. 비용이 실제로 나가는 기능이라 안 막으면 그대로 요금이 된다.

## 🚫 흔한 오해

- **제한을 걸면 사용자가 불편해진다** — 제한이 없을 때 모두가 느려지는 쪽이 훨씬 불편하다. 잘 잡은 한도는 정상 사용자에게 닿지 않는다.
- **IP 단위로 막으면 충분하다** — 회사나 학교는 수백 명이 한 IP를 쓴다. 계정이나 API 키 단위로 세는 게 정확하다.
- **`429`는 서버 오류다** — 서버는 멀쩡하다. 의도대로 거절한 것이라 재시도하면 통과한다.

## 🚨 주의사항

- **서버가 여러 대면 횟수도 같이 세야 한다.** 서버마다 따로 세면 서버 수만큼 한도가 늘어난다. Redis 같은 공용 저장소에 센다.
- **`Retry-After`를 빼먹지 않는다.** 언제 다시 오라는 말이 없으면 클라이언트가 바로 다시 두드린다.

## 📝 정리

Rate Limiting은 시간당 호출 횟수에 상한을 두는 장치다. 서버를 지키고 무차별 대입을 막으며, 거절할 때는 언제 다시 오면 되는지 함께 알려주어야 한다.

## ❓ 이해했는지

- 서버를 세 대로 늘렸더니 실제 한도가 세 배가 됐다면 왜 그런가 → 주의사항
- 회사 사무실에서 일부 사용자만 막힌다면 무엇을 기준으로 세고 있을 가능성이 큰가 → 흔한 오해
- `429`를 받은 클라이언트가 곧바로 다시 요청하게 만드는 실수는 무엇인가 → 작동 원리
