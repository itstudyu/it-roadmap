# Idempotency (멱등성)

## 📝 정의

Idempotency는 **여러 번 해도 한 번 한 것과 결과가 같은 성질**이다.

RFC 9110 은 "같은 요청을 여러 번 보냈을 때 서버에 의도된 효과가 한 번 보냈을 때와 같으면" 그 메서드를 멱등이라 부르고, `PUT` 과 `DELETE` 와 안전한 메서드들이 여기 든다고 적는다. 분산된 시스템에서 이 성질이 중요한 이유는 하나다 — 멱등한 것만 마음 놓고 다시 보낼 수 있다.

### 이름
idem :: 같은
potent :: 힘
= 이어 읽으면 "몇 번을 눌러도 같은 힘". 힘이 같으니 또 눌러도 된다는 뜻이다

### 비유
이미 불이 들어온 엘리베이터 버튼을 열 번 더 눌러도 엘리베이터는 한 번만 온다.

### 예
송금 버튼을 눌렀는데 화면이 멈춰서 다시 눌러야 할지 망설였던 그 순간이 멱등이 아닐 때다.

## 🖼️ 그림으로 보기

```도해
층: 여러 번 해도 결과가 같아지는 것은 어디서 정해지나
메서드가 정한다 :: 조회·덮어쓰기·지우기는 규격이 이미 멱등이라 적어 뒀다
연산이 정한다 :: "5로 맞춰라" 는 같고 "5를 더해라" 는 매번 달라진다
붙인 표가 정한다 :: 요청마다 표를 달고, 본 적 있는 표면 첫 결과를 다시 준다
뒤에서 합친다 :: 중복을 찾아 하나로 붙인다. 이미 두 번 일어난 뒤다
= 위에서 정해질수록 공짜고, 아래로 내려올수록 저장하고 관리할 것이 늘어난다
```

## ⚠️ 해결하는 문제

```도해
대조: 응답을 못 받았을 때 다시 보내도 되나
멱등이 아니면 || 멱등이면
재시도 :: 두 건 될까 봐 못 함 || 그냥 다시 보낸다
자동 복구 :: 사람이 확인해야 || 기계가 알아서 한다
중복 전달 :: 그대로 두 번 처리 || 한 번과 같다
= 재시도도 자동 복구도 중복 대비도 전부 이 성질 하나에 매달려 있다
```

보낸 쪽은 **응답이 안 왔다는 사실만으로는 아무것도 알 수 없다.** 요청이 가다가 사라진 것인지, 이미 처리까지 끝났는데 응답만 사라진 것인지 구별할 방법이 없기 때문이다. 다시 보내면 두 번 처리될 수 있고, 안 보내면 아예 빠질 수 있다.

멱등하면 이 갈림길이 없어진다. RFC 9110 은 멱등한 메서드가 특별한 이유가 바로 이것이라고 적는다 — 응답을 읽기 전에 연결이 끊기면 새 연결을 열어 그냥 다시 보내면 된다. 첫 요청이 성공했더라도 의도한 효과는 같기 때문이다. AWS 문서도 재시도와 백오프를 쓸 때 연산이 멱등이어야 하며, 아니면 반쯤 반영된 갱신이 상태를 망칠 수 있다고 적는다. 재시도·자동 복구·"적어도 한 번" 전달이 전부 이 성질 위에 서 있다.

## 📊 비교: 어떤 연산이 저절로 멱등인가

| 하는 일 | 멱등인가 | 왜 |
|---|---|---|
| **조회** (`GET`) | 그렇다 | 상태를 안 바꾼다 |
| **덮어쓰기** (`PUT`) | 그렇다 | 몇 번을 써도 같은 값이 남는다 |
| **지우기** (`DELETE`) | 그렇다 | 두 번째는 이미 없는 것을 지운다 |
| **새로 만들기** (`POST`) | 아니다 | 부를 때마다 하나가 더 생긴다 |
| **값 더하기** (`+1`) | 아니다 | 부른 횟수가 그대로 결과에 남는다 |
| **상태 바꾸기** (`승인함`) | 정하기 나름 | 이미 승인된 건을 또 승인하면 어떻게 할지 적어 둬야 한다 |

설계에서 갈리는 자리는 맨 아래 두 줄이다. "잔액을 5000원으로 맞춰라" 로 쓸 수 있는 것을 "5000원을 더해라" 로 쓰면 재시도가 위험해진다. **표현을 바꾸는 것만으로 멱등을 공짜로 얻는 경우가 많다.**

## 💡 실제 사례

- **결제 승인** — 응답이 끊겨도 같은 표를 붙여 다시 보내면 승인은 한 건만 남는다. 이 성질이 없으면 재시도를 아예 못 건다.
- **메시지 소비** — 큐는 대개 "적어도 한 번" 을 보장한다. 같은 메시지가 두 번 와도 처리한 id 를 적어 두고 걸러야 결과가 한 번과 같아진다.
- **설정 적용** — 같은 선언을 열 번 적용해도 결과가 같게 만들어 두면, 도중에 실패한 작업을 처음부터 그냥 다시 돌릴 수 있다.

## 🚫 흔한 오해

- **응답이 안 왔으면 실패한 거니까 다시 보내면 된다** — 이미 처리되고 응답만 유실됐을 수 있다. 보낸 쪽에는 둘을 구별할 방법이 없고, RFC 9110 은 그래서 프록시가 멱등하지 않은 요청을 자동으로 재시도해서는 안 된다고 못 박는다.
- **멱등이면 두 번째 요청은 아무 일도 안 한다** — 결과가 같다는 뜻이지 아무 일도 안 한다는 뜻이 아니다. RFC 9110 은 서버가 요청마다 따로 기록을 남기거나 이력을 쌓는 것은 멱등과 무관하다고 적는다.
- **전부 멱등하게 만들어 두면 안전하다** — 멱등이 아닌 것을 멱등하게 만들려면 표와 처리 결과를 저장하고 언제 지울지까지 관리해야 한다. 두 번 일어나도 손해가 없는 일에는 그 저장소가 순수한 낭비다.

## 🚨 주의사항

- **응답까지 같아야 하는 것은 아니다.** 두 번째에 첫 결과를 그대로 주든 겹쳤다고 알리든, 남는 상태만 같으면 멱등이다. 무엇을 줄지는 문서에 밝힌다.
- **기록을 언제 지울지가 곧 재시도 유효기간이다.** 하루만 들고 있으면 이틀 뒤에 온 재시도는 새 요청으로 취급된다.
- **어디서 재시도가 일어나는지 그림에 그려 둔다.** 앞단, 미들웨어, 라이브러리, 큐가 저마다 몰래 다시 보내면 멱등하지 않은 자리가 조용히 두 번 실행된다.

## 📝 정리

**"몇 번을 눌러도 같은 그 성질"** 이라고 읽으면 된다. 응답이 안 온 요청은 성공인지 실패인지 알 수 없고, 그래서 다시 보내도 되는지는 이 성질 하나가 정한다. 규격이나 표현으로 공짜로 얻어지는 자리가 있고 표를 저장해 사서 써야 하는 자리가 있으니, 두 번 일어나면 손해인 일에만 값을 치른다.

## 🧒 열 살에게

엘리베이터 버튼에 이미 불이 켜져 있으면 열 번을 더 눌러도 엘리베이터는 한 번만 오지? 몇 번을 눌렀든 똑같으니까 마음 놓고 또 눌러도 돼. 그런데 붕어빵은 시킬 때마다 하나씩 더 나오니까 두 번 말하면 두 개가 돼 버려.

## ❓ 이해했는지

- 보낸 쪽이 성공인지 실패인지 끝내 알 수 없는 경우는 왜 생기나 → 해결하는 문제
- 값을 5로 맞추는 것과 5를 더하는 것은 무엇이 다른가 → 비교
- 모든 일을 멱등하게 만들어 두는 것이 낭비가 되는 까닭은 → 흔한 오해
