# BFF (Backend for Frontend)

## 📝 정의

BFF는 **화면 종류마다 따로 두는 전용 백엔드**다.

폰 앱과 데스크톱 화면은 화면 크기도, 성능도, 한 번에 보여줄 수 있는 양도 다르다. 그런데 뒤쪽이 하나면 그 서로 다른 요구가 한 곳에 몰려 부딪친다. BFF는 그 부딪침을 화면별 층 하나로 흡수하는 자리다.

### 이름
Backend :: 뒤에서 일하는 쪽
for :: ~만을 위한
Frontend :: 눈에 보이는 화면
= 붙여 읽으면 "그 화면 하나만을 위한 뒤쪽". 이름이 곧 이 층의 범위다

### 비유
손님마다 따로 싸 주는 도시락. 같은 주방에서 만들지만 아이 것은 양을 줄이고 반찬을 골라 담는다.

### 예
같은 서비스인데 폰에서는 목록이 한 화면씩 오고 웹에서는 여러 화면이 한꺼번에 오는 그 차이다.

## 🖼️ 그림으로 보기

```도해
층: 화면과 업무 서비스 사이에 무엇이 끼어 있나
화면 :: 폰 앱과 데스크톱처럼 요구가 다른 앞쪽들
공용 관문 :: 인가·기록·요청량 제한 같은 공통 일을 맡는다
전용 뒤쪽 :: 화면 종류마다 하나씩. 그 화면에 맞게만 다듬는다
업무 서비스 :: 주문·결제·재고. 어느 화면인지 모른다
= 화면마다 다른 요구를 전용 층에서 받아내고, 아래 업무 서비스는 그대로 둔다
```

## ⚠️ 해결하는 문제

```도해
대조: 앞쪽이 여럿인데 뒤쪽이 하나면 무슨 일이 생기나
공용 뒤쪽 하나 || 화면마다 하나
요구가 부딪치면 :: 서로 조율해야 || 각자 정한다
배포 :: 남을 기다린다 || 팀이 알아서 낸다
폰에 맞추기 :: 다 같이 받는다 || 그 화면만 바꾼다
= 앞쪽이 여럿이면 공용 뒤쪽 하나가 병목이 된다. 그 병목을 화면 수만큼 쪼갠 것이다
```

뒤쪽 하나가 여러 앞쪽의 요구를 동시에 받으면 고칠 일이 잦아지고, 그 하나를 고치려고 줄을 서게 된다. 한 앞쪽 팀이 요청한 변경을 다른 앞쪽 팀들과 맞춰 본 뒤에야 넣을 수 있고, 호환을 지키느라 손을 못 대는 자리가 늘어난다. 뒤쪽을 따로 관리하는 팀이 있으면 그 사이가 더 벌어진다.

BFF는 그 층을 화면 수만큼 나눠 놓는다. 앞쪽 팀이 자기 뒤쪽을 직접 들고 있으면 언어도, 낼 시점도, 무엇을 먼저 할지도 스스로 정한다. 각 뒤쪽이 작아지므로 다루기도 쉬워진다.

## ⚙️ 작동 원리

```도해
흐름: 폰 화면 하나를 열면 무엇이 순서대로 일어나나
화면 :: 자기 전용 뒤쪽 한 곳에만 요청을 보낸다
전용 뒤쪽 :: 주문·재고·추천을 한꺼번에 부른다
업무 서비스 :: 각자 자기 것만 돌려준다
전용 뒤쪽 :: 폰에 쓸 것만 골라 하나로 합친다
< 화면 :: 받은 그대로 그린다. 더 부를 곳이 없다
= 여러 번 오갈 일을 뒤쪽 한 자리로 옮겨서 화면은 한 번만 부른다
```

화면은 업무 서비스의 주소를 하나도 모른다. 아는 것은 자기 전용 뒤쪽 하나뿐이다. 화면이 셋을 직접 부르면 느린 회선에서 왕복이 세 번 일어나고, 그 셋을 합치는 코드가 앱 안에 들어가 앱을 새로 받아야 고칠 수 있게 된다. 뒤쪽에서 합치면 왕복은 한 번이고, 고칠 때는 뒤쪽만 다시 배포한다.

한 서비스가 답을 못 줄 때 무엇을 내놓을지도 이 층이 정한다. 추천이 죽었을 때 그 칸만 비운 응답을 내려보낼지 요청 전체를 실패로 칠지는 화면마다 다르고, 그 판단을 화면별로 따로 둘 수 있는 것이 뒤쪽을 나눠 둔 값이다.

## 📊 비교: BFF · API 게이트웨이 · GraphQL

| 무엇 | 무엇을 맡나 | 몇 개 두나 |
|---|---|---|
| **BFF** | 그 화면 하나에만 해당하는 다듬기 | 화면 종류만큼 |
| **API 게이트웨이** | 인가·기록·캐시·라우팅 같은 공통 일 | 대개 하나 |
| **GraphQL** | 화면이 필요한 것만 골라 물어보게 하기 | 대개 하나 |

세 자리가 겹쳐 보이지만 맡는 것이 다르다. 공통 일을 BFF에 넣으면 화면 수만큼 같은 코드를 복사하게 되고, 화면별 다듬기를 게이트웨이에 넣으면 다시 공용 병목이 된다. Azure 문서는 앞쪽에서 필요한 것만 골라 가져가는 방식을 이미 쓰고 있다면 BFF 층이 값을 못 할 수도 있다고 적고, 게이트웨이와 마이크로서비스 조합만으로 충분한 경우도 있다고 덧붙인다.

## 💡 실제 사례

- **폰과 데스크톱** — 폰 쪽은 대역폭을 아끼려고 한 화면씩 내려주고, 데스크톱 쪽은 여러 화면을 한 번에 모아 내려준다.
- **여러 곳의 값 모으기** — 앞쪽이 서비스 여럿을 각각 부르는 대신 전용 뒤쪽이 모아서 한 번에 내려준다. 오가는 횟수와 양이 줄어든다.
- **화면에 열어 줄 수 없는 API** — 밖에 공개하지 않은 내부 API를 전용 뒤쪽이 대신 부른다. 화면은 그 주소도 열쇠도 갖지 않는다.

## 🚫 흔한 오해

- **앞쪽이 둘이면 뒤쪽도 둘로 나누는 게 맞다** — 아니다. Azure 문서는 여러 화면이 같거나 비슷한 것만 물어보는 경우, 그리고 화면이 하나뿐인 경우에는 이 패턴이 맞지 않는다고 적는다. 나누는 순간 서비스 하나가 늘고, 그만큼 배포·유지·보안을 따로 감당한다.
- **BFF에 인가랑 요청량 제한도 같이 넣으면 편하다** — BFF는 그 화면의 사용자 경험에 딸린 일만 맡는 자리다. 공통으로 걸릴 일은 따로 빼서 관문에 두라고 문서가 적는다.
- **여러 화면이 BFF 하나를 같이 쓰면 중복이 준다** — 줄기는 하지만 그 하나가 다시 서로 다른 요구를 받는 자리가 된다. AWS 문서는 BFF가 자기 경계 안에서만 돌아야 하고 다른 경계와 공유되어서는 안 된다고 못 박는다.

## 🚨 주의사항

- **한 번 더 건너간다.** 화면이 업무 서비스를 직접 부르지 않고 전용 뒤쪽을 거치므로 지연이 붙는다. 층을 하나 세울 때마다 응답 목표를 다시 잰다.
- **코드가 겹치는 것은 이 패턴이 치르는 값이다.** 화면마다 비슷한 코드를 또 쓰게 된다. 그 중복과 화면에 딱 맞는 응답 중 무엇이 더 값진지 저울에 올려 정한다.
- **몇 개까지 둘지 비용으로 정한다.** 뒤쪽 하나가 늘 때마다 수명 주기와 배포, 유지, 보안이 한 벌 더 생긴다. 화면 수가 아니라 감당할 수 있는 운영량이 상한이다.

## 📝 정리

**"그 화면 하나만 챙기는 전용 뒤쪽"** 이라고 읽으면 된다. 공용 뒤쪽 하나가 여러 앞쪽의 요구에 눌려 병목이 될 때, 그 층을 화면 종류만큼 쪼개 앞쪽 팀에게 넘기는 방법이다. 화면들이 서로 다른 것을 요구할 때만 값을 하고, 비슷한 것만 물어본다면 뒤쪽 개수만 늘어난다.

## 🧒 열 살에게

급식실 한 곳에서 밥을 만들어도 1학년 도시락은 양을 줄이고 반찬을 골라 담아 주지? 그러면 1학년이 반찬을 바꿔 달라고 해도 6학년 도시락은 그대로야. 대신 도시락 종류가 늘어날수록 싸는 사람은 더 바빠져.

## ❓ 이해했는지

- 게이트웨이만으로 충분한 경우와 전용 뒤쪽이 필요한 경우는 무엇이 다른가 → 비교
- 화면마다 뒤쪽을 나누면 코드가 겹치는데 그 중복을 왜 감수하나 → 주의사항
- 앞쪽 팀이 자기 배포 시점을 스스로 정할 수 있게 되는 이유는 무엇인가 → 해결하는 문제
