# 모놀리스 vs 마이크로서비스

## 📝 정의

모놀리스(Monolith)와 마이크로서비스(Microservices)는 소프트웨어 아키텍처의 두 가지 대비되는 패러다임입니다. 모놀리스는 모든 기능이 하나의 큰 코드베이스와 단일 서버에서 실행되는 전통적 방식이며, 마이크로서비스는 기능을 여러 개의 독립적인 작은 서비스로 분리하여 각각 독립적으로 배포하고 운영하는 현대적 방식입니다.

모놀리스는 개발 초기 단계에서 빠른 개발과 배포가 가능하며 단순한 구조로 유지보수가 쉽습니다. 그러나 서비스가 커질수록 코드베이스가 거대해지고, 작은 변경도 전체 시스템에 영향을 미치며, 특정 기능만 확장할 수 없다는 한계가 있습니다. 반면 마이크로서비스는 높은 확장성과 기술 자유도를 제공하지만, 네트워크 통신 오버헤드, 분산 시스템의 복잡성, 데이터 일관성 문제 등 새로운 도전과제를 만듭니다.

> 모놀리스 = 모든 기능이 하나의 코드베이스와 서버에 있는 전통적 아키텍처 / 마이크로서비스 = 기능별로 분리된 독립 서비스들이 협력하는 현대적 아키텍처

**비유 1**: 모놀리스는 백화점이고 마이크로서비스는 쇼핑몰입니다. 백화점은 모든 기능(의류, 식품, 전자제품)이 한 건물에 있고 중앙에서 관리하지만, 한 부서 변경이 전체에 영향을 미칩니다. 쇼핑몰은 각 가게가 독립적으로 운영되므로 유연하지만, 가게 간 이동과 통신이 필요합니다.

**비유 2**: 모놀리스는 자동차의 엔진이고 마이크로서비스는 자동차의 부품입니다. 엔진은 하나로 통합되어 제어가 간단하지만, 부품 교체가 어렵습니다. 부품으로 분리하면 특정 부분만 업그레이드할 수 있지만, 호환성과 조립이 복잡합니다.

## 🎯 핵심 개념

### 1. 모놀리스의 특징
모놀리스는 모든 기능이 하나의 애플리케이션으로 통합되어 있습니다. 사용자 관리, 상품 관리, 결제, 배송 등 모든 기능이 같은 프로그래밍 언어로 작성되고, 같은 데이터베이스를 사용하며, 같은 서버에서 실행됩니다. 배포도 전체 애플리케이션을 한 번에 배포하므로 과정이 단순합니다.

### 2. 마이크로서비스의 특징
마이크로서비스는 기능별로 서비스를 분리합니다. 각 서비스는 자신의 데이터베이스를 가지고 독립적으로 배포되며, 각 팀이 자신의 기술 스택을 선택할 수 있습니다. API(주로 REST 또는 메시지 큐)를 통해 서비스 간 통신을 합니다.

### 3. 개발 팀 구조의 차이
모놀리스는 기능 단위가 아닌 기술 단위로 팀을 구성합니다(프론트엔드팀, 백엔드팀, 데이터베이스팀). 마이크로서비스는 기능 단위로 팀을 구성하며(사용자팀, 상품팀, 결제팀), 각 팀이 기획부터 배포까지 전체 라이프사이클을 담당하는 'Full-Stack' 팀이 됩니다.

## ⚠️ 해결하는 문제

### 문제 1: 스타트업의 빠른 시장 진출 (모놀리스 해결)
초기 스타트업은 빠르게 시장에 진출해야 합니다. 마이크로서비스의 복잡한 인프라를 구축하는 것은 시간과 비용 낭비입니다. 모놀리스는 간단한 구조로 신속하게 MVP(최소 실행 제품)를 만들고 배포할 수 있습니다.

### 문제 2: 성장 단계의 확장성 요구 (마이크로서비스 해결)
서비스가 성장하면서 특정 기능(예: 결제 처리)에만 트래픽이 집중됩니다. 모놀리스에서는 전체 서버를 확장해야 하므로 비효율적입니다. 마이크로서비스는 트래픽이 많은 서비스만 선택적으로 확장할 수 있습니다.

### 문제 3: 기술 스택 고정의 제약 (마이크로서비스 해결)
모놀리스에서는 전체 애플리케이션이 같은 기술로 작성되므로, 새로운 기술로 마이그레이션할 수 없습니다. 마이크로서비스는 각 서비스를 독립적으로 기술 스택을 선택할 수 있어, 새로운 기술 도입이 용이합니다.

## ⚙️ 작동 원리

**모놀리스의 요청 처리:**

사용자가 상품을 구매하려 할 때:
1. 프론트엔드에서 백엔드 API로 요청 전송
2. 같은 서버의 모놀리틱 애플리케이션이 모든 로직 처리
3. 사용자 정보 조회, 상품 확인, 결제 처리, 배송 예약을 모두 처리
4. 하나의 데이터베이스에 모든 정보를 저장
5. 응답을 사용자에게 반환

**마이크로서비스의 요청 처리:**

사용자가 상품을 구매하려 할 때:
1. 프론트엔드에서 API Gateway로 요청 전송
2. API Gateway가 요청을 각 마이크로서비스로 라우팅
3. 사용자 서비스 → 사용자 정보 조회 및 저장
4. 상품 서비스 → 상품 정보 조회
5. 결제 서비스 → 결제 처리 및 저장
6. 배송 서비스 → 배송 예약 및 저장
7. 각 서비스가 독립적인 데이터베이스에 데이터 저장
8. API Gateway가 모든 응답을 모아서 사용자에게 반환

각 서비스는 각각의 기술 스택을 사용할 수 있으며, 서로 다른 팀이 독립적으로 개발하고 배포할 수 있습니다.

## ✅ 장단점

**모놀리스의 장점:**
- 개발이 간단하고 빠릅니다. 모든 것이 한 코드베이스에 있어 이해하기 쉽습니다.
- 배포 프로세스가 단순합니다. 전체 애플리케이션을 한 번에 배포하면 됩니다.
- 트랜잭션 관리가 쉽습니다. 데이터베이스 ACID 속성을 그대로 사용할 수 있습니다.
- 운영 초기 비용이 저렴합니다. 복잡한 인프라가 필요하지 않습니다.
- 디버깅과 테스트가 상대적으로 간단합니다. 모든 것이 하나의 프로세스에서 실행됩니다.

**모놀리스의 단점:**
- 코드베이스가 커질수록 유지보수가 어려워집니다.
- 작은 변경도 전체 시스템을 다시 배포해야 하므로 위험합니다.
- 특정 기능만 확장할 수 없습니다. 전체 서버를 확장해야 합니다.
- 한 부분의 장애가 전체 시스템을 내릴 수 있습니다.
- 기술 스택을 변경할 수 없으므로 새로운 기술 도입이 어렵습니다.

**마이크로서비스의 장점:**
- 독립 배포로 배포 속도가 매우 빠릅니다.
- 필요한 서비스만 선택적으로 확장할 수 있습니다.
- 각 팀이 원하는 기술 스택을 선택할 수 있습니다.
- 한 서비스의 장애가 다른 서비스에 영향을 미치지 않습니다(장애 격리).
- 팀 간 개발이 병렬로 진행되므로 개발 속도가 빠릅니다.

**마이크로서비스의 단점:**
- 분산 시스템의 복잡성이 매우 높습니다.
- 서비스 간 네트워크 통신으로 지연 시간이 발생합니다.
- 데이터 일관성 관리가 어렵습니다. ACID 트랜잭션을 사용할 수 없습니다.
- 운영 인프라가 복잡하고 비용이 많이 듭니다(Docker, Kubernetes 등).
- 서비스 간 통신 오류를 처리해야 합니다.
- 모니터링과 디버깅이 매우 복잡합니다.

## 💡 실제 사례

**사례 1: Amazon의 전환**
Amazon은 2002년 모놀리스 아키텍처에서 마이크로서비스로 전환했습니다. 각 팀이 자신의 서비스를 API로 노출하도록 강제했으며, 이를 통해 개발 속도가 획기적으로 향상되었습니다. 오늘날 Amazon은 수십만 개의 마이크로서비스로 구성되어 있습니다.

**사례 2: Netflix의 마이크로서비스 여정**
Netflix는 초기에 모놀리스 구조로 시작했으나, 2008년 서버 장애로 8일간 서비스 중단을 겪었습니다. 이후 마이크로서비스로 전환하여 현재는 200개 이상의 서비스로 구성되어 있으며, 하루에 수백 번의 배포가 이루어집니다.

**사례 3: 스타트업의 모놀리스 시작**
Uber, Airbnb 등 대부분의 성공한 스타트업은 모놀리스로 시작했습니다. 신속한 시장 진출이 필수적이었고, 초기에는 모놀리스의 단순함이 장점이었습니다. 사용자가 수백만 명으로 증가한 후에야 마이크로서비스로 전환했습니다.

**사례 4: 모놀리스 유지의 경우**
Slack, Discord 같은 일부 성공한 서비스도 여전히 모놀리스 또는 준(Semi)-모놀리스 구조를 유지하고 있습니다. 팀 규모가 크더라도 조직 문화와 개발 규율로 모놀리스를 효과적으로 관리할 수 있습니다.

## 🔗 관련 용어

- **API Gateway**: 마이크로서비스 앞단에서 모든 요청을 받아 적절한 서비스로 라우팅하는 컴포넌트
- **서비스 메시**: 마이크로서비스 간 통신을 위한 인프라 기술
- **분산 트랜잭션**: 여러 마이크로서비스에 걸친 트랜잭션 처리
- **Saga 패턴**: 마이크로서비스에서 분산 트랜잭션을 관리하는 패턴
- **Docker**: 마이크로서비스를 컨테이너로 패키징하는 기술
- **Kubernetes(K8s)**: 마이크로서비스 오케스트레이션 플랫폼
- **CI/CD**: 지속적 통합/배포, 마이크로서비스에서 필수
- **서킷 브레이커(Circuit Breaker)**: 마이크로서비스 간 장애 전파 방지 패턴
