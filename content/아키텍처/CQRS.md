# CQRS (Command Query Responsibility Segregation)

## 📝 정의

CQRS는 **읽기와 쓰기를 서로 다른 모델로 가르는 설계**다.

한 모델이 둘을 다 감당하면 한쪽에 맞출 때마다 다른 쪽이 손해를 본다. 쓰기는 업무 규칙을 따지느라 무거워야 하고, 읽기는 화면에 낼 모양 그대로 가벼워야 한다. 두 요구가 원래 다르다는 것을 인정하고 모델을 갈라 놓은 것이 이 패턴이다.

### 이름
Command :: 바꾸라는 지시
Query :: 물어보는 일
Responsibility :: 맡은 몫
Segregation :: 갈라 놓기
= 붙여 읽으면 "바꾸는 일과 묻는 일의 몫을 갈라 놓기". 한국어로는 명령 질의 책임 분리라고 읽는다

### 비유
주문서는 주방으로 들어가고 손님은 사진까지 박아 둔 메뉴판만 보는 식당.

### 예
리뷰를 올리면 "등록되었습니다" 는 곧바로 뜨는데 상품 페이지의 별점 평균은 몇 초 뒤에야 바뀌는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
대조: 바꾸는 일과 묻는 일을 갈라 놓으면 각자 무엇을 하나
쓰기 모델 |=| 읽기 모델
받는 것 :: "예약해" 라는 지시 || "목록 줘" 라는 질문
하는 일 :: 규칙을 따져 고친다 || 만들어 둔 표를 읽는다
맞춘 곳 :: 업무 규칙 || 화면 모양
= 한 모델이 둘을 겸하지 않는다. 바꾸는 쪽과 묻는 쪽을 갈라 각자에 맞춘다
```

## ⚠️ 해결하는 문제

```도해
대조: 읽기와 쓰기가 한 모델을 같이 쓰면 무엇이 걸리나
한 모델로 || 두 모델로
구조 :: 한쪽에 맞추면 손해 || 각자에 맞춘다
확장 :: 같이 늘려야 한다 || 따로 늘린다
잠금 :: 같은 줄을 두고 다툰다 || 다툴 일이 준다
= 두 일은 요구가 다르다. 한 모델은 그 차이를 담지 못한다
```

읽기와 쓰기는 성능과 확장 요구가 서로 다른데, 전통적인 CRUD 구조는 그 비대칭을 반영하지 않는다. Microsoft 문서는 그래서 생기는 것으로 넷을 든다 — 갱신에만 필요한 항목까지 조회가 떠안는 표현의 불일치, 같은 자료를 동시에 건드릴 때의 잠금 다툼, 복잡한 질의가 저장소에 얹는 부하, 그리고 하나의 개체가 읽기와 쓰기를 겸할 때 어려워지는 권한 관리다.

CQRS는 그 둘을 갈라서 각자 다르게 손보게 한다. 조회가 쓰기보다 열 배쯤 많은 화면이라면 읽기 쪽만 늘리면 되고, 조회용 표는 조인 없이 바로 읽히는 모양으로 따로 만들어 둘 수 있다. 반대로 업무 규칙이 단순하고 CRUD 화면으로 충분한 곳이라면, Microsoft 문서도 이 패턴이 맞지 않는다고 적는다.

## ⚙️ 작동 원리

```도해
층: 가르는 깊이를 어디까지 밀 수 있나
모델만 가르기 :: 저장소는 하나. 읽기 로직과 쓰기 로직만 나눈다
저장소까지 가르기 :: 읽기 전용 복제본이나 다른 종류의 저장소를 둔다
원본까지 가르기 :: 사건 기록이 원본이 되고 조회용 표는 거기서 만든다
= 아래로 갈수록 얻는 것도 크고 감당할 것도 크다. 필요한 깊이까지만 내려간다
```

가장 얕은 단계는 저장소 하나를 그대로 두고 모델만 나누는 것이다. 쓰기 모델은 검증과 업무 규칙을 담고, 읽기 모델은 업무 규칙 없이 화면에 넘길 자료 묶음만 만든다. 여기까지만 해도 책임이 갈라져서 두 쪽 코드가 서로를 방해하지 않는다.

한 단계 내려가면 저장소를 따로 둔다. 그러면 읽기와 쓰기를 각자의 부하에 맞춰 늘릴 수 있고, 한쪽은 문서 저장소 다른 쪽은 관계형처럼 종류를 달리 고를 수도 있다. 대신 둘을 맞춰 주어야 한다. 흔한 방법은 쓰기 쪽이 바뀔 때마다 사건을 발행하고 읽기 쪽이 그걸 받아 자기 표를 고치는 것이다.

가장 깊은 단계가 [[Event Sourcing]]과 붙인 형태다. 사건 기록 자체가 쓰기 모델이자 유일한 원본이 되고, 조회용 표는 그 사건을 재생해 만든 결과가 된다. 표를 새로 만들거나 모양을 바꾸고 싶으면 과거 사건을 다시 재생하면 된다.

## 💡 실제 사례

- **읽기 쪽만 늘리기** — 조회가 쓰기보다 열 배쯤 많은 화면에서는 읽기 모델만 여러 대로 늘리고 쓰기 모델은 적은 수로 둔다.
- **화면에 맞춘 표** — 조인을 여러 번 해야 나오는 목록을 미리 한 줄로 만들어 두고, 조회는 그 표만 읽는다.
- **팀을 나눠 붙이기** — 복잡한 업무 규칙은 쓰기 쪽 팀이 맡고, 화면과 조회는 읽기 쪽 팀이 따로 만든다.

## 🚫 흔한 오해

- **CQRS를 쓰면 어떤 시스템이든 더 낫다** — 업무 규칙이 단순하고 CRUD 화면으로 충분한 곳에서는 모델만 둘로 늘어난다. Microsoft 문서도 그런 자리에는 이 패턴이 맞지 않는다고 적는다.
- **저장소를 두 개 써야 CQRS다** — 아니다. 저장소 하나를 그대로 두고 읽기 모델과 쓰기 모델만 나누는 것이 이 패턴의 기본 단계다.
- **CQRS는 곧 이벤트 소싱이다** — 자주 같이 쓸 뿐 다른 패턴이다. 메시징조차 필수가 아니고, 둘을 합치면 설계 난도가 한 단계 더 올라간다.

## 🚨 주의사항

- **읽는 값은 잠깐 옛것이다.** 저장소를 가르는 순간 조회 쪽은 최신 변경을 바로 보여주지 못한다. 사용자가 낡은 값을 보고 행동하는 경우를 어떻게 다룰지 미리 정해야 한다.
- **원본을 고치는 일과 소식을 보내는 일은 한 묶음이 아니다.** Microsoft 문서는 메시지 브로커와 데이터베이스를 하나의 분산 트랜잭션으로 묶을 수 없는 것이 보통이라 적고, 상태 변경과 사건을 함께 확정하는 아웃박스와 같은 소식을 두 번 받아도 결과가 같은 소비자를 쓰라고 권한다.
- **도구가 대신 만들어 주지 않는다.** 스키마에서 코드를 뽑아 주던 O/RM 방식이 여기서는 통하지 않아서, 두 모델 사이를 잇는 로직을 직접 써야 한다.

## 📝 정리

**"바꾸는 길과 묻는 길을 따로 낸 설계"** 라고 읽으면 된다. 저장소를 하나 둔 채 모델만 가르는 것부터 저장소와 원본까지 가르는 것까지 깊이가 여러 단계이고, 깊이 내려갈수록 얻는 것도 감당할 것도 커진다. 값이 잠깐 어긋나는 것을 받아들일 수 있고 읽기와 쓰기의 요구가 실제로 다를 때만 고른다.

## 🧒 열 살에게

식당에서 주문서는 주방으로 들어가지? 그런데 너는 주방을 들여다보는 게 아니라 사진 붙은 메뉴판만 보고 고르잖아. 그래서 주방에서 재료가 다 떨어져도, 누가 메뉴판을 바꿔 붙이기 전까지는 그 사진이 그대로 걸려 있어.
