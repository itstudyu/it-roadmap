# Circuit Breaker (서킷 브레이커)

## 📝 정의

Circuit Breaker는 **고장 난 서비스 호출을 잠시 끊어버리는 장치**다.

응답이 없는 서비스를 계속 부르면 기다리는 요청이 쌓이고, 결국 부르는 쪽까지 같이 죽는다. 그래서 실패가 일정 횟수를 넘으면 아예 부르지 않고 즉시 실패로 처리한다.

### 비유
집의 두꺼비집. 전선에 문제가 생기면 알아서 내려가서 집 전체가 타는 걸 막는다. 고쳤다고 확신하기 전에 한 번 올려보고, 또 튀면 다시 내린다.

## 🖼️ 그림으로 보기

```도해
흐름: 결제 서비스가 죽으면 주문 서비스는 무엇을 하나
주문 서비스 :: 결제 서비스를 부른다. 응답이 없다
차단기 :: 실패를 센다. 다섯 번째다
차단기 :: 열린다. 이제부터 부르지 않는다
주문 서비스 :: 즉시 "결제 잠시 불가" 로 답한다
차단기 :: 30초 뒤 한 번만 시험 삼아 통과시킨다
< 차단기 :: 성공하면 닫고, 또 실패하면 다시 연다
= 죽은 곳을 계속 두드리지 않는 것이 무너짐을 막는다
```

## ⚠️ 해결하는 문제

```도해
대조: 아래 서비스 하나가 느려지면 어떻게 되나
차단기 없이 || 차단기로
대기 요청 :: 계속 쌓인다 || 즉시 실패 처리
스레드 :: 전부 붙잡힌다 || 풀려 있다
결과 :: 부르는 쪽도 죽음 || 그 기능만 막힘
= 한 곳의 고장이 옆으로 번지지 않게 벽을 세우는 것이다
```

서비스 하나가 죽는 것보다 무서운 건 그 죽음이 번지는 것이다. 결제 서비스가 응답하지 않으면 주문 서비스의 스레드가 하나씩 거기 붙잡히고, 몇 분 안에 주문 서비스도 새 요청을 못 받는다. 주문이 멈추면 그 위의 화면 서비스도 멈춘다.

차단기는 그 사슬을 끊는다. 결제가 안 되는 것과 사이트 전체가 안 되는 것은 전혀 다른 사고다.

## ⚙️ 작동 원리

상태가 셋이다.

```도해
층: 차단기는 어떤 상태를 오가나
닫힘 :: 평소. 그냥 통과시키고 실패만 센다
열림 :: 실패가 한도를 넘음. 부르지 않고 즉시 실패
반열림 :: 일정 시간 뒤. 한 건만 시험 삼아 통과
= 반열림이 있어서, 회복됐는지 확인하려고 폭주시키지 않아도 된다
```

열림 상태에서 무엇을 돌려줄지 정해두는 것이 중요하다. 캐시에 있던 옛 값을 주거나, 기본값을 주거나, 사용자에게 솔직하게 알리거나. 이 대비책을 폴백이라고 한다.

## 💡 실제 사례

- **추천 목록** 추천 서비스가 죽으면 인기 상품 목록으로 대체한다. 화면은 계속 뜬다.
- **외부 API** 환율 API가 응답하지 않으면 마지막으로 받은 환율을 그대로 쓰고 표시만 바꾼다.
- **부분 장애 표시** 결제만 막히면 "결제 점검 중"으로 안내하고 장바구니는 계속 쓰게 둔다.

## 🚫 흔한 오해

- **차단기가 장애를 고쳐준다** — 고치지 않는다. 번지는 것을 막을 뿐이고, 고장 난 서비스는 여전히 고장 나 있다.
- **재시도를 하면 차단기는 필요 없다** — 반대다. 재시도만 하면 죽어가는 서비스에 부하를 더 얹어 더 빨리 죽인다. 재시도와 차단기는 같이 써야 한다.
- **열림 상태는 오류다** — 설계대로 동작하는 정상 상태다. 오류로 취급해 알람을 끄면 정작 볼 신호를 잃는다.

## 🚨 주의사항

- **폴백을 정해두지 않으면 절반만 쓴 것이다.** 열렸을 때 무엇을 돌려줄지가 사용자 경험을 정한다.
- **한도를 너무 낮게 잡지 않는다.** 일시적인 지연에도 열려버리면 멀쩡한 기능이 자주 막힌다.

## 📝 정리

Circuit Breaker는 실패가 반복되는 호출을 잠시 끊어 장애가 번지는 것을 막는 장치다. 닫힘, 열림, 반열림 세 상태를 오가며, 열렸을 때 무엇을 돌려줄지 정해두어야 제 값을 한다.

## ❓ 이해했는지

- 결제 서비스 하나가 느려졌는데 사이트 전체가 멈추는 이유는?
- 재시도만 넣으면 왜 상황이 더 나빠지나?
- 반열림 상태가 없으면 회복 확인을 어떻게 해야 하고, 그게 왜 위험한가?
