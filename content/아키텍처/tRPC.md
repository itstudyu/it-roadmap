# tRPC

## 📝 정의

tRPC는 **서버 함수의 타입을 클라이언트에 그대로 물려주는 도구**다.

TypeScript로 서버와 클라이언트를 함께 만들 때, 주고받는 값의 모양을 양쪽에 따로 적어두지 않아도 클라이언트가 서버 타입을 알아본다. 이름의 RPC는 원격 함수 호출을 뜻한다.

### 비유
같은 회사 안의 두 부서. 양식을 새로 만들어 주고받지 않고 원본 문서를 그대로 돌려 본다.

## 🖼️ 그림으로 보기

```도해
흐름: 서버 함수 하나가 클라이언트에서 어떻게 불리나
서버 :: `getUser` 라는 프로시저를 만든다
입력 :: 받을 값의 모양을 함께 적어둔다
타입 :: 라우터 전체의 타입이 하나로 모인다
클라이언트 :: 그 타입을 가져다 붙인다
호출 :: `trpc.getUser.query({ id })` 를 부른다
< 결과 :: 돌아온 값의 모양을 편집기가 이미 안다
= 타입을 옮겨 적는 자리가 없어서 어긋날 자리도 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 서버가 응답 모양을 바꾸면 무엇이 달라지나
REST 로 || tRPC 로
클라이언트 코드 :: 그대로 통과됨 || 컴파일이 막힘
오류를 아는 때 :: 실행 중에 || 코드 쓸 때
타입 정의 :: 양쪽에 따로 || 한 군데만
= 어긋남을 사람이 찾는 대신 컴파일러가 찾게 만드는 것이다
```

REST로 API를 만들면 서버가 내려주는 값의 모양과 클라이언트가 기대하는 모양이 각각 따로 적힌다. 서버에서 나이를 숫자로 바꿨는데 클라이언트가 여전히 문자열로 알고 있으면 코드는 멀쩡히 컴파일되고, 그 화면을 실제로 열었을 때 깨진다.

tRPC는 서버에서 정의한 타입을 클라이언트가 그대로 가져다 쓴다. 옮겨 적는 자리가 없으니 어긋날 자리도 없다. 서버 쪽 모양이 바뀌면 부르는 코드가 그 자리에서 컴파일 오류를 낸다.

## ⚙️ 작동 원리

```도해
층: tRPC 는 무엇을 쌓아 만드나
프로시저 :: 함수 하나. 입력 모양과 하는 일을 적는다
라우터 :: 프로시저들을 모아둔 것
타입 :: 라우터에서 뽑아낸 전체 모양
= 클라이언트가 가져가는 것은 코드가 아니라 이 타입 하나다
```

프로시저에는 받을 값의 모양을 함께 적는다. 이 검사는 실행할 때도 돌아서, 모양이 안 맞는 값이 들어오면 함수 안까지 가지 않고 그 앞에서 막힌다.

클라이언트가 가져가는 것은 타입뿐이고 서버 코드를 실행하지는 않는다. 호출 자체는 여느 API처럼 네트워크를 탄다. 그래서 서버와 클라이언트가 같은 저장소에 있고 둘 다 TypeScript일 때 쓸 수 있다.

## 💡 실제 사례

- **한 저장소에 화면과 서버가 같이 있는 프로젝트** 서버 함수 이름을 바꾸면 부르는 쪽에서 곧바로 오류가 뜬다.
- **응답 필드 삭제** 서버에서 필드를 지우면 그 필드를 쓰던 화면 코드가 컴파일되지 않아 배포 전에 걸린다.
- **자동 완성** 호출할 때 어떤 값을 넣어야 하는지 편집기가 목록으로 띄워준다.

## 🚫 흔한 오해

- **tRPC를 쓰면 REST나 GraphQL을 안 써도 된다** — TypeScript로 양쪽을 다 만들 때에 한한다. 다른 언어로 만든 클라이언트나 밖에 공개하는 API에는 쓸 수 없다.
- **클라이언트가 서버 코드를 가져다 실행한다** — 가져가는 것은 타입뿐이다. 실제 호출은 여느 API처럼 네트워크를 탄다.
- **타입이 맞으면 값도 맞다** — 타입은 코드를 쓸 때 확인하는 것이다. 밖에서 들어오는 값은 실행 시점의 검사를 따로 붙여야 한다.

## 📝 정리

tRPC는 서버에서 정의한 타입을 클라이언트가 그대로 가져다 쓰게 만드는 도구다. 값의 모양을 양쪽에 따로 적지 않으므로 어긋날 자리가 없고, 서버가 바뀌면 클라이언트 코드가 컴파일 단계에서 막힌다. 서버와 클라이언트가 둘 다 TypeScript일 때만 쓸 수 있다.

## ❓ 이해했는지

- 서버가 응답 필드 하나를 지웠을 때 REST와 tRPC에서 문제가 드러나는 시점이 어떻게 다른가?
- 파이썬으로 만든 서버에는 tRPC를 붙일 수 없다. 왜 그런가?
- 타입이 맞는데도 실행 시점 검사를 따로 두는 이유는?
