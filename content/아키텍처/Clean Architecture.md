# Clean Architecture (클린 아키텍처)

## 📝 정의

클린 아키텍처는 **업무 규칙이 바깥 기술에 기대지 않게 뒤집은 구조**다.

같은 구조가 이름을 여럿 달고 있다. 2005년의 헥사고날 아키텍처(육각형), 포트와 어댑터, 어니언 아키텍처(양파), 그리고 클린 아키텍처가 전부 같은 원리를 가리킨다. 공통점 하나는 **의존 방향을 뒤집는다**는 것이다.

### 이름
Clean :: 섞이지 않은
Architecture :: 짜임새
= 붙여 읽으면 "섞이지 않은 짜임새". 업무 규칙 안에 기술 이야기가 섞여 들지 않는다는 뜻이다

### 비유
벽에 붙은 콘센트. 구멍 모양만 정해 두면 선풍기를 빼고 난로를 꽂아도 벽은 한 군데도 안 뜯는다.

### 예
규칙 하나를 시험하려는데 진짜 DB 가 떠 있어야만 해서 한참 기다렸던 그 순간이다.

### 직접
지금 만드는 프로젝트에서 업무 규칙이 든 파일이 저장소 라이브러리를 직접 불러오는 줄이 있는지 찾아보라. 있으면 방향이 아직 안 뒤집힌 것이다.

## 🖼️ 그림으로 보기

```도해
층: 의존은 어느 쪽으로만 흐르나
UI 와 인프라 :: 화면·저장소·메일·바깥 호출. 안쪽이 정한 약속을 구현한다
도메인 서비스 :: 업무 일을 엮는다. 안쪽 인터페이스만 쓴다
개체와 인터페이스 :: 업무 규칙 그 자체와 약속. 아무 데도 안 기댄다
= 바깥은 안쪽을 알고 안쪽은 바깥을 모른다. 그래서 바깥만 갈아 끼울 수 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 층을 위에서 아래로 쌓으면 무엇이 막히나
전통 N층 || 클린
의존 방향 :: 위에서 아래로 || 전부 안쪽으로
업무 규칙 :: 저장소에 매인다 || 혼자 선다
단위 시험 :: DB 를 띄워야 || 그냥 돌린다
= 방향 하나를 뒤집으면 업무 규칙이 기술보다 오래 산다
```

전통적인 N층 구조에서 화면은 업무 층에 기대고, 업무 층은 자료 접근 층에 기댄다. Microsoft 문서는 이 배치의 단점을 한 문장으로 적는다 — 앱에서 가장 중요한 로직을 담은 업무 층이 자료 접근의 구현 세부와 데이터베이스의 존재에 매달리게 된다. 그래서 업무 규칙을 시험하려면 시험용 DB 부터 띄워야 한다.

클린 아키텍처는 업무 모델을 한가운데 두고 그 의존을 **뒤집는다.** 인터페이스를 안쪽에서 정의하고 바깥이 그것을 구현하게 만드는 방식이다. 그러면 저장소를 자체 DB 에서 다른 것으로 바꾸는 일이 같은 인터페이스를 구현한 새 구현체를 끼우는 일로 줄고, 시험은 가짜 구현을 넣어 인프라 없이 돌아간다.

## ⚙️ 작동 원리

바깥과 만나는 자리를 **포트**로 열어 둔다. 포트는 기술을 가리지 않는 창구라, 누가 구현하든 상관하지 않는다. AWS 문서는 이것을 USB 포트에 빗댄다 — 어댑터만 맞으면 어떤 기기든 붙는다. 실제로 붙는 쪽이 **어댑터**다. 어댑터는 포트에 꽂혀 자료를 받거나 건네고, 그 기술에 맞게 모양을 바꿔 준다.

포트도 두 갈래다. 안쪽은 들어오는 명령과 조회를 포트로 받고, 바깥 자원이 필요하면 역시 포트로 요청을 내보낸다. 한 포트에 어댑터를 여럿 꽂아도 포트와 안쪽은 그대로다. REST 어댑터가 붙어 있는 포트에 GraphQL 어댑터를 하나 더 꽂아도 기존 것은 아무 영향을 안 받는다.

컴파일 시점과 실행 시점을 갈라 보는 것이 요령이다. 컴파일할 때 화면 쪽은 안쪽 인터페이스만 알고 인프라의 구체 타입은 모른다. 다만 실행할 때는 그 구체 타입이 있어야 하므로 시작 지점에서 인터페이스와 구현을 이어 준다. 그 이어 주는 한 자리를 조립 지점(composition root)이라 부른다.

## 📊 비교: 언제 이 구조를 들이나

```도해
대조: 이 구조를 들일지 무엇으로 정하나
들일 만한 곳 |=| 다시 따져 볼 곳
바깥 붙는 곳 :: 여럿이고 바뀐다 || 하나로 고정이다
업무 규칙 :: 두껍다 || 화면과 저장뿐
어댑터 값 :: 유지비를 넘는다 || 층만 하나 는다
= 바깥이 여럿이거나 앞으로 바뀔 때만 어댑터 값이 유지비를 넘는다
```

AWS 문서는 이 판단을 아주 또렷하게 적어 둔다. 구조를 꽂았다 뺐다 할 수 있게 만드는 어댑터 코드는 **입력원과 출력처가 여럿이거나 앞으로 바뀔 때만** 정당하다. 그렇지 않으면 어댑터는 그냥 관리할 층이 하나 더 생긴 것이고, 유지 부담만 는다. 포트와 어댑터가 층을 하나 더하니 지연이 늘 수도 있다고도 적는다.

반대로 들일 만한 자리도 문서에 나열되어 있다. 완전히 시험 가능한 부품으로 떼어내고 싶을 때, 여러 종류의 클라이언트가 같은 업무 규칙을 쓸 때, 화면과 저장소가 주기적으로 기술을 갈아탈 때, 입력과 출력이 여럿이라 로직을 손볼수록 코드가 복잡해지고 늘리기 어려워질 때다.

## 💡 실제 사례

- **저장소 갈아 끼우기** — 자체 DB 에서 다른 저장소로 옮길 때, 같은 인터페이스를 구현한 새 어댑터만 끼우고 업무 규칙은 건드리지 않는다.
- **인프라 없이 시험하기** — 안쪽이 인프라를 안 부르니 가짜 구현을 넣고 규칙만 따로 돌린다. 환경을 통째로 띄울 일이 없다.
- **입구가 여럿일 때** — 같은 업무 규칙을 REST 어댑터와 GraphQL 어댑터가 나란히 부른다. 포트와 안쪽은 그대로다.

## 🚫 흔한 오해

- **클린 아키텍처를 쓰면 언제나 낫다** — AWS 문서는 어댑터 값이 유지비를 넘을 때만 정당하다고 적는다. 입출력이 하나로 고정된 작은 부품에서는 관리할 층만 하나 늘어난다.
- **폴더를 도메인·응용·인프라로 나누면 그게 클린이다** — 이름이 아니라 의존 방향이 정한다. 안쪽 코드가 저장소 라이브러리를 직접 부르는 순간 그건 그냥 N층이다.
- **이건 마이크로서비스용 구조다** — Microsoft 문서는 이 구조를 자잘하지 않은 **모놀리스**를 짜는 가장 알맞은 방식으로 적는다. 한 덩어리 안에서도 방향은 뒤집을 수 있다.

## 🚨 주의사항

- **조립 지점 한 곳은 예외다.** 실행 시점에 구현을 이어 주려면 시작 코드가 인프라를 참조해야 한다. Microsoft 문서는 이 참조를 조립 지점 한 자리로만 제한하라고 적는다.
- **층을 하나 더 두면 지연이 는다.** AWS 문서가 포트와 어댑터의 대가로 명시하는 항목이다. 응답 시간이 빡빡한 자리에서는 이 값을 재고 들어간다.
- **어설픈 분리는 안 하느니만 못하다.** 같은 문서가 업무 규칙과 인프라를 가르는 일을 조심히 다루면 큰 이득이지만 그러지 못하면 문제가 더 풀기 어려워진다고 적는다.

## 📝 정리

**"업무 규칙을 한가운데 두고 기술을 바깥에 꽂는 구조"** 라고 읽으면 된다. 판단의 기준은 하나다. 바깥에 붙는 것이 여럿이거나 앞으로 바뀔 때만 어댑터를 만드는 값이 유지비를 넘는다.

## 🧒 열 살에게

벽에 있는 구멍은 안 바뀌지? 그래서 선풍기를 빼고 난로를 꽂아도 벽은 하나도 안 뜯어. 자주 바뀌는 건 꽂았다 뺐다 하게 두고 잘 안 바뀌는 건 벽 쪽에 붙여 둔 거야.

## ❓ 이해했는지

- 저장소를 다른 것으로 바꾸는데 업무 규칙 파일을 안 고쳐도 되는 까닭은 무엇인가 → 그림
- 입출력이 하나로 고정된 작은 부품에 이 구조를 들이면 무엇이 손해인가 → 비교
- 컴파일할 때는 몰랐던 구현체가 실행할 때는 어떻게 이어지나 → 작동 원리
