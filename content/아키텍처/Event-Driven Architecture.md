# 이벤트 기반 아키텍처 (Event-Driven Architecture)

## 📝 정의

이벤트 기반 아키텍처는 **일어난 일을 알리기만 하고 넘어가는 구조**다.

서비스가 서로를 직접 부르면 부르는 쪽이 받는 쪽을 전부 알아야 한다. 이벤트로 바꾸면 알리는 쪽은 누가 받는지 모르고, 받는 쪽은 누가 보냈는지 모른 채로 각자 일한다.

### 비유
신문. 신문사는 누가 어느 면을 읽는지 모르고, 독자는 기사를 누가 썼는지 몰라도 읽는다.

## 🖼️ 그림으로 보기

```도해
흐름: 주문 한 건이 들어오면 어디까지 퍼지나
주문 서비스 :: "주문 생성됨" 을 발행하고 끝낸다
브로커 :: 그 사건을 받아 쌓아둔다
결제 서비스 :: 구독하고 있다가 꺼내 처리한다
재고 서비스 :: 같은 사건을 따로 꺼내 처리한다
< 알림 서비스 :: 또 따로 꺼내 문자를 보낸다
= 주문 서비스는 셋이 있다는 것도 모른다. 넷째가 생겨도 고칠 게 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 서비스 하나를 새로 붙이면 무엇을 고쳐야 하나
직접 호출로 || 이벤트로
새 기능 추가 :: 부르는 쪽 수정 || 구독만 추가
한 곳이 느리면 :: 전부 같이 기다림 || 각자 진행
받는 쪽 목록 :: 부르는 쪽이 앎 || 알 필요 없음
= 누가 받는지 모르게 만들어두면, 받는 쪽이 늘어도 보내는 쪽은 그대로다
```

주문이 끝나면 결제도 하고 재고도 줄이고 문자도 보내야 한다. 주문 서비스가 이 셋을 직접 부르면 셋의 주소와 형식을 전부 알아야 하고, 넷째가 생길 때마다 주문 서비스를 고치게 된다. 셋 중 하나가 느리면 주문 응답도 그만큼 늦어진다.

이벤트로 바꾸면 주문 서비스는 "주문이 생겼다" 만 남기고 끝낸다. 받는 쪽이 몇이든, 얼마나 느리든 주문 응답 시간은 달라지지 않는다.

## ⚙️ 작동 원리

브로커는 사건을 받아 저장해두고, 구독한 쪽이 가져갈 때까지 들고 있다. 받는 쪽이 잠시 죽어 있어도 살아난 뒤에 밀린 것부터 처리한다.

대신 같은 사건을 두 번 받는 일이 생긴다. 브로커가 보냈는데 처리했다는 응답을 못 받으면 다시 보내기 때문이다. 그래서 받는 쪽은 같은 사건을 두 번 처리해도 결과가 같아지도록 짜야 한다.

도착 순서도 보장되지 않는다. 결제 완료가 주문 생성보다 먼저 도착하는 경우까지 감안해서 짜지 않으면, 평소에는 잘 돌다가 부하가 몰릴 때만 어긋난다.

## 📊 비교

| | 이벤트 기반 | 직접 호출 |
|---|---|---|
| 응답 | 발행하고 바로 끝 | 상대가 답할 때까지 기다림 |
| 받는 쪽을 아는가 | 모른다 | 알아야 한다 |
| 한 곳이 죽으면 | 나머지는 계속 | 부른 쪽도 막힌다 |
| 흐름 추적 | 어렵다 | 쉽다 |
| 데이터 일치 | 잠시 어긋난다 | 그 자리에서 맞는다 |

## 💡 실제 사례

- **주문 처리** 주문 하나가 결제, 재고, 배송, 알림으로 각각 흘러가고 한 곳이 실패해도 나머지는 진행된다.
- **댓글 알림** 댓글이 달렸다는 사건 하나로 푸시와 이메일과 추천 갱신이 각자 돌고, 쓴 사람은 기다리지 않는다.
- **센서 데이터** 온도가 바뀌었다는 사건을 제어, 기록, 경고가 따로 구독해 처리한다.

## 🚫 흔한 오해

- **이벤트를 쓰면 빨라진다** — 응답이 빨리 돌아오는 것뿐이고 전체 처리는 오히려 늦게 끝난다. 짧아지는 건 사용자가 기다리는 구간이다.
- **발행했으니 처리된 것이다** — 발행은 알렸다는 데까지다. 받는 쪽이 실패해도 발행한 쪽은 모르므로 실패를 따로 감시해야 한다.
- **보낸 순서대로 도착한다** — 보장되지 않는다. 나중 사건이 먼저 도착하는 경우를 감안하지 않으면 부하가 몰릴 때 어긋난다.

## 📝 정리

이벤트 기반 아키텍처는 서비스가 서로를 부르는 대신 일어난 일을 브로커에 남기고 넘어가는 구조다. 받는 쪽이 늘어도 보내는 쪽을 고칠 일이 없고 한 곳의 장애가 옆으로 번지지 않는다. 대신 흐름을 추적하기 어렵고 데이터가 잠시 어긋난다.

## ❓ 이해했는지

- 주문 서비스를 하나도 안 고치고 알림 기능을 붙일 수 있는 이유는?
- 같은 결제 완료 처리가 두 번 실행될 수 있는 이유는?
- 발행은 성공했는데 사용자에게 문자가 안 갔다면 어디를 봐야 하나?

- [[Pub-Sub]] — 하나가 발행하고 여럿이 구독하는 기본 형태
