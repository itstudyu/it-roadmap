# 이벤트 기반 아키텍처 (Event-Driven Architecture, EDA)

## 📝 정의

이벤트 기반 아키텍처(EDA)는 시스템의 각 컴포넌트들이 **이벤트를 생산(발행)하고 소비**함으로써 서로 통신하는 아키텍처 패턴입니다. 전통적인 동기식 통신(REST API, 직접 호출)과 달리, EDA는 컴포넌트들 간의 **느슨한 결합(Loose Coupling)**을 추구하여 확장성과 유연성이 뛰어난 시스템을 구축할 수 있습니다.

EDA의 핵심 원리는 **이벤트 브로커(Event Broker)** 또는 **메시지 큐(Message Queue)** (Kafka, RabbitMQ 등)가 중심이 되어 생산자(Producer)가 이벤트를 발행하면, 소비자(Consumer)들이 이들 이벤트를 구독(Subscribe)하여 처리하는 형태입니다. 이러한 방식은 서로 다른 팀에서 개발한 마이크로서비스들이 느슨한 결합 상태로 협업할 수 있게 해줍니다.

> **한 줄 요약**: 컴포넌트들이 중앙의 이벤트 브로커를 통해 비동기적으로 이벤트를 주고받으며 통신하는 아키텍처 패턴

**비유 1**: EDA는 신문사와 독자들의 관계와 같습니다. 신문사(생산자)가 신문을 발행하면, 구독자(소비자)들이 각자 필요한 섹션을 읽는데, 신문사는 누가 어떻게 읽는지 신경쓰지 않습니다. 생산자와 소비자가 완전히 독립적입니다.

**비유 2**: EDA는 콘서트 무대와 관객들의 관계입니다. 가수(생산자)가 노래를 부르면, 관객들(소비자)은 각자 다양한 반응을 합니다(춤을 춘다, 영상을 찍는다, 응원한다). 가수는 모든 관객의 반응을 알지 못해도 공연은 계속됩니다.

## 🎯 핵심 개념

### 1. 이벤트 (Event)
이벤트란 시스템에서 발생하는 **상태 변화나 중요한 사건**을 나타내는 데이터 메시지입니다. 예를 들어 '주문 생성', '결제 완료', '배송 시작' 같은 비즈니스 이벤트가 있습니다. 각 이벤트는 시간, 타입, 관련 데이터 등을 포함합니다.

### 2. 생산자/소비자 (Producer/Consumer)
- **생산자(Producer)**: 이벤트를 생성하고 브로커에 발행하는 컴포넌트. 소비자가 누구인지 알 필요가 없습니다.
- **소비자(Consumer)**: 이벤트 브로커에서 이벤트를 구독하고 처리하는 컴포넌트. 누가 이를 발행했는지 신경쓰지 않습니다.

### 3. 이벤트 브로커/메시지 큐 (Event Broker/Message Queue)
Kafka, RabbitMQ, AWS SQS 같은 중앙 집중식 시스템으로, 생산자와 소비자 사이의 메시지 전달을 담당합니다. 브로커는 이벤트를 임시 저장하고, 소비자가 이를 처리할 때까지 유지합니다.

## ⚠️ 해결하는 문제

### 문제 1: 강한 결합도로 인한 확장성 부족
전통적인 REST API 기반 아키텍처에서는 새로운 기능을 추가할 때마다 기존 코드를 수정해야 합니다. 예를 들어 주문 서비스에 새로운 알림 기능을 추가하려면 주문 서비스 코드를 직접 변경해야 합니다. EDA는 기존 코드를 수정하지 않고 새로운 소비자만 추가하면 됩니다.

### 문제 2: 시간에 따른 성능 저하와 의존성 증가
동기식 통신에서는 모든 서비스가 정상 작동해야 요청이 처리됩니다. 하나의 서비스가 느리거나 다운되면 전체 시스템이 영향을 받습니다. EDA는 비동기 처리로 서비스들이 각자의 속도대로 일할 수 있어 장애 전파를 방지합니다.

## ⚙️ 작동 원리

1. **이벤트 발행 (Publishing)**: 생산자가 어떤 일이 발생했음을 나타내는 이벤트를 생성하여 브로커에 발행합니다. 예: "OrderCreated" 이벤트.

2. **브로커 수신**: Event Broker가 이벤트를 받아 메시지 큐에 저장합니다. 이는 각 이벤트가 손실되지 않도록 보장합니다.

3. **소비자 구독**: 여러 소비자들이 특정 이벤트 타입을 구독하고 있습니다. 브로커는 새로운 이벤트가 들어오면 해당 이벤트를 구독 중인 모든 소비자에게 전달합니다.

4. **비동기 처리**: 각 소비자는 독립적으로 이벤트를 처리합니다. 결제 서비스가 느리더라도 다른 서비스들은 영향을 받지 않습니다.

5. **응답 이벤트**: 소비자가 처리를 완료하면 또 다른 이벤트를 발행할 수 있으며, 이는 다시 다른 소비자들에게 전달됩니다.

## 📊 비교

| 항목 | Event-Driven Architecture | REST API | Message Queue | Pub-Sub Pattern |
|------|--------------------------|----------|---------------|-----------------|
| **통신 방식** | 비동기 (이벤트 기반) | 동기 (Request-Response) | 비동기 (메시지 기반) | 비동기 (구독 기반) |
| **결합도** | 느슨한 결합 | 강한 결합 | 느슨한 결합 | 느슨한 결합 |
| **확장성** | 매우 높음 | 낮음 | 높음 | 높음 |
| **지연 시간** | 높음 (비동기) | 낮음 (동기) | 중간 | 중간 |
| **에러 처리** | 복잡 (재시도 메커니즘 필요) | 단순 (즉시 응답) | 중간 | 중간 |
| **컴포넌트 의존성** | 최소 (이벤트만 알면 됨) | 높음 (API 스펙 알아야 함) | 중간 (메시지 스펙) | 낮음 (토픽 구조만) |
| **데이터 일관성** | 최종 일관성 (Eventual Consistency) | 강한 일관성 | 최종 일관성 | 최종 일관성 |
| **대규모 분산 시스템** | 최적 | 부족 | 적합 | 적합 |

## ✅ 장단점

**장점:**
- **높은 확장성**: 새로운 소비자 추가가 기존 코드 수정 없이 가능
- **느슨한 결합**: 컴포넌트 간 의존성이 최소화되어 독립적 개발 가능
- **향상된 복원력**: 특정 서비스 장애가 전체 시스템에 영향을 미치지 않음
- **비동기 처리**: 서비스들이 각자의 속도대로 작업 가능하여 성능 향상
- **유연한 통신**: 1:1, 1:N, N:N 다양한 통신 패턴 지원
- **감사(Audit) 용이**: 모든 이벤트가 기록되어 시스템의 상태 변화 추적 가능

**단점:**
- **복잡한 설계**: 아키텍처 설계가 복잡하며 이벤트 간 의존성 관리 어려움
- **디버깅 어려움**: 비동기 처리로 인한 요청 흐름 추적이 어려움
- **최종 일관성**: 데이터 일관성 보장이 약하여 일시적 불일치 가능
- **메시지 순서 보장 문제**: 이벤트 처리 순서가 보장되지 않을 수 있음
- **높은 운영 복잡도**: Event Broker 관리, 모니터링, 버전 관리 필요
- **초기 구축 비용**: 개발, 테스트, 배포에 더 많은 시간과 리소스 필요

## 💡 실제 사례

### 사례 1: 전자상거래 주문 처리 시스템
고객이 쇼핑몰에서 상품을 주문하면 "OrderCreated" 이벤트가 발행됩니다. 이를 구독하는 여러 서비스들이 동시에 작동합니다:
- **결제 서비스**: 결제 처리
- **재고 서비스**: 상품 재고 감소
- **배송 서비스**: 배송 준비
- **알림 서비스**: 주문 확인 이메일/SMS 발송
- **분석 서비스**: 주문 데이터 저장

각 서비스가 느려도 다른 서비스는 계속 진행되며, 어느 한 서비스 실패가 전체 주문 프로세스를 중단시키지 않습니다.

### 사례 2: 실시간 알림 시스템
사용자가 SNS에 댓글을 달면 "CommentCreated" 이벤트가 발행됩니다:
- **푸시 알림 서비스**: 게시물 주인에게 푸시 알림 전송
- **이메일 알림 서비스**: 이메일 전송
- **추천 서비스**: 댓글 기반 추천 알고리즘 업데이트
- **모더레이션 서비스**: 부정적 댓글 필터링
- **분석 서비스**: 사용자 상호작용 데이터 수집

사용자는 댓글 작성 후 즉시 완료되는 경험을 하지만, 백그라운드에서 여러 처리가 비동기적으로 진행됩니다.

### 사례 3: IoT 센서 데이터 처리
스마트홈 시스템에서 온도 센서가 "TemperatureChanged" 이벤트를 발행합니다:
- **에어컨 제어 서비스**: 온도에 따라 에어컨 자동 조절
- **로깅 서비스**: 온도 데이터 저장
- **경고 서비스**: 비정상 온도 감지 시 알림
- **분석 서비스**: 장기적 온도 패턴 분석

수백 개의 센서에서 초당 수천 개의 이벤트가 발생하지만, EDA 구조로 안정적으로 처리할 수 있습니다.

## 🔗 관련 용어

- **마이크로서비스 아키텍처 (Microservices Architecture)**: EDA와 자주 함께 사용되는 아키텍처 패턴
- **메시지 큐 (Message Queue)**: Kafka, RabbitMQ 등 EDA의 핵심 기술
- **비동기 처리 (Asynchronous Processing)**: EDA의 기본 작동 방식
- **느슨한 결합 (Loose Coupling)**: EDA의 주요 목표
- **이벤트 소싱 (Event Sourcing)**: 모든 상태 변화를 이벤트로 저장하는 패턴
- **CQRS (Command Query Responsibility Segregation)**: EDA와 함께 자주 사용되는 패턴
- **최종 일관성 (Eventual Consistency)**: EDA에서 데이터 일관성 모델
- **Pub-Sub 패턴 (Publish-Subscribe)**: EDA의 기본 메시징 패턴
