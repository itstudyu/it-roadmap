# API Gateway (API 게이트웨이)

## 📝 정의

API Gateway는 **여러 서버로 가는 요청을 한 문에서 받는 서버**다.

뒤에 서비스가 열 개든 스무 개든 밖에서는 주소 하나만 보인다. 인증, 요청량 제한, 로그처럼 모든 서비스가 똑같이 해야 하는 일을 이 문에서 한 번에 처리한다.

### 비유
회사 로비의 안내 데스크. 방문객은 로비 하나만 알면 되고, 신분 확인과 출입증 발급은 여기서 한 번만 한다. 각 층 사무실이 저마다 검문소를 둘 필요가 없다.

## 🖼️ 그림으로 보기

```도해
흐름: 요청 하나가 게이트웨이를 지나며 무슨 일을 겪나
클라이언트 :: `/api/orders` 로 요청한다
게이트웨이 :: 토큰이 유효한지 확인한다
게이트웨이 :: 이 사용자가 한도를 넘지 않았는지 본다
게이트웨이 :: 주문 서비스로 넘긴다
주문 서비스 :: 자기 일만 한다. 인증은 이미 끝났다
< 게이트웨이 :: 응답을 받아 로그를 남기고 돌려준다
= 서비스마다 하던 공통 작업을 문 앞에서 한 번만 한다
```

## ⚠️ 해결하는 문제

```도해
대조: 서비스가 스무 개일 때 무엇이 달라지나
게이트웨이 없이 || 게이트웨이로
인증 코드 :: 스무 벌 || 한 벌
주소 :: 스무 개를 안다 || 하나만 안다
정책 변경 :: 스무 곳 배포 || 한 곳만
= 같은 일을 여러 번 하지 않게 만드는 것이 이 장치의 전부다
```

서비스를 잘게 나누면 각 서비스는 단순해지지만, 공통으로 해야 하는 일이 서비스 수만큼 복제된다. 토큰 검증 로직이 스무 벌 생기고, 그중 한 곳만 업데이트를 놓쳐도 구멍이 된다.

클라이언트 쪽도 복잡해진다. 화면 하나를 그리려고 서비스 세 곳을 각각 호출하고 결과를 합쳐야 한다. 게이트웨이가 그 조합을 대신 맡으면 클라이언트는 한 번만 부르면 된다.

## ⚙️ 작동 원리

게이트웨이가 맡는 일은 대체로 정해져 있다.

| 하는 일 | 내용 |
|---|---|
| 라우팅 | 경로를 보고 어느 서비스로 보낼지 정한다 |
| 인증·인가 | 토큰을 확인하고 권한을 본다 |
| 요청량 제한 | 한 사용자가 너무 많이 부르는 것을 막는다 |
| 응답 조합 | 여러 서비스 결과를 하나로 합친다 |
| 로그·추적 | 요청 하나가 어디를 거쳤는지 기록한다 |

## 💡 실제 사례

- **모바일 앱 전용 응답** — 앱에는 가벼운 형태로, 웹에는 자세한 형태로 같은 데이터를 다르게 내려준다.
- **버전 관리** — `/v1`은 옛 서비스로, `/v2`는 새 서비스로 보내면서 클라이언트를 천천히 옮긴다.
- **외부 공개** — 내부 서비스는 그대로 두고 게이트웨이에서만 공개 규칙을 정한다.

## 🚫 흔한 오해

- **게이트웨이가 [[Load Balancer]]와 같은 것이다** — 분산기는 같은 서버 여럿에 요청을 나눈다. 게이트웨이는 서로 다른 서비스로 보내면서 인증과 조합까지 한다.
- **게이트웨이에 비즈니스 로직을 넣어도 된다** — 넣기 시작하면 여기가 다시 모놀리스가 된다. 문을 만들려다 건물을 지은 셈이 된다.
- **한 번 두면 장애가 줄어든다** — 모든 요청이 지나는 지점이라 여기가 죽으면 전부 죽는다. 이중화가 필수다.

## 🚨 주의사항

- **여기가 단일 장애점이다.** 이중으로 띄우고 헬스체크를 건다.
- **지연이 한 겹 늘어난다.** 요청마다 홉이 하나 추가되므로 게이트웨이 자체가 느리면 전부 느려진다.

## 📝 정리

API Gateway는 여러 서비스 앞에 서서 공통 작업을 대신 하는 문이다. 중복을 없애는 대신 모든 요청이 지나는 지점이 하나 생기므로, 그 지점을 얼마나 튼튼하게 두느냐가 관건이다.
