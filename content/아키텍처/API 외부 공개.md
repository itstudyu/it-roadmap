# API 외부 공개 방법 (외부 사용자가 API를 사용하게 하려면)

## 📝 정의

API 외부 공개란 로컬 컴퓨터에서만 접근 가능한 API를 인터넷을 통해 외부 사용자가 사용할 수 있도록 공개하는 과정입니다. 개발자가 localhost:3000에서 만든 API를 다른 팀원이나 외부 클라이언트도 사용할 수 있게 하려면, 공인 IP 주소나 도메인을 가진 서버가 필요합니다. 단순히 코드만 작성하는 것이 아니라, 접근 가능한 네트워크 주소, 암호화된 통신(HTTPS), 인증 체계, 서버 운영 등을 모두 준비해야 합니다.

많은 초보 개발자들이 "API를 만들었는데 외부 사용자가 어떻게 사용하지?"라는 질문을 합니다. 답은 간단합니다. 접근 가능한 서버에 배포해야 합니다. 현재 컴퓨터의 localhost는 오직 그 컴퓨터 내부에서만 접근 가능하기 때문에, 외부 사용자를 위해서는 클라우드 서버(AWS, GCP, Azure), 전용 호스팅, 또는 터널링 도구(ngrok)가 필수입니다. 각 방법은 목적, 비용, 안정성에 따라 선택됩니다.

> **한 줄 요약**: "로컬 API를 외부에 공개하려면 공인 IP와 도메인이 있는 서버에 배포해야 함"

**비유**:
- **도로 비유**: 내 집 거실에서 손님을 맞는 것(localhost)은 내 주소를 알아야 들어올 수 있습니다. 만약 거실 주소가 없다면 아무도 올 수 없습니다. 외부 손님을 맞으려면 건물 주소(공인 IP)와 호출 벨(도메인)이 필요합니다.
- **식당 비유**: 집에서 음식을 만드는 것(localhost)은 가족만 먹을 수 있습니다. 손님을 받으려면 건물을 임차하고(클라우드 서버), 간판을 달고(도메인), 위생 인증을 받아야 합니다(HTTPS, 보안).

## 🎯 핵심 개념

### 1. Localhost의 한계
Localhost(127.0.0.1)는 내 컴퓨터의 네트워크 루프백 주소입니다. 이것은 나의 컴퓨터 내부에서만 존재하는 주소이며, 외부 인터넷에서는 접근할 수 없습니다. 내 컴퓨터가 꺼지거나 네트워크가 끊어지면 API도 즉시 접근 불가능합니다. 따라서 개발 단계에서만 사용하고, 외부 공개가 필요하면 반드시 다른 서버로 이동해야 합니다.

### 2. 공인 IP의 필요성
인터넷의 모든 서버는 공인 IP 주소가 할당됩니다. 외부 사용자가 API에 접근하려면, 그 IP 주소를 알거나 도메인 이름을 통해 IP로 변환할 수 있어야 합니다. 따라서 API를 외부에 공개하려면 반드시 공인 IP가 있는 서버가 필요합니다.

### 3. 외부 공개 방법 3가지: 클라우드, 포트 포워딩, 터널링
- **클라우드 배포**: AWS EC2, Google Cloud, Azure VM 등의 공인 IP와 도메인을 활용. 프로덕션 환경에 적합하며, 자동 스케일링, 로드 밸런싱 등 고급 기능 지원.
- **포트 포워딩**: 가정/사무실 네트워크의 공유기에서 특정 포트를 내 컴퓨터로 포워딩. 비용이 없지만 불안정하고 보안에 취약함.
- **터널링 도구(ngrok)**: ngrok이 로컬 서버와 인터넷을 연결하는 터널을 생성. 테스트와 임시 공유에 적합하며, 빠르게 설정 가능.

### 4. 도메인과 HTTPS의 중요성
프로덕션 환경에서는 IP 주소로 직접 접근하는 것이 아니라, 도메인 이름(예: api.example.com)으로 접근합니다. 또한 모든 통신은 HTTPS로 암호화되어야 합니다. HTTP API는 현대 브라우저가 차단하고, 데이터가 평문으로 전송되어 중간자 공격에 노출됩니다.

### 5. API Gateway의 역할
외부 공개된 API 앞단에는 보통 API Gateway가 있습니다. 이것은 인증, 요청 검증, 레이트 제한, 캐싱, 로깅 등을 처리합니다. AWS API Gateway, Kong, Nginx 등이 대표적입니다. API Gateway를 통해 여러 개의 백엔드 서버에 요청을 분산시키고, 사용자별 할당량을 관리합니다.

## ⚠️ 해결하는 문제

### 문제 1: 팀원이나 외부 클라이언트가 API를 사용할 수 없음
개발자가 로컬호스트에서 API를 완성했어도, 다른 팀원이나 클라이언트는 그 API에 접근할 방법이 없습니다. 매번 파일을 공유하거나 데이터를 수동으로 전달해야 하며, 이는 비효율적입니다. API를 외부에 공개하면, 누구든지 필요한 엔드포인트를 호출하여 데이터를 얻을 수 있습니다.

### 문제 2: 개발 환경과 실제 운영 환경의 갭
로컬호스트에서는 정상 작동하던 API도, 실제 서버에 배포하면 예기치 않은 문제가 발생합니다. 네트워크 지연, 동시 접속, 리소스 부족 등 현실적인 상황에서의 문제를 테스트할 수 없습니다. 실제 서버에 배포하면 이런 문제들을 조기에 발견하고 해결할 수 있습니다.

### 문제 3: 보안 취약점으로 인한 공격 노출
HTTP API는 중간자 공격(MITM)에 취약하고, 인증이 없으면 무제한 접근이 가능합니다. 외부 공개 시 반드시 HTTPS, 인증(API Key, JWT), 요청 검증, 레이트 제한 등의 보안 조치를 해야 합니다.

## ⚙️ 작동 원리

### 1단계: 로컬호스트 API 개발
개발자는 자신의 컴퓨터에서 API 서버를 개발합니다. Node.js, Python, Go 등으로 작성된 API가 localhost:3000 또는 다른 포트에서 실행됩니다. 이 단계에서는 자신의 컴퓨터에서만 테스트합니다.

### 2단계: 외부 공개 방법 선택
목적에 따라 방법을 선택합니다. 빠른 테스트라면 ngrok, 팀 내부 공유라면 클라우드 VM, 실제 서비스라면 클라우드 + 도메인 + 인증서를 선택합니다.

### 3단계: ngrok을 이용한 임시 공개 (개발/테스트)
ngrok 클라이언트를 설치하고 `ngrok http 3000` 명령을 실행하면, ngrok이 로컬 포트 3000과 인터넷을 연결하는 터널을 만듭니다. 그러면 https://abc.ngrok.io 같은 임시 URL이 생성되고, 이 URL을 통해 외부 사용자가 API에 접근할 수 있습니다. 다만 ngrok을 종료하면 URL이 회수되고, 무료 플랜은 하루에 연결 횟수 제한이 있습니다.

### 4단계: 클라우드 VM에 배포 (프로덕션 준비)
AWS EC2, Google Compute Engine 등에 서버 인스턴스를 생성합니다. 인스턴스는 공인 IP를 할당받으며, 개발자의 API 코드를 배포합니다. 하지만 IP 주소로 직접 접근하는 것은 임시방편이므로, 도메인 이름을 구입하고 DNS 설정을 합니다.

### 5단계: 도메인 및 HTTPS 설정
Route53, CloudFlare 등의 DNS 서비스에 도메인을 등록하고, IP 주소로 연결합니다. 또한 Let's Encrypt(무료)나 AWS ACM(무료)을 이용하여 SSL/TLS 인증서를 받아 HTTPS를 설정합니다. 모든 HTTP 요청은 HTTPS로 리다이렉트합니다.

### 6단계: API Gateway 및 보안 설정
AWS API Gateway를 API 앞단에 배치하여, 인증(API Key, OAuth), 요청 검증, 레이트 제한(throttling), 로깅 등을 처리합니다. 각 클라이언트마다 API Key를 발급하고, 할당량을 관리합니다.

### 7단계: 모니터링 및 운영
CloudWatch 또는 다른 모니터링 도구로 API의 성능, 에러율, 응답 시간을 추적합니다. 자동 알림을 설정하여 문제 발생 시 빠르게 대응합니다. 로그를 분석하여 사용 패턴을 이해하고 개선합니다.

## ✅ 장단점

**장점**:
- ngrok은 설정이 간단하고 즉시 공개 가능하여 빠른 테스트와 데모에 최적
- 클라우드 배포는 확장성이 뛰어나고, 자동 백업, 로드 밸런싱 등 고급 기능 제공
- 도메인과 HTTPS로 전문적인 이미지 제공 및 보안 강화
- API Gateway로 인증, 레이트 제한, 모니터링을 중앙에서 관리
- 글로벌 CDN을 통해 빠른 응답 속도 제공
- 자동 스케일링으로 갑작스런 트래픽 증가 대응 가능

**단점**:
- ngrok은 무료 플랜에 회수 가능한 URL과 대역폭 제한이 있음
- 클라우드 서비스는 월간 비용이 계속 발생하며, 데이터 전송량에 따라 추가 비용 발생 가능
- 초기 설정(도메인 구입, 인증서, IAM 설정)이 복잡할 수 있음
- 클라우드 서비스의 다양한 설정 옵션으로 인한 학습 곡선
- 포트 포워딩은 ISP가 동적 IP를 할당하면 불안정함
- 보안 설정 실수로 인한 데이터 유출 위험

## 💡 실제 사례

### 1. 개발 단계: localhost에서 ngrok으로 빠른 피드백
신입 개발자가 Node.js Express로 간단한 TODO API를 만들었습니다. 로컬호스트:3000에서 정상 작동하지만, 팀 리더가 테스트하려면 어떻게 할까요? 개발자가 ngrok을 실행하면 https://xyz.ngrok.io라는 URL이 생성되고, 리더는 이 URL로 API에 접근할 수 있습니다. 피드백 후 수정하면 ngrok을 다시 실행하여 새로운 URL을 공유합니다.

### 2. 테스트 단계: AWS t2.micro에 임시 배포
팀에서 API를 완성하고 테스트할 준비가 되었습니다. ngrok의 대역폭 제한이 마음에 걸리므로, AWS에서 t2.micro 인스턴스를 생성합니다(1년 무료). 인스턴스의 공인 IP는 35.123.45.67입니다. Route53에 test-api.mycompany.com 도메인을 이 IP로 연결하고, ACM에서 무료 HTTPS 인증서를 받습니다. 이제 내부 팀이 https://test-api.mycompany.com으로 테스트할 수 있습니다.

### 3. 프로덕션 단계: API Gateway와 함께 클라우드 배포
API가 상용화되어, 외부 클라이언트들이 사용하기로 결정되었습니다. AWS에서 프로덕션 EC2 인스턴스(t3.small)를 생성하고, 로드 밸런서를 앞단에 배치합니다. API Gateway를 설정하여 각 클라이언트마다 API Key를 발급하고, 분당 1000 요청 제한을 설정합니다. CloudFront CDN으로 전 세계에서 빠른 응답을 제공합니다. CloudWatch로 에러율과 응답 시간을 모니터링하고, 문제 발생 시 자동으로 알림을 받습니다.

## 🔗 관련 용어

- **공인 IP (Public IP)**: 인터넷에서 식별 가능한 주소. ISP가 할당하거나 클라우드에서 제공
- **도메인 이름**: IP 주소를 사람이 읽을 수 있는 이름으로 변환 (api.example.com)
- **DNS (Domain Name System)**: 도메인 이름을 IP 주소로 변환하는 시스템
- **HTTPS/TLS**: HTTP 통신을 암호화하는 프로토콜
- **SSL/TLS 인증서**: 서버의 신원을 증명하고 통신을 암호화하는 인증서
- **API Gateway**: API 앞단에서 인증, 레이트 제한, 로깅을 처리하는 서비스
- **로드 밸런서**: 여러 서버에 트래픽을 분산시키는 장치
- **CDN (Content Delivery Network)**: 전 세계에 콘텐츠를 캐싱하여 빠른 전달
- **ngrok**: 로컬 서버를 인터넷에 노출하는 터널링 도구
- **포트 포워딩**: 공유기에서 특정 포트를 내부 기기로 리다이렉트
