# Distributed Lock (분산 락)

## 📝 정의

분산 락은 서로 다른 기계의 작업을 **한 번에 하나만 들여보내는 자물쇠**다.

한 기계 안에서 쓰는 잠금은 그 기계 밖을 모른다. 그래서 같은 코드를 두 대에 올리는 순간 잠금은 아무것도 못 막는다. Redis 문서는 분산 락이 지켜야 할 것을 셋으로 줄인다 — 한 순간에 한 쪽만 잡는다(상호 배제), 잡은 쪽이 죽거나 끊겨도 언젠가는 다시 잡을 수 있다(교착 없음), 과반이 살아 있으면 잡고 푸는 일이 된다(장애 감내).

### 이름
Distributed :: 여러 대에 흩어진
Lock :: 한 번에 하나만
= 붙여 읽으면 "흩어져 있어도 한 번에 하나만". 기계 안의 잠금을 밖으로 꺼낸 것이다

### 비유
수영장 옷장 열쇠. 한 사람이 가져가면 아무도 못 열고, 문 닫을 시간이 되면 저절로 풀린다.

### 예
재고가 하나 남은 상품을 두 사람이 동시에 담았는데 둘 다 결제가 끝나 버린 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 여러 대가 같은 일에 달려들면 무엇이 걸러지나
동시 시도 :: 여러 대가 같은 열쇠 이름으로 잠금을 건다
선착순 :: 없을 때만 만드는 조건이라 딱 한 대만 성공한다
나머지 :: 실패한 쪽은 잠깐 쉬었다가 다시 시도한다
작업 :: 성공한 한 대만 공유 자원을 건드린다
반납 :: 값이 자기 것과 같을 때만 열쇠를 지운다
@ 다음 차례로 :: 열쇠가 사라지면 기다리던 쪽이 다시 건다
= 여럿이 달려들어도 안으로 들어가는 것은 언제나 하나뿐이다
```

## ⚠️ 해결하는 문제

```도해
대조: 기계 한 대 안의 잠금으로는 왜 모자라나
한 대 안의 잠금 || 분산 락
잠금이 사는 곳 :: 그 기계 안 || 밖에 하나만
막는 범위 :: 같은 기계끼리 || 모든 기계 사이
두 대로 늘리면 :: 둘 다 통과한다 || 하나만 통과한다
= 잠금이 지켜야 할 것은 기계가 아니라 자원 하나다
```

한 대로 돌 때는 잠금이 잘 돌아간다. 대를 늘리는 순간 조용히 무너진다. 각 기계가 자기 안에서만 순서를 지키기 때문에, 두 대는 서로를 모른 채 같은 재고를 동시에 깎는다. 코드는 그대로인데 결과만 틀어지니 재현도 어렵다.

분산 락은 잠금을 기계 밖 한 곳으로 옮긴다. 모두가 같은 이름의 열쇠를 같은 곳에 걸러 가고, 거기서 선착순이 갈린다. 지켜야 할 것이 기계가 아니라 자원 하나라는 사실을 자리로 옮겨 놓은 것이다.

## ⚙️ 작동 원리

한 대짜리 저장소로 만든다면 이렇게 된다. `SET 자원이름 무작위값 NX PX 30000` — 키가 없을 때만 만들고(NX), 30초 뒤에 저절로 지워지게 한다(PX). 이 만료 시간이 곧 자동 반납이다. 잡은 쪽이 통째로 죽어도 30초 뒤에는 자물쇠가 풀리므로 자원이 영원히 잠기지 않는다.

값이 무작위여야 하는 이유는 반납 때문이다. 그냥 지우는 명령을 쓰면, 내 작업이 만료 시간을 넘겨 늘어진 사이에 다른 쪽이 새로 건 자물쇠를 내가 지워 버릴 수 있다. 그래서 "값이 내가 넣은 것과 같을 때만 지운다" 를 한 덩어리로 실행한다. 자물쇠마다 서명이 붙어 있는 셈이다.

만료 시간은 자동 반납 시간인 동시에 **작업에 주어진 시간**이다. 상호 배제는 잡은 쪽이 그 시간 안에 일을 끝낼 때만 참이다. 시간이 지나면 자물쇠는 내 손을 떠나고, 내가 아직 일하는 중이어도 다른 쪽이 들어온다.

여러 저장소로 흩어 놓는 방식(Redlock)은 여기서 한 걸음 더 간다. 서로 독립인 노드 다섯 대에 같은 열쇠를 동시에 걸어 보고, 과반인 세 대 이상에서 성공했고 걸리는 데 쓴 시간이 만료 시간보다 짧을 때만 잡은 것으로 친다. 실패하면 부분적으로 잡은 것까지 전부 즉시 푼다.

## 📊 비교

이 자물쇠를 고르기 전에 물어야 할 것은 하나다. 겹쳐 잡히면 무엇이 틀어지나.

| 걸려 있는 것 | 겹쳐 잡혔을 때 | 어디까지 하나 |
|---|---|---|
| **효율** | 같은 일이 두 번 돌 뿐이다 | 저장소 한 대짜리 잠금이면 충분하다 |
| **정확성** | 돈이나 재고가 되돌릴 수 없이 틀어진다 | 과반 방식을 쓰고 펜싱 토큰까지 둔다 |

Redis 문서가 갈라 놓는 자리도 여기다. 장애 같은 특수한 상황에서 잠깐 둘이 동시에 잡는 일이 괜찮다면 복제 기반의 간단한 방식으로 충분하고, 그게 아니라면 더 조심스러운 방식을 쓰라고 한다.

## 💡 실제 사례

- **재고 차감** — 마지막 하나 남은 상품에 두 주문이 동시에 들어와도, 자물쇠를 잡은 쪽만 재고를 깎고 나머지는 품절 응답을 받는다.
- **주기 작업 한 번만 돌리기** — 여러 대에 올라간 같은 배치가 같은 이름의 자물쇠를 두고 경쟁하고, 잡은 한 대만 실제로 돈다.
- **리더 뽑기** — Azure 의 리더 선출 예제는 저장소 blob 에 임차를 걸어 분산 뮤텍스를 만든다. 임차를 먼저 얻은 쪽이 대표가 되고, 갱신에 실패하면 임차가 풀려 다음 대표에게 넘어간다.

## 🚫 흔한 오해

- **자물쇠를 잡았으면 일이 끝날 때까지 내 것이다** — 만료 시간이 지나면 내 손을 떠난다. 잡은 프로세스가 살아 있는 동안 계속 잡고 있다고 가정하면 안 된다고 Redis 문서가 못 박는다.
- **복제본을 하나 붙여 두면 잠금도 안전해진다** — 복제는 비동기다. 주 노드가 쓰기를 넘기기 전에 죽고 복제본이 승격되면, 같은 자원에 두 쪽이 동시에 자물쇠를 잡는다.
- **여럿이 같은 자원을 건드리면 일단 분산 락을 걸면 된다** — 자물쇠를 파는 쪽이 단일 장애점이 되고, 망이 끊기면 만료 시간만큼 아무도 못 들어간다. 데이터베이스 한 줄만 지키면 되는 일은 그 안의 낙관적·비관적 잠금이 훨씬 가볍다.

## 🚨 주의사항

- **만료 시간을 작업 시간보다 넉넉히 잡는다.** 상호 배제는 잡은 쪽이 만료 전에 끝낼 때만 성립한다. 길어질 것 같으면 도중에 만료를 연장하되, 연장 횟수에는 상한을 둔다.
- **지울 때는 값을 대조해서 지운다.** 그냥 지우면 남이 새로 건 자물쇠를 지운다.
- **오래 걸리는 작업이면 펜싱 토큰을 붙인다.** 잠금을 잡을 때마다 커지는 번호를 함께 넘겨서, 늦게 깨어난 옛 주인의 쓰기를 받는 쪽에서 거절하게 만든다.
- **시계에 기대고 있다는 걸 잊지 마라.** 만료는 벽시계로 재므로, 서버 시각이 갑자기 어긋나면 둘이 동시에 잡는 일이 생길 수 있다.

## 📝 정리

**"기계가 달라도 한 번에 하나만 들여보내는 걸쇠"** 라고 읽으면 된다. 이 걸쇠에는 기한이 붙어 있어서, 잡은 쪽이 그 기한 안에 일을 끝낼 때만 "하나만 들어간다" 는 말이 참이 된다. 그래서 고를 때 물어야 할 것은 겹쳐 잡히면 무엇이 틀어지는가 하나다.

## 🧒 열 살에게

수영장 옷장은 열쇠가 하나뿐이라, 먼저 집은 사람이 다 쓸 때까지 다른 사람은 못 열지? 그리고 그 사람이 열쇠를 안 돌려주고 집에 가 버려도 문 닫을 시간이 되면 아저씨가 열어 주니까, 다음 사람이 쓸 수 있어.

## ❓ 이해했는지

- 자물쇠를 잡은 채로 그 기계가 통째로 죽으면 다음 사람은 어떻게 들어가나 → 작동 원리
- 반납할 때 값을 대조하지 않고 그냥 지우면 무엇이 잘못될 수 있나 → 주의사항
- 복제본을 하나 더 붙여 두는 것으로는 왜 상호 배제가 안 되나 → 흔한 오해
