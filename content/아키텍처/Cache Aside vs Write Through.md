# Cache Aside vs Write Through (캐시 쓰기 전략)

## 📝 정의

둘은 **캐시를 읽다가 채우느냐 쓰면서 채우느냐의 갈림**이다.

캐시에 둔 사본은 원본과 어긋나기 마련이다. 애저 문서는 그래서 "캐시를 얼마나 최신으로 둘지" 를 앱이 전략으로 정해 두어야 한다고 적는다. 이 갈림이 그 전략의 첫 번째 갈래고, AWS 문서는 앞쪽 방식을 지연 적재(lazy loading)라는 이름으로 설명한다.

### 이름
Cache :: 가까이 둔 사본
Aside :: 비켜서
Write :: 쓰기
Through :: 지나서
= "캐시를 비켜서" 는 읽다 없을 때 원본에 다녀와 채우고, "지나서 쓰기" 는 쓸 때 원본까지 한 번에 쓴다

### 비유
밥상의 작은 반찬통에 부엌 큰 통의 반찬을 언제 덜어 오느냐 — 먹고 싶을 때 그때그때냐, 새로 담글 때마다 미리냐.

### 예
상품 이름을 고쳤는데 목록에는 한동안 옛 이름이 그대로 떠 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
대조: 캐시를 언제 채우느냐로 무엇이 갈리나
캐시 비켜 읽기 |=| 지나서 쓰기
채우는 때 :: 읽다 없을 때 || 쓸 때마다
쓴 직후 읽기 :: 잠깐 옛값 || 곧바로 새값
안 읽는 값 :: 안 담긴다 || 그래도 담긴다
= 읽다 채우면 안 쓰는 값이 안 쌓이고, 쓰며 채우면 옛값이 안 남는다
```

## ⚠️ 해결하는 문제

```도해
대조: 전략을 안 정해 두면 캐시는 어떻게 되나
정하지 않으면 || 정해 두면
옛값 :: 언제 지울지 모른다 || 지우는 때가 있다
새로 띄운 기계 :: 텅 빈 채로 받는다 || 채울 길이 정해진다
자리 :: 안 읽는 값이 쌓인다 || 만료로 걷어낸다
= 어긋남을 없앨 수는 없고, 어디로 몰지 정하는 것이 전략이다
```

캐시를 붙이면 빨라진다. 대신 같은 값이 두 군데에 있게 되고, 그 둘은 반드시 어긋난다. 어긋남은 세 자리에서 나온다 — 원본을 고친 직후, 캐시가 가득 차서 무언가를 버릴 때, 캐시를 담은 기계(노드)를 새로 띄워 캐시가 텅 비었을 때.

이 갈림은 그 어긋남을 **어느 쪽으로 몰지** 고르는 일이다. 읽다 채우면 안 읽는 값이 안 쌓이고 빈 노드도 스스로 채워지지만, 쓴 직후에 잠깐 옛값이 보인다. 쓰며 채우면 옛값이 안 남지만, 한 번도 안 읽힐 값까지 캐시를 차지하고 새 노드는 다시 쓸 때까지 비어 있다.

## 📊 비교: 둘 중 무엇을 고르나

| 보는 자리 | Cache Aside (읽다 채우기) | Write Through (쓰며 채우기) |
|---|---|---|
| **캐시에 없는 값** | 세 번 오간다 — 캐시·원본·다시 캐시 | 쓴 적 없으면 여전히 없다 |
| **쓴 직후 읽기** | 잠깐 옛값이 보일 수 있다 | 곧바로 새 값이 보인다 |
| **새로 띄운 노드** | 없는 값마다 원본에 다녀오며 스스로 채워진다 | 다시 쓸 때까지 비어 있다 |
| **캐시 낭비** | 요청된 값만 담긴다 | 안 읽을 값까지 담긴다 |
| **고르는 자리** | 무엇이 읽힐지 모를 때 | 고친 사람이 곧바로 다시 보는 화면 |

**둘은 배타적이지 않다.** AWS 문서가 권하는 조합은 쓰며 채우되 만료 시간을 함께 거는 것이다. 그러면 빈 노드는 읽다 채워지고, 안 읽는 값은 시간이 지나 걷힌다. 기본은 읽다 채우기로 두고, 쓴 직후 바로 읽는 화면에만 쓰며 채우기를 얹는 것이 대개 안전한 순서다.

## 🚨 주의사항

- **만료 시간을 접근 주기에 맞춘다.** 너무 짧으면 원본에 계속 다녀오고, 너무 길면 옛값이 오래 남는다. 캐시는 자주 읽히고 잘 안 바뀌는 값에 가장 잘 듣는다.
- **비싼 값은 따로 정한다.** 캐시가 가득 차면 대개 가장 오래 안 쓴 것부터 버린다. 꺼내오기 비싼 값은 전체 정책 말고 그 값만의 정책을 준다.
- **민감한 값은 담지 않는다.** 여럿이 함께 쓰는 캐시라면 더 그렇다. 그런 값은 원본에서 바로 읽는다.

## 💡 실제 사례

- **상품 상세 화면** — 처음 열릴 때 원본에서 읽어 담고 그다음부터는 캐시가 답한다. 아무도 안 여는 상품은 담기지도 않는다.
- **고쳐서 바로 보여주는 화면** — 수정 버튼을 누른 사람이 그 값을 곧바로 다시 읽는다면, 쓸 때 캐시까지 같이 채운다.
- **둘을 겹쳐 쓰기** — 쓰며 채우되 만료 시간을 함께 건다. 빈 노드는 읽다 채워지고, 안 읽는 값은 시간이 지나면 걷힌다.

## 🚫 흔한 오해

- **쓰며 채우는 쪽이 언제나 낫다** — 대부분의 값은 한 번도 안 읽힌다. 쓸 때마다 담으면 안 읽을 값이 캐시를 차지하고, 새로 띄운 노드는 다시 쓸 때까지 비어 있다.
- **고칠 때 캐시부터 지우면 된다** — 순서가 반대다. 원본을 먼저 고치고 그다음 캐시를 지운다. 캐시를 먼저 지우면 그 틈에 누가 읽어 가서 옛값을 도로 담아 놓는다.
- **캐시를 붙이면 어차피 빨라진다** — 대부분의 요청이 캐시에서 안 맞으면 캐시를 확인하고 채우는 비용만 더 든다. 그럴 때는 캐시를 빼는 편이 낫다.

## 📝 정리

**"읽다 채울까 쓰며 채울까의 갈림"** 이라고 읽으면 된다. 읽다 채우면 안 읽는 값이 안 쌓이고 빈 노드가 스스로 차는 대신 쓴 직후에 잠깐 옛값이 보이고, 쓰며 채우면 그 반대다. 둘 중 하나를 고르는 문제로 보지 말고, 기본을 읽다 채우기로 두고 만료 시간을 건 뒤 곧바로 다시 읽는 화면에만 쓰며 채우기를 얹는다.

## 🧒 열 살에게

밥상에는 작은 반찬통을 놓고 큰 통은 부엌에 두지? 먹고 싶을 때만 큰 통에서 덜어 오면 아무도 안 먹는 반찬은 아예 안 담기는 대신, 방금 담근 김치가 작은 통에는 아직 없을 수 있어. 담글 때마다 미리 덜어 두면 늘 새것이지만 안 먹을 반찬까지 자리를 차지해.
