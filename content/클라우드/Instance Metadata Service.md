# Instance Metadata Service (인스턴스 신원 조회 창구)

## 📝 정의

Instance Metadata Service 는 그 서버가 **자기 정보를 물어보는** 고정 주소다.

세 클라우드가 약속이나 한 듯 같은 주소를 쓴다 — `169.254.169.254`. 바깥으로 나가지 않는 링크 로컬 주소라 그 대 안에서만 닿고, 밖에서는 아무리 두드려도 열리지 않는다. AWS 는 Instance Metadata Service(IMDS), Azure 는 Azure Instance Metadata Service, Google Cloud 는 메타데이터 서버라 부른다.

### 이름
Instance :: 띄워 놓은 한 대
Metadata :: 그 대를 설명하는 값
Service :: 물으면 답하는 쪽
= 붙여 읽으면 "한 대를 설명하는 값을 물으면 답해 주는 쪽". 묻는 주소가 늘 같다

### 비유
들기만 하면 프런트로 이어지고 "여기가 몇 호실인지" 를 대신 알려 주는 호텔 객실의 내선 전화.

### 예
클라우드에 올린 앱에 열쇠 문자열을 한 줄도 안 적었는데 저장소에 파일이 잘 올라가는 그 상황이다.

## 🖼️ 그림으로 보기

```도해
흐름: 앱은 저장소에 들어갈 열쇠를 어디서 얻어 오나
앱 :: 열쇠가 파일에 없다. 어디서 받나
고정 주소 :: 어느 대에서든 같은 그 주소로 묻는다
조회 창구 :: 이 대에 붙여 둔 역할을 확인한다
< 앱 :: 몇 시간 뒤 만료되는 임시 열쇠를 받는다
= 열쇠를 심어 두는 대신, 그때그때 자기 신원으로 빌려 온다
```

## ⚠️ 해결하는 문제

```도해
대조: 열쇠를 파일에 적어 두면 무엇이 달라지나
파일에 적어 두면 || 창구에서 받으면
샜을 때 :: 그 열쇠는 계속 산다 || 몇 시간 뒤 죽는다
열쇠 교체 :: 전부 찾아 고친다 || 저절로 갈린다
대 늘리기 :: 대마다 심어야 한다 || 심을 것이 없다
= 아예 안 심어 두면 훔쳐 갈 열쇠도 없다
```

앱이 저장소나 큐를 쓰려면 권한이 있어야 한다. 옛날 방식은 설정 파일이나 환경 변수에 긴 열쇠 문자열을 적어 두는 것이었다. 그러면 그 파일이 저장소에 올라가고, 이미지에 구워지고, 화면 공유에 찍히고, 실수로 공개 저장소에 올라간다. 한 번 새면 누가 언제 쓸지 알 수 없는데, 그 열쇠는 사람이 손으로 갈아 끼우기 전까지 계속 살아 있다.

조회 창구는 열쇠를 심을 필요를 없앤다. 대를 만들 때 "이 대는 이런 역할이다" 라고 붙여 두면, 그 대 안에서 창구에 물었을 때만 몇 시간짜리 임시 열쇠가 나온다. 대를 몇 대로 늘리든 심을 것이 없고, 그 대를 지우면 열쇠도 같이 사라진다.

## ⚙️ 작동 원리

창구는 그 대 안에서만 보이는 주소에 앉아 있다. Azure 문서는 이 주소가 **밖으로 나가지 않는 주소이고, 대와 창구 사이의 통신은 호스트를 절대 벗어나지 않는다** 고 적는다. Google 은 `metadata.google.internal` 이라는 이름도 함께 준다.

문제는 "그 대 안에서만 열린다" 가 생각만큼 강한 담이 아니라는 점이다. 앱에 남이 준 주소를 대신 열어 주는 구멍(SSRF)이 있으면, 공격자는 그 앱을 시켜 창구에 물어보게 하고 답만 받아 간다. 대 안에서 도는 것은 앱이지 공격자가 아니므로 담은 그대로 뚫린다.

그래서 세 클라우드 모두 "그냥 GET 하면 나오는" 상태를 막는 장치를 붙였다. Azure 와 Google 은 특별한 머리표(`Metadata: true`, `Metadata-Flavor: Google`)가 붙은 요청만 받는다. 브라우저나 단순한 중계기는 그 머리표를 못 붙이므로 속아서 대신 물어보는 일이 걸러진다. AWS 는 한 걸음 더 가서, 먼저 PUT 으로 토큰을 받고 그 토큰을 달아야 답하는 IMDSv2 를 만들었다. 토큰을 내주는 응답에는 홉 제한이 붙어서, 기본값 1 이면 그 답이 대를 벗어나 컨테이너 밖이나 옆 기기로 나가지 못한다.

창구는 신원 증명도 내준다. AWS 는 서명이 붙은 인스턴스 아이덴티티 문서를, Azure 는 검증 가능한(attested) 데이터를, Google 은 ID 토큰을 준다. 받은 쪽은 그 서명을 검증해 "정말 그 클라우드의 그 대가 맞다" 를 확인할 수 있다.

## 📊 비교: 세 클라우드의 창구는 어떻게 다른가

| | AWS | Azure | Google Cloud |
|---|---|---|---|
| 부르는 이름 | Instance Metadata Service | Azure Instance Metadata Service | 메타데이터 서버 |
| 주소 | `169.254.169.254` | `169.254.169.254` | `metadata.google.internal` · `169.254.169.254` |
| 통과 조건 | IMDSv2 는 먼저 PUT 으로 토큰을 받아야 | 머리표 `Metadata: true` 필수 | 머리표 `Metadata-Flavor: Google` 필수 |
| 임시 열쇠 | 역할에 붙은 임시 자격 증명 | 관리 ID 토큰 | 서비스 계정 토큰 |
| 서명된 신원 | 인스턴스 아이덴티티 문서 | attested 데이터 | ID 토큰 |
| 나가는 길 막기 | 홉 제한(기본 1) | 프록시를 타면 안 된다 | 프록시를 타면 안 된다 |

## 💡 실제 사례

- **열쇠 없는 접근** — 대에 역할만 붙여 두면 앱은 열쇠 문자열 없이 저장소를 읽고 쓴다.
- **자기 자리 알아내기** — 부팅 스크립트가 자기 인스턴스 아이디와 가용 영역을 물어 이름표와 로그 꼬리표를 붙인다.
- **쫓겨나기 전 신호** — 스팟 인스턴스는 회수 예고가 창구에 뜨는지 지켜보다가 뜨면 하던 일을 정리하고 내려간다.

## 🚫 흔한 오해

- **그 대 안에서만 열리니까 안전하다** — 앱에 남의 주소를 대신 열어 주는 구멍이 있으면 그 앱을 통해 열쇠가 새어 나간다. 담은 사람이 아니라 위치를 볼 뿐이다.
- **여기 담긴 값은 다 공개해도 되는 것이다** — AWS 문서는 이 값들이 인증이나 암호로 보호되지 않으며 그 대에서 도는 어떤 프로그램이든 볼 수 있으니, 비밀번호나 오래 쓰는 열쇠를 user data 에 넣지 말라고 적는다.
- **토큰을 요구하게 바꿔도 앱은 그대로 돈다** — IMDSv1 방식으로 묻던 옛 프로그램과 에이전트는 토큰을 안 붙이므로 그 자리에서 깨진다. AWS 문서도 강제 전환 전에 반드시 시험하라고 적는다.

## 🚨 주의사항

- **컨테이너에서 부르면 홉이 하나 늘어난다.** 기본 홉 제한 1 이면 컨테이너 안의 앱은 답을 못 받는다.
- **프록시를 타면 안 된다.** Azure 문서는 클라이언트의 프록시 설정을 반드시 우회하라고, 그것도 프록시를 모르는 환경에서까지 그렇게 하라고 적는다.
- **아예 끌 수도 있다.** 창구를 안 쓰는 대라면 꺼 두는 것이 가장 확실하다. 다만 창구에 기대는 에이전트가 같이 죽는다.

## 📝 정리

**"자기가 누구인지 물어보는 그 고정 주소"** 라고 읽으면 된다. 열쇠를 심는 대신 빌려 오게 만들었다는 것이 핵심이고, 그래서 새어도 몇 시간이면 죽는다. 대신 앱이 남의 주소를 대신 열어 주는 순간 이 창구가 그대로 통로가 되므로, 토큰과 머리표와 홉 제한이 다 그 하나를 막으려고 있다.

## 🧒 열 살에게

호텔 방에 있는 전화기 알지? 번호를 안 눌러도 들기만 하면 프런트로 이어지고, 그 방에서 걸어야만 여기가 몇 호실인지 알려 줘. 그래서 방마다 열쇠를 따로 적어 붙여 두지 않아도 되는 거야.

## ❓ 이해했는지

- 앱에 열쇠를 한 줄도 안 적었는데 저장소에 파일이 올라가는 이유는 무엇인가 → 그림
- 남이 준 주소를 대신 열어 주는 구멍이 왜 이 창구까지 위험하게 만드나 → 흔한 오해
- 컨테이너 안에서 이 주소를 물었는데 답이 안 오는 일은 왜 생기나 → 주의사항

## 🔗 관련 용어

- [[EC2]] — AWS 에서 이 창구가 붙어 있는 그 한 대
- [[IAM]] — 창구가 내주는 임시 열쇠에 어떤 권한이 실릴지 정하는 쪽
- [[Secret Management]] — 열쇠를 심어야 할 때 쓰는 다른 길. 창구는 심을 필요를 없앤다
- [[Instance Template]] — 이 창구로 읽히는 시작 스크립트가 들어 있는 틀
- [[Least Privilege]] — 임시 열쇠라도 권한이 넓으면 새었을 때 똑같이 위험하다
