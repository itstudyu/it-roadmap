# Application Dependency Mapping (응용 의존 관계 지도)

## 📝 정의

Application Dependency Mapping은 **서로 붙어 있는 것을 찾아 그리는 일**이다.

옮기기 전에 하는 일이다. 기계 목록은 무엇이 있는지만 알려주고, 무엇이 무엇을 부르고 있는지는 알려주지 않는다. Azure 문서는 이 작업의 목적을 "함께 옮겨야 하는 기계를 찾아내는 것" 과 "아무것도 뒤에 남지 않게 해서 옮긴 뒤의 갑작스러운 중단을 피하는 것" 으로 적는다.

### 이름
Application :: 돌아가는 응용
Dependency :: 남에게 기댄 관계
Mapping :: 지도로 그리기
= 붙여 읽으면 "응용이 무엇에 기대고 있는지 지도로 그리기"

### 비유
냉장고 뒤에 숨은 전선. 냉장고만 먼저 옮기면 거기 물려 있던 정수기가 같이 멎는다.

### 예
옮긴 다음 날 아침에 엉뚱한 화면이 하얗게 뜨고, 알고 보니 아직 옛 자리에 남은 무언가를 부르고 있던 그 장면이다.

### 직접
와이파이를 끈 채로 폰의 앱을 하나씩 열어 보라. 혼자 도는 앱과 밖에 기대는 앱이 그 자리에서 갈린다.

## 🖼️ 그림으로 보기

```도해
층: 응용 하나는 어디까지 기대고 있나
같은 기계 안 :: 함께 도는 것들끼리 포트로 서로 부른다
옆 기계 :: 자료를 넣어 두는 곳, 로그인을 확인해 주는 곳
회사 안 다른 팀 :: 밤마다 파일을 받아 가는 쪽. 부르는 쪽이 저기 있다
회사 밖 :: 결제·문자 같은 바깥 업체. 아예 못 옮기는 것도 여기 있다
= 멀리 있는 기댐일수록 늦게 발견되고, 늦게 발견될수록 끊긴 뒤에야 보인다
```

## ⚠️ 해결하는 문제

```도해
대조: 기댄 관계를 안 그리고 옮기면 무엇이 달라지나
지도 없이 || 지도를 그리면
묶는 근거 :: 짐작으로 묶는다 || 오간 연결로 묶는다
빠뜨린 것 :: 끊긴 뒤에 안다 || 옮기기 전에 안다
못 옮기는 것 :: 그날 알게 된다 || 미리 남기기로 한다
= 안 보이는 줄은 끊어져야 보인다. 끊기 전에 보이게 만드는 일이다
```

응용 하나를 옮긴다는 말은 실제로는 한 덩어리를 옮긴다는 뜻이다. 화면을 그리는 쪽, 자료를 넣어 두는 쪽, 로그인을 확인해 주는 쪽, 밤에 정산을 도는 쪽이 서로를 부르고 있다. 이 중 하나만 남겨 두면 남은 쪽도 옮긴 쪽도 반쯤 죽는다. 문제는 이 줄들이 **도면 어디에도 안 적혀 있다**는 것이다. 만든 사람이 이미 퇴사했거나, 급할 때 임시로 연결해 두고 잊었기 때문이다.

의존 관계 지도는 그 줄을 **문서가 아니라 실제로 오간 연결에서 찾아낸다.** Azure 문서는 대리인 없는 방식이 기계마다 5분에 한 번 TCP 연결 자료를 걷고, 출발한 쪽의 프로그램과 도착한 쪽의 기계·프로그램·포트를 하나의 의존 관계로 묶는다고 적는다. 사람의 기억이 아니라 기계가 실제로 부른 기록이 근거가 된다.

## ⚙️ 작동 원리

거두는 방식은 둘이다. **대리인 없는 방식**(agentless)은 기계마다 무언가를 깔지 않고 밖에서 걷는다. Azure 문서 기준으로 5분마다 연결을 훑고 여섯 시간에 한 번 모아 올린다. 깔 것이 없어 수백 대에도 바로 켤 수 있는 대신, 안에서 벌어지는 일까지는 못 본다.

**대리인을 깐 방식**(agent-based)은 기계마다 프로그램을 하나 깔아 안에서 본다. AWS 문서는 이 방식이 정적인 설정값과 시계열 성능값에 더해 **들어오고 나가는 연결과 돌고 있는 프로세스**까지 걷는다고 적고, 걷는 간격을 약 15초로 적는다. 밖에서 보는 방식은 약 60분이다. 같은 문서가 밖에서만 보는 수집기는 "가상 기계 안을 들여다볼 수 없어 어떤 프로세스가 도는지도, 어떤 연결이 있는지도 알아낼 수 없다" 고 못박는다.

**얼마나 오래 지켜보느냐가 지도의 품질을 정한다.** 하루만 보면 하루에 한 번 도는 것만 잡힌다. 월말 정산, 분기 마감, 연말 결산처럼 드물게 도는 줄은 그 기간을 포함해 지켜봐야 지도에 그려진다.

## 📊 비교: 세 클라우드는 이 일을 무엇이라 부르나

| | AWS | Azure | Google |
|---|---|---|---|
| 이름 | Application Discovery Service (지금은 AWS Transform) | Azure Migrate 의 종속성 분석 | Migration Center |
| 대리인 없이 | Agentless Collector — 설정값과 사용량 | 기본이자 권장 방식 — TCP 연결을 5분마다 | 자동 훑기로 자산 목록 |
| 대리인을 깔면 | Discovery Agent — 연결과 프로세스까지, 약 15초 간격 | 예전 화면에서만 지원 | — |
| 지도 다음에 주는 것 | Migration Hub 에서 묶고 진행 상황을 본다 | 묶어서 이전 물결을 짠다 | 총소유비용 보고서와 제품 추천 |

이름과 화면은 다르지만 묻는 것은 하나다 — **같이 옮겨야 하는 것이 무엇인가.** Google 문서도 이 기능을 "함께 옮겨야 하는 구성 요소를 알기 위해 응용과 망의 의존 관계를 찾아내는 것" 으로 적는다.

## 💡 실제 사례

- **이전 물결 나누기** — 서로 부르는 것끼리 한 묶음으로 묶어 같은 밤에 옮긴다. Azure 문서는 붙어 있는지 애매하면 일단 같이 묶으라고 적는다.
- **못 옮기는 것 골라내기** — 특수 장비나 규정 때문에 남아야 하는 것을 먼저 찾아, 양쪽에 걸쳐 도는 기간을 되도록 짧게 잡는다.
- **버릴 것 찾기** — 90일 동안 아무도 부르지 않은 것은 옮길 대상이 아니라 지울 대상이다. 목록의 앞머리가 여기서 줄어든다.

## 🚫 흔한 오해

- **자산 목록을 뽑았으니 지도는 다 됐다** — 목록은 무엇이 있는지만 말한다. 누가 누구를 부르는지는 실제로 오간 연결을 일정 기간 지켜봐야 나온다.
- **한 번 찍어 두면 그게 지도다** — 월말에만 도는 일은 월말을 끼고 봐야 잡힌다. 지켜본 기간 밖의 줄은 지도에 아예 그려지지 않는다.
- **다 그린 다음에 옮기면 된다** — 다 그려지는 날은 오지 않는다. Azure 문서는 애매하면 같이 묶어 두라고 적는다. 나중에 떼어내는 편이 못 찾은 줄을 찾는 것보다 쉽기 때문이다.

## 📝 정리

**"같이 옮겨야 할 것을 미리 찾아내는 그림"** 이라고 읽으면 된다. 근거는 사람의 기억이나 도면이 아니라 기계가 실제로 주고받은 연결이고, 얼마나 오래 지켜봤느냐가 곧 지도의 정확도가 된다. 밖에서만 걷는 방식은 넓게 빨리 보고, 안에 깔아 걷는 방식은 어떤 프로그램이 부르는지까지 본다.

## 🧒 열 살에게

이사할 때 냉장고만 먼저 옮겨 놓으면, 그 옆에 꽂혀 있던 정수기가 물을 못 받아서 같이 못 쓰게 되지? 그래서 무엇이 무엇에 붙어 있는지를 먼저 그려 두고 붙은 것끼리 같이 옮기는 거야. 안 그리고 옮기면 옮긴 다음에야 뭐가 안 되는지 알게 돼.

## ❓ 이해했는지

- 한 달 내내 멀쩡하던 것이 월말에만 안 되는 일은 왜 생기나 → 흔한 오해
- 기계 목록을 다 뽑아 놓고도 함께 옮길 묶음을 못 짜는 이유는 무엇인가 → 해결하는 문제
- 어떤 프로그램이 그 연결을 열었는지까지 알려면 무엇이 더 필요한가 → 작동 원리
