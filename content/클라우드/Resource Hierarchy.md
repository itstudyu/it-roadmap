# Resource Hierarchy (자원 계층)

## 📝 정의

Resource Hierarchy 는 **규칙이 위에서 아래로 흐르는 나무**다.

클라우드를 쓰기 시작하면 계정이 하나다. 그러다 팀이 늘고 개발용과 운영용을 갈라야 하고 감사가 붙으면 계정이 스물, 쉰으로 는다. 이때 계정을 평평하게 늘어놓으면 새 계정이 생길 때마다 사람이 규칙을 다시 걸어야 하고, 한 번만 빠뜨려도 그 계정 하나가 구멍이 된다. 자원 계층은 계정 위에 **덮개**를 씌워, 위에 한 번 건 규칙이 아래 전부에 저절로 닿게 만드는 구조다.

### 이름
Resource :: 만들어 쓰는 것
Hierarchy :: 위아래로 선 층
= 붙여 읽으면 "자원을 위아래로 세운 층". 위에 건 것이 아래로 흐른다

### 비유
학교의 규칙. 교장이 정한 것은 모든 반이 지켜야 하고, 담임은 자기 반만 더 조일 수 있을 뿐 교장이 정한 것을 풀지는 못한다.

### 예
계정을 새로 하나 받았는데 아무것도 안 건드렸는데도 특정 지역이 이미 막혀 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
층: 규칙은 어디서 걸려 어디까지 내려가나
최상위 :: 회사 전체를 덮는 뿌리. 예외를 안 둔다
가운데 묶음 :: 본부·팀으로 갈라 맡기는 칸
값 매기는 그릇 :: 청구서와 권한이 붙는 단위
자원 :: 실제로 도는 기계와 저장통
= 위에서 건 규칙은 아래로 흐르고, 아래에서는 못 푼다
```

## ⚠️ 해결하는 문제

```도해
대조: 계정을 평평하게 늘어놓으면 무엇이 무너지나
평평하게 || 계층으로
새 계정 규칙 :: 사람이 매번 건다 || 들어가면 붙는다
빠뜨림 :: 하나만 새면 끝 || 위에서 막힌다
값 나누기 :: 꼬리표에만 기댄다 || 그릇째 갈린다
= 계정이 스무 개를 넘는 순간 손으로 맞추는 방식은 반드시 샌다
```

계정을 평평하게 늘어놓으면 규칙의 개수가 계정 수만큼 는다. 새 팀이 계정을 하나 받을 때마다 누군가 붙어서 열 가지를 걸어야 하고, 그 사람이 휴가면 그 계정은 며칠 동안 아무 덮개 없이 돈다. Google Cloud 문서가 계층의 이점으로 든 것이 정확히 이것이다 — 높은 자리에 준 권한과 정책이 아래로 흘러 내려가서, 프로젝트마다 손으로 맞출 필요가 없어진다.

두 번째 이점은 **소유**다. 같은 문서는 계층이 "자원의 수명을 바로 위 부모에 묶는다" 고 적는다. 사람이 만든 것이 사람에게 딸리지 않고 조직에 딸리게 되어서, 담당자가 회사를 떠나도 그가 만든 것이 주인 없이 남지 않는다. 관리자 없이 굴러다니는 계정과 몰래 만든 계정이 사라지는 자리도 여기다.

## 📊 비교: 같은 층을 세 곳은 뭐라 부르나

| 층 | AWS | Azure | Google Cloud |
|---|---|---|---|
| **뿌리** | Root (Organizations) | 테넌트 루트 관리 그룹 | 조직(Organization) |
| **가운데 묶음** | 조직 단위 OU (다섯 겹까지) | 관리 그룹 | 폴더 |
| **값 매기는 그릇** | 계정(Account) | 구독(Subscription) | 프로젝트(Project) |
| **수명이 같은 것끼리 묶는 칸** | 없다 (꼬리표로 대신) | 리소스 그룹 | 없다 (꼬리표로 대신) |
| **위에서 거는 제한** | SCP · RCP | Azure Policy · 역할 할당 | 조직 정책 · IAM |

이름이 셋이라 헷갈리지만, 고를 때 물어야 할 것은 하나다. **터졌을 때 어디까지 번지나.** 계정·구독·프로젝트가 그 선이다. 여기가 값이 갈리는 단위이자 권한이 갈리는 단위이고, 하나가 오염돼도 옆으로 안 번지는 벽이다. 그래서 개발용과 운영용을 같은 그릇에 담지 않는다. Azure 문서도 개발·시험·운영을 구독으로 갈라 격리와 값 추적을 함께 얻으라고 적는다.

한 겹 위의 묶음은 **같은 규칙을 걸 대상을 모으는 자리**다. AWS 문서는 같은 통제를 계정 일부에만 걸어야 할 때 조직 단위가 쓸모 있다고 적고, 겹쳐 만들면 더 잘게 나눌 수 있다고 쓴다. 뿌리와 가장 아래를 빼고 **다섯 겹까지** 파고들 수 있다.

## 💡 실제 사례

- **운영 계정에는 실험을 못 열게 한다** — 운영 묶음에만 제한 정책을 걸어 두면, 그 아래로 새로 들어오는 계정은 처음부터 그 제한을 쓰고 태어난다.
- **지역을 잠근다** — 규제 때문에 특정 지역만 써야 하면 뿌리나 묶음 한 곳에 한 번 걸어 둔다. 계정마다 걸고 다니지 않는다.
- **청구서를 부서별로 가른다** — 값이 그릇 단위로 갈리므로, 부서를 그릇으로 나눠 두면 꼬리표를 잘 붙였는지와 상관없이 총액이 먼저 갈린다.

## 🚫 흔한 오해

- **계정을 여러 개 만드는 건 관리만 복잡해진다** — 계정은 관리 단위가 아니라 **벽**이다. AWS 문서는 여러 계정을 쓰는 것이 값의 경계이자 보안 격리라서 규모를 키울 때의 권장이라고 적는다.
- **위에서 막아도 아래에서 풀 수 있다** — 아니다. 위에서 건 제한은 아래에서 넓힐 수 없다. AWS 의 제한 정책은 아래 계정이 가질 수 있는 **권한의 천장**을 낮추는 장치다.
- **층을 깊게 팔수록 좋다** — 겹이 늘수록 어느 규칙이 어디서 왔는지 추적이 어려워지고, AWS 는 애초에 다섯 겹이 한계다. 겹은 규칙을 걸 자리가 실제로 필요할 때만 판다.

## 🚨 주의사항

- **제한 정책이 관리 계정에는 안 걸린다.** AWS 문서는 뿌리에 건 제한 정책이 조직의 관리 계정에는 적용되지 않는다고 못 박는다. 그래서 자원을 관리 계정에 두지 말라고 권한다.
- **꼬리표는 계층을 대신하지 못한다.** Azure 문서는 자원이 리소스 그룹이나 구독의 꼬리표를 물려받지 않는다고 적는다. 물려받는 것은 정책과 권한이지 이름표가 아니다.
- **이름은 나중에 못 바꾼다.** Azure 문서는 자원 이름이 만든 뒤에 바뀌지 않으니 변하지 않을 것만 이름에 넣고 나머지는 꼬리표에 넣으라고 적는다. 층 이름도 같은 조심이 든다.

## 📝 정리

**"위에 한 번 걸면 아래가 다 따르는 나무"** 라고 읽으면 된다. 세 곳이 뿌리와 묶음과 그릇을 저마다 다르게 부르지만, 값과 권한과 폭발 범위가 갈리는 선은 언제나 계정·구독·프로젝트다. 그러니 층을 짤 때 던질 물음은 "어떻게 예쁘게 나누나" 가 아니라 "여기가 터지면 어디까지 번지나" 다.

## 🧒 열 살에게

교장 선생님이 "복도에서 뛰지 마" 하고 정하면 모든 반이 다 지켜야 하지? 담임 선생님은 우리 반만 더 조일 수 있고, 교장 선생님이 정한 걸 풀지는 못해. 반이 백 개가 돼도 같은 말을 백 번 할 필요가 없는 이유가 그거야.

## ❓ 이해했는지

- 계정이 쉰 개로 늘었을 때 규칙을 손으로 거는 방식이 왜 반드시 새나 → 해결하는 문제
- 부서를 나눌 때 묶음이 아니라 그릇으로 갈라야 하는 이유는 무엇인가 → 비교
- 뿌리에 제한을 걸었는데도 안 막히는 계정이 있는 까닭은 무엇인가 → 주의사항

## 🔗 관련 용어
