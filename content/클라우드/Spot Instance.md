# Spot Instance (스팟 인스턴스)

## 📝 정의

Spot Instance는 **남는 자리를 싸게 쓰되 언제든 회수당하는 서버**다.

클라우드는 늘 여분의 용량을 들고 있다. 그 여분을 정가보다 크게 깎아 파는 대신, 필요해지면 도로 가져간다. 값이 싼 만큼 자리를 언제까지 쓸지는 내가 못 정한다.

### 이름
Spot :: 그때그때 값
Instance :: 빌려 쓰는 한 대
= 붙여 읽으면 "그때그때 값으로 빌린 한 대". 값이 흔들리는 만큼 자리도 흔들린다

### 비유
공연 직전에 남은 자리를 크게 깎아 파는 표와 같아서, 정가 손님이 오면 비켜 줘야 한다.

### 예
밤새 돌려도 되는 변환 작업을 이 자리에서 돌리다가, 끊기면 남은 몫부터 다시 돌리는 그 방식이다.

## 🖼️ 그림으로 보기

```도해
흐름: 남는 자리를 빌리면 어떤 일을 겪나
남는 용량 :: 정가보다 크게 깎인 값이 붙는다
빌려 쓰기 :: 정가 자리와 똑같은 기계가 돌아간다
회수 통보 :: 클라우드가 용량이 필요해지면 알린다
정리 :: 짧은 예고 뒤 멈추거나 사라진다
@ 다시 빌리기 :: 자리가 나면 또 빌려 이어서 돈다
= 값이 싼 대신 자리를 언제까지 쓸지는 내가 못 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 끊겨도 되는 일에 정가를 내면 무엇이 아쉬운가
정가로만 || 남는 자리로
값 :: 그대로 다 낸다 || 크게 깎인다
밤새 도는 일 :: 비싸게 돈다 || 싸게 돈다
남는 용량 :: 그냥 논다 || 누가 쓴다
= 끊겨도 되는 일에 굳이 정가를 낼 이유가 없다
```

정가로 빌리면 값이 정해져 있고 내가 끄기 전에는 안 끊긴다. 그 안심에 값을 매긴 것이 정가다. 그런데 밤새 도는 일괄 작업, 대량 변환, 실험처럼 중간에 끊겨도 다시 하면 되는 일에는 그 안심이 필요 없다.

AWS 문서는 이 자리를 "언제 돌릴지 유연하고 중단을 견딜 수 있다면 비용 면에서 좋은 선택" 이라 적고, 데이터 분석·일괄 작업·백그라운드 처리·있으면 좋은 작업을 예로 든다. 뒤집으면 판단 기준이 하나로 줄어든다 — **이 일이 중간에 멈춰도 되는가.**

## ⚙️ 작동 원리

이 자리는 그 순간 그 지역·그 기계 종류에 남아 있는 여유 용량에서 뜬다. 남는 용량은 기계 종류와 영역마다 따로 잡히므로, 한 종류에 몰아 두면 그 한 곳의 여유가 마르는 순간 전부가 한꺼번에 회수 대상이 된다.

정가 수요가 늘어 그 여유가 필요해지면 회수가 시작된다. 먼저 예고가 오는데, 이 예고는 사람에게 오는 메일이 아니라 기계 안에서 읽는 신호다 — 기계 정보 칸에 회수 표시가 뜨거나 종료 신호가 안으로 들어오고, 그때부터 AWS 는 2분, Azure 와 Google 은 30초를 센다. 그래서 이 신호를 지켜보다 스스로 마무리하는 코드를 넣어 두지 않으면 예고는 있으나 마나다.

예고 시간 동안 할 일은 정해져 있다. 하던 일의 중간 지점을 밖에 남기고, 새 요청은 더 안 받겠다고 알리고, 앞의 분배기 목록에서 자기를 뺀다. 그 뒤 기계는 멈추거나 사라진다. 자리가 다시 나면 새 기계를 띄워 남겨 둔 중간 지점부터 잇는데, 그 자리가 언제 날지도 나긴 할지도 약속되어 있지 않다.

## 📊 비교: 세 곳은 이 자리를 어떻게 회수하나

| 어디 | 이름 | 회수 예고 | 회수 조건 |
|---|---|---|---|
| **AWS** | Spot Instance | 2분 전 통보 | 용량이 필요해질 때 |
| **Azure** | Spot Virtual Machine | 30초 전 통보 | 용량이 필요하거나 내가 정한 최대 가격을 넘을 때 |
| **Google Cloud** | Spot VM | 종료까지 최대 30초 | 언제든 선점할 수 있다 |

AWS 는 두 분 통보 전에 "회수 위험이 높아졌다" 는 재균형 권고를 따로 보낸다. Azure 는 최대 가격을 `-1` 로 두면 가격 때문에는 안 쫓겨나고 표준 가격 이상은 안 낸다. Google 은 Spot VM 을 아예 SLA 대상에서 뺀다.

## 🚨 주의사항

- **가용성 약속이 없다.** Google 문서는 Spot VM 을 Compute Engine SLA 에서 제외한다고 적고, Azure 문서도 이 자리에는 SLA 가 없다고 적는다. 급하게 용량이 필요하면 표준 자리를 쓰라고 권한다.
- **예고가 짧다.** 2분이나 30초 안에 마무리할 수 있게 짜야 한다. 진행 중인 일은 중간 지점을 남겨 두고, 끊기면 거기서부터 잇는다.
- **되돌아온다는 보장이 없다.** Azure 의 Deallocate 정책은 나중에 다시 띄울 수 있게 해 주지만, 할당이 성공한다는 보장은 없다고 문서가 적는다.

## 💡 실제 사례

- **밤에 도는 일괄 작업** — 데이터 분석·일괄 처리·백그라운드 작업처럼 언제 돌아도 되는 일이 이 자리의 제자리다.
- **정가와 섞어 쓴다** — 늘 필요한 최소 대수는 정가나 약정으로 깔고, 늘어나는 몫만 이 자리로 채운다.
- **한 종류에 몰지 않는다** — 남는 용량은 기계 종류와 존마다 따로 잡힌다. 한 곳에만 몰아 두면 그곳이 회수될 때 전부 같이 멈춘다.

## 🚫 흔한 오해

- **싸니까 웬만하면 이걸로 돌리면 된다** — 회수되면 그냥 멈춘다. 사람이 기다리는 화면이나 상태를 들고 있는 자리에는 쓰지 않는다.
- **값이 오를 때만 끊긴다** — AWS 는 용량이 필요해질 때 회수한다. Azure 는 용량이 필요하거나 내가 정한 최대 가격을 넘을 때 내보낸다.
- **성능이 정가 자리보다 떨어진다** — 같은 기계다. 다른 것은 값과, 언제까지 쓸 수 있느냐뿐이다.

## 📝 정리

**"싸게 빌리는 대신 언제든 비켜 줘야 하는 자리"** 라고 읽으면 된다. 끊겨도 다시 하면 되는 일에만 쓰고, 예고가 2분이나 30초라는 것을 전제로 짠다. 사람이 기다리는 화면과 상태를 들고 있는 자리에는 쓰지 않는다.

## 🧒 열 살에게

공연 시작 직전에 남은 자리를 아주 싸게 파는 걸 본 적 있지? 대신 제값 내고 온 손님이 나타나면 너는 일어나 줘야 해. 값이 싼 만큼 언제 비켜 줄지는 네가 못 정하는 거야.

## ❓ 이해했는지

- 값이 그대로인데도 자리를 회수당할 수 있는 이유는 무엇인가 → 흔한 오해
- 회수 통보를 받은 뒤 남은 시간에 무엇을 해 두어야 하나 → 주의사항
- 사람이 기다리는 화면을 이 자리에 올리면 안 되는 이유는 무엇인가 → 그림
