# Control Plane vs Data Plane (지시하는 층과 나르는 층)

## 📝 정의

Control Plane vs Data Plane은 **만들고 바꾸는 길과 실제로 일하는 길의 갈림**이다.

Microsoft 문서는 이 갈림을 한 줄로 적는다 — "자원을 관리할 때는 컨트롤 플레인을 쓰고, 그 자원이 내놓는 기능을 쓸 때는 데이터 플레인을 쓴다." AWS 문서는 앞쪽을 "자원을 만들고 읽고 고치고 지우고 나열하는 관리용 API", 뒤쪽을 "날마다 오가는 실제 처리" 로 적는다.

### 이름
Control :: 만들고 바꾸기
Data :: 실어 나르는 것
Plane :: 갈라 놓은 층
= 붙여 읽으면 "바꾸는 층"과 "나르는 층". 한 서비스가 성질이 다른 두 층으로 갈려 있다

### 비유
놀이공원. 새 기구를 세우고 고치는 사무실과, 이미 세워져 손님을 태우고 도는 기구는 서로 다른 물건이다.

### 예
장애 때 관리 화면에서는 새 기계 하나를 못 띄우는데 이미 떠 있던 기계는 멀쩡히 돌고 있던, 그 이상한 조합이다.

### 직접
폰 설정에서 와이파이를 새로 등록하는 화면과, 이미 붙어서 영상이 흐르는 상태를 견줘 보라. 앞이 바꾸는 층이고 뒤가 나르는 층이다.

## 🖼️ 그림으로 보기

```도해
대조: 한 서비스의 두 층은 무엇이 다른가
바꾸는 층 Control |=| 나르는 층 Data
하는 일 :: 만들고 고치고 지운다 || 이미 만든 게 일한다
겨냥하는 것 :: 값이 안 어긋나게 || 언제나 답하게
움직이는 부품 :: 많고 서로 얽힌다 || 적고 단순하다
장애가 나면 :: 먼저 흔들린다 || 대체로 버틴다
= 두 층은 노리는 것이 서로 달라서, 급할 때 기댈 곳은 나르는 층이다
```

## ⚠️ 해결하는 문제

```도해
대조: 복구를 어느 층에 기대느냐로 무엇이 달라지나
바꾸는 층에 기대면 || 나르는 층에 기대면
필요한 일 :: 새로 만들어야 || 있는 걸 쓰면 된다
장애 때 성공률 :: 같이 흔들린다 || 훨씬 높다
걸리는 시간 :: 길고 들쭉날쭉 || 짧고 일정하다
= 무너지는 중에 새로 만들어 달라고 부탁하는 방법이 가장 잘 실패한다
```

장애가 났을 때 대부분의 복구 계획은 "새로 띄운다" 로 시작한다. 새 기계를 띄우고, DNS 레코드를 고치고, 다른 지역에 자원을 만든다. 그런데 이 동작들은 전부 바꾸는 층에 있다. AWS 문서는 기계 하나를 띄우는 일에 **빈자리가 있는 물리 장비 찾기, 망 인터페이스 할당, 저장 장치 준비, 자격 증명 생성, 보안 규칙 추가**가 줄줄이 딸려 있다고 적고, 바꾸는 층을 "복잡한 오케스트레이션" 이라 부른다.

부품이 많으면 고장 확률이 높다. AWS 문서는 바꾸는 층이 나르는 층보다 움직이는 부품과 의존이 많아 **통계적으로 더 자주 상한다**고 적고, 그 상하는 시점이 하필 장애가 난 그 시점과 겹친다고 적는다. 그래서 같은 문서가 복구 원칙 하나를 못박는다 — 복구할 때는 바꾸는 층 동작을 최소한으로 쓰고, **나르는 층 동작을 앞세우라**는 것이다.

## ⚙️ 작동 원리

복구를 나르는 층으로 옮기는 방법에는 이름이 있다. **정적 안정성**(static stability)이다. 사건이 나도 아무것도 새로 만들지 않고 이미 있는 것만으로 버티게 만드는 설계다. 한 구역이 죽었을 때 그만큼을 새로 띄우는 대신, 처음부터 여분을 띄워 두고 죽은 쪽으로 가던 몫을 살아 있는 쪽이 받게 한다.

바꾸던 자리를 하나씩 옮겨 적는 일이 실제 작업이다. AWS 문서는 바꿔치기 목록을 이렇게 든다 — 자동 크기 조절(바꾸는 층) 대신 미리 띄워 둔 기계(나르는 층), 기계 늘리기(바꾸는 층) 대신 함수 늘리기(나르는 층), DNS 레코드 고치기(바꾸는 층) 대신 미리 만들어 둔 전환 장치와 건강 검사(나르는 층). 쿠버네티스에 대해서도 같은 문장을 적는다 — **파드를 더하는 일은 나르는 층이고 노드를 더하는 일은 바꾸는 층이니, 노드를 넉넉히 미리 띄워 두라**는 것이다.

두 층은 사는 곳도 다르다. AWS 문서는 Route 53 의 바꾸는 층이 강한 일관성과 내구성을 위해 **버지니아 북부 한 지역**에 모여 있고 가용성 SLA 에 포함되지 않는다고 적는 반면, 질의에 답하고 건강 검사를 도는 나르는 층은 전 세계에 흩어져 있고 100% 가용성 SLA 로 설계됐다고 적는다. 같은 서비스 이름 안에 성질이 정반대인 두 물건이 들어 있는 셈이다.

## 📊 비교: 세 클라우드에서 이 갈림은 어디에 드러나나

| | AWS | Azure | Google |
|---|---|---|---|
| 부르는 말 | control plane · data plane | 컨트롤 플레인 · 데이터 플레인 | control plane · 노드 |
| 바꾸는 층의 얼굴 | 관리용 API (CRUDL) | Azure Resource Manager · `management.azure.com` | Kubernetes API 서버 · 스케줄러 |
| 나르는 층의 얼굴 | 도는 기계, 표에서 읽고 쓰기 | 인스턴스별 주소 · `계정.blob.core.windows.net` | 실제로 일감을 돌리는 노드 |
| 한쪽이 멈추면 | 나르는 층이 대체로 버틴다 | 바꾸는 층이 안 돼도 나르는 층은 쓸 수 있다 | 관리 층 수명은 제공자가 맡는다 |
| 권한·정책이 걸리는 곳 | 관리용 API | RBAC · 정책 · 잠금이 바꾸는 층에 | 클러스터 관리 층 |

이름과 얼굴은 다르지만 물음은 하나다 — **지금 하려는 이 동작이 새로 만드는 일인가, 이미 있는 것을 쓰는 일인가.** 시험 문제가 "장애 상황에서 복구 시간을 줄이려면 무엇을 고르나" 로 물으면, 답은 거의 언제나 새로 만들지 않는 쪽이다.

## 💡 실제 사례

- **여분을 미리 띄워 둔다** — 한 구역이 죽어도 새로 띄우지 않고 이미 떠 있는 것으로 받는다. AWS 문서가 정적 안정성이라 부르는 그 설계다.
- **레코드를 고치지 않고 돌린다** — 이름 바꾸기는 바꾸는 층이라 장애 때 함께 흔들린다. 건강 검사와 미리 만들어 둔 전환 장치로 나르는 층에서 돌린다.
- **노드가 아니라 파드를 늘린다** — 노드를 넉넉히 잡아 두면 갑자기 몰릴 때 파드만 더하면 된다. 노드를 더하는 순간 바꾸는 층에 기대게 된다.

## 🚫 흔한 오해

- **관리 화면이 안 열리면 서비스도 죽은 것이다** — Microsoft 문서는 바꾸는 층을 못 쓰는 동안에도 나르는 층은 그대로 쓸 수 있다고 적는다. 저장통 주소로 읽고 쓰는 일은 계속된다.
- **잠금을 걸어 뒀으니 안의 내용도 안전하다** — Microsoft 문서는 자원 삭제를 막는 잠금이 질의로 안의 내용을 지우는 것까지 막지는 않는다고 적는다. 잠금과 정책은 대개 바꾸는 층에만 걸린다.
- **자동으로 되기만 하면 어느 쪽이든 같다** — 자동으로 도는 그 동작이 새로 만드는 일이면 그건 바꾸는 층이다. 장애 때 같이 흔들리는 쪽에 복구를 통째로 맡긴 셈이 된다.

## 🚨 주의사항

- **복구 절차의 줄마다 어느 층인지 적어 둔다.** AWS 문서는 복구 계획의 각 동작을 층으로 분류해 바꾸는 층 동작을 최소로 줄이라고 적는다.
- **바꾸는 층 동작은 사건 전에 끝내 둔다.** 새 함수, 새 부하 분산기, 새 표를 만드는 일은 미리 만들어 두고 전환 연습까지 해 둔다.
- **바꾸는 층이 어느 지역에 사는지 확인한다.** 전 세계를 상대하는 서비스라도 그 관리 층은 한 지역에만 있을 수 있고, 그 지역이 흔들리면 관리가 통째로 멈춘다.

## 📝 정리

**"새로 만드는 길과 이미 만든 게 일하는 길"** 이라고 읽으면 된다. 바꾸는 층은 값이 어긋나지 않는 쪽을, 나르는 층은 언제나 답하는 쪽을 노려서 부품 수와 고장 확률이 애초에 다르다. 그래서 복구 계획은 새로 만드는 동작을 줄이고 이미 있는 것으로 버티게 짜는 것이 원칙이다.

## 🧒 열 살에게

놀이공원에는 새 기구를 세우고 고치는 사무실이 따로 있고, 사람을 태우고 도는 기구가 또 따로 있지? 사무실이 문을 닫아도 이미 돌고 있는 기구는 그대로 돌아. 그래서 사람이 갑자기 몰릴 때는 사무실에 새 기구를 만들어 달라고 하는 것보다 이미 돌고 있는 쪽으로 보내는 게 훨씬 안전해.

## ❓ 이해했는지

- 무너지는 중에 새 기계를 띄워 달라는 방법이 가장 잘 실패하는 이유는 무엇인가 → 해결하는 문제
- 삭제를 막는 잠금을 걸어 뒀는데 안의 내용이 지워지는 일은 왜 생기나 → 흔한 오해
- 갑자기 몰릴 때 노드가 아니라 파드를 늘리라는 말은 무슨 뜻인가 → 작동 원리
