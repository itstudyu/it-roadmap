# Cloud Security Posture Management (클라우드 보안 자세 관리)

## 📝 정의

Cloud Security Posture Management는 **잘못 잠긴 곳을 계속 찾아내는 일**이다.

Microsoft 문서는 이것을 "클라우드 자산과 작업의 보안 상태를 끊임없이 보여 주고 자세를 개선할 실행 가능한 안내를 주는 것" 으로 적고, 하는 일을 "정해진 보안 기준에 견주어 계속 평가하고 잘못된 설정과 위험을 줄이도록 권고를 내는 것" 으로 적는다. 공격을 잡는 장치가 아니라 **열어 둔 곳을 세는 장치**다.

### 이름
Cloud :: 빌려 쓰는 남의 기계
Security :: 안전하게 지키기
Posture :: 지금 취한 자세
Management :: 계속 살펴 고치기
= 붙여 읽으면 "빌려 쓰는 곳이 지금 어떤 자세인지 계속 살펴 고치기"

### 비유
집을 나서기 전 창문·가스·현관을 한 바퀴 돌아보는 점검. 다만 방이 백 개면 사람 손으로는 못 돈다.

### 예
저장통을 새로 만들면서 공개 설정을 무심코 켜 두었고, 그대로 몇 달이 지나 있던 그 상황이다.

### 직접
폰 설정에서 앱마다 위치와 사진 권한이 어떻게 열려 있는지 훑어보라. 쓰지도 않는 앱에 열려 있는 것이 꼭 하나쯤 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 자세는 어떻게 재고 어떻게 되돌리나
자산 긁기 :: 계정마다 무엇이 있는지 전부 모아 온다
기준 견줌 :: 정해 둔 안전 기준표와 하나씩 맞춰 본다
어긋난 것 :: 권고 목록으로 나온다. 점수도 같이 나온다
줄 세우기 :: 밖에 열려 있고 중요한 것부터 위로 올린다
@ 다시 긁기 :: 고친 뒤 또 모아 온다. 설정은 계속 바뀐다
= 한 번 점검하고 끝나는 일이 아니라 설정이 바뀔 때마다 다시 재는 일이다
```

## ⚠️ 해결하는 문제

```도해
대조: 설정을 계속 안 보면 무엇이 달라지나
안 보면 || 계속 보면
열린 곳 :: 사고 나서 안다 || 그날 목록에 뜬다
계정이 늘면 :: 손으로 못 따라간다 || 같은 잣대로 잰다
고칠 순서 :: 감으로 정한다 || 위험한 것부터
= 뚫려서 나는 사고보다 열어 둔 채로 나는 사고를 겨누는 장치다
```

클라우드에서 자원을 만드는 일은 버튼 한 번이다. 그 버튼에는 "공개" 를 켜는 자리, 아무 데서나 들어오게 여는 자리, 기록을 안 남기는 자리가 같이 달려 있다. 계정이 셋이고 팀이 열이면 그런 자리가 하루에도 수십 개씩 생긴다. 문제는 **잘못 열린 자리가 아무 소리도 안 낸다**는 것이다. 잘 돌아가고, 아무도 불평하지 않고, 그래서 발견되는 시점은 대개 사고가 난 뒤다.

보안 자세 관리는 그 침묵을 목록으로 바꾼다. 사람이 도는 대신 **기준표에 견주어 기계가 돈다.** AWS 문서는 이 기준표로 AWS 기초 보안 모범 사례(FSBP)와 CIS · PCI DSS · NIST 같은 바깥 규격을 들고, 규격마다 여러 개의 통제(control)가 있으며 통제마다 검사를 돌려 결과를 낸다고 적는다. Microsoft 문서는 그 결과를 점수 하나로 모아 "점수가 높을수록 확인된 위험이 낮다" 는 눈금으로 쓴다.

## ⚙️ 작동 원리

세 걸음이 계속 돈다. **모으기** — 계정과 프로젝트에 무엇이 있는지 자산 목록을 만든다. 이게 없으면 세는 대상 자체가 없다. **견주기** — 자산의 설정을 기준표와 맞춰 어긋난 것을 권고로 낸다. **줄 세우기** — 권고가 수천 개 나오면 그 목록은 안 읽힌다.

세 번째 걸음이 이 도구들의 실제 값어치다. Microsoft 문서는 유료 단계에서만 되는 기능으로 **공격 경로 분석**과 **위험 우선순위 매기기**, **인터넷 노출 분석**을 든다. 열린 자리 하나가 위험한지 아닌지는 그 자리만 봐서는 모른다. 밖에서 닿을 수 있고, 그 안에 중요한 것이 있고, 거기서 권한이 더 큰 곳으로 이어질 때 위험해진다. Google 문서도 같은 자리를 "잘못된 설정, 밖에 공개된 자원, 새어 나간 자격 증명" 을 함께 찾아내는 일로 적는다.

**돌아가는 값은 대개 남의 도구가 대준다.** AWS 문서는 대부분의 통제 검사가 AWS Config 의 규칙으로 돌기 때문에 Config 를 켜고 자원을 기록해 두지 않으면 검사 결과 자체가 안 나온다고 적는다. 켜 두는 것만으로 끝나지 않는다는 뜻이다.

## 📊 비교: 세 클라우드는 이 일을 무엇이라 부르나

| | AWS | Azure | Google |
|---|---|---|---|
| 이름 | Security Hub CSPM | Defender for Cloud 의 CSPM | Security Command Center |
| 기준표 | FSBP · CIS · PCI DSS · NIST | Microsoft 클라우드 보안 벤치마크(MCSB) | 자세를 정의해 배포하고 어긋남을 본다 |
| 점수 | 보안 점수 | 보안 점수(secure score) | 위험 기준으로 정리한 발견 항목 |
| 남의 클라우드도 보나 | Azure 연동 항목이 따로 있다 | Azure · AWS · GCP 를 한 화면에 | 엔터프라이즈 단계에서 AWS · Azure 연결 |
| 자동 처리 | 자동화 규칙 · EventBridge | 워크플로 자동화 · 거버넌스 규칙 | BigQuery · Pub/Sub 로 내보내기 |
| 공짜로 되는 데까지 | 30일 시험 뒤 유료 | 기초 CSPM 은 무료, 공격 경로 분석은 유료 | 단계별로 갈린다 |

세 이름이 다 다르고 화면도 다르지만 묻는 것은 같다 — **지금 열려 있는 곳이 어디이고, 그중 무엇부터 닫아야 하나.** 시험 문제가 "여러 계정의 설정을 한 화면에서 규격에 맞춰 보려면 무엇을 쓰나" 로 물으면 그 클라우드의 이 자리에 있는 이름이 답이다.

## 💡 실제 사례

- **계정이 늘어날 때** — 팀마다 계정을 하나씩 파 주면 잣대가 팀 수만큼 생긴다. 자세 관리는 그 위에 같은 기준표 하나를 덮는다.
- **규격 감사 준비** — CIS 나 PCI DSS 같은 규격을 사람이 항목별로 확인하던 일을 통제 검사 결과로 대신한다. 못 지킨 항목이 목록으로 남는다.
- **밖에 열린 것부터 닫기** — 권고가 수천 개면 순서가 곧 전략이다. 인터넷에서 닿을 수 있고 중요한 자원부터 위로 올린다.

## 🚫 흔한 오해

- **켜 두면 공격을 막아 준다** — 막는 장치가 아니다. 열린 곳을 세어 목록으로 주고, 닫는 일은 사람이나 따로 붙인 자동 처리가 한다.
- **점수가 높으면 안전하다** — 점수는 기준표에 있는 항목만 센다. 기준표에 없는 우리 회사만의 규칙은 세지 않고, 안 세는 것은 점수에 안 나온다.
- **이것만 있으면 보안 도구는 더 필요 없다** — 자세를 재는 일과 지금 벌어지는 공격을 잡는 일은 다른 일이다. Google 문서도 잘못된 설정을 찾는 자리와 악성 코드·침입을 탐지하는 자리를 따로 적는다.

## 📝 정리

**"열어 둔 곳을 계속 세어 주는 그 목록"** 이라고 읽으면 된다. 공격을 막는 장치가 아니라 설정이 기준에서 얼마나 어긋났는지를 재는 장치이고, 그래서 값어치는 찾아내는 데보다 **무엇부터 닫을지 줄 세우는 데** 있다. 설정은 계속 바뀌므로 한 번 점검한 결과는 그날까지만 유효하다.

## 🧒 열 살에게

집을 나설 때 창문이 열려 있진 않은지, 가스는 잠갔는지 한 바퀴 돌아보지? 방이 백 개면 사람이 다 못 도니까, 대신 돌면서 열린 곳을 적어 주는 사람을 두는 거야. 그 사람은 적어 줄 뿐이라 잠그는 건 결국 네가 해야 해.
