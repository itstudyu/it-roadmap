# Serverless (서버리스)

## 📝 정의

Serverless는 **서버를 직접 띄우지 않고 함수만 올려 실행하는 방식**이다.

서버는 여전히 있지만 내가 관리하지 않는다. 요청이 오면 클라우드가 알아서 실행하고, 요청이 없으면 아무것도 돌지 않아서 비용도 들지 않는다.

### 비유
택시와 자가용. 자가용은 안 타도 보험료와 주차비가 나가지만 택시는 탄 만큼만 낸다. 대신 부를 때마다 잡히기까지 잠깐 기다린다.

### 예
오랜만에 여는 서비스에서 첫 요청만 유난히 느리고 두 번째부터 멀쩡한 적이 있다. 그 첫 한 번이 실행할 자리를 새로 만드는 시간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 요청 하나가 함수를 어떻게 깨우나
사용자 :: API 주소로 요청을 보낸다
클라우드 :: 지금 떠 있는 실행 환경이 있나 본다
클라우드 :: 없으면 새로 만든다. 여기서 시간이 걸린다
< 함수 :: 코드가 실행되고 결과를 돌려준다
클라우드 :: 잠시 살려뒀다가 요청이 없으면 지운다
= 요청이 없을 때 아무것도 안 도는 것이 이 방식의 값어치이자 약점이다
```

## ⚠️ 해결하는 문제

```도해
대조: 하루 몇 번만 쓰는 API 를 어떻게 운영하나
서버 상시 운영 || 서버리스
요청 없을 때 :: 계속 돈다. 돈이 나간다 || 안 돈다. 0원
갑작스런 몰림 :: 서버를 미리 늘려야 || 알아서 늘어난다
운영 :: OS 패치, 모니터링 || 클라우드가 맡는다
= 트래픽이 들쭉날쭉할수록 이득이 커진다
```

트래픽이 일정하지 않은 서비스에서 서버를 상시 띄우는 것은 낭비다. 하루 열 번 쓰는 관리자용 API를 위해 서버 한 대가 24시간 돌아간다.

반대로 갑자기 몰릴 때는 미리 늘려두지 않으면 못 견딘다. 언제 몰릴지 모르니 넉넉히 잡아두게 되고, 그 여유분이 대부분의 시간 동안 논다.

서버리스는 이 양쪽을 없앤다. 쓰는 만큼만 내고 몰리면 알아서 늘어난다.

## ⚙️ 작동 원리

가장 중요한 성질은 **상태를 들고 있지 않다**는 것이다. 실행이 끝나면 환경이 사라질 수 있어서, 메모리나 로컬 파일에 뭔가를 저장해두면 다음 호출에서 없다.

그래서 서버리스에 올리는 것은 함수 코드뿐이다. 상태와 데이터는 반드시 바깥, 곧 DB 나 오브젝트 스토리지에 둔다. 사용자가 올린 파일도 로컬 디스크가 아니라 스토리지로 보낸다. 함수는 매번 처음 켜진 것처럼 굴어야 안전하다.

첫 호출이 느린 현상을 콜드 스타트라고 한다. 실행 환경을 새로 만드느라 수백 밀리초에서 몇 초가 걸리고, 한동안 안 쓰이면 다시 그 상태로 돌아간다.

## 💡 실제 사례

- **이미지 변환** — 파일이 업로드되면 함수가 깨어나 썸네일을 만들고 끝난다.
- **웹훅 처리** — 결제 알림처럼 언제 올지 모르는 요청을 받는다.
- **정기 작업** — 매일 새벽에 한 번 도는 집계 작업을 위해 서버를 둘 이유가 없다.

## 🚫 흔한 오해

- **서버가 없다** — 있다. 내가 관리하지 않을 뿐이다. 이름 때문에 생기는 대표적인 오해다.
- **항상 더 싸다** — 요청이 꾸준히 많으면 상시 서버가 더 싸다. 서버리스가 유리한 건 들쭉날쭉하거나 드문 경우다.
- **아무 워크로드나 올릴 수 있다** — 실행 시간 상한이 있고 상태를 못 들고 있어서, 오래 도는 작업이나 연결을 유지하는 작업에는 안 맞는다.

## 🚨 주의사항

- **콜드 스타트를 사용자 경험에 넣고 계산한다.** 사용자가 기다리는 화면 앞단에 두면 첫 요청이 느리다.
- **DB 연결 수를 조심한다.** 함수가 동시에 수백 개 뜨면 각자 연결을 열어 DB가 먼저 죽는다. 연결 풀을 앞에 둬야 한다.

## 📝 정리

Serverless는 서버 관리를 넘기고 실행한 만큼만 내는 방식이다. 트래픽이 들쭉날쭉할수록 유리하고, 상태를 들고 있을 수 없다는 제약이 설계를 정한다.

## ❓ 이해했는지

- 요청이 꾸준히 많은 서비스에서 서버리스가 더 비쌀 수 있는 이유는 → 흔한 오해
- 함수 안에서 파일을 만들어 다음 호출에 쓰려 하면 무엇이 문제인가 → 작동 원리
- 함수가 동시에 수백 개 떴을 때 DB가 먼저 죽는 이유는 → 주의사항
