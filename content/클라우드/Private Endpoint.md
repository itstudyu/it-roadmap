# Private Endpoint (사설 접점)

## 📝 정의

Private Endpoint 는 **바깥 서비스를 내 망 안 주소로 끌어들이는 입구**다.

클라우드가 파는 저장통이나 데이터베이스는 대개 인터넷에 열린 이름 하나로 나온다. 열쇠가 있어야 열리긴 하지만, 문 자체는 전 세계 아무 데서나 두드릴 수 있는 자리에 서 있다. 사설 접점은 그 문을 **내 망 안쪽에 다시 내는 일**이다. 이름은 그대로 두고, 그 이름이 가리키는 주소만 내 망 안의 사설 주소로 바꿔 끼운다.

### 이름
Private :: 바깥엔 안 열린
End :: 끝
Point :: 점
= 붙여 읽으면 "바깥엔 안 열린 끝점". 그 끝점이 내 망 안의 사설 주소다

### 비유
회사 건물 안에 낸 은행 창구. 같은 은행인데 길 건너 지점까지 나갈 일이 없고, 길에 서 있는 사람은 그 창구가 있는 줄도 모른다.

### 예
보안 심사에서 "이 저장통이 인터넷에서 보이나요" 라는 한 줄에 답하지 못해 결재가 멎던 그 자리다.

## 🖼️ 그림으로 보기

```도해
흐름: 사설 접점을 두면 요청은 어디로 가나
앱 :: 저장통 이름을 평소처럼 그대로 부른다
이름 풀이 :: 공인 주소 대신 사설 주소를 돌려준다
사설 접점 :: 내 망의 한 칸에 꽂힌 랜카드 한 장
제공자 망 :: 인터넷을 안 거치고 그 안에서 간다
< 앱 :: 같은 이름 · 같은 응답. 밖에 나간 적이 없다
= 이름은 그대로 두고 그 이름이 가리키는 주소만 안쪽으로 바꾼 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 공인 주소로만 닿을 수 있으면 무엇이 걸리나
공인 주소로 || 사설 접점으로
가는 길 :: 인터넷을 거친다 || 안에서 끝난다
막는 방법 :: 주소 목록 관리 || 아예 안 연다
새 나갈 때 :: 어디로든 나간다 || 그 하나만 닿는다
= 자물쇠를 잘 채우는 문제가 아니라 문을 바깥에 안 내는 문제다
```

공인 주소로 열린 문을 안전하게 만드는 길은 하나뿐이다 — 들어와도 되는 주소 목록을 적어 두고 계속 손보는 것. 그런데 그 목록은 사무실이 늘거나 재택이 늘거나 협력사가 붙을 때마다 길어지고, 한 줄만 잘못 적어도 전 세계가 문 앞에 선다. 게다가 안에서 밖으로 나가는 길이 열려 있으면, 열쇠를 손에 넣은 쪽이 **내 저장통이 아닌 남의 저장통으로** 자료를 실어 낼 수도 있다.

사설 접점은 문제를 다른 자리로 옮긴다. AWS 문서는 이 방식을 두고 인터넷 관문도, 주소 변환 장치도, 공인 주소도, 전용선도 없이 붙는다고 적고, 그래서 "내 망에서 닿을 수 있는 것이 무엇인지 내가 정하게 된다" 고 쓴다. 목록을 잘 적는 문제가 아니라 **문을 바깥에 안 내는 문제**로 바뀐 것이다. Azure 문서도 접점이 승인된 상태일 때만 통신이 되고, 연결은 손님 쪽에서만 걸 수 있으며 서비스 쪽에서 내 망으로 들어오는 길은 없다고 못 박는다.

## 📊 비교: 같은 물건을 세 곳은 뭐라 부르나

| 하는 일 | AWS | Azure | Google Cloud |
|---|---|---|---|
| **내 망 안에 사설 주소를 꽂는다** | 인터페이스 VPC 엔드포인트 (PrivateLink) | Private Endpoint | Private Service Connect 엔드포인트 |
| **내가 만든 것을 남에게 사설로 판다** | 엔드포인트 서비스 (앞에 로드밸런서 필요) | Private Link service | 서비스 어태치먼트 |
| **경로표만 고쳐 붙이는 값싼 길** | 게이트웨이 엔드포인트 (S3·DynamoDB 전용) | 없다 | 없다 |
| **연결을 허락하는 방식** | 제공자가 수락·거절 | 자동 승인 또는 수동 승인 | 명시적 허가 |

고르는 기준은 **값**과 **닿을 범위**다. AWS 의 게이트웨이 엔드포인트는 경로표에 한 줄을 더하는 방식이라 시간당 값도 데이터 값도 안 붙지만 S3 와 DynamoDB 에만 있고, 같은 리전 안에서만 쓰이며, 다른 망에서 빌려 쓸 수 없다. 인터페이스 엔드포인트는 랜카드가 실제로 꽂히므로 시간당 값과 오간 양만큼의 값이 붙는 대신 거의 모든 서비스에 붙고, 망을 맞대 놓았거나 전용선·터널로 이어진 사무실에서도 그 사설 주소로 닿는다.

## 💡 실제 사례

- **저장통을 인터넷에서 지운다** — 접점을 꽂은 뒤 그 서비스의 공인 접근을 아예 끈다. 접점을 꽂는 것만으로 바깥 문이 닫히지는 않아서, Azure 문서도 접근 제어를 따로 걸라고 적는다.
- **협력사에게 한 서비스만 판다** — 망을 통째로 맞대지 않고 내 서비스 하나만 접점으로 내준다. 상대는 내 망의 다른 것에 닿지 못하고, 연결마다 수락·거절을 내가 쥔다.
- **사무실에서 사설 주소로 닿는다** — 전용선이나 터널로 이어 둔 사무실이 같은 이름을 부르면 같은 사설 주소가 나온다. 사무실마다 공인 주소를 허용 목록에 넣고 다닐 일이 없어진다.

## 🚫 흔한 오해

- **접점을 꽂으면 바깥 문이 닫힌다** — 아니다. Azure 문서는 사설 접점이 사설 주소를 하나 주는 것일 뿐 공인 접근을 반드시 막지는 않는다고 적는다. 바깥 문은 따로 잠가야 한다.
- **무조건 접점을 붙이는 쪽이 낫다** — 접점 하나마다 시간당 값과 오간 양만큼의 값이 붙고, 이름 풀이를 사설 쪽으로 따로 손봐야 한다. S3 처럼 게이트웨이로 공짜로 끝나는 자리에 인터페이스를 꽂으면 값만 는다.
- **접점을 꽂으면 저쪽에서도 내 망에 들어올 수 있다** — 아니다. 연결은 한 방향뿐이다. Azure 문서는 서비스 쪽에 내 망으로 오는 경로 설정 자체가 없다고 적는다.

## 🚨 주의사항

- **이름 풀이가 반이다.** 같은 이름이 안에서는 사설 주소로, 밖에서는 공인 주소로 풀려야 한다. Azure 는 사설 영역을 따로 두라고 적고, AWS 도 사설 호스팅 영역으로 같은 이름을 안팎에서 다르게 풀 수 있다고 적는다. 여기를 빠뜨리면 접점은 꽂혀 있는데 요청은 계속 밖으로 나간다.
- **하위 대상마다 따로 꽂아야 한다.** Azure 는 저장 계정의 파일과 블롭에 각각 접점이 필요하다고 못 박는다. 하나 꽂았다고 그 서비스 전부가 안으로 들어오지는 않는다.
- **수동 승인이면 기다려야 한다.** 권한이 없어 수동으로 요청하면 상대가 수락할 때까지 접점은 대기 상태로 서 있고, 그동안 통신은 안 된다.

## 📝 정리

**"바깥에 있던 문을 내 망 안쪽에 다시 낸 것"** 이라고 읽으면 된다. 이름은 그대로 두고 그 이름이 가리키는 주소만 사설 주소로 바꾸는 일이라, 이름 풀이를 안 고치면 아무것도 달라지지 않는다. 그리고 안쪽 문을 냈다고 바깥 문이 저절로 닫히지는 않으니 그건 따로 잠가야 한다.

## 🧒 열 살에게

네가 사는 아파트 안에 은행 창구가 하나 생겼다고 해 봐. 이제 큰길을 건너 지점까지 안 나가도 되고, 길에 서 있는 사람은 그런 창구가 있는 줄도 몰라. 대신 아파트 안내판을 안 고쳐 두면 사람들은 계속 큰길로 나가.

## 🔗 관련 용어

- [[VPC]] — 사설 주소를 꽂아 넣을 내 망 그 자체
- [[Subnet]] — 접점의 랜카드가 실제로 앉는 칸
- [[DNS]] — 같은 이름을 안팎에서 다르게 풀어 주는 장치
- [[Security Group]] — 접점에 닿을 수 있는 쪽을 다시 한 번 좁히는 자리
- [[Egress Cost]] — 인터넷으로 안 나가면서 함께 줄어드는 값
