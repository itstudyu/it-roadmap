# Cost Allocation Tag (비용 배분 꼬리표)

## 📝 정의

Cost Allocation Tag 는 자원마다 붙여 **청구서를 나눠 보는 이름표**다.

키와 값 한 쌍(`팀=결제`)으로 자원에 붙는다. AWS 는 이것을 비용 배분 태그, Azure 는 그냥 태그, Google Cloud 는 라벨이라 부른다. 같은 물건인데 셋의 한도와 규칙이 조금씩 다르고, 특히 "붙였다" 와 "청구서에 나온다" 가 같은 말이 아니라는 점이 셋 다 걸리는 자리다.

### 이름
Cost :: 값
Allocation :: 나눠 붙이기
Tag :: 이름표
= 붙여 읽으면 "값을 나눠 붙이는 이름표". 이름이 곧 하는 일이다

### 비유
여러 식구가 같이 쓰는 냉장고에서 반찬통마다 붙여 둔 이름 스티커.

### 예
클라우드 요금 고지서에 큰 숫자 한 줄만 찍혀 있고, 어느 팀이 얼마를 썼는지 아무도 답을 못 하던 그 회의다.

### 직접
휴대폰 요금 명세서를 열어 항목별로 나뉜 줄을 보라. 총액 한 줄만 있었다면 무엇을 줄일지 정할 수 없다.

## 🖼️ 그림으로 보기

```도해
흐름: 요금이 팀별로 갈려 나오기까지 무엇을 거치나
자원 :: 만들 때 `팀=결제` 같은 이름표를 단다
이름표 :: 키와 값 한 쌍으로 그 자원에 붙는다
활성화 :: 청구 화면에서 그 키를 따로 켠다
청구 자료 :: 켠 키가 표의 열 하나로 생긴다
읽는 사람 :: 팀별로 갈린 금액을 그 열에서 본다
= 붙이는 일과 켜는 일은 다르다. 켜야 청구서에 열이 생긴다
```

## ⚠️ 해결하는 문제

```도해
대조: 이름표가 없으면 요금 고지서에서 무엇을 못 하나
이름표 없이 || 이름표를 붙이면
누가 썼나 :: 총액만 보인다 || 팀별로 갈린다
줄일 자리 :: 짐작으로 고른다 || 큰 것부터 짚는다
새는 자원 :: 주인이 없다 || 주인이 적혀 있다
= 나뉘지 않은 숫자는 아무도 자기 것으로 여기지 않는다
```

클라우드 요금은 한 계정 안에서 수천 개의 자원이 뒤섞여 한 덩어리로 나온다. 그 덩어리를 놓고 "이번 달에 왜 늘었나" 를 물으면 아무도 답할 수 없고, 답할 수 없으면 아무도 줄이지 않는다. 자원을 만든 사람과 요금을 받는 사람이 다른 순간부터 이 문제가 시작된다.

꼬리표는 **자원 하나하나에 주인과 용도를 미리 적어 두는 일**이다. AWS 는 켜 둔 꼬리표 키를 청구 자료의 열로 만들어 주고, 태그가 붙지 않은 자원까지 같은 보고서에 함께 담아 총액이 청구서와 맞아떨어지게 한다. 그래서 이 자료 하나로 "누가" 와 "얼마나" 가 동시에 나온다.

다만 이건 **미리 해 두는 일**이지 나중에 하는 일이 아니다. AWS 문서는 꼬리표를 만들기 전에 만들어진 자원에는 꼬리표가 붙지 않는다고 못 박고, 켠 뒤에도 화면에 나타나기까지 최대 하루가 걸린다고 적는다. 이번 달 고지서를 보고 놀라서 붙이기 시작하면, 그 달은 이미 늦었다.

## 📊 비교: 같은 물건을 세 곳은 각각 뭐라고 부르나

| 어디 | 부르는 이름 | 알아 둘 한도와 규칙 |
|---|---|---|
| **AWS** | Cost Allocation Tag (비용 배분 태그) | 붙인 뒤 청구 화면에서 따로 **켜야** 열이 생긴다. `aws:` 는 예약 접두사, 사용자가 붙인 것은 보고서에서 `user:` 로 나온다 |
| **Azure** | Tag (태그) | 자원·자원 그룹·구독에 붙는다. 자원 하나당 50쌍, 키 512자·값 256자. **자원 그룹의 태그를 안쪽 자원이 물려받지 않는다** |
| **Google Cloud** | Label (라벨) | 자원 하나당 64개, 키·값 각 63자. 청구 자료로 넘어가 요금을 쪼갠다. 같은 곳의 Tag 는 이름만 같고 정책 조건을 거는 다른 물건이다 |

세 곳 다 "키와 값 한 쌍" 이라는 뼈대는 같다. 갈리는 건 **누가 자동으로 물려주느냐**와 **따로 켜야 하느냐** 둘이다. 시험 문제와 실무 사고가 나는 자리도 거의 그 둘이다.

## 💡 실제 사례

- **부서별 정산** — `팀`, `환경`, `제품` 세 키를 표준으로 정하고 전 자원에 강제한다. 월말에 고지서가 그대로 부서별 표가 된다.
- **주인 없는 자원 찾기** — 꼬리표가 안 붙은 자원만 골라 목록을 뽑는다. 대개 그 목록이 쓰지도 않으면서 돈만 먹는 자원 목록이다.
- **예산 알림 걸기** — 팀 꼬리표별로 한도를 걸어 두면, 총액이 터지기 전에 어느 팀이 넘겼는지가 먼저 온다.

## 🚫 흔한 오해

- **꼬리표를 붙였으니 지난달 요금도 갈려서 나온다** — 아니다. AWS 문서는 꼬리표를 만들기 전에 만들어진 자원에는 꼬리표가 붙지 않는다고 적는다. 갈리는 건 붙이고 켠 뒤의 사용분부터다.
- **자원 그룹에 붙였으니 안쪽 자원도 물려받는다** — Azure 문서는 자원이 자원 그룹이나 구독의 태그를 상속하지 않는다고 못 박는다. 물려주고 싶으면 정책으로 따로 찍어야 한다.
- **꼬리표에는 아무 말이나 적어도 된다** — AWS 와 Azure 문서 둘 다 꼬리표에 민감한 값을 넣지 말라고 경고한다. 평문으로 저장되고 요금 보고서·배포 이력·감사 기록에 그대로 실려 나간다.

## 🚨 주의사항

- **키 이름을 먼저 정하고 시작한다.** `team`, `Team`, `팀` 이 섞이면 열이 셋으로 갈라진다. Azure 는 키의 대소문자를 구분하지 않고 처리하지만 요금 보고서에는 처음 적은 그대로 보인다.
- **켜는 것은 관리 계정만 할 수 있다.** AWS 는 조직의 관리 계정과 조직에 속하지 않은 단독 계정만 비용 배분 태그 화면에 들어갈 수 있다고 적는다.
- **손으로 붙이면 반드시 빠진다.** 자원을 만드는 자리에서 꼬리표 없이는 못 만들게 막는 편이 낫다. Azure 는 그 목적의 태그 정책을 따로 둔다.

## 📝 정리

**"청구서를 팀별로 가르는 그 이름표"** 라고 읽으면 된다. 붙이는 일과 청구 화면에서 켜는 일은 다르고, 켜기 전의 사용분은 되돌려 가를 수 없다. 그래서 이건 요금이 놀라운 달에 시작하는 일이 아니라 자원을 만드는 첫날에 정해 두는 일이다.

## 🧒 열 살에게

여럿이 같이 쓰는 냉장고에 반찬통을 넣을 때 이름을 안 적으면, 자리가 꽉 찼을 때 누구 걸 빼야 할지 아무도 몰라. 그래서 넣는 그 순간에 이름을 적어 붙여 두는 거야. 나중에 붙이려고 하면 이미 들어가 있던 통들은 여전히 주인이 없어.
