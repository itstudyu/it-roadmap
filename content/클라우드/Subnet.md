# Subnet (서브넷)

## 📝 정의

서브넷은 Subnet의 약자로, VPC(Virtual Private Cloud) 또는 IP 네트워크를 더 작은 논리적 네트워크 단위로 분할한 것을 의미합니다. 원래의 거대한 IP 주소 범위를 여러 개의 작은 범위로 나누어서, 각 범위가 별도의 네트워크처럼 동작하게 하는 기술입니다. 예를 들어 VPC의 IP 범위가 10.0.0.0/16이라면, 이를 10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24 같은 여러 서브넷으로 나눌 수 있습니다.

서브넷은 CIDR(Classless Inter-Domain Routing) 표기법을 사용하여 표현됩니다. CIDR의 숫자는 네트워크 비트 수를 나타내므로, /24는 /16보다 더 작은 네트워크를 의미합니다. 각 서브넷은 특정 가용 영역(Availability Zone)에 속하므로, 여러 서브넷을 여러 가용 영역에 배치하면 자동으로 고가용성 아키텍처를 구축할 수 있습니다. 서브넷은 현대 클라우드 아키텍처의 기초이며, 보안, 성능, 관리 측면에서 네트워크를 체계적으로 구조화할 수 있게 합니다.

### 한 줄 요약
> 큰 네트워크를 더 작은 관리 가능한 단위로 나누되, 각 단위가 특정 가용 영역에 속하는 논리적 네트워크 분할

### 비유
- 🔵 **비유 1**: 도시를 구(區)로 나누는 것처럼, VPC라는 도시를 여러 지역(서브넷)으로 나누어 관리합니다. 각 지역의 도로(네트워크)는 독립적으로 작동하면서도 도시 전체가 연결되어 있습니다.
- 🟡 **비유 2**: 회사의 건물을 층으로 나누는 것과 같습니다. 각 층(서브넷)은 자신의 주소, 복도(라우팅), 방문자 출입 규칙(보안)을 가집니다.
- 🟢 **비유 3**: 대학 캠퍼스를 단과대학별로 나누는 것처럼, 캠퍼스(VPC) 내에서 단과대학(서브넷)마다 별도의 영역을 할당하고 관리합니다.

## 🎯 핵심 개념

### 1. CIDR 표기법과 IP 주소 계산
CIDR는 IP 주소와 함께 슬래시 뒤에 숫자를 붙여서 네트워크 주소 범위를 표현합니다. 예를 들어 10.0.1.0/24는 10.0.1.0부터 10.0.1.255까지 256개의 IP 주소를 가진 네트워크를 의미합니다. 여기서 /24는 첫 24비트가 네트워크 주소(고정)이고, 나머지 8비트가 호스트 주소(변수)라는 뜻입니다. 더 큰 네트워크일수록 숫자가 작으므로, /16은 /24보다 큽니다. /16은 65,536개(2^16)의 주소를 가지고, /24는 256개(2^8)의 주소를 가집니다. 실제로 사용 가능한 호스트 주소는 이에서 네트워크 주소와 브로드캐스트 주소 2개를 빼야 하므로, /24 서브넷의 경우 256-2 = 254개의 호스트를 수용할 수 있습니다.

### 2. 퍼블릭 서브넷과 프라이빗 서브넷의 구분
서브넷은 인터넷 접근 여부에 따라 두 가지로 구분됩니다. 퍼블릭 서브넷은 인터넷 게이트웨이(IGW)로 직접 라우팅되는 라우팅 테이블을 가지고 있어서, 이 서브넷 내의 리소스가 인터넷으로부터 직접 요청을 받을 수 있습니다. 웹 서버, API 서버, 로드 밸런서 같은 외부에 노출되어야 하는 서비스가 퍼블릭 서브넷에 배치됩니다. 프라이빗 서브넷은 NAT 게이트웨이나 VPN 경유로만 인터넷과 통신하는 라우팅 테이블을 가지고 있어서, 외부에서 직접 접근할 수 없습니다. 데이터베이스, 백엔드 애플리케이션, 캐시 서버 같은 내부 서비스가 프라이빗 서브넷에 배치됩니다.

### 3. 가용 영역과 서브넷의 관계
AWS에서는 각 서브넷이 정확히 하나의 가용 영역(Availability Zone)에 속합니다. 예를 들어 서울 리전(ap-northeast-2)에는 ap-northeast-2a, 2b, 2c, 2d 4개의 가용 영역이 있으므로, 같은 VPC 내에서 최대 4개의 서브넷을 만들 수 있고 각각을 다른 가용 영역에 배치할 수 있습니다. 고가용성을 위해서는 보통 각 가용 영역에 하나씩 퍼블릭 서브넷과 프라이빗 서브넷을 만듭니다. 이렇게 하면 한 가용 영역에 장애가 발생해도 다른 가용 영역의 리소스가 자동으로 서비스를 계속할 수 있습니다.

### 4. 서브넷 내 예약된 IP 주소
각 서브넷 내에서 5개의 IP 주소는 AWS가 예약하여 사용할 수 없습니다. 10.0.1.0/24 서브넷의 경우, 10.0.1.0(네트워크 주소), 10.0.1.1(VPC 라우터), 10.0.1.2(DNS 서버), 10.0.1.3(향후 사용), 10.0.1.255(브로드캐스트 주소)가 예약됩니다. 따라서 256개의 주소 중 5개를 빼면 251개가 아니라, 브로드캐스트 주소를 제외한 4개를 빼서 252개가 됩니다. 하지만 실무에서는 보통 "256개 중 약 250개 사용 가능"으로 간단히 계산합니다. 이를 감안하여 서브넷 크기를 계획해야 하므로, 필요한 IP 주소 수보다 충분히 큰 서브넷을 선택하는 것이 좋습니다.

## ⚠️ 해결하는 문제

### 문제 1: 거대한 네트워크의 관리 불가능성
VPC의 IP 범위를 10.0.0.0/16(65,536개 주소)으로 설정했다면, 이를 하나의 네트워크처럼 관리하면 매우 복잡합니다. 모든 리소스가 같은 네트워크에 있으면 보안 정책을 세분화할 수 없고, 특정 리소스 그룹에 대한 라우팅을 별도로 제어할 수 없습니다. 또한 네트워크가 커질수록 브로드캐스트 트래픽이 증가하여 성능이 저하됩니다. 서브넷으로 네트워크를 나누면 각 서브넷을 독립적인 단위로 관리할 수 있으므로, 정책과 라우팅을 체계적으로 구성할 수 있습니다.

### 문제 2: 무분별한 IP 주소 할당과 낭비
서브넷 없이 전체 VPC에 리소스를 배치하면, 각 리소스가 충분한 IP 주소를 차지하므로 IP 주소 공간을 낭비합니다. 예를 들어 웹 서버 3대가 필요한데 /16 네트워크 전체를 사용하면 65,533개의 미사용 IP가 낭비됩니다. 서브넷을 사용하여 웹 서버를 위한 작은 네트워크(예: /27, 30개 주소)를 할당하고, 다른 용도로는 다른 서브넷을 사용하면 IP 주소를 효율적으로 활용할 수 있습니다.

### 문제 3: 장애 영향 범위의 제어 불가
대규모 네트워크에서 네트워크 문제가 발생하면, 영향을 받는 범위를 알기 어렵습니다. 하지만 서브넷으로 나누어져 있으면, 한 서브넷의 문제가 다른 서브넷에 직접 영향을 주지 않습니다. 특히 여러 가용 영역에 걸쳐 서브넷을 배치하면, 한 가용 영역의 장애가 다른 가용 영역에 영향을 주지 않으므로 장애 격리가 가능합니다.

### 문제 4: 보안 정책 적용의 세분화 어려움
전체 VPC에 동일한 보안 정책을 적용하면, 내부 트래픽과 외부 트래픽 모두에 같은 규칙이 적용되어 보안이 약해집니다. 서브넷으로 나누고 각 서브넷에 다른 NACL(Network ACL)을 적용하면, 웹 계층은 외부 트래픽을 허용하고 데이터베이스 계층은 내부 트래픽만 허용하는 식으로 세분화된 보안 정책을 구현할 수 있습니다.

### 문제 5: 고가용성 구현의 어려움
모든 리소스가 하나의 네트워크에 있으면, 그 네트워크가 속한 가용 영역에 장애가 발생했을 때 모든 리소스가 영향을 받습니다. 하지만 여러 가용 영역에 걸쳐 서브넷을 만들고 각 서브넷에 리소스를 배치하면, 자동으로 고가용성 아키텍처를 구축할 수 있습니다. 로드 밸런서가 여러 가용 영역의 서버로 트래픽을 분산하면, 한 가용 영역의 장애는 사용자 경험에 영향을 주지 않습니다.

### 전형적인 3-계층 서브넷 아키텍처

```
VPC: 10.0.0.0/16
│
├─ Availability Zone 1 (ap-northeast-2a)
│  │
│  ├─ Public Subnet (10.0.1.0/24) → Internet Gateway
│  │  └─ EC2 Instance: 웹 서버 (10.0.1.10)
│  │     NAT Gateway (10.0.1.250)
│  │
│  └─ Private Subnet (10.0.11.0/24) → NAT Gateway
│     └─ EC2 Instance: 애플리케이션 (10.0.11.10)
│
├─ Availability Zone 2 (ap-northeast-2b)
│  │
│  ├─ Public Subnet (10.0.2.0/24) → Internet Gateway
│  │  └─ EC2 Instance: 웹 서버 (10.0.2.10)
│  │     NAT Gateway (10.0.2.250)
│  │
│  └─ Private Subnet (10.0.12.0/24) → NAT Gateway
│     └─ EC2 Instance: 애플리케이션 (10.0.12.10)
│
└─ Shared Resource Subnet
   ├─ Database Subnet Group (10.0.21.0/24, 10.0.22.0/24)
   │  └─ RDS Multi-AZ (마스터: 10.0.21.100, 슬레이브: 10.0.22.100)
   │
   └─ Cache Subnet Group (10.0.31.0/24, 10.0.32.0/24)
      └─ ElastiCache Redis (10.0.31.50, 10.0.32.50)
```

## ⚙️ 작동 원리

### 1단계: 서브넷 생성 및 CIDR 블록 할당
관리자가 AWS 콘솔이나 IaC(Infrastructure as Code)를 사용하여 VPC 내에 서브넷을 생성합니다. 이때 VPC의 CIDR 블록 내에서 새로운 CIDR 블록을 선택해야 합니다. 예를 들어 VPC가 10.0.0.0/16이면, 서브넷은 10.0.0.0/24, 10.0.1.0/24, ... 10.0.255.0/24 중 하나를 선택할 수 있습니다. 동시에 서브넷을 배치할 가용 영역을 지정해야 하며, 일단 생성된 후에는 변경할 수 없습니다. 따라서 고가용성을 위해 미리 여러 가용 영역에 서브넷을 생성합니다.

### 2단계: 라우팅 테이블 연결
서브넷을 생성한 후, 라우팅 테이블을 연결합니다. 퍼블릭 서브넷으로 만들려면 인터넷 게이트웨이(IGW)로 라우팅하는 라우팅 테이블을 연결합니다 (예: 0.0.0.0/0 → igw-xxxxxx). 프라이빗 서브넷으로 만들려면 NAT 게이트웨이로 라우팅하는 라우팅 테이블을 연결합니다 (예: 0.0.0.0/0 → nat-xxxxxx). VPC 내부 트래픽(10.0.0.0/16)은 기본 라우팅에 의해 로컬(local)로 라우팅되므로, 따로 설정할 필요가 없습니다.

### 3단계: 네트워크 ACL 설정
각 서브넷에는 기본적으로 기본 NACL이 적용되며, 필요에 따라 커스텀 NACL을 생성하여 적용할 수 있습니다. NACL은 서브넷 경계를 통과하는 모든 트래픽을 제어합니다. 예를 들어 데이터베이스 서브넷의 NACL은 웹 서버 서브넷(10.0.1.0/24)의 3306 포트(MySQL) 요청은 허용하되, 외부 인터넷(0.0.0.0/0)의 요청은 차단하도록 설정할 수 있습니다.

### 4단계: 리소스 배치
서브넷이 준비되면, EC2 인스턴스, RDS 데이터베이스, 캐시 서버 등의 리소스를 각 서브넷에 배치합니다. 각 리소스는 그 서브넷의 CIDR 범위 내에서 IP 주소를 할당받습니다. 퍼블릭 서브넷의 리소스는 추가로 Elastic IP나 공용 IP를 할당받아야 인터넷에 접근할 수 있습니다.

### 5단계: 보안 그룹 설정
각 리소스마다 보안 그룹을 연결하여, 인/아웃바운드 트래픽을 제어합니다. 보안 그룹은 서브넷과 무관하게 인스턴스 수준에서 작동하므로, 같은 서브넷 내의 리소스도 다른 보안 그룹을 가질 수 있습니다. 예를 들어 웹 서버의 보안 그룹은 포트 80과 443을 허용하되, 애플리케이션 서버의 보안 그룹은 웹 서버 보안 그룹에서의 8080 포트 요청만 허용하도록 설정합니다.

### 6단계: 트래픽 흐름 및 라우팅
사용자의 요청이 들어오면, 라우팅 테이블에 따라 경로가 결정됩니다. 인터넷에서 온 요청이 퍼블릭 서브넷의 웹 서버로 들어올 때, 먼저 NACL의 인바운드 규칙을 통과하고, 그 다음 웹 서버 보안 그룹의 인바운드 규칙을 통과합니다. 웹 서버에서 애플리케이션 서버로 통신할 때는 VPC 내부이므로 라우팅 테이블의 로컬 라우팅을 따릅니다. 마지막으로 응답이 돌아올 때도 같은 경로를 역방향으로 따릅니다.

```
요청 흐름:

1. 인터넷 사용자 (203.0.113.50)
   │
   ▼
2. Internet Gateway (공용 IP ↔ 프라이빗 IP 변환)
   │ 요청: 203.0.113.5:80 → 10.0.1.10:80
   ▼
3. Public Subnet NACL (인바운드 확인)
   │ 규칙: 포트 80 허용, 1024~65535 응답 포트 허용
   ▼
4. 웹 서버 보안 그룹 (인바운드 확인)
   │ 규칙: 포트 80 허용
   ▼
5. EC2 웹 서버 (10.0.1.10)
   │ 요청 처리, 애플리케이션 서버로 쿼리 전송
   │ 내부 요청: 10.0.1.10 → 10.0.11.10:8080
   ▼
6. 라우팅 테이블 (VPC 내부 로컬 라우팅)
   │ 목표: 10.0.11.0/24 → 로컬
   ▼
7. Private Subnet NACL (인바운드 확인)
   │ 규칙: 웹 서버 보안 그룹(10.0.1.0/24) 포트 8080 허용
   ▼
8. 애플리케이션 서버 보안 그룹 (인바운드 확인)
   │ 규칙: 웹 서버 보안 그룹 포트 8080 허용
   ▼
9. EC2 애플리케이션 서버 (10.0.11.10)
   │ 요청 처리 및 응답
   ▼
10. 역방향 경로로 응답 반환
```

## ✅ 장점과 단점

### 장점

**1. 네트워크의 체계적 관리**: VPC를 여러 서브넷으로 나누면 각 서브넷을 독립적으로 관리할 수 있습니다. 웹 계층, 애플리케이션 계층, 데이터베이스 계층을 별도의 서브넷으로 구성하면, 각 계층의 설정과 정책을 체계적으로 구성할 수 있습니다.

**2. 향상된 보안**: 서브넷별로 다른 NACL과 보안 그룹을 적용하여 세분화된 보안 정책을 구현할 수 있습니다. 예를 들어 데이터베이스 서브넷은 데이터베이스 포트(3306)만 허용하고 다른 포트는 모두 차단할 수 있습니다.

**3. 효율적인 IP 주소 사용**: 필요한 만큼만의 IP 주소를 할당할 수 있으므로, 전체 VPC 내에서 IP 주소를 낭비하지 않고 효율적으로 배분할 수 있습니다.

**4. 자동 고가용성**: 여러 가용 영역에 걸쳐 서브넷을 배치하고 로드 밸런서를 구성하면, 자동으로 고가용성 아키텍처를 구현할 수 있습니다. 한 가용 영역의 장애 시에도 다른 가용 영역의 리소스가 자동으로 서비스를 계속합니다.

**5. 장애 격리**: 한 서브넷의 문제가 다른 서브넷에 직접 영향을 주지 않으므로, 문제의 영향 범위를 제한할 수 있습니다.

**6. 쉬운 트러블슈팅**: 각 서브넷이 명확한 목적을 가지고 있으므로, 문제가 발생했을 때 어느 서브넷에서 발생했는지 빠르게 파악할 수 있습니다.

### 단점

**1. IP 주소 계획의 복잡성**: 미리 충분한 IP 주소 공간을 계획해야 합니다. 나중에 서브넷을 추가로 만들려면 IP 주소 범위 충돌이 없는지 확인해야 하고, 기존 서브넷을 확대하려면 매우 복잡한 작업이 필요합니다.

**2. 초기 설계 비용**: 적절한 서브넷 크기와 구조를 설계하는 데 시간이 소요됩니다. 잘못된 설계는 나중에 큰 문제가 될 수 있으므로, 초기에 충분한 검토가 필요합니다.

**3. 관리 복잡도 증가**: 여러 서브넷을 관리하면 라우팅 테이블, NACL, 보안 그룹 설정이 복잡해집니다. 관리할 리소스 수가 많아질수록 설정 오류의 가능성도 증가합니다.

**4. 성능 오버헤드**: 트래픽이 여러 라우팅 테이블과 NACL을 통과해야 하므로, 극도로 많은 패킷을 처리하는 상황에서는 약간의 지연이 발생할 수 있습니다. (대부분의 경우 무시할 수 있는 수준)

**5. 마이그레이션 어려움**: 리소스를 다른 서브넷으로 옮기려면 IP 주소가 바뀌므로, 관련 설정과 연결을 모두 수정해야 합니다.

**6. 서브넷 간 통신의 지연**: 같은 VPC이지만 다른 가용 영역의 서브넷과 통신할 때 약간의 네트워크 지연이 발생할 수 있습니다. (일반적으로 1-2ms 수준)

## 💡 실제 사용 사례

### 전자상거래 플랫폼 아키텍처
전자상거래 플랫폼은 VPC를 10.0.0.0/16으로 설정하고, 3개의 가용 영역(a, b, c)에 걸쳐 서브넷을 배치합니다. 각 가용 영역마다 10.0.1.0/24(웹 서버), 10.0.11.0/24(애플리케이션), 10.0.21.0/24(데이터베이스) 서브넷을 만듭니다. 웹 서버 서브넷에는 로드 밸런서를 배치하여 트래픽을 분산합니다. 애플리케이션 서버는 프라이빗 서브넷에 배치하여 인터넷에 직접 노출되지 않게 합니다. 데이터베이스는 또 다른 프라이빗 서브넷에 배치하여 애플리케이션 서버하고만 통신하게 합니다. 한 가용 영역에 장애가 발생해도, 다른 두 가용 영역이 자동으로 트래픽을 처리합니다.

### 멀티 테넌트 SaaS 플랫폼
SaaS 플랫폼 제공업체는 모든 고객을 위한 공유 VPC를 구성합니다. 공유 리소스(로드 밸런서, 웹 서버)는 퍼블릭 서브넷에, 공유 데이터베이스는 프라이빗 서브넷에 배치합니다. 높은 보안 요구사항이 있는 엔터프라이즈 고객을 위해서는 별도의 VPC를 생성하고 VPC Peering으로 연결합니다. 이를 통해 대부분의 고객은 비용 효율적인 공유 리소스를 사용하면서도, 요구사항이 높은 고객은 격리된 환경을 제공할 수 있습니다.

### 하이브리드 클라우드 환경
기업은 온프레미스 데이터센터와 AWS VPC를 연결합니다. VPC를 10.0.0.0/16으로 설정하고 서브넷을 여러 개 만들 때, 온프레미스 네트워크(172.16.0.0/16)와 충돌하지 않도록 주의합니다. VPN 또는 Direct Connect로 연결된 라우팅 테이블에 온프레미스 네트워크 경로를 추가하여, VPC에서 온프레미스 리소스에 접근할 수 있게 합니다. 이를 통해 점진적으로 워크로드를 클라우드로 마이그레이션할 수 있습니다.

### 개발/테스트/프로덕션 환경 분리
회사는 각 환경별로 별도의 VPC를 구성합니다. 개발 환경 VPC는 10.1.0.0/16, 테스트 환경은 10.2.0.0/16, 프로덕션은 10.0.0.0/16으로 설정합니다. 각 VPC 내에서는 동일한 서브넷 구조를 유지하여 관리를 용이하게 합니다. 각 환경은 완전히 격리되므로, 개발자가 프로덕션 리소스에 우연히 접근할 수 없습니다. VPC Peering 또는 Transit Gateway로 연결하여 필요한 경우만 통신하게 합니다.

## 🔗 관련 용어

- **VPC (Virtual Private Cloud)**: 서브넷이 속하는 상위 네트워크입니다.
- **CIDR (Classless Inter-Domain Routing)**: IP 주소 범위를 표현하는 표기법입니다.
- **라우팅 테이블 (Route Table)**: 트래픽의 경로를 결정하는 규칙 집합입니다.
- **NACL (Network Access Control List)**: 서브넷 수준의 방화벽입니다.
- **보안 그룹 (Security Group)**: 인스턴스 수준의 방화벽입니다.
- **가용 영역 (Availability Zone)**: AWS 리전 내의 물리적으로 분리된 데이터센터입니다.
- **인터넷 게이트웨이 (Internet Gateway)**: VPC와 인터넷을 연결합니다.
- **NAT 게이트웨이 (NAT Gateway)**: 프라이빗 리소스의 아웃바운드 통신을 지원합니다.
- **Elastic IP**: 인스턴스에 할당되는 고정 공용 IP 주소입니다.
- **호스트 (Host)**: 서브넷 내의 개별 컴퓨터나 리소스입니다.
