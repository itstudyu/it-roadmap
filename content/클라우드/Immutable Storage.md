# Immutable Storage (고칠 수 없는 저장소)

## 📝 정의

Immutable Storage 는 정해 둔 기간 동안 **아무도 못 지우는** 저장소다.

한 번 쓰고 여러 번 읽기만 된다고 해서 WORM(Write Once, Read Many) 이라 부른다. AWS 는 S3 Object Lock, Azure 는 변경 불가 저장소(immutable storage), Google Cloud 는 Bucket Lock 이라는 이름으로 같은 것을 판다. 셋 다 SEC 17a-4·CFTC·FINRA 같은 금융 기록 보존 규정을 겨냥해 만들어졌고, AWS 와 Azure 는 같은 독립 평가 기관(Cohasset Associates)의 검증서를 문서에 걸어 두고 있다.

### 이름
Im- :: 아니다
Mutable :: 바꿀 수 있는
Storage :: 넣어 두는 곳
= 붙여 읽으면 "바꿀 수 없게 넣어 두는 곳". 못 바꾸는 것이 결함이 아니라 기능이다

### 비유
정해진 날이 오기 전에는 열쇠를 쥔 지점장도 못 여는 은행 금고의 시간 잠금 장치.

### 예
은행 앱의 지난 거래 내역에 지우거나 고치는 단추가 하나도 없는 것이 같은 이유다.

### 직접
쓰는 은행 앱의 거래 내역 화면을 열어 보라. 어느 줄에도 수정·삭제 단추가 없다.

## 🖼️ 그림으로 보기

```도해
흐름: 잠근 파일을 지우라는 명령이 오면 무슨 일이 벌어지나
지우기 :: 그 판을 지우라고 요청한다
보존 기한 :: 아직 남았으면 여기서 막힌다
보류 표시 :: 걸려 있으면 기한과 상관없이 막힌다
저장소 :: 둘 다 풀렸을 때만 실제로 지운다
< 요청한 쪽 :: 막히면 거부를, 풀렸으면 삭제됨을 받는다
= 기한과 보류 중 하나만 살아 있어도 못 지운다
```

## ⚠️ 해결하는 문제

```도해
대조: 지울 수 있는 백업만 갖고 있으면 무엇이 무너지나
지울 수 있으면 || 못 지우게 하면
털린 계정 :: 백업까지 지운다 || 손도 못 댄다
실수 삭제 :: 그대로 사라진다 || 기한 전엔 남는다
감사 대응 :: 원본 증명 못 한다 || 규정을 채운다
= 지울 권한이 어딘가에 하나라도 남아 있으면 그 백업은 최후의 보루가 아니다
```

백업은 대개 "지울 수 있는 파일" 이다. 그래서 계정 하나가 털리면 원본과 백업이 같은 손에 들어가고, 랜섬웨어는 그걸 노려 백업부터 지운다. 실수도 마찬가지다 — 잘못 돌린 정리 스크립트 한 줄이 십 년치 기록을 함께 데려간다.

잠긴 저장소는 지우는 길 자체를 없앤다. 권한을 조이는 것과 다르다. 권한은 관리자가 풀 수 있지만, 잠긴 보존 정책은 계정 주인도 못 푼다. AWS 문서는 컴플라이언스 모드로 잠근 개체를 기한 전에 지우는 유일한 방법이 **그 AWS 계정 자체를 해지하는 것** 이라고 적는다.

## ⚙️ 작동 원리

```도해
층: 잠금은 얼마나 세게 걸 수 있나
지연 삭제 :: 지운 것을 잠시 남긴다. 실수만 막는다
느슨한 보존 :: 특별 권한이 있으면 풀 수 있다. 사내 사고용
잠긴 보존 :: 계정 주인도 못 푼다. 기한이 지나야 열린다
법적 보류 :: 기한이 없다. 사람이 걷어낼 때까지 막는다
= 아래로 갈수록 되돌릴 길이 사라진다. 세게 걸수록 잘못 걸었을 때도 못 푼다
```

잠금은 두 갈래다. **보존 기한**은 "언제까지" 를 못 박고, **법적 보류**는 기한 없이 "사람이 풀 때까지" 를 막는다. 둘은 서로 독립이라 같이 걸 수 있고, 기한이 끝나도 보류가 살아 있으면 여전히 못 지운다.

세기는 따로 정한다. AWS 는 거버넌스 모드와 컴플라이언스 모드로 나누고, Azure 는 정책을 잠그지 않은 상태(테스트용)와 잠근 상태로 나눈다. Azure 문서는 잠그지 않은 정책을 하루 넘게 쓰지 말라고 권한다. Google 은 버킷의 보존 정책을 잠그면 그 행동이 되돌릴 수 없고, 통 안의 모든 개체가 기한을 채우기 전에는 통 자체도 못 지운다고 적는다.

기한은 늘릴 수만 있고 줄일 수 없다. AWS 는 더 늦은 만료일로 다시 걸면 늘어난다고 적고, Azure 는 잠긴 컨테이너 정책의 경우 연장 횟수를 다섯 번으로 제한한다. 최소·최대 기한은 서비스마다 다른데, Azure 는 하루에서 146,000일(400년), Google 은 최대 100년까지 받는다.

## 📊 비교: 세 클라우드는 이 잠금을 뭐라 부르나

| | AWS S3 | Azure Blob | Google Cloud Storage |
|---|---|---|---|
| 기능 이름 | Object Lock | 변경 불가 저장소 | Bucket Lock |
| 기한 있는 잠금 | 보존 기간 | 시간 기반 보존 정책 | 보존 정책 |
| 기한 없는 잠금 | 법적 보류 | 법적 보류 | 개체 보류 |
| 되돌릴 수 없게 굳히기 | 컴플라이언스 모드 | 정책 잠금 | 정책 잠금 |
| 판 보관이 먼저 필요한가 | 필수 | 판 단위 정책이면 필수 | 필요 없다 |
| 거는 자리 | 개체 판 하나하나 | 계정 · 컨테이너 · 판 | 버킷 전체 · 개체 보류 |

## 💡 실제 사례

- **랜섬웨어 대비 백업** — 마지막 백업 한 벌을 잠긴 통에 두면 관리자 계정이 통째로 털려도 그 한 벌은 남는다.
- **금융·의료 기록 보존** — 몇 년을 남기라는 규정이 있는 기록에 그 햇수만큼 기한을 걸어 두고 감사 때 그대로 낸다.
- **소송 대비 보류** — 언제 끝날지 모르는 조사가 걸리면 기한 없는 보류를 걸고, 끝난 뒤에 사람이 걷어낸다.

## 🚫 흔한 오해

- **켜 두면 그 파일은 영원히 안 변한다** — 잠긴 건 그 판 하나다. AWS 문서는 보존 기한과 법적 보류가 같은 이름의 새 판이 생기는 것도, 그 위에 삭제 표가 얹히는 것도 막지 않는다고 적는다.
- **비상시에는 관리자가 풀 수 있다** — 세게 건 잠금은 못 푼다. AWS 는 컴플라이언스 모드를 기한 전에 푸는 길이 계정 해지뿐이라고 적고, Azure 도 잠근 정책은 삭제할 수 없다고 적는다.
- **어차피 안전하니 길게 걸수록 좋다** — 기한을 길게 잡으면 그동안 못 지우니 그만큼 보관료를 계속 낸다. 잘못 걸어도 못 줄인다.

## 🚨 주의사항

- **먼저 느슨하게 걸어 시험해라.** Azure 는 잠그지 않은 정책을, AWS 는 거버넌스 모드를 시험용으로 두라고 권한다. 굳히는 건 되돌릴 수 없다.
- **통을 못 지우게 된다.** Google 은 개체가 전부 기한을 채우기 전에는 버킷을 못 지운다고 적고, Azure 도 잠긴 컨테이너는 비어야 지워진다고 적는다.
- **자동 정리 규칙이 안 먹는다.** Azure 문서는 변경 불가 컨테이너의 블롭에는 수명 주기 정책의 삭제 동작이 통하지 않는다고 못 박는다.

## 📝 정리

**"기한이 지나야 열리는 그 금고"** 라고 읽으면 된다. 권한을 조이는 것과 다른 점 하나만 기억하면 된다 — 권한은 관리자가 풀 수 있지만 잠긴 보존은 계정 주인도 못 푼다. 그 힘이 곧 위험이라, 굳히기 전에 반드시 느슨한 모드로 먼저 시험한다.

## 🧒 열 살에게

은행 금고에 시간 자물쇠가 달린 거 알지? 정해진 날이 오기 전에는 열쇠를 가진 은행장도 못 열어. 그래서 나쁜 사람이 몰래 들어와도 그 안에 넣어 둔 건 없애지 못해.
