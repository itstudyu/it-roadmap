# Availability Zone (AZ, 가용 영역)

## 📝 정의

가용 영역(Availability Zone, AZ)은 하나의 AWS 리전 내에서 물리적으로 분리된 독립적인 데이터센터 그룹을 의미합니다. 각 가용 영역은 별도의 전원 공급 시스템, 냉각 시스템, 물리적 네트워크 인프라를 가지고 있어서, 한 가용 영역의 장애가 다른 가용 영역에 영향을 주지 않도록 설계되었습니다. 예를 들어 AWS 서울 리전(ap-northeast-2)에는 ap-northeast-2a, 2b, 2c, 2d 4개의 가용 영역이 있으며, 각 가용 영역은 서울 지역의 다른 위치에 물리적으로 떨어져 있습니다.

가용 영역은 리전과 달리 지역적으로 가까이 위치하므로, 가용 영역 간 통신 지연은 1-2ms 정도로 매우 낮습니다. 따라서 여러 가용 영역에 걸쳐 리소스를 배포하면, 고가용성(High Availability)을 달성할 수 있으면서도 네트워크 성능을 희생하지 않습니다. 가용 영역은 클라우드 아키텍처에서 재해 복구와 고가용성을 구현하는 가장 기본적인 수준의 격리 단위입니다.

### 한 줄 요약
> 같은 리전 내에서 물리적으로 분리된 독립적인 데이터센터 그룹으로, 지연 최소화와 고가용성을 함께 달성할 수 있는 단위

### 비유
- 🔵 **비유 1**: 같은 도시의 다른 지역에 위치한 여러 병원 지점. 한 지점이 정전이나 구조적 문제로 문을 닫아도, 다른 지점들은 계속 환자를 치료할 수 있습니다.
- 🟡 **비유 2**: 같은 회사의 여러 사무실. 본사가 있는 강남이 화재로 일시 폐쇄되어도, 강북 지점, 홍대 지점이 있으면 업무는 계속됩니다.
- 🟢 **비유 3**: 같은 지역의 여러 변전소(전기 송전소). 각각 독립적인 전원을 공급받아, 한 변전소의 장애가 다른 변전소에 영향을 주지 않습니다.

## 🎯 핵심 개념

### 1. 가용 영역의 물리적 구조와 독립성
각 가용 영역은 수십 개의 데이터센터(건물)를 포함하며, 이들은 저지연 네트워크로 연결되어 있습니다. 중요한 것은 각 가용 영역이 완전히 독립적인 인프라를 갖춘다는 점입니다. 예를 들어 ap-northeast-2a 가용 영역에서 정전이 발생해도, ap-northeast-2b 가용 영역의 전원은 영향을 받지 않습니다. 마찬가지로 지진이나 홍수가 한 가용 영역을 타격해도, 몇 킬로미터 떨어진 다른 가용 영역은 안전합니다. 이러한 물리적 분리가 AWS의 고가용성 아키텍처의 기초를 이룹니다. AWS는 실제로 각 가용 영역 간 거리를 계산하여, 자연재해가 여러 가용 영역을 동시에 타격할 가능성을 최소화합니다.

### 2. 리전과 가용 영역의 관계
리전은 지리적으로 넓은 지역(예: 한국 전체)을 커버하고, 가용 영역은 그 리전 내의 구체적인 지역(예: 서울, 인천)을 커버합니다. 각 리전은 최소 3개, 대부분 4-6개의 가용 영역을 가집니다. 예를 들어 AWS 서울 리전(ap-northeast-2)은 4개의 가용 영역을 가지는데, 이는 고객이 여러 가용 영역에 걸쳐 배포하여 고가용성을 달성할 수 있다는 뜻입니다. 리전을 선택하면 그 리전의 모든 가용 영역에 접근할 수 있으므로, 리전 선택은 고객이 어느 국가/지역의 데이터센터를 사용할지를 결정하고, 가용 영역 선택은 그 리전 내 어디에 리소스를 배치할지를 결정합니다.

### 3. 가용 영역 간 통신과 지연
같은 리전 내의 다른 가용 영역 간 통신은 매우 빠르며, 일반적으로 1-2ms의 지연만 발생합니다. 이는 가용 영역들이 전용 고속 네트워크로 연결되어 있기 때문입니다. 반면 다른 리전 간 통신은 100ms 이상의 지연이 발생할 수 있습니다. 따라서 실시간 동기화가 필요한 데이터베이스 복제나 로드 밸런싱은 같은 리전 내의 다른 가용 영역 간에서 이루어지는 것이 최적입니다. 이를 통해 고가용성(여러 가용 영역에 배포)을 달성하면서도, 낮은 지연(같은 리전 내)을 유지할 수 있습니다.

### 4. 고가용성 아키텍처의 핵심
고가용성 아키텍처는 일반적으로 2개 이상의 가용 영역에 리소스를 배포하는 것을 기본으로 합니다. 예를 들어 웹 서버는 AZ-a와 AZ-b에 각각 배치하고, 로드 밸런서가 두 서버 간에 트래픽을 분산합니다. 만약 AZ-a의 데이터센터에 정전이 발생하면, 로드 밸런서는 자동으로 AZ-b의 서버로 모든 트래픽을 전환합니다. 사용자는 이러한 전환을 느끼지 못하고 서비스를 계속 사용할 수 있습니다. 이를 "자동 페일오버(Automatic Failover)"라고 합니다. 더 높은 가용성을 위해 3개 이상의 가용 영역에 배포할 수도 있습니다.

## ⚠️ 해결하는 문제

### 문제 1: 데이터센터 장애로 인한 서비스 중단
전통적인 온프레미스 데이터센터에서는 보통 하나의 건물에 모든 서버를 배치합니다. 만약 그 건물에 정전, 화재, 홍수, 또는 구조적 손상이 발생하면, 모든 서버가 동시에 다운되어 서비스 전체가 중단됩니다. 이는 막대한 경제적 손실을 초래합니다. 가용 영역을 사용하면, 여러 물리적으로 분리된 데이터센터에 리소스를 배포할 수 있으므로, 한 데이터센터의 장애가 서비스 전체에 영향을 주지 않습니다. 예를 들어 서울 강남의 데이터센터(AZ-a)가 정전되어도, 강북의 데이터센터(AZ-b)에 배치된 서버가 자동으로 서비스를 계속합니다.

### 문제 2: 정전과 전력 공급 장애
데이터센터의 정전은 생각보다 자주 발생합니다. 날씨, 외부 공사, 기계 고장 등 다양한 이유로 전력 공급이 중단될 수 있습니다. 만약 하나의 데이터센터에만 의존한다면, 정전 시 서비스가 중단됩니다. 가용 영역은 각각 독립적인 전력 공급 시스템을 가지고 있으므로, 한 가용 영역의 정전이 다른 가용 영역에 영향을 주지 않습니다. 또한 각 가용 영역은 여러 개의 독립적인 변전소에서 전력을 공급받도록 설계되어 있어, 단일 변전소의 장애도 대비합니다.

### 문제 3: 자연재해로 인한 광범위 피해
지진, 태풍, 홍수 같은 자연재해는 발생 예측이 어렵고 피해 범위가 광대합니다. 하나의 지역에만 데이터센터가 있으면, 그 지역을 타격하는 자연재해로 서비스 전체가 중단됩니다. 가용 영역은 리전 내에서 물리적으로 충분히 떨어져 있어서(보통 수 킬로미터), 같은 자연재해가 모든 가용 영역을 동시에 타격할 가능성이 거의 없습니다. AWS는 지진 위험도, 홍수 위험도, 기후 조건 등을 분석하여 가용 영역 위치를 결정합니다.

### 문제 4: 네트워크 장애와 단일 경로 의존성
만약 하나의 데이터센터에 모든 사용자의 트래픽이 집중되면, 그 데이터센터로 가는 네트워크 경로에 문제가 발생할 경우 전체 서비스가 중단됩니다. 여러 가용 영역에 리소스를 배포하고 로드 밸런서를 사용하면, 트래픽이 여러 경로를 통해 다양한 가용 영역으로 분산됩니다. 한 경로에 장애가 발생해도 다른 경로를 통한 통신은 계속되므로, 서비스 중단을 방지할 수 있습니다.

### 문제 5: 높은 가용성 요구사항 충족 불가
금융, 의료, 통신 같은 산업은 서비스의 가용성에 대해 99.99% (연간 약 52분 이하의 다운타임) 이상을 보장해야 한다는 규제가 있습니다. 하나의 데이터센터에 의존해서는 이러한 높은 가용성을 달성할 수 없습니다. 가용 영역을 활용하면, 이론적으로 무한에 가까운 가용성을 달성할 수 있습니다. (각 가용 영역의 개별 가용성이 99.99%이면, 2개 이상에 배포하면 99.9999% 이상 달성 가능)

### 장애 시나리오와 대응

```
시나리오 1: AZ-a 정전
┌─ Route 53 감지 (AZ-a LB 헬스 체크 실패)
├─ 자동으로 AZ-b, c로 트래픽 전환
└─ 결과: 서비스 중단 없음 (사용자 영향 0)

시나리오 2: AZ-a 데이터센터 화재
┌─ RDS 자동 페일오버 (Master → Replica in AZ-b)
├─ EC2 인스턴스 데이터 손실 (상태 비저장이면 문제없음)
└─ Auto Scaling이 AZ-b, c에 새 인스턴스 자동 생성
    결과: 몇 분 내 정상화

시나리오 3: 지진으로 AZ-a, b 피해
┌─ 즉시 AZ-c로 모든 트래픽 전환
├─ 백업 (S3)에서 데이터 복구
└─ 다른 리전에서 복제본 활성화 (RTO: 수십 분)
    결과: 높은 다운타임 (일반적인 재해)

시나리오 4: 여러 AZ에 배포된 상태
┌─ 어떤 단일 AZ 장애도 서비스 중단 불가
├─ 2개 이상 AZ 동시 장애 확률: 극히 낮음
└─ 결과: 99.95% 이상 가용성 보장
```

## ⚙️ 작동 원리

### AZ 장애 시나리오와 자동 복구 흐름

```도해
흐름: Availability Zone, 무슨 순서로 오가나
사용자 :: 요청
로드밸런서 :: 트래픽 전달 시도
로드밸런서 :: 트래픽 전환
가용 영역 A 정상 :: 정상 응답
로드밸런서 :: 응답 서비스 지속
```

### 1단계: 리소스를 여러 가용 영역에 배포
애플리케이션 아키텍트가 리소스를 여러 가용 영역에 배치합니다. 예를 들어 웹 서버를 AZ-a와 AZ-b에 배치하고, 로드 밸런서를 두 서버 앞에 배치합니다. 데이터베이스는 마스터를 AZ-a에, 읽기 전용 복제본을 AZ-b와 AZ-c에 배치합니다. 정적 파일들은 S3에 저장하고, S3도 내부적으로 여러 가용 영역에 자동으로 복제됩니다.

### 2단계: 헬스 체크를 통한 상태 모니터링
로드 밸런서와 Route 53이 각 가용 영역의 리소스 상태를 지속적으로 모니터링합니다. 로드 밸런서는 주기적으로 HTTP 요청을 각 EC2 인스턴스로 보내서 정상 작동 여부를 확인합니다. Route 53도 주기적으로 로드 밸런서 자체의 상태를 확인합니다. 만약 어떤 리소스가 응답하지 않으면, 즉시 그 리소스를 "비정상"으로 표시합니다.

### 3단계: 자동 트래픽 전환
로드 밸런서가 비정상 리소스를 감지하면, 자동으로 그 리소스로의 새로운 요청 전송을 중단합니다. 이미 진행 중인 연결은 graceful shutdown(우아한 종료)을 통해 정상 완료한 후 연결을 끝냅니다. 모든 새로운 트래픽은 정상 상태의 다른 가용 영역으로 전달됩니다. 이 과정은 자동이므로 별도의 개입이 필요하지 않습니다.

### 4단계: 장애 격리 및 데이터 보호
만약 특정 가용 영역이 완전히 다운되면, 그 가용 영역의 데이터는 더 이상 접근할 수 없을 수 있습니다. 하지만 데이터가 다른 가용 영역에도 복제되어 있으므로, 데이터 손실은 발생하지 않습니다. RDS 데이터베이스의 경우, 자동으로 복제본 중 하나를 새로운 마스터로 승격(Promotion)시켜, 데이터베이스 쓰기 작업도 계속할 수 있습니다.

### 5단계: 자동 리소스 생성 및 복구
Auto Scaling을 설정했다면, 가용 영역의 리소스 손실을 감지하면 자동으로 새로운 리소스를 생성합니다. 예를 들어 AZ-a의 EC2 인스턴스가 다운되면, Auto Scaling은 AZ-b나 AZ-c에 새로운 인스턴스를 자동으로 생성합니다. 몇 분 내에 서비스 용량이 복구되므로, 사용자는 거의 느끼지 못하는 수준의 영향만 받습니다.

### 6단계: 수동 개입 (선택사항)
자동 복구가 완료된 후, 운영팀은 장애 원인을 분석하고 필요시 수동으로 개입합니다. 예를 들어 특정 AZ의 네트워크 장애가 발견되면, AWS 지원팀에 보고하여 근본 원인을 파악합니다. 하지만 이 모든 과정에서 사용자 영향은 최소화됩니다.

```
실시간 트래픽 흐름:

정상 상태:
사용자 → Route 53 → Load Balancer
                    ├─ AZ-a: EC2-1 (30% 트래픽)
                    ├─ AZ-b: EC2-2 (35% 트래픽)
                    └─ AZ-c: EC2-3 (35% 트래픽)

AZ-a 장애 감지:
1. LB가 AZ-a 헬스 체크 실패 감지
2. EC2-1을 트래픽 대상에서 제거
3. 새로운 트래픽 분배:
   ├─ AZ-a: 0% (비정상)
   ├─ AZ-b: 50% 트래픽
   └─ AZ-c: 50% 트래픽

자동 복구:
1. Auto Scaling이 손실된 용량 감지
2. AZ-a 또는 다른 AZ에 새 인스턴스 생성
3. 새 인스턴스가 정상 상태 확인 후 트래픽 수신
4. 트래픽 재분배 (일반적으로 2-3분 소요)
```

## ✅ 장점과 단점

### 장점

**1. 자동 고가용성**: 여러 AZ에 리소스를 배포하면, 하나의 AZ 장애로 인한 서비스 중단을 자동으로 방지할 수 있습니다. 사용자 개입 없이 자동 페일오버가 이루어집니다.

**2. 낮은 네트워크 지연**: 같은 리전 내의 다른 AZ는 1-2ms의 매우 낮은 지연으로 통신하므로, 고가용성을 달성하면서도 성능을 희생하지 않습니다.

**3. 예측 가능한 아키텍처**: AZ 장애는 드물고 예측 불가능하지만, 여러 AZ에 배포하면 어떤 단일 AZ 장애도 서비스 중단을 유발하지 않으므로, 안정적인 아키텍처를 설계할 수 있습니다.

**4. 쉬운 스케일링**: Auto Scaling을 설정하면, 한 AZ에서 리소스 손실이 발생해도 자동으로 다른 AZ에 리소스를 생성하여 용량을 복구합니다.

**5. 데이터 보호**: 대부분의 AWS 서비스가 내부적으로 여러 AZ에 데이터를 자동으로 복제하므로, 데이터 손실 위험이 매우 낮습니다.

**6. 규제 준수 용이**: 일부 규제는 지리적으로 분산된 백업을 요구하는데, 같은 리전의 여러 AZ는 이를 간단하게 충족시킵니다.

### 단점

**1. 비용 증가**: 여러 AZ에 리소스를 배포하면 비용이 증가합니다. 특히 데이터베이스의 경우, 읽기 복제본을 여러 AZ에 만들면 비용이 크게 증가합니다.

**2. 복잡한 아키텍처 관리**: 여러 AZ를 관리하면 로드 밸런싱, 복제 설정, 모니터링 등이 복잡해집니다.

**3. 데이터 동기화 지연**: 쓰기 작업을 마스터 데이터베이스에 하고 다른 AZ의 복제본에 동기화하는 과정에서 약간의 지연이 발생합니다. (일반적으로 수 밀리초)

**4. 네트워크 트래픽 비용**: AZ 간 데이터 전송에는 비용이 발생합니다. 대량의 동기화나 백업 이동은 상당한 네트워크 비용을 초래할 수 있습니다.

**5. 초기 설계 복잡도**: 여러 AZ를 고려한 아키텍처 설계는 싱글 AZ 설계보다 복잡합니다.

**6. 상태 관리의 어려움**: 세션이나 임시 데이터를 로컬 스토리지에 저장하면, 로드 밸런서가 다른 AZ의 인스턴스로 요청을 전환할 때 데이터가 손실될 수 있습니다.

## 💡 실제 사용 사례

### 전자상거래 플랫폼 (Coupang 방식)
온라인 쇼핑몰은 AP-NE-2 (서울)의 3개 AZ에 웹 서버를 배치합니다. 각 AZ에 5개씩 총 15개의 EC2 인스턴스를 운영하면서 로드 밸런서가 트래픽을 분산합니다. RDS 데이터베이스는 AZ-a에 마스터, AZ-b와 AZ-c에 읽기 복제본을 배치하여, 읽기 부하를 분산하면서도 쓰기 가용성을 보장합니다. 만약 AZ-a 정전이 발생해도, 웹 서버는 AZ-b/c가 계속 서비스하고, 데이터베이스는 복제본 중 하나가 새로운 마스터로 승격되어 서비스가 중단되지 않습니다.

### 금융회사의 거래 시스템
은행의 계좌이체 시스템은 99.999% 가용성을 보장해야 합니다. 따라서 AP-NE-2의 모든 4개 AZ에 서버를 배치하고, 여러 금융 규제 요구사항을 충족시킵니다. 심지어 한 AZ 전체가 다운되어도 다른 3개 AZ에서 거래를 처리합니다. 또한 실시간 동기화로 어떤 AZ에서 거래하든 최신 계좌 정보를 조회할 수 있습니다.

### SaaS 제공업체 (GitHub 방식)
개발자 협업 플랫폼은 US-EAST-1의 3개 주요 AZ에 배포하면서, 동시에 다른 리전에도 복제합니다. 미국 사용자는 US-EAST-1에서 빠른 응답을 받고, 유럽 사용자는 EU-WEST-1에서 받습니다. 어떤 단일 AZ 장애도 서비스 중단을 유발하지 않으며, 동시에 리전 차원의 재해에도 대비합니다.

### 게임 서버 운영사
온라인 게임의 게임 서버들은 AP-NE-2의 여러 AZ에 배치되어, 플레이어들의 요청이 가장 가까운 AZ의 서버로 라우팅됩니다. 만약 AZ-a가 다운되어도, 플레이어들은 자동으로 AZ-b/c의 서버로 연결되며, 게임 진행 상황이 S3와 DynamoDB에 저장되어 있어 데이터 손실이 없습니다.

## 🔗 관련 용어

- **리전 (Region)**: 여러 가용 영역을 포함하는 광범위한 지리적 지역입니다.
- **엣지 로케이션 (Edge Location)**: CDN 캐싱을 위한 AWS의 글로벌 네트워크 포인트입니다.
- **로드 밸런서 (Load Balancer)**: 여러 AZ의 리소스 간 트래픽을 분산합니다.
- **Auto Scaling**: 리소스 손실을 감지하여 자동으로 새로운 리소스를 생성합니다.
- **헬스 체크 (Health Check)**: 리소스의 정상 작동 여부를 주기적으로 확인합니다.
- **페일오버 (Failover)**: 장애 발생 시 다른 리소스로 자동 전환합니다.
- **RDS Multi-AZ**: 데이터베이스를 여러 AZ에 자동으로 복제합니다.
- **가용성 (Availability)**: 서비스가 정상 작동하는 시간의 비율입니다.
- **SLA (Service Level Agreement)**: 클라우드 제공업체가 보장하는 가용성입니다.
- **RTO (Recovery Time Objective)**: 장애 복구에 소요되는 목표 시간입니다.
