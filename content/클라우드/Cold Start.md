# Cold Start (콜드 스타트)

## 📝 정의

Cold Start는 **실행 환경을 새로 만드느라 첫 호출이 늦어지는 것**이다.

늦은 쪽은 함수가 아니라 함수를 놓을 자리다. 코드를 내려받고 환경을 세우고 준비 코드를 한 번 돌리는 시간이 첫 호출에만 얹힌다. 두 번째부터는 그 환경을 다시 써서 그 시간이 통째로 빠진다.

### 이름
Cold :: 아직 안 데워진
Start :: 첫 시동
= 붙여 읽으면 "식은 채로 거는 첫 시동". 데워 두면 그 시간이 사라진다

### 비유
겨울 아침의 자동차는 첫 시동이 굼뜨지만, 방금까지 몰던 차는 타자마자 달린다.

### 예
오랜만에 부른 첫 요청만 유독 오래 걸리고, 뒤이은 요청은 곧바로 끝나는 그 차이다.

## 🖼️ 그림으로 보기

```도해
흐름: 잠자던 함수에 첫 요청이 오면 무슨 일이 일어나나
요청 도착 :: 쓸 수 있는 실행 환경이 하나도 없다
환경 준비 :: 코드를 내려받고 실행 환경을 세운다
초기화 :: 핸들러 밖에 적어 둔 준비 코드가 한 번 돈다
첫 실행 :: 그제야 본 함수가 돌아 답이 나간다
환경 보관 :: 끝난 환경을 얼려 두고 얼마간 남겨 둔다
@ 다음 요청 :: 남아 있으면 녹여 바로 쓰고, 없으면 처음부터
= 늦은 것은 함수가 아니라 함수를 놓을 자리를 만드는 시간이다
```

## ⚠️ 해결하는 문제

```도해
대조: 식은 호출과 데워진 호출은 무엇이 다른가
식은 호출 || 데워진 호출
실행 환경 :: 그 자리서 만든다 || 이미 서 있다
준비 코드 :: 한 번 다 돈다 || 건너뛴다
첫 응답 :: 눈에 띄게 늦다 || 곧바로 나간다
= 코드가 느린 게 아니다. 코드를 놓을 자리가 없던 것이다
```

이 현상에 이름이 없으면 "가끔 느리다" 로 뭉뚱그려진다. 평균 응답 시간만 보면 아예 안 보이기도 한다. AWS 문서는 식은 호출이 전체 호출의 1% 미만에서 일어나고, 그때 걸리는 시간은 0.1초 아래에서 1초 위까지 흩어진다고 적는다. 백 번에 한 번이지만 그 한 번을 사람이 기다린다.

이름이 붙으면 고를 것이 생긴다. 미리 띄워 둘 것인가, 준비 코드를 줄일 것인가, 아니면 그냥 견딜 것인가. 셋은 값도 다르고 효과도 다르다.

## ⚙️ 작동 원리

실행 환경은 세 단계를 산다. AWS 문서는 이를 Init · Invoke · Shutdown 으로 적는다. Init 에서 확장을 켜고 런타임을 준비하고 핸들러 밖의 정적 코드를 실행한다. 호출이 끝나면 Lambda 는 환경을 얼려 두고, 얼마 뒤 같은 함수의 요청이 오면 녹여서 다시 쓴다. 이것이 warm start 다. 다만 계속 불리는 함수라도 몇 시간마다 환경을 정리하므로, 환경이 영원히 남는다고 가정하면 안 된다.

가장 큰 지연 요인은 핸들러 밖 초기화 코드다. AWS 문서는 함수 실행 전 지연의 최대 기여자가 초기화 코드라고 못박고, 꾸러미를 통째로 부르는 대신 쓰는 것만 부르라고 적는다.

미리 띄워 두는 장치는 세 곳 이름이 다르다. AWS 의 프로비저닝된 동시성은 실행 환경을 미리 초기화해 둔다. Azure Functions 프리미엄 요금제는 항상 준비 인스턴스와 미리 데운 인스턴스를 함께 두어 식은 호출을 없앤다. Cloud Run 은 최소 인스턴스를 두어 요청을 처리하지 않는 동안에도 인스턴스를 남겨 둔다. 셋 다 공짜가 아니다 — Cloud Run 문서는 최소 인스턴스로 남겨 둔 인스턴스에도 요금이 붙는다고 적고, Azure 문서는 최소 인스턴스 수만큼은 함수가 실행되지 않아도 과금된다고 적는다.

## 💡 실제 사례

- **뜸한 관리자 화면** — 하루 몇 번만 열리는 함수는 열 때마다 첫 화면이 늦다. 사람이 화면 앞에서 기다리는 자리라 티가 크다.
- **한꺼번에 몰린 요청** — 남아 있는 환경보다 요청이 많으면 그 수만큼 환경을 새로 만든다. 늘어나는 동안 들어온 사람들이 이 지연을 나눠 겪는다.
- **무거운 준비 코드** — 핸들러 밖에서 큰 꾸러미를 통째로 불러오면 그 시간이 전부 첫 호출에 얹힌다. 쓰는 것만 골라 부르면 그만큼 줄어든다.

## 🚫 흔한 오해

- **서버리스는 원래 느리다** — 열에 아홉은 데워진 환경을 다시 쓴다. AWS 문서는 식은 호출이 전체의 1% 미만이라고 적는다.
- **첫 호출이 걱정되면 무조건 미리 띄워 두면 된다** — 미리 띄운 자리는 놀고 있어도 요금이 붙는다. 하루 몇 번 부르는 함수라면 지연을 견디는 쪽이 싸다.
- **함수 코드를 빠르게 고치면 사라진다** — 늦은 구간은 대개 본 코드가 아니라 환경을 세우고 준비 코드를 도는 시간이다.

## 📝 정리

**"쓸 자리를 새로 만드느라 첫 판만 늦는 것"** 이라고 읽으면 된다. 늦는 구간은 본 코드가 아니라 환경을 세우고 핸들러 밖 준비 코드를 도는 시간이다. 미리 띄워 두면 그 시간은 사라지지만 노는 자리에도 요금이 붙으니, 이 지연을 견딜 수 있는지부터 묻는다.

## 🧒 열 살에게

아주 추운 날 아침에 세워 둔 차는 시동을 걸어도 한참 있다가 움직이지? 그런데 조금 전까지 달리던 차는 타자마자 바로 가. 오래 안 쓴 것을 다시 쓰려면 깨우는 시간이 먼저 든다는 거야.

## ❓ 이해했는지

- 같은 함수인데 어떤 호출만 유독 늦는 이유는 무엇인가 → 그림
- 미리 띄워 두는 설정을 켰더니 청구서가 늘었다. 왜인가 → 흔한 오해
- 하루 몇 번만 부르는 함수가 이 지연을 더 자주 겪는 이유는 무엇인가 → 실제 사례
