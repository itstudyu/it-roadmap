# Landing Zone (첫 착륙장)

## 📝 정의

Landing Zone 은 일을 올리기 전에 **미리 깔아 두는** 클라우드 바닥이다.

누가 들어오는지, 칸을 어떻게 가르는지, 망을 어떻게 잇는지, 무엇을 금지하는지 — 이 넷을 첫 서비스보다 먼저 정해 놓은 상태를 말한다. AWS 는 랜딩 존(Control Tower 가 만들어 준다), Azure 는 Azure 랜딩 존, Google Cloud 는 랜딩 존 또는 클라우드 파운데이션이라 부른다. Google 문서는 이것을 "조직이 클라우드를 도입할 수 있게 하는 모듈식이고 확장 가능한 구성" 이라고 적는다.

### 이름
Landing :: 내려앉는 일
Zone :: 미리 정해 둔 구역
= 붙여 읽으면 "내려앉으라고 미리 정해 둔 구역". 헬기가 아무 데나 못 내리는 것과 같다

### 비유
비행기가 오기 전에 이미 깔려 있어야 하는 공항의 활주로와 관제탑.

### 예
새 프로젝트를 시작할 때 계정 하나 받는 데 2주가 걸리고, 받고 나면 망도 권한도 팀마다 제각각인 그 상황이다.

## 🖼️ 그림으로 보기

```도해
층: 여기서 건 규칙은 어디까지 내려오나
조직 :: 회사 전체. 결제와 최상위 금지 항목이 여기 붙는다
칸 :: 운영·개발·감사처럼 성격이 같은 것끼리 묶는다
계정 :: 자원이 실제로 사는 곳. 사고가 여기서 멈춘다
일 :: 그 계정 안에서 도는 하나의 서비스
= 위에서 건 규칙이 아래로 내려온다. 그래서 칸을 어떻게 가르느냐가 곧 통제다
```

## ⚠️ 해결하는 문제

```도해
대조: 착륙장 없이 계정부터 만들면 무엇이 달라지나
바닥 없이 || 착륙장 위에
새 계정 :: 매번 손으로 짠다 || 같은 꼴로 찍힌다
사고 범위 :: 한 계정에 다 있다 || 계정 하나로 끝난다
감사 :: 계정마다 뒤진다 || 한곳에 모여 있다
= 나중에 까는 바닥은 이미 올라간 일들을 전부 들어내야 깔린다
```

클라우드는 계정 하나로 시작하기가 너무 쉽다. 그래서 대부분 그렇게 시작하고, 2년 뒤에는 운영과 실험이 같은 계정에서 돌고, 청구서는 한 덩어리이고, 실수로 지운 것이 무엇에 영향을 줄지 아무도 모르는 상태가 된다. AWS 백서는 계정 자체가 **접근 제어의 격리 경계**이며 기본적으로 계정 사이에는 아무 접근도 허용되지 않는다고 적는다. 계정을 안 가르면 그 경계를 통째로 버리는 셈이다.

착륙장은 그 경계를 미리 그어 둔다. 폭발 반경(사고가 번지는 범위), 청구 단위, 한도 단위가 전부 계정·구독·프로젝트 단위로 갈리기 때문에, 칸을 어떻게 가르느냐가 나중에 되돌리기 가장 어려운 결정이 된다. 이미 자원이 올라간 뒤에 칸을 다시 가르는 일은 설정 변경이 아니라 이사다.

## ⚙️ 작동 원리

착륙장은 크게 두 덩어리다. 하나는 모두가 함께 쓰는 **바닥**(계정 나무, 공용 망, 로그 모으는 곳, 보안 감시)이고, 다른 하나는 팀에게 나눠 주는 **한 칸**이다. Microsoft 는 이 둘을 플랫폼 랜딩 존과 애플리케이션 랜딩 존이라 부르고, 하나의 테넌트에 플랫폼은 하나만 두라고 권한다.

규칙은 위에서 걸어 아래로 내린다. AWS 는 이것을 컨트롤(가드레일)이라 부르며 예방·탐지·사전 검사 세 갈래로 나눈다. Azure 는 관리 그룹 나무에 Azure Policy 를 걸고, 그 밑의 구독이 정책을 상속받게 한다. Google 은 폴더와 프로젝트 나무에 조직 정책을 건다. 어느 쪽이든 "팀이 각자 지키기" 가 아니라 "위에서 아예 못 하게 막기" 라는 점이 같다.

새 칸은 손으로 만들지 않는다. AWS 는 Account Factory 로, Azure 는 구독 벤딩으로, Google 은 프로젝트를 자동으로 찍어 내는 파이프라인으로 만든다. 이 자동화가 있어야 규칙이 붙은 계정을 하루 만에 내줄 수 있고, 그래야 팀이 몰래 개인 계정을 만들지 않는다.

그리고 착륙장은 가만두면 벌어진다. AWS 는 그 벌어짐을 **드리프트**라 부르고, 그것을 계속 감지하는 것을 기능으로 판다.

## 📊 비교: 세 클라우드는 착륙장을 어떻게 세우나

| | AWS | Azure | Google Cloud |
|---|---|---|---|
| 칸을 가르는 단위 | 계정 | 구독 | 프로젝트 |
| 칸을 묶는 나무 | 조직 단위(OU) | 관리 그룹 | 폴더 |
| 규칙 거는 법 | 컨트롤(가드레일) · SCP | Azure Policy | 조직 정책 · IAM |
| 새 칸 찍어 내기 | Account Factory | 구독 벤딩 | 프로젝트 생성 파이프라인 |
| 미리 만드는 특수 칸 | 로그 보관 · 감사 계정 | 관리 · 보안 · 연결 구독 | 로깅 · 공유 망 호스트 프로젝트 |
| 대표 도구 | Control Tower | 랜딩 존 액셀러레이터 | 클라우드 파운데이션 청사진 |

## 💡 실제 사례

- **새 팀 온보딩** — 신청을 넣으면 규칙과 로그 전달이 이미 붙은 계정이 하루 만에 나온다.
- **감사 대응** — 모든 계정의 기록이 건드릴 수 없는 한 계정에 모여 있어서 한 번에 제출한다.
- **비용 나누기** — 계정을 팀 단위로 갈라 놨으니 청구서가 태그 없이도 저절로 팀별로 갈린다.

## 🚫 흔한 오해

- **작은 회사는 계정 하나면 충분하다** — 계정 하나면 사고 하나가 전부를 삼킨다. AWS 백서는 계정 자체가 격리 경계이고 계정 사이에는 기본적으로 아무 접근도 없다고 적는다.
- **착륙장은 한 번 깔면 끝이다** — 규칙도 팀도 계속 바뀐다. AWS 가 드리프트 감지를 기능으로 파는 이유가 그것이다.
- **도구를 켜면 착륙장이 생긴다** — 도구는 결정을 대신해 주지 않는다. Google 문서도 신원·자원 나무·망·보안 통제 네 가지를 먼저 정해야 한다고 적는다.

## 🚨 주의사항

- **칸을 가르는 결정을 가장 먼저 해라.** 자원이 올라간 뒤에 계정을 다시 가르는 일은 설정 변경이 아니라 이사다.
- **너무 세게 조이면 우회로가 생긴다.** 팀이 일을 못 하면 개인 카드로 계정을 만든다. 그건 착륙장 밖이라 아무 규칙도 안 걸린다.
- **로그 보관 계정은 잠가라.** 사고를 낸 사람이 로그까지 지울 수 있으면 그 로그는 증거가 아니다.

## 📝 정리

**"일을 올리기 전에 깔아 두는 그 바닥"** 이라고 읽으면 된다. 핵심은 도구가 아니라 칸을 어떻게 가르느냐다 — 계정·구독·프로젝트가 곧 사고가 멈추는 선이자 청구서가 갈리는 선이기 때문이다. 나중에 깔면 이미 올라간 것을 전부 들어내야 하므로, 착륙장은 첫 서비스보다 먼저 서 있어야 한다.

## 🧒 열 살에게

비행기가 내리려면 활주로가 먼저 깔려 있어야 하지? 어디로 가라고 알려 주는 관제탑도 미리 서 있어야 하고. 비행기부터 잔뜩 불러 놓고 그 밑에 활주로를 까는 건 못 하는 일이야.
