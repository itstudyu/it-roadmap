# Instance Template (인스턴스 붕어빵 틀)

## 📝 정의

Instance Template 은 같은 서버를 몇 대든 똑같이 찍어 내는 **틀**이다.

어떤 이미지로, 어떤 크기로, 어떤 망에 붙여, 어떤 시작 스크립트를 물려 띄울지를 한곳에 적어 둔 것이다. Google Cloud 는 인스턴스 템플릿, AWS 는 시작 템플릿(Launch Template), Azure 는 확장 집합(Virtual Machine Scale Sets) 안의 모델이라 부른다. 자동 확장이 새 대를 만들 때 들여다보는 것이 바로 이 틀이다.

### 이름
Instance :: 띄워 놓은 한 대
Template :: 찍어 내는 틀
= 붙여 읽으면 "한 대를 찍어 내는 틀". 틀을 깎는 게 아니라 새 틀을 짠다

### 비유
반죽을 바꾸려면 쓰던 틀을 깎는 대신 새 틀을 짜서 바꿔 끼우는 붕어빵 틀.

### 예
세일이 시작되면 서버가 열 대로 늘었다가 끝나면 두 대로 줄어드는 쇼핑몰에서, 늘어난 여덟 대가 전부 이 틀에서 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 손님이 갑자기 몰리면 새 서버는 어디서 나오나
틀 :: 어떤 이미지, 어떤 크기, 어떤 망인지 적어 둔다
대 묶음 :: 몇 대를 유지할지만 정해 둔다
붐빔 신호 :: 지금 몇 대가 모자란지 센다
새 대 :: 틀 그대로 찍혀 나와 묶음에 붙는다
= 사람이 만드는 게 아니라, 틀과 숫자만 있으면 알아서 찍힌다
```

## ⚠️ 해결하는 문제

```도해
대조: 새 서버를 사람이 손으로 만들면 무엇이 달라지나
손으로 만들면 || 틀로 찍으면
걸리는 시간 :: 사람을 기다린다 || 몇 분이면 뜬다
서로 다름 :: 대마다 조금씩 || 전부 똑같다
되돌리기 :: 기억에 기댄다 || 옛 틀로 바꾼다
= 대가 늘어날수록, 손으로 만들며 생긴 차이가 장애의 원인이 된다
```

대가 한 대일 때는 손으로 만들어도 된다. 열 대가 되면 아홉 대는 첫 대를 흉내 낸 것이고, 흉내는 매번 조금씩 어긋난다. 어긋난 한 대는 평소엔 조용하다가 트래픽이 몰릴 때만 다르게 죽는다. 그때 "이 대만 왜 이러지" 를 뒤지는 시간이 장애 시간의 대부분이 된다.

틀은 그 흉내를 없앤다. 새 대는 사람 손을 거치지 않고 틀에서 바로 나오므로 서로 다를 수가 없다. 자동 확장은 이 성질 위에 서 있다 — 새벽 세 시에 사람 없이 열 대가 더 떠야 한다면, 그 열 대가 무엇인지 미리 글로 적혀 있어야 한다.

## ⚙️ 작동 원리

틀의 성격은 "고칠 수 없다" 로 거의 다 정해진다. Google 문서는 인스턴스 템플릿이 똑같은 구성의 대를 만들려고 설계된 것이라 **만든 뒤에는 고칠 수 없다** 고 못 박는다. 바꾸려면 새 틀을 만들고, 대 묶음이 바라보는 틀을 새것으로 갈아 끼운다.

AWS 는 같은 성질을 번호로 다룬다. 시작 템플릿 하나 안에 번호가 붙은 여러 버전이 있고, 각 버전은 만든 뒤 그대로 굳는다. 대를 띄울 때 버전을 안 고르면 **기본 버전**이 쓰인다. 그래서 AWS 에서 "틀을 고쳤다" 는 말은 대개 새 버전을 만들고 기본 버전을 그쪽으로 옮겼다는 뜻이다.

Azure 는 틀을 따로 떼어 두지 않는다. 확장 집합 자체가 모델을 들고 있고, 그 모델을 고친 다음 도는 대들을 새 모델로 올린다. Microsoft 문서는 확장 집합의 모든 대가 **같은 기본 이미지와 구성에서 만들어진다** 고 적는다.

틀 안에 "설치할 때 최신 것을 받아 와라" 라고 적으면 이 모든 것이 무너진다. 어제 찍힌 대와 오늘 찍힌 대가 달라지기 때문이다. Google 문서가 소프트웨어 버전과 의존성을 틀에 못 박으라고 권하는 이유가 이것이다.

## 📊 비교: 세 클라우드는 이 틀을 어떻게 다루나

| | AWS | Azure | Google Cloud |
|---|---|---|---|
| 틀 이름 | 시작 템플릿 | 확장 집합의 모델 | 인스턴스 템플릿 |
| 찍어 내는 묶음 | Auto Scaling 그룹 · EC2 Fleet | Virtual Machine Scale Sets | 관리형 인스턴스 그룹 |
| 따로 떨어진 자원인가 | 그렇다 | 아니다. 집합 안에 있다 | 그렇다 |
| 바꾸는 법 | 새 버전을 만들고 기본 버전을 옮긴다 | 모델을 고치고 대를 새 모델로 올린다 | 못 고친다. 새 틀을 만든다 |
| 범위 | 리전 안 | 리소스 그룹 안 | 전역 또는 리전 |
| 틀 자체 요금 | 없다 | 없다 | 없다 |

## 💡 실제 사례

- **자동 확장** — 붐빔 신호가 뜨면 묶음이 틀에서 새 대를 찍어 붙이고, 한가해지면 도로 줄인다.
- **무중단 교체** — 새 틀을 만들어 갈아 끼우고 도는 대를 한 대씩 새 틀 것으로 바꿔 넣는다.
- **되돌리기** — 새 틀이 문제를 내면 옛 틀로 되돌린다. 그다음 찍히는 대부터 옛 모습으로 돌아온다.

## 🚫 흔한 오해

- **틀을 바꾸면 이미 도는 대도 같이 바뀐다** — 안 바뀐다. 틀은 다음에 찍히는 대에만 닿는다. 도는 대를 바꾸려면 하나씩 갈아 끼워야 한다.
- **틀 안에서 최신 것을 받아 오게 해 두면 늘 최신이라 좋다** — 같은 틀에서 찍은 대들이 찍힌 날짜에 따라 달라진다. Google 문서는 버전을 틀에 못 박으라고 적는다.
- **틀을 많이 만들면 요금이 는다** — 틀 자체는 공짜다. Google 문서는 틀에는 값을 매기지 않고 그것으로 만든 자원에만 값을 매긴다고 적는다.

## 🚨 주의사항

- **어느 버전이 기본인지 늘 확인해라.** AWS 는 버전을 여럿 두는 구조라, 기본 버전을 안 옮기면 고쳐 놓고도 옛 설정으로 대가 뜬다.
- **이름에 날짜를 넣어라.** Google 은 아예 못 고치므로 틀이 계속 쌓인다. 어느 것이 지금 쓰는 것인지 이름으로 알 수 있어야 한다.
- **비밀을 틀에 박지 마라.** 시작 스크립트와 사용자 데이터는 그 대 안의 조회 창구로 그대로 읽힌다.

## 📝 정리

**"같은 대를 몇 대든 찍어 내는 그 틀"** 이라고 읽으면 된다. 고칠 수 없다는 성질이 불편이 아니라 핵심이다 — 고칠 수 없으니 어제 찍힌 대와 오늘 찍힌 대가 같고, 그래야 자동 확장이 새벽에 사람 없이 돌 수 있다. 바꾸고 싶으면 새 틀을 만들고 가리키는 곳을 옮긴다.

## 🧒 열 살에게

붕어빵 틀 본 적 있지? 틀이 하나 있으면 백 개를 구워도 모양이 똑같고, 손님이 갑자기 몰려도 그냥 더 구우면 돼. 대신 모양을 바꾸고 싶으면 굽던 틀을 깎는 게 아니라 새 틀을 짜서 바꿔 끼워야 해.

## ❓ 이해했는지

- 틀을 바꿨는데 이미 도는 대들이 그대로인 이유는 무엇인가 → 흔한 오해
- 새벽에 손님이 몰릴 때 새 대는 누가 무엇을 보고 만드나 → 그림
- AWS 에서 틀을 고쳐 놓고도 옛 설정으로 대가 뜨는 일은 왜 생기나 → 주의사항
