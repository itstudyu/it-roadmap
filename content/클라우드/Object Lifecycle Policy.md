# Object Lifecycle Policy (객체 수명 규칙)

## 📝 정의

Object Lifecycle Policy 는 오래된 파일을 **저절로 내리거나 지우는** 규칙이다.

"며칠 지나면 싼 칸으로, 며칠 더 지나면 삭제" 를 미리 적어 두면 저장소가 알아서 실행한다. AWS 는 S3 Lifecycle, Azure 는 수명 주기 관리 정책, Google Cloud 는 객체 수명 주기 관리라 부른다. 사람이 지우러 오지 않는 저장소에서 요금이 조용히 불어나는 것을 막으려고 만들어졌다.

### 이름
Object :: 통에 넣은 덩어리
Life cycle :: 나서 죽기까지
Policy :: 미리 정해 둔 규칙
= 붙여 읽으면 "덩어리가 나서 죽기까지를 미리 정해 둔 규칙". 사람이 안 와도 실행된다

### 비유
사흘 지난 반찬은 아래 칸으로, 한 달 지난 건 버리기로 미리 정해 둔 냉장고 정리 규칙.

### 예
몇 년 전 로그가 그대로 쌓여 있고 아무도 안 열어 보는데 요금만 나가고 있는 그 청구서다.

## 🖼️ 그림으로 보기

```도해
흐름: 올려 둔 파일 하나는 어떤 길을 밟나
올린 날 :: 자주 여는 칸에 둔다
30일 :: 뜸해지면 싼 칸으로 내린다
90일 :: 거의 안 열면 보관용 칸으로 더 내린다
365일 :: 기한이 차면 지운다
= 사람이 손대지 않아도 이 길을 따라 저절로 내려간다
```

## ⚠️ 해결하는 문제

```도해
대조: 규칙을 안 걸어 두면 오래된 파일은 어떻게 되나
규칙 없이 || 규칙을 걸면
비싼 칸 :: 그대로 눌러앉는다 || 저절로 내려간다
지우기 :: 사람이 기억해야 || 기한이 되면 지운다
남은 옛 판 :: 조용히 쌓인다 || 몇 벌만 남긴다
= 저장소는 지우라고 말하기 전에는 절대 스스로 안 지운다
```

오브젝트 스토리지는 넣기가 너무 쉽다. 로그도, 백업도, 임시 파일도 다 들어가고 아무것도 저절로 나가지 않는다. 개수 제한도 없으니 경고도 안 뜬다. 그래서 몇 년치 로그가 가장 비싼 칸에 그대로 앉아 있고, 그것을 알아채는 건 대개 청구서를 뜯어보는 날이다.

수명 규칙은 그 청소를 미리 글로 적어 두는 일이다. 지우는 것만 하는 게 아니라 **등급을 내리는 일**이 절반이다. 안 여는 파일을 싼 칸으로 옮겨 두면 지우지 않고도 값이 떨어진다. 사람이 기억할 필요가 없다는 것이 핵심이다 — 기억에 기댄 청소는 반드시 잊힌다.

## ⚙️ 작동 원리

규칙 하나는 **조건**과 **동작**으로 이루어진다. 조건은 나이, 이름 앞머리, 태그, 마지막으로 연 날 같은 것이고, 동작은 크게 셋이다 — 등급을 내리기, 지우기, 올리다 만 조각 치우기. Google 문서는 조건을 **전부** 만족해야 동작이 걸린다고 적는다.

내려가는 칸은 값과 기다림을 맞바꾼 사다리다.

```도해
층: 등급을 내리면 무엇을 내주고 무엇을 얻나
자주 여는 칸 :: 보관은 비싸고 꺼내기는 거의 공짜다
뜸한 칸 :: 보관이 싸지는 대신 꺼낼 때 값을 낸다
차가운 칸 :: 더 싸지고 최소 보관 기간이 길어진다
보관용 칸 :: 가장 싸지만 꺼내는 데 분에서 시간이 걸린다
= 내려갈수록 두는 값은 싸지고, 꺼내는 값과 기다리는 시간은 커진다
```

그래서 무엇을 어디에 둘지는 "얼마나 자주 여나" 가 아니라 "급할 때 몇 분 안에 필요하나" 로 고른다. 복구 목표 시간이 한 시간인 백업을 보관용 칸에 두면 규정상 백업은 있지만 실제로는 못 쓴다.

실행은 즉시가 아니다. Google 문서는 규칙을 바꾸면 반영에 최대 24시간이 걸리고, 조건을 만족한 뒤에도 실제 동작까지 시차가 있다고 적는다. Azure 도 규칙을 넣거나 고치면 첫 실행까지 최대 24시간이 걸린다고 적는다. AWS 는 조금 다르게, 실제 처리가 늦더라도 **자격이 생긴 시점부터** 요금을 바꿔 매긴다고 적는다.

## 📊 비교: 세 클라우드는 이 규칙을 어떻게 쓰나

| | AWS S3 | Azure Blob | Google Cloud Storage |
|---|---|---|---|
| 부르는 이름 | S3 Lifecycle | 수명 주기 관리 정책 | 객체 수명 주기 관리 |
| 등급 내리기 | Transition | tierToCool · tierToCold · tierToArchive | SetStorageClass |
| 지우기 | Expiration | delete | Delete |
| 고르는 조건 | 앞머리 · 태그 · 나이 | 앞머리 · 인덱스 태그 · 만든 날 · 고친 날 · 마지막으로 연 날 | 나이 · 앞머리 · 남은 새 판 수 |
| 옛 판 정리 | 비현행 판 만료 규칙 | 이전 버전 규칙 | numNewerVersions · daysSinceNoncurrentTime |
| 언제 도나 | 자격이 생긴 뒤 비동기 | 규칙 변경 뒤 최대 24시간 | 규칙 변경 반영에 최대 24시간 |

## 💡 실제 사례

- **로그 정리** — 30일은 자주 여는 칸, 90일 뒤 보관용, 1년 뒤 삭제를 규칙 한 줄로 정해 둔다.
- **옛 판 정리** — 판 보관을 켠 통에서 최신 세 판만 남기고 나머지는 지우게 걸어 둔다.
- **끊긴 업로드 청소** — 여러 조각으로 나눠 올리다 만 찌꺼기를 이레 뒤 자동으로 걷어낸다.

## 🚫 흔한 오해

- **저장하면 그 자리에서 바로 정리된다** — 아니다. Google 문서는 규칙 변경 반영에 최대 24시간, Azure 는 첫 실행까지 최대 24시간이 걸린다고 적는다.
- **지우는 규칙이니 요금은 무조건 준다** — 등급을 내리는 요청 하나하나에 값이 붙고, 싼 칸에는 최소 보관 기간이 있어 일찍 지우면 그만큼 더 문다. 자잘한 파일이 수억 개면 옮기는 값이 아낀 값을 넘길 수도 있다.
- **버킷 권한으로 막아 두면 규칙도 못 지운다** — AWS 문서는 버킷 정책으로 수명 규칙의 삭제나 이동을 막을 수 없다고, 모든 주체에게 모든 행동을 거부해도 수명 규칙은 정상 동작한다고 못 박는다.

## 🚨 주의사항

- **잠긴 통에는 안 먹는다.** Azure 문서는 변경 불가 컨테이너의 블롭에는 삭제 동작이 통하지 않는다고 적는다. 잠금과 수명 규칙을 같이 쓸 때는 기한이 겹치지 않게 잡아야 한다.
- **판 보관을 켰으면 규칙을 따로 걸어라.** AWS 문서는 판 보관을 켠 뒤에도 옛 판을 지우려면 비현행 판 만료 규칙을 따로 넣어야 한다고 적는다.
- **꺼내는 값을 먼저 세어라.** 자주 꺼낼 것을 싼 칸으로 내리면 보관비는 줄고 꺼내는 값이 그보다 크게 는다.

## 📝 정리

**"오래되면 알아서 내리고 지우는 그 규칙"** 이라고 읽으면 된다. 고르는 기준은 파일이 얼마나 오래됐느냐가 아니라 **급할 때 몇 분 안에 필요하냐**다. 그리고 실행은 즉시가 아니라서, 규칙을 걸어 놓고 그날 밤에 확인하면 아무 일도 안 일어나 있다.

## 🧒 열 살에게

냉장고에 반찬을 넣어 두면 아무도 안 치우니까 계속 쌓이지? 그래서 사흘 지나면 아래 칸, 한 달 지나면 버리기라고 미리 종이에 적어 붙여 두는 거야. 그러면 매번 기억하지 않아도 오래된 건 저절로 자리를 옮기거나 없어져.

## ❓ 이해했는지

- 규칙을 저장했는데 그날 밤에도 아무것도 안 지워진 이유는 무엇인가 → 흔한 오해
- 싼 칸으로 내렸는데 요금이 되레 늘어나는 일은 왜 생기나 → 작동 원리
- 판 보관을 켠 통에서 옛 판이 안 지워지는 건 무엇이 빠진 탓인가 → 주의사항
