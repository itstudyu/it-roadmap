# Well-Architected (잘 설계된 프레임워크)

## 📝 정의

Well-Architected는 **설계가 좋은지 기둥별로 캐묻는 질문 목록**이다.

AWS 문서는 이 틀을 "특정 아키텍처가 클라우드 모범 사례에 맞는지 알아보게 하는 기본 질문들" 이라고 적고, 검토는 감사가 아니라 설계 결정을 놓고 나누는 건설적인 대화라고 못 박는다. 세 클라우드가 저마다 같은 이름의 틀을 두고 있다.

### 이름
Well :: 잘
Architected :: 설계된
= 붙여 읽으면 "잘 설계된". 무엇이 '잘' 인지를 기둥 몇 개로 못 박아 둔 것이 이 틀이다

### 비유
건강검진 문진표. 어디가 아프냐고 한 번 묻는 대신 눈·이·허리를 하나씩 짚어야 빠뜨린 곳이 나온다.

### 예
"이 구성 괜찮나요" 라는 물음에 "괜찮은 것 같은데요" 로 끝나던 회의가, 기둥별로 나눠 물으면 빈칸이 줄줄이 나온다.

## 🖼️ 그림으로 보기

```도해
대조: "이 구성 괜찮나요" 를 어떻게 물어야 하나
기둥 없이 || 기둥별로
대답 :: "괜찮은 것 같다" || 항목마다 답이 나온다
빠진 것 :: 안 물었으니 모른다 || 빈칸이 드러난다
맞바꿈 :: 무엇을 내줬는지 흐릿 || 내준 기둥이 보인다
= 좋은 설계는 감으로 정하는 것이 아니라 기둥별 질문에 답한 결과다
```

## ⚠️ 해결하는 문제

```도해
대조: 기둥 목록이 없으면 무엇이 빠지나
잣대가 없으면 || 기둥 목록으로
놓치는 것 :: 비용만 보다 만다 || 여섯 칸을 다 짚는다
문제 발견 :: 사고 난 뒤에 안다 || 설계할 때 안다
팀 합의 :: 취향 싸움이 된다 || 기둥 이름을 댄다
= 무엇을 물어야 하는지 정해 두면, 안 물어서 빠지는 칸이 없어진다
```

설계가 좋은지는 눈으로 봐서는 안 나온다. 급한 사람은 비용만 보고, 겁이 많은 사람은 보안만 본다. 그러면 안 본 기둥이 남고, 그 기둥은 대개 사고가 난 뒤에야 이름이 불린다.

AWS 의 기둥은 여섯이다 — 운영 우수성·보안·안정성·성능 효율·비용 최적화·지속 가능성. 기둥 목록이 하는 일은 답을 주는 것이 아니라 **물음을 고정하는 것**이다. 기둥마다 설계 원칙과 모범 사례가 딸려 있어서, 같은 워크로드를 두 사람이 봐도 같은 자리를 짚게 된다. 그래서 논쟁이 취향 싸움 대신 "어느 기둥을 얼마나 내줄 것인가" 로 바뀐다.

## 📊 비교: 세 곳의 기둥은 어디가 같고 어디가 다른가

| 기둥 | AWS (여섯) | Azure (다섯) | Google (여섯) |
|---|---|---|---|
| **운영 우수성** | 있다 | 있다 | 있다 |
| **보안** | 있다 | 있다 | 있다 (개인정보·규정 준수 포함) |
| **안정성** | 있다 | 있다 | 있다 |
| **성능** | 성능 효율 | 성능 효율 | 성능 최적화 |
| **비용 최적화** | 있다 | 있다 | 있다 |
| **지속 가능성** | 있다 | 없다 | 있다 |

## ⚙️ 작동 원리

검토는 워크로드 하나를 고르는 것에서 시작한다. AWS 문서는 워크로드를 "업무 가치를 함께 만들어 내는 구성 요소 묶음" 으로 정의하고, 회사에 필요한 워크로드를 전부 모은 것은 따로 기술 포트폴리오라 부른다. 재는 단위는 그 포트폴리오가 아니라 워크로드 하나다. 그 워크로드를 놓고 기둥별 질문에 답하면 답이 안 나오는 칸이 남고, 그 칸이 곧 개선 항목이 된다. AWS는 이 과정을 도구로도 제공하며, 문서는 이것이 감사 장치가 아니라 대화라고 적는다. Azure도 같은 자리에 검토 도구를 두고, 그 결과를 Azure Advisor 점수로 기둥별로 묶어 보여준다.

핵심은 **기둥끼리 맞바꿈이 있다**는 것이다. Azure 문서는 기둥마다 tradeoffs(맞바꿈) 문서를 따로 둔다. 한 기둥을 올리면 다른 기둥이 내려간다는 뜻이다 — 복제본을 늘리면 안정성 쪽은 올라가고 비용 최적화 쪽은 내려간다. 그래서 목표는 여섯 칸 만점이 아니라 **무엇을 내주었는지 말할 수 있는 상태**다. 다만 AWS 문서는 보안과 운영 우수성은 대체로 다른 기둥과 맞바꾸지 않는다고 적는다.

## 💡 실제 사례

- **설계 검토 회의** — 기둥 이름으로 안건을 나누면 "느낌상 불안하다" 가 "안정성 기둥의 복구 목표가 없다" 로 바뀐다.
- **검토 도구를 돌렸을 때** — Azure 는 결과를 기둥별 점수로 묶어 보여준다. 어느 기둥이 낮은지가 먼저 눈에 띈다.
- **이전 뒤 정리** — 옮겨온 구성을 기둥별로 한 번 훑으면 손대야 할 곳이 목록으로 나온다.

## 🚫 흔한 오해

- **여섯 기둥을 다 만점 받아야 한다** — 아니다. 기둥끼리 맞바꿈이 있어서 Azure 문서는 기둥마다 맞바꿈 문서를 따로 둔다.
- **검토는 통과와 탈락을 가리는 감사다** — AWS 문서는 이것이 감사 장치가 아니라 설계 결정을 놓고 나누는 건설적인 대화라고 적는다.
- **한 곳 것이니 다른 클라우드에는 안 쓴다** — 세 곳 모두 같은 이름의 틀을 두고 있고 기둥 이름이 거의 겹친다.

## 📝 정리

**"좋은 설계인지 기둥별로 캐묻는 목록"** 이라고 읽으면 된다. 답을 주는 문서가 아니라 물음을 고정하는 문서라서, 안 물어봐서 빠지는 칸이 없어지는 것이 값어치다. 기둥끼리는 서로 맞바꿈이라, 목표는 전부 만점이 아니라 무엇을 내주었는지 말할 수 있는 상태다.

## 🧒 열 살에게

어디 아프냐고 한 번 물으면 "그냥 좀 이상해" 밖에 말 못 하지? 그래서 병원에서는 눈은 어때, 이는 어때, 하나씩 나눠서 물어봐. 그렇게 칸을 나눠 물어야 빠뜨린 데가 안 생겨.
