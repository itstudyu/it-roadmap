# VPC (Virtual Private Cloud)

## 📝 정의

VPC는 Virtual Private Cloud의 약자로, 클라우드 제공업체(AWS, GCP, Azure 등)의 공용 클라우드 인프라 내에서 논리적으로 격리된 사설 네트워크 환경을 의미합니다. 마치 공용 시설(인터넷) 위에 자신의 사설 네트워크를 구축하는 것과 같으며, VPC 내의 모든 리소스(서버, 데이터베이스, 로드밸런서 등)는 자신이 정의한 네트워크 규칙에 따라 통신하게 됩니다.

VPC는 클라우드 컴퓨팅의 가장 기본적이면서도 중요한 개념으로, 온프레미스(온사이트) 데이터센터의 네트워크처럼 동작합니다. 고객은 VPC 내에서 IP 주소 범위를 결정하고, 서브넷을 구성하고, 방화벽 규칙을 설정하며, 인터넷 접근을 제어할 수 있습니다. 이를 통해 기업은 클라우드에서도 온프레미스만큼의 네트워크 제어와 보안을 달성할 수 있게 되었습니다.

### 한 줄 요약
> 클라우드 내에서 자신만의 사설 네트워크를 구축하고 완전히 제어할 수 있는 격리된 환경

### 비유
- 🔵 **비유 1**: 아파트 단지와 같은 개념. 전체 클라우드는 거대한 도시이지만, VPC는 철저히 보안된 담장이 있는 아파트 단지 같은 별도의 공간입니다. 단지 안의 건물들(인스턴스)만 안의 도로(네트워크)를 통해 서로 통신합니다.
- 🟡 **비유 2**: 은행의 사설 네트워크와 같습니다. 인터넷 어딘가의 클라우드 위에 있지만, 은행만의 독립된 네트워크 규칙과 보안 정책이 적용됩니다.
- 🟢 **비유 3**: 회사의 사무실 건물. 건물 안에는 여러 부서(서브넷)가 있고, 각 부서는 건물 내 복도(라우팅)를 통해 소통합니다.

## 🎯 핵심 개념

### 1. VPC의 기본 구성 요소
VPC는 여러 핵심 구성 요소로 이루어집니다. 첫째, IP 주소 공간(CIDR 블록)으로, VPC 내 모든 리소스의 사설 IP 주소 범위를 정의합니다. AWS에서는 보통 10.0.0.0/16 같은 범위를 사용합니다. 둘째, 서브넷(Subnet)으로, VPC를 더 작은 네트워크로 나누는 단위입니다. 셋째, 라우트 테이블(Route Table)로, 트래픽이 어디로 이동해야 하는지를 정의합니다. 넷째, 인터넷 게이트웨이(Internet Gateway)로, VPC 내의 리소스가 인터넷과 통신하게 해줍니다. 다섯째, NAT 게이트웨이(NAT Gateway)로, 프라이빗 리소스가 아웃바운드 인터넷 통신을 할 수 있게 해줍니다. 여섯째, 보안 그룹(Security Group)과 네트워크 ACL(Access Control List)로, 인/아웃바운드 트래픽을 제어합니다.

### 2. 퍼블릭과 프라이빗 서브넷
VPC 내의 서브넷은 크게 두 가지 유형으로 나뉩니다. 퍼블릭 서브넷은 인터넷 게이트웨이로 직접 연결되어 있어서, 이 서브넷 내의 리소스(예: 웹 서버)가 인터넷으로부터 직접 요청을 받을 수 있습니다. 반면 프라이빗 서브넷은 인터넷과 직접 연결되지 않아서, 이 서브넷 내의 리소스(예: 데이터베이스)는 외부에서 직접 접근할 수 없습니다. 대신 NAT 게이트웨이를 통해 아웃바운드 통신을 할 수 있으므로, 인터넷에서 패치를 다운로드할 수 있으면서도 인바운드 접근으로부터 보호됩니다. 이러한 구조는 "다중 계층 아키텍처"의 기반이 되어, 웹 계층은 퍼블릭 서브넷에 배치하고 데이터베이스 계층은 프라이빗 서브넷에 배치할 수 있습니다.

### 3. 네트워크 보안과 접근 제어
VPC에서 네트워크 보안은 여러 계층에서 구현됩니다. 첫째, 보안 그룹(Security Group)은 인스턴스 수준의 가상 방화벽으로, 각 인스턴스에 대한 인/아웃바운드 트래픽을 제어합니다. 예를 들어 웹 서버의 보안 그룹은 80번(HTTP)과 443번(HTTPS) 포트만 허용하고 나머지는 차단할 수 있습니다. 둘째, 네트워크 ACL(NACL)은 서브넷 수준의 방화벽으로, 서브넷 내외의 트래픽을 제어합니다. 셋째, VPC 내의 리소스들은 기본적으로 사설 IP 주소를 가지고 있어서 인터넷으로부터 직접 접근이 불가능하므로, 이미 상당한 보안이 구현되어 있습니다. 이러한 다층 방어 체계는 네트워크 레벨의 공격으로부터 인프라를 보호합니다.

### 4. 온프레미스와의 연결
기업은 종종 기존의 온프레미스 데이터센터와 AWS VPC를 연결해야 합니다. 이를 위해 몇 가지 방법이 있습니다. VPN(Virtual Private Network)을 사용하면 인터넷을 통해 암호화된 터널을 만들어 연결할 수 있습니다. 더 안정적인 연결이 필요하면 AWS Direct Connect를 사용하여 전용 네트워크 연결을 구축할 수 있습니다. 또한 VPC Peering을 사용하여 다른 VPC와 연결할 수 있고, Transit Gateway를 사용하면 여러 VPC와 온프레미스 네트워크를 중앙에서 관리할 수 있습니다. 이러한 연결 방식들은 하이브리드 클라우드 아키텍처를 가능하게 합니다.

## ⚠️ 해결하는 문제

### 문제 1: 클라우드 환경에서의 네트워크 보안
퍼블릭 클라우드는 매우 많은 사용자가 사용하는 공용 인프라이므로, 기본적으로 보안 위험이 높습니다. 자신의 리소스가 클라우드의 어디에 위치하든 다른 조직의 리소스와 물리적으로 가까울 수 있으며, 인터넷을 통해 어디서든 접근 가능한 상태입니다. VPC는 이러한 문제를 해결하여, 클라우드 내에서도 자신의 네트워크를 논리적으로 격리하고 완전히 통제할 수 있게 합니다. 보안 그룹과 네트워크 ACL을 통해 어떤 트래픽을 허용할지를 세밀하게 제어할 수 있으므로, 온프레미스 데이터센터 수준의 보안을 달성할 수 있습니다. 이를 통해 기업은 클라우드의 비용 효율성을 누리면서도 보안을 타협하지 않을 수 있습니다.

### 문제 2: 복잡한 네트워크 아키텍처 관리
전통적인 온프레미스 환경에서 기업은 여러 부서나 팀을 위해 복잡한 네트워크 구조를 구축해야 했습니다. 각 부서는 자신의 IP 주소 범위를 가져야 하고, 부서 간 통신 정책을 정의해야 하며, 외부 인터넷과의 연결을 제어해야 했습니다. 이러한 작업은 물리적 라우터와 방화벽 설정을 통해 수행되었으므로 매우 복잡했습니다. VPC는 이를 코드처럼 정의할 수 있게 함으로써, 복잡한 네트워크 아키텍처를 빠르게 구축하고 수정할 수 있게 합니다. Infrastructure as Code 원칙에 따라 네트워크 설정을 버전 관리하고 자동화할 수 있으므로, 재현 가능하고 일관성 있는 환경 구축이 가능합니다.

### 문제 3: 멀티 테넌트 환경에서의 데이터 격리
클라우드 제공업체는 수많은 고객을 동시에 서빙합니다. 각 고객의 데이터와 리소스가 서로 격리되어야 하는데, VPC가 없다면 모든 리소스가 공용 네트워크에 노출됩니다. VPC를 통해 각 고객은 자신만의 격리된 네트워크 환경을 가질 수 있으므로, 한 고객의 리소스가 다른 고객의 리소스에 접근할 수 없게 합니다. 이는 네트워크 수준의 자연스러운 격리를 제공하므로, 멀티 테넌트 환경의 기본 보안 요구사항을 충족합니다. 더군다나 각 VPC는 자신만의 라우팅 테이블, 보안 규칙, 주소 공간을 가지므로, 완전히 독립적인 네트워크처럼 동작합니다.

### 문제 4: 고가용성과 재해 복구
단일 지역의 단일 데이터센터에 모든 리소스를 배치하면, 그 데이터센터에 장애가 발생할 경우 전체 서비스가 다운됩니다. VPC는 여러 가용 영역(Availability Zone)에 걸쳐 리소스를 배포할 수 있게 하므로, 한 데이터센터의 장애로부터 자동으로 복구될 수 있습니다. 각 가용 영역에 서브넷을 배치하고, 로드 밸런서를 앞에 두면 자동으로 트래픽이 정상 가용 영역으로 전달됩니다. 또한 VPC는 여러 지역에 복제할 수 있으므로, 지역 전체의 재해로부터도 복구할 수 있는 아키텍처를 구축할 수 있습니다.

## ⚙️ 작동 원리

### 1단계: VPC 생성 및 IP 주소 공간 할당
VPC를 생성할 때 먼저 CIDR 블록을 지정합니다. 예를 들어 10.0.0.0/16으로 설정하면, VPC 내에서 10.0.0.1부터 10.0.255.254까지의 주소를 사용할 수 있습니다. 이 주소들은 VPC 내에서만 유효하며, 인터넷에서 직접 라우팅되지 않습니다(RFC 1918 사설 주소). 이렇게 설정된 IP 주소 공간은 VPC의 기초가 되며, 이 범위 내에서만 서브넷과 리소스를 생성할 수 있습니다.

### 2단계: 서브넷 생성 및 가용 영역 배치
VPC를 생성한 후, 이를 더 작은 서브넷으로 나눕니다. 각 서브넷은 특정 가용 영역에 속하며, 고가용성을 위해 여러 가용 영역에 걸쳐 배치합니다. 예를 들어 10.0.1.0/24는 가용 영역 1a에, 10.0.2.0/24는 가용 영역 1b에 배치합니다. 각 서브넷 내에서도 첫 4개(10.0.1.0~10.0.1.3)와 마지막 주소(10.0.1.255)는 AWS가 예약하므로, 실제로 사용 가능한 주소는 10.0.1.4부터 10.0.1.254까지입니다.

### 3단계: 라우팅 테이블 설정
라우팅 테이블은 트래픽이 어디로 이동해야 하는지를 정의합니다. 예를 들어 "0.0.0.0/0(모든 외부 트래픽)은 Internet Gateway로 보내라"는 규칙을 설정하면 퍼블릭 서브넷이 됩니다. 반면 "0.0.0.0/0(모든 외부 트래픽)은 NAT Gateway로 보내라"는 규칙을 설정하면, 내부에서 인터넷 요청을 할 수 있으면서도 외부에서 들어오는 요청은 차단됩니다. VPC 내부의 트래픽(10.0.0.0/16)은 기본적으로 로컬 라우팅되어 같은 VPC 내의 다른 서브넷으로 이동합니다.

### 4단계: 인터넷 게이트웨이와 NAT 게이트웨이 구성
인터넷 게이트웨이(IGW)는 VPC와 인터넷을 연결하는 게이트웨이입니다. IGW가 없으면 VPC의 리소스가 인터넷에 접근할 수 없습니다. IGW를 통한 통신은 공용 IP 주소를 필요로 하므로, 인터넷에 노출되려는 리소스만 공용 IP를 할당받습니다. NAT 게이트웨이는 프라이빗 리소스가 아웃바운드 인터넷 통신을 할 수 있게 해주는 게이트웨이입니다. NAT 게이트웨이를 통과하는 트래픽은 NAT 게이트웨이의 공용 IP에서 출발하는 것으로 보이므로, 프라이빗 리소스의 IP 주소가 인터넷에 노출되지 않습니다.

### 5단계: 보안 그룹과 네트워크 ACL 설정
보안 그룹(Security Group)은 인스턴스 수준의 스테이트풀(Stateful) 방화벽입니다. 인바운드 규칙에서 80번 포트를 허용하면, 해당 포트로 들어오는 트래픽과 그에 대한 응답이 모두 허용됩니다. 보안 그룹은 기본적으로 모든 아웃바운드를 허용하고 모든 인바운드를 차단하는 "화이트리스트" 방식으로 작동합니다. 네트워크 ACL(NACL)은 서브넷 수준의 스테이트리스(Stateless) 방화벽으로, 인바운드와 아웃바운드를 모두 명시적으로 규칙으로 지정해야 합니다. 보안 그룹과 NACL 두 계층을 모두 통과해야 트래픽이 리소스에 도달합니다.

### 6단계: 트래픽 전달 및 응답
사용자의 요청이 들어오면, 먼저 라우팅 테이블에 따라 어느 게이트웨이로 보낼지가 결정됩니다. 인터넷에서 온 트래픽은 IGW를 통해 VPC에 진입합니다. 그 다음 NACL과 보안 그룹을 통과하는지 확인됩니다. 두 방화벽을 모두 통과하면 트래픽이 대상 인스턴스에 도달합니다. 응답은 역방향으로 이동하며, 보안 그룹과 NACL의 아웃바운드 규칙을 확인하여 인터넷으로 돌려보냅니다.

### Mermaid 다이어그램: VPC 트래픽 흐름

```도해
흐름: VPC, 무슨 순서로 오가나
사용자 :: 요청 (인터넷)
Internet Gateway :: 라우팅
퍼블릭 서브넷 (웹 서버) :: 내부 통신 (DB 조회)
프라이빗 서브넷 (DB 서버) :: 응답
퍼블릭 서브넷 (웹 서버) :: 응답
Internet Gateway :: 최종 응답
```

| 항목 | VPC | 온프레미스 |
|------|-----|----------|
| **물리적 위치** | 클라우드 데이터센터 | 회사 건물 |
| **구축 시간** | 분 단위 | 주/월 단위 |
| **초기 투자** | 없음 | 수백만 원 |
| **유지보수** | 클라우드 제공업체 | 자체 관리 |
| **확장성** | 즉시 확장 가능 | 물리적 제약 있음 |
| **보안 제어** | 사용자가 설정 | 사용자가 설정 |
| **라우팅 변경** | 수 분 내 | 수 일 소요 |
| **리소스 이동** | 클릭 한 번 | 물리적 재배치 |
| **비용 모델** | 사용한 만큼 지불 | 고정 비용 |
| **다중 위치** | 클릭으로 지역 확대 | 별도 건설 필요 |

### 보안 그룹 vs 네트워크 ACL

| 항목 | 보안 그룹 | 네트워크 ACL |
|------|---------|-----------|
| **적용 대상** | 인스턴스 | 서브넷 |
| **상태 추적** | Stateful (연결 추적) | Stateless (규칙만 확인) |
| **기본 정책** | 모두 차단, 허용 추가 | 모두 차단, 허용 추가 |
| **규칙 적용** | 모든 규칙 평가 | 순서대로 평가, 일치 시 중단 |
| **성능 영향** | 인스턴스 수준 | 서브넷 수준 |
| **응답 트래픽** | 자동 허용 | 명시적 규칙 필요 |
| **관리 복잡도** | 낮음 | 높음 |
| **사용 사례** | 대부분의 경우 | 서브넷 수준 격리 필요 |

### 퍼블릭 vs 프라이빗 서브넷

| 항목 | 퍼블릭 서브넷 | 프라이빗 서브넷 |
|------|-----------|------------|
| **인터넷 접근** | 직접 가능 | 간접 가능 (NAT 경유) |
| **인바운드** | 외부에서 직접 접근 가능 | 외부에서 직접 접근 불가 |
| **아웃바운드** | 직접 인터넷으로 | NAT 경유로 인터넷으로 |
| **공용 IP** | 필수 | 선택사항 |
| **라우팅** | IGW로 기본 라우팅 | NAT/NAT Gateway로 라우팅 |
| **용도** | 웹 서버, 로드밸런서 | 데이터베이스, 애플리케이션 서버 |
| **보안 수준** | 낮음 (인터넷 노출) | 높음 (격리됨) |
| **구성 복잡도** | 간단 | 복잡 |

## ✅ 장점과 단점

### 장점

**1. 완벽한 네트워크 제어**: VPC 내에서 IP 주소, 라우팅, 보안 규칙을 완전히 제어할 수 있습니다. 온프레미스 네트워크처럼 자신만의 네트워크를 설계할 수 있으면서도, 클라우드의 유연성과 확장성을 누릴 수 있습니다.

**2. 향상된 보안**: 격리된 네트워크 환경으로 인해 다른 조직의 리소스로부터 기본적으로 보호됩니다. 보안 그룹과 NACL을 통한 다층 방어로 의도하지 않은 접근을 원천 차단할 수 있습니다.

**3. 비용 효율성**: 온프레미스에서는 초기에 큰 비용을 들여 물리적 네트워크를 구축해야 하지만, VPC는 필요한 만큼만 사용하고 비용을 지불합니다.

**4. 빠른 구축 및 변경**: 물리적 라우터나 스위치 구축 없이 분 단위로 네트워크를 구축하고 변경할 수 있습니다. 개발 환경, 테스트 환경, 프로덕션 환경을 각각 별도의 VPC로 구성할 수 있습니다.

**5. 높은 가용성**: 여러 가용 영역에 걸쳐 리소스를 배포할 수 있으므로, 자동으로 장애 복구 기능을 구현할 수 있습니다.

**6. 하이브리드 환경 지원**: VPN이나 Direct Connect를 통해 온프레미스 네트워크와 VPC를 연결하여 하이브리드 클라우드 환경을 구축할 수 있습니다.

### 단점

**1. 네트워크 설계의 복잡성**: VPC, 서브넷, 라우팅, 보안 그룹 등 여러 개념을 이해하고 올바르게 설계해야 합니다. 잘못된 설계는 보안 문제나 성능 저하로 이어질 수 있습니다.

**2. IP 주소 관리의 어려움**: IP 주소 공간을 미리 계획해야 하고, 나중에 변경하기 어렵습니다. VPC CIDR을 10.0.0.0/16으로 설정했는데 나중에 10.0.0.0/8로 확대하려면 복잡한 마이그레이션이 필요합니다.

**3. 보안 설정의 실수 위험**: 보안 그룹을 0.0.0.0/0(모든 IP)에서 접근 가능하게 설정하면 대량의 공격 대상이 됩니다. 또는 프라이빗 서브넷이 인터넷에 노출되도록 설정하는 등의 실수가 발생할 수 있습니다.

**4. 모니터링의 복잡성**: 네트워크 트래픽을 모니터링하고 문제를 디버깅하는 것이 온프레미스보다 어려울 수 있습니다. VPC Flow Logs 등의 도구를 사용해야 하며, 데이터 해석이 복잡합니다.

**5. 비용 증가**: 각 Elastic IP, NAT Gateway, VPC Endpoint 등이 비용을 발생시킵니다. 복잡한 네트워크 구조는 더 많은 리소스 사용으로 이어져 비용이 증가할 수 있습니다.

**6. 트러블슈팅의 어려움**: 네트워크 문제가 발생했을 때, 라우팅 테이블, 보안 그룹, NACL, 라우트 53 DNS 설정 등 여러 곳을 확인해야 하므로 원인 파악이 어렵습니다.

**7. 학습 곡선**: VPC를 이해하고 효과적으로 설계하려면 네트워킹에 대한 기본 지식과 AWS 서비스에 대한 이해가 필요합니다.

## 💡 실제 사용 사례

### 전자상거래 플랫폼의 VPC 구성
한 전자상거래 회사는 VPC를 사용하여 웹 서버, 애플리케이션 서버, 데이터베이스를 계층별로 분리합니다. 퍼블릭 서브넷에는 로드 밸런서와 웹 서버를 배치하여 고객의 요청을 받습니다. 프라이빗 서브넷에는 애플리케이션 서버와 RDS 데이터베이스를 배치하여 인터넷에 노출되지 않게 합니다. 또한 여러 가용 영역에 동일한 구조를 복제하여 한 데이터센터 장애 시에도 서비스가 계속되도록 합니다.

### 멀티 테넌트 SaaS 서비스
SaaS 회사는 각 고객을 위해 별도의 VPC를 생성하거나, 같은 VPC 내에서 보안 그룹으로 고객을 분리합니다. 이를 통해 고객 간 데이터를 네트워크 레벨에서 격리하고, 각 고객의 피크 사용 시간이 다르므로 리소스를 효율적으로 공유합니다. 또한 높은 보안 요구사항이 있는 고객에게는 전용 VPC를 제공할 수 있습니다.

### 하이브리드 클라우드 환경
기존 온프레미스 데이터센터를 운영하는 기업은 VPC를 생성하고 VPN 또는 Direct Connect로 온프레미스 네트워크와 연결합니다. 레거시 시스템은 온프레미스에 유지하면서, 새로운 마이크로서비스는 클라우드 VPC에 배포합니다. 이를 통해 점진적으로 클라우드로 전환하면서도 기존 시스템의 가동을 유지할 수 있습니다.

### 개발/테스트 및 프로덕션 환경 분리
개발팀은 프로덕션 환경과 동일한 구조의 별도 VPC를 구성하여 테스트 환경을 만듭니다. 개발자들이 프로덕션 리소스에 우연히 접근할 수 없도록 네트워크 레벨에서 격리하고, 각 환경에 다른 보안 정책을 적용합니다. 또한 프로덕션 환경의 실제 데이터는 사용하지 않고 테스트 데이터만 사용하여 보안과 프라이버시를 보호합니다.

## 🔗 관련 용어

- **서브넷 (Subnet)**: VPC를 더 작은 네트워크 단위로 나누는 것입니다.
- **라우팅 테이블 (Route Table)**: 트래픽이 어디로 이동해야 하는지를 정의하는 규칙 집합입니다.
- **인터넷 게이트웨이 (Internet Gateway)**: VPC와 인터넷을 연결하는 게이트웨이입니다.
- **NAT 게이트웨이 (NAT Gateway)**: 프라이빗 리소스가 아웃바운드 인터넷 통신을 할 수 있게 합니다.
- **보안 그룹 (Security Group)**: 인스턴스 수준의 스테이트풀 방화벽입니다.
- **네트워크 ACL (Network ACL)**: 서브넷 수준의 스테이트리스 방화벽입니다.
- **CIDR 표기법**: IP 주소 범위를 표현하는 표기법입니다.
- **Elastic IP**: 인스턴스에 할당할 수 있는 고정 공용 IP 주소입니다.
- **VPC Peering**: 두 VPC를 직접 연결하는 기능입니다.
- **AWS Transit Gateway**: 여러 VPC와 온프레미스 네트워크를 중앙에서 관리하는 게이트웨이입니다.
