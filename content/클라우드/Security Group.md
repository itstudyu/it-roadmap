# Security Group (보안 그룹)

## 📝 정의

보안 그룹은 **자원 하나하나에 붙는 허용 규칙 묶음**이다.

적을 수 있는 것은 허용뿐이고 거부는 적을 수 없다. 새로 만든 보안 그룹에는 인바운드 규칙이 하나도 없어서 규칙을 넣기 전까지 들어오는 것이 전부 막히고, 나가는 쪽은 반대로 처음부터 전부 허용된 규칙 하나가 들어 있다. 클라우드마다 이름도 규칙도 조금씩 다르다 — Azure 의 네트워크 보안 그룹(NSG)은 자리는 같지만 허용과 거부를 둘 다 적고, 우선순위 번호가 낮은 것부터 보다가 맞으면 거기서 멈춘다.

### 이름
Security :: 지킬 규칙
Group :: 이름 붙인 묶음
= 붙여 읽으면 "지킬 규칙을 묶어 놓은 이름표". 기계가 아니라 묶음에 규칙을 적고, 그 묶음을 자원에 붙인다

### 비유
아파트 현관의 방문객 명단. 명단에 적힌 사람만 들어오고, 내가 내보낸 심부름꾼이 돌아오는 것은 따로 안 적어도 통과한다.

### 예
새로 띄운 서버에 접속이 안 돼서 22번 포트를 열어 준 그 순간이 이 규칙을 만지는 자리다.

## 🖼️ 그림으로 보기

```도해
흐름: 밖에서 온 접속 하나에 보안 그룹은 무엇을 하나
접속 도착 :: 출발지 주소와 포트를 달고 온다
규칙 모으기 :: 그 자원에 붙은 그룹들의 규칙을 다 합친다
맞춰 보기 :: 허용 규칙 하나라도 맞으면 통과, 없으면 버린다
자원 :: 통과한 것만 자원까지 닿는다
< 응답 :: 나가는 규칙을 안 봐도 그대로 돌아간다
= 자원마다 붙는 허용 명단이다. 적어 둔 것만 들어오고, 그 답은 안 적어도 나간다
```

## ⚠️ 해결하는 문제

```도해
대조: 규칙을 기계마다 적으면 무엇이 힘든가
그룹 없이 || 보안 그룹으로
규칙 적는 곳 :: 기계마다 따로 || 묶음에 한 번
서버가 늘면 :: 규칙을 또 적는다 || 그룹만 붙인다
웹에서 DB :: 주소를 다 적는다 || 그룹을 적는다
= 규칙을 기계가 아니라 역할에 붙이는 것이 보안 그룹이다
```

방화벽 규칙을 기계마다 적으면 서버가 한 대 늘 때마다 같은 규칙을 또 적어야 한다. 웹 서버가 오토 스케일링으로 늘었다 줄었다 하면 DB 쪽에 적어 둔 허용 주소 목록은 언제나 반 박자 늦는다.

보안 그룹은 규칙을 **역할에 붙인다.** 규칙의 출발지 자리에 주소 대신 다른 보안 그룹의 id 를 적을 수 있어서, "웹 서버 그룹에서 오는 것만 DB 포트로 허용" 이라고 한 번 적어두면 웹 서버가 몇 대로 늘든 규칙은 그대로다. 그룹의 규칙을 고치면 그 그룹이 붙은 자원 전부에 곧바로 적용된다.

## 📊 비교: 보안 그룹과 네트워크 ACL

| | 보안 그룹 | 네트워크 ACL |
|---|---|---|
| **붙는 자리** | 자원(인스턴스) 단위 | 서브넷 단위 |
| **규칙 종류** | 허용만 | 허용과 거부 둘 다 |
| **판정 방식** | 규칙을 다 본 뒤 정한다 | 번호 순으로 보다 맞으면 멈춘다 |
| **돌아오는 트래픽** | 자동 허용(상태 기억) | 따로 열어야 한다(상태 없음) |

AWS 문서는 보안 그룹을 1차 수단으로 쓰고 네트워크 ACL 은 서브넷 단위의 굵은 방어선으로 쓰라고 적는다. 시험에서 "특정 IP 한 곳만 막아라" 가 나오면 답은 보안 그룹이 아니라 네트워크 ACL 이다.

## 💡 실제 사례

- **3계층 구성** — 로드 밸런서 그룹은 인터넷에서 열고, 웹 서버 그룹은 로드 밸런서 그룹에서만, DB 그룹은 웹 서버 그룹에서만 받게 한다.
- **관리 접속** — 22번 포트를 회사 대역이나 배스천 호스트 그룹에서만 허용하고 나머지는 아예 열지 않는다.
- **같은 층끼리 통신** — 그룹이 자기 자신을 출발지로 참조하면 그 그룹에 속한 자원끼리만 서로 오갈 수 있다.

## 🚫 흔한 오해

- **보안 그룹으로 저 IP 를 막아 두자** — 막을 수가 없다. 허용 규칙만 쓸 수 있어서, 한 곳을 골라 차단하는 일은 서브넷에 붙는 네트워크 ACL 의 몫이다.
- **나가는 규칙을 안 열어서 응답이 막혔다** — 보안 그룹은 상태를 기억한다. 들어온 접속의 응답은 아웃바운드 규칙과 상관없이 나가고, 나간 요청의 응답도 인바운드 규칙과 상관없이 들어온다.
- **그룹을 잘게 쪼갤수록 안전하다** — AWS 는 반대로 필요한 최소 개수만 만들라고 적는다. 그룹이 많을수록 실수가 늘고, 한 자원에 여러 그룹을 붙이면 규칙이 합쳐져 하나만 허용해도 통과한다.

## 🚨 주의사항

- **관리 포트를 `0.0.0.0/0` 으로 열지 않는다.** 22번(SSH)이나 3389번(RDP)을 전 세계에 열면 아무나 그 포트로 시도할 수 있다. AWS 문서는 특정 주소 대역만 허용하라고 적는다.
- **규칙 하나를 고치면 그 그룹을 쓰는 자원이 전부 같이 바뀐다.** 한 서버만 손보려던 변경이 같은 그룹을 단 자원 전부에 걸린다.
- **참조하던 그룹이 사라지면 규칙이 낡은 규칙(stale)이 된다.** 피어링 연결이나 상대 그룹이 지워지면 그 그룹을 가리키던 규칙은 그대로 남아 아무 일도 하지 않는다.

## 📝 정리

**"들어와도 되는 것만 적어 둔 그 명단"** 이라고 읽으면 된다. 거부를 못 적으니 한 곳을 콕 집어 막는 일은 네트워크 ACL 에 맡기고, 규칙은 기계가 아니라 그룹에 붙으니 출발지 자리에 주소 대신 그룹 이름을 적는 습관을 들인다.

## 🧒 열 살에게

우리 집에 들어와도 되는 사람 이름을 문 앞에 적어 둔다고 해 봐. 적힌 사람만 들어오고 나머지는 벨을 눌러도 문이 안 열려. 대신 네가 심부름 보낸 친구가 돌아오는 건 이름을 안 적어도 그냥 들여보내 줘.
