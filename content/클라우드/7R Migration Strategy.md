# 7R Migration Strategy (일곱 갈래 이전 전략)

## 📝 정의

7R Migration Strategy는 **응용마다 어떻게 옮길지 고르는 일곱 갈래**다.

AWS 문서는 이 일곱을 버리기(Retire) · 남기기(Retain) · 그대로 옮기기(Rehost) · 통째 옮기기(Relocate) · 사서 바꾸기(Repurchase) · 바탕 갈아 끼우기(Replatform) · 다시 짜기(Refactor) 로 적는다. 이름이 전부 R 로 시작해서 7R 이라 부른다. 세는 개수는 문서마다 다르다 — Azure 는 여덟으로, Google 은 여섯으로 센다. 개수는 달라도 눈금은 같다.

### 이름
7 :: 일곱
R :: 알 자로 시작
Migration :: 옮겨 가기
Strategy :: 고르는 방침
= 붙여 읽으면 "알 자로 시작하는 일곱 중에 하나를 고르는 방침"

### 비유
이삿짐을 하나씩 들어 보며 정하는 일. 그대로 쌀지, 상자만 바꿔 쌀지, 새로 살지, 버릴지, 두고 갈지.

### 예
이전 계획서에 응용 이름이 죽 적혀 있고 그 옆 칸마다 R 로 시작하는 낱말이 하나씩 박혀 있는, 바로 그 칸이다.

## 🖼️ 그림으로 보기

```도해
층: 일곱 갈래는 손을 얼마나 대느냐로 어떻게 갈리나
손을 안 댄다 :: 버리기 Retire · 남기기 Retain. 옮기지 않기로 정하는 자리다
짐만 옮긴다 :: 그대로 옮기기 Rehost · 통째 옮기기 Relocate. 구조는 안 건드린다
그릇을 바꾼다 :: 바탕 갈아 끼우기 Replatform. 관리형 위에 얹어 운영을 덜어낸다
안을 갈아탄다 :: 사서 쓰기 Repurchase · 다시 짜기 Refactor. 응용 자체가 달라진다
= 일곱은 손대는 정도로 줄 세워진다. 위는 빠르고 싸고, 아래는 오래 걸리고 비싼 대신 얻는 것이 크다
```

## ⚠️ 해결하는 문제

```도해
대조: 갈래를 안 정하고 옮기면 무엇이 달라지나
갈래 없이 || 갈래를 정하면
정하는 단위 :: 회사 통째로 || 응용 하나씩
안 쓰는 것 :: 같이 옮겨 간다 || 옮기기 전에 뺀다
값과 기간 :: 옮겨 봐야 안다 || 갈래별로 센다
= 물을 것은 "옮길까 말까" 가 아니라 "이건 어느 갈래인가" 다
```

"클라우드로 갑니다" 는 결정이 아니다. 응용이 삼백 개면 삼백 개가 저마다 다른 사정을 갖고 있다. 이미 아무도 안 쓰는 것, 규정 때문에 못 나가는 것, 특수 장비에 물려 있는 것, 사서 쓰면 그만인 것이 한 목록에 섞여 있다. 이걸 한 덩어리로 다루면 안 쓰는 것까지 그대로 옮겨 놓고 매달 돈을 내게 된다.

일곱 갈래는 그 목록을 **응용 하나 단위의 결정으로 쪼갠다.** 쪼개 놓으면 그때부터 셀 수 있다 — 이 갈래는 얼마가 들고, 얼마나 걸리고, 잘못됐을 때 어디까지 번지는가. AWS 문서가 갈래마다 "언제 이걸 고르나" 를 따로 나열하는 이유가 여기 있다.

## ⚙️ 작동 원리

고르는 순서는 대체로 같다. **먼저 안 옮길 것부터 뺀다.** AWS 문서는 90일 동안 들어온 연결이 하나도 없거나 프로세서와 기억 장치 사용률이 평균 5% 아래인 것을 버리기 후보로 꼽는다. 5%에서 20% 사이도 따로 이름을 붙여 다룬다. 목록의 앞머리를 여기서 잘라내면 뒤의 일이 통째로 가벼워진다.

그다음이 **못 옮기는 것을 남기기로 정하는 일**이다. 규정상 자료가 나라 밖으로 못 나가는 경우, 다른 응용을 먼저 옮겨야 하는 경우, 클라우드에 짝이 없는 특수 장비에 물린 경우가 여기 온다. Azure 문서는 이 자리에 "옮겨서 얻는 것이 거의 없는 경우" 도 같이 넣는다.

남은 것에 갈래를 붙일 때 기준은 세 가지다. **이 응용을 앞으로 얼마나 오래 그대로 쓸 것인가**, **잘못됐을 때 몇 사람이 멈추는가**, **손을 대면 그만큼 값이 돌아오는가.** Azure 문서는 앞으로 2년 안에 손댈 일이 없다고 확신할 때만 그대로 옮기라고 적는다. 2년 안에 고칠 것 같으면 같은 일을 두 번 하게 되기 때문이다.

## 📊 비교: 세 클라우드는 같은 갈래를 어떻게 세나

| 하는 일 | AWS (7개) | Azure (8개) | Google (6개) |
|---|---|---|---|
| 그대로 옮긴다 | Rehost | Rehost | Rehost — lift and shift |
| 통째로 옮긴다 | Relocate | (Rehost 에 포함) | (Rehost 에 포함) |
| 바탕만 바꾼다 | Replatform | Replatform | Replatform — lift and optimize |
| 구조를 고친다 | Refactor / Re-architect | Refactor · Rearchitect (둘로 나눔) | Refactor · Re-architect (둘로 나눔) |
| 새로 만든다 | (Refactor 에 포함) | Rebuild | Rebuild |
| 사서 쓴다 | Repurchase | Replace | Repurchase |
| 안 옮긴다 | Retire · Retain | Retire · Retain | (따로 세지 않음) |

개수 차이는 같은 눈금을 몇 칸으로 나눴느냐일 뿐이다. Azure 가 Refactor 와 Rearchitect 를 갈라 여덟이 되고, Google 이 Retire 와 Retain 을 목록 밖에 두어 여섯이 된다. 시험에서 물어보는 것은 이름 개수가 아니라 **주어진 상황이 어느 칸에 앉는가**다.

## 💡 실제 사례

- **하드웨어 수명이 다 됐다** — 새 장비를 사기 전에 시한이 걸린 상황이다. 그대로 옮기기가 답이고, 손보는 일은 옮긴 뒤로 미룬다.
- **월 사용료가 라이선스 값에 먹힌다** — 운영 체제나 데이터베이스 라이선스가 값의 대부분이면 바탕 갈아 끼우기로 관리형 쪽에 얹어 그 값을 없앤다.
- **인사·고객 관리처럼 남들도 다 쓰는 응용** — 직접 고칠 이유가 없으면 사서 쓰기다. 대신 자료 옮기기와 로그인 붙이기가 새 일감으로 생긴다.

## 🚫 흔한 오해

- **어차피 옮길 거면 이참에 제대로 고쳐야 한다** — AWS 문서는 큰 이전에서 다시 짜기를 권하지 않는다. 옮기는 일과 고치는 일을 겹치면 실패했을 때 둘 중 무엇이 원인인지 못 가른다. 먼저 옮기고 나중에 고치라고 적는다.
- **그대로 옮기기는 아무 이득이 없는 갈래다** — 가장 빠르고 위험이 가장 적은 갈래다. 옮겨 놓은 뒤에는 관리형으로 갈아타기가 오히려 쉬워진다.
- **일곱 개를 다 외워야 한다** — 개수는 문서마다 다르다. 외울 것은 이름이 아니라 손대는 정도라는 눈금 하나다.

## 📝 정리

**"응용마다 따로 정하는 그 일곱 칸"** 이라고 읽으면 된다. 옮길지 말지를 회사 통째로 정하는 것이 아니라 응용 하나씩 갈래를 붙이는 일이고, 갈래마다 드는 값과 걸리는 기간과 잘못됐을 때 번지는 범위가 다르다. 큰 이전에서는 손을 덜 대는 갈래로 먼저 옮기고 손대는 일은 옮긴 뒤로 미루는 편이 안전하다.

## 🧒 열 살에게

이사 갈 때 짐을 하나씩 들어 보면서 정하지? 이건 그대로 싸 가고, 저건 상자를 바꿔서 가고, 이건 낡았으니 새로 사고, 저건 버리고, 저건 그냥 두고 가고. 물건마다 따로 정해야 짐도 줄고 돈도 덜 들어.

## ❓ 이해했는지

- 큰 이전에서 옮기는 일과 고치는 일을 한꺼번에 하면 왜 위험한가 → 흔한 오해
- 아무도 안 쓰는 응용을 그대로 옮겨 놓으면 그다음에 무슨 일이 생기나 → 해결하는 문제
- 어떤 문서는 여섯으로 세고 어떤 문서는 여덟으로 세는데 왜 그런가 → 비교
