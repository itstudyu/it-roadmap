# Resource Tag (자원 꼬리표)

## 📝 정의

Resource Tag 는 **자원에 붙여 두는 낱말 한 쌍**이다.

클라우드는 만든 것을 계정·구독·프로젝트라는 그릇에 담아 준다. 그런데 알고 싶은 것은 대개 그릇을 가로지른다 — "운영 것만", "결제 팀 것만", "이번 행사 때 급히 띄운 것만". 이 축은 그릇으로 안 갈린다. 꼬리표는 자원 하나하나에 `열쇠=값` 두 낱말을 적어 붙여, 그릇과 다른 축으로 골라낼 수 있게 만드는 장치다.

### 이름
Resource :: 만들어 쓰는 것
Tag :: 붙이는 쪽지
= 붙여 읽으면 "자원에 붙이는 쪽지". 열쇠와 값 두 낱말짜리 쪽지다

### 비유
이삿짐 상자에 매직으로 쓴 글씨. 상자를 열지 않고도 어느 방 것인지 누구 것인지 골라낼 수 있다.

### 예
지난달 청구서를 열었는데 어느 팀이 쓴 돈인지 아무도 답을 못 해서 회의가 한 시간 길어지던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 쪽지 한 장이 청구서까지 어떻게 이어지나
만들 때 :: 열쇠와 값 두 낱말을 적어 붙인다
쓰는 동안 :: 목록을 그 값으로 걸러서 본다
값 매길 때 :: 청구서가 그 값으로 갈린다
안 붙은 것 :: "미분류" 한 덩어리로 남는다
= 붙인 뒤부터만 세어진다. 지난달 청구서는 나중에 붙여도 안 갈린다
```

## ⚠️ 해결하는 문제

```도해
대조: 꼬리표가 없으면 무엇을 못 하나
꼬리표 없이 || 꼬리표로
값 나누기 :: 총액 하나뿐 || 팀별로 갈린다
주인 찾기 :: 물어보고 다닌다 || 적힌 대로 안다
치우기 :: 못 지운다 || 골라 지운다
= 이름만으로는 못 나눈다. 이름은 못 바꾸고 뜻도 하나뿐이다
```

이름으로 어떻게든 해 보려는 시도는 꼭 한 번씩 나온다. `prod-pay-web-01` 처럼 이름 안에 모든 것을 욱여넣는 방식이다. 문제는 이름을 나중에 못 고친다는 데 있다. Azure 문서는 아예 "이름은 만든 뒤에 바꿀 수 없으니 변하지 않는 것만 이름에 넣고 나머지는 꼬리표로 잡으라" 고 적는다. 팀이 바뀌거나 담당자가 바뀌면 이름은 그대로 거짓말을 시작한다.

두 번째 문제는 축이 하나뿐이라는 것이다. 이름 한 줄은 한 가지 순서로만 읽힌다. 꼬리표는 같은 자원에 여러 축을 동시에 붙일 수 있어서, 오늘은 팀으로 묶어 보고 내일은 환경으로 묶어 볼 수 있다. 그리고 그 값이 청구서에 그대로 실린다 — Azure 는 꼬리표가 사용 내역 파일의 한 칸으로 나온다고 적는다. **주인 없는 돈이 사라지는 자리가 여기다.**

## 📊 비교: 같은 쪽지를 세 곳은 어떻게 다루나

| 물음 | AWS | Azure | Google Cloud |
|---|---|---|---|
| **부르는 말** | Tag | Tag | Label (Tag 는 다른 물건이다) |
| **한 자원에 몇 개** | 대개 50개 | 50개 (일부 자원은 15개) | 64개 |
| **대소문자** | 열쇠·값 모두 구분한다 | 열쇠는 안 구분, 값은 구분 | 소문자·숫자·밑줄·붙임표만 |
| **위에서 물려받나** | 안 받는다 | 안 받는다 | 안 받는다 |
| **강제하는 장치** | 태그 정책 | Azure Policy | 조직 정책 |

**Google Cloud 에서 Tag 라는 말이 다른 것을 가리키는 것이 가장 흔한 함정이다.** 값을 가르고 목록을 거르는 쪽지는 Google Cloud 에서 Label 이라 부르고, Tag 는 정책의 조건으로 쓰는 별개의 물건이다. Google 문서도 "라벨은 물어보기 위한 주석이지만 정책의 조건으로는 못 쓰고, 태그는 그 자원에 특정 태그가 있는지에 따라 정책을 허용하거나 거부하게 해 준다" 고 갈라 적는다.

세 곳이 똑같은 것도 하나 있다. **위에서 아래로 안 물려받는다.** 그릇에 붙인 꼬리표는 그 안의 자원에 저절로 붙지 않는다. 그래서 셋 다 "안 붙이면 못 만들게" 하는 정책 장치를 따로 판다.

## 💡 실제 사례

- **청구서를 팀별로 가른다** — `owner`, `cost-center`, `env` 세 개면 대부분의 물음이 풀린다. 대신 못 붙은 것이 "미분류" 한 덩어리로 남는데, 그 덩어리 크기가 곧 꼬리표 정책이 얼마나 지켜지는지의 점수다.
- **밤에 개발용을 끈다** — `env=dev` 가 붙은 것만 골라 저녁에 끄고 아침에 켠다. 자동으로 도는 장치가 무엇을 만질지 고르는 기준이 꼬리표다.
- **권한을 값으로 건다** — 특정 값이 붙은 자원만 만질 수 있게 권한을 준다. 자원이 늘어도 권한을 다시 안 고쳐도 된다.

## 🚫 흔한 오해

- **그릇에 붙이면 안에 있는 것에 다 붙는다** — 아니다. Azure 문서는 자원이 리소스 그룹이나 구독의 꼬리표를 물려받지 않는다고 못 박는다. 물려받는 것은 정책과 권한이지 이름표가 아니다.
- **나중에 붙여도 지난 값이 갈린다** — 아니다. 청구는 그때그때 쓰인 꼬리표로 기록된다. 이번 달에 붙인 쪽지가 지난달 청구서를 다시 나눠 주지 않는다.
- **일단 많이 붙여 두면 좋다** — 한 자원에 50개나 64개라는 벽이 있고, 아무도 안 읽는 축이 늘수록 값이 제각각으로 적혀 오히려 못 거르게 된다. 셋에서 다섯 개를 정해 강제하는 편이 낫다.

## 🚨 주의사항

- **비밀을 넣지 마라.** AWS 는 개인 식별 정보나 민감한 값을 꼬리표에 넣지 말라고 적고, Azure 는 꼬리표가 평문으로 저장되며 값 보고서·명령 결과·배포 이력·내보낸 템플릿·감시 기록으로 새어 나갈 수 있다고 적는다.
- **대소문자에서 갈린다.** AWS 는 열쇠와 값을 모두 구분하므로 `Env` 와 `env` 는 다른 축이 된다. Google Cloud 는 아예 소문자만 받는다. 규칙을 정해 두지 않으면 같은 뜻이 세 갈래로 적힌다.
- **꼬리표가 안 붙는 자원이 있다.** Azure 는 꼬리표를 지원하지 않는 자원 종류가 있고 관리 그룹에는 아예 못 붙인다고 적는다. 모든 값을 꼬리표로만 가르려고 하면 반드시 구멍이 남는다.

## 📝 정리

**"열지 않고도 골라낼 수 있게 붙여 둔 쪽지"** 라고 읽으면 된다. 붙인 뒤부터만 세어지고 위에서 물려받지도 않으니, 사람의 성실함이 아니라 못 만들게 막는 정책으로 강제해야 채워진다. 그리고 평문으로 남는 자리라 비밀은 절대 여기 적지 않는다.

## 🧒 열 살에게

이사할 때 상자마다 "내 방", "부엌" 이라고 크게 써 붙이지? 안 써 붙인 상자는 나중에 전부 열어 봐야 하고, 다 옮긴 다음에 써 봤자 이미 아무 데나 쌓인 뒤야. 그래서 그건 옮기기 전에 붙여야 해.
