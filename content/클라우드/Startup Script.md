# Startup Script (시동 스크립트)

## 📝 정의

Startup Script 는 **기계가 켜질 때 저절로 도는 명령 묶음**이다.

기계 한 대를 새로 띄우면 그 안은 비어 있다. 필요한 것을 깔고 설정 파일을 놓고 서비스를 켜는 일은 누군가 접속해서 손으로 쳐야 한다. 한 대면 몇 분이지만, 몰릴 때마다 저절로 늘어나는 무리라면 **사람이 붙어야 하는 순간 그 무리는 못 늘어난다.** 시동 스크립트는 그 명령들을 기계를 띄울 때 함께 실어 보내서, 켜지는 순간 저 혼자 돌게 만드는 자리다.

### 이름
Startup :: 켜질 때
Script :: 적어 둔 명령
= 붙여 읽으면 "켜질 때 도는 적어 둔 명령". 사람이 붙어 칠 필요가 없다

### 비유
커피 머신의 예약 버튼. 아침에 일어나 순서대로 누를 필요 없이, 전날 넣어 둔 순서대로 전원이 들어오면 저 혼자 내린다.

### 예
새 기계를 띄울 때마다 접속해서 똑같은 설치 명령 열 줄을 다시 치던 그 시간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 켜질 때 도는 그 명령은 어디서 와서 어떻게 도나
띄울 때 :: 본문을 기계 정보 칸에 함께 실어 보낸다
켜지면 :: 안의 심부름꾼이 그 칸을 읽어 온다
돌린다 :: 가장 센 권한으로 위에서 아래로 훑는다
기록 :: 돌린 흔적을 정해진 파일에 남긴다
= 이미지에 굽지 않고 켜질 때 밖에서 받아 돈다는 것이 핵심이다
```

## ⚠️ 해결하는 문제

```도해
대조: 켜질 때 도는 명령이 없으면 무엇이 달라지나
손으로 치면 || 적어 두면
새 기계 하나 :: 사람이 붙는다 || 저 혼자 선다
열 대로 늘 때 :: 열 번 되풀이한다 || 같은 값이 든다
새벽에 늘 때 :: 사람을 깨운다 || 저절로 는다
= 저절로 늘어나는 무리는 사람이 붙어야 하면 늘어나지 못한다
```

같은 명령을 사람이 여러 번 치면 반드시 갈린다. 한 대는 최신판이 깔리고 한 대는 지난주 판이 깔리며, 급할 때 친 한 줄이 그 기계에만 남는다. 이렇게 대마다 조금씩 다른 상태가 되면, 장애가 났을 때 "이 기계만 왜" 를 푸는 데 시간을 다 쓴다. 켜질 때 도는 명령은 **모든 대가 같은 글을 읽고 서게** 만든다.

이 자리에는 값이 없다. AWS 는 기계를 띄울 때 넘기는 자료를 두고 "준 것을 그대로 돌려주는 불투명한 자료" 라 적고, 해석은 기계가 알아서 한다고 쓴다. 클라우드가 대신 실행해 주는 특별한 장치가 있는 게 아니라, 기계 안의 심부름꾼이 켜질 때 그 칸을 읽어서 돌리는 것뿐이다. 그래서 넣을 수 있는 크기에 벽이 있고, 안에서 그 칸을 읽을 수 있다는 사실도 여기서 나온다.

## 📊 비교: 같은 물건을 세 곳은 뭐라 부르나

| 물음 | AWS | Azure | Google Cloud |
|---|---|---|---|
| **부르는 말** | User data | cloud-init 사용자 지정 데이터 | Startup script |
| **어디에 적나** | 인스턴스의 user data 칸 | `--custom-data` 로 넘긴 파일 | `startup-script` 메타데이터 열쇠 |
| **언제 도나** | 기본은 **첫 부팅 한 번** | 자원이 마련된 뒤 첫 부팅 | **켤 때마다 매번** |
| **크기 상한** | 16KB (인코딩 전) | 문서가 따로 못 박지 않는다 | 256KB, 넘으면 저장통에서 읽어 온다 |
| **어느 권한으로** | root, 그래서 sudo 를 안 쓴다 | 배포판의 cloud-init 규칙대로 | root |

**여기서 가장 크게 갈리는 것이 "언제 도나" 다.** AWS 문서는 기본적으로 처음 띄울 때의 부팅에서만 돈다고 적고, 다시 켤 때마다 돌리려면 설정을 따로 바꾸라고 쓴다. Google 문서는 반대로 `startup-script` 열쇠에 넣은 것이 **부팅할 때마다** 돈다고 적는다. 같은 글을 두 곳에 그대로 옮겨 붙이면, 한쪽에서는 한 번만 돌고 다른 쪽에서는 재부팅마다 돈다.

그래서 고르는 기준이 하나 생긴다. **두 번 돌아도 안 망가지게 쓰는가.** 이미 있으면 넘어가고 없으면 만드는 식으로 적으면 어느 클라우드에 옮겨도 같다. 두 번 돌면 망가지는 글을 첫 부팅에만 도는 곳에 기대어 쓰는 것은, 옮기는 순간 터지는 빚이다.

## 💡 실제 사례

- **자동으로 늘어나는 무리** — 새벽 세 시에 한 대가 더 뜨면 그 대는 저 혼자 서서 일을 받아야 한다. 사람이 붙는 단계가 하나라도 있으면 그 무리는 자동이 아니다.
- **기계마다 다른 값을 넣기** — 이름·역할·설정 파일을 켜질 때 심는다. AWS 문서의 예는 기계 정보 칸에서 꼬리표 값을 읽어 와 이름을 바꾸고 재부팅하는 글이다.
- **이미지 굽기 전의 임시 자리** — 매번 설치하는 것이 느려지면, 자주 안 바뀌는 부분은 이미지에 미리 굽고 켜질 때 도는 명령은 자주 바뀌는 설정만 맡는다.

## 🚫 흔한 오해

- **어차피 한 번만 도니까 두 번 돌 걱정은 없다** — 클라우드마다 다르다. Google Cloud 는 켤 때마다 돌리고, AWS 도 설정을 바꾸면 재부팅마다 돈다.
- **여기에 비밀번호나 열쇠를 적어도 안 보인다** — 아니다. 기계 안에서 그 칸을 읽을 수 있고, AWS 는 돌린 글을 정해진 폴더에 남긴 채 지우지 않는다고 적는다. 그 상태로 이미지를 뜨면 그 글이 새로 뜨는 모든 기계에 따라간다.
- **설치는 전부 여기에 넣으면 된다** — 넣을수록 켜지는 시간이 길어진다. AWS 도 부팅 시간이 그만큼 늘어난다고 적는다. 자주 안 바뀌는 것은 이미지에 굽는 편이 빠르고 안전하다.

## 🚨 주의사항

- **실패해도 기계는 "떴다" 고 보고된다.** Azure 문서는 명령이 실패해도 마련 자체는 성공으로 보고될 수 있다고 적는다. 다 섰는지 확인하는 것은 건강 확인이 따로 해야 할 일이다.
- **기록이 어디 남는지 먼저 알아 둬라.** AWS 는 `/var/log/cloud-init-output.log`, Azure 는 `/var/log/cloud-init.log` 를 든다. 여기를 모르면 "왜 안 떴는지" 를 짐작으로만 다투게 된다.
- **이미지를 뜨기 전에 지워라.** AWS 는 돌린 글이 폴더에 남으므로 이미지를 만들기 전에 지우라고 적는다. 안 지우면 그 이미지에서 태어나는 모든 기계가 그 글을 안고 태어난다.

## 📝 정리

**"켜지는 순간 저 혼자 도는, 실어 보낸 명령"** 이라고 읽으면 된다. 이미지에 굽는 것이 아니라 띄울 때 밖에서 실어 보내는 물건이라 크기에 벽이 있고 안에서 읽을 수 있으니 비밀은 넣지 않는다. 그리고 한 번만 도는 곳과 켤 때마다 도는 곳이 갈리므로, 두 번 돌아도 안 망가지게 적는 것이 유일하게 안전한 방식이다.

## 🧒 열 살에게

아침마다 물 붓고 버튼 누르는 게 귀찮으면 전날 밤에 순서를 미리 넣어 두잖아? 그러면 아침엔 전원만 들어와도 저 혼자 그대로 해. 대신 순서를 잘못 적어 두면 매일 아침 똑같이 잘못해.
