# Hybrid Cloud (섞어 쓰는 클라우드)

## 📝 정의

Hybrid Cloud 는 따로인 두 곳을 **하나처럼 묶어 쓰는 방식**이다.

NIST 는 이것을 "각자 고유한 실체로 남아 있으면서, 자료와 앱이 오갈 수 있게 표준 기술이나 자체 기술로 묶인 둘 이상의 구성" 으로 정의한다. 핵심은 "섞었다" 가 아니라 **묶였다** 다 — 두 곳에 계정만 따로 있는 것은 여기에 안 들어간다.

### 이름
Hybrid :: 두 종을 섞은
Cloud :: 빌려 쓰는 전산 자원
= 붙여 읽으면 "섞어 쓰는 빌린 자원". 한쪽을 버리지 않고 둘을 함께 쓴다는 말이다

### 비유
계약이 아직 남은 옛 집과 새로 얻은 집 — 짐을 한 번에 못 빼서 한동안 두 집 살림을 한다.

### 예
명절 이틀만 손님이 열 배로 몰리는데, 그 이틀 때문에 장비를 일 년 내내 열 배로 사 둘 수는 없던 그 계산이다.

### 직접
폰의 사진첩 설정을 열어 보라. 어떤 사진은 폰 안에 있고 어떤 사진은 바깥에만 있는데, 화면에서는 한 줄로 이어져 보인다.

## 🖼️ 그림으로 보기

```도해
흐름: 손님이 갑자기 몰리면 섞어 쓰는 쪽은 어떻게 넘기나
평소 :: 제 장비 안에서 다 처리한다
몰릴 때 :: 제 장비가 꽉 찬다
빌린 쪽 :: 모자란 만큼만 밖에서 더 띄운다
< 사용자 :: 어느 쪽이 받았는지 모른 채 같은 화면을 본다
= 두 곳이 따로 서 있어도 쓰는 사람에게는 한 곳이다
```

## ⚠️ 해결하는 문제

```도해
대조: 한쪽만 골라야 한다면 무엇이 걸리나
한쪽만 쓰면 || 섞어 쓰면
못 옮기는 자료 :: 통째로 포기한다 || 제자리에 둔다
잠깐의 폭주 :: 최대치로 사 둔다 || 그때만 빌린다
옮기는 속도 :: 한 번에 다 옮긴다 || 되는 것부터 옮긴다
= 전부 아니면 전무를 강요받지 않는 것이 이 방식이 파는 값이다
```

현실의 회사는 "제 건물이냐 클라우드냐" 를 깨끗하게 못 고른다. 법이나 계약 때문에 건물 밖으로 못 내보내는 자료가 있고, 20년 된 시스템은 옮기는 데만 몇 년이 걸리고, 이미 사 둔 장비의 감가상각이 아직 남아 있다. 그런데 새로 만드는 것은 클라우드에서 훨씬 빠르다.

섞어 쓰기는 이 둘을 **동시에 살려 두는 방식**이다. 못 옮기는 것은 제자리에 두고, 옮길 수 있는 것부터 옮기고, 잠깐 몰리는 만큼만 밖에서 빌린다. NIST 가 정의에 예로 붙인 "클라우드 버스팅" 이 마지막 경우다 — 평소 쓰는 만큼만 갖추고, 몰리는 며칠만 밖으로 넘긴다.

대신 값이 붙는다. 두 곳을 다 굴려야 하니 사람 손은 오히려 늘고, 두 곳 사이를 오가는 자료에는 나가는 요금이 붙는다. 그래서 이건 "싸게 하는 방법" 이 아니라 **한쪽을 못 버릴 때 고르는 방법**이다.

## ⚙️ 작동 원리

두 곳을 하나처럼 만드는 일은 한 번에 되지 않고, 어디까지 겹치게 하느냐로 깊이가 갈린다.

```도해
층: 두 곳을 얼마나 깊게 묶을 수 있나
전용선만 :: 두 곳이 사설망으로만 이어진 상태
신원까지 :: 한 계정으로 양쪽에 들어간다
관리 창구까지 :: 목록·정책·기록을 한 화면에서 본다
같은 장비까지 :: 사업자의 장비를 제 건물에 들인다
= 아래로 갈수록 "하나처럼" 에 가까워지고, 그만큼 값과 묶임도 커진다
```

뻗는 방향도 두 가지다. **밖으로 뻗는 쪽**은 클라우드 사업자의 장비를 고객 건물로 보낸다 — AWS 는 Outposts 를 가용 영역과 그 지역의 연장이라 적고, 그 장비를 AWS 가 직접 운영·관리한다고 못 박는다. 구글의 Distributed Cloud 도 같은 모양이고, 소프트웨어 갱신과 보안 패치를 원격으로 맡는다.

**안으로 끌어들이는 쪽**은 반대다. Azure Arc 는 사내와 다른 클라우드의 서버·쿠버네티스·데이터베이스를 Azure 의 자원 관리자 안으로 투영해서, 그것들이 Azure 에서 도는 것처럼 다루게 한다. 장비는 그대로 두고 관리 창구만 하나로 모으는 방식이다.

## 📊 비교: 세 곳은 섞어 쓰기를 무엇으로 파나

| 어디 | 부르는 이름 | 어느 쪽으로 뻗나 | 무엇이 하나가 되나 |
|---|---|---|---|
| **AWS** | Outposts · Local Zones | 클라우드 장비를 고객 건물·도시로 보낸다 | 같은 API·같은 도구·같은 VPC. Outpost 는 가용 영역의 연장으로 다뤄진다 |
| **Azure** | Azure Arc · Azure Local | 밖의 자원을 Azure 관리 창구 안으로 끌어들인다 | 목록·역할·정책·태그. 장비는 그 자리에 그대로 둔다 |
| **Google Cloud** | Distributed Cloud (connected) | 전용 장비를 고객 현장에 둔다 | 현장에서 도는 쿠버네티스. 갱신과 패치는 구글이 원격으로 맡는다 |

고를 때의 기준은 하나다. **장비를 옮길 수 있나 없나.** 옮길 수 없다면(법·이미 산 자산·몇 년짜리 이관) 관리 창구를 끌어오는 쪽이고, 옮길 수는 있는데 그 자리에 클라우드가 필요하다면 장비를 들이는 쪽이다. 고르는 까닭이 거리와 지연이라면 그건 이 편이 아니라 [[Edge Computing]] 쪽 물음이다 — 이 편이 재는 것은 거리가 아니라 두 곳이 얼마나 한 살림으로 묶였느냐다.

## 💡 실제 사례

- **못 내보내는 자료** — 구글은 Distributed Cloud 를 들이는 이유 중 하나로 "법이나 규정이 자료를 현장에 두라고 정한 경우" 를 적는다. 그런 자료는 제자리에 두고 나머지 계산만 밖에서 돌린다.
- **잠깐의 폭주** — 평소는 제 장비로, 몰리는 며칠만 밖에서 더 빌린다. NIST 정의가 예로 든 바로 그 방식이다.
- **한 번에 못 옮길 때** — 옛 시스템을 통째로 옮기는 데 몇 년이 걸리는 동안, 두 곳이 동시에 살아 있어야 한다.

## 🚫 흔한 오해

- **두 회사 클라우드를 같이 쓰면 하이브리드다** — NIST 정의의 핵심은 "섞었다" 가 아니라 "자료와 앱이 오갈 수 있게 묶였다" 다. 두 곳에 계정만 따로 있고 서로 오갈 길이 없으면 그냥 둘을 따로 쓰는 것이다.
- **섞어 쓰면 값이 준다** — 두 곳을 다 굴려야 하니 사람 손은 오히려 늘고, 두 곳 사이를 오가는 자료에는 나가는 요금이 붙는다. 한쪽을 못 버릴 때 고르는 방법이지 아껴 쓰는 방법이 아니다.
- **제 건물에 장비를 두면 그건 클라우드가 아니다** — AWS 는 Outposts 를 자기 지역의 연장으로 설명하고 그 장비를 AWS 가 운영·관리한다고 적는다. 어디에 놓였느냐가 아니라 누가 굴리고 어떻게 부르느냐가 가른다.

## 📝 정리

**"제 것과 빌린 것을 한 살림으로 묶은 것"** 이라고 읽으면 된다. 둘이 따로 남아 있으면서도 자료와 앱이 오갈 수 있게 묶여야 이 이름이 붙고, 계정만 두 곳에 있는 것은 여기에 안 들어간다. 값이 아니라 못 버리는 쪽이 있어서 고르는 방법이다.

## 🧒 열 살에게

이사를 가는데 옛날 집 계약이 아직 남아서 짐을 한 번에 다 못 빼는 때가 있어. 그러면 한동안 두 집을 오가며 살아야 하고, 두 군데를 다 챙겨야 하니까 손은 오히려 더 가. 그래도 그렇게 하는 건 아껴서가 아니라 옛날 집을 당장 버릴 수가 없어서야.

- 두 곳을 어디까지 깊게 묶을 수 있나 → 작동 원리
