# Object Storage (오브젝트 스토리지)

## 📝 정의

Object Storage 는 파일을 **통째로 넣고 통째로 꺼내는** 저장소다.

넣는 통을 버킷, 넣어 둔 것 하나하나를 오브젝트라고 부른다. 폴더 나무를 타고 내려가는 대신 오브젝트마다 붙은 이름표(키) 하나로 바로 닿는다. AWS 의 S3, Azure 의 Blob Storage, Google Cloud 의 Cloud Storage 가 같은 개념을 파는 이름이다.

### 이름
Object :: 하나로 다루는 덩어리
Storage :: 넣어 두는 곳
= 붙여 읽으면 "덩어리째 넣어 두는 곳". 덩어리가 단위라는 말이 곧 정의다

### 비유
지하철역 물품 보관함. 가방을 통째로 넣고 번호로 꺼내며, 안의 공책 한 권만 바꾸려면 가방을 꺼내 다시 넣어야 한다.

### 예
폰을 바꿔도 사진첩이 그대로 따라오는 그 자리다. 사진은 폰이 아니라 바깥의 통에 한 장씩 들어 있다.

### 직접
웹사이트의 사진을 눌러 이미지 주소를 복사해 보라. 사이트 주소와 전혀 다른 주소가 나오면 그 사진만 다른 통에서 오는 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 사진 한 장을 오브젝트 스토리지에 맡기면 어떻게 다시 꺼내나
앱 :: 사진 한 장을 통째로 올린다
버킷 :: 이름표(키)를 붙여 한 덩어리로 둔다
저장소 :: 같은 덩어리를 여러 벌 복제해 둔다
앱 :: 그 이름표를 주소로 불러 본다
< 버킷 :: 덩어리를 통째로 돌려준다
= 넣을 때도 꺼낼 때도 통째다. 가운데만 고치는 문은 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 파일이 수억 개로 늘어나면 무엇이 달라지나
폴더에 쌓으면 || 오브젝트로 두면
찾는 법 :: 경로를 따라간다 || 이름표로 바로 간다
늘리기 :: 디스크를 붙인다 || 그냥 더 넣는다
망가짐 :: 그 디스크가 끝 || 여러 벌로 남는다
= 이름표 하나로 바로 닿게 하면 개수가 늘어도 찾는 값이 안 변한다
```

파일을 서버 디스크에 두면 그 서버가 파일을 들고 있게 된다. 서버를 두 대로 늘리면 한쪽에 올린 것이 다른 쪽에 없고, 디스크가 차면 그때마다 늘려야 하고, 그 디스크가 망가지면 거기까지다. 폴더를 아무리 깊게 파도 개수가 억 단위가 되면 목록을 읽는 일부터 느려진다.

오브젝트 스토리지는 파일을 서버 밖으로 뺀다. 통 하나에 넣을 수 있는 오브젝트 개수에 정해진 한도가 없고, 같은 것을 여러 대에 복제해 두므로 장치 한 대가 죽어도 남는다. 서버는 파일을 들고 있지 않고 주소만 안다.

## ⚙️ 작동 원리

오브젝트 하나는 파일 내용과 그 파일을 설명하는 이름-값 쌍(메타데이터)으로 이루어진다. 통 안에서 그 오브젝트를 가리키는 유일한 이름표가 키다. 폴더처럼 보이는 것은 키 안에 들어간 슬래시일 뿐이고, 일반 버킷의 구조 자체는 평평하다.

고치는 문이 없다는 것이 이 저장소의 성격을 거의 다 정한다. Google 문서는 오브젝트를 "바꿀 수 없는 데이터 한 덩어리" 라고 적는다. 한 글자를 고치려면 같은 키에 새 덩어리를 통째로 올려 덮어쓴다. 버전 관리를 켜 두면 덮이거나 지워진 옛 덩어리가 이전 버전으로 남는다.

같은 키에 두 요청이 동시에 들어오면 나중 것이 이긴다. 대신 올리기가 성공했다는 응답을 받은 뒤에 읽으면 반드시 새것이 나온다. 자주 여느냐 아니냐에 따라 등급(스토리지 클래스·액세스 티어)을 나누고, 수명주기 규칙을 걸어 오래된 것을 싼 등급으로 내리거나 지우게 할 수 있다.

## 📊 비교: 오브젝트 · 블록 · 파일

| | 오브젝트 | 블록 | 파일 |
|---|---|---|---|
| 다루는 단위 | 파일 한 덩어리 | 번호 붙은 조각 | 경로가 있는 파일 |
| 붙는 방식 | 주소로 부른다 | 서버 한 대에 붙인다 | 여러 서버가 함께 붙인다 |
| 가운데만 고치기 | 안 된다 | 된다 | 된다 |
| 잘 맞는 일 | 사진·영상·백업·로그 | 데이터베이스, 부팅 디스크 | 공유 폴더 |

## 💡 실제 사례

- **사용자 업로드** — 사진과 영상을 앱 서버 밖의 통에 올려 두고, 서버는 주소만 들고 있는다.
- **백업과 로그 보관** — 지난 로그와 백업본을 옮겨 두고, 자주 안 여는 것은 값싼 등급으로 내린다.
- **정적 파일 배포** — 사이트의 이미지와 내려받기 파일을 통에 두고 앞에 [[CDN]] 을 붙여 가까운 곳에서 주게 한다.

## 🚫 흔한 오해

- **디스크처럼 붙여서 쓰면 된다** — 마운트해서 쓰는 디스크가 아니다. 큰 파일의 가운데만 조금 고치는 일에는 맞지 않고, 고치려면 통째로 다시 올려야 한다.
- **싸고 안 죽으니 무엇이든 여기에 두면 된다** — 데이터베이스 파일이나 부팅 디스크를 여기에 얹으면 안 된다. 조각 단위로 고치고 지연이 짧아야 하는 자리는 [[Block Storage]] 쪽이다.
- **올리면 바로 인터넷에 공개된다** — 기본은 비공개다. AWS 문서는 버킷과 그 안의 오브젝트가 기본적으로 비공개이고 권한을 명시적으로 줘야 접근된다고 적는다.

## 🚨 주의사항

- **공개할 통과 안 할 통을 나눈다.** 접근 규칙은 통 전체에 걸리므로 공개용 버킷에 개인 파일을 같이 두면 그것까지 열린다.
- **자주 안 여는 것을 비싼 등급에 두지 않는다.** 수명주기 규칙으로 자동으로 내리게 해 두지 않으면 요금이 그대로 나간다.
- **지운 것까지 지켜주지는 않는다.** 여러 벌 복제는 저장된 것이 스스로 상하는 일을 막을 뿐이다. 실수로 덮어쓰거나 지운 것을 되돌리려면 버전 관리를 켜 둬야 한다.

## 📝 정리

**"덩어리째 맡기고 이름표로 찾는 그 통"** 이라고 읽으면 된다. 폴더 나무 대신 이름표 하나로 바로 닿게 만들어 개수가 억을 넘어도 찾는 값이 안 변하고, 서버를 몇 대로 늘리거나 통째로 갈아도 파일은 그 자리에 남는다. 대신 가운데만 고치는 문이 없으니 데이터베이스와 부팅 디스크는 여기에 얹지 않는다.

## 🧒 열 살에게

지하철역에 짐 넣는 칸 있는 거 알지? 가방을 통째로 넣고 번호를 받아 두면 네가 어디를 돌아다니다 와도 그 번호만 대면 가방이 그대로 나와. 안에서 공책 한 권만 바꾸고 싶으면 가방을 꺼내서 통째로 다시 넣어야 해.

## ❓ 이해했는지

- 파일 한 줄만 고치는데 왜 파일 전체를 다시 올려야 하나 → 작동 원리
- 데이터베이스 파일을 이 저장소 위에 바로 얹으면 무엇이 문제인가 → 흔한 오해
- 실수로 지운 파일을 되돌리려면 미리 무엇을 켜 둬야 하나 → 주의사항

## 🔗 관련 용어

- [[S3]] — AWS 가 이 개념을 파는 이름
- [[Block Storage]] — 같은 자리를 두고 겨루는 다른 저장 방식. 조각 단위로 고칠 수 있다
- [[CDN]] — 오브젝트를 사용자 가까운 곳에 복사해 두는 앞단
- [[File System]] — 폴더 나무로 파일을 다루는 방식. 오브젝트에는 그 나무가 없다
- [[IAM]] — 어떤 계정이 통에 무엇을 할 수 있는지 정한다
