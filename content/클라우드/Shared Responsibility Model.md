# Shared Responsibility Model (책임 공유 모델)

## 📝 정의

책임 공유 모델은 **클라우드의 안전을 제공자와 내가 나눠 맡는 약속**이다.

AWS는 이것을 두 마디로 적는다 — 클라우드 **자체**의 보안은 제공자가, 클라우드 **안에서**의 보안은 사용자가 맡는다. Azure 문서는 같은 선을 표로 그려두고, 배포 형태(IaaS·PaaS·SaaS)마다 그 선이 오르내린다고 적는다.

### 이름
Shared :: 나눠 가진
Responsibility :: 맡은 몫
Model :: 그려 둔 그림
= 붙여 읽으면 "맡은 몫을 나눠 그린 그림". 무엇을 하는 물건이 아니라 선을 그은 그림이다

### 비유
전세 아파트. 건물 골조와 승강기는 집주인이 고치지만, 현관을 잠그는 일과 집 안의 물건은 세입자 몫이다.

### 예
저장소를 공개로 열어 둬서 파일이 새는 사고가 나도 제공자는 책임지지 않는다. 그 설정 스위치는 내 칸에 있다.

## 🖼️ 그림으로 보기

```도해
층: 어디까지가 제공자 몫이고 어디부터가 내 몫인가
내 데이터·계정 :: 무엇을 담고 누구에게 열지. 어느 형태든 내 몫
내 설정 :: 권한·방화벽·암호화 선택. 사고가 가장 많이 나는 칸
운영체제·런타임 :: IaaS 면 내 몫, PaaS 부터는 제공자 몫
하드웨어·가상화 :: 제공자가 맡는다. 내가 만질 수 없다
물리 시설 :: 건물·전원·출입 통제. 제공자가 맡는다
= 위는 언제나 내 몫, 아래는 언제나 제공자 몫이고, 가운데 선만 서비스마다 오르내린다
```

## ⚠️ 해결하는 문제

```도해
대조: 이 선을 안 그어두면 무엇이 비는가
선이 없으면 || 선을 그으면
패치 :: 서로 미룬다 || 맡은 쪽이 한다
설정 사고 :: 누구 탓인지 다툰다 || 내 몫으로 정해진다
점검 :: 어디를 볼지 모른다 || 내 칸만 짚는다
= 나눈 선이 곧 내가 할 일 목록이다. 선이 없으면 아무도 안 한 칸이 생긴다
```

클라우드로 옮기면 할 일이 사라지는 것이 아니라 주인이 바뀐다. 그런데 누가 무엇을 맡는지 적어두지 않으면 양쪽 다 상대가 할 줄 안다. 그 사이에 낀 일이 패치와 설정이고, 사고는 대개 거기서 난다.

Google 문서는 대부분의 클라우드 보안 침해가 잘못된 설정에서 직접 비롯된다고 적는다. 설정은 어느 서비스에서도 사용자 칸에 남는 일이라, 선을 미리 그어두는 것만으로 볼 곳이 정해진다.

## ⚙️ 작동 원리

AWS는 서비스를 굴리는 하드웨어·소프트웨어·망·시설을 맡는다. 사용자는 게스트 운영체제(갱신과 보안 패치 포함), 자기가 올린 애플리케이션, AWS가 제공한 방화벽 설정을 맡는다. S3나 DynamoDB처럼 추상화된 서비스에서는 운영체제가 사용자 눈에서 사라지고, 대신 데이터 관리(암호화 선택 포함)와 자산 분류, [[IAM]] 권한 적용이 사용자 몫으로 남는다.

Azure 문서는 그 선을 표로 못 박아 둔다. 고객 데이터·구성·계정은 온프레미스든 SaaS 든 전부 고객 칸이다. 운영체제는 IaaS 까지만 고객이고 PaaS 부터 Microsoft 로 넘어간다. 물리 호스트·물리 망·물리 시설은 IaaS 부터 이미 Microsoft 칸이다. 애플리케이션과 망 제어는 가운데에 걸쳐 있어서, 형태에 따라 반씩 나눠 맡는다.

Google은 여기서 한 걸음 더 나간 말을 쓴다. 공유 책임 모델이 "고객이 더 나은 보안 결과에 닿는 데까지는 돕지 못한다" 며, 청사진과 검증된 인프라 코드로 함께 감당하는 shared fate(운명 공유)를 내놓았다. 선을 긋는 것과 그 칸을 채우도록 돕는 것은 다른 일이라는 뜻이다.

## 💡 실제 사례

- **계정이 털려 자료가 샜을 때** — 제공자 쪽에는 아무 고장이 없었는데 사고가 난다. 계정은 어느 형태에서도 내 칸이라 여기서 막았어야 했다.
- **저장소를 공개로 열어 둔 사고** — 관리형 저장소라도 권한과 암호화 선택은 사용자 칸이라고 AWS 문서가 적는다.
- **가상 머신에서 관리형으로 옮길 때** — 운영체제 패치가 제공자 쪽으로 넘어간다. 데이터와 계정은 그대로 내 쪽에 남는다.

## 🚫 흔한 오해

- **클라우드에 올렸으니 보안은 제공자가 다 해준다** — 아니다. Azure 문서는 데이터·엔드포인트·계정·접근 관리를 어느 형태에서도 고객이 계속 맡는다고 적는다.
- **관리형으로 바꾸면 내 책임이 0이 된다** — 줄어들 뿐 사라지지 않는다. 추상화된 서비스에서도 데이터 분류와 권한은 사용자 칸에 남는다.
- **선은 어느 서비스나 똑같다** — 같은 제공자 안에서도 다르다. 가상 머신과 관리형 저장소는 운영체제 칸의 주인부터 다르다.

## 🚨 주의사항

- **서비스마다 문서를 보고 선을 확인한다.** 형태가 IaaS 인지 PaaS 인지에 따라 운영체제와 망 제어의 주인이 바뀐다.
- **설정은 어느 칸에서도 안 넘어간다.** Google 문서는 대부분의 침해가 잘못된 설정에서 비롯된다고 적는다.
- **네 가지는 절대 안 넘어간다.** Azure 문서가 표 밖에 따로 적어둔 것이 데이터·엔드포인트·계정·접근 관리다.

## 📝 정리

**"내 몫과 남의 몫 사이에 그어 둔 선"** 이라고 읽으면 된다. 아래쪽 시설과 장비는 언제나 제공자, 위쪽 데이터와 계정과 접근 권한은 언제나 나이고, 가운데 운영체제와 망 제어만 서비스 형태에 따라 오르내린다. 그러니 "안전한가" 대신 "이 서비스에서 선이 어디 있나" 를 물어야 답이 나온다.

## 🧒 열 살에게

빌린 집에서 지붕이 새면 집주인이 고쳐 주지? 그런데 현관문을 안 잠가서 물건이 없어진 건 집주인 탓이 아니야. 그래서 누가 무엇을 맡을지 미리 적어 두는 거야.

## ❓ 이해했는지

- 같은 사고인데 왜 어떤 것은 제공자 잘못이고 어떤 것은 내 잘못이 되나 → 그림
- 추상화된 저장소를 써도 여전히 내가 해야 하는 일은 무엇인가 → 작동 원리
- 이 선을 안 그어두면 실제로 어떤 칸이 비게 되나 → 해결하는 문제
