# File Storage (파일 저장소)

## 📝 정의

File Storage 는 여러 대가 **같은 폴더를 함께 여는** 저장소다.

폴더 나무와 파일 이름이 그대로 있고, 서버마다 그것을 제 폴더처럼 걸어 쓴다. 클라우드 저장소 세 갈래 중 하나다 — 한 대가 자기 판처럼 쓰는 블록, 통째로 넣고 꺼내는 오브젝트, 그리고 여럿이 같은 서랍을 함께 여는 파일.

### 이름
File :: 이름이 붙은 자료 하나
Storage :: 넣어 두는 곳
= 붙여 읽으면 "파일 단위로 넣어 두는 곳". 폴더와 이름이 그대로 남는 쪽이다

### 비유
사무실 한가운데 놓인 공용 캐비닛 — 여러 사람이 동시에 열어 같은 서랍의 서류를 꺼내 보고 고쳐 넣는다.

### 예
회사 컴퓨터의 탐색기에 내 디스크가 아닌 드라이브가 하나 더 잡혀 있고, 거기 있는 파일을 여럿이 같이 열던 그 자리다.

### 직접
탐색기 왼쪽에 잡혀 있는 공유 드라이브를 눌러 보라. 내 디스크가 아닌데 폴더와 파일이 그대로 보이면 그게 이 저장소다.

## 🖼️ 그림으로 보기

```도해
흐름: 서버 여러 대가 같은 파일 하나를 어떻게 함께 여나
파일 저장소 :: 폴더 나무를 그대로 들고 있다
붙이기 :: 각 대가 그 저장소를 제 폴더처럼 건다
읽고 쓰기 :: 평소 파일 다루듯 열고 고친다
잠금 :: 한 대가 고치는 동안 겹치지 않게 잡아 둔다
다른 대 :: 고친 결과를 같은 경로에서 곧바로 본다
= 옮겨 담는 게 아니라 같은 서랍을 여럿이 함께 여는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 여러 대가 같은 파일을 봐야 할 때 무엇이 달라지나
파일 저장소 없이 || 파일 저장소로
같은 파일 :: 대마다 복사한다 || 한 벌을 같이 본다
고친 뒤 :: 사본이 갈라진다 || 곧바로 같이 보인다
옛 앱 옮기기 :: 코드를 고쳐야 한다 || 그대로 붙인다
= 자료를 나누는 문제가 아니라 자리를 나눠 쓰는 문제다
```

서버가 한 대일 때는 파일이 그 대의 디스크에 있으면 됐다. 두 대로 늘리는 순간 문제가 생긴다 — 사용자가 올린 사진이 1번 서버에 저장됐는데 다음 요청이 2번 서버로 가면 그 사진은 없는 파일이 된다. 대마다 복사해 두는 방법은 고치는 순간 사본들이 갈라져서 어느 게 맞는지 아무도 모르게 된다.

블록 저장소로는 이 문제가 안 풀린다. 블록 저장소는 한 대가 자기 판처럼 쓰라고 만든 것이라, 여러 대가 같이 붙여 각자 쓰면 파일 시스템이 깨진다. 오브젝트 저장소는 여럿이 써도 되지만 폴더 나무도 없고 파일 가운데만 고치는 문도 없어서, 공유 폴더를 전제로 만든 옛 앱은 그대로 못 올라간다.

파일 저장소는 **여럿이 같은 서랍을 열도록 만들어진 쪽**이다. 잠금과 권한 같은 파일 시스템의 약속을 그대로 지켜 주기 때문에, 앱은 자기가 클라우드에 있는지도 모른 채 평소처럼 파일을 연다. Azure 문서가 첫 용도로 "코드를 고치지 않고 옮기기" 를 드는 이유가 여기 있다.

## 📊 비교: 무엇과 견주고, 세 곳은 뭐라고 부르나

먼저 세 갈래를 가른다. 시험 문제가 "이 상황에서 무엇을 고르나" 로 묻는 자리가 대개 여기다.

| 갈래 | 다루는 단위 | 누가 붙나 | 언제 고르나 |
|---|---|---|---|
| **블록** | 판 위의 칸 | 한 대만 | 데이터베이스처럼 한 대가 빠르게 갈아 써야 할 때 |
| **파일** | 폴더와 파일 | 여러 대가 동시에 | 여럿이 같은 폴더를 봐야 할 때, 옛 앱을 그대로 옮길 때 |
| **오브젝트** | 덩어리 하나 | 아무나, 주소로 | 사진·로그·백업처럼 통째로 넣고 꺼낼 때 |

같은 파일 저장소를 세 곳은 이렇게 판다.

| 어디 | 부르는 이름 | 붙는 방식 | 알아 둘 것 |
|---|---|---|---|
| **AWS** | EFS (Elastic File System) | NFS | 파일을 넣고 빼는 대로 저절로 늘고 준다. 여러 가용 영역에 두는 방식과 한 영역에만 두는 방식이 나뉜다 |
| **Azure** | Azure Files | SMB · NFS · REST | 클라우드와 사내 컴퓨터에서 동시에 걸 수 있다. SMB 는 윈도·리눅스·맥, NFS 는 리눅스 |
| **Google Cloud** | Filestore | NFSv3 · NFSv4.1 | 용량을 정해 두고 무중단으로 키운다. 등급에 따라 지역 범위와 성능이 갈린다 |

## 💡 실제 사례

- **옛 앱 그대로 옮기기** — 공유 폴더를 전제로 만든 앱을 코드 한 줄 안 고치고 올린다. Azure 가 첫 용도로 드는 것이다.
- **여러 대가 쓰는 설정과 기록** — 서버가 몇 대로 늘어도 설정 파일과 남기는 기록을 한 자리에 둔다.
- **컨테이너의 붙박이 저장 자리** — 어느 대에서 뜨든 같은 폴더가 붙는다. 상태를 들고 있어야 하는 컨테이너가 이 방식을 쓴다.

## 🚫 흔한 오해

- **파일 저장소가 오브젝트 저장소보다 낫다** — 다른 물건이다. 폴더와 잠금이 필요한 일에는 파일 쪽이고, 웹으로 뿌리는 사진이나 아주 큰 자료 더미는 오브젝트 쪽이 훨씬 싸다. 나은 쪽이 아니라 맞는 쪽을 고르는 문제다.
- **디스크 하나를 여러 대에 같이 붙이면 같은 일이 된다** — 블록 저장소는 한 대가 자기 판처럼 쓰는 것이라 여럿이 각자 쓰면 파일 시스템이 깨진다. 여럿이 같이 쓰라고 만든 쪽이 파일 저장소다.
- **파일 저장소는 크기를 미리 잡아 둬야 한다** — AWS 의 EFS 는 파일을 넣고 빼는 대로 저절로 늘고 준다고 문서가 적는다. 다만 다 그런 것은 아니어서, Google 의 Filestore 는 용량을 정해 두고 필요할 때 무중단으로 키운다.

## 🚨 주의사항

- **붙는 규약이 손님을 정한다.** Azure 는 SMB 는 윈도·리눅스·맥이, NFS 는 리눅스가 붙는다고 나눈다. 윈도 자산이 섞였으면 SMB, 리눅스만 쓸 참이면 NFS 다.
- **어디까지 퍼뜨릴지 고른다.** AWS 는 여러 가용 영역에 나눠 두는 방식과 한 영역에만 두는 방식을 나누고, 뒤쪽은 그 영역이 통째로 상하면 자료를 잃을 수 있다고 적는다.
- **못 붙는 손님이 있다.** AWS 문서는 윈도 기반 EC2 인스턴스에서 EFS 를 쓰는 것은 지원하지 않는다고 못 박는다.

## 📝 정리

**"여럿이 같이 여는 그 공용 서랍"** 이라고 읽으면 된다. 한 대가 자기 판처럼 쓰면 블록, 통째로 넣고 꺼내면 오브젝트, 여럿이 같은 폴더를 열면 파일이다. 붙는 규약과 퍼뜨릴 범위 둘이 고를 때 보는 자리다.

## 🧒 열 살에게

교실 뒤에 다 같이 쓰는 사물함이 하나 있다고 해 봐. 각자 자기 것만 따로 복사해 두면 누구 게 진짜인지 아무도 모르는데, 한 칸에 모아 두면 누가 고쳐도 다 같이 그걸 봐. 대신 한 명이 꺼내 고치는 동안엔 다른 애가 못 건드리게 잠깐 잠가 둬.

## 🔗 관련 용어

- [[Block Storage]] — 한 대가 자기 판처럼 쓰는 쪽. 여럿이 같이 붙이면 깨진다
- [[Object Storage]] — 통째로 넣고 꺼내는 쪽. 폴더도 잠금도 없다
