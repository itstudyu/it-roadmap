# Tenant (테넌트)

## 📝 정의

테넌트는 멀티테넌시(Multi-tenancy) 환경에서 동일한 클라우드 인프라와 애플리케이션을 공유하지만 논리적으로 완전히 격리된 각각의 고객, 조직, 또는 사용자 단위를 의미합니다. 마치 빌딩의 여러 세입자(Tenant)가 같은 건물에 살지만 각자 독립된 집처럼, 각 테넌트는 공유 리소스를 효율적으로 사용하면서도 자신의 데이터와 설정이 다른 테넌트와 섞이지 않도록 보호됩니다.

멀티테넌시 아키텍처는 클라우드 시대의 핵심 개념으로, Slack, Salesforce, GitHub, Microsoft 365 같은 SaaS 서비스들이 수백만 고객을 효율적으로 관리할 수 있게 해줍니다. 각 회사가 별도의 서버와 데이터베이스를 구축하지 않고도 동일한 애플리케이션을 사용하면서 자신의 데이터만 접근할 수 있다는 것이 멀티테넌시의 가장 큰 장점입니다.

### 한 줄 요약
> 클라우드 인프라를 공유하면서도 논리적으로 완전히 격리된 각각의 고객 또는 조직 단위

### 비유
- 🔵 **비유 1**: 아파트 건물 같은 구조. 같은 건물(클라우드)을 여러 세입자(테넌트)가 공유하지만, 각 가구(테넌트)는 자신의 물건만 볼 수 있고 이웃의 짐은 볼 수 없습니다.
- 🟡 **비유 2**: 은행의 여러 고객 계좌처럼, 같은 은행 시스템을 사용하지만 각 고객의 잔액과 거래 내역은 완벽히 분리되어 있습니다.
- 🟢 **비유 3**: 도시의 여러 상점들이 같은 거리에 위치하면서도 독립적인 비즈니스를 운영하는 것과 같습니다.

## 🎯 핵심 개념

### 1. 멀티테넌시 아키텍처
멀티테넌시는 단일 애플리케이션 인스턴스가 여러 테넌트를 동시에 서빙하는 방식입니다. 이는 각 테넌트가 별도의 애플리케이션 인스턴스를 보유하는 싱글 테넌시와 다릅니다. 멀티테넌시 방식은 서버 리소스를 효율적으로 활용하여 비용을 크게 절감할 수 있으며, 유지보수와 업데이트가 간편합니다. 특히 SaaS 비즈니스 모델에서 필수적이며, 많은 수의 고객을 동시에 관리할 수 있는 확장성을 제공합니다. 하지만 테넌트 간 데이터 격리가 완벽하지 않으면 보안 위험이 발생할 수 있어, 철저한 격리 메커니즘이 필요합니다.

### 2. 데이터 격리 방식
테넌트 데이터를 격리하는 방식은 세 가지가 있습니다. 첫째, 데이터베이스 분리(Database Isolation) 방식은 각 테넌트가 완전히 독립된 데이터베이스를 가지는 방식으로 최고 수준의 격리를 제공하지만 비용이 많이 듭니다. 둘째, 스키마 분리(Schema Isolation) 방식은 같은 데이터베이스 인스턴스 내에서 각 테넌트마다 별도의 스키마를 사용하는 것으로, 비용과 격리 수준 사이의 균형을 제공합니다. 셋째, 행 수준 격리(Row-level Isolation) 방식은 같은 테이블에 모든 테넌트의 데이터를 저장하되 'tenant_id' 같은 칼럼으로 데이터를 구분하는 방식으로, 가장 효율적이지만 격리 실수의 위험이 있습니다.

### 3. 테넌트의 역할과 책임
각 테넌트는 자신의 애플리케이션 인스턴스 내에서 독립적인 관리자, 사용자, 설정 정보를 가집니다. 테넌트는 자신의 데이터만 접근할 수 있으며, 자신의 보안 정책과 접근 권한을 설정할 수 있습니다. 클라우드 제공업체는 모든 테넌트에게 동일한 인프라와 기능을 제공하면서도, 각 테넌트의 데이터가 절대로 혼합되지 않도록 보장할 책임이 있습니다. 테넌트 간의 격리 실패는 심각한 보안 사고로 이어질 수 있으므로, 멀티테넌시 시스템의 모든 계층에서 철저한 검증과 감사가 필요합니다.

## ⚠️ 해결하는 문제

### 문제 1: 비효율적인 인프라 활용
전통적으로는 각 고객이 독립된 서버, 데이터베이스, 애플리케이션을 구축해야 했습니다. 이 방식은 리소스 활용도가 낮았는데, 예를 들어 어떤 고객의 애플리케이션은 CPU 자원을 10% 정도만 사용하면서도 전체 서버를 점유하고 있어 많은 리소스가 낭비되었습니다. 멀티테넌시 방식으로 전환하면, 여러 테넌트가 같은 리소스를 공유하므로 활용도를 70~90%까지 높일 수 있습니다. 결과적으로 클라우드 제공업체와 고객 모두 인프라 비용을 대폭 절감할 수 있게 되었고, 이것이 SaaS 서비스의 경제성 기반을 만들었습니다.

### 문제 2: 유지보수의 복잡성
각 고객이 독립된 애플리케이션 인스턴스를 가진다면, 버그 수정이나 기능 업데이트를 할 때마다 모든 인스턴스에 일일이 배포해야 합니다. 수천 개의 고객이 있다면 이는 관리 불가능한 수준의 복잡성을 야기합니다. 멀티테넌시 시스템에서는 단 하나의 애플리케이션 인스턴스만 관리하면 되므로, 새로운 기능이나 보안 패치는 한 번의 배포로 모든 테넌트에게 즉시 적용됩니다. 이를 통해 일관된 버전 관리가 가능하고, 보안 취약점에 대응하는 속도도 획기적으로 향상됩니다.

### 문제 3: 확장성의 한계
싱글 테넌시 방식에서는 새로운 고객을 확보할 때마다 새로운 인프라를 구축해야 하므로, 초기 구축 비용과 시간이 상당히 소요됩니다. 특히 초기 스타트업 단계에서 수백만 달러의 인프라 투자 없이는 서비스 출시가 어렵습니다. 멀티테넌시 아키텍처는 이미 구축된 인프라에 새 테넌트를 추가하는 비용이 매우 낮으므로, 빠른 고객 확보와 확장이 가능합니다. 이는 클라우드 기반 SaaS 회사들이 빠르게 성장할 수 있는 핵심 동력이 되었습니다.

## ⚙️ 작동 원리

### 1단계: 요청 도착 및 테넌트 식별
사용자가 SaaS 서비스에 접속하면 (예: company-a.example.com 또는 example.com에서 회사 A 토큰으로 로그인), 시스템은 먼저 이 요청이 어느 테넌트로부터 온 것인지 식별합니다. URL의 서브도메인, HTTP 헤더, 쿠키, API 토큰 등을 통해 테넌트를 파악합니다. 이 단계가 가장 중요한데, 여기서 실수하면 테넌트 A의 사용자가 테넌트 B의 데이터에 접근할 수 있는 심각한 보안 사고가 발생합니다.

### 2단계: 요청 컨텍스트에 테넌트 ID 설정
요청이 식별된 후, 애플리케이션의 모든 처리 과정에서 현재 테넌트 ID를 추적합니다. 이를 위해 요청이 시작되는 시점에 컨텍스트 변수(Context Variable)에 테넌트 ID를 저장합니다. 이후 데이터베이스 쿼리, 파일 접근, 캐시 조회 등 모든 작업에서 이 테넌트 ID를 사용하여 자동으로 데이터를 필터링합니다. 예를 들어 'SELECT * FROM users'라는 쿼리는 실제로는 'SELECT * FROM users WHERE tenant_id = X'처럼 자동으로 변환됩니다.

### 3단계: 데이터베이스 필터링
데이터베이스 쿼리 시 항상 'WHERE tenant_id = current_tenant_id' 조건을 추가하여, 현재 테넌트만 자신의 데이터에 접근할 수 있도록 합니다. 이는 애플리케이션 레벨과 데이터베이스 레벨 두 곳에서 모두 검증되어야 합니다. 데이터베이스 뷰(View)나 Row-Level Security(RLS) 같은 데이터베이스 네이티브 기능을 사용하면 이 검증을 더욱 견고하게 할 수 있습니다.

### 4단계: 응답 반환 및 요청 정리
데이터베이스에서 반환된 데이터는 현재 테넌트에 속하는 데이터만 포함하므로, 응답을 사용자에게 안전하게 전송할 수 있습니다. 요청 처리가 완료된 후에는 컨텍스트의 테넌트 ID와 모든 민감한 정보를 명시적으로 제거하여, 다음 요청에서 이전 요청의 정보가 남아있지 않도록 합니다.

```
요청 흐름도:

┌──────────────────┐
│ 1. 요청 도착     │ (URL: company-a.example.com)
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 2. 테넌트 식별   │ (Tenant ID: A 확인)
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 3. Context 설정  │ (current_tenant = A)
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 4. 데이터 접근   │ (WHERE tenant_id = A)
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 5. 응답 반환     │ (Tenant A 데이터만)
└────────┬─────────┘
         ▼
┌──────────────────┐
│ 6. Context 정리  │ (테넌트 ID 제거)
└──────────────────┘
```

## 📊 비교

### 싱글 테넌시 vs 멀티 테넌시

| 항목 | 싱글 테넌시 | 멀티 테넌시 |
|------|----------|----------|
| **개념** | 각 고객이 독립된 애플리케이션 인스턴스 보유 | 여러 고객이 단일 애플리케이션 인스턴스 공유 |
| **데이터 격리** | 물리적으로 완전히 분리됨 | 논리적으로 격리됨 |
| **비용** | 높음 (고객당 별도 인프라 필요) | 낮음 (인프라 공유) |
| **리소스 활용도** | 20~40% | 70~90% |
| **업데이트/배포** | 고객마다 별도로 진행 | 한 번에 모든 고객에게 적용 |
| **초기 구축 시간** | 길음 | 짧음 |
| **확장성** | 제한적 | 뛰어남 |
| **보안 복잡도** | 낮음 | 높음 |
| **커스터마이징** | 용이 | 제한적 |
| **비즈니스 모델** | 엔터프라이즈 솔루션 | SaaS |

### 데이터 격리 방식 비교

| 항목 | DB 분리 | 스키마 분리 | 행 수준 격리 |
|------|--------|----------|-----------|
| **격리 수준** | 매우 높음 | 높음 | 중간 |
| **보안성** | 최고 | 높음 | 보통 |
| **비용** | 높음 | 중간 | 낮음 |
| **확장성** | 제한적 | 중간 | 뛰어남 |
| **관리 복잡도** | 높음 | 중간 | 낮음 |
| **신규 테넌트 추가** | 느림 | 중간 | 빠름 |
| **백업/복구** | 테넌트별 독립 | 데이터 필터링 | 데이터 필터링 |
| **마이그레이션** | 가능 | 어려움 | 어려움 |
| **사용 사례** | 엔터프라이즈 | 중규모 SaaS | 대규모 SaaS |

## ✅ 장점과 단점

### 장점

**1. 비용 효율성**: 여러 고객이 동일한 인프라를 공유하므로 인프라 비용이 크게 감소합니다. 클라우드 제공업체는 이를 통해 고객에게 저렴한 구독료를 제공할 수 있고, 고객들은 초기 투자 비용 없이 서비스를 시작할 수 있습니다.

**2. 빠른 배포 및 업데이트**: 단일 애플리케이션 인스턴스만 관리하므로, 새로운 기능이나 보안 패치를 한 번의 배포로 모든 테넌트에게 적용할 수 있습니다. 이는 개발 생산성을 높이고 보안 대응 속도를 향상시킵니다.

**3. 용이한 확장성**: 새로운 고객을 추가할 때 새로운 인프라 구축이 필요 없으므로, 빠르게 고객 기반을 확대할 수 있습니다. 이는 SaaS 기업의 급속한 성장을 가능하게 합니다.

**4. 자동화된 유지보수**: 중앙 집중식 관리로 인해 업그레이드, 패치, 모니터링 등이 자동화되고 일관성 있게 진행됩니다.

**5. 리소스 최적화**: 여러 테넌트의 사용 패턴이 다르므로, 한 테넌트가 리소스를 많이 사용할 때 다른 테넌트는 적게 사용하는 식으로 자연스럽게 리소스가 분산되어 활용도가 높아집니다.

### 단점

**1. 높은 보안 복잡도**: 테넌트 간 데이터 격리를 완벽하게 구현해야 하므로, 보안 설계와 구현이 매우 복잡합니다. 격리 실수는 치명적인 데이터 유출로 이어질 수 있습니다.

**2. 제한된 커스터마이징**: 모든 테넌트가 동일한 코드베이스를 사용하므로, 특정 고객만을 위한 커스터마이징이 어렵고, 과도한 커스터마이징은 시스템 복잡도를 높입니다.

**3. 성능 격리 어려움**: 한 테넌트의 과다 사용이 다른 테넌트의 성능에 영향을 줄 수 있습니다. (Noisy Neighbor Problem) 이를 방지하기 위해서는 복잡한 리소스 할당 및 제한 메커니즘이 필요합니다.

**4. 규정 준수 복잡성**: 특정 산업(금융, 의료)의 데이터 격리 요구사항을 멀티테넌시로 충족시키기 어려울 수 있습니다. 예를 들어 HIPAA나 GDPR 준수를 위해 데이터 격리 수준을 높여야 할 수도 있습니다.

**5. 디버깅의 어려움**: 프로덕션 환경에서 여러 테넌트의 데이터가 섞여 있어, 특정 테넌트의 문제를 재현하고 디버깅하기 어렵습니다.

**6. 확장의 한계**: 수십억 건 이상의 데이터를 다루거나 매우 높은 동시성을 처리해야 할 때, 싱글 데이터베이스의 확장성이 한계에 도달할 수 있습니다.

## 💡 실제 사용 사례

### Slack
Slack은 멀티테넌시의 대표적인 사례입니다. 모든 회사가 동일한 Slack 애플리케이션을 사용하지만, 각 회사(테넌트)의 메시지, 파일, 멤버 정보는 완벽히 격리되어 있습니다. A사의 직원이 B사의 Slack 채널이나 메시지에 절대로 접근할 수 없습니다. Slack은 row-level 격리 방식을 사용하여 비용 효율성과 빠른 배포를 달성했습니다.

### Salesforce
Salesforce는 초기부터 멀티테넌시 아키텍처를 설계했으며, 이것이 엄청난 성공의 기반이 되었습니다. 모든 고객이 동일한 애플리케이션을 사용하면서도, 각 조직의 고객 데이터, 거래 정보, 보고서는 완벽히 격리됩니다. Salesforce의 멀티테넌시는 초기 비용 없이 CRM을 도입할 수 있게 했으며, 이것이 온프레미스 솔루션을 거의 완전히 대체하게 되었습니다.

### GitHub
GitHub는 개발자들이 자신의 코드 저장소를 호스팅하는 멀티테넌시 플랫폼입니다. 수백만의 저장소(각각이 별도의 테넌트)가 같은 인프라에서 실행되지만, 각 저장소의 코드와 이슈 정보는 격리되어 있습니다. GitHub Actions 같은 새로운 기능도 한 번의 배포로 모든 사용자에게 제공됩니다.

### Microsoft 365
Microsoft 365는 여러 조직이 동일한 클라우드 인프라에서 Office, Teams, OneDrive 등을 사용합니다. 각 조직의 문서, 메일, 대화 내용은 완벽히 격리되어 있으며, Microsoft는 중앙에서 모든 서비스를 관리하고 정기적으로 업데이트합니다. 이를 통해 기업들은 자신의 IT 인프라를 관리할 필요 없이 최신 기술을 사용할 수 있게 되었습니다.

## 🔗 관련 용어

- **SaaS (Software as a Service)**: 클라우드 기반의 소프트웨어 서비스 모델로, 테넌트 개념의 실제 적용 사례입니다.
- **데이터 격리 (Data Isolation)**: 테넌트 간 데이터가 혼합되지 않도록 보장하는 메커니즘입니다.
- **싱글 테넌시 (Single Tenancy)**: 각 고객이 독립된 애플리케이션과 인프라를 보유하는 아키텍처입니다.
- **Row-Level Security (RLS)**: 데이터베이스 수준에서 행(row) 단위로 접근 제어를 하는 기술입니다.
- **멀티테넌시 (Multi-tenancy)**: 여러 테넌트가 단일 인스턴스를 공유하는 아키텍처 패턴입니다.
- **API 토큰**: 테넌트 식별 및 인증에 사용되는 보안 토큰입니다.
- **테넌트 격리 (Tenant Isolation)**: 테넌트 간 데이터와 리소스의 논리적 또는 물리적 분리를 의미합니다.
