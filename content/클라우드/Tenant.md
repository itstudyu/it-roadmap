# Tenant (테넌트)

## 📝 정의

테넌트는 **같은 시스템을 나눠 쓰면서 서로 격리된 고객 단위**다.

SaaS 서비스 하나가 수많은 회사를 동시에 받는다. 그 회사 하나하나가 테넌트고, 애플리케이션과 서버는 같이 쓰되 데이터와 설정은 섞이지 않도록 갈라둔다.

### 비유
아파트. 건물과 엘리베이터는 같이 쓰지만 집 안 물건은 각자의 것이고 이웃 집은 들여다볼 수 없다.

## 🖼️ 그림으로 보기

```도해
흐름: 요청 하나가 어느 테넌트 것인지 어떻게 가려내나
요청 :: 회사별 주소나 토큰을 달고 도착한다
식별 :: 주소, 헤더, 토큰을 보고 테넌트 A 로 판정한다
컨텍스트 :: 요청이 끝날 때까지 A 를 들고 다닌다
DB 조회 :: 모든 쿼리에 A 라는 조건이 붙는다
< 응답 :: A 의 데이터만 담겨 돌아간다
= 처음 한 번 판정한 값을 끝까지 끌고 가는 구조다
```

## ⚠️ 해결하는 문제

```도해
대조: 고객사가 천 곳으로 늘면 무엇이 달라지나
고객마다 따로 || 하나를 나눠 쓰면
서버 :: 고객 수만큼 || 한 벌로 끝난다
업데이트 :: 천 번 배포한다 || 한 번 배포한다
자원 활용 :: 20~40% || 70~90%
= 하나를 나눠 쓰면 비용은 줄고 격리 책임은 커진다
```

고객마다 서버와 DB와 애플리케이션을 따로 세우면 자원이 남는다. 어떤 고객은 CPU를 10%만 쓰면서 서버 한 대를 통째로 차지한다. 고객이 늘수록 이 낭비도 같이 늘어난다.

배포는 더 큰 문제다. 버그 하나를 고쳐도 고객 수만큼 배포해야 하고, 고객이 천 곳이면 관리가 불가능해진다. 애플리케이션 한 벌이 모든 테넌트를 받도록 만들면 한 번 배포로 전부에 적용되고, 새 고객을 붙이는 비용도 거의 없어진다.

## ⚙️ 작동 원리

```도해
층: 테넌트 데이터를 어디까지 갈라놓을 수 있나
DB 분리 :: 테넌트마다 데이터베이스를 통째로 따로 둔다
스키마 분리 :: 한 DB 안에서 스키마만 나눠 쓴다
행 수준 격리 :: 같은 표에 담고 tenant_id 로 가른다
= 위로 갈수록 안전하고 비싸며 아래로 갈수록 싸고 실수에 약하다
```

가장 흔한 것은 맨 아래 방식이다. 모든 테넌트의 데이터를 같은 표에 넣고 `tenant_id` 열로 구분한다. 새 테넌트를 추가하는 비용이 거의 없고 확장에 유리하지만, 조건 하나를 빠뜨리면 남의 데이터가 그대로 나가므로 거르는 일을 코드에 맡길 수 없다.

그래서 실제 구현은 두 단계로 간다. 요청이 도착하면 주소의 앞부분이나 헤더, 토큰을 보고 어느 테넌트인지 먼저 판정한다. 그리고 그 값을 요청 컨텍스트에 넣어두고 이후 모든 조회에 조건으로 자동으로 붙인다. 여기에 더해 데이터베이스 자체의 행 수준 보안 기능으로 한 번 더 막아둔다.

자원은 나뉘지 않는다는 점도 알아둬야 한다. 한 테넌트가 무거운 작업을 돌리면 같은 서버를 쓰는 다른 테넌트가 느려진다. 이것을 시끄러운 이웃 문제라고 부르고, 테넌트별로 쓸 수 있는 양을 제한해서 다룬다.

## 📊 비교: 싱글 테넌시 와 멀티 테넌시

| | 싱글 테넌시 | 멀티 테넌시 |
|---|---|---|
| 인스턴스 | 고객마다 하나 | 전체가 하나 |
| 격리 | 물리적으로 분리 | 논리적으로 분리 |
| 비용 | 고객 수만큼 | 나눠 쓴다 |
| 배포 | 고객마다 따로 | 한 번에 전부 |
| 보안 설계 | 단순하다 | 복잡하다 |
| 맞춤 변경 | 쉽다 | 제한된다 |

## 💡 실제 사례

- **회사별 주소로 들어가는 SaaS** — 앞부분만 회사마다 다르고 뒤는 같은 서비스가 뜬다.
- **한 번 고치면 모두에게 적용** — 보안 취약점을 고쳐 배포하면 모든 고객사에 동시에 반영된다.
- **규제 때문에 따로 떼는 고객** — 금융이나 의료 고객이 물리적 분리를 요구하면 그 고객만 DB를 따로 준다.

## 🚫 흔한 오해

- **테넌트마다 서버가 따로 있다** — 대개 애플리케이션 한 벌이 전부를 처리한다. 나뉘어 있는 것은 서버가 아니라 데이터를 거르는 조건이다.
- **격리는 데이터베이스가 알아서 해준다** — 조건 하나를 빠뜨린 쿼리면 남의 데이터가 그대로 나간다. 애플리케이션과 DB 양쪽에서 검증해야 한다.
- **한 고객이 무엇을 하든 다른 고객은 영향이 없다** — 데이터는 갈라져 있어도 CPU와 메모리는 같이 쓴다. 한쪽이 무거운 작업을 돌리면 옆이 느려진다.

## 📝 정리

테넌트는 같은 애플리케이션과 인프라를 나눠 쓰면서 데이터만 갈라놓은 고객 단위다. 격리 방법은 DB를 통째로 나누는 쪽부터 한 표 안에서 `tenant_id`로 가르는 쪽까지 있고, 쌀수록 실수에 약해진다. 자원은 여전히 공유되므로 한 테넌트의 부하가 옆으로 번지는 것은 따로 막아야 한다.

## ❓ 이해했는지

- 같은 서비스인데 회사마다 다른 데이터가 보이는 이유는 → 그림

- 데이터가 갈라져 있는데도 옆 고객 때문에 느려지는 일이 생기는 이유는 → 작동 원리
