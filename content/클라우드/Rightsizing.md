# Rightsizing (크기 맞추기)

## 📝 정의

Rightsizing 은 **쓰는 만큼으로 크기를 다시 맞추는 일**이다.

처음 기계를 고를 때 크기는 짐작으로 정한다. 아직 아무도 안 써 봤으니 당연하고, 모자라면 장애가 나니까 넉넉하게 잡는 편이 안전하다. 그 짐작이 몇 달 뒤에도 그대로 돌고 있는 것이 문제다. 크기 맞추기는 며칠에서 몇 주치 실제로 쓴 값을 모아, 짐작으로 잡았던 크기를 **잰 값으로 바꿔 끼우는** 일이다.

### 이름
Right :: 알맞은
Sizing :: 크기 정하기
= 붙여 읽으면 "알맞게 크기 정하기". 줄이는 일이 아니라 맞추는 일이다

### 비유
옷 수선. 처음엔 넉넉하게 사 두지만, 몇 달 입어 보고 나서야 어디를 얼마나 줄일지 잰 값이 나온다.

### 예
쓰지도 않는 큰 기계가 몇 달째 돌고 있었다는 걸 청구서를 뜯어보다 알게 되는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 크기를 어떻게 다시 맞추나
재기 :: 몇 주치 실제로 쓴 값을 모은다
견주기 :: 평균만 보지 않고 봉우리를 함께 본다
고르기 :: 한 칸 줄일지 종류를 바꿀지 정한다
바꾸기 :: 멈췄다 켜거나 새로 띄워 옮긴다
@ 다시 재기로 :: 바꾸면 값이 또 달라진다
= 한 번 하고 끝나는 일이 아니라 도는 일이다
```

## ⚠️ 해결하는 문제

```도해
대조: 처음 고른 크기를 그대로 두면 어떻게 되나
그대로 두면 || 맞춰 두면
빈 자리 :: 매달 그대로 낸다 || 쓴 만큼만 낸다
느려질 때 :: 원인을 못 짚는다 || 재 둔 값이 있다
새 세대 기계 :: 옛것에 남는다 || 갈아탄다
= 처음 고른 크기는 짐작이었다. 몇 주만 돌려 보면 진짜 값이 나온다
```

넉넉하게 잡는 것은 값이 안 든다는 착각이 문제의 뿌리다. 절반만 쓰는 기계는 절반의 값을 매달 그냥 버리고, 그런 기계가 백 대면 버리는 값이 사람 한 팀 몫이 된다. 게다가 크게 잡아 둔 기계는 **성능 문제를 가린다.** 왜 느린지 물을 때 "여유가 있는데도 느리다" 는 정보와 "꽉 차서 느리다" 는 정보는 완전히 다른 곳을 가리키는데, 잰 값이 없으면 둘 다 짐작으로 남는다.

세 곳 모두 이 일을 사람 눈에 맡기지 않고 도구로 판다. AWS 는 Compute Optimizer 가 자원의 설정과 쓴 값을 분석해 크기 맞추기 권고를 내고 노는 자원을 찾아낸다고 적는다. Google Cloud 는 Compute Engine 이 도는 기계의 CPU 와 메모리 사용률을 지켜보다 머신 유형을 권한다고 적고, Azure 는 Advisor 가 낮게 쓰는 자원을 찾아 값을 줄여 준다고 적는다. **어느 쪽이든 사람이 하는 일은 "권고를 볼지 말지" 가 아니라 "이 권고를 믿어도 되는 창인지" 를 따지는 일이다.**

## 📊 비교: 세 곳은 무엇을 근거로 권해 주나

| 물음 | AWS | Azure | Google Cloud |
|---|---|---|---|
| **도구 이름** | Compute Optimizer | Advisor 의 비용 항목 | 머신 유형 권장(Recommender) |
| **보는 기간** | 기본 14일, 돈 내면 93일 | 최근 7일 | 최근 8일 |
| **무엇을 보나** | CPU · 망 · 디스크 등, 메모리는 따로 넣어야 | 낮은 사용률 | CPU · 메모리 (60초 평균) |
| **어떻게 말하나** | 모자람 · 남음 · 알맞음 | "크기 줄이거나 끄라" | 더 작은 · 더 큰 유형 |
| **손대는 값** | 여유와 문턱, 기간을 조절 가능 | 정해진 기준 | 정해진 기준 |

**고르는 기준은 창의 길이다.** 7일에서 14일이라는 창은 월말 정산이나 분기 마감처럼 한 달에 한 번 오는 봉우리를 못 본다. 그 봉우리가 진짜인 시스템이라면 권고대로 줄였다가 정확히 그날 무너진다. AWS 가 창을 93일로 늘리는 것을 돈 받고 파는 이유가 여기 있고, 여유와 문턱을 손댈 수 있게 열어 둔 이유도 같다.

두 번째 기준은 **무엇을 못 보고 있나**다. Google 문서는 권고가 60초 평균을 근거로 하므로 그보다 짧은 순간의 치솟음은 안 잡힌다고 스스로 적는다. AWS 에서 메모리는 기본으로 안 보이고 따로 넣어 줘야 한다. 잰 적 없는 축은 권고에 안 들어간다.

## 💡 실제 사례

- **개발용 기계 정리** — 낮에만 쓰는 것을 밤새 큰 크기로 두는 자리가 가장 흔하다. 크기를 줄이는 것보다 끄는 편이 나은 경우도 여기서 갈린다.
- **저장 장치 갈아타기** — 기계만 보는 게 아니다. AWS 는 디스크·서버리스 함수·데이터베이스·주소 변환 장치까지 같은 도구로 권고를 낸다.
- **새 세대로 옮기기** — 같은 값에 더 빠른 세대가 나온 뒤에도 옛 세대에 남아 있는 경우다. 크기를 줄이는 게 아니라 종류를 바꾸는 쪽이 답인 자리다.

## 🚫 흔한 오해

- **권고대로 다 줄이면 된다** — 권고는 지난 며칠의 평균이다. 한 달에 하루 오는 봉우리, 재해가 났을 때 감당해야 할 몫, 앞으로 늘 계획은 그 창 안에 없다.
- **크기 맞추기는 값을 줄이는 일이다** — 모자란 것을 키우는 것도 같은 일이다. AWS 는 도구가 자원을 모자람·남음·알맞음으로 나눈다고 적는다. 이름이 "알맞게" 인 이유가 그것이다.
- **한 번 맞춰 두면 끝난다** — 쓰는 양이 바뀌면 다시 어긋난다. 도구가 매일 다시 재는 이유이고, 크기 맞추기가 행사가 아니라 도는 일인 이유다.

## 🚨 주의사항

- **메모리는 대개 안 보인다.** 안에서 재서 내보내지 않으면 밖에서는 메모리 사용률을 모른다. 메모리가 병목인 것을 CPU 만 보고 줄이면 그대로 사고가 된다.
- **바꾸려면 대개 멈춰야 한다.** 크기를 바꾸는 일은 무중단이 아니다. 언제 멈출지, 새로 띄워 옮길지를 먼저 정해 두고 시작한다.
- **미리 사 둔 할인과 부딪친다.** 1년·3년치를 미리 사 두었다면 크기를 바꾸는 순간 그 할인이 안 맞을 수 있다. 줄이기 전에 무엇을 얼마에 사 두었는지부터 본다.

## 📝 정리

**"짐작으로 잡은 크기를 잰 값으로 바꿔 끼우는 일"** 이라고 읽으면 된다. 세 곳 모두 도구를 파는데 근거로 삼는 창이 7일에서 14일이라, 그 창 밖에 있는 봉우리는 아무도 안 본 채로 권고가 나온다. 그러니 권고를 받았을 때 물을 것은 "얼마 아끼나" 가 아니라 "이 창이 내 봉우리를 담고 있나" 다.

## 🧒 열 살에게

작년에 산 옷이 너무 커서 소매를 접고 다녔지? 몇 달 입어 보면 어디가 얼마나 남는지 알게 되고, 그때 딱 맞게 줄이면 걸리적거리지 않아. 그런데 키가 크는 중이면 너무 바짝 줄여 놨다가 금방 못 입게 돼.
