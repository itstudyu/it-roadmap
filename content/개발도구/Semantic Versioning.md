# Semantic Versioning (유의적 버전)

## 📝 정의

Semantic Versioning 은 **세 자리 숫자로 호환을 약속하는 규칙**이다.

이름이 곧 규칙이다 — semantic(뜻이 있는) version(버전), 숫자 자체가 뜻을 갖는다. 순서는 `MAJOR.MINOR.PATCH` 이고 왼쪽 자리일수록 큰 약속이다. 앞자리를 올렸다는 것은 "고쳐 써야 한다" 는 통보, 가운데는 "기능이 늘었다", 끝자리는 "버그만 고쳤다" 는 뜻이다.

### 비유
책의 판과 쇄 표시. 개정판은 쪽수가 어긋나 같이 수업할 수 없지만, 2쇄는 오타만 고친 것이라 그대로 쓴다.

## 🖼️ 그림으로 보기

```도해
층: 1.4.2 의 세 자리는 각각 무엇을 약속하나
MAJOR :: 앞자리. 뒤로 호환이 깨졌다 — 고쳐 쓰라는 통보
MINOR :: 가운데. 기능이 늘었다 — 그대로 써도 된다
PATCH :: 끝자리. 버그만 고쳤다 — 그대로 써도 된다
= 왼쪽 자리일수록 큰 약속이다. 앞자리가 그대로면 올려도 안 깨진다
```

## ⚠️ 해결하는 문제

```도해
대조: 버전 숫자에 규칙이 없으면 무엇이 곤란한가
규칙 없는 번호 || 유의적 버전
올려도 되나 :: 바꿔보고 안다 || 자리만 보면 안다
자동 갱신 :: 못 맡긴다 || 범위를 적어 맡긴다
깨질 때 :: 예고가 없다 || 앞자리가 예고한다
= 숫자에 약속을 실어 두면, 올릴지 말지를 열어보지 않고 정할 수 있다
```

번호가 그냥 일련번호면 `1.4.2` 에서 `1.5.0` 으로 올려도 되는지 알 방법이 없다. 바꿔서 돌려 보고 깨지면 되돌리는 것이 유일한 확인법이고, 의존성이 수십 개면 그 확인을 수십 번 해야 한다.

유의적 버전은 그 판단을 **번호 안으로 옮긴다.** 자리마다 뜻이 정해져 있으니 "가운데 자리까지는 자동으로 받고 앞자리는 사람이 본다" 처럼 미리 정해 둘 수 있다.

## ⚙️ 작동 원리

전제가 하나 있다. 이 규칙을 쓰는 소프트웨어는 **공개 API 를 반드시 선언해야 한다** — 코드로 드러내든 문서로 적어두든. 무엇이 공개 약속인지 정해지지 않으면 "깨졌다" 를 판정할 기준이 없기 때문이다. `1.0.0` 이 그 공개 API 를 확정하고, 그 뒤의 번호 올림은 전부 이 API 가 어떻게 바뀌는지에 달린다.

| 자리 | 언제 올리나 | 같이 하는 일 |
|---|---|---|
| **PATCH** | 뒤로 호환되는 버그 수정만 있을 때 | 없음 |
| **MINOR** | 공개 API 에 뒤로 호환되는 기능이 늘었을 때 | PATCH 를 0 으로 |
| **MAJOR** | 공개 API 에 뒤로 호환되지 않는 변경이 들어갔을 때 | MINOR·PATCH 를 0 으로 |

`0.y.z` 는 이 표의 바깥이다. 초기 개발 구간이라 **무엇이든 아무 때나 바뀔 수 있고**, 공개 API 를 안정된 것으로 봐서는 안 된다. 정식 전 시험판은 패치 자리 뒤에 붙임표를 달아 적는다 — `1.0.0-alpha`. 이 표시가 붙은 판은 불안정하며, 붙임표 앞의 번호가 약속하는 호환을 아직 만족하지 못할 수 있다.

## 💡 실제 사례

- **의존성 범위 적기** — `~1.0.4` 는 끝자리만, `^1.0.4` 는 가운데 자리까지 올라오는 것을 허용한다. 앞자리를 올리는 일만 사람 몫으로 남는다.
- **첫 공개** — 처음 내보내는 판은 `1.0.0` 으로 시작한다. 그 번호가 공개 API 를 확정하고, 이후의 모든 올림이 그 기준을 따른다.
- **시험판 내보내기** — 정식판 전에 `1.0.0-alpha` 처럼 붙임표를 달아 낸다. 같은 `1.0.0` 이 약속하는 호환을 아직 못 지킬 수 있다는 표시다.

## 🚫 흔한 오해

- **버전 숫자가 올라가면 좋아진 것이다** — 앞자리가 올라간 건 개선 소식이 아니라 "그대로 쓰면 깨진다" 는 통보다. 뒤로 호환되지 않는 변경이 들어갔을 때 올리는 자리다.
- **유의적 버전을 붙이면 깨질 일이 없다** — 숫자는 약속을 표시할 뿐이다. 이 규칙은 공개 API 선언을 먼저 요구하는데, 그게 없으면 무엇이 깨진 것인지 가릴 기준부터 없다.
- **`0.2.0` 에서 `0.3.0` 이면 안 깨진다** — 앞자리가 0 인 구간에는 그 약속이 없다. 초기 개발용이라 무엇이든 아무 때나 바뀔 수 있다.

## 🚨 주의사항

- **내보낸 판의 내용은 고치지 않는다** — 한 번 배포된 버전은 그대로 둔다. 고쳤으면 새 번호로 다시 낸다. 오타 하나여도 끝자리를 올린다.
- **올릴 때 아래 자리를 0 으로 되돌린다** — `1.4.7` 에 기능을 더하면 `1.5.0` 이지 `1.5.7` 이 아니다. 앞자리를 올리면 가운데와 끝자리가 둘 다 0 이 된다.
- **범위 표기는 앞자리를 넘지 않는다** — `^` 는 가운데 자리까지만 열어 준다. 앞자리 갱신은 자동으로 받는 물건이 아니라 사람이 확인할 일이다.

## 📝 정리

유의적 버전은 세 자리 숫자에 호환 약속을 실어 두는 규칙이다. 앞자리는 깨짐, 가운데는 추가, 끝자리는 수정이고, 그 판단의 기준은 미리 선언해 둔 공개 API 다. 그래서 번호를 정하는 일은 취향 문제가 아니라 사용자에게 보내는 통보다.

## ❓ 이해했는지

- `^1.2.3` 이라고 적어 두면 `2.0.0` 은 왜 자동으로 안 올라오나 → 실제 사례
- 오타 하나만 고친 판을 같은 번호로 다시 올리면 안 되는 이유는 → 주의사항
- 앞자리가 올라간 새 판을 봤을 때 가장 먼저 의심할 것은 → 그림
