# Git Branch (브랜치)

## 📝 정의

Git Branch 는 **커밋 하나를 가리키는 이름표**다.

옛 버전 관리 도구는 가지를 하나 내려면 프로젝트 파일을 전부 다른 폴더로 복사했고, 프로젝트 크기에 따라 몇 초에서 몇 분이 걸렸다. Git 은 커밋의 SHA-1 체크섬 40자와 줄바꿈 하나, 합쳐서 41바이트를 파일에 적는 것으로 끝낸다. 그래서 브랜치를 만드는 일이 프로젝트가 아무리 커도 언제나 즉시다.

### 비유
책갈피. 하나 더 꽂아도 책이 두 권이 되지는 않고, 읽던 자리가 옮겨 가면 따라 옮겨 간다.

## 🖼️ 그림으로 보기

```도해
대조: 브랜치를 하나 만들면 무엇이 생기나
파일 사본으로 || 이름표 하나로
생기는 것 :: 프로젝트 사본 || 41바이트 파일
그 안에 :: 파일 전부 || 커밋 해시 40자
만드는 시간 :: 크기에 비례 || 언제나 즉시
버리는 값 :: 폴더째 지움 || 파일 하나 지움
= 브랜치는 복사한 작업 공간이 아니라 커밋 하나를 가리키는 이름표다
```

## ⚠️ 해결하는 문제

```도해
대조: 브랜치 없이 main 에서만 일하면 어떻게 되나
main 에서만 || 브랜치로
실험 :: 남에게 다 보인다 || 내 가지에만
반쯤 한 일 :: main 에 섞인다 || 따로 쌓인다
되돌리기 :: 커밋을 골라내야 || 가지를 버린다
= 이름표를 하나 더 두는 것만으로 작업이 서로 섞이지 않는다
```

한 줄기에서만 일하면 반쯤 만든 기능과 남이 쓰고 있는 코드가 같은 자리에 쌓인다. 실험이 망가지면 그 망가진 상태가 그대로 팀의 최신 상태가 되고, 되돌리려면 어느 커밋이 실험 것이었는지 골라내야 한다.

브랜치는 이력을 **가둬 놓을 자리**를 만들어 준다. 가지를 하나 내고 거기서만 커밋하면 그 작업은 그 이름표 뒤에만 쌓이고, 잘되면 합치고 아니면 이름표를 지운다. GitHub 문서도 브랜치를 "저장소 안의 가둬진 영역에서 기능을 만들고 버그를 고치고 안전하게 실험하게 해주는 것" 이라고 적는다.

## ⚙️ 작동 원리

```도해
흐름: 브랜치에서 커밋하면 이름표는 어떻게 움직이나
branch :: 지금 있는 커밋을 가리키는 이름표를 하나 더 만든다
HEAD :: 아직 옛 이름표에 있다. 만들었을 뿐 옮겨 가지 않았다
switch :: HEAD 가 새 이름표를 가리키도록 옮긴다
commit :: 새 커밋이 쌓인다
이름표 :: HEAD 가 가리키던 이름표가 새 커밋으로 따라간다
= 움직이는 것은 파일이 아니라 이름표 하나다
```

브랜치는 파일 하나다. 그 안에 든 것은 가리키는 커밋의 SHA-1 체크섬 40자뿐이고, 줄바꿈까지 세어도 41바이트다. 만들고 지우는 값이 이만큼이라 Git 에서는 가지를 부담 없이 낸다.

지금 어느 가지에 있는지는 `HEAD` 라는 별도의 포인터가 들고 있다. `git branch` 는 이름표만 만들고 `HEAD` 는 그대로 두기 때문에, 만든 가지로 옮겨 가려면 `git switch` 를 따로 해야 한다. 커밋을 하면 `HEAD` 가 가리키던 가지의 이름표가 새 커밋으로 자동으로 나아간다.

## 💡 실제 사례

- **기능 개발** — 새 기능마다 가지를 하나 내서, 절반만 된 코드가 팀의 최신 상태에 섞이지 않게 둔다.
- **급한 버그 수정** — 하던 일을 가지에 그대로 남겨 두고, 기본 브랜치에서 가지를 하나 더 내 고친 다음 돌아온다.
- **기본 브랜치** — 저장소를 복제하면 Git 이 로컬에 처음 꺼내 주는 가지가 이것이고, GitHub 은 저장소를 열었을 때 이 가지를 보여준다.

## 🚫 흔한 오해

- **브랜치를 만들면 코드가 복사된다** — 아니다. 커밋 해시 40자를 적은 파일 하나가 생긴다. 프로젝트 파일을 통째로 복사하던 것은 Git 이전 도구들의 방식이다.
- **브랜치를 만들면 그 가지로 옮겨 간다** — `git branch` 는 이름표만 만든다. 만든 가지에서 일하려면 `git switch` 로 `HEAD` 를 옮겨야 한다.
- **가지마다 작업 폴더가 따로 있다** — 작업 폴더는 한 판만 꺼내 놓은 자리다. 가지를 바꾸면 새 폴더가 생기는 게 아니라, 그 폴더의 파일이 그 가지에서 마지막으로 커밋했던 모습으로 되돌아간다.

## 📝 정리

브랜치는 커밋 하나를 가리키는 이름표다. 이름표를 하나 더 두는 값이 41바이트라서 만드는 일도 버리는 일도 부담이 안 된다. 그래서 Git 에서는 실험이든 버그 수정이든 일단 가지를 하나 내고 시작하는 것이 기본이 됐다.

## ❓ 이해했는지

- `git branch feature` 를 쳤는데도 여전히 예전 가지에서 일하고 있는 이유는 → 흔한 오해
- 프로젝트가 아무리 커도 브랜치 만드는 시간이 달라지지 않는 이유는 → 그림
- 실험하던 가지가 완전히 망가졌는데 팀의 최신 상태가 멀쩡한 이유는 → 해결하는 문제
