# Cherry-pick (체리픽)

## 📝 정의

Cherry-pick은 **커밋 하나만 골라 지금 가지에 옮겨 얹는 일**이다.

`git cherry-pick <커밋>` 은 그 커밋이 만든 변경을 지금 가지에 다시 적용하고, 그 결과를 **새 커밋으로 기록**한다. 그래서 원본은 그대로 남고 같은 변경이 두 커밋으로 존재하게 된다 — 적용된 시점이 다르니 해시도 다르다. Git 공식 문서는 이 명령이 하는 일을 "주어진 커밋들이 각각 도입한 변경을 적용하고, 그 각각에 대해 새 커밋을 기록한다" 로 적어 뒀고, 시작하려면 작업 트리가 깨끗해야 한다는 조건도 같은 문단에 붙여 뒀다.

### 비유
책에서 마음에 든 문장 하나를 내 공책에 베껴 적는 일 — 원래 책에도 그 문장은 그대로 남는다.

### 예
가지를 잘못 고른 채 커밋한 것을 뒤늦게 알았을 때, 그 커밋 하나만 옳은 가지로 옮겨 붙이는 자리다.

## 🖼️ 그림으로 보기

```도해
흐름: 남의 가지에 있는 커밋 하나만 어떻게 가져오나
가지 B :: 커밋 셋이 쌓여 있다
고르기 :: 그중 급한 하나의 해시를 적는다
내 가지 :: 깨끗한 상태여야 시작된다
적용 :: 그 커밋이 만든 변경만 얹는다
새 커밋 :: 같은 변경, 다른 해시로 기록된다
= 가지째 합치지 않고 커밋 하나만 베껴 오는 일이다
```

## ⚠️ 해결하는 문제

```도해
대조: 급한 수정 하나만 필요할 때 가지째 합치면 어떻게 되나
가지째 합치기 || 커밋 하나만
들어오는 것 :: 안 끝난 것도 || 고른 것만
검증 범위 :: 가지 전체 || 커밋 하나
릴리스 :: 미룰 수밖에 || 오늘 나간다
= 필요한 변경만 떼어 오면 나머지가 끝나기를 기다릴 필요가 없다
```

가지에는 대개 커밋이 여럿 쌓여 있고, 그중 하나만 급할 때가 있다. 가지를 통째로 합치면 아직 리뷰도 안 끝난 커밋까지 같이 들어오고, 그러면 검증해야 할 범위가 가지 전체로 늘어난다. 릴리스는 가장 늦게 끝나는 커밋을 기다려야 한다.

체리픽은 그 사이를 끊는다. GitHub 문서도 이 명령을 "한 가지의 커밋을 다른 가지에 같은 변경을 담은 사본으로 만드는 일" 이라고 설명하면서, 풀 리퀘스트를 만들거나 합칠 준비가 되기 전에 쓸 수 있는 방법으로 든다.

## ⚙️ 작동 원리

```bash
git switch release-1.4
git cherry-pick -x a1b2c3d     # 어디서 왔는지 메시지에 남긴다
# 충돌이 나면 멈춘다
git add .
git cherry-pick --continue     # 이어서 마친다 (--abort 로 되돌릴 수도 있다)
```

적용이 깔끔하지 않으면 명령은 **중간에 멈춘 채로 남는다.** 가지와 `HEAD` 는 마지막으로 성공한 커밋에 그대로 있고, 문제가 된 커밋은 `CHERRY_PICK_HEAD` 에 기록된다. 깔끔히 적용된 파일은 이미 반영돼 있고, 충돌한 파일에는 `<<<<<<<` 와 `>>>>>>>` 로 감싼 표시가 들어간다. 손으로 풀고 `--continue`, 없던 일로 하려면 `--abort`, 멈춘 상태만 치우려면 `--quit` 이다.

자주 쓰는 갈래는 셋이다. `-x` 는 커밋 메시지 끝에 "(cherry picked from commit …)" 한 줄을 붙여 출처를 남긴다(충돌 없이 딸 때만 붙는다). `-n` 은 적용만 하고 커밋을 안 만들어서, 여러 커밋의 결과를 한 커밋으로 묶을 때 쓴다. 머지 커밋은 어느 쪽을 본줄기로 볼지 알 수 없어 그냥 딸 수 없고, `-m` 으로 부모 번호를 대야 한다.

## 💡 실제 사례

- **핫픽스 내려보내기** — 줄기에서 먼저 고쳐 검사를 통과시키고, 그 커밋만 릴리스 가지로 옮겨 그 가지만 다시 내보낸다.
- **리뷰가 끝나기 전에 먼저 필요한 조각** — 남의 가지에서 공용 함수 하나를 만든 커밋만 가져와 내 작업을 이어 간다.
- **가지를 잘못 골랐을 때** — 엉뚱한 가지에 쌓아 둔 커밋을 옳은 가지로 베껴 오고, 원래 가지는 원래대로 되돌린다.

## 🚫 흔한 오해

- **체리픽하면 그 커밋이 옮겨 간다** — 옮겨 가지 않는다. 원본은 그대로 있고 같은 변경을 담은 커밋이 하나 더 생긴다. 해시도 달라서 두 커밋은 서로를 모른다.
- **급한 건 일단 체리픽으로 옮기는 게 낫다** — 같은 변경이 두 곳에 따로 존재하면 어느 가지에 그 수정이 들어갔는지 사람이 기억해야 한다. 가지를 합칠 수 있는 상황이면 합치는 편이 낫다.
- **머지 커밋도 그냥 체리픽된다** — 안 된다. 어느 쪽을 본줄기로 볼지 알 수 없어서, `-m` 으로 부모 번호를 직접 대야 한다.

## 🚨 주의사항

- **한 방향으로만 딴다.** 트렁크 기반 개발 규범 문서는 릴리스 가지에서 고친 뒤 나중에 줄기로 체리픽할 생각을 하지 말라고 못 박는다. 가져오기를 잊으면 몇 주 뒤에 같은 버그가 다시 나온다.
- **작업 트리가 깨끗해야 시작된다.** 고치던 게 손에 남아 있으면 명령이 시작조차 안 된다. `git stash` 로 치워 두고 딴 뒤에 다시 꺼낸다.
- **출처를 남겨라.** `-x` 를 붙이면 원래 커밋이 무엇인지 메시지에 남는다. 다만 남이 볼 수 없는 개인 가지에서 딸 때는 받는 사람에게 쓸모없는 정보라 붙이지 말라고 문서가 말한다.

## 📝 정리

체리픽은 가지를 합치지 않고 커밋 하나가 만든 변경만 지금 가지에 다시 적용해 새 커밋으로 남기는 일이다. 그래서 급한 수정을 릴리스 가지로 내려보낼 수 있는 대신, 같은 변경이 해시가 다른 두 커밋으로 갈라져 남는다. 그 대가를 감당할 수 있는 한 방향으로만 쓰는 것이 규칙이다.

## ❓ 이해했는지

- 체리픽한 뒤에도 원본 가지의 이력이 그대로인 이유는 무엇인가 → 흔한 오해
- 해시가 원본과 다른데도 같은 변경이라고 말할 수 있는 까닭은 → 그림
- 체리픽을 시작하려는데 작업 트리가 깨끗하지 않다고 한다. 무엇을 먼저 하나 → 주의사항
