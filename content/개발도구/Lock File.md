# Lock File (잠금 파일)

## 📝 정의

잠금 파일은 **실제로 깔린 버전을 그대로 적어 둔 파일**이다.

npm 은 `package-lock.json` 을 쓰고, Python 쪽에는 표준 형식으로 `pylock.toml` 이 있다. 이름은 달라도 하는 일은 하나다 — 사람이 적은 범위가 아니라 도구가 고른 실물을 남긴다.

### 비유
장 볼 목록에는 "우유"라고만 적혀 있지만 영수증에는 어느 브랜드 몇 밀리리터를 샀는지 남는 것과 같다.

## 🖼️ 그림으로 보기

```도해
대조: 잠금 파일이 없으면 무엇이 달라지나
잠금 파일 없이 || 잠금 파일로
적힌 버전 :: 범위 `^1.2.3` || 실물 `1.2.9`
팀원끼리 :: 다른 게 깔린다 || 같은 게 깔린다
전이 의존성 :: 기록이 없다 || 전부 적힌다
= 범위는 "이 안이면 아무거나", 잠금 파일은 "바로 이것"이다
```

## ⚠️ 해결하는 문제

```도해
흐름: "내 컴퓨터에서는 되는데" 는 어떻게 생기나
나 :: 3월에 설치. 범위에 맞는 `1.2.3` 이 깔린다
내 화면 :: 잘 돌아간다. 소스만 커밋해 올린다
동료 :: 5월에 같은 명령. 이번엔 `1.9.0` 이 깔린다
동료 화면 :: 같은 소스인데 여기서 깨진다
= 소스를 맞춰도 깔린 버전이 다르면 결과가 다르다
```

소스는 같았다. 다른 것은 그 소스가 기대는 코드였다. 범위로 적어 두면 설치하는 시점마다 조건을 만족하는 가장 높은 버전이 뽑히고, [[Dependency]] 의 사슬을 따라 그 아래까지 전부 그렇게 뽑힌다. 그래서 "내 컴퓨터에서는 되는데" 는 사람 문제가 아니라 기록이 없어서 생기는 문제다.

잠금 파일은 그 시점의 트리 전체를 적어 둔다. npm 문서는 이 파일을 커밋해야 하는 이유로 "팀원, 배포, 지속적 통합이 정확히 같은 의존성을 설치하도록 보장된다"는 것을 첫째로 든다. Python 쪽 `pylock.toml` 규격도 첫 문장에서 이 형식의 목적을 "재현 가능한 설치" 라고 밝힌다.

## ⚙️ 작동 원리

사람이 쓰는 파일이 아니다. npm 문서는 `package-lock.json` 이 "npm 이 `node_modules` 트리나 `package.json` 을 바꾸는 모든 작업에서 자동으로 생성된다"고 적는다. 설치할 때마다 도구가 다시 쓴다.

적히는 것은 트리 전체다. 내가 목록에 안 적은 전이 의존성까지 어느 버전이 어디서 왔는지 남는다. npm 문서는 그 덕에 얻는 것으로 트리 변화가 소스 관리 diff 로 읽힌다는 점, `node_modules` 폴더를 커밋하지 않고도 예전 상태로 되돌아갈 수 있다는 점을 함께 든다.

`pylock.toml` 은 버전만 적지 않는다. 규격은 아카이브와 휠마다 해시 표에 최소 한 항목을 요구하고 `sha256` 을 권한다. 같은 버전 이름을 붙인 다른 파일이 와도 그 자리에서 걸러진다는 뜻이다.

읽는 쪽에는 전용 명령이 따로 있다. `npm ci` 는 잠금 파일이 **반드시** 있어야 하고, `package.json` 과 어긋나면 잠금 파일을 고치는 대신 오류로 멈춘다. npm 문서는 이 명령이 "`package.json` 이나 어떤 잠금 파일에도 절대 쓰지 않는다 — 설치가 사실상 얼어 있다" 고 적는다.

## 💡 실제 사례

- **새로 들어온 사람의 첫 설치** — 몇 달 전에 세팅한 사람과 같은 트리가 깔린다. npm 문서가 팀원·배포·CI 가 정확히 같은 것을 깔도록 보장한다고 말하는 자리다.
- **CI 빌드** — `npm ci` 로 돌린다. 잠금 파일이 없으면 시작조차 안 하고, `package.json` 과 어긋나면 조용히 맞추는 대신 오류로 세운다.
- **버전을 올린 커밋 리뷰** — 잠금 파일이 소스 관리에 들어 있으면 트리에서 무엇이 바뀌었는지 diff 로 보인다. npm 문서가 이 파일의 이유로 드는 것 중 하나다.

## 🚫 흔한 오해

- **도구가 만든 파일이니 커밋할 필요 없다** — 반대다. npm 문서는 이 파일이 소스 저장소에 커밋되도록 만들어졌다고 못 박는다. 커밋하지 않으면 팀원과 CI 가 같은 것을 깔았다고 말할 근거가 없다.
- **`package.json` 에 버전을 적어 뒀으니 같은 게 깔린다** — 거기 적힌 것은 대개 범위다. 조건을 만족하는 더 높은 버전이 나오면 그것이 깔리고, 전이 의존성은 아예 적혀 있지도 않다.
- **잠금 파일이 있으면 버전은 신경 쓸 필요 없다** — 못 박아 둔 그대로 낡는다. 잠금은 "안 바뀐다"는 보장이지 "최신이다"는 보장이 아니라서, 올리는 일은 사람이 따로 해야 한다.

## 🚨 주의사항

- **커밋해라.** 잠금 파일을 `.gitignore` 에 넣는 순간 이 파일은 아무 일도 하지 않는다. 팀과 나눠 갖지 않은 기록은 기록이 아니다.
- **CI 에서는 설치 명령을 바꿔라.** `npm install` 은 어긋난 것을 맞추면서 잠금 파일을 고치고, `npm ci` 는 고치지 않고 멈춘다. 어긋난 것을 알아야 하는 자리에서는 멈추는 쪽이 맞다.
- **잠금 파일은 손으로 고치지 않는다.** 도구가 만드는 파일이라, 충돌이 났으면 다시 만들게 하는 편이 안전하다.

## 📝 정리

잠금 파일은 범위로 적어 둔 의존성이 실제로 어느 버전으로 깔렸는지를 트리 전체에 대해 적어 둔 파일이다. 도구가 만들고 사람이 커밋해서 팀원과 CI 가 같은 것을 깔게 만든다. "내 컴퓨터에서는 되는데" 를 막는 일은 소스를 맞추는 일이 아니라 이 파일을 맞추는 일이다.
