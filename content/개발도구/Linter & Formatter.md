# Linter & Formatter (린터와 포매터)

## 📝 정의

린터는 **버그**를 찾고, 포매터는 모양을 맞추는 도구다.

ESLint 문서는 스스로를 "설정할 수 있는 JavaScript 린터" 라 하고 코드에서 문제를 찾아 고치도록 돕는다고 적는다. Prettier 문서는 둘의 관계를 한 줄로 정리한다 — 모양은 포매터에, 버그 잡기는 린터에 맡기라는 것이다.

### 비유
원고를 두 사람이 본다 — 교정자는 "이건 사실이 틀렸다"고 하고, 조판사는 줄 간격만 맞춘다.

## 🖼️ 그림으로 보기

```도해
대조: 린터와 포매터는 무엇이 다른가
린터 |=| 포매터
잡는 것 :: 버그가 될 것 || 모양이 다른 것
어겼다는 말 :: 실제로 위험하다 || 취향이 다르다
고치는 법 :: 사람이 판단한다 || 다시 찍어낸다
= 린터는 옳고 그름을, 포매터는 모양을 다룬다
```

## ⚠️ 해결하는 문제

```도해
대조: 린터와 포매터를 안 나누면 무슨 일이 생기나
구분 없이 || 나눠 두면
코드 리뷰 :: 공백 얘기로 끝난다 || 로직을 본다
규칙 정하기 :: 취향으로 싸운다 || 도구가 정한다
진짜 버그 :: 잔소리에 묻힌다 || 눈에 띈다
= 취향을 옳고 그름처럼 다루면 팀은 취향으로 다툰다
```

Prettier 문서는 린터 규칙을 두 부류로 나눈다. `max-len`, `no-mixed-spaces-and-tabs`, `keyword-spacing`, `comma-style` 처럼 **모양을 다루는 규칙**과 `no-unused-vars`, `no-implicit-globals`, `prefer-promise-reject-errors` 처럼 **버그가 될 것을 잡는 규칙**이다.

앞의 부류에는 정답이 없다. 줄 길이를 100 자로 할지 120 자로 할지는 옳고 그름이 아니라 취향인데, 린터에 얹으면 "위반" 이라는 같은 옷을 입고 나와서 팀이 그걸 옳고 그름처럼 논쟁한다. Prettier 문서는 이 부류를 통째로 없애는 쪽을 택했다 — 프로그램을 처음부터 다시 찍어내니 프로그래머가 그 자리에서 실수할 수가 없다는 것이다.

뒤의 부류는 반대다. 안 쓰는 변수는 취향이 아니라 지우다 만 코드일 때가 많다. Prettier 문서는 이런 규칙에 대해 자기는 "아무 도움도 안 준다" 고 하면서, 그것이 실제 버그를 잡을 가능성이 커서 린터가 주는 가장 중요한 것이라고 덧붙인다.

## ⚙️ 작동 원리

린터는 규칙을 하나씩 견준다. ESLint 문서는 규칙을 "코드가 어떤 기대를 지키는지, 지키지 않으면 무엇을 할지를 판정하는 것" 이라고 정의한다. 규칙 목록은 성질로 갈라져 있다.

| 분류 | ESLint 문서의 설명 |
|---|---|
| Possible Problems | 코드에 있을 수 있는 논리 오류에 관한 것 |
| Suggestions | 다르게 하는 방법을 제안하는 것 |
| Layout & Formatting | 어떻게 실행되는지가 아니라 어떻게 보이는지에 관한 것 |

자동 고침도 두 갈래다. 문서는 fix 를 "애플리케이션 로직을 바꾸지 않고 위반을 안전하게 고치는 것" 이라 하고, suggestion 은 "로직을 바꿀 수 있어서 자동으로 적용할 수 없다" 고 적는다. 그래서 suggestion 은 CLI 로는 안 되고 편집기에서 사람이 골라야 한다.

ESLint 는 세 번째 분류를 스스로 코어에서 내렸다. `indent`, `semi`, `quotes`, `keyword-spacing` 같은 모양 규칙은 deprecated 로 내려가 `@stylistic/eslint-plugin` 으로 옮겨졌고, 코어의 Layout & Formatting 자리에 남은 규칙은 `unicode-bom` 하나뿐이다.

포매터는 규칙을 견주지 않는다. Prettier 문서에 따르면 프로그램 전체를 일관된 방식으로 처음부터 다시 찍어낸다. 검사하고 지적하는 것이 아니라 결과물을 갈아 끼우는 쪽이다.

## 💡 실제 사례

- **코드 리뷰에서 공백 지적이 사라진다** — 저장할 때 포매터가 한 번 돌면 모양이 이미 하나로 맞아 있어서, 남는 지적이 로직뿐이다.
- **안 쓰는 변수 경고** — 모양 문제가 아니라 지우다 만 코드의 흔적일 때가 많다. Prettier 문서가 포매터로는 못 잡는다고 인정하면서 린터의 가장 중요한 몫이라고 하는 부류다.
- **저장할 때마다 같은 줄이 왕복하는 프로젝트** — 린터의 모양 규칙과 포매터가 그 줄을 서로 다르게 고치고 있다. 모양은 한 도구에만 맡기면 왕복이 멈춘다.

## 🚫 흔한 오해

- **린터가 코드를 예쁘게 만들어 준다** — 그건 포매터 몫이다. ESLint 는 모양 규칙을 코어에서 내려 별도 플러그인으로 옮기고 `unicode-bom` 하나만 남겼다.
- **포매터를 쓰면 린터는 필요 없다** — Prettier 문서가 직접 아니라고 한다. 모양 규칙은 없애 주지만 안 쓰는 변수처럼 버그가 될 것에는 아무 도움도 안 준다.
- **린터가 잡아 준 건 다 자동으로 고쳐도 된다** — 로직을 안 바꾸는 fix 만 그렇다. 로직이 바뀔 수 있는 suggestion 은 자동으로 적용되지 않고 사람이 골라야 한다.

## 🚨 주의사항

- **모양 규칙을 두 곳에서 켜지 마라.** 같은 줄을 두 도구가 다르게 고치면 저장할 때마다 코드가 왕복한다.
- **규칙을 켜기 전에 물어라.** 이걸 어기면 실제로 위험한가. 아니라면 그건 린터가 아니라 포매터가 정할 일이다.
- **자동 고침을 믿기 전에 종류를 보라.** fix 와 suggestion 은 안전 등급이 다르고, 후자는 애플리케이션 로직을 바꿀 수 있다.

## 📝 정리

린터는 "이건 버그가 될 수 있다"를 말하고, 포매터는 "이건 이렇게 찍는다"를 말한다. 앞은 옳고 그름이라 사람이 판단해야 하고, 뒤는 취향이라 도구가 정하면 그것으로 끝난다. 이 둘을 한 도구에 섞으면 팀은 취향을 옳고 그름처럼 놓고 다투게 된다.
