# Monorepo (모노레포)

## 📝 정의

Monorepo 는 **여러 프로젝트를 저장소 하나에 함께 두는 방식**이다.

이름 그대로 하나(mono)의 저장소(repo)다. 프로젝트를 폴더로 나누는 것은 그대로 두고, 그걸 담는 저장소만 하나로 합친다. 그래서 "합쳐지는 것" 은 코드가 아니라 저장소와 그걸 다루는 명령들이다.

### 비유
칸을 나눠 쓰는 냉장고 한 대. 각자 자리는 따로지만 문이 하나여서, 열 때마다 남의 칸까지 같이 보인다.

### 예
저장소를 하나 받았는데 열어 보니 앱과 라이브러리 폴더가 여러 개 나란히 들어 있는 그 모양이다.

## 🖼️ 그림으로 보기

```도해
대조: 저장소를 여러 개 두는 것과 하나로 묶는 것은 무엇이 다른가
저장소 여러 개 |=| 모노레포
프로젝트 자리 :: 저장소마다 하나 || 한 저장소 안에
옆 것 가져오기 :: 배포된 판을 받는다 || 폴더째 이어 쓴다
한 번에 받는 양 :: 필요한 것만 || 저장소 전체
의존성 올리기 :: 저장소마다 따로 || 한 번에 묶는다
= 프로젝트 여러 개를 한 폴더 나무에 모아 둔 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 프로젝트를 저장소마다 나눠 두면 옆 코드를 어떻게 쓰나
따로 둘 때 || 한 저장소일 때
옆 코드 잇기 :: 손으로 이어 붙인다 || 설치가 이어 붙인다
고친 것 확인 :: 올려서 받아 본다 || 그 자리에서 본다
같은 의존성 :: 저장소마다 올린다 || 한 번에 올린다
= 옆 프로젝트를 남처럼 다루던 일이, 한 폴더 안 이웃으로 바뀐다
```

저장소가 갈려 있으면 내가 방금 고친 라이브러리를 옆 프로젝트에서 쓰려면 먼저 내보내야 한다. 안 내보내고 확인하려면 로컬 링크를 손으로 걸었다 풀었다 해야 하고, 그걸 잊으면 어제 판을 보면서 오늘 버그를 찾는다.

한 저장소면 옆 프로젝트가 그냥 옆 폴더다. npm 은 이 연결을 `npm install` 의 일부로 자동화해서 **손으로 `npm link` 를 걸 필요를 없앴다.** 의존성 갱신도 폴더마다 따로가 아니라 이름으로 묶어 한 번에 처리할 수 있다.

## 🧱 구성

```도해
층: 모노레포 한 저장소 안에는 무엇이 겹쳐 있나
Git 저장소 :: 이력과 커밋이 하나뿐인 바깥 테두리
루트 패키지 :: 어느 폴더가 패키지인지 선언해 두는 자리
하위 패키지 :: 각자 이름과 의존성을 가진 별개 프로젝트
= 하나로 합쳐진 것은 바깥 테두리뿐이고, 안쪽 프로젝트는 나뉜 채로 남는다
```

## ⚙️ 작동 원리

npm 은 이 구조를 **워크스페이스**라고 부른다. 문서의 정의는 "하나의 최상위 루트 패키지 안에서 로컬 파일 시스템의 여러 패키지를 관리하도록 돕는 기능 묶음" 이다.

루트 `package.json` 에 하위 패키지 경로를 배열로 적어 둔다 — `"workspaces": ["packages/a"]`. 이 상태에서 `npm install` 을 돌리면 `packages/a` 폴더가 현재 디렉터리의 `node_modules` 로 심볼릭 링크된다. 그래서 옆 패키지를 레지스트리에서 받아 설치한 것처럼 불러 쓰면서도, 실제로는 그 자리에서 고치는 원본을 보고 있다.

저장소를 합치는 데 특별한 기능이 필요한 게 아니라는 점이 중요하다. 저장소는 여전히 Git 저장소 하나이고, 달라지는 것은 **폴더 경계를 도구가 알아보게 만드는 선언 한 줄**이다.

## 💡 실제 사례

- **한 저장소, 여러 패키지** — 루트 `package.json` 에 `workspaces` 를 적어 두면 `npm install` 한 번으로 하위 패키지들이 서로 이어진다.
- **의존성 갱신 묶기** — 여러 폴더가 같이 쓰는 의존성을 이름으로 묶으면, 폴더마다 열리던 PR 이 하나로 합쳐진다. 테스트도 폴더 수만큼 돌지 않는다.
- **필요한 폴더만 꺼내 쓰기** — 저장소는 통째로 두고 작업 트리만 지금 만지는 디렉터리로 줄인다. 파일이 많은 저장소에서 지금 중요한 건 몇 개뿐일 때 쓰는 방법이다.

## 🚫 흔한 오해

- **모노레포가 저장소 여러 개보다 낫다** — 파일이 늘어난 만큼 도구가 볼 것도 늘어난다. `package.json` 이 수백 개인 모노레포는 의존성 갱신 작업이 제한 시간을 넘겨 실패하는 대표적인 사례로 문서에 적혀 있다.
- **한 저장소로 합치면 코드도 하나로 합쳐진다** — 아니다. 프로젝트는 폴더로 나뉜 채 그대로 있고, 하나가 되는 것은 저장소와 그걸 다루는 명령들뿐이다.
- **모노레포는 한 덩어리로 배포하는 것이다** — 저장소가 하나인 것과 배포 단위가 하나인 것은 다른 이야기다. 안의 폴더들은 각자 이름을 가진 별개 패키지로 남는다.

## 🚨 주의사항

- **도구가 먼저 지친다** — 의존성 갱신 봇은 제한 시간(GitHub 호스팅 러너에서 55분)이 있다. 매니페스트가 수백 개인 저장소는 그 안에 못 끝나서 "시간 초과" 로 떨어진다.
- **PR 이 폴더 수만큼 늘어난다** — 갱신을 폴더별로 두면 같은 의존성 하나에 PR 이 여러 개 열린다. 여러 디렉터리를 이름으로 묶으면 PR 한 개로 줄고 CI 비용도 같이 줄어든다.
- **묶기에는 조건이 있다** — 여러 디렉터리를 이름으로 묶으려면 그 디렉터리들이 **같은 생태계**여야 한다(전부 npm, 또는 전부 bundler). 언어가 섞인 저장소는 그 이득을 못 본다.

## 📝 정리

모노레포는 프로젝트 여러 개를 저장소 하나에 담는 방식이다. 옆 프로젝트를 배포된 판이 아니라 같은 폴더 안 이웃으로 다룰 수 있게 되고, 그 대가로 한 번에 받고 검사할 양이 저장소 전체로 커진다. 저장소를 합치는 것과 배포를 합치는 것은 별개의 결정이다.

## ❓ 이해했는지

- 저장소를 하나로 합쳤는데 의존성 갱신 PR 이 왜 폴더마다 열리나 → 주의사항
- `npm link` 를 손으로 걸지 않아도 옆 패키지가 잡히는 이유는 → 작동 원리
- 저장소를 하나로 묶으면 한 번에 받아 오는 양은 왜 늘어나나 → 그림
