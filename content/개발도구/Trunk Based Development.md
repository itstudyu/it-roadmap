# Trunk Based Development (트렁크 기반 개발)

## 📝 정의

Trunk Based Development는 **모두가 한 줄기에 매일 합치는 방식**이다.

이름의 trunk 가 나무 줄기다. 가지(branch)를 길게 늘어놓지 않고 줄기 하나에서 함께 일한다는 뜻이 이름에 들어 있다. 규범 문서는 이것을 "개발자들이 trunk 라는 단일 브랜치에서 협업하고, 다른 오래 사는 개발 브랜치를 만들려는 압력에 저항하는 소스 관리 분기 모델" 로 정의하고, 팀은 하루에 한 번 이상 줄기에 커밋해야 한다고 못 박는다.

### 비유
설거지. 먹고 바로 하면 5분인데 사흘을 모아 두면 손도 대기 싫어진다.

### 예
세 주 만에 가지를 합치려다 충돌 파일이 수십 개 쏟아지는 일을 한 번 겪으면 이 방식을 찾게 된다.

## 🖼️ 그림으로 보기

```도해
대조: 브랜치를 오래 두면 무엇이 달라지나
오래 둔 브랜치 || 하루 안에 합치기
합칠 때 충돌 :: 몇 주 분량 || 하루 분량
남의 코드 :: 합칠 때 처음 봄 || 매일 본다
릴리스 :: 합치기를 기다린다 || 언제든 가능
= 줄기 하나에 매일 합치는 것이 트렁크 기반 개발이다
```

## ⚠️ 해결하는 문제

```도해
흐름: 브랜치를 세 주 동안 두면 마지막에 무슨 일이 생기나
1일차 :: 가지를 내고 혼자 고친다
1주차 :: 줄기는 남들 커밋으로 앞서간다
3주차 :: 기능은 다 됐다. 이제 합친다
합치기 :: 줄기를 먼저 받아 오다 충돌이 쏟아진다
검증 :: 무엇이 깨졌는지 짚어야 할 범위가 세 주다
= 늦게 합치면 합치는 일 자체가 새 프로젝트가 된다
```

합치기를 미루는 동안 줄기는 계속 움직인다. 규범 문서가 짧은 수명 가지의 상한을 이틀로 잡은 이유가 이것이다 — 이틀을 넘기면 그 가지가 오래 사는 가지가 될 위험이 있다고 적어 뒀다.

트렁크 기반 개발은 합치는 주기를 하루로 줄여서 한 번에 마주할 충돌을 하루 분량으로 만든다. 충돌이 사라지는 게 아니라, 매일 조금씩 만나서 작아지는 것이다. 문서가 이 모델을 지속적 통합의 핵심 조건이라고 부르는 것도 같은 이야기다 — 자주 합치는 팀만 줄기를 언제든 내보낼 수 있는 상태로 유지한다.

## ⚙️ 작동 원리

```도해
흐름: 트렁크 기반 개발에서 하루가 어떻게 돌아가나
아침 :: 줄기를 받아 내 가지에 먼저 합친다
낮 :: 작은 변경 하나를 끝낸다
CI :: 빌드와 테스트가 자동으로 돈다
리뷰 :: 동료 한 명이 본다
합치기 :: 줄기로 넣고 가지를 지운다
@ 다음 날 :: 가지 수명은 이틀을 넘기지 않는다
= 가지는 검사와 리뷰를 통과하기 위한 임시 통로일 뿐이다
```

가지를 아주 안 쓰는 것은 아니다. 규범 문서는 **짧은 수명 가지**를 리뷰와 빌드 검사용으로 권하면서, 거기 올라타는 사람은 한 명(짝 프로그래밍이면 두 명)이어야 하고 팀이 공유하는 개발 가지가 되면 안 된다고 못 박는다. 줄기로 넣기 전에는 줄기를 먼저 자기 가지로 받아 오는 순서를 권한다 — 충돌을 남의 자리가 아니라 내 자리에서 풀라는 뜻이다.

덜 끝난 일을 줄기에 두는 장치가 **기능 플래그**다. 꺼진 채로 프로덕션까지 올려 두고 필요할 때 켜면, 코드는 매일 합쳐지면서도 사용자에게는 안 보인다. 구조를 크게 갈아치울 때는 새 구현을 옆에 세워 두고 호출하는 곳을 조금씩 옮기는 branch by abstraction 을 쓴다.

릴리스는 줄기에서 필요할 때만 가지를 딴다. 버그는 **줄기에서 먼저 고치고** 그 커밋만 릴리스 가지로 옮긴다. 반대로 릴리스 가지에서 고친 뒤 나중에 줄기로 가져올 생각은 하지 말라고 문서가 못 박는다 — 지친 사람이 가져오기를 잊으면 몇 주 뒤에 같은 버그가 다시 나온다. GitHub 쪽에서 이 규칙을 강제하는 장치는 보호된 브랜치다. 상태 검사와 리뷰를 통과하지 않으면 줄기로 합쳐지지 않게 막아 준다.

## 📊 비교

| 항목 | Git Flow | Trunk Based Development |
|---|---|---|
| 오래 사는 가지 | 여럿 둔다 | 줄기 하나만 |
| 한 가지에 붙는 사람 | 여러 명이 함께 | 한 명(짝이면 두 명) |
| 기능 플래그 | 잘 살리지 못한다 | 전제로 삼는다 |
| 연속된 릴리스 | 동시 진행이 어렵다 | 줄기에서 언제든 |

규범 문서는 두 모델이 양립하지 않는다고 쓰고, 오래 사는 가지를 여럿 두는 모델 대신 트렁크 기반 개발을 하라고 권한다.

## 💡 실제 사례

- **급한 버그 수정** — 줄기에서 먼저 고쳐 자동 검사를 통과시키고, 그 커밋만 릴리스 가지로 옮겨 내보낸다.
- **덜 끝난 기능** — 플래그를 끈 채로 줄기에 합쳐 둔다. 남들 코드와 매일 같이 빌드되지만 사용자에게는 안 보인다.
- **큰 구조 변경** — 가지를 몇 주 두는 대신 새 구현을 옆에 세워 두고, 호출하는 곳을 하나씩 옮겨 간다.

## 🚫 흔한 오해

- **브랜치를 아예 안 쓰는 방식이다** — 쓴다. 다만 한 명이 이틀 안에 지울 가지만 쓴다. 규범 문서 자체가 그 가지를 리뷰와 빌드 검사 용도로 권한다.
- **어떤 팀이든 트렁크 기반이 낫다** — 커밋마다 자동으로 도는 빌드와 테스트가 먼저 있어야 한다. 그것 없이 매일 합치면 깨진 커밋이 곧바로 모두에게 간다.
- **기능 플래그를 걸었으면 그걸로 끝이다** — 규범 문서가 가장 길게 경고하는 자리다. 켠 뒤에 지우지 않으면 플래그가 쌓이고, 꺼진 쪽 코드까지 테스트를 계속 떠안는다.

## 📝 정리

트렁크 기반 개발은 오래 사는 가지를 두지 않고 줄기 하나에 하루 한 번 이상 합치는 분기 모델이다. 가지를 안 쓰는 게 아니라 이틀 안에 사라질 가지만 쓰고, 덜 끝난 일은 플래그를 끈 채 줄기에 둔다. 이렇게 하려면 커밋마다 도는 자동 검사가 먼저 서 있어야 한다.

## ❓ 이해했는지

- 기능이 아직 덜 끝났는데도 줄기에 합쳐 둘 수 있는 이유는 무엇인가 → 작동 원리
- 세 주 만에 합치려니 파일 수십 개가 충돌한다. 무엇이 이 상황을 만들었나 → 해결하는 문제
- 커밋마다 도는 자동 검사 없이 매일 합치기 시작하면 무슨 일이 생기나 → 흔한 오해
