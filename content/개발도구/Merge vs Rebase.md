# Merge vs Rebase (병합과 리베이스)

## 📝 정의

merge 와 rebase 는 가지를 합칠 때 **이력을 남길지 다시 쓸지**가 갈리는 두 방법이다.

merge 는 두 가지의 최신 상태와 공통 조상을 함께 보고 합친 결과를 담은 커밋을 하나 새로 만들어 얹는다. rebase 는 내 가지의 커밋들이 만든 변경을 하나씩 떼어 상대 가지 끝에 다시 붙인다. 합쳐진 뒤의 파일 내용은 어느 쪽이든 같고, 남는 이력의 모양만 다르다.

### 비유
여행 사진 정리. 찍힌 순서대로 그대로 두는 쪽과, 나중에 보기 좋게 한 줄로 다시 배열하는 쪽이 있다.

## 🖼️ 그림으로 보기

```도해
대조: 가지를 합칠 때 이력은 어떻게 달라지나
Merge |=| Rebase
합친 자리 :: 커밋이 하나 생김 || 아무것도 안 생김
이력 모양 :: 갈라진 자국 남음 || 한 줄로 펴짐
내 커밋 :: 그대로 있다 || 새로 만들어진다
합친 결과 :: 같다 || 같다
= 결과는 같고, 갈라졌던 사실을 남기느냐 지우느냐가 다르다
```

## ⚠️ 해결하는 문제

```도해
대조: 갈라진 가지를 합칠 방법이 없으면 어떻게 되나
합칠 수 없으면 || 합치는 명령으로
가지의 작업 :: 거기서 끝난다 || 본가지로 간다
이력 :: 갈라진 채 남음 || 다시 하나가 됨
옮기는 방법 :: 복사해 붙인다 || 명령 한 줄
= 갈라 놓는 것과 다시 합치는 것은 한 벌이다
```

브랜치는 이력을 갈라 놓는 장치일 뿐이다. 가지에서 한 일이 본가지로 들어가려면 합치는 단계가 따로 있어야 하고, 없으면 그 작업은 가지 안에 갇힌 채 끝난다.

Git 은 그 단계를 두 가지로 준다. **merge** 는 두 가지의 최신 스냅샷과 가장 가까운 공통 조상, 세 지점을 놓고 합쳐서 새 커밋을 하나 만든다. **rebase** 는 내 커밋들이 만든 변경을 상대 가지 끝에 다시 얹는다. 어느 쪽으로 끝내든 합쳐진 지점의 파일 내용은 똑같다.

## ⚙️ 작동 원리

```도해
흐름: rebase 는 커밋을 어떻게 옮겨 붙이나
공통 조상 :: 두 가지가 갈라진 지점을 찾는다
변경 뜨기 :: 내 커밋마다 무엇이 바뀌었는지 떼어 둔다
가지 옮김 :: 내 가지를 상대 가지 끝으로 옮긴다
다시 붙임 :: 떼어 둔 변경을 하나씩 차례로 얹는다
새 커밋 :: 내용은 같지만 해시가 다른 커밋이 생긴다
= 커밋을 옮긴 게 아니라 같은 변경으로 새로 만든 것이다
```

rebase 가 끝나면 원래 커밋은 버려지고, 비슷하지만 다른 커밋이 그 자리를 대신한다. 이력을 보면 병렬로 진행됐던 일이 한 줄로 이어진 것처럼 보인다. merge 쪽은 반대로 있던 커밋을 하나도 건드리지 않고, 갈라졌다 합쳐진 자국을 병합 커밋에 그대로 남긴다.

GitHub 에서 pull request 를 합치는 방법 세 가지도 이 둘에서 나온다. **merge commit** 은 가지의 커밋 전부와 병합 커밋 하나를 남기고, **squash** 는 가지의 커밋들을 하나로 눌러 합치고, **rebase and merge** 는 병합 커밋 없이 커밋들을 base 가지에 하나씩 얹으면서 커미터 정보와 커밋 해시를 새로 만든다.

## 💡 실제 사례

- **올리기 전 정리** — push 하기 전 내 가지를 rebase 해서 커밋 순서와 메시지를 다듬고, 그다음에 올린다.
- **합친 시점 남기기** — 릴리스 가지를 본가지에 넣을 때는 merge 로 해서 언제 무엇이 한꺼번에 들어왔는지를 병합 커밋에 남긴다.
- **pull request 합치기** — 팀이 이력을 그대로 보고 싶으면 merge commit, 한 줄로 유지하고 싶으면 rebase and merge, 작업 중 커밋을 남기고 싶지 않으면 squash 를 고른다.

## 🚫 흔한 오해

- **rebase 가 merge 보다 항상 낫다** — 이력이 한 줄로 펴져 읽기 좋아지는 것뿐이다. 언제 무엇이 합쳐졌는지가 기록으로 남아야 하는 자리에서는 merge 가 맞고, 이미 공유한 커밋에는 아예 쓸 수 없다.
- **rebase 는 커밋을 옮긴다** — 옮기는 게 아니라 버린다. 있던 커밋을 놓아두고 같은 변경으로 새 커밋을 만들기 때문에 해시가 전부 달라진다.
- **merge 와 rebase 는 결과 코드가 다르다** — 같다. 같은 지점까지 합쳤다면 파일 내용은 똑같고, 달라지는 것은 이력의 모양뿐이다.

## 🚨 주의사항

- **내 저장소 밖으로 나간 커밋은 rebase 하지 않는다.** 남이 그 위에 작업을 쌓았을 수 있는 커밋이 그것이다. 이미 push 한 커밋을 다시 쓰는 것은 나쁜 습관으로 본다.
- **왜 문제가 되나.** rebase 는 있던 커밋을 버리고 비슷하지만 다른 커밋을 새로 만든다. 남이 그 옛 커밋을 받아다 위에 작업을 쌓아 뒀다면, 고쳐 올린 뒤에는 그 사람이 자기 작업을 다시 합쳐야 하고 서로의 작업을 당겨 오는 순간부터 엉킨다.
- **그래서 이렇게 나눠 쓴다.** push 하기 전의 내 커밋은 rebase 로 다듬고, 이미 push 한 것은 rebase 하지 않는다. 이 둘을 지키면 양쪽의 이점을 다 가진다.

## 📝 정리

merge 와 rebase 는 갈라진 가지를 합치는 두 방법이고, 합친 뒤의 파일은 어느 쪽이든 같다. 다른 것은 이력이다 — merge 는 갈라졌던 자국을 병합 커밋으로 남기고, rebase 는 커밋을 새로 만들어 한 줄로 펴 놓는다. 새로 만든다는 그 성질 때문에, 남이 이미 받아 간 커밋에는 rebase 를 쓰지 않는다.

## ❓ 이해했는지

- 남이 이미 받아 간 커밋을 rebase 하면 그 사람에게 무슨 일이 생기나 → 주의사항
- rebase 를 하고 나면 커밋 해시가 전부 달라지는 이유는 → 작동 원리
- 이력만 보고 merge 로 합쳤는지 rebase 로 합쳤는지 알아내려면 어디를 보나 → 그림
