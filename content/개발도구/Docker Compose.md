# Docker Compose (도커 컴포즈)

## 📝 정의

Docker Compose는 **여러 컨테이너를 한 파일로 정의해 함께 띄우는 도구**다.

공식 문서는 이것을 "여러 컨테이너로 이루어진 애플리케이션을 정의하고 실행하는 도구" 라고 쓴다. 설정은 YAML 파일 한 장(`compose.yaml`)이고, 명령 한 줄로 그 파일에 적힌 서비스를 전부 만들어 띄운다. 띄운 뒤에는 시작·정지·다시 만들기, 상태 보기, 로그 흘려 보기, 일회성 명령 실행을 같은 도구로 한다.

### 비유
세트 메뉴. 한 줄만 주문하면 밥과 국과 반찬이 한 상에 함께 나온다.

## 🖼️ 그림으로 보기

```도해
대조: 컨테이너 다섯 개를 함께 띄우려면 무엇이 달라지나
따로따로 || 컴포즈로
띄우기 :: 명령 다섯 번 || 명령 한 번
설정 위치 :: 각자 명령줄에 || 파일 한 장에
공용 통로 :: 손으로 붙인다 || 파일이 만든다
전부 지우기 :: 하나씩 찾아서 || 한 번에
= 여러 컨테이너를 한 파일로 정의해 함께 띄우는 도구다
```

## ⚠️ 해결하는 문제

```도해
흐름: 컨테이너를 손으로 하나씩 띄우면 어디서 어긋나나
첫날 :: 필요한 명령 다섯 줄을 위키에 적어 둔다
새 동료 :: 위키를 보고 옮겨 치다 포트를 하나 빼먹는다
DB :: 컨테이너 이름이 달라 앱이 못 찾는다
설정 변경 :: 다섯 줄 중 어디를 고칠지 각자 짐작한다
서버 반영 :: 노트북과 서버가 조용히 달라진다
= 손으로 붙인 설정은 문서에만 남고, 문서는 실행되지 않는다
```

컨테이너 하나를 띄우는 일은 명령 한 줄이다. 문제는 앱·DB·캐시처럼 **여러 개가 서로를 찾아야** 할 때 생긴다. 어느 컨테이너가 어느 이름으로 불려야 하는지, 어느 망에 함께 들어가야 하는지, 어떤 데이터가 컨테이너보다 오래 살아야 하는지가 전부 사람의 손과 기억에 남는다.

Compose 는 그 손버릇을 **파일로 옮긴다.** 파일은 위키와 달리 실행되기 때문에, 노트북에서 도는 것과 서버에서 도는 것이 같은 문장에서 나온다. 문서는 이 파일을 공유해 협업하는 것과, 파일 안에 변수를 써서 환경마다 다르게 쓰는 것을 Compose 의 이점으로 든다.

## ⚙️ 작동 원리

```도해
흐름: `docker compose up` 한 줄이 무슨 일을 하나
컴포즈 :: 작업 폴더의 `compose.yaml` 을 읽는다
프로젝트 :: 이 파일 한 장을 한 벌로 묶어 이름을 붙인다
네트워크 :: 서비스끼리 IP 로 서로를 찾을 통로를 만든다
볼륨 :: 지워지면 안 되는 데이터의 자리를 붙인다
서비스 :: 같은 이미지와 설정을 정한 개수만큼 띄운다
= 한 벌로 세우기 때문에 한 벌로 걷을 수도 있다
```

기본 파일 이름은 작업 폴더의 `compose.yaml`(또는 `compose.yml`)이고, 그 안의 문법은 Compose 규격이 정한다. 규격은 셋을 구분한다 — **서비스**는 같은 이미지(컨테이너를 찍어내는 원본)와 설정을 한 번 이상 띄우는 단위, **네트워크**는 서비스끼리 IP 로 서로에게 닿는 통로, **볼륨**은 컨테이너보다 오래 살아야 하는 데이터의 자리다.

이 한 벌 전체를 **프로젝트**라고 부른다. 프로젝트는 "이 명세를 한 번 실제로 올린 것" 이고, 그 이름이 자원을 한데 묶으면서 다른 애플리케이션이나 같은 파일의 다른 설치본과 서로를 격리한다. 그래서 같은 파일로 격리된 환경을 여러 벌 만들 수 있고, 테스트가 끝나면 그 벌만 통째로 지울 수 있다.

## 📊 비교: Docker Compose vs Kubernetes

| 항목 | Docker Compose | Kubernetes |
|---|---|---|
| 문서가 말하는 배포 범위 | 호스트 **한 대** | 노드 여러 대로 이룬 클러스터 |
| 적는 방식 | `compose.yaml` 한 장 | 원하는 상태를 선언한다 |
| 서비스 찾기 | 파일이 만든 망 안에서 | DNS 이름·자체 IP 로 노출하고 부하를 나눈다 |
| 판올림 | 서비스를 다시 만든다 | 정해진 속도로 롤아웃하고 롤백한다 |
| 컨테이너가 죽으면 | 그 호스트 안에서만 대응한다 | 재시작·교체하고, 준비되기 전에는 안 보낸다 |
| 어느 기계에 놓을지 | 놓을 기계가 한 대뿐이다 | CPU·메모리를 보고 노드에 맞춰 넣는다 |

Compose 문서는 "프로덕션·스테이징·개발·테스트·CI 모든 환경에서 동작한다" 고 쓰면서, 운영 배포는 **한 호스트** 항목으로 따로 적어 둔다. 오른쪽 칸의 일들은 쿠버네티스가 자기 소개에서 스스로 드는 목록이다.

## 💡 실제 사례

- **로컬 개발 환경** — 앱·DB·캐시를 한 파일에 적어 두면 새로 온 사람이 명령 한 줄로 같은 환경을 세운다.
- **자동 테스트** — 테스트 묶음을 돌리기 전에 격리된 환경을 만들고, 끝나면 그 벌만 통째로 지운다.
- **한 호스트 배포** — 문서가 인정하는 운영 용도다. 원격 도커 호스트에 같은 파일로 올리고 환경별 설정만 갈아 끼운다.

## 🚫 흔한 오해

- **컴포즈만 있으면 쿠버네티스는 필요 없다** — 노드 여러 대에 걸쳐 자리를 잡고, 죽은 컨테이너를 갈아 끼우고, 정해진 속도로 판올림하는 일은 쿠버네티스가 자기 몫으로 적어 둔 것이다. Compose 문서의 운영 배포는 호스트 한 대다.
- **컴포즈는 개발용이라 운영에는 못 쓴다** — 문서는 프로덕션·스테이징·개발·테스트·CI 를 다 든다. 못 쓰는 것이 아니라 **한 대까지**다.
- **컴포즈가 컨테이너를 만든다** — 컨테이너를 만드는 것은 도커다. 컴포즈는 여러 개를 한 파일로 묶어 함께 세우고 함께 걷는 층이다.

## 📝 정리

Docker Compose 는 여러 컨테이너를 파일 한 장으로 정의해 한 번에 세우고 한 번에 걷는 도구다. 그 파일이 서비스·네트워크·볼륨을 프로젝트 한 벌로 묶기 때문에, 노트북과 시험 환경과 서버가 같은 문장을 공유한다. 운영에서도 쓰지만 문서가 정한 범위는 호스트 한 대이고, 그 선을 넘는 일부터가 쿠버네티스의 자리다.

## ❓ 이해했는지

- `up` 한 줄이 컨테이너를 띄우기 전에 무엇부터 만드나 → 작동 원리
- 위키에 적어 둔 실행 명령이 사람마다 다르게 돌아가는 까닭은 무엇인가 → 해결하는 문제
- 서버를 세 대로 늘리려는데 컴포즈 파일만으로는 안 되는 까닭은 무엇인가 → 비교
