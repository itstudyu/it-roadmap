# Git Stash (깃 스태시)

## 📝 정의

Git Stash는 **커밋하지 않은 변경을 잠깐 치워 두는 서랍**이다.

Git 공식 문서는 이 명령을 "작업 디렉터리와 인덱스의 현재 상태를 기록해 두되 깨끗한 작업 디렉터리로 돌아가고 싶을 때 쓴다" 로 적어 뒀다. 넣은 것은 이력에 붙지 않고 따로 쌓인다 — 가장 최근 것이 `refs/stash` 에 있고, 그보다 앞의 것들은 그 참조의 reflog 에 남아 `stash@{0}`, `stash@{1}` 로 부른다.

### 이름
Git :: 이력을 남기는 도구
Stash :: 슬쩍 넣어 둔 자리
= 붙여 읽으면 "이력 밖에 슬쩍 넣어 둔 자리". 넣은 것은 목록을 열어야 보인다

### 비유
책상 위 물건을 서랍에 쓸어 넣는 일 — 책상은 깨끗해지지만 서랍은 안 열어 보면 잊는다.

### 예
고치던 것이 손에 남은 채로 가지를 옮기려다 명령이 거부당하는 그 순간에 꺼내 쓰는 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 커밋하기엔 이른 변경을 안고 가지를 옮기려면 어떻게 하나
작업 중 :: 고친 파일이 손에 남아 있다
stash :: 그 변경을 서랍에 넣는다
작업 트리 :: `HEAD` 상태로 돌아가 깨끗해진다
다른 일 :: 가지를 옮겨 급한 것을 처리한다
pop :: 돌아와 서랍에서 꺼내 다시 얹는다
@ 다시 작업 중 :: 꺼낸 것은 서랍에서 사라진다
= 커밋하지 않은 변경을 잠깐 맡겨 두고 나중에 되찾는 서랍이다
```

## ⚠️ 해결하는 문제

```도해
대조: 고치던 것을 안고 가지를 옮기려 하면 어떻게 되나
서랍 없이 || stash 로
가지 옮기기 :: 막히거나 딸려감 || 깨끗해서 옮긴다
급한 수정 :: 임시 커밋을 쌓음 || 이력이 안 더러워짐
되찾기 :: 어디 뒀는지 기억 || 목록에서 꺼낸다
= 커밋으로 남기기엔 이른 변경을 이력 밖에 잠깐 둘 자리다
```

`git switch` 문서는 지금 가지와 옮겨 갈 가지에서 서로 다른 파일에 고친 게 있으면 "고친 것을 그 맥락에 보존하려고 명령이 대개 가지 옮기기를 거부한다" 고 적어 뒀다. 겹치지 않으면 거부하지는 않지만, 이번에는 고친 것이 옮겨 간 가지로 그대로 딸려간다. 둘 다 원하는 상태가 아니다. GitHub Desktop 이 이 상황에서 "치워 둘까요, 저쪽으로 데려갈까요" 를 묻는 것도 그래서다.

남은 길은 임시 커밋을 쌓는 것뿐인데, 그러면 "일단 저장" 같은 커밋이 가지 이력에 박힌다. 서랍은 그 둘 사이의 자리다. 작업 트리를 `HEAD` 상태로 되돌려 가지를 옮길 수 있게 만들면서, 치운 것은 이력 밖에 둔다.

## ⚙️ 작동 원리

```bash
git stash push -u -m "검색 필터 작업 중"   # -u 는 새로 만든 파일까지
git switch hotfix
# ... 급한 것을 처리하고 돌아와서
git switch feature/search
git stash list            # stash@{0}: On feature/search: 검색 필터 작업 중
git stash pop             # 꺼내고 목록에서 지운다
```

꺼내는 방법이 둘이다. `pop` 은 목록에서 빼면서 지금 작업 트리 위에 얹고, `apply` 는 얹기만 하고 목록에 그대로 남겨 둔다. 문서가 `apply` 를 "pop 과 같지만 목록에서 상태를 지우지 않는다" 로 정의한다. 하나를 여러 가지에 각각 얹어 보고 싶을 때가 `apply` 자리다.

원래 가지가 그동안 많이 바뀌어 `apply` 가 충돌로 실패하면 `git stash branch <이름>` 이 답이다. 넣을 때 `HEAD` 였던 커밋에서 새 가지를 만들어 거기에 얹기 때문에, 문서 표현대로 "충돌 없이 원래 치워 둔 상태를 되살린다". 성공하면 그 항목은 알아서 사라진다.

## 💡 실제 사례

- **급한 리뷰 요청** — 고치던 것을 서랍에 넣고 다른 가지로 옮겨 확인해 준 뒤, 돌아와 `pop` 으로 꺼낸다.
- **가지를 잘못 골랐을 때** — 줄기에서 고치고 있었다는 걸 뒤늦게 알면, 치워 두고 `git stash branch` 로 그때의 커밋에서 새 가지를 만들어 그리로 꺼낸다.
- **커밋할 것만 테스트하기** — 남길 것만 `add` 해 두고 `--keep-index` 로 넣으면 인덱스에 담은 변경은 그대로 남아, 실제로 커밋될 상태만으로 테스트를 돌릴 수 있다.

## 🚫 흔한 오해

- **stash 하면 이력에 남는다** — 가지 이력에는 안 붙는다. `git log` 에는 안 나오고 `git stash list` 로만 보인다. 별도의 참조에 따로 쌓이기 때문이다.
- **apply 하면 서랍이 비워진다** — 안 비워진다. 문서가 `apply` 를 "목록에서 지우지 않는다" 로 못 박아 뒀다. 같은 변경을 두 번 얹어 놓고 왜 중복이 생겼는지 헤매는 일이 여기서 나온다.
- **커밋하기 애매하면 일단 stash 해두면 된다** — 몇십 분이면 맞다. 하루를 넘길 것이면 가지에 임시 커밋을 쌓는 편이 낫다. 서랍은 기본 이름이 `WIP on <가지>` 뿐이어서, 사흘 뒤에 목록을 열면 그게 무엇이었는지 모른다.

## 🚨 주의사항

- **치워 둔 걸 잊는 게 실제 사고다.** 목록은 가지마다 따로 있지 않고 한 군데에 쌓인다. 넣을 때 `-m` 으로 설명을 붙여 두면 나중에 목록만 보고 알아볼 수 있다.
- **`git stash clear` 는 되돌릴 수 없다.** 문서가 지운 항목은 정리(pruning) 대상이 되어 "복구가 불가능할 수 있다" 고 적어 뒀다. 하나만 지울 때는 `drop` 을 쓴다.
- **`pop` 이 충돌하면 목록에서 안 사라진다.** 문서는 이때 손으로 충돌을 풀고 `git stash drop` 을 직접 해야 한다고 말한다. 안 그러면 같은 항목이 남아 있어 다음에 또 꺼내진다.
- **추적하지 않는 새 파일은 기본으로 안 들어간다.** `-u` 를 붙여야 새 파일까지 함께 치워진다. 안 붙이면 새 파일만 작업 트리에 남아 가지를 따라다닌다.

## 📝 정리

**"이력 밖 서랍에 잠깐 밀어 넣는 그 자리"** 라고 읽으면 된다. 그 덕에 임시 커밋을 쌓지 않고도 가지를 옮길 수 있지만, 목록은 가지와 무관하게 한 군데에 쌓이고 이름도 기본값뿐이다. 잠깐 치우는 서랍으로 쓰고, 오래 둘 것은 커밋으로 남기는 편이 안전하다.

## 🧒 열 살에게

손님 온다고 책상 위 물건을 서랍에 우르르 쓸어 넣어 본 적 있지? 책상은 금세 깨끗해지고 하던 건 서랍에 그대로 있으니까 볼일 끝나면 다시 꺼내면 돼. 그런데 서랍은 안 열어 보면 뭘 넣었는지 잊어버려서, 며칠 지나면 그게 뭐였는지 아무도 몰라.

## ❓ 이해했는지

- 서랍에서 꺼냈는데 같은 변경이 두 번 얹혀 있다. 무엇을 잘못했나 → 흔한 오해
- 새로 만든 파일이 서랍에 안 들어가는 이유는 무엇인가 → 주의사항
- 가지를 옮기려고 임시 커밋을 쌓지 않아도 되는 까닭은 → 해결하는 문제
