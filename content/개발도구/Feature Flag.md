# Feature Flag (기능 플래그)

## 📝 정의

Feature Flag는 **다시 배포하지 않고 기능을 켜고 끄는 스위치**다.

규격 문서는 이것을 "배포된 소프트웨어 안에 대체 코드 경로를 정의해 두고, 규칙에 따라 실행 시점에 조건부로 실행되게 하는 장치" 라고 쓴다. 더 짧게는 "런타임에 제어할 수 있는 if/else 문" 이라고도 적는다. 핵심은 **새 코드를 배포하지 않고도** 애플리케이션의 동작을 바꾼다는 데 있다.

### 비유
벽에 미리 깔아 둔 전선. 공사가 다 끝나도 스위치를 올리기 전까지는 불이 안 들어온다.

## 🖼️ 그림으로 보기

```도해
대조: 배포와 공개를 떼어 놓으면 무엇이 달라지나
플래그 없이 || 플래그로
공개 시점 :: 배포와 한 날 || 원하는 날에
미완성 코드 :: 가지에 남긴다 || 꺼둔 채 합친다
되돌리기 :: 되돌려 배포 || 스위치 내림
공개 범위 :: 전부 아니면 전무 || 규칙으로 고른다
= 다시 배포하지 않고 기능을 켜고 끄는 스위치다
```

## ⚠️ 해결하는 문제

```도해
흐름: 배포와 공개가 같은 날이면 무엇이 어긋나나
개발 :: 기능이 반쯤 됐다. 아직 내보낼 수 없다
가지 :: 다 될 때까지 줄기 밖에 따로 둔다
합치기 :: 3주 뒤, 남들 코드와 한꺼번에 부딪는다
공개 :: 배포하는 순간 모든 사용자에게 열린다
사고 :: 문제를 발견하면 되돌려 배포하는 수밖에 없다
= 배포 하나에 완성·공개·되돌리기가 전부 묶여 있다
```

배포와 공개가 한 사건이면 세 가지가 동시에 묶인다. 덜 끝난 코드는 줄기 밖에 남아야 하고, 공개는 전부 아니면 전무이고, 되돌리려면 또 배포해야 한다. 규격 문서가 "가지 수명을 줄여 분기 부담을 낮추는 것" 을 플래그의 용도로 드는 이유가 여기 있다 — 꺼진 코드는 프로덕션에 있어도 사용자에게 없는 것과 같으니, 다 되기 전에 합쳐도 된다.

플래그는 그 셋을 **떼어 놓는다.** 규격 문서가 드는 용도가 그대로 이 목록이다 — 가지 수명 줄이기, 소수에게 먼저 여는 점진 공개, 끝나지 않은 일을 사용자에게 감춘 채 내부에서 시험하기, A/B 테스트, 장애 때 일부만 접어 두기, 지역이나 IP 에 따라 접근 제한하기.

## ⚙️ 작동 원리

```도해
흐름: 코드가 플래그 값을 어떻게 받아 오나
코드 :: 플래그 키와 기본값을 대고 묻는다
맥락 :: 누가 보낸 요청인지, 어느 환경인지 함께 넘긴다
공급자 :: 값의 원본인 플래그 관리 시스템에 붙는다
규칙 :: 대상 지정·개별 지정·비율로 갈래를 고른다
< 코드 :: 받은 값으로 if/else 를 탄다. 못 받으면 기본값
= 값은 코드에 박혀 있지 않고, 물을 때 맥락을 보고 정해진다
```

플래그는 **키**(문자열 이름)로 식별하고, 한 번 묻는 일을 **평가**라고 부른다. 규격은 평가가 무엇을 포함하는지까지 정해 뒀다 — 설정된 공급자에서 값을 얻어내는 일, 그리고 그게 비정상으로 끝났을 때 **넘겨준 기본값으로 물러나는 일**까지다. 그래서 관리 시스템에 못 닿아도 코드는 멈추지 않는다.

값을 정하는 재료가 **평가 맥락**이다. 실행 환경, 호스트, 클라이언트, 그리고 요청의 주체(사용자)가 여기 담긴다. 규칙은 그 맥락을 보고 갈래를 고르는데, 갈래에는 **variant** 라는 이름이 붙어서 값 자체를 적지 않고도 어느 쪽인지 가리킬 수 있다.

플래그는 참/거짓만 담지 않는다. 규격은 플래그에 타입이 있다고 적고 `string`·`boolean`·`json` 을 든다. 서버 쪽은 요청마다 맥락을 넘겨 그때그때 평가하고, 클라이언트 쪽은 시작할 때 미리 평가된 값을 받아 두고 맥락이 바뀔 때만 다시 평가하는 방식을 쓴다.

## 💡 실제 사례

- **점진 공개** — 새 기능을 소수에게만 켜 두고 지표를 확인한 뒤 범위를 넓힌다.
- **장애 때 접어 두기** — 무거운 기능 하나를 끄고 나머지를 살려 둔다. 시스템 일부를 안전하게 낮춰 쓰는 용도다.
- **지역·라이선스 제한** — 나라나 IP 에 따라 어떤 기능을 보일지 규칙으로 나눈다. 규정이나 라이선스 때문에 필요할 때가 있다.

## 🚫 흔한 오해

- **플래그로 꺼 뒀으면 아직 배포한 게 아니다** — 배포는 이미 끝났다. 꺼진 코드가 프로덕션에 함께 올라가 있고, 사용자에게만 안 보이는 것이다.
- **플래그는 그냥 켜고 끄는 참/거짓이다** — 규격은 플래그에 타입이 있다고 적는다. 문자열이나 JSON 도 값이 되고, 갈래 이름으로 여러 값 중 하나를 고른다.
- **플래그를 많이 걸어 두는 게 항상 낫다** — 규범 문서는 단위 검사 뒤에 뜻이 있는 조합마다 갈래를 쳐서 돌리라고 적는다. 플래그 하나가 늘 때마다 시험해야 할 갈래도 함께 갈라진다.

## 🚨 주의사항

- **켠 다음에 지우는 것까지가 일이다** — 규범 문서는 릴리스 한 달 뒤에 플래그와 그 코드를 걷어내도록 미리 합의를 받아 두라고 권한다.
- **잊힌 플래그가 쌓인다** — 문서가 지목하는 실패 방식이 이것이다. 팀이 다음 과제로 옮겨 가는 동안 플래그는 그대로 남고, 앱이 멀쩡히 돌기 때문에 아무도 눈치채지 못한다.
- **짧게 살릴 생각으로 넣은 것이 오래 산다** — 문서가 인용한 경고 그대로다. 플래그의 문제는 존재가 아니라 수명이다.

## 📝 정리

Feature Flag 는 배포와 공개를 떼어 놓는, 실행 중에 값이 정해지는 스위치다. 코드는 꺼진 채로 프로덕션까지 올라가 있고, 켜는 일은 다른 날 맥락과 규칙이 정한다. 그래서 플래그는 만드는 것이 절반이고 걷어내는 것이 나머지 절반이다.

## ❓ 이해했는지

- 아직 다 안 된 기능을 줄기에 합쳐 둘 수 있는 까닭은 무엇인가 → 해결하는 문제
- 같은 요청인데 사람에 따라 다른 화면이 나오는 일은 어떻게 벌어지나 → 작동 원리
- 반년 전에 전부 켠 플래그를 그냥 두면 무엇이 쌓이나 → 주의사항
