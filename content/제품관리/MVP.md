# MVP (Minimum Viable Product)

## 📝 정의

MVP는 **가설을 확인할 만큼만 만들어 내놓는 제품**이다.

기능을 다 갖춘 뒤에 내놓으면 아무도 안 쓴다는 사실도 그때 알게 된다. MVP는 그 답을 앞으로 당기려고 확인에 필요한 부분만 먼저 만든다.

### 비유
식당을 차리기 전에 푸드트럭부터 세워보는 것. 주방을 다 짓기 전에 그 메뉴가 팔리는지부터 안다.

## 🖼️ 그림으로 보기

```도해
흐름: MVP 로 만들면 무엇이 언제 확인되나
가설 :: "사람들이 이걸 돈 내고 쓸 것이다"
최소 기능 :: 그 가설을 확인할 것만 만든다
출시 :: 다 만들기 전에 사람 앞에 내놓는다
반응 :: 쓰는지 안 쓰는지가 숫자로 나온다
@ 다음 판 :: 맞았으면 늘리고 틀렸으면 방향을 튼다
= 오래 만들수록 틀렸다는 사실을 늦게 안다
```

## ⚠️ 해결하는 문제

```도해
대조: 다 만들고 내놓으면 무엇을 잃나
완성 후 출시 || MVP 로
답을 얻는 때 :: 6개월 뒤 || 1개월 뒤
틀렸을 때 :: 전부 버린다 || 방향만 튼다
만든 기능 :: 안 쓰는 게 많다 || 쓰는 것만 있다
= 늦게 알수록 되돌리는 값이 커진다
```

기능을 백 개 만들어 내놓았는데 실제로 쓰이는 게 열 개면 아홉은 헛일이다. 문제는 그 아홉이 어느 것인지를 만들기 전에는 알 수 없다는 데 있다.

MVP는 그 질문을 실제 사용자에게 넘긴다. 확인에 필요한 만큼만 만들어 내놓고, 사람들이 쓰는지를 보고 다음에 무엇을 만들지 정한다. 틀렸다면 한 달치를 버리는 것으로 끝난다.

## ⚙️ 작동 원리

```도해
층: 기능을 자를 때 무엇부터 남기나
핵심 가치 :: 이게 없으면 제품이라 할 수 없는 것
쓸 만한 최소 :: 그 가치를 실제로 쓰게 해주는 것
편의 :: 있으면 편하지만 없어도 되는 것
치장 :: 나중에 붙여도 늦지 않은 것
= 위를 자르면 검증이 안 되고, 아래를 붙들면 출시가 밀린다
```

사진 공유 서비스라면 핵심은 올리고 링크로 넘기는 것이다. 편집과 앨범 정리와 댓글은 아래 두 층이라 첫 판에서 뺀다.

무엇을 확인하려는지 먼저 적어두는 것이 순서다. 그게 없으면 자르는 기준도 없고, 반응이 나와도 무엇이 확인된 것인지 말할 수 없다.

## 💡 실제 사례

- **데모 영상 먼저** — Dropbox는 제품 없이 동작 영상만 올려 75,000명의 가입을 받고 수요를 확인했다.
- **직접 손으로 처리** — Airbnb는 자기 아파트 방 세 개를 단순한 웹사이트로 내놓고 예약이 되는지 봤다.
- **기능 잘라내기** — 사진 공유라면 업로드와 링크 생성까지만 만들고 편집과 앨범은 다음으로 미룬다.

## 🚫 흔한 오해

- **MVP는 대충 만든 제품이다** — 기능 개수는 줄이지만 남긴 기능은 제대로 돌아가야 한다. 업로드가 되다 말면 사람들이 안 쓴다는 결과가 나오는데, 아이디어 때문인지 버그 때문인지 구분할 수 없다.
- **MVP는 개발 기간을 줄이는 방법이다** — 목적은 시간 절약이 아니라 답을 얻는 것이다. 무엇을 확인하려는지 정하지 않고 기능만 덜어내면 그냥 작은 제품이 나온다.
- **반응이 없으면 MVP는 실패다** — 안 쓴다는 것도 답이다. 6개월치를 만들기 전에 알아냈다면 MVP는 제 일을 한 것이다.

## 📊 비교

| | MVP | 완제품 |
|---|---|---|
| 개발 기간 | 1~3개월 | 6~12개월 |
| 기능 수 | 3~5개 | 50개 이상 |
| 목적 | 가설 확인 | 완성 |
| 방향 바꾸기 | 쉽다 | 이미 늦었다 |

## 📝 정리

MVP는 가설을 확인할 만큼만 만들어 내놓는 제품이다. 기능을 덜어내는 것이 목적이 아니라 틀렸는지를 일찍 아는 것이 목적이고, 그래서 무엇을 확인하려는지 먼저 정해야 한다.

## ❓ 이해했는지

- 제품을 만들지 않고 데모 영상만 올렸는데도 검증이 됐다고 보는 이유는 → 실제 사례
- 남긴 기능이 자꾸 깨지면 사용자가 안 쓴다는 결과에서 무엇을 알 수 없게 되나 → 흔한 오해
- 완성한 다음에 내놓은 쪽이 가설이 틀렸을 때 더 크게 손해 보는 이유는 → 해결하는 문제
