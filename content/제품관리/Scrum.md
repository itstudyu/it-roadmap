# Scrum (스크럼)

## 📝 정의

Scrum은 **짧은 주기를 반복해 제품을 만드는 방식**이다.

시작할 때 전부 정해놓고 끝까지 그대로 만드는 대신, 몇 주 단위로 끊어서 만들고 보여주고 고친다. 애자일이라는 생각을 실제 일정과 자리로 옮긴 형태다.

### 비유
요리하면서 중간에 맛을 본다. 다 끓이고 나서 짠 걸 아는 것보다 낫다.

## 🖼️ 그림으로 보기

```도해
흐름: 스프린트 한 번은 어떻게 돌아가나
계획 :: 목록에서 이번에 할 것만 골라 담는다
개발 :: 정해진 기간 동안 범위를 고정하고 만든다
매일 :: 짧게 모여 막힌 것을 꺼낸다
리뷰 :: 만든 것을 실제로 보여주고 의견을 받는다
회고 :: 일하는 방식에서 고칠 것을 정한다
< 계획 :: 받은 의견을 목록에 넣고 다음 주기를 연다
= 제품과 일하는 방식을 같은 주기로 함께 고친다
```

## ⚠️ 해결하는 문제

```도해
대조: 처음에 전부 정하고 끝까지 만들면 어떻게 되나
한 번에 만들면 || 스프린트로
방향 확인 :: 다 만든 뒤에 || 몇 주마다
요구 변경 :: 되돌리기 어렵다 || 다음 주기에 반영
문제 발견 :: 막판에 몰린다 || 주기마다 나온다
= 틀린 것을 언제 알게 되느냐가 갈린다
```

계획을 한 번에 세우면 그 계획이 맞았는지는 다 만든 뒤에야 알 수 있다. 중간에 요구가 바뀌어도 이미 짜인 일정 위에 얹기 어렵고, 문제는 대부분 마감 직전에 한꺼번에 드러난다.

스크럼은 확인 지점을 앞으로 당긴다. 몇 주마다 쓸 수 있는 결과물을 내놓고 보여주니, 방향이 틀렸다면 그 주기만큼만 잃는다.

## ⚙️ 작동 원리

역할이 셋으로 나뉜다. 무엇을 먼저 만들지 정하는 사람, 팀이 일하는 방식을 돌보고 막힌 것을 치우는 사람, 실제로 만드는 팀이다. 무엇을 만들지와 어떻게 만들지를 다른 사람이 맡는 것이 이 구분의 뜻이다.

```도해
층: 할 일 목록은 어떤 단위로 쪼개지나
제품 백로그 :: 만들 것 전부. 우선순위 순으로 쌓인다
스프린트 백로그 :: 이번 주기에 하기로 한 것만 내려온다
작업 :: 하루 안에 손댈 수 있는 크기로 다시 쪼갠다
= 아래로 내려올수록 범위가 좁아지고 대신 확정된다
```

## 💡 실제 사례

- **2주 주기 개발** 격주 금요일에 결과를 보여주고 다음 주 월요일에 다음 주기를 시작한다.
- **급한 요청 처리** 주기 중에 들어온 요청을 목록 맨 앞에 놓고 다음 주기에 먼저 집는다.
- **회고에서 나온 변경** 매일 모이는 시간이 길어진다는 말이 나오면 그 자리에서 규칙을 바꾼다.

## 🚫 흔한 오해

- **스크럼을 하면 계획을 안 세운다** — 오히려 자주 세운다. 한 번에 멀리까지 세우는 대신 주기마다 다시 세우는 것이다.
- **매일 모이는 자리는 진행 보고 시간이다** — 관리자에게 보고하는 자리가 아니라 막힌 것을 꺼내 서로 치우는 자리다. 보고가 되면 길어지고 사람이 빠지기 시작한다.
- **주기 도중에도 일을 계속 넣을 수 있다** — 넣으면 그 주기에 하기로 한 것이 밀린다. 급한 일은 다음 주기 맨 앞에 놓는 것이 원칙이다.

## 📝 정리

Scrum 은 짧은 주기로 만들고 보여주고 고치기를 반복하는 개발 방식이다. 주기마다 범위를 고정하는 것과 회고로 일하는 방식까지 손보는 것이 이 방식의 뼈대다.

## ❓ 이해했는지

- 주기 도중에 새 요구가 들어오면 어디에 놓나?
- 리뷰에서 다루는 것과 회고에서 다루는 것은 어떻게 다른가?
- 매일 모이는 자리가 길어진다면 무엇이 잘못된 것인가?
