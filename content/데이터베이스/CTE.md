# CTE (공통 테이블 식)

## 📝 정의

CTE는 **질의 하나 안에서만 사는 이름 붙인 중간 표**다.

MySQL 문서는 이것을 "한 문장의 범위 안에서만 존재하고 그 문장 안에서 여러 번 갖다 쓸 수 있는, 이름 붙은 임시 결과 집합" 으로 적는다. PostgreSQL 문서는 "큰 질의 안에서 쓰라고 쓰는 보조 문장" 이자 "그 질의 하나 동안만 존재하는 임시 테이블" 로, SQLite 문서는 "한 문장이 도는 동안만 존재하는 임시 뷰" 로 적는다. 셋 다 같은 말을 한다 — 문장이 끝나면 사라진다.

### 이름
Common :: 여러 번 같이 쓴다
Table :: 표 하나처럼 보인다
Expression :: 질의 안에서 정의한다
= 세 낱말을 펴면 "질의 안에서 정의해 두고 여러 번 갖다 쓰는 표"

### 비유
요리 중간에 한 냄비 만들어 둔 소스. 그 요리에만 쓰고, 필요할 때마다 떠 쓰고, 다 하면 버린다.

### 예
서브쿼리가 세 겹으로 겹쳐서 어디부터 읽어야 할지 몰라 스크롤을 오르내리던 그 질의문이다.

## 🖼️ 그림으로 보기

```도해
대조: 중간 결과에 이름을 붙이면 질의가 어떻게 달라지나
이름 없이 || 이름을 붙여
읽는 방향 :: 안쪽부터 뒤진다 || 위에서 아래로
같은 결과 재사용 :: 통째로 또 적는다 || 이름만 또 쓴다
자기 참조 :: 아예 안 된다 || 스스로를 부른다
= 중간 결과에 이름이 붙으면 질의 하나가 여러 단으로 펴진다
```

## ⚠️ 해결하는 문제

```도해
대조: 같은 중간 계산을 두 번 쓰려면 어떻게 되나
서브쿼리로 || 이름을 붙여
같은 계산 :: 두 번 적는다 || 한 번 적는다
고칠 때 :: 두 군데를 고친다 || 한 군데만 고친다
계층 타고 오르기 :: 못 한다 || 반복해 오른다
= 이름이 생기면 고칠 자리가 하나로 모이고, 스스로를 부를 수도 있게 된다
```

자료를 다루는 질의는 대개 여러 단이다 — 원본에서 필요한 기간만 거르고, 그것을 열쇠별로 묶고, 묶은 것에 순위를 매기고, 순위 안쪽만 남긴다. 이 네 단을 서브쿼리로 적으면 가장 안쪽 괄호가 첫 단계라서, 읽는 사람은 맨 안에서 시작해 밖으로 나와야 한다. 게다가 같은 중간 결과를 두 번 쓰려면 그 덩어리를 통째로 두 번 적어야 하고, 고칠 때 한쪽만 고치는 사고가 난다.

CTE 는 **중간 결과에 이름을 주어 순서를 뒤집는다.** 위에서 아래로 읽히고, 이름이 하나라 고칠 자리도 하나다. 그리고 표준 서브쿼리로는 아예 못 하는 일이 하나 열린다 — 자기 자신을 부르는 것. 깊이가 몇 단인지 모르는 조직도나 분류 나무를 끝까지 타고 오르는 질의가 여기서 나온다.

## ⚙️ 작동 원리

```도해
흐름: 스스로를 부르는 CTE 는 어떻게 계층을 끝까지 타고 오르나
비재귀 항 :: 출발 줄을 만들어 작업 표에 넣는다
재귀 항 :: 작업 표에 있는 줄로 다음 줄을 찾는다
작업 표 :: 새로 나온 줄로 갈아 끼운다
결과 쌓기 :: 나온 줄을 결과에 계속 더한다
@ 다시 재귀 항 :: 새 줄이 없으면 멈추고, 있으면 한 바퀴 더
= 재귀라고 적지만 안에서는 새 줄이 안 나올 때까지 도는 반복이다
```

PostgreSQL 문서는 이 점을 못 박는다 — "재귀적으로 적을 수 있게 해줄 뿐, 안에서는 반복으로 평가한다". 멈추는 조건을 잘못 적으면 영영 돈다. MySQL 은 그래서 깊이 상한을 두고 기본값을 1000 단으로 잡아 두었고, 그보다 깊이 내려가면 서버가 그 질의를 끊는다.

두 번째로 알아둘 것은 **CTE 가 반드시 따로 계산되지는 않는다**는 점이다. PostgreSQL 은 재귀가 아니고 부작용이 없으며 바깥에서 딱 한 번만 참조하는 CTE 를 바깥 질의에 접어 넣는다. `WITH w AS (SELECT * FROM 큰표) SELECT * FROM w WHERE 열쇠 = 123` 은 그냥 큰 표에 조건을 건 것과 같은 계획이 된다. 반대로 같은 CTE 를 두 번 붙여 쓰면 그때는 따로 계산해 두고 재사용한다. `MATERIALIZED` 와 `NOT MATERIALIZED` 는 이 판단을 손으로 뒤집는 자리다.

자료를 옮기는 일에는 세 번째 성질이 쓰인다. PostgreSQL 에서는 `WITH` 안에 `INSERT` · `UPDATE` · `DELETE` 를 넣을 수 있고, 이들은 바깥 질의가 결과를 읽든 말든 "정확히 한 번, 그리고 끝까지" 실행된다. 지운 줄을 `RETURNING` 으로 돌려받아 그대로 다른 표에 넣는 것이 대표적인 쓰임이다. 다만 하위 문장들은 전부 같은 스냅숏에서 동시에 돌기 때문에 **서로의 변경을 못 본다.** 값을 넘기는 길은 `RETURNING` 하나뿐이다.

## 💡 실제 사례

- **여러 단으로 나눈 집계** — 거르기, 묶어 세기, 순위 매기기를 단마다 이름 붙여 위에서 아래로 읽히게 만든다.
- **조직도 타고 오르기** — 팀장의 팀장을 끝까지 따라가는 질의를 재귀 항 하나로 적는다. 깊이를 몰라도 된다.
- **옮기면서 지우기** — 지운 줄을 `RETURNING` 으로 돌려받아 보관용 표에 넣는다. 지우기와 넣기가 한 문장 안에서 한 번씩만 돈다.

## 🚫 흔한 오해

- **CTE 로 빼면 한 번만 계산되니까 빨라진다** — 그렇지 않다. 한 번만 참조하고 부작용이 없으면 PostgreSQL 은 그것을 바깥 질의에 접어 넣는다. 서브쿼리로 적은 것과 같은 계획이 나온다.
- **읽기 좋으니 어디든 잘게 쪼개는 게 낫다** — 여러 번 참조하는 CTE 는 따로 계산해 두는데, 그러면 바깥 조건이 안으로 못 들어가서 큰 표를 통째로 훑고 그중 한 줄만 쓰는 일이 생긴다.
- **WITH 안에서 지운 줄은 뒤 문장에서 이미 없다** — 못 본다. 하위 문장들은 같은 스냅숏으로 동시에 돌기 때문에 서로의 변경이 안 보인다. 넘기려면 `RETURNING` 으로 돌려받아야 한다.

## 📝 정리

**"질의 하나 안에서만 사는 이름 붙인 중간 표"** 라고 읽으면 된다. 이름이 붙으니 위에서 아래로 읽히고 고칠 자리가 하나로 모이며, 스스로를 부르는 질의가 열린다. 다만 이름을 붙였다고 저절로 한 번만 계산되는 것은 아니다.

## 🧒 열 살에게

요리할 때 소스를 한 냄비 만들어 두고 "양념장" 이라고 이름을 붙여 두면, 쓸 때마다 만드는 법을 처음부터 다시 말하지 않아도 되지? 맛을 바꾸고 싶을 때도 냄비 하나만 고치면 돼. 대신 그 요리가 끝나면 냄비째 버려서 다음 요리 때는 없어.

## ❓ 이해했는지

- 이름을 붙여 뺐는데도 계획에 그 계산이 두 번 찍히지 않는 일은 왜 생기나 → 흔한 오해
- 깊이가 몇 단인지 모르는 조직도를 질의 하나로 타고 오르면 안에서는 무슨 일이 도나 → 작동 원리
- 지운 줄을 다른 표로 옮길 때 그 줄을 어떻게 건네나 → 실제 사례
