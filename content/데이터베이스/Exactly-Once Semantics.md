# Exactly-Once Semantics (정확히 한 번)

## 📝 정의

Exactly-Once Semantics 는 **같은 사건이 결과에 딱 한 번만 남는 보장**이다.

흐르는 데이터를 다루는 곳에서는 재시도가 일상이다. 응답이 안 오면 다시 보내고, 기계가 죽으면 읽던 자리로 되감아 다시 읽는다. 그래서 "한 번만 보낸다" 는 애초에 불가능하다. 이 보장이 약속하는 것은 전송 횟수가 아니라 **결과에 남은 횟수**다.

### 이름
Exactly :: 정확히
Once :: 한 번
Semantics :: 그 말의 뜻
= 붙여 읽으면 "정확히 한 번이라는 뜻". 몇 번 왔느냐가 아니라 결과에 몇 번 남았느냐다

### 비유
영수증 번호를 적어 두는 계산대. 같은 번호가 또 오면 아까 이미 찍은 것으로 보고 그냥 흘려보낸다.

### 예
결제 버튼이 안 눌린 것 같아 한 번 더 눌렀는데 카드는 한 번만 빠져나간 그 순간이다.

## 🖼️ 그림으로 보기

```도해
층: 정확히 한 번은 어디까지 지켜지나
보내는 쪽 :: 같은 번호가 또 오면 브로커가 버린다
엔진 안 :: 사건 하나가 상태에 한 번만 반영된다
내보내는 쪽 :: 한 묶음으로 확정하거나 통째로 무른다
바깥 부수 효과 :: 메일 발송·남의 API 호출은 여기서 샌다
= 몇 번을 보내든 결과에 한 번만 남기는 울타리다. 울타리 밖은 각자 막아야 한다
```

## ⚠️ 해결하는 문제

```도해
대조: 답을 못 받아 그냥 다시 보내면 무엇이 달라지나
그냥 다시 보내면 || 정확히 한 번으로
결제 :: 두 번 빠진다 || 한 번만 빠진다
집계 :: 매출이 부푼다 || 수치가 맞는다
장애 복구 :: 겁나서 못 돌린다 || 그냥 다시 돌린다
= 재시도를 못 하면 장애가 곧 데이터 손실이 된다. 이 보장은 재시도를 안전하게 만든다
```

흐르는 것을 다루는 파이프라인은 반드시 어딘가에서 다시 한다. 응답이 늦으면 보낸 쪽은 실패로 보고 재전송하고, 처리하던 기계가 죽으면 마지막으로 확정한 자리로 되감아 다시 읽는다. 이 재시도를 없앨 수는 없다. 없애면 한 번의 실패가 그대로 유실이 된다.

그래서 문제를 뒤집는다. 여러 번 오는 것을 막는 대신, 여러 번 와도 결과가 같아지게 만든다. 보낸 것마다 번호를 달아 두 번째를 알아보고, 읽은 자리와 계산 결과를 한 묶음으로 확정한다. 그러면 새벽에 장애가 나도 "다시 돌리면 숫자가 두 배가 되나" 를 걱정하지 않고 어제치를 그대로 재처리할 수 있다. 데이터 엔지니어에게 이 보장의 값어치는 정확함보다 **겁내지 않고 다시 돌릴 수 있다는 것**에 있다.

## ⚙️ 작동 원리

보내는 쪽부터 본다. Kafka 의 producer 문서는 두 가지 모드를 적어 둔다 — 멱등 producer 와 트랜잭션 producer 다. 멱등 쪽은 "Kafka 의 전달 보장을 최소 한 번에서 정확히 한 번으로 끌어올린다" 고 적혀 있고, 하는 일은 단순하다. 보내는 것마다 번호를 붙이고 같은 번호가 또 오면 받는 쪽이 버린다. 그래서 재시도가 중복을 만들지 않는다. 3.0 부터는 이 모드가 기본으로 켜져 있다. 다만 문서는 곧바로 단서를 단다 — 그 보장은 **한 세션 안에서만**이다. 보내던 쪽이 죽었다 살아나면 번호표를 새로 받는다.

여러 곳에 한꺼번에 쓰는 일은 트랜잭션 producer 가 맡는다. `transactional.id` 를 주면 여러 파티션과 여러 토픽에 원자적으로 쓸 수 있고, 읽는 쪽도 확정된 것만 읽도록 맞춰야 양 끝이 성립한다. Amazon SQS 의 FIFO 큐는 같은 일을 더 단순하게 한다. 보낼 때 중복 제거 번호를 주거나 본문의 SHA-256 해시를 쓰게 하고, **5분** 안에 같은 번호가 다시 오면 큐에 넣지 않는다.

엔진 안쪽은 다르게 푼다. Flink 문서의 정의가 가장 정확하다 — 정확히 한 번은 "모든 사건이 엔진이 관리하는 상태에 정확히 한 번 반영된다" 는 뜻이지, 사건이 한 번만 처리된다는 뜻이 **아니다**. 방법은 스냅숏이다. 흐름 속에 장벽을 끼워 넣고, 장벽은 레코드를 앞지르지 않은 채 같이 떠내려간다. 입력이 둘 이상인 마디는 장벽에서 줄을 맞춘 다음 상태를 통째로 찍어 둔다. 이 줄 맞추기를 건너뛰는 스위치가 최소 한 번 모드이고, 지연은 줄지만 복구할 때 중복이 생긴다.

끝까지 가려면 양쪽 끝이 조건을 만족해야 한다. Flink 문서는 두 줄로 적는다 — 원본을 되감아 다시 읽을 수 있어야 하고, 내보내는 쪽은 트랜잭션이거나 멱등해야 한다. Dataflow 는 또 다른 방식을 쓴다. 재시도가 중복을 만들 수 있으니 모든 메시지에 고유 번호를 붙이고, 받는 쪽마다 **이미 본 번호의 장부**를 들고 있다가 걸러낸다.

## 💡 실제 사례

- **결제 재시도** — Amazon SQS 의 FIFO 큐는 같은 중복 제거 번호가 **5분** 안에 다시 오면 아예 큐에 넣지 않는다. 번호를 직접 안 주면 본문의 SHA-256 해시로 대신 만들어 쓴다.
- **어제치 재처리** — Kafka 는 3.0 부터 `enable.idempotence` 가 기본으로 켜져 있고, Flink 는 스냅숏 자리로 되감아 다시 읽는다. 그래서 집계 잡을 다시 돌려도 매출이 두 배가 되지 않는다.
- **읽은 자리와 결과를 한 묶음으로** — Kafka 에 `transactional.id` 를 주면 여러 파티션과 여러 토픽에 원자적으로 쓸 수 있다. 어디까지 읽었는지 표시하는 일과 계산 결과를 함께 확정해야 중간에 죽어도 반쪽만 남지 않는다.

## 🚫 흔한 오해

- **정확히 한 번이면 딱 한 번만 전송된다** — 아니다. 전송은 몇 번이고 다시 일어난다. 결과에 한 번만 반영될 뿐이다.
- **켜 두면 파이프라인 끝까지 안전하다** — 엔진 안에서만 그렇다. Dataflow 문서는 외부 저장소에 쓰는 일 같은 부수 효과는 이 보장 밖이라고 못 박는다.
- **정확히 한 번이 항상 낫다** — 공짜가 아니다. 확정을 묶느라 지연이 늘어서, 최신값만 맞으면 되는 집계에는 최소 한 번 + 멱등한 계산이 더 싸고 빠르다.

## 🚨 주의사항

- **보내는 쪽 설정 하나로 끝나지 않는다.** 원본이 되감기고, 엔진이 상태를 스냅숏으로 찍고, 목적지가 확정을 묶어야 세 자리가 다 이어진다. 한 자리라도 빠지면 그 지점에서 중복이 샌다.
- **기계가 죽으면 번호표가 바뀐다.** Kafka 문서가 못 박는 "한 세션" 이 그 뜻이다. 세션을 넘어서까지 막으려면 업무 상 뜻이 있는 키를 직접 붙여야 한다.
- **중복 제거에는 시간 제한이 있다.** SQS FIFO 의 창은 5분이다. 그보다 늦게 온 재시도는 새 메시지로 들어간다.

## 📝 정리

**"여러 번 와도 결과에는 한 번만 남는 그 약속"** 이라고 읽으면 된다. 한 번만 보낸다는 뜻이 아니라 몇 번을 보내도 결과가 같아지게 만든다는 뜻이고, 그래서 보내는 쪽의 번호표와 받는 쪽의 장부와 확정을 묶는 장치가 함께 있어야 성립한다. 메일 발송처럼 바깥으로 나가는 일은 이 울타리 밖이라 따로 막아야 한다.

## 🧒 열 살에게

가게에서 계산할 때마다 영수증에 번호를 하나씩 적어 둬. 그러면 같은 번호가 또 나왔을 때 아까 이미 계산한 거라고 알아보고 그냥 넘길 수 있어. 그래서 네가 헷갈려 두 번 내밀어도 돈은 한 번만 나가.

## ❓ 이해했는지

- 결제 버튼을 두 번 눌렀는데 카드가 한 번만 빠지게 하려면 무엇이 필요한가 → 작동 원리
- 이 보장을 켜 뒀는데도 알림 메일이 두 번 오는 일은 왜 생기나 → 흔한 오해
- 보내는 쪽 설정만 고쳐서는 왜 끝까지 안 되나 → 그림
