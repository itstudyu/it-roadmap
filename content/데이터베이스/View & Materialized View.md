# View & Materialized View (뷰와 구체화 뷰)

## 📝 정의

뷰는 **저장된 질문**이고, 구체화 뷰는 그 질문의 저장된 답이다.

Materialize 는 "실체가 되게 한다" 는 뜻이다. 이름이 곧 차이다 — 구체화 뷰는 질의만 적어 두는 대신 그 질의를 한 번 돌린 결과를 표처럼 눌러 담아 둔다.

### 이름
View :: 보여 주기
Materialize :: 실체로 만듦
= 붙여 읽으면 "보여 주기" 와 "실체로 만들어 둔 보여 주기". 답을 실제로 담았느냐가 갈림이다

### 비유
조리법과 냉장고의 반찬. 조리법은 먹을 때마다 새로 만들어야 하고, 반찬은 바로 꺼내 먹지만 어제 만든 것이다.

### 예
가계부 화면 밑에 어제 자정 기준이라고 적혀 있는 숫자가 담아 둔 답 쪽이다.

## 🖼️ 그림으로 보기

```도해
대조: 뷰와 구체화 뷰는 무엇이 다른가
뷰 |=| 구체화 뷰
저장하는 것 :: 질문만 저장한다 || 답까지 저장한다
읽을 때 :: 매번 다시 돈다 || 담아 둔 것을 낸다
값의 신선도 :: 늘 지금 값이다 || 갱신 때의 값이다
= 뷰는 저장된 질문, 구체화 뷰는 저장된 답이다
```

## ⚠️ 해결하는 문제

```도해
대조: 같은 복잡한 조회를 여러 곳에서 쓰면 어떻게 되나
뷰 없이 || 뷰로
질의문 :: 곳곳에 베껴 둔다 || 이름 하나로 부른다
규칙이 바뀌면 :: 베낀 곳을 다 고친다 || 뷰만 고친다
권한 :: 원본 표를 열어준다 || 뷰만 열어준다
= 복잡한 조회에 이름을 붙여 한 곳에서만 고치게 한다
```

표 여섯 개를 [[JOIN]] 하고 조건을 다섯 줄 붙인 질의가 화면 열 곳에서 쓰인다면, 그 질의는 열 벌 베껴 적혀 있다는 뜻이다. 집계 규칙이 한 번 바뀌면 열 곳을 다 찾아 고쳐야 하고, 한 곳을 놓치면 같은 지표가 화면마다 다른 숫자로 뜬다. 원본 표를 열어줘야 한다는 문제도 따라온다 — 민감한 컬럼이 같은 표에 있으면 필요한 것만 보여줄 방법이 없다.

뷰는 그 질의에 이름을 붙여 데이터베이스 안에 한 벌만 둔다. 부르는 쪽은 표 이름 하나만 알면 되고, 규칙이 바뀌면 뷰 정의만 고친다. 원본 표 권한 없이 뷰 권한만 주는 것도 되므로, 보여줄 컬럼만 남긴 뷰가 그대로 접근 통제 수단이 된다.

## ⚙️ 작동 원리

뷰를 만들 때 데이터베이스는 결과를 저장하지 않는다. 질의를 적어 두고, 그 뷰가 참조될 때마다 그 질의를 다시 돌린다. 그래서 뷰는 늘 지금 값을 내지만, 원본 표를 직접 조회하는 것과 같은 일을 매번 한다.

구체화 뷰는 만들 때 그 질의를 실제로 돌려 결과를 표 같은 형태로 저장한다. 이후 조회는 저장된 데이터를 바로 읽으므로 원본 표나 뷰를 거치는 것보다 훨씬 싸다. 하루에 천 번 보는 집계라면 뷰는 천 번 계산하고 구체화 뷰는 갱신할 때 한 번 계산한다.

대신 저장해 둔 답은 저절로 낡는다. PostgreSQL 에서 새 값을 채우려면 `REFRESH MATERIALIZED VIEW` 로 내용을 통째로 갈아치우는데, 흔한 운영 방식이 밤마다 이 갱신을 걸어두는 것이다. SQL Server 에서는 뷰에 유일 클러스터드 인덱스를 만들면 정의가 계산되어 표처럼 저장되고, 그것을 인덱스 뷰라고 부른다.

## 💡 실제 사례

- **집계 화면** — 매출 요약을 구체화 뷰로 두고 밤마다 갱신하면 화면은 담아 둔 답만 읽는다.
- **권한 분리** — 민감한 컬럼을 뺀 뷰만 열어주고 원본 표 권한은 주지 않는다.
- **바뀐 스키마 감추기** — 없어진 옛 표 이름을 뷰로 흉내내 그 표를 쓰던 질의를 그대로 살려 둔다.

## 🚫 흔한 오해

- **뷰를 만들면 조회가 빨라진다** — 뷰는 결과를 갖고 있지 않다. 참조될 때마다 그 질의를 다시 돌리니 빨라질 이유가 없다.
- **구체화 뷰는 원본이 바뀌면 따라 바뀐다** — 갱신해 줄 때까지 옛 답을 그대로 낸다. 저장된 답이라 원본을 보고 있지 않다.
- **구체화 뷰가 뷰보다 낫다** — 지금 값이어야 하는 자리에서는 낡은 답이 그냥 틀린 답이다. 원본이 자주 바뀌는 데이터에는 맞지 않는다.

## 🚨 주의사항

- **갱신은 내용을 통째로 갈아치운다.** 바뀐 행만 골라 고치는 것이 아니라 구체화 뷰의 내용 전체를 다시 채운다.
- **갱신하는 동안 읽기가 막힐 수 있다.** PostgreSQL 에서 `CONCURRENTLY` 없이 갱신하면 그 구체화 뷰를 읽으려는 연결이 기다리게 된다. `CONCURRENTLY` 를 쓰려면 그 구체화 뷰에 유일 [[Index]] 가 하나 있어야 한다.
- **집계가 든 뷰로는 원본을 고칠 수 없다.** `GROUP BY` · `DISTINCT` · 집계 함수가 들어가면 자동 갱신 가능 뷰가 아니게 되어 그 뷰에 `INSERT` 나 `UPDATE` 를 할 수 없다. 구체화 뷰도 직접 고칠 수 없다.

## 📝 정리

**"적어 둔 조리법과 만들어 둔 반찬"** 이라고 읽으면 된다. 그래서 뷰는 늘 지금 값을 내는 대신 매번 계산하고, 구체화 뷰는 바로 내놓는 대신 갱신한 시점의 값을 낸다. 고르는 기준은 속도가 아니라 얼마나 낡아도 되는지다.

## 🧒 열 살에게

조리법은 종이에 적힌 만드는 법이라 먹을 때마다 새로 만들어야 해. 냉장고 반찬은 꺼내면 바로 먹지만 어제 만든 거야. 그래서 고를 때 묻는 건 어느 쪽이 빠르냐가 아니라 어제 것이어도 괜찮냐야.

## ❓ 이해했는지

- 복잡한 질의를 뷰로 바꿨는데 조회가 그대로 느리다면 무엇을 잘못 기대한 것인가 → 흔한 오해
- 구체화 뷰를 갱신하는 동안 그 뷰를 읽는 요청이 멈춰 섰다면 왜 그런가 → 주의사항
- 원본 표 권한을 주지 않고도 일부 컬럼만 보여주려면 어떻게 하나 → 실제 사례
