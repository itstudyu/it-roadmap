# ELT (추출 적재 변환)

## 📝 정의

ELT 는 **원본을 먼저 담고 담은 자리에서 바꾸는 순서**다.

[[ETL]] 과 세 글자가 같고 가운데 둘의 자리만 바뀌었는데, 실무에서 달라지는 것은 순서가 아니라 **원본이 남느냐**다. 바꾸기가 담기보다 앞에 있으면 목적지에는 결과만 도착하고, 뒤에 있으면 손대지 않은 원본이 목적지 안에 그대로 남는다.

### 이름
Extract :: 뽑아내기
Load :: 그대로 담기
Transform :: 담은 자리에서 바꾸기
= 붙여 읽으면 "뽑아서 담고 나서 바꾸기". 바꾸는 일이 담기 뒤로 갔다

### 비유
사진은 원본 그대로 다 넣어 두고 자르고 밝기 고치는 일은 앨범에서 하는 것 — 잘못 잘라도 원본이 남아 있어 다시 만들면 된다.

### 예
매출 기준이 바뀌었는데 원본을 다시 받아 오지 않고 표만 새로 짜서 하루 만에 끝낸 적이 있다면, 그게 이 순서다.

## 🖼️ 그림으로 보기

```도해
층: 담아 둔 원본이 어떻게 쓸 만한 표가 되나
원본 그대로 :: 온 모양 그대로 쌓는다. 손대지 않는다
맞춘 것 :: 형식을 맞추고 중복과 시험용 줄을 걷어낸다
쓰라고 만든 것 :: 화면과 보고서가 바로 읽을 모양으로 짠다
= 아래로 갈수록 쓰기 쉬워지고, 맨 위에는 손대지 않은 원본이 늘 남아 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 담기 전에 다 바꿔 두면 나중에 무엇이 막히나
바꿔서 담으면 || 담고 나서 바꾸면
규칙이 바뀜 :: 원본부터 다시 받는다 || 그 자리에서 다시 짠다
버린 칸 :: 영영 못 되살린다 || 원본에 남아 있다
새 질문 :: 옮기는 판을 고친다 || 질의만 새로 쓴다
= 원본을 남겨 두면, 나중에 생각이 바뀌어도 처음으로 되돌아가지 않아도 된다
```

옮기는 길에 다 정리해서 담으면 목적지가 깔끔하다. 문제는 **버린 것을 되살릴 수 없다**는 데 있다. 반년 뒤에 "취소된 주문도 세 봅시다" 라는 말이 나오면, 옮길 때 걸러 버린 그 줄들은 목적지 어디에도 없다. 원본 쪽에 아직 남아 있기를 빌면서 처음부터 다시 받아 와야 하고, 원본이 이미 지웠으면 그 기간은 영영 답이 없다.

ELT 는 **판단을 뒤로 미룬다.** 무엇이 필요할지 모르는 채로 일단 온 모양 그대로 담고, 무엇이 필요한지 알게 된 뒤에 목적지 안에서 골라 짠다. Fabric 문서가 원본 층을 두고 "도착한 그대로 저장한다. 고치는 것을 허용하지 않는다" 고 적고, 그 위에 정제 층과 제공 층을 얹어 "구조와 품질을 단계적으로 올린다" 고 설명하는 구조가 그것이다. 원본 사본이 진실의 기준으로 보존되기 때문에, 위층은 언제든 지우고 다시 만들어도 되는 것이 된다.

## ⚙️ 작동 원리

바꾸는 일은 목적지 안에서 **질의로** 한다. BigQuery 문서는 이 자리를 "코드 조각들을 순서대로 걸어 두고 실행하는 파이프라인" 으로 설명하고, 실행 순서를 사람이 매기는 대신 "정의된 의존 관계가 정하는 순서대로 실행한다" 고 적는다. 어느 표가 어느 표에서 나왔는지를 적어 두면 다시 만들 순서는 저절로 나온다는 뜻이다.

**매일 도는 것은 대개 전체가 아니라 구간이다.** 어제치만 새로 담고 위층 표를 그 구간만 다시 짠다. 여기서 실무의 진짜 함정이 나온다 — 같은 구간을 두 번 담으면 줄이 두 벌이 된다. 실패해서 다시 돌리든, 사람이 손으로 한 번 더 누르든, 빠진 날을 채우든 두 번 도는 일은 반드시 생긴다. 그래서 넣기가 아니라 **열쇠로 맞춰 덮어쓰기**(`MERGE`)로 짠다. Fabric 문서도 새 것이 올 때는 덧붙이지만 이미 있는 것을 함께 고쳐야 할 때는 덮어쓰기를 쓰라고 적는다.

원본 층과 위층은 **저장하는 모양이 다르다.** 원본 층은 온 형식 그대로 두는 것이 원칙이고(원본이 다른 저장소에 있으면 복사하지 않고 바로 가리키기도 한다), 정제·제공 층은 표 형식으로 굳혀 둔다. 그 형식이 변경 이력을 함께 들고 있어서 잘못 만든 표를 이전 시점으로 되돌릴 수 있고, 오래된 이력은 따로 청소한다 — 다만 최근 이레치는 일관성을 위해 기본적으로 못 지운다.

**파일 크기가 성능을 정한다.** 조각이 잘게 흩어지면 계산보다 파일 관리에 시간이 간다. 문서가 드는 목표는 파일 하나에 128MB에서 1GB 사이이고, 원본 층은 작아도 참지만 제공 층으로 갈수록 크게 뭉쳐 두라고 적는다.

## 💡 실제 사례

- **Microsoft Fabric 의 세 층으로 쌓기** — 청동·은·금 세 층을 각각 따로 떼어 두고, 청동 층은 "도착한 그대로 저장하고 고치는 것을 허용하지 않는다". 원본이 S3 나 ADLS Gen2 처럼 다른 저장소에 있으면 복사하지 않고 바로 가리키는 지름길을 만든다.
- **지표 정의가 바뀐 날** — 원본을 다시 받지 않는다. 제공 층 표를 지우고 정제 층에서 다시 짜면 과거치까지 새 기준으로 채워진다.
- **Google BigQuery 의 파이프라인에 순서를 맡기기** — 노트북과 질의 같은 조각을 묶어 두면 실행 순서를 사람이 매기지 않는다. "정의된 의존 관계가 정하는 순서" 대로 돌고, 같은 구간을 두 번 담아도 `MERGE` 로 짜 두었으면 줄이 두 벌이 되지 않는다.

## 🚫 흔한 오해

- **원본 층에 다 부어 두면 나중에 알아서 쓸 수 있다** — 담긴 것과 읽을 수 있는 것은 다르다. 어떤 열이 무슨 뜻인지 함께 적어 두지 않으면 몇 달 뒤의 원본 층은 자료가 아니라 쓰레기다.
- **ELT 는 변환이 단순해서 다시 돌려도 안전하다** — 같은 구간을 두 번 담으면 줄이 두 벌이 된다. 열쇠로 덮어쓰도록 짜 두지 않으면 재시도가 곧 중복이다.
- **요즘은 무조건 ELT 로 간다** — 과잉 적용이다. 바꾸는 값을 목적지가 무는 방식이라, 계산량만큼 돈을 받는 창고에서는 매일 도는 무거운 질의가 그대로 청구서가 된다. 개인정보처럼 애초에 담으면 안 되는 것도 있다.

## 📝 정리

**"일단 담고 나서 고치는 그 순서"** 라고 읽으면 된다. 손대지 않은 원본이 목적지에 남기 때문에, 규칙이 바뀌어도 원본을 다시 받지 않고 위층 표만 다시 짜면 된다. 대신 같은 구간이 두 번 담기는 일이 반드시 생기므로 넣기가 아니라 열쇠로 덮어쓰기로 짜 둔다.

## 🧒 열 살에게

찍은 사진을 자르고 색까지 고쳐서 저장해 버리면, 나중에 다르게 자르고 싶어도 못 하지? 그래서 처음 찍은 건 그대로 두고 고친 건 따로 만들어 두는 거야. 그러면 마음이 바뀔 때마다 처음 것에서 새로 만들면 돼.

## ❓ 이해했는지

- 반년 뒤에 "취소된 주문도 세자" 는 말이 나왔을 때 두 순서 중 어느 쪽이 곤란해지나 → 해결하는 문제
- 어제치를 두 번 담았는데 줄이 두 벌이 되지 않게 하려면 무엇으로 짜야 하나 → 작동 원리
- 계산량만큼 돈을 받는 창고에서 이 순서가 위험해지는 자리는 어디인가 → 흔한 오해
