# CAP Theorem (CAP 정리)

## 📝 정의

CAP Theorem은 **네트워크가 갈라지면 일관성과 가용성 중 하나를 내주게 된다는 정리**다.

이름은 세 글자다 — Consistency(일관성) · Availability(가용성) · Partition tolerance(분할 내성). 셋을 나란히 놓고 "둘만 고른다" 로 외우면 정작 중요한 조건이 빠진다. 거래가 청구되는 시점이다. Microsoft 문서는 이 정리가 네트워크 분할이 일어난 동안의 일관성과 가용성 사이의 거래를 설명한다고 적고, 분할이 없을 때도 일관성과 성능 사이의 거래는 따로 있다고 덧붙인다.

### 이름
Consistency :: 어디서 물어도 최신값
Availability :: 그래도 답은 준다
Partition :: 사이의 선이 끊김
Tolerance :: 그래도 버팀
= 셋을 나란히 두면 "선이 끊겨도 버티려면 최신값과 응답 중 하나를 내준다". 이름이 곧 갈림길이다

### 비유
전화선이 끊긴 두 지점 가게 — 재고를 정확히 맞추려면 주문을 멈춰야 하고, 주문을 계속 받으려면 재고가 어긋난 채로 받아야 한다.

### 예
은행이 장애 나면 송금 자체가 접수되지 않는데, SNS 는 장애 중에도 글은 올라가고 친구 화면에만 한참 뒤에 뜬다.

## 🖼️ 그림으로 보기

```도해
흐름: 평시에는 되던 것이 언제 갈림길이 되나
평시 :: 최신값도 주고 요청도 다 받는다
분할 :: 복제본 사이의 선이 끊긴다
갈림길 :: 최신값이냐 응답이냐, 둘 중 하나만 된다
선택 :: 쓰기를 거부하거나, 받아두고 나중에 맞춘다
복구 :: 선이 붙으면 살아나는 대로 갱신된다
= 거래는 평시에 청구되지 않는다. 갈라진 그 순간에만 청구된다
```

## ⚠️ 해결하는 문제

```도해
대조: 선이 끊기면 쓰기 요청은 어떻게 되나
동기 복제 쪽 |=| 최종 일관성 쪽
쓰기 요청 :: 거부된다 || 받아준다
확정 조건 :: 복제본 전부 갱신 || 살아나는 대로
직후 읽기 :: 최신값만 나온다 || 옛값도 나온다
= 어느 쪽도 공짜가 아니다. 무엇을 내줄지를 미리 골라 두는 것이다
```

복제본을 여러 대에 두면 빨라지고 잘 버틴다. 그런데 그 복제본들 사이의 선이 끊긴 순간에 무엇을 해야 하는지는 아무도 미리 정해주지 않는다. 그때 할 수 있는 일은 둘뿐이다. 최신값만 주기 위해 요청을 막을 것인가, 요청을 받되 값이 어긋나는 것을 허용할 것인가.

Microsoft 문서는 이 갈림길을 양쪽에서 그려 보인다. 동기 복제로 묶인 클러스터는 다른 복제본에 그 변경을 전파할 수 없으면 쓰기를 거부한다 — 모든 복제본이 갱신돼야 트랜잭션이 끝나기 때문이다. 반대쪽에서는 쓰기를 받아두고 복제본이 살아나는 대로 갱신한다. CAP 정리는 이 갈림길에 이름을 붙여, 설계할 때 "분할이 나면 어느 쪽으로 간다" 를 미리 적게 만든다.

## ⚙️ 작동 원리

쓰기 하나가 들어오면 받은 노드는 그것을 자기만 적고 끝내지 않는다. 같은 변경을 다른 복제본에 보내고 응답을 기다린다. 몇 개의 응답을 받아야 "끝났다" 고 할지, 그 하나가 이 시스템이 분할에서 어느 쪽으로 갈지를 미리 정해 버린다.

전부의 응답을 기다리기로 했다면, 복제본 하나로 가는 선이 끊긴 순간 그 쓰기는 끝날 수가 없다. 기다리다 시간이 지나면 거부하는 것 말고는 할 일이 없다 — 일관성 쪽이다. 반대로 응답을 안 기다리고 받아둔 뒤 나중에 전하기로 했다면 쓰기는 계속 되지만, 아직 못 받은 복제본에 물은 사람은 옛값을 본다 — 가용성 쪽이다.

그 사이에 과반만 기다리는 방법이 있다. Spanner 는 투표 자격이 있는 복제본의 과반이 동의하면 커밋한다. 과반은 갈라진 두 조각 중 한쪽에만 생기므로 양쪽이 서로 다른 값을 확정하는 일이 없고, 과반을 못 모은 쪽은 그동안 쓰기를 받지 못한다. 선이 붙으면 뒤처져 있던 복제본이 밀린 변경을 차례로 따라잡는다.

## 📊 비교: CAP 와 PACELC

| | CAP | PACELC |
|---|---|---|
| 언제를 말하나 | 분할이 난 동안 | 분할이 났을 때 **와 안 났을 때** |
| 무엇 사이의 거래 | 일관성 ↔ 가용성 | 분할 중엔 일관성 ↔ 가용성, 평시엔 일관성 ↔ 지연 |
| 어디에 잘 맞나 | 기기가 자주 끊기는 환경 | 클라우드 분산 시스템 |

Microsoft 문서는 CAP 를 사물 인터넷, 환경 모니터링, 모바일처럼 정전이나 엘리베이터 같은 이유로 기기가 실제로 갈라지는 환경에 특히 들어맞는 정리로 소개한다. 그리고 클라우드 애플리케이션 같은 분산 시스템에는 CAP 를 확장한 PACELC 가 더 적절하다고 적는다. 분할이 없을 때의 지연과 일관성 거래까지 함께 보기 때문이다.

## 💡 실제 사례

- **잔액처럼 어긋나면 안 되는 값** — 동기 복제 클러스터는 다른 복제본에 전파할 수 없으면 쓰기를 거부한다. 모든 복제본이 갱신돼야 트랜잭션이 끝난다.
- **과반 투표로 확정하는 쓰기** — Spanner 는 투표 자격이 있는 복제본의 과반이 동의하면 커밋한다. 과반만 있으면 되니 일부 복제본이 죽어도 쓰기가 계속된다.
- **잠깐 어긋나도 되는 값** — Bigtable 의 복제는 기본이 최종 일관성이다. 클러스터가 응답을 멈추면 다른 클러스터로 넘겨 트래픽을 계속 받는다.

## 🚫 흔한 오해

- **셋 중 둘을 고르는 문제다** — 고르는 시점이 빠졌다. 분할이 없는 동안 청구되는 거래는 일관성과 가용성 사이가 아니라 일관성과 성능 사이다. 갈림길은 선이 끊긴 그때 열린다.
- **CAP 의 C 는 ACID 의 C 와 같은 말이다** — Microsoft 문서가 둘이 기술적으로 구별되는 뜻이라고 따로 못 박는다. 여기서 일관성은 "어느 노드에 물어도 가장 최신 값을 준다" 는 뜻이고, 그러려면 복제본이 다 갱신될 때까지 요청을 붙들어야 할 수도 있다.
- **일관성 쪽을 고르면 언제나 안전하다** — 그 선택의 값은 분할 중 쓰기 거부다. 잠깐 어긋나도 손해가 없는 값까지 그렇게 다루면, 멀쩡한 요청이 선 하나 끊긴 것 때문에 막힌다.

## 🚨 주의사항

- **가용성을 골라도 고가용성이 되는 건 아니다.** 같은 문서는 가용성을 택하더라도 분할 시점에는 가용성이 떨어진다고 적는다. CAP 의 가용성은 일부 클라이언트에게 더 응답한다는 뜻이고, 모두에게 늘 응답한다는 뜻이 아니다.
- **실패 전환 직후를 조심한다.** 응답 없는 클러스터에서 다른 클러스터로 넘겼는데 아직 전파되지 않은 쓰기가 있으면, 전파가 끝날 때까지 일부 읽기가 옛 데이터를 돌려준다.

## 📝 정리

**"선이 끊기면 둘 중 하나는 내준다는 그 말"** 이라고 읽으면 된다. 세 글자에서 둘을 고르는 문제가 아니라, 분할이 났을 때 어느 쪽으로 갈지를 미리 정해두는 문제다. 여기서 말하는 일관성은 ACID 의 일관성과 다른 뜻이고, 가용성도 흔히 말하는 고가용성과 다른 뜻이다.

## 🧒 열 살에게

같은 빵집이 두 군데인데 서로 전화가 끊겼다고 해 봐. 남은 빵 개수를 정확히 맞추려면 손님을 잠깐 못 받고, 손님을 계속 받으면 두 가게가 세는 개수가 어긋나. 둘 다는 안 되니까 끊기기 전에 어느 쪽을 포기할지 정해 둬야 해.

## ❓ 이해했는지

- 분할이 나지 않은 평소에도 무언가를 내주고 있다면 그것은 무엇인가 → 비교
- ACID 를 지키는 DB 인데 CAP 의 일관성은 포기했다는 말이 성립할 수 있는 이유는 → 흔한 오해
- 다른 클러스터로 넘긴 직후에 옛 데이터가 읽히는 일은 왜 생기나 → 주의사항
