# Change Data Capture (변경 데이터 포착)

## 📝 정의

CDC 는 **표에서 바뀐 줄만 골라 흐름으로 흘려보내는 일**이다.

원본 표를 다시 훑는 것이 아니라, 데이터베이스가 이미 쓰고 있던 변경 기록을 읽어 낸다. SQL Server 문서는 "변경 데이터의 출처는 트랜잭션 로그다" 라고 못 박고, PostgreSQL 문서는 같은 일을 "미리 쓰기 로그의 내용을 해독해 밖에서 읽을 수 있는 모양으로 바꾸는 것" 이라 적는다.

### 이름
Change :: 바뀐 것
Data :: 그 값
Capture :: 놓치지 않고 잡기
= 붙여 읽으면 "바뀐 값을 놓치지 않고 잡기". 표 전체가 아니라 바뀐 것만 집는 일이다

### 비유
창고를 매번 다시 세는 대신, 들어오고 나갈 때마다 이미 적어 둔 입출고 장부를 통째로 넘겨주는 것.

### 예
쇼핑몰에 주문이 하나 들어간 지 몇 초 만에 사내 분석 화면에도 그 줄이 떠 있는 그 장면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 줄이 바뀐 사실이 어떻게 밖으로 새어 나오나
원본 표 :: 넣고 고치고 지운 일이 벌어진다
기록 파일 :: 그 일이 순서대로 먼저 적힌다
읽는 일꾼 :: 표가 아니라 그 기록 파일을 훑는다
변경 흐름 :: 바뀐 줄만 순서대로 밖으로 나간다
받는 쪽 :: 받은 순서대로 자기 표에 얹는다
= 원본 표를 다시 훑지 않는다. 이미 적혀 있던 기록을 읽어 낼 뿐이다
```

## ⚠️ 해결하는 문제

```도해
대조: 바뀐 것을 알아내려고 표를 다시 훑으면 어떻게 되나
매번 훑으면 || 기록을 읽으면
원본 부담 :: 훑을 때마다 무겁다 || 거의 없다
지운 줄 :: 사라져서 못 본다 || 지운 사실이 남는다
중간 변경 :: 마지막 값만 본다 || 한 번씩 다 본다
= 표는 지금 모습만 갖고 있다. 무슨 일이 있었는지는 기록 파일에만 남는다
```

바뀐 것을 알아내는 가장 손쉬운 방법은 갱신 시각 열을 두고 "최근 10분 안에 바뀐 줄" 을 긁어 오는 것이다. 이 방법에는 조용한 구멍이 셋 있다. 훑는 동안 원본이 무거워지고, 지워진 줄은 아예 조회에 안 잡히고, 10분 사이에 값이 세 번 바뀌었다면 마지막 하나만 보인다. 중간의 두 번은 없었던 일이 된다.

CDC 는 표를 보지 않고 **이미 적히고 있던 기록**을 읽는다. 데이터베이스는 어차피 고장에 대비해 모든 변경을 순서대로 로그에 먼저 적는다([[WAL]]). 그 로그에는 넣기·고치기·지우기가 벌어진 순서대로 다 남아 있으므로, 그것을 읽으면 원본에 부담을 거의 주지 않고 지운 사실과 중간 변경까지 빠짐없이 건진다.

## ⚙️ 작동 원리

읽어 낸 것은 **줄 하나가 아니라 사건 하나**다. SQL Server 는 이것을 변경 표로 떨어뜨리는데, 넣기와 지우기는 한 줄로 남지만 고치기는 두 줄이 된다 — 바뀌기 전 모습 하나와 바뀐 뒤 모습 하나다. 각 줄에는 확정 로그 번호가 붙어서 "같은 트랜잭션 안에서 확정된 것들" 을 묶어 주고 트랜잭션들 사이의 순서도 매긴다. 받는 쪽이 순서를 지켜 얹을 수 있는 근거가 이 번호다.

**시차가 없을 수는 없다.** 문서는 "포착 과정이 로그에서 변경을 뽑아내므로, 원본에 확정된 시각과 변경 표에 나타나는 시각 사이에 태생적인 지연이 있다" 고 적는다. 기본 설정에서 포착 작업은 쉬지 않고 돌되 한 바퀴에 트랜잭션 1000건까지 처리하고 5초를 쉰다. 실시간이라는 말은 여기서 초 단위를 뜻하지 즉시를 뜻하지 않는다.

읽어 가는 자리는 **원본 쪽에 표시로 남는다.** PostgreSQL 은 이것을 복제 슬롯이라 부르고, 슬롯을 "원본에서 일어난 순서 그대로 다시 재생해 줄 수 있는 변경의 흐름" 으로 정의한다. 슬롯은 연결이 끊겨도 남고 재시작에도 살아남는데, 바로 그 성질이 위험이기도 하다. 문서의 경고가 직설적이다 — 슬롯이 필요로 하는 로그는 지워지지 않으므로 저장 공간을 계속 먹고, "극단적인 경우 트랜잭션 번호가 한 바퀴 도는 것을 막으려고 데이터베이스가 멈출 수 있다."

**같은 것이 두 번 오는 것도 정상 동작이다.** 슬롯의 현재 위치는 체크포인트에서만 저장되므로, 죽었다 살아나면 조금 전 위치로 되돌아가 최근 것을 다시 보낸다. 문서는 책임을 받는 쪽에 명확히 넘긴다 — "같은 메시지를 두 번 이상 다루더라도 나쁜 결과가 나지 않게 하는 것은 읽는 쪽의 몫이다." 그래서 받는 표는 줄을 넣는 대신 열쇠로 덮어쓰도록([[Idempotency]]) 짜 둔다.

## 💡 실제 사례

- **SQL Server 에서 창고로 옮겨 담기** — 밤마다 표 전체를 다시 붓는 대신, 낮 동안 바뀐 줄만 흘려보내 분석용 표에 얹는다. 기본값으로 포착 작업은 한 바퀴에 트랜잭션 1000건까지 처리하고 5초를 쉬며, 청소 작업은 매일 새벽 두 시에 돌아 사흘 지난 변경 줄을 치운다.
- **PostgreSQL 의 복제 슬롯으로 검색 색인 따라 붙이기** — 상품 정보가 고쳐지면 그 사건이 슬롯을 통해 검색 쪽으로 흘러가 색인을 고친다. 슬롯은 연결이 끊겨도 남고 재시작에도 살아남아서, 다시 붙으면 끊긴 자리부터 이어 준다.
- **낡은 것에서 새것으로 옮겨 가기** — 옛 데이터베이스를 켜 둔 채 변경 흐름을 새 쪽으로 흘려 두 벌을 나란히 맞춰 놓고, 다 따라잡은 뒤에 읽는 곳만 바꾼다.

## 🚫 흔한 오해

- **CDC 도 결국 원본을 계속 조회하는 거 아닌가** — 아니다. 원본 표가 아니라 이미 쓰이고 있던 로그를 읽는다. 그래서 지워진 줄과 중간에 스쳐 간 값까지 남는다.
- **켜 두면 실시간이라 시차가 없다** — 로그에 적힌 뒤 포착 과정이 훑어 갈 때까지 시차가 있다. 공식 문서 자체가 "태생적인 지연" 이라고 적는다.
- **바뀐 걸 알아야 하면 무조건 CDC 다** — 과잉 적용이다. 원본의 로그를 붙잡아 두는 방식이라 안 읽어 가면 저장 공간이 차고 최악에는 원본이 멈춘다. 하루 한 번이면 갱신 시각 열로 긁는 편이 훨씬 싸다.

## 🚨 주의사항

- **읽어 가지 않는 구멍은 원본을 죽인다.** 슬롯을 만들어 두고 소비를 멈추면 로그가 지워지지 못해 쌓인다. 안 쓰는 슬롯은 반드시 지운다.
- **보관 기한 밖으로 밀려나면 그 구간은 영영 못 받는다.** SQL Server 는 기본으로 사흘치만 남기고 나머지를 치운다. 며칠 멈춰 있던 소비자는 이어 읽는 대신 처음부터 다시 채워야 한다.
- **원본의 열 구조가 바뀌면 흐름의 모양도 흔들린다.** 포착을 켠 뒤에 생긴 열은 잡히지 않고, 지워진 열은 빈 값으로 나간다. 받는 쪽이 모르는 사이에 값이 비기 시작한다.

## 📝 정리

**"표 말고 그 표의 기록을 읽는 일"** 이라고 읽으면 된다. 표는 지금 모습만 갖고 있어서 지운 줄과 중간 변경을 알려 주지 못하지만, 로그에는 벌어진 순서 그대로 다 남아 있다. 대신 어디까지 읽었는지가 원본 쪽에 표시로 남으므로, 소비를 멈추면 원본이 위험해지고 죽었다 살아나면 같은 것이 두 번 온다.

## 🧒 열 살에게

가게에 물건이 몇 개 남았는지 알려고 매번 창고를 통째로 세면 힘들지? 그런데 들어오고 나갈 때마다 이미 장부에 적어 두잖아. 그 장부에서 새로 적힌 줄만 읽으면 창고를 안 세고도 뭐가 달라졌는지 다 알 수 있어.

## ❓ 이해했는지

- 갱신 시각 열로 긁을 때 지워진 줄을 못 보는 이유는 무엇인가 → 해결하는 문제
- 죽었다 살아난 소비자에게 같은 변경이 두 번 오는 일은 왜 생기나 → 작동 원리
- 만들어 두고 아무도 안 읽는 구멍 하나가 원본을 멈추게 할 수 있는 이유는 → 주의사항

## 🔗 관련 용어

- [[WAL]] — CDC 가 읽어 내는 바로 그 기록. 원래는 고장 대비용으로 적히던 것이다
- [[Transaction]] — 변경 줄에 붙는 확정 번호가 묶어 주는 단위
- [[Apache Kafka]] — 뽑아낸 변경 흐름을 흘려보내는 가장 흔한 다음 자리
- [[Replication]] — 같은 로그를 읽어 사본을 맞추는 쪽. CDC 와 뿌리가 같다
- [[ETL]] — 표 전체를 다시 붓던 자리를 바뀐 줄만으로 바꾸는 대상
