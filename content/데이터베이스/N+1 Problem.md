# N+1 Problem (N+1 문제)

## 📝 정의

N+1 문제는 **목록 하나를 얻고 항목마다 또 묻는** 낭비다.

이름이 곧 셈이다 — 목록을 가져오는 질의 1 개에, 항목 N 개마다 하나씩 더해 N + 1 개가 나간다. 목록이 100줄이면 질의는 1번이 아니라 101번, 백 배 넘게 늘어난다. EF Core 문서는 게으른 로딩이 이 문제를 너무 쉽게 불러온다며 아예 쓰지 말라고 권한다.

### 비유
장 볼 목록은 한 번에 받았는데, 물건 하나 살 때마다 가게를 새로 다녀오는 일이다.

### 예
목록 한 쪽을 여는 데 몇 초가 걸리다가, 한 쪽에 담는 줄 수를 줄이자 딱 그만큼 빨라지는 그 화면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 목록 하나를 화면에 그리는데 질의는 몇 번 나가나
앱 :: 글 목록을 한 번 청한다 — 질의 1번
DB :: 글 10줄을 돌려준다
앱 :: 첫 글의 작성자를 꺼내 본다
DB :: 그 한 사람만 찾아 준다 — 질의 2번
앱 :: 남은 9줄에도 똑같이 한 번씩
= 목록은 한 번, 항목은 하나하나. 다 합쳐 1 + N 번이다
```

## ⚠️ 해결하는 문제

```도해
대조: 목록을 그릴 때 질의를 한 번에 모으면 무엇이 달라지나
항목마다 따로 || 한 번에 함께
질의 수 :: 1 + N 번 || 1~2번
왕복 :: 항목 수만큼 || 정해져 있다
느려지는 때 :: 데이터가 늘면 || 거의 그대로
= 목록 길이가 질의 수를 정하지 않게 만드는 것이 답이다
```

질의 수가 목록 길이에 매달려 있으면, 데이터가 늘어난 만큼 그대로 느려진다. 개발용 DB 에는 열 줄이 들어 있어서 열한 번이면 끝나고 아무 일도 안 일어난다. 같은 코드가 운영에서 만 줄을 만나는 순간 왕복이 만 번이 된다.

미리 함께 읽으면 이 매달림이 끊긴다. EF Core 문서는 어떤 관계를 쓸지 미리 아는 경우라면 즉시 로딩을 써서 필요한 데이터를 **한 번의 왕복으로** 가져오는 편이 언제나 낫다고 적어 두었다.

## ⚙️ 작동 원리

```도해
층: 목록 하나를 그리는데 질의 수는 무엇에 매달리나
미리 함께 읽기 :: 한 번에 다 가져온다. 왕복 1번
쪼개 함께 읽기 :: 관계마다 한 번. 목록 길이와 무관
항목마다 읽기 :: 목록 길이가 곧 질의 수다. 1 + N 번
= 아래로 갈수록 질의 수가 목록 길이에 매달린다
```

게으른 로딩은 관계를 미리 읽지 않고, 코드가 그 속성을 건드리는 순간에 읽는다. 그래서 반복문 안에서 작성자를 꺼내 보는 한 줄이 곧 질의 한 번이 된다. 코드에는 질의문이 한 자도 안 보이는데 로그에는 같은 모양의 질의가 목록 길이만큼 찍힌다.

EF Core 문서가 게으른 로딩을 권하지 않는 까닭이 이것이다. 즉시 로딩이나 명시적 로딩으로 바꾸면 **왕복이 일어나는 자리가 소스에 드러난다.**

## 💡 실제 사례

- **글 목록에 작성자 이름 붙이기** — 글 스무 줄을 읽고 반복문에서 작성자를 건드리면 질의가 21번 나간다.
- **GraphQL 중첩 필드** — 목록 5개에 관계 필드를 두 겹으로 파면 리졸버 호출이 1 + 5 + 25 = 31 번이 된다. AWS AppSync 문서가 이 셈을 그대로 보여준다.
- **묶어서 묻기로 바꾸기** — 항목 하나씩 묻는 대신 여러 항목을 한 묶음으로 넘겨 받게 고친다. AppSync 는 이 묶음을 기본 다섯 개씩 모아 보낸다.

## 🚫 흔한 오해

- **질의를 잘 못 써서 생기는 문제다** — 질의문은 손으로 쓴 적조차 없다. ORM 이 관계를 알아서 읽어 주기 때문에 생기고, 코드에 남는 흔적은 반복문 한 개뿐이다.
- **한 번에 다 조인해 오면 항상 낫다** — 일대다를 한 질의로 묶으면 부모 줄이 자식 수만큼 복제된다. EF Core 는 이걸 카테시안 폭발이라 부르고, 일대다를 여럿 묶을수록 중복이 커져 성능을 해친다고 경고한다.
- **DB 에서만 생기는 문제다** — GraphQL 도 같은 꼴로 걸린다. 필드 하나를 한 겹 더 파는 것만으로 호출 수가 곱셈으로 불어난다.

## 📝 정리

N+1 문제는 목록 질의 하나에 항목마다의 질의 N 개가 따라붙는 꼴이다. 고치는 방법은 질의를 빠르게 하는 것이 아니라 **질의 수를 목록 길이에서 떼어내는** 것이다. 미리 함께 읽거나 여러 항목을 한 묶음으로 묻는 두 갈래가 그 일을 한다.

## ❓ 이해했는지

- 개발할 때는 멀쩡했는데 운영에서만 느려지는 일은 왜 벌어지나 → 해결하는 문제
- 코드에는 반복문 하나뿐인데 질의가 스물한 번 나가는 까닭은 → 작동 원리
- 관계를 한 질의로 다 조인해 오는 것이 늘 정답이 아닌 까닭은 → 흔한 오해

## 🔗 관련 용어

- [[ORM]] — 이 문제가 대개 생기는 자리. 질의를 감춰 주면서 질의 수도 함께 감춘다
- [[GraphQL]] — 중첩 필드를 파고들 때 같은 꼴로 걸리는 다른 무대
- [[Index]] — 질의 한 개를 빠르게 하는 장치. 질의 수는 줄이지 못한다
- [[Latency]] — 왕복이 늘어날 때 실제로 커지는 값
- [[Caching]] — 같은 질의가 되풀이될 때 왕복 자체를 없애는 다른 길
