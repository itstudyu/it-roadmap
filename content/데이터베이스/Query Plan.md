# Query Plan (쿼리 실행 계획)

## 📝 정의

Query Plan 은 **DB 가 이 질문을 어떻게 풀지 미리 고른 순서**다.

SQL 에는 원하는 결과만 적고 어떻게 꺼낼지는 적지 않는다. 그 "어떻게" 를 정하는 쪽이 옵티마이저다. MySQL 문서는 옵티마이저가 고른 동작들의 묶음을 쿼리 실행 계획이라 부르고, PostgreSQL 은 그것이 플랜 노드의 트리라고 적는다 — 맨 아래가 표에서 행을 꺼내 오는 마디이고 그 위로 조인·집계·정렬이 얹힌다.

### 비유
길찾기 앱. 목적지만 넣으면 지하철과 버스와 걷기를 어떤 순서로 섞을지 앱이 알아서 정하고, 출발하기 전에 그 순서를 펼쳐 볼 수 있다.

## 🖼️ 그림으로 보기

```도해
흐름: SQL 한 줄이 결과가 되기까지 무엇을 거치나
SQL :: 원하는 결과만 적혀서 들어온다
옵티마이저 :: 어떻게 풀지 고르는 쪽. 후보를 여러 개 떠올린다
비용 견적 :: 통계를 보고 후보마다 예상 비용을 잰다
계획 :: 가장 싼 하나가 계획으로 굳는다
실행기 :: 계획에 적힌 순서대로만 움직인다
< 결과 :: 행이 돌아온다
= 계획은 실행 전에 정해진다. 통계가 달라지면 같은 SQL 도 계획이 달라진다
```

## ⚠️ 해결하는 문제

```도해
대조: 계획을 DB 가 안 정해 주면 어떻게 되나
사람이 정하면 || 옵티마이저가 정하면
질의에 적는 것 :: 순서까지 적는다 || 원하는 결과만
데이터가 바뀌면 :: 질의를 다시 쓴다 || 계획을 다시 고른다
표가 셋 이상 :: 순서를 손으로 고름 || 후보를 비교한다
= SQL 이 "무엇" 만 적어도 되는 것은 "어떻게" 를 옵티마이저가 맡기 때문이다
```

같은 결과를 내는 방법은 여러 가지다. 표를 앞에서부터 훑을 수도 있고 인덱스로 자리를 좁힐 수도 있으며, 표가 셋이면 어느 것을 먼저 읽고 무엇을 붙일지도 갈린다. 이걸 질의를 쓰는 사람이 정하게 하면, 데이터가 늘거나 값이 치우칠 때마다 잘 돌던 질의를 다시 써야 한다.

옵티마이저는 그 선택을 실행 직전에 스스로 한다. MySQL 문서는 커다란 표를 다 읽지 않고도, 여러 표를 붙이면서 모든 조합을 견주지 않고도 답을 낼 수 있게 하는 여러 기법을 옵티마이저가 고려한다고 적는다. 그렇게 고른 동작 묶음이 계획이다.

## ⚙️ 작동 원리

고르는 기준은 하나다. 예상 비용이 가장 싼 계획을 잡는다. PostgreSQL 은 이 비용이 실제 시간이 아니라 임의 단위이며, 관례적으로 디스크 쪽 하나를 순서대로 읽는 값을 1.0 으로 두고 나머지를 거기에 맞춰 잡은 상대값이라고 적는다. 위 마디의 비용에는 아래 마디의 비용이 모두 포함되므로, 맨 윗줄의 숫자가 그 계획 전체의 견적이다.

견적의 재료는 통계다. 표에 행이 몇 개이고 몇 쪽을 쓰는지, 어떤 열에 어떤 값이 흔한지를 미리 모아 두고 조건에 걸릴 행 수를 거기서 어림한다.

```도해
대조: 같은 질문에 계획이 둘이면 무엇으로 고르나
전부 훑기 |=| 인덱스 타기
읽는 방식 :: 표를 앞에서부터 || 자리를 좁혀 간다
1만 중 7천 행 :: 이쪽이 싸다 || 이보다 비싸다
1만 중 100 행 :: 1만 행을 다 훑음 || 이쪽이 싸다
= 옳고 그름이 아니라 그때의 예상 비용이 싼 쪽으로 정해진다
```

PostgreSQL 문서에 나오는 만 행짜리 표가 이 대조를 그대로 보여준다. 걸리는 행이 칠천 개인 조건에서는 인덱스가 있어도 전부 훑는 계획이 나오는데, 조건을 걸어도 어차피 만 행을 다 방문하기 때문이다. 같은 표에서 걸리는 행을 백 개로 좁히면 같은 인덱스를 타는 계획으로 바뀐다.

## 💡 실제 사례

- **실행 전에 계획을 본다** — 질의 앞에 `EXPLAIN` 을 붙이면 실행하지 않고 계획만 보여준다. MySQL 문서는 이걸로 인덱스를 어디에 걸어야 할지, 조인 순서가 제대로 잡혔는지 볼 수 있다고 적는다.
- **예상과 실제를 나란히 본다** — PostgreSQL 의 `EXPLAIN ANALYZE` 는 질의를 실제로 실행해서 예상 행 수 옆에 실제 행 수와 걸린 시간을 함께 찍는다. 두 숫자가 크게 벌어지면 계획을 고른 근거부터 틀렸다는 뜻이다.
- **쓸 수 있던 인덱스와 쓴 인덱스** — MySQL 의 `EXPLAIN` 은 고를 수 있었던 인덱스를 `possible_keys` 에, 실제로 고른 것을 `key` 에 따로 적는다. 앞칸에 이름이 있는데 뒷칸이 비었으면 있는데 안 쓴 것이다.

## 🚫 흔한 오해

- **인덱스를 만들었으면 계획이 그걸 쓴다** — 고를 수 있는 인덱스와 실제로 고른 인덱스는 다른 칸이다. 조건에 걸리는 행이 표의 대부분이면 훑는 편이 싸다고 보고 안 쓴다.
- **EXPLAIN 은 질의를 돌려 본 결과다** — 돌리지 않는다. 옵티마이저가 이렇게 하겠다고 말하는 계획이고, 거기 적힌 행 수도 실제로 센 값이 아니라 통계에서 어림한 예상값이다.
- **계획에 찍힌 비용 숫자는 밀리초다** — 아니다. PostgreSQL 의 비용은 임의 단위의 상대값이라 계획끼리 견주는 데만 쓴다. 결과 값을 글자로 바꿔 클라이언트로 보내는 시간처럼, 계획을 바꿔도 달라지지 않는 것은 이 숫자에 아예 안 들어 있다.

## 🚨 주의사항

- **통계가 낡으면 계획이 어긋난다.** 행 수와 쪽 수는 실시간으로 갱신되지 않고 `ANALYZE` 나 `VACUUM` 같은 것이 돌 때 갱신된다. PostgreSQL 문서는 그래서 이 값들이 보통 얼마간 낡아 있다고 적는다.
- **`EXPLAIN ANALYZE` 는 진짜로 실행한다.** 쓰기 질의에 붙이면 그 쓰기가 그대로 일어난다. PostgreSQL 문서는 표를 건드리지 않고 보려면 트랜잭션으로 감싸고 뒤에 `ROLLBACK` 하라고 안내한다.

## 📝 정리

Query Plan 은 DB 가 이 질문을 어떻게 풀지 미리 고른 순서다. 옵티마이저가 후보를 여러 개 떠올려 통계로 예상 비용을 재고 가장 싼 하나를 고르기 때문에, 인덱스가 있어도 훑는 편이 싸면 안 쓴다. `EXPLAIN` 은 그 고른 결과를 실행 전에 펼쳐 보여준다.

- 인덱스를 만들어 뒀는데도 전부 훑는 계획이 나오는 이유는 → 흔한 오해
