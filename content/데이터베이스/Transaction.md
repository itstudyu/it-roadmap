# Transaction

## 📝 정의

Transaction(트랜잭션)은 데이터베이스에서 하나의 논리적 작업 단위를 나타냅니다. 여러 개의 SQL 명령어들을 하나의 원자적(Atomic) 단위로 묶어서 "모두 성공하거나 모두 실패"하도록 보장합니다. 트랜잭션이 없으면 중간에 실패했을 때 데이터가 불일치한 상태가 될 수 있습니다.

트랜잭션은 ACID 속성이라 불리는 4가지 특성을 만족해야 합니다. 이를 통해 데이터베이스의 안정성과 일관성을 보장합니다. 예를 들어 은행에서 A 계좌에서 출금하고 B 계좌로 입금하는 과정에서 중간에 시스템이 다운되면, 출금만 되고 입금이 안 되는 불일치 상황이 발생할 수 있습니다. 트랜잭션은 이러한 상황을 방지합니다.

> **한 줄 요약**: 하나의 작업 단위로 묶인 SQL 명령어들이 모두 성공하거나 모두 실패하는 것을 보장하는 메커니즘

### 비유
- 🔵 **은행 이체**: 100원 출금과 100원 입금이 둘 다 성공해야 완료. 하나만 성공하면 안 됨
- 🟡 **게임 아이템 거래**: A가 골드를 주고 B가 아이템을 주는데, 둘 중 하나만 일어나면 사기 상황 발생

## 🎯 핵심 개념

### 1. ACID 속성

**Atomicity (원자성)**
트랜잭션의 모든 연산이 완벽하게 수행되거나, 아무것도 실행되지 않아야 합니다. 부분적인 완료가 허용되지 않습니다.

**Consistency (일관성)**
트랜잭션 실행 전후로 데이터베이스가 일관된 상태를 유지해야 합니다. 데이터의 규칙(제약 조건)이 항상 만족되어야 합니다.

**Isolation (격리성)**
동시에 실행되는 여러 트랜잭션이 서로 간섭하지 않아야 합니다. 한 트랜잭션의 중간 상태가 다른 트랜잭션에 노출되면 안 됩니다.

**Durability (지속성)**
트랜잭션이 완료(커밋)되면, 시스템 장애가 발생해도 그 결과가 영구적으로 저장되어야 합니다.

### 2. Commit과 Rollback
- **Commit**: 트랜잭션의 모든 변경사항을 데이터베이스에 확정하고 저장
- **Rollback**: 트랜잭션 실행 중 오류가 발생하면 모든 변경사항을 원래 상태로 되돌림

### 3. 격리 수준(Isolation Levels)
동시성과 안정성의 균형을 맞추기 위해 4가지 격리 수준이 있습니다. READ UNCOMMITTED는 빠르지만 위험하고, SERIALIZABLE은 안전하지만 느립니다.

## ⚠️ 해결하는 문제

### 문제 1: 중간 실패로 인한 데이터 불일치
A 계좌에서 100원 출금 후 B 계좌 입금 중 시스템 다운 → 100원이 사라짐. 트랜잭션으로 묶으면 출금도 없었던 것으로 처리 (Rollback).

### 문제 2: Dirty Read (더티 리드)
트랜잭션1이 데이터를 수정 중이고 아직 커밋하지 않았는데, 트랜잭션2가 그 미완성된 데이터를 읽음. 나중에 트랜잭션1이 롤백되면 트랜잭션2는 존재하지 않는 데이터를 가짐.

## 🏗️ 구조


```도해
흐름: Transaction, 무슨 순서로 오가나
클라이언트 :: BEGIN TRANSACTION 이체 시작
데이터베이스 :: SELECT 잔액 1000원 확인
데이터베이스 :: UPDATE 잔액 -= 100 1000 → 900
계좌A 잔액:1000원 :: 성공
데이터베이스 :: UPDATE 잔액 += 100 500 → 600
계좌B 잔액:500원 :: 성공
데이터베이스 :: COMMIT 변경 사항 확정
데이터베이스 :: 200 OK 이체 완료
데이터베이스 :: ROLLBACK 모든 변경 취소
계좌A 잔액:1000원 :: 잔액 복원: 900 → 1000
계좌B 잔액:500원 :: 잔액 복원: 600 → 500
데이터베이스 :: 이체 실패 원래 상태 복원
```

## ⚙️ 작동 원리

트랜잭션의 작동 원리는 다음과 같습니다. 먼저 클라이언트가 BEGIN TRANSACTION (또는 START TRANSACTION) 명령으로 트랜잭션을 시작합니다.

그 이후 실행되는 모든 SQL 명령어(INSERT, UPDATE, DELETE)의 변경사항은 메모리에만 저장되고 실제 데이터베이스에는 아직 적용되지 않습니다. 이 상태를 "더티 상태(Dirty State)"라고 합니다.

모든 SQL 명령이 성공적으로 실행되면 COMMIT 명령으로 트랜잭션을 확정합니다. COMMIT하면 메모리의 변경사항이 영구 저장소(디스크)에 쓰여져 데이터베이스에 반영됩니다.

만약 중간에 에러가 발생하거나 조건을 만족하지 못하면 ROLLBACK 명령으로 트랜잭션을 취소합니다. 모든 변경사항이 폐기되고 데이터베이스는 트랜잭션 시작 전 상태로 돌아갑니다.

동시성을 위해 여러 트랜잭션이 동시 실행될 때는 Lock 메커니즘이 작동합니다. 트랜잭션이 데이터를 수정할 때 다른 트랜잭션이 접근하지 못하도록 잠금을 걸고, 트랜잭션이 끝나면 잠금을 해제합니다.

## ✅ 장단점

**장점**
- 데이터 무결성 보장 → 불일치 상황 방지
- ACID 속성으로 안정성 확보
- 문제 발생 시 자동으로 이전 상태로 복원 (Rollback)
- 동시성 문제 해결 (Lock 메커니즘)
- 금융, 의료 등 중요한 데이터에 필수

**단점**
- 성능 저하 → Lock으로 인한 대기 시간
- 복잡한 구현 → 코드 작성 어려움
- 데드락(Deadlock) 위험 → 여러 트랜잭션이 서로 기다리는 상황
- 격리 수준이 높을수록 동시성 감소
- 롱 트랜잭션(Long Transaction)은 성능 문제 유발
- 테스트가 복잡 (상태 관리, 롤백 테스트)

## 💡 실제 사례

**은행 계좌 이체**
A 계좌에서 B 계좌로 100,000원 이체할 때:
1. BEGIN TRANSACTION
2. A 계좌 출금 (잔액 -= 100,000)
3. B 계좌 입금 (잔액 += 100,000)
4. 모두 성공하면 COMMIT
5. 중간에 실패하면 ROLLBACK → 두 계좌 모두 원래 상태로

**온라인 쇼핑몰 주문 처리**
상품 구매 시:
1. BEGIN TRANSACTION
2. 재고 차감 (상품 개수 -= 1)
3. 결제 처리 (신용카드 승인)
4. 주문 정보 생성 (orders 테이블에 INSERT)
5. 모두 성공하면 COMMIT
6. 결제 실패 시 ROLLBACK → 재고 복원, 주문 미생성

**항공사 표 예약**
좌석 예약 시:
1. BEGIN TRANSACTION
2. 좌석 상태 확인 (사용 가능 여부)
3. 좌석 상태 변경 (예약됨으로 마킹)
4. 예약 정보 저장
5. 결제 완료 후 COMMIT
6. 결제 실패 시 ROLLBACK → 좌석 다시 사용 가능으로
