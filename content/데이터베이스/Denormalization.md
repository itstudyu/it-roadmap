# Denormalization (역정규화)

## 📝 정의

Denormalization 은 **읽기를 위해 중복을 일부러 되살리는** 설계다.

[[Normalization]] 을 안 한 상태가 아니라, 정규화로 사실의 제자리를 정한 다음 읽기 경로에 필요한 조각만 골라 되돌리는 것이다. 문서 저장소에서는 참조 대신 값을 문서 안에 품는 방식(임베딩)으로 나타난다.

### 비유
자주 찾는 번호를 주소록에서 매번 뒤지지 않고 냉장고 문에 한 장 더 붙여 두는 것 — 번호가 바뀌면 두 곳을 고쳐야 한다.

### 예
닉네임을 바꿨는데 예전 댓글에는 한동안 옛 이름이 그대로 남아 있는 그 어긋남이다.

## 🖼️ 그림으로 보기

```도해
대조: 같은 화면을 그리는 데 몇 번 다녀오나
가리켜 두면 |=| 베껴 두면
읽기 :: 표마다 다녀온다 || 한 번에 끝난다
쓰기 :: 한 줄만 고친다 || 베낀 곳을 다 고침
자주 바뀌면 :: 문제없다 || 갱신이 폭발한다
= 역정규화는 쓰기 일을 늘려 읽기 횟수를 사는 거래다
```

## ⚠️ 해결하는 문제

```도해
대조: 읽기가 압도적인 화면에서 정규화만 지키면 어떻게 되나
베낀 값 없이 || 조금 베껴 두면
목록 한 화면 :: 줄마다 또 조회 || 한 번으로 끝난다
왕복 횟수 :: 줄 수만큼 늘어난다 || 한 번에 고정된다
합계 값 :: 읽을 때마다 센다 || 쓸 때 세어 둔다
= 읽기가 많으면 계산과 조회를 쓰기 쪽으로 옮기는 게 남는 장사다
```

책 목록 화면에 책마다 저자 이름과 사진이 같이 나와야 한다고 하자. 참조만 들고 있으면 책 하나마다 저자 문서를 한 번 더 읽어야 해서, 목록 줄이 서른이면 왕복도 서른 번쯤으로 늘어난다. 정규화한 모델이 서버 왕복을 더 쓰게 된다는 말이 이 뜻이다.

역정규화는 그중 화면에 꼭 필요한 조각만 베껴 둔다. 저자의 이름과 썸네일만 책 문서에 같이 적어 두면 목록은 읽기 한 번으로 끝난다. 저자가 이름이나 사진을 바꾸면 그 저자의 책을 전부 고쳐야 하지만, 이름이 거의 안 바뀌는 앱이라면 받아들일 만한 거래다.

## 📊 비교: 베껴 둘까 가리킬까

| 조건 | 베껴 둔다 (역정규화) | 가리킨다 (정규화) |
|---|---|---|
| **관계** | 하나에 몇 개, 품고 있는 관계 | 하나에 여럿, 여럿에 여럿 |
| **바뀌는 빈도** | 거의 안 바뀐다 | 자주 바뀐다 |
| **자라는 크기** | 끝이 있다 | 끝없이 자랄 수 있다 |
| **읽는 방식** | 늘 같이 읽는다 | 따로도 읽는다 |

DynamoDB 문서도 같은 자리를 짚는다 — 관계형에서는 접근 패턴을 모른 채 정규화 모델을 먼저 만들어도 되지만, 여기서는 답해야 할 질문을 알기 전에 스키마를 시작하지 말고 표 수를 되도록 적게 유지하라고 못 박는다.

왼쪽 조건이 다 맞으면 대개 읽기가 빨라지고, 오른쪽 조건이 하나라도 세게 걸리면 베끼지 않는다. 특히 끝이 없는 목록을 문서에 품게 만들면 항목 크기가 한없이 커져서 전송·읽기·갱신이 다 어려워진다. 댓글은 문서 안에 최근 몇 개만 두고 나머지는 따로 두는 쪽이 낫다.

## 💡 실제 사례

- **목록에 쓰는 저자 이름** — 책 문서에 저자 이름과 썸네일만 같이 적어 두면 목록 한 화면이 읽기 한 번으로 끝난다. 저자 문서로 가는 참조는 그대로 남겨 둔다.
- **미리 세어 둔 합계** — 저자 문서에 책 권수를 적어 두고 책이 새로 실릴 때 그 값을 다시 계산한다. 읽기가 많은 쪽에서 계산을 쓰기로 옮기는 방식이다.
- **데이터 웨어하우스** — MySQL 은 역정규화를 "표를 외래 키와 조인으로 잇는 대신 데이터를 여러 표에 복제하는 전략" 으로 적고, 적재 뒤에 갱신이 없는 창고 쪽에서 주로 쓴다고 말한다.

## 🚫 흔한 오해

- **정규화가 항상 옳으니 역정규화는 잘못된 설계다** — 읽기가 압도적인 자리에서는 계산과 조회를 쓰기 쪽으로 옮기는 것이 정석에 가깝다. 관계형에서도 창고성 조회는 이 방향으로 짠다.
- **역정규화는 정규화를 안 한 상태다** — 순서가 다르다. 먼저 정규화해서 사실의 제자리를 정하고, 그중 읽기 경로에 필요한 조각만 골라 되돌리는 것이다.
- **베끼면 읽기가 빨라지니 다 베끼면 된다** — 베낀 값이 자주 바뀌면 그 값을 품은 문서를 전부 다시 써야 한다. 하루에 수백 번 바뀌는 시세를 수천 개 포트폴리오 문서에 베껴 두면 확장되지 않는다.

## 📝 정리

역정규화는 정규화를 안 한 상태가 아니라, 정규화한 설계에서 읽기 경로에 필요한 조각만 골라 되돌린 것이다. 얻는 것은 왕복 횟수와 읽기 비용이고, 내주는 것은 값이 바뀔 때 다시 써야 하는 문서의 수다. 그래서 무엇을 베낄지는 "이 값이 얼마나 자주 바뀌나" 하나로 좁혀진다.
