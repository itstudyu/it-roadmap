# Stored Procedure (저장 프로시저)

## 📝 정의

Stored Procedure는 **SQL 여러 줄을 DB 안에 이름 붙여 저장한 것**이다.

이름이 곧 구조다 — stored(저장된) procedure(절차). 절차를 앱 소스가 아니라 DB 서버 안에 저장해 두고, 클라이언트는 그 이름만 부른다. MySQL 문서는 저장 루틴을 서버에 저장해 둘 수 있는 SQL 문의 모음이라고 정의한다.

### 비유
주방 벽에 붙여둔 세트 메뉴 조리표. 손님은 이름 하나만 말하고, 재료를 하나씩 주문하지 않는다.

## 🖼️ 그림으로 보기

```도해
대조: 같은 SQL 을 앱에 두는 것과 DB 안에 두는 것은 무엇이 다른가
앱에 두면 |=| 프로시저로
SQL 이 사는 곳 :: 앱 소스 안 || DB 서버 안
부르는 법 :: 문장을 다 보냄 || 이름으로 CALL
바꿀 때 :: 앱을 다시 배포 || DB 에 적용
= SQL 을 앱에 두느냐, DB 안에 이름 붙여 두느냐의 차이다
```

## ⚠️ 해결하는 문제

```도해
대조: 같은 DB 작업을 여러 앱이 할 때 무엇이 문제가 되나
프로시저 없이 || 프로시저로
로직 위치 :: 앱마다 따로 || 서버에 한 벌
오가는 양 :: 문장을 다 보냄 || 이름만 보냄
권한 :: 테이블을 열어줌 || 실행만 허용
= 여러 앱이 같은 일을 한다면, 그 일을 DB 쪽에 한 벌만 둘 수 있다
```

자바로 만든 배치와 파이썬으로 만든 관리 도구가 같은 정산 절차를 쓴다면, 그 절차는 두 곳에 각각 구현된다. 한쪽만 고치면 두 앱의 계산이 갈라진다. MySQL 문서가 프로시저를 권하는 상황 하나가 바로 이것이다 — 여러 언어로 만들었거나 서로 다른 플랫폼에서 도는 클라이언트들이 같은 DB 작업을 해야 할 때.

권한도 같이 정리된다. 앱에 테이블 접근을 아예 주지 않고 정해진 프로시저만 실행하게 하면, 앱이 할 수 있는 일이 그 목록으로 한정된다. MySQL 문서는 은행이 이런 식으로 모든 공통 작업을 프로시저로 둔다고 예로 든다.

## ⚙️ 작동 원리

프로시저는 함수와 한 짝이고, 둘을 합쳐 루틴(routine)이라 부른다. 헷갈리는 자리는 셋이다.

| | 프로시저 | 함수 |
|---|---|---|
| 반환값 | 없다. 출력 인자로 준다 | 있다. `RETURNS` 를 쓴다 |
| 부르는 법 | `CALL` 로 따로 부른다 | 쿼리 안에서 불린다 |
| 커밋·롤백 | 실행 중에 할 수 있다 | 못 한다 |

PostgreSQL 문서가 이 셋을 프로시저와 함수의 차이로 명시한다. 실행 중에 커밋할 수 있다는 것이 프로시저의 진짜 무기다 — 커밋한 뒤에는 새 트랜잭션이 자동으로 시작된다. 다만 조건이 붙는다. `CALL` 이 명시적 트랜잭션 블록 안에 있으면 못 하고, `SECURITY DEFINER` 나 `SET` 절이 붙은 프로시저도 못 한다.

## 💡 실제 사례

- **여러 언어로 만든 클라이언트** — 자바 앱과 파이썬 앱이 같은 정산 절차를 각자 구현하는 대신, 프로시저 하나를 양쪽에서 `CALL` 한다.
- **테이블 권한을 닫기** — 앱 계정에 테이블 권한을 주지 않고 지정된 프로시저 실행 권한만 준다. 할 수 있는 일이 그 목록으로 좁혀진다.
- **오가는 정보 줄이기** — 문장을 매번 다 보내는 대신 이름 하나를 보낸다. 서버와 클라이언트 사이에 오갈 정보가 그만큼 적어진다.

## 🚫 흔한 오해

- **로직은 DB 안에 두는 게 항상 낫다** — 클라이언트가 하던 일이 서버로 옮겨오는 것이라 DB 서버 부하가 그만큼 늘어난다. MySQL 문서도 이걸 대가로 적어 뒀다.
- **프로시저로 옮기면 SQL 이 빨라진다** — 줄어드는 것은 서버와 클라이언트 사이에 오가는 정보량이다. 같은 SQL 은 여전히 같은 DB 가 실행한다.
- **프로시저는 함수와 같은 것이다** — 프로시저는 반환값이 없고 `CALL` 로 따로 부른다. 대신 실행 중에 커밋·롤백을 할 수 있는데, 함수는 그걸 못 한다.

## 🚨 주의사항

- **정의가 서버 안에 산다.** 프로시저는 DB 서버에 저장되는 것이라, 앱 소스를 이전 버전으로 되돌려도 서버의 프로시저는 새것이 그대로 남아 있다. 앱 배포와 프로시저 적용을 따로 챙겨야 한다.
- **커밋 권한을 미리 확인한다.** `SECURITY DEFINER` 로 만들거나 `SET` 절을 붙이면 그 프로시저는 `COMMIT`·`ROLLBACK` 을 실행할 수 없다. 트랜잭션을 쪼갤 생각으로 프로시저를 골랐다면 이 조건에 걸린다.

## 📝 정리

Stored Procedure 는 여러 SQL 문을 DB 서버에 이름 붙여 저장해 두고 `CALL` 로 부르는 것이다. 오가는 정보가 줄고 테이블 권한을 닫을 수 있는 대신, 그 일과 그 코드가 DB 서버 쪽으로 옮겨간다. 여러 앱이 같은 절차를 써야 할 때 가장 잘 맞는다.

## ❓ 이해했는지

- 자바 앱과 파이썬 앱이 같은 정산 절차를 각자 구현하고 있다. 프로시저는 이걸 어떻게 바꾸나 → 실제 사례
- 프로시저로 옮겼는데 DB 서버 부하가 오히려 올라갔다면 왜인가 → 흔한 오해
- 앱을 이전 버전으로 되돌렸는데도 잘못된 계산이 계속되는 일은 왜 생기나 → 주의사항
