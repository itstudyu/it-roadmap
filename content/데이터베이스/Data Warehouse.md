# Data Warehouse (데이터 웨어하우스)

## 📝 정의

데이터 웨어하우스는 **여러 시스템의 데이터를 분석용으로 모아 정리해 둔 저장소**다.

판매 시스템, 재고 시스템, 회계 시스템은 저마다 자기 형식으로 데이터를 쌓는다. 웨어하우스는 그것들을 공통 형식으로 맞춰 한곳에 모으고 오래 보관해서, 과거까지 훑는 보고서를 만들 수 있게 한다.

### 비유
여러 농장에서 온 채소를 씻고 다듬어 종류별로 진열해 둔 매대. 고를 때는 바구니에 담기만 하면 된다.

## 🖼️ 그림으로 보기

```도해
흐름: 판매·재고·회계 데이터가 보고서 한 장이 되기까지 무엇을 거치나
소스 시스템 :: 판매·재고·회계가 저마다 다른 형식으로 쌓인다
ETL :: 공통 형식으로 맞추고 걸러 낸다
웨어하우스 :: 표로 담아 오래 보관한다
분석 도구 :: SQL 로 집계를 묻는다
< 웨어하우스 :: 쌓인 표를 훑어 결과를 돌려준다
= 흩어진 것을 먼저 모아 정리해 두는 곳이다. 묻는 일은 그다음이다
```

## ⚠️ 해결하는 문제

```도해
대조: 데이터를 시스템마다 그대로 두면 무엇이 어려워지나
그대로 두면 || 웨어하우스로
데이터 위치 :: 시스템마다 흩어짐 || 한곳에 모임
보고서 만들기 :: 시스템마다 물어야 || SQL 한 번으로
집계 쿼리 :: 서비스를 밀어냄 || 분석 자리에서 함
= 흩어진 것을 모아 두면 묻는 일이 한 번으로 줄어든다
```

시스템마다 같은 것을 다르게 적는다. 한쪽은 고객을 이메일로, 다른 쪽은 사번으로 센다. 이 상태에서 "이번 달 매출"을 구하려면 사람이 세 군데에 각각 묻고 손으로 맞춰야 하고, 맞추는 방식이 사람마다 달라 숫자가 어긋난다.

운영 중인 서비스의 데이터베이스에 직접 집계를 돌리는 것도 문제다. 읽기·쓰기와 분석이 같은 자원을 나눠 쓰면 서로 부딪치고 쿼리가 느려진다. 웨어하우스는 데이터를 **공통 형식으로 맞춰 옮겨 둔 다음 분석은 그쪽에서만** 하게 해서 이 둘을 함께 푼다.

## ⚙️ 작동 원리

웨어하우스는 **담을 때** 정리한다. 여러 곳에서 온 값을 공통 형식으로 맞춰 넣기 때문에, 꺼낼 때는 형식을 다시 맞출 일이 없다. 이 성질 때문에 정해진 질문에 빠르게 답하는 대신, 형식이 정해지지 않은 데이터는 애초에 담기 어렵다.

저장 방식도 분석에 맞춰져 있다. BigQuery는 분석 쿼리에 최적화된 **열 단위 저장 형식**으로 데이터를 둔다. 한 행을 통째로 꺼내는 일보다 한 열을 통째로 훑는 일이 잦다는 전제다.

요즘 웨어하우스는 **저장과 계산을 떼어 놓는다.** BigQuery는 데이터를 담는 층과 계산하는 층이 따로 있어서, 한쪽이 자원을 늘려도 다른 쪽의 성능과 가용성에 영향을 주지 않는다. Redshift도 데이터를 별도의 저장 계층에 두고 계산과 저장을 따로 늘리고 따로 지불한다. 저장은 페타바이트 자리까지 늘어난다 — 1테라바이트 디스크 천 개 몫이다.

## 📊 비교: 운영 DB 와 웨어하우스

| | 운영 DB | 데이터 웨어하우스 |
|---|---|---|
| 주로 하는 일 | 한 건 넣고 고치기 | 크게 훑어 집계하기 |
| 담는 범위 | 지금 돌아가는 값 | 오래 쌓인 값까지 |
| 데이터 출처 | 그 서비스 하나 | 여러 시스템을 모은다 |
| 자원 | 거래와 분석이 나눠 쓴다 | 분석에만 쓴다 |
| 잘 맞는 질문 | "이 주문 지금 어떻게 됐나" | "작년 이맘때보다 늘었나" |

Redshift는 관계형 데이터베이스라서 한 건을 넣고 지우는 일도 되지만, 아주 큰 데이터를 분석하고 보고하는 쪽에 맞춰져 있다. 큰 표 여럿을 조인하는 복잡한 쿼리에서 특히 잘 돈다.

## 💡 실제 사례

- **월 마감 보고서** — 판매·재고·회계에 각각 물어보는 대신, 웨어하우스에 쌓인 표에 SQL 한 번을 던져 만든다.
- **몇 년치 추세 보기** — 운영 DB 에서 이미 지운 옛 주문도 웨어하우스에는 남아 있어 작년과 올해를 나란히 놓고 본다.
- **BI 도구 연결** — 대시보드 도구를 웨어하우스에 붙여 두면 사람마다 SQL 을 짜지 않아도 같은 숫자를 본다.

## 🚫 흔한 오해

- **웨어하우스는 그냥 큰 DB 다** — 크기가 아니라 쓰임이 다르다. 여러 시스템의 값을 공통 형식으로 모아 크게 훑는 쪽에 맞춰져 있고, 주문 한 건을 넣고 잔액 한 줄을 고치는 잦은 거래는 운영 DB 몫이다.
- **분석할 데이터는 웨어하우스에 넣는 게 항상 낫다** — 담기 전에 공통 형식으로 맞추는 단계를 통과해야 한다. 형식이 정해지지 않은 로그나 이미지는 그 단계에서 막히고, 그런 데이터는 원본으로 쌓아 두는 편이 낫다.
- **웨어하우스에 담기만 하면 분석이 된다** — 담는 것과 맞추는 것은 다른 일이다. 시스템마다 다른 모양으로 들어온 "고객"을 하나로 맞추지 않으면 집계한 숫자가 서로 어긋난다.

## 📝 정리

데이터 웨어하우스는 여러 시스템의 데이터를 공통 형식으로 맞춰 모아 두고 크게 훑어 집계하는 저장소다. 담을 때 정리해 두기 때문에 꺼낼 때가 빠르고, 그 정리하는 일이 [[ETL]] 이다. 정리를 미루고 원본부터 쌓는 반대쪽 선택이 [[Data Lake]] 다.

## ❓ 이해했는지

- 판매·재고·회계를 각 시스템에 그대로 두고 매출을 구하면 무엇이 어긋나나 → 해결하는 문제
- 주문 한 건을 넣고 잔액을 고치는 일을 웨어하우스에 맡기지 않는 이유는 → 비교
- 분석 쿼리 하나가 서비스 응답을 느리게 만드는 일이 웨어하우스에서는 왜 덜 생기나 → 작동 원리
