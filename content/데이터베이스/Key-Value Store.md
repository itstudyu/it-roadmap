# Key-Value Store (키-값 저장소)

## 📝 정의

Key-Value Store는 **열쇠 하나로 값 하나를 꺼내는 저장소**다.

값이 무엇인지는 저장소가 들여다보지 않는다. Redis 문서는 값을 글과 직렬화한 객체와 이진 데이터까지 담는 바이트 열이라고 적어두고, 크기 상한만 정해 둔다. 열쇠를 알면 그 바이트를 그대로 내주고, 열쇠를 모르면 내줄 방법이 없다.

### 이름
Key :: 값을 여는 열쇠
Value :: 열쇠에 매단 것
Store :: 넣어 두는 곳
= 붙여 읽으면 "열쇠에 값을 매달아 두는 곳". 열쇠가 없으면 열 길이 없다

### 비유
우편함. 호수를 알면 곧장 그 함을 열지만, 안에 무엇이 들었는지로는 찾을 수 없다.

### 예
짧게 줄인 주소를 누르는 순간 원래 긴 주소로 곧장 넘어가는 그 자리다.

## 🖼️ 그림으로 보기

```도해
흐름: 열쇠 하나를 대면 값이 어떻게 나오나
프로그램 :: `user:42` 라는 열쇠를 댄다
저장소 :: 그 열쇠를 해시해 어느 칸인지 셈한다
저장소 :: 그 칸에 매달린 값 하나를 집는다
< 프로그램 :: 담아둔 바이트를 그대로 받는다
= 열쇠를 알면 한 번에 값 하나다. 열쇠를 모르면 찾을 길이 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 값 하나를 꺼낼 때 표 구조는 무엇을 더 하나
표에 담으면 |=| 열쇠에 담으면
찾는 방법 :: 조건을 해석한다 || 열쇠로 바로 집는다
값의 모양 :: 열을 미리 정한다 || 바이트면 다 된다
읽는 비용 :: 인덱스가 있어야 || 늘어도 O(1)
= 조건을 걸 능력을 내주고, 값 하나에 곧장 닿는 길을 산다
```

로그인 세션이나 화면에 붙일 조회 결과처럼, 무엇을 꺼낼지 이미 열쇠로 정해져 있는 값이 있다. 이런 값에까지 조건을 해석하고 어느 인덱스를 쓸지 고르는 일을 시키면, 하지 않아도 되는 일을 요청마다 반복하는 셈이 된다.

열쇠-값 저장소는 그 중간 과정을 아예 없앤다. 물어볼 수 있는 것이 "이 열쇠의 값" 하나뿐이라서, 담긴 값이 열 개일 때와 백만 개일 때 꺼내는 비용이 같다. Redis 의 `SET` 과 `GET` 이 O(1) 인 것도 이 때문이다.

## ⚙️ 작동 원리

열쇠가 곧 주소다. DynamoDB 는 파티션 열쇠 값을 내부 해시 함수에 넣고, 그 결과로 이 항목을 어느 파티션에 둘지 정한다. 그래서 서버를 여러 대로 나눠도 열쇠만 있으면 어디에 있는지 계산으로 바로 나온다. 파티션 열쇠만 있는 표에서는 같은 열쇠 값을 가진 항목이 둘일 수 없다 — 열쇠 하나에 값 하나라는 말이 여기서 지켜진다.

범위는 공짜로 따라오지 않는다. DynamoDB 의 `Query` 는 파티션 열쇠 이름과 값 하나를 반드시 받아야 시작하고, 정렬 열쇠를 따로 둔 표에서만 비교 연산자로 결과를 좁혀준다. 열쇠 전체를 훑는 쪽은 값이 다르다 — Redis 의 `KEYS` 는 그 데이터베이스의 열쇠 수에 비례해서 커진다.

## 💡 실제 사례

- **세션 보관** — 세션 id 를 열쇠로 삼으면 요청이 어느 서버로 가도 같은 값을 꺼낸다.
- **조회 캐시** — 자주 읽는 결과를 열쇠에 담고 살 시간을 함께 건다. Redis 의 `SETEX` 가 값과 만료 시간을 한 번에 정한다.
- **횟수 세기** — `INCR` 로 열쇠 하나의 숫자를 올린다. 여러 클라이언트가 같은 열쇠에 동시에 보내도 값이 어긋나지 않는다.

## 🚫 흔한 오해

- **열쇠-값이니 값으로도 찾을 수 있다** — 값은 조건을 걸 대상이 아니다. 열쇠를 훑는 `KEYS` 는 열쇠 수에 비례하고, Redis 문서도 디버깅용이라며 실제 코드에 쓰지 말라고 못 박는다.
- **범위로 물으면 알아서 골라준다** — 물어볼 수 있는 것은 열쇠 하나다. DynamoDB 도 파티션 열쇠 값을 정확히 하나 받은 다음에야, 정렬 열쇠를 둔 표에서 범위를 좁혀준다.
- **빠르니까 다 여기에 담으면 된다** — 조건으로 여러 건을 고르거나 두 종류를 이어 붙이는 일은 표와 쿼리 쪽이 짧다. 열쇠가 이미 정해진 값을 꺼낼 때만 이 저장소가 이긴다.

## 🚨 주의사항

- **열쇠 이름 규칙을 먼저 정한다.** 값으로는 찾을 수 없으니 열쇠만 보고 무엇이 들었는지 알아야 한다. Redis 문서의 예제도 `bike:1` 처럼 갈래와 번호를 콜론으로 나눠 적는다.
- **값을 한없이 키우지 않는다.** Redis 문자열 하나는 기본 512MB 까지이고, 값의 일부만 잘라 읽는 `GETRANGE` 는 읽는 길이에 비례해 비싸진다.

## 📝 정리

**"호수를 알아야 열리는 그 우편함"** 이라고 읽으면 된다. 조건 검색과 이어 붙이기를 포기한 대가로, 값 하나를 꺼내는 비용이 데이터가 늘어도 그대로다. 그래서 열쇠를 어떻게 지을지가 이 저장소 설계의 대부분이다.

## 🧒 열 살에게

우편함은 몇 호인지만 알면 곧장 그 칸을 열지? 대신 안에 무엇이 들었는지로는 찾을 수가 없어. 그래서 칸마다 이름을 어떻게 붙여 둘지가 제일 중요해.

## ❓ 이해했는지

- 값이 백만 개로 늘어도 열쇠로 꺼내는 시간이 비슷한 이유는 → 작동 원리
- 값에 든 이메일로 회원을 찾아야 한다면 이 저장소에서 무엇을 하게 되나 → 흔한 오해
- 열쇠 이름을 번호만으로 지어두면 나중에 무엇이 곤란해지나 → 주의사항
