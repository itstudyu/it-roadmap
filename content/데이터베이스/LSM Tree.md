# LSM Tree (엘에스엠 트리)

## 📝 정의

LSM Tree 는 **쓰기를 모아 두었다가 통째로 내려쓰는 저장 구조**다.

값을 고칠 때 제자리를 찾아가 덮어쓰지 않는다. 고침도 지움도 전부 "새 줄" 로 뒤에 이어 적고, 그 줄이 메모리에 얼마쯤 쌓이면 파일 한 장으로 한 번에 내린다. 한 번 내려쓴 파일은 다시 고치지 않는다. 대신 같은 열쇠가 여러 파일에 흩어지므로, 뒤에서 파일들을 합쳐 낡은 판을 버리는 일이 계속 돈다. Cassandra 문서는 자기 저장 엔진을 "B 트리를 쓰는 전통적 설계 대신 덧붙이기만 하는 방식" 이라고 적는다.

### 이름
Log :: 적어 나가는 기록
Structured :: 그 꼴로 짜인
Merge :: 합치기
Tree :: 층층이 쌓인 구조
= 붙여 읽으면 "적어 나간 것을 나중에 합치는 층층 구조". 이름이 곧 저장 방식이다

### 비유
책상 위 메모지. 틀린 곳을 지우개로 지우는 대신 새 메모를 위에 얹어 두다가, 쌓이면 한꺼번에 깨끗한 공책으로 옮겨 적는다.

### 예
쓰기가 초당 수만 건씩 밀려드는 기록 적재에서, 넣는 속도는 멀쩡한데 오래된 값을 한 건 찾는 게 유독 느린 그 느낌이다.

## 🖼️ 그림으로 보기

```도해
흐름: 새로 쓴 값이 디스크에 자리 잡기까지 무엇을 거치나
덧붙이기 :: 고침도 지움도 새 줄로 뒤에 적는다
메모리 표 :: 그 줄을 메모리에 정렬해 모아 둔다
내려쓰기 :: 가득 차면 통째로 파일 한 장으로 내린다
파일 :: 한 번 쓴 파일은 다시 고치지 않는다
합치기 :: 쌓인 파일을 뒤에서 합쳐 낡은 판을 버린다
= 제자리를 찾아 고치는 대신, 뒤에 적고 나중에 합친다
```

## ⚠️ 해결하는 문제

```도해
대조: 쓰기가 쏟아질 때 제자리를 찾아 고치면 왜 느린가
제자리를 고치면 || 뒤에 이어 적으면
한 건 쓰기 :: 자리를 찾아가 고침 || 끝에 붙이면 끝
쏟아질 때 :: 자리 찾기에 묶임 || 몰아서 한 번에 씀
지움 :: 그 자리까지 찾아감 || 표시만 뒤에 적음
= 쓰기를 순차로 바꾸는 대신, 읽기와 뒤처리에 일을 넘긴다
```

들어오는 것이 멈추지 않는 곳에서는 쓰기 한 건의 비용이 전부를 정한다. 제자리를 찾아 고치는 구조는 값 하나를 바꿀 때마다 그 값이 있는 자리를 찾아가야 하고, 그 자리는 디스크 위에 흩어져 있다. 쓰기가 초당 수만 건이면 대부분의 시간이 자리를 찾는 데 쓰인다.

덧붙이기는 그 찾기를 통째로 없앤다. 어디에 적을지 고민하지 않고 끝에 이어 붙이면 되고, 실제 디스크 쓰기는 메모리에 모아 뒀다가 한 번에 나간다. 대신 값 하나가 여러 파일에 흩어지므로, 읽을 때는 여러 곳을 봐야 하고 뒤에서는 계속 합쳐야 한다. Cassandra 문서는 이 합치기를 "여러 작은 파일을 읽어 합치고 갱신·삭제를 처리해 새 파일로 다시 쓰는" 일이라 적고, 그 때문에 쓰기 증폭이 생긴다고 밝힌다. 앞에서 아낀 것을 뒤에서 조금씩 갚는 셈이다.

## ⚙️ 작동 원리

읽기는 위에서부터 훑어 내려간다.

```도해
층: 값 하나를 읽을 때 어디부터 찾나
메모리 표 :: 방금 쓴 것. 여기서 끝나면 디스크를 안 본다
새 파일 :: 최근에 내려쓴 것. 걸러내기로 대부분 건너뛴다
오래된 파일 :: 합치기를 여러 번 거친 것. 여기까지 오면 느리다
= 같은 열쇠가 여러 층에 있으면 가장 나중에 적힌 판이 답이다
```

파일이 여러 장이면 없는 열쇠를 찾을 때가 가장 억울하다. 그래서 파일마다 작은 걸러내기 표를 함께 둔다. Cassandra 는 한 파일 묶음을 `Data.db`(내용) · `Index.db`(열쇠 위치) · `Filter.db`(걸러내기) · `Summary.db`(색인 간추림) 같은 여러 파일로 나눠 두는데, 이 중 `Filter.db` 가 [[Bloom Filter]] 다. "이 파일에는 없다" 는 답을 디스크를 안 열고 얻는 자리다.

멈춤에 대비하는 것은 기록장이 맡는다. 메모리 표는 전원이 나가면 사라지므로, 쓰기는 먼저 덧붙이기 전용 기록에 적힌다. Cassandra 문서는 이걸 "쓰기가 일어나면 로컬 디스크의 덧붙이기 전용 커밋 로그에 먼저 기록한다" 고 적고, 다시 켜질 때 그 기록을 메모리 표로 되돌린다. 같은 얼개를 Bigtable 도 쓴다 — 구글 문서는 쓰기가 승인되는 즉시 공유 로그에 저장된다고 적고, 삭제된 항목을 실제로 걷어내는 일은 압축(compaction)이 주기적으로 한다고 밝힌다.

## 💡 실제 사례

- **사건 기록 적재** — 사용자 행동이나 장비 측정값처럼 끝없이 밀려드는 쓰기를 받는 자리. 넣는 쪽 비용이 일정해야 밀리지 않는다.
- **늦게 도착한 갱신** — 순서가 뒤엉켜 들어와도 쓰기는 늘 뒤에 붙는다. 어느 판이 이기는지는 적힌 시각이 정하고, 합치기가 나머지를 버린다.
- **지움이 잦은 표** — 지움도 표시 한 줄이라 쓰기가 싸다. 대신 그 표시가 걷힐 때까지 읽기가 그것까지 훑는다.

## 🚫 흔한 오해

- **덧붙이기만 하니까 파일이 계속 커지기만 한다** — 아니다. 합치기가 뒤에서 같은 열쇠의 낡은 판과 지움 표시를 걷어내며 새 파일로 다시 쓴다.
- **쓰기가 빠르니까 어디에나 쓰면 된다** — 한 건 조회와 범위 조회가 주된 일이면 제자리를 지키는 [[B-Tree]] 쪽이 대개 낫다. 얻은 것은 쓰기 속도이고 내준 것은 읽기 경로다.
- **지웠으면 디스크에서 바로 없어진다** — 지움도 새 줄이다. 표시가 남았다가 합치기가 지나갈 때에야 실제로 사라진다.

## 🚨 주의사항

합치기는 공짜가 아니다. 같은 내용을 여러 번 다시 쓰는 일이라 디스크 쓰기량과 대역폭을 계속 먹고, 밀리면 파일 장수가 늘어 읽기가 함께 느려진다. 넣는 속도만 보고 용량을 잡으면 뒤처리가 돌 여유가 없어 어느 순간 읽기가 무너진다.

걷어내기가 언제 도는지도 알아 두는 편이 낫다. Bigtable 문서는 압축이 끝나 삭제 같은 작업이 실제로 반영되기까지 평균 일주일이 걸린다고 적는다. "지웠다" 와 "디스크에서 사라졌다" 사이의 간격이 생각보다 길다.

## 📝 정리

**"고칠 자리를 찾지 않고 뒤에 적어 두는 구조"** 라고 읽으면 된다. 쓰기를 순차로 바꿔 넣는 쪽을 싸게 만드는 대신, 같은 열쇠가 여러 파일에 흩어져 읽기와 합치기에 빚을 진다. 그 빚을 걸러내기와 합치기가 갚고 있으니, 이 구조를 쓸 때 봐야 할 것은 넣는 속도가 아니라 합치기가 밀리지 않는지다.

## 🧒 열 살에게

숙제하다 틀린 데를 지우개로 지우고 다시 쓰면 오래 걸리지? 그래서 새로 쓴 쪽지를 계속 위에 얹어 두다가, 쌓이면 한꺼번에 깨끗한 공책에 옮겨 적는 거야. 대신 뭘 찾을 때는 맨 위 쪽지부터 차례로 뒤져야 해.

## ❓ 이해했는지

- 쓰기가 초당 수만 건일 때 제자리를 고치는 방식이 먼저 무너지는 이유는 무엇인가 → 해결하는 문제
- 없는 열쇠를 물었을 때 디스크를 거의 안 여는 장치는 무엇인가 → 작동 원리
- 넣는 속도는 그대로인데 조회가 점점 느려진다면 무엇이 밀린 것인가 → 주의사항
