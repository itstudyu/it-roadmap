# Transparent Data Encryption (저장할 때 통째로 잠그기)

## 📝 정의

TDE 는 **앱을 안 고치고 저장된 파일을 통째로 잠그는 기능**이다.

값 하나하나를 골라 잠그는 방식은 앱을 고쳐야 하고, 어디를 빠뜨렸는지 아무도 모른다. TDE 는 반대로 간다 — 페이지가 디스크로 내려가기 직전에 잠그고 올라올 때 푼다. 그래서 잠그는 범위가 "이 DB 파일 전부" 로 단순해지고, 앱은 자기가 잠긴 DB 를 쓰고 있다는 사실조차 모른다. 이름의 "투명" 이 가리키는 것이 그 무지다.

### 이름
Transparent :: 앱이 못 느끼는
Data :: 담긴 내용
Encryption :: 잠가 두기
= 붙여 읽으면 "앱이 못 느끼게 내용을 잠가 두기". 투명하다는 말은 안전하다가 아니라 앱이 모른다는 뜻이다

### 비유
사무실 서류함 자물쇠. 열쇠를 받고 방에 들어온 사람에게는 아무것도 달라지지 않지만, 서류함째 들고 나간 사람에게는 종이 뭉치가 낙서로 보인다.

### 예
관리형 DB 를 새로 만들 때 "저장 시 암호화" 가 이미 켜진 채로 놓여 있던 그 체크 상자다.

## 🖼️ 그림으로 보기

```도해
층: 어디까지 잠기고 어디부터 안 잠기나
앱과 질의 :: 아무것도 안 바뀐다. 평문 그대로 보인다
메모리 :: 읽어 올린 페이지는 풀린 상태로 놓인다
디스크 파일 :: 페이지를 내려쓰기 직전에 잠근다
백업과 로그 :: 같은 열쇠로 함께 잠겨 밖으로 나간다
= 잠기는 것은 놓여 있는 것뿐이다. 도는 것과 묻는 것은 그대로다
```

## ⚠️ 해결하는 문제

```도해
대조: 저장된 파일이 그대로 놓여 있으면 무엇이 위험한가
안 잠그면 || 잠가 두면
디스크 반출 :: 파일째 읽힌다 || 낙서만 나온다
백업 유출 :: 그대로 열린다 || 열쇠가 있어야
규정 대응 :: 못 맞춘다 || 요건을 맞춘다
= 겨누는 것은 훔쳐 간 파일이다. 로그인해 들어온 사람이 아니다
```

DB 는 결국 디스크 위의 파일이다. 접근 권한을 아무리 촘촘히 짜도 그 파일 자체가 밖으로 나가면 권한은 따라가지 않는다. 고장 난 디스크를 반납할 때, 백업을 다른 곳에 보관할 때, 스냅숏을 다른 계정으로 복사할 때 — 파일은 DB 를 떠나 혼자 놓인다. Azure 문서가 TDE 의 겨냥 대상을 "악의적인 오프라인 활동" 이라고 적는 이유가 여기 있다.

값마다 골라 잠그는 방식으로 이 구멍을 막으려면 앱을 고쳐야 하고, 새 칸이 늘 때마다 다시 고쳐야 하고, 어디를 빠뜨렸는지 확인할 방법이 없다. TDE 는 고르는 일을 없앤다. 파일 전체가 대상이고 백업과 트랜잭션 로그도 같은 열쇠로 함께 잠기므로, "무엇이 잠겼나" 를 세지 않아도 된다. 대신 잠기는 자리도 디스크 경계 한 곳으로 못 박힌다.

## ⚙️ 작동 원리

```도해
흐름: 한 페이지가 디스크를 오갈 때 무엇이 일어나나
DB 시동 :: 잠겨 있던 속열쇠를 보호자로 푼다
읽기 :: 디스크에서 올린 페이지를 푼다
메모리 :: 풀린 페이지 위에서 질의가 돈다
쓰기 :: 디스크로 내려가기 직전에 다시 잠근다
백업 :: 백업과 로그도 같은 속열쇠로 잠긴 채 나간다
= 잠그고 푸는 자리는 디스크 경계 한 곳뿐이다
```

열쇠는 두 층이다. 실제로 내용을 잠그는 것은 DB 마다 하나씩 있는 대칭 키(DEK)이고, 그 키 자체는 **보호자**(TDE protector)가 잠가 둔다. DB 가 뜰 때 보호자로 DEK 를 풀고, 그다음부터는 엔진 안에서 그 DEK 로 페이지를 풀고 잠근다. AWS 문서도 RDS for SQL Server 의 구조를 같은 두 층으로 적는다 — 마스터 키에서 만든 인증서가 데이터 암호화 키를 보호하고, 실제 암복호는 데이터 암호화 키가 한다.

갈리는 것은 그 보호자를 누가 쥐느냐다. 기본값은 서비스가 쥔다. Azure 는 서버마다 다른 내장 인증서를 만들어 AES 256(CBC) 로 잠그고, 그 인증서를 해마다 자동으로 갈아 끼운다. 지리적 복제나 복원 때 열쇠를 따라 옮기는 일도 서비스가 한다. 켜는 사람이 할 일이 없다시피 하고, 그래서 새로 만든 Azure SQL Database 는 기본으로 켜진 채 나온다.

내가 쥐는 쪽이 BYOK 다. 보호자를 내 키 자격 증명 모음이나 관리형 HSM 안의 비대칭 키로 바꾸면 그 키는 모음 밖으로 나오지 않고, 회전·권한·백업·감사 기록을 내가 들게 된다. 열쇠를 다루는 사람과 데이터를 다루는 사람을 갈라 놓을 수 있다는 것이 이 방식의 값이다. 같은 문장이 위험이기도 하다 — 서버의 모음 권한이 회수되면 그 DB 는 접근할 수 없게 되고, 데이터는 잠긴 채로 남는다.

## 💡 실제 사례

- **관리형 DB 를 새로 만들 때** — 새 Azure SQL Database 는 기본으로 켜져 나온다. 켜는 일이 아니라 예전에 만든 DB 가 꺼져 있지 않은지 확인하는 일이 남는다.
- **파일을 바깥에 건네야 할 때** — 데이터 파일과 백업을 제삼자에게 넘기는 상황이 AWS 문서가 든 대표 용례다. 파일은 나가도 내용은 안 나간다.
- **열쇠를 내가 쥐어야 할 때** — 회전 주기와 감사 기록을 직접 증명해야 하는 규정이 걸리면 보호자를 내 키 자격 증명 모음의 키로 바꾼다.

## 🚫 흔한 오해

- **TDE 를 켜 뒀으니 데이터가 안전하다** — 로그인해서 조회하는 사람에게는 아무것도 안 가려진다. Azure 문서가 적는 겨냥 대상은 "악의적인 오프라인 활동" 이고, 그건 파일을 들고 나간 쪽을 말한다.
- **투명하다니까 공짜라는 뜻이다** — 투명은 앱 코드를 안 고쳐도 된다는 뜻일 뿐이다. AWS 문서는 TDE 가 성능에 영향을 줄 수 있고 같은 인스턴스에 잠긴 DB 가 하나라도 있으면 안 잠근 DB 까지 느려질 수 있으니 인스턴스를 나누라고 권한다.
- **내 열쇠로 바꾸면 언제나 더 안전하다** — 열쇠를 쥐면 잃을 수도 있다. Azure 문서는 서버의 키 자격 증명 모음 권한이 회수되면 그 DB 에 접근할 수 없게 되고 모든 데이터가 잠긴 채로 남는다고 적는다. 회전과 백업을 감당할 조직이 아니면 서비스가 쥐는 쪽이 낫다.

## 🚨 주의사항

- **내보내기는 잠금 밖이다.** Azure 문서는 TDE 로 보호된 DB 를 BACPAC 파일로 내보내면 내보낸 내용은 암호화되지 않는다고 적는다. 파일이 나가는 경로마다 따로 확인해야 한다.
- **시스템 DB 는 대상이 아니다.** `master` 같은 시스템 DB 는 잠글 수 없다. 민감한 값을 거기 두면 잠금 밖에 두는 셈이다.
- **백업만으로는 못 연다.** 잠긴 DB 를 다른 인스턴스로 되살리려면 그 인증서를 먼저 들여와야 한다. 열쇠 백업을 안 챙기면 백업은 있는데 못 여는 상태가 된다.

## 📝 정리

**"놓여 있는 것만 통째로 잠그는 자물쇠"** 라고 읽으면 된다. 페이지가 디스크로 내려가기 직전에 잠기고 올라올 때 풀리므로 앱은 한 줄도 안 고쳐도 되고, 백업과 로그까지 같은 열쇠로 함께 잠긴다. 대신 로그인해 들어온 사람 앞에서는 아무것도 안 가려지니, 이건 접근 통제가 아니라 파일 도난 대비로 세어야 한다.

## 🧒 열 살에게

학교 사물함에 자물쇠를 채워 두면 누가 사물함을 통째로 떼어 가도 안에 든 걸 못 봐. 그런데 네가 열쇠로 열어서 친구한테 보여 주면 친구는 다 볼 수 있지. 이 자물쇠는 들고 가는 사람만 막지, 네가 열어 준 사람은 못 막아.

## ❓ 이해했는지

- 잠긴 백업만 챙겨 두면 왜 복원이 안 될 수 있나 → 주의사항
