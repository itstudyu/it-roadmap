# 인덱스 (Database Index)

## 📝 정의

데이터베이스 인덱스(Index)는 **데이터베이스 테이블의 검색 속도를 획기적으로 향상시키기 위해 특정 컬럼의 데이터를 별도로 정렬하여 저장하는 자료구조**입니다. 책의 색인(Index)처럼, 데이터베이스 인덱스도 원하는 정보를 빠르게 찾을 수 있게 해줍니다. 인덱스가 없으면 데이터베이스는 원하는 데이터를 찾기 위해 테이블의 모든 행을 스캔해야 하지만, 인덱스가 있으면 특정 위치로 직접 이동할 수 있습니다.

인덱스의 핵심은 **B-Tree** 같은 균형 잡힌 트리 구조를 사용하여 데이터를 저장한다는 것입니다. 이를 통해 O(log n)의 시간 복잡도로 데이터를 검색할 수 있습니다(풀 테이블 스캔은 O(n)). 하지만 인덱스를 유지하는 비용이 있으므로, 쓰기 성능이 약간 저하되고 추가 저장 공간이 필요합니다.

> **한 줄 요약**: 특정 컬럼의 데이터를 정렬하여 별도로 저장함으로써 검색 속도를 획기적으로 향상시키는 데이터베이스 구조

**비유 1**: 데이터베이스 인덱스는 책의 색인과 같습니다. 책의 모든 페이지를 읽어서 원하는 주제를 찾으면 시간이 오래 걸리지만, 책 뒤의 색인에서 주제를 찾으면 해당 페이지 번호를 즉시 알 수 있습니다.

**비유 2**: 데이터베이스 인덱스는 전화번호부와 같습니다. 이름이 정렬된 전화번호부를 보면 "김김자" 씨의 번호를 몇 초 안에 찾을 수 있지만, 무작위로 섞인 번호 목록에서는 찾는 데 오래 걸립니다.

## 🎯 핵심 개념

### 1. 인덱스의 기본 원리 - B-Tree
가장 일반적인 인덱스 구조는 **B-Tree(Balanced Tree)**입니다. B-Tree는 다음과 같은 특성이 있습니다:

- **균형 잡힌 구조**: 모든 리프 노드가 같은 높이에 있어 검색 시간이 일정
- **정렬된 데이터**: 인덱스 컬럼의 값이 정렬된 상태로 유지
- **범위 검색 효율**: `WHERE age BETWEEN 20 AND 30` 같은 범위 쿼리가 효율적
- **시간 복잡도**: O(log n)의 빠른 검색 속도

예를 들어 100만 개의 행이 있으면, 풀 테이블 스캔은 최악의 경우 100만 회 비교가 필요하지만, B-Tree 인덱스는 약 20회의 비교만 필요합니다.

### 2. 인덱스의 장단점
**장점:**
- **검색 성능 대폭 향상**: 특히 WHERE, JOIN, ORDER BY 절에서 효과적
- **정렬 비용 감소**: 인덱스된 컬럼의 정렬이 매우 빠름

**단점:**
- **쓰기 성능 저하**: INSERT, UPDATE, DELETE 시 인덱스도 함께 수정해야 함
- **저장 공간 증가**: 테이블의 10-30%에 해당하는 추가 저장 공간 필요
- **메모리 사용 증가**: 인덱스가 메모리에 캐시되면서 메모리 소비 증가
- **유지보수 비용**: 인덱스 생성, 삭제, 최적화에 시간과 리소스 소요

### 3. 인덱스 선택의 기준
효율적인 인덱스를 만들기 위해서는:
- **선택도(Selectivity) 높은 컬럼**: 컬럼의 값들이 다양할수록 좋음 (성별 같은 이진 값은 나쁨)
- **자주 검색되는 컬럼**: WHERE, JOIN, ORDER BY에 자주 사용되는 컬럼
- **큰 테이블**: 작은 테이블(1000행 미만)은 인덱스의 이점이 작음
- **쓰기가 적은 컬럼**: INSERT/UPDATE가 자주 발생하면 인덱스 유지 비용 증가

## ⚠️ 해결하는 문제

### 문제 1: 느린 조회 성능
사용자 100만 명이 있는 테이블에서 `SELECT * FROM users WHERE email = 'user@example.com'` 쿼리를 실행하면, 인덱스 없이는 최악의 경우 100만 행을 모두 검사해야 합니다. 결과적으로 조회에 수 초가 걸릴 수 있습니다. 인덱스가 있으면 밀리초 단위로 결과를 반환할 수 있습니다.

### 문제 2: JOIN 성능 저하
여러 테이블을 조인할 때 인덱스가 없으면 각 테이블을 풀 스캔해야 하므로 성능이 급격히 저하됩니다. 예를 들어 1000만 행 테이블 2개를 조인하면, 인덱스 없이는 최악의 경우 1000억 번의 행 비교가 필요합니다.

## 🏗️ 구조


```도해
흐름: 인덱스, 무슨 순서로 오가나
쿼리 요청 :: SELECT * FROM users WHERE user_id…
쿼리 최적화기 :: user_id 인덱스 존재 확인
인덱스 :: B-Tree 탐색 (user_id=5)
인덱스 :: 행 위치 결정 (예: 메모리 주소 1000)
테이블 :: 행 데이터 반환 (1ms)
쿼리 최적화기 :: Full Table Scan 시작
테이블 :: 모든 100만 행 검사
테이블 :: 행 데이터 반환 (5000ms)
```

## ⚙️ 작동 원리

1. **인덱스 생성**: 관리자가 `CREATE INDEX idx_user_id ON users(user_id)` 같은 명령어로 인덱스를 생성합니다. 데이터베이스는 즉시 해당 컬럼의 모든 데이터를 정렬하여 인덱스 구조(B-Tree)에 저장합니다.

2. **쿼리 최적화**: 사용자가 `SELECT * FROM users WHERE user_id = 5` 쿼리를 실행하면, 쿼리 옵티마이저가 `user_id` 컬럼에 인덱스가 있는지 확인합니다.

3. **인덱스 경로 선택**: 인덱스가 있으면 풀 테이블 스캔 대신 인덱스를 사용하기로 결정합니다. 비용 분석을 통해 인덱스 사용이 더 빠르다고 판단해야만 인덱스를 사용합니다.

4. **B-Tree 탐색**: B-Tree 구조를 따라가며 `user_id = 5`인 노드를 찾습니다. 각 단계에서 절반의 데이터를 제외하므로 log n 시간에 완료됩니다.

5. **행 위치 파악**: B-Tree 리프 노드에는 실제 행의 메모리 주소나 Row ID(RID)가 저장되어 있습니다. 이를 통해 메인 테이블에서 실제 행을 찾을 위치를 즉시 파악할 수 있습니다.

6. **데이터 조회**: 파악한 위치에서 메인 테이블의 실제 행 데이터를 조회합니다. 필요한 컬럼이 인덱스에 모두 있으면 이 단계를 건너뜁니다(커버링 인덱스).

7. **결과 반환**: 조회한 행을 결과 집합에 추가합니다.

8. **통계 업데이트**: 데이터가 변경되면(INSERT, UPDATE, DELETE) 인덱스도 함께 수정되고, 통계 정보가 업데이트됩니다.

## 📊 비교

| 항목 | B-Tree Index | Hash Index | Full-Text Index | Composite Index |
|------|-------------|-----------|-----------------|-----------------|
| **구조** | 균형 트리 구조 | 해시 테이블 | 역 인덱스(Inverted Index) | 여러 컬럼 포함 |
| **적합 쿼리** | 범위 검색, 정렬 | 등호 검색만 | 텍스트 검색, LIKE | 여러 조건 동시 필터링 |
| **검색 시간** | O(log n) | O(1) | O(1) ~ O(log n) | O(log n) |
| **범위 검색** | 매우 효율적 | 비효율적 | 가능 | 효율적 |
| **정렬** | 매우 효율적 | 비효율적 | 비효율적 | 효율적 |
| **저장 공간** | 중간 | 중간 | 크다 | 크다 |
| **쓰기 성능** | 중간 | 낮음 | 낮음 | 매우 낮음 |
| **사용처** | 일반적 조회 | 고속 조회 | 검색 엔진 | 다중 필터 쿼리 |

## ✅ 장단점

**장점:**
- **검색 성능 대폭 향상**: 풀 테이블 스캔 대비 100배 이상 빠름
- **정렬 성능 향상**: ORDER BY가 인덱스로 커버되면 별도 정렬 불필요
- **JOIN 성능 개선**: 조인 조건에 인덱스가 있으면 중첩 루프 성능 향상
- **범위 검색 효율**: `BETWEEN`, `>`, `<` 같은 범위 쿼리가 효율적
- **유니크 제약 구현**: 유니크 인덱스로 중복 값 방지
- **외래키 성능**: 참조 무결성 확인이 빨라짐

**단점:**
- **삽입 성능 저하**: INSERT 시 인덱스도 함께 수정해야 하므로 느림
- **수정 성능 저하**: UPDATE 시 인덱스 업데이트 비용 발생
- **삭제 성능 저하**: DELETE 시 인덱스에서도 해당 항목 제거 필요
- **저장 공간 낭비**: 테이블 크기의 10-30%에 해당하는 추가 공간 필요
- **메모리 압박**: 자주 사용되는 인덱스는 메모리에 캐시되어 메모리 사용 증가
- **유지보수 비용**: 인덱스 생성, 삭제, 재구성(REBUILD)에 시간 소요
- **과도한 인덱스의 부작용**: 너무 많은 인덱스가 있으면 쿼리 최적화 비용 증가, 쓰기 성능 급격히 저하
- **대량 데이터 로드 느림**: 마이그레이션이나 초기 데이터 로드 시 인덱스 생성으로 인한 지연

## 💡 실제 사례

### 사례 1: 사용자 로그인 성능 최적화
**문제**: 500만 사용자가 있는 서비스에서 로그인 쿼리가 느림
```sql
SELECT * FROM users WHERE email = 'user@example.com';
```

**분석**:
- 인덱스 없을 때: 평균 2-3초 (500만 행 풀 스캔)
- 데이터베이스 부하 급증, 사용자 환경 저하

**해결책**:
```sql
CREATE INDEX idx_email ON users(email);
```

**결과**:
- 인덱스 생성 후: 5-10ms (100배 이상 빠름)
- 동시 사용자 처리량 10배 증가
- 서버 CPU 사용률 50% 감소

### 사례 2: 복합 필터 쿼리 최적화
**문제**: 여러 조건으로 필터링하는 쿼리가 느림
```sql
SELECT * FROM orders
WHERE user_id = 123 AND order_date > '2024-01-01' AND status = 'completed';
```

**분석**:
- 각 조건을 개별 인덱스로는 한계 있음
- 모든 조건을 동시에 처리할 방법 필요

**해결책**:
```sql
CREATE INDEX idx_user_date_status
ON orders(user_id, order_date, status);
```

**결과**:
- 단일 인덱스로 3개 조건 모두 처리
- 쿼리 실행 시간 80% 감소
- 데이터베이스 I/O 90% 감소

### 사례 3: 정렬 성능 최적화
**문제**: 사용자 목록을 최신순으로 정렬하는 쿼리가 느림
```sql
SELECT * FROM users WHERE status = 'active' ORDER BY created_at DESC;
```

**분석**:
- 인덱스 없을 때: 메모리에서 전체 데이터 정렬 (매우 느림)
- 100만 건 이상이면 디스크 정렬 필요 (초 단위 소요)

**해결책**:
```sql
CREATE INDEX idx_status_created ON users(status, created_at DESC);
```

**결과**:
- 인덱스가 이미 정렬되어 있어 별도 정렬 불필요
- 쿼리 실행 시간 95% 감소
- 추가 메모리 사용 제거

### 사례 4: JOIN 성능 향상
**문제**: 사용자와 주문을 조인하는 쿼리가 느림
```sql
SELECT users.name, COUNT(orders.id)
FROM users
LEFT JOIN orders ON users.id = orders.user_id
GROUP BY users.id;
```

**분석**:
- 1000만 사용자 × 5000만 주문 = 최악의 경우 5조 행 비교
- 여러 분 소요

**해결책**:
```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
```

**결과**:
- 조인이 인덱스 기반으로 변경
- 쿼리 실행 시간 분 단위 → 초 단위
- 데이터베이스 부하 1% 수준으로 감소

### 사례 5: 검색 기능 최적화
**문제**: 상품명으로 검색하는 LIKE 쿼리가 느림
```sql
SELECT * FROM products WHERE name LIKE '%laptop%';
```

**분석**:
- 일반 B-Tree 인덱스로는 LIKE '%'를 활용할 수 없음
- 풀 텍스트 검색 필요

**해결책**:
```sql
CREATE FULLTEXT INDEX idx_product_name ON products(name);

SELECT * FROM products WHERE MATCH(name) AGAINST('laptop' IN BOOLEAN MODE);
```

**결과**:
- 풀텍스트 인덱스로 단어 단위 검색 가능
- 쿼리 실행 시간 90% 감소
- 검색 정확도 향상 (스템밍, 동의어 처리 등)

## 🔗 관련 용어

- **B-Tree Index**: 가장 일반적인 인덱스 구조
- **Hash Index**: 등호 검색에만 적합한 인덱스
- **Full-Text Index**: 텍스트 검색 전용 인덱스
- **Composite Index**: 여러 컬럼을 포함하는 인덱스
- **Unique Index**: 중복 값을 허용하지 않는 인덱스
- **Primary Key Index**: 기본키 인덱스 (자동으로 생성)
- **Foreign Key Index**: 외래키 인덱스 (참조 무결성 확인용)
- **Covering Index**: 쿼리의 모든 컬럼을 포함하는 인덱스
- **Query Optimizer**: 인덱스 사용 여부를 결정하는 데이터베이스 엔진
- **Execution Plan**: 쿼리 실행 계획 (인덱스 사용 확인)
- **EXPLAIN**: 쿼리 실행 계획을 확인하는 명령어
- **Index Fragmentation**: 인덱스 조각화 (성능 저하 원인)
- **Index Rebuild**: 조각화된 인덱스 재구성
