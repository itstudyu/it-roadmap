# Data Catalog (데이터 카탈로그)

## 📝 정의

Data Catalog는 **어디에 무엇이 어떤 모양으로 있는지 적어 둔 목록**이다.

AWS 문서는 이것을 "조직의 자료 묶음에 대한 메타데이터를 저장하는 중앙 저장소" 로 적고, 하는 일을 한 낱말로 못 박는다 — **색인**이다. 원본의 위치, 칸 구성, 그리고 작업이 돌며 남긴 지표를 가리키는 색인이지 원본 자체가 아니다. 구글 쪽 문서도 같은 구조를 쓴다. 항목 하나가 자료 자산 하나를 가리키고, 그 항목에 설명 묶음이 여러 개 붙는다.

### 이름
Data :: 쌓아 둔 자료
Catalog :: 가진 것을 적어 둔 목록
= 붙여 읽으면 "가진 자료의 목록". 들어가는 것은 자료가 아니라 자료에 대한 설명이다

### 비유
도서관 열람 목록. 목록에 책이 들어 있는 게 아니라, 무슨 책이 몇 층 어느 칸에 있는지가 들어 있다.

### 예
"이 숫자 어느 표에서 나온 거예요" 를 메신저로 묻고 답을 기다리던 그 30분이 이것이 없어서 생긴다.

## 🖼️ 그림으로 보기

```도해
층: 목록 한 줄에는 무엇이 쌓여 있나
어디에 :: 어느 저장소 어느 경로에 있는지
어떤 모양 :: 칸 이름과 자료형, 나눠 담은 기준
누구 것 :: 맡은 사람, 볼 수 있는 사람, 다루기 규칙
무슨 뜻 :: 업무 용어와 설명, 믿어도 되는지 알려주는 점수
= 자료 자체는 한 줄도 안 들어간다. 위쪽은 기계가 채우고 아래쪽은 사람이 채운다
```

## ⚠️ 해결하는 문제

```도해
대조: 목록이 없으면 표 하나를 찾는 데 무엇이 드나
목록 없이 || 목록이 있으면
찾는 법 :: 아는 사람에게 || 이름으로 검색
믿어도 되나 :: 짐작으로 쓴다 || 맡은 사람이 있다
같은 표 또 만들기 :: 모르니 또 만든다 || 있는 걸 먼저 본다
= 어디에 무엇이 있는지 아무 데도 안 적혀 있으면 아는 사람이 병목이 된다
```

자료를 다루는 조직에서 가장 자주 나오는 물음은 "이 숫자가 어느 표에서 나왔나" 와 "지역별 매출은 어느 표를 봐야 하나" 다. 이 물음의 답이 사람 머릿속에만 있으면 그 사람이 병목이 되고, 그 사람이 떠나면 답이 통째로 사라진다. 그러는 사이에 비슷한 표가 하나씩 더 생기고, 같은 이름의 표 다섯 개 중 어느 것이 진짜인지 아무도 모르게 된다.

목록은 이 물음의 답을 **자료 밖에 따로 세워 둔다.** 그래서 목록이 하는 일은 저장이 아니라 색인이다. 원본은 있던 자리에 그대로 두고, 그것을 가리키는 설명만 한곳에 모아 검색되게 만든다.

## ⚙️ 작동 원리

기계가 채우는 몫이 먼저다. AWS 쪽은 훑는 도구가 저장소를 돌며 칸 이름과 자료형과 나눠 담은 기준을 알아내 표로 등록하고, 구글 쪽은 지원하는 저장소에서 기술 메타데이터를 자동으로 들여온다. 손으로도 등록할 수 있지만, 표가 수천 개인 곳에서 손으로 따라가는 것은 애초에 불가능하다.

```도해
흐름: 폴더에 쌓인 파일 더미가 어떻게 물어볼 수 있는 표가 되나
저장소 :: 파일이 폴더째 쌓여 있다. 아직 표가 아니다
훑는 도구 :: 폴더를 훑어 칸 이름과 자료형을 알아낸다
목록 :: 표 하나로 등록한다. 나눠 담은 기준까지 적는다
질의 엔진 :: 목록에서 표 정의를 받아 파일을 읽는다
< 물어본 사람 :: 파일 더미를 표처럼 SQL 로 묻고 결과를 받는다
= 파일은 그대로 두고 설명만 따로 세운 것이다. 목록이 틀리면 질의도 틀린다
```

사람이 채우는 몫은 자동으로 안 된다. 이 칸이 무슨 뜻인지, 누가 맡는지, 어느 화면이 이걸 믿고 쓰는지는 훑어서 알아낼 수 없다. 목록을 오래 쓰는 조직과 금세 버리는 조직을 가르는 것도 대개 이쪽이다.

마지막으로, 목록은 읽히려고만 있는 게 아니라 **다른 도구가 실제로 물어보는 자리**다. 질의 엔진이 저장소 위의 파일을 SQL 로 읽을 때 표 정의를 여기서 받아 간다. 그래서 목록의 칸 정의가 실제 파일과 어긋나면 검색이 불편해지는 정도가 아니라 질의가 틀린 답을 준다.

## 💡 실제 사례

- **처음 보는 표 찾기** — 이름과 설명으로 검색해 어디 있고 누가 맡는지부터 본다. 사람에게 묻는 단계가 통째로 빠진다.
- **파일 더미를 표처럼 묻기** — 저장소의 폴더를 훑어 표로 등록해 두면 질의 도구가 그 정의를 받아 SQL 로 읽는다.
- **권한을 한 곳에서** — 표와 칸 단위 규칙을 목록에 걸어 두면 어느 도구로 들어와도 같은 규칙이 걸린다.

## 🚫 흔한 오해

- **카탈로그에 자료가 들어간다** — 안 들어간다. 위치와 칸 구성과 통계 같은 설명만 들어가고, 원본은 있던 자리에 그대로 있다. 목록을 통째로 지워도 원본은 안 사라진다.
- **훑는 도구를 걸어 두면 알아서 다 채워진다** — 칸 이름과 자료형까지다. 이 칸이 무슨 뜻인지, 누가 맡는지, 믿어도 되는지는 사람이 적어야 한다.
- **표를 많이 등록할수록 좋은 목록이다** — 설명이 빈 항목이 늘면 검색 결과만 길어진다. 목록의 값어치는 등록한 표 수가 아니라 채워진 설명의 양에서 나온다.

## 📝 정리

**"자료가 아니라 자료의 설명을 모아 둔 목록"** 이라고 읽으면 된다. 위치와 칸 구성은 기계가 훑어 채우지만, 무슨 뜻이고 누가 맡는지는 사람이 채워야 비로소 쓸 수 있는 목록이 된다. 다른 도구가 표 정의를 여기서 받아 가므로, 목록이 틀리면 질의도 틀린다.

## 🧒 열 살에게

도서관에 가면 책이 아니라 책 이름이 적힌 목록을 먼저 보지? 목록에는 무슨 책이 몇 층 어느 칸에 있는지만 적혀 있고 책은 원래 자리에 그대로 있어. 이게 없으면 책 한 권 찾을 때마다 사서 아저씨한테 일일이 물어봐야 해.

## ❓ 이해했는지

- 목록을 통째로 지워도 원본 자료가 안 사라지는 이유는 무엇인가 → 흔한 오해
- 폴더에 쌓인 파일 더미를 표처럼 묻게 하려면 그 전에 무슨 일이 있어야 하나 → 작동 원리
- 표를 수천 개 등록해 두고도 아무도 쓸 표를 못 고르는 일은 어디에서 비롯되나 → 그림
