# Data Lake (데이터 레이크)

## 📝 정의

데이터 레이크는 **정리하지 않은 원본을 그대로 쌓아 두는 저장소**다.

표로 된 데이터, JSON·XML·로그 같은 반쯤 정리된 데이터, 이미지·음성·영상처럼 표에 넣을 수 없는 데이터를 원래 형식 그대로 받는다. 정리는 담을 때가 아니라 읽을 때 한다.

### 비유
창고에 들어온 짐을 상자째 쌓아 두는 것. 무엇을 쓸지 정해지면 그때 상자를 열어 꺼낸다.

## 🖼️ 그림으로 보기

```도해
대조: 데이터를 언제 정리하느냐로 무엇이 갈리나
웨어하우스 |=| 데이터 레이크
정리 시점 :: 담을 때 맞춘다 || 꺼낼 때 맞춘다
담는 형식 :: 표로 맞춘 것만 || 원본 아무 형식
영상·로그 :: 못 담는다 || 그대로 담는다
= 먼저 정리하면 묻기 쉽고, 안 정리하면 무엇이든 남는다
```

## ⚠️ 해결하는 문제

```도해
대조: 정해진 표에만 담을 수 있으면 무슨 일이 생기나
표에만 담으면 || 레이크에 쌓으면
로그·영상 :: 버려진다 || 원본이 남는다
새 질문 :: 데이터가 없다 || 다시 훑어본다
담기 전 :: 형식을 정해야 || 그냥 넣는다
= 무엇을 알아낼지 모를 때는 원본을 남겨 두는 편이 낫다
```

표에 넣으려면 열이 몇 개이고 무엇이 들어갈지 먼저 정해야 한다. 그런데 서버 로그나 센서 값처럼 형식이 제각각인 데이터는 그 단계에서 걸리고, 걸린 데이터는 대개 버려진다.

버려지는 것이 아까운 이유는 **지금 무엇을 알아낼지 모르기 때문**이다. 데이터에서 나올 수 있는 답을 미리 알 수 없는 자리에서는 원본을 남겨 두는 것 자체가 이득이다. 레이크는 담는 쪽의 규칙을 없애서 그것을 가능하게 한다.

## ⚙️ 작동 원리

```도해
층: 레이크에 쌓인 원본이 어떻게 쓸 만한 표가 되나
원본 층 :: 들어온 그대로 둔다. 거의 손대지 않는다
정제 층 :: 검증하고 변환한 것. 분석과 기계학습이 쓴다
완성 층 :: 집계해 바로 쓸 표. 보고서와 대시보드가 읽는다
= 원본을 지우지 않고 그 위에 정제한 층을 얹는다
```

담을 때 구조를 강제하지 않고 읽을 때 맞추는 이 방식을 **schema-on-read** 라고 한다. 반대로 웨어하우스는 담는 동안 구조를 강제하고 변환하는데, 그쪽은 schema-on-write 다. 레이크의 세 층은 원본을 지우고 갈아 끼우는 것이 아니라 위에 얹는 것이라, 정제 규칙이 틀렸다고 판명되면 원본 층에서 다시 시작할 수 있다.

읽을 때 맞춘다는 말이 무슨 뜻인지는 질의 도구를 보면 분명해진다. Athena는 S3 에 놓인 CSV·JSON·Parquet 파일에 표 정의만 붙여 두면, 옮기거나 적재하지 않고 그 자리에서 SQL 로 묻게 해준다. 무엇이 어디 있는지는 크롤러가 파일을 읽어 스키마를 추론해 카탈로그에 적어 둔다.

## 🚨 주의사항

- **카탈로그가 없으면 늪이 된다.** 무엇이 어디 있는지 적어 두지 않으면 데이터는 다 있는데 아무도 찾지 못하는 상태가 된다. 이걸 data swamp 라고 부른다.
- **값은 꺼낼 때 치른다.** 변환을 질의 시점에 하므로 미리 정리해 둔 웨어하우스보다 응답이 느리다. 자주 묻는 질문은 정제·완성 층으로 미리 내려 두는 편이 낫다.
- **권한을 열·행 단위까지 잠가야 한다.** 원본을 그대로 받으면 개인정보가 섞여 들어온다. Lake Formation 같은 층에서 열·행·셀 단위로 접근을 제한하고 누가 무엇을 봤는지 감사 로그를 남긴다.

## 💡 실제 사례

- **로그를 일단 쌓아 두기** — 무엇을 볼지 정하기 전에 서버 로그를 원본 형식으로 넣어 두고, 나중에 질문이 생기면 그때 훑는다.
- **옮기지 않고 묻기** — 파일을 적재하거나 집계하지 않고 표 정의만 붙여 S3 에 둔 채로 SQL 즉석 질의를 돌린다.
- **모델 학습용 데이터** — 이미지나 음성처럼 표에 넣을 수 없는 것을 그대로 담아 두고 학습과 미세조정에 쓴다.

## 🚫 흔한 오해

- **레이크는 아무거나 넣는 창고라 관리가 필요 없다** — 담는 규칙이 없는 것과 관리가 없는 것은 다르다. 카탈로그와 권한을 갖추지 않으면 값이 있는데 못 쓰는 늪이 된다.
- **레이크만 있으면 웨어하우스는 필요 없다** — 정해진 질문에 빨리 답해야 하는 보고서와 대시보드는 미리 정리해 둔 웨어하우스가 낫다. 실제로는 레이크를 상류에 두고 둘을 함께 쓴다.
- **원본 그대로 넣으니 나중에 정리할 일이 없다** — 정리를 안 하는 게 아니라 읽는 쪽으로 미룬 것이다. 미룬 만큼 질의할 때마다 값을 치른다.

## 📝 정리

데이터 레이크는 정리하지 않은 원본을 형식 그대로 쌓아 두는 저장소다. 담을 때 구조를 강제하지 않고 읽을 때 맞추기 때문에 무엇을 알아낼지 모르는 데이터를 잃지 않는다. 대신 카탈로그와 권한을 갖추지 않으면 있는 데이터를 아무도 못 찾는 늪이 된다.

## ❓ 이해했는지

- 같은 서버 로그를 웨어하우스는 받기 어렵고 레이크는 그대로 받는 이유는 → 그림
- 데이터는 다 들어 있는데 아무도 원하는 것을 못 찾는 상태는 왜 생기나 → 주의사항
- 정제한 표를 만든 뒤에도 원본 층을 지우지 않고 두면 무엇이 이득인가 → 작동 원리
