# Partitioning (파티셔닝)

## 📝 정의

Partitioning은 **한 테이블을 여러 조각으로 쪼개 두고 하나처럼 쓰는 것**이다.

PostgreSQL 문서는 이걸 논리적으로 하나인 큰 테이블을 더 작은 물리적 조각들로 쪼개는 것이라고 정의한다. 쪼갠 조각을 파티션이라 부르고, 조각마다 어떤 값을 담을지가 파티션 경계로 정해져 있다. 묻는 쪽에서는 여전히 테이블 하나다 — SQL Server 문서도 질의하거나 갱신할 때는 하나의 논리적 실체로 다뤄진다고 적는다.

### 이름
= 영어 partition 은 방을 가르는 "칸막이" 다. 표를 없애고 새로 만드는 게 아니라 칸막이로 나눠 둘 뿐이라 밖에서는 여전히 표 하나다

### 비유
한 권짜리 두꺼운 장부를 월별 열두 권으로 나눠 꽂아 둔 것. 3월 것을 찾을 때는 3월 권만 꺼낸다.

### 예
같은 조회인데 이번 달 내역은 곧바로 뜨고 3년 전 것을 찾을 때만 눈에 띄게 오래 걸리는 그 차이다.

## 🖼️ 그림으로 보기

```도해
흐름: 3월 매출만 찾을 때 파티션한 테이블은 어디를 읽나
앱 :: 매출 테이블 하나에 3월 조건으로 묻는다
DB :: 조각마다 정해둔 경계를 조건과 견준다
DB :: 3월 조각 밖에는 답이 있을 수 없다고 판정
3월 조각 :: 자기가 가진 행만 훑는다
< 앱 :: 테이블 하나에 물었고 하나로 받는다
= 조각으로 나뉘어 있어도 묻는 쪽에는 여전히 한 테이블이다
```

## ⚠️ 해결하는 문제

```도해
대조: 한 테이블이 너무 커지면 무엇이 힘들어지나
파티션 없이 || 파티션으로
오래된 행 정리 :: 대량 DELETE || 조각을 떼어냄
자주 쓰는 부분 :: 인덱스 위층이 큼 || 메모리에 들어감
찬 데이터 이전 :: 테이블째 옮김 || 조각만 옮김
= 큰 테이블을 나누면 큰 일이 조각 단위의 작은 일이 된다
```

테이블이 커지면 큰 일이 전부 통째로만 된다. 지난달 것을 지우려면 수백만 행을 `DELETE` 해야 하고, 오래된 데이터만 값싼 저장 장치로 내리려 해도 옮길 단위가 테이블 하나뿐이다.

파티셔닝은 그 단위를 조각으로 낮춘다. PostgreSQL 문서는 조각을 `DROP TABLE` 로 지우거나 `ALTER TABLE DETACH PARTITION` 으로 떼어내는 것이 같은 양의 대량 작업보다 훨씬 빠르고, 대량 `DELETE` 가 남기는 `VACUUM` 부담도 아예 생기지 않는다고 적는다. 자주 읽는 행이 한두 조각에 모여 있으면 인덱스의 자주 쓰이는 부분이 메모리에 들어갈 가능성도 커진다.

## 🧱 구성

```도해
층: 파티션한 표는 무엇 위에 무엇이 얹혀 있나
논리 표 :: 앱이 보는 이름 하나. 여기에 묻는다
파티션 키 :: 어느 조각에 무엇이 들어갈지 가르는 칸
조각들 :: 행이 실제로 담기는 물리적인 표들
= 위에서는 표 하나로 보이고 아래에서는 여러 조각이다
```

## 📊 비교: 파티셔닝 vs 샤딩

이름이 비슷해서 가장 많이 섞이는 자리다. 둘은 나누는 **범위**가 다르다.

| | Partitioning | [[Sharding]] |
|---|---|---|
| 조각이 사는 곳 | 한 데이터베이스 안 | 서버를 넘어 여러 대 |
| 앱이 보는 것 | 테이블 하나 | 어느 서버인지 계산해야 |
| 얻는 것 | 관리·질의 단위가 작아짐 | 서버 한 대의 한계를 넘음 |

SQL Server 문서는 이 경계를 못 박아 둔다 — 한 테이블이나 인덱스의 모든 파티션은 같은 데이터베이스 안에 있어야 한다. 그래서 파티셔닝으로는 서버 한 대의 한계를 넘지 못한다. 그 한계를 넘는 쪽이 샤딩이다.

다만 PostgreSQL 은 파티션 자리에 외부 테이블을 붙이는 것도 허용한다. 대신 그 외부 테이블의 내용이 파티션 규칙을 지키는지는 사용자가 책임져야 한다고 문서가 경고한다.

## 💡 실제 사례

- **월별 매출 테이블** — 날짜로 열두 조각으로 나누면 3월 집계가 3월 조각만 읽는다.
- **보관 기간 정리** — 지난달 데이터를 대량 `DELETE` 하는 대신 그 달 조각을 떼어내거나 지운다.
- **찬 데이터 내리기** — 오래된 조각은 값싸고 느린 저장 장치에 두고, 최근 조각만 빠른 곳에 둔다.

## 🚫 흔한 오해

- **파티셔닝하면 질의가 다 빨라진다** — 조건에 파티션 컬럼이 없으면 조각을 전부 뒤진다. 한 행을 콕 찍어 읽는 질의는 조각 수만큼 탐색이 늘어나서, SQL Server 문서는 그런 질의가 많은 OLTP 에서는 파티셔닝이 성능을 거의 못 올린다고 적는다.
- **파티셔닝은 샤딩의 다른 이름이다** — 한 테이블의 파티션은 모두 같은 데이터베이스 안에 있어야 한다. 서버를 넘어 나누는 쪽이 샤딩이다.
- **조각을 많이 쪼갤수록 좋다** — SQL Server 는 수백~수천 개 파티션 설계를 꼭 필요한 경우가 아니면 피하라고 경고한다. 조각이 많아지면 메모리와 인덱스 작업, 무결성 검사가 다 무거워진다.

## 🚨 주의사항

- **조건에 파티션 컬럼을 넣어야 이득이 온다.** 조건이 파티션 컬럼을 가리켜야 DB 가 읽지 않아도 되는 조각을 걸러낼 수 있다. 다른 컬럼으로만 찾는 화면이 많다면 파티션 키를 잘못 고른 것이다.
- **지원 한도는 권장치가 아니다.** SQL Server 는 테이블당 15,000개까지 지원하지만, 조각이 늘면 인덱스를 만들고 다시 세우는 데 필요한 메모리가 함께 늘어난다. 조각을 늘리기 전에 그 설계를 실제 질의로 확인해야 한다.

## 📝 정리

**"한 표를 조각으로 나눠 둔 것"** 이라고 읽으면 된다. 조건이 파티션 컬럼을 가리키면 DB 가 필요 없는 조각을 건너뛰고, 오래된 데이터는 조각째 떼어내면 된다. 한 테이블의 조각은 모두 같은 데이터베이스 안에 있어야 하므로, 서버를 넘어 나누는 샤딩과는 다른 일이다.

## 🧒 열 살에게

공책 한 권에 일 년치 일기를 다 써 놨으면 3월 일기를 찾을 때 앞장부터 한참 넘겨야 하지? 그런데 달마다 공책을 따로 만들어 열두 권을 꽂아 두면 3월 공책만 쏙 뽑으면 돼. 작년 것을 버리고 싶을 때도 한 장씩 찢을 필요 없이 그 공책 한 권만 빼면 끝이야.

## ❓ 이해했는지

- 월별로 나눠 놓았는데 고객 이름으로 찾는 질의가 더 느려졌다면 왜인가 → 흔한 오해
- 지난달 데이터를 지우는 데 대량 DELETE 보다 빠른 방법이 있는 이유는 → 해결하는 문제
- 조각이 여러 개인데 앱이 테이블 하나로 다루는 것은 어떻게 가능한가 → 그림
