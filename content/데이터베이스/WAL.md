# WAL (Write-Ahead Log)

## 📝 정의

WAL 은 **고칠 내용을 먼저 적어두는 기록 방식**이다.

이름이 곧 순서다. Write-Ahead — 쓰기보다 앞선다. 표와 인덱스가 들어 있는 데이터 파일을 고치는 것은 나중이고, 무엇을 어떻게 고칠지 적은 기록을 먼저 디스크에 못 박는다. PostgreSQL 문서는 이 순서 하나를 WAL 의 중심 개념이라고 적는다.

### 이름
Write :: 데이터 파일 고치기
Ahead :: 그보다 앞서
Log :: 무엇을 할지 적은 기록
= 붙여 읽으면 "고치기에 앞서 적는 기록". 이름이 곧 순서다

### 비유
가계부. 지갑에서 돈을 꺼내기 전에 먼저 적어두면, 나중에 지갑만 봐도 무슨 일이 있었는지 되짚어 맞출 수 있다.

### 예
문서를 쓰다 컴퓨터가 꺼졌는데 다시 켜니 마지막까지 쓴 내용이 복구되어 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 고칠 내용을 먼저 적어두면 복구가 어떻게 되나
변경 :: 행을 고쳐 달라는 요청이 온다
WAL 기록 :: 무엇을 어떻게 고칠지 먼저 적는다
커밋 :: 그 기록이 디스크에 박히면 성공이다
데이터 파일 :: 표와 인덱스는 나중에 따라간다
멈춤 :: 여기서 전원이 끊긴다
재시작 :: 기록을 다시 실행해 못 따라간 것을 메운다
= 먼저 적었기 때문에, 나중이 안 끝나도 기록을 되짚어 맞출 수 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 기록을 안 남기고 바로 고치면 어떻게 되나
WAL 없이 || WAL 로
커밋할 때 :: 고친 곳을 다 밀어냄 || 기록 하나만 밀어냄
디스크 움직임 :: 흩어진 자리에 쓴다 || 이어진 자리에 쓴다
도중에 멈추면 :: 반만 고쳐져 남는다 || 기록으로 다시 맞춘다
= 고친 곳을 다 못 박는 대신, 무엇을 고칠지 한 곳에 못 박는다
```

기록이 없으면 커밋을 확정하려고 그 트랜잭션이 건드린 데이터 파일을 전부 디스크에 밀어내야 한다. 고친 자리는 파일 곳곳에 흩어져 있어서 그때마다 디스크가 여기저기를 오간다. 그러다 도중에 전원이 끊기면 어디까지 반영됐는지 알 방법이 없다.

WAL 은 순서를 뒤집어 이 둘을 함께 없앤다. 커밋을 보장하는 데 디스크에 밀어내야 하는 것은 기록 파일뿐이고, 기록 파일은 이어진 자리에 순서대로 쓰이기 때문에 데이터 파일을 밀어내는 것보다 훨씬 싸다. PostgreSQL 문서는 작은 트랜잭션이 여럿 몰릴 때 기록 파일을 한 번 동기화하는 것으로 여러 커밋을 함께 확정할 수 있다고 적는다.

## ⚙️ 작동 원리

되돌리는 방향이 아니라 다시 실행하는 방향이라는 점이 핵심이다. 다시 켜면 데이터 파일에 아직 반영되지 않은 변경을 기록에서 찾아 그대로 다시 실행한다. PostgreSQL 은 이것을 앞으로 굴리는 복구, REDO 라고 부른다.

SQLite 는 이 순서가 예전 방식의 정확한 뒤집기라고 설명한다. 옛 롤백 저널은 원본 내용을 다른 파일에 베껴두고 본 파일을 바로 고쳤다. WAL 은 반대다 — 원본은 본 파일에 그대로 남고, 변경은 딴 파일 뒤에 덧붙는다.

그러면 읽는 쪽과 쓰는 쪽이 안 부딪힌다. 읽기가 시작될 때 기록 파일에서 마지막으로 온전한 커밋 지점을 기억해 두고(SQLite 는 이 지점을 end mark 라고 부른다) 그 앞까지만 본다. 쓰는 쪽은 그 뒤에 붙이므로 읽는 쪽이 보는 것을 건드리지 않는다.

```도해
흐름: WAL 파일은 계속 커지기만 하나
커밋 :: 기록이 파일 뒤에 이어 붙는다
읽는 쪽 :: 마지막 커밋 지점까지만 본다
체크포인트 :: 쌓인 기록을 본 파일로 옮긴다
되감기 :: 다 옮겼고 읽는 쪽이 없으면 처음으로
@ 다시 쌓임 :: 그다음 커밋이 처음부터 덮어 쓴다
= 늘기만 하지 않는다. 다 옮겨지면 처음으로 되감아 덮어 쓴다
```

쌓인 기록을 본 파일로 옮기는 이 일을 체크포인트라고 부른다. SQLite 는 체크포인트가 기록 파일을 잘라내는 것이 아니라 그 파일을 처음부터 덮어 쓰기 시작하게 만드는 것이라고 못 박아 둔다.

## 💡 실제 사례

- **커밋이 빨라진다** — 고친 곳을 하나하나 밀어내는 대신 기록 파일만 디스크에 못 박으면 커밋이 끝난다. 작은 트랜잭션이 몰릴 때는 한 번의 동기화가 여러 커밋을 함께 확정한다.
- **원하는 시점으로 되돌리기** — 예전 백업을 깔아 두고 그 뒤의 기록을 원하는 시각까지만 다시 실행하면 그 순간의 상태가 나온다. PostgreSQL 의 시점 복구가 이 방식이다.
- **읽기와 쓰기가 안 겹친다** — 쓰는 쪽은 기록 파일 뒤에 붙이고 읽는 쪽은 원본과 그 지점까지의 기록만 보므로, 읽는 쪽이 쓰는 쪽을 기다리지 않는다.

## 🚫 흔한 오해

- **커밋됐다는 말은 표에 다 써졌다는 뜻이다** — 그 시점에 디스크에 확실히 있는 것은 기록이다. 표와 인덱스가 들어 있는 데이터 파일은 나중에 따라간다.
- **따로 또 적으니 두 번 쓰는 셈이라 느리다** — 오히려 디스크에 쓰는 횟수가 크게 줄어든다. 커밋마다 흩어진 데이터 파일을 다 밀어내는 것보다, 이어진 기록 파일 하나를 밀어내는 것이 훨씬 싸기 때문이다.
- **WAL 로 바꾸면 무조건 빨라진다** — SQLite 문서는 대부분의 상황에서 빠르다고 하면서도, 읽기가 대부분이고 쓰기가 드문 작업에서는 1~2% 쯤 느릴 수 있다고 적는다. 읽는 쪽마다 기록 파일을 뒤져 봐야 하고 그 시간이 파일 크기에 비례하기 때문이다.

## 🚨 주의사항

- **기록 파일은 저절로 줄지 않는다.** 체크포인트가 밀리거나 오래된 읽기가 붙어 있으면 되감지 못하고 계속 커진다. SQLite 는 커밋 때 기록이 1000 쪽쯤 넘으면 자동으로 체크포인트를 잡는다.
- **한 대 안에서만 쓴다.** SQLite 의 WAL 은 같은 컴퓨터의 프로세스들이 공유 메모리로 위치를 주고받는 구조라서, 네트워크 파일 시스템에 올린 파일에는 동작하지 않는다.

## 📝 정리

**"꺼내기 전에 먼저 적어 두는 그 가계부"** 라고 읽으면 된다. 그 순서 덕분에 커밋은 기록 하나만 밀어내면 끝나고, 도중에 죽어도 기록을 다시 실행해 맞출 수 있다. 대신 쌓인 기록을 본 파일로 옮기는 체크포인트를 따로 챙겨야 한다.

## 🧒 열 살에게

지갑에서 돈을 꺼내기 전에 가계부에 먼저 적어 두는 사람이 있어. 적어 두고 꺼내다가 중간에 놓쳐도, 가계부를 보면 무엇을 하려던 참인지 알아서 다시 맞출 수 있어. 순서를 바꾼 것뿐인데 잃어버릴 일이 없어지는 거야.
