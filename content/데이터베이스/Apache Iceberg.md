# Apache Iceberg (아이스버그)

## 📝 정의

Iceberg는 **파일 더미를 표 하나로 다루게 하는 규격**이다.

Athena 문서는 이것을 "아주 큰 분석용 데이터셋을 위한 열린 표 형식" 이라 부르고, "파일의 큰 묶음을 표로 관리하며 한 건 단위의 넣기·고치기·지우기와 시간 여행 질의를 지원한다" 라고 적는다. 파일을 새로 발명한 것이 아니라, 이미 쌓여 있던 파일 더미 위에 "지금 이 표는 어느 파일들인가" 를 적는 층을 얹은 것이다.

### 이름
Apache :: 재단 이름
Iceberg :: 빙산
= 물 위에 뜬 표 하나 밑에 목록과 파일이 층층이 잠겨 있다는 뜻이다

### 비유
게시판을 옆에서 새로 다 만들어 두고 입구 안내판의 화살표만 슥 옮기는 것 — 옮기기 전까지는 모두 옛 게시판만 본다.

### 예
폴더에 파일을 붓는 동안 그 폴더를 읽던 쪽이 반쯤 쓰인 파일을 집어 가 숫자가 틀어지던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
층: 표 하나라고 부르는 것이 실은 무엇으로 이어져 있나
카탈로그 :: 지금 판을 가리키는 화살표 하나. 커밋 때 여기만 바뀐다
메타데이터 :: 스키마와 지금까지 쌓인 스냅샷 목록
매니페스트 목록 :: 이 스냅샷 하나에 든 매니페스트들
매니페스트 :: 데이터 파일 목록과 파일마다의 값 범위
데이터 파일 :: 실제 값이 든 파케이·ORC 파일
= 화살표 하나만 바꿔 끼우면 표 전체가 한꺼번에 다른 판이 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 폴더째 다룰 때와 표 형식으로 다룰 때 무엇이 다른가
폴더로 다루면 || 표 형식으로 다루면
쓰는 도중 :: 반쯤 쓴 게 읽힌다 || 다 되면 한꺼번에
되돌리기 :: 지운 건 끝이다 || 옛 판을 지목한다
동시에 쓰기 :: 뒤에 쓴 게 이긴다 || 한쪽이 다시 한다
= 파일을 늘어놓는 것과 표를 이루는 것은 다르다. 그 사이를 메우는 규격이다
```

파일을 폴더에 늘어놓고 "이 폴더가 그 표다" 라고 부르면, 쓰는 일과 읽는 일이 겹치는 순간마다 사고가 난다. 하루치를 붓는 도중에 누가 질의를 던지면 반쯤 쓰인 파일이 딸려 들어가고, 잘못 넣은 하루를 되돌리려면 무엇을 지워야 하는지 사람이 기억해야 하고, 두 배치가 같은 자리를 동시에 건드리면 나중 것이 앞의 것을 조용히 덮는다.

Iceberg 는 **파일 목록 자체를 판으로 관리하고, 한 번의 커밋으로 그 판을 통째로 갈아 끼운다.** 읽는 쪽은 자기가 시작할 때의 판을 끝까지 보고, 쓰는 쪽은 다 쓴 다음에야 화살표를 옮긴다. 그래서 "쓰는 중" 이라는 어정쩡한 상태가 읽는 쪽에 보이지 않는다.

## ⚙️ 작동 원리

커밋은 남을 기다리게 하는 자물쇠 없이 **낙관적 동시성**으로 한다. 새 데이터 파일을 먼저 다 쓰고, 그 파일들을 담은 새 메타데이터를 만든 뒤, 카탈로그의 화살표를 "내가 읽었던 그 판" 에서 새 판으로 바꿔 달라고 청한다. 그 사이에 남이 먼저 바꿨으면 이 청은 실패하고, 실패한 쪽이 다시 읽고 다시 시도한다. Athena 문서가 "AWS Glue 낙관적 잠금만 지원하며, 다른 잠금 구현으로 Iceberg 표를 고치면 데이터 손실과 트랜잭션 파손이 일어날 수 있다" 라고 못 박는 이유가 여기 있다 — 화살표를 바꾸는 그 한 걸음이 원자적이어야 전부가 성립한다.

지나간 판은 지우지 않으므로 시간 여행이 공짜로 따라온다. "각 Iceberg 표는 자신이 담은 객체들의 판 붙은 목록을 유지한다" 라고 문서는 적는다. `FOR TIMESTAMP AS OF` 로 그때의 시각을, `FOR VERSION AS OF` 로 스냅샷 번호를 지목하면 그 판이 그대로 읽힌다.

스키마 변경은 파일을 건드리지 않는다. "Iceberg 스키마 갱신은 메타데이터만의 변경이다. 스키마를 갱신해도 데이터 파일은 하나도 바뀌지 않는다." 칸 더하기·빼기·이름 바꾸기·순서 바꾸기, 그리고 정수를 큰 정수로, 실수를 배정도로, 소수의 자릿수를 늘리는 타입 넓히기가 그렇게 된다.

대신 청소가 일이 된다. 스냅샷과 작은 파일이 쌓이면 목록을 읽는 값이 본문보다 커진다. `OPTIMIZE ... REWRITE DATA` 가 작은 파일과 지움 파일을 큰 파일로 합치고, `VACUUM` 이 보존 기간이 지난 스냅샷을 만료시키고 아무 판에도 안 걸린 고아 파일을 치운다.

## 💡 실제 사례

- **두 번 들어온 것 막기** — 같은 열쇠가 또 오면 `MERGE INTO` 로 있으면 고치고 없으면 넣는다. 폴더 시절에는 하루치를 통째로 다시 쓰던 일이다.
- **늦게 온 기록 끼워 넣기** — 사흘 전 자리에 몇 줄을 넣어도 새 스냅샷 하나만 생긴다. 그동안 읽던 쪽은 끝까지 옛 판을 본다.
- **틀린 배치 되돌리기** — 어제 배치가 잘못된 값을 밀어 넣었으면 그 직전 스냅샷 번호를 지목해 그 판으로 돌아간다.

## 🚫 흔한 오해

- **아이스버그가 파일 형식이다** — 값이 담기는 파일은 여전히 파케이나 ORC 다. 이건 "지금 이 표가 어느 파일들인가" 를 적어 두는 층이다.
- **폴더의 파일을 직접 옮겨도 표는 그대로다** — 목록에 안 적힌 파일은 표에 없는 파일이다. BigQuery 문서도 밖에서 데이터 파일을 고치면 질의 실패나 데이터 손실이 날 수 있다고 적는다.
- **표는 다 아이스버그로 두면 된다** — 한 건씩 집어 오고 수시로 고치는 업무에는 맞지 않는다. 커밋 한 번이 파일 여러 개를 새로 쓰고 목록을 다시 짜는 일이다.

## 📝 정리

**"어느 파일들이 지금 이 표인지 적어 둔 그 장부"** 라고 읽으면 된다. 값은 여전히 파케이 파일에 있고, 커밋이 바꾸는 것은 그 장부를 가리키는 화살표 하나다. 그래서 쓰는 도중에도 읽는 쪽은 옛 판을 온전히 보고, 어제로 되돌리는 일도 파일을 뒤지지 않고 번호 하나로 끝난다.

## 🧒 열 살에게

알림장을 벽에 붙여 놓고 그 위에 덧칠해 고치면, 고치는 동안 온 애는 반만 고쳐진 걸 읽게 되지? 그래서 새 종이를 옆에서 다 쓴 다음 압정만 옮겨 꽂아. 옛 종이도 버리지 않고 두니까 지난주에 뭐라고 적혀 있었는지 다시 꺼내 볼 수 있어.

## ❓ 이해했는지

- 표 하나를 통째로 바꾸는데 왜 화살표 한 개만 바꾸면 되나 → 그림
- 두 쪽이 같은 표에 동시에 커밋하면 무슨 일이 벌어지나 → 작동 원리
- 값이 든 파일을 폴더에서 직접 옮겨 놓으면 그 표는 어떻게 되나 → 흔한 오해
