# ACID

## 📝 정의

ACID는 **트랜잭션이 보장하는 네 가지 성질**이다.

이름이 곧 목록이다 — Atomicity(원자성) · Consistency(일관성) · Isolation(격리성) · Durability(지속성). 넷은 서로 다른 사고를 하나씩 맡는다. 중간에 실패했을 때가 A, 옆에서 다른 트랜잭션이 돌고 있을 때가 I, 커밋한 뒤에 기계가 멈췄을 때가 D, 그 셋을 다 넘긴 뒤에도 데이터가 규칙을 지키고 있는지가 C다.

### 비유
택배 하나 — 통째로 오거나 아예 안 오고, 오는 동안 남이 열어볼 수 없고, 수령 사인을 하면 없던 일이 되지 않는다.

### 예
이체가 실패했다는 알림을 받고 잔액을 확인했는데 한 푼도 안 빠져 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
층: 네 글자는 각각 어디에 걸려 있나
원자성 A :: `COMMIT` 과 `ROLLBACK`. 내가 부르는 명령이다
격리성 I :: 격리 수준과 잠금. 내가 고르는 설정이다
일관성 C :: 이중 쓰기 버퍼와 크래시 복구. 엔진 안의 처리다
지속성 D :: 플러시 설정 · `fsync()` · 저장 장치 · UPS · 백업까지
= 위로 갈수록 내가 부르는 것이고, 아래로 갈수록 DB 밖까지 걸린 약속이다
```

## ⚠️ 해결하는 문제

```도해
대조: 네 가지 보장이 없으면 무슨 일이 생기나
보장이 없으면 || ACID 로
중간에 실패 :: 반만 반영된다 || 전부 없던 일 된다
옆에서 동시에 :: 미확정값이 보인다 || 수준만큼만 보인다
커밋 뒤 정전 :: 확정이 날아간다 || 그대로 남는다
= 셋은 서로 다른 사고이고, 네 글자는 그 사고들의 목록이다
```

명령을 하나씩 따로 실행하면 사고가 각자 다른 자리에서 터진다. 중간에 실패하는 것, 옆에서 도는 트랜잭션이 아직 확정되지 않은 값을 읽어가는 것, 확정한 뒤에 기계가 멈추는 것. 셋을 "데이터가 깨진다" 한 마디로 뭉쳐 부르면 무엇을 손봐야 하는지가 안 보인다.

ACID는 그 사고들에 각각 이름을 붙인 목록이다. 이름이 붙으면 물을 수 있다 — 어디까지가 한 묶음인가, 기본 격리 수준은 무엇인가, 커밋 응답이 왔으면 어디까지 내려간 것인가. MySQL 문서가 네 글자마다 관련 기능을 따로 나열하는 이유도 여기 있다. 넷은 한 스위치가 아니라 서로 다른 장치가 맡는다.

## ⚙️ 작동 원리

원자성은 명령으로 다룬다. PostgreSQL 문서는 트랜잭션을 "여러 단계를 하나의 전부-또는-전무 연산으로 묶는 것" 이라 적고, 원자적이라는 말을 "다른 트랜잭션이 볼 때 전부 일어났거나 아예 안 일어난 것" 으로 정의한다. `BEGIN` 과 `COMMIT` 으로 묶고, 도중에 `ROLLBACK` 을 부르면 지금까지의 갱신이 전부 취소된다. `SAVEPOINT` 를 두면 트랜잭션의 일부만 골라 버리고 나머지를 커밋할 수도 있어서, 원자성의 경계를 손으로 옮기는 셈이 된다.

나머지 셋은 각자 다른 데 걸려 있다. MySQL 문서는 글자마다 관련 기능을 따로 나열한다. 격리성 쪽에는 격리 수준과 `SET TRANSACTION`, 그리고 낮은 수준의 잠금이 온다. 일관성 쪽에는 이중 쓰기 버퍼와 크래시 복구가 온다 — 여기서 말하는 일관성은 크래시로부터 데이터를 지키는 엔진 내부 처리다.

지속성 항목이 가장 길다. 이중 쓰기 버퍼와 `innodb_flush_log_at_trx_commit` 같은 설정으로 시작해서, 저장 장치의 쓰기 버퍼, 배터리 백업 캐시, 운영체제의 `fsync()` 지원, 무정전 전원 장치, 백업 전략까지 같은 목록에 들어간다. 커밋이 성공했다는 응답 하나에 이만큼이 매달려 있다.

## 💡 실제 사례

- **DB 를 고를 때** — "안전한가" 대신 네 글자로 나눠 묻는다. 어디까지가 한 묶음인가, 기본 격리 수준은 무엇인가, 커밋이 어디까지 내려가면 확정인가.
- **부분 취소** — `SAVEPOINT` 를 걸어두면 트랜잭션의 일부만 버리고 나머지를 커밋할 수 있다. 원자성의 경계를 내가 옮기는 자리다.
- **정전 대비 점검** — 지속성은 DB 설정만으로 끝나지 않는다. 플러시 설정, 저장 장치의 쓰기 버퍼, 전원까지 같은 목록에 있으니 함께 본다.

## 🚫 흔한 오해

- **I 가 있으니 동시에 돌아도 서로 안 보인다** — 격리는 켜고 끄는 게 아니라 수준이다. PostgreSQL 의 기본은 Read Committed 이고, 그 수준에서는 반복 불가 읽기와 팬텀 읽기가 그대로 허용된다.
- **커밋이 성공했으면 D 는 DB 가 알아서 지킨다** — MySQL 문서는 지속성을 소프트웨어 기능이 하드웨어 설정과 맞물리는 문제로 적는다. 플러시 설정, 저장 장치의 쓰기 버퍼, `fsync()` 지원, 무정전 전원 장치, 백업 전략이 전부 같은 목록에 있다.
- **C 가 내 업무 규칙까지 봐준다** — MySQL 문서는 일관성을 "크래시로부터 데이터를 보호하는 InnoDB 내부 처리" 로 설명한다. 제약으로 적어두지 않은 규칙은 DB 가 모르고, 모르는 규칙은 지켜주지도 않는다.

## 📝 정리

ACID 는 트랜잭션이 무엇을 어디까지 보장하는지 네 글자로 쪼개 놓은 목록이다. A 는 중간 실패를, I 는 동시 실행을, D 는 커밋 뒤의 고장을 맡고, C 는 그 뒤에도 규칙이 성립하는지를 말한다. 넷은 한 스위치가 아니라 서로 다른 장치가 맡으므로, "안전한가" 대신 네 글자로 나눠 물어야 어디까지 믿어도 되는지가 나온다.

## ❓ 이해했는지

- 격리 수준을 건드리지 않았는데도 같은 줄을 두 번 읽어 값이 달라지는 일은 왜 생기나 → 흔한 오해
- 커밋이 성공했다는 응답을 받고도 그 건을 잃을 수 있는 이유는 무엇인가 → 작동 원리
- "이 DB 는 안전합니다" 라는 대답만으로는 무엇을 알 수 없나 → 해결하는 문제
