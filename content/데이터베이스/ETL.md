# ETL (Extract Transform Load)

## 📝 정의

ETL 은 **뽑고 바꾸고 담는 순서로 데이터를 옮기는 일**이다.

이름 세 글자가 그대로 순서다 — Extract(뽑기), Transform(바꾸기), Load(담기). 여러 시스템에 흩어진 데이터를 하나의 저장소로 모으면서, 옮기는 길에 형식을 맞추고 걸러 낸다.

### 비유
이삿짐. 집에서 짐을 빼고, 버릴 것을 버려 상자에 정리한 다음, 새집의 정해진 방에 넣는다.

### 예
가계부 앱에 카드 내역을 불러오면 뒤죽박죽이던 가맹점 이름이 업종별로 정리된 채로 들어와 있다.

## 🖼️ 그림으로 보기

```도해
흐름: 흩어진 원본이 분석용 표가 되기까지 무엇을 거치나
소스 :: 판매·재고·회계가 저마다 다른 형식으로 있다
E 뽑기 :: 필요한 것만 읽어 낸다
T 바꾸기 :: 걸러 내고 합치고 중복을 지운다
L 담기 :: 목적지 저장소의 표에 넣는다
목적지 :: 맞춰진 표만 놓인다. 여기서 분석한다
= 이름 세 글자가 순서다. 바꾸는 일이 담기 전에 온다
```

## ⚠️ 해결하는 문제

```도해
대조: 원본을 손대지 않고 그대로 합치면 어떻게 되나
그대로 합치면 || ETL 로 옮기면
날짜 형식 :: 시스템마다 다름 || 하나로 맞춘다
중복 행 :: 그대로 쌓인다 || 지우고 넣는다
집계 :: 매번 손으로 || 표만 읽으면 됨
= 옮기는 길에 한 번 맞춰 두면 읽는 쪽이 매번 맞추지 않는다
```

시스템이 셋이면 같은 것을 적는 방식도 셋이다. 날짜를 한쪽은 `2026-08-17`, 다른 쪽은 `08/17/26` 으로 쓰고, 같은 고객이 양쪽에 따로 등록되어 있다. 이걸 그대로 한곳에 부으면 데이터는 모였지만 셀 수가 없다.

ETL 은 맞추는 일을 **옮기는 길에 한 번만** 하게 만든다. 걸러 내기, 정렬, 집계, 조인, 정제, 중복 제거, 검증이 그 자리에서 일어난다. 읽는 사람이 매번 손으로 맞추는 대신, 한 번 짜 둔 파이프라인이 매번 같은 방식으로 맞춘다.

## ⚙️ 작동 원리

세 단계는 이름 순서대로 줄을 서지만, **시간까지 줄을 서지는 않는다.** 대개 세 단계가 겹쳐 돈다 — 뽑는 동안 이미 받은 것을 바꾸고, 바꾼 것부터 담기 시작한다. 뽑기가 다 끝나기를 기다리지 않아서 전체 시간이 줄어든다.

바꾸는 동안 데이터를 잠깐 얹어 두는 자리를 staging 표라고 한다. 여기서 형식을 맞추고 검증한 뒤 목적지로 넘긴다. 나눠 돌릴 때는 날짜나 고객 구간처럼 서로 겹치지 않는 경계로 쪼개는데, 그래야 같은 자리에 두 번 쓰지 않고 실패한 조각만 다시 돌릴 수 있다.

바꾸는 일을 맡는 것은 목적지가 아니라 **따로 둔 변환 엔진**이다. 이 자리를 누가 맡느냐가 ETL 과 ELT 를 가른다.

## 📊 비교: ETL 과 ELT

| | ETL | ELT |
|---|---|---|
| 순서 | 뽑기 → 바꾸기 → 담기 | 뽑기 → 담기 → 바꾸기 |
| 바꾸는 곳 | 따로 둔 변환 엔진 | 목적지 저장소 안 |
| 목적지가 받는 것 | 정리된 결과만 | 원본까지 |
| 목적지에 드는 부담 | 담기만 하면 된다 | 변환까지 맡는다 |
| 잘 맞는 때 | 목적지가 약할 때, 정리 이력을 남겨야 할 때 | 목적지가 탄력적으로 커질 때 |

**왜 순서가 바뀌었나.** ELT 는 ETL 과 오직 변환하는 자리만 다르다. 변환을 목적지 저장소가 맡으면 파이프라인에서 변환 엔진을 아예 뺄 수 있어 구조가 단순해지고, 목적지를 키우면 파이프라인 성능도 같이 커진다. 큰 데이터에서 오래 걸리는 복사 단계를 건너뛰는 것도 이득이다. 클라우드 웨어하우스가 계산 자원을 탄력적으로 늘리게 되면서 이 조건이 실제로 갖춰졌다 — 예를 들어 원본을 BigQuery 에 먼저 담고, 그 안에서 SQL 로 표를 만들어 가는 방식이다. 단, 이 방식은 목적지가 변환을 감당할 만큼 셀 때만 잘 돈다.

## 💡 실제 사례

- **밤마다 도는 적재** — 낮에 쌓인 주문을 새벽에 한 번 뽑아 형식을 맞추고 웨어하우스 표에 넣는다. 일정을 걸어 두거나 사건이 생길 때 돌린다.
- **중복 손님 합치기** — 시스템마다 따로 등록된 같은 고객을 옮기는 길에 한 사람으로 묶어 담는다.
- **원본을 먼저 담고 SQL 로 바꾸기** — 원본을 웨어하우스에 그대로 넣은 뒤 SQL 로 검증된 표를 만들어 간다. 이것이 ELT 다.

## 🚫 흔한 오해

- **T 가 다 끝나야 L 이 시작된다** — 이름 순서는 논리적 순서다. 실제로는 세 단계가 겹쳐 돌아서, 바꾼 조각부터 담기가 시작된다.
- **ELT 가 ETL 보다 항상 낫다** — 변환을 목적지가 맡는 방식이라, 목적지가 그만큼 세지 않으면 변환이 목적지를 잡아먹는다. 목적지가 약하거나 정리 이력을 남겨야 하는 규정이 있으면 ETL 이 맞다.
- **ELT 는 변환을 안 하는 것이다** — 변환을 빼는 게 아니라 자리를 옮긴 것이다. 담은 뒤에 목적지 안에서, 대개 SQL 로 한다.

## 📝 정리

ETL 은 뽑고 바꾸고 담는 순서로 데이터를 옮기는 일이고, 이름이 곧 순서다. 바꾸는 자리를 목적지 안으로 옮기면 순서가 ELT 로 바뀐다. 목적지가 탄력적으로 커지는 클라우드 웨어하우스라면 ELT 가, 목적지가 약하거나 정리 이력을 남겨야 한다면 ETL 이 맞다.

## ❓ 이해했는지

- ELT 는 세 단계 중 무엇이 자리를 바꾼 것인가 → 비교
- 목적지가 약한 서버인데 ELT 로 바꾸면 무엇이 잘못되나 → 흔한 오해
- 뽑기가 다 끝나기 전에 담기가 시작될 수 있는 이유는 → 작동 원리
