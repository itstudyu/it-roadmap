# OLTP vs OLAP

## 📝 정의

OLTP 와 OLAP 는 **한 건을 다루는 쪽과 모아 보는 쪽**이다.

이름의 가운데 글자가 전부다 — T 는 Transaction(거래), A 는 Analytical(분석)이다. OLTP 는 조직이 날마다 벌이는 거래를 일어나는 대로 기록하는 일을 가리키고, OLAP 는 그렇게 쌓인 큰 데이터를 정리해 복잡한 계산과 추세 분석을 하는 기술이다.

### 이름
Online :: 그때그때 바로
Transaction :: 거래 한 건
Analytical :: 모아서 따져 봄
Processing :: 처리하기
= 가운데 글자만 다르다 — "거래를 바로 처리" 와 "모아서 따져 처리". 이름이 곧 쓰임이다

### 비유
가게의 영수증과 월말 결산 — 영수증은 손님 한 사람을 한 장에 적고, 결산은 그 장들을 다 모아 한 줄로 줄인다.

### 예
주문 하나는 누르자마자 끝나는데, 같은 쇼핑몰의 판매 통계 화면은 한참 돌고서야 뜬다.

## 🖼️ 그림으로 보기

```도해
대조: 같은 데이터를 OLTP 와 OLAP 는 어떻게 다르게 쓰나
OLTP |=| OLAP
한 번에 :: 한 건을 넣고 고침 || 수백만 건을 모음
주로 하는 일 :: 쓰기가 많다 || 읽기만 한다
데이터 모양 :: 잘게 정규화 || 별·눈송이 모양
= 한 건을 처리하는 쪽과 모아 보는 쪽. 같은 데이터, 반대 방식
```

## ⚠️ 해결하는 문제

```도해
대조: 운영 DB 에서 바로 집계를 돌리면 무엇이 나빠지나
한 DB 로 다 || 나눠서
집계 질의 :: 자원을 다 먹는다 || 분석 쪽에서만
거래 처리 :: 막혀서 늦어진다 || 영향이 없다
질의 쓰기 :: 조인이 뒤엉킨다 || 이름이 쉬워진다
= 분석을 떼어내는 까닭은 거래를 막지 않으려는 것이다
```

수백만 건을 놓고 합계를 내는 질의는 OLTP 에게 몹시 무겁다. 오래 걸리는 것으로 끝나지 않고 같은 DB 의 다른 거래를 막아 세우기 때문에, 결산 한 번 돌리는 사이 주문이 밀린다. 데이터를 잘게 쪼개 둔 것도 여기서는 짐이 된다 — 무엇을 물어도 조인부터 엮어야 하고, 그러면 담당자 없이는 질의를 쓸 수 없다.

그래서 분석은 밖으로 내보낸다. 운영 DB 에는 이번 회계연도처럼 필요한 기간만 남기고 지난 기록은 데이터 웨어하우스로 옮기고, 분석용 쪽에서는 표와 칸 이름도 사람이 알아보기 쉽게 다시 붙인다.

## ⚙️ 작동 원리

```도해
대조: 줄로 쌓느냐 칸으로 쌓느냐에 따라 무엇이 달라지나
줄로 쌓기 |=| 칸으로 쌓기
한 건 꺼내기 :: 한 자리에 다 있다 || 칸마다 찾아야
한 칸 집계 :: 줄을 다 훑는다 || 그 칸만 읽는다
눌러 담기 :: 값이 뒤섞여 있다 || 닮은 값끼리 모임
= 한 건을 다루면 줄로, 한 칸을 모으면 칸으로 쌓는 게 낫다
```

BigQuery 는 표를 칸 단위로 따로 저장한다. 분석 질의는 보통 표의 몇 칸만 보기 때문에, 백만 줄에서 한 칸의 합을 낼 때 **줄마다 모든 칸을 읽지 않고 그 칸만 읽으면 된다.** 칸 하나에 모인 값은 줄을 가로지른 값들보다 서로 닮아 있어서 더 잘 눌리고, 눌린 만큼 읽는 양도 줄어든다.

거꾸로 한 건을 통째로 넣고 고치는 일은 칸으로 쌓아 두면 칸 수만큼 흩어진 자리를 건드려야 한다. 그 일을 하는 쪽이 OLTP 이고, 그래서 두 쪽은 저장하는 모양부터 다르다.

## 📊 비교

| | OLTP | OLAP |
|---|---|---|
| 정규화 | 잘게 쪼갠다 | 별·눈송이 모양 |
| 갱신 | 그때그때 고친다 | 대개 다시 계산해 채운다 |
| 트랜잭션 | 쓴다 | 안 쓴다 |
| 일감 | 쓰기 많고 읽기 보통 | 읽기 위주, 읽기 전용 |
| 규모 | 수 MB ~ 수 TB | 수백 GB ~ 수 PB |

## 💡 실제 사례

- **결제 한 건 기록** — 주문과 결제를 한 묶음으로 넣고, 중간에 실패하면 앞의 것까지 되돌린다. 반쯤 끝난 상태로 남지 않는 것이 여기서는 가장 중요하다.
- **월말 매출 집계** — 수백만 건을 기간·지역·상품으로 잘라 합친다. 운영 DB 에서 돌리면 주문까지 늦어지니 분석 쪽으로 옮겨 둔 데이터를 쓴다.
- **오래된 기록 넘기기** — 운영 DB 에는 올해치만 두고 지난 기록은 데이터 웨어하우스로 내보낸다.

## 🚫 흔한 오해

- **OLAP 이 OLTP 보다 발전한 것이다** — 세대 차이가 아니라 쓰임 차이다. 한 건을 정확히 넣는 일은 OLAP 쪽에서 아예 하지 않는다. 갱신도 트랜잭션도 없는 것이 그쪽의 정상이다.
- **분석은 전부 따로 떼어내야 한다** — 실제 일감은 대개 어느 한쪽으로 딱 갈리지 않는다. 운영계에 리포트를 바로 돌려야 하는 경우를 HTAP 이라 부르고, 열 저장 인덱스를 얹어 한 판에서 둘 다 하는 길도 있다.
- **분석 화면의 숫자는 지금 숫자다** — 운영 DB 는 거래가 들어올 때마다 바뀌지만 분석 쪽은 훨씬 느린 간격으로 새로 채워진다. 방금 넣은 주문이 아직 안 보이는 것이 고장이 아니다.

## 📝 정리

**"영수증 한 장 쪽과 몽땅 모아 세는 쪽"** 이라고 읽으면 된다. 한 건을 정확히 넣고 고쳐야 하면 OLTP, 수백만 건을 모아 봐야 하면 OLAP 이다. 둘을 나누는 까닭은 집계가 거래를 막아 세우기 때문이고, 나눈 값으로 치르는 대가는 분석 쪽 숫자가 조금 늦다는 것이다.

## 🧒 열 살에게

가게에서는 손님 한 사람이 살 때마다 영수증을 한 장씩 적어 두지? 그러다 한 달이 끝나면 그 영수증을 몽땅 모아서 얼마 벌었는지 한 줄로 줄여. 한 장을 적는 일과 몽땅 모아 세는 일은 하는 방식이 아예 달라.

## ❓ 이해했는지

- 매출 집계를 운영 DB 에서 돌렸는데 주문까지 느려진 까닭은 → 해결하는 문제
- 백만 줄에서 한 칸만 합치는 질의가 칸으로 쌓은 쪽에서 빠른 까닭은 → 작동 원리
- 분석 화면이 방금 넣은 주문을 아직 모르는 일은 왜 생기나 → 흔한 오해
