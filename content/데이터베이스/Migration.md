# Migration (스키마 마이그레이션)

## 📝 정의

마이그레이션은 **스키마 변경을 코드로 적어 이력으로 쌓는** 일이다.

기능이 늘면 표와 칸도 따라 바뀐다. 마이그레이션은 있는 데이터를 지키면서 스키마를 조금씩 맞춰 가는 길이고, 그 변경 하나하나가 소스 파일로 남아 다른 코드와 함께 형상 관리에 들어간다. 어디까지 걸었는지는 DB 안의 이력 표가 기억하기 때문에, 다시 걸면 안 걸린 것만 걸린다.

### 이름
= 영어 migration 은 "옮겨 가기" 다. 값을 옮기는 게 아니라 스키마를 옛 모양에서 새 모양으로 옮겨 세운다

### 비유
집을 고칠 때마다 적어 두는 공사 일지인데, 뜯어낸 벽이 일지 덕에 돌아오지는 않는다.

### 예
앱을 새로 받았더니 프로필에 없던 칸이 하나 생겨 있다. 그 칸을 만들어 넣은 작업이 이것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 스키마 한 번 바꾸는 일이 어떤 자리를 거치나
모델 수정 :: 표에 칸 하나를 더하기로 정한다
차이 뜨기 :: 옛 모델 사본과 견줘 바뀐 데를 찾는다
파일 생성 :: 거는 코드와 되돌리는 코드가 한 짝
사람 검토 :: 이름 바꾸기가 지우기로 나왔는지 본다
적용 :: DB 에 걸고 이력 표에 걸었다고 적는다
@ 다음 변경으로 :: 모델이 또 바뀌면 이 짝이 하나 더 쌓인다
= 스키마 변경 하나가 한 짝씩 쌓여 이력이 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 스키마를 손으로 고치면 무엇이 나빠지나
이력 없이 || 이력으로
지금 모양 :: 서버마다 다르다 || 어디든 같다
적용 여부 :: 기억에 의지한다 || 이력 표가 안다
새 환경 :: 손으로 다시 || 처음부터 재생
= 스키마도 코드처럼 순서와 이력을 가져야 재현된다
```

손으로 고치면 남는 것이 없다. 개발 DB 에만 걸고 검수 DB 를 잊으면 같은 코드가 두 곳에서 다르게 돌고, 그게 언제 갈라졌는지 아무도 모른다. 새 팀원의 빈 DB 를 지금 모양으로 맞추는 일도 누군가의 기억에 달린다.

마이그레이션은 변경마다 파일 하나를 남기고, DB 안의 이력 표에 무엇을 걸었는지 적어 둔다. 그래서 **빈 DB 에 차례로 걸면 지금 스키마가 그대로 만들어지고**, 이미 걸린 DB 에는 새것만 걸린다.

## ⚙️ 작동 원리

```도해
대조: 되돌리기가 어떤 때는 되고 어떤 때는 안 되나
칸을 더했다 |=| 칸을 지웠다
되돌리는 코드 :: 그 칸을 지운다 || 그 칸을 다시 만든다
들어 있던 값 :: 잃을 게 없다 || 안 돌아온다
쓸 수 있나 :: 그대로 되돌린다 || 백업이 있어야 한다
= 구조는 코드가 되돌리지만 값은 코드가 되돌리지 못한다
```

마이그레이션 파일 하나에는 거는 코드와 되돌리는 코드가 한 짝으로 들어 있다. 되돌리는 코드는 구조를 되짚을 뿐이라, 되짚는 과정에서 값이 사라지는 변경은 짝이 성립하지 않는다. EF Core 문서도 원래 값을 안전하게 되살릴 수 있을 때만 되돌리는 코드를 쓰고, 그럴 수 없으면 **차라리 실패시키고 백업 복원을 절차에 넣으라**고 적어 두었다.

PostgreSQL 의 `DROP COLUMN` 은 칸을 물리적으로 뽑아내지 않고 SQL 에서 안 보이게 만든다. 자리는 나중에 행이 갱신되면서 천천히 회수된다. 그러니 되돌리는 코드가 같은 이름의 칸을 다시 만들어도 그 칸은 빈 칸이고, 예전 값은 그리로 돌아오지 않는다.

## 🚨 주의사항

- **이미 운영에 나간 마이그레이션은 지우지 않는다.** 지우면 그것을 되돌릴 길이 없어지고, 뒤에 온 마이그레이션이 세운 가정도 깨진다. 대신 바로잡는 마이그레이션을 하나 더 얹는다.
- **이름 바꾸기는 손으로 고쳐야 한다.** 도구는 이름 바꾸기와 "지우고 새로 만들기" 를 구분하지 못해서 대개 뒤쪽으로 적어 낸다. 그대로 걸면 그 칸의 값이 전부 사라진다.
- **큰 표는 멈춰 선다.** PostgreSQL 에서 칸의 자료형을 바꾸면 표와 인덱스를 통째로 다시 쓰는 일이 벌어져 시간이 오래 걸리고 디스크가 한때 두 배까지 든다. 게다가 `ALTER TABLE` 은 따로 적어 두지 않은 한 가장 센 잠금을 잡는다.

## 💡 실제 사례

- **새 팀원의 첫 실행** — 빈 DB 에 마이그레이션을 처음부터 차례로 걸면 지금 스키마가 그대로 만들어진다.
- **칸 하나를 둘로 나누기** — 새 칸을 널 허용으로 먼저 만들고, 옛 칸에서 값을 옮겨 채우고, 그다음 필수로 조이고, 마지막에 옛 칸을 지운다. 순서를 지켜야 값이 안 날아간다.
- **승인이 필요한 배포** — 도구로 바로 걸지 않고 SQL 스크립트를 뽑아 검토를 받은 뒤 그 스크립트를 건다.

## 🚫 흔한 오해

- **되돌리는 코드가 있으니 언제든 되돌릴 수 있다** — 되돌아오는 건 구조뿐이다. 지운 칸에 들어 있던 값은 코드가 아니라 백업에서만 돌아온다.
- **도구가 뽑아 준 파일은 그냥 걸면 된다** — 이름 바꾸기가 지우고 새로 만들기로 적혀 나오는 자리가 있다. 그대로 걸면 그 칸의 값이 전부 사라지니, 걸기 전에 사람이 읽어야 한다.
- **마이그레이션 도구가 손 SQL 보다 항상 낫다** — SQL 을 승인받거나 손봐야 하는 배포에서는 검토를 거친 스크립트를 쓰는 편이 낫다고 EF Core 문서도 권한다.

## 📝 정리

**"집 고친 것을 날짜대로 적어 둔 그 공사 일지"** 라고 읽으면 된다. 이력 표가 어디까지 걸렸는지 기억하므로 걸기는 그 이력을 앞으로 미는 일이라 언제나 되지만, 되돌리기는 구조만 되짚기 때문에 값을 잃는 변경에서는 성립하지 않는다. 그래서 운영에서는 되돌리는 것보다 바로잡는 마이그레이션을 하나 더 얹는 편이 안전하다.

## 🧒 열 살에게

집을 고칠 때마다 "오늘은 문을 하나 달았다" 하고 공책에 차례로 적어 둔다고 해 봐. 그 공책만 있으면 빈터에 똑같은 집을 처음부터 다시 세울 수 있어. 그런데 벽을 허문 날도 적혀 있긴 해도, 그 벽 안에 있던 물건까지 도로 나오지는 않아.
