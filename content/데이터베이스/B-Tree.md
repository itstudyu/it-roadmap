# B-Tree (B 트리)

## 📝 정의

B-Tree 는 **정렬된 값을 여러 갈래로 갈라 담은 균형 트리**다.

PostgreSQL 문서는 이것을 여러 갈래로 갈라지는 균형 트리(multi-way balanced tree)라고 적는다. 담기는 단위는 쪽(page)이다 — 디스크에서 한 번에 읽어 오는 덩어리를 말한다. 갈래가 많으면 같은 개수를 담는 데 필요한 층이 줄어들고, 그래서 보통 전체 쪽의 99% 넘는 부분이 맨 아래 잎에 몰려 있다. 뒤집어 말하면 뿌리에서 잎까지 내려오는 길에 놓인 위층 전부가 1% 도 안 된다.

### 비유
도서관 안내판. 1층 안내판이 "문학은 3층", 3층 안내판이 "한국 소설은 왼쪽 끝"을 알려주니 책 한 권을 찾으려고 서가를 다 훑을 일이 없다.

## 🖼️ 그림으로 보기

```도해
층: 값 하나를 찾는 데 왜 몇 쪽만 읽으면 되나
뿌리 쪽 :: 한 쪽뿐. 값의 전체 범위를 갈래로 나눈다
중간 쪽 :: 갈래마다 한 쪽. 더 좁은 범위를 다시 나눈다
잎 쪽 :: 전체 쪽의 99% 가 여기다. 값이 정렬돼 있고 행을 가리킨다
표의 행 :: 잎이 가리킨 행 하나만 읽는다
= 층 수만큼만 읽는다. 갈래가 많을수록 층은 좀처럼 안 늘어난다
```

## ⚠️ 해결하는 문제

```도해
대조: 정렬만 해두면 왜 모자라나
한 줄 목록 || 층으로 갈라 담기
값 찾기 :: 앞에서부터 훑는다 || 층마다 갈래를 고른다
읽는 쪽 수 :: 목록 길이만큼 || 층 수만큼
값이 열 배로 :: 읽을 쪽도 열 배 || 층은 거의 그대로
= 정렬해 두는 것만으로는 안 된다. 층으로 갈라 담아야 읽는 횟수가 준다
```

값을 정렬해 한 줄로 늘어놓기만 하면, 찾는 값이 어디 있는지 알려면 그 줄을 훑어야 한다. 줄이 길어질수록 읽어야 하는 쪽 수가 그만큼 늘어난다. 디스크에서 한 쪽을 읽어 오는 것이 비용의 대부분인 자리에서는 이 숫자가 곧 걸리는 시간이다.

B-Tree 는 그 정렬된 값을 층으로 갈라 담는다. 위 쪽은 "이 범위는 저 아래쪽"이라는 갈림길만 담고, 값과 행 위치는 맨 아래 잎에 있다. 그래서 읽는 쪽 수가 데이터 양이 아니라 층 수로 정해진다.

## ⚙️ 작동 원리

한 쪽이 몇 갈래로 갈라지는지가 층 수를 정한다. SQLite 문서는 중간 쪽 하나에 키 K 개와 자식 쪽을 가리키는 포인터 K+1 개가 들어가고, K 의 상한은 그 쪽에 들어가는 만큼이라고 적는다. 기본 쪽 크기가 4096 바이트이니 키가 짧으면 한 쪽이 수백 갈래가 되고, 그러면 층이 하나 늘 때 담을 수 있는 값이 수백 배로 늘어난다.

한 쪽 안의 키는 왼쪽에서 오른쪽으로 커지는 순서로 놓인다. 어떤 키의 왼쪽 포인터는 그보다 작은 값들이 있는 쪽을, 오른쪽 포인터는 큰 값들이 있는 쪽을 가리킨다. 그래서 찾는 값을 들고 뿌리에서 시작하면 층마다 갈래 하나만 고르며 내려가면 된다.

PostgreSQL 쪽에서는 층마다 쪽들이 앞뒤로 이어진 목록으로도 쓰인다고 적는다. 시작 자리를 찾은 다음 잎 층을 옆으로 이어 읽을 수 있기 때문에, 같은지 보는 조건뿐 아니라 범위 조건과 정렬해 꺼내기까지 이 한 모양으로 받는다.

```도해
흐름: 값이 계속 들어오면 트리는 어떻게 자라나
잎 쪽 :: 새 값이 들어갈 자리가 없다
쪼개기 :: 절반을 새 쪽으로 옮긴다
부모 쪽 :: 새 쪽을 가리키는 줄을 받는다
위로 번짐 :: 부모도 꽉 차면 부모가 쪼개진다
뿌리 쪽 :: 뿌리가 넘치면 그 위에 새 뿌리가 선다
= 층은 뿌리가 넘칠 때만 하나 늘어난다. 그래서 좀처럼 깊어지지 않는다
```

## 💡 실제 사례

- **인덱스의 기본값** — `CREATE INDEX` 에 종류를 따로 적지 않으면 B-Tree 가 만들어진다. PostgreSQL 문서는 이 모양이 가장 흔한 상황에 맞는다고 적는다.
- **범위와 정렬** — 값이 정렬된 채 갈라져 있어서 `BETWEEN` 같은 범위 조건에도 쓰이고, 정렬된 결과를 꺼낼 때 정렬 작업 자체를 건너뛰는 데도 쓰인다.
- **앞이 정해진 문자열 검색** — `LIKE 'foo%'` 처럼 앞부분이 고정된 패턴은 이 순서로 자리를 좁힐 수 있다. `LIKE '%bar'` 는 안 된다.

## 🚫 흔한 오해

- **B 트리는 이진 트리의 다른 이름이다** — 한 쪽이 두 갈래로 갈라지는 게 아니다. 키 K 개와 자식 K+1 개를 갖는 여러 갈래 트리이고, 갈래가 많다는 것이 이 모양의 핵심이다.
- **값이 늘어나면 트리가 계속 깊어진다** — 층은 뿌리가 넘칠 때만 하나 늘어난다. 그래서 전체 쪽의 99% 넘는 부분이 맨 아래 잎에 몰려 있게 된다.
- **인덱스는 B-Tree 로 걸어두면 뭐든 빨라진다** — 정렬 순서를 쓸 수 있는 조건에만 걸린다. `LIKE '%bar'` 처럼 앞이 열린 패턴은 순서를 못 쓰니 훑는 것으로 돌아간다.

## 🚨 주의사항

- **키가 길면 층이 깊어진다.** 한 쪽에 들어가는 키 수가 줄어 갈래가 좁아지기 때문이다. PostgreSQL 은 인덱스 항목 하나가 쪽의 약 3분의 1을 넘을 수 없다고 못 박아 둔다.
- **같은 값이 많으면 쪽을 더 잡아먹는다.** PostgreSQL 은 중복된 잎 항목을 하나로 묶어 값은 한 번만 두고 행 위치만 배열로 잇는 중복 제거를 쓴다. 인덱스 크기가 줄고 조회도 함께 빨라진다.

## 📝 정리

B-Tree 는 정렬된 값을 여러 갈래로 갈라 담아 층을 얕게 유지하는 트리다. 값 하나를 찾는 데 읽는 쪽 수가 데이터 양이 아니라 층 수로 정해지고, 층은 뿌리가 넘칠 때만 하나 늘어난다. 인덱스가 빠른 이유는 정렬해 뒀다는 데 있는 게 아니라 이 모양에 있다.

## ❓ 이해했는지

- 행이 열 배로 늘었는데도 값 하나 찾는 데 읽는 쪽 수가 거의 그대로인 이유는 → 그림
- 트리에 새 층이 하나 생기는 순간은 언제인가 → 작동 원리
- 인덱스를 걸어뒀는데 `LIKE '%검색어%'` 에서 안 걸리는 이유는 → 흔한 오해
