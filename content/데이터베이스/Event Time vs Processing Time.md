# Event Time vs Processing Time (발생 시각과 처리 시각)

## 📝 정의

발생 시각과 처리 시각은 **한 사건에 달린 서로 다른 두 시계**다.

Beam 문서는 둘을 이렇게 갈라 적는다. 발생 시각은 "사건이 일어난 시각으로, 그 항목 자체에 박힌 값" 이고, 처리 시각은 "그 항목이 파이프라인의 어느 단계에서 실제로 처리된 시각으로, 처리하는 기계의 시계가 정한다". 흐르는 것을 세는 일에서 거의 모든 어려움이 이 둘의 차이에서 나온다.

### 이름
Event :: 사건
Processing :: 처리
Time :: 시각
= 앞은 사건이 난 시각, 뒤는 그걸 처리한 시각. 이름이 곧 두 시계의 이름이다

### 비유
지진은 땅이 흔들린 순간과 멀리 있는 관측소의 바늘이 그것을 종이에 적은 순간이 서로 다르다.

### 예
지하철에서 끊긴 채 찍힌 사진들이 지상에 나오자마자 한꺼번에 올라가는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
대조: 같은 사건을 두 시계로 세면 무엇이 달라지나
처리 시각 |=| 발생 시각
어디서 오나 :: 기계의 벽시계 || 사건에 박힌 값
다시 돌리면 :: 값이 달라진다 || 값이 그대로다
늦게 온 것 :: 도착한 칸에 || 원래 칸으로
기다림 :: 안 기다린다 || 늦은 것을 기다림
= 한 사건에 시계가 둘 달려 있다. 어느 쪽으로 세느냐에 따라 답이 갈린다
```

## ⚠️ 해결하는 문제

```도해
대조: 처리 시각으로만 세면 집계가 어떻게 되나
시각을 안 나누면 || 두 시각을 나누면
자정 직전 주문 :: 다음 날로 센다 || 그날로 센다
장애 뒤 몰림 :: 한 칸에 뭉친다 || 제 칸에 흩어진다
어제 재집계 :: 숫자가 달라진다 || 숫자가 같다
= 처리 시각만 보면 집계는 사건이 아니라 기계가 언제 바빴는지를 세게 된다
```

흐르는 것은 순서대로 오지 않는다. 폰이 지하철에서 끊겨 있었고, 중간 큐가 밀렸고, 한 조각을 다시 읽느라 늦었다. 이 늦음은 예외가 아니라 기본값이다.

처리 시각만 쓰면 집계는 사건이 아니라 **기계의 사정**을 센다. 30분 밀렸던 큐가 풀리면 그 30분치가 한 칸에 뭉쳐 들어와 트래픽 급증처럼 보이고, 자정 직전 주문은 다음 날 매출이 된다. 더 나쁜 것은 되돌릴 수 없다는 점이다. 같은 원본으로 어제치를 다시 돌리면 처리 시각이 달라지므로 숫자도 달라진다. 발생 시각을 쓰면 몇 번을 다시 돌려도 같은 답이 나온다 — 값이 사건에 박혀 있기 때문이다. 다만 공짜는 아니다. 늦게 오는 것을 얼마나 기다릴지 정해야 하고, 그 기다림이 곧 결과가 늦어지는 시간이다.

## ⚙️ 작동 원리

기본값은 대체로 처리 시각 쪽이다. Azure Stream Analytics 문서는 도착 시각과 응용 시각 둘 중에 고르게 하는데, `TIMESTAMP BY` 절을 안 쓰면 도착 시각으로 처리한다고 적어 둔다. 발생 시각으로 세겠다는 것은 **한 줄을 더 써서 기본값을 바꾸는 일**이다. Flink 쪽도 같은 구조다 — 발생 시각은 "레코드가 엔진에 들어오기 전에 그 안에 박혀 있는" 값이라 소스에서 뽑아 붙여 줘야 한다.

바꾸는 순간 새 문제가 따라온다. 처리 시각으로 세면 지금이 몇 시인지 벽시계를 보면 되지만, 발생 시각으로 세면 "이 시각까지는 다 들어왔다" 를 누군가 판단해 줘야 한다. 그 판단이 [[Watermark]] 다. Azure 문서는 그 값을 어림으로 만든다고 적는다 — 들어온 것이 있으면 **지금까지 본 가장 큰 발생 시각에서 순서 어긋남 허용치를 뺀 값**이고, 아무것도 안 들어오면 어림한 도착 시각에서 지각 허용치를 뺀 값이다.

허용치를 벗어난 것은 그냥 넘어가지 않는다. Azure 는 지각한 것을 버리거나 그 시각을 워터마크 값으로 **고쳐 붙이도록** 고르게 하고, 고쳐 붙인 경우 `System.Timestamp` 만 바뀌고 원본의 발생 시각 필드는 그대로 남는다. 반대쪽 끝도 막혀 있다. 보내는 쪽 시계가 앞서 가서 발생 시각이 도착 시각보다 5분 넘게 **미래로** 찍혀 오면 그 사건은 그대로 버려진다. 이 5분은 사람이 못 바꾸는 고정값이다.

시계가 저마다 다른 기기를 다룰 때가 가장 어렵다. 낡은 기기 하나가 시계를 잘못 맞춰 두면 전체 워터마크가 그 기기 때문에 끌려다닌다. Azure 는 이를 위해 서브스트림을 둔다. `TIMESTAMP BY ... OVER deviceid` 처럼 키를 주면 기기마다 워터마크를 따로 굴려서, 한 기기의 시계 오차가 다른 기기의 집계를 늦추지 않는다.

## 💡 실제 사례

- **모바일 앱 지표** — 비행기 모드였던 폰이 착륙 뒤 한꺼번에 올려 보내는 기록. Azure Stream Analytics 라면 `TIMESTAMP BY` 한 줄을 써야 비행 중 사용량이 착륙 시각에 뭉치지 않는다. 그 줄이 없으면 기본값인 도착 시각으로 센다.
- **시계가 제각각인 기기 수천 대** — Azure 는 `TIMESTAMP BY ... OVER deviceid` 로 기기마다 시각 정책을 따로 매긴다. 문서는 기본 지각 허용치 5초가 이런 곳에는 너무 작으니 5분부터 잡고 기기 시계 편차를 보며 맞추라고 적는다.
- **장애 뒤 재처리** — 밀렸던 큐가 풀릴 때 처리 시각으로 세면 없던 급증이 생긴다. Azure 문서가 워터마크를 도착 시각과 응용 시각에서 끌어내는 이유도 이것이다 — 둘 다 브로커에 남아 있어서 다시 돌려도 같은 값이 나온다.

## 🚫 흔한 오해

- **발생 시각은 그냥 데이터에 있는 시각 아닌가** — 있어도 쓰이지 않는다. 기본값은 도착 시각이고, `TIMESTAMP BY` 같은 지정을 해야 그 값으로 센다.
- **발생 시각을 쓰면 결과도 그만큼 정확해진다** — 대신 늦어진다. 늦은 것을 기다리는 시간이 그대로 결과 지연이 되고, 허용치를 크게 잡으면 지연도 같이 커진다.
- **발생 시각이 항상 낫다** — 보내는 쪽 시계를 믿는다는 뜻이다. 기기 시계가 틀어져 있으면 틀린 칸에 들어가므로, 그냥 쌓아 두는 보관 용도에는 도착 시각이 더 안전하다.

## 🚨 주의사항

- **지각한 것의 시각이 조용히 고쳐질 수 있다.** Azure 는 허용치를 넘긴 것을 버리거나 워터마크 값으로 당겨 붙인다. 당겨 붙이면 원본 필드와 집계에 쓰인 시각이 서로 달라진다.
- **너무 이른 것도 버려진다.** 보내는 쪽 시계가 5분 넘게 앞서면 그대로 사라진다. 출력에 안 보이니 알아채기가 늦다.
- **오래된 것을 밀어 넣으면 지각으로 걸린다.** 과거치를 흐름에 그냥 붓는 방식은 지각 허용치에 막힌다. 옛 기록은 배치 경로로 넣는 편이 낫다.

## 📝 정리

**"사건의 시계와 기계의 시계, 둘 중 무엇으로 셀 것인가"** 라고 읽으면 된다. 처리 시각은 늘 있고 안 기다려도 되지만 다시 돌리면 답이 달라지고, 발생 시각은 몇 번을 다시 돌려도 같은 답이 나오지만 늦게 오는 것을 얼마나 기다릴지 정해야 한다. 발생 시각을 고르는 순간 워터마크가 따라온다.

## 🧒 열 살에게

땅이 흔들린 시각하고, 멀리 있는 기계가 그 흔들림을 종이에 적은 시각은 서로 달라. 언제 흔들렸는지 알고 싶으면 종이에 적힌 시각 말고 땅이 흔들린 시각을 세야 해.

## ❓ 이해했는지

- 지하철에서 찍힌 사진이 지상에서 한꺼번에 올라갈 때 집계가 왜 틀어지나 → 해결하는 문제
- 발생 시각으로 세기로 했더니 결과가 왜 더 늦게 나오나 → 작동 원리
- 기기 시계를 믿는 것이 왜 위험한가 → 흔한 오해
