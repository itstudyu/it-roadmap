# 구조화 데이터 (Structured Data)

## 📝 정의

구조화 데이터는 **모양을 미리 정해두고 담은 데이터**다.

행과 열로 된 표에 넣고, 열마다 무엇이 들어가는지와 어떤 형식인지를 먼저 정해둔다. 담는 쪽에 규칙을 걸어두는 대신 꺼낼 때 조건을 걸어 고를 수 있게 된다.

### 비유
칸이 나뉜 약통. 요일과 시간에 맞춰 넣어야 하는 대신, 화요일 아침 약을 찾을 때 통 전체를 뒤지지 않아도 된다.

## 🖼️ 그림으로 보기

```도해
흐름: 흩어진 값이 물어볼 수 있는 데이터가 되기까지 무엇을 거치나
스키마 :: 어떤 열이 있고 무슨 형식인지 먼저 정한다
입력 :: 정해둔 형식에 맞는 값만 들어간다
검사 :: 나이 칸에 글자를 넣으면 거부된다
질문 :: 나이가 30 을 넘는 사람만 달라고 묻는다
< 결과 :: 조건에 맞는 줄만 골라 돌려준다
= 모양을 먼저 정해뒀기 때문에 나중에 물을 수 있게 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 나이를 25 로도 스물다섯으로도 적어두면 어떻게 되나
형식 없이 || 형식을 정하고
값의 모양 :: 제각각이다 || 하나로 맞는다
찾기 :: 전부 읽어본다 || 조건으로 고른다
평균 내기 :: 할 수 없다 || 한 줄이면 된다
= 담을 때 규칙을 지킨 만큼 꺼낼 때 물을 수 있는 것이 늘어난다
```

고객 정보를 그냥 글로 적어두면 "김철수, 010-1234-5678, 서울"처럼 사람은 읽을 수 있지만 기계는 어디까지가 이름이고 어디부터가 지역인지 모른다. 서울 사는 사람만 세려면 모든 줄을 읽고 사람이 판단해야 한다.

형식이 흔들리면 더 곤란해진다. 나이를 어떤 줄에는 25로, 어떤 줄에는 스물다섯으로 적어두면 평균을 낼 수가 없다. 열마다 형식을 못 박아두면 그런 값은 애초에 들어가지 못하고, 그래서 나중에 조건을 걸거나 합계를 내는 일이 가능해진다.

## ⚙️ 작동 원리

```도해
층: 데이터는 얼마나 정돈되어 있나
구조화 :: 표. 열마다 뜻과 형식이 정해져 있다
반구조화 :: JSON, XML. 이름표는 있고 형식은 느슨하다
비구조화 :: 글, 그림, 영상. 정해진 자리가 없다
= 위로 갈수록 묻기 쉽고 아래로 갈수록 담기 쉽다
```

구조화 데이터를 만들려면 먼저 스키마를 정한다. 표 이름과 열 이름을 적고 열마다 형식을 붙인다. 이름은 글자, 나이는 정수, 만든 시각은 시간 같은 식이다. 이 선언 자체가 검사 규칙이 되어서 형식에 안 맞는 값은 들어가는 순간 거부된다.

담기고 나면 SQL 같은 언어로 묻는다. 어떤 열이 있고 무슨 형식인지 이미 정해져 있으니 조건을 걸어 고르거나 평균과 합계를 내는 일을 짧게 적을 수 있다. 특정 열에 색인을 붙여 찾는 속도를 올리는 것도 열이 정해져 있어서 가능한 일이다.

## 💡 실제 사례

- **고객 명부** — 이름, 전화번호, 사는 곳을 각각 다른 열에 담으면 지역별로 세는 일이 한 줄로 끝난다.
- **주문 기록** — 금액을 숫자 형식으로 못 박아두면 월별 합계를 바로 낼 수 있다.
- **로그를 표로 옮기기** — 줄글로 쌓인 기록에서 시각, 사용자, 동작을 뽑아 열로 나누면 그때부터 집계할 수 있다.

## 🚫 흔한 오해

- **표처럼 생겼으면 구조화 데이터다** — 표 모양인 것과 형식이 지켜지는 것은 다르다. 한 열에 25와 스물다섯이 섞여 있으면 표에 담겨 있어도 집계할 수 없다.
- **JSON도 구조화 데이터다** — 이름표는 붙어 있지만 문서마다 항목이 달라도 되므로 표만큼 엄격하지 않다. 그래서 그 중간을 반구조화라고 따로 부른다.
- **구조화가 언제나 낫다** — 모양을 먼저 정해야 담을 수 있다. 무엇이 들어올지 모르는 데이터나 문서와 이미지처럼 열로 나눌 수 없는 것에는 맞지 않는다.

## 📝 정리

구조화 데이터는 열과 형식을 미리 정해둔 표에 담긴 데이터다. 담을 때 규칙을 지키게 만드는 대신 조건 검색과 집계가 가능해진다. 모양을 정할 수 없는 것들은 반구조화나 비구조화 쪽에 남는다.

- JSON을 구조화가 아니라 반구조화라고 부르는 이유는?
- 담기 전에 스키마를 먼저 정해두면 나중에 무엇이 가능해지나?
