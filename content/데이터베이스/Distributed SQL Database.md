# Distributed SQL Database (흩어 놓은 관계형 데이터베이스)

## 📝 정의

분산 SQL DB 는 **여러 대에 흩어 놓고도 한 대처럼 쓰는 관계형 DB**다.

관계형 DB 는 오래 한 대짜리였다. 더 큰 기계로 바꾸는 것 말고는 늘릴 방법이 없어서, 커진 서비스는 표를 손으로 쪼개 여러 대에 나눠 붙였다. 그 순간부터 조인도 트랜잭션도 앱이 떠맡는다. 분산 SQL DB 는 그 쪼개기를 DB 안으로 들여놓은 것이다 — 밖에서는 SQL 과 트랜잭션이 그대로 보이고, 안에서는 표가 조각나 여러 대에 흩어져 있다.

### 이름
Distributed :: 여러 대에 흩어진
SQL :: 표와 질의의 말
Database :: 자료를 담는 곳
= 붙여 읽으면 "여러 대에 흩어 놓은, SQL 로 묻는 저장소". 흩어 놓고도 SQL 을 안 버린 것이 이름의 요점이다

### 비유
창구는 하나인데 뒤에 창고가 여러 개인 가게. 손님은 창구만 보지만 물건은 창고마다 나뉘어 있고, 창고 하나가 닫혀도 다른 창고가 그 몫을 낸다.

### 예
DB 사양을 최고로 올려놓고도 쓰기가 밀려서, 표를 손으로 쪼개 여러 대에 나눠 붙이던 그 작업이다.

## 🖼️ 그림으로 보기

```도해
층: 여러 대인데 왜 한 대로 보이나
접속 창구 :: 앱은 주소 하나에 붙고 SQL 도 그대로 쓴다
트랜잭션 :: 여러 대에 걸친 쓰기를 한 묶음으로 확정한다
조각 :: 표를 키 범위로 잘라 여러 대에 나눠 둔다
복제본 :: 조각마다 사본이 여럿. 과반이 살면 계속 쓴다
= 아래 세 층이 하는 일을 맨 위가 감춘다. 안 감춰지는 것이 이 기술의 값이다
```

## ⚠️ 해결하는 문제

```도해
대조: 한 대짜리 관계형 DB 를 계속 키우면 어디서 막히나
한 대로 키우면 || 흩어 놓으면
쓰기 상한 :: 그 한 대가 끝 || 대를 늘려 넘는다
그 대가 죽으면 :: 다 멈춘다 || 남은 대가 받는다
먼 지역 :: 늘 바다를 건넌다 || 가까운 대가 받는다
= 더 큰 기계는 언젠가 없다. 늘리는 축을 세로에서 가로로 바꾼 것이다
```

한 대짜리 DB 를 키우는 방법은 하나뿐이다. 더 빠른 기계로 갈아 끼우는 것. 그런데 그 기계에도 끝이 있고, 끝에 닿으면 남는 수는 표를 손으로 쪼개 여러 대에 나눠 붙이는 것뿐이다. 그때부터 조각을 넘는 조인은 앱 코드가 되고, 조각을 넘는 트랜잭션은 사실상 포기하게 된다. 확장을 얻는 대가로 SQL 을 잃는 셈이다.

NoSQL 은 그 거래를 아예 받아들인 쪽이었다. 분산 SQL DB 는 거래를 거부한 쪽이다. Aurora DSQL 문서는 스스로를 "트랜잭션 작업에 맞춘 서버리스 분산 관계형 DB" 라 적고, 단일 리전 99.99% · 다중 리전 99.999% 가용성과 함께 강한 일관성과 스냅숏 격리를 갖춘 ACID 트랜잭션을 내세운다. 쪼개는 일을 앱이 아니라 DB 가 맡으면, 앱은 표가 몇 대에 걸쳐 있는지 몰라도 된다.

## ⚙️ 작동 원리

```도해
흐름: 쓰기 하나가 확정되기까지 무엇을 거치나
앱 :: SQL 을 접속 창구 한 곳에 보낸다
조각 찾기 :: 그 키가 어느 조각에 있는지 본다
과반 합의 :: 그 조각의 사본 과반이 같은 값을 적는다
시계 :: 확정 시각을 붙이고 그 시각이 지나기를 기다린다
< 앱 :: 커밋 응답. 이후 누가 읽어도 이 값이 보인다
= 한 대가 혼자 정하던 순서를 과반과 시계가 나눠 정한다
```

먼저 표를 자른다. Spanner 문서는 표를 이어진 키 범위인 **split(조각)** 으로 나눈다고 적고, 조각 경계를 크기와 부하에 따라 자동으로 더하고 뺀다고 밝힌다. 한 조각에 읽기가 몰리면 부하 기반 분할이 그 조각을 다시 쪼개 다른 기계로 흩는다. 사람이 샤드 개수를 정하지 않는다.

다음은 안 죽게 만드는 일이다. 조각마다 사본을 서로 다른 장애 구역에 두고, 사본들 사이의 일치는 Paxos 라는 합의 절차가 맡는다. 문서 표현으로 "투표하는 사본의 과반이 살아 있는 한, 그중 하나가 리더로 뽑혀 쓰기를 처리한다". 기계 한 대가 죽어도 그 조각은 계속 쓰인다.

마지막이 순서다. 한 대짜리 DB 에서는 순서가 저절로 정해지지만 여러 대에서는 아니다. Spanner 는 TrueTime 이라는, 구글 데이터센터의 모든 기계가 몇 밀리초 오차 안에서 전역 시각을 알 수 있게 하는 장치를 쓴다. 리더는 커밋 시각을 붙인 뒤 **그 시각이 실제로 지나갈 때까지 기다렸다가**(commit wait) 응답한다. 그래서 "결과를 받아 본 사람이 있으면, 다른 모든 읽는 쪽도 그 결과를 본다" 가 성립한다. Aurora DSQL 은 다른 길을 골랐다 — 잠그지 않고 진행시키다 커밋 시점에 충돌을 잡는 낙관적 동시성 제어라서, 부딪치면 대기 대신 직렬화 오류가 돌아오고 앱이 재시도한다.

## 💡 실제 사례

- **한 대의 상한에 닿았을 때** — 읽기는 복제본으로 나눠도 쓰기는 못 나누는 상태가 오면, 갈아 끼울 더 큰 기계가 아니라 늘릴 축을 바꾼다.
- **여러 지역에서 같이 쓰는 서비스** — Aurora DSQL 의 다중 리전 클러스터는 두 리전에 각각 접속점을 두고 둘 다 읽고 쓸 수 있으면서 하나의 논리 DB 로 보인다.
- **손으로 쪼갠 것을 되돌릴 때** — 앱이 들고 있던 "이 키는 몇 번 DB" 표와 조각을 넘는 조인 우회 코드가 통째로 사라진다. 앱이 지던 [[Sharding]] 을 DB 가 진다.

## 🚫 흔한 오해

- **분산이니까 언제나 더 낫다** — 한 대로 충분한 서비스에서는 잃는 것만 남는다. 지역을 넘는 쓰기는 빛의 속도만큼 느리고, 못 쓰는 SQL 기능 목록이 붙고, 재시도 코드를 새로 써야 한다.
- **PostgreSQL 호환이면 쓰던 걸 그대로 옮기면 된다** — Aurora DSQL 문서는 외래 키를 앱 계층에서 검증하라 하고, 트리거와 PL/pgSQL 과 임시 테이블을 안 쓴다고 적는다. 격리 수준은 Repeatable Read 로 고정이고 한 트랜잭션이 고칠 수 있는 줄은 3,000 개까지다.
- **키는 아무렇게나 만들어도 DB 가 알아서 흩어 준다** — Spanner 문서는 1씩 늘어나는 정수를 키로 쓰면 언제나 키 공간의 맨 끝에 넣게 되어 한 대에만 쓰기가 몰린다고 경고한다. UUID 를 쓰거나 비트를 뒤집으라고 권한다.

## 🚨 주의사항

- **재시도는 선택이 아니다.** 낙관적 동시성 제어를 쓰는 쪽에서는 충돌이 대기가 아니라 오류로 온다. 같은 일을 두 번 해도 결과가 같도록 짜 두지 않으면 재시도가 사고가 된다.
- **핫스팟은 설계 시점에 정해진다.** 자동 분할이 있어도 쓰기가 한 키 근처에만 몰리면 조각을 아무리 쪼개도 그 줄은 안 짧아진다. 키를 정하는 순간이 마지막 기회다.
- **옮기기 전에 못 쓰는 목록부터 본다.** 클러스터당 DB 하나, 연결은 한 시간 뒤 끊김, DDL 은 한 트랜잭션에 하나 같은 제약이 코드가 아니라 운영 습관을 바꾼다.

## 📝 정리

**"쪼개는 일을 앱 대신 DB 가 맡은 관계형 저장소"** 라고 읽으면 된다. 표는 키 범위로 잘려 여러 대에 흩어지고, 조각마다 사본 과반이 합의해서 쓰고, 전역 시각으로 순서를 맞춰서 밖에서는 여전히 한 대처럼 보인다. 대신 SQL 기능 일부와 키 설계의 자유를 내주므로, 한 대로 버틸 수 있는 동안은 안 옮기는 편이 싸다.

## 🧒 열 살에게

가게 하나에 창고가 여러 개면 물건이 아무리 많아져도 창고를 더 지으면 되지? 손님은 여전히 창구 한 곳에서만 사니까 창고가 몇 개인지도 몰라. 대신 잘 나가는 물건을 한 창고에만 쌓아 두면 창고를 아무리 늘려도 그 물건 사려는 줄은 안 짧아져.

## ❓ 이해했는지

- 한 대짜리 DB 를 최고 사양으로 올려도 결국 못 넘는 벽은 무엇인가 → 해결하는 문제
- 여러 대에 흩어 놓고도 커밋 순서가 뒤엉키지 않는 이유는 무엇인가 → 작동 원리
- 자동으로 조각을 나눠 주는데도 한 대만 뜨거워지는 일이 왜 생기나 → 흔한 오해

## 🔗 관련 용어

- [[CAP Theorem]] — 여러 대로 흩어지면 무엇까지 동시에 가질 수 있는지를 다루는 자리
- [[Partitioning]] — 표를 조각내는 일. 여기서는 사람이 아니라 DB 가 한다
- [[Replication]] — 조각마다 사본을 두는 일. 과반 합의가 얹히는 바탕
- [[NoSQL]] — 같은 벽 앞에서 SQL 과 트랜잭션을 내주고 확장을 택한 쪽
- [[Sharding]] — 앱이 손으로 하던 그 일. 분산 SQL DB 는 그걸 DB 안으로 들여놓은 것이다
