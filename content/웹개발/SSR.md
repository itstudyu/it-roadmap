# SSR (Server Side Rendering)

## 📝 정의

SSR은 **서버가 완성된 HTML을 만들어 보내는 방식**이다.

브라우저는 받은 HTML을 그리기만 하면 된다. 화면에 들어갈 데이터를 서버가 미리 채워 넣고 보내기 때문이다.

### 비유
완성된 도시락. 받자마자 열어서 먹으면 된다. 재료만 받아 직접 조리하는 쪽은 먹기까지 시간이 더 걸린다.

## 🖼️ 그림으로 보기

```도해
흐름: 주소를 열면 화면이 언제 보이나
브라우저 :: 페이지 주소를 요청한다
서버 :: 화면에 필요한 데이터를 조회한다
서버 :: 데이터를 끼워 HTML을 완성한다
< 브라우저 :: 받은 HTML을 바로 그린다
< 브라우저 :: 뒤이어 JS를 받아 버튼을 살린다
= 글자는 먼저 보이고 클릭은 조금 뒤에 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 빈 HTML을 먼저 보내면 어떻게 되나
브라우저가 조립 || 서버가 조립
첫 화면 :: JS 받고 나서 || 받자마자 보임
검색 로봇 :: 빈 화면으로 봄 || 내용까지 읽음
느린 기기 :: 조립이 더 느림 || 차이가 적다
= 화면을 누가 조립하느냐가 첫 화면이 뜨는 시점을 정한다
```

빈 HTML을 먼저 보내는 방식은 브라우저가 JS를 받아 실행하고 데이터를 다시 요청한 다음에야 글자가 뜬다. 기기가 느리거나 회선이 나쁘면 그 사이가 길어지고, 그동안 사용자는 흰 화면을 본다.

검색 로봇도 같은 문제를 만난다. HTML을 가져갔는데 안이 비어 있으면 그 페이지에 무슨 내용이 있는지 알 수 없다. SSR은 서버가 데이터를 채워 보내서 두 경우를 한 번에 해결한다.

## ⚙️ 작동 원리

서버는 요청이 올 때마다 데이터베이스를 읽고 템플릿에 값을 채워 HTML 문자열을 만든다. 브라우저가 하던 조립을 서버가 대신 하는 것이라 사용자가 늘면 그 부담이 서버 쪽에 쌓인다.

그래서 자주 바뀌지 않는 페이지는 만들어 둔 HTML을 캐시에 올려 다시 쓴다. 같은 결과를 매번 새로 조립할 이유가 없기 때문이다.

## 💡 실제 사례

- **상품 상세 페이지** 검색 결과에 내용이 잡혀야 해서 서버에서 만들어 내려보낸다.
- **뉴스 기사** 본문은 HTML에 담아 바로 보이게 하고, 댓글처럼 늦어도 되는 것은 나중에 불러온다.
- **로그인 후 대시보드** 사용자마다 내용이 달라 캐시가 안 되므로, 서버 부담을 재보고 브라우저 조립으로 넘기기도 한다.

## 🚫 흔한 오해

- **SSR이 CSR보다 빠르다** — 빠른 것은 첫 화면이 뜨는 시점이다. 페이지를 옮겨 다닐 때는 매번 서버를 다시 거쳐야 해서 오히려 느려질 수 있다.
- **SSR이면 JavaScript가 필요 없다** — 화면을 그리는 데만 필요 없다. 버튼과 입력이 동작하려면 뒤이어 JS를 받아 붙여야 한다.
- **서버에서 만들어도 서버 부하는 비슷하다** — 요청마다 조립이 일어난다. 브라우저가 하던 일을 서버가 떠안는 것이라 부담의 위치가 옮겨온다.

## 📊 비교

| | SSR | CSR |
|---|---|---|
| 첫 화면 | 서버가 완성해 보냄 | 브라우저가 조립 |
| 페이지 이동 | 매번 서버를 거침 | 필요한 데이터만 받음 |
| 검색 노출 | 내용이 그대로 잡힘 | 따로 대응이 필요 |
| 부담이 가는 곳 | 서버 | 사용자 기기 |

## 📝 정리

SSR은 서버가 데이터를 채워 완성한 HTML을 보내는 방식이다. 첫 화면이 빨리 뜨고 검색 로봇이 내용을 읽을 수 있는 대신, 조립 부담이 서버로 옮겨온다.

## ❓ 이해했는지

- 검색 결과에 페이지 내용이 잡혀야 할 때 SSR을 고르는 이유는?
- SSR 페이지인데도 JavaScript를 내려받는 이유는 무엇인가?
- 사용자가 늘었을 때 SSR에서 먼저 부담이 걸리는 곳은 어디인가?
