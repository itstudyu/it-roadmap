# CSS (Cascading Style Sheets)

## 📝 정의

CSS는 **겹쳐 쌓인 규칙**으로 문서의 생김새를 정하는 스타일 언어다.

이름이 곧 구조다 — Cascading, 곧 "여러 스타일시트가 한 문서의 표현에 함께 영향을 준다" 는 것이 이 언어의 기본 설계 원리다. 그래서 CSS 를 아는 일은 속성 이름을 외우는 일이 아니라, 규칙이 겹쳤을 때 무엇이 이기는지를 아는 일이다.

### 이름
Cascading :: 위에서 흘러내림
Style :: 생김새
Sheets :: 규칙을 적은 장
= 붙여 읽으면 "생김새 규칙을 적은 장이 위에서 흘러내린다". 흘러내려 겹친 자리에서 하나가 이긴다

### 비유
여러 사람이 같은 서류에 저마다 고쳐 적었을 때, 누가 어디에 적었는지로 어느 글씨를 따를지 정하는 사무실 규칙.

### 예
웹페이지를 그대로 인쇄했더니 메뉴와 광고가 빠지고 본문만 나온 종이, 그 차이를 만든 것이 CSS 다.

### 직접
아무 웹페이지에서 개발자 도구로 요소 하나를 골라 Styles 칸을 보라. 취소선이 그어진 선언이 캐스케이드에서 진 규칙이다.

## 🖼️ 그림으로 보기

```도해
층: 같은 글자에 규칙이 여러 개 걸리면 무엇이 이기나
!important :: 못 덮게 못 박아 둔 선언
style 속성 :: 태그에 직접 붙인 한 줄
선택자 점수 :: 더 좁게 짚은 규칙이 이긴다
쓴 순서 :: 여기까지 같으면 마지막 줄이 이긴다
= 겹친 규칙은 섞이지 않는다. 위층부터 따져 이긴 하나가 생김새를 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 생김새를 문서에서 떼어내면 무엇이 달라지나
문서 안에 || 스타일시트로
색 하나 바꾸기 :: 파일을 전부 고친다 || 한 줄만 고친다
같은 문서 :: 한 모습만 된다 || 화면·인쇄 따로
글의 뜻 :: 표시에 섞인다 || 태그만 남는다
= 무엇인지와 어떻게 보일지를 갈라놓은 것이 CSS 다
```

[[HTML]] 명세는 **매체별로 표현을 손보는 장치를 자기 범위에서 빼두었다.** 그 자리를 CSS 가 맡는다. MDN 의 표현으로는 "화면에서, 종이에서, 음성으로, 또 다른 매체에서 요소가 어떻게 표현될지를 기술하는" 언어다.

덕분에 문서 하나로 화면과 인쇄를 모두 감당하고, 색을 한 번 고쳐 전체를 바꾼다. 대신 여러 스타일시트의 규칙이 한 요소로 몰리는 일이 생기고, 그 몰림을 정리하는 장치가 캐스케이드다.

## ⚙️ 작동 원리

겹친 선언은 정해진 순서로 걸러진다. 먼저 **누가 쓴 것인지(원산지)와 중요도**를 보고, 그 둘이 같을 때에야 선택자 점수를 본다. MDN 이 특별히 못 박는 대목이 여기다 — 사용자 스타일시트의 `:root p { color: red }` 와 저자 스타일시트의 `p { color: blue }` 가 부딪히면, 점수가 낮은 쪽이 이겨서 문단은 파랗게 나온다.

점수는 한 숫자가 아니라 세 칸이다.

| 칸 | 무엇이 들어가나 | 하나당 |
|---|---|---|
| **ID** | `#nav` | 1-0-0 |
| **CLASS** | `.btn`, `[type="radio"]`, `:hover` | 0-1-0 |
| **TYPE** | `p`, `td`, `::before` | 0-0-1 |

왼쪽 칸부터 차례로 견주고, 앞 칸에서 결판이 나면 뒤 칸은 보지 않는다. 그래서 `#nav` 하나가 `.btn` 열 개를 이긴다. `*` 는 요소에 맞기는 하지만 점수는 0-0-0 이다.

글자색처럼 **상속되는 속성**은 그 요소에 아무 선언도 안 걸렸을 때 부모의 계산값을 물려받는다. 명세는 "상속은 부모의 속성값을 자식에게 전파한다" 고 적고, 상속되지 않는 속성은 그 자리에서 초깃값을 쓴다고 덧붙인다.

## 📊 비교: 누가 쓴 규칙이 이기나

| 세기 | 누가 쓴 것 | 중요도 |
|---|---|---|
| 가장 약함 | 브라우저 기본 | 보통 |
| ↓ | 사용자 | 보통 |
| ↓ | 저자(개발자) | 보통 |
| ↓ | 저자(개발자) | `!important` |
| ↓ | 사용자 | `!important` |
| 가장 셈 | 브라우저 기본 | `!important` |

`!important` 가 붙으면 순서가 뒤집힌다. 보통 선언에서는 저자가 사용자를 이기지만, `!important` 끼리 붙으면 사용자가 저자를 이긴다. 시력이 나쁜 사용자가 브라우저에 걸어둔 큰 글씨 설정을 개발자가 덮어쓰지 못하게 하려고 이렇게 만들었다. 진행 중인 트랜지션은 이 표에서 가장 센 것보다도 위에 있고, 애니메이션은 보통 선언과 `!important` 선언 사이에 끼어든다.

## 💡 실제 사례

- **디자인 갈아 끼우기** — 문서는 그대로 두고 스타일시트만 바꿔 화면을 새로 만든다.
- **인쇄용 스타일** — 같은 페이지를 종이에 낼 때 메뉴와 배너를 빼고 본문만 남긴다.
- **남의 스타일 덮기** — 가져다 쓴 컴포넌트의 색을 바꿀 때, 선택자 점수를 올리거나 `!important` 를 붙여 캐스케이드에서 이긴다.

## 🚫 흔한 오해

- **선택자를 길게 쓰면 이긴다** — 길이가 아니라 칸으로 센다. `#nav` 하나가 태그를 열 개 이어 붙인 선택자를 이긴다.
- **`!important` 를 붙이면 무조건 이긴다** — 같은 원산지 안에서만 확실하다. 사용자와 브라우저가 붙인 `!important`, 그리고 진행 중인 트랜지션이 그 위에 있다.
- **인라인 `style` 로 적으면 깔끔하게 해결된다** — 그 줄은 보통 저자 규칙 중 가장 세다. 점수가 훨씬 높은 선택자를 새로 써도 CSS 파일에서는 못 덮는다.

## 📝 정리

**"겹친 규칙 중에 이긴 하나가 생김새를 정한다는 약속"** 이라고 읽으면 된다. 이름의 Cascading 이 곧 그 이긴 하나를 고르는 절차다. 원산지와 중요도가 먼저고, 선택자 점수는 그 둘이 같을 때 비로소 쓰인다.

## 🧒 열 살에게

한 장의 종이에 여러 사람이 저마다 다른 글씨로 고쳐 적으면 어느 걸 따라야 할지 헷갈리지? 그래서 누가 어디에 적은 글씨가 이기는지 순서를 미리 정해 놨어. 겹친 자리에서는 그 순서대로 딱 하나만 골라서, 글자 색이랑 크기가 그 하나대로 정해져.

## ❓ 이해했는지

- 점수가 훨씬 높은 선택자를 새로 썼는데도 색이 안 바뀌는 일이 왜 생기나 → 흔한 오해
- 사용자가 브라우저에 큰 글씨 설정을 걸어두면 저자의 `!important` 는 어떻게 되나 → 비교
- 아무 규칙도 안 걸린 글자가 부모와 같은 색으로 나오는 까닭은 → 작동 원리
