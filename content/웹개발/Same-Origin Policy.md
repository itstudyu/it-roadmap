# Same-Origin Policy (동일 출처 정책)

## 📝 정의

Same-Origin Policy는 **다른 출처의 응답을 못 읽게 막는 브라우저 규칙**이다.

이름이 규칙을 그대로 말한다 — 출처(origin)가 같은(same) 것끼리만이다. 출처는 스킴과 호스트와 포트 셋을 묶은 것이고, 셋이 전부 같을 때만 같은 출처다. 표준은 출처가 같은 둘은 서로를 믿고 같은 권한을 가진 것으로 보고, 출처가 다르면 서로에게 적일 수 있다고 본다.

### 비유
아파트 현관. 다른 동 사람도 초인종은 누를 수 있지만 안을 들여다볼 수는 없다.

### 예
은행에 로그인해 둔 채로 다른 탭에서 낯선 사이트를 열어도 그쪽이 내 잔액을 못 읽는 것이 이 규칙이다.

## 🖼️ 그림으로 보기

```도해
대조: 다른 출처의 자원은 어디까지 쓸 수 있나
읽기 |=| 싣기·보내기
이미지 :: 픽셀을 못 꺼낸다 || 화면에 뜬다
스크립트 :: 에러가 가려진다 || 그대로 실행된다
API 응답 :: 스크립트가 못 본다 || 요청은 도착한다
= 불러다 쓰는 것은 되고, 그 안을 읽는 것은 안 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 브라우저 안의 사이트들이 서로를 믿으면 어떻게 되나
경계 없이 || 출처로 갈라서
열어둔 탭 :: 서로 안을 읽는다 || 서로를 모른다
저장한 값 :: 아무나 꺼내 간다 || 제 출처만 읽는다
프레임 안 :: 부모를 읽는다 || 부모를 못 읽는다
= 브라우저는 남남인 코드를 한 자리에서 돌린다. 출처가 그 사이의 담이다
```

브라우저는 서로 모르는 사람이 쓴 코드를 같은 프로그램 안에서 동시에 돌린다. 지금 열려 있는 탭 열 개는 열 곳에서 온 남남이고, 그중 하나만 악의를 가져도 나머지가 위험해진다. 담이 없다면 광고로 끼워 넣은 프레임 하나가 옆 탭에 열린 메일 본문을 읽어 밖으로 보낼 수 있다.

표준은 이 담을 출처로 긋는다. 그러면서 링크를 눌러 넘어가는 것이나 이미지를 불러오는 것처럼 웹을 굴러가게 하던 일은 그대로 열어두고, **응답을 읽는 것**만 막는다. 이 절충 덕에 웹은 서로를 엮어 쓰면서도 격리된다. 막은 자리에 문을 내야 할 때 쓰는 것이 [[CORS]] 다.

## ⚙️ 작동 원리

출처 판정은 [[URL]] 의 앞부분만 본다. 경로도 쿼리도 보지 않고, 스킴과 호스트와 포트 셋을 글자 그대로 견준다. 표준에 적힌 판정은 한 줄이다 — 셋이 전부 같으면 같은 출처, 하나라도 다르면 다른 출처.

| 견주는 두 주소 | 같은 출처인가 |
|---|---|
| `https://a.com/x` 와 `https://a.com/y` | 같다 — 경로는 안 본다 |
| `https://a.com` 과 `http://a.com` | 다르다 — 스킴이 다르다 |
| `https://a.com` 과 `https://a.com:8443` | 다르다 — 포트가 다르다 |
| `https://a.com` 과 `https://api.a.com` | 다르다 — 호스트가 다르다 |

같은 회사 것이라거나 상위 도메인이 같다거나 하는 사정은 판정에 안 들어간다. 그래서 같은 도메인이라도 [[HTTPS]] 로 옮긴 페이지는 옛 http 판과 남남이다.

판정하고 막는 쪽은 브라우저 하나다. 서버는 이 계산에 참여하지 않는다.

## 💡 실제 사례

- **캔버스에 남의 이미지 그리기** — 다른 출처의 이미지를 그린 캔버스는 오염된 것으로 표시되고, 거기서 데이터를 꺼내려 하면 SecurityError 가 난다.
- **정체를 알 수 없는 콘솔 에러** — 다른 출처에서 불러온 스크립트가 터지면 에러 기록으로 넘어오는 내용이 제한된다. `crossorigin` 을 붙이고 서버가 허락해야 내용이 보인다.
- **프레임으로 붙인 위젯** — 결제 창이나 광고를 다른 출처의 프레임으로 넣으면 화면에는 나오지만, 부모 쪽 스크립트가 그 안의 창 객체에 손댈 수 있는 것은 몇 가지뿐이다.

## 🚫 흔한 오해

- **다른 출처면 아무것도 못 불러온다** — 이미지도 스크립트도 CSS 도 폰트도 그대로 불러와 쓴다. 막히는 건 불러온 것의 내용을 스크립트가 읽는 쪽이다.
- **도메인만 같으면 같은 출처다** — 스킴과 포트까지 셋이 다 같아야 한다. `http://a.com` 과 `https://a.com` 도, `a.com` 과 `api.a.com` 도 서로 다른 출처다.
- **이 정책이 있으니 남이 내 API 를 마음대로 못 부른다** — 부르는 것은 안 막는다. 응답을 읽는 것만 막는다. 그래서 폼 전송으로 요청만 보내는 [[CSRF]] 는 이 정책으로 안 막히고, 브라우저를 안 거치는 요청은 애초에 대상이 아니다.

## 🚨 주의사항

- **막는 쪽은 브라우저뿐이다.** `curl`, 서버끼리 부르는 요청, 모바일 앱에는 이 정책이 없다. 인증과 권한 검사를 서버에 두지 않으면 실제로 지켜지는 것은 없다.
- **localhost 도 포트가 다르면 다른 출처다.** 프런트를 3000, API 를 8000 에 띄우면 같은 컴퓨터인데도 남남이다. 개발 첫날 이 벽을 만나는 자리가 여기다.
- **저장소도 출처 단위로 갈라져 있다.** Web Storage 와 IndexedDB 는 출처마다 따로 주어져서, 한 출처의 스크립트가 다른 출처의 저장소를 읽거나 쓸 수 없다.
- **담 안으로 코드가 들어오면 끝이다.** [[XSS]] 로 내 페이지에 스크립트가 심어지면 그 코드는 같은 출처이므로, 이 정책은 아무것도 막지 않는다.

## 📝 정리

동일 출처 정책은 브라우저 안에 담을 세워, 출처가 다른 코드가 서로의 내용을 읽지 못하게 한다. 불러오는 것과 보내는 것은 그대로 열어둔 덕에 웹은 여전히 서로를 엮어 쓴다. 이 담에 문을 내는 방법이 [[CORS]] 다.

## ❓ 이해했는지

- `https://a.com` 과 `https://api.a.com` 이 서로 다른 출처인 까닭은 → 작동 원리
- 다른 출처의 이미지를 캔버스에 그린 뒤 데이터를 꺼내려 하면 왜 막히나 → 실제 사례
- 남의 사이트에 놓인 폼이 내 서버로 값을 보내는 것은 왜 안 막히나 → 흔한 오해

## 🔗 관련 용어

- [[CORS]] — 이 정책이 막은 자리에 서버가 문을 내는 방법
- [[URL]] — 출처를 이루는 스킴·호스트·포트가 적혀 있는 곳
- [[HTTPS]] — 스킴이 달라지면 출처도 달라지므로 http 판과 남남이 된다
- [[CSRF]] — 이 정책이 쓰기 요청을 안 막기 때문에 남는 공격
- [[XSS]] — 담 안으로 코드를 밀어 넣어 이 정책을 없는 것으로 만드는 공격
