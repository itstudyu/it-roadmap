# Service Worker (서비스 워커)

## 📝 정의

Service Worker는 **웹앱과 네트워크 사이에서 요청을 가로채는 프록시**다.

뒤에 붙은 워커라는 말이 실행 자리를 알려준다 — 화면을 움직이는 자바스크립트와 다른 [[Thread]] 에서 돈다. 그래서 DOM 에 손을 못 대고, 페이지 하나에 매달린 것이 아니라 출처 단위로 등록되어 그 문서보다 오래 산다.

### 이름
Service :: 심부름을 맡는
Worker :: 화면 밖에서 도는 일꾼
= 붙여 읽으면 "화면 밖에서 심부름을 맡는 일꾼". 화면과 다른 자리에서 돌아 화면에 직접 손을 못 댄다

### 비유
오가는 편지를 모두 먼저 받아보는 집 앞 우편함이라, 안에 있는 것이면 밖에 나가지 않고 바로 건넨다.

### 예
지하철에서 신호가 끊겼는데도 어제 열어 본 웹앱 화면이 그대로 뜨는 그 순간이다.

### 직접
웹앱을 하나 열고 개발자 도구의 Application 탭에서 Service Workers 를 눌러 보라. 등록된 워커와 activated·waiting 같은 상태가 보인다.

## 🖼️ 그림으로 보기

```도해
흐름: 서비스 워커가 있는 페이지의 요청은 어디로 가나
페이지 :: 파일이나 데이터를 요청한다
서비스 워커 :: 그 요청을 브라우저 안에서 먼저 받는다
캐시 :: 이미 받아둔 응답이 있나 본다
네트워크 :: 없을 때만 밖으로 나간다
< 서비스 워커 :: 어느 쪽에서 왔든 페이지에 응답으로 건넨다
= 페이지는 네트워크에 직접 닿지 않는다. 사이에 앉은 워커가 먼저 답한다
```

## ⚠️ 해결하는 문제

```도해
대조: 네트워크가 끊기면 웹앱은 어떻게 되나
워커 없이 || 서비스 워커로
지하철에서 :: 오류 화면만 뜬다 || 받아둔 것이 뜬다
두 번째 방문 :: 매번 다시 받는다 || 있는 건 안 받는다
서버 장애 :: 아무것도 못 본다 || 껍데기는 뜬다
= 웹앱이 네트워크에 목숨을 걸지 않게 하는 것이 이 워커의 일이다
```

웹앱은 파일을 서버에서 받아 와야 뜬다. 그래서 지하철이나 엘리베이터에서 연결이 끊기면 어제까지 잘 쓰던 화면조차 못 열고, 서버가 잠깐 죽으면 아무것도 안 보인다. 설치한 앱과 웹앱의 차이가 사용자에게 가장 크게 느껴지는 자리가 여기다.

서비스 워커는 요청을 가로챌 자리를 하나 만들어 이 문제를 없앤다. 표준은 이 워커를 네트워크와 문서 사이에 두어 **오프라인일 때도 문서에 내용을 줄 수 있게** 하는 것이라고 적어두었고, 그러기 위해 HTTP [[Cache]] 와 닮은 요청·응답 저장소를 함께 준다. 서버 앞에 놓는 [[Proxy]] 와 하는 일이 같고, 놓인 자리만 브라우저 안이다.

## ⚙️ 작동 원리

```도해
흐름: 새로 올린 서비스 워커는 왜 바로 안 먹히나
등록 :: 페이지가 워커 파일의 주소를 알려준다
설치 :: 파일 내용이 전과 다르면 install 이 돈다
대기 :: 옛 워커를 쓰는 탭이 남아 있으면 기다린다
활성화 :: 그 탭이 다 닫히면 activate 가 돈다
제어 :: 그때부터 요청을 가로채기 시작한다
= 설치는 조용히 끝나고, 자리를 넘겨받는 것은 옛 탭이 다 닫힌 뒤다
```

표준은 워커의 상태를 여섯으로 적어두었다 — parsed, installing, installed, activating, activated, redundant. 개발자가 손대는 자리는 그 사이에 끼는 두 사건이다. `install` 에서는 앞으로 쓸 파일을 미리 받아 저장소에 넣고, `activate` 에서는 옛 판이 남긴 저장소를 지운다.

새 워커가 곧바로 활성화되지 않는 이유는, 옛 워커를 쓰는 페이지가 하나도 남지 않을 때까지 기다리게 되어 있기 때문이다. 그래서 배포했는데 안 바뀌는 것처럼 보이는 일이 생긴다.

워커는 페이지 하나가 아니라 **범위**를 맡는다. 범위를 안 적으면 워커 파일이 놓인 폴더가 그대로 범위가 되고, 한 출처에 범위가 서로 다른 워커를 여러 개 둘 수도 있다.

## 💡 실제 사례

- **비행기 모드에서 여는 웹앱** — 설치할 때 받아둔 화면 파일을 워커가 저장소에서 꺼내 주므로, 연결이 없어도 화면이 그대로 뜬다.
- **이 학습 앱 자신** — `sw.js` 가 설치 때 화면과 단어 데이터를 통째로 받아두어, 그 뒤로는 네트워크를 타지 않고 지하철에서도 똑같이 열린다.
- **배포한 뒤에도 옛 화면이 보이는 일** — 새 워커가 대기 중이면 탭을 전부 닫고 다시 열 때까지 옛 판이 계속 응답한다.

## 🚫 흔한 오해

- **파일을 올리면 바로 적용된다** — 새 파일은 설치까지만 되고 대기한다. 옛 워커를 쓰는 탭이 다 닫혀야 활성화되니, 새로고침 한 번으로는 안 바뀐다.
- **서비스 워커도 자바스크립트니까 화면을 고칠 수 있다** — DOM 에 손을 못 댄다. 화면과 다른 자리에서 돌기 때문에, 페이지에 무엇을 알리려면 메시지로 주고받아야 한다.
- **캐시가 빠르니 전부 캐시로 주면 된다** — 워커가 옛 응답을 계속 건네면 사용자는 고친 것을 영영 못 본다. 무엇을 저장소에서 주고 무엇을 네트워크에서 받을지 요청마다 정해야 한다.

## 🚨 주의사항

- **HTTPS 가 아니면 등록되지 않는다.** [[HTTPS]] 로 준 문서에서만 쓸 수 있고 `localhost` 만 예외다. 사내 http 주소에 올리면 개발 컴퓨터에서만 되고 실제 사용자에게는 아예 안 걸린다.
- **워커 파일도 같은 출처여야 한다.** 다른 출처의 주소를 넘기면 등록이 SecurityError 로 실패한다. [[Same-Origin Policy]] 가 여기에도 걸린다.
- **저장소 이름을 판마다 바꾼다.** `activate` 에서 옛 저장소를 지우지 않으면 판이 늘어날 때마다 사용자 기기에 계속 쌓인다.

## 📝 정리

**"요청을 먼저 받아 답하는 그 중간 자리"** 라고 읽으면 된다. 그 자리에 응답을 저장해 둘 수 있어서 웹앱이 오프라인에서도 열린다. 대신 설치와 활성화를 거치게 되어 있어서, 새로 올린 워커가 자리를 잡는 시점은 배포한 순간이 아니다.

## 🧒 열 살에게

집 앞에 오는 편지를 다 먼저 받아 두는 상자가 하나 있다고 해 봐. 뭘 달라고 하면 그 상자가 먼저 뒤져 보고, 안에 있으면 밖에 나가지 않고 바로 꺼내 줘. 그래서 지하철에서 인터넷이 끊겨도 어제 봤던 화면이 그냥 떠.

## ❓ 이해했는지

- 새 `sw.js` 를 올렸는데 새로고침해도 옛 화면이 나오는 까닭은 → 작동 원리
- 연결이 끊긴 지하철에서도 이 앱의 화면이 뜨는 까닭은 → 해결하는 문제
- 서비스 워커 안에서 화면의 요소를 직접 고칠 수 없는 까닭은 → 흔한 오해

## 🔗 관련 용어

- [[Proxy]] — 서비스 워커가 브라우저 안에서 맡는 역할과 같은 것
- [[Cache]] — 오프라인에 쓸 응답을 워커가 담아두는 곳
- [[HTTPS]] — 서비스 워커를 등록하려면 먼저 갖춰야 하는 조건
- [[Same-Origin Policy]] — 워커 파일을 같은 출처에만 둘 수 있게 하는 규칙
- [[Thread]] — 워커가 화면과 따로 도는 실행 자리
