# CORS (Cross-Origin Resource Sharing)

## 📝 정의

CORS는 **다른 출처의 응답을 읽어도 되는지 정하는 규칙**이다.

브라우저는 기본적으로 지금 열린 페이지와 출처가 다른 곳의 응답을 스크립트에 넘기지 않는다. 출처는 프로토콜과 도메인과 포트를 합친 것이고, 셋 중 하나만 달라도 다른 출처다. CORS는 서버가 응답 헤더로 "이 출처는 괜찮다"고 밝히는 방법이다.

### 비유
클럽 입구의 명단. 문 앞 직원이 명단에 이름이 있는지 확인하고 없으면 돌려보낸다.

## 🖼️ 그림으로 보기

```도해
흐름: 다른 도메인의 API 를 부르면 무슨 일이 일어나나
브라우저 :: 요청에 Origin 헤더를 붙여 보낸다
서버 :: 요청을 받아 그대로 처리한다
< 서버 :: 응답에 허용 출처를 적어 보낸다
브라우저 :: 적힌 출처가 내 출처와 맞는지 본다
브라우저 :: 맞으면 넘겨주고 아니면 에러를 낸다
= 막는 쪽은 서버가 아니라 브라우저다. 요청은 이미 갔다
```

## ⚠️ 해결하는 문제

```도해
대조: 브라우저가 아무 출처의 응답이나 읽게 하면 어떻게 되나
검사 없이 || CORS 로
남의 사이트 :: 내 쿠키로 조회 || 응답을 못 읽는다
정상 연동 :: 구분 없이 막힘 || 서버가 열어준다
허용 범위 :: 전부 아니면 전무 || 메서드까지 지정
= 무조건 막는 것과 서버가 고른 곳만 여는 것의 차이다
```

로그인한 상태로 다른 사이트를 열면, 그 사이트의 스크립트도 내 브라우저 안에서 돈다. 검사가 없다면 그 스크립트가 내 쿠키를 실어 은행 API를 부르고 응답까지 읽을 수 있다. 그래서 브라우저는 출처가 다른 응답을 기본으로 막는다.

그런데 프런트엔드와 API 서버가 다른 도메인에 있는 구성은 흔하다. 전부 막으면 이런 정상적인 연동까지 못 하게 된다. CORS는 서버가 허용할 출처를 직접 적게 해서 둘을 갈라낸다.

## ⚙️ 작동 원리

```도해
흐름: PUT 요청은 왜 두 번 오가나
브라우저 :: 본 요청 전에 OPTIONS 를 먼저 보낸다
서버 :: 허용 메서드와 허용 헤더를 답한다
브라우저 :: 보내려던 것이 그 안에 드는지 본다
브라우저 :: 들면 그때 본 요청을 보낸다
< 서버 :: 본 응답에도 허용 출처를 다시 적는다
= 사전 요청은 엉뚱한 요청이 서버에 닿기 전에 확인하는 절차다
```

GET과 HEAD, 그리고 몇 가지 정해진 형식의 POST는 사전 요청 없이 바로 나간다. 반면 PUT이나 DELETE, JSON 본문을 쓰는 POST, 직접 만든 헤더가 붙은 요청은 OPTIONS를 먼저 보낸다.

인증 정보를 함께 보내려면 양쪽에 설정이 하나씩 더 필요하다. 클라이언트는 요청에 자격 증명을 포함하겠다고 밝히고, 서버는 응답에 이를 허용한다고 적는다. 이때는 허용 출처를 전체로 열어둘 수 없고 도메인을 정확히 적어야 한다.

## 💡 실제 사례

- **로컬 개발** — 프런트엔드는 localhost에서 돌고 API는 다른 도메인에 있어서, 서버에 개발 주소를 허용 출처로 넣어둔다.
- **지도나 결제 위젯** — 발급받은 키를 등록한 도메인에서만 쓰게 막아, 키가 새어 나가도 남의 사이트에서는 안 먹힌다.
- **화면을 나눠 붙인 서비스** — 팀마다 다른 도메인에 올린 조각들을 한 페이지에 모을 때 서로의 출처를 열어준다.

## 🚫 흔한 오해

- **CORS 에러가 뜨면 요청이 안 간 것이다** — 대개 이미 갔고 서버도 처리했다. 브라우저가 응답을 스크립트에 안 넘겼을 뿐이라, DELETE 가 실제로 실행된 다음에 에러만 보이는 일도 생긴다.
- **CORS 는 서버를 보호하는 장치다** — 보호 대상은 사용자의 브라우저다. 스크립트를 거치지 않고 서버로 직접 부르면 CORS 와 상관없이 그대로 처리된다.
- **모든 출처를 허용해두면 다 해결된다** — 쿠키를 함께 보내는 요청에는 전체 허용을 쓸 수 없다. 그리고 열어둔 순간 아무 사이트나 내 API 응답을 읽을 수 있다.

## 🚨 주의사항

- **에러 메시지는 일부러 자세하지 않다.** 콘솔에 찍힌 문구만 보고 서버 코드를 고치기 전에, 응답 헤더가 실제로 무엇인지 먼저 본다.
- **사전 요청도 요청이다.** 캐시 시간을 짧게 두면 요청마다 왕복이 두 번씩 생겨 느려진다.

## 📝 정리

CORS는 다른 출처의 응답을 스크립트에 넘겨도 되는지 서버가 헤더로 밝히는 규칙이다. 판단은 브라우저 안에서 일어나므로, 요청 자체를 막는 방화벽과는 하는 일이 다르다.

## ❓ 이해했는지

- CORS 에러가 떴는데 서버 로그에는 요청이 찍혀 있다면 무슨 일이 일어난 것인가 → 흔한 오해
- JSON 본문을 담은 POST 요청이 OPTIONS 를 먼저 보내는 이유는 → 작동 원리
- 브라우저가 다른 출처의 응답을 그냥 읽게 두면 로그인한 사용자에게 무슨 일이 생기나 → 해결하는 문제
