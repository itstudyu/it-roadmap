# Pagination (페이지네이션)

## 📝 정의

Pagination 은 **목록을 여러 쪽으로 잘라 주는 방식**이다.

쪽을 나누는 길은 두 갈래다. 앞에서 몇 개를 건너뛸지 숫자로 세는 **offset** 방식과, 마지막으로 본 자리를 표로 받아 "그 다음부터" 를 달라고 하는 **cursor** 방식이다. 공개 API 는 한 쪽에 담는 개수에 상한을 두는데, GitHub REST API 는 `per_page` 를 100 까지만 받고 그보다 큰 값은 조용히 100 으로 내려 쓴다.

### 비유
쪽 번호로 아무 쪽이나 펼치는 책과, 읽던 자리에 끼워 둔 책갈피의 차이다.

## 🖼️ 그림으로 보기

```도해
흐름: 만 건짜리 목록을 서버는 어떻게 나눠 주나
클라이언트 :: "스무 건만 주세요" 하고 묻는다
서버 :: 목록에서 그만큼만 잘라 담는다
< 응답 :: 스무 건 + 다음 쪽을 찾을 표 하나
클라이언트 :: 받은 표를 붙여 다음 쪽을 묻는다
@ 다시 서버로 :: 표가 없으면 끝. 있으면 한 쪽 더
= 한 번에 다 주는 게 아니라, 다음을 찾을 표와 함께 한 쪽씩 준다
```

## ⚠️ 해결하는 문제

```도해
대조: 목록을 한 번에 다 주면 무엇이 문제인가
통째로 || 나눠서
응답 크기 :: 만 건이 다 온다 || 스무 건만 온다
첫 화면 :: 다 받아야 뜬다 || 바로 뜬다
서버 부담 :: 한 요청이 다 읽는다 || 필요한 만큼만
= 목록은 자라고 화면은 그대로다. 그래서 잘라서 준다
```

목록은 시간이 갈수록 늘어나는데 한 화면에 보이는 줄 수는 그대로다. 통째로 내려주는 API 는 데이터가 만 건이 되는 날 응답이 무거워지고, 그 요청 하나가 서버의 여유를 다 먹는다. 요청하는 쪽이 개수를 마음대로 정할 수 있으면 그것 자체가 서버를 넘어뜨리는 손잡이가 된다.

그래서 나눠 주는 쪽이 **개수의 상한을 쥔다.** GitHub 은 GraphQL API 에서 `first` 나 `last` 를 반드시 적게 하고 그 값을 1~100 으로 묶어 두는데, 서버로 오는 과한 요청을 막기 위한 것이라고 밝히고 있다. Azure 의 API 설계 지침도 `limit=25`, `offset=0` 같은 기본값을 주고 상한을 넘는 요청에는 상한까지만 주거나 오류로 답하라고 권한다.

## 📊 비교: offset 방식과 cursor 방식

```도해
대조: offset 과 cursor 중 무엇을 골라야 하나
offset 방식 |=| cursor 방식
가리키는 값 :: 몇 개를 건너뛸까 || 어디 다음부터
목록이 바뀔 때 :: 밀려서 빠뜨린다 || 그 자리를 짚는다
깊은 쪽 :: 건너뛴 몫을 센다 || 값으로 바로 찾는다
아무 쪽 열기 :: 번호로 바로 || 앞뒤로만
= 쪽 번호를 줄 참이면 offset, 목록이 움직이면 cursor 다
```

offset 이 어긋나는 자리는 이렇다. 2쪽을 보고 3쪽으로 넘어가는 사이에 앞쪽 항목 하나가 지워지면 목록 전체가 한 칸씩 위로 밀려서, 3쪽의 첫 항목이 되었어야 할 것이 아무 쪽에도 안 나온다. 반대로 항목이 추가되면 같은 것이 두 쪽에 겹쳐 나온다.

cursor 방식은 "몇 번째" 가 아니라 **마지막으로 본 값** 을 기억한다. `id > 55` 처럼 조건으로 건너뛰기 때문에 앞쪽에서 무엇이 생기고 사라지든 이어지는 자리가 흔들리지 않고, 정렬 기준에 색인이 있으면 깊은 쪽도 빠르다. 대신 47쪽으로 바로 뛰는 일은 못 한다 — 앞뒤로만 넘길 수 있다.

## 💡 실제 사례

- **무한 스크롤** — 화면 끝에 닿을 때마다 응답이 준 표를 그대로 붙여 다음 쪽을 이어 받는다.
- **관리자 목록 화면** — 47쪽으로 바로 뛰어야 하는 화면이라 쪽 번호, 즉 offset 을 쓴다.
- **API 로 전체 내려받기** — 한 번에 100건까지만 받고, 응답 헤더가 준 다음 쪽 주소를 따라 끝까지 돈다.

## 🚫 흔한 오해

- **cursor 방식이 언제나 낫다** — 아무 쪽이나 바로 열어야 하는 화면에서는 쓸 수 없다. 앞뒤로 한 쪽씩만 갈 수 있어서, 쪽 번호가 필요하면 offset 을 남겨 둬야 한다.
- **쪽을 나눠 주면 서버가 그만큼만 읽는다** — offset 은 건너뛴 줄까지 서버가 계산한다. 1,000쪽을 열면 앞의 999쪽 몫을 다시 세서 버리는 셈이다.
- **쪽 번호가 있으면 순서는 고정된다** — 정렬 기준이 겹치면 같은 값끼리의 순서는 매 요청마다 달라질 수 있다. 그래서 한 건이 새어 나가거나 두 번 나온다.

## 🚨 주의사항

- **정렬을 유일하게 만들어라.** 날짜만으로 정렬하면 같은 날짜인 것들의 순서가 두 요청 사이에 달라져 항목이 빠진다. 날짜 + id 처럼 겹치지 않는 값을 함께 걸어야 한다. 관계형 DB 는 정렬을 안 적으면 기본 순서를 보장하지 않는다.
- **다음 쪽 주소는 응답이 준 것을 그대로 써라.** 쪽을 가리키는 이름은 엔드포인트마다 다를 수 있다. 직접 조립하면 그쪽이 방식을 바꾼 날 조용히 깨진다.
- **한 쪽의 크기는 서버가 정한다.** 클라이언트가 1000건을 달라고 해도 상한까지만 주거나 잘못된 요청으로 답한다.

## 📝 정리

Pagination 은 목록을 자르는 일이 아니라 **다음을 어디서 이을지 정하는 일**이다. 번호로 이으면 아무 쪽이나 펼칠 수 있는 대신 목록이 움직일 때 어긋나고, 마지막으로 본 값으로 이으면 어긋나지 않는 대신 앞뒤로만 갈 수 있다.
