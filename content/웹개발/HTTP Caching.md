# HTTP Caching (HTTP 캐싱)

## 📝 정의

HTTP Caching 은 **응답을 얼마나 들고 있어도 되는지 헤더로 정하는 규약**이다.

규약이 말하는 캐시는 "응답 메시지를 담아 두는 지역 저장소와 그것을 넣고 꺼내고 지우는 부속" 이다. [[Caching]] 이 "가까이 두고 다시 쓴다" 는 생각이라면, 이쪽은 그 생각을 HTTP 위에서 조문으로 만든 것이다 — 누가 담아도 되고, 얼마나 신선하며, 만료된 뒤엔 무엇을 해야 하는지까지 정해져 있다.

### 이름
HyperText :: 서로 이어지는 글
Transfer :: 옮겨 나름
Protocol :: 약속
Caching :: 두고 다시 쓰기
= 붙여 읽으면 "글을 옮기는 약속 위에서 두고 다시 쓰기". 얼마나 들고 있을지가 그 약속 안에 적혀 있다

### 비유
반찬통에 붙인 "○일까지" 쪽지. 만든 사람이 기한을 적어 주고, 꺼내 먹는 사람은 그 쪽지만 보고 판단한다.

### 예
고친 화면이 안 보여 새로고침을 몇 번씩 눌러 본 적이 있다면, 담아둔 사본의 기한이 아직 안 지난 것이다.

### 직접
컴퓨터에서 F12 로 네트워크 칸을 열고 같은 페이지를 두 번 새로고침해 보라. 두 번째 줄에는 크기 대신 캐시나 `304` 가 뜬다.

## 🖼️ 그림으로 보기

```도해
흐름: 서버가 준 응답을 캐시는 언제까지 그대로 쓰나
서버 :: 응답에 `Cache-Control: max-age` 를 붙인다
캐시 :: 응답과 그 기한을 함께 저장한다
기한 안 :: 같은 요청은 서버까지 가지 않는다
기한 뒤 :: `If-None-Match` 로 아직 같은지만 묻는다
< 서버 :: 같으면 `304` 만 준다. 본문은 안 싣는다
= 얼마나 들고 있을지를 서버가 헤더로 정하고 캐시는 그 말을 지킨다
```

## ⚠️ 해결하는 문제

```도해
대조: 얼마나 들고 있을지 서버가 안 말하면 어떻게 되나
말이 없으면 || Cache-Control 로
보관 기간 :: 캐시가 짐작한다 || 서버가 정한다
고친 내용 :: 언제 보일지 모름 || 기한 뒤에 보임
개인 응답 :: 공용 캐시에 담김 || private 이 막는다
= 안 적으면 캐시가 스스로 정한다. 캐시를 끄는 것이 아니다
```

HTTP 는 되도록 캐시하도록 설계되어 있다. 그래서 아무 헤더도 안 붙이면 응답이 안 담기는 것이 아니라, 캐시가 조건을 보고 **스스로 기간을 짐작해** 담는다. MDN 은 그 짐작이 대개 "마지막으로 바뀐 뒤 흐른 시간의 10% 쯤" 이라고 적는다. 짐작한 값이 얼마인지는 서버를 만든 사람이 모른다.

Cache-Control 은 그 판단을 응답 만든 쪽으로 되돌린다. 얼마나 신선한지(`max-age`), 누가 담아도 되는지(`private` / `public`), 만료된 뒤에 확인을 받아야 하는지(`no-cache` / `must-revalidate`)를 서버가 한 줄로 못 박는다.

## 🧱 구성

```도해
층: 같은 응답의 사본은 어디에 남나
브라우저 캐시 :: 사설 캐시. 나 한 사람만 쓴다
공용 캐시 :: CDN·역프록시. 여러 사람이 같은 사본을 본다
원본 서버 :: 원본. 바뀐 게 없으면 `304` 로만 답한다
= 위는 나만 보고 아래는 모두가 본다. `private` 은 아래 칸을 막는 말이다
```

## ⚙️ 작동 원리

신선한지는 두 값을 견줘 판단한다 — **신선도 수명**과 저장된 뒤 흐른 **나이**다. 나이가 수명을 넘지 않은 응답이 신선하고, 넘은 것이 stale 이다. 수명은 순서까지 정해져 있다: 공용 캐시에 `s-maxage` 가 있으면 그 값, 없으면 `max-age`, 그것도 없으면 `Expires` 에서 `Date` 를 뺀 값이다. [[TTL]] 과 같은 일을 하는데, 그 값을 저장하는 쪽이 아니라 응답을 만든 쪽이 내려준다.

| 지시어 | 캐시가 해야 하는 일 |
|---|---|
| `max-age=N` | N 초가 지나면 신선하지 않은 것으로 본다 |
| `no-cache` | 담아도 되지만, 확인받기 전에는 그 응답을 쓰지 않는다 |
| `no-store` | 요청도 응답도 어느 부분도 저장하지 않는다 |
| `private` | 공용 캐시는 이 응답을 저장하지 않는다 |
| `must-revalidate` | 만료된 뒤에는 확인에 성공하기 전까지 쓰지 않는다 |

만료됐다고 버릴 필요는 없다. `ETag` 나 `Last-Modified` 를 들고 조건부 요청을 보내면, 내용이 그대로일 때 서버는 본문 없이 `304` 만 돌려준다. 상태 줄과 헤더뿐이라 전송량이 아주 작고, 캐시는 받은 헤더로 저장분을 갱신해 그대로 다시 쓴다.

## 💡 실제 사례

- **해시를 붙인 정적 파일** — `bundle.v123.js` 처럼 이름에 판을 넣고 `max-age=31536000, immutable` 을 걸어 1년을 그대로 쓰게 한다. 내용이 바뀌면 이름이 바뀌므로 옛 사본은 다시 불리지 않는다.
- **로그인한 사람에게 주는 HTML** — 주소를 바꿀 수 없으니 `no-cache, private` 으로 둔다. 쓸 때마다 서버에 확인하고, 공용 캐시에는 담기지 않는다.
- **여러 사람이 같은 것을 동시에 요청할 때** — 공용 캐시가 원본에 요청 하나만 보내고 그 결과를 모두에게 나눠 준다. 개인화된 응답이면 `private` 을 붙여 이 나눔에서 빼야 한다.

## 🚫 흔한 오해

- **`no-cache` 를 걸면 캐시에 안 남는다** — 저장은 된다. "쓸 때마다 확인받아라" 는 뜻이고, 저장 자체를 막는 것은 `no-store` 다.
- **캐시는 길게 걸수록 좋다** — 주소가 그대로인 파일에 긴 `max-age` 를 걸면 고친 내용이 그 기간 내내 안 보인다. 이미 담긴 응답은 그 기한이 끝날 때까지 신선한 것으로 쓰이기 때문이다.
- **`Cache-Control` 을 안 적으면 캐시가 안 된다** — HTTP 는 되도록 캐시하는 쪽으로 설계되어 있다. 안 적으면 캐시가 기간을 짐작해서 담는다.

## 🚨 주의사항

- **개인화된 응답에는 `private` 을 붙인다.** 안 붙이면 [[CDN]] 같은 공용 캐시가 그 응답을 담아 다른 사람에게 줄 수 있다. 규약은 인수 없이 쓴 `private` 이 붙은 응답을 공용 캐시가 저장하지 못하게 한다 — 사설 캐시인 브라우저는 그대로 담는다.
- **주소를 못 바꾸는 것에는 긴 기한을 걸지 않는다.** HTML 처럼 주소가 고정된 것은 `no-cache` 로 두고 `ETag` 로 확인시킨다. 대신 주소를 바꿀 수 있는 정적 파일은 마음껏 길게 걸어도 된다.

## 📝 정리

**"얼마나 들고 있어도 되는지 적어 붙이는 그 쪽지"** 라고 읽으면 된다. 기한 안에는 서버에 묻지 않고 쓰고, 기한이 지나면 `ETag` 로 아직 같은지만 확인해 `304` 로 끝낸다. 아무것도 안 적으면 캐시가 기간을 짐작하므로, 안 적는 것은 캐시를 끄는 것과 다르다.

## 🧒 열 살에게

반찬통에 "언제까지" 하고 쪽지를 붙여 두면 꺼낼 때 그 쪽지만 보면 되지? 날짜가 안 지났으면 그냥 먹고, 지났으면 만든 사람한테 아직 그대로냐고 한 번만 물어봐. 그래서 매번 새로 만들어 달라고 조르지 않아도 돼.
