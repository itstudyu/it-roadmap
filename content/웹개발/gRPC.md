# gRPC

## 📝 정의

gRPC는 **먼 서버의 함수를 내 함수처럼 부르게 해주는 방식**이다.

Google이 2015년에 공개했고 마이크로서비스가 퍼지면서 같이 쓰이기 시작했다. HTTP/2 위에서 돌고, 주고받는 데이터는 Protocol Buffers라는 바이너리 형식으로 싣는다.

### 이름
g :: 판마다 뜻이 바뀐다
Remote :: 먼 곳의
Procedure :: 함수 한 개
Call :: 불러 쓰기
= 붙여 읽으면 "먼 곳의 함수 하나를 불러 쓰기". 앞의 g 는 판마다 다른 낱말을 붙이는 농담이고, 뜻은 뒤 셋에 다 들어 있다

### 비유
미리 나눠 가진 서식 용지. 칸이 정해져 있어 적을 것도 읽을 것도 짧아지지만, 서식이 없는 사람은 무슨 내용인지 못 읽는다.

### 예
화면에서는 보이지 않는다. 서비스를 여러 개로 쪼갠 시스템의 안쪽 통신에서 만나는 이름이다.

## 🖼️ 그림으로 보기

```도해
흐름: proto 파일 한 장이 어떻게 호출이 되나
proto :: 주고받을 데이터와 함수 이름을 적는다
컴파일 :: 언어별 호출 코드와 서버 뼈대가 생성된다
호출 :: 클라이언트가 `GetUser(1)` 을 부른다
직렬화 :: 인자를 바이너리로 바꿔 HTTP/2 로 보낸다
서버 :: 풀어서 실제 함수를 돌린다
< 응답 :: 결과를 다시 바이너리로 담아 돌려준다
= 부르는 쪽 코드에는 네트워크가 안 보인다. 그냥 함수 호출이다
```

## ⚠️ 해결하는 문제

```도해
대조: 서비스끼리 JSON 으로 주고받으면 무엇이 걸리나
JSON 과 HTTP/1.1 || gRPC 로
보내는 양 :: 글자로 다 담는다 || 바이너리로 압축
동시 요청 :: 앞이 끝나야 뒤 || 한 연결에 여럿
서식 맞추기 :: 문서로 약속한다 || 파일에서 생성
= 안에서 자주 오가는 통신일수록 이 차이가 쌓인다
```

서비스를 잘게 나누면 화면 하나를 그리는 데도 서비스끼리 여러 번 주고받는다. 이때 JSON은 글자 그대로 실려 가므로 크기가 크고, 받는 쪽은 매번 그 글자를 해석해야 한다. HTTP/1.1에서는 앞 요청이 끝나야 다음이 나가서 대기도 붙는다.

gRPC는 이 두 가지를 함께 줄인다. 바이너리라 크기가 작고, HTTP/2의 다중화로 한 연결에 여러 요청이 동시에 흐른다. 실측에서는 REST보다 5~7배 빠르다는 결과가 나오기도 한다.

서식이 어긋나는 문제도 같이 푼다. `.proto` 파일 하나에서 각 언어의 코드가 생성되므로, 서비스가 서로 다른 언어로 쓰여 있어도 주고받는 모양이 갈라지지 않는다.

## 🧱 구성

```도해
층: gRPC 호출 한 번은 무엇 위에 얹혀 가나
생성 코드 :: proto 에서 뽑아낸 함수. 부르는 쪽이 만지는 자리
gRPC :: 어느 함수를 부르고 어떻게 답할지 정하는 규약
Protobuf :: 인자와 결과를 이진 덩이로 바꾸는 형식
HTTP/2 :: 그 덩이를 한 연결에 여럿 실어 나른다
= 새 통신망이 생긴 게 아니다. HTTP/2 위에 이진 형식과 호출 규약을 얹은 것이다
```

## ⚙️ 작동 원리

`.proto` 파일에는 데이터 모양과 함수 이름을 적는다. 컴파일러가 이 파일을 읽어 각 언어의 호출 코드와 서버 뼈대를 만들어주므로, 개발자는 서버 쪽 내용만 채우고 클라이언트에서는 생성된 함수를 그냥 부른다.

주고받는 모양은 네 가지다. REST 로는 맨 앞의 하나만 되고, 나머지는 다른 기술을 따로 붙여야 한다.

- **단일** — 한 번 묻고 한 번 답한다
- **서버 스트리밍** — 한 번 물으면 답이 계속 온다
- **클라이언트 스트리밍** — 계속 보내고 마지막에 한 번 답받는다
- **양방향** — 양쪽이 동시에 계속 주고받는다

필드에는 번호가 붙는다. 새 필드를 뒤에 더해도 이미 배포된 쪽은 모르는 번호를 건너뛰기 때문에 깨지지 않는다. 다만 있던 번호를 다른 필드에 다시 쓰면 옛 쪽이 엉뚱한 값으로 읽는다.

## 💡 실제 사례

- **서비스 사이 내부 호출** — 주행 서비스가 사용자 서비스와 결제 서비스를 부르는 것처럼 안에서만 오가는 통신에 쓴다.
- **시세 스트리밍** — 한 번 요청해두면 값이 바뀔 때마다 서버가 계속 보내준다.
- **여러 언어가 섞인 팀** — `.proto` 한 장에서 Java와 Python과 Go 코드가 같이 생성되어 서식이 어긋나지 않는다.

## 🚫 흔한 오해

- **gRPC가 REST를 대체한다** — 안에서 오가는 통신에 유리하고 바깥에 여는 API로는 불리하다. 브라우저에서 바로 못 부르고 HTTP 캐싱도 쓰기 어렵다.
- **바이너리로 보내니까 안전하다** — 읽기 불편한 것과 못 읽는 것은 다르다. 바이너리는 크기를 줄이려는 형식이고, 내용을 가리는 일은 TLS가 한다.
- **브라우저에서도 그냥 쓸 수 있다** — 브라우저는 gRPC가 필요로 하는 부분까지 열어주지 않는다. gRPC-Web이라는 중간 계층을 두어야 한다.

## 📊 비교

| | gRPC | REST |
|---|---|---|
| 싣는 형식 | 바이너리 | JSON 글자 |
| 바탕 | HTTP/2 | HTTP/1.1 또는 2 |
| 스트리밍 | 네 가지 모양 | 요청과 응답 하나씩 |
| 브라우저 | 중간 계층이 필요 | 그대로 된다 |
| 캐싱 | 쓰기 어렵다 | HTTP 캐시를 쓴다 |

## 🚨 주의사항

- **`curl`로 두드려볼 수 없다.** 바이너리라 눈으로 못 읽고 `grpcurl` 같은 전용 도구가 필요하다.
- **쓰던 필드 번호를 재사용하지 않는다.** 새 필드를 더하는 것은 안전하지만 번호를 돌려쓰면 옛 클라이언트가 다른 값으로 읽는다.

## 📝 정리

**"먼 서버의 함수를 내 함수처럼 부르는 그 방식"** 이라고 읽으면 된다. 바이너리와 HTTP/2 덕에 서비스끼리 자주 주고받는 통신에서 유리하고, 브라우저와 캐싱을 포기하는 대신 그 속도를 얻는다.

## 🧒 열 살에게

빈 종이에 하나하나 다 적어 보내는 대신, 칸이 미리 그어진 종이를 양쪽이 똑같이 나눠 갖는다고 해 봐. 칸 번호만 채우면 되니까 적을 것도 짧고 읽는 것도 빨라. 대신 그 종이를 안 가진 사람은 받아도 무슨 말인지 하나도 몰라.

## ❓ 이해했는지

- `.proto` 파일 하나로 Java와 Go 코드가 같이 생성되면 무엇이 어긋나지 않게 되나 → 실제 사례
- 같은 내용을 보낼 때 JSON보다 오가는 양이 적은 이유는 → 해결하는 문제
- 공개용 API를 gRPC 대신 REST로 내는 이유는 → 흔한 오해
