# GraphQL

## 📝 정의

GraphQL은 Meta(구 페이스북)에서 개발한 API 쿼리 언어 및 런타임입니다. REST API의 한계를 극복하기 위해 만들어졌으며, 클라이언트가 필요한 데이터를 정확히 명시하여 요청할 수 있는 강력한 데이터 조회 언어입니다. 단일 엔드포인트를 통해 모든 데이터 요청을 처리하며, 강타입의 스키마 기반으로 동작합니다.

GraphQL은 클라이언트와 서버 간의 데이터 통신을 효율적으로 만들어줍니다. 필요한 필드만 요청하기 때문에 불필요한 데이터 전송(Over-fetching)을 제거할 수 있고, 여러 리소스를 한 번에 조회하여 여러 번의 API 호출(Under-fetching)을 방지할 수 있습니다.

> **한 줄 요약**: 클라이언트가 필요한 데이터 구조를 명시적으로 정의하여 요청하는 API 쿼리 언어

### 비유
- 🔵 **레스토랑 주문**: REST는 정해진 메뉴판(정해진 응답 구조)을 사서 먹는 것, GraphQL은 원하는 재료만 선택해서 요리해달라고 하는 것
- 🟡 **맞춤형 패키징**: REST는 모든 정보를 다 담아 보내는 큰 상자(Over-fetching), GraphQL은 필요한 것만 담아 보내는 정확한 패키징

---

## 🎯 핵심 개념

### 1. 단일 엔드포인트 구조
REST API는 여러 엔드포인트(/users, /posts, /comments)가 필요하지만, GraphQL은 단 하나의 엔드포인트(/graphql)에서 모든 데이터를 처리합니다.

### 2. Query, Mutation, Subscription
- **Query**: 데이터 조회 (읽기)
- **Mutation**: 데이터 생성/수정/삭제 (쓰기)
- **Subscription**: 실시간 데이터 변경 구독 (푸시)

### 3. 강타입 스키마(Schema)
모든 쿼리와 응답은 사전에 정의된 스키마를 따릅니다. 타입 정의를 통해 클라이언트와 서버 간의 계약을 명확히 합니다.

---

## ⚠️ 해결하는 문제

### 문제 1: Over-fetching (과도한 데이터 전송)
REST API에서 /users/1을 조회하면 사용자의 모든 정보가 반환되는데, 이름과 이메일만 필요한 경우에도 전체 데이터를 받아야 합니다. GraphQL에서는 필요한 필드만 명시하여 요청할 수 있습니다.

### 문제 2: Under-fetching (데이터 부족으로 인한 추가 요청)
사용자 정보와 그 사용자의 게시물을 함께 표시하려면 /users/1 후 /users/1/posts를 추가로 호출해야 합니다. GraphQL에서는 한 번의 쿼리에 중첩된 구조로 요청할 수 있습니다.

## ⚙️ 작동 원리

GraphQL은 클라이언트가 보낸 쿼리를 수신하면 먼저 스키마와 비교하여 유효성을 검증합니다. 스키마에 정의된 타입과 필드가 올바르게 요청되었는지 확인하고, 구문 오류나 타입 불일치가 있으면 에러를 반환합니다.

검증을 통과한 쿼리는 리졸버(Resolver)라는 함수에 의해 처리됩니다. 각 필드마다 해당하는 리졸버가 실행되어 데이터베이스나 다른 데이터 소스에서 데이터를 조회합니다. 리졸버는 재귀적으로 중첩된 필드를 처리하여 클라이언트가 요청한 정확한 구조의 데이터를 반환합니다.

응답은 요청한 쿼리의 구조와 정확히 일치하는 JSON 형태로 반환되므로, 클라이언트는 예측 가능한 형태의 데이터를 받을 수 있습니다.

## 📊 비교

| 항목 | GraphQL | REST API | gRPC |
|------|---------|----------|------|
| **엔드포인트 수** | 단일 (/graphql) | 다중 (/users, /posts 등) | 다중 (각 서비스별) |
| **데이터 조회** | 정확히 필요한 필드만 | 정해진 응답 구조 | 프로토콜 버퍼 기반 |
| **쿼리 언어** | GraphQL 쿼리 언어 사용 | URL 경로와 쿼리 파라미터 | 서비스 정의 파일 |
| **실시간 기능** | Subscription 지원 | Polling/WebSocket 별도 구현 | 양방향 스트리밍 가능 |
| **학습 곡선** | 중간~높음 | 낮음 | 높음 |
| **클라이언트 요청 복잡도** | 복잡한 쿼리 가능 | URL 구성이 간단 | 프로토콜 정의 필요 |
| **성능** | 네트워크 효율적 | 오버-페칭 가능 | 매우 빠름 (이진 프로토콜) |
| **브라우저 친화성** | 우수 (JSON) | 우수 | 약함 (웹브라우저 미지원) |

## ✅ 장단점

**장점**
- 클라이언트가 필요한 데이터를 정확히 요청 가능 → 네트워크 트래픽 감소
- 단일 요청으로 복잡한 데이터 구조 조회 가능
- 강타입 스키마로 API 안정성과 문서화 자동화
- 개발자 도구가 우수 (자동 완성, 타입 검사)
- 버전 관리가 간단 (REST의 /v1/, /v2/ 불필요)

**단점**
- 학습 곡선이 가파름
- 복잡한 쿼리는 성능 최적화 어려움 (N+1 문제)
- 파일 업로드 처리가 REST보다 복잡
- 간단한 API에는 오버엔지니어링일 수 있음
- 캐싱 전략이 REST보다 복잡

## 💡 실제 사례

**GitHub API v4**
GitHub은 REST API(v3)에서 GraphQL(v4)로 전환하여, 개발자가 필요한 저장소 정보, 이슈, PR 데이터를 한 번에 조회할 수 있도록 제공합니다.

**Shopify API**
쇼핑몰 데이터(상품, 주문, 고객)를 GraphQL로 조회하여 필요한 필드만 선택적으로 가져올 수 있습니다.
