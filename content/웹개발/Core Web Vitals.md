# Core Web Vitals (코어 웹 바이탈)

## 📝 정의

Core Web Vitals 는 **웹 경험을 셋으로 나눠 재는 성능 지표**다.

Chrome 팀이 잴 것 셋과 그 기준값까지 함께 정해 두었다 — 로딩은 LCP, 반응은 INP, 흔들림은 CLS 다. 세 이름이 각각 무엇을 재는지 그대로 담고 있다. Largest Contentful Paint 는 "가장 큰 내용이 그려진 시점", Interaction to Next Paint 는 "상호작용에서 다음 그림까지", Cumulative Layout Shift 는 "쌓인 배치 밀림" 이다.

### 이름
Core :: 핵심만 추린
Web :: 웹 페이지
Vitals :: 활력 징후
= 붙여 읽으면 "웹의 핵심 활력 징후". 맥박·체온처럼 몇 가지만 재서 상태를 본다

### 비유
건강검진표. 한 가지만 재서는 건강을 말할 수 없으니 서로 다른 항목 몇 개를 정해두고 각각에 정상 범위를 붙인다.

### 예
기사를 읽는 중에 광고가 늦게 떠서 문단이 아래로 밀리는 그 짜증이 셋 중 하나로 점수가 된다.

### 직접
pagespeed.web.dev 에 늘 가는 사이트 주소를 넣어 보라. 셋의 값과 통과 여부가 그대로 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 한 번의 방문에서 Core Web Vitals 는 무엇을 재나
열 때 :: 가장 큰 그림·글이 뜨기까지. LCP, 2.5초
누를 때 :: 다음 화면이 그려지기까지. INP, 200ms
보는 동안 :: 저절로 밀린 배치의 크기. CLS, 0.1
판정 :: 실제 방문을 모아 75번째 백분위로 본다
= 뜨는 속도·반응·흔들림 셋을 각각의 기준값으로 재는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 좋은 성능의 기준을 정해두지 않으면 어떻게 되나
기준 없이 || Core Web Vitals 로
좋다의 뜻 :: 팀마다 다르다 || 2.5초·200ms·0.1
무엇을 잴까 :: 재는 것도 다르다 || 셋으로 못 박음
누구의 값 :: 개발자 기기 || 실제 방문 75%
= 무엇을 얼마까지 재는지 정해두지 않으면 "빠르다" 는 말이 남는다
```

성능을 "빠르다 / 느리다" 로만 말하면 무엇을 고쳐야 하는지가 안 나온다. 뜨는 속도만 재면 뜨자마자 버튼이 안 먹는 페이지가 통과하고, 반응만 재면 읽는 도중에 글이 밀려 내려가는 페이지가 통과한다. 게다가 개발자 기기에서 한 번 잰 값은 사용자 기기의 값이 아니다.

Core Web Vitals 는 잴 것을 셋으로 쪼개고 각각에 숫자를 못 박아 이 문제를 없앤다. 권장값은 LCP 2.5초 이내, INP 200밀리초 이하, CLS 0.1 이하이고, 이 값을 실제 방문의 **75번째 백분위**(느린 쪽 4분의 1을 잘라낸 지점)에서 모바일과 데스크톱을 나눠 재라고 정해두었다. 셋 다 그 지점에서 기준을 지키면 통과다.

## ⚙️ 작동 원리

| 지표 | 무엇을 재나 | 좋다고 보는 값 |
|---|---|---|
| **LCP** | 화면에 보이는 가장 큰 그림이나 글 덩이가 그려진 시각 | 2.5초 이내 |
| **INP** | 누른 뒤 다음 화면이 그려질 때까지 걸린 시간 | 200밀리초 이하 |
| **CLS** | 사용자가 시키지 않은 배치 밀림이 쌓인 정도 | 0.1 이하 |

LCP 의 대상은 그림과 글 덩이다. `<img>`, SVG 안의 `<image>`, `<video>` 의 표지 그림, `background-image` 가 걸린 요소, `<p>` 같은 글 뭉치가 후보이고, 그중 화면에서 가장 큰 것이 언제 그려졌는지를 잰다.

INP 는 세 토막을 합친 값이다. 누른 것이 처리되기까지 기다린 시간, 처리기가 도는 시간, 브라우저가 다음 프레임을 그리는 시간이다. [[Latency]] 를 사용자의 손끝에서 재는 것이라고 보면 된다.

CLS 는 시간이 아니라 점수다. 밀림 하나의 점수는 **영향 비율 × 이동 비율** — 밀린 요소가 화면에서 차지한 비율에, 화면의 긴 쪽 대비 얼마나 멀리 밀렸는지를 곱한다. 그리고 이 점수를 전부 더하지 않는다. 1초 안에 잇달아 일어난 밀림을 한 묶음으로 묶고(한 묶음은 최대 5초), 합이 가장 큰 묶음의 점수만 CLS 로 쓴다.

## 💡 실제 사례

- **크기를 안 적은 이미지** — 그림이 늦게 도착하면서 아래 글이 밀려 내려간다. `width` 와 `height` 를 적어두면 브라우저가 자리를 미리 비워 두므로 CLS 점수가 오르지 않는다.
- **첫 화면의 큰 배너** — 화면에서 가장 큰 그림이 대개 LCP 대상이 되므로, 그 한 장을 먼저 받게 하는 것이 로딩 점수를 가장 크게 움직인다.
- **누르면 잠깐 멈추는 버튼** — 눌린 순간 무거운 자바스크립트가 돌면 다음 프레임이 늦게 그려지고, 그 지연이 INP 로 잡힌다.

## 🚫 흔한 오해

- **셋 다 통과하면 사이트가 빠른 것이다** — 이 셋은 로딩·반응·흔들림만 본다. 검색이 오래 걸리거나 결제가 실패하는 것은 여기에 안 잡힌다.
- **INP 는 첫 클릭이 얼마나 빨리 먹히나를 재는 것이다** — 그건 INP 가 2024년에 갈아치운 옛 지표 FID 다. INP 는 방문 중의 상호작용을 전부 보고 그중 가장 나쁜 값을 쓴다.
- **내 컴퓨터에서 잰 값이 우리 사이트의 값이다** — 판정은 실제 방문들을 모은 값의 75번째 백분위에서 한다. 개발 기기 한 대의 한 번 측정은 그 분포의 점 하나다.

## 🚨 주의사항

- **누르지 않으면 INP 는 안 잡힌다.** INP 는 방문 중에 일어난 상호작용을 보고 그중 가장 나쁜 값을 쓴다. 아무도 누르지 않은 측정에는 값이 없고, 판정에 쓰는 값은 실제 방문들을 모은 75번째 백분위다.
- **CLS 는 전체 합이 아니다.** 잇달아 일어난 밀림을 한 묶음으로 묶고 합이 가장 큰 묶음만 점수로 쓴다. 그래서 페이지를 끝까지 내려도 점수가 계속 오르지는 않는다.
- **상호작용이 많은 페이지는 극단값을 뺀다.** 상호작용이 50번을 넘으면 98번째 백분위를 써서, 페이지 전체의 반응성을 대표하지 못하는 값을 걸러낸다.

## 📝 정리

**"로딩·반응·흔들림 셋을 숫자로 못 박은 그 검진표"** 라고 읽으면 된다. 판정은 한 번의 측정이 아니라 실제 방문을 모은 값의 75번째 백분위에서 한다. 그래서 이 셋을 고치는 일은 내 컴퓨터를 빠르게 하는 일이 아니라 느린 쪽 사용자들의 값을 끌어올리는 일이다.

## 🧒 열 살에게

건강한지 볼 때 키만 재지는 않지? 키도 재고 몸무게도 재고 눈도 보고, 항목마다 "이만큼이면 괜찮아" 하는 줄이 있어. 인터넷 페이지도 뜨는 속도, 눌렀을 때 바로 움직이는지, 보는 중에 글이 저절로 밀리는지 셋을 따로 재서 그 줄을 넘었나 봐.
