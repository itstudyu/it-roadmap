# Idempotency Key (멱등 키)

## 📝 정의

Idempotency Key 는 **같은 요청을 한 번만 처리하게 만드는 열쇠**다.

멱등(idempotent)은 한 번 보낸 결과와 여러 번 보낸 결과가 서버에서 같다는 뜻이다. HTTP 는 `GET` 같은 안전한 메서드와 `PUT`·`DELETE` 를 멱등으로 정해 뒀지만 `POST` 와 `PATCH` 는 아니다. 그래서 `POST` 에는 클라이언트가 만든 열쇠를 하나 붙여서 "이건 아까 그 요청이다" 를 서버가 알아보게 한다. IETF 에는 이 열쇠를 `Idempotency-Key` 라는 요청 헤더로 싣는 초안이 올라와 있다.

### 비유
옷 맡기고 받은 번호표를 두 번 내밀어도 나오는 옷은 한 벌인 것과 같다.

## 🖼️ 그림으로 보기

```도해
흐름: 결제 버튼을 두 번 눌러도 왜 한 번만 결제되나
클라이언트 :: 요청에 열쇠 하나를 적어 보낸다
서버 :: 그 열쇠를 본 적 있는지 찾는다
처음이면 :: 결제하고 결과를 열쇠와 함께 적어 둔다
< 응답 :: 결과를 돌려준다. 열쇠는 서버에 남는다
@ 같은 열쇠로 :: 두 번째부터는 적어 둔 결과를 그대로
= 두 번째 요청은 처리되지 않는다. 첫 결과가 다시 나올 뿐이다
```

## ⚠️ 해결하는 문제

```도해
대조: 응답을 못 받고 다시 보내면 무슨 일이 벌어지나
열쇠 없이 || 열쇠를 붙여
재시도 :: 두 번 결제된다 || 한 번만 남는다
응답 유실 :: 성공인지 모른다 || 첫 결과를 다시 받는다
자동 재시도 :: 섣불리 못 한다 || 마음 놓고 한다
= 통신이 끊기면 보낸 쪽은 성공했는지 알 수 없다. 그래서 열쇠를 붙인다
```

결제 요청을 보냈는데 응답이 오기 전에 연결이 끊겼다면, 보낸 쪽은 **결제가 됐는지 안 됐는지 알 방법이 없다.** 다시 보내면 두 번 결제될 수 있고, 안 보내면 결제가 빠질 수 있다. 요청이 이미 서버에 닿아 처리까지 끝난 뒤에 응답만 유실된 경우가 그렇다.

여기에 열쇠를 붙이면 **다시 보내도 되는 요청**이 된다. 서버는 그 열쇠를 이미 처리했는지 먼저 보고, 처리했다면 두 번째 요청을 처리하지 않고 첫 결과를 그대로 돌려준다. Azure 의 설계 지침도 접수형 API 에 이 열쇠를 요구해서, 같은 열쇠가 또 오면 일감을 하나 더 넣는 대신 먼저 만든 상태 자원을 돌려주라고 권한다.

## ⚙️ 작동 원리

열쇠는 **클라이언트가 만든다.** UUID 처럼 겹칠 일 없는 문자열 하나를 요청마다 만들고, 재시도할 때는 새로 만들지 않고 같은 값을 다시 보낸다. IETF 초안의 예시는 이렇게 생겼다.

```
Idempotency-Key: "8e03978e-40d5-43e8-bc93-6894a57f9324"
```

서버는 열쇠와 함께 요청 본문의 지문(체크섬 같은 요약값)을 남겨 둘 수 있다. 그러면 "같은 열쇠, 다른 내용" 을 구별할 수 있다.

| 두 번째 요청이 왔을 때 | 서버가 하는 일 |
|---|---|
| 첫 요청이 이미 끝났다 | 처리하지 않고 첫 결과를 준다. 성공이든 오류든 그때 것을 그대로 |
| 첫 요청이 아직 도는 중이다 | `409 Conflict` — 겹쳤으니 기다리라고 알린다 |
| 열쇠는 같은데 본문이 다르다 | `422 Unprocessable Content` — 열쇠를 잘못 쓴 것이다 |

열쇠가 어느 범위에서 유일해야 하는지, 얼마나 지나면 지울 수 있는지는 **서버가 정해서 문서에 밝힌다.** 서버는 열쇠를 영원히 들고 있을 수 없기 때문이다.

## 💡 실제 사례

- **결제 승인** — 버튼을 두 번 누르든 응답이 끊겨 다시 보내든, 같은 열쇠로 온 것이면 승인은 한 건만 남는다.
- **오래 걸리는 작업 접수** — 요청을 큐에 넣고 접수만 알리는 API 는, 같은 열쇠가 또 오면 일감을 하나 더 만들지 않고 먼저 만든 진행 상태를 돌려준다.
- **자동 재시도** — 실패하면 다시 보내도록 만든 클라이언트는 같은 요청을 여러 번 보낸다. 열쇠가 없으면 그 재시도가 그대로 중복 처리가 된다.

## 🚫 흔한 오해

- **실패했으면 그냥 다시 보내면 된다** — 멱등한 메서드만 그렇다. `POST` 는 서버가 이미 받아 처리했을 수 있어서, 다시 보내면 하나가 더 생긴다.
- **열쇠는 서버가 만들어 준다** — 클라이언트가 만든다. 재시도할 때 같은 값을 다시 보내야 하니, 요청을 만든 쪽이 쥐고 있어야 한다.
- **모든 요청에 열쇠를 붙이는 게 안전하다** — `GET`·`PUT`·`DELETE` 는 이미 멱등이라 붙여서 얻는 것이 없다. 서버는 열쇠마다 결과를 저장하고 언제 지울지까지 관리해야 하니, 두 번 일어나면 안 되는 요청에만 붙인다.

## 📝 정리

Idempotency Key 는 요청을 막는 자물쇠가 아니라 **"아까 그 요청" 이라고 알려주는 이름표**다. 이름표가 있으면 서버는 두 번째를 처리하지 않고 첫 결과를 다시 꺼내 주고, 그래서 클라이언트는 응답을 못 받았을 때 마음 놓고 다시 보낼 수 있다.

## ❓ 이해했는지

- 카드 결제에 자동 재시도를 붙일 때 `POST` 를 그냥 다시 보내면 안 되는 까닭은 → 해결하는 문제
- 열쇠는 같은데 요청 본문이 다르면 서버가 왜 거절하나 → 작동 원리
- 열쇠를 서버가 아니라 클라이언트가 만드는 까닭은 → 흔한 오해
