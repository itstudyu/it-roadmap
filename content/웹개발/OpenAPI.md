# OpenAPI (오픈API)

## 📝 정의

OpenAPI 는 **HTTP API 의 사용법을 기계도 읽게 적는** 표준 형식이다.

소스 코드를 받지 않고, 문서를 따로 읽지 않고, 오가는 패킷을 들여다보지 않고도 그 서비스가 무엇을 할 수 있는지 알게 하려고 만들었다. 2015년에 SmartBear 가 Swagger 2.0 명세를 기부했고, 2016년부터 Linux Foundation 아래의 OpenAPI Initiative 가 맡는 별개 프로젝트가 됐다. 이름이 갈린 지점이 거기다.

### 비유
전자제품 상자에 든 설명서. 뚜껑을 열어 회로를 뜯어보지 않아도 어느 단추가 무슨 일을 하는지 다 적혀 있다.

## 🖼️ 그림으로 보기

```도해
대조: API 사용법을 사람 말로만 적어 두면 무엇이 달라지나
명세 파일 없이 || OpenAPI 파일로
사용법 :: 문서를 읽고 짐작 || 기계가 그대로 읽음
클라이언트 :: 손으로 짜 맞춤 || 파일에서 뽑아냄
문서와 실제 :: 조용히 어긋남 || 같은 파일에서 나옴
= API 의 사용법을 기계도 읽을 한 파일로 적어 두는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 서버를 만든 언어에 사용법이 매이면 무엇이 막히나
언어에 매인 설명 || 언어 무관 명세
다른 언어 팀 :: 다시 손으로 옮김 || 그대로 읽어 씀
쓸 수 있는 도구 :: 그 언어 것만 됨 || 아무 도구나 됨
합의할 자리 :: 코드를 봐야 함 || 파일만 보면 됨
= 형식이 언어를 안 가리니, 그 파일을 읽는 도구도 언어를 안 가린다
```

API 를 쓰려면 세 가지를 알아야 한다. 어떤 주소로 무슨 메서드를 보내는지, 무엇을 어디에 담아 보내는지, 무엇이 어떤 모양으로 돌아오는지. 이걸 사람 말로 적은 문서로만 두면 읽는 사람마다 다르게 짐작하고, 구현이 바뀔 때 문서는 조용히 뒤처진다.

OpenAPI 는 그 셋을 **프로그래밍 언어를 가리지 않는 한 파일**로 옮긴다. 서버를 무엇으로 만들었는지 몰라도 그 파일만 있으면 문서 화면을 그리고 클라이언트 코드를 뽑고 들어온 요청을 검증할 수 있다. 짐작이 파싱으로 바뀐다.

## ⚙️ 작동 원리

파일은 JSON 이나 YAML 로 적는다. OpenAPI 문서 자체가 하나의 JSON 객체이고, YAML 은 같은 것을 사람이 쓰기 좋게 적는 표기다. 한 파일로 다 적어도 되고, 여러 파일로 쪼개 URI 참조로 이어 붙여도 된다.

데이터의 모양은 JSON Schema(JSON 데이터의 구조와 제약을 적는 선언형 언어)를 스키마 객체라는 이름으로 그대로 품어 쓴다. 그래서 "이 필드는 문자열이고 최대 40자" 같은 제약이 명세 안에 같이 들어간다.

파일 한 장에서 나오는 것이 여럿이다.

| 무엇 | 파일에서 나오는 것 |
|---|---|
| 문서 | 사람이 읽는 API 문서 화면과 그 자리에서 보내 보는 단추 |
| 클라이언트 | 여러 언어의 SDK 코드 |
| 서버 | 컨트롤러 골격 코드 |
| 검증 | 경로·파라미터·본문이 명세와 맞는지 확인 |
| 시험 | 구현이 설계와 어긋나지 않는지 보는 계약 테스트 |

적는 순서는 둘 중 하나다. 파일을 먼저 쓰고 그에 맞춰 구현하거나(설계 먼저), 구현에 주석을 달아 파일을 뽑아내거나(코드 먼저). 어느 쪽이든 결과물은 같은 형식의 파일 한 장이다.

## 💡 실제 사례

- **문서와 시험판이 한 번에** — 명세 파일을 문서 도구에 넣으면 사람이 읽는 화면이 나오고, 그 화면에서 바로 요청을 보내 볼 수 있다.
- **[[SDK]] 자동 생성** — 같은 파일로 여러 언어의 클라이언트 코드를 뽑아낸다. API 가 바뀌면 파일을 고치고 다시 뽑는다.
- **요청 걸러내기** — 들어온 요청의 경로와 파라미터, 본문이 명세와 맞는지 앞단에서 확인한다. 틀린 요청은 안쪽 코드에 닿기 전에 막힌다.

## 🚫 흔한 오해

- **Swagger 와 OpenAPI 는 서로 다른 규격이다** — 지금의 OpenAPI 명세가 기부받은 Swagger 2.0 명세에서 출발했다. 이름이 갈렸고 관리 주체가 바뀐 것이지 계보가 둘인 게 아니다.
- **명세에 적어 뒀으니 서버도 그대로 동작한다** — 명세는 약속을 적은 종이다. 실제 응답이 그 약속과 맞는지는 계약 테스트로 따로 확인해야 어긋남이 드러난다.
- **API 라면 무엇이든 OpenAPI 로 적을 수 있다** — HTTP API 를 적는 형식이다. HTTP 로 주고받지 않는 인터페이스는 이 형식이 담지 못한다.

## 🚨 주의사항

- **파일과 구현은 저절로 붙어 있지 않다.** 명세는 약속이고 서버는 코드다. 둘을 붙여 두는 것은 계약 테스트지 파일 자체가 아니다.
- **본문이 반드시 JSON 일 필요는 없다.** 명세 파일이 JSON 이나 YAML 인 것과 그 API 가 주고받는 본문 형식은 별개다. 파일이든 폼이든 적을 수 있다.
- **버전 표기를 먼저 봐라.** 2.0 은 기부받은 Swagger 명세에서 이름만 갈린 것이고, 3.x 는 OpenAPI Initiative 가 이어서 낸 것이다. 도구가 어느 쪽을 읽는지 확인해야 한다.

## 📝 정리

OpenAPI 는 HTTP API 의 사용법을 기계가 읽을 형식으로 적어 두는 표준이다. 파일 한 장이 문서와 클라이언트 코드와 검증의 공통 원본이 되니, 세 곳이 따로 낡을 일이 없다. 다만 그 파일이 실제 구현과 맞는지는 여전히 따로 확인해야 한다.

## ❓ 이해했는지

- 소스 코드를 못 받은 남의 API 를 쓸 수 있게 되는 근거는 무엇인가 → 그림
- 명세에 응답 모양을 적어 뒀는데도 실제 서버가 다른 것을 내보낼 수 있는 이유는 무엇인가 → 주의사항
- 서버를 어떤 언어로 만들었는지 몰라도 클라이언트 코드를 뽑을 수 있는 이유는 무엇인가 → 해결하는 문제

## 🔗 관련 용어

- [[API]] — OpenAPI 가 적어 두는 대상 그 자체
- [[REST]] — HTTP 메서드로 API 를 설계하는 방식. OpenAPI 가 주로 적는 모양이다
- [[JSON]] — 명세 파일의 본래 형태. 문서 자체가 하나의 JSON 객체다
- [[YAML]] — 같은 명세를 사람이 쓰기 좋게 적는 표기
- [[SDK]] — 명세 파일에서 뽑아내는 결과물 중 하나
