# HTTP 상태 코드 (Status Code)

## 📝 정의

HTTP 상태 코드는 웹 서버가 클라이언트의 HTTP 요청에 대한 처리 결과를 나타내는 3자리 숫자 코드입니다. 클라이언트(웹 브라우저, 모바일 앱, API 클라이언트 등)가 서버에 요청을 보내면, 서버는 요청 처리 결과를 상태 코드와 응답 메시지로 함께 반환합니다. 이를 통해 클라이언트는 요청의 성공 여부, 리다이렉트 필요 여부, 오류 발생 여부 등을 즉시 파악할 수 있습니다.

HTTP 상태 코드는 HTTP/1.0 표준(1996년)에 처음 정의되었으며, HTTP/1.1, HTTP/2를 거쳐 오늘날까지 동일한 규약으로 사용되고 있습니다. 각 상태 코드는 첫 자리 숫자에 따라 5가지 카테고리로 분류되며, 같은 카테고리의 코드들은 유사한 의미를 갖습니다. 예를 들어 2xx는 성공, 4xx는 클라이언트 오류, 5xx는 서버 오류를 나타냅니다. 웹 개발, API 설계, 네트워크 디버깅에서 상태 코드를 정확히 이해하고 사용하는 것은 필수입니다.

> **한 줄 요약**: HTTP 상태 코드는 서버가 클라이언트의 요청 처리 결과를 나타내는 3자리 숫자로, 성공(2xx), 리다이렉트(3xx), 클라이언트 오류(4xx), 서버 오류(5xx) 등으로 분류됩니다.

**비유 1**: HTTP 상태 코드는 마치 택배 수령 확인 시스템과 같습니다. 택배를 보냈을 때 "배송 중(2xx)", "주소 변경 필요(3xx)", "잘못된 주소(4xx)", "배송사 문제(5xx)"라는 피드백이 오는 것처럼, 서버도 요청에 대한 처리 상황을 코드로 알려줍니다.

**비유 2**: HTTP 상태 코드는 도서관의 책 대출 결과 알림과 유사합니다. "대출 성공(200 OK)", "책이 다른 위치로 이동(301 Moved)", "책을 찾을 수 없음(404 Not Found)", "도서관 시스템 오류(500 Internal Error)"처럼, 각 상황을 명확한 메시지로 사용자에게 알려줍니다.

## 🎯 핵심 개념

### 1. 상태 코드의 5가지 분류

HTTP 상태 코드는 첫 자리 숫자에 따라 5가지 카테고리로 분류됩니다:

**1xx (정보성 - Informational)**: 요청을 받았으며 계속 처리 중임을 나타냅니다. 예: 100 Continue(계속 진행 가능), 101 Switching Protocols(프로토콜 변경)

**2xx (성공 - Success)**: 요청이 성공적으로 처리되었음을 나타냅니다. 예: 200 OK(요청 성공), 201 Created(자원 생성), 204 No Content(응답 본문 없음)

**3xx (리다이렉션 - Redirection)**: 추가 작업이 필요하며 일반적으로 다른 URL로 리다이렉트하라는 의미입니다. 예: 301 Moved Permanently(영구 이동), 302 Found(임시 이동), 304 Not Modified(캐시된 버전 사용)

**4xx (클라이언트 오류 - Client Error)**: 클라이언트의 요청에 오류가 있음을 나타냅니다. 예: 400 Bad Request(잘못된 요청), 401 Unauthorized(인증 필요), 403 Forbidden(접근 금지), 404 Not Found(자원 없음)

**5xx (서버 오류 - Server Error)**: 서버가 요청을 처리하지 못했음을 나타냅니다. 예: 500 Internal Server Error(내부 오류), 502 Bad Gateway(게이트웨이 오류), 503 Service Unavailable(서비스 이용 불가)

### 2. 주요 상태 코드의 상세 설명

**200 OK**: 가장 일반적인 성공 코드입니다. GET 요청으로 페이지를 조회하거나, POST 요청으로 데이터를 전송했을 때 성공하면 반환됩니다. 응답 본문에 요청한 자원의 데이터가 포함됩니다.

**201 Created**: 새로운 자원이 성공적으로 생성되었을 때 반환됩니다. 주로 POST 요청 후 발생하며, 응답 헤더의 Location 필드에 생성된 자원의 URL이 포함됩니다.

**301 vs 302**: 두 코드 모두 리다이렉트를 나타내지만, 301은 영구적 이동(검색 엔진이 새 URL로 인덱싱 변경), 302는 임시 이동(원래 URL 유지)을 의미합니다.

**400 Bad Request**: 서버가 요청을 이해할 수 없음을 의미합니다. 잘못된 파라미터, 잘못된 JSON 형식, 필수 필드 누락 등의 이유로 발생합니다.

**401 vs 403**: 401은 인증(Authentication) 필요 상태로, 사용자가 로그인하지 않았을 때 발생합니다. 403은 인가(Authorization) 실패로, 사용자는 인증되었으나 특정 자원에 접근할 권한이 없을 때 발생합니다.

**404 Not Found**: 요청한 자원이 서버에 존재하지 않음을 의미합니다. 가장 흔한 오류 중 하나로, 삭제된 페이지, 잘못된 URL 등의 이유로 발생합니다.

**429 Too Many Requests**: 클라이언트가 일정 시간 내에 너무 많은 요청을 보냈을 때 반환됩니다. API 레이트 제한(Rate Limiting)을 구현할 때 사용됩니다.

**500 Internal Server Error**: 서버에서 요청을 처리하다가 예상하지 못한 오류가 발생했을 때 반환됩니다. 데이터베이스 연결 실패, 코드 예외 등으로 인해 발생합니다.

**503 Service Unavailable**: 서버가 일시적으로 요청을 처리할 수 없는 상태입니다. 서버 유지보수, 과부하 등의 이유로 발생합니다. 응답 헤더의 Retry-After 필드로 언제 다시 시도할지 나타낼 수 있습니다.

### 3. 상태 코드의 실무 활용

웹 개발에서 상태 코드는 단순한 응답 신호 이상의 역할을 합니다. **REST API 설계**에서는 각 HTTP 메서드(GET, POST, PUT, DELETE)에 적절한 상태 코드를 반환하는 것이 중요합니다. 예를 들어 POST로 새 사용자를 생성하면 201 Created를 반환하고, Location 헤더에 생성된 사용자의 URL을 포함시켜야 합니다.

**클라이언트 개발**에서는 각 상태 코드에 따라 다른 처리를 해야 합니다. 200이면 데이터를 표시하고, 301/302면 새 URL로 리다이렉트하고, 401이면 로그인 페이지로 이동하고, 404면 오류 페이지를 표시해야 합니다.

**SEO와 크롤링**에서도 상태 코드는 중요합니다. 검색 엔진 봇은 404나 500을 받으면 해당 페이지를 인덱싱에서 제외하고, 301을 받으면 새 URL로 인덱싱을 변경합니다.

## ⚠️ 해결하는 문제

### 문제 1: 요청 처리 결과의 명확한 전달

**문제**: HTTP가 없던 초기에는 요청이 성공했는지 실패했는지 명확히 알 방법이 없었습니다. 응답의 유무로만 판단해야 했기 때문에, 같은 응답도 성공인지 실패인지 구분하기 어려웠습니다.

**해결 방법**: HTTP 상태 코드는 3자리 숫자로 요청의 결과를 명확하게 분류합니다. 클라이언트는 상태 코드만 보고도 즉시 요청이 성공했는지, 어떤 종류의 실패인지 파악할 수 있습니다. 이를 통해 사용자에게 적절한 피드백을 제공하고 프로그래밍 로직을 올바르게 작성할 수 있습니다.

### 문제 2: 서버의 리다이렉트 지시

**문제**: 웹사이트 구조가 변경되거나 페이지가 이동했을 때, 기존 링크들을 모두 수정해야 했습니다. 또한 클라이언트가 자동으로 새 위치로 이동할 방법이 없었습니다.

**해결 방법**: 3xx 상태 코드와 Location 헤더를 통해 서버는 클라이언트를 새로운 URL로 자동 리다이렉트할 수 있습니다. 브라우저는 3xx를 받으면 자동으로 Location 헤더의 URL로 새 요청을 보냅니다. 이를 통해 기존 링크를 유지하면서 페이지 이동을 투명하게 처리할 수 있으며, SEO에서도 301을 통해 검색 순위를 새 URL로 이전할 수 있습니다.

### 문제 3: 클라이언트 오류와 서버 오류의 구분

**문제**: 요청이 실패했을 때 그 원인이 클라이언트의 잘못인지(예: 잘못된 데이터), 서버의 문제인지(예: 데이터베이스 오류) 알 수 없으면, 적절한 해결책을 수립할 수 없습니다.

**해결 방법**: 4xx는 클라이언트 오류, 5xx는 서버 오류로 명확히 구분합니다. 클라이언트는 4xx를 받으면 입력 데이터를 수정하거나 권한을 확인하고, 5xx를 받으면 서버 상태를 확인할 때까지 대기합니다. API 개발자는 적절한 4xx/5xx 코드를 반환함으로써 버그 원인을 빠르게 파악할 수 있습니다.

## ⚙️ 작동 원리

### 1단계: 클라이언트 요청
클라이언트가 HTTP 요청을 서버로 보냅니다. 요청에는 메서드(GET, POST, PUT, DELETE 등), URL, 헤더, 바디 등이 포함됩니다.

### 2단계: 서버 처리
서버가 요청을 받고 처리를 시작합니다. 여기서 여러 가지 검증 및 처리 단계가 일어납니다:
- URL이 유효한지 확인 (존재하지 않으면 404)
- 사용자가 인증되었는지 확인 (아니면 401)
- 사용자가 권한을 가졌는지 확인 (아니면 403)
- 요청 데이터가 유효한지 검증 (아니면 400)
- 처리 중 오류 발생 (5xx)

### 3단계: 상태 코드 결정
서버가 처리 결과에 따라 적절한 상태 코드를 결정합니다. 위의 검증 단계에서 문제가 없으면 성공 코드(2xx)를 반환합니다.

### 4단계: HTTP 응답 생성
서버가 상태 코드, 응답 헤더(Content-Type, Location, Set-Cookie 등), 응답 바디를 포함한 HTTP 응답을 구성합니다.

### 5단계: 응답 전송 및 클라이언트 처리
클라이언트가 응답을 받고 상태 코드에 따라 다른 처리를 수행합니다:
- 2xx: 정상 처리 (데이터 표시, UI 업데이트)
- 3xx: 리다이렉트 (새 URL로 요청)
- 4xx: 사용자 오류 처리 (입력 재시도, 로그인 등)
- 5xx: 서버 오류 처리 (재시도, 오류 메시지 표시)

### 6단계: 로깅 및 모니터링
서버는 모든 요청과 상태 코드를 로그에 기록합니다. 통계 분석을 통해 4xx, 5xx의 빈도를 모니터링하고, 문제 패턴을 파악할 수 있습니다.

## 📊 비교

| 상태 코드 | 의미 | 언제 발생하는가 | 해결 방법 |
|----------|------|-----------------|----------|
| **200 OK** | 요청 성공 | GET, POST, PUT 등이 정상 처리됨 | 응답 데이터를 사용하면 됨 |
| **201 Created** | 자원 생성 성공 | POST로 새 자원 생성 완료 | Location 헤더의 자원 URL 확인 |
| **301 Moved Permanently** | 영구 이동 | 페이지가 새 URL로 이동(검색 순위 이전) | 북마크/링크를 새 URL로 변경 |
| **302 Found** | 임시 이동 | 페이지가 임시로 다른 URL로 이동 | 브라우저 자동 리다이렉트 (원래 URL은 변경 안함) |
| **400 Bad Request** | 잘못된 요청 | 잘못된 파라미터, 잘못된 JSON 형식 | 요청 데이터 재검토 및 수정 |
| **401 Unauthorized** | 인증 필요 | 사용자가 로그인하지 않음 | 로그인 페이지로 이동 후 인증 |
| **403 Forbidden** | 접근 금지 | 사용자는 인증되었으나 권한 부족 | 관리자에게 권한 요청 또는 다른 계정 사용 |
| **404 Not Found** | 자원 없음 | 요청한 페이지/API 엔드포인트가 없음 | URL 확인, 검색 활용, 홈 페이지 이동 |

## ✅ 장단점

### 장점

1. **명확한 의도 표현**: 각 상태 코드는 정확한 상황을 나타내므로, 클라이언트가 적절한 처리를 할 수 있습니다.

2. **국제 표준**: HTTP 상태 코드는 RFC 7231 등의 표준으로 정의되어 있어, 모든 웹 서버와 클라이언트가 동일하게 이해합니다.

3. **디버깅 용이**: 웹 개발 시 브라우저의 개발자 도구나 API 테스트 도구로 상태 코드를 즉시 확인하고 문제를 진단할 수 있습니다.

4. **자동화된 처리**: 3xx 리다이렉트는 브라우저가 자동으로 처리하므로, 페이지 이동을 투명하게 관리할 수 있습니다.

5. **SEO 최적화**: 301/302 상태 코드를 올바르게 사용하면 검색 엔진 순위 이전과 크롤링 효율성을 높일 수 있습니다.

### 단점

1. **코드 오용**: 개발자가 상태 코드를 부정확하게 사용하면(예: 404 대신 500 반환), 클라이언트가 잘못된 판단을 할 수 있습니다.

2. **기본 분류의 한계**: 2xx, 3xx, 4xx, 5xx의 5가지 분류로는 모든 상황을 완벽하게 표현하기 어려울 수 있습니다.

3. **사용자 혼동**: 최종 사용자가 4xx나 5xx 오류를 받을 때 정확한 원인을 이해하기 어려울 수 있어, 추가적인 오류 메시지가 필요합니다.

4. **표준 확장의 부족**: 표준에 없는 사용자 정의 상태 코드를 만들면 호환성 문제가 발생할 수 있습니다.

5. **개발자 경험**: 복잡한 시나리오에서 어떤 상태 코드를 반환해야 할지 애매할 수 있습니다(예: 401 vs 403).

## 💡 실제 사례

### 사례 1: 전자상거래 API의 상태 코드 활용

```
POST /api/orders (새 주문 생성)
요청 성공 → 201 Created + Location: /api/orders/12345

POST /api/orders (잘못된 상품 ID)
요청 실패 → 400 Bad Request + { "error": "Invalid product ID" }

GET /api/orders/99999 (존재하지 않는 주문)
조회 실패 → 404 Not Found + { "error": "Order not found" }

GET /api/admin/orders (비로그인 사용자)
접근 실패 → 401 Unauthorized + { "error": "Login required" }

GET /api/admin/orders (일반 사용자)
권한 부족 → 403 Forbidden + { "error": "Admin access required" }
```

### 사례 2: 웹사이트 리뉴얼에서의 301 리다이렉트

기존 사이트: https://old-site.com/products
새 사이트: https://new-site.com/catalog

서버 설정:
```
GET /products → 301 Moved Permanently
Location: https://new-site.com/catalog
```

효과:
- 사용자가 기존 링크에 접속하면 자동으로 새 사이트로 이동
- 검색 엔진 순위가 새 URL로 자동 이전
- 기존 북마크도 여전히 작동

### 사례 3: 레이트 리미팅(Rate Limiting)에서의 429 응답

API 서버에서 분당 100개 요청 제한 설정:

```
첫 100개 요청 → 200 OK
101번째 요청 → 429 Too Many Requests
응답 헤더: Retry-After: 60 (60초 후 재시도)
```

클라이언트는 429를 받으면:
- 사용자에게 "요청이 너무 많습니다. 잠시 후 다시 시도하세요" 표시
- 자동으로 60초 후 재시도

## 🔗 관련 용어

- **HTTP (HyperText Transfer Protocol)**: URL의 자원을 요청하기 위한 프로토콜
- **REST API**: HTTP 메서드와 상태 코드를 기반으로 설계하는 API 스타일
- **HTTPS**: HTTP에 보안(SSL/TLS)을 추가한 프로토콜
- **HTTP 메서드**: GET, POST, PUT, DELETE 등 요청의 동작 지정
- **응답 헤더**: Content-Type, Location, Set-Cookie 등 추가 정보 전달
- **리다이렉트**: 3xx 상태 코드로 지시하는 다른 URL로의 이동
- **레이트 리미팅**: 429 상태 코드로 구현하는 요청 제한
- **에러 핸들링**: 4xx/5xx 상태 코드에 따른 클라이언트 처리 로직
