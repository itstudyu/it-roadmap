# Browser Rendering (브라우저 렌더링)

## 📝 정의

브라우저 렌더링은 **글자로 온 문서를 화면 픽셀로 바꾸는 과정**이다.

서버가 보내오는 것은 그림이 아니라 글자다. MDN 은 HTML·CSS·JavaScript 를 화면 픽셀로 바꾸기까지 브라우저가 거치는 단계들을 **Critical Rendering Path(중요 렌더링 경로)** 라고 부른다. 이 경로를 짧게 만드는 것이 첫 화면을 앞당기는 일이다.

### 비유
인쇄소. 원고와 편집 지시를 받아 먼저 판을 짜고, 판이 정해진 다음에야 잉크를 얹는다.

## 🖼️ 그림으로 보기

```도해
흐름: 받아 온 HTML 이 화면 픽셀이 되기까지 무엇을 거치나
파싱 :: HTML 을 읽어 DOM 트리로 쌓는다
스타일 :: CSS 를 모아 어떤 규칙이 붙는지 계산한다
렌더 트리 :: 둘을 합쳐 보이는 것만 남긴다
레이아웃 :: 무엇이 어디에 얼마만큼 놓이는지 정한다
페인트 :: 글자·색·테두리·그림자를 픽셀로 칠한다
합성 :: 여러 겹을 순서대로 겹쳐 화면에 올린다
= 글자에서 픽셀까지 여섯 단계다. 앞이 정해져야 뒤를 할 수 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 렌더링이 한 덩어리라면 무엇이 나빠지나
한 덩어리로 || 단계를 나눠
색만 바꿀 때 :: 처음부터 다시 || 칠하기만 다시
스크롤할 때 :: 매번 전부 계산 || 겹치기만 다시
안 보이는 것 :: 다 계산한다 || 트리에서 뺀다
= 단계가 나뉘어 있어서, 바뀐 만큼만 다시 하고 넘어갈 수 있다
```

문서가 글자로 오니 누군가 픽셀로 바꿔야 한다. 문제는 그 일이 한 번으로 끝나지 않는다는 것이다. 화면이 부드럽게 움직이려면 이 과정이 매초 수십 번 되풀이돼야 한다.

web.dev 는 그 예산을 숫자로 준다 — 요즘 화면은 대개 **1초에 60번** 새로 그려지니 한 장을 만드는 데 쓸 수 있는 시간이 16.66ms 이고, 브라우저 자체의 몫을 빼면 개발자가 쓸 수 있는 것은 **10ms 안쪽**이다. 이 예산을 못 지키면 프레임이 떨어지고 화면이 덜컹거린다.

여섯 단계로 쪼개 둔 것이 그 예산을 지키는 방법이다. 무엇을 바꿨는지에 따라 뒤쪽 단계만 다시 하면 되기 때문이다. 처음 열 때는 화면 전체를 칠하지만 그다음부터는 영향받은 자리만 다시 칠한다. `display: none` 인 것과 그 안의 것들은 [[DOM]] 에는 있어도 렌더 트리에 아예 들어가지 않아 계산에서 빠진다.

## ⚙️ 작동 원리

```도해
층: 무엇을 바꿨느냐에 따라 어디서부터 다시 하나
합성만 :: `transform`·`opacity`. 겹치기부터
칠하기부터 :: `color`·`box-shadow`. 레이아웃을 건너뛴다
레이아웃부터 :: `width`·`top`. 트리를 다시 잰다
= 위에서 끝나는 변화가 싸다. 아래로 갈수록 다시 하는 일이 늘어난다
```

레이아웃이 왜 비싼가. 웹의 배치 모형에서는 **한 요소가 다른 요소에 영향을 준다.** web.dev 는 `<body>` 의 너비가 그 자식들의 크기를 트리 위아래로 죄다 바꿔놓는다는 예를 들면서, 그래서 이 계산이 상당히 번거로운 일이 된다고 적었다. 요소 하나의 기하를 건드리면 브라우저는 **다른 요소를 전부 확인해서 페이지를 다시 흘려야** 한다.

여기에 규모가 곱해진다. MDN 은 레이아웃 성능이 DOM 에 달려 있다고 못 박는다 — 노드가 많아질수록 레이아웃이 오래 걸린다. 그리고 렌더 트리가 바뀌는 모든 순간, 즉 노드가 추가되거나 내용이 달라지거나 박스 모형 스타일이 갱신될 때마다 레이아웃이 일어난다.

반대쪽 끝은 싸다. 레이아웃도 페인트도 필요 없는 속성을 바꾸면 브라우저는 곧장 합성 단계로 건너뛸 수 있고, web.dev 는 이것을 픽셀 파이프라인에서 **가장 싸고 가장 바람직한 길**이라고 적었다. 그런 속성은 딱 둘이다 — `transform` 과 `opacity`.

## 💡 실제 사례

- **애니메이션을 `transform` 으로 짠다** — `left` 로 옮기면 매 프레임 레이아웃부터 다시 하지만, `transform` 이면 겹치기만 다시 한다.
- **화면을 돌리면 페이지가 다시 짜인다** — 레이아웃은 화면 크기에 딸린 계산이라, 기기를 돌리거나 창 크기를 바꿀 때마다 다시 일어난다.
- **`display: none` 은 자리도 차지하지 않는다** — 렌더 트리에 아예 안 들어가므로 그 안에 든 것까지 계산에서 빠진다.

## 🚫 흔한 오해

- **HTML 을 다 받아야 화면이 그려진다** — DOM 은 읽는 대로 조금씩 쌓인다. 정작 화면을 막는 쪽은 CSS 다 — 뒤에 오는 규칙이 앞을 덮을 수 있어서, 브라우저는 CSS 를 다 처리할 때까지 그리기를 미룬다.
- **레이아웃이 화면을 칠하는 단계다** — 레이아웃은 자리와 크기만 정한다. 픽셀을 채우는 것은 그다음 페인트고, 그래서 레이아웃이 끝나기 전에는 칠할 수가 없다.
- **화면이 덜컹거리면 페인트를 줄여야 한다** — 대개 범인은 레이아웃이다. MDN 도 페인트는 아주 빠른 편이라 성능을 손볼 때 가장 효과 큰 자리가 아니라고 적었다.

## 🚨 주의사항

- **CSS 는 화면을 막는다.** 규칙이 뒤에서 덮일 수 있어 CSSOM 이 완성될 때까지 브라우저가 그리기를 미룬다. 지금 화면에 필요 없는 CSS 를 앞에 두면 첫 화면이 그만큼 늦는다.
- **갱신은 모아서 한 번에 한다.** 렌더 트리가 바뀔 때마다 레이아웃이 일어난다. MDN 은 레이아웃이 벌어지는 횟수와 시간을 줄이려면 갱신을 묶고 박스 모형 속성으로 애니메이션하지 말라고 적었다.
- **노드 수가 곧 비용이다.** 몇 개 늘어난 것은 티가 안 나지만, 노드를 많이 늘리면 뒤따르는 모든 단계가 그만큼 길어진다.

## 📝 정리

브라우저 렌더링은 글자로 온 문서를 픽셀로 바꾸는 여섯 단계다. 단계가 나뉘어 있어서 무엇을 바꿨는지에 따라 다시 하는 범위가 달라지고, 그 범위가 가장 넓은 것이 레이아웃이다. 한 요소의 크기가 다른 요소의 자리까지 바꿔놓기 때문이다.

## ❓ 이해했는지

- 위치를 `left` 대신 `transform` 으로 옮기면 무엇이 줄어드나 → 작동 원리
- HTML 은 읽는 대로 쌓이는데도 첫 화면이 늦는 까닭은 무엇인가 → 주의사항
- 레이아웃이 끝나기 전에는 페인트를 시작할 수 없는 까닭은 → 그림
