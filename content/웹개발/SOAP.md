# SOAP (Simple Object Access Protocol)

## 📝 정의

SOAP은 **XML 봉투로 감싸 메시지를 주고받는 규격**이다.

이름은 Simple Object Access Protocol 의 약자였지만 1.2 부터는 약자가 아니다. 원격으로 객체를 부르는 규격이 아니라 특정 프로그래밍 모델과 무관하게 설계된 메시지 틀이고, 신뢰성·보안·라우팅 같은 것은 틀에서 일부러 빼고 확장에 맡겼다.

### 비유
등기 우편 봉투. 겉봉에 "누가 어떻게 다뤄야 하는지"를 적어 붙이고, 안의 편지는 봉투를 뜯은 사람이 읽는다.

### 예
새로 만드는 API 에서는 보기 어렵고, 오래 굴러온 기업 시스템을 손볼 때 문서에서 만난다.

## 🖼️ 그림으로 보기

```도해
흐름: SOAP 으로 한 번 부르면 무엇이 오가나
보내는 쪽 :: 보낼 내용을 Body 에 적는다
겉장 :: 처리 규칙을 Header 에 얹는다(생략 가능)
봉투 :: Envelope 로 둘을 한 XML 문서로 감싼다
바인딩 :: HTTP POST 같은 전송에 그 봉투를 싣는다
받는 쪽 :: 겉장을 먼저 보고 Body 를 처리한다
< 받는 쪽 :: 결과나 Fault 를 봉투에 담아 돌려준다
= 오가는 것은 언제나 XML 봉투다. 겉장이 규칙, 안이 내용이다
```

## ⚠️ 해결하는 문제

```도해
대조: 봉투 규격이 없으면 시스템 연동은 어떻게 되나
규격 없이 || SOAP 으로
메시지 틀 :: 제품마다 다르다 || 봉투 하나로 같다
전송 :: 틀에 묶여 있다 || 골라 갈아끼운다
처리 규칙 :: 본문에 섞인다 || 겉장에 따로 싣는다
= 내용과 규칙과 전송을 떼어놓아서, 서로 다른 시스템이 같은 봉투로 말한다
```

서로 다른 조직의 시스템이 구조화된 정보를 주고받으려면 메시지의 틀부터 합의해야 한다. 그 틀이 특정 언어나 특정 전송에 묶여 있으면 한쪽이 그 제품을 안 쓰는 순간 연동이 끊긴다.

SOAP 은 봉투 하나로 그 틀을 고정한다. 규격이 스스로 밝힌 목표는 **단순함과 확장성** 둘이고, 그래서 신뢰성·보안·상관관계·라우팅·메시지 교환 패턴 같은 것을 틀에서 일부러 뺐다. 필요하면 겉장에 확장으로 얹으라는 뜻이다.

## 🧱 구성

```도해
층: SOAP 봉투는 어디까지가 규격이고 어디부터가 내 일인가
Envelope :: 바깥 껍데기. 모든 SOAP 메시지가 이걸로 시작한다
Header :: 선택. 어느 노드가 무엇을 처리할지 겉장에 적는다
Body :: 필수. 여기에 실제 내용이 들어간다. 오류는 Fault
Body 안쪽 :: 구조도 뜻도 규격이 정하지 않는다. 계약은 밖에서
= 봉투와 겉장까지가 SOAP 이고, 안의 뜻은 SOAP 밖의 일이다
```

## ⚙️ 작동 원리

봉투를 다루는 주체를 규격은 **노드**라고 부른다. 메시지를 보내고 받고 처리하고 중계하는 처리 논리가 노드고, 노드는 URI 로 표시된 역할(role)을 맡는다. 겉장의 블록은 그 역할을 겨눠 붙인다.

여기에 규칙 하나가 붙는다 — 자기에게 겨눠진 필수 블록이 있으면, 노드는 그것을 처리하거나 아니면 **메시지를 아예 처리하지 않아야** 한다. 모르는 규칙을 조용히 건너뛰고 본문만 처리하는 길은 막혀 있다. 처리가 틀어지면 Fault 를 돌려주는데, 분류를 담은 Code 와 사람이 읽을 Reason 은 필수고 Node·Role·Detail 은 선택이다.

전송에 싣는 일은 **바인딩**이 맡는다. HTTP 바인딩에서 요청-응답은 POST 로 가고, 봉투는 `application/soap+xml` 이라는 미디어 타입으로 실린다. 무엇을 하려는 요청인지는 그 미디어 타입의 `action` 파라미터가 가리키지만, 그 값의 뜻은 규격 바깥에서 따로 알아내야 하고 받는 쪽이 그것을 요구해서도 안 된다.

## 📊 비교: SOAP 과 REST 는 무엇을 다르게 정하나

| | SOAP | REST |
|---|---|---|
| 정하는 것 | 봉투 구조와 처리 규칙 | HTTP 를 쓰는 방식 |
| 본문 형식 | XML 1.0 직렬화로 못 박힘 | 정하지 않는다. 주로 JSON |
| 무엇을 하려는지 | 봉투 안과 `action` 파라미터 | 주소와 메서드 |
| HTTP 메서드 | 요청-응답은 POST 하나 | 동작마다 갈라 쓴다 |
| 계약 | WSDL 같은 별도 문서 | 규칙이 같아 짐작 가능 |

밀려난 자리는 가운데 세 줄이다. 요청-응답을 POST 하나로만 보내면 주소와 메서드가 뜻을 나르지 못하고, 무엇을 하려는지는 `action` 에 적히는데 그 값은 규격 밖에서 알아내야 한다. 봉투 안의 구조와 뜻도 규격이 정하지 않으니 계약 문서가 하나 더 붙는다. REST 는 이 셋을 HTTP 에 맡겨 덜어냈다.

## 💡 실제 사례

- **여러 노드를 거쳐 가는 메시지** — 겉장 블록을 특정 역할에 겨눠 필수로 걸어두면, 그 규칙을 모르는 중계 노드가 본문만 처리하고 넘어가는 일을 규격이 막아준다.
- **HTTP 가 아닌 길로 보낼 때** — 봉투는 그대로 두고 바인딩만 갈아 끼운다. 규격이 전송을 정해두지 않은 덕이다.
- **계약을 문서로 못 박아야 할 때** — 봉투 안을 규격이 정하지 않으므로, 무엇을 어떤 형태로 주고받는지는 WSDL 같은 기술 문서가 대신 못 박는다.

## 🚫 흔한 오해

- **SOAP 은 HTTP 위에서만 쓴다** — 규격은 전송을 정하지 않는다. HTTP 는 여러 바인딩 중 하나이고, 같은 봉투를 다른 전송에 실어도 SOAP 이다.
- **이름에 Object 가 있으니 원격으로 객체를 부르는 것이다** — 1.2 부터 SOAP 은 약자가 아니다. 틀 자체가 특정 프로그래밍 모델과 무관하게 설계됐고, Body 안을 어떻게 해석할지는 규격이 정하지 않는다.
- **REST 가 언제나 SOAP 보다 낫다** — 겉장에 처리 규칙을 싣고, 중계 노드가 그걸 반드시 이해하게 만들고, HTTP 가 아닌 전송에도 같은 메시지를 태우는 일은 SOAP 이 규격으로 정해둔 자리다. 그 셋이 필요 없는 웹 API 라면 REST 가 가볍다.

## 📝 정리

SOAP 은 보낼 내용을 XML 봉투에 넣고 겉장에 처리 규칙을 얹는 메시지 규격이다. 전송을 가리지 않고 중계 노드에 규칙을 강제할 수 있는 대신, 봉투 안의 뜻은 정해주지 않아 계약 문서가 따로 필요하다. REST 는 그 두 자리를 HTTP 에 맡겨 덜어냈고, SOAP 은 앞 세대가 됐다.

## ❓ 이해했는지

- 같은 요청인데 SOAP 쪽은 주소만 봐도 무엇을 하려는지 알 수 없는 까닭은 → 비교
- 겉장의 규칙 하나를 모르는 노드가 본문만 처리하고 넘어가면 안 되는 까닭은 → 작동 원리
- 이름에 Object 가 들어 있는데도 객체를 부르는 규격이 아닌 까닭은 → 흔한 오해
