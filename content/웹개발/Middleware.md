# Middleware

## 📝 정의

Middleware는 웹 애플리케이션에서 요청(Request)과 응답(Response) 사이에 실행되는 중간 처리 함수 또는 레이어입니다. HTTP 요청이 실제 핸들러(컨트롤러)에 도달하기 전에 전처리를 수행하거나, 응답을 반환하기 전에 후처리를 수행합니다. 미들웨어는 파이프라인 구조로 연결되어 순차적으로 실행됩니다.

미들웨어의 핵심은 공통된 로직을 한곳에 집중시켜 코드 중복을 제거하고, 요청 처리의 흐름을 제어한다는 것입니다. 인증 확인, 로깅, CORS 처리, 요청 데이터 검증, 압축 등 횡단 관심사(Cross-Cutting Concerns)를 효과적으로 관리할 수 있습니다.

> **한 줄 요약**: 요청과 응답 사이에서 실행되는 중간 처리 함수로, next() 호출을 통해 파이프라인으로 연결

### 비유
- 🔵 **공항 수하물 검사**: 탑승객(요청) → 보안검색 → 게이트 → 탑승(응답) 각 단계가 미들웨어 같이 연결
- 🟡 **생산 라인의 품질검사**: 원재료 → 검사1(색상) → 검사2(크기) → 포장 각 단계가 순차 실행

---

## 🎯 핵심 개념

### 1. 파이프라인 구조
요청 → 미들웨어1 → 미들웨어2 → 미들웨어3 → 핸들러 → 응답

각 미들웨어는 다음 미들웨어로 제어를 넘기기 위해 next() 함수를 호출합니다. next()를 호출하지 않으면 요청 흐름이 중단되고 응답을 반환합니다.

### 2. 요청-응답 가로채기
미들웨어는 요청 객체(req)와 응답 객체(res)에 접근하여 데이터를 수정하거나 검증할 수 있습니다. 예를 들어 토큰을 검증하여 user 객체를 req에 추가할 수 있습니다.

### 3. 공통 로직 분리
인증, 로깅, 에러 처리 등을 각 핸들러에서 반복하지 않고 미들웨어에서 한 번만 정의합니다.

---

## ⚠️ 해결하는 문제

### 문제 1: 코드 중복
매 요청마다 인증을 확인하려면 모든 핸들러에 동일한 로그인 검증 코드를 작성해야 합니다. 나중에 인증 로직이 변경되면 모든 핸들러를 수정해야 합니다.

### 문제 2: 관심사의 혼재
핸들러 함수가 비즈니스 로직뿐 아니라 로깅, 인증, 에러 처리 등을 모두 담당하면 코드가 복잡해집니다. 미들웨어를 사용하면 각 계층의 책임을 분명히 할 수 있습니다.

## 🏗️ 구조


```도해
흐름: Middleware, 무슨 순서로 오가나
클라이언트 :: GET /api/user Authorization: Bear…

인증 미들웨어 :: 토큰 검증

로깅 미들웨어 :: 로그 기록 GET /api/user by user-1
로깅 미들웨어 :: next() 호출
핸들러 :: 사용자 데이터 조회
데이터베이스 :: 데이터 반환
핸들러 :: 200 OK {id:1, name:...}
```

## ⚙️ 작동 원리

미들웨어의 작동 원리는 다음과 같습니다. 클라이언트의 HTTP 요청이 서버에 도착하면 먼저 라우팅 전에 글로벌 미들웨어가 실행됩니다.

첫 번째 미들웨어가 요청 객체(req)와 응답 객체(res)에 접근하여 필요한 전처리를 수행합니다. 예를 들어 인증 미들웨어는 Authorization 헤더에서 토큰을 추출하여 검증하고, 유효하면 사용자 정보를 req.user에 저장합니다.

각 미들웨어는 처리를 마친 후 next() 함수를 호출하여 다음 미들웨어로 제어를 넘깁니다. 만약 미들웨어가 요청을 거부하거나 에러가 있으면 next()를 호출하지 않고 직접 응답을 반환하여 파이프라인을 중단합니다.

모든 미들웨어를 거친 후 최종적으로 라우트 핸들러(컨트롤러)가 실행되어 비즈니스 로직을 처리하고 응답을 생성합니다. 응답은 다시 역순으로 미들웨어를 지나가면서 응답 헤더 조정, 데이터 변환 등의 후처리를 거친 후 클라이언트에게 반환됩니다.

## ✅ 장단점

**장점**
- 코드 중복 제거 → DRY(Don't Repeat Yourself) 원칙 준수
- 횡단 관심사를 체계적으로 관리
- 요청 처리 흐름이 명확하고 제어하기 쉬움
- 새로운 기능 추가 시 미들웨어만 추가하면 됨
- 테스트가 용이 (단위 테스트 가능)
- 재사용성 높음 (여러 프로젝트에서 재사용)

**단점**
- 미들웨어 순서에 따라 동작이 달라짐 (순서 관리 필수)
- 과도한 미들웨어는 성능 저하
- 디버깅이 복잡할 수 있음 (여러 계층 거침)
- 미들웨어 체인이 길면 유지보수 어려움
- 에러 처리가 복잡할 수 있음

## 💡 실제 사례

**로그인 체크 미들웨어**
모든 보호된 라우트(/dashboard, /profile, /settings)에 접근하기 전에 로그인 여부를 확인하는 미들웨어를 적용하면, 각 핸들러에서 중복으로 확인하지 않아도 됩니다.

**CORS 처리 미들웨어**
프론트엔드가 다른 도메인의 API에 접근할 때 CORS 정책을 위반하지 않도록, 서버 시작 시 CORS 미들웨어를 등록합니다. 모든 요청에 대해 자동으로 필요한 CORS 헤더가 추가됩니다.

**요청 데이터 압축 미들웨어**
응답 데이터가 크면 자동으로 gzip 압축을 적용하여 네트워크 트래픽을 줄일 수 있습니다. compression 미들웨어를 Express에 등록하면 모든 응답이 자동 압축됩니다.

**로깅 미들웨어**
모든 요청의 메서드, URL, 응답 시간, 상태 코드를 기록하여 서버 모니터링과 디버깅을 쉽게 합니다.
