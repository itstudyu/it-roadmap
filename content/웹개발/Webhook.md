# Webhook

## 📝 정의

Webhook은 특정 이벤트 발생 시 서버가 지정된 URL로 자동으로 HTTP 요청을 보내는 메커니즘입니다. 전통적인 폴링(Polling) 방식과 달리 이벤트 기반(Event-driven) 구조로 동작하여, 변화가 발생했을 때만 알림을 보냅니다. Webhook을 통해 시스템 간의 실시간 연동이 가능합니다.

Webhook은 "역방향 API(Reverse API)"라고도 불립니다. 일반적으로 클라이언트가 서버에 요청하지만, Webhook은 서버가 클라이언트에게 먼저 알림을 보내는 방식입니다. 클라이언트는 미리 콜백 URL을 서버에 등록하고, 특정 이벤트 발생 시 서버가 그 URL로 데이터를 푸시합니다.

> **한 줄 요약**: 이벤트 발생 시 서버가 지정된 URL로 자동으로 HTTP POST 요청을 보내는 이벤트 알림 메커니즘

### 비유
- 🔵 **배달 앱 알림**: 음식이 준비되면 가게가 손님에게 "준비됐어요" 메시지를 먼저 보내는 것 (Webhook)
- 🟡 **우편함 확인**: 매번 우편함을 열어보는 것 (Polling) vs 편지가 도착하면 종을 울려주는 것 (Webhook)

## 🎯 핵심 개념

### 1. 이벤트 기반 아키텍처(Event-Driven)
특정 조건이나 사건(결제 완료, 주문 생성, 파일 업로드)이 발생했을 때만 서버가 등록된 URL로 데이터를 전송합니다.

### 2. Push vs Pull 방식
- **Pull(폴링)**: 클라이언트가 계속 서버에 "업데이트 있나요?" 확인 → 비효율적
- **Push(Webhook)**: 서버가 변화 발생 시 클라이언트에게 먼저 알림 → 효율적

### 3. 페이로드(Payload)
Webhook 요청에 포함된 JSON 데이터로, 이벤트 관련 정보(사용자 ID, 주문 번호, 타임스탐프 등)를 담고 있습니다.

---

## ⚠️ 해결하는 문제

### 문제 1: 폴링의 비효율성
매초 또는 매분마다 서버에 "변화 있나요?" 요청을 보내면 대부분의 요청이 "변화 없음"을 반환하므로 불필요한 트래픽과 서버 부하가 발생합니다.

### 문제 2: 실시간 업데이트의 지연
폴링 간격이 길수록 업데이트 감지가 늦어집니다. 예를 들어 1분마다 확인하면 최대 1분의 지연이 발생합니다.

## ⚙️ 작동 원리

Webhook의 작동 방식은 다음과 같습니다. 먼저 수신자(클라이언트)가 발신자(서버)에게 "특정 이벤트가 발생하면 이 URL로 데이터를 보내주세요"라고 콜백 URL을 등록합니다.

이후 발신자에서 등록된 이벤트가 발생하면, 서버는 즉시 페이로드(event 관련 데이터)를 JSON 형태로 구성하여 HTTP POST 요청으로 콜백 URL에 전송합니다.

수신자는 Webhook 엔드포인트에서 요청을 받아 처리하고 200 OK 등의 성공 응답을 반환합니다. 만약 수신자가 응답하지 않거나 오류를 반환하면, 발신자는 일반적으로 지수 백오프(Exponential Backoff) 방식으로 재시도합니다(예: 5초 후, 30초 후, 5분 후).

보안을 위해 많은 서버는 Webhook 요청에 서명(HMAC)을 포함하여 위변조를 방지합니다.

## 📊 비교

| 항목 | Webhook | Polling | WebSocket | SSE(Server-Sent Events) |
|------|---------|---------|-----------|--------------------------|
| **통신 방향** | 서버 → 클라이언트 (푸시) | 클라이언트 → 서버 | 양방향 (풀더플렉스) | 서버 → 클라이언트 (단방향) |
| **프로토콜** | HTTP POST | HTTP GET | WebSocket | HTTP |
| **실시간성** | 높음 (이벤트 기반) | 낮음 (지연 가능) | 매우 높음 | 높음 |
| **네트워크 효율** | 효율적 | 비효율적 | 매우 효율적 | 효율적 |
| **서버 부하** | 낮음 | 높음 | 중간 | 중간 |
| **구현 복잡도** | 중간 | 낮음 | 높음 | 중간 |
| **브라우저 지원** | 우수 | 우수 | 우수 | 우수 |
| **사용 사례** | 이벤트 알림, CI/CD | 간단한 상태 확인 | 실시간 채팅, 게임 | 실시간 뉴스 피드 |

## ✅ 장단점

**장점**
- 이벤트 발생 시에만 요청 → 네트워크 효율적
- 서버 부하 감소 → 비용 절감
- 거의 실시간 알림 가능
- 구현이 비교적 간단
- 여러 시스템 간 느슨한 결합 가능

**단점**
- 요청 실패 시 재시도 로직 필요 (복잡성 증가)
- 페이로드 전송 보장 어려움 (최대한 1회 전송 방식)
- 보안: URL 노출, MITM 공격 위험
- 디버깅이 어려움 (비동기, 실시간 처리)
- 수신자가 다운되면 데이터 손실 가능
- 네트워크 분할 상황에서 처리 복잡

## 💡 실제 사례

**GitHub의 PR 생성 Webhook**
GitHub에서 Pull Request가 생성되면 Webhook을 통해 Slack 채널로 자동 알림을 보냅니다. 개발팀이 즉시 PR을 검토할 수 있습니다.

**결제 게이트웨이의 결제 완료 알림**
Stripe, PayPal 등의 결제 서비스에서 결제가 완료되면 Webhook으로 쇼핑몰 서버에 알려줍니다. 쇼핑몰 서버는 이를 받아 주문 상태를 "결제완료"로 업데이트하고 배송 준비를 시작합니다.

**Git 저장소 푸시 이벤트**
개발자가 코드를 푸시하면 Webhook을 통해 CI/CD 파이프라인이 자동으로 시작됩니다. 빌드, 테스트, 배포가 순차적으로 진행됩니다.
