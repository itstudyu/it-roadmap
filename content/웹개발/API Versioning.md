# API Versioning (API 버저닝)

## 📝 정의

API Versioning 은 **API 를 고치면서 옛 클라이언트를 살려 두는 장치**다.

고칠 권한은 만든 쪽에 있지만, 그 API 를 부르는 코드는 남의 손에 있다. Azure 의 API 설계 지침은 이 비대칭을 그대로 적어 뒀다 — API 를 만든 사람은 API 를 완전히 통제하지만, 다른 조직이 만든 클라이언트는 그만큼 통제할 수 없다는 것이다. 그래서 규격을 깨는 변경이 필요할 때는 지금 것을 고치는 대신 번호를 하나 올려 **새 버전을 따로 낸다.** Semantic Versioning 이 major 번호를 "호환이 깨지는 변경을 넣을 때" 올리라고 정해 둔 것과 같은 뜻이다.

### 비유
이사한 뒤에도 옛 주소로 오는 편지를 한동안 받아 주는 것과 같다.

## 🖼️ 그림으로 보기

```도해
흐름: 필드 이름을 바꾸면서 옛 앱을 어떻게 안 깨뜨리나
v1 :: 지금 옛 이름으로 답하고 있다
새 규격 :: 이름을 바꾸면 쓰던 앱이 깨진다
v2 내기 :: 바꾼 규격을 새 버전으로 따로 낸다
클라이언트 :: 옛 앱은 v1 에 머물고, 새 앱만 v2 로 간다
v1 닫기 :: 다 옮겨간 뒤에 옛 버전을 접는다
@ 다시 처음으로 :: v2 가 '지금' 이 되고, 다음 변경 때 또 한 바퀴
= 고쳐 끼우는 게 아니라, 새 버전을 나란히 세우고 옮겨갈 시간을 주는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 버전을 안 나누고 API 를 고치면 무슨 일이 벌어지나
버전 없이 || 버전을 나눠
필드 이름 바꾸기 :: 쓰던 앱이 깨진다 || 옛 앱은 그대로
고칠 시점 :: 다 같이 당장 || 각자 옮길 때
옛 규격 :: 어디에도 안 남는다 || v1 로 남아 있다
= 내 코드는 하나지만, 그것을 부르는 코드는 여러 곳에 있다
```

응답에서 필드 하나를 지우거나 이름을 바꾸는 것은 서버 쪽에서 보면 한 줄짜리 변경이다. 그런데 그 필드를 읽던 앱은 그 순간부터 동작을 멈춘다. 앱스토어에 올라간 옛 버전, 남의 회사가 만든 연동, 누군가의 배치 스크립트까지 전부 내 손 밖에 있다.

버전을 나누면 이 문제가 **시간 문제로 바뀐다.** 옛 주소는 옛 규격 그대로 계속 답하고, 새 규격은 새 버전에서만 보인다. Google Cloud 의 API 문서는 한 API 의 major 버전 여럿을 동시에 돌릴 수 있고, 그래야 쓰는 쪽이 언제 옮길지 스스로 고를 수 있다고 적는다. GitHub REST API 는 새 버전을 낸 뒤에도 이전 버전을 최소 24개월 더 지원한다고 약속해 두었다.

## 📊 비교: 버전을 어디에 적나

| 자리 | 어떻게 적나 | 성질 |
|---|---|---|
| **주소** | `/v2/customers/3` | 가장 흔하다. 옛 주소는 옛 규격으로 계속 답한다 |
| **쿼리 문자열** | `?version=2` | 주소는 하나로 유지된다. 안 적으면 기본값으로 |
| **헤더** | `X-GitHub-Api-Version: 2022-11-28` | 주소가 안 더러워진다. 안 적으면 기본 버전 |
| **미디어 타입** | `Accept: application/vnd.example.v1+json` | 요청 형식과 같은 자리에서 고른다 |

주소와 쿼리 문자열은 값이 같으면 내용도 같아서 캐시와 잘 맞는다. 헤더와 미디어 타입 방식은 그 값을 들여다보는 처리가 더 필요하고, 클라이언트마다 버전이 갈리면 중간 캐시에 같은 데이터가 여러 벌 쌓인다.

## 💡 실제 사례

- **주소에 버전을 박기** — `/v1/...` 을 그대로 열어 두고, 규격을 깨야 할 때 `/v2/...` 를 새로 낸다.
- **날짜로 버전을 매기기** — GitHub REST API 는 `X-GitHub-Api-Version` 헤더로 `2022-11-28` 같은 날짜를 받고, 헤더가 없는 요청은 그 기본 버전으로 처리한다.
- **닫힌 버전에 답하기** — 지원이 끝난 버전을 부르면 `410 Gone` 으로 "여긴 이제 없다" 를 알린다. 아무 답도 안 주는 것보다 고칠 곳을 빨리 찾게 해준다.

## 🚫 흔한 오해

- **뭘 고치든 버전을 올려야 한다** — 보태는 변경은 대개 안 깨진다. 응답에 필드를 하나 더 넣어도 그것을 모르는 앱은 무시하고 지나가기 때문에, 이런 변경에는 버전을 올리지 않는다. 번호를 남발하면 지원할 버전만 늘어난다.
- **버전은 주소에만 붙인다** — 헤더나 `Accept` 값으로도 나눈다. GitHub 은 주소가 아니라 헤더에 실린 날짜로 버전을 가른다.
- **새 버전을 냈으니 옛 버전은 닫아도 된다** — 옛 앱은 내 손에 없다. 언제까지 열어 둘지 미리 알리고 그 기간을 지켜야 하며, 그동안 두 버전이 함께 돌아간다.

## 📝 정리

API Versioning 은 API 를 여러 벌 만드는 일이 아니라 **깨지는 변경에 유예 기간을 붙이는 일**이다. 보태는 변경은 그대로 내보내고, 지우거나 이름을 바꾸는 변경만 새 버전으로 가른 뒤 옛 버전을 예고한 기간까지 함께 돌린다.

- 응답에 필드를 하나 더 넣는 변경에는 새 버전을 안 내는 까닭은 → 흔한 오해
