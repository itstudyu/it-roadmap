# REST (Representational State Transfer)

## 📝 정의

REST는 **HTTP 를 자원 중심으로 쓰기로 한 약속**이다.

새로 만든 프로토콜이 아니다. 이미 있던 HTTP 의 주소와 메서드를 어떻게 나눠 쓸지 정한 설계 방식이고, 안 지켜도 통신은 그대로 된다.

### 비유
도서관 서가 번호. 무엇을 찾는지는 번호가 말하고, 빌릴지 반납할지는 창구에서 따로 말한다.

## 🖼️ 그림으로 보기

```도해
흐름: 사용자 정보를 고치려면 무엇을 보내나
주소 :: /users/123 으로 대상을 가리킨다
메서드 :: PUT 으로 무엇을 할지 말한다
본문 :: 바꿀 내용을 JSON 으로 싣는다
서버 :: 이 요청 하나만 보고 처리한다
< 서버 :: 상태 코드와 결과를 돌려준다
= 대상은 주소가, 동작은 메서드가 맡아 둘로 나뉜다
```

## ⚠️ 해결하는 문제

```도해
대조: API 주소를 각자 편한 대로 지으면 어떻게 되나
제각각일 때 || REST 로
주소 :: 동작까지 넣는다 || 대상만 가리킨다
동작 구분 :: 이름으로 짐작 || 메서드로 명시
처음 보는 API :: 문서를 다 읽어야 || 형태로 짐작 가능
= 같은 규칙을 따르면 안 배운 API 도 절반은 읽힌다
```

주소를 짓는 방식에 합의가 없으면 같은 회사 안에서도 API 마다 규칙이 달라진다. 어떤 곳은 `/getUser`, 어떤 곳은 `/user/fetch`, 또 어떤 곳은 `/user?action=get` 이 된다. 쓰는 쪽은 매번 문서를 처음부터 읽어야 하고, 만드는 쪽도 새 기능마다 이름을 놓고 고민한다.

REST 는 이 자리를 둘로 나눠 고정한다. 주소는 대상만 가리키고 동작은 메서드가 맡는다. 규칙이 같으면 처음 보는 API 도 목록 조회와 삭제쯤은 문서 없이 짐작할 수 있다.

## ⚙️ 작동 원리

서버는 요청 사이의 상태를 들고 있지 않는다. 앞선 요청에서 무슨 일이 있었는지 기억하지 않으므로, 요청 하나에 필요한 정보가 전부 들어 있어야 한다. 이 성질 덕분에 서버를 여러 대로 늘려도 어느 대가 받든 결과가 같다.

## 📊 비교: 메서드가 나눠 갖는 동작

| 메서드 | 하는 일 | 예 |
|---|---|---|
| GET | 가져온다. 바꾸지 않는다 | `GET /users/123` |
| POST | 새로 만든다 | `POST /users` |
| PUT | 통째로 바꾼다 | `PUT /users/123` |
| DELETE | 지운다 | `DELETE /users/123` |

## 💡 실제 사례

- **모바일 앱과 서버** — 앱이 같은 주소 규칙으로 목록을 받고 새 글을 올린다.
- **외부 공개 API** — 다른 회사가 붙어 쓰는 API 는 규칙이 예측 가능해야 문의가 줄어든다.
- **관리 도구 연동** — 자원 주소가 일정하면 스크립트로 반복 작업을 짜기 쉽다.

## 🚫 흔한 오해

- **JSON 을 주고받으면 REST API 다** — 형식은 상관없다. 자원을 주소로 가리키고 동작을 메서드로 구분하는지가 기준이라, JSON 을 쓰면서 REST 가 아닌 API 도 많다.
- **주소에 동사를 넣어도 된다** — `/createUser` 처럼 주소에 동작을 넣으면 메서드가 할 일을 주소가 가져간다. 그러면 규칙이 다시 제각각이 된다.
- **무상태라서 로그인을 유지할 수 없다** — 서버가 요청 사이의 상태를 안 들고 있다는 뜻이다. 로그인 정보는 요청마다 토큰으로 같이 보내면 된다.

## 📝 정리

REST 는 주소로 대상을 가리키고 메서드로 동작을 나타내기로 한 API 설계 방식이다. 강제되는 규격이 아니라 합의라서, 지키면 처음 보는 API 도 읽히고 안 지키면 그 이점만 사라진다.

## ❓ 이해했는지

- `/users/123` 에 DELETE 를 보내면 무엇을 뜻하나 → 비교
- 서버가 상태를 안 들고 있는데 로그인은 어떻게 유지하나 → 흔한 오해
- 처음 보는 API 인데도 목록 조회와 삭제쯤은 짐작할 수 있는 이유는 → 해결하는 문제
