# Class (클래스)

## 📝 정의

Class는 **데이터와 기능을 한 덩어리로 묶은 설계도**다.

이름, 나이, 이메일을 따로 변수로 두면 사용자가 늘 때마다 변수가 셋씩 늘어난다. 클래스는 그 값들과 그 값을 다루는 기능을 한 자리에 적어두고, 필요할 때마다 그 틀에서 하나씩 찍어낸다.

### 이름
= class 는 원래 "같은 부류". 같은 부류로 묶어 이름을 붙인 틀이라는 뜻이다

### 비유
붕어빵 틀. 틀은 하나지만 찍어낸 붕어빵은 여러 개고, 각각에 다른 속을 넣을 수 있다.

### 예
앱 설정 화면이 계정마다 값만 다르고 항목과 순서는 똑같은 것이 틀 하나를 쓴 결과다.

## 🖼️ 그림으로 보기

```도해
흐름: 클래스 하나에서 객체가 어떻게 만들어지나
클래스 :: 속성과 기능만 적어둔 틀. 값은 없다
호출 :: User("Alice", 25) 라고 부른다
생성자 :: 넘겨받은 값을 자기 속성에 채운다
객체 :: 값이 채워진 것 하나가 생긴다
사용 :: user.greet() 은 자기 값으로 동작한다
@ 다시 호출로 :: 또 부르면 값이 다른 것이 또 생긴다
= 틀은 하나, 찍혀 나온 것은 여럿. 각자 자기 값을 들고 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 값과 기능이 흩어져 있으면 어떻게 되나
클래스 없이 || 클래스로
사용자 추가 :: 변수 3개씩 늘어남 || 한 줄로 생성
값과 기능 :: 따로 떨어짐 || 한 곳에 묶임
비슷한 구조 :: 복사해서 만듦 || 물려받아 씀
= 함께 다뤄야 할 것을 함께 두는 것이 클래스가 하는 일이다
```

사용자 정보를 `user1_name`, `user1_age`, `user1_email`처럼 두면 사용자가 셋만 돼도 변수가 아홉 개다. 이 값들을 다루는 함수도 매번 이름과 나이와 이메일을 전부 받아야 한다.

값이 흩어지면 어떤 값들이 한 묶음인지 코드만 봐서는 알 수 없다. 클래스는 그 묶음을 이름으로 만들어 눈에 보이게 하고, 그 묶음을 다루는 기능도 같은 자리에 둔다.

## ⚙️ 작동 원리

```python
class User:
    def __init__(self, name, age):   # 생성자
        self.name = name             # 속성
        self.age = age

    def greet(self):                 # 메서드
        return f"{self.name}입니다"

alice = User("Alice", 25)   # 객체 하나
bob = User("Bob", 30)       # 값이 다른 또 하나
```

`__init__`은 객체가 만들어질 때 한 번 불리며 넘겨받은 값을 속성에 채운다. 메서드마다 앞에 붙는 `self`는 지금 이 객체 자신을 가리킨다. 같은 메서드를 여러 객체가 나눠 쓰기 때문에 누구의 값인지 알려주는 자리가 필요하다.

```도해
층: 상속을 쓰면 코드가 어떻게 겹치나
Animal :: 이름과 나이. 모든 동물이 갖는 것
Dog :: 위를 그대로 물려받고 품종을 더한다
바둑이 :: Dog 로 만든 객체. 실제 값을 들고 있다
= 위로 갈수록 공통이고, 아래로 갈수록 구체적이다
```

## 📊 비교: 클래스 vs 객체

| | 클래스 | 객체 |
|---|---|---|
| 정체 | 설계도 | 설계도로 만든 것 |
| 개수 | 하나 | 필요한 만큼 |
| 값 | 없다 | 각자 다른 값을 들고 있다 |
| 코드 | `class Car:` | `car1 = Car()` |

## 💡 실제 사례

- **은행 계좌** — 잔액을 속성으로 두고 입금과 출금만 메서드로 열어, 잔액이 코드 여기저기서 직접 바뀌지 않게 한다.
- **비밀번호 보관** — 값 자체는 밖에서 못 읽게 감추고 맞는지 확인하는 메서드만 내준다.
- **동물 분류** — 이름과 나이는 부모 클래스에 두고, 강아지와 고양이는 우는 소리만 각자 구현한다.

## 🚫 흔한 오해

- **클래스를 만들면 그때 값이 생긴다** — 클래스는 틀이라 그 자체로는 아무것도 들고 있지 않다. 값은 객체를 만드는 순간 생긴다.
- **클래스가 많을수록 잘 짠 코드다** — 메서드 하나뿐인 클래스는 함수로 두는 편이 낫다. 묶을 것이 없는데 묶으면 이름만 늘어난다.
- **상속은 코드를 줄여주니 깊을수록 좋다** — 다섯 단계쯤 내려가면 이 동작이 어느 층에서 왔는지 찾기 어려워진다. 대개 두 단계면 충분하다.

## 🚨 주의사항

- **한 클래스에 여러 책임을 넣지 않는다.** 저장하고 메일 보내고 보고서까지 만드는 클래스는 하나를 고칠 때마다 나머지가 흔들린다.
- **감출 것과 열 것을 정해둔다.** 속성을 전부 밖에서 고칠 수 있으면 메서드를 만들어둔 뜻이 없어진다.

## 📝 정리

**"찍어낼 것을 미리 적어 둔 그 틀"** 이라고 읽으면 된다. 함께 다뤄야 할 값과 기능을 한 이름으로 묶어둔 자리다. 클래스 자체는 값을 들고 있지 않고, 객체를 만들 때마다 자기 값을 가진 것이 하나씩 생긴다.

## 🧒 열 살에게

붕어빵 틀은 하나인데 붕어빵은 여러 개 나오지? 틀에는 팥도 슈크림도 들어 있지 않고, 구울 때마다 속을 따로 넣어서 서로 다른 붕어빵이 돼. 그래서 모양은 다 같은데 안에 든 건 저마다 달라.

## ❓ 이해했는지

- 사용자가 100명이어도 클래스는 하나면 되는 이유는 → 그림
- 메서드마다 `self` 를 받는 이유는 → 작동 원리
- 메서드가 하나뿐인 클래스를 함수로 바꾸는 편이 나은 이유는 → 흔한 오해
