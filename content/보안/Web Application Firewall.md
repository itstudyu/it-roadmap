# Web Application Firewall (웹 앞단 방화벽)

## 📝 정의

Web Application Firewall은 **오가는 웹 요청을 규칙에 비춰 걸러내는 앞단**이다.

OWASP 는 이 말을 "HTTP 응용을 위한 응용 계층 방화벽" 이라 적고, 하는 일을 "HTTP 로 오가는 대화에 규칙 묶음을 적용하는 것" 이라고 한 줄로 정의한다. 포트를 여닫는 보통 방화벽과 갈리는 자리가 여기다. 이쪽은 봉투를 여닫는 게 아니라 봉투 안에 적힌 글자를 읽는다.

### 이름
Web :: 오가는 웹 요청
Application :: 앱이 읽는 내용까지
Firewall :: 막아 세우는 벽
= 붙여 읽으면 "웹 요청의 내용까지 보고 막는 벽". 어느 층을 보느냐가 이름에 적혀 있다

### 비유
공연장 입구의 검색대. 표가 맞는지만 보는 게 아니라 가방을 열어 안에 든 것을 보고 들여보낸다.

### 예
로그인 창에 따옴표 하나를 넣었을 뿐인데 "요청이 차단되었습니다" 안내가 대신 뜨던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 웹 요청 하나가 앱에 닿기까지 어디서 걸러지나
사용자 :: 주소를 열어 요청을 보낸다
앞단 :: 앱보다 먼저 이 앞에 닿는다
대조 :: 주소·머리글·본문을 규칙과 맞춘다
판정 :: 통과 · 차단 · 세기만 · 사람인지 묻기
앱 :: 통과한 것만 받는다. 나머지는 여기 못 온다
= 앱 안을 고치지 않고도 앞에서 한 겹 걸러 내는 자리다
```

## ⚠️ 해결하는 문제

```도해
대조: 앞에 한 겹을 세우면 무엇이 달라지나
앞단 없이 || 앞단을 세우면
새 구멍 대응 :: 고쳐 다시 올린다 || 규칙 한 줄 켠다
막는 자리 :: 앱마다 따로 || 한 군데서 전부
급할 때 :: 다음 판을 기다린다 || 몇 분이면 된다
= 고치는 일과 막는 일은 다른 일이다. 앞단은 고칠 때까지 시간을 벌어 준다
```

같은 공격을 앱 코드 안에서 막으려면 앱마다 따로 손봐야 하고, 앱이 열 개면 열 번 손봐야 한다. Azure 문서는 이 점을 두고 앱 코드에서 막는 일은 여러 층에 걸친 점검과 손질을 계속 요구한다고 적으면서, 앞단을 한 군데 두면 알려진 구멍을 중앙에서 한 번 막아 더 빨리 반응할 수 있다고 설명한다.

시간이 갈림길이다. 구멍이 공개되고 고친 판이 나가기까지는 며칠이 걸릴 수 있는데, 공격은 공개된 날부터 온다. 앞단은 그 사이를 메우는 임시 덮개다.

## 📊 비교: 세 클라우드는 같은 일을 뭐라고 부르나

| 클라우드 | 이름 | 어디에 붙나 |
|---|---|---|
| **AWS** | AWS WAF | CloudFront · API Gateway · Application Load Balancer 앞에 web ACL 을 붙인다 |
| **Azure** | Azure Web Application Firewall | Application Gateway 나 Front Door 위에 얹어 쓴다 |
| **GCP** | Google Cloud Armor | 부하 분산기 앞 가장자리에서 보안 정책으로 막는다 |

이름은 셋 다 다르지만 기본 규칙 묶음의 뿌리는 같다. Cloud Armor 문서는 미리 만들어 둔 규칙이 OWASP Core Rule Set 에서 온 것이라고 밝히고 있고, 다른 두 곳의 관리형 규칙도 같은 목록을 겨눈다.

## 💡 실제 사례

- **급할 때 덮기** — 널리 쓰는 라이브러리에 구멍이 공개됐는데 고친 판을 올릴 시간이 없다. 그 형태의 요청만 막는 규칙을 켜서 시간을 번다.
- **세어만 보기** — 새 규칙을 곧바로 차단으로 켜지 않고 세기만 한다. 진짜 사용자가 몇 명이나 걸리는지 먼저 보고 나서 켠다.
- **횟수로 걸기** — 같은 곳에서 1분에 수천 번 들어오면 그 출처만 잠시 막는다. 내용이 아니라 빈도로 거는 갈래다.

## 🚫 흔한 오해

- **앞단을 세웠으니 앱 구멍은 안 고쳐도 된다** — 아니다. 앞단은 그 형태의 요청을 알아보는 것뿐이라, 같은 뜻을 다른 모양으로 적어 보내면 지나간다. 고치는 일을 없애는 게 아니라 고칠 때까지 버는 것이다.
- **방화벽이 이미 있으니 이건 필요 없다** — 포트를 여닫는 쪽과 요청 내용을 읽는 쪽은 보는 층이 다르다. 웹을 열어 둔 이상 그 포트는 어차피 열려 있고, 공격은 그 열린 포트로 정상 요청인 척 들어온다.
- **관리형 규칙을 켜 두면 알아서 된다** — OWASP 는 앱에 맞추는 품이 상당하고 앱이 바뀌면 계속 손봐야 한다고 적는다. 켜자마자 멀쩡한 요청이 막히는 일이 흔해서, 맞추는 일이 켜는 일보다 오래 걸린다.

## 🚨 주의사항

- **차단부터 켜지 마라.** 세기만 하는 자리를 먼저 두고 어떤 요청이 걸리는지 본 다음 막는다. 순서를 건너뛰면 결제나 글쓰기처럼 본문이 긴 화면이 먼저 막힌다.
- **암호가 풀린 자리에 세워야 한다.** 내용을 읽어야 거를 수 있으니 잠긴 채로 지나가는 구간에서는 아무것도 못 본다.
- **앞단을 안 거치는 길을 남기지 마라.** 원본 주소가 그대로 노출돼 있으면 공격은 앞단을 건너뛰고 곧장 들어간다. 원본은 앞단에서 온 것만 받도록 잠가 둔다.

## 📝 정리

**"앱 앞에 세워 요청 내용까지 보고 거르는 문지기"** 라고 읽으면 된다. 앞단은 그 형태를 알아보는 것이지 구멍을 메우는 것이 아니라서, 고칠 시간을 벌어 줄 뿐 고치는 일을 대신하지 않는다. 그래서 새 규칙은 막는 것부터가 아니라 세어 보는 것부터 시작한다.

## 🧒 열 살에게

공연장에 들어갈 때 표만 보는 게 아니라 가방을 열어 보지? 안에 위험한 걸 넣어 온 사람을 입구에서 돌려보내니까, 공연장 안을 다 뜯어고치지 않아도 그날은 버틸 수 있어. 대신 가방을 안 열고 다른 문으로 들어오는 사람은 못 잡아.
