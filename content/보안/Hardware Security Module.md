# Hardware Security Module (열쇠 전용 금고 장치)

## 📝 정의

Hardware Security Module은 **열쇠를 밖으로 안 내보내는 전용 금고 장치**다.

AWS 문서는 이것을 "암호 연산을 처리하고 암호 키를 안전하게 보관하는 컴퓨팅 장치" 로 적는다. 소프트웨어가 아니라 물건이라는 점이 핵심이라, 얼마나 잘 만들어졌는지를 사람이 아니라 규격이 판정한다. 그 규격이 NIST 의 FIPS 140-3 이고, 네 단계로 나뉜 등급 중 레벨 3 이 이 바닥에서 자주 요구되는 선이다.

### 이름
Hardware :: 만질 수 있는 장치
Security :: 지켜 내는 일
Module :: 한 덩어리 부품
= 붙여 읽으면 "지키는 일을 맡은 장치 한 덩어리". 소프트웨어가 아니라 물건이라는 게 이름의 요점이다

### 비유
도장을 맡기면 절대 안 돌려주는 대신, 서류를 창구로 밀어 넣으면 안에서 찍어서 내주는 가게.

### 예
회사에서 받은 손톱만 한 보안 열쇠를 꽂고 버튼을 눌러 로그인하던 그 순간이다. 그 안의 비밀은 한 번도 밖으로 나오지 않는다.

## 🖼️ 그림으로 보기

```도해
흐름: 열쇠를 안 꺼내는데 어떻게 잠그고 풀 수 있나
만들기 :: 열쇠를 장치 안에서 만든다
맡기기 :: 만든 열쇠는 장치 밖으로 안 나온다
시키기 :: 잠글 것을 장치 안으로 들여보낸다
< 받기 :: 잠근 결과만 돌려받는다
= 열쇠가 나가는 게 아니라 일이 들어온다. 나갈 것이 없으니 베껴 갈 것도 없다
```

## ⚠️ 해결하는 문제

```도해
대조: 열쇠를 보통 저장 장치에 파일로 두면 무엇이 위험한가
파일로 두면 || 금고 장치에 두면
복사 :: 통째로 복사된다 || 꺼낼 수가 없다
관리자 :: 읽을 수 있다 || 못 읽는다
샜을 때 :: 티가 안 난다 || 물건을 뜯어야 한다
= 열쇠를 더 잘 숨기는 게 아니라, 꺼낼 수 없는 곳에 둔다
```

파일로 둔 열쇠의 문제는 잘 숨기고 말고가 아니라 **복사되면 똑같다**는 것이다. 원본이 그대로 있으니 사라진 티도 안 나고, 백업에도 실려 가고, 옛 노트북에도 남는다. 파일을 다루는 권한이 있는 사람은 사실상 그 열쇠를 가진 사람이다.

금고 장치는 그 전제를 뒤집는다. 열쇠는 장치 안에서 만들어져 밖으로 나오지 않고, 잠그거나 서명하는 일은 장치 안에서 끝나고 결과만 나온다. FIPS 140-3 은 이 장치가 지켜야 할 것을 물리적 보안, 역할과 인증, 자체 시험, 민감 파라미터 관리 같은 영역으로 나눠 규정하고, 네 단계의 등급으로 그 엄격함을 매긴다. AWS 는 여기에 한 가지를 더 얹는다 — 데이터 평면이 종단 간 암호화되어 AWS 에게도 안 보이고, 그래서 사용자 관리도 내가 진다.

## 📊 비교: 세 클라우드는 이걸 뭐라 부르나

| 어디 | 부르는 이름 | 무엇을 내세우나 |
|---|---|---|
| **AWS** | CloudHSM | 단일 테넌트 범용 HSM. FIPS 모드 클러스터는 140-2 또는 140-3 레벨 3 검증 |
| **Google Cloud** | Cloud HSM | FIPS 140-2 레벨 3 인증 클러스터. 입력 상한이 8KiB 로 소프트웨어 키(64KiB)보다 작다 |
| **Azure** | Key Vault Managed HSM | 단일 테넌트, FIPS 140-3 레벨 3 검증. 고객마다 별도 보안 도메인으로 갈라 둔다 |

## 💡 실제 사례

- **인증서를 발급하는 뿌리 열쇠** — AWS 는 공개 키 기반 구조를 CloudHSM 으로 옮기는 것을 이 장치의 대표 쓰임으로 든다. 한 번 새면 그 아래 전부가 무너지는 열쇠라, 장치 안에서 만들고 장치 안에서만 쓴다.
- **규정 맞추기** — Azure 의 Managed HSM 은 FIPS 140-3 레벨 3 검증 장치임을 앞세운다. 그 검증을 요구받는 자리에서는 소프트웨어 열쇠로 맞출 수 없다.
- **감싸는 열쇠만 넣기** — Azure 문서는 이 장치에서 만들거나 사내 장치에서 들여온 열쇠로 저장소·데이터베이스의 저장 자료를 잠근다고 적는다. 장치에 드는 것은 감싸는 쪽 열쇠뿐이고, 자료는 장치 밖에서 잠긴다.

## 🚫 흔한 오해

- **금고 장치를 쓰면 그걸로 안전해진다** — 열쇠는 안 나오지만 "이거 서명해 줘" 라는 부탁은 밖에서 온다. 부를 수 있는 사람을 안 줄이면 열쇠를 훔칠 필요 자체가 없다.
- **중요한 건 다 장치에 넣는 게 낫다** — 느리고 비싸고 입력도 작다. Google 의 HSM 키 입력 상한은 8KiB 이고 소프트웨어 키는 64KiB 다. 비대칭 키는 지연도 눈에 띄게 커진다.
- **관리형 키 서비스와 같은 물건이다** — 다르다. AWS 문서는 HSM 을 직접 운영하고 싶지 않으면 관리형 키 서비스를 쓰라고 따로 안내한다. 통제를 더 갖는 대신 사용자 관리까지 내가 지는 쪽이 장치다.

## 📝 정리

**"열쇠가 못 나오는 그 물건"** 이라고 읽으면 된다. 열쇠를 더 잘 숨기는 방식이 아니라 아예 꺼낼 수 없게 만드는 방식이라, 훔쳐 갈 원본이 없다. 대신 그 안에 일을 시킬 수 있는 사람을 줄이지 않으면 장치는 아무것도 막지 못한다.

## 🧒 열 살에게

도장을 남한테 절대 안 빌려주는 대신, 종이를 창구로 밀어 넣으면 안에서 찍어서 돌려주는 가게가 있다고 해 봐. 도장이 한 번도 밖으로 안 나오니까 누가 몰래 베껴 갈 수가 없어. 그런데 창구에 아무나 종이를 밀어 넣을 수 있으면 그건 그거대로 소용이 없겠지.

## ❓ 이해했는지

- 열쇠를 한 번도 밖으로 안 내보내는데 어떻게 잠근 결과가 나오나 → 그림
- 장치를 썼는데도 열쇠가 남의 뜻대로 쓰이는 일은 왜 생기나 → 흔한 오해
- 열쇠를 파일로 두는 것과 견주어 결정적으로 달라지는 지점은 → 해결하는 문제
