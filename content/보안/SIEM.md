# SIEM (기록을 한데 모아 보는 눈)

## 📝 정의

SIEM은 **흩어진 보안 기록을 한곳에 모아 이상을 찾아내는 도구**다.

Microsoft 문서는 이 도구가 하는 일을 "사내와 여러 클라우드에 걸친 모든 사용자·기기·애플리케이션·인프라에서 자료를 모으는 것" 으로 적고, 그다음 일을 "서로 다른 대상에 대한 낮은 신뢰도의 경보들을 이어 붙여 신뢰도 높은 보안 사건으로 만드는 것" 이라고 적는다. 모으는 절반과 이어 붙이는 절반이 이 이름 안에 같이 들어 있다.

### 이름
Security :: 보안
Information :: 쌓아 둔 기록
Event :: 그때 일어난 일
Management :: 모아서 다루기
= 붙여 읽으면 "보안 기록과 사건을 모아서 다루기". 모으는 일과 이어 붙이는 일이 한 이름에 있다

### 비유
건물 관제실. 층마다 따로 달린 화면을 한 방에 모아 놓아야 수상한 사람이 층을 옮겨 다니는 것이 보인다.

### 예
로그인 실패 기록은 여기, 파일 내려받기 기록은 저기에 있어서 같은 사람이 한 일인지 맞춰 보지 못하던 그때다.

### 직접
폰 계정 설정에서 "로그인한 기기" 목록을 열어 보라. 흩어진 기록도 한 화면에 모으면 낯선 것이 눈에 띈다.

## 🖼️ 그림으로 보기

```도해
흐름: 흩어진 기록이 어떻게 하나의 사건이 되나
수집 :: 여러 곳의 기록을 한곳으로 끌어온다
정규화 :: 제각각인 칸 이름을 한 양식으로 맞춘다
탐지 :: 규칙과 위협 정보에 걸리는 것을 고른다
묶기 :: 낱낱의 경보를 한 사건으로 모은다
조사 :: 사람이 그 사건 하나를 파고든다
= 모으는 것이 절반, 같은 말로 바꿔 놓는 것이 나머지 절반이다
```

## ⚠️ 해결하는 문제

```도해
대조: 기록이 도구마다 흩어져 있으면 무엇이 달라지나
흩어져 있으면 || 한데 모으면
한 사람 좇기 :: 도구마다 따로 본다 || 한 줄로 이어 본다
양식 :: 도구마다 다르다 || 한 양식으로 맞춘다
규칙 :: 도구마다 새로 짠다 || 한 번 짜서 다 건다
= 기록이 없어서가 아니라 이어 붙일 수 없어서 놓친다
```

공격 하나는 대개 한 도구 안에서 끝나지 않는다. 로그인 시도는 신원 쪽에, 이상한 접속은 망 쪽에, 파일을 퍼 가는 일은 저장소 쪽에 남는다. 각각만 보면 어느 것도 경보를 울릴 만큼 수상하지 않은데, 이어 붙이면 한 사람이 한 일이 된다.

그래서 이 도구가 먼저 하는 일은 **모으고 같은 말로 바꾸는 것**이다. AWS 문서는 자기네 자료 호수를 두고 "AWS 환경과 사스 제공자, 사내, 다른 클라우드와 외부 출처의 보안 자료를 자동으로 한곳에 모은다" 고 적고, 모은 것을 공개 규격으로 바꿔 "여러 보안 제품이 나란히 그 자료를 쓸 수 있게 한다" 고 덧붙인다. 양식이 하나로 맞아야 규칙도 한 번 짜서 모든 출처에 걸린다.

## ⚙️ 작동 원리

정규화가 먼저다. 같은 "로그인 실패" 라도 도구마다 칸 이름과 시각 표기가 달라서, 그대로 두면 출처 수만큼 규칙을 따로 짜야 한다. Microsoft 문서는 "여러 출처를 하나의 정규화된 시야로 옮기려고 질의 시점과 수집 시점 양쪽에서 정규화를 쓴다" 고 적고, AWS 쪽은 아예 공개 규격으로 바꿔 저장한다고 적는다. Google 쪽 문서도 수집과 파싱 다음에 통일 양식을 두고 그 위에 규칙과 조사를 얹는 차례로 목차를 짠다.

그다음이 탐지와 묶기다. 규칙과 위협 정보에 걸린 것이 경보가 되고, 경보들이 다시 하나의 **사건**으로 묶인다. Microsoft 문서는 이 묶는 일의 목적을 "소음을 줄이고 검토·조사해야 할 경보 수를 최소화하는 것" 이라고 적는다. 경보를 더 많이 만드는 장치가 아니라 사람이 볼 것을 줄이는 장치라는 뜻이다.

마지막은 사람이다. 묶인 사건 하나를 붙들고 대상과 연결을 따라가며 뿌리를 찾고, 아직 경보가 안 뜬 것을 먼저 뒤져 보는 사냥도 같은 자료 위에서 한다.

## 📊 비교: 세 클라우드는 이걸 뭐라 부르나

| 이름 | 어디 | 무엇을 앞세우나 |
|---|---|---|
| **Microsoft Sentinel** | Azure · Defender | 수집기와 분석 규칙, 경보를 사건으로 묶는 자리 |
| **Google Security Operations** | Google Cloud | 통일 양식으로 바꿔 두고 그 위에 규칙과 조사를 얹는다 |
| **Amazon Security Lake** | AWS | 자료를 공개 규격으로 모아 두고 보는 쪽은 골라 붙인다 |

셋이 나눠 가진 일은 같다 — 모으기, 같은 양식으로 바꾸기, 규칙 걸기, 사람이 파고들기. 다만 AWS 쪽은 모아 두는 자리와 보는 도구를 갈라 놓았고, 나머지 둘은 한 제품 안에서 잇는다.

## 💡 실제 사례

- **계정 탈취 좇기** — 다른 나라에서의 로그인 성공과 대량 내려받기가 각각은 조용해도, 한 사람으로 묶이면 사건이 된다.
- **규칙 한 번에 걸기** — 양식을 맞춰 두면 새 도구를 붙여도 기존 규칙이 그대로 걸린다.
- **사고 뒤 되짚기** — 언제 처음 들어왔는지를 여러 곳의 기록을 시간 순으로 이어 붙여 찾는다.

## 🚫 흔한 오해

- **기록을 다 넣어 두면 알아서 알려준다** — 넣기만 한 기록은 쌓이기만 한다. 양식을 맞추고 규칙을 걸어야 걸리고, 두 문서 모두 정규화를 따로 한 단계로 둔다.
- **경보가 많이 뜰수록 잘 잡는 것이다** — Microsoft 문서는 이 도구의 분석이 하는 일을 소음을 줄이고 검토할 경보 수를 최소화하는 것으로 적는다. 세는 것은 경보 수가 아니라 묶인 사건 수다.
- **감사 로그를 남기고 있으니 이건 없어도 된다** — 감사 로그는 한 곳의 기록이다. 여러 곳의 기록을 같은 말로 바꿔 이어 붙이는 자리는 따로 있어야 한다.

## 🚨 주의사항

- **안 넣은 기록은 영영 안 보인다.** 사고가 난 뒤에 그 출처를 붙여도 지난 일은 남아 있지 않다. 무엇을 넣을지가 곧 무엇을 볼 수 있는지다.
- **보관 기간이 곧 비용이다.** 오래 두면 되짚을 수 있는 기간이 늘지만 저장 값도 같이 는다. 두 문서 다 보관 설정을 따로 두는 이유다.
- **기록이 지워지면 증거가 아니다.** Microsoft 문서는 이 도구가 바탕 저장소의 변조 방지와 불변성 관행을 물려받는다고 적는다. 고칠 수 있는 기록은 조사에서 힘을 잃는다.

## 📝 정리

**"흩어진 기록을 한 눈으로 모아 보는 자리"** 라고 읽으면 된다. 모으기와 양식 맞추기가 절반이고, 규칙에 걸린 경보를 하나의 사건으로 묶어 사람이 볼 것을 줄이는 일이 나머지 절반이다. 넣지 않은 출처는 아무리 좋은 규칙을 걸어도 보이지 않는다.

## 🧒 열 살에게

큰 건물에는 층마다 카메라가 있는데 화면을 층마다 따로 두면, 수상한 사람이 계단으로 옮겨 다녀도 아무도 못 봐. 그래서 화면을 한 방에 모아 놓고 나란히 보는 거야. 대신 카메라를 안 달아 둔 층은 아무리 들여다봐도 안 보여.
