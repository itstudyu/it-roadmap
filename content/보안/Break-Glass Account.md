# Break-Glass Account (비상 시 깨는 유리 계정)

## 📝 정의

Break-Glass Account는 **평소엔 아무도 안 쓰는 비상용 관리자 계정**이다.

이 계정에는 다른 계정과 정반대의 요구가 걸린다. 보통 계정은 회사 로그인에 딸려 있어야 관리가 되는데, 이 계정은 **회사 로그인이 멎은 날에 쓰려고 만드는 것**이라 거기에 기대면 안 된다. Microsoft 문서는 그래서 "클라우드 전용 계정으로 만들고, 연동하거나 사내에서 동기화하지 말라" 고 적고, AWS 문서는 "비상 접근 절차가 평소 접근과 같은 시스템에 기대는 것" 을 대표적인 안티패턴으로 든다.

### 이름
Break :: 깨다
Glass :: 유리
Account :: 계정
= 붙여 읽으면 "유리를 깨고 쓰는 계정". 깨면 표가 난다는 것까지가 이름이다

### 비유
복도 벽에 붙은 소화기 상자 — 평소엔 손대지 않지만 유리를 깨면 그 소리가 온 건물에 들린다.

### 예
로그인 담당 회사가 통째로 멎어 아무도 관리자 화면에 못 들어가던 그 순간을 위한 계정이다.

## 🖼️ 그림으로 보기

```도해
흐름: 평소 들어가던 문이 전부 막히면 어디로 들어가나
평상시 :: 모두가 회사 로그인으로 들어간다
사고 :: 그 로그인 자체가 멎거나 설정이 깨진다
유리 계정 :: 회사 로그인에 기대지 않는 별도 계정
금고 :: 열쇠는 서로 다른 금고에 나뉘어 잠겨 있다
경보 :: 쓰이는 순간 보안팀에 알림이 울린다
= 다른 길이 다 끊겨도 열리는 길 하나. 대신 열면 반드시 표가 난다
```

## ⚠️ 해결하는 문제

```도해
대조: 로그인 담당이 멎은 날 무엇이 갈리나
비상 계정 없이 || 비상 계정으로
들어갈 길 :: 한 곳도 없다 || 한 곳이 남는다
고치는 시각 :: 남이 고쳐 줄 때 || 지금 바로
쓴 기록 :: 남길 데가 없다 || 경보와 함께 남는다
= 미리 안 만들어 둔 비상구는 비상 때 만들 수 없다
```

무너지는 방식은 여러 가지인데 결말이 하나다. Microsoft 문서가 든 상황은 연동 로그인 장애, 추가 확인 수단을 든 기기의 분실이나 통신 장애, 최고 권한을 가진 마지막 사람의 퇴사, 자연재해, 그리고 권한 승인자가 아무도 남지 않아 승인 자체가 불가능해진 경우다. AWS 문서는 여기에 하나를 더 붙인다 — 연동 설정에 쓰던 증명서가 만료되거나 관리자가 실수로 지운 경우다.

어느 쪽이든 그때 가서 새 계정을 만들 수는 없다. 계정을 만드는 화면에 들어가는 것부터가 막혀 있기 때문이다. 그래서 AWS 문서는 **미리 만들어 두라**고 적는다 — 비상용 계정과 역할, 그리고 각 업무 계정에 들어갈 교차 역할까지 사고 전에 만들어 두면, 비상 때 자원을 새로 만드는 API 에 기대지 않아도 된다.

## 📊 비교: 평소 관리자 계정과 무엇이 다른가

| | 평소 관리자 계정 | 유리 계정 |
|---|---|---|
| **소속** | 회사 로그인에 딸려 있다 | 거기에 기대지 않는 독립 계정 |
| **로그인 방법** | 평소 쓰는 그 방법 | 일부러 다른 방법을 고른다 |
| **조건부 정책** | 그대로 적용받는다 | 막거나 제한하는 정책에서 뺀다 |
| **쓰는 때** | 매일 | 훈련할 때와 진짜 비상 때뿐 |
| **쓰면** | 아무 일도 안 난다 | 경보가 울리고 사후 검토가 열린다 |

Microsoft 문서는 로그인 수단까지 일부러 달리하라고 적는다. 평소 계정이 인증 앱을 쓴다면 비상 계정은 보안 키를 쓰는 식이다. 같은 수단을 쓰면 그 수단이 무너지는 날 둘 다 못 쓴다.

## 💡 실제 사례

- **로그인 담당 장애** — Microsoft 가 첫 상황으로 드는 것이 이것이다. 연동 로그인 쪽이 멎으면 아무도 못 들어가므로, 그쪽에 기대지 않는 이 계정으로 들어가 급한 설정을 고친다.
- **증명서 만료** — AWS 가 실패 유형 2로 적은 경우다. 연동 설정에 넣어 둔 X.509 증명서가 만료되거나 관리자가 실수로 지우면 로그인이 통째로 끊긴다. 이 계정으로 들어가 새 설정 파일을 올린다.
- **분기 훈련** — Microsoft 는 최소 90일마다 실제로 로그인해 보라고 적는다. 들어가지는지만 보는 게 아니라 그때 경보가 제대로 울리는지까지 함께 확인한다.

## 🚫 흔한 오해

- **비상 계정도 조건부 정책으로 조여야 안전하다** — 막거나 제한하는 정책에서는 빼 둔다. Microsoft 문서는 "그 계정이 설계된 바로 그 비상 상황에서 못 쓰게 될 수 있다" 고 적는다.
- **만들어 두기만 하면 된다** — 금고 번호를 아는 사람이 퇴사했거나 열쇠가 만료됐으면 비상 날에 안 열린다. 그래서 분기마다 실제로 열어 본다.
- **아무도 안 쓰니 감시할 필요가 없다** — 반대다. 평소에 안 쓰는 계정이라 한 번의 로그인이 곧 사건이다. AWS 문서는 이 절차를 "뒷문으로 볼 수 있다" 고까지 적는다.

## 📝 정리

**"평소엔 손대지 않다가 깨면 소리가 나는 그 계정"** 이라고 읽으면 된다. 다른 문이 다 막혀도 열리려면 회사 로그인에 기대지 않아야 하고, 그 대가로 쓰이는 순간이 곧 사건이 되도록 경보와 기록을 걸어 둔다. 만들어 두고 잊으면 정작 비상 날에 그 문도 안 열리므로 분기마다 실제로 열어 본다.

## 🧒 열 살에게

복도에 걸린 소화기 상자 봤지? 불이 난 다음에 사러 갈 수는 없으니까 아무도 안 쓸 때 미리 걸어 두는 거야. 대신 유리를 깨면 소리가 나서 누가 언제 꺼냈는지 다 알게 돼.
