# User Provisioning (계정 만들고 지우기)

## 📝 정의

User Provisioning은 **사람이 오고 갈 때 계정을 자동으로 맞추는 일**이다.

Microsoft 문서는 이 말을 "사용자가 써야 할 애플리케이션에 사용자 신원과 역할을 자동으로 만드는 것" 으로 적고, 만드는 일만이 아니라 "상태나 역할이 바뀔 때의 유지와 제거" 까지 같은 말 안에 넣는다. 지우는 쪽만 따로 부를 때는 디프로비저닝이라 한다.

### 이름
User :: 쓸 사람
Provision :: 미리 마련해 두기
-ing :: 하는 일
= 붙여 읽으면 "쓸 사람 몫을 미리 마련해 두기". 이름엔 없지만 치우는 일까지 한 짝이다

### 비유
새 직원 첫 출근 날의 책상. 자리와 사물함과 출입증이 이미 준비돼 있고, 그만두는 날에는 같은 목록을 거꾸로 걷는다.

### 예
입사 첫날 오전 내내 계정이 안 열려서 아무것도 못 하고 앉아 있던 그 시간이다.

### 직접
쓰던 서비스 하나의 탈퇴 안내를 읽어 보라. 계정이 그 자리에서 사라지는지 며칠 뒤에 지워진다고 적혀 있는지가 갈린다.

## 🖼️ 그림으로 보기

```도해
흐름: 계정 하나는 어디서 나서 어디서 사라지나
사람 기록 :: 인사 기록에 새 사람이 생긴다
신원 창고 :: 그 사람의 신원이 한 곳에 만들어진다
앱마다 :: 쓸 앱들에 같은 사람이 자동으로 만들어진다
바뀔 때 :: 부서와 역할이 바뀌면 앱 쪽도 따라 바뀐다
나갈 때 :: 인사 기록이 닫히면 앱 계정도 함께 꺼진다
= 원본은 한 곳이고 나머지는 따라간다. 들어올 때보다 나갈 때가 어렵다
```

## ⚠️ 해결하는 문제

```도해
대조: 손으로 계정을 만들고 지우면 무엇이 어긋나나
손으로 하면 || 자동으로 하면
첫날 :: 오전을 그냥 보낸다 || 켜져 있다
그만둔 뒤 :: 어딘가 살아 있다 || 함께 꺼진다
부서 이동 :: 옛 권한이 남는다 || 바뀐 만큼 따라간다
= 사람 손은 만드는 건 잘하고 지우는 건 잊는다
```

계정을 손으로 만드는 일은 처음엔 견딜 만하다. 앱이 다섯 개면 다섯 번 누르면 되고, 사람이 한 달에 둘이면 열 번이다. 그런데 이 방식은 **만드는 쪽으로만 압력이 온다.** 새 사람은 계정이 없으면 일을 못 하니 재촉하지만, 나간 사람은 아무도 재촉하지 않는다.

그래서 손으로 하는 조직에는 언제나 주인 없는 계정이 쌓인다. 아무도 안 쓰고, 아무도 안 보고, 비밀번호도 안 바뀌는 계정이다. Microsoft 문서가 자동화의 동기로 "사람이 조직을 떠날 때 주요 앱에서 신원을 즉시 제거해 조직을 지킨다" 를 드는 이유가 여기 있다. 자동으로 만드는 것보다 **자동으로 지우는 것**이 이 말의 값어치다.

## ⚙️ 작동 원리

앱마다 사용자를 만드는 방법이 제각각인 것이 원래 문제였다. Microsoft 문서는 이것을 "앱마다 같은 일을 하려는 자기만의 API 가 있고, 만드는 사람마다 조금씩 다르게 구현한다 — 경로가 다르고, 사용자 정보를 넘기는 방법이 다르고, 표현하는 틀이 다르다" 로 적는다.

여기에 답한 규격이 SCIM 이다. RFC 7644 는 이것을 "여러 도메인에 걸친 신원 관리를 표준화된 방식으로 더 쉽게 만드는 HTTP 기반 프로토콜" 로 적는다. 사용자와 그룹을 담는 공용 틀을 정하고, `/Users` 와 `/Groups` 라는 정해진 자리에 만들기·읽기·바꾸기·지우기를 표준 방식으로 건다. 앱이 이 자리를 열어 두면 어느 신원 저장소와도 같은 방법으로 붙는다.

SCIM 만 쓰는 것은 아니다. Microsoft 쪽은 회사 안 디렉터리, 데이터베이스, 웹 서비스처럼 오래된 통로도 연결자로 받는다. 로그인 규격과는 자리가 다르다는 점이 중요하다 — 로그인 쪽은 문을 열어 주고, 프로비저닝은 그 문 안에 자리를 만들어 둔다. 둘을 함께 써야 처음부터 끝까지 이어진다.

## 💡 실제 사례

- **입사 첫날** — 인사 기록에 사람이 생기면 쓸 앱들에 계정이 이미 만들어져 있다. 첫날 오전을 기다리는 데 쓰지 않는다.
- **퇴사 당일** — 인사 기록이 닫히는 순간 앱 쪽 계정이 함께 꺼진다. 어느 앱에 계정이 있었는지 기억해 낼 필요가 없다.
- **주인 없는 계정 찾기** — 앱 안에 이미 있는 계정 중 짝이 없는 것을 먼저 찾아 사람에게 붙이거나 지운다. 자동화를 켜기 전에 하는 일이다.

## 🚫 흔한 오해

- **로그인만 연결해 두면 계정은 알아서 생긴다** — 한 번에 로그인하게 해 주는 것과 그 앱 안에 사람을 만들어 두는 것은 다른 일이다. 앞은 문을 여는 쪽이고 뒤는 자리를 만드는 쪽이다.
- **퇴사하면 로그인이 막히니 그걸로 끝이다** — 앱 안의 계정은 그대로 남아 있을 수 있다. 그 앱이 자체 비밀번호를 갖고 있으면 로그인 쪽을 끊어도 문이 하나 남는다.
- **몇 개 안 되니 손으로 하는 게 빠르다** — 만드는 일은 그렇지만 지우는 일은 아니다. 손으로 만든 계정은 어느 목록에도 안 올라가서, 나중에는 그런 게 있었다는 것조차 아무도 모른다.

## 📝 정리

**"사람이 오고 가는 것을 계정이 따라가게 해 두는 일"** 이라고 읽으면 된다. 만드는 쪽보다 지우는 쪽이 어렵고 위험해서, 원본을 한 곳으로 정하고 나머지가 따라오게 만든다. 이름은 만드는 일만 가리키는 것 같아도 절반은 치우는 일이다.

## 🧒 열 살에게

새 친구가 반에 오면 책상이랑 사물함이랑 이름표를 미리 만들어 두지? 전학 가면 그걸 하나씩 도로 걷어야 하는데, 걷는 걸 잊으면 빈 사물함에 그 애 열쇠가 계속 남아 있게 돼.

## ❓ 이해했는지

- 퇴사자의 로그인을 막았는데도 문이 하나 남는 일은 왜 생기나 → 흔한 오해
- 여러 앱에 같은 사람을 만들 때 공용 규격이 왜 필요했나 → 작동 원리
- 원본을 한 곳으로 정해 두면 부서가 바뀔 때 무엇이 달라지나 → 그림

## 🔗 관련 용어

- [[SSO]] — 문을 여는 쪽. 이쪽은 그 문 안에 자리를 만들어 둔다
- [[SAML]] — 로그인 정보를 넘겨 주는 규격. 프로비저닝과 짝으로 쓰인다
- [[IAM]] — 만들어 둔 계정에 무엇을 허용할지 정하는 자리
- [[Audit Log]] — 누가 언제 만들어지고 지워졌는지 남는 자리
- [[Least Privilege]] — 만들 때 얼마만큼 줄지 정하는 원칙
