# DAC (Data Access Control)

## 📝 정의

DAC는 **데이터 접근을 가운데서 통제하고 기록하는 계층**이다.

사람마다 데이터베이스에 직접 붙으면 누가 무엇을 봤는지 아무도 모른다. DAC는 그 사이에 서서 쿼리를 받아 허용 여부를 판단하고, 통과한 것과 막힌 것을 모두 남긴다.

### 비유
금고실 출입 관리대. 들어갈 사람인지 확인하고, 누가 언제 무엇을 꺼냈는지 장부에 적는다.

## 🖼️ 그림으로 보기

```도해
흐름: 개발자가 운영 DB 에 쿼리를 던지면 어디를 거치나
사용자 :: DAC 를 통해 쿼리를 보낸다
DAC :: 이 계정이 이 테이블을 볼 수 있는지 본다
DAC :: 안 되면 거기서 막고 이유를 돌려준다
DB :: 통과한 쿼리만 실제로 실행된다
< DAC :: 누가 무엇을 조회했는지 기록에 남긴다
= 막는 일과 남기는 일이 같은 자리에서 일어난다
```

## ⚠️ 해결하는 문제

```도해
대조: 각자 DB 계정으로 직접 붙으면 어떻게 되나
직접 접속 || DAC 경유
권한 :: 계정마다 제각각 || 한 곳에서 정한다
조회 기록 :: 남지 않는다 || 쿼리까지 남는다
퇴사자 계정 :: 찾아 지워야 || 한 번에 끊는다
= 흩어진 통로를 하나로 모아야 통제도 기록도 가능해진다
```

운영 데이터베이스의 계정은 시간이 지나면서 늘어난다. 급해서 만든 계정, 여러 명이 돌려 쓰는 계정, 만든 사람이 퇴사한 계정이 섞이고, 어느 계정에 어떤 권한이 붙어 있는지 아무도 다 알지 못하게 된다.

DAC는 접속 경로를 하나로 모아 그 상태를 되돌린다. 권한을 한 곳에서 보고 고칠 수 있게 되고, 사고가 났을 때 누가 언제 무엇을 봤는지 되짚을 자료가 남는다.

## ⚙️ 작동 원리

```도해
층: 데이터 보안은 어떤 물음에 답해야 하나
인증 :: 당신은 누구인가. 계정을 확인한다
인가 :: 이 데이터를 볼 자격이 있는가
감사 :: 누가 언제 무엇을 봤는가를 남긴다
= DAC 는 가운데 인가와 아래 감사를 같은 자리에서 맡는다
```

판단 기준은 계정 하나가 아니라 역할과 대상의 조합이다. 어떤 역할은 특정 테이블만 볼 수 있고, 어떤 역할은 개인 정보 열을 가린 채로만 볼 수 있다.

기록은 결과만 남기지 않는다. 실행된 쿼리 문장과 시각, 그리고 막힌 요청까지 남겨야 나중에 무슨 일이 있었는지 재구성할 수 있다.

## 💡 실제 사례

- **운영 데이터 조회** 개발자가 장애를 확인할 때 조회는 되고 수정은 막히도록 역할을 나눠 둔다.
- **개인 정보 열** 주민번호나 연락처가 담긴 열은 권한이 있는 역할에게만 원본으로 보이고 나머지에게는 가려진다.
- **감사 대응** 특정 기간에 어떤 계정이 어떤 테이블을 조회했는지 기록에서 뽑아 제출한다.

## 🚫 흔한 오해

- **DB 계정 권한과 같은 것이다** — 계정 권한은 대개 테이블 단위까지다. DAC 는 그 앞에 서서 어떤 쿼리를 보냈는지까지 보고 판단한다.
- **기록만 남기면 통제가 된다** — 기록은 사고가 난 뒤에 쓰는 것이다. 막는 규칙이 없으면 잘 적힌 사고가 남을 뿐이다.
- **개발자를 못 믿는다는 뜻이다** — 사람을 의심하는 장치가 아니라 실수의 범위를 줄이는 장치다. 잘못 지운 데이터도 누가 언제 지웠는지 알아야 되돌릴 수 있다.

## 📝 정리

DAC는 데이터베이스 앞에 서서 접근을 판단하고 그 결과를 남기는 계층이다. 인증과 인가와 감사 중에서 뒤의 둘을 한 자리에 모으는 것이 이 계층의 일이다.

## ❓ 이해했는지

- 사고가 난 뒤에 누가 데이터를 봤는지 알 수 없는 상황은 어떤 구성에서 생기나?
- 막는 규칙 없이 기록만 남기면 무엇이 부족한가?
- 퇴사자의 접근을 한 번에 끊을 수 있는 이유가 무엇인가?
