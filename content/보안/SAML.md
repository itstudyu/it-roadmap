# SAML (Security Assertion Markup Language)

## 📝 정의

SAML은 **한 곳에서 확인한 신원을 여러 서비스가 믿게 하는 규약**이다.

회사가 인증을 담당하는 서버를 하나 두고, 직원이 거기 로그인해두면 연동된 업무 서비스들이 그 결과를 받아 자기 쪽 로그인으로 인정한다. 인증을 맡는 쪽을 IdP, 서비스를 내주는 쪽을 SP 라고 부른다. 주고받는 문서는 XML이고 위조를 막기 위해 디지털 서명이 붙는다.

### 비유
공항 출입증. 신원 확인은 발급 창구에서 한 번 하고, 게이트는 카드가 진짜인지만 볼 뿐 신원 조사를 다시 하지 않는다.

## 🖼️ 그림으로 보기

```도해
흐름: 회사 계정으로 다른 서비스에 로그인되기까지 무엇을 거치나
사용자 :: 업무용 서비스 주소를 연다
SP :: 아직 로그인 전이다. 회사 IdP 로 보낸다
IdP :: 로그인된 세션이 있으면 다시 묻지 않는다
IdP :: 신원과 부서를 담은 보증서에 서명해 건넨다
< SP :: 서명과 유효기간을 확인하고 자기 세션을 만든다
= 비밀번호는 IdP 에만 주고 SP 는 서명된 보증서만 본다
```

## ⚠️ 해결하는 문제

```도해
대조: 직원이 퇴사하면 계정을 어디까지 지워야 하나
SAML 없이 || SAML 로
비밀번호 :: 서비스마다 따로 || 회사 계정 하나
입사 처리 :: 서비스마다 생성 || IdP 에 한 번
퇴사 처리 :: 빠뜨리면 남는다 || IdP 에서 끄면 끝
= 계정을 한 곳에서만 만들고 끄면 빠뜨릴 자리가 없어진다
```

회사에서 쓰는 서비스가 스무 개쯤 되면 비밀번호를 스무 개 기억할 수 없다. 결국 같은 것을 돌려쓰거나 어딘가에 적어두게 된다.

더 위험한 쪽은 퇴사 처리다. 서비스마다 계정을 따로 지워야 하는데 하나라도 빠뜨리면 그 사람은 그 서비스에 계속 들어올 수 있다. SAML로 묶여 있으면 인증 서버에서 계정을 끄는 것으로 연동된 서비스 전체가 막힌다.

## ⚙️ 작동 원리

```도해
층: 비밀번호는 어디까지 가고 어디서 멈추나
IdP :: 비밀번호와 신원을 원본으로 들고 있다
보증서 :: 신원과 부서만 옮겨 담고 서명을 붙인다
SP :: 보증서에 적힌 것만 안다. 비밀번호는 모른다
= 아래로 갈수록 아는 것이 줄고, 비밀번호는 첫 층을 못 넘는다
```

주체는 셋이다. 서비스를 쓰려는 사용자, 신원을 확인하고 보증서를 발급하는 IdP, 실제 서비스를 제공하는 SP다.

오가는 것은 SAML Assertion이라 부르는 보증서다. 안에는 이메일과 이름, 부서와 역할 같은 정보가 들어가고 IdP의 디지털 서명과 유효기간이 붙는데, 기간은 보통 5분 정도로 짧다. SP는 서명이 맞는지, 기간이 지나지 않았는지, 자기 앞으로 온 것이 맞는지 확인한 다음 자기 쪽 세션을 만들고, 그 뒤로는 보증서를 다시 받지 않는다.

계정을 미리 만들어둘 필요도 없다. 처음 접속할 때 보증서에 담긴 정보로 계정을 그 자리에서 만드는 방식을 JIT Provisioning이라고 하며, 부서나 역할 값에 따라 권한까지 자동으로 붙일 수 있다.

## 📊 비교: SAML 과 이웃한 것들

| | SAML | OAuth 2.0 | LDAP |
|---|---|---|---|
| 하는 일 | 기업 SSO | 권한 위임 | 디렉터리 조회 |
| 주 대상 | 회사 직원 | 일반 사용자 | 기업 내부 |
| 주고받는 형식 | XML | JSON과 HTTP | 자체 이진 형식 |
| 잘 맞는 곳 | 사내 서비스, B2B SaaS | 소셜 로그인, 모바일 | 사내 계정 저장소 |

## 💡 실제 사례

- **아침에 한 번 로그인** — 회사 계정으로 들어와 있으면 업무 도구를 열 때마다 다시 묻지 않는다.
- **입사자 계정 만들기** — 인증 서버에 한 번만 등록하면 각 서비스에는 첫 접속 때 계정이 생긴다.
- **B2B SaaS 도입** — 고객사가 자기 회사 계정으로 로그인하게 해달라고 요구하면 SAML 연동을 붙인다.

## 🚫 흔한 오해

- **SAML이 비밀번호를 서비스마다 대신 넣어준다** — 비밀번호는 IdP 밖으로 나가지 않는다. SP가 받는 것은 서명된 보증서뿐이고 거기에 비밀번호는 들어 있지 않다.
- **SAML은 OAuth의 옛날 버전이다** — 대체 관계가 아니라 하는 일이 다르다. SAML은 이 사람이 누구인지 확인해 넘겨주는 쪽이고, OAuth는 내 자원에 접근할 권한을 다른 앱에 내주는 쪽이다.
- **한 번 로그인하면 그 뒤로는 계속 그 로그인이 쓰인다** — 보증서 유효기간은 5분 정도로 짧다. 그것으로 SP 쪽 세션을 한 번 만들고 나면 그다음부터는 SP 세션이 유지되는 것이다.

## 🚨 주의사항

- **서명을 반드시 검증한다.** XML만 열어 이메일을 꺼내 쓰면 누구나 보증서를 만들어 남의 계정으로 들어올 수 있다.
- **같은 보증서를 두 번 받지 않는다.** 보증서는 사용자 브라우저를 거쳐 오므로 가로채였을 수 있다. 이미 쓴 ID를 기록해두고 다시 들어오면 거부한다.

## 📝 정리

SAML은 인증을 한 곳에 모아두고 그 결과를 서명된 XML 보증서로 각 서비스에 전달하는 규약이다. 직원은 비밀번호 하나만 기억하면 되고, 계정 생성과 차단은 인증 서버 한 곳에서 끝난다. 대신 받은 쪽이 서명과 유효기간과 대상을 제대로 검증하지 않으면 신뢰 구조 전체가 무너진다.
