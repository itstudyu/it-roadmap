# CSRF (Cross-Site Request Forgery)

## 📝 정의

CSRF는 **로그인한 사용자의 브라우저로 몰래 요청을 보내는 공격**이다.

브라우저는 어떤 사이트로 요청을 보낼 때 그 사이트의 쿠키를 자동으로 같이 보낸다. 공격자는 이 자동 첨부를 이용한다. 쿠키 값을 훔칠 필요 없이 요청만 만들어내면 서버는 본인이 한 일로 처리한다.

### 비유
남의 도장을 훔치는 게 아니라, 도장을 들고 있는 사람 손을 슬쩍 눌러 서류에 찍게 만드는 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 로그인만 해둔 채로 다른 사이트에 들어가면 무슨 일이 일어나나
사용자 :: 은행에 로그인한다. 세션 쿠키를 받는다
사용자 :: 다른 탭에서 공격자 페이지를 연다
그 페이지 :: 보이지 않는 폼이 은행으로 송금 요청을 보낸다
브라우저 :: 은행 주소로 가는 요청이라 쿠키를 자동으로 붙인다
< 은행 서버 :: 로그인한 본인의 요청으로 보고 송금한다
= 훔친 건 쿠키가 아니라 로그인해둔 상태 그 자체다
```

## ⚠️ 해결하는 문제

```도해
대조: 서버가 요청의 출처를 안 보면 어떻게 되나
막지 않으면 || 토큰으로 막으면
요청 판단 :: 쿠키만 보고 통과 || 토큰까지 본다
남의 페이지 :: 그대로 먹힌다 || 토큰이 없어 거절
피해 :: 송금, 설정 변경 || 아무 일도 없음
= 누구인지만 확인하고 어디서 왔는지 안 보면 뚫린다
```

쿠키 기반 로그인은 편하다. 한 번 로그인하면 그 도메인으로 가는 모든 요청에 브라우저가 알아서 쿠키를 붙여준다. 문제는 그 요청이 우리 화면에서 시작됐든 남의 페이지에서 시작됐든 똑같이 붙는다는 데 있다.

그래서 서버는 "누가 보냈나"만이 아니라 "우리 화면에서 시작된 요청인가"를 따로 확인해야 한다. 이 확인이 없으면 로그인 상태 자체가 공격 도구가 된다.

## ⚙️ 작동 원리

막는 방법은 크게 둘이다.

CSRF 토큰은 서버가 화면을 내려줄 때 예측할 수 없는 값을 같이 심어두고, 요청이 올 때 그 값이 함께 왔는지 본다. 공격자 페이지는 그 값을 읽을 수 없다. 다른 출처의 페이지가 우리 서버의 응답 내용을 읽는 걸 브라우저가 막기 때문이다.

SameSite 쿠키는 브라우저 쪽에서 끊는다. 쿠키에 이 속성을 붙이면 다른 사이트에서 시작된 요청에는 쿠키를 아예 붙이지 않는다. 요청은 여전히 도착하지만 로그인 안 한 사람의 요청이 되어 거절된다.

조회만 하는 요청은 GET으로, 상태를 바꾸는 요청은 POST 같은 메서드로 나눠두는 것도 함께 간다. 링크 하나 클릭으로 계정 설정이 바뀌면 막을 자리 자체가 없다.

## 💡 실제 사례

- **송금** — 숨겨진 폼이 자동 제출되어 사용자 계좌에서 공격자 계좌로 이체된다.
- **계정 설정 변경** — 비밀번호 복구용 이메일 주소가 공격자 것으로 바뀐다. 그다음은 계정을 통째로 가져간다.
- **메일 전달 규칙 추가** — 받은 메일을 전부 다른 주소로 전달하는 규칙이 조용히 추가된다.

## 🚫 흔한 오해

- **CSRF는 쿠키를 훔치는 공격이다** — 훔치지 않는다. 값은 모른 채로 브라우저가 알아서 붙이게 만드는 것이라, 쿠키를 아무리 잘 감춰도 막히지 않는다.
- **HTTPS를 쓰면 막힌다** — 관계가 없다. HTTPS는 오가는 내용을 가려줄 뿐이고, 요청이 어디서 시작됐는지는 따지지 않는다.
- **공격자가 응답을 볼 수 있으니 정보도 새어 나간다** — 대개 못 본다. 브라우저가 다른 출처의 응답 읽기를 막기 때문에, CSRF로 노리는 건 정보를 빼내는 것이 아니라 상태를 바꾸는 것이다.

## 🚨 주의사항

- **조회와 변경을 메서드로 나눈다.** GET 하나로 데이터가 바뀌면 이미지 태그 한 줄로도 공격이 된다.
- **API에도 같은 문제가 있다.** 쿠키로 인증한다면 요청 형식이 JSON이어도 안전하지 않다. 헤더 검사나 SameSite 설정이 함께 있어야 한다.

## 📝 정리

CSRF는 로그인해둔 상태를 남이 대신 써먹는 공격이다. 브라우저가 쿠키를 자동으로 붙여준다는 성질에서 나오므로, 누구인지 확인하는 것과 별개로 어디서 시작된 요청인지 확인해야 막힌다.

## ❓ 이해했는지

- 쿠키 값을 전혀 모르는 공격자가 어떻게 본인 명의의 요청을 만들 수 있나?
- 사이트를 HTTPS로 바꿔도 이 공격이 그대로 통하는 이유는?
- 공격자가 훔쳐 가는 것이 정보가 아니라면 무엇을 노리는 것인가?

## 🔗 관련 용어

- [[Cookie]] — 브라우저가 자동으로 붙여주는 성질이 이 공격의 출발점이다
- [[Session]] — CSRF가 빌려 쓰는 로그인 상태
- [[XSS]] — 스크립트를 심는 공격. 이게 뚫리면 CSRF 방어도 같이 무너진다
- [[JWT]] — 쿠키 대신 헤더로 보내면 자동 첨부가 없어 표면이 줄어든다
