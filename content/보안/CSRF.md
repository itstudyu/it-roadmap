# CSRF (Cross-Site Request Forgery)

## 📝 정의

CSRF(Cross-Site Request Forgery)는 공격자가 로그인된 사용자의 브라우저를 이용하여, 사용자도 모르게 다른 웹사이트로 의도하지 않은 요청을 보내도록 유도하는 보안 공격입니다. 사용자의 인증 상태(세션 쿠키, 토큰)를 악용하여, 마치 사용자가 직접 한 요청인 것처럼 보이게 만듭니다.

CSRF 공격은 사용자가 로그인된 상태에서 악성 웹사이트를 방문하거나 악의적인 이메일 링크를 클릭할 때 발생합니다. 공격자는 사용자의 인증 정보에 직접 접근할 필요 없이, 단순히 인증된 사용자의 행동을 조작하여 목표를 달성할 수 있습니다.

> **한 줄 요약**: CSRF는 인증된 사용자의 세션을 악용하여 의도하지 않은 요청을 강제 실행하는 공격

**비유 1**: CSRF는 대리인을 사칭하는 것과 같습니다. 공격자가 피해자의 신분증을 훔친 것은 아니지만, 피해자가 자신의 신분증을 들고 있는 상태에서 몰래 위임장에 서명하도록 유도합니다.

**비유 2**: CSRF는 피해자가 은행에서 나온 후 몰래 찍은 사진을 이용해 은행 담당자를 속이는 것과 같습니다. 은행원은 사진 속 사람이 실제로 그 거래를 요청한 줄 알고 처리합니다.

## 🎯 핵심 개념

### 1. 세션/쿠키 기반 인증의 취약성
사용자가 로그인하면 브라우저에 세션 쿠키가 저장되고, 같은 도메인으로의 모든 요청에 자동으로 포함됩니다. CSRF 공격은 이 특성을 악용합니다.

### 2. 출처 간 요청 (Cross-Origin Request)
사용자가 A 웹사이트에 로그인한 상태에서 B라는 악성 웹사이트를 방문하면, B에서 A로의 요청이 A의 세션 쿠키와 함께 전송됩니다.

### 3. 상태 변경 요청의 위험성
CSRF는 조회(GET) 요청보다 데이터 수정(POST, PUT, DELETE) 요청에서 더 위험합니다. 사용자 정보 변경, 결제, 계정 삭제 등이 의도하지 않게 실행될 수 있습니다.

### 4. CSRF 토큰
서버가 각 사용자 세션마다 고유한 토큰을 생성하여 폼에 포함시킵니다. 요청 시 이 토큰을 검증하여, 정상적인 폼에서 온 요청인지 확인합니다.

### 5. SameSite 쿠키 속성
쿠키에 SameSite 속성을 설정하여, 같은 도메인의 요청에만 쿠키를 전송하도록 제한합니다.

## ⚠️ 해결하는 문제

### 문제 1: 의도하지 않은 계정 설정 변경
공격자가 악성 사이트에서 피해자의 인증 상태를 악용하여, 비밀번호, 이메일, 복구 연락처 등을 변경하면 피해자의 계정을 장악할 수 있습니다.

### 문제 2: 금전 거래 유도
인증된 사용자를 대상으로 피해자도 모르게 송금, 결제, 구매 등의 금융 거래를 실행하게 하여 경제적 손실을 초래합니다.

### 문제 3: 데이터 조작 및 삭제
피해자의 권한으로 데이터를 삭제하거나 수정하여, 시스템의 무결성을 훼손하고 다른 사용자에게도 영향을 미칩니다.

### 문제 4: 소셜 미디어 악용
인증된 사용자를 통해 의도하지 않은 게시물 공유, 팔로우, 친구 추가 등을 수행하여 평판을 훼손하거나 악성 콘텐츠를 전파합니다.

## ⚙️ 작동 원리

CSRF 공격은 다음과 같은 단계로 진행됩니다:

1. **피해자의 인증**: 피해자가 정상적인 웹사이트(예: 은행)에 로그인하여 세션 쿠키를 획득합니다.

2. **악의적인 사이트 방문**: 피해자가 공격자의 악성 웹사이트를 방문하거나, 악의적인 이메일 링크를 클릭합니다.

3. **숨겨진 요청 생성**: 악성 웹사이트는 피해자의 브라우저에서 보이지 않는 폼이나 JavaScript를 통해, 피해자가 로그인한 웹사이트로 요청을 전송합니다.

4. **자동 쿠키 포함**: 브라우저는 자동으로 같은 도메인으로의 요청에 세션 쿠키를 포함시킵니다.

5. **서버의 검증 실패**: 정상 요청과 구분할 방법이 없으면, 서버는 이 요청을 피해자의 정상 요청으로 간주하고 처리합니다.

6. **피해 발생**: 피해자의 의도와 무관하게 송금, 설정 변경, 데이터 삭제 등이 실행됩니다.

## ✅ 장단점

### 공격 방식 관점

#### 장점 (공격자 입장)
- **기술적 진입 장벽 낮음**: 간단한 HTML 폼만으로도 공격 가능
- **자동화 용이**: 사용자가 클릭하거나 페이지 방문하기만 하면 자동 실행
- **세션 탈취 불필요**: 쿠키 값을 알 필요 없음
- **광범위한 피해**: 같은 도메인의 모든 사용자가 잠재적 피해자

#### 단점 (공격자 입장)
- **방어 기법 확산**: 대부분의 현대 웹 프레임워크가 기본 방어 제공
- **요청 결과 확인 어려움**: 브라우저의 Same-Origin Policy로 응답 확인 불가
- **상태 변경 요청 필요**: GET 요청으로는 상태를 변경하기 어려움

### 방어 관점

#### 장점 (방어)
- **방어 기법 효과적**: CSRF 토큰, SameSite 쿠키 등이 매우 효과적
- **프레임워크 지원**: Django, Laravel, Spring 등 대부분의 프레임워크가 자동 방어 제공
- **구현 간단**: 방어 기법을 추가하기 위한 개발 복잡도가 낮음

#### 단점 (방어)
- **토큰 관리 복잡성**: 분산 시스템에서 CSRF 토큰 검증이 복잡할 수 있음
- **API 설계 고려**: RESTful API에서는 토큰 방식보다 상태 코드 검증 필요
- **사용자 경험 영향**: 일부 방어 기법이 정상적인 사용 환경에 영향을 줄 수 있음

## 💡 실제 사례

### 사례 1: 은행 송금 CSRF
피해자가 악성 웹사이트를 방문하면, 숨겨진 폼이 자동으로 은행 API를 호출하여 피해자 계정에서 공격자 계정으로 송금 요청을 전송합니다. 은행이 CSRF 토큰을 검증하지 않으면, 요청이 그대로 처리되어 금전 손실이 발생합니다.

### 사례 2: SNS 프로필 변조
공격자가 악성 링크를 SNS 메시지로 전송합니다. 링크를 클릭한 사용자(로그인 상태)는 자신도 모르게 프로필 이름, 프로필 사진, 소개글이 변경되고, 악성 콘텐츠로 가득 찬 게시물이 공유됩니다.

### 사례 3: 온라인 쇼핑몰 설정 변경
쇼핑몰에 로그인한 사용자가 공격자의 악성 이메일 링크를 클릭하면, 자신도 모르게 배송지 주소가 공격자의 주소로 변경되고, 고가 상품이 주문 확정됩니다.

### 사례 4: 이메일 자동 전달 설정
공격자가 Outlook이나 Gmail에 로그인한 사용자를 타겟으로 CSRF 공격을 수행하면, 모든 이메일이 공격자의 계정으로 자동 전달되는 규칙이 추가되어 개인정보와 비즈니스 정보가 유출됩니다.

### 사례 5: 관리자 계정 권한 남용
관리자가 관리 페이지에 로그인한 상태에서 악성 웹사이트를 방문하면, CSRF 공격으로 인해 새로운 관리자 계정이 생성되거나, 보안 정책이 변경되어, 공격자가 시스템에 대한 접근 권한을 얻게 됩니다.

## 🔗 관련 용어

- **세션 쿠키 (Session Cookie)**: CSRF 공격이 악용하는 인증 메커니즘
- **XSS (Cross-Site Scripting)**: CSRF와 함께 발생하기 쉬운 웹 보안 취약점
- **SameSite 쿠키 속성**: CSRF 방어를 위한 현대적 쿠키 설정
- **CSRF 토큰**: CSRF 공격 방어의 표준 기법
- **Referer 헤더**: 요청의 출처를 나타내는 HTTP 헤더
- **Same-Origin Policy**: 브라우저의 보안 정책
- **사전 조회 요청 (Preflight Request)**: CORS 기반 CSRF 방어
- **더블 제출 쿠키 (Double Submit Cookie)**: CSRF 토큰의 변형 방식
