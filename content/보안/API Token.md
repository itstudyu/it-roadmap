# API Token (API 토큰)

## 📝 정의

API Token은 **비밀번호 대신 API 를 부를 때 쓰는 문자열**이다.

사람은 화면에서 로그인하지만 프로그램은 그럴 수 없다. 그래서 프로그램에게는 비밀번호 대신, 할 수 있는 일이 미리 정해진 문자열을 하나 쥐여준다.

### 비유
방문객 출입증. 열쇠는 모든 방을 열지만 출입증은 정해진 층만 열고, 잃어버리면 그 출입증만 무효로 만들면 된다.

## 🖼️ 그림으로 보기

```도해
흐름: 토큰 하나로 API 를 부르면 무엇이 오가나
사용자 :: ID 와 비밀번호로 토큰을 발급받는다
서버 :: 토큰을 만들어 화면에 한 번만 보여준다
서버 :: 저장은 해시로 한다. 원본은 안 남긴다
프로그램 :: 요청 헤더에 토큰을 실어 보낸다
서버 :: 해시를 맞춰보고 권한 범위를 확인한다
< 서버 :: 맞으면 데이터, 아니면 401 로 거절한다
= 비밀번호는 처음 한 번만 쓰이고 그다음부터는 토큰만 오간다
```

## ⚠️ 해결하는 문제

```도해
대조: 스크립트에 비밀번호를 그대로 넣으면 어떻게 되나
비밀번호로 || 토큰으로
유출 범위 :: 계정 전체 || 준 권한만
차단 방법 :: 비번을 바꾼다 || 토큰만 지운다
용도 구분 :: 하나로 다 쓴다 || 용도마다 발급
= 잃어버렸을 때 무엇까지 잃느냐가 다르다
```

코드에 비밀번호를 적어두면 그 코드가 유출되는 순간 계정 전체가 넘어간다. 로그인부터 결제까지 그 계정으로 할 수 있는 일이 전부 열린다. 막으려면 비밀번호를 바꿔야 하고, 같은 비밀번호를 쓰던 다른 스크립트도 전부 멈춘다.

토큰은 이 범위를 좁힌다. 읽기만 하는 토큰을 따로 발급해두면 유출돼도 읽히는 것으로 끝나고, 그 토큰 하나만 지우면 다른 곳은 그대로 돌아간다.

## ⚙️ 작동 원리

토큰에는 할 수 있는 일의 목록이 붙는다. 이것을 권한 범위라고 부른다. 저장소를 읽기만 할 토큰에 쓰기 권한까지 붙일 이유가 없다.

서버는 토큰 원본을 저장하지 않는다. 비밀번호와 같은 방식으로 해시(되돌릴 수 없는 지문 값으로 바꾸는 것)해서 넣어두고, 들어온 토큰을 해시해 맞춰본다. 그래서 발급 화면을 닫으면 원본을 다시 볼 방법이 없고, 잃어버리면 새로 만드는 수밖에 없다.

만료 시간도 같이 정해둔다. 유출을 즉시 알아채지 못해도 시간이 지나면 스스로 못 쓰게 된다.

## 💡 실제 사례

- **배포 스크립트** — 빌드 서버가 저장소에서 코드를 내려받을 때 사람 계정 대신 읽기 전용 토큰을 쓴다.
- **서비스 연동** — 결제 대행사 API 를 부를 때 발급받은 토큰을 헤더에 넣어 보낸다.
- **사고 대응** — 실수로 토큰이 공개된 코드에 올라가면 그 토큰만 폐기하고 새로 발급한다.

## 🚫 흔한 오해

- **토큰은 암호화된 비밀번호다** — 비밀번호를 바꿔놓은 게 아니라 따로 만들어진 별개의 자격이다. 그래서 비밀번호를 바꿔도 이미 나간 토큰은 그대로 살아 있다.
- **토큰을 쓰면 그것만으로 안전해진다** — 토큰 자체는 그냥 문자열이라 손에 넣은 사람은 그대로 쓴다. 안전해지는 건 권한을 좁히고 만료와 폐기를 붙였을 때다.
- **한 번 발급받으면 계속 쓰는 것이다** — 만료가 있으면 끊기고, 없더라도 주기적으로 새로 발급해 바꾸는 편이 낫다.

## 🚨 주의사항

- **코드에 적어두지 않는다.** 환경 변수나 별도 설정 파일로 빼고, 그 파일은 저장소에 올리지 않는다.
- **주소 뒤에 붙여 보내지 않는다.** 쿼리 문자열에 넣으면 웹 서버 로그와 브라우저 기록에 그대로 남는다. 헤더에 실어야 한다.

## 📝 정리

API Token 은 프로그램이 비밀번호 없이 API 를 부를 수 있게 해주는 자격증명이다. 권한을 좁혀 발급하고 만료와 폐기를 붙였을 때 비로소 비밀번호보다 나아진다.

## ❓ 이해했는지

- 발급 화면을 닫고 나면 토큰 원본을 다시 볼 수 없는 이유는 → 작동 원리
- 읽기 전용 토큰이 유출됐을 때 비밀번호를 바꾸면 막히나 → 흔한 오해
- API 주소 뒤에 토큰을 붙여 호출하면 어디에 흔적이 남나 → 주의사항
