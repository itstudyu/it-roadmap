# CA (인증 기관, Certificate Authority)

## 📝 정의

CA(Certificate Authority, 인증 기관)는 디지털 인증서를 발급하고 서명하는 신뢰할 수 있는 제3자 기관입니다. "이 서버가 진짜 google.com입니다"라는 것을 보증하며, 브라우저는 CA가 서명한 인증서를 신뢰합니다. 사용자가 웹사이트에 접속할 때 브라우저는 해당 서버가 제시하는 인증서를 CA가 발급했는지 검증합니다. CA는 도메인의 소유권을 확인하고, 인증서에 디지털 서명을 함으로써 그 인증서의 진정성을 보증합니다.

CA의 신뢰 구조는 계층적입니다. 루트 CA(Root CA)는 보안이 매우 강화된 오프라인 환경에 보관되며, 중간 CA(Intermediate CA)를 서명합니다. 중간 CA는 실제로 서버 인증서를 발급하는 업무를 합니다. 이런 방식으로 루트 CA의 개인 키가 절대 외부에 노출되지 않으면서도, 신뢰 체인이 유지됩니다. 전 세계의 브라우저와 운영 체제는 주요 CA들의 루트 인증서를 미리 내장하고 있으므로, 그 CA가 발급한 인증서는 자동으로 신뢰됩니다.

> **한 줄 요약**: "CA는 서버 신원을 보증하는 제3자 기관. 브라우저는 CA를 신뢰하므로 인증서도 신뢰합니다"

**비유**:
- **여권과 대사관 비유**: CA는 대사관 같은 공식 기관이고, 서버는 국민입니다. 국민이 여권(인증서)을 신청하면 대사관이 신원을 확인하고 서명합니다. 다른 나라에서 그 여권을 보면 "아, 대사관이 서명했다. 이 사람은 신뢰할 수 있겠군"이라고 생각합니다. 여권 자체가 아니라 발급 기관(CA)의 신뢰도가 중요합니다.
- **은행 인장 비유**: CA의 개인 키는 은행의 인장입니다. 서버는 은행에 가서 문서(인증서)에 인장을 받습니다. 다른 사람이 그 문서를 보고 은행 인장을 확인하면 "이것은 신뢰할 수 있는 은행에서 확인한 문서"라고 인정합니다. 가짜 인장을 사용하면 적발됩니다.

## 🎯 핵심 개념

### 1. CA의 역할과 신원 보증
CA는 서버가 정말로 자신이 주장하는 조직인지 검증합니다. 예를 들어, 어떤 회사가 "우리는 amazon.com입니다"라고 주장하고 인증서를 신청하면, CA는 그 회사가 정말로 amazon.com 도메인을 소유하고 있는지 확인합니다. DNS 레코드 변경, 이메일 확인, 서류 확인 등의 방법을 사용합니다. 확인되면 인증서에 디지털 서명을 하여 발급합니다.

### 2. 인증서 체인 (Certificate Chain)
인증서는 단독으로 신뢰되지 않고, 체인 형태로 신뢰됩니다. 최상단의 루트 CA가 있고, 그 아래 중간 CA가 있으며, 최하단에 서버 인증서가 있습니다. 브라우저는 서버 인증서 → 중간 CA 인증서 → 루트 CA 인증서 순으로 검증합니다. 각 단계에서 디지털 서명을 검증하여, 전체 체인이 타당한지 확인합니다. 한 단계라도 검증에 실패하면 전체 인증서가 거부됩니다.

### 3. Root CA와 Intermediate CA의 분리
루트 CA는 절대 손상되면 안 되는 최고 수준의 보안을 가집니다. 루트 CA의 개인 키는 오프라인 환경의 하드웨어 보안 모듈(HSM)에 보관되며, 매우 제한된 인원만 접근할 수 있습니다. 반면 중간 CA는 실제 인증서 발급 업무를 담당하므로, 온라인에 노출됩니다. 만약 중간 CA가 손상되어도 루트 CA의 개인 키는 안전하므로, 새로운 중간 CA를 발급받을 수 있습니다.

### 4. CA 종류: 상업 CA vs 무료 CA vs 사설 CA
상업 CA(DigiCert, Comodo, GlobalSign 등)는 높은 신뢰도를 제공하며, 회사 정보 검증(OV) 또는 확장 검증(EV)을 수행합니다. 비용이 들지만 공인 신뢰도가 높습니다. 무료 CA(Let's Encrypt)는 자동화된 도메인 검증(DV)만 수행하여 비용이 없지만, 신뢰도는 낮습니다. 사설 CA는 기업 내부에서 자체 루트 인증서를 만들어 사용하므로, 외부 신뢰는 없지만 내부 시스템 간 통신에만 필요합니다.

### 5. 인증서 유형: DV, OV, EV
- **DV (Domain Validated)**: 도메인 소유권만 확인. Let's Encrypt가 대표. 최소 비용, 최소 신뢰도.
- **OV (Organization Validated)**: 도메인 + 조직 실체 확인. 회사 서류 제출 필요. 비용 중간, 신뢰도 높음.
- **EV (Extended Validation)**: 철저한 법적 신원 확인. 주소창에 회사명 표시. 금융, 은행 등에서 사용. 비용 높음, 최고 신뢰도.

## ⚠️ 해결하는 문제

### 문제 1: 가짜 서버로부터의 보호
중간자 공격(MITM)에서 공격자가 가짜 서버를 구축하고, 사용자가 접속하도록 유도합니다. 만약 인증서 검증이 없다면 사용자는 가짜 서버를 실제 서버로 믿고 비밀번호나 신용카드 정보를 입력합니다. CA의 인증서는 가짜 서버에 제공할 수 없으므로(도메인 소유권 증명 불가), 브라우저는 인증서 오류를 표시하고 접속을 거부합니다.

### 문제 2: 인증서 위조 방지
누군가 amazon.com을 위한 가짜 인증서를 만들 수는 없을까요? 기술적으로는 가능하지만, 그 인증서는 CA가 서명하지 않았으므로 브라우저가 검증할 때 거부됩니다. CA의 공개 키로 서명을 검증하는데, 가짜 인증서는 CA의 개인 키로 서명되지 않았으므로 검증 실패입니다. 따라서 CA의 개인 키를 탈취하지 않는 이상 인증서 위조는 불가능합니다.

### 문제 3: 신뢰 기반 없는 HTTPS의 무의미
HTTPS는 통신을 암호화하지만, 상대방이 누구인지 확인하지는 않습니다. 인증서 없이 누구나 HTTPS 서버를 구축할 수 있습니다. 하지만 CA의 인증서 검증으로, 상대방이 정말로 자신이 주장하는 사람인지 확인합니다. 따라서 HTTPS + CA 인증서로만 완전한 보안이 구성됩니다.

## ⚙️ 작동 원리

### 1단계: 인증서 요청 (CSR - Certificate Signing Request)
서버 관리자(예: Google 보안팀)가 CA에 인증서를 신청합니다. 이때 CSR 파일을 생성하는데, 여기에는 도메인(google.com), 회사명, 소재지 등의 정보가 포함됩니다. CSR에는 서버의 공개 키도 포함되며, 개인 키는 절대 공유되지 않습니다.

### 2단계: 도메인 소유권 검증
CA는 신청자가 정말로 google.com 도메인을 소유했는지 확인합니다. 일반적으로 3가지 방법을 사용합니다:
- DNS 레코드: google.com의 DNS에 CA가 지정한 TXT 레코드를 추가
- 이메일 검증: google.com의 이메일 주소로 확인 링크를 보냄
- 파일 검증: google.com 웹사이트의 특정 경로에 파일을 업로드

신청자가 이 중 하나를 완료하면, CA는 신청자가 도메인을 정말로 소유했다고 확인합니다.

### 3단계: 추가 검증 (OV/EV의 경우)
DV 인증서는 도메인 검증만 하지만, OV나 EV 인증서는 더 많은 정보를 검증합니다. 회사의 사업자등록증, 주소, 전화번호 등을 확인합니다. EV의 경우 더욱 엄격하여, 법적 서류를 통해 회사의 실제 존재를 확인합니다.

### 4단계: 인증서 발급 및 서명
모든 검증이 완료되면, CA는 인증서를 생성하고 CA의 개인 키로 서명합니다. 서명된 인증서는 서버 관리자에게 전달됩니다. 이 인증서에는 서버의 공개 키, 도메인, 유효 기간(보통 1년), CA의 서명 등이 포함됩니다.

### 5단계: 서버에 인증서 설치
서버 관리자는 발급받은 인증서를 웹서버(Nginx, Apache 등)에 설치합니다. 인증서 파일(google.com.crt)과 개인 키 파일(google.com.key)을 서버의 특정 경로에 저장합니다. 이제 사용자가 google.com에 접속할 때 서버는 인증서를 제시합니다.

### 6단계: 브라우저가 인증서 검증
사용자가 google.com에 접속하면, 브라우저가 서버로부터 인증서를 받습니다. 브라우저는 다음을 검증합니다:
- CA의 서명 유효성: CA의 공개 키로 서명을 검증
- 도메인 일치: 인증서의 도메인과 접속한 도메인이 일치
- 만료 기간: 인증서가 유효 기간 내인지 확인
- CA 신뢰: 발급 CA가 브라우저의 신뢰 저장소에 있는지 확인

모든 검증이 통과하면 주소창에 초록색 락 표시가 나타나고, HTTPS 연결이 수립됩니다.

### 7단계: 갱신
인증서는 보통 1년 유효합니다. 만료 전에 새로운 인증서를 신청해야 합니다. Let's Encrypt는 90일마다 갱신을 권장하여, 자동화를 장려합니다. 일반적인 상용 CA는 1년마다 갱신이 필요합니다.

## ✅ 장단점

**장점**:
- 사용자가 서버의 신원을 확인할 수 있어 중간자 공격 방지
- CA의 신뢰 체인으로 인증서 위조 불가능
- 브라우저에 내장된 CA 목록으로 자동 검증 가능
- Let's Encrypt 같은 무료 CA의 등장으로 모든 사이트가 HTTPS 지원 가능
- 자동 갱신 기능으로 관리 부담 감소
- EV 인증서로 최고 수준의 신뢰 표시 가능

**단점**:
- CA 개인 키 탈취 시 대규모 신뢰 붕괴 위험(실제 사례: DigiNotar)
- 인증서 갱신 비용이 서비스마다 필요(사설 CA 제외)
- 상용 CA는 갱신 절차가 복잡하고 수동 개입 필요
- 자동 갱신 실패 시 인증서 만료되어 서비스 중단
- 도메인 갱신과 인증서 갱신을 동시에 관리해야 함
- EV 인증서는 매우 높은 비용으로 대부분의 중소 기업 접근성 낮음

## 💡 실제 사례

### 1. Let's Encrypt를 활용한 소규모 서비스
작은 스타트업이 https://api.myservice.com 웹 서비스를 운영합니다. 비용을 절약하기 위해 Let's Encrypt를 사용합니다. Certbot을 설치하고 자동 갱신을 설정하면, 90일마다 인증서가 자동으로 갱신됩니다. 비용은 0원이고, 신뢰도는 유명 상용 CA 수준입니다. 다만 DV만 지원되므로, 주소창에 초록색 락만 표시되고 회사명은 표시되지 않습니다.

### 2. 은행의 EV 인증서
은행 웹사이트(예: www.bankname.com)에 접속하면 주소창에 "BankName Bank"라는 회사명이 초록색으로 표시됩니다. 이것은 EV(Extended Validation) 인증서입니다. 은행은 철저한 법적 심사를 받고 매년 높은 비용(연 1000달러 이상)을 내고 유지합니다. 사용자는 주소창의 회사명을 보고 진짜 은행 웹사이트임을 확신합니다.

### 3. 기업 내부 시스템의 사설 CA
대형 금융 회사가 내부 시스템(내부 직원만 접근)에 사용할 인증서가 필요합니다. 외부 사용자가 없으므로 외부 CA는 필요하지 않습니다. 회사는 자체 루트 CA를 만들고, 내부 API, 데이터베이스, 관리 포털용 인증서를 발급합니다. 직원의 컴퓨터에 이 회사 루트 인증서를 미리 설치하면, 모든 내부 서비스가 신뢰됩니다. 비용은 초기 설정만 필요하고, 이후 갱신은 무료입니다.

### 4. 마이그레이션 중 인증서 문제
어느 회사가 api.oldname.com에서 api.newname.com으로 마이그레이션합니다. 서버 관리자가 새 도메인용 Let's Encrypt 인증서를 발급받고 배포합니다. 하지만 DNS를 변경하기 전에 실수로 서비스를 시작했습니다. 사용자들의 클라이언트는 여전히 oldname.com으로 접속하는데, 서버는 newname.com 인증서를 제시합니다. 도메인 불일치로 인해 인증서 경고가 표시됩니다. 이를 해결하려면 SAN(Subject Alternative Name)으로 두 도메인을 모두 포함하는 인증서를 발급받아야 합니다.

## 🔗 관련 용어

- **인증서 (Certificate)**: 공개 키와 신원 정보를 포함하며, CA가 서명한 파일
- **개인 키 (Private Key)**: 서버만 소유하며, 절대 외부 공개되면 안 됨
- **공개 키 (Public Key)**: 인증서에 포함되며, 누구나 볼 수 있음
- **CSR (Certificate Signing Request)**: CA에 인증서를 요청할 때 제출하는 파일
- **TLS/SSL**: HTTPS 프로토콜의 기반 기술
- **자체 서명 인증서 (Self-Signed)**: CA 없이 자신이 서명한 인증서 (신뢰 불가)
- **와일드카드 인증서**: *.example.com처럼 모든 서브도메인을 포함하는 인증서
- **SAN (Subject Alternative Name)**: 하나의 인증서로 여러 도메인 지원
- **인증서 체인 (Certificate Chain)**: Root → Intermediate → Server 인증서 구조
- **OCSP/CRL**: 인증서 상태 확인(폐지, 유효성) 방법
