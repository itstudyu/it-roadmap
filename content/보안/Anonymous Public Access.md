# Anonymous Public Access (누구나 열리는 공개 접근)

## 📝 정의

Anonymous Public Access는 **누가 왔는지 묻지 않고 내주는 설정**이다.

세 클라우드가 입을 모아 "기본값은 잠김" 이라고 적는다. Azure 문서는 "익명 접근은 언제나 기본으로 금지된다. 명시적으로 켜지 않는 한 모든 요청은 허가를 받아야 한다" 고 쓰고, AWS 문서도 "기본적으로 새 버킷·접근 지점·객체는 공개 접근을 허용하지 않는다" 고 쓴다. 즉 이 설정은 저절로 생기는 상태가 아니라 **누군가 손으로 켜는 상태**다.

### 이름
Anonymous :: 이름 없는
Public :: 누구에게나
Access :: 들어가 보는 일
= 붙여 읽으면 "이름 없이 누구나 들어가 보는 일". 이름을 안 물으니 나중에 물을 사람도 없다

### 비유
문을 안 잠그고 퇴근한 가게 — 밤새 누가 들어와 무엇을 가져갔는지 아무도 모른다.

### 예
링크만 알면 로그인 없이 열리는 파일 주소가 그것이다. 편하려고 켰다가 검색에 걸려 사고가 난다.

### 직접
로그아웃하거나 시크릿 창으로 그 파일 주소를 다시 열어 보라. 그래도 열리면 그건 공개 상태다.

## 🖼️ 그림으로 보기

```도해
흐름: 이름표 없는 방문 하나가 파일까지 닿으려면 어디를 지나나
방문자 :: 로그인도 열쇠도 없이 주소만 친다
계정 상한 :: 이 계정에 공개를 허용해 뒀나
통 설정 :: 그 통이 공개로 열려 있나
정책 :: "누구나(`*`)" 에게 읽기를 줬나
저장소 :: 셋이 다 열려 있으면 파일을 그대로 내준다
= 어디에서도 "너 누구냐" 를 묻지 않는다. 세 겹 중 하나만 닫혀도 안 열린다
```

## ⚠️ 해결하는 문제

```도해
대조: 공개 접근을 켜 두면 무엇이 달라지나
공개로 두면 || 공개를 막으면
들어온 사람 :: 누구인지 모른다 || 이름이 남는다
사고 범위 :: 인터넷 전체 || 허락한 쪽만
되돌리기 :: 이미 퍼진 뒤 || 애초에 안 샌다
= 이름을 안 묻는 문은 사고가 난 뒤에도 누구였는지 못 묻는다
```

공개 접근 자체가 문제인 것은 아니다. 정적 웹사이트나 공개 이미지처럼 정말 누구나 봐야 하는 것이 있다. 문제는 이 설정이 **한 번 켜지면 조용하다**는 데 있다. 실수로 켜도 아무 오류가 안 나고, 오히려 잘 열리니 잘 됐다고 여긴다.

그래서 세 클라우드가 택한 방법이 같다 — 켜는 자리를 하나 더 위에 만들어 두는 것이다. AWS 는 계정과 조직 단위로 공개 차단 네 스위치를 두고 "가장 제한적인 설정을 적용한다" 고 적는다. Azure 는 저장소 계정의 `AllowBlobPublicAccess` 를 끄면 "그 계정 안 어떤 통도 공개로 설정할 수 없게 된다" 고 적는다. 구글은 조직 정책으로 공개 접근 방지를 강제하면 `allUsers` 로 온 접근이 401·403 으로 떨어진다고 적는다. 아래에서 켜도 위에서 막으면 안 열린다.

## 📊 비교: 세 곳이 "누구나" 를 어떻게 부르나

| 곳 | 누구나를 가리키는 말 | 위에서 막는 물건 |
|---|---|---|
| **AWS S3** | ACL 의 `AllUsers`, 정책의 `"Principal": "*"` | 공개 차단 네 설정. 계정·조직 단위로 건다 |
| **Azure Storage** | 통의 익명 접근 수준(Blob · Container) | 계정의 `AllowBlobPublicAccess` 를 끈다 |
| **Google Cloud** | `allUsers` · `allAuthenticatedUsers` | 공개 접근 방지. 조직 정책으로 강제한다 |

AWS 는 정책을 "일단 공개라고 가정하고 시작해서, 고정된 값으로만 대상을 좁혔을 때 비로소 비공개로 친다". 와일드카드가 하나라도 섞이면 공개로 센다는 뜻이다.

## 💡 실제 사례

- **S3 정적 웹사이트 호스팅** — 이미지와 스크립트는 누구나 받아야 한다. AWS 문서도 이 경우에는 네 스위치 중 필요한 것만 골라 풀라고 적는다. 이 설정이 정당한 거의 유일한 쪽이다.
- **테스트하다 그대로 남은 통** — 잠깐 열어 확인하고 닫는 걸 잊는다. 아무 경고도 안 나서 몇 달을 그대로 간다. AWS 가 공개로 열린 통만 따로 모아 보여주는 화면(IAM Access Analyzer for S3)을 둔 이유가 이것이다.
- **조직 단위 일괄 차단** — 통을 일일이 보지 않고 AWS Organizations 정책으로 네 설정을 한꺼번에 건다. 회원 계정이 아래에서 풀어 놔도 위쪽 설정이 덮어써서 앞으로 만들 통까지 함께 잠긴다.

## 🚫 흔한 오해

- **주소를 아무에게도 안 알려줬으니 괜찮다** — 주소는 링크·로그·검색·스캐너를 타고 새어 나간다. 공개로 열린 것은 결국 발견된다고 보는 편이 맞다.
- **계정에서 공개를 허용해 뒀으니 안에 든 파일은 이미 다 공개다** — 아니다. Azure 문서는 "계정 설정이 어떻든, 통마다 따로 켜지 않는 한 자료는 결코 익명으로 열리지 않는다" 고 적는다. 계정과 통 두 겹이 다 열려야 비로소 열린다.
- **공개 차단을 켜면 이미 공개된 것도 정리된다** — AWS 문서는 "차단 설정은 기존 정책이나 ACL 을 바꾸지 않는다" 고 적는다. 차단을 풀면 그 통은 다시 공개로 돌아온다.

## 🚨 주의사항

- **막는 스위치를 위에 걸어라.** 통마다 거는 것보다 계정·조직에 거는 편이 낫다. 통 정책을 고칠 수 있는 사람은 그 통의 차단도 풀 수 있기 때문이다.
- **끈 뒤의 오류 코드가 달라진다.** Azure 는 익명 접근을 막으면 401 이 아니라 403 이 돌아온다고 적는다. 익명으로 붙던 프로그램이 조용히 죽는 자리다.
- **정적 사이트는 예외다.** Azure 의 `$web` 통은 계정에서 익명 접근을 막아도 계속 공개로 열린다.

## 📝 정리

**"이름을 안 묻고 내주는 그 한 칸"** 이라고 읽으면 된다. 켜는 자리가 계정·통·정책 세 겹이라 하나만 닫혀도 안 열리고, 반대로 셋이 다 열려 있으면 아무 경고 없이 조용히 열린다. 켠 사람은 그날 잘 됐다고 여기고, 그 사실은 사고가 난 뒤에야 드러난다.

## 🧒 열 살에게

가게 문을 안 잠그고 퇴근하면 밤새 누구든 들어올 수 있지? 들어올 때 이름을 적는 게 아니라서 누가 뭘 가져갔는지도 몰라. 그래서 문 잠그는 걸 한 번 잊은 게 제일 큰 사고가 돼.
