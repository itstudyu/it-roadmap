# SSO (Single Sign-On)

## 📝 정의

SSO는 **한 번 로그인하면 여러 서비스를 그대로 쓰는 방식**이다.

회사에서 메일, 위키, 근태 시스템을 각각 로그인하지 않고 한 번만 인증하면 전부 열린다. 각 서비스는 비밀번호를 갖고 있지 않고, 중앙의 인증 서버가 발급한 증표만 믿는다.

### 비유
놀이공원 자유이용권. 입구에서 한 번 확인받고 손목띠를 받으면 놀이기구마다 신분증을 다시 보여주지 않는다. 각 기구는 손목띠만 확인한다.

## 🖼️ 그림으로 보기

```도해
흐름: 위키에 처음 들어갈 때 무슨 확인이 일어나나
사용자 :: 사내 위키 주소를 연다
위키 :: 로그인 안 된 상태다. 인증 서버로 보낸다
인증 서버 :: 이미 로그인돼 있는지 본다. 돼 있다
인증 서버 :: 위키용 증표를 만들어 돌려보낸다
< 위키 :: 증표를 확인하고 들여보낸다
= 사용자는 아무것도 입력하지 않았는데 로그인이 끝나 있다
```

## ⚠️ 해결하는 문제

```도해
대조: 사내 시스템이 열 개면 무엇이 달라지나
SSO 없이 || SSO 로
비밀번호 :: 열 개를 기억 || 하나만
퇴사 처리 :: 열 곳에서 삭제 || 한 곳에서 차단
비밀번호 보관 :: 열 곳이 갖고 있음 || 인증 서버만
= 계정을 한 곳에 모으는 것이 편의보다 보안에서 더 큰 이득이다
```

시스템마다 계정이 따로 있으면 사람들은 같은 비밀번호를 돌려 쓴다. 한 곳이 털리면 전부 털린다는 뜻이다. 관리자 쪽도 문제다. 퇴사자 계정을 열 곳에서 지워야 하고, 한 곳을 놓치면 그 사람은 계속 들어올 수 있다.

SSO는 계정을 한 곳에 모은다. 퇴사 처리도 한 번이고, 비밀번호를 여러 시스템이 나눠 갖는 상황도 사라진다.

## ⚙️ 작동 원리

```도해
층: 누가 무엇을 맡나
인증 서버 :: 계정과 비밀번호를 갖고 신원을 확인
증표 :: 확인 결과를 담아 서명한 것
각 서비스 :: 증표만 검증한다. 비밀번호를 모른다
= 신뢰가 한 방향이다. 서비스가 인증 서버를 믿는 구조
```

증표를 주고받는 방식은 크게 두 갈래다. 예전부터 기업에서 쓰던 SAML은 XML 기반이고, 요즘 웹과 앱에서 많이 쓰는 [[OIDC]]는 [[OAuth]] 위에 얹은 방식이다.

## 💡 실제 사례

- **사내 시스템 통합** 회사 계정 하나로 메일, 위키, 배포 도구를 전부 쓴다.
- **소셜 로그인** 구글이나 카카오 계정으로 여러 서비스에 들어간다.
- **퇴사자 차단** 인증 서버에서 계정을 끄면 그 사람이 쓰던 모든 시스템이 동시에 막힌다.

## 🚫 흔한 오해

- **SSO는 비밀번호가 같은 것이다** — 다르다. 비밀번호를 여러 곳에 똑같이 쓰는 것(SSO가 아닌 것)과, 비밀번호를 한 곳에만 두는 것(SSO)은 정반대다.
- **SSO가 있으면 더 안전하다** — 계정 하나가 뚫리면 전부 뚫린다. 그래서 SSO에는 다단계 인증이 사실상 필수다.
- **로그아웃하면 전부 로그아웃된다** — 서비스마다 자기 세션을 따로 갖고 있어서, 전체 로그아웃은 별도로 구현해야 한다.

## 🚨 주의사항

- **인증 서버가 단일 장애점이다.** 여기가 죽으면 아무도 아무 데도 못 들어간다. 이중화가 필수다.
- **다단계 인증을 같이 건다.** 열쇠 하나로 전부 열리는 구조라 그 열쇠를 지키는 일이 전부가 된다.

## 📝 정리

SSO는 한 번의 인증으로 여러 서비스를 쓰게 하는 구조다. 계정 관리와 퇴사 처리가 단순해지지만, 인증 서버가 뚫리거나 죽으면 전부 영향을 받는다.

## ❓ 이해했는지

- 여러 서비스에 같은 비밀번호를 쓰는 것과 SSO는 어떻게 다른가?
- SSO 환경에서 다단계 인증이 사실상 필수인 이유는?
- 위키에서 로그아웃했는데 메일은 여전히 열려 있다면 왜 그런가?

## 🔗 관련 용어

- [[OAuth]] — 권한을 빌려주는 규약. SSO의 재료로 쓰인다
- [[OIDC]] — OAuth 위에 인증을 얹은 방식
- [[SAML]] — 기업 환경에서 오래 쓰인 증표 교환 방식
- [[Zero Trust]] — 한 번 통과했다고 계속 믿지 않는 반대 방향의 원칙
