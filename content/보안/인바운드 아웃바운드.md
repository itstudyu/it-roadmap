# 인바운드 / 아웃바운드 트래픽 (Inbound / Outbound)

## 📝 정의

인바운드와 아웃바운드는 **트래픽이 서버로 들어오는지 나가는지의 방향**이다.

사용자가 웹사이트를 여는 것은 인바운드이고, 그 웹서버가 결제 API를 부르는 것은 아웃바운드다. 방화벽은 이 두 방향에 각각 다른 규칙을 걸어 따로 통제한다.

### 비유
공항의 입국 심사와 출국 심사. 같은 건물이지만 검문소가 따로 있고 보는 것도 다르다.

## 🖼️ 그림으로 보기

```도해
흐름: 결제 한 건이 오갈 때 방화벽은 어디서 검사하나
사용자 :: 웹서버의 443 번 포트로 요청한다
방화벽 :: 인바운드 규칙에 443 이 있어 통과시킨다
웹서버 :: 외부 결제 API 를 부른다
방화벽 :: 아웃바운드 규칙을 보고 내보낸다
방화벽 :: 그 응답은 나간 요청의 짝이라 그냥 통과
< 웹서버 :: 결과를 사용자에게 돌려준다
= 나간 요청의 응답은 인바운드 규칙이 없어도 들어온다
```

## ⚠️ 해결하는 문제

```도해
대조: 방향별 규칙이 없으면 무엇이 달라지나
규칙 없이 || 방향별 규칙으로
열린 포트 :: 전부 || 쓰는 것만
DB 접속 :: 밖에서도 됨 || 웹서버만 됨
데이터 유출 :: 아무 데로나 || 정해진 곳만
= 방향마다 문을 따로 세워야 들어오는 것과 나가는 것을 나눠 막는다
```

포트가 전부 열려 있으면 밖에서 아무나 두드릴 수 있다. SSH 22번이 열려 있으면 봇이 계속 비밀번호를 넣어보고, 데이터베이스 3306번이 열려 있으면 웹서버를 거치지 않고 바로 DB를 공격한다.

나가는 쪽도 문제다. 서버에 악성 소프트웨어가 들어오면 그것이 밖으로 데이터를 보낸다. 인바운드만 조여두면 들어오는 길은 좁혔더라도 나가는 길은 아무 제한이 없다.

두 방향을 나눠 규칙을 걸면 각각을 따로 좁힐 수 있다. 웹서버는 80과 443만 받고, 나갈 때는 443으로 정해진 결제 API 쪽으로만 나가게 하는 식이다.

## ⚙️ 작동 원리

```도해
층: 방화벽 규칙 하나는 무엇으로 이루어지나
방향 :: 인바운드인지 아웃바운드인지
상대 :: 출발지 또는 목적지 IP 범위
포트와 프로토콜 :: 443, TCP 같은 값
허용 여부 :: 통과시킬지 막을지
= 이 넷이 다 맞아야 그 규칙이 패킷에 걸린다
```

요즘 쓰는 방화벽은 대개 상태를 기억한다. 나간 요청을 적어뒀다가 그 응답이 돌아오면 인바운드 규칙을 보지 않고 통과시킨다. 그래서 아웃바운드 규칙 하나로 왕복이 함께 처리된다.

기본값은 두 방향이 다르다. AWS Security Group은 인바운드를 전부 막고 시작하고 아웃바운드는 전부 열고 시작한다. 들어오는 쪽은 허용 목록을 쌓아 올리는 방식이고, 나가는 쪽은 서버가 인터넷을 써야 하니 일단 열어둔 것이다. 보안을 조일 때 손대는 자리가 여기다.

## 📊 비교: 인바운드 vs 아웃바운드

| | 인바운드 | 아웃바운드 |
|---|---|---|
| 방향 | 밖에서 서버로 | 서버에서 밖으로 |
| 예 | 사용자 접속, 관리자 SSH | 결제 API 호출, DNS 조회 |
| AWS 기본값 | 모두 차단 | 모두 허용 |
| 막아서 줄이는 것 | 포트 스캔, 무차별 접속 | 데이터 유출 |
| 흔한 포트 | 80, 443, 22 | 443, 53 |

## 💡 실제 사례

- **웹서버와 DB 분리** — DB는 3306번을 웹서버 IP에서만 받는다. 웹서버가 뚫려도 한 단계를 더 거쳐야 DB에 닿는다.
- **SSH 출발지 제한** — 22번을 사무실 IP 한 곳에서만 허용한다. 인터넷의 봇이 아무리 두드려도 규칙에서 걸린다.
- **아웃바운드 최소화** — 웹서버가 443으로 정해진 API 쪽으로만 나가게 둔다. 악성 소프트웨어가 다른 포트로 내보내려 하면 막힌다.

## 🚫 흔한 오해

- **방화벽은 들어오는 것을 막는 장치다** — 나가는 쪽에도 규칙이 있다. 데이터가 밖으로 새는 것을 막는 자리는 아웃바운드다.
- **아웃바운드는 응답이 나가는 것뿐이라 열어둬도 된다** — 아웃바운드는 서버가 먼저 거는 연결이다. 서버에 들어온 악성 소프트웨어가 밖으로 나가는 통로가 여기다.
- **응답을 받으려면 인바운드에도 규칙을 넣어야 한다** — 상태를 기억하는 방화벽은 나간 요청의 응답을 알아서 들여보낸다. 규칙을 더 넣으면 필요 없는 문을 여는 셈이 된다.

## 🚨 주의사항

- **아웃바운드 기본 허용을 그대로 두지 않는다.** 클라우드 기본값은 전부 열려 있으니 필요한 곳만 남기고 좁힌다.
- **막힌 트래픽을 기록해둔다.** 어떤 요청이 걸렸는지가 남아야 포트 스캔이나 잘못된 설정을 나중에 찾아낼 수 있다.

## 📝 정리

인바운드는 들어오는 트래픽, 아웃바운드는 나가는 트래픽이고 방화벽은 두 방향에 각각 규칙을 건다. 들어오는 쪽은 필요한 포트만 열어 두드릴 자리를 줄이고, 나가는 쪽은 정해진 곳만 열어 데이터가 새는 길을 줄인다. 상태를 기억하는 방화벽은 나간 요청의 응답을 알아서 들여보낸다.

## ❓ 이해했는지

- 인바운드만 조여두면 무엇을 못 막나?
- DB의 3306번을 웹서버 IP에서만 여는 것이 공격을 어떻게 어렵게 만드나?
