# 인바운드 / 아웃바운드 트래픽 (Inbound / Outbound)

## 📝 정의

인바운드 트래픽은 외부에서 서버로 들어오는 모든 네트워크 통신을 의미하고, 아웃바운드 트래픽은 서버에서 외부로 나가는 모든 네트워크 통신을 의미합니다. 예를 들어, 사용자가 웹사이트에 접속할 때 사용자의 브라우저에서 웹서버로 HTTP 요청을 보내면 이것이 인바운드입니다. 반대로 웹서버가 외부 결제 API에 요청을 보내면 이것이 아웃바운드입니다. 방화벽과 네트워크 보안에서는 이 두 방향의 트래픽을 별도로 제어하며, 각각에 대한 명시적인 규칙이 필요합니다.

방화벽의 기본 원칙은 화이트리스트 방식입니다. 인바운드는 기본적으로 모두 차단하고, 필요한 포트와 출발지만 명시적으로 허용합니다. 이렇게 하면 예상 외의 공격으로부터 보호됩니다. 아웃바운드도 마찬가지로, 서버가 필요한 통신(외부 API, 다른 내부 서버 등)만 허용하고 나머지는 차단합니다. 이를 통해 악성 소프트웨어나 손상된 애플리케이션이 임의로 데이터를 외부로 유출하는 것을 방지합니다.

> **한 줄 요약**: "인바운드는 들어오는 요청, 아웃바운드는 나가는 요청. 각각 방화벽으로 제어합니다"

**비유**:
- **공항 보안 비유**: 탑승객이 공항(서버)에 들어오는 것이 인바운드(검사대 통과, 신분증 확인). 탑승객이 비행기(외부)를 타고 나가는 것이 아웃바운드(보안 검문). 각 방향마다 별도의 검문소와 규칙이 있습니다.
- **편의점 문 비유**: 손님이 들어오는 것(인바운드)과 나가는 것(아웃바운드)은 같은 출입문이지만, 편의점은 들어올 수 있는 짐의 크기와 나갈 수 있는 짐에 제한을 둘 수 있습니다. 들어오는 것은 넓지만 나가는 것은 좁은 가방만 가능하면, 소매치기를 방지할 수 있습니다.

## 🎯 핵심 개념

### 1. 인바운드 트래픽 (Inbound Traffic)
인바운드는 외부에서 서버로 들어오는 모든 통신입니다. 사용자의 웹 브라우저가 보낸 HTTP/HTTPS 요청, 관리자가 SSH로 원격 접속, 모바일 앱이 API 서버에 보낸 요청 등이 모두 인바운드입니다. 웹서버는 80번(HTTP) 또는 443번(HTTPS) 포트를 열어야 외부 사용자가 접속할 수 있습니다. 데이터베이스 서버는 3306번(MySQL) 포트를 내부 웹서버에서만 접속 가능하도록 제한해야 합니다.

### 2. 아웃바운드 트래픽 (Outbound Traffic)
아웃바운드는 서버에서 외부로 나가는 모든 통신입니다. 웹서버가 외부 결제 게이트웨이(PG)에 결제 요청을 보내는 것, 서버가 DNS 조회를 하는 것, 로그 서버로 데이터를 전송하는 것 모두 아웃바운드입니다. 기본적으로는 모든 아웃바운드를 차단하고, 필요한 것만 명시적으로 허용하는 것이 보안입니다. 이렇게 하면 악성 소프트웨어가 감염되었거나, 내부자가 데이터를 유출하려고 해도 제한된 통신만 가능합니다.

### 3. 포트와 프로토콜
각 트래픽은 특정 포트와 프로토콜을 사용합니다. HTTP는 80번, HTTPS는 443번, SSH는 22번, MySQL은 3306번 등입니다. 방화벽 규칙은 "출발지 IP, 목적지 IP, 포트, 프로토콜(TCP/UDP), 인바운드/아웃바운드, 허용/차단"의 6가지 요소로 이루어집니다. 예를 들어, "0.0.0.0/0(모든 IP) → 서버(목적지) 443번(HTTPS) TCP 인바운드 허용"이라는 규칙이 있으면, 누구든지 서버의 443번 포트(HTTPS)에 접속할 수 있습니다.

### 4. AWS Security Group의 기본 정책
AWS의 Security Group은 인바운드와 아웃바운드를 별도로 관리합니다. 기본적으로 인바운드는 모두 차단(화이트리스트), 아웃바운드는 모두 허용(블랙리스트)입니다. 이것은 보안과 사용성 사이의 균형입니다. 인바운드는 엄격하게 필요한 것만 열고, 아웃바운드는 서버가 인터넷 접근이 필요하기 때문에 일반적으로 허용합니다.

### 5. 상태 기반 방화벽 (Stateful Firewall)
현대 방화벽은 대부분 상태 기반입니다. 클라이언트가 서버에 요청(아웃바운드)을 보냈다면, 서버로부터 돌아오는 응답(인바운드)은 자동으로 허용합니다. 예를 들어, 웹서버가 외부 API에 요청을 보냈다면, 그 API로부터의 응답은 자동으로 인바운드로 허용됩니다. 이렇게 하면 아웃바운드 규칙 하나로 양방향 통신을 관리할 수 있습니다.

## ⚠️ 해결하는 문제

### 문제 1: 예상 외의 공격으로부터의 보호
방화벽 규칙 없이 모든 포트가 열려있다면, 해커가 DDoS, 포트 스캔, 브루트 포스 공격을 시도할 수 있습니다. 인바운드 규칙으로 필요한 포트만 열고 출발지를 제한하면, 예상 외의 공격은 차단됩니다. 예를 들어, SSH 22번 포트는 특정 관리자 IP에서만 허용하면, 인터넷의 봇이 무차별적으로 접속을 시도해도 모두 차단됩니다.

### 문제 2: 악성 소프트웨어로 인한 데이터 유출
서버에 악성 소프트웨어가 감염되거나, 악의적인 내부자가 데이터를 빼내려고 시도할 수 있습니다. 아웃바운드 규칙으로 필요한 통신만 허용하면, 악성 소프트웨어가 임의의 외부 서버로 데이터를 전송하는 것을 차단합니다. 예를 들어, 웹서버는 443번(HTTPS)으로만 외부 API에 통신하도록 제한하면, 다른 포트로의 데이터 유출 시도는 차단됩니다.

### 문제 3: 과도한 권한으로 인한 보안 침해
데이터베이스 서버에 외부 인터넷에서 직접 접속이 가능하면, 해커가 데이터베이스를 직접 공격할 수 있습니다. 인바운드 규칙으로 데이터베이스 3306번을 내부 웹서버 IP(예: 10.0.1.100)에서만 허용하면, 외부 인터넷에서의 직접 접속은 불가능합니다. 해커는 먼저 웹서버를 뚫어야만 데이터베이스에 접근할 수 있으므로, 공격의 난이도가 높아집니다.

## ⚙️ 작동 원리

### 1단계: 패킷 도착 (Inbound)
사용자의 웹 브라우저에서 웹서버의 443번(HTTPS) 포트로 요청을 보냅니다. 이 요청이 인터넷을 통해 웹서버에 도달합니다. 하지만 방화벽이 먼저 이 패킷을 검사합니다.

### 2단계: 인바운드 규칙 확인
방화벽은 인바운드 규칙을 차례대로 확인합니다. "0.0.0.0/0(모든 IP):443(HTTPS) 허용"이라는 규칙이 있으므로, 이 패킷은 허용됩니다. 규칙에 없다면 기본 정책에 따라 차단됩니다. 허용된 패킷만 웹서버에 도달합니다.

### 3단계: 아웃바운드 요청 (Outbound)
웹서버가 외부 결제 API(포트 443)에 요청을 보내려고 합니다. 이 요청도 방화벽에 검사됩니다. 아웃바운드 규칙 중 "0.0.0.0/0:443 허용"이 있으므로 통과합니다. 만약 이 규칙이 없다면 요청은 차단됩니다.

### 4단계: 응답 자동 허용 (Stateful)
상태 기반 방화벽은 나가는 요청을 추적합니다. 웹서버가 결제 API(포트 443)로 요청을 보냈으면, 그 API로부터의 응답(인바운드)은 자동으로 허용합니다. 이렇게 하면 인바운드 규칙에 "0.0.0.0/0:443"을 따로 추가할 필요가 없습니다.

### 5단계: 데이터베이스 통신 제어
웹서버에서 데이터베이스 서버(포트 3306)로 쿼리를 보냅니다. 웹서버의 아웃바운드 규칙에 "DB서버 10.0.1.100:3306 허용"이 있으므로 통과합니다. 동시에 DB서버의 인바운드 규칙에 "웹서버 10.0.1.50:3306만 허용"이 있으므로, 오직 웹서버에서만 접속 가능합니다. 외부 인터넷에서 직접 데이터베이스에 접속할 수 없습니다.

### 6단계: 거부된 트래픽
규칙에 맞지 않는 패킷(예: 외부 IP에서 데이터베이스 포트 3306 접속)은 차단됩니다. 방화벽은 이를 로깅하여, 보안 담당자가 추후 분석할 수 있습니다. DDoS 공격이나 포트 스캔 시도가 감지될 수 있습니다.

## ✅ 장단점

**장점**:
- 명확한 방향성(인바운드/아웃바운드)으로 규칙 설정이 체계적
- 포트 기반의 세분화된 제어가 가능하여, 정확한 보안 정책 구현
- 상태 기반 방화벽으로 양방향 통신을 효율적으로 관리
- Security Group 같은 도구로 UI 친화적인 규칙 설정
- 로깅으로 통신 기록을 추적하여 보안 감시 및 감사 용이
- AWS, GCP 등 클라우드 서비스의 표준 보안 메커니즘

**단점**:
- 초기 설정 시 필요한 모든 포트/프로토콜을 파악해야 함
- 규칙이 많아지면 관리가 복잡해지고, 충돌 가능성 증가
- 순서 기반 규칙에서 상단의 차단 규칙이 하단의 허용 규칙을 무시할 수 있음
- 비상태 방화벽은 각 방향마다 규칙을 작성해야 하므로 수동 작업량 증가
- 포트 번호를 변경하면 규칙도 모두 수정해야 함
- 동적 IP 환경에서 IP 기반 규칙 유지보수가 어려움

## 💡 실제 사례

### 1. 웹서버와 데이터베이스 분리 보안
어느 회사의 웹서버와 데이터베이스가 같은 VPC에 있습니다. 웹서버의 Security Group은 인바운드 80/443을 모든 IP(0.0.0.0/0)에서 허용하고, 아웃바운드는 데이터베이스 서버 IP(10.0.1.100)의 3306번 포트만 허용합니다. 데이터베이스의 Security Group은 인바운드 3306을 오직 웹서버 IP(10.0.1.50)에서만 허용합니다. 이렇게 하면 웹서버가 뚫려도, 해커는 웹서버를 거쳐야만 데이터베이스에 접근할 수 있습니다.

### 2. SSH 접근 제한으로 공격 방어
개발팀이 VPN을 사용하지 않고, 특정 사무실 IP(203.0.113.50)에서만 SSH 22번 포트 접근을 허용하기로 결정했습니다. Security Group 인바운드 규칙: "203.0.113.50:22 허용". 그 결과, 인터넷의 봇이 22번 포트를 무차별적으로 스캔해도 모두 차단됩니다. 사무실에서만 개발 서버에 SSH로 접속할 수 있습니다.

### 3. 아웃바운드 제한으로 악성 소프트웨어 억제
금융회사의 서버에서 아웃바운드를 최소로 제한합니다. 웹서버는 443번(HTTPS)으로 특정 결제 API 서버들과만 통신 가능하게 설정합니다. 만약 악성 소프트웨어가 웹서버를 감염시키고 공격자의 C&C 서버(포트 8080)로 통신하려고 해도, 아웃바운드 규칙에 없으므로 차단됩니다. 이로써 피해를 최소화합니다.

## 🔗 관련 용어

- **Security Group**: AWS의 가상 방화벽. 인바운드/아웃바운드 규칙을 관리
- **Network ACL**: AWS의 서브넷 레벨 방화벽. Security Group보다 상위 레벨
- **방화벽 규칙**: 특정 트래픽을 허용/차단하는 정책
- **포트**: 네트워크 통신의 논리적 끝점 (0~65535)
- **프로토콜**: TCP, UDP, ICMP 등 통신 방식
- **화이트리스트**: 허용 목록 기반 (기본 차단)
- **블랙리스트**: 차단 목록 기반 (기본 허용)
- **상태 기반 방화벽**: 연결 상태를 추적하는 방화벽
- **비상태 방화벽**: 각 패킷을 독립적으로 판단하는 방화벽
- **CIDR 표기법**: IP 범위를 표현하는 방법 (예: 10.0.0.0/8)
