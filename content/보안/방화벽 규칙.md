# 방화벽 규칙 (Firewall Rules)

## 📝 정의

방화벽 규칙은 어떤 트래픽을 허용하고 어떤 트래픽을 차단할지를 정의하는 정책 집합입니다. 각 규칙은 출발지 IP, 목적지 IP, 포트, 프로토콜(TCP/UDP), 통신 방향(인바운드/아웃바운드), 그리고 수행할 동작(허용/차단)으로 이루어집니다. 방화벽은 이 규칙들을 위에서 아래로 순서대로 평가하여, 첫 번째로 일치하는 규칙을 적용합니다. 규칙이 복잡해질수록 관리와 디버깅이 어려워지므로, 효율적인 규칙 설계가 중요합니다.

방화벽 규칙의 철학은 두 가지 접근 방식으로 나뉩니다. 화이트리스트(허용 목록) 방식은 허용할 것을 명시하고 나머지는 차단하는 것으로, 보안이 강하지만 관리가 복잡합니다. 블랙리스트(차단 목록) 방식은 차단할 것을 명시하고 나머지는 허용하는 것으로, 사용성은 좋지만 보안에 취약합니다. 현대 보안 모범 사례는 인바운드는 화이트리스트(기본 차단), 아웃바운드도 화이트리스트(필요한 것만 허용)를 권장합니다. AWS Security Group, Google Cloud Firewall, Nginx, iptables 등 다양한 도구가 방화벽 규칙을 구현합니다.

> **한 줄 요약**: "방화벽 규칙은 네트워크 통신을 화이트리스트 기반으로 세밀하게 제어하는 정책 목록"

**비유**:
- **입국 심사 비유**: 공항(방화벽)의 입국 심사(규칙)는 순서대로 진행됩니다. 여권 확인(출발지) → 여행 목적 확인(목적지) → 금지 물품 확인(포트) → 통관(허용/차단). 한 단계에서 거부되면 이후 단계로 진행할 수 없습니다.
- **경비원 체크리스트 비유**: 빌딩(서버) 경비원이 방문객을 받을 때 체크리스트를 위에서 아래로 읽습니다. "CEO는 항상 들어오기" → "마케팅팀은 평일 9~5시만" → "외부인은 사전 예약 필수". 각 규칙을 순서대로 확인하여 첫 번째 일치하는 규칙을 따릅니다.

## 🎯 핵심 개념

### 1. 규칙의 6가지 요소
방화벽 규칙은 다음 6가지 요소로 구성됩니다:
- **출발지 IP (Source)**: 트래픽이 어디서 나왔는가 (예: 0.0.0.0/0 = 모든 IP, 203.0.113.50 = 특정 IP)
- **목적지 IP (Destination)**: 트래픽이 어디로 가는가 (예: 10.0.1.100 = 특정 서버)
- **포트 (Port)**: 어느 포트인가 (예: 80, 443, 3306)
- **프로토콜 (Protocol)**: 통신 방식 (TCP, UDP, ICMP)
- **방향 (Direction)**: 인바운드인지 아웃바운드인지
- **동작 (Action)**: 허용(Allow)인지 차단(Deny)인지

예: "0.0.0.0/0 → 10.0.1.50:443 TCP 인바운드 허용" = 모든 IP에서 웹서버의 443번(HTTPS)으로 들어오는 요청을 허용합니다.

### 2. 화이트리스트 vs 블랙리스트 접근 방식
**화이트리스트 (Allowlist, 권장)**:
- 기본 정책: 모든 트래픽 차단
- 명시적으로 허용한 것만 통과
- 보안 강함 (예상치 못한 공격 차단)
- 관리 복잡 (필요한 모든 통신을 명시해야 함)
- AWS Security Group의 기본 인바운드 정책

**블랙리스트 (Blocklist)**:
- 기본 정책: 모든 트래픽 허용
- 명시적으로 차단한 것만 차단
- 보안 약함 (새로운 공격에 대응 어려움)
- 관리 간단 (문제 생기면 차단 규칙만 추가)
- 일부 레거시 시스템에서 사용

### 3. 규칙 우선순위와 선착순 적용 (First Match Wins)
방화벽은 규칙을 위에서 아래로 순서대로 평가합니다. 패킷이 어떤 규칙과 일치하면, 그 규칙의 동작을 즉시 적용하고 하단의 규칙은 평가하지 않습니다. 따라서 규칙의 순서가 매우 중요합니다. 상단의 광범위한 규칙이 하단의 세분화된 규칙을 무시할 수 있습니다.

### 4. 상태 기반 방화벽 (Stateful Firewall)
대부분의 현대 방화벽은 상태 기반입니다. 세션(연결)을 추적하여, 나가는 요청(아웃바운드)에 대한 응답(인바운드)은 자동으로 허용합니다. 웹서버가 외부 API(포트 443)로 요청을 보냈다면, 그 API로부터의 응답은 인바운드 규칙에 없어도 자동으로 허용됩니다. 이렇게 하면 규칙 개수를 크게 줄일 수 있습니다.

### 5. 기본 정책 (Default Policy)
모든 규칙에 일치하지 않는 트래픽에 대해 적용되는 정책입니다. 대부분의 경우 기본 정책은 "차단"입니다. AWS의 기본 정책은 인바운드 차단, 아웃바운드 허용이며, 이는 보안과 사용성의 좋은 균형입니다.

## ⚠️ 해결하는 문제

### 문제 1: 무차별 포트 스캔과 공격 방지
해커는 무작위로 포트들을 스캔하여 열려있는 포트를 찾습니다. 모든 포트가 열려있으면 DDoS, 브루트 포스, 익스플로잇 공격에 노출됩니다. 방화벽 규칙으로 필요한 포트만 열면, 예상치 못한 공격은 자동으로 차단됩니다.

### 문제 2: 내부 자원을 외부 공격으로부터 보호
데이터베이스, 관리자 포털, 내부 API 등은 외부 인터넷에 노출되면 안 됩니다. 방화벽 규칙으로 이들 포트를 내부 IP 범위에서만 허용하면, 외부에서 직접 접근할 수 없습니다. 해커는 먼저 웹서버를 뚫어야만 데이터베이스에 접근할 수 있으므로, 공격의 난이도가 올라갑니다.

### 문제 3: 악성 소프트웨어로 인한 데이터 유출
아웃바운드 규칙이 없으면, 감염된 서버가 임의의 외부 서버로 데이터를 전송할 수 있습니다. 아웃바운드 규칙으로 필요한 통신만 허용하면, 악성 소프트웨어의 명령 제어(C&C) 서버나 데이터 유출 시도를 차단합니다.

## ⚙️ 작동 원리

### 1단계: 패킷 도착
외부 인터넷에서 패킷이 도착합니다. 패킷에는 출발지 IP, 목적지 IP, 포트, 프로토콜 등의 헤더 정보가 포함되어 있습니다. 방화벽은 이 패킷을 받으면 즉시 규칙 평가를 시작합니다.

### 2단계: 규칙 순서대로 평가
방화벽은 설정된 규칙들을 위에서 아래로 하나씩 확인합니다. 각 규칙마다 "이 패킷의 출발지, 목적지, 포트, 프로토콜이 이 규칙과 일치하는가?"를 판단합니다.

### 3단계: 첫 번째 일치 규칙 적용
어떤 규칙과 일치하면, 그 규칙의 동작(허용/차단)을 즉시 적용합니다. 하단의 다른 규칙들은 평가하지 않습니다. 이것이 "First Match Wins" 원칙입니다.

예시:
- 패킷: 출발지 203.0.113.100, 목적지 10.0.1.50:443
- 규칙 1: 0.0.0.0/0:443 허용 → 일치 → 즉시 허용, 규칙 2 이하는 평가 안 함
- 만약 규칙 1이 0.0.0.0/0:80만 허용이었다면 규칙 2로 진행

### 4단계: 기본 정책 적용
모든 규칙에 일치하지 않으면, 기본 정책을 적용합니다. 일반적으로 기본 정책은 "차단"입니다.

### 5단계: 상태 기반 추적 (Stateful)
나가는 요청(아웃바운드)을 추적합니다. 웹서버가 외부 API(포트 443)로 요청을 보냈으면, 그 요청은 "확립된 연결"로 표시됩니다. 그 API로부터의 응답(인바운드)이 도착하면, 상태 기반 방화벽은 자동으로 이를 허용합니다. 인바운드 규칙에 "0.0.0.0/0:443"을 따로 추가할 필요가 없습니다.

### 6단계: 로깅 및 모니터링
차단된 패킷들은 로그에 기록됩니다. 보안 담당자는 이 로그를 분석하여 공격 시도, 비정상 트래픽 등을 감시합니다. 반복된 공격 출발지는 규칙에 추가하여 완전히 차단할 수 있습니다.

|------|----------------------|----------------------|------------------|-----------------|
| **기본 정책** | 차단 (명시적 허용만) | 허용 (명시적 차단만) | 양방향 추적 | 독립 평가 |
| **보안 수준** | 매우 높음 | 낮음 | 높음 | 중간 |
| **관리 복잡도** | 높음(모두 명시) | 낮음(문제만 추가) | 중간 | 높음(수동) |
| **오탐(False Positive)** | 없음(명시된 것만) | 많음(예상 밖 공격) | 적음 | 많음 |
| **미탐(False Negative)** | 가능(규칙 빠뜨림) | 많음(알려지지 않은 공격) | 적음 | 많음 |
| **적용 상황** | AWS Security Group | 레거시 방화벽 | 현대적 클라우드 | 복잡한 네트워크 |
| **프로덕션 권장** | 네(필수) | 아니오(위험) | 네(표준) | 아니오 |
| **자동화 가능** | 용이 | 어려움 | 용이 | 복잡함 |

## ✅ 장단점

**장점**:
- 화이트리스트 방식으로 예상하지 못한 공격 자동 차단
- 포트, IP, 프로토콜 기반 세밀한 제어로 정확한 보안 정책 구현
- AWS, GCP, Azure 등 모든 클라우드의 표준 보안 메커니즘
- 상태 기반 추적으로 양방향 통신을 효율적으로 관리
- 로깅과 분석으로 보안 감시 및 감사 용이
- IaC(Infrastructure as Code)로 자동화 가능

**단점**:
- 초기 설계 시 필요한 모든 포트와 프로토콜을 파악해야 함
- 규칙이 많아지면 관리가 복잡해지고, 규칙 간 충돌 가능성 증가
- 규칙 순서의 중요성으로 인한 실수 위험 (상단 규칙이 하단을 무시)
- 비상태 방화벽은 각 방향(인바운드/아웃바운드)마다 규칙을 작성해야 함
- 서비스 포트 변경 시 모든 규칙을 수정해야 함
- 동적 IP 환경에서는 IP 기반 규칙 유지보수가 어려움
- 거짓 긍정(정상 서비스 차단)으로 인한 운영 이슈

## 💡 실제 사례

### 1. 전형적인 3층 아키텍처의 방화벽 규칙
회사가 웹 서버, 애플리케이션 서버, 데이터베이스를 분리하여 운영합니다.

**웹 서버 (10.0.1.50)**:
- 인바운드: 0.0.0.0/0:80 허용, 0.0.0.0/0:443 허용, 203.0.113.0/24:22 허용 (관리자만)
- 아웃바운드: 10.0.2.0/24:8080 허용 (앱 서버), 0.0.0.0/0:443 허용 (외부 API), 0.0.0.0/0:53 허용 (DNS)

**애플리케이션 서버 (10.0.2.100)**:
- 인바운드: 10.0.1.50:8080 허용 (웹 서버만), 203.0.113.0/24:22 허용 (관리자)
- 아웃바운드: 10.0.3.100:3306 허용 (DB), 0.0.0.0/0:443 허용 (외부 API)

**데이터베이스 (10.0.3.100)**:
- 인바운드: 10.0.2.100:3306 허용 (앱 서버만)
- 아웃바운드: 최소화 (필요시에만 설정)

결과: 각 층이 필요한 것과만 통신하고, 외부 인터넷은 웹 서버를 통해서만 접근 가능합니다. 데이터베이스는 외부에서 직접 접근할 수 없습니다.

### 2. SSH 접근 제한으로 보안 강화
보안 정책을 수립하여 SSH(22번 포트) 접근을 제한합니다.

**변경 전 (위험)**:
- 인바운드: 0.0.0.0/0:22 허용 (누구나 SSH 접속 가능)
- 결과: 인터넷의 봇이 계속 SSH 접속 시도, 로그가 가득 찬다.

**변경 후 (보안)**:
- 인바운드: 203.0.113.50:22 허용 (사무실 IP만), VPN IP:22 허용 (원격근무)
- 결과: 사무실과 VPN에서만 SSH 접속 가능. 무차별 스캔은 차단.

### 3. DDoS 공격 차단
특정 IP에서 대량의 요청이 발생합니다.

**대응 방법**:
- 로그에서 공격 출발지 IP(예: 192.0.2.100) 확인
- 임시 규칙 추가: "192.0.2.100:* 차단" (우선순위 최상단)
- 결과: 해당 IP의 모든 요청이 즉시 차단

### 4. 포트 번호 변경 사건
웹서버의 포트를 보안상 8443으로 변경합니다.

**문제**:
- 방화벽 규칙이 443으로 고정되어 있음
- 외부 사용자가 접속 불가

**해결**:
- 인바운드 규칙 수정: 0.0.0.0/0:443 → 0.0.0.0/0:8443
- 또는 WAF(Web Application Firewall)를 앞단에 두어, 443 요청을 8443으로 포워드

## 🔗 관련 용어

- **Security Group**: AWS의 가상 방화벽. 인스턴스 수준 제어
- **Network ACL**: AWS의 서브넷 수준 방화벽. 더 상위 레벨
- **iptables/firewalld**: Linux의 방화벽 도구
- **ufw (Uncomplicated Firewall)**: Linux의 간단한 방화벽 관리 도구
- **WAF (Web Application Firewall)**: L7(애플리케이션) 레벨 방화벽
- **포트 스캔**: 열려있는 포트를 찾기 위한 공격
- **DDoS (Distributed Denial of Service)**: 대량의 트래픽으로 서비스 마비
- **화이트리스트/블랙리스트**: 허용/차단 목록 기반 정책
- **CIDR 표기법**: IP 범위 표현 (예: 10.0.0.0/8 = 10.0.0.0 ~ 10.255.255.255)
- **로깅/모니터링**: 방화벽을 통과한 트래픽 기록 및 분석
