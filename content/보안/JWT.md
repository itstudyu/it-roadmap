# JWT (JSON Web Token)

## 📝 정의

JWT는 **내용과 서명을 함께 담아 위조를 막은 토큰**이다.

서버가 사용자 정보를 적고 자기만 아는 열쇠로 서명해서 준다. 다음 요청에 그 토큰이 오면, 서버는 저장소를 뒤지지 않고 서명만 확인해서 진짜인지 안다.

### 비유
공연 티켓의 홀로그램. 티켓에 좌석 정보가 적혀 있고 위조 방지 무늬가 찍혀 있다. 직원은 명단을 찾아볼 필요 없이 무늬만 보고 통과시킨다.

### 예
앱을 며칠 만에 열면 아무것도 안 했는데 로그인 화면부터 나오는 때가 있다. 들고 있던 토큰에 박힌 시각이 지난 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 로그인한 뒤 요청마다 무슨 확인이 일어나나
사용자 :: 아이디와 비밀번호로 로그인한다
서버 :: 사용자 정보를 적고 서명해서 토큰을 준다
브라우저 :: 토큰을 저장해둔다
브라우저 :: 다음 요청 헤더에 토큰을 붙인다
서버 :: 서명이 맞는지만 계산한다. DB 조회 없음
< 사용자 :: 통과. 서버는 아무것도 기억하지 않았다
= 서버가 기억하는 대신 토큰이 스스로를 증명한다
```

## ⚠️ 해결하는 문제

```도해
대조: 서버를 여러 대로 늘리면 무엇이 달라지나
세션 방식 |=| JWT 방식
로그인 확인 :: 저장소를 뒤진다 || 서명만 계산
서버 추가 :: 저장소 공유 필요 || 열쇠만 있으면 됨
즉시 로그아웃 :: 지우면 끝 || 만료까지 유효
= 저장소를 없애는 대신 강제 로그아웃을 잃는 거래다
```

전통적인 세션 방식은 서버가 로그인 상태를 기억한다. 서버가 한 대일 때는 문제가 없지만 여러 대로 늘리면 그 기억을 공유해야 한다. 요청이 어느 서버로 갈지 모르기 때문이다.

JWT는 기억을 토큰 쪽으로 옮긴다. 서버는 서명 열쇠만 갖고 있으면 되고, 저장소를 공유할 필요가 없다. 대신 발급한 토큰을 중간에 취소할 수 없다는 문제가 생긴다.

## 🧱 구성

```도해
층: 토큰 세 조각은 각각 무엇인가
헤더 :: 어떤 방식으로 서명했는지
페이로드 :: 사용자 ID, 권한, 만료 시각
서명 :: 앞의 둘을 열쇠로 계산한 값
= 앞의 둘은 누구나 읽을 수 있다. 서명만 못 만든다
```

## ⚙️ 작동 원리

토큰은 점으로 구분된 세 부분이다.

여기가 가장 많이 오해받는 지점이다. 페이로드는 암호화된 게 아니라 그냥 인코딩된 것이라 누구나 열어볼 수 있다. 서명이 막는 것은 **읽기가 아니라 고치기**다.

## 💡 실제 사례

- **API 인증** — 로그인 후 받은 토큰을 헤더에 붙여 보낸다.
- **서비스 간 신뢰** — 게이트웨이가 검증한 사용자 정보를 토큰에 담아 뒤쪽 서비스로 넘긴다.
- **짧은 만료 + 갱신 토큰** — 접근 토큰은 몇 분짜리로 짧게 두고, 갱신 토큰으로 새로 받는다.

## 🚫 흔한 오해

- **JWT의 내용은 암호화되어 있다** — 인코딩일 뿐이라 누구나 열어 읽는다. 비밀번호나 주민번호를 페이로드에 넣으면 그대로 노출된다.
- **로그아웃하면 토큰이 무효가 된다** — 서버가 기억하지 않으므로 만료 전까지 계속 유효하다. 즉시 차단하려면 별도의 차단 목록이 필요하다.
- **JWT가 세션보다 항상 낫다** — 서버가 한두 대면 세션이 더 단순하고 강제 로그아웃도 된다.

## 🚨 주의사항

- **`alg: none` 을 거부한다.** 서명 방식을 토큰이 스스로 정하게 두면 공격자가 서명을 없앤 토큰을 보낼 수 있다. 서버가 허용할 방식을 못 박는다.
- **만료를 짧게 잡는다.** 취소할 수 없으니 유효 기간이 곧 피해 시간이다.

## 📝 정리

JWT는 내용과 서명을 함께 담아 서버가 기억하지 않아도 되게 만든 토큰이다. 서버를 늘리기 쉬워지는 대신 발급한 토큰을 취소할 수 없다.

## ❓ 이해했는지

- 토큰에 비밀번호를 담으면 왜 위험한가 → 작동 원리
- 로그아웃 버튼을 눌러도 토큰이 살아 있는 이유는 → 해결하는 문제
- 서버가 한 대뿐인 서비스에서 세션 대신 JWT를 쓸 이유가 있나 → 흔한 오해
