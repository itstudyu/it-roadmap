# Attribute-Based Access Control (속성으로 정하는 권한)

## 📝 정의

Attribute-Based Access Control은 **꼬리표끼리 맞는지 보고 허락하는 방식**이다.

NIST 는 이것을 "주체·객체·요청된 동작, 때로는 환경 조건에 붙은 속성을 정책·규칙과 견주어 권한을 정하는 논리적 접근 통제 방법론" 으로 적는다. 문장이 길지만 뼈대는 짧다 — **사람 목록도 자원 목록도 적지 않고, 양쪽에 붙은 값이 맞는지만 본다.** AWS 는 그 속성을 태그라고 부르고, Azure 는 역할 할당에 붙이는 조건이라고 부른다.

### 이름
Attribute :: 붙어 있는 성질
Based :: 그것에 기대어
Access :: 들어가는 일
Control :: 통제
= 붙여 읽으면 "붙어 있는 성질에 기대어 출입을 통제". 사람이 아니라 꼬리표를 본다

### 비유
손목 띠 색깔만 보고 태워 주는 놀이공원 — 이름을 묻지 않고 띠와 기구에 적힌 색이 같은지만 본다.

### 예
프로젝트 꼬리표가 같은 사람만 그 자원을 만지게 해 둔 회사가 그렇다. 자원이 새로 생겨도 권한 문서를 안 고친다.

### 직접
사내 계정 화면에서 부서·직급 같은 항목을 찾아보라. 그 값 하나가 바뀌면 열리는 문이 달라지는 곳이 여기다.

## 🖼️ 그림으로 보기

```도해
흐름: 꼬리표만 보고 허락이 나기까지 무엇을 견주나
사람 :: `프로젝트=파랑` 이라는 꼬리표를 달고 온다
자원 :: 열려는 파일에도 프로젝트 꼬리표가 붙어 있다
환경 :: 시각·접속 위치·기기 상태도 값으로 들어온다
정책 :: "두 꼬리표가 같으면 허락" 한 줄과 견준다
판정 :: 같으면 통과, 다르면 거절. 이름 목록은 없다
= 누구인지가 아니라 무엇이 붙어 있는지를 본다. 자원이 늘어도 정책은 그대로다
```

## ⚠️ 해결하는 문제

```도해
대조: 자원이 늘 때마다 권한 문서를 고쳐야 하나
꼬리표 없이 || 꼬리표로
새 자원 추가 :: 정책을 또 고친다 || 안 고쳐도 된다
정책 개수 :: 일마다 하나씩 || 한 줄이면 된다
빠뜨림 :: 고칠 때 새어난다 || 붙일 때 정해진다
= 늘어나는 쪽이 자원이면 손으로 적은 목록은 못 따라간다
```

역할로만 권한을 주면 자원 목록을 역할 안에 적어야 한다. AWS 문서가 든 예가 그렇다 — `Star` 프로젝트에 새 인스턴스를 하나 추가하면, 그 자원 이름을 `Star` 역할 정책에 적어 넣기 전까지는 팀원 누구도 못 만진다. 사람이 셋이고 자원이 셋일 때는 괜찮지만, 자원이 매일 늘어나는 곳에서는 정책 고치기가 병목이 된다.

꼬리표로 바꾸면 그 고리가 끊긴다. 정책은 "사람 꼬리표와 자원 꼬리표가 같으면 허락" 한 줄로 고정되고, 새 자원은 만들 때 꼬리표를 달기만 하면 곧바로 규칙 안으로 들어온다. AWS 는 이것을 "권한이 새 자원과 함께 저절로 늘어난다", "정책 개수가 줄어든다" 로 정리한다. 사람이 팀을 옮길 때도 값 하나만 바꾸면 된다.

## ⚙️ 작동 원리

요청이 오면 판정하는 쪽이 값을 두 묶음 모은다. 주체에 붙은 꼬리표(`aws:PrincipalTag/...`)와 자원에 붙은 꼬리표(`aws:ResourceTag/...`)다. 시각이나 출발지 주소 같은 요청 문맥도 같은 자리에 함께 실린다.

정책의 조건식은 그 값들을 변수로 받아 참·거짓 하나만 낸다. `StringEquals` 로 두 변수를 곧장 맞대 놓으면 정책 문서에는 사람 이름도 자원 이름도 남지 않는다. 적어 둔 목록이 없으니 자원이 늘어도 문서가 늘지 않는다.

판정은 두 단계다. 먼저 역할이 그 동작을 허락하는지 보고, 그다음 조건식이 참인지 본다. 둘 다여야 통과한다. 그래서 꼬리표를 아직 안 단 자원은 맞댈 값이 없어 조건식이 참이 못 되고 그대로 막힌다 — 새로 만든 것의 기본이 닫힘이 되는 자리가 여기다.

## 📊 비교: 세 곳이 같은 것을 뭐라고 부르나

| 곳 | 부르는 이름 | 속성이 어디에서 오나 |
|---|---|---|
| **AWS IAM** | ABAC. 속성을 **태그**라고 부른다 | 주체 태그와 자원 태그. 외부 로그인에서 온 세션 태그도 쓴다 |
| **Azure RBAC** | 역할 할당 **조건** | 주체의 보안 속성, 자원의 인덱스 태그·경로, 환경 값 |
| **Google Cloud IAM** | IAM **조건** | 요청 속성(시각·접근 수준), 자원 속성(종류·이름·태그) |

이름은 달라도 자리가 같다. Azure 문서의 표현이 가장 또렷하다 — 조건은 "역할 할당에 **선택적으로 덧붙이는 추가 검사**" 이고, "역할 정의가 준 권한을 걸러 좁힌다".

## 💡 실제 사례

- **프로젝트별 격리** — AWS 문서가 드는 예가 이것이다. 역할과 자원에 `access-project` 꼬리표를 같은 값으로 달고, 정책은 "값이 같으면 허락" 한 줄만 둔다. 새 프로젝트를 열 때도 정책은 안 고친다.
- **꼬리표로 읽기 범위 좁히기** — Azure 는 역할 할당에 "`Project=Cascade` 꼬리표가 붙은 것만 읽기" 같은 조건을 달아, 이미 준 읽기 권한을 그 꼬리표 안으로 좁힌다.
- **인사 정보 그대로 쓰기** — 바깥 로그인 공급자(SAML·OIDC)가 부서·직급을 세션 꼬리표로 실어 보내면 AWS 가 그 값으로 바로 판정한다. 사람이 부서를 옮기면 권한도 따라 옮겨진다.

## 🚫 흔한 오해

- **꼬리표 방식이 역할 방식보다 낫다** — 둘은 겹쳐 쓰는 물건이다. Azure 문서는 조건을 "역할 할당 위에 덧붙이는 추가 검사" 로 적는다. 역할이 밑바탕이고 꼬리표는 그 위에서 좁힌다.
- **조건을 걸면 권한이 늘어난다** — 반대다. 조건은 이미 준 권한을 걸러 좁힐 뿐이고, Azure 문서는 "조건으로 특정 자원의 접근을 명시적으로 거부할 수는 없다" 고까지 적는다.
- **꼬리표를 달면 관리가 저절로 된다** — 꼬리표를 아무나 고칠 수 있으면 자기 꼬리표를 바꿔 남의 자원을 여는 길이 열린다. 꼬리표를 다는 권한 자체를 따로 잠가야 성립한다.

## 📝 정리

**"양쪽에 붙은 꼬리표가 같은지만 보는 그 규칙"** 이라고 읽으면 된다. 사람 목록도 자원 목록도 안 적으니 자원이 늘어도 정책은 한 줄로 버티지만, 그 대신 꼬리표를 다는 일 자체가 권한을 주는 일이 되어 버린다. 역할을 대체하는 물건이 아니라 역할이 준 것을 좁히는 물건이다.

## 🧒 열 살에게

놀이공원에서 손목에 두른 띠 색이 맞아야 그 기구를 태워 주지? 이름을 확인하는 게 아니라 띠 색만 보는 거야. 그래서 기구가 새로 생겨도 색 규칙은 그대로라 아무것도 안 고쳐도 돼.

## 🔗 관련 용어

- [[RBAC]] — 역할로 주는 밑바탕. 대체가 아니라 그 위에 얹힌다
- [[Resource Tag]] — 자원 쪽 꼬리표를 실제로 다는 물건
- [[IAM]] — 두 꼬리표를 견주는 판정이 벌어지는 자리
- [[Least Privilege]] — 꼬리표로 좁혀서 다다르려는 목표
- [[Conditional Access]] — 같은 조건 판정을 로그인 관문 쪽에서 하는 사촌
