# Identity-Based SSH Access (신원으로 여는 원격 접속)

## 📝 정의

Identity-Based SSH Access는 **열쇠 파일 대신 신원으로 여는 원격 접속**이다.

AWS 문서는 이 방식을 "IAM 정책과 주체로 SSH 접근을 통제해 SSH 키를 나눠 주고 관리할 필요를 없앤다" 로 적는다. Google 은 리눅스 계정을 구글 신원에 붙이는 쪽으로, Azure 는 회사 신원을 인증 기관 삼아 OpenSSH 인증서를 발급하는 쪽으로 같은 일을 한다. SSH 를 버리는 것이 아니라, 문에 미리 붙여 두던 열쇠를 걷어내는 것이다.

### 이름
Identity :: 누구인지를 대는 것
Based :: ~에 기대는
SSH :: 멀리 있는 기계에 붙기
Access :: 들어가 쓰기
= 붙여 읽으면 "신원에 기대어 여는 원격 접속". 기준이 열쇠 파일이 아니라 사람이다

### 비유
열쇠 꾸러미 대신 사원증을 대고 여는 문 — 사원증 하나를 정지시키면 그 순간부터 어느 문도 안 열린다.

### 예
새 팀원이 올 때마다 기계마다 공개키를 붙여 넣고, 나간 사람 것을 지우다 하나를 빼먹던 그 일이다.

### 직접
쓰는 컴퓨터에서 `~/.ssh/authorized_keys` 파일을 한번 열어 보라. 저기 적힌 줄을 지우지 않으면 그 사람은 계속 들어올 수 있다.

## 🖼️ 그림으로 보기

```도해
흐름: 열쇠를 미리 안 심어 뒀는데 어떻게 접속이 열리나
사람 :: 회사 신원으로 먼저 로그인한다
권한 확인 :: 그 기계에 들어갈 역할이 있는지 본다
짧은 증명 :: 그 자리에서 잠깐 쓸 증명을 내준다
< 기계 :: 그 증명을 확인하고 문을 연다
= 열쇠를 미리 심는 게 아니라, 들어갈 자격이 있는지를 그때 묻는다
```

## ⚠️ 해결하는 문제

```도해
대조: 접속용 열쇠를 기계마다 심어 두면 무엇이 위험한가
열쇠를 심어 두면 || 신원으로 열면
나간 사람 :: 기계마다 지운다 || 역할만 뗀다
누가 들어갔나 :: 열쇠 주인만 안다 || 사람 이름이 남는다
안 쓰는 열쇠 :: 그대로 쌓인다 || 쌓일 것이 없다
= 문마다 열쇠를 붙여 두는 대신, 들어갈 때마다 자격을 묻는다
```

기계가 열 대일 때는 공개키를 붙여 넣는 일이 귀찮은 정도지만, 백 대가 되면 그건 못 하는 일이 된다. 더 위험한 것은 지우는 쪽이다. 사람이 나가도 그 사람의 공개키는 붙여 둔 기계에 그대로 남아 있고, 어디에 남았는지는 아무도 완전히 모른다. Azure 문서는 이 상태를 "낡은 SSH 공개키가 번져 무단 접근을 부를 수 있다" 고 적는다.

신원으로 여는 방식은 그 목록을 **기계에서 걷어 신원 쪽으로 옮긴다.** 들어갈 자격은 역할로 정해지고, 접속할 때마다 그 자격이 아직 있는지 확인한다. Google 문서는 로그인 시도마다 권한을 확인하며 "신원에서 권한을 떼면 인스턴스 접근이 사라진다" 고 적고, Azure 문서는 사람이 조직을 떠나 계정이 막히면 그 순간 자원 접근도 끝난다고 적는다. 기계는 한 대도 건드리지 않는다.

## ⚙️ 작동 원리

세 곳이 방법은 다르지만 순서는 같다 — 먼저 신원을 확인하고, 그다음 그 기계에 대한 역할이 있는지 보고, 마지막에 짧게 사는 증명을 만들어 준다.

AWS 의 EC2 Instance Connect 는 접속 순간 SSH 공개키를 인스턴스 메타데이터에 밀어 넣는데, 그 키는 **60초 뒤 사라진다.** 기계의 SSH 데몬은 `AuthorizedKeysCommand` 로 그 메타데이터를 뒤져 키를 찾아 인증한다. 밀어 넣을 권한은 IAM 정책이 정하고, 모든 접속 요청은 CloudTrail 에 남는다.

Google 의 OS Login 은 구글 신원에 POSIX 계정 정보(사용자 이름, 사용자 ID, 홈 디렉터리)를 자동으로 붙여 준다. 역할이 두 갈래인 것이 특징이다 — `roles/compute.osLogin` 은 `sudo` 없는 로그인, `roles/compute.osAdminLogin` 은 `sudo` 있는 로그인이다. 같은 기계에 들어가도 할 수 있는 일이 갈린다.

Azure 는 회사 신원을 인증 기관으로 삼아 OpenSSH 인증서를 발급한다. 가상 머신에는 시스템 할당 관리 ID 와 로그인 확장이 켜져 있어야 하고, 사람에게는 가상 머신 관리자 로그인이나 사용자 로그인 역할이 붙어야 한다. 여기에 조건부 접근을 걸면 접속 시점에 다단계 확인이나 기기 준수 검사까지 요구할 수 있다.

## 📊 비교: 세 클라우드는 이걸 뭐라 부르나

| 어디 | 부르는 이름 | 어떻게 여나 |
|---|---|---|
| **AWS** | EC2 Instance Connect | 공개키를 인스턴스 메타데이터에 밀어 넣고 60초 뒤 사라진다. CloudTrail 에 남는다 |
| **Google Cloud** | OS Login | 구글 신원에 리눅스 계정을 붙인다. `osLogin`(sudo 없음)과 `osAdminLogin`(sudo 있음)으로 갈린다 |
| **Azure** | Microsoft Entra 로그인 + OpenSSH 인증서 | 가상 머신 관리자·사용자 로그인 역할로 정하고, 조건부 접근까지 건다 |

## 💡 실제 사례

- **나간 사람 막기** — Azure 문서는 사람이 조직을 떠나 그 계정이 막히거나 지워지면 그 순간부터 자원에 닿지 못한다고 적는다. 기계를 돌며 공개키를 지우지 않는다.
- **관리자와 일반 사용자 가르기** — Google 은 `osLogin` 과 `osAdminLogin` 으로, Azure 는 가상 머신 사용자 로그인과 관리자 로그인으로 같은 기계 안에서 `sudo` 를 쓸 수 있고 없고를 가른다.
- **접속에도 다단계 확인** — Azure 의 조건부 접근은 접속 시점에 다단계 확인이나 기기 준수 검사를 요구한다. 정책에 걸리는 앱 이름은 Azure Linux VM Sign-In 이다.

## 🚫 흔한 오해

- **기계를 만들 권한이 있으면 그 기계에 들어갈 수도 있다** — 아니다. Azure 문서는 소유자나 기여자 역할이 있어도 SSH 로그인 권한이 자동으로 생기지 않는다고 못 박는다. 기계를 통제하는 사람과 접속하는 사람을 일부러 갈라 놓은 것이다.
- **신원으로 열면 SSH 를 안 쓰는 것이다** — SSH 는 그대로 쓴다. 바뀌는 것은 열쇠를 미리 심어 두느냐, 접속할 때 자격을 확인해 짧은 증명을 내주느냐다.
- **한 번 열어 주면 계속 열려 있다** — Google 은 로그인 시도마다 권한을 확인하고 권한을 떼면 접근이 사라진다. AWS 가 밀어 넣는 공개키는 60초 뒤 없어진다.

## 📝 정리

**"열쇠 대신 사원증으로 여는 원격 접속"** 이라고 읽으면 된다. 들어갈 자격이 기계가 아니라 신원 쪽에 적혀 있어서, 사람을 막을 때 기계를 한 대도 건드리지 않고 접속 기록에도 사람 이름이 남는다. 기계를 만들 권한과 그 기계에 들어갈 권한은 일부러 갈라 놓은 별개의 것이다.

## 🧒 열 살에게

방마다 열쇠를 하나씩 만들어 나눠 주면, 누가 그만두고 나갈 때 그 열쇠를 다 걷어야 하는데 꼭 하나를 빠뜨리지? 그래서 아예 열쇠를 없애고 목에 건 이름표를 문에 대게 만든 거야. 이름표 하나만 정지시키면 그날부터 어느 방도 안 열려.
