# Envelope Encryption (열쇠를 열쇠로 감싸기)

## 📝 정의

Envelope Encryption은 **자료를 잠근 열쇠를 다른 열쇠로 또 잠그는 방식**이다.

Google 문서는 이 말을 아주 짧게 정의한다 — "열쇠를 다른 열쇠로 암호화하는 일". 자료를 직접 잠근 쪽을 자료 암호화 키(DEK), 그 키를 감싸는 쪽을 키 암호화 키(KEK)라 부른다. 감싸는 것을 영어로 wrap 이라 하고, 푸는 것을 unwrap 이라 한다.

### 이름
Envelope :: 편지를 담는 봉투
Encryption :: 잠가서 못 읽게 하기
= 붙여 읽으면 "봉투에 넣어 잠그기". 봉투에 든 것은 자료가 아니라 자료를 잠근 열쇠다

### 비유
집 열쇠를 작은 상자에 넣어 두고, 그 상자 열쇠 하나만 은행 금고에 맡기는 것.

### 예
저장소 설정에서 내 열쇠로 바꿨는데 안에 든 파일을 하나도 다시 잠그지 않고 곧바로 적용되던 그 장면이다.

## 🖼️ 그림으로 보기

```도해
층: 자료 하나를 열려면 열쇠를 몇 겹 풀어야 하나
자료 :: 실제로 잠긴 파일. 크기에 제한이 없다
자료 열쇠 :: 그 파일을 직접 잠근 열쇠. 잠긴 채로 파일 옆에 둔다
감싸는 열쇠 :: 자료 열쇠를 잠그는 열쇠. 금고 밖으로 안 나온다
= 아래로 갈수록 수가 많고, 위로 갈수록 적은 열쇠가 많은 것을 덮는다
```

## ⚠️ 해결하는 문제

```도해
대조: 열쇠 하나로 자료를 직접 다 잠그면 무엇이 막히나
한 열쇠로 직접 || 열쇠를 감싸면
큰 파일 :: 금고가 안 받는다 || 밖에서 잠근다
열쇠 교체 :: 전부 다시 잠근다 || 겉만 다시 잠근다
열쇠 세기 :: 수억 개를 센다 || 몇 개만 센다
= 자료는 밖에서 잠그고, 금고에는 열쇠만 맡긴다
```

열쇠를 맡아 주는 금고는 자료를 통째로 받도록 만들어지지 않았다. Google 문서는 Cloud KMS 가 "KEK 를 관리하도록 설계됐고, 그래서 암·복호화 입력 크기가 최대 64KiB" 라고 못 박는다. 파일이 수 기가바이트면 금고에 넣을 방법 자체가 없다.

봉투 방식은 그 벽을 우회하지 않고 **일을 나눈다.** 자료는 내 쪽에서 자료 열쇠로 잠그고, 금고에는 그 작은 열쇠 하나만 감싸 달라고 맡긴다. 그러면 열쇠는 수억 개여도 금고가 세어야 할 것은 몇 개뿐이다. Google 문서가 이 방식의 이점으로 "DEK 보다 KEK 수가 적고 중앙 키 관리 서비스를 쓰는 편이 대규모 저장·암호화를 다루기 쉽게 만든다" 를 드는 이유가 여기 있다.

## ⚙️ 작동 원리

AWS 에서는 `GenerateDataKey` 를 부른다. 그러면 KMS 가 자료 열쇠를 만들어 **평문 한 벌과 KMS 키로 잠근 암호문 한 벌**을 함께 돌려준다. 평문으로 자료를 잠근 뒤에는 그 평문을 메모리에서 즉시 지우고, 잠긴 열쇠는 잠긴 자료 옆에 그대로 저장한다. 읽을 때는 그 잠긴 열쇠를 KMS 에 보내 풀어 달라고 하고, 돌려받은 평문으로 자료를 풀고 다시 지운다.

여기서 놓치기 쉬운 것은 **금고가 자료 열쇠를 보관하지 않는다**는 점이다. AWS 문서는 "KMS 는 데이터 키를 저장하지도, 관리하지도, 추적하지도 않는다" 고 적는다. 만들어 주고 잠가 주고 풀어 줄 뿐, 보관은 내 몫이다. Google 문서도 같은 자리에서 두 가지를 지시한다 — 자료 열쇠는 **자료 가까이** 두고, 감싸는 열쇠는 **중앙에** 둔다. 그리고 굵게 덧붙인다. 평문 자료 열쇠는 절대 저장하지 마라.

## 📊 비교: 같은 것을 어디서는 뭐라 부르나

| 어디 | 자료를 직접 잠그는 열쇠 | 그것을 감싸는 열쇠 |
|---|---|---|
| **AWS** | 데이터 키. `GenerateDataKey` 가 평문·암호문 두 벌로 준다 | KMS 키. 금고 밖으로 안 나온다 |
| **Google Cloud** | DEK. 내 쪽에서 만들어 자료 옆에 잠긴 채로 둔다 | KEK. Cloud KMS 가 맡고 입력 상한은 64KiB |
| **Azure** | 계정 암호화 키 | 고객 관리 키. `wrapkey`·`unwrapkey` 권한으로 감싸고 푼다 |

## 💡 실제 사례

- **큰 파일 저장** — 금고가 받는 입력 크기가 작아서, 파일은 밖에서 잠그고 그 열쇠만 금고에 감싸 달라고 맡긴다.
- **열쇠 교체** — 겉 열쇠만 새것으로 바꾸면 안에 든 자료를 하나도 다시 잠그지 않고 보호가 바뀐다. Azure 문서는 이때도 자료는 내내 잠긴 상태라고 적는다.
- **잠긴 열쇠를 자료 옆에 두기** — AWS 문서는 잠긴 자료 열쇠를 잠긴 자료와 함께 저장해도 안전하다고 적는다. 자료를 옮기면 그 열쇠도 따라가고, 금고에 남는 일은 풀어 주는 것뿐이다.

## 🚫 흔한 오해

- **두 번 잠갔으니 두 배 안전하다** — 자료를 두 겹으로 덮은 게 아니다. 자료는 한 번만 잠기고, 두 번째 열쇠는 그 첫 열쇠만 잠근다.
- **자료를 그냥 금고에 넣으면 되지 않나** — 금고가 받는 입력에 상한이 있다. Google 의 소프트웨어 키 상한은 64KiB 이고, 금고는 애초에 감싸는 열쇠를 맡으라고 만든 물건이다.
- **자료 열쇠는 금고가 보관해 준다** — 안 해 준다. AWS 문서는 데이터 키를 저장·관리·추적하지 않는다고 못 박는다. 잠긴 열쇠를 자료 옆에 챙겨 두는 것도, 평문 열쇠를 바로 지우는 것도 내가 할 일이다.

## 📝 정리

**"열쇠만 금고에 맡기는 방식"** 이라고 읽으면 된다. 자료는 내 쪽에서 잠그고 금고는 그 열쇠를 감쌀 뿐이라, 파일이 아무리 커도 금고가 감당하고 겉 열쇠만 바꿔도 보호가 통째로 바뀐다. 대신 잠긴 열쇠를 어디에 둘지와 평문 열쇠를 언제 지울지는 내가 지는 몫이다.

## 🧒 열 살에게

장난감 상자에 자물쇠를 채우고, 그 열쇠는 작은 통에 넣어서 엄마한테 맡긴다고 해 봐. 장난감이 아무리 많아도 엄마가 맡는 건 작은 통 하나야. 엄마가 그 통을 안 열어 주면 장난감 상자도 영영 못 열어.
