# SQL Injection (SQL 삽입)

## 📝 정의

SQL Injection은 **입력값이 데이터가 아니라 명령으로 실행되는 공격**이다.

로그인 칸에 아이디 대신 SQL 문법 조각을 넣으면, 서버가 그것을 문자열이 아니라 질의문의 일부로 읽는다. 그러면 비밀번호 없이 로그인하거나 테이블을 통째로 지울 수 있다.

### 비유
받아쓰기와 지시의 혼동. 비서에게 "이 문장을 받아 적어: 모든 서류를 파쇄하라"고 말했는데 비서가 받아 적는 대신 실제로 파쇄해버리는 상황이다.

## 🖼️ 그림으로 보기

```도해
흐름: 아이디 칸에 따옴표를 넣으면 무슨 일이 생기나
공격자 :: 아이디 칸에 `' OR '1'='1` 을 입력한다
서버 :: 입력값을 질의문 문자열에 그대로 이어 붙인다
질의문 :: 조건이 항상 참이 되도록 바뀐다
DB :: 문법상 올바른 질의라 그대로 실행한다
< 공격자 :: 첫 번째 사용자로 로그인된다
= 문제는 입력값이 아니라 문자열을 이어 붙인 방식이다
```

## ⚠️ 해결하는 문제

이 항목은 해결하는 문제가 아니라 **막아야 할 공격**이다.

```도해
대조: 질의문에 사용자 입력을 어떻게 넣나
문자열 이어 붙이기 || 파라미터 바인딩
따옴표 입력 :: 문법이 바뀐다 || 그냥 글자로
DB 가 보는 것 :: 매번 다른 질의문 || 같은 질의문 + 값
방어 :: 필터링에 의존 || 구조상 불가능
= 걸러내는 게 아니라 값과 명령을 애초에 섞지 않는 것이 답이다
```

이 공격이 오래 살아남은 이유는 사람들이 필터링으로 막으려 했기 때문이다. 따옴표를 지우고, 특정 단어를 막고, 특수문자를 걸러낸다. 그런데 우회 방법은 계속 발견된다.

파라미터 바인딩은 방향이 다르다. 질의문의 구조를 먼저 확정하고 값은 나중에 따로 전달한다. DB는 값을 명령으로 해석할 기회 자체가 없다. 필터링이 아니라 구조로 막는 방식이다.

## ⚙️ 작동 원리

```도해
층: 어디서 막을 수 있나
파라미터 바인딩 :: 여기서 막힌다. 유일하게 확실한 층
최소 권한 :: 뚫려도 삭제 권한이 없으면 피해가 준다
입력 검증 :: 도움은 되지만 이것만으로는 못 막는다
= 위층 하나가 제대로면 아래는 보조다. 반대는 성립하지 않는다
```

ORM을 쓰면 대체로 안전하지만 자동으로 안전한 것은 아니다. 원시 질의문을 직접 쓰는 기능이 대부분의 ORM에 있고, 거기서 문자열을 이어 붙이면 똑같이 뚫린다.

## 💡 실제 사례

- **로그인 우회** — 비밀번호 조건이 무력화되어 아무 계정으로나 들어간다.
- **데이터 유출** — 질의문을 합쳐 다른 테이블 내용까지 화면에 출력시킨다.
- **테이블 삭제** — 세미콜론으로 명령을 하나 더 붙여 삭제문을 실행한다.

## 🚫 흔한 오해

- **특수문자를 걸러내면 막힌다** — 우회 방법이 계속 나온다. 인코딩을 바꾸거나 다른 함수를 쓰면 필터를 지나간다.
- **ORM을 쓰면 안전하다** — 원시 질의문 기능에서 문자열을 이어 붙이면 똑같이 뚫린다.
- **내부용 시스템은 괜찮다** — 내부 계정 하나만 뚫려도 그대로 통한다. 공격 경로가 좁을 뿐 없는 게 아니다.

## 🚨 주의사항

- **숫자도 반드시 바인딩한다.** "숫자니까 괜찮다"고 이어 붙이는 실수가 흔하다. 숫자 자리에도 문자열을 넣을 수 있다.
- **DB 계정 권한을 좁힌다.** 웹 서버가 쓰는 계정에 `DROP` 권한이 있을 이유가 없다.

## 📝 정리

SQL Injection은 입력값이 명령으로 실행되는 공격이다. 필터링으로 막으려 하면 계속 우회되고, 파라미터 바인딩으로 값과 명령을 분리하는 것이 유일하게 확실한 방법이다.
