# CSP (Content Security Policy)

## 📝 정의

CSP는 **이 페이지가 무엇을 실어도 되는지 미리 정해 보내는 헤더**다.

W3C 규격은 이것을 "특정 페이지가 가져오거나 실행할 수 있는 자원을 웹 개발자가 통제하는 방법" 으로 적는다. 서버가 응답 헤더에 규칙을 한 줄 실어 보내면, 그 규칙을 집행하는 쪽은 받은 브라우저다. 노리는 것은 [[XSS]] 로 심어진 스크립트가 실제로 하는 일을 줄이는 것이다.

### 이름
Content :: 페이지가 싣는 것
Security :: 지키기
Policy :: 미리 정한 규칙
= 붙여 읽으면 "무엇을 실을지 미리 정해 둔 안전 규칙". 이름이 곧 하는 일이다

### 비유
공연장 출입 명단. 명단에 없는 사람은 아무리 그럴듯하게 차려입고 와도 무대 뒤로 못 들어간다.

### 예
사이트에 붙인 위젯이 화면에 안 나오고 콘솔에만 정책 위반 경고가 찍히던 그 순간이다.

### 직접
개발자 도구의 콘솔을 열어 둔 채 아무 사이트나 새로 고쳐 보라. 막힌 것이 있으면 어느 지시어에 걸렸는지 콘솔이 그 자리에서 말해 준다.

## 🖼️ 그림으로 보기

```도해
대조: 정책이 없는 페이지와 있는 페이지는 무엇이 다른가
정책이 없으면 || 정책이 있으면
실리는 것 :: 끼어든 것도 실린다 || 적어 둔 것만 실린다
심어진 스크립트 :: 그대로 실행된다 || 실행 전에 막힌다
정하는 쪽 :: 정한 적이 없다 || 서버가 미리 정한다
= 무엇을 싣고 실행할지를, 서버가 미리 적어 보낸 목록이 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 입력을 잘 걸러내는데 왜 정책까지 필요한가
거르기만 || 거르기 + 정책
빠뜨린 한 자리 :: 그대로 실행된다 || 실행이 막힌다
새로 만든 화면 :: 매번 다시 검토 || 정책이 그대로 덮는다
뚫렸을 때 :: 피해가 다 난다 || 피해가 줄어든다
= 거르기를 대신하는 것이 아니라, 거르기가 뚫린 뒤에 서 있는 다음 겹이다
```

입력을 거르고 출력을 인코딩하는 것이 1차 방어다. 그런데 화면 하나만 빠뜨려도 그 자리가 통로가 되고, 사람이 손으로 지키는 규칙은 화면이 늘수록 새는 곳이 생긴다.

W3C 규격은 CSP 의 자리를 못 박아 둔다 — **1차 방어선으로 쓰라고 만든 것이 아니라 겹으로 쓰라고 만든 것**이고, 악의적 주입이 일으키는 피해를 줄일 뿐 입력 검증과 출력 인코딩을 대신하지 않는다. MDN 도 같은 말을 반대편에서 한다. 정책을 두는 것은 입력을 정제하는 일의 대안이 아니고, 둘 다 하라는 것이다.

OWASP Top 10 은 2025년판에서 **A02 보안 설정 오류**의 증상 하나로 "서버가 보안 헤더나 지시어를 보내지 않거나, 안전한 값으로 설정하지 않은 경우" 를 든다. 정책을 안 보내는 것 자체가 취약점으로 세어진다.

## ⚙️ 작동 원리

```도해
흐름: 브라우저는 받은 정책을 어떻게 집행하나
서버 :: 응답 헤더에 정책 한 줄을 실어 보낸다
브라우저 :: 지시어마다 허용된 출처를 읽어 둔다
페이지 :: 그림·스크립트·글꼴을 가져오려 한다
브라우저 :: 그 자원이 지시어에 맞는지 견준다
브라우저 :: 안 맞으면 아예 가져오지 않는다
= 정책을 적는 쪽은 서버지만, 집행하는 쪽은 받은 브라우저다
```

정책은 `지시어 값` 꼴을 세미콜론으로 이어 붙인 것이다. `default-src` 는 다른 가져오기 지시어들의 대비책이다 — `img-src` 를 안 적어두면 그림에는 `default-src` 가 적용된다.

`default-src` 나 `script-src` 중 하나라도 있으면 **인라인 자바스크립트가 기본으로 막힌다.** 페이지 안에 직접 쓴 `<script>` 블록, `onclick` 같은 속성 처리기, `javascript:` 주소, `eval()` 에 넘긴 문자열이 전부 여기 해당한다. XSS 가 가장 흔히 지나가는 통로를 통째로 닫아 두는 것이다.

닫아 둔 문을 특정 스크립트에만 열어 주는 방법이 둘 있다. **nonce** 는 응답마다 새로 만든 무작위 값을 헤더와 `<script>` 태그 양쪽에 같이 적어 두는 방식이고, **해시** 는 스크립트 내용의 요약값을 헤더에 적어 두는 방식이다. MDN 은 허용 목록 방식보다 이쪽을 권한다 — 허용 목록은 제대로 맞추기 어렵고 안전하지 않은 도메인이 실수로 끼어들기 쉽기 때문이다.

## 💡 실제 사례

- **인라인 스크립트만 골라 살리기** — 응답마다 새 nonce 를 만들어 헤더와 스크립트 태그에 같은 값을 적는다. 그 값이 없는 스크립트는 안 돈다.
- **끼워 넣기 막기** — `frame-ancestors 'none'` 을 넣으면 남의 화면 안에 내 페이지를 겹쳐 놓는 클릭재킹을 막는다. 끼워 넣기를 허용할 이유가 없으면 이 값이 권고다.
- **막지 않고 먼저 재보기** — `Content-Security-Policy-Report-Only` 로 보내면 실행은 그대로 두고 위반만 보고받는다. 켜기 전에 무엇이 걸릴지 세어 보는 자리다.

## 🚫 흔한 오해

- **정책을 켜면 XSS 가 막힌다** — W3C 는 이것을 1차 방어선이 아니라 겹으로 쓰라고 적는다. 심기는 것을 막는 게 아니라 심긴 것이 할 수 있는 일을 줄인다.
- **입력을 잘 거르면 이건 필요 없다** — MDN 은 정책이 입력 정제의 대안이 아니라고 못 박는다. 둘 중 하나를 고르는 문제가 아니라 둘 다 두는 문제다.
- **일단 `'unsafe-inline'` 을 넣고 시작하면 된다** — MDN 은 그 키워드가 정책을 두는 목적을 대부분 무너뜨린다고 경고한다. 인라인 스크립트가 XSS 의 가장 흔한 통로이기 때문이다.

## 🚨 주의사항

- **nonce 는 응답마다 새로 만든다.** MDN 은 값이 모든 응답에서 달라야 하고 예측할 수 없어야 한다고 적는다. 페이지에 고정해 박아 두면 없느니만 못하다.
- **허용 목록만으로 끝내지 마라.** 도메인을 나열하는 방식은 안전하지 않은 곳이 목록에 섞여 들어가기 쉽다. nonce 나 해시 쪽이 권고다.
- **바로 강제하지 마라.** 보고 전용으로 먼저 켜서 무엇이 걸리는지 본 다음 강제로 옮긴다. 순서를 뒤집으면 멀쩡한 화면이 같이 멈춘다.

## 📝 정리

**"무엇을 실어도 되는지 미리 적어 보낸 그 목록"** 이라고 읽으면 된다. 적는 쪽은 서버고 집행하는 쪽은 브라우저이며, 인라인 스크립트를 기본으로 막고 nonce 나 해시로만 예외를 연다. 거르기를 대신하는 물건이 아니라 거르기가 뚫린 자리에서 피해를 줄이는 다음 겹이다.

## 🧒 열 살에게

공연할 때 무대 뒤로 들어갈 수 있는 사람 이름을 미리 적어서 문에 붙여 두는 거야. 그러면 아무리 진짜처럼 차려입고 와도 그 종이에 이름이 없으면 문 앞에서 돌려보내. 구경하는 사람 틈에 나쁜 사람이 섞여 있어도 무대는 못 건드려.

## ❓ 이해했는지

- 입력을 이미 잘 걸러내고 있는데도 이 헤더를 따로 두는 이유는 무엇인가 → 해결하는 문제
- 인라인 스크립트 하나를 살리려면 응답마다 무엇을 새로 만들어야 하나 → 작동 원리
- 정책이 없는 페이지에서는 몰래 심어진 스크립트가 어떻게 되나 → 그림
