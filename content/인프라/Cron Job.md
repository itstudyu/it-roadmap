# Cron Job (크론 잡)

## 📝 정의

Cron Job은 **정해진 시각마다 명령을 자동 실행하는 예약 작업**이다.

Unix 계열 시스템에는 cron이라는 데몬(화면 없이 배경에서 계속 도는 프로그램)이 늘 떠 있다. 이 데몬이 1분마다 깨어나 시계를 보고, 등록해둔 시각과 맞으면 적어둔 명령을 대신 실행한다.

### 이름
Cron :: 때를 뜻하는 옛말
Job :: 시켜 놓은 일
= 붙여 읽으면 "때가 되면 하는 일". 시간을 뜻하는 그리스말 chronos 에서 왔다는 설이 유력하다

### 비유
알람 시계. 한 번 맞춰두면 매일 그 시각에 알아서 울린다. 맞춰둔 사람이 잊어버려도 울린다.

### 예
매달 같은 날 같은 시각에 오는 요금 안내 문자는 그때마다 사람이 보내는 것이 아니다.

### 직접
맥이나 리눅스에서 터미널을 열고 `crontab -l` 을 쳐 보라. 이 컴퓨터에 등록된 예약 줄이 있으면 시각과 명령이 그대로 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 새벽 2시가 되면 무슨 일이 일어나나
cron :: 1분마다 깨어나 지금 시각을 본다
crontab :: 등록해둔 줄들을 읽는다
비교 :: `0 2 * * *` 와 지금 시각을 맞춰본다
실행 :: 맞으면 그 줄의 명령을 실행한다
기록 :: 결과를 로그에 남기거나 메일로 보낸다
@ cron :: 1분 뒤 다시 깨어나 처음부터 본다
= 매 분 확인하고 맞을 때만 실행한다. 그래서 최소 단위가 1분이다
```

## ⚠️ 해결하는 문제

```도해
대조: 정기 작업을 사람이 직접 하면 어떻게 되나
cron 없이 || cron 으로
새벽 백업 :: 사람이 깨야 함 || 알아서 돈다
실행 시각 :: 매번 달라짐 || 정각에 고정
빠뜨림 :: 휴가면 건너뜀 || 등록하면 계속
= 반복되는 일을 사람의 기억에서 떼어놓는 것이 목적이다
```

매일 자정에 데이터베이스를 백업해야 한다면 누군가 매일 자정에 명령을 쳐야 한다. 휴일에도, 휴가 중에도 마찬가지다. 한 번 빠뜨린 날의 데이터는 되돌릴 방법이 없다.

시각이 흔들리는 것도 문제가 된다. 주간 리포트를 어떤 날은 8시 50분에, 어떤 날은 9시 10분에 만들면 집계 구간이 매번 달라진다. cron은 등록한 시각에만 실행하므로 이 흔들림이 없어진다.

## ⚙️ 작동 원리

crontab에 한 줄을 등록하면 된다. 앞의 다섯 칸이 시각이고 그 뒤가 실행할 명령이다.

```
분  시  일  월  요일   명령
0   9   *   *   1     /usr/local/bin/report.sh
```

- `*` 모든 값
- `,` 여러 값 (`1,3,5`)
- `-` 범위 (`1-5`)
- `/` 간격 (`*/5` 는 5분마다)

위 줄은 매주 월요일 오전 9시를 뜻한다. `0 2 * * *` 는 매일 새벽 2시, `0 0 1 * *` 는 매월 1일 자정이다. 등록은 `crontab -e`, 목록 확인은 `crontab -l` 로 한다.

다섯 칸이 전부 맞아야 실행된다. 하나라도 어긋나면 그 분은 넘어가고, cron은 다음 분에 처음부터 다시 확인한다.

## 📊 비교: 예약 실행 vs 이벤트 기반

| | Cron Job | 이벤트 기반 |
|---|---|---|
| 언제 실행 | 정해진 시각 | 일이 생긴 순간 |
| 등록 | 한 줄 | 수신기를 만들어야 함 |
| 최소 간격 | 1분 | 제한 없음 |

## 💡 실제 사례

- **매일 백업** — 자정에 데이터베이스를 덤프해 압축하고 원격 저장소로 올린다.
- **주간 리포트** — 월요일 오전 9시에 지난주 집계를 만들어 메일로 보낸다.
- **로그 정리** — 새벽 3시에 30일이 지난 로그 파일을 지워 디스크를 비운다.

## 🚫 흔한 오해

- **cron으로 초 단위 작업도 만든다** — 확인 주기가 1분이라 그보다 잦게는 못 돈다. 초 단위가 필요하면 다른 도구를 써야 한다.
- **터미널에서 됐으니 cron에서도 된다** — cron은 로그인 환경의 환경 변수를 물려받지 않는다. 명령을 전체 경로로 적지 않으면 못 찾는 일이 흔하다.
- **실패하면 알아서 다시 해준다** — 재시도가 없다. 실패한 회차는 그냥 지나가고 다음 시각이 되면 새로 실행될 뿐이다.

## 🚨 주의사항

- **출력을 어디로 보낼지 정해둔다.** 결과가 아무 데도 남지 않으면 언제부터 안 돌았는지 알 방법이 없다.
- **서버가 여러 대면 같은 작업이 여러 번 돈다.** 대수만큼 백업이 뜨거나 같은 메일이 중복으로 나간다.
- **`crontab -r` 은 묻지 않고 전부 지운다.** 편집하려던 `-e` 대신 눌리기 쉬우니 `-l` 로 먼저 확인하는 편이 안전하다.

## 📝 정리

**"때가 되면 알아서 울리는 그 알람"** 이라고 읽으면 된다. 데몬이 매 분 시계와 등록된 표현식을 맞춰보고 일치할 때만 실행하며, 실패한 회차를 다시 시도하지는 않는다.

## 🧒 열 살에게

알람을 한 번 맞춰 두면 네가 까맣게 잊어도 매일 그 시각에 울리지? 컴퓨터한테도 시각을 적어 주면 밤 열두 시가 될 때마다 시켜 둔 일을 혼자 해 둬. 대신 그 시각에 못 했다고 나중에 따로 챙겨 주지는 않고 그냥 넘어가.

## ❓ 이해했는지

- 30초마다 도는 작업을 cron으로 만들 수 없는 이유는 → 그림
- 터미널에서 잘 되던 스크립트가 cron에서만 실패하는 흔한 이유는 → 흔한 오해
- `0 9 * * 1` 로 등록하면 언제 실행되나 → 작동 원리
