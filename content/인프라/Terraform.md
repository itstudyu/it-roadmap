# Terraform (테라폼)

## 📝 정의

Terraform 은 **원하는 인프라를 적어 두면 그대로 만들어 주는 도구**다.

HashiCorp 문서는 이것을 "클라우드와 온프레미스 자원을 안전하고 효율적으로 만들고 바꾸고 버전 관리하게 해 주는 코드형 인프라 도구" 로 적는다. 사람이 읽을 수 있는 설정 파일에 자원을 정의해 두면, 그 파일을 버전으로 남기고 재사용하고 나눠 쓸 수 있다.

### 이름
Terra :: 땅
form :: 모양을 잡다
= 붙여 읽으면 "땅을 살 만하게 고쳐 만든다". 서비스가 올라설 바닥을 만드는 일이다

### 비유
장보기 쪽지. 우유 두 개라고 적어 두면 냉장고에 하나 있을 때 하나만 더 사 오지, 무조건 두 개를 더 사 오지 않는다.

### 예
적용 단추를 누르기 전에 무엇이 새로 생기고 무엇이 지워지는지를 목록으로 먼저 보여 주는 그 화면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 적어 둔 대로 인프라가 만들어지기까지 무엇을 거치나
설정 파일 :: 원하는 최종 모습을 적는다
상태 파일 :: 지금 실제로 무엇이 있는지 적혀 있다
plan :: 둘을 견줘 할 일 목록을 뽑는다
사람 :: 그 목록을 보고 승인한다
apply :: 의존 순서를 지켜 실제로 만든다
< 상태 파일 :: 만들어진 것을 받아 기록에 적는다
= 원하는 모습과 지금 모습의 차이만큼만 움직인다
```

## ⚠️ 해결하는 문제

```도해
대조: 인프라를 손으로 고칠 때와 무엇이 다른가
손으로 || Terraform 으로
바꾸기 전 :: 해 봐야 안다 || 목록을 먼저 본다
지금 상태 :: 아무도 모른다 || 상태 파일에 있다
같은 걸 또 :: 처음부터 다시 || 파일을 복제한다
= 무엇이 있는지 적어 두었기에, 무엇이 달라질지 미리 말해 줄 수 있다
```

콘솔에서 자원을 만들면 그 결과가 어디에도 정리되지 않는다. 무엇이 무엇에 딸려 있는지, 지우면 무엇이 같이 죽는지를 아는 사람은 그때 만든 사람뿐이다. 그래서 인프라 변경은 늘 "해 보고 확인하는" 일이 된다.

Terraform 은 설정과 실제 자원 사이의 짝을 **상태 파일**에 적어 둔다. HashiCorp 문서는 상태의 첫째 목적을 "원격 시스템의 객체와 설정에 선언된 자원 인스턴스 사이의 결합을 저장하는 것" 이라 적고, 이 결합 덕에 나중에 그 객체를 고치거나 지울 수 있다고 말한다. 지금 무엇이 있는지 적혀 있으니, 적용 전에 무엇이 달라질지도 계산해서 보여 줄 수 있다.

## ⚙️ 작동 원리

일하는 순서는 셋이다. **Write** 에서 여러 클라우드와 서비스에 걸친 자원을 정의하고, **Plan** 에서 Terraform 이 기존 인프라와 내 설정을 근거로 무엇을 만들고 바꾸고 지울지 실행 계획을 만들고, **Apply** 에서 승인이 나면 자원 의존 관계를 지킨 올바른 순서로 그 작업을 수행한다. Google Cloud 문서는 계획 단계를 "설정을 평가해 실행 계획을 생성한다" 로, 적용 단계를 "실행 계획에 따라 뒤에서 해당하는 Google Cloud API 를 호출해 인프라를 프로비저닝한다" 로 적는다.

붙는 대상은 **프로바이더**가 정한다. 프로바이더는 접근 가능한 API 를 가진 거의 모든 플랫폼·서비스와 Terraform 을 이어 주는 플러그인이고, HashiCorp 와 커뮤니티가 이미 수천 개를 만들어 두었다. AWS 를 다루든 [[Kubernetes]] 를 다루든 설정 문법은 그대로고 프로바이더만 갈아 끼운다.

계산의 근거는 **상태 파일**이다. 실제 자원과 설정을 짝지어 두고, 메타데이터를 기억하고, 자원이 많을 때 성능을 낸다. 어떤 작업을 하기 전에 Terraform 은 새로 고침을 먼저 돌려 상태와 실제를 맞춘다 — 밖에서 손으로 바뀐 것이 여기서 드러난다.

## 🚨 주의사항

- **상태 파일을 아무 데나 두지 마라.** HashiCorp 문서는 상태를 원격 백엔드에 두어 안전하게 보관하고 팀과 함께 쓰기를 권하고, 상태 잠금과 접근 통제를 지원하지 않는 저장소에 두면 자료 유실이나 상태 파일에 든 비밀 노출로 이어질 수 있다고 경고한다.
- **적용 계획을 눈으로 읽어라.** 값 하나를 바꾼 것이 제자리 수정이 아니라 자원 교체로 잡히기도 한다. 원격 API 가 그 항목의 수정을 받지 않으면 지우고 새로 만드는 수밖에 없기 때문이다. 계획 단계는 그걸 미리 보라고 있는 자리다.
- **밖에서 손대면 다음 적용이 되돌린다.** 콘솔에서 고친 값은 설정 파일에 없으므로, 새로 고침 뒤 "적힌 대로" 돌려놓는 계획이 나온다.

## 💡 실제 사례

- **환경을 통째로 복제한다** — 같은 설정에 변수만 바꿔 개발·스테이징·운영을 같은 모양으로 세운다.
- **여러 서비스를 한 벌로 묶는다** — 서로 다른 클라우드와 서비스의 자원을 한 설정에 정의하고, 적용은 의존 순서대로 한 번에 한다.
- **지울 때도 목록으로 본다** — 실험용 환경을 걷을 때 무엇이 함께 지워지는지 계획으로 먼저 확인하고 내린다.

## 🚫 흔한 오해

- **Terraform 을 쓰면 서버 안까지 다 관리된다** — 자원을 만들어 세우는 데까지가 이 도구의 자리다. 그 안에 무엇을 깔고 어떤 설정 파일을 놓을지는 [[Ansible]] 같은 설정 관리 쪽이 맡는 편이 보통이다.
- **설정 파일만 있으면 상태 파일은 없어도 된다** — 상태는 설정과 실제 객체를 잇는 짝이다. 이게 없으면 도구는 이미 만들어 둔 것을 알아보지 못하고 처음부터 만들려 든다.
- **인프라는 Terraform 하나로 통일하는 편이 항상 낫다** — 이미 관리 도구가 붙어 있는 자원까지 끌어오면 짝을 맞추는 일만 늘어난다. 여러 벌을 반복해 세울 자원부터 옮기고, 한 벌뿐인 것은 굳이 옮기지 않아도 된다.

## 📝 정리

**"적어 둔 모습과 지금 모습의 차이만큼 움직이는 도구"** 라고 읽으면 된다. 무엇이 있는지를 상태 파일에 적어 두기 때문에, 적용 전에 무엇이 생기고 무엇이 지워질지를 목록으로 먼저 보여 줄 수 있다. 그래서 이 도구를 쓸 때 가장 중요한 습관은 계획을 눈으로 읽는 것과, 상태 파일을 잃지 않는 것이다.

## 🧒 열 살에게

엄마가 준 장보기 쪽지에 우유 두 개라고 적혀 있어. 집에 이미 하나가 있으면 하나만 더 사 오면 되지? 쪽지랑 냉장고를 맞춰 보고 모자란 것만 사 오는데, 사러 가기 전에 "이만큼 살게" 하고 먼저 말해 주는 심부름꾼이 있는 거야.
