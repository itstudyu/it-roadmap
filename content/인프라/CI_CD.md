# CI/CD

## 📝 정의

CI/CD는 소프트웨어 개발 과정을 자동화하여 개발자가 작성한 코드를 빠르고 안정적으로 운영 환경에 배포하는 방식입니다. CI(Continuous Integration, 지속적 통합)는 개발자들이 작성한 코드를 중앙 저장소에 자주 통합하고, 자동으로 빌드와 테스트를 수행합니다. CD(Continuous Delivery/Deployment, 지속적 전달/배포)는 테스트를 통과한 코드를 자동으로 또는 수동 승인을 거쳐 운영 환경에 배포합니다.

> **한 줄 요약**: 코드 변경 → 자동 빌드/테스트 → 자동/수동 배포의 반복 프로세스

**비유 1**: 공장의 컨베이어 벨트 같이, 제품이 계속 생산되고 자동으로 품질 검사를 거친 후 출하됩니다.

**비유 2**: 음악을 작곡한 후 즉시 자동으로 음질 검사를 거쳐 스트리밍 서비스에 배포하는 것처럼, 코드도 지속적으로 품질 보증과 함께 배포됩니다.

---

## 🎯 핵심 개념

### 1. Continuous Integration (CI)
소스 코드 저장소(Git)에 코드가 push될 때마다 자동으로 빌드, 컴파일, 테스트가 실행되는 과정입니다. 개발자들의 작업 충돌을 조기에 발견하고 품질 문제를 빠르게 파악할 수 있습니다.

### 2. Continuous Delivery/Deployment (CD)
CI를 통과한 코드를 스테이징(테스트) 환경과 운영 환경으로 자동으로 배포하는 과정입니다. Delivery는 수동 승인 후 배포, Deployment는 완전 자동 배포를 의미합니다.

### 3. 자동화 파이프라인
코드 push → 빌드 → 단위 테스트 → 통합 테스트 → 스테이징 배포 → 운영 배포의 전체 과정을 자동화하여 수동 개입을 최소화합니다.

## ⚠️ 해결하는 문제

### 문제 1: 배포 속도와 안정성의 trade-off
수동 배포는 느리고 실수가 많지만, CI/CD는 자동화를 통해 빠르면서도 안정적인 배포를 가능하게 합니다.

### 문제 2: 코드 품질 관리
통합되지 않은 코드의 문제는 운영 환경에서 발견되어 비용이 증가하지만, CI는 즉시 문제를 감지합니다.

### 문제 3: 배포 간 시간 격차
릴리즈 주기가 길수록 변경 사항이 많아져 위험이 증가하지만, CI/CD는 자주, 작은 단위로 배포하여 위험을 줄입니다.

## 🏗️ 구조


```도해

Dev :: 코드 Push
Git 저장소 :: Webhook 트리거
CI 서버 :: 빌드 및 테스트 실행
CI 서버 :: 테스트 통과 시 배포
스테이징 :: 최종 검증
CI 서버 :: 승인 후 배포
운영 환경 :: 모니터링
```

## ⚙️ 작동 원리

1. **코드 변경 감지**: 개발자가 코드를 저장소(GitHub, GitLab)에 push하면 webhook이 CI 서버를 자동으로 트리거합니다.

2. **자동 빌드**: CI 서버가 코드를 체크아웃하여 컴파일, 의존성 설치, 빌드를 수행합니다.

3. **자동 테스트**: 단위 테스트, 통합 테스트, 성능 테스트 등이 자동으로 실행됩니다.

4. **테스트 결과 판단**: 모든 테스트가 통과하면 다음 단계로 진행하고, 실패하면 개발자에게 알림을 보냅니다.

5. **배포**: 스테이징 환경에 자동 배포 후 수동 검증을 거쳐 운영 환경에 배포합니다.

6. **모니터링**: 배포 후 로그, 성능, 에러를 실시간으로 모니터링합니다.

## 📊 비교

| 항목 | CI | CD | DevOps |
|------|----|----|--------|
| **목표** | 코드 통합 및 테스트 자동화 | 배포 자동화 | 개발과 운영의 통합 |
| **범위** | 빌드/테스트 단계 | 배포 단계 | 전체 개발/운영 라이프사이클 |
| **배포 방식** | 자동화 없음 | 자동 또는 수동 승인 | 완전 자동화 |
| **피드백 주기** | 수 분 | 수 시간 | 즉시 |
| **주요 도구** | Jenkins, GitHub Actions | Spinnaker, Argo CD | Kubernetes, Terraform |
| **실패 처리** | 빌드 실패 알림 | 배포 실패 시 자동 롤백 | 무중단 배포 |
| **문화적 영향** | 개발팀 중심 | 개발 + QA 협업 | 개발 + 운영 완전 통합 |
| **비용** | 낮음 | 중간 | 높음 (자동화 도구/인력) |

## ✅ 장단점

### 장점
- **빠른 배포**: 자동화로 인한 배포 시간 단축 (주 단위 → 일 단위 또는 시간 단위)
- **높은 품질**: 자동 테스트로 버그를 조기에 발견
- **낮은 배포 위험**: 작은 단위의 자주 배포로 문제 추적이 쉬움
- **개발 생산성 향상**: 반복적인 빌드/테스트 작업 자동화로 개발자 집중력 증대
- **빠른 피드백**: 코드 변경의 결과를 수 분 내에 확인 가능

### 단점
- **초기 구축 비용**: CI/CD 인프라 구축과 설정에 시간/비용 필요
- **테스트 커버리지 의존성**: 자동 테스트가 충분하지 않으면 효과 제한
- **복잡한 모니터링**: 배포 후 문제 추적 및 모니터링이 어려워질 수 있음
- **학습 곡선**: 팀의 프로세스 변화와 도구 학습 필요
- **초기 생산성 저하**: 도입 초기에는 설정과 학습으로 인한 생산성 저하

## 💡 실제 사례

### Case 1: GitHub Actions로 자동 테스트 및 배포
개발자가 Pull Request를 생성하면 GitHub Actions가 자동으로 테스트를 실행하고, main 브랜치로 merge되면 자동으로 AWS S3와 CloudFront에 배포하는 정적 웹사이트 호스팅 사례입니다.

### Case 2: Jenkins와 Docker를 활용한 마이크로서비스 배포
대규모 회사에서 Jenkins를 중앙 빌드 서버로 사용하여 수십 개의 마이크로서비스를 자동으로 빌드/테스트하고, Docker 이미지로 생성한 후 Kubernetes에 배포하는 사례입니다.

### Case 3: GitLab CI/CD와 자동 성능 테스트
GitLab CI를 사용하여 코드 push 시 자동 빌드, 테스트, 성능 벤치마크를 수행하고, 성능 저하 시 자동으로 배포를 차단하는 품질 보증 사례입니다.

## 🔗 관련 용어

- **Continuous Monitoring**: 배포 후 실시간으로 시스템 상태, 로그, 에러를 모니터링
- **Infrastructure as Code (IaC)**: 인프라를 코드로 관리하여 CI/CD와 함께 배포 자동화
- **Blue-Green Deployment**: 기존 버전(Blue)과 새 버전(Green)을 동시에 운영 후 전환
- **Canary Deployment**: 새 버전을 일부 사용자에게만 배포하여 점진적으로 확대
- **Rollback**: 배포 후 문제 발생 시 이전 버전으로 자동 복구
