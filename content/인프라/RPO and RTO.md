# RPO and RTO (얼마까지 잃어도 되나와 얼마 만에 살아나나)

## 📝 정의

RPO 와 RTO 는 **사고 때 어디까지 참을지 미리 정해 둔 두 숫자**다.

AWS Well-Architected 문서의 정의는 짧다. RTO 는 서비스가 끊긴 때부터 다시 살아날 때까지 참을 수 있는 최대 지연이고, RPO 는 마지막으로 되살릴 수 있는 지점 이후로 참을 수 있는 최대 시간이다. 하나는 사고 시각의 왼쪽을 재고 하나는 오른쪽을 잰다. 그래서 둘은 같은 사고를 놓고 서로 다른 것을 묻는다.

### 이름
Recovery :: 되살리기
Point :: 어느 시점까지
Time :: 얼마 동안
Objective :: 목표로 삼은 값
= 앞은 "되살릴 시점의 목표", 뒤는 "되살리는 데 걸릴 시간의 목표". 둘 다 약속한 숫자다

### 비유
자동 저장이 걸린 게임. 마지막 저장 뒤에 한 것은 날아가고, 다시 켜서 이어 하기까지는 또 얼마쯤 걸린다.

### 예
장애 공지에 "일부 자료가 유실되었습니다" 와 "복구까지 4시간 예상" 이 나란히 적혀 있던 그 화면이다.

### 직접
폰의 사진 자동 백업 설정을 열어 "마지막 백업" 시각을 보라. 지금 폰을 잃어버리면 잃는 것이 딱 그 시각 이후의 사진들이다.

## 🖼️ 그림으로 보기

```도해
흐름: 사고 하나를 놓고 두 숫자는 각각 어디를 재나
마지막 저장 :: 여기까지는 안전하다
그 뒤 :: 여기서 만든 것이 잃을 몫이다
사고 :: 여기서 멈춘다. 앞 숫자는 여기서 끝난다
되살리기 :: 터를 세우고 자료를 되돌린다
다시 열림 :: 사고부터 여기까지가 뒤 숫자다
= 앞 숫자는 사고 왼쪽의 잃는 양, 뒤 숫자는 오른쪽의 멈춘 시간이다
```

## ⚠️ 해결하는 문제

```도해
대조: 두 숫자를 정해 두지 않으면 무엇이 달라지나
안 정해 두면 || 숫자로 정하면
얼마나 쓸지 :: 감으로 고른다 || 값이 따라 나온다
사고 났을 때 :: 언제 끝날지 모른다 || 약속한 시각이 있다
훈련 :: 무엇을 재는지 없다 || 넘겼는지 잰다
= 목표가 숫자가 아니면 대비가 충분한지 아무도 판정할 수 없다
```

"안전하게 해 주세요" 는 살 수 없는 물건이다. 대비는 단계마다 값이 다르고, 어느 단계를 살지는 멈췄을 때 얼마를 잃느냐로만 정해진다. 숫자가 없으면 그 자리에서 이야기가 멈추고, 대개 감으로 고르게 된다.

두 숫자는 그 대화를 **맞바꿈으로 바꾼다**. AWS 문서는 잘못된 패턴으로 아무렇게나 정하기, 잃음도 멈춤도 0으로 정하기, 실제 사업 목표보다 빡빡하게 정하기를 함께 꼽는다. 마지막이 특히 값비싸다 — 필요보다 짧은 시간을 적으면 그만큼 비싸고 복잡한 구조를 억지로 세우게 된다. Google 문서도 두 값을 줄일수록 값과 손이 급하게 늘어난다고 적는다.

## 📊 비교: 두 숫자는 무엇이 다른가

| | 앞 숫자 (RPO) | 뒤 숫자 (RTO) |
|---|---|---|
| **재는 것** | 잃어도 되는 자료의 양 | 멈춰도 되는 시간 |
| **시간축** | 사고 왼쪽 | 사고 오른쪽 |
| **줄이려면** | 더 자주, 끊임없이 복사한다 | 예비를 더 많이 켜 둔다 |
| **0 으로 만들면** | 모든 쓰기를 두 곳에 동시에 | 두 곳이 늘 손님을 받아야 |

## 💡 실제 사례

- **등급표로 나눠 적기** — 일감마다 따로 정하지 않고 중요도 등급을 몇 개 만들어, 등급마다 두 숫자를 적어 둔다. 새 일감은 등급만 고르면 목표가 따라온다.
- **딸린 쪽까지 따져 보기** — 내가 30분을 약속해도 내가 기대는 쪽이 4시간이면 그 약속은 못 지킨다. 아래쪽 목표를 먼저 확인해야 내 숫자가 성립한다.
- **때에 따라 다르게 잡기** — 명절 대목이나 큰 출시 날처럼 멈추면 손해가 커지는 기간에는 같은 일감에도 더 빡빡한 숫자를 건다.

## 🚫 흔한 오해

- **둘 다 0 으로 잡아 두면 제일 좋다** — AWS 문서는 그것을 잘못된 패턴으로 꼽는다. 못 지킬 목표를 적으면 값만 오르고, 지켰는지 판정도 안 된다.
- **백업을 자주 하면 두 숫자가 같이 좋아진다** — 자주 뜨는 백업은 앞 숫자만 줄인다. 되살리는 데 세 시간 걸리면 뒤 숫자는 그대로 세 시간이다.
- **이건 기술팀이 정하는 값이다** — 멈췄을 때 얼마를 잃는지는 장사하는 쪽이 안다. 기술이 하는 일은 그 목표가 지금 구조로 가능한지, 얼마면 가능한지를 되말해 주는 것이다.

## 📝 정리

**"얼마까지 잃어도 되고 얼마 만에 돌아와야 하나"** 라고 읽으면 된다. 앞 숫자는 사고 왼쪽의 잃는 양이고 뒤 숫자는 오른쪽의 멈춘 시간이며, 둘을 줄일수록 값이 가파르게 오른다. 그래서 이 둘은 기술 결정이기 전에 얼마를 낼지의 결정이다.

## 🧒 열 살에게

게임을 하다 갑자기 꺼지면 마지막으로 저장한 데까지만 남아 있지? 저장을 자주 할수록 덜 잃지만 그만큼 자주 멈춰서 저장해야 해. 그리고 다시 켜서 이어 하기까지 걸리는 시간은 그것과 또 다른 이야기야.

## ❓ 이해했는지

- 백업 주기를 10분에서 1분으로 줄였는데 뒤 숫자는 왜 그대로인가 → 흔한 오해
- 내가 30분을 약속해 두고도 못 지키게 되는 경우는 언제인가 → 실제 사례
- 두 숫자 중 사고보다 앞쪽을 재는 것은 어느 쪽이고 왜 그런가 → 그림
