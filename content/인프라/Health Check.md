# Health Check (헬스 체크)

## 📝 정의

Health Check는 **멀쩡한지 주기마다 물어 걸러 내는 짧은 확인**이다.

묻는 쪽은 사람이 아니라 기계다. 로드 밸런서는 등록된 대상에게, 쿠버네티스의 kubelet 은 컨테이너에게 정해진 간격마다 같은 질문을 던지고, 그 답에 따라 요청을 보낼지 말지 또는 다시 띄울지를 스스로 정한다.

### 이름
Health :: 멀쩡한 상태
Check :: 맞는지 확인
= 붙여 읽으면 "멀쩡한지 확인". 그 확인을 사람이 아니라 기계가 주기마다 대신 한다

### 비유
출석 부르기. 이름을 불러 대답이 없는 사람은 오늘 명단에서 빼고, 대답이 다시 돌아오면 도로 넣는다.

### 예
새 버전을 올린 직후 몇 초 동안만 오류가 나다가 저절로 멎는 일을 겪어 봤을 것이다. 아직 준비 안 된 쪽으로 요청이 들어갔던 그 몇 초다.

## 🖼️ 그림으로 보기

```도해
흐름: 헬스 체크는 답이 없는 대상을 어떻게 걸러내나
설정 :: 간격·제한 시간·연속 횟수를 미리 정한다
검사자 :: 그 간격마다 정한 주소로 물어본다
대상 :: 멀쩡하면 성공 코드를, 아니면 실패를 답한다
< 판정 :: 연속 실패면 빼고, 연속 성공이면 도로 넣는다
= 한 번 실패로 빼지 않는다. 연속 몇 번인가가 빼고 넣는 기준이다
```

## ⚠️ 해결하는 문제

```도해
대조: 죽은 대상을 걸러내지 않으면 어떻게 되나
확인 없이 || 헬스 체크로
죽은 한 대 :: 그리로도 보낸다 || 목록에서 빠진다
뜨는 중 :: 준비 전에 받는다 || 준비되면 받는다
멈춘 채 살아있음 :: 영영 그대로다 || 다시 띄운다
= 켜져 있는 것과 일할 수 있는 것은 다르다. 그 둘을 갈라 주는 것이 헬스 체크다
```

여러 대로 늘려 두어도 그중 한 대가 죽으면 그 한 대로 간 요청은 그대로 실패한다. 대상이 켜져 있다는 사실만으로는 부족하다 — 아직 뜨는 중이라 받을 수 없는 것, 교착에 걸려 살아만 있는 것은 겉보기에 멀쩡하다.

헬스 체크는 **"켜져 있나" 대신 "지금 일할 수 있나" 를 묻는다**. 대답이 정한 횟수만큼 연달아 없으면 목록에서 빼고 남은 대상으로만 보낸다. 확인 종류에 따라 요청만 끊기도 하고, 아예 다시 띄우기도 한다.

## ⚙️ 작동 원리

묻는 방법은 몇 가지 중 하나를 고른다. 쿠버네티스는 넷을 둔다 — `httpGet` 은 정한 경로로 요청해 200~399 가 오면 성공으로 보고, `exec` 는 컨테이너 안에서 명령을 돌려 종료 코드 0 이면 성공, `tcpSocket` 은 포트가 열려 있는지, `grpc` 는 상태가 `SERVING` 인지 본다. 프로브 하나는 이 중 정확히 하나만 쓴다.

판정은 한 번으로 하지 않는다. Application Load Balancer 를 예로 들면, 대상이 인스턴스나 IP 일 때 간격(`HealthCheckIntervalSeconds`)은 기본 30초이고 응답이 없다고 볼 제한 시간(`HealthCheckTimeoutSeconds`)은 기본 5초다. 연속 실패가 `UnhealthyThresholdCount`(기본 2회)를 넘기면 대상을 목록에서 빼고, 연속 성공이 `HealthyThresholdCount`(기본 5회)를 넘기면 도로 넣는다. 어떤 응답 코드를 성공으로 볼지도 따로 정한다.

실패했을 때 하는 일은 확인 종류가 정한다. 쿠버네티스에서 살아 있음(liveness) 확인이 실패하면 kubelet 이 그 컨테이너를 죽이고, 그다음은 컨테이너의 재시작 정책이 맡는다. 준비됨(readiness) 확인이 실패하면 파드의 주소를 목록에서 빼서 요청만 끊는다. 죽이지는 않는다. 시작(startup) 확인은 뜨는 동안만 도는데, 이것이 성공하기 전에는 나머지 둘을 아예 돌리지 않는다.

## 📊 비교: 쿠버네티스의 세 확인은 무엇이 다른가

| 확인 | 무엇을 묻나 | 실패하면 |
|---|---|---|
| **startup** | 다 떴나 | 뜨기를 포기하고 죽인다. 재시작 정책이 이어받는다 |
| **liveness** | 아직 일하고 있나 | 죽인다. 재시작 정책이 이어받는다 |
| **readiness** | 지금 받아도 되나 | 요청만 끊는다. 죽이지는 않는다 |

시작 확인이 성공하기 전에는 나머지 둘이 돌지 않는다. 살아 있음 확인은 교착처럼 돌고는 있는데 나아가지 못하는 상태를 잡는 자리이고, 준비됨 확인은 시작 준비나 잠깐의 장애 회복처럼 곧 돌아올 상태를 다루는 자리다.

## 💡 실제 사례

- **무중단 배포** — 새로 뜬 쪽은 준비됨 확인을 통과하기 전까지 요청을 받지 않는다. 통과한 뒤에야 목록에 들어간다.
- **한 대만 죽었을 때** — 로드 밸런서가 그 대상만 빼고 남은 대상으로 보낸다. 쓰는 사람 쪽에서는 아무 일도 일어나지 않는다.
- **멈춘 채 살아 있는 것 잡기** — 교착에 걸려 응답만 못 하는 컨테이너는 살아 있음 확인이 걸러 낸다. 그다음은 재시작 정책이 맡는다.

## 🚫 흔한 오해

- **한 번 실패하면 바로 빠진다** — 아니다. 기준은 연속 횟수다. Application Load Balancer 기본값으로는 연속 2회 실패해야 빠지고, 도로 넣으려면 연속 5회 성공해야 한다.
- **살아 있음 확인 하나면 충분하다** — 둘은 실패했을 때 하는 일이 다르다. 살아 있음이 실패하면 컨테이너를 죽여 재시작 정책에 넘기고, 준비됨이 실패하면 요청만 끊는다. 잠깐 못 받을 뿐인 상태를 살아 있음으로 재면 곧 돌아올 것을 계속 죽이게 된다.
- **대상이 다 죽으면 요청을 막아 준다** — 반대다. 대상 그룹에 비정상 대상만 남으면 로드 밸런서는 상태와 상관없이 모든 대상으로 요청을 보낸다. 열린 채로 실패한다고 해서 fail-open 이라 부른다.

## 🚨 주의사항

- **빠지기까지 걸리는 시간은 간격 곱하기 횟수다.** ALB 에 인스턴스를 붙인 기본값이면 30초 간격에 연속 2회이므로, 죽은 대상이 목록에서 빠지기까지 1분 남짓이 흐른다. 더 빨리 빼려면 간격과 횟수를 함께 줄인다.
- **뜨는 데 오래 걸리는 앱에는 시작 확인을 건다.** 시작 확인이 성공하기 전에는 나머지 둘이 돌지 않는다. 이걸 안 걸면 아직 뜨는 중인 컨테이너를 살아 있음 확인이 죽이고, 다시 뜨는 동안 또 죽인다.
- **전부 죽었을 때의 동작을 미리 안다.** 모든 대상이 동시에 실패하면 로드 밸런서가 열린 채로 실패한다. 확인이 방패가 되어 주는 것은 일부만 죽었을 때다.

## 📝 정리

**"연속 몇 번 대답이 없으면 빼는 출석 부르기"** 라고 읽으면 된다. 켜져 있는 것과 일할 수 있는 것은 다르고, 실패했을 때 무엇을 하느냐가 확인의 종류를 가른다. 빠지기까지 걸리는 시간은 간격에 연속 횟수를 곱한 만큼이다.

## 🧒 열 살에게

선생님이 이름을 부르는데 한 번 대답이 없다고 바로 결석으로 적지는 않지? 몇 번을 연달아 불러도 소식이 없어야 오늘 명단에서 빼. 나중에 대답이 다시 들리면 도로 넣어 줘.
