# Signal (시그널)

## 📝 정의

Signal 은 **프로세스에게 번호 하나로 보내는 짧은 통지**다.

내용을 실을 수 없는 것이 특징이다. 번호만 도착하고, 그 번호를 무슨 뜻으로 받을지는 받는 쪽이 미리 정해 둔다. 유닉스가 만든 가장 오래된 프로세스 조종 수단이고, 오늘도 배포마다 이것으로 프로세스를 내린다.

### 이름
Signal :: 짧게 알리는 신호
= 한 낱말이다. 말을 못 싣고 종류만 전해지는, 프로세스에게 보내는 통지를 가리킨다

### 비유
학교 종. 무슨 일인지 길게 말해 주지 않고 종류만 알려 주며, 듣고 무엇을 할지는 각자 정한다.

### 예
터미널에서 Ctrl-C 를 눌러 돌던 명령을 멈춰 본 적이 있다면 그때 보낸 것이 이것이다.

### 직접
터미널에서 kill -l 을 쳐 보라. 이 기계가 보낼 수 있는 신호의 번호와 이름이 전부 나온다.

## 🖼️ 그림으로 보기

```도해
흐름: 신호를 받은 프로세스는 무엇을 하나
보내는 쪽 :: 커널이나 kill 명령이 번호 하나를 던진다
커널 :: 받는 프로세스에 그 번호가 왔다고 표시한다
처리 지정 :: 잡아서 처리할지, 무시할지, 기본대로 둘지
기본 동작 :: 지정이 없으면 종료·중지·무시 중 정해진 대로
예외 둘 :: 죽이기와 멈추기는 잡지도 무시하지도 못한다
= 말은 안 오고 번호만 온다. 무엇을 할지는 받는 쪽이 미리 정해 둔다
```

## ⚠️ 해결하는 문제

```도해
대조: 신호가 없으면 밖에서 프로세스를 어떻게 다루나
신호가 없으면 || 신호로
멈춰 달라 :: 전할 길이 없다 || 번호 하나면 된다
정리할 틈 :: 없이 끊긴다 || 받고 마무리한다
설정 다시 읽기 :: 껐다 켜야 한다 || 끊지 않고 시킨다
= 밖에서 도는 프로세스에게 말을 거는 가장 오래된 통로다
```

돌고 있는 프로세스에 밖에서 말을 걸 방법이 없다면 남는 선택은 하나뿐이다 — 전원을 끊듯 끊는 것. 그러면 쓰던 파일은 반쯤 쓰인 채로 남고, 받아 둔 요청은 답 없이 사라지고, 설정 한 줄을 고치려 해도 서비스를 통째로 껐다 켜야 한다.

신호는 이 문제를 아주 작은 것으로 푼다. 실어 나르는 것은 번호 하나뿐이지만, **번호가 도착한다는 사실 자체가 약속의 자리**가 된다. 받는 쪽이 그 번호에 처리기를 걸어 두면 끝내기 전에 정리할 틈이 생기고, 다른 번호에는 "설정을 다시 읽어라" 같은 자기만의 뜻을 붙일 수 있다.

## ⚙️ 작동 원리

받는 쪽은 번호마다 **처리 지정**을 하나씩 갖는다. 잡아서 자기 함수를 부르게 하거나, 무시하게 하거나, 기본 동작에 맡긴다. POSIX 는 신호마다 그 기본 동작을 표로 못 박아 두었다 — `T` 는 프로세스를 비정상 종료, `A` 는 종료에 더해 추가 동작, `S` 는 정지, `I` 는 무시, `C` 는 멈춰 있으면 계속시키고 아니면 무시다.

여기에 딱 둘, 손댈 수 없는 것이 있다. 표준은 `SIGKILL` 옆에 "잡을 수도 무시할 수도 없음", `SIGSTOP` 옆에 "실행 정지, 잡을 수도 무시할 수도 없음" 이라고 적는다. 그래서 `kill -9` 는 확실하지만 동시에 **정리할 틈을 주지 않는다.** 하던 쓰기가 중간이면 중간인 채로 끝난다.

나머지 번호의 뜻은 프로그램마다 자기가 정한다. nginx 문서의 표가 그 예다. 주 프로세스는 `TERM`·`INT` 를 빠른 종료로, `QUIT` 를 우아한 종료로, `HUP` 을 설정 다시 읽기로, `USR1` 을 로그 파일 다시 열기로, `USR2` 를 실행 파일 갈아 끼우기로 받는다. 보낼 곳도 문서가 정해 둔다 — 주 프로세스의 번호는 기본적으로 `/usr/local/nginx/logs/nginx.pid` 에 적혀 있고, 신호는 그 번호로 보낸다.

한 가지 함정이 1번 프로세스다. 컨테이너의 1번은 자기가 처리기를 걸지 않은 신호에 대해 기본 동작이 적용되지 않는다. 셸 스크립트를 1번으로 띄워 두면 `TERM` 을 보내도 아무 일이 안 일어나고, 유예 시간이 지나 `KILL` 로 끊길 때까지 그대로 서 있는다. 파드 안에서 프로세스 범위를 공유한 경우도 비슷하다 — 쿠버네티스 문서의 말대로 1번 자리는 파드 샌드박스가 차지하므로 `kill -HUP 1` 이 엉뚱한 쪽으로 간다.

## 📊 비교: 자주 쓰는 신호는 무엇이 다른가

| 신호 | 기본 동작 | 실제로 무엇에 쓰나 |
|---|---|---|
| **TERM** | 종료 | "정중히 끝내 달라". kill 명령이 아무것도 안 적으면 이것이다 |
| **INT** | 종료 | 터미널에서 Ctrl-C 를 눌렀을 때 |
| **QUIT** | 종료 | nginx 에서는 하던 일을 끝내고 내려가는 우아한 종료 |
| **HUP** | 종료 | 원래는 접속 끊김. 대개 "설정을 다시 읽어라" 로 다시 정의해 쓴다 |
| **KILL** | 종료 | 잡을 수도 무시할 수도 없다. 정리할 틈이 없는 마지막 수단 |
| **STOP · CONT** | 정지 · 계속 | 멈춰 두었다가 그대로 다시 굴린다 |

## 💡 실제 사례

- **끊지 않고 설정 바꾸기** — nginx 문서는 주 프로세스에 HUP 을 보내면 문법을 먼저 검사하고, 통과하면 새 설정으로 작업 프로세스를 띄운 뒤 옛것을 우아하게 내린다고 적는다. 검사에서 걸리면 옛 설정 그대로 돌아간다.
- **멈추지 않고 실행 파일 갈아 끼우기** — 새 파일을 자리에 놓고 USR2 를 보내면 옛 주 프로세스 옆에 새 주 프로세스가 함께 선다. WINCH 로 옛 작업 프로세스를 내리고, 문제가 없으면 QUIT 로 옛 주 프로세스를 끝낸다.
- **로그 파일 갈아 끼우기** — 파일 이름을 먼저 바꾼 뒤 USR1 을 보내면 열어 두었던 파일을 다시 연다. 같은 번호에 프로그램마다 자기 뜻을 붙여 쓰는 예다.

## 🚫 흔한 오해

- **kill 은 죽이는 명령이다** — 이름만 그렇다. 하는 일은 번호를 하나 보내는 것이고, 멈추기·계속하기·설정 다시 읽기도 전부 같은 명령으로 보낸다.
- **kill -9 를 먼저 쓰면 확실하다** — 잡을 수 없는 신호라 정리할 틈 없이 끊긴다. 쓰던 파일과 받아 둔 일이 반쯤 남는 대가를 치른다.
- **신호를 보냈으니 그대로 끝난다** — 잡아서 처리하기로 해 둔 쪽은 자기가 정한 일을 한다. 끝낼지 말지는 받는 쪽이 정한다.

## 📝 정리

**"번호 하나만 실어 보내는 짧은 통지"** 라고 읽으면 된다. 무엇을 할지는 보내는 쪽이 아니라 받는 쪽이 미리 정해 두고, 죽이기와 멈추기 둘만은 그 선택권이 없다. 그래서 신호를 보냈다는 것과 프로세스가 끝났다는 것은 같은 말이 아니다.

## 🧒 열 살에게

학교에서 종이 울리면 무슨 일인지 길게 말해 주지 않아도 다들 알지? 종소리는 "지금 이거야" 하나만 알려 주고 무엇을 할지는 각자 정하는 거야. 그런데 딱 하나, 불이 났을 때 울리는 종만은 못 들은 척할 수가 없어.

## ❓ 이해했는지

- kill -9 로 끝낸 쪽이 쓰던 파일을 망가뜨리기 쉬운 까닭은 무엇인가 → 흔한 오해
- 같은 HUP 을 받고도 프로그램마다 하는 일이 다른 까닭은 무엇인가 → 비교
- 종료 신호를 보냈는데 컨테이너가 안 끝나고 버티는 일은 왜 생기나 → 작동 원리
