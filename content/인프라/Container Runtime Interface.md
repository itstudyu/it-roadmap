# Container Runtime Interface (컨테이너 런타임 인터페이스)

## 📝 정의

kubelet 이 어떤 런타임과도 말할 수 있게 정한 **하나의 규약**이다.

쿠버네티스 문서는 이걸 "클러스터 부품을 다시 빌드하지 않고도 kubelet 이 여러 런타임을 쓸 수 있게 하는 꽂이식 규약" 이라 적는다. 노드 안에서 kubelet 과 런타임 사이에 오가는 gRPC 규약이고, kubelet 이 손님 쪽이다. 규약이 생기기 전에는 도커를 부르는 코드가 kubelet 안에 박혀 있었고(dockershim), 그래서 런타임을 바꾸려면 쿠버네티스 본체를 고쳐야 했다.

### 이름
Container :: 격리해 담은 한 벌
Runtime :: 실제로 굴리는 쪽
Interface :: 둘 사이의 약속
= 붙여 읽으면 "굴리는 쪽과 맺은 약속". 굴리는 쪽을 갈아 끼워도 부르는 법은 그대로다

### 비유
벽에 난 콘센트 구멍 — 무엇을 꽂든 구멍 모양이 같아서, 기기를 바꿔도 벽은 안 뜯는다.

### 예
노드 하나가 갑자기 NotReady 로 바뀌고 kubelet 로그에 런타임에 못 붙는다는 줄만 반복되던 그 새벽이다.

## 🖼️ 그림으로 보기

```도해
층: 파드 하나가 뜨기까지 누가 누구를 부르나
kubelet :: 파드를 띄우라는 지시를 노드에서 받는다
CRI :: 유닉스 소켓 위의 gRPC 약속. 갈아 끼우는 자리가 여기다
containerd·CRI-O :: 이미지를 받아 파드의 빈 껍데기를 만든다
runc :: 리눅스에게 실제 격리를 시키고 프로세스를 띄운다
= 위 둘은 쿠버네티스 것이고 아래 둘은 아니다. 그 사이를 이 약속이 끊어 놓았다
```

## ⚠️ 해결하는 문제

```도해
대조: 굴리는 쪽을 바꿀 때 무엇이 달라지나
약속이 없으면 || 약속이 있으면
런타임 교체 :: 본체를 고친다 || 소켓만 바꾼다
새 런타임 :: 본체에 넣어야 || 밖에서 붙는다
장애 확인 :: 도구가 제각각 || 한 도구로 본다
= 굴리는 쪽을 본체 밖으로 밀어낸 덕에 교체가 설정 한 줄이 됐다
```

굴리는 쪽을 부르는 코드가 본체 안에 있으면, 새 런타임이 하나 생길 때마다 쿠버네티스에 코드가 한 벌 더 들어온다. 그 코드는 쿠버네티스 팀이 남의 제품에 맞춰 유지해야 하고, 그 제품이 바뀔 때마다 쿠버네티스가 따라 고쳐야 한다. dockershim 이 딱 그 상태였고, 결국 1.24 에서 본체에서 빠졌다.

이 규약은 그 관계를 **소켓 하나로 잘라 놓는다.** kubelet 은 `--container-runtime-endpoint` 가 가리키는 소켓에 정해진 호출만 던지고, 그 뒤에 무엇이 있는지 모른다. 그래서 containerd 를 CRI-O 로 바꾸는 일이 코드 수정이 아니라 소켓 경로 한 줄 수정이 된다. 대신 조건이 붙는다 — 1.26 이후의 kubelet 은 v1 규약만 받으므로, 런타임이 이걸 못 하면 노드가 등록조차 안 된다.

## ⚙️ 작동 원리

규약은 두 갈래 호출로 나뉜다. 하나는 파드와 컨테이너를 만들고 없애는 쪽(RuntimeService), 하나는 이미지를 받고 지우는 쪽(ImageService)이다. 요즘 kubelet 은 이 둘을 소켓 하나로 함께 부르고(`--container-runtime-endpoint`, 기본값은 containerd 의 소켓), 사람이 손으로 짚어 볼 때 쓰는 `crictl` 만 `--runtime-endpoint` 와 `--image-endpoint` 를 따로 받는다.

노드가 이상할 때 이 구간을 사람이 직접 짚어 볼 수 있는 도구가 `crictl` 이다. 쿠버네티스를 거치지 않고 같은 소켓에 직접 말하기 때문에, **관문이 죽었는지 런타임이 죽었는지를 가른다.** `kubectl` 은 안 되는데 `crictl` 은 되면 런타임은 멀쩡하다는 뜻이고, 둘 다 안 되면 노드 안쪽이 문제다.

```bash
crictl --runtime-endpoint unix:///run/containerd/containerd.sock info
crictl ps -a          # 이 노드에서 실제로 도는 컨테이너 (kubectl 을 안 거친다)
crictl images         # 이 노드가 받아 둔 이미지
crictl logs <id>      # 파드 객체가 안 잡혀도 로그는 볼 수 있다
```

또 하나 자주 무는 함정은 **cgroup 드라이버**다. kubelet 과 런타임이 자원을 나누는 방식을 서로 다르게 잡아 두면(하나는 systemd, 하나는 cgroupfs) 노드가 불안정해진다. 쿠버네티스 문서는 양쪽을 `systemd` 로 맞추라고 못 박는다.

## 💡 실제 사례

- **도커 없이 도는 클러스터** — 요즘 관리형 클러스터의 노드는 대부분 containerd 만 얹고 있고, 도커 명령은 아예 없다.
- **노드 장애 가르기** — 관문이 답을 안 할 때 노드에 들어가 `crictl ps` 로 컨테이너가 도는지부터 본다.
- **런타임 갈아 끼우기** — 소켓 경로와 cgroup 드라이버만 맞추면 노드를 하나씩 비워 가며 바꿀 수 있다.

## 🚫 흔한 오해

- **쿠버네티스가 도커를 버려서 도커 이미지를 못 쓴다** — 못 쓰는 것은 도커라는 프로그램이지 이미지가 아니다. 이미지 형식은 [[OCI]] 규격이라 어느 런타임이든 그대로 받는다.
- **CRI 가 컨테이너를 만든다** — 아니다. 규약은 부르는 법만 정하고, 실제로 만드는 것은 그 뒤의 containerd 나 CRI-O 다.
- **런타임은 아무거나 최신으로 두면 된다** — 1.26 이후 kubelet 은 v1 규약을 요구하고, 못 맞추면 노드가 등록에 실패해 아예 안 보인다.

## 🚨 주의사항

- **kubelet 과 런타임의 cgroup 드라이버를 같은 값으로 맞춰라.** 어긋나면 재시작이 잦고 원인이 잘 안 잡힌다.
- **노드를 올리기 전에 런타임 버전을 먼저 봐라.** 규약 버전이 안 맞으면 노드가 아예 등록되지 않는다.
- **`crictl` 은 디버깅용이다.** 여기서 컨테이너를 손으로 지우면 kubelet 이 곧바로 다시 띄우거나 상태가 어긋난다.
- **소켓 파일 권한을 조여라.** 이 소켓에 닿으면 그 노드에서 아무 컨테이너나 띄울 수 있다.

## 📝 정리

**"굴리는 쪽과 맺어 둔 소켓 하나짜리 약속"** 이라고 읽으면 된다. 이 약속 덕에 kubelet 은 뒤에 무엇이 있는지 모른 채 정해진 호출만 던지고, 런타임 교체가 코드 수정이 아니라 소켓 경로 한 줄이 된다. 노드가 이상할 때 같은 소켓에 직접 말하는 도구로 관문 문제인지 런타임 문제인지를 가를 수 있다.

## 🧒 열 살에게

벽에 있는 구멍 모양이 다 똑같아서 선풍기든 충전기든 그냥 꽂으면 되지? 구멍 모양만 미리 정해 두면 안쪽 배선을 통째로 바꿔도 벽을 다시 뚫을 필요가 없어. 대신 구멍 모양이 안 맞는 걸 들고 오면 그 자리에선 아무것도 못 켜.

## ❓ 이해했는지

- 도커를 안 깐 노드에서 도커로 만든 이미지가 그대로 도는 이유는 무엇인가 → 흔한 오해
- 목록 조회는 안 되는데 노드의 컨테이너는 살아 있는지 어떻게 가르나 → 작동 원리
- 노드를 올렸더니 아예 목록에 안 나타나는 일은 왜 생기나 → 해결하는 문제
