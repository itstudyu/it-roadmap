# Ingress (인그레스)

## 📝 정의

Ingress는 **밖에서 온 웹 요청을 어느 서비스로 보낼지 적어 둔 규칙**이다.

쿠버네티스 문서는 인그레스가 클러스터 밖에서 안의 서비스(같은 일을 하는 파드 여럿을 이름 하나로 묶어 부르는 자리)로 가는 HTTP · HTTPS 경로를 열어 주며, 그 경로 배분은 인그레스 자원에 정의한 규칙이 정한다고 적는다. 규칙을 적어 둔 자원일 뿐이라, 그 규칙을 읽고 실제로 길을 여는 컨트롤러가 따로 있어야 한다.

### 이름
In :: 안으로
gress :: 걸음, 들어감
= 붙여 읽으면 "안으로 들어오는 길". 밖에서 클러스터 안으로 들어오는 문이 곧 이름이다

### 비유
건물 1층 안내 데스크. 출입문은 하나지만, 찾는 곳을 대면 몇 층 몇 호로 가라고 갈라 준다.

### 예
같은 도메인인데 `/api` 로 들어오면 백엔드로, 나머지는 프론트로 가도록 갈라 둔 그 설정이다.

## 🖼️ 그림으로 보기

```도해
흐름: 주소 하나로 들어온 웹 요청이 어떻게 갈라지나
사용자 :: `shop.example.com/pay` 를 연다
인그레스 :: 호스트와 경로로 어디로 보낼지 적어 둔 규칙
컨트롤러 :: 그 규칙을 읽어 실제 길을 여는 쪽
서비스 :: `/pay` 는 결제로, `/` 는 상점으로 나뉜다
< 사용자 :: 골라 간 파드의 응답이 같은 길로 돌아온다
= 문은 하나인데, 들어온 주소를 보고 그 안에서 갈래가 나뉜다
```

## ⚠️ 해결하는 문제

```도해
대조: 서비스마다 부하 분산기를 하나씩 두면 무엇이 문제인가
서비스마다 하나씩 || 인그레스 하나로
공인 주소 :: 서비스 수만큼 || 하나로 끝난다
인증서 :: 곳곳에 따로 둔다 || 한 자리에서 끊는다
경로로 가르기 :: 못 한다 || 규칙으로 가른다
아는 범위 :: 포트만 본다 || 주소까지 본다
= 입구를 하나로 모으고, 들어온 주소를 보고 안에서 가른다
```

서비스를 밖으로 열 때 LoadBalancer 타입을 쓰면 서비스마다 부하 분산기가 하나씩 생긴다. 그 부하 분산기는 4계층에서 돈다 — 정해진 포트로 파드에 나눠 줄 뿐이다. Azure 문서는 4계층 서비스가 실제 앱을 알지 못해 이런 복잡한 배분 규칙을 구현할 수 없다고 적는다.

인그레스는 입구를 하나로 모으고 7계층에서 가른다. 들어온 URL 을 보고 어느 앱으로 보낼지 고르므로 도메인 하나에 여러 앱을 붙일 수 있다. 쿠버네티스 문서는 인그레스가 서비스에 밖에서 닿는 URL 을 주고, 부하를 나누고, SSL / TLS 를 끊고, 이름 기반 가상 호스팅을 제공하도록 설정될 수 있다고 적는다. 여기서 끊는다는 것은 암호를 이 자리에서 풀고 뒤로는 평문으로 넘긴다는 뜻이다.

## ⚙️ 작동 원리

인그레스 자원 하나만 만들어서는 아무 일도 일어나지 않는다. 문서가 못 박아 둔 문장이 있다 — "인그레스를 만족시키려면 인그레스 컨트롤러가 있어야 한다. 인그레스 자원을 만들기만 하는 것은 아무 효과가 없다." 컨트롤러는 클러스터 안에서 도는 프록시이거나, 클라우드가 대신 띄워 주는 부하 분산기다.

규칙은 호스트와 경로 둘로 잡는다. HTTP 규칙마다 선택적인 host 가 있고 그 아래에 경로 목록이 온다. 경로마다 `service.name` 과 포트로 지정한 백엔드가 붙는다. 문서는 들어온 요청의 내용에 host 와 path 가 둘 다 맞아야 그 서비스로 보낸다고 적는다.

어느 컨트롤러가 이 인그레스를 맡을지는 `ingressClassName` 으로 고른다. 이 값을 빼려면 기본 인그레스 클래스가 정의되어 있어야 한다. 규칙이 하나도 없는 인그레스는 모든 요청을 `.spec.defaultBackend` 로 보낸다.

## 💡 실제 사례

- **한 도메인에 여러 앱** — `/api` 는 백엔드로, 나머지는 프론트로 경로 규칙 하나로 가른다. 도메인을 더 사지 않아도 된다.
- **인증서를 한 자리에서** — TLS 를 인그레스에서 끊으면 뒤에 선 서비스들은 평문만 다루면 된다.
- **공인 주소 아끼기** — 서비스마다 LoadBalancer 를 붙이면 밖에서 닿는 주소가 그만큼 필요하다. 인그레스는 입구를 하나로 모은다.

## 🚫 흔한 오해

- **인그레스를 만들어 두면 밖에서 들어온다** — 컨트롤러가 없으면 아무 일도 안 일어난다. 문서가 "인그레스 자원을 만들기만 하는 것은 아무 효과가 없다" 고 그대로 적어 뒀다.
- **밖으로 여는 건 전부 인그레스로 한다** — HTTP 와 HTTPS 만이다. 문서는 그 밖의 포트나 프로토콜을 밖으로 열 때는 NodePort 나 LoadBalancer 타입 서비스를 쓴다고 적는다.
- **인그레스가 요청을 직접 나른다** — 인그레스는 규칙을 적어 둔 자원이다. 실제로 나르는 것은 그 규칙을 읽은 컨트롤러가 세운 프록시나 부하 분산기다.

## 🚨 주의사항

- **인그레스 API 는 동결됐다.** 쿠버네티스 문서는 이제 Gateway(인그레스 자리를 이어받을 새 규격)를 쓰라고 권하고, 인그레스 API 는 더 개발되지 않으며 앞으로 변경이나 갱신이 없을 것이라고 적는다. 새로 짓는 것이라면 여기서부터 따져 본다.
- **컨트롤러의 수명도 따로 본다.** Azure 문서는 Ingress NGINX 프로젝트의 유지보수가 2026년 3월에 끝난다고 공지하고 Gateway API 로 옮기는 경로를 안내한다. 규격이 살아 있어도 쓰던 구현이 먼저 끝날 수 있다.
- **원래 접속 주소는 그냥 안 남는다.** Azure 문서는 컨트롤러가 요청을 넘기면 원래 출발지 주소가 대상 컨테이너에 보이지 않으며, 보존을 켜야 `X-Forwarded-For` 헤더에 담긴다고 적는다.

## 📝 정리

**"밖에서 안으로 들어오는 길을 적어 둔 안내판"** 이라고 읽으면 된다. 문은 하나로 모으고 호스트와 경로를 보고 어느 서비스로 갈지 가르되, HTTP 와 HTTPS 만 다룬다. 안내판만 세워서는 아무도 안 움직이니 그 판을 읽고 길을 여는 컨트롤러가 반드시 함께 있어야 한다.

## 🧒 열 살에게

큰 건물에 가면 문은 하나인데, 들어가면 안내하는 분이 "치과는 3층, 학원은 5층" 하고 갈라 주지? 밖에서 온 사람은 그 문 하나만 알면 되고, 안에서 방이 늘어나도 안내판만 고쳐 쓰면 돼. 대신 안내판만 세워 두고 안내하는 사람이 없으면 아무도 못 찾아가.
