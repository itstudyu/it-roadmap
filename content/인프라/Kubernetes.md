# Kubernetes (K8s)

## 📝 정의

Kubernetes는 Docker 컨테이너를 대규모로 자동 관리하고 오케스트레이션하는 오픈소스 플랫폼입니다. 여러 서버(노드)에 산재된 수백 개의 컨테이너를 마치 하나의 시스템처럼 관리하여, 자동 배포, 스케일링, 업데이트, 장애 복구를 수행합니다. Google이 내부적으로 사용하던 Borg 시스템을 기반으로 개발되었으며, 현재 클라우드 네이티브 표준 플랫폼입니다.

> **한 줄 요약**: 컨테이너 오케스트레이션 플랫폼으로, 자동 배포/스케일링/자가 치유를 제공합니다.

**비유 1**: 쿠버네티스는 마치 데이터센터의 운영 체제(OS)처럼, 수많은 물리 서버와 컨테이너를 효율적으로 관리합니다.

**비유 2**: 오케스트라 지휘자처럼, 많은 수의 악기(컨테이너)를 조화롭게 연주하도록 지휘하고, 악기가 고장나면 즉시 대체합니다.

---

## 🎯 핵심 개념

### 1. Pod (포드)
쿠버네티스의 최소 배포 단위로, 하나 이상의 컨테이너를 포함합니다. 보통 하나의 메인 컨테이너와 사이드카 컨테이너로 구성되며, 같은 Pod 내 컨테이너들은 네트워크와 스토리지를 공유합니다.

### 2. Node (노드)
Pod이 실행되는 물리 또는 가상 서버입니다. 각 Node는 kubelet(에이전트), Container Runtime(Docker), kube-proxy를 실행하며, Master Node가 할당한 작업을 수행합니다.

### 3. Cluster (클러스터)
Master Node(제어 평면)와 Worker Node들의 집합입니다. Master Node는 클러스터 전체의 상태를 관리하고, Worker Node는 Pod을 실행합니다.

### 4. Service (서비스)
Pod들의 네트워크 엔드포인트를 추상화하여 일정한 IP와 DNS 이름으로 접근 가능하게 합니다. Pod이 동적으로 생성/삭제되어도 Service를 통해 안정적으로 접근할 수 있습니다.

### 5. Deployment (배포)
Pod의 배포와 업데이트를 관리합니다. 원하는 상태(desired state)를 선언하면 쿠버네티스가 현재 상태를 자동으로 맞춥니다.

---

## ⚠️ 해결하는 문제

### 문제 1: 대규모 컨테이너 관리의 복잡성
수백 개의 컨테이너를 수동으로 관리하는 것은 불가능하므로, 자동화 도구가 필수입니다.

### 문제 2: 컨테이너 장애와 자동 복구
컨테이너가 갑자기 중단되었을 때 자동으로 새 컨테이너를 생성하여 서비스 가용성을 보장해야 합니다.

### 문제 3: 트래픽 증감에 따른 자동 스케일링
수요 변화에 따라 자동으로 컨테이너 개수를 증감하여 비용과 성능을 최적화해야 합니다.

### 문제 4: 무중단 업데이트
서비스 중단 없이 새 버전으로 업데이트하기 위한 방식이 필요합니다.

## ⚙️ 작동 원리

1. **선언적 상태 관리**: 사용자가 원하는 상태(Deployment yaml)를 쿠버네티스에 선언하면, 현재 상태를 자동으로 맞춥니다.

2. **API Server와 컨트롤러**: Master Node의 API Server가 모든 요청을 받고, Controller Manager가 현재 상태를 지속적으로 감시합니다.

3. **etcd 데이터베이스**: 클러스터의 모든 상태 정보(Pod, Node, Service 등)를 저장합니다.

4. **kubelet 에이전트**: 각 Worker Node에서 실행되어 Pod의 생성, 삭제, 상태 관리를 수행합니다.

5. **스케줄러**: 새로운 Pod을 어느 Node에 배치할지 결정합니다 (리소스, 레이블 등을 고려).

6. **자동 복구**: Pod 또는 Node 장애를 감지하면 자동으로 새로운 Pod을 생성하여 원하는 상태를 유지합니다.

## ✅ 장단점

### 장점
- **자동 스케일링**: CPU/메모리 기반 자동 스케일링으로 효율적인 리소스 관리
- **자가 치유 (Self-healing)**: Pod 또는 Node 장애 시 자동 복구로 높은 가용성
- **무중단 배포**: 롤링 업데이트로 서비스 중단 없이 새 버전 배포
- **선언적 관리**: yaml로 원하는 상태를 선언하면 자동으로 유지
- **클라우드 무관**: 어떤 클라우드나 온프레미스에서도 동일하게 동작
- **풍부한 에코시스템**: Helm, Prometheus, Istio 등 다양한 플러그인 지원

### 단점
- **높은 복잡도**: 처음 배우기 어렵고 설정과 운영이 복잡함
- **리소스 오버헤드**: 클러스터 자체가 상당한 리소스 소비
- **초기 구축 비용**: 마스터/워커 노드, 네트워크, 스토리지 설정 필요
- **운영 난이도**: 문제 진단과 디버깅이 어려움
- **작은 규모 프로젝트에 과도함**: 소규모 팀이나 프로젝트에는 Docker Compose로 충분
- **네트워크 복잡성**: 서비스 간 통신, DNS, CNI 플러그인 등 복잡한 네트워킹

## 💡 실제 사례

### Case 1: Netflix의 마이크로서비스 관리
Netflix는 Kubernetes를 사용하여 Hystrix, Eureka 등의 마이크로서비스를 AWS에서 관리합니다. 자동 스케일링으로 트래픽 급증 시 자동으로 인스턴스를 증가시키고, 장애 시 자동 복구하여 높은 가용성을 유지합니다.

### Case 2: Google Cloud Platform (GKE)
Google은 자체 개발한 Kubernetes를 GCP의 관리형 서비스(GKE, Google Kubernetes Engine)로 제공합니다. 사용자는 컨테이너 배포에만 집중하고, Google이 마스터 노드와 인프라를 관리합니다.

### Case 3: 스타트업의 비용 최적화
팀 규모가 작은 스타트업에서도 Kubernetes를 사용하여 자동 스케일링으로 비용을 절감합니다. 야간에는 워커 노드를 줄이고, 피크 시간에만 확대하여 인프라 비용을 최적화합니다.

### Case 4: 다중 클라우드 운영
기업이 AWS, Google Cloud, Azure 등 여러 클라우드를 사용할 때, Kubernetes를 공통 플랫폼으로 사용하여 벤더 종속성을 줄입니다.

## 🔗 관련 용어

- **Pod**: 쿠버네티스의 최소 배포 단위, 하나 이상의 컨테이너 포함
- **Service**: Pod들의 네트워크 엔드포인트 추상화, 로드 밸런싱 제공
- **Deployment**: Pod의 배포 및 업데이트 관리, Replica Set 제어
- **StatefulSet**: 순서와 고유성이 필요한 스테이트풀 애플리케이션 관리
- **DaemonSet**: 모든 노드에서 동일한 Pod 실행 (로깅, 모니터링 에이전트)
- **Helm**: Kubernetes 패키지 관리자, 복잡한 배포를 템플릿화
- **Istio**: 서비스 메시 (Service Mesh), 마이크로서비스 간 통신 관리
- **Persistent Volume**: 컨테이너 삭제 후에도 데이터 지속성 보장
- **Ingress**: 외부 트래픽을 클러스터 내부의 Service로 라우팅
