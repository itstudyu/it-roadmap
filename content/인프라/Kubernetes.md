# Kubernetes (쿠버네티스)

## 📝 정의

Kubernetes는 **컨테이너를 어디에 몇 개 띄울지 알아서 관리하는 시스템**이다.

컨테이너가 열 개를 넘어가면 어느 서버에 올릴지, 죽으면 누가 다시 띄울지, 배포할 때 어떻게 바꿔치기할지를 사람이 감당하기 어려워진다. 원하는 상태만 적어두면 그 상태를 계속 맞춰준다.

### 비유
창고 관리자. 물건을 어느 선반에 둘지, 하나가 없어지면 어디서 채울지, 재고를 몇 개로 유지할지를 알아서 한다. 주인은 "이 물건 열 개 유지" 라고만 적어둔다.

## 🖼️ 그림으로 보기

```도해
흐름: 컨테이너 하나가 죽으면 무슨 일이 일어나나
사용자 :: "이 앱을 3개 유지" 라고 적어 제출한다
컨트롤러 :: 지금 몇 개인지 센다. 3개다. 할 일 없음
서버 B :: 컨테이너 하나가 죽는다
컨트롤러 :: 다시 센다. 2개다. 원하는 상태와 다르다
스케줄러 :: 여유 있는 서버를 골라 하나 더 띄운다
< 상태 :: 다시 3개. 사람이 아무것도 하지 않았다
= 명령을 실행하는 게 아니라 원하는 상태와 현재를 계속 비교해 좁힌다
```

## ⚠️ 해결하는 문제

```도해
대조: 컨테이너가 수십 개면 무엇이 달라지나
직접 관리 || 쿠버네티스
컨테이너 죽음 :: 사람이 확인하고 재시작 || 자동 복구
어느 서버에 :: 사람이 정한다 || 여유 보고 배치
배포 :: 하나씩 수동 교체 || 순차 교체 자동
= 사람이 절차를 적는 대신 원하는 결과만 적게 만든다
```

컨테이너가 서너 개면 직접 관리해도 된다. 수십 개가 되면 이야기가 달라진다. 새벽에 하나가 죽으면 누군가 깨어나야 하고, 서버를 늘리면 무엇을 어디로 옮길지 정해야 하고, 배포할 때마다 순서를 지켜 교체해야 한다.

쿠버네티스는 이 일들을 선언 방식으로 바꾼다. 절차를 적는 대신 원하는 상태를 적고, 시스템이 현재와 비교해서 차이를 좁힌다. 사람이 개입하지 않아도 상태가 유지되는 이유다.

## ⚙️ 작동 원리

```도해
층: 무엇이 무엇을 담고 있나
클러스터 :: 서버 여러 대를 묶은 전체
노드 :: 실제 서버 한 대
파드 :: 배치의 최소 단위. 컨테이너 하나나 몇 개
컨테이너 :: 실제로 도는 프로세스
= 쿠버네티스가 옮기고 세는 단위는 컨테이너가 아니라 파드다
```

원하는 상태는 YAML 파일로 적는다. "이 이미지를 3개, 메모리는 각 512MB, 8080 포트로 노출" 같은 내용이고, 이 파일을 저장소에 넣어 관리하면 인프라 자체가 코드로 남는다.

## 💡 실제 사례

- **자동 복구** — 컨테이너나 서버가 죽으면 다른 곳에 다시 띄운다.
- **무중단 배포** — 새 버전을 하나씩 올리고 정상 확인 후 옛 것을 내린다. 실패하면 되돌린다.
- **부하 대응** — CPU 사용률을 보고 컨테이너 수를 자동으로 늘리고 줄인다.

## 🚫 흔한 오해

- **컨테이너를 쓰면 쿠버네티스가 필요하다** — 서비스가 몇 개뿐이면 과하다. 관리 대상이 늘어나기 전까지는 더 단순한 방법이 낫다.
- **쿠버네티스가 앱을 빠르게 만든다** — 빠르게 하지 않는다. 죽었을 때 스스로 회복하고 배포가 안전해지는 것이 이득이다.
- **한 번 띄우면 손이 안 간다** — 버전 업그레이드, 인증서 갱신, 자원 조정이 계속 필요하다. 관리 대상이 앱에서 클러스터로 옮겨간 것에 가깝다.

## 🚨 주의사항

- **자원 요청과 상한을 적는다.** 안 적으면 스케줄러가 판단할 근거가 없어 한 서버에 몰리고 서로 죽인다.
- **헬스체크를 실제 동작으로 만든다.** 프로세스가 살아 있는지만 보면, DB 연결이 끊긴 컨테이너도 정상으로 잡힌다.

## 📝 정리

Kubernetes는 원하는 상태를 적어두면 컨테이너 배치와 복구를 알아서 맞춰주는 시스템이다. 규모가 커질 때 값을 하고, 작을 때는 관리 대상만 늘린다.

## ❓ 이해했는지

- 컨테이너가 죽었는데 아무도 손대지 않았는데 다시 뜨는 원리는?
- 서비스가 두 개뿐인 팀에 쿠버네티스가 과한 이유는?
- 자원 요청을 안 적으면 스케줄러가 왜 잘못된 결정을 하나?
