# NTP (망 시각 프로토콜)

## 📝 정의

NTP는 **여러 기계의 시계를 같은 시각에 맞춰 두는 약속**이다.

시계는 반드시 어긋난다. 수정 진동자마다 빠르기가 조금씩 달라서 하루만 놔둬도 몇 초씩 벌어진다. RFC 5905 는 NTPv4 를 "흩어진 시각 서버와 클라이언트 사이에서 시스템 시계를 동기화하는 데 널리 쓰이는" 약속으로 정의한다. 재는 방법은 소포처럼 오간 시각 넷을 적어 두고, 오가는 데 걸린 시간을 빼고 남는 폭을 구하는 것이다.

### 이름
Network :: 서로 이어진 기계들
Time :: 시각
Protocol :: 주고받는 약속
= 붙여 읽으면 "이어진 기계들이 시각을 맞추는 약속". 이름이 곧 하는 일이다

### 비유
학교 종. 교실마다 시계가 조금씩 달라도 종이 울리는 순간을 기준 삼으면 다들 같은 시각을 쓴다.

### 예
두 대의 로그를 나란히 놓고 원인을 찾는데 원인이 결과보다 뒤에 찍혀 있던 그 순간이다.

### 직접
폰 설정의 날짜·시각 화면에서 "자동으로 설정" 스위치를 찾아보라. 그게 켜져 있을 때 폰이 밖에 물어보며 하고 있던 일이 이것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 내 시계가 얼마나 틀렸는지 어떻게 알아내나
내 기계 :: 보내는 순간의 내 시각을 적어 넣는다
시각 서버 :: 받은 순간의 제 시각을 적는다
시각 서버 :: 답을 띄우며 보내는 순간도 적는다
< 내 기계 :: 받은 순간을 적는다. 이로써 넷이 모였다
= 오가는 데 걸린 시간을 빼고 남는 폭이 어긋난 크기다. 그만큼 밀면 같은 시각이 된다
```

## ⚠️ 해결하는 문제

```도해
대조: 기계마다 제 시계를 믿으면 무엇이 무너지나
시계 제각각 || 시각을 맞추면
로그 대조 :: 앞뒤가 뒤집힌다 || 순서대로 읽힌다
증서 검사 :: 멀쩡한데 만료다 || 기한이 통한다
서명 요청 :: 시각이 안 맞다 || 그대로 통과한다
= 시각은 한 대의 설정이 아니라 여러 대가 함께 쓰는 좌표다
```

시각이 어긋나면 가장 먼저 무너지는 것이 사건의 순서다. AWS 문서도 로그의 시각이 "문제가 언제 일어났는지와 사건의 시간 순서를 가리는" 근거라고 적는다. 두 대의 시계가 3초 어긋나 있으면 원인이 결과보다 뒤에 찍히고, 추적은 첫 걸음부터 틀어진다.

두 번째로 무너지는 것은 기한이다. 증서의 유효 기간, 토큰의 만료, 요청 서명이 전부 "지금이 몇 시인가" 위에 서 있다. 같은 문서가 짚는 사례가 그것이다 — 인스턴스의 날짜·시각이 부정확하면 서명에 적힌 날짜와 요청의 날짜가 어긋나서 요청 자체가 거절된다. 코드는 그대로인데 어제부터 안 되는 일이 이 자리에서 자주 난다.

## 🧱 구성

```도해
층: 정확한 시각은 어디서 내려오나
0층 기준 시계 :: 위성이나 원자시계. 여기가 원본이다
1층 서버 :: 기준 시계에 직접 붙어 있는 첫 줄
2층 아래 :: 위층에 물어 맞추고 아래층에 나눠 준다
16 번 :: 못 맞춘 상태를 가리키는 번호다
= 번호가 클수록 원본에서 멀다. 16 은 층이 아니라 "못 맞췄다" 는 표다
```

## ⚙️ 작동 원리

시계를 실제로 맞추는 쪽은 chrony 같은 데몬이다. AWS 가 EC2 에 권하는 설정은 `/etc/chrony.conf` 에 한 줄을 다른 `server` 줄보다 앞에 넣는 것이다.

```
server 169.254.169.123 prefer iburst minpoll 4 maxpoll 4
```

`169.254.169.123` 은 링크 로컬 주소라 밖으로 안 나가고, 그래서 방화벽을 따로 열지 않아도 닿는다. `minpoll 4 maxpoll 4` 의 4 는 RFC 5905 가 말하는 폴 지수다. NTPv4 에서 이 지수는 4(16초)에서 17(36시간)까지 움직이는데, 여기서는 4 로 못 박아 16초마다 묻게 한 것이다.

맞고 있는지는 두 명령으로 본다.

```
$ chronyc sources -v | grep -F ^*
^* 169.254.169.123               3   4   377    13  -4325ns[-9201ns] +/-  401us

$ chronyc tracking
Reference ID    : A9FEA97B (169.254.169.123)
Stratum         : 4
System time     : 0.000002191 seconds fast of NTP time
Frequency       : 3.710 ppm slow
Leap status     : Normal
```

`^*` 가 지금 고른 기준이라는 표시고, 그 옆 숫자가 그 서버의 계층이다. `chronyc tracking` 의 `Frequency ... ppm slow` 는 데몬이 시계의 **흐름 속도 자체**를 고쳐 두고 있다는 뜻이다. 값을 확 당기는 대신 빠르기를 손봐 따라잡기 때문에 시각이 뒤로 가는 일이 안 생긴다. `Leap status` 와 `System time` 은 장애 때 "이 기계 시계 맞나" 를 3초 만에 끝내는 두 줄이다.

정확도는 자릿수 세 개로 기억하면 된다. RFC 5905 는 요즘 기계로 도는 맨 윗줄 서버가 수십 마이크로초, 빠른 랜에 붙은 아래층 서버와 그 손님이 묻는 간격 1024초까지에서 수백 마이크로초, 묻는 간격을 36시간까지 늘리면 수십 밀리초라고 적는다. 밀리초를 다투는 일에는 넉넉하고, 그 아래를 다투는 일에는 다른 장치가 필요하다.

## 💡 실제 사례

- **로그 두 대를 겹쳐 볼 때** — 원인과 결과가 뒤집혀 찍혀 있으면 추적이 처음부터 틀어진다. 여러 대의 기록을 한 줄로 세우는 일의 전제가 이것이다.
- **서명이 거절될 때** — 요청에 적힌 시각과 서명의 시각이 어긋나면 요청 자체가 거절된다. 코드를 안 바꿨는데 어제부터 안 되는 일이 여기서 온다.
- **증서 기한** — 시계가 앞서 있으면 아직 유효한 증서가 만료로 보이고, 뒤처져 있으면 방금 발급한 증서가 아직 시작 안 한 것으로 보인다.

## 🚫 흔한 오해

- **인터넷에 붙어 있으면 시각은 알아서 맞는다** — 맞춰 주는 데몬이 실제로 돌고 있어야 맞는다. `chronyc tracking` 의 `Leap status` 와 `System time` 을 보기 전에는 맞는지 아무도 모른다.
- **계층 번호가 낮을수록 좋은 서버다** — 계층은 원본에서 몇 다리 건넜는지를 세는 숫자지 품질 등급이 아니다. 16 은 등급이 아니라 "아직 못 맞췄다" 는 표다.
- **더 정밀하게 맞추려면 더 촘촘히 물으면 된다** — 간격을 좁히면 좋아지긴 한다. RFC 5905 는 묻는 간격이 1024초까지면 빠른 랜에서 수백 마이크로초, 36시간까지 늘리면 수십 밀리초라고 적는다. 다만 그 아래로는 더 묻는 것만으로 안 내려간다. AWS 가 마이크로초를 다투는 자리에 하드웨어 시계를 따로 두는 이유가 그것이다.

## 🚨 주의사항

- **윤초를 다루는 방식이 섞이면 안 된다.** AWS 는 NTP 로 주는 시각은 윤초를 펴 발라 나누고 PTP 하드웨어 시계는 안 편다고 적으면서, 윤초가 있는 동안 두 방식을 한 클라이언트 설정에 같이 쓰지 말라고 못 박는다.
- **링크 로컬 주소에는 초당 한도가 있다.** 같은 문서는 링크 로컬을 쓰는 요청 — 이름 해석 질의, 메타데이터 조회, 시각 질의 — 을 **합쳐서** 초당 1024 패킷까지라고 적는다. 시각만 보고 있으면 못 잡는 한도다.
- **시각을 맞춘다는 것은 흐름을 고치는 일이다.** 데몬은 어긋난 폭을 한 번에 당기는 대신 시계의 빠르기를 손봐 따라잡는다. 그래서 큰 폭이 쌓여 있으면 좁히는 데 시간이 걸리고, 그동안은 어긋난 채로 돈다.

## 📝 정리

**"여러 대가 같은 순간을 가리키게 맞춰 두는 약속"** 이라고 읽으면 된다. 오간 시간을 빼고 남는 폭만큼 시계의 빠르기를 손봐 따라잡고, 어디까지 좁혀졌는지는 chronyc tracking 한 화면으로 확인한다. 시각은 한 대의 설정이 아니라 여러 대가 함께 쓰는 좌표다.

## 🧒 열 살에게

교실마다 시계가 조금씩 다르면 누가 먼저 왔는지를 두고 다투게 되지? 그래서 학교는 종 하나를 정해 두고 다들 그 종에 맞춰. 각자 시계를 믿으면 같은 일을 두고도 순서를 다르게 기억하게 돼.

## ❓ 이해했는지

- 코드를 안 바꿨는데 어제부터 요청이 거절되는 일은 왜 생기나 → 실제 사례
- 어긋난 시각을 한 번에 당기지 않고 빠르기부터 손보는 이유는 무엇인가 → 주의사항
- 원본 시계에서 몇 다리 건넌 서버인지는 무엇을 보고 아나 → 구성
