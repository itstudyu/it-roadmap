# Load Test (부하 테스트)

## 📝 정의

Load Test는 **예상한 만큼의 사용량을 미리 걸어 보는 시험**이다.

성능 문제는 부하가 걸리기 전까지 대개 드러나지 않는다. 그래서 진짜 사용자가 몰려오기 전에 가짜 사용자를 만들어 같은 사용량을 먼저 만들어 보고, 그때의 응답 시간과 실패율을 잰다.

### 이름
Load :: 얹히는 짐
Test :: 시험
= 붙여 읽으면 "짐을 얹어 보는 시험". 무거워졌을 때 어디가 먼저 휘는지 보는 것이다

### 비유
새로 놓은 다리를 열기 전에 모래주머니 실은 트럭을 줄줄이 올려 보는 하중 시험.

### 예
예매가 열리자마자 화면이 멈추고 대기 숫자만 돌던 그 순간을, 열기 전에 미리 만들어 보는 일이다.

## 🖼️ 그림으로 보기

```도해
흐름: 부하 테스트는 무엇을 걸어서 무엇을 보나
각본 :: 진짜 사용자가 하는 일을 그대로 적는다
가짜 사용자 :: 그 각본을 수백 명이 동시에 돈다
올리기 :: 전체 시간의 5~15% 동안 목표까지 늘린다
버티기 :: 올린 시간의 다섯 배는 그 사용량을 유지한다
< 받은 답 :: 응답 시간·초당 요청 수·실패율이 돌아온다
= 예상한 사용량을 미리 만들어 걸고, 그때 돌아오는 답이 얼마나 늦고 얼마나 깨지는지 잰다
```

## ⚠️ 해결하는 문제

```도해
대조: 열기 전에 걸어 보지 않으면 무슨 일이 생기나
안 걸어 보면 || 걸어 보면
드러나는 때 :: 진짜 손님 앞 || 아무도 없을 때
느려진 원인 :: 짐작으로 찾는다 || 지표로 좁힌다
서버 수 :: 감으로 잡는다 || 재 보고 정한다
= 성능 문제는 부하가 걸려야 보인다. 그 부하를 먼저 만들어 보는 것이다
```

기능 시험은 혼자 한 번 눌러 보는 것이라 대개 통과한다. 같은 화면이 동시에 수백 번 열릴 때에만 드러나는 문제는 그 방식으로 잡히지 않는다.

부하 테스트는 그 조건을 손으로 만든다. 예상 사용량에서 얼마나 빠른지, 그때 느려지는 곳이 어디인지를 열기 전에 숫자로 남긴다. 목표를 못 채우면 서버를 늘리든 코드를 고치든 선택지가 생기고, 그 판단이 장애 한복판이 아니라 책상에서 이뤄진다.

## ⚙️ 작동 원리

각본은 진짜 사용자의 행동을 흉내 낸 요청 묶음이다. 부하 발생기 한 대가 그 각본을 돌려 가상 사용자를 한꺼번에 만들어 내고, 규모를 키우려면 발생기 수를 늘린다.

지표는 두 갈래로 본다. 클라이언트 쪽에는 가상 사용자 수, 응답 시간, 초당 요청 수가 있고, 서버 쪽에는 저장소 읽기 횟수, 응답 코드 분포, 자원 사용량이 있다. 둘을 나란히 놓아야 느려진 자리가 앱인지 저장소인지 갈린다. 한쪽만 보면 "느리다" 에서 더 못 나간다.

통과 기준을 미리 적어 둘 수도 있다. 평균 응답 시간이나 오류 수가 정해 둔 값을 넘으면 그 시험을 실패로 처리한다. 이 기준이 있으면 부하 테스트를 배포 파이프라인 안에 관문으로 걸 수 있다. 잘못된 주소를 때리는 시험이 끝없이 도는 일을 막으려고 자동 중단 조건도 함께 건다.

## 📊 비교: 부하를 어떻게 거느냐에 따른 시험 종류

| 시험 | 얼마나 거나 | 무엇을 보나 |
|---|---|---|
| **Smoke** | 아주 조금 | 각본 자체가 도는지 |
| **Load** | 평소 예상만큼 | 그 사용량에서의 응답 시간 |
| **Stress** | 예상보다 많이 | 한계를 넘겼을 때의 모습 |
| **Spike** | 갑자기 확 | 짧고 큰 폭증을 넘기나 |
| **Soak** | 평소만큼 오래 | 오래 돌 때 새는 곳 |
| **Breakpoint** | 끊길 때까지 | 한계 지점이 어디인가 |

## 💡 실제 사례

- **출시 전 용량 산정** — 열고 나서 예상되는 만큼을 미리 걸어 보고 서버를 몇 대로 둘지 정한다.
- **배포 관문** — 릴리스 후보에 부하를 걸고, 평균 응답 시간이 기준을 넘으면 그 빌드를 세운다.
- **병목 가르기** — 부하 중에 클라이언트 지표와 서버 지표를 나란히 놓고, 느려진 곳이 앱인지 저장소인지 가른다.

## 🚫 흔한 오해

- **부하는 세게 걸수록 좋은 시험이다** — 그건 스트레스 테스트다. 부하 테스트는 평소 예상만큼만 걸고 그 사용량에서 얼마나 빠른지를 잰다. 목적이 다르니 결과를 섞어 읽으면 안 된다.
- **통과했으니 실제로도 버틴다** — 각본에 없는 행동, 실제 데이터 양, 지역별 분포는 재지 않았다. 통과에는 "이 각본, 이 사용량에서는" 이라는 조건이 늘 붙는다.
- **한 번 재 두면 된다** — 코드와 데이터가 쌓이면 같은 사용량에서도 느려진다. 배포마다 돌려서 지난 결과와 견줘야 느려진 시점이 잡힌다.

## 📝 정리

**"손님이 오기 전에 미리 밀어 넣어 보는 시험"** 이라고 읽으면 된다. 서서히 올려 목표 사용량에서 한참 버티게 두고, 그때 돌아오는 응답 시간과 실패율을 남기는 것이 전부다. 세게 때려 한계를 보는 일은 스트레스 테스트가 따로 맡는다.

## 🧒 열 살에게

새로 놓은 다리를 사람들한테 열어 주기 전에, 무거운 짐차를 줄줄이 올려서 흔들리는지 먼저 봐. 그때 삐걱대면 그날 고치면 되고 아무도 안 다치잖아. 열고 나서 알면 그때는 이미 사람이 위에 서 있는 거야.

## ❓ 이해했는지

- 부하를 서서히 올렸다가 한참 그대로 두는 이유는 무엇인가 → 그림
- 시험은 통과했는데 행사 당일에 결제가 멈췄다면 무엇을 의심해야 하나 → 흔한 오해
- 느려진 곳이 앱인지 저장소인지는 무엇을 보고 가르나 → 작동 원리
