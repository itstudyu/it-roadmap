# DevOps

## 📝 정의

DevOps는 **개발과 운영을 한 팀이 함께 맡는 방식**이다.

예전에는 개발팀이 코드를 만들어 넘기면 운영팀이 배포하고 지켰다. 그 경계에서 배포가 밀리고 장애 책임이 갈렸다. DevOps는 경계를 지우고 커밋부터 배포와 감시까지를 자동화된 한 줄기로 잇는다.

### 비유
요리와 서빙을 같은 사람이 맡는 작은 식당. 손님 반응이 곧바로 주방에 닿아서 다음 접시가 달라진다.

### 예
새벽에 점검 공지를 띄우고 몇 시간씩 서비스를 세우던 일이 요즘 앱에서 드물어진 이유다.

## 🖼️ 그림으로 보기

```도해
흐름: 코드를 커밋하면 배포까지 무엇이 자동으로 일어나나
커밋 :: 개발자가 저장소에 코드를 올린다
빌드 :: 컴파일하고 의존성을 푼다
테스트 :: 실패하면 여기서 멈추고 알린다
패키징 :: 결과물을 이미지로 묶어 올린다
배포 :: 테스트 환경에 먼저, 통과하면 운영으로
@ 모니터링 :: 로그와 지표를 보고 다음 커밋에 반영한다
= 개발에서 운영까지 벽 없이 한 바퀴 돈다. 사람 손은 맨 앞 커밋뿐이다
```

## ⚠️ 해결하는 문제

```도해
대조: 변경을 모아뒀다 한꺼번에 배포하면 어떻게 되나
모아서 배포 || 자주 배포
한 번에 나가는 양 :: 변경 수백 개 || 변경 몇 개
장애 원인 찾기 :: 후보가 너무 많다 || 방금 그것
되돌리기 :: 통째로 되감는다 || 한 건만 뺀다
= 배포를 작게 자르면 무엇이 잘못됐는지가 저절로 좁혀진다
```

분기에 한 번 배포하면 그 한 번에 변경 수백 개가 실린다. 장애가 나도 어느 변경 탓인지 알기 어렵고, 되돌리려면 멀쩡한 것까지 함께 되감아야 한다. 그래서 배포가 무서워지고, 무서우니 더 모으게 되고, 모을수록 더 위험해진다.

DevOps는 그 고리를 반대로 돌린다. 작게 자주 내보내면 방금 나간 것만 의심하면 되고, 되돌릴 것도 그 한 건이다. 자주 하려면 손으로 할 수 없으니 자동화가 따라온다.

## ⚙️ 작동 원리

세 가지가 맞물린다. 커밋을 방아쇠로 빌드와 테스트와 배포가 이어지는 CI/CD, 서버와 네트워크 구성을 파일로 적어 버전 관리하는 IaC, 그리고 개발과 운영 환경을 같게 만드는 컨테이너다.

```yaml
on:
  push:
    branches: [main]
jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2
      - run: npm test
      - run: docker build -t myapp:latest .
      - run: docker push myapp:latest
```

여기서 `npm test`가 실패하면 뒤 단계는 실행되지 않는다. 잘못된 것이 운영까지 가지 못하게 막는 문이 이 자리다.

## 📊 비교

| 항목 | 모아서 배포하던 방식 | DevOps |
|---|---|---|
| 배포 주기 | 분기 또는 연 단위 | 하루에도 여러 번 |
| 팀 구조 | 개발과 운영이 나뉨 | 한 팀이 함께 맡음 |
| 배포 위험 | 큰 변경을 드물게 | 작은 변경을 자주 |
| 환경 차이 | 개발과 운영이 다름 | 컨테이너로 맞춤 |
| 초기 비용 | 낮다 | 도구와 인프라에 든다 |

## 💡 실제 사례

- **손으로 하던 배포 없애기** — 배포 절차를 스크립트로 옮기면 순서를 외우거나 밤에 모여 배포할 일이 없어진다.
- **환경 차이로 나는 버그** — 내 컴퓨터에서는 되는데 운영에서 안 되는 문제는 같은 컨테이너 이미지를 쓰면 크게 줄어든다.
- **먼저 아는 장애** — 지표와 로그를 자동으로 모아두면 사용자가 알려주기 전에 알림이 먼저 온다.

## 🚫 흔한 오해

- **도구를 깔면 DevOps다** — 파이프라인을 붙여놔도 배포 책임이 여전히 다른 팀에 있으면 전과 같다. 도구는 일을 대신할 뿐 경계를 지우지는 못한다.
- **DevOps는 직군 이름이다** — 일하는 방식이지 사람 이름표가 아니다. 한 명을 뽑아 배포를 다 맡기면 넘기던 벽이 자리만 옮긴 것이다.
- **자동화하면 사람이 볼 일이 없어진다** — 파이프라인 자체도 고장 나고 손봐야 한다. 반복 작업이 옮겨간 것이지 사라진 것이 아니다.

## 🚨 주의사항

- **작은 팀에는 과할 수 있다.** 도구를 다 갖추는 비용이 얻는 것보다 클 수 있어서, 자주 아픈 자리부터 하나씩 자동화하는 편이 낫다.
- **파이프라인도 지켜야 한다.** 배포 자동화는 운영에 바로 닿는 통로라, 여기 붙은 권한과 비밀 값이 새면 서버가 뚫린 것과 같다.

## 📝 정리

DevOps는 개발과 운영을 갈라놓던 경계를 지우고 커밋부터 배포까지를 자동화하는 방식이다. 작게 자주 내보내서 장애 원인을 좁히고 되돌리기 쉽게 만드는 것이 핵심이다. 도구를 들이는 것만으로는 되지 않고 누가 배포에 책임을 지는지가 함께 바뀌어야 한다.

## ❓ 이해했는지

- 배포를 자주 하면 더 위험할 것 같은데 왜 반대인가 → 해결하는 문제
- 파이프라인에서 테스트가 실패하면 그다음에는 무슨 일이 일어나나 → 작동 원리
- CI/CD 도구를 다 깔았는데도 배포가 여전히 한 달에 한 번이라면 어디를 봐야 하나 → 흔한 오해
