# DevOps

## 📝 정의

DevOps는 Development(개발)과 Operations(운영)의 합성어로, 소프트웨어 개발과 운영 사이의 벽을 허물고 두 팀이 협력하여 제품 개발부터 배포, 운영까지의 전체 사이클을 자동화하고 단축하는 문화, 방법론, 기술의 집합입니다. DevOps는 단순히 도구의 모음이 아니라, 개발팀과 운영팀이 함께 책임을 지고 빠르고 안정적으로 가치를 전달하는 철학입니다.

DevOps의 핵심은 자동화와 협업입니다. 과거에는 개발팀이 코드를 작성하고 운영팀에 넘겨주는 분리된 구조였다면, DevOps에서는 개발팀이 배포와 운영까지 책임지고, 운영팀이 인프라 자동화와 모니터링을 통해 개발을 지원합니다. 이를 통해 배포 주기를 주 단위에서 일일 또는 시간 단위로 단축할 수 있으며, 장애 대응도 빨라집니다.

> DevOps = 개발과 운영의 경계를 허물고 전체 라이프사이클을 자동화하여 빠르고 안정적인 가치 전달을 추구하는 문화 및 방법론

**비유 1**: DevOps는 자동차 생산 라인과 같습니다. 과거에는 엔진 제작팀, 차체팀, 조립팀이 따로 일했다면(폭포수), 현대의 자동차 공장은 모든 팀이 함께 일하며 자동화를 통해 빠르게 자동차를 생산합니다(DevOps).

**비유 2**: DevOps는 음식 배달 앱과 같습니다. 주문 접수, 식당에 전달, 요리, 배달 각 단계가 실시간으로 추적되고 자동화되어, 고객이 빠르게 음식을 받습니다. 한 단계의 문제(예: 요리 지연)가 즉시 감지되고 대응됩니다.

## 🎯 핵심 개념

### 1. CI/CD (Continuous Integration / Continuous Deployment)
CI/CD는 DevOps의 핵심입니다. 개발자가 코드를 커밋하는 즉시 자동으로 빌드, 테스트, 배포가 이루어집니다. 과거의 주 단위 배포에서 하루에 여러 번의 배포가 가능하게 되므로, 버그 수정도 빠르고 새로운 기능도 빠르게 릴리스할 수 있습니다.

### 2. IaC (Infrastructure as Code)
인프라를 코드로 관리하는 개념입니다. 서버 구성, 네트워크, 데이터베이스 등을 YAML, JSON 같은 파일로 정의하고 버전 관리하며, 필요할 때 자동으로 프로비저닝합니다. 이를 통해 인프라 관리도 코드처럼 재현 가능하고 자동화됩니다.

### 3. 자동화와 모니터링
DevOps는 반복적인 작업을 최대한 자동화합니다. 배포, 테스트, 보안 검사, 로그 수집 등을 자동화하여 수동 작업을 줄입니다. 동시에 프로덕션 환경을 지속적으로 모니터링하여 문제를 조기에 발견하고 대응합니다.

## ⚠️ 해결하는 문제

### 문제 1: 배포 위험과 지연
전통적인 개발에서는 변경 사항이 모여서 분기마다 또는 연간 몇 번 배포합니다. 한 번의 배포에 수백 개의 변경이 포함되므로, 어느 변경이 장애를 일으켰는지 추적하기 어렵고 롤백도 어렵습니다. DevOps는 작은 변경을 자주 배포하므로 위험을 낮추고 빠르게 대응할 수 있습니다.

### 문제 2: 개발과 운영 팀의 갈등
개발팀은 빠른 변경을 원하고, 운영팀은 안정성을 원했습니다. 이 갈등으로 변경 요청이 지연되고, 배포 후 문제 발생 시 책임 전가가 일어났습니다. DevOps는 두 팀을 하나로 통합하여 같은 목표(빠르고 안정적인 서비스)를 추구하게 합니다.

### 문제 3: 환경 차이로 인한 버그
개발 환경에서는 정상이지만 프로덕션 환경에서는 장애가 나는 현상이 자주 발생했습니다. DevOps는 Docker 같은 컨테이너 기술로 개발, 테스트, 프로덕션 환경을 동일하게 만들어 이 문제를 해결합니다.

## ⚙️ 작동 원리

**DevOps 파이프라인의 상세 동작:**

**1단계: 코드 커밋**
개발자가 코드를 작성하고 Git 저장소에 커밋합니다. 이 순간이 자동화의 시작입니다.

**2단계: 자동 트리거**
Git에 코드가 커밋되면 CI/CD 시스템(예: GitHub Actions, Jenkins)이 자동으로 트리거됩니다.

**3단계: 빌드**
소스 코드를 컴파일하고 의존성을 해결합니다. 빌드 실패 시 개발자에게 즉시 알림이 갑니다.

**4단계: 자동 테스트**
단위 테스트, 통합 테스트, E2E 테스트가 자동으로 실행됩니다. 테스트 실패 시 배포를 중지합니다.

**5단계: 코드 품질 검사**
정적 분석 도구(SonarQube 등)가 코드 품질을 검사하고, 보안 취약점을 스캔합니다.

**6단계: 도커 이미지 생성**
빌드 결과물을 Docker 이미지로 패키징하고 레지스트리에 푸시합니다.

**7단계: 자동 배포**
Docker 이미지를 스테이징 환경에 먼저 배포하고 추가 테스트를 합니다. 성공 후 프로덕션 배포 승인을 기다리거나, 자동으로 배포합니다(Continuous Deployment).

**8단계: 실시간 모니터링**
프로덕션 환경의 로그, 메트릭, 에러를 수집하고 모니터링합니다. 문제 발생 시 자동으로 알림이 갑니다.

**9단계: 피드백 루프**
모니터링 데이터를 분석하여 다음 계획에 반영합니다.

**예시: GitHub Actions를 통한 자동 배포**
```yaml
name: CI/CD Pipeline

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v2

      - name: Run tests
        run: npm test

      - name: Build Docker image
        run: docker build -t myapp:latest .

      - name: Push to registry
        run: docker push myapp:latest

      - name: Deploy to K8s
        run: kubectl set image deployment/myapp myapp=myapp:latest
```

## 📊 비교

| 항목 | DevOps | 전통적 개발 방식 |
|------|--------|-----------|
| 배포 주기 | 1일 여러 번 (수십 번) ⚡ | 분기 또는 연간 (1~4회) 🐢 |
| 팀 구조 | 개발과 운영 통합 (Cross-functional) | 개발팀 ↔ 운영팀 분리 |
| 자동화 수준 | 매우 높음 (90% 이상) | 낮음 (10~20%) |
| 배포 위험도 | 낮음 (작은 변경 자주) | 높음 (큰 변경 드물게) |
| 장애 복구 시간 | 매우 빠름 (분 단위) | 느림 (시간 단위) |
| 환경 일관성 | 높음 (컨테이너화) | 낮음 (환경 차이) |
| 모니터링 | 실시간 자동화 | 수동 모니터링 |
| 초기 투자 | 높음 (인프라/도구) | 낮음 |

## ✅ 장단점

**장점:**
- 배포 주기를 획기적으로 단축하여 시장 진입 속도가 빠릅니다.
- 작은 변경을 자주 배포하므로 위험을 최소화합니다.
- 자동화로 수동 작업을 줄여 인적 오류를 감소시킵니다.
- 개발과 운영 팀의 협업이 증가하여 소통이 개선됩니다.
- 실시간 모니터링으로 문제를 조기에 발견하고 빠르게 해결합니다.
- 인프라를 코드로 관리하여 재현 가능성과 유지보수성이 높습니다.
- 장애 시 빠른 롤백이 가능하여 다운타임을 최소화합니다.

**단점:**
- 초기 인프라 구축 비용과 복잡도가 높습니다.
- 다양한 도구와 기술 스택을 학습해야 합니다.
- 문화 변화가 어렵습니다. 조직 전체의 마인드셋 변화가 필요합니다.
- 보안 관리가 복잡해집니다. 자동화 파이프라인 자체도 보호해야 합니다.
- 분산 시스템의 복잡성으로 디버깅이 어려울 수 있습니다.
- 작은 팀에서는 오버엔지니어링이 될 수 있습니다.

## 💡 실제 사례

**사례 1: GitHub Actions를 통한 자동 배포**
```
개발자가 코드 커밋
    ↓
GitHub가 자동으로 감지
    ↓
GitHub Actions 워크플로우 실행
    ├─ 코드 체크아웃
    ├─ 의존성 설치
    ├─ 테스트 실행
    ├─ Docker 이미지 빌드
    └─ 레지스트리에 푸시
    ↓
Kubernetes 자동 배포
    ↓
모니터링 시작
```

**사례 2: Netflix의 DevOps 사례**
Netflix는 매일 수백 번의 배포를 수행합니다. 마이크로서비스 아키텍처와 자동화된 배포 파이프라인으로 한 서비스의 문제가 다른 서비스에 영향을 미치지 않도록 합니다. 장애 발생 시에도 자동으로 문제 서비스를 종료하고 다른 인스턴스로 트래픽을 우회(Chaos Engineering)합니다.

**사례 3: 아마존의 마이크로배포**
Amazon은 "Two Pizza Team" 문화를 도입했습니다. 각 팀(약 6~10명)이 자신의 서비스를 소유하고, 독립적으로 개발하고, 독립적으로 배포합니다. 각 팀은 하루에 수십 번의 배포를 할 수 있으며, 이를 통해 엄청난 민첩성을 확보했습니다.

**사례 4: CI/CD 성공 사례**
한 팀이 Jenkins를 도입하여 다음과 같이 개선했습니다:
- 배포 시간: 수동 배포 2시간 → 자동 배포 5분
- 배포 빈도: 월 1회 → 일 10회 이상
- 버그 발견 시간: 프로덕션 배포 후 → 개발 단계에서 자동 테스트
- 팀 스트레스: 배포 시기 불안감 → 안정적 배포로 신뢰성 증가

## 🔗 관련 용어

- **CI (Continuous Integration)**: 코드 변경이 주기적으로 빌드/테스트되어 통합되는 프로세스
- **CD (Continuous Deployment)**: 자동으로 프로덕션 환경에 배포하는 프로세스
- **아티팩트**: 빌드 결과물 (JAR, WAR, Docker 이미지 등)
- **Jenkinsfile**: Jenkins CI/CD 파이프라인 정의 파일
- **GitHub Actions**: GitHub 기본 제공 CI/CD 서비스
- **Docker**: 애플리케이션을 컨테이너로 패키징하는 기술
- **Kubernetes**: 컨테이너 오케스트레이션 플랫폼
- **Prometheus**: 메트릭 수집 및 모니터링 도구
- **Grafana**: 메트릭 시각화 대시보드
- **Infrastructure as Code (IaC)**: 인프라를 코드로 정의/관리 (Terraform, Ansible)
- **Blue-Green Deployment**: 두 환경을 번갈아 가며 배포하는 무중단 배포 방식
- **Canary Deployment**: 새 버전을 작은 비율의 사용자에게만 먼저 배포하는 방식
- **롤백**: 배포 후 문제 발생 시 이전 버전으로 복구
