# Infrastructure as Code (코드형 인프라)

## 📝 정의

Infrastructure as Code 는 **인프라를 손이 아니라 코드로 만드는 방식**이다.

서버·망·부하 분산기·연결 구조를 사람이 콘솔에서 하나씩 만들지 않고, 원하는 최종 상태를 파일에 적어 두고 그 파일을 실행해 만든다. 같은 소스가 늘 같은 실행 파일을 내놓듯, 같은 정의 파일은 배포할 때마다 같은 환경을 만든다.

### 이름
Infra :: 밑에 깔린
structure :: 구조물
as Code :: 코드의 모습으로
= 붙여 읽으면 "밑에 깔린 구조물을 코드의 모습으로". 밑판을 손이 아니라 파일로 다룬다

### 비유
집을 짓는 설계 도면. 도면대로 지으면 같은 집이 몇 채든 똑같이 나오고, 고칠 곳은 지어 놓은 집이 아니라 도면에서 고친다.

### 예
서버를 두 대 더 늘려 달라는 말에 콘솔을 열지 않고, 파일에 적힌 대수 2 를 4 로 고쳐 올리는 그 장면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 파일에 적어 둔 대로 서버 한 대가 어떻게 생기나
사람 :: 원하는 최종 상태를 파일에 적는다
저장소 :: 그 파일을 버전으로 남긴다
도구 :: 적힌 상태와 지금 상태를 견준다
클라우드 :: 모자란 것만 실제로 만든다
< 도구 :: 만들어진 결과를 받아 기록에 적는다
= 사람이 만드는 게 아니라, 적어 둔 대로 도구가 만든다
```

## ⚠️ 해결하는 문제

```도해
대조: 환경을 손으로 만들면 무엇이 어긋나나
손으로 || 코드로
개발과 운영 :: 조금씩 달라진다 || 같은 파일에서
다시 만들기 :: 기억을 더듬는다 || 그대로 적용
바뀐 내역 :: 남지 않는다 || 커밋에 남는다
= 손으로 만든 환경은 하나뿐인 눈송이가 된다. 코드로 만들면 몇 벌이든 같다
```

Microsoft 문서는 IaC 가 나온 까닭을 **환경 표류**(environment drift) 하나로 적는다. 환경마다 설정을 따로 손보다 보면 각각이 자동으로는 재현할 수 없는 "눈송이"가 되고, 환경 사이의 차이가 그대로 배포 사고가 된다. AWS 문서도 같은 자리를 짚는다 — 스크립트와 런북을 사람이 손으로 따라가는 방식은 문서를 자주 갱신하지 않으면 배포를 막는 걸림돌이 되고, 새 환경 만들기가 반복 가능하지도 믿을 만하지도 않게 된다.

IaC 는 원하는 환경 상태를 잘 적힌 코드로 표현해서 손 설정을 없앤다. 고칠 것이 있으면 대상이 아니라 **원본을 고친다.** 그러면 운영과 같은 모양의 시험 환경을 필요할 때마다 여러 벌 띄웠다가 걷어낼 수 있다.

## ⚙️ 작동 원리

IaC 는 되도록 **선언형** 정의 파일로 쓴다. 선언형 파일은 그 환경에 무엇이 필요한지를 적고, 그것을 어떻게 만드는지는 적지 않는다. 서버의 버전과 설정은 적되 설치 절차는 안 적는 식이다. 절차를 안 적으면 그 인프라 제공자가 가진 더 나은 방법을 쓸 여지가 남고, 배포 스크립트 같은 절차 코드를 계속 손봐야 하는 기술 부채도 줄어든다.

두 번째 기둥은 **멱등성**이다. 같은 명령을 몇 번 돌리든 대상 환경이 늘 같은 설정에 도달한다는 뜻이고, 시작 상태가 무엇이었든 상관없다. 이루는 길은 둘이다 — 이미 있는 대상을 자동으로 맞춰 놓거나, 있던 것을 버리고 새로 세우거나.

선언 문법에는 표준이 없다. 대상 플랫폼이 요구하는 대로 정해져서, 플랫폼마다 YAML · JSON · XML 같은 파일 형식을 쓴다.

## 💡 실제 사례

- **시험 환경을 필요할 때만 세운다** — 운영과 같은 모양의 환경을 정의 파일로 여러 벌 띄우고, 다 쓰면 걷어낸다.
- **인프라 변경을 코드처럼 다룬다** — 망 규칙 하나를 여는 일도 애플리케이션 코드와 같은 저장소에 커밋으로 쌓여 변경 이력이 남는다.
- **설정 실수를 미리 잡는다** — 인프라 코드 자체를 검사해 잘못된 설정을 배포 전에 걸러낸다.

## 🚫 흔한 오해

- **급한 것만 콘솔에서 손으로 고치고 코드는 나중에 맞추면 된다** — 그 순간부터 파일과 실제가 다르다. 다음 적용이 손으로 고친 것을 도로 지우거나, 아무도 그 차이를 모른 채 다음 환경이 잘못 만들어진다.
- **자동화 스크립트를 짜 두었으면 그게 IaC 다** — 절차를 순서대로 적은 스크립트는 시작 상태가 다르면 결과도 다르다. IaC 가 요구하는 것은 몇 번을 돌려도 같은 상태에 도달하는 멱등성이다.
- **인프라는 전부 코드로 두는 편이 항상 낫다** — 한 번 세우고 곧 버릴 실험 환경까지 정의 파일로 만들면 얻는 반복성보다 파일을 손보는 비용이 커진다. 값을 하는 자리는 같은 환경을 여러 번, 여러 벌 만들어야 하는 곳이다.

## 📝 정리

**"환경을 손이 아니라 파일에서 고치는 방식"** 이라고 읽으면 된다. 손으로 만든 환경은 저마다 하나뿐인 눈송이가 되어 개발과 운영이 조금씩 어긋나지만, 같은 정의 파일에서 만든 환경은 몇 벌을 세워도 같다. 그래서 이 방식을 재는 잣대는 "자동화했나" 가 아니라 "몇 번을 돌려도 같은 상태에 도달하나" 다.

## 🧒 열 살에게

블록으로 집을 만들 때 설명서를 보고 만들면 친구도 똑같은 집을 만들 수 있지? 설명서 없이 손으로만 만들면 두 번째 집은 어딘가 달라져. 그래서 만드는 법을 종이에 다 적어 두고, 고칠 일이 생기면 집이 아니라 종이를 고치는 거야.

## ❓ 이해했는지

- 같은 파일을 두 번 적용했는데 서버가 두 대로 늘지 않는 이유는 무엇인가 → 작동 원리
- 개발에서는 되던 것이 운영에서만 안 되는 일이 왜 되풀이되나 → 해결하는 문제
- 파일로 적어 두었는데도 콘솔에서 누가 손으로 고치면 무슨 일이 생기나 → 흔한 오해
