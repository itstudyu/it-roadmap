# RAID (레이드)

## 📝 정의

RAID는 **여러 원반을 묶어 빠르게 또는 안 죽게 만드는 방식**이다.

원반은 반드시 죽는다. 언제 죽느냐만 모를 뿐이다. RAID 는 그 사실을 전제로 깔고, 여러 장을 하나처럼 보이게 묶어서 속도를 합치거나 한 장의 고장을 견디게 한다. 리눅스에서는 커널의 md 드라이버가 이 일을 맡고, 묶고 나면 원반 대신 `/dev/md0` 같은 장치 하나를 쓴다.

### 이름
Redundant :: 남는, 여벌의
Array :: 줄지어 세운 것
Independent :: 따로 도는
Disks :: 원반들
= 붙여 읽으면 "따로 도는 원반을 여벌까지 줄 세운 것". 여벌이 있어야 한 장이 죽어도 산다

### 비유
같은 서류를 두 벌 복사해 서랍 두 칸에 따로 넣거나, 한 벌을 반씩 갈라 두 칸에 나눠 넣는 일.

### 예
mdadm --detail 을 쳤더니 State 줄이 clean 이 아니라 degraded 로 바뀌어 있던 순간이다. 서비스는 멀쩡히 돌고 있었다.

## 🖼️ 그림으로 보기

```도해
대조: 같은 원반 두 장을 0 으로 묶을 때와 1 로 묶을 때 무엇이 다른가
RAID 0 |=| RAID 1
쓰는 용량 :: 두 장을 다 쓴다 || 한 장 몫만 쓴다
읽기 속도 :: 갈라 담아 빠르다 || 한 장 속도쯤
한 장 고장 :: 전부 잃는다 || 그대로 돈다
= 0 은 빠르라고, 1 은 안 죽으라고 묶는다. 같은 두 장인데 목적이 반대다
```

## ⚠️ 해결하는 문제

```도해
대조: 원반 한 장에 다 넣어 두면 무엇이 걸리나
한 장에 || 묶어서
한 장 고장 :: 그대로 멈춘다 || 남은 장으로 돈다
한계 속도 :: 그 한 장이 끝 || 여러 장을 합친다
한계 용량 :: 그 한 장이 끝 || 이어 붙여 늘린다
= 원반은 반드시 죽는다. 언제 죽느냐만 모를 뿐이다
```

원반 한 장에 다 넣어 두면 세 가지가 한꺼번에 그 한 장에 묶인다. 속도도 용량도 그 장의 몫이 천장이고, 무엇보다 그 장이 죽는 날이 곧 서비스가 멈추는 날이다. 백업이 있어도 마찬가지다. 백업은 잃은 것을 되찾게 해 주지 실시간으로 도는 일을 대신해 주지 않는다.

RAID 는 이 셋을 **묶는 방식을 골라서** 나눠 푼다. 갈라 담으면 속도와 용량이 합쳐지고, 겹쳐 담으면 한 장이 빠져도 남은 장으로 계속 돈다. 무엇을 얻고 무엇을 내줄지는 레벨 숫자 하나로 정해진다.

## ⚙️ 작동 원리

만드는 명령은 한 줄이다. AWS 가 EBS 볼륨 여러 장을 묶는 예로 보여주는 형태가 그대로 표준이다.

```
sudo mdadm --create --verbose /dev/md0 --level=0 --name=MY_RAID --raid-devices=2 /dev/xvdb /dev/xvdc
```

`--level` 숫자가 묶는 방식이고, 만들고 나면 `/dev/md0` 위에 파일 시스템을 얹는다. 재부팅해도 다시 조립되게 하려면 `mdadm --detail --scan` 의 결과를 `/etc/mdadm.conf` 에 남겨 둬야 한다. 이 줄을 빼먹으면 부팅 뒤에 배열이 안 서고, 그러면 `/etc/fstab` 에서 마운트도 실패한다.

지금 상태는 한 줄로 본다.

```
$ cat /proc/mdstat
Personalities : [raid0]
md0 : active raid0 xvdc[1] xvdb[0]
      41910272 blocks super 1.2 512k chunks
```

커널 문서는 두 가지를 따로 적어 둔다. 배열이 지금 어떤 상태인지는 `clean`(밀린 쓰기가 없다), `active`(입출력과 맞추기가 함께 돈다), `readonly` 같은 이름이고, 지금 무슨 작업 중인지는 `resync`, `recover`, `check`, `repair`, `idle` 로 따로 센다. 한 장이 빠졌다는 사실은 `mdadm --detail` 의 State 줄에 `degraded` 로 붙고, 여벌이 있는 방식이라면 남은 장으로 계속 돌면서 `recover` 로 잃은 여벌을 다시 만든다. 커널 문서가 `recover` 를 예비 원반이 죽거나 없어진 장치를 대신해 만들어지는 중이라고 적은 그것이라, 미리 꽂아 둔 예비 원반이 있으면 사람이 손대기 전에 그 자리로 들어간다.

가장 위험한 순간도 커널 문서가 못 박아 뒀다. RAID 5·6 이 아직 정리되지 않은 상태와 한 장이 빠진 상태에 동시에 놓이면 패리티를 믿을 수 없고 빠진 자리도 되살릴 수 없어서 **알아챌 수 없는 데이터 손상**이 생길 수 있다. 재구성 중인 배열이 가장 약한 배열이라는 말이 여기서 나온다.

## 📊 비교: 흔히 쓰는 셋은 무엇을 내주고 무엇을 얻나

| 묶는 방식 | 쓰는 용량 | 한 장이 죽으면 | 주로 쓰는 자리 |
|---|---|---|---|
| **RAID 0** | 전부 | 배열 전체를 잃는다 | 속도만 필요한 임시 작업 공간 |
| **RAID 1** | 절반 | 그대로 돈다 | 작지만 죽으면 안 되는 자리 |
| **RAID 5·6** | 한두 장 몫을 뺀 나머지 | 돌긴 하지만 재구성이 위태롭다 | 원반이 많은 저장 전용 기계 |

클라우드 원반 위에서는 셈이 또 달라진다. AWS 는 EBS 에 RAID 5 와 6 을 권하지 않는다 — 패리티를 쓰는 데 IOPS 가 들어가서 같은 구성 대비 20~30% 적은 IOPS 가 나오고, 볼륨 두 장짜리 RAID 0 이 값이 두 배인 네 장짜리 RAID 6 보다 나을 수 있다고 적는다. RAID 1 도 권하지 않는데, 같은 값을 두 볼륨에 동시에 쓰느라 대역폭만 더 쓰고 쓰기 속도는 안 빨라지기 때문이다. EBS 자체가 이미 가용 영역 안의 여러 대에 복제되어 있다는 것이 그 밑에 깔린 이유다.

## 💡 실제 사례

- **속도만 필요한 작업 공간** — 중간 결과를 쏟아 놓는 자리라면 0 으로 묶어 원반 수만큼 처리량을 올린다. 날아가면 다시 만들면 되는 값이라 여벌이 필요 없다.
- **죽으면 안 되는 자리** — 1 로 묶어 두면 한 장이 빠져도 기계가 계속 돈다. 다만 AWS 는 배열에서 부팅하는 것 자체를 피하라고 적는다. 한 장치가 죽으면 운영체제가 안 뜰 수 있어서다.
- **일관된 백업 뜨기** — 배열을 이루는 볼륨의 스냅숏을 따로따로 뜨면 시점이 어긋나 복원했을 때 배열이 깨진다. 여러 볼륨을 한 시점으로 묶어 뜨는 기능을 쓴다.

## 🚫 흔한 오해

- **RAID 를 걸었으니 백업은 안 해도 된다** — 지우기와 덮어쓰기는 모든 장에 똑같이 반영된다. 이 묶음이 막아 주는 것은 원반의 물리적 고장 하나뿐이다.
- **RAID 는 무조건 여벌을 만든다** — 0 에는 여벌이 없다. AWS 문서도 RAID 0 에서 한 볼륨을 잃으면 배열 전체의 데이터가 사라진다고 적는다. 이름에 R 이 들어 있다고 다 여벌은 아니다.
- **원반을 많이 묶을수록 안전해진다** — 장수가 늘면 그중 하나가 죽을 확률도 같이 는다. 5·6 은 재구성하는 동안 또 한 장이 빠지면 그대로 끝이라, 커널 문서가 그 겹침을 가장 위험한 상태로 적어 뒀다.

## 📝 정리

**"원반 여러 장을 한 장처럼 쓰되 무엇을 내줄지 고르는 일"** 이라고 읽으면 된다. 0 은 여벌을 내주고 속도를 얻고, 1 과 5·6 은 용량을 내주고 고장 한 번을 견딘다. 어느 쪽이든 지운 파일은 모든 장에서 같이 지워지므로 백업은 따로 있어야 한다.

## 🧒 열 살에게

중요한 종이를 한 장만 갖고 있으면 그게 찢어지는 날 끝이지? 그래서 여러 장에 나눠 두는데, 똑같이 베껴 두면 한 장이 찢어져도 그대로 읽을 수 있고 반씩 갈라 두면 두 사람이 한꺼번에 읽어서 빨라져. 대신 갈라 둔 쪽은 한 장만 잃어도 글이 안 이어져.
