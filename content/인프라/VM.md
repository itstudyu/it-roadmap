# VM (Virtual Machine)

## 📝 정의

VM(가상 머신)은 하나의 물리 서버를 논리적으로 여러 개의 독립된 컴퓨터 환경으로 나누는 기술입니다. Hypervisor라는 소프트웨어가 물리 하드웨어의 CPU, 메모리, 디스크 등의 자원을 가상화하여 각 VM에 할당하고, 각 VM은 자신의 독립된 운영체제와 애플리케이션을 실행할 수 있습니다.

VM 기술은 1960년대 IBM에서 처음 등장했으며, 초기에는 메인프레임 컴퓨터에서 여러 사용자가 동시에 작업할 수 있도록 하기 위해 개발되었습니다. 현대에는 클라우드 컴퓨팅의 핵심 기술로 자리 잡았으며, AWS EC2, Google Compute Engine, Microsoft Azure 등 모든 주요 클라우드 플랫폼이 VM 기반으로 서비스를 제공하고 있습니다.

### 한 줄 요약
> 물리 서버 하나를 여러 독립된 가상 컴퓨터로 나누어 동시에 여러 운영체제와 애플리케이션을 실행하는 기술

### 비유
- 🔵 **비유 1**: 하나의 큰 아파트 건물(물리 서버)을 여러 개의 독립된 가구(VM)로 나누는 것과 같습니다. 각 가구의 주민은 자신의 독립된 공간에서 생활하지만, 실제로는 같은 건물의 공용 설비(전기, 수도, 가스)를 공유합니다.

- 🟡 **비유 2**: 한 명의 배우(CPU)가 무대에서 여러 역할(VM)을 동시에 연기하는 것처럼, 한 개의 물리 CPU가 여러 VM의 작업을 시간을 나누어 처리합니다.

## 🎯 핵심 개념

### 1. 하드웨어 추상화 (Hardware Abstraction)
VM은 물리 하드웨어의 직접적인 제어를 숨기고, 추상화된 가상 하드웨어 인터페이스를 제공합니다. 이를 통해 각 VM의 게스트 운영체제는 실제 하드웨어를 모르고도 일반적인 하드웨어처럼 상호작용할 수 있습니다. 예를 들어, VM 내의 OS는 물리적으로 존재하지 않는 가상 디스크를 읽고 쓸 수 있으며, 실제로는 Hypervisor가 이를 물리 디스크로 변환합니다. 이 추상화 계층은 VM의 이식성과 유연성을 크게 향상시킵니다.

### 2. 리소스 격리 (Resource Isolation)
각 VM은 다른 VM으로부터 격리된 독립적인 환경에서 실행됩니다. 한 VM의 크래시나 보안 침해가 다른 VM에 영향을 주지 않으며, 각 VM은 할당받은 CPU, 메모리, 디스크 할당량을 초과할 수 없습니다. 이 격리는 멀티테넌트 환경에서 여러 고객의 데이터와 애플리케이션을 안전하게 분리하는 데 매우 중요합니다. Hypervisor는 모든 VM의 리소스 접근을 감시하고 제어하여 이러한 격리를 보장합니다.

### 3. 멀티테넌시 (Multi-tenancy)
하나의 물리 서버에서 여러 독립된 고객이나 부서의 VM을 동시에 실행할 수 있습니다. 이를 통해 하드웨어 비용을 여러 사용자에게 분산시킬 수 있고, 각 사용자는 자신만의 독립된 컴퓨팅 환경을 가질 수 있습니다. 클라우드 서비스 제공자들은 이 멀티테넌시를 최대한 활용하여 비용 효율성을 높이고, 고객에게는 저렴한 가격에 전용 서버와 유사한 성능을 제공할 수 있게 됩니다.

### 4. 동적 리소스 할당 (Dynamic Resource Allocation)
필요에 따라 각 VM에 할당되는 CPU, 메모리, 디스크를 동적으로 조정할 수 있습니다. 트래픽이 많아져서 더 많은 리소스가 필요한 VM에는 추가 리소스를 할당하고, 현재 필요 없는 리소스는 다른 VM으로 재배분할 수 있습니다. 이러한 유연성 덕분에 클라우드 플랫폼에서는 사용자가 필요한 만큼만 리소스를 사용하고 비용을 지불할 수 있으므로, 비용 효율성이 크게 향상됩니다.

## ⚠️ 해결하는 문제

### 문제 1: 하드웨어 낭비 (Server Underutilization)
전통적인 물리 서버 방식에서는 한 대의 서버가 보통 전체 용량의 10~30% 정도만 사용되고 나머지는 유휴 상태였습니다. 이는 서버 구입 비용, 전력, 냉각, 공간 등에 막대한 낭비를 초래했으며, 기업의 IT 비용을 크게 증가시켰습니다.

VM 기술은 하나의 물리 서버를 여러 VM으로 나누어 각 애플리케이션이 공유하도록 함으로써, 물리 서버의 리소스 사용률을 70~80% 이상으로 높일 수 있습니다. 예를 들어, 과거에는 메일 서버 하나를 위해 물리 서버 5대가 필요했다면, 이제는 1대의 물리 서버에서 5개의 VM으로 운영할 수 있게 되었습니다.

그 결과 전체 IT 인프라 비용이 대폭 감소하고, 같은 예산으로 더 많은 서비스를 운영할 수 있게 되었으며, 기업의 경쟁력이 향상됩니다.

### 문제 2: 인프라 확장의 어려움 (Infrastructure Scalability)
새로운 애플리케이션이나 서비스를 추가하려면 새로운 물리 서버를 구입하고 설치하는 데 몇 주일이 걸렸습니다. 또한 트래픽이 예상보다 많으면 추가 서버 구입을 위해 다시 몇 주일을 기다려야 했고, 트래픽이 줄어들면 비용 낭비만 늘어났습니다.

VM을 사용하면 관리자가 몇 분 내에 새로운 VM을 생성할 수 있고, 필요에 따라 즉시 리소스를 추가하거나 삭제할 수 있습니다. Hypervisor의 동적 할당 기능으로 인해 인프라 확장이 매우 유연해졌으며, 비즈니스 요구사항에 빠르게 대응할 수 있게 되었습니다.

결과적으로 기업은 시장 변화에 빠르게 대응할 수 있고, 리소스 낭비를 최소화하며, 고객 만족도를 높일 수 있게 됩니다.

### 문제 3: 서버 간 격리 부족 (Isolation and Security)
물리 서버에서 여러 애플리케이션이 같은 OS 위에서 실행되면, 한 애플리케이션의 크래시가 전체 서버와 다른 모든 애플리케이션에 영향을 미쳤습니다. 또한 보안 침해 시에도 전체 서버가 위험에 노출되었습니다.

VM은 각각 독립된 운영체제를 가지고 있어서, 한 VM의 문제가 다른 VM에 영향을 주지 않습니다. 호스팅 회사에서는 여러 고객의 VM을 한 물리 서버에서 안전하게 실행할 수 있으며, 각 고객의 데이터와 애플리케이션은 완벽하게 격리됩니다.

이러한 격리 덕분에 멀티테넌트 환경의 보안성과 안정성이 크게 향상되었으며, 클라우드 서비스의 보급이 가능하게 되었습니다.

## ⚙️ 작동 원리

### VM의 라이프사이클

1. **생성 (Creation)**: 관리자가 Hypervisor에 새 VM 생성을 요청하면, Hypervisor는 가상 디스크 파일을 생성하고, 가상 CPU와 메모리를 할당합니다. 이 시점에서 VM은 아직 실행되지 않은 상태입니다.

2. **부팅 (Boot)**: VM이 실행되면 Hypervisor는 BIOS 에뮬레이션을 통해 부팅 시퀀스를 시작합니다. 게스트 OS의 부팅 로더가 실행되고, 게스트 OS의 커널이 메모리로 로드됩니다.

3. **실행 (Execution)**: 게스트 OS가 완전히 부팅되면 애플리케이션을 실행할 수 있습니다. Hypervisor는 게스트 OS의 모든 명령어를 모니터링하고, 특권 명령어(privileged instruction)는 트랩(trap)되어 Hypervisor가 처리합니다.

4. **리소스 관리 (Resource Management)**: 실행 중인 VM은 할당받은 CPU 시간, 메모리, 디스크를 사용합니다. Hypervisor는 모든 VM에 공정하게 리소스를 분배하고, 과다 사용을 방지합니다.

5. **중지 및 스냅샷 (Stop & Snapshot)**: VM은 실행 중 언제든지 일시 중지할 수 있고, 이 시점의 완전한 상태(메모리, 디스크 내용, CPU 상태)를 스냅샷으로 저장할 수 있습니다. 나중에 정확히 같은 상태에서 재개할 수 있습니다.

6. **마이그레이션 (Migration)**: VM의 상태를 다른 물리 서버로 옮길 수 있습니다. 실시간 마이그레이션을 사용하면 VM이 실행 중인 상태에서도 다른 서버로 옮길 수 있어 서비스 중단 없이 유지보수를 수행할 수 있습니다.

7. **삭제 (Deletion)**: VM이 더 이상 필요 없으면 삭제할 수 있고, 할당되었던 모든 리소스가 반환됩니다.

### VM에서의 I/O 처리

```도해
흐름: VM, 무슨 순서로 오가나
게스트 OS :: I/O 요청 (예: 디스크 읽기)
가상 디바이스 드라이버 :: 트랩 (Trap)
Hypervisor :: 요청 해석 및 변환
Hypervisor :: 실제 I/O 수행
물리 디바이스 :: 데이터 반환
Hypervisor :: 가상 인터럽트 발생
가상 디바이스 드라이버 :: 데이터 전달
```

### CPU 스케줄링

Hypervisor는 여러 VM의 가상 CPU를 하나의 물리 CPU에서 시간을 나누어 실행합니다. 이를 CPU 스케줄링이라고 하며, 다음과 같은 원칙으로 동작합니다:

- 각 VM의 가상 CPU는 일정한 시간 슬라이스(타임 슬라이스)를 할당받습니다.
- Hypervisor는 모든 VM에 공정하게 CPU 시간을 분배하려고 하지만, 우선순위를 설정할 수 있습니다.
- 한 VM이 I/O 작업을 기다리는 동안, Hypervisor는 그 시간을 다른 VM에 할당합니다.
- 현대의 멀티코어 CPU에서는 여러 VM이 서로 다른 코어에서 동시에 실행될 수 있습니다.

## ✅ 장점과 단점

### 장점
- **하드웨어 활용도 증가**: 물리 서버의 유휴 리소스를 최소화하여 비용 효율성이 높습니다.
- **빠른 배포**: 새로운 VM을 몇 분 내에 생성할 수 있어 인프라 확장이 빠릅니다.
- **유연한 스케일링**: 필요에 따라 VM의 리소스를 동적으로 조정할 수 있습니다.
- **강력한 격리**: 각 VM이 독립된 OS를 가지므로, 한 VM의 문제가 다른 VM에 영향을 주지 않습니다.
- **마이그레이션 가능**: VM을 다른 물리 서버로 쉽게 옮길 수 있고, 심지어 운영 중에도 가능합니다.
- **스냅샷과 복제**: VM의 상태를 저장했다가 복구하거나, 쉽게 복제할 수 있습니다.
- **다양한 OS 지원**: 한 물리 서버에서 Windows, Linux, 기타 OS를 동시에 실행할 수 있습니다.
- **개발/테스트 환경 구축 용이**: 개발자들이 쉽게 자신만의 격리된 테스트 환경을 만들 수 있습니다.

### 단점 / 주의사항
- **오버헤드**: 각 VM이 전체 OS를 포함하므로 리소스 오버헤드가 Container에 비해 높습니다.
- **부팅 시간**: Container에 비해 부팅 시간이 길어서 빠른 확장이 필요한 경우 부담이 될 수 있습니다.
- **관리 복잡성**: 각 VM의 OS 패치, 업데이트, 보안 관리를 따로 해야 합니다.
- **Hypervisor 의존성**: Hypervisor의 버그나 문제가 모든 VM에 영향을 미칠 수 있습니다.
- **CPU 캐시 효율 저하**: 여러 VM이 같은 물리 CPU를 공유하면서 CPU 캐시 효율이 떨어질 수 있습니다.
- **라이선스 비용**: 상용 Hypervisor(VMware, Hyper-V)의 라이선스 비용이 상당할 수 있습니다.
- **성능 저하**: 물리 서버에 비해 약 5~10%의 성능 저하가 발생할 수 있습니다.
- **메모리 압박**: 많은 VM을 한 물리 서버에서 실행하면 메모리 부족 문제가 발생할 수 있습니다.

## 💡 실제 사용 사례

### 사례 1: AWS EC2 인스턴스
Amazon Web Services의 EC2(Elastic Compute Cloud) 서비스는 VM 기술 기반으로 구현되어 있습니다. 사용자가 AWS 콘솔에서 인스턴스 유형(t2.micro, m5.large 등)을 선택하고 생성 버튼을 클릭하면, 수 초 내에 새로운 VM이 생성되고 실행됩니다. 사용자는 이 VM을 마치 자신의 물리 서버인 것처럼 사용할 수 있으며, 필요에 따라 인스턴스 타입을 변경(수직 확장)하거나, 여러 인스턴스를 동시에 실행(수평 확장)할 수 있습니다. 이를 통해 기업은 초기 인프라 투자 없이 필요한 만큼만 비용을 지불할 수 있습니다.

### 사례 2: 엔터프라이즈 데이터 센터 가상화
대규모 금융사나 기업들은 자신의 데이터 센터에 VMware vSphere나 Microsoft Hyper-V를 설치하여 물리 서버들을 가상화합니다. 기존에 50대의 물리 서버가 필요했던 작업을 이제는 10대의 고성능 물리 서버 위의 VM들로 운영합니다. 이를 통해 에너지 비용, 냉각 비용, 공간 비용을 크게 절감하고, 더 효율적인 IT 자원 관리가 가능해집니다. 또한 VM 마이그레이션을 통해 물리 서버 유지보수를 서비스 중단 없이 수행할 수 있습니다.

### 사례 3: 개발자의 로컬 테스트 환경
개발자가 VirtualBox나 VMware Workstation을 사용하여 자신의 노트북에서 여러 VM을 실행할 수 있습니다. Linux 테스트용 VM, Windows 테스트용 VM, 데이터베이스 서버용 VM을 동시에 실행하면서 애플리케이션을 개발하고 테스트할 수 있습니다. 필요한 환경을 VM으로 미리 구성해 두면, 나중에 팀원들이 같은 환경을 쉽게 재현할 수 있어 "내 컴퓨터에서는 되는데 다른 곳에서는 안 된다"는 문제를 해결할 수 있습니다.

### 사례 4: 멀티테넌트 호스팅 서비스
호스팅 회사들은 하나의 물리 서버에 여러 고객의 VM을 운영합니다. 각 고객은 자신만의 격리된 VM을 가지고 있어서, 다른 고객의 데이터나 애플리케이션에 접근할 수 없으며, 다른 고객의 문제의 영향도 받지 않습니다. 호스팅 회사는 물리 서버를 최대한 활용하면서도 각 고객에게 전용 서버와 같은 경험을 제공할 수 있어, 비용 효율성과 고객 만족도를 동시에 달성합니다.

### 사례 5: 재해 복구 및 비즈니스 지속성
조직에서 중요한 서버들을 VM으로 운영하면, 이들 VM을 정기적으로 스냅샷으로 백업할 수 있습니다. 주 데이터 센터에 문제가 생기면, 이 스냅샷을 다른 물리 서버에서 복구하여 빠르게 서비스를 재개할 수 있습니다. 또한 VM 복제 기술을 사용하여 다른 지역의 데이터 센터에 실시간으로 VM을 동기화할 수 있어, 재해 발생 시에도 비즈니스 연속성을 보장할 수 있습니다.
