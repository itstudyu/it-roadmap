# Hypervisor

## 📝 정의

Hypervisor(하이퍼바이저)는 물리 컴퓨터의 하드웨어 리소스(CPU, 메모리, 디스크, 네트워크)를 관리하고, 그 위에서 여러 개의 독립적인 가상 머신(VM)을 생성하고 실행하는 소프트웨어 계층입니다. Hypervisor는 각 VM의 요청을 가로채서 물리 하드웨어로 변환하고, 각 VM이 독립적으로 동작하도록 제어합니다.

Hypervisor라는 용어는 1960년대 IBM의 메인프레임 컴퓨터에서 유래했으며, "supervisor(감시자)"보다 위에서 모든 것을 감시한다는 의미에서 "hyper"를 붙였습니다. 현대에는 클라우드 데이터 센터와 엔터프라이즈 가상화의 필수 요소가 되었으며, VMware ESXi, Microsoft Hyper-V, KVM, Xen 등 다양한 Hypervisor 제품이 존재합니다.

### 한 줄 요약
> 물리 하드웨어와 VM 사이에서 리소스를 관리하고 VM들을 제어하는 가상화 계층

### 비유
- 🔵 **비유 1**: Hypervisor는 다중 사용자 컴퓨터 시스템의 운영체제처럼, 여러 VM이 같은 물리 리소스를 공동으로 사용할 때 각 VM이 자신만의 독립된 컴퓨터를 사용하는 것처럼 착각하도록 관리합니다.

- 🟡 **비유 2**: 아파트 건물의 관리자가 전기, 물, 가스 등의 공용 설비를 각 가구에 공정하게 배분하는 것처럼, Hypervisor는 CPU, 메모리, 디스크 등의 물리 리소스를 각 VM에 공정하게 할당합니다.

## 🎯 핵심 개념

### 1. Type 1 (Bare Metal) Hypervisor
Type 1 Hypervisor는 물리 하드웨어 위에 직접 설치되는 Hypervisor입니다. 운영체제가 없고, Hypervisor 자체가 하드웨어를 직접 제어합니다. VMware ESXi, Microsoft Hyper-V Server, Citrix XenServer, KVM(Linux의 일부로) 등이 이에 해당합니다. Type 1 Hypervisor는 매우 효율적이고 성능이 우수하며, 엔터프라이즈 데이터 센터에서 널리 사용됩니다. 하드웨어와 직접 상호작용하므로 최소한의 오버헤드로 최대한의 성능을 얻을 수 있으며, 보안성도 높습니다.

### 2. Type 2 (Hosted) Hypervisor
Type 2 Hypervisor는 호스트 운영체제(Windows, macOS, Linux) 위에 설치되어 실행되는 Hypervisor입니다. VirtualBox, VMware Workstation, Parallels Desktop 등이 이에 해당합니다. Type 2 Hypervisor는 기존 OS 위에서 애플리케이션처럼 실행되므로 설치와 사용이 간단하고, 개발자나 일반 사용자가 쉽게 사용할 수 있습니다. 다만 호스트 OS 계층이 추가되므로 오버헤드가 커서 성능이 Type 1보다 낮지만, 개발, 테스트, 학습 목적으로는 충분합니다.

### 3. 하드웨어 지원 가상화 (Hardware-Assisted Virtualization)
현대의 CPU들(Intel VT, AMD-V)은 Hypervisor의 작업을 도와주는 하드웨어 기능을 내장하고 있습니다. 이를 통해 Hypervisor는 VM의 명령어를 더 효율적으로 처리할 수 있습니다. 하드웨어 가상화 기능이 없으면 Hypervisor가 모든 특권 명령어를 소프트웨어적으로 트랩해야 하므로 상당한 성능 오버헤드가 발생합니다. 현대 Hypervisor들은 대부분 하드웨어 가상화 기능을 활용하므로, CPU에서 이 기능이 활성화되어 있는지 확인하는 것이 중요합니다.

### 4. 리소스 스케줄링 및 할당 (Resource Scheduling and Allocation)
Hypervisor의 중요한 역할은 물리 리소스를 여러 VM에 공정하게 할당하는 것입니다. CPU 스케줄러는 각 VM의 가상 CPU가 물리 CPU 시간을 할당받도록 관리하고, 메모리 관리자는 물리 메모리를 VM에 할당합니다. 오버커밋(overcommit) 기능을 사용하면 물리 리소스보다 더 많은 리소스를 VM에 할당할 수 있으며, Hypervisor가 자동으로 페이징이나 메모리 압축을 통해 관리합니다. 이 스케줄링이 효율적이지 않으면 성능 문제가 발생하므로, 고급 스케줄링 알고리즘이 중요합니다.

### 5. I/O 가상화 (I/O Virtualization)
VM은 가상 디스크, 가상 네트워크 인터페이스, 가상 USB 등의 가상 I/O 디바이스를 가집니다. Hypervisor는 이러한 가상 디바이스에 대한 VM의 요청을 가로채서, 이를 물리 I/O 디바이스로의 요청으로 변환합니다. I/O 가상화의 성능이 중요한데, 모던 Hypervisor들은 SR-IOV(Single-Root I/O Virtualization) 등의 기술을 사용하여 VM이 물리 디바이스와 거의 직접 상호작용하도록 함으로써 I/O 성능을 개선합니다. 네트워크 인터페이스의 경우, Hypervisor가 VM 간의 네트워크 트래픽을 스위칭하고, 외부 네트워크로의 통신을 관리합니다.

## ⚠️ 해결하는 문제

### 문제 1: 하드웨어 리소스 관리의 복잡성 (Complex Hardware Management)
물리 서버에서는 하드웨어를 직접 관리하고, 각 애플리케이션이 하드웨어 자원을 놓고 충돌할 수 있으며, 하나의 애플리케이션이 하드웨어를 독점할 수 있습니다. 또한 새로운 하드웨어를 추가하거나 교체할 때마다 애플리케이션을 중단해야 했습니다.

Hypervisor는 물리 하드웨어를 추상화하여 VM으로부터 숨김으로써, 각 VM이 자신만의 전용 하드웨어를 가지고 있다고 생각하게 만듭니다. 또한 Hypervisor가 물리 하드웨어를 관리하므로, 하드웨어 교체나 업그레이드를 할 때 VM들은 영향을 받지 않습니다.

그 결과 하드웨어 관리가 단순해지고, 물리 하드웨어의 변경이 VM에 미치는 영향이 최소화되며, 인프라 관리 업무가 크게 줄어듭니다.

### 문제 2: VM 간 격리 부족 (Lack of VM Isolation)
Hypervisor가 없으면 여러 애플리케이션이 같은 물리 서버에서 실행될 때, 한 애플리케이션의 메모리 누수, CPU 폭주, 또는 보안 침해가 다른 모든 애플리케이션에 영향을 미칩니다. 하나의 애플리케이션 버그로 인해 전체 시스템이 마비될 수 있으며, 악의적 공격으로부터 보호가 어렵습니다.

Hypervisor는 각 VM을 독립적인 프로세스로 격리하고, 각 VM의 메모리 접근을 제어하며, CPU 자원을 공정하게 분배합니다. 한 VM에서의 문제가 다른 VM으로 전파되지 않으며, 한 VM의 고장이 다른 VM에 영향을 주지 않습니다. 또한 Hypervisor는 VM 간의 네트워크 격리도 제공합니다.

결과적으로 멀티테넌트 환경의 안정성과 보안성이 크게 향상되고, 여러 고객의 VM을 안전하게 같은 물리 서버에서 실행할 수 있습니다.

### 문제 3: 유연하지 않은 확장 (Inflexible Scaling)
물리 서버 기반에서는 새로운 서버를 추가하려면 몇 주가 걸렸고, 리소스가 부족하면 서버를 재구성하는 데 시간이 오래 걸렸습니다. 또한 리소스 재할당이 매우 제한적이었습니다.

Hypervisor가 리소스를 관리하므로, 관리자는 기존 물리 서버의 리소스를 VM 간에 동적으로 재할당할 수 있습니다. 필요하면 몇 분 내에 새로운 VM을 생성하고 리소스를 할당할 수 있으며, 더 이상 필요 없는 VM의 리소스를 다른 VM으로 옮길 수 있습니다. 물리 서버 추가 시에도 기존 VM들을 새 서버로 마이그레이션하는 것이 자동화될 수 있습니다.

그 결과 인프라 확장이 매우 빨라지고 유연해지며, 비즈니스 요구사항에 빠르게 대응할 수 있게 됩니다.

## ⚙️ 작동 원리

### Hypervisor의 핵심 작동 메커니즘

Hypervisor는 다음과 같은 기본 원리로 동작합니다:

1. **트래핑 (Trapping)**: VM의 게스트 OS가 특권 명령어(privileged instruction)를 실행하려 하면, 이 명령어는 CPU의 보호 메커니즘에 의해 트랩되어 Hypervisor로 제어가 이동합니다.

2. **해석 및 에뮬레이션 (Interpretation & Emulation)**: Hypervisor는 트랩된 명령어가 무엇인지 파악하고, 이 명령어가 물리 하드웨어에 어떤 영향을 주는지 결정합니다. 필요하면 Hypervisor가 대신 명령어를 실행하거나 에뮬레이션합니다.

3. **리소스 접근 제어 (Resource Access Control)**: 명령어가 실제로 물리 하드웨어에 접근하려 하면, Hypervisor는 접근을 허용할지 거부할지 결정합니다. 각 VM의 할당된 리소스 범위를 초과하면 접근을 거부합니다.

4. **제어 반환 (Return of Control)**: 명령어 처리가 완료되면, 제어를 다시 VM으로 반환합니다.

### CPU 명령어 처리 흐름

```도해
흐름: Hypervisor, 무슨 순서로 오가나
VM의 게스트 OS :: 특권 명령어 실행 시도
CPU 보호 메커니즘 :: 트랩 (trap)
Hypervisor :: 명령어 분석
Hypervisor :: 메모리 접근 확인 및 처리
Hypervisor :: I/O 요청 처리
Hypervisor :: 예외 발생
Hypervisor :: 제어 반환
```

### 메모리 가상화

Hypervisor는 각 VM에 연속된 가상 메모리 공간을 제공하지만, 실제 물리 메모리는 단편화되어 있을 수 있습니다. Hypervisor는 페이지 테이블(page table)을 유지하여 가상 주소에서 물리 주소로의 매핑을 관리합니다:

- VM의 게스트 OS가 관리하는 게스트 페이지 테이블
- Hypervisor가 관리하는 그림자 페이지 테이블(shadow page table)이 실제 물리 메모리 매핑을 수행

이 두 계층의 페이지 테이블 매핑으로 인해 메모리 접근 성능이 저하될 수 있으므로, 최신 Hypervisor들은 확장 페이지 테이블(extended page table, EPT 또는 NPT) 기술을 사용하여 성능을 개선합니다.

## 📊 비교: Type 1 vs Type 2 Hypervisor

| 항목 | Type 1 (Bare Metal) | Type 2 (Hosted) |
|------|---------------------|-----------------|
| **설치 위치** | 물리 하드웨어 위에 직접 설치 | 호스트 OS 위에 설치 |
| **호스트 OS** | 없음 | Windows, macOS, Linux 등 |
| **성능** | 매우 높음 (최소 오버헤드) | 낮음 (호스트 OS 계층으로 인한 오버헤드) |
| **하드웨어 접근** | 직접 | 호스트 OS를 통해 간접 |
| **보안** | 높음 (OS 계층이 없어 공격 범위 축소) | 낮음 (호스트 OS 취약성 영향) |
| **사용 대상** | 엔터프라이즈, 데이터 센터 | 개발자, 테스트, 학습 |
| **설치 복잡도** | 높음 (하드웨어와 호환성 확인 필요) | 낮음 (기존 OS에 애플리케이션처럼 설치) |
| **라이선스** | 상용 제품 비용 높음 | 오픈소스 무료 제품 많음 |
| **확장성** | 우수함 | 제한적 |
| **동시 VM 개수** | 수십~수백 개 | 수 개~수십 개 |
| **예시 제품** | ESXi, Hyper-V, XenServer, KVM | VirtualBox, VMware Workstation, Parallels |

## ✅ 장점과 단점

### 장점
- **하드웨어 활용 효율화**: Hypervisor가 리소스를 효율적으로 관리하여 물리 서버의 유휴 자원을 최소화합니다.
- **유연한 리소스 관리**: 각 VM에 할당되는 CPU, 메모리를 동적으로 조정할 수 있습니다.
- **멀티테넌시 지원**: 여러 고객이나 부서의 VM을 안전하게 분리하여 같은 물리 서버에서 실행할 수 있습니다.
- **빠른 VM 배포**: 몇 분 내에 새로운 VM을 생성하고 실행할 수 있습니다.
- **VM 마이그레이션**: 실행 중인 VM을 다른 물리 서버로 옮길 수 있어 서비스 중단 없이 유지보수가 가능합니다.
- **스냅샷과 백업**: VM의 상태를 저장했다가 복구할 수 있습니다.
- **다양한 OS 지원**: 한 Hypervisor에서 Windows, Linux 등 여러 OS를 동시에 실행할 수 있습니다.
- **성능 격리**: 한 VM의 부하가 다른 VM에 심각한 영향을 주지 않도록 리소스를 격리합니다.

### 단점 / 주의사항
- **성능 오버헤드**: Hypervisor 계층으로 인해 3~10% 정도의 성능 저하가 발생할 수 있습니다.
- **관리 복잡성**: Hypervisor 자체의 설치, 구성, 관리가 복잡할 수 있습니다.
- **라이선스 비용**: 상용 Hypervisor(VMware, Hyper-V)의 라이선스 비용이 높을 수 있습니다.
- **하드웨어 지원 필수**: 최적의 성능을 위해서는 VT(Intel) 또는 AMD-V 같은 하드웨어 가상화 기능이 필요합니다.
- **Hypervisor 버그의 영향**: Hypervisor의 버그가 모든 VM에 영향을 미칠 수 있습니다.
- **보안 위험**: Hypervisor 자체가 공격 대상이 될 수 있으며, 보안 취약점이 발견되면 영향 범위가 넓습니다.
- **디버깅의 어려움**: VM 내에서 문제가 발생했을 때 Hypervisor 계층의 문제인지 구별하기 어려울 수 있습니다.
- **리소스 오버커밋의 위험**: VM에 물리 리소스보다 더 많은 리소스를 할당하면 성능 저하가 발생할 수 있습니다.

## 💡 실제 사용 사례

### 사례 1: VMware vSphere를 이용한 엔터프라이즈 가상화
대규모 금융회사가 수백 대의 물리 서버를 VMware ESXi Hypervisor로 가상화하여 관리합니다. 기존에는 각 애플리케이션을 위해 개별 물리 서버가 필요했지만, Hypervisor 도입 후 리소스 사용률을 70% 이상으로 높일 수 있었습니다. 또한 VM 마이그레이션 기능을 통해 유지보수 시에도 서비스를 중단하지 않을 수 있으며, 새로운 서비스 추가 시 몇 분 내에 VM을 생성하여 배포할 수 있게 되었습니다. 스냅샷 기능으로 중요한 서버의 정기적 백업이 가능해져 재해 복구 능력도 향상되었습니다.

### 사례 2: Microsoft Hyper-V를 이용한 프라이빗 클라우드 구축
중규모 IT 회사가 Windows Server 기반의 Hyper-V Hypervisor를 사용하여 프라이빗 클라우드를 구축합니다. Hyper-V는 Windows Server 표준 에디션에 포함되어 있어 추가 라이선스 비용이 없으며, System Center를 통해 여러 물리 서버의 VM들을 통합 관리할 수 있습니다. 개발 팀이 자체 요청으로 새로운 VM을 생성하고 필요한 리소스를 할당받을 수 있어, IT 부서의 관리 부담이 크게 줄어들었습니다.

### 사례 3: KVM을 이용한 오픈소스 기반 가상화
스타트업이 Linux 커널의 KVM(Kernel-based Virtual Machine) Hypervisor를 사용하여 비용 효율적인 가상화 인프라를 구축합니다. KVM은 오픈소스이고 무료이며, libvirt 같은 관리 도구와 함께 사용하여 여러 개의 Linux 서버를 효율적으로 관리할 수 있습니다. Proxmox VE나 OpenStack 같은 오픈소스 클라우드 플랫폼과 함께 사용하여, 적은 비용으로도 대규모 가상화 인프라를 운영할 수 있습니다.

### 사례 4: VirtualBox를 이용한 개발자의 로컬 환경
개발자가 자신의 노트북에 VirtualBox(Type 2 Hypervisor)를 설치하고, Linux 개발 환경, Windows 테스트 환경, 데이터베이스 서버 VM 등을 동시에 실행합니다. Type 2 Hypervisor이므로 설치가 간단하고, 필요한 VM을 스냅샷으로 저장해 두었다가 언제든지 빠르게 복구할 수 있습니다. 팀 내 모든 개발자가 같은 Hypervisor 환경을 공유하므로, 환경 차이로 인한 버그를 줄일 수 있습니다.

### 사례 5: 클라우드 서비스 제공자의 멀티테넌시 환경
AWS, Azure, GCP 같은 클라우드 서비스 제공자들이 각자 고성능 Hypervisor를 사용하여 수백만 개의 VM을 관리합니다. 이들 Hypervisor는 고도로 최적화되고 커스터마이징되어 있으며, 매우 높은 멀티테넌시를 지원합니다. Hypervisor의 성능과 안정성이 곧 서비스의 품질과 직결되므로, 끊임없는 개선과 최적화가 이루어집니다.
