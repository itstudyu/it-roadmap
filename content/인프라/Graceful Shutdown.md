# Graceful Shutdown (우아한 종료)

## 📝 정의

Graceful Shutdown 은 **새 일은 그만 받고 하던 일을 끝낸 뒤 내려가는 것**이다.

배포와 축소는 늘 무언가를 내리는 일이다. 내리는 방법은 둘뿐이다 — 그 자리에서 끊거나, 하던 것을 비우고 내려가거나. 무중단 배포라고 부르는 것들이 실제로 무중단이 되는지는 이 한 갈래에서 갈린다.

### 이름
Graceful :: 서두르지 않는
Shutdown :: 끄기
= 붙여 읽으면 "서두르지 않고 끄기". 우아하다는 멋이 아니라, 하던 일을 끊지 않고 끈다는 뜻이다

### 비유
문 닫을 시간이 된 식당. 새 손님은 안 받지만, 이미 앉은 손님이 다 먹고 나갈 때까지는 불을 안 끈다.

### 예
앱이 새로 올라가는 중인 걸 모르고 결제 버튼을 눌렀는데 아무 일 없이 잘 끝난 그때다.

## 🖼️ 그림으로 보기

```도해
흐름: 내리라는 신호를 받은 프로세스는 어떤 순서로 꺼지나
종료 신호 :: 내려가라는 신호가 먼저 온다
빼내기 :: 앞단이 새 요청을 더 안 보낸다
문 닫기 :: 듣던 자리를 닫아 새 일을 안 받는다
남은 일 :: 이미 받은 것만 끝까지 처리한다
자진 종료 :: 다 비웠으면 스스로 내려간다
강제 종료 :: 유예 시간을 넘기면 그대로 끊긴다
= 끊고 내려가는 게 아니라, 새 것을 막고 하던 것을 비운 뒤 내려간다
```

## ⚠️ 해결하는 문제

```도해
대조: 그냥 끊고 내리면 무엇이 달라지나
바로 끊으면 || 다 비우고
처리 중이던 일 :: 중간에 끊긴다 || 끝까지 간다
사용자가 보는 것 :: 오류 화면 || 정상 화면
남는 자국 :: 반만 쓴 기록 || 없다
= 배포마다 몇 건씩 조용히 실패하던 것이 이 한 단계에서 갈린다
```

내리는 순간에도 그 프로세스는 일을 받고 있다. 앞단이 아직 이 대상을 목록에 두고 있고, 방금 넘어온 요청은 답을 기다리는 중이고, 큐에서 꺼내 반쯤 처리한 건도 있다. 여기서 그냥 끊으면 그 전부가 실패로 끝난다. 사용자는 오류를 보고, 반만 쓰인 기록이 남고, 다시 시도해도 되는 일인지 아닌지를 아무도 모른다.

배포와 축소는 매일 일어나므로 이 손실은 매일 조금씩 쌓인다. 그런데 건수가 적고 배포 때만 몰려서, 원인을 모른 채 "가끔 나는 오류" 로 넘어가기 쉽다. 우아한 종료는 이 손실을 없애기 위해 종료를 한 순간이 아니라 여러 단계로 늘려 놓는다.

## ⚙️ 작동 원리

시작은 신호다. 오케스트레이터가 파드를 지우면 컨테이너 안 주 프로세스에 `SIGTERM` 을 보내고, 정해진 유예 시간만큼 기다린다. 기본 유예 시간은 30초이고 파드 명세에서 바꿀 수 있다. 유예 시간이 지나도 안 끝난 프로세스는 `SIGKILL` 로 끊긴다. 그러니까 우아한 종료는 켜고 끄는 스위치가 아니라, 프로세스가 이 유예 시간 안에 스스로 마무리하는 일이다.

같은 무렵 앞단에서 이 대상을 빼내는 일도 진행된다. 지워지는 파드는 곧 "내려가는 중" 으로 표시되고, 앞단은 그렇게 표시된 대상에는 정상 요청을 더 보내지 않는다. 다만 이 표시가 퍼지는 일과 종료 신호가 가는 일은 나란히 벌어진다. 그래서 표시가 닿기 직전에 출발한 요청이 아직 오고 있을 수 있다. 종료 직전에 잠깐 멈추는 `preStop` 훅을 두는 이유가 이 틈을 메우기 위해서다.

받는 쪽 처리는 프로그램이 한다. Go 의 `http.Server` 는 `Shutdown` 을 부르면 듣던 자리를 먼저 닫고, 놀고 있는 연결을 닫고, 처리 중인 요청이 끝나기를 기다린다. 같은 자료가 `Close` 는 즉시 끊는다고 적어 두고 우아한 종료에는 `Shutdown` 을 쓰라고 말한다. nginx 도 신호마다 종료 방식을 갈라 둔다 — `TERM` 과 `INT` 는 빠른 종료, `QUIT` 는 우아한 종료다.

## 💡 실제 사례

- **파드 교체** — 배포로 옛 파드를 내릴 때마다 이 절차가 돈다. 처리 시간이 유예 시간보다 긴 작업이 있으면 그 값을 늘려 잡는다.
- **웹 서버 재시작** — 설정을 바꿔 다시 읽힐 때 옛 작업 프로세스는 듣던 자리를 닫고, 붙어 있던 연결만 마저 처리하고 내려간다.
- **큐 소비자 종료** — 메시지를 꺼내 처리하던 프로그램은 신호를 받으면 새 메시지를 더 안 꺼내고, 손에 든 것만 끝낸 뒤 내려간다.

## 🚫 흔한 오해

- **신호만 보내면 알아서 다 비운다** — 신호를 받는 쪽이 처리해야 비워진다. 신호를 안 듣는 프로그램은 유예 시간을 다 쓰고 결국 끊긴다.
- **유예 시간을 넉넉히 주면 안전하다** — 내려가는 중이라는 표시가 앞단에 닿기 직전에 출발한 요청은 이미 이쪽으로 오고 있다. 그 틈을 메우지 않으면 유예 시간이 아무리 길어도 몇 건은 끊긴다.
- **끝까지 기다려 주는 쪽이 언제나 낫다** — 오래 걸리는 작업을 붙들고 있으면 배포가 그만큼 밀리고 급할 때 못 내린다. 어디까지 기다릴지를 정하는 것이 유예 시간이다.

## 📝 정리

**"새 일은 막고 하던 일은 비우고 내려가는 종료"** 라고 읽으면 된다. 신호를 받는 쪽이 이 절차를 직접 해야 하고, 안 하면 유예 시간을 다 쓴 뒤 그냥 끊긴다. 무중단 배포가 실제로 무중단인지는 이 한 단계에서 갈린다.

## 🧒 열 살에게

문 닫을 시간이 된 분식집을 떠올려 봐. 아주머니가 문에 "준비 중" 을 걸어서 새 손님은 안 받지만, 이미 떡볶이를 시킨 사람은 다 먹고 나갈 때까지 기다려 주지. 그러고 나서 불을 끄는 거야.

## ❓ 이해했는지

- 유예 시간을 늘렸는데도 배포 때마다 몇 건씩 오류가 나는 까닭은 무엇인가 → 흔한 오해
- 종료 신호를 못 알아듣는 프로그램은 결국 어떻게 끝나나 → 작동 원리
- 그냥 끊고 내렸을 때 사용자 화면과 기록에 무엇이 남나 → 해결하는 문제
