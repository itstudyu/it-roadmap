# Container

## 📝 정의

Container(컨테이너)는 운영체제 커널을 공유하면서 애플리케이션 프로세스를 격리하는 경량 가상화 기술입니다. VM과 달리 각 Container가 별도의 운영체제를 가질 필요가 없으므로, 리소스 사용량이 매우 적고 부팅 시간이 매우 빠릅니다. Container는 애플리케이션과 그 의존성(라이브러리, 설정 파일 등)을 모두 하나의 이미지로 패킹하여 배포하므로, 어느 환경에서나 동일하게 작동합니다.

Container 기술은 Docker가 2013년 대중화시켰으며, 현대에는 마이크로서비스 아키텍처의 필수 요소가 되었습니다. Kubernetes는 수천 개의 Container를 자동으로 관리하고 스케일링하는 오케스트레이션 플랫폼으로, Container 기술의 가능성을 극대화합니다. Cloud Native Computing Foundation에서는 Container를 클라우드 네이티브 애플리케이션의 핵심 기술로 지정했습니다.

### 한 줄 요약
> 운영체제 커널을 공유하면서 애플리케이션을 격리 실행하는 초경량 가상화 기술

### 비유
- 🔵 **비유 1**: Container는 배의 컨테이너처럼, 하나의 호스트(배)에 여러 개의 표준화된 상자(Container)를 싣고 운반합니다. 각 상자 안의 화물은 격리되어 있지만, 배는 한 척입니다.

- 🟡 **비유 2**: 아파트의 여러 층(OS 커널)을 공유하면서도, 각 호실(Container)이 독립된 문과 열쇠(프로세스 격리)로 격리되어 있는 것과 같습니다.

## 🎯 핵심 개념

### 1. 커널 공유 (Kernel Sharing)
VM은 각각 완전한 운영체제를 포함하고 있어서 리소스 오버헤드가 큽니다. 하지만 Container는 호스트 OS의 커널을 공유하고, 애플리케이션 계층만 격리합니다. 이를 통해 각 Container의 크기가 수십 MB 정도로 매우 작아지고, 메모리 사용량도 극히 적어집니다. Container의 부팅 시간이 수백 밀리초 정도로 매우 빠른 이유도 이 때문입니다. 다만 호스트 OS의 커널에 버그가 있으면 모든 Container에 영향을 미친다는 단점도 있습니다.

### 2. 프로세스 격리 (Process Isolation)
Container는 Linux의 네임스페이스(namespace)와 cgroups(control groups) 기능을 사용하여 프로세스 격리를 구현합니다. 각 Container는 자신만의 프로세스 ID 공간, 네트워크 인터페이스, 파일시스템, IPC 리소스를 가집니다. 그러나 이들은 모두 같은 커널의 추상화일 뿐이므로, Container 간의 컨텍스트 스위칭이 매우 빠릅니다. 한 Container에서 fork() 시스템 호출을 하더라도, 호스트에서는 단순한 프로세스 생성일 뿐입니다.

### 3. 이미지 기반 배포 (Image-Based Distribution)
Container는 Docker 이미지라는 표준화된 형식으로 패킹됩니다. 이미지는 애플리케이션, 라이브러리, 설정 파일, 환경 변수 등을 모두 포함하는 자체 완결적인 패키지입니다. 개발자는 이미지를 Docker Hub 같은 레지스트리에 업로드하고, 다른 개발자는 이 이미지를 다운로드하여 자신의 환경에서 정확히 같은 환경을 얻을 수 있습니다. 이를 통해 "내 컴퓨터에서는 되는데 배포 환경에서는 안 된다"는 문제를 근본적으로 해결합니다.

### 4. 레이어드 파일시스템 (Layered Filesystem)
Docker 이미지는 레이어로 구성됩니다. 기본 OS 레이어 위에 라이브러리 레이어, 애플리케이션 코드 레이어 등이 쌓이는 구조입니다. 이렇게 레이어로 구성하면, 여러 이미지가 같은 기본 레이어를 공유할 수 있어 디스크 공간을 절약할 수 있습니다. 또한 이미지 변경 시 변경된 레이어만 업로드하면 되므로 배포 속도가 빠릅니다. 각 레이어는 읽기 전용(read-only)이고, Container가 실행될 때 최상단에 쓰기 가능(writable)한 레이어가 추가됩니다.

### 5. 오케스트레이션 (Orchestration)
개수가 적을 때는 Container를 수동으로 관리할 수 있지만, 수백 또는 수천 개의 Container를 관리하는 것은 불가능합니다. Kubernetes 같은 오케스트레이션 플랫폼은 다음을 자동으로 처리합니다: Container 배포, 리소스 할당, 네트워킹, 스토리지 관리, 자동 재시작, 자동 스케일링, 로드 밸런싱. 오케스트레이션 없이는 현대의 마이크로서비스 아키텍처를 운영하기 어렵습니다.

## ⚠️ 해결하는 문제

### 문제 1: 개발과 배포 환경의 불일치 (Development-Production Parity)
개발자는 자신의 로컬 환경(Windows 또는 macOS)에서 애플리케이션을 개발하지만, 배포 환경은 Linux입니다. 또한 개발 환경에는 Python 3.8이 설치되어 있지만 배포 환경에는 Python 3.10이 설치되어 있을 수 있습니다. 이러한 환경 차이로 인해 개발할 때는 잘 작동하던 코드가 배포 환경에서 오류가 발생할 수 있습니다.

Container는 개발부터 배포까지 정확히 동일한 환경을 보장합니다. 개발자가 만든 Dockerfile과 이미지는 모든 환경에서 동일하게 작동하므로, 환경 차이로 인한 버그가 발생하지 않습니다. 또한 마이크로서비스를 개발할 때, 여러 개의 서로 다른 Container를 Docker Compose로 한 번에 구성할 수 있어 개발이 간단해집니다.

그 결과 배포 성공률이 높아지고, 배포 후 발견되는 환경 관련 버그가 크게 줄어듭니다.

### 문제 2: 느린 배포와 확장 (Slow Deployment and Scaling)
전통적인 방식에서는 새로운 서버를 준비하고, 필요한 소프트웨어를 설치하고, 애플리케이션을 배포하는 데 몇 시간 또는 몇 일이 걸렸습니다. 또한 트래픽이 증가해서 새로운 서버를 추가하려 해도, 이 모든 준비 과정을 다시 거쳐야 했습니다.

Container는 이미지가 준비되면 몇 초 안에 배포할 수 있습니다. Kubernetes 같은 오케스트레이션 플랫폼을 사용하면, 트래픽 증가를 감지하여 자동으로 새로운 Container 인스턴스를 생성하고, 트래픽이 줄어들면 자동으로 종료합니다. 이를 수평 자동 확장(horizontal auto-scaling)이라고 합니다.

그 결과 배포 시간이 몇 시간에서 몇 초로 단축되고, 자동 스케일링으로 인해 비즈니스 요구사항에 빠르게 대응할 수 있게 됩니다.

### 문제 3: 높은 인프라 비용과 유휴 리소스 (High Infrastructure Cost)
전통적인 방식에서는 피크 트래픽에 대응하기 위해 미리 많은 서버를 준비해야 합니다. 하지만 일반적으로는 이 서버들의 리소스가 20~30% 정도만 사용되고 대부분이 유휴 상태입니다. VM을 사용하더라도 각 VM이 차지하는 메모리가 크므로, 같은 물리 서버에서 많은 애플리케이션을 실행할 수 없습니다.

Container는 리소스 사용량이 매우 적어서, 한 대의 서버에서 수백 개의 Container를 실행할 수 있습니다. 또한 자동 스케일링으로 인해 필요한 만큼만 Container를 실행하므로, 유휴 리소스를 최소화할 수 있습니다. Kubernetes의 bin packing 알고리즘은 물리 서버의 리소스를 최대한 효율적으로 사용합니다.

그 결과 전체 인프라 비용이 크게 절감되고, 같은 예산으로 더 높은 성능을 얻을 수 있습니다.

### 문제 4: 마이크로서비스 아키텍처의 관리 어려움 (Microservices Management)
마이크로서비스 아키텍처에서는 여러 개의 작은 서비스가 각각 배포되고 관리되어야 합니다. 각 서비스가 버전 업데이트될 때마다 배포해야 하고, 서비스 간의 네트워킹을 구성해야 하며, 서비스가 다운되면 자동으로 재시작해야 합니다. 이러한 작업을 수동으로 하기는 매우 복잡합니다.

Container와 Kubernetes 오케스트레이션 플랫폼을 함께 사용하면, 이러한 모든 작업이 자동화됩니다. 개발자가 할 일은 애플리케이션을 Container 이미지로 만들고, Kubernetes의 manifest 파일에 원하는 상태를 선언하는 것뿐입니다. Kubernetes가 나머지를 모두 처리합니다.

그 결과 마이크로서비스의 배포와 관리가 간단해지고, 서비스 간 통신도 자동으로 처리됩니다.

## ⚙️ 작동 원리

### Container의 라이프사이클

1. **이미지 생성 (Image Creation)**: Dockerfile에 기본 OS, 라이브러리, 애플리케이션 등을 정의합니다. `docker build` 명령으로 이미지를 생성하면, 각 명령이 하나의 레이어가 되어 쌓입니다.

2. **이미지 저장 (Image Storage)**: 생성된 이미지는 로컬 디스크에 저장되거나, Docker Hub 같은 레지스트리에 업로드됩니다.

3. **Container 생성 (Container Creation)**: `docker run` 명령으로 이미지로부터 Container를 생성합니다. 이 시점에서 이미지의 읽기 전용 레이어들 위에 새로운 쓰기 가능한 레이어가 추가됩니다.

4. **Container 실행 (Container Execution)**: Container의 엔트리포인트(entrypoint) 명령이 실행되고, 애플리케이션이 시작됩니다.

5. **Container 중지 (Container Stop)**: 애플리케이션이 종료되면 Container도 중지됩니다.

6. **Container 삭제 (Container Deletion)**: Container를 삭제하면, 쓰기 가능한 레이어도 함께 삭제됩니다. 이미지는 남아있으므로 언제든지 새로운 Container를 생성할 수 있습니다.

### 네트워킹

Docker는 각 Container에 가상 네트워크 인터페이스(veth)를 제공합니다. 호스트의 docker0 브리지 인터페이스를 통해 Container들이 서로 통신할 수 있습니다:

- Container 간 통신: docker0 브리지를 통해 172.17.0.0/16 네트워크에서 통신
- 외부 통신: 호스트의 NAT를 통해 외부 네트워크와 통신
- Port Publishing: Container의 포트를 호스트의 포트에 매핑 (예: 호스트의 8080을 Container의 80에 연결)

## 📊 비교: VM vs Container vs Bare Metal

| 항목 | VM | Container | Bare Metal |
|------|-----|-----------|-----------|
| **가상화 수준** | OS 수준 | 프로세스 수준 | 가상화 없음 |
| **이미지 크기** | 수 GB | 수십~수백 MB | 해당 없음 |
| **부팅 시간** | 수십 초 | 수백 밀리초 | 수 초 |
| **메모리 오버헤드** | 높음 (VM당 500MB~수GB) | 낮음 (Container당 50MB~수백MB) | 없음 |
| **격리 수준** | 강함 (OS 수준) | 중간 (프로세스 수준, 커널 공유) | 없음 |
| **배포 속도** | 느림 | 매우 빠름 | 해당 없음 |
| **호스트당 수량** | 수십 개 | 수백~수천 개 | 1개 |
| **성능** | 좋음 (5~10% 오버헤드) | 매우 좋음 (1~2% 오버헤드) | 최고 |
| **보안** | 강함 | 중간 | 약함 |
| **이식성** | 높음 | 매우 높음 | 낮음 |
| **사용 사례** | 다양한 OS 필요, 완전 격리 필요 | 마이크로서비스, 클라우드 네이티브 | 고성능 요구, 극저 지연시간 |

## ✅ 장점과 단점

### 장점
- **극도로 가벼움**: 각 Container는 수십 MB 정도로 매우 작아서 배포가 빠릅니다.
- **빠른 부팅**: 부팅 시간이 수백 밀리초 정도로 매우 빠릅니다.
- **높은 밀도**: 한 대의 서버에서 수백 개 이상의 Container를 실행할 수 있습니다.
- **완벽한 이식성**: Container 이미지는 모든 환경에서 동일하게 작동합니다.
- **개발과 배포 환경의 일치**: 개발 환경과 배포 환경을 정확히 동일하게 구성할 수 있습니다.
- **자동 스케일링**: Kubernetes 같은 오케스트레이션 플랫폼과 함께 자동 확장이 가능합니다.
- **빠른 배포**: 이미지만 준비되면 몇 초 내에 배포할 수 있습니다.
- **마이크로서비스에 최적화**: 작고 독립적인 서비스 배포에 매우 적합합니다.
- **리소스 효율성**: 커널을 공유하므로 VM에 비해 메모리와 디스크 사용량이 훨씬 적습니다.

### 단점 / 주의사항
- **커널 수준 보안 위험**: 호스트 커널의 버그가 모든 Container에 영향을 미칠 수 있습니다.
- **운영체제 제한**: Linux 기반이므로, Container에서 Windows 애플리케이션을 실행할 수 없습니다. (Windows Container도 있지만 제한적)
- **관리 복잡성**: 수많은 Container를 관리하려면 Kubernetes 같은 오케스트레이션 플랫폼이 필수입니다.
- **네트워킹 복잡성**: 여러 Container 간의 네트워킹을 설정하고 디버깅하기가 복잡할 수 있습니다.
- **스토리지 관리**: 상태 저장(stateful) 애플리케이션의 스토리지 관리가 VM보다 복잡합니다.
- **디버깅 어려움**: Container 내부에서 문제를 디버깅하기가 VM보다 어려울 수 있습니다.
- **보안 업데이트**: 기본 이미지에 보안 업데이트가 필요하면, 이미지를 다시 빌드하고 모든 Container를 재배포해야 합니다.
- **상태 관리**: Container는 일반적으로 상태가 없는(stateless) 설계를 권장하므로, 상태 저장이 필요한 애플리케이션은 특별한 처리가 필요합니다.

## 💡 실제 사용 사례

### 사례 1: Netflix의 마이크로서비스 아키텍처
Netflix는 Docker Container와 Kubernetes를 사용하여 수천 개의 마이크로서비스를 관리합니다. 각 서비스는 독립적인 Container로 배포되며, Kubernetes가 자동으로 리소스 할당, 로드 밸런싱, 장애 복구를 처리합니다. 이를 통해 Netflix는 초당 수백만 건의 요청을 처리하면서도, 개발팀이 자신의 서비스에만 집중할 수 있도록 합니다. Container의 빠른 배포 덕분에 새로운 기능을 수분 내에 배포할 수 있습니다.

### 사례 2: Google Cloud Run의 서버리스 Container
Google Cloud Run은 Container를 받아서 자동으로 확장 가능한 서버리스 환경에서 실행합니다. 개발자는 자신의 애플리케이션을 Container 이미지로 만들고, Cloud Run에 푸시하면 됩니다. Cloud Run이 자동으로 트래픽에 따라 Container의 개수를 조정하고, 사용한 리소스만 비용을 청구합니다. 이를 통해 개발자는 인프라 관리 없이 애플리케이션 개발에만 집중할 수 있습니다.

### 사례 3: 개발자의 로컬 개발 환경
개발팀이 Docker Compose를 사용하여 웹 애플리케이션의 전체 개발 스택을 정의합니다: 웹 서버 Container, 데이터베이스 Container, 캐시 서버 Container 등. 개발자는 `docker-compose up` 한 번만 실행하면, 모든 서비스가 자동으로 시작되고 서로 통신할 수 있습니다. 이전에는 각 개발자가 복잡한 설치 과정을 거쳐야 했지만, Container 덕분에 새로운 팀원도 5분 내에 개발 환경을 구성할 수 있습니다.

### 사례 4: 마이크래래프트 서버 호스팅
게임 호스팅 회사가 Docker를 사용하여 각 플레이어의 게임 서버를 독립적인 Container로 실행합니다. 플레이어가 새로운 게임 서버를 요청하면, 호스팅 회사는 미리 준비한 Minecraft Server 이미지로부터 새로운 Container를 생성합니다. 게임이 끝나면 Container를 종료합니다. Container 기술이 없었다면, 각 플레이어를 위해 별도의 가상 머신을 관리해야 했을 것입니다.

### 사례 5: CI/CD 파이프라인
소프트웨어 회사가 Container를 사용하여 빌드, 테스트, 배포를 자동화합니다. 개발자가 코드를 푸시하면, CI/CD 파이프라인이 자동으로 Container를 빌드하고, 테스트용 Container에서 테스트하고, 통과하면 프로덕션용 Container로 배포합니다. Container 덕분에 개발 환경과 배포 환경이 동일하므로, "나의 환경에서는 되는데"라는 문제가 발생하지 않습니다.

## 🔗 관련 용어
- [[Docker]]: Container를 만들고 실행하는 가장 널리 사용되는 플랫폼
- [[Kubernetes]]: Container를 자동으로 관리하고 스케일링하는 오케스트레이션 플랫폼
- [[마이크로서비스]]: Container와 함께 사용되는 아키텍처 패턴
- [[VM]]: Container와 비교되는 다른 가상화 기술
- [[Bare Metal]]: 가상화를 사용하지 않는 물리 서버
- [[이미지]]: Container의 템플릿으로 사용되는 읽기 전용 파일 시스템
- [[레지스트리]]: Docker 이미지를 저장하고 배포하는 저장소
- [[오케스트레이션]]: 많은 수의 Container를 자동으로 관리하는 기술
