# NFS (망 파일 시스템)

## 📝 정의

NFS는 **남의 기계에 있는 폴더를 내 폴더처럼 쓰게 하는 약속**이다.

앱은 `/data/사진.jpg` 를 평범하게 열 뿐이고, 그 경로가 다른 기계의 원반이라는 사실은 커널 아래에서만 안다. RFC 8881 은 NFSv4.1 을 "RPC 버전 2 와 그에 딸린 XDR 을 쓰는 원격 프로시저 호출 응용" 으로 정의하고, 서버가 "여러 파일 시스템에 대한 클라이언트의 접근을 조율할 책임을 진다" 고 적는다. 파일을 열고 읽고 잠그는 동작 하나하나가 그대로 망을 건너간다는 뜻이다.

### 이름
Network :: 서로 이어진 기계들
File :: 파일
System :: 다루는 체계
= 붙여 읽으면 "이어진 기계들의 파일을 다루는 체계". 남의 원반이 내 폴더 자리에 들어와 앉는다

### 비유
우리 집 벽에 옆집 책장을 그대로 뚫어 놓은 것 — 손은 우리 책장처럼 뻗지만 옆집이 문을 잠그면 그 손이 허공에서 멈춘다.

### 예
ls 를 쳤는데 커서만 깜빡이고 아무 줄도 안 나오던 그 순간이다. 원격 폴더가 붙어 있는 자리에서 흔히 벌어진다.

## 🖼️ 그림으로 보기

```도해
흐름: 남의 폴더가 내 폴더 자리에 붙기까지 무엇을 거치나
앱 :: /data 밑의 파일을 연다. 남의 것인 줄 모른다
커널 :: 그 경로는 붙여 둔 자리라고 알아본다
클라이언트 :: 파일 열기를 원격 호출로 바꿔 보낸다
파일 서버 :: 제 원반에서 읽어 답을 만든다
< 앱 :: 평범한 파일 읽기처럼 값이 돌아온다
= 앱은 끝내 모른다. 남의 기계라는 사실은 커널 밑에서만 안다
```

## ⚠️ 해결하는 문제

```도해
대조: 같은 파일을 기계마다 복사해 두면 무엇이 어긋나나
각자 복사 || 한 곳에 두고
고친 파일 :: 기계마다 다르다 || 모두 같은 것을 본다
새 기계 :: 다 받아야 뜬다 || 붙이면 바로 쓴다
쓰는 자리 :: 대수만큼 늘어난다 || 한 벌이면 된다
= 여러 대가 같은 파일을 봐야 할 때, 복사본을 늘리는 대신 원본 하나에 창을 낸다
```

웹 서버 열 대가 같은 업로드 폴더를 봐야 한다고 해 보자. 각자 복사해 두면 누가 언제 무엇을 고쳤는지에 따라 열 벌이 조금씩 달라지고, 새 기계를 한 대 띄울 때마다 전부 내려받을 때까지 기다려야 한다. 사용자가 방금 올린 그림이 새로고침할 때마다 보였다 안 보였다 하는 장애가 여기서 나온다.

NFS 는 **원본을 한 곳에 두고 나머지 기계는 그 자리를 자기 경로에 붙여** 이 문제를 없앤다. 앱 코드는 한 글자도 안 바뀐다 — 파일을 열고 읽는 평범한 코드가 그대로 돌고, 그 경로가 남의 기계라는 사실만 커널 아래에서 처리된다. 대신 그 대가로 파일 접근 하나하나가 망을 타게 되고, 망이 조용해지면 파일 읽기도 같이 조용해진다.

## ⚙️ 작동 원리

붙이는 명령은 이렇게 생겼다. AWS 가 관리형 파일 저장소에 권하는 값이 그대로다.

```
sudo mount -t nfs -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport 10.1.25.30:/ /mnt/data
```

`rsize` 와 `wsize` 는 한 번의 읽기·쓰기 호출에 담을 최대 바이트다. `timeo=600` 은 응답을 600데시초, 곧 60초까지 기다린다는 뜻이고 `retrans=2` 는 그다음 복구 동작에 들어가기 전까지 두 번 다시 보낸다는 뜻이다. 여기서 가장 중요한 값이 `hard` 다. AWS 는 데이터 무결성을 위해 이 값을 쓰라고 적는다 — 요청이 시간 안에 안 돌아오면 서버가 답할 때까지 **무한히** 다시 시도한다. `soft` 를 굳이 쓸 거라면 `timeo` 를 최소 150(15초)으로 두라고 덧붙이는데, 소프트 마운트에는 데이터가 깨질 위험이 본래 있기 때문이다.

4.1 이 그 전 판에 더한 것은 세션이다. RFC 8881 은 세션이 "모든 요청에 클라이언트 문맥을 주고, 멱등하지 않은 요청에도 튼튼한 재생 방지를 제공한다" 고 적는다. 같은 요청이 망 사정으로 두 번 도착해도 한 번만 실행되게 하는 장치다.

그리고 이 약속은 상태를 서버가 들고 있다. 서버가 재시작하면 클라이언트들이 정해진 유예 기간 안에 자기 잠금을 되찾는 절차를 밟는다. 파일 서버를 재부팅한 직후에 몇십 초 동안 이상하게 굼뜬 구간이 생기는 이유가 여기 있다.

## 💡 실제 사례

- **여러 대가 같은 파일을 봐야 할 때** — 업로드된 그림을 웹 서버 열 대가 다 읽어야 하면, 열 벌을 복사하는 대신 한 자리를 열 대가 함께 붙인다.
- **붙는 순간부터 막히는 장애** — 방화벽에서 2049 포트가 막혀 있으면 mount 가 2분쯤 멎어 있다가 `mount.nfs: Connection timed out` 으로 끝난다. 저장 문제처럼 보이지만 망 문제다.
- **이름만 못 푸는 실패** — 이름 해석 설정이 꺼져 있으면 `mount.nfs: Failed to resolve server ... Name or service not known` 이 나온다. 파일 서버는 멀쩡한데 주소를 못 찾은 것뿐이다.

## 🚫 흔한 오해

- **한번 붙여 놓으면 내 원반이랑 똑같다** — 경로만 같아 보인다. 모든 읽기가 망을 건너고, 저쪽이 조용해지면 내 쪽 프로세스가 그대로 멈춘다.
- **응답이 없으면 오류가 나겠지** — `hard` 로 붙였으면 오류가 아니라 무한히 다시 시도한다. AWS 가 무결성을 위해 권하는 값이 그것이고, 멈춤은 그 대가다.
- **파일을 나눠 쓸 일이 있으면 일단 붙이면 된다** — 여러 대가 같은 파일을 동시에 봐야 할 때 쓰는 것이다. 한 대만 쓰는 자리에 끼워 넣으면 원반의 고장에 망의 고장과 서버 재시작 뒤의 유예 기간까지 더 얹는 셈이 된다.

## 🚨 주의사항

- **멎은 것처럼 보일 때 실제로 멎은 것은 프로세스다.** AWS 문서는 붙여 둔 자리가 응답 없어 보이고 `ls` 같은 명령이 멎을 때 `ps aux` 로 그 자리를 쓰는 쪽을 보라 하고, 그 예시 줄의 상태 칸이 `D+`, 곧 끊을 수 없는 잠듦이다. 저쪽이 끝낼 때까지 기다리는 중이라는 뜻이고, `hard` 로 붙였다면 그 기다림에 정해진 끝이 없다.
- **부팅이 통째로 막힐 수 있다.** `/etc/fstab` 에 원격 자리를 적을 때 `_netdev` 를 빼면 망이 서기 전에 붙이려 들어 기계가 응답을 멈출 수 있다고 같은 문서가 적는다. 없어도 떠야 하는 자리면 `nofail` 을 함께 붙인다.
- **끊겼다 붙을 때 같은 포트를 다시 잡으려 든다.** 리눅스 5.4 이하의 클라이언트는 끊긴 뒤 같은 출발 포트로 재접속을 시도하는데, AWS 는 이 동작이 표준에 어긋나고 재접속을 늦춘다며 `noresvport` 를 강하게 권한다. 이때 로그에 남는 말이 `nfs: server_name still not responding` 이다.

## 📝 정리

**"남의 원반을 내 폴더 자리에 끌어다 붙이는 약속"** 이라고 읽으면 된다. 앱은 평범한 파일 읽기라고 믿지만 그 아래는 매번 망을 건너는 호출이고, 그래서 저쪽이 조용해지면 오류가 아니라 멈춤으로 나타난다.

## 🧒 열 살에게

우리 집 벽에 구멍을 내서 옆집 책장에 손이 닿게 해 놨다고 해 봐. 우리 책처럼 꺼내 읽을 수 있으니 똑같은 책을 두 집이 따로 사지 않아도 돼. 그런데 옆집이 문을 잠그면 네 손은 허공에서 계속 기다려.
