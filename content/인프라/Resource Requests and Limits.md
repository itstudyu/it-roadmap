# Resource Requests and Limits (요청량과 상한)

## 📝 정의

Requests 는 **자리를 잡을 때 쓰는 값**이고, Limits 는 못 넘게 막는 선이다.

쿠버네티스 문서는 둘을 한 문장씩으로 가른다 — 요청량을 적으면 kube-scheduler 가 그 값을 보고 어느 노드에 놓을지 정하고, 상한을 적으면 kubelet 이 그 컨테이너가 그보다 더 못 쓰게 막는다. 보는 사람도 다르고 보는 때도 다르다. 장애 때 "왜 안 뜨나" 와 "왜 죽었나" 가 갈리는 지점이 여기다.

### 이름
Request :: 이만큼은 달라
Limit :: 여기까지만
= 앞은 자리를 잡을 때 쓰는 약속, 뒤는 넘으면 깎이거나 죽는 선이다

### 비유
비행기 좌석 예약과 짐 무게 제한 같은 것이다 — 예약한 만큼 자리는 확보되고, 무게 선을 넘으면 아예 안 실어 준다.

### 예
아무것도 안 고쳤는데 밤새 파드가 여러 번 다시 뜬 흔적만 남아 있던 그 아침이다.

## 🖼️ 그림으로 보기

```도해
대조: 두 값은 각각 누가 언제 보나
Requests |=| Limits
보는 쪽 :: 스케줄러 || 커널과 kubelet
보는 때 :: 자리를 고를 때 || 도는 내내
안 맞으면 :: Pending 으로 멈춤 || 깎이거나 죽음
= 앞은 "어디에 놓을까" 를, 뒤는 "얼마까지 쓰게 둘까" 를 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 두 값을 안 적으면 무엇이 벌어지나
안 적으면 || 적어 두면
자리 고르기 :: 빈 데나 밀어 넣음 || 남는 만큼만 받음
한 놈이 폭주 :: 옆 파드까지 죽음 || 그 컨테이너만 죽음
쫓겨날 순서 :: 아무나 || 요청량 넘은 쪽부터
= 안 적으면 사고가 노드 전체로 번지고, 적어 두면 한 칸 안에서 끝난다
```

같은 노드에 올라탄 파드들은 그 기계의 CPU 와 메모리를 나눠 쓴다. 아무 값도 안 적으면 스케줄러는 그 파드가 얼마를 쓸지 모른 채 자리를 고르고, 커널은 어디서 잘라야 할지 모른 채 다 내준다. 그러다 한 파드가 메모리를 끌어 쓰면 노드 전체가 압박을 받고, 커널의 OOM killer 가 고른 프로세스가 죽는다 — 폭주한 놈이 아니라 옆 파드가 죽는 일이 흔하다.

두 값은 그 사고를 **한 컨테이너 안에 가둔다.** 요청량은 스케줄러에게 "이만큼은 남아 있는 노드로 보내라" 를 알려주고, 상한은 커널에게 "여기 넘으면 이 칸 안에서 끝내라" 를 알려준다. 그러면 폭주한 컨테이너만 죽고 옆 파드는 계속 돈다.

## ⚙️ 작동 원리

```도해
흐름: 메모리를 상한 너머로 쓰면 무슨 일이 벌어지나
컨테이너 :: 상한보다 더 달라고 한다
커널 :: 그 칸 안에서 회수할 게 있는지 본다
못 줄이면 :: 그 칸 안에서 OOM killer 를 부른다
프로세스 :: 죽는다. 종료 코드는 137 이다
kubelet :: 다시 띄운다. `RESTARTS` 가 하나 오른다
= 상한은 예방이 아니라 사후 집행이다. 넘는 순간이 아니라 못 줄일 때 죽는다
```

메모리와 CPU 는 성질이 다르다. 리눅스 cgroup v2 문서는 `memory.max` 를 "메모리 사용량의 강한 한도" 로 적고, 그 한도에 닿았는데 줄일 수 없으면 그 cgroup 안에서 OOM killer 가 불린다고 쓴다. 쿠버네티스 문서도 같은 것을 다른 말로 적는다 — 상한 집행은 반응적이라, 커널이 압박을 감지할 때 일어나므로 넘긴 즉시 죽지 않을 수도 있다.

노드가 모자라지 않아도 이 일은 일어난다. Azure 문서는 노드 자체가 압박을 안 받고 있어도 컨테이너가 제 상한을 넘기면 그 칸 안에서 죽는다고 적는다. 기계가 통째로 바닥나서 커널이 누구를 죽일지 고르는 [[OOM Killer]] 쪽과 달리, 여기서 죽는 대상은 처음부터 정해져 있다 — 선을 넘은 그 칸이다.

CPU 는 안 죽고 깎인다. cgroup 의 `cpu.max` 는 "$MAX $PERIOD" 꼴로 "이 주기 동안 이만큼까지" 를 정하고, 그 선에 닿으면 커널이 CPU 를 그만큼만 준다. 그래서 CPU 상한을 낮게 잡은 장애는 종료 코드도 재시작 기록도 안 남기고 그냥 느리기만 하다. 가장 찾기 어려운 자리다.

단위도 짝이 다르다. CPU 는 `1` 이 코어 하나이고 `100m` 이 0.1 코어다. 메모리는 `Mi`(2의 20제곱 바이트)와 `Gi` 를 쓴다. 상한만 적고 요청량을 비워 두면 쿠버네티스가 상한 값을 요청량에 그대로 복사해 넣는다.

## 📊 비교: QoS 세 등급은 무엇이 다른가

| 등급 | 조건 | 노드가 모자라면 |
|---|---|---|
| `Guaranteed` | 모든 컨테이너가 CPU·메모리 요청량 = 상한 | 가장 나중에 쫓긴다 |
| `Burstable` | 위도 아래도 아닌 나머지 전부 | 중간. 요청량을 넘겨 쓰는 쪽부터 |
| `BestEffort` | 아무것도 안 적었다 | 가장 먼저 쫓긴다 |

## 💡 실제 사례

- **파드가 Pending 에서 안 넘어감** — `kubectl describe pod` 의 이벤트에 `FailedScheduling` 과 `Insufficient memory` 가 찍힌다. 앱이 고장 난 게 아니라 요청량이 어느 노드에도 안 들어간다는 뜻이다.
- **밤새 `RESTARTS` 만 오름** — `kubectl describe pod` 의 `Last State` 에 `Reason: OOMKilled`, `Exit Code: 137` 이 남는다. 상한을 넘겨 커널이 죽인 것이다.
- **노드에 얼마가 잡혀 있나** — `kubectl describe node` 의 `Allocated resources` 가 요청량 합계를, `kubectl top node` 가 실제 사용량을 보여준다. 둘이 크게 벌어지면 값이 현실과 안 맞는 것이다.

## 🚫 흔한 오해

- **`Exit Code: 137` 이면 무조건 메모리 부족이다** — 137 은 SIGKILL 을 받았다는 뜻일 뿐이다. Azure 문서는 `Reason: OOMKilled` 인지 `Reason: Error` 인지를 보라고 적는다. 뒤쪽이면 헬스 체크 실패나 사람이 지운 것일 수 있다.
- **상한을 넉넉히 잡아 두면 안전하다** — 스케줄러는 상한이 아니라 요청량으로 자리를 고른다. 요청량은 낮고 상한만 높으면 노드에 실제보다 많이 밀어 넣게 되고, 다 같이 몰리는 순간 노드가 통째로 흔들린다.
- **CPU 상한을 꽉 조여 두면 안정적이다** — CPU 는 넘겨도 안 죽고 깎이기만 한다. 너무 낮게 잡으면 죽지도 않으면서 계속 느린, 로그에 아무 흔적도 안 남는 장애가 된다.

## 🚨 주의사항

- **요청량은 실제 쓰는 양에 가깝게 적어라.** Azure 문서는 kubelet 이 쫓아낼 때 요청량을 넘겨 쓰는 파드부터 고른다고 적는다. 낮게 적어 두면 남는 자리를 얻는 대신 제일 먼저 쫓긴다.
- **상한만 적으면 요청량이 상한과 같아진다.** 노드가 실제보다 빨리 차서, 넉넉히 잡았다고 생각한 값이 오히려 다른 파드를 못 들어오게 막는다.
- **OOM killer 가 고르는 프로세스는 정해져 있지 않다.** Azure 문서는 커널이 휴리스틱으로 고르므로 가장 많이 쓰는 프로세스가 죽는다는 보장이 없다고 적는다. 죽은 것과 원인이 다를 수 있다.

## 📝 정리

**"자리 잡을 때 쓰는 값과 넘으면 안 되는 선"** 이라고 읽으면 된다. 앞의 값이 어느 기계에 놓일지를 정하고 뒤의 값이 얼마까지 쓰게 둘지를 정하는데, 메모리는 넘으면 죽고 CPU 는 넘으면 느려진다.

## 🧒 열 살에게

비행기 탈 때 자리는 미리 예약해 두지? 예약을 안 하면 앉을 자리가 남았는지도 모르는 채로 가야 하고, 가방이 정해진 무게를 넘으면 그 자리에서 도로 내려놔야 해. 그래서 "이만큼 쓸게" 를 미리 말해 두고 "여기까지만" 도 같이 정해 두는 거야.
