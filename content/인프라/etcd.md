# etcd (이티시디)

## 📝 정의

클러스터의 모든 상태가 적혀 있는 **합의된 저장소**다.

etcd 문서는 스스로를 "설정 관리·서비스 찾기·분산 작업 조율을 위한 일관된 키-값 저장소" 라 적고, 곧바로 성격을 못 박는다 — **갈라진 채로 각자 도는 상태를 절대 못 견디고, 그걸 막기 위해서라면 가용성을 내놓겠다는 쪽**이다. 쿠버네티스 문서도 etcd 를 "모든 클러스터 자료의 뒷단 저장소" 라 부르고, etcd 에 닿는 것은 클러스터의 관리자 권한과 같다고 적는다. 파드도 시크릿도 노드 목록도 결국 여기 한 군데에만 적혀 있다.

### 이름
etc :: 리눅스의 설정 폴더
d :: 여러 대에 흩어진
= 붙여 읽으면 "여러 대가 함께 보는 설정 폴더". 그 폴더가 클러스터의 유일한 원본이다

### 비유
동아리 회칙 공책 한 권 — 여러 명이 돌려 보되, 한 줄을 고치려면 과반이 동의해야 한다.

### 예
목록 조회가 전부 먹통이 되고 관문 로그에 저장소가 꽉 찼다는 줄만 반복되던 그 새벽이다.

## 🖼️ 그림으로 보기

```도해
층: 클러스터의 상태는 어디에 진짜로 적혀 있나
kubectl :: 사람이 치는 명령. 아무것도 안 들고 있다
kube-apiserver :: 유일한 관문. 검사해 넘길 뿐 저장하지 않는다
etcd :: 실제로 적히는 곳. 여기 없으면 없는 것이다
디스크 :: 과반이 동의한 뒤 각 대의 파일로 내려간다
= 다른 부품은 전부 etcd 를 다시 읽어 스스로를 만든다. 원본은 한 군데다
```

## ⚠️ 해결하는 문제

```도해
대조: 상태를 각 대가 따로 들고 있으면 무슨 일이 생기나
따로 들고 있으면 || 한 군데에 모으면
정전 뒤 :: 서로 다른 답 || 한 답으로 복구
망이 끊기면 :: 양쪽이 주인 행세 || 과반만 쓴다
백업 :: 무엇을 뜰지 모름 || 한 파일이면 끝
= 여러 대가 하나처럼 굴려면 "무엇이 참인가" 를 정하는 곳이 하나여야 한다
```

여러 대가 함께 일하는 판에서 가장 무서운 사고는 고장이 아니라 **의견이 갈리는 것**이다. 망이 잠깐 끊겨 세 대가 둘과 하나로 나뉘었을 때 양쪽이 각자 "내가 주인" 이라고 믿고 쓰기 시작하면, 망이 붙은 뒤에 어느 쪽이 맞는지 정할 방법이 없다. 고친 자국은 남아 있는데 원본이 둘인 상태가 된다.

etcd 는 이걸 **쓰기 전에 과반의 동의를 받는 규칙**으로 막는다. 세 대 중 둘, 다섯 대 중 셋이 동의해야 한 줄이 적힌다. 그래서 대수를 홀수로 두라는 권고가 나오고(짝수는 견딜 수 있는 고장 수가 같으면서 대수만 는다), 과반을 못 채운 쪽은 아예 쓰기를 거절한다. 못 쓰는 것이 잘못 쓰는 것보다 낫다는 선택이다.

## ⚙️ 작동 원리

고친 자국마다 전 클러스터에서 유일한 번호(revision)가 붙는다. 값을 덮어써도 옛 판이 그 자리에 남고, 번호만 하나 올라간다. 지켜보기(watch)가 놓치는 것 없이 동작하는 것도 이 번호 덕이고, 저장 크기가 쓴 만큼이 아니라 **고친 횟수만큼** 자라는 것도 같은 이유다.

그래서 운영에서 실제로 마주치는 사고 하나가 **저장 용량 초과**다. 기본 한도는 2GiB 이고(`--quota-backend-bytes` 로 바꾼다) 권고 상한은 8GiB 인데, 넘으면 NOSPACE 경보가 서고 클러스터가 읽기와 지우기만 받는다. 이때 나오는 문구가 `etcdserver: mvcc: database space exceeded` 다. 관문이 아무것도 못 쓰니 배포도 스케일도 전부 멎는다.

푸는 순서는 셋이다 — 옛 판을 정리하고(`compact`), 빈틈을 디스크에 돌려주고(`defrag`), 경보를 내린다(`alarm disarm`). 경보를 안 내리면 공간을 비워도 쓰기가 안 열린다.

```bash
etcdctl --write-out=table endpoint status   # 어느 대가 리더인지, DB 가 몇 바이트인지
etcdctl alarm list                          # NOSPACE 가 서 있나
etcdctl compact 1234567                     # 그 번호 이전 판을 버린다
etcdctl defrag                              # 빈틈을 디스크에 돌려준다
etcdctl alarm disarm                        # 경보를 내려 쓰기를 연다
etcdctl snapshot save backup.db             # 이거 없이 잃으면 클러스터가 끝난다
```

## 💡 실제 사례

- **클러스터 백업** — 사실상 etcd 스냅숏 한 파일이 전부다. 이 파일이 없으면 되살릴 원본이 없다.
- **리더 뽑기와 잠금** — 만료 시간이 붙은 열쇠와 지켜보기를 써서, 여러 대 중 한 대만 일하게 만드는 장치의 바탕이 된다.
- **느려진 클러스터** — 명령이 전부 굼뜰 때 디스크가 느린 노드에 etcd 가 얹혀 있는 경우가 흔하다. etcd 는 디스크와 망 지연에 특히 민감하다.

## 🚫 흔한 오해

- **etcd 는 쿠버네티스의 일부다** — 아니다. 따로 만들어진 저장소를 쿠버네티스가 골라 쓰는 것이고, 다른 것들도 조율용으로 쓴다.
- **키-값 저장소니까 앱 자료도 여기 넣으면 되겠다** — etcd 문서 스스로 몇 GB 까지를 가정한다고 적는다. 조율용 메타 자료를 두는 곳이지 앱 저장소가 아니다.
- **파드가 다 살아 있으면 클러스터는 무사하다** — etcd 가 멎어도 이미 뜬 파드는 계속 돈다. 다만 아무것도 바꿀 수 없고, 무언가 죽어도 새로 안 뜬다.

## 🚨 주의사항

- **홀수 대로 두고 서로 다른 자리에 나눠라.** 다섯 대면 두 대가 죽어도 과반이 남는다.
- **디스크를 나눠 쓰지 마라.** 다른 것이 디스크를 잡으면 심장박동이 밀려 리더가 계속 바뀐다.
- **스냅숏을 뜨고 복원을 실제로 해 봐라.** 떠 놓기만 하고 안 풀어 본 백업은 백업이 아니다.
- **접근을 조인다.** etcd 를 읽을 수 있으면 클러스터의 모든 시크릿을 평문으로 읽을 수 있다.

## 📝 정리

**"클러스터가 뭘 정했는지 적혀 있는 단 한 권"** 이라고 읽으면 된다. 여러 대가 갈라진 채 각자 주인 행세를 하는 사고를 막으려고, 한 줄을 적을 때마다 과반의 동의를 받고 못 받으면 아예 거절한다. 고친 자국이 번호와 함께 쌓이는 구조라 크기가 한도를 넘으면 클러스터가 통째로 읽기 전용이 되고, 그때는 정리·조각모음·경보 해제 순서로 푼다.

## 🧒 열 살에게

반에서 정한 규칙을 각자 수첩에 적어 두면 나중에 서로 다르게 기억하지? 그래서 공책 한 권만 진짜로 치고, 거기에 한 줄 적으려면 반 인원의 절반 넘게 손을 들어야 해. 그 공책이 사라지면 반이 뭘 정했는지 아무도 모르니까 매일 베껴 둬.

## ❓ 이해했는지

- 망이 잠깐 끊겨 두 덩이로 나뉘었을 때 양쪽이 다 쓰지 못하게 막는 것은 무엇인가 → 해결하는 문제
- 값을 지우기만 했는데 저장 크기가 안 줄어드는 이유는 무엇인가 → 작동 원리
- etcd 가 멎었는데도 사이트는 계속 열리는 일은 왜 생기나 → 흔한 오해
