# GitOps (깃옵스)

## 📝 정의

GitOps 는 **저장소에 적힌 상태로 실제 환경을 계속 맞추는 방식**이다.

Flux 문서는 이것을 "전체 시스템을 선언적으로 기술하고 버전 관리하며, 배포된 환경이 하나 이상의 Git 저장소에 명시된 상태와 일치하도록 보장하는 자동화된 과정을 갖추는, 인프라와 애플리케이션 관리 방식" 으로 적는다.

### 이름
Git :: 버전 저장소
Ops :: 운영하기
= 붙여 읽으면 "저장소로 운영한다". 무엇을 바꾸든 저장소를 고치는 일로 한다

### 비유
교실 벽에 붙은 자리표. 자리를 바꾸려면 책상을 미는 게 아니라 자리표를 고치고, 누가 몰래 옮겨 앉아도 다음 점검 때 자리표대로 되돌려진다.

### 예
운영 환경이 이상하다 싶을 때 기계에 접속하지 않고 저장소의 파일부터 열어 보게 되는 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 저장소를 고치면 실제 환경이 어떻게 따라오나
저장소 :: 원하는 상태가 선언으로 적혀 있다
에이전트 :: 그 선언을 스스로 끌어온다
견주기 :: 지금 상태와 적힌 상태를 맞대 본다
맞추기 :: 다른 만큼만 실제 환경에 적용한다
@ 다시 견주기로 :: 손으로 고쳐 놓아도 다음 바퀴에 되돌아간다
= 한 번 밀어 넣는 게 아니라, 저장소와 같아질 때까지 계속 도는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 배포를 밖에서 밀어 넣으면 무엇이 어긋나나
밀어 넣기 || GitOps
지금 상태 :: 물어봐야 안다 || 저장소가 답한다
손댄 흔적 :: 조용히 남는다 || 곧 되돌아간다
되돌리기 :: 절차를 다시 || 이전 커밋으로
= 무엇이 돌고 있는지 저장소만 보면 알고, 되돌리는 일도 저장소에서 끝난다
```

밖에서 밀어 넣는 방식에서는 "지금 무엇이 돌고 있나" 에 답할 수 있는 곳이 환경 자체뿐이다. 급해서 손으로 한 번 고쳐 놓은 값, 실패한 채 절반만 반영된 변경, 아무도 기억 못 하는 임시 설정이 거기 그대로 남는다. 되돌리려 해도 무엇을 되돌려야 하는지부터 조사해야 한다.

GitOps 는 원하는 상태의 원본을 환경 밖의 저장소로 옮긴다. 그러면 지금 어떤 모습이어야 하는지는 저장소를 읽어 알 수 있고, 되돌리기는 이전 커밋으로 돌아가는 일이 된다. 그리고 안에서 도는 소프트웨어 에이전트가 계속 견주기 때문에, 손으로 고쳐 놓은 값은 남는 것이 아니라 곧 지워진다.

## ⚙️ 작동 원리

OpenGitOps 는 이 방식을 원칙 넷으로 못 박는다. 첫째, GitOps 로 관리되는 시스템은 **원하는 상태가 선언으로 표현**되어야 한다. 둘째, 그 원하는 상태는 **불변성과 버전 관리를 강제하는 방식**으로 저장되고 전체 변경 이력을 남긴다. 셋째, 소프트웨어 에이전트가 그 선언을 원본에서 **자동으로 끌어온다**. 넷째, 에이전트가 실제 시스템 상태를 **계속 지켜보며 원하는 상태를 적용하려 한다**.

뒤의 둘이 이 방식의 성격을 정한다. 밖에서 환경으로 밀어 넣는 것이 아니라 환경 안쪽에서 끌어오고, 한 번 적용하고 끝나는 것이 아니라 계속 견준다. Flux 문서는 이 견주기를 **조정**(reconciliation)이라 부르며 "주어진 상태가 어딘가에 선언적으로 정의된 원하는 상태와 일치하도록 보장하는 것" 으로 적고, 그래서 명령으로 클러스터(같이 묶여 도는 기계 떼)를 직접 고치면 그 변경이 곧 되돌려진다고 말한다.

원칙 문장 어디에도 특정 실행 환경 이름은 없다. [[Kubernetes]] 에서 가장 먼저 자리 잡았을 뿐, 선언으로 적을 수 있고 끌어와 맞출 에이전트를 둘 수 있으면 같은 얼개가 선다.

## 💡 실제 사례

- **되돌리기가 커밋 하나로 끝난다** — 저장소를 이전 커밋으로 돌리면 에이전트가 환경을 그 상태로 도로 맞춘다.
- **손댄 것이 스스로 지워진다** — Flux 문서는 클러스터를 명령으로 직접 고치면 그 변경이 곧 되돌려진다고 적는다.
- **무엇이 돌고 있는지 한 곳에서 본다** — 환경마다 물어보는 대신 저장소의 선언과 커밋 이력을 읽는다.

## 🚫 흔한 오해

- **소스를 Git 에 두고 있으니 우리는 이미 GitOps 다** — 저장소에 파일이 있는 것과, 에이전트가 그 선언을 스스로 끌어와 실제 상태를 계속 맞추는 것은 다른 일이다. 원칙 넷 중 뒤의 둘이 그 차이를 가리킨다.
- **GitOps 를 하면 파이프라인이 필요 없어진다** — 빌드하고 시험해 산출물을 만드는 일은 그대로 남는다. 이 방식이 바꾸는 것은 그 결과를 환경에 어떻게 반영하느냐 쪽이다.
- **모든 것을 GitOps 로 옮기는 편이 항상 낫다** — 선언으로 적을 수 없는 일회성 작업까지 저장소에 밀어 넣으면 저장소가 실행 기록으로 지저분해진다. 계속 같은 모습으로 유지되어야 하는 것부터 옮긴다.

## 📝 정리

**"저장소에 적힌 대로 계속 되돌려 놓는 방식"** 이라고 읽으면 된다. 저장소가 원하는 상태의 원본이고, 안에서 도는 에이전트가 실제 상태를 계속 지켜보다가 다를 때마다 적힌 대로 맞춘다. 그래서 여기서 "배포한다" 는 환경에 밀어 넣는 일이 아니라 저장소를 고치는 일이 된다.

## 🧒 열 살에게

교실 벽에 자리표가 붙어 있어. 자리를 바꾸고 싶으면 책상을 미는 게 아니라 벽의 자리표를 고치면 돼. 반장이 계속 둘러보다가 자리표랑 다른 데 앉은 애가 있으면 자리표대로 도로 앉혀.

## ❓ 이해했는지

- 환경을 손으로 고쳐 놓아도 얼마 뒤 원래대로 돌아가는 이유는 무엇인가 → 그림
- 지금 무엇이 돌고 있는지 알려면 어디부터 열어 봐야 하나 → 해결하는 문제
- 저장소를 쓴다고 해서 다 이 방식이 되지는 않는 까닭은 무엇인가 → 흔한 오해
