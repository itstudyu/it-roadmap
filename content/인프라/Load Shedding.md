# Load Shedding (부하 덜어내기)

## 📝 정의

Load Shedding은 **넘치는 요청을 일부러 빨리 거절해 나머지를 살리는 일**이다.

감당할 수 있는 양을 넘어선 뒤에도 다 받아 주면 대기 줄이 끝없이 길어지고, 결국 답이 나갈 때쯤에는 부른 쪽이 이미 포기한 뒤다. Google SRE 책은 이 상황을 방치하면 일부의 실패가 다른 부품의 실패를 불러 전체가 무너질 수 있다고 적는다. 덜어내기는 지금 이 한 대를 살리는 일이라기보다 옆 대까지 안 끌고 가는 일이다.

### 이름
Load :: 짊어진 짐
Shed :: 벗어 던지다
-ing :: 하고 있음
= 붙여 읽으면 "짐을 벗어 던지는 일". 다 지고 가다 주저앉느니 일부를 내려놓는다

### 비유
엘리베이터의 정원 초과 경고음. 한두 명이 내려야 나머지가 올라간다.

### 예
표가 열리는 순간의 예매 창에서 "잠시 후 다시 시도해 주세요" 를 곧바로 받았던 그 순간이다. 한참 돌다 끊기는 것보다 낫다.

## 🖼️ 그림으로 보기

```도해
흐름: 요청이 감당할 양을 넘으면 무엇을 하나
문 앞 :: 지금 동시에 몇 개를 물고 있는지 센다
상한 :: 정해 둔 수를 넘었는지 견준다
가름 :: 급한 것과 미뤄도 되는 것을 나눈다
버림 :: 미뤄도 되는 쪽에 곧바로 거절을 돌려준다
남긴 것 :: 상한 안쪽이라 제 속도로 끝난다
= 다 받아 다 늦게 하느니, 일부를 즉시 돌려보내고 나머지를 제때 끝낸다
```

## ⚠️ 해결하는 문제

```도해
대조: 넘치는 요청을 다 받으면 무엇이 무너지나
다 받으면 || 덜어내면
대기 줄 :: 끝없이 길어진다 || 상한에서 멈춘다
응답 시간 :: 전부 같이 느려진다 || 받은 것은 제때
끝낸 일 :: 답할 때쯤 끊긴다 || 처리량이 버틴다
= 다 받아 주는 것은 친절이 아니다. 아무도 답을 못 받는 상태로 가는 길이다
```

용량을 넘긴 뒤에도 계속 받으면 요청은 사라지지 않고 대기 줄에 쌓인다. 줄이 길어지면 모든 요청의 응답 시간이 같이 늘어나고, 늘어난 응답 시간은 부르는 쪽의 시간 초과를 부른다. 이미 포기한 요청을 계속 처리하고 있는 상태가 되고, 그때부터는 일한 만큼 아무 성과도 안 남는다.

덜어내기는 **넘친 몫을 저장하지 않고 즉시 돌려보내서** 이 나선을 끊는다. 다 받아 전부 늦어지는 대신, 일부를 곧바로 거절하고 받은 것은 제때 끝낸다. 그러면 부하가 아무리 올라가도 실제로 끝나는 일의 양이 무너지지 않는다.

## ⚙️ 작동 원리

정할 것이 둘이다 — **얼마나 받을지**와 **누구를 먼저 버릴지**.

얼마나는 초당 요청 수로 못 잰다. Google SRE 책은 요청마다 드는 비용이 크게 달라서 초당 요청 수로 용량을 잡으면 잘 안 맞고, 실제 자원을 직접 세는 편이 훨씬 낫다고 적는다. 주로 쓰는 신호가 CPU 인데, 메모리 압박도 결국 가비지 컬렉션을 거쳐 CPU 사용으로 나타나기 때문이다.

누구를 먼저는 등급으로 정한다. 같은 책은 요청을 네 등급으로 나눈다 — 가장 높은 CRITICAL_PLUS, 기본값인 CRITICAL, 배치 작업이 쓰는 SHEDDABLE_PLUS, 자주 못 써도 괜찮은 SHEDDABLE. 넘칠 때는 아래 등급부터 거절한다. 사람이 화면 앞에서 기다리는 요청과 밤에 도는 집계가 같은 줄에 서 있으면 안 된다는 뜻이다.

쿠버네티스의 API 서버가 이 구조를 그대로 갖고 있다. 문서는 `--max-requests-inflight` 같은 전체 상한만으로는 "높은 트래픽 시기에 가장 중요한 요청이 통과하도록 보장하기에 충분하지 않다" 고 적고, 대신 FlowSchema 로 요청을 갈래로 나누고 PriorityLevelConfiguration 으로 갈래마다 동시 처리 한도를 따로 준다. 아주 짧은 몰림은 거절하지 않고 큐에 잠깐 담고, 그래도 넘치면 `429 Too Many Requests` 로 돌려준다. 얼마나 거절했는지는 `apiserver_flowcontrol_rejected_requests_total` 이 센다.

한 갈래가 상한을 다 먹지 못하게 하는 장치도 들어 있다. 같은 문서는 공정 큐 기법을 써서 "행실이 나쁜 컨트롤러 하나가 같은 등급의 다른 요청을 굶기지 않게" 한다고 적는다. 크게 나올 것이 뻔한 목록 조회는 자리를 여러 칸 차지한 것으로 세서, 무거운 요청 하나가 동시성을 통째로 먹는 일도 막는다.

## 💡 실제 사례

- **손쓸 창구는 살려 두기** — 쿠버네티스는 API 서버가 밀릴 때도 일부 요청을 면제 등급으로 두어 통과시킨다. 고칠 창구까지 같이 막히면 손쓸 방법이 없어진다.
- **배치를 먼저 버리기** — 밤에 도는 집계와 사람이 누른 결제가 같이 밀려 있으면 집계 쪽을 먼저 거절한다. 등급을 미리 붙여 둬야 그 순간에 고를 수 있다.
- **429 를 받는 쪽의 몫** — 거절을 받은 쪽이 곧바로 다시 부르면 아무것도 안 덜어진다. SRE 책이 요청당 3회, 클라이언트당 재시도 비율 10% 같은 예산을 두는 이유다.

## 🚫 흔한 오해

- **요청을 버리는 건 그 자체로 장애다** — 아니다. 다 받아 전부 늦어지는 것이 장애고, 일부를 즉시 돌려보내 나머지를 제때 끝내는 것이 대응이다.
- **덜어내기를 걸어 두면 자동 확장은 필요 없다** — 덜어내기는 늘어나는 동안 버티는 장치다. 용량을 만들어 주지는 않으니 둘은 서로를 대신하지 못한다.
- **모든 요청에 같은 상한을 걸면 공평하다** — 한 갈래가 그 상한을 다 먹으면 나머지가 굶는다. 쿠버네티스가 갈래마다 한도를 따로 두고 공정 큐를 쓰는 것도, 행실이 나쁜 하나가 같은 등급의 다른 요청을 굶기지 않게 하려는 것이다.

## 🚨 주의사항

- **재시도가 거절을 배로 키운다.** SRE 책은 이미 과부하 상태의 작업에 세 번 떨어진 요청이라면 한 번 더 해서 될 가능성이 낮다고 적고, 요청당 최대 3회와 클라이언트당 재시도 비율 10% 라는 예산을 둔다. 거절만 걸고 재시도를 안 막으면 덜어낸 만큼 그대로 되돌아온다.
- **거절은 빨라야 한다.** 오래 붙들고 있다가 거절하면 부른 쪽의 자원도 그동안 묶인다. 큐는 짧은 몰림을 흡수하는 자리지 넘치는 양을 저장하는 자리가 아니다.
- **덜어낸 양이 안 보이면 안 걸린 것과 같다.** 얼마나 거절했는지를 숫자로 내보내고 알림에 걸어 두지 않으면, 조용히 거절만 늘어난 채로 며칠이 간다.

## 📝 정리

**"넘칠 때 일부를 먼저 내려놓고 나머지를 제때 끝내는 일"** 이라고 읽으면 된다. 얼마나 받을지는 초당 요청 수가 아니라 실제 자원으로 재고, 누구를 버릴지는 미리 붙여 둔 등급으로 고른다. 거절만 걸고 재시도를 안 막으면 덜어낸 양이 그대로 되돌아온다.

## 🧒 열 살에게

엘리베이터에 사람이 너무 많이 타면 문이 안 닫히고 삐 소리가 나지? 그때 한두 명이 내려야 나머지가 올라갈 수 있어. 다 타겠다고 버티면 결국 아무도 못 올라가.
