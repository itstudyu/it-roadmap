# Logging (로그, 로깅)

## 📝 정의

Logging은 **프로그램이 한 일을 나중에 볼 수 있게 남기는 일**이다.

운영 중인 서버에는 디버거를 붙여 멈춰 세울 수 없다. 이미 지나간 일이 왜 그렇게 됐는지 알 수 있는 재료는 그때 남긴 기록뿐이다.

### 이름
= 배의 속도를 재려고 바다에 던지던 통나무(log)에서 항해 일지가 나왔다. 그 일지를 적는 일이 그대로 이 말이다

### 비유
항공기 블랙박스. 사고를 다시 일으켜볼 수는 없으니 남은 기록으로 되짚는다.

### 예
고객센터에 문의하면 몇 시쯤 무엇을 눌렀는지 되묻는데, 그 시각으로 남은 기록을 찾기 때문이다.

### 직접
윈도우에서 "이벤트 뷰어", 맥에서 "콘솔" 을 열어 보라. 시각과 등급이 앞에 붙은 줄이 지금 이 순간에도 쌓이고 있다.

## 🖼️ 그림으로 보기

```도해
흐름: 코드 한 줄이 남긴 기록은 어디까지 가나
코드 :: 이 지점에서 무슨 일이 있었는지 적는다
설정 :: 정해둔 레벨보다 낮으면 여기서 버린다
포맷 :: 시각과 레벨과 내용을 정해진 모양으로 만든다
수집기 :: 여러 서버에 흩어진 것을 한곳으로 모은다
저장소 :: 검색할 수 있게 색인해 쌓아둔다
사람 :: 조건을 걸어 그때 무슨 일이 있었는지 찾는다
= 남기는 것만큼 나중에 찾을 수 있게 만드는 일이 절반이다
```

## ⚠️ 해결하는 문제

```도해
대조: 운영 서버에서 오류가 났는데 기록이 없으면 어떻게 되나
기록 없이 || 로그로
원인 파악 :: 재현부터 해야 || 그때 기록을 봄
간헐적 오류 :: 사실상 못 잡음 || 조건을 좁혀감
느려진 구간 :: 짐작만 한다 || 단계별 시간
= 다시 일으킬 수 없는 일을 되짚는 유일한 재료다
```

사용자가 "어제 저녁에 결제가 안 됐다"고 알려오면 그 상황을 다시 만들어야 원인을 볼 수 있다. 그런데 같은 시각, 같은 데이터, 같은 부하를 다시 만드는 일은 대개 불가능하다. 재현을 못 하면 코드를 눈으로 읽으며 짐작하는 수밖에 없다.

로그는 그 순간을 남겨둔다. 어느 단계까지 갔는지, 어떤 값이 들어왔는지, 어디서 예외가 났는지가 적혀 있으면 재현하지 않고도 원인을 좁힐 수 있다.

## ⚙️ 작동 원리

```도해
층: 레벨은 무엇을 기준으로 나뉘나
DEBUG :: 개발 중에만 본다. 양이 가장 많다
INFO :: 정상 동작 중 남길 사건. 시작과 완료
WARN :: 지금은 도는데 곧 문제가 될 것
ERROR :: 그 요청은 실패했다. 서비스는 돈다
FATAL :: 더 못 돈다. 여기서 멈춘다
= 아래로 갈수록 건수는 줄고 한 줄의 무게가 커진다
```

레벨을 나누는 이유는 환경마다 남길 양을 다르게 하기 위해서다. 개발 환경에서는 DEBUG 까지 켜두고, 운영에서는 INFO 아래를 버린다. 코드에는 같은 줄이 그대로 있고 설정만 바뀐다.

남기는 모양도 정해둔다. 시각과 레벨을 문장 앞에 붙이는 것은 기본이고, 요청마다 같은 식별자를 넣어두면 흩어진 줄들을 하나의 요청으로 다시 묶을 수 있다.

## 📊 비교: 평문 로그와 구조화 로그

| | 평문 | 구조화 |
|---|---|---|
| 모양 | 한 줄 문장 | 필드가 나뉜 JSON |
| 검색 | 문자열로 찾는다 | 필드 조건으로 거른다 |
| 문구를 고치면 | 찾던 조건이 깨진다 | 필드가 그대로면 괜찮다 |
| 사람이 읽기 | 그대로 읽힌다 | 도구를 거치는 편이 낫다 |

## 💡 실제 사례

- **장애 원인 추적** — 실패한 요청의 시각과 식별자로 걸러 어느 단계에서 끊겼는지 찾는다.
- **느려진 구간 찾기** — 단계마다 걸린 시간을 남겨두면 어디서 밀렸는지가 드러난다.
- **이상 접근 감지** — 짧은 시간에 한 주소에서 로그인 실패가 몰리는 패턴을 알아챈다.

## 🚫 흔한 오해

- **로그는 많이 남길수록 좋다** — 양이 늘면 찾는 일이 어려워지고 저장 비용과 쓰기 부담도 같이 는다. 운영에서 DEBUG 를 켜두면 정작 봐야 할 줄이 파묻힌다.
- **로그는 오류가 났을 때 쓰는 것이다** — 정상 동작 기록이 있어야 무엇이 달라졌는지 비교가 된다. 오류 줄만 있으면 그 앞에서 무슨 일이 있었는지 알 수 없다.
- **일단 다 남기고 나중에 골라 보면 된다** — 비밀번호나 주민번호가 한 번 로그에 들어가면 그 로그가 복사된 곳마다 같이 퍼진다.

## 🚨 주의사항

- **민감한 값은 가리고 남긴다.** 비밀번호와 카드번호와 토큰은 아예 빼거나 일부만 남긴다.
- **보관 기간을 정해둔다.** 지우는 규칙이 없으면 디스크가 먼저 차고, 그때는 로그를 남길 자리도 없다.

## 📝 정리

**"지나간 일을 되짚을 수 있게 그때그때 적어 두는 일"** 이라고 읽으면 된다. 무엇을 어떤 레벨로 남기고 얼마나 오래 두느냐를 정하는 것이 실제 작업이며, 찾을 수 없는 기록은 안 남긴 것과 같다.

## 🧒 열 살에게

비행기에는 무슨 일이 있었는지 계속 적어 두는 까만 상자가 실려 있어. 사고가 나면 그 비행을 똑같이 다시 해 볼 수는 없으니까 그 상자에 적힌 걸 읽어서 어디서부터 잘못됐는지 알아내. 컴퓨터도 그때그때 적어 두지 않으면 어제 있었던 일은 아무도 못 되짚어.

## ❓ 이해했는지

- 운영 서버에서 DEBUG 를 계속 켜두면 무엇이 나빠지나 → 흔한 오해
- 한 요청이 남긴 줄들이 여기저기 흩어졌을 때 다시 묶으려면 무엇이 필요한가 → 작동 원리
- 평문 대신 JSON 으로 남기면 무엇이 쉬워지나 → 비교
