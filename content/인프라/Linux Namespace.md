# Linux Namespace (리눅스 이름공간)

## 📝 정의

Linux Namespace 는 **프로세스마다 무엇이 보이는지를 나누는 커널 기능**이다.

컨테이너가 "격리되어 있다" 고 할 때 그 격리의 절반이 이것이다. 나머지 절반인 자원의 양은 [[cgroups]] 가 맡는다. 도커 문서는 이름공간을 "가장 먼저이자 가장 직접적인 격리의 형태" 라고 적는다.

### 이름
Name :: 이름
Space :: 이름이 통하는 범위
= 붙여 읽으면 "이름이 통하는 범위". 같은 이름이 범위마다 다른 것을 가리킨다

### 비유
학교의 여러 반. 어느 반에서나 "1번" 을 부르지만 가리키는 아이는 반마다 다르다.

### 예
컨테이너 안에서 ps 를 쳤는데 한두 줄만 나오고 호스트의 수백 개가 안 보이던 그 장면이다.

### 직접
리눅스에서 ls -l /proc/self/ns 를 쳐 보라. 지금 이 명령이 어느 범위들에 속해 있는지 종류별로 줄줄이 나온다.

## 🖼️ 그림으로 보기

```도해
층: 이름공간으로 나눈 격리는 어디까지 내려가나
보이는 것 :: 프로세스 번호·파일 트리·랜카드가 각자 한 벌씩
할 수 있는 것 :: 안에서의 0번이 밖에서는 평범한 번호가 된다
못 나누는 것 :: 커널은 한 벌뿐이다. 여기 구멍이 나면 다 넘어간다
= 나뉘는 것은 자원의 양이 아니라 "무엇이 보이느냐" 이고, 그 밑의 커널은 여전히 하나다
```

## ⚠️ 해결하는 문제

```도해
대조: 한 기계에 여럿을 태우면 무엇이 달라지나
범위가 하나면 || 이름공간으로
프로세스 :: 남의 것이 다 보인다 || 자기 것만 보인다
포트 :: 한 놈만 잡는다 || 저마다 하나씩
파일 트리 :: 한 벌을 같이 쓴다 || 각자 자기 뿌리
사고 :: 옆을 죽일 수 있다 || 밖이 안 보인다
= 격리는 벽을 세우는 일이 아니라, 보이는 범위를 좁히는 일이다
```

한 기계에 프로그램을 여럿 태우면 이름이 부딪힌다. 둘 다 80번 포트를 잡으려 하고, 둘 다 `/etc/config` 를 자기 것이라고 여기고, 한쪽이 다른 쪽의 프로세스 번호를 알아내 신호를 보낼 수도 있다. 기계를 통째로 하나씩 떼어 주면 해결되지만 그건 비싸다.

이름공간은 기계를 늘리는 대신 **보이는 범위를 좁힌다.** 각자에게 자기 몫의 프로세스 번호판, 자기 몫의 파일 트리, 자기 몫의 랜카드 한 벌을 주면 이름이 겹쳐도 부딪히지 않는다. 도커 문서가 적듯 "컨테이너마다 자기 망 묶음을 갖기 때문에, 한 컨테이너가 다른 컨테이너의 소켓이나 인터페이스에 특권적으로 접근하지 못한다".

## ⚙️ 작동 원리

종류마다 나누는 것이 다르다. 프로세스 번호 범위를 나누면 안에서 번호가 1번부터 새로 매겨지고, 파일 트리 범위를 나누면 무엇을 뿌리로 볼지가 달라지고, 망 범위를 나누면 랜카드와 주소와 포트가 한 벌 새로 생긴다. 여기에 기계 이름과 프로세스 간 통로가 각각 따로 있고, 사용자 번호 범위가 하나 더 있다.

사용자 번호 범위가 보안에서 특히 중요하다. 쿠버네티스 문서는 이것을 "컨테이너 안에서 도는 사용자를 호스트의 사용자로부터 격리하는 리눅스 기능" 이라 부르고, "컨테이너 안에서 root 로 도는 프로세스가 호스트에서는 다른 비특권 사용자로 돌 수 있다 — 다시 말해 그 프로세스는 범위 안의 작업에는 모든 권한을 갖지만 범위 밖의 작업에는 비특권" 이라고 적는다. kubelet 은 파드마다 겹치지 않는 번호 구간을 골라 주고, 그러면 `CAP_SYS_MODULE` 같은 권한은 무력해지고 `CAP_SYS_ADMIN` 도 그 파드 범위 안에서만 유효하다. 문서는 이 기능이 켜져 있었다면 터지지 않았을 HIGH·CRITICAL 등급 취약점이 여럿 있다고 밝힌다.

범위를 **나누는 것만큼 합치는 것도 설정**이다. 같은 파드의 컨테이너들이 프로세스 범위를 공유하도록 켜면, 쿠버네티스 문서의 말대로 "컨테이너 프로세스가 더 이상 1번이 아니게" 되고 그 자리는 파드 샌드박스(`/pause`)가 차지한다. 그래서 `kill -HUP 1` 은 엉뚱한 쪽으로 간다. 동시에 "프로세스가 파드 안의 다른 컨테이너에게 보이게" 되어 `/proc` 에 드러난 인자와 환경 변수, 나아가 `/proc/$pid/root` 를 통한 남의 파일까지 보인다.

## 💡 실제 사례

- **한 기계에 여러 컨테이너** — 저마다 자기 프로세스 번호판과 랜카드 한 벌을 받기 때문에, 열 개가 다 같이 80번 포트를 잡아도 부딪히지 않는다.
- **사이드카가 옆 컨테이너를 들여다본다** — 파드에서 프로세스 범위 공유를 켜면 로그 처리기가 같은 파드의 프로세스를 직접 보고 신호를 보낼 수 있다.
- **탈출 피해 줄이기** — 사용자 번호 범위를 켜 두면 컨테이너 안의 0번이 호스트에서는 평범한 번호라, 뚫려도 기계 전체를 건드리지 못한다.

## 🚫 흔한 오해

- **이름공간이 있으니 컨테이너는 가상 기계만큼 안전하다** — 커널은 한 벌뿐이다. 커널 자체에 구멍이 있으면 범위를 나눠 둔 것과 상관없이 넘어간다.
- **컨테이너 안에서 1번이니 진짜 1번이다** — 밖에서 보면 여러 프로세스 중 하나일 뿐이다. 파드 안에서 프로세스 범위를 공유하면 1번 자리는 아예 다른 것이 차지한다.
- **이름공간이 자원까지 나눠 준다** — 나누는 것은 보이는 범위뿐이다. 메모리와 CPU 를 얼마나 쓸지는 제어 그룹이 따로 나눈다.

## 📝 정리

**"같은 이름이 저마다 다른 것을 가리키게 만드는 칸막이"** 라고 읽으면 된다. 나뉘는 것은 자원의 양이 아니라 보이는 범위이고, 양을 나누는 일은 제어 그룹이 따로 맡는다. 커널은 한 벌뿐이라 이 칸막이가 가상 기계만 한 벽은 아니다.

## 🧒 열 살에게

학교에서 반마다 1번인 아이가 다 다르지? 그래도 "1번 나와" 하면 헷갈리지 않는 건 다들 자기 반 안에서만 세기 때문이야. 이렇게 세는 범위를 반 단위로 잘라 두면 한 학교에 아이가 수백 명이어도 번호가 서로 부딪히지 않아.

## ❓ 이해했는지

- 컨테이너 안에서 1번이던 것이 밖에서는 1번이 아닌 까닭은 무엇인가 → 흔한 오해
- 컨테이너 열 개가 똑같이 80번 포트를 잡고도 안 부딪히는 까닭은 무엇인가 → 해결하는 문제
- 안에서 0번으로 도는 프로세스가 호스트를 못 건드리게 하려면 무엇을 켜나 → 작동 원리
