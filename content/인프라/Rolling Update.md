# Rolling Update (굴러가는 갱신)

## 📝 정의

옛 파드를 몇 개씩 새 파드로 **바꿔 끼우며** 넘어가는 방식이다.

쿠버네티스 Deployment 의 기본값이고, 반대편에는 전부 내렸다가 전부 올리는 Recreate 가 있다. 새 판을 올리라고 하면 컨트롤러는 옛 파드를 고치는 게 아니라 **새 묶음(ReplicaSet)을 하나 만들고** 그것을 조금씩 키우면서 옛 묶음을 조금씩 줄인다. 한 번에 몇 개씩 움직일지는 두 손잡이가 정한다 — 새로 더 띄워도 되는 여분(`maxSurge`, 기본 25%)과 동시에 빠져도 되는 수(`maxUnavailable`, 기본 25%). 옛 묶음이 지워지지 않고 남아 있어서 되돌리기가 "반대로 굴리기" 로 끝난다.

### 이름
Rolling :: 조금씩 굴러가는
Update :: 새것으로 바꾸기
= 붙여 읽으면 "굴러가듯 조금씩 바꾸기". 한꺼번에 안 내리는 것이 요점이다

### 비유
다리의 차선 공사 — 한 차선씩 막아 고치고 다시 열어서, 차는 그동안에도 계속 지나간다.

### 예
새 판을 올린 몇 분 동안 새로고침할 때마다 옛 화면과 새 화면이 번갈아 나오던 그 시간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 새 판은 옛 판을 어떻게 밀어내나
새 묶음 :: 여분 한도만큼 새 파드를 띄운다
준비 확인 :: 통과한 것만 받는 파드로 센다
옛 묶음 :: 통과한 수만큼 옛 파드를 줄인다
가용 한도 :: 살아 있는 수가 밑돌면 멈춰 기다린다
@ 다시 띄우기 :: 옛 파드가 0 이 될 때까지 되풀이
= 두 한도가 한 번에 몇 개를 갈아 끼울지를 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 한꺼번에 내렸다 올리면 무엇이 달라지나
전부 내렸다 올리면 || 굴려서 바꾸면
그동안 :: 아무도 못 쓴다 || 계속 쓴다
새 판이 불량 :: 이미 다 바뀜 || 몇 개에서 멎음
되돌리기 :: 다시 전부 내림 || 반대로 굴린다
= 한 번에 다 바꾸지 않는 덕에 실패가 전부가 아니라 일부에서 멎는다
```

전부 내렸다 올리는 방식의 진짜 비용은 그 몇 분의 중단이 아니라 **되돌릴 자리가 없다는 것**이다. 옛 판을 이미 다 내려버렸으니, 새 판이 뜨자마자 문제를 일으켜도 돌아갈 곳이 없다. 확인은 전부 바뀐 뒤에야 가능하고, 그때는 사고가 이미 전체에 퍼져 있다.

굴러가는 갱신은 **바뀌는 폭을 한도로 묶는다.** 새 파드가 준비 확인을 통과하기 전에는 다음 파드로 안 넘어가고, 살아 있는 수가 가용 한도를 밑돌면 그 자리에서 멈춘다. 그래서 새 판이 아예 안 뜨는 종류의 사고는 몇 개에서 멎고, 옛 묶음이 그대로 남아 있으니 되돌리기는 그 묶음을 다시 키우는 일이 된다.

## ⚙️ 작동 원리

두 한도가 실제로 무엇을 뜻하는지는 대수로 놓고 보면 분명하다. 파드 4개에 기본값 25% 면 여분 1개·동시 결원 1개다. 그러니 도는 동안 파드 수는 3에서 5 사이를 오가고, 갈아 끼우기는 한 번에 하나씩 진행된다. `maxUnavailable: 0` 으로 두면 결원을 아예 안 내겠다는 뜻이라 항상 새 파드를 먼저 띄우고 옛것을 내린다. 반대로 `maxSurge: 0` 이면 새 자원을 한 톨도 더 안 쓰겠다는 뜻이라 반드시 먼저 비우고 채운다. 둘 다 0 은 아예 적을 수 없다 — 규격이 "한쪽이 0 이면 다른 쪽은 0 일 수 없다" 고 못 박아 두었다. 새 파드를 더 띄우지도, 옛 파드를 비우지도 못하면 한 칸도 움직일 방법이 없기 때문이다.

멈춰 있는 것과 실패한 것도 구분해서 본다. 진행이 `progressDeadlineSeconds`(기본 600초) 동안 한 발짝도 못 나가면 Deployment 에 `ProgressDeadlineExceeded` 조건이 붙는다. 다만 **컨트롤러가 알아서 되돌리지는 않는다** — 옛 파드를 그대로 둔 채 멈춰 서서 기다린다.

```bash
kubectl set image deployment/web web=myapp:2.4.0   # 새 판을 올린다
kubectl rollout status deployment/web              # Waiting for rollout to finish: 2 out of 4 ...
kubectl rollout history deployment/web             # 몇 판까지 되돌아갈 수 있나
kubectl rollout undo deployment/web                # 바로 앞판으로 되돌린다
kubectl rollout pause deployment/web               # 반쯤 간 상태로 세워 둔다
```

되돌아갈 수 있는 판 수는 `revisionHistoryLimit`(기본 10)이 정한다. 이 값을 0 으로 두면 옛 묶음이 남지 않아서 `undo` 가 갈 곳을 잃는다.

## 💡 실제 사례

- **무중단 판 올리기** — 앞단이 준비된 파드에만 보내므로, 옛 판과 새 판이 몇 분간 함께 도는 동안에도 화면은 계속 열린다.
- **이미지 이름 오타** — 새 파드가 이미지를 못 받아 멎으면 갱신이 그 자리에 서고 옛 파드는 그대로 돈다. 10분 뒤 진행 초과 조건이 붙는다.
- **덜 익은 판 되돌리기** — `rollout undo` 는 새로 빌드하거나 이미지를 받아 오는 일이 아니라 노드에 이미 있는 옛 판을 도로 세우는 일이라, 올릴 때보다 훨씬 빨리 끝난다.

## 🚫 흔한 오해

- **굴려서 바꾸면 무중단이다** — 준비 확인이 없으면 아직 못 받는 파드가 목록에 먼저 들어가서, 갱신하는 내내 일부 요청이 실패한다.
- **새 판이 잘못되면 알아서 되돌아간다** — 아니다. 진행 초과 조건만 붙고 그 자리에 멈춘다. 되돌리는 것은 사람이 명령해야 한다.
- **옛 판과 새 판이 섞이는 시간은 없다** — 굴리는 방식의 정의상 두 판이 반드시 함께 돈다. 그래서 이번 판이 옛 판과 나란히 돌 수 있는지를 먼저 봐야 한다.

## 🚨 주의사항

- **DB 를 먼저 옛 판도 읽을 수 있게 바꿔라.** 두 판이 같이 도는 동안 옛 파드가 새 표를 못 읽으면 그 몇 분이 그대로 장애다.
- **`maxUnavailable: 0` 은 자리를 한 개 더 요구한다.** 노드에 빈자리가 없으면 새 파드가 Pending 에 멎어 갱신이 시작도 못 한다.
- **되돌릴 판을 남겨 둬라.** 이력 한도를 0 으로 줄이면 되돌리기 명령이 갈 곳을 잃는다.
- **긴 요청을 처리하는 앱은 종료 유예를 넉넉히 줘라.** 안 그러면 옛 파드가 처리 중인 것을 끊고 죽는다.

## 📝 정리

**"한 차선씩 막아 고치고 도로 여는 것"** 이라고 읽으면 된다. 새 묶음을 만들어 조금씩 키우고 옛 묶음을 조금씩 줄이는 방식이라, 한 번에 몇 개가 움직일지는 여분과 가용 한도 두 값이 정한다. 옛 묶음이 남아 있어 되돌리기는 빠르지만, 두 판이 반드시 함께 도는 시간이 생긴다는 대가가 붙는다.

## 🧒 열 살에게

다리를 통째로 막고 고치면 그동안 아무도 못 건너지? 그래서 한 차선씩만 막아 고치고 도로 열어서, 고치는 내내 차가 계속 지나가. 새로 깐 쪽이 이상해도 아직 안 고친 차선이 남아 있으니까 되돌리기도 쉬워.

## ❓ 이해했는지

- 갱신하는 동안 새로고침할 때마다 화면이 달라지는 이유는 무엇인가 → 흔한 오해
- 이미지 이름을 잘못 적고 올렸을 때 사이트가 멀쩡한 이유는 무엇인가 → 실제 사례
- 두 한도를 다 0 으로 적으면 왜 아예 받아들여지지 않나 → 작동 원리
