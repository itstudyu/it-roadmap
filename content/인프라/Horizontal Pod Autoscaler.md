# Horizontal Pod Autoscaler (수평 파드 자동 확장기)

## 📝 정의

쓰는 양에 맞춰 **파드 대수를 스스로 늘리고 줄이는** 장치다.

쿠버네티스 문서는 수평 확장을 "파드를 더 띄우는 것", 수직 확장을 "이미 뜬 파드에 자원을 더 주는 것" 으로 갈라 적는다. 이 장치가 맡는 것은 앞쪽이라 손대는 값도 워크로드의 `replicas` 하나뿐이고, 그래서 대수를 못 바꾸는 것(DaemonSet 처럼 노드마다 한 개인 것)에는 붙지 않는다.

부하에 맞춰 대수를 조절한다는 생각 자체는 [[Auto Scaling]] 이 다룬다. 이 편이 다루는 것은 그 생각을 쿠버네티스가 실제로 어떻게 셈으로 바꿔 놓았는가, **나눗셈 한 줄**이다.

### 이름
Horizontal :: 옆으로 늘리기
Pod :: 파드 한 벌
Auto :: 스스로
Scaler :: 크기를 바꾸는 것
= 붙여 읽으면 "파드를 옆으로 스스로 늘리는 것". 한 대를 키우는 게 아니라 대수를 바꾼다

### 비유
대청소 인원 배정. 한 사람이 책상 몇 개를 맡을지만 정해 두면, 부를 사람 수는 나눗셈이 정한다.

### 예
파드 목록을 새로고침할 때마다 개수가 2에서 11까지 늘었다가, 한참 뒤에 아무도 손대지 않았는데 도로 줄어 있던 그 화면이다.

## 🖼️ 그림으로 보기

```도해
흐름: 파드 대수는 무엇을 보고 저절로 바뀌나
계측기 :: 파드마다 쓴 양을 모아 준다
확장기 :: 평균을 목표치와 견준다
셈 :: 지금 대수 × (지금 값 ÷ 목표 값)
맞추기 :: 올림한 수만큼 대수를 바꾼다
@ 15초 뒤 다시 :: 목표에 닿아도 재는 일은 안 멈춘다
= 사람이 정하는 건 목표치와 상한·하한뿐, 대수는 이 나눗셈이 정한다
```

## ⚠️ 해결하는 문제

```도해
대조: 대수를 정하려면 사람이 무엇을 알고 있어야 하나
대수를 정하면 || 한 대의 몫만 정하면
알아야 할 것 :: 몇 대가 맞는지 || 한 대가 견디는 양
부하가 두 배 :: 다시 세어 고친다 || 그대로 둔다
앱이 무거워짐 :: 옛 대수가 틀려진다 || 나눗셈이 맞춘다
= 사람은 재 볼 수 있는 것만 정하고, 셀 수 있는 것은 나눗셈에 넘긴다
```

대수를 손으로 잡을 때 진짜 어려운 것은 부지런함이 아니라 **답을 알 수 없다는 것**이다. "이 앱은 몇 대가 맞는가" 는 부하와 파드 성능이 함께 정하는 값이라, 코드가 한 번 바뀌면 어제 맞던 답이 오늘 틀린 답이 된다. 그래서 손으로 잡은 대수는 결국 가장 붐빌 때에 맞춰 부풀어 있게 된다.

확장기는 이걸 **사람이 답할 수 있는 물음으로 바꾼다.** "파드 하나가 얼마나 일하면 적당한가" 는 부하 시험 한 번으로 잴 수 있는 값이고, 그 값과 상한·하한만 정해 두면 대수는 `지금 대수 × (지금 값 ÷ 목표 값)` 을 올림한 값이 정한다. 부하가 두 배가 되든 앱이 무거워지든 사람이 고칠 것이 없다 — 나눗셈의 양쪽이 저절로 바뀌기 때문이다.

## ⚙️ 작동 원리

확장기는 기본 15초마다 도는 고리다(`--horizontal-pod-autoscaler-sync-period`). 한 바퀴마다 계측 API 에서 값을 읽고, 위의 나눗셈으로 원하는 대수를 구하고, 워크로드의 `scale` 를 고쳐 쓴다.

값이 목표 근처에서 흔들릴 때마다 대수를 바꾸면 파드가 떴다 죽었다만 반복한다. 그래서 두 겹의 제동이 있다. **오차 허용치 10%** — 비율이 1.0 에서 10% 안쪽이면 아무것도 안 한다. **내릴 때의 안정화 창 300초** — 지난 5분 동안 나온 권고 중 가장 큰 값을 고른다. 그래서 늘어나는 건 빠르고 줄어드는 건 느리다.

터미널에서 가장 먼저 확인하는 것은 목표 칸이다. 여기 `<unknown>` 이 뜨면 확장기가 고장난 게 아니라 **잴 값이 없는 것**이다. 원인은 둘 중 하나다 — 계측기(metrics-server)가 안 떠 있거나, 컨테이너에 자원 요청량(`resources.requests`)이 안 적혀 있어 몇 퍼센트인지 계산할 밑변이 없거나.

```text
$ kubectl get hpa
NAME    REFERENCE          TARGETS         MINPODS  MAXPODS  REPLICAS  AGE
web     Deployment/web     <unknown>/50%   2        10       2         3m
```

## 💡 실제 사례

- **목표치를 반으로 내린 날** — 50% 를 25% 로 고치면 나눗셈의 분모가 반이 되어 대수가 곧바로 두 배로 뛴다. 손잡이 하나가 대수 전체를 옮긴다.
- **줄 길이로 늘리기** — 사용량 대신 대기열 길이 같은 바깥 값을 목표로 걸면, 밀린 일감 수에 맞춰 일꾼 파드가 붙는다.
- **노드가 모자란 순간** — 대수는 늘었는데 새 파드가 Pending 에 멎어 있으면 확장기가 아니라 노드를 늘리는 쪽이 밀린 것이다.

## 🚫 흔한 오해

- **켜 두면 알아서 다 해 준다** — 컨테이너에 자원 요청량이 안 적혀 있으면 퍼센트를 계산할 밑변이 없어서 아무 일도 안 일어난다.
- **파드를 늘리면 자리는 알아서 생긴다** — 아니다. 확장기는 파드 수만 바꾼다. 노드에 빈자리가 없으면 새 파드는 그대로 Pending 이다.
- **자동 확장을 걸면 손으로 잡을 때보다 늘 낫다** — 부하가 종일 평평하거나 한 대로 충분한 앱이면, 흔들릴 때마다 파드가 떴다 죽었다 하는 값만 치른다.

## 🚨 주의사항

- **목표치는 여유를 남긴다.** 80% 로 잡으면 새 파드가 뜨고 준비될 때까지의 몇십 초를 이미 꽉 찬 상태로 버텨야 한다.
- **내려가는 쪽이 느린 건 기본값이다.** 5분 창을 줄이려면 `behavior.scaleDown.stabilizationWindowSeconds` 를 직접 손댄다.
- **파드 대수와 노드 대수는 다른 장치가 맡는다.** 둘을 같이 켜 두지 않으면 한쪽만 늘고 멈춘다.
- **값이 안 잡히면 안 줄인다.** 계측이 끊긴 사이에는 대수가 그대로 남아 있으므로 계측기 자체를 감시 대상에 넣는다.

## 📝 정리

**"한 대에 얼마까지만 시킬지 정하면 대수는 나눗셈이 정한다"** 라고 읽으면 된다. 사람이 정하는 것은 목표치와 상한·하한뿐이고, 대수는 `지금 대수 × (지금 값 ÷ 목표 값)` 을 올림한 값을 15초마다 다시 구한 것이다. 늘리는 쪽은 곧바로 움직이지만 줄이는 쪽은 지난 5분의 최댓값을 보고 늦게 움직이며, 자원 요청량이 안 적혀 있으면 나눗셈의 밑변이 없어 아무 일도 안 일어난다.

## 🧒 열 살에게

대청소를 할 때 몇 명을 부를지 세지 않고, 한 사람이 책상 열 개씩 맡는다고만 정해 둔다고 해 봐. 그러면 책상이 백 개인 날은 열 명, 스무 개인 날은 두 명이 저절로 나와서 사람이 다시 셀 일이 없어. 대신 일이 늘면 곧바로 더 부르지만, 줄었다고 바로 집에 보내진 않고 한참 지켜본 뒤에 보내.

## ❓ 이해했는지

- 확장기를 걸었는데 목표 칸에 값이 안 뜨고 대수도 안 변하는 일은 왜 생기나 → 작동 원리
- 늘어나는 건 빠른데 줄어드는 건 느린 이유는 무엇인가 → 작동 원리
- 대수는 늘었는데 새 파드가 계속 Pending 이면 무엇이 밀린 것인가 → 흔한 오해
