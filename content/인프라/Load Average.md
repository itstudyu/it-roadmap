# Load Average (부하 평균)

## 📝 정의

Load Average 는 **일하려고 줄 서 있는 프로세스 수의 최근 평균**이다.

퍼센트가 아니라 개수라는 것이 이 값의 전부다. 위로 끝이 없고, 코어가 몇 개인 기계인지를 함께 봐야 비로소 뜻이 생긴다. 게다가 리눅스는 CPU 를 기다리는 것뿐 아니라 디스크를 기다리는 것까지 같은 줄에 세운다.

### 이름
Load :: 짊어진 일감
Average :: 평균
= 붙여 읽으면 "짊어진 일감의 평균". 지금 값이 아니라 지난 1·5·15분의 평균이다

### 비유
계산대 앞의 줄. 계산대가 넷인데 넷이 서 있으면 딱 맞고, 여덟이면 절반은 기다리는 중이다.

### 예
서버가 느리다는 말을 듣고 접속하자마자 치는 uptime 의 맨 끝에 붙어 나오는 숫자 셋이다.

### 직접
터미널에서 uptime 을 쳐 보라. 맨 끝에 1분·5분·15분 평균이 순서대로 세 개 나온다.

## 🖼️ 그림으로 보기

```도해
층: 숫자 셋은 각각 무엇을 말하나
1분 평균 :: 방금 줄에 몇이 서 있었나. 잡음이 많고 확 튄다
5분 평균 :: 그 줄이 이어지고 있나. 튐이 걸러진 값
15분 평균 :: 오래 그랬나. 늦게 오르고 늦게 내린다
= 줄에 선 수를 세 가지 길이로 평균 낸 값이다. 지금 이 순간의 값이 아니다
```

## ⚠️ 해결하는 문제

```도해
대조: 순간 값만 보면 무엇이 달라지나
그때그때 값만 || 부하 평균으로
튀는 값 :: 매번 놀란다 || 걸러져 보인다
방향 :: 알 수 없다 || 셋을 견주면 안다
기준 :: 높은지 모른다 || 코어 수와 견준다
= 한 번 찍은 값이 아니라 세 길이의 평균이라 방향이 보인다
```

바쁜 정도를 그때그때 찍어 보면 값이 초 단위로 널뛴다. 그 순간 무거운 명령이 하나 돌고 있었는지 아닌지에 따라 화면의 숫자가 달라지고, 그래서 두 번 재면 두 번 다른 답이 나온다. 사람은 그걸 보고 판단을 못 한다.

부하 평균은 같은 값을 **세 가지 길이로 평균 내어 나란히 놓는다.** 그러면 한 숫자로는 못 하던 일이 된다 — 1분이 15분보다 훨씬 높으면 지금 막 오르는 중이고, 반대면 이미 지나간 일이다. 값 하나가 아니라 셋의 관계가 답을 준다.

## ⚙️ 작동 원리

값은 커널이 직접 적어 둔다. 커널 문서는 `/proc/loadavg` 의 내용을 "지난 1·5·15분의 부하 평균, 지금 실행 가능한(도는 중이거나 대기 줄에 있는) 프로세스 수, 시스템의 전체 프로세스 수, 마지막으로 만들어진 pid" 로 적는다. 실제 한 줄은 `0.61 0.61 0.55 3/828 22084` 처럼 생겼다. 앞의 셋이 우리가 말하는 그 값이고, 뒤의 `3/828` 은 828개 중 3개가 지금 실행 가능하다는 뜻이다.

리눅스만의 특징이 하나 있다. GNU coreutils 문서는 `uptime` 을 설명하면서 "어떤 시스템은 지난 1·5·15분의 실행 가능한 프로세스 수 평균으로 계산하지만, 어떤 시스템은 중단 불가능한 대기 상태의 프로세스도 포함한다" 고 적고, 리눅스가 후자라고 밝힌다. **디스크나 원격 저장소의 응답을 기다리는 프로세스가 이 값에 함께 세어진다는 뜻**이다. 그래서 리눅스에서는 CPU 가 거의 놀고 있는데 부하 평균만 치솟는 일이 흔하고, 그때 범인은 CPU 가 아니라 저장 장치다.

읽는 기준은 코어 수다. 값이 코어 수와 같으면 줄이 정확히 소화되는 상태이고, 두 배면 절반은 기다리는 중이다. 그러니 같은 4.0 이라도 코어 여덟 개짜리에서는 여유이고 코어 둘짜리에서는 네 배가 밀린 상태다. 참고로 같은 화면에 뜨는 CPU 사용률 쪽은 커널이 타이머 인터럽트마다 상태를 찍어 세는 방식이라 따로 오차를 갖는다. 커널 문서는 "두 타이머 인터럽트 사이에 시스템이 여러 상태를 오갔더라도 마지막 상태에 대해서만 카운터가 올라간다" 고 적어 둔다.

## 📊 비교: 부하 평균과 CPU 사용률은 무엇이 다른가

```도해
대조: 부하 평균과 CPU 사용률은 무엇이 다른가
CPU 사용률 |=| 부하 평균
세는 것 :: 쓴 시간의 비율 || 줄에 선 개수
상한 :: 100% 에서 막힘 || 위로 끝이 없다
디스크 대기 :: 안 잡힌다 || 리눅스는 센다
= 사용률은 얼마나 썼나를, 부하 평균은 얼마나 밀렸나를 말한다
```

## 💡 실제 사례

- **느린데 CPU 는 놀고 있다** — 부하 평균만 높고 사용률이 낮으면 리눅스에서는 디스크나 원격 저장소를 기다리는 중일 때가 많다.
- **코어 수와 견주기** — 코어 여덟 개짜리에서 8 은 딱 맞는 상태이고, 코어 두 개짜리에서 8 은 네 배가 밀려 있다는 뜻이다.
- **셋을 나란히 읽기** — 1분이 15분보다 훨씬 높으면 막 오르는 중이고, 15분만 높으면 이미 지나간 일의 잔상이다.

## 🚫 흔한 오해

- **1.0 은 100% 라는 뜻이다** — 비율이 아니라 개수다. 코어가 넷이면 4.0 이 꽉 찬 상태이고, 그 위로는 얼마든지 올라간다.
- **부하 평균이 높으니 CPU 가 모자란다** — 리눅스는 디스크를 기다리는 프로세스도 함께 센다. CPU 는 놀면서 값만 오르는 일이 흔하다.
- **지금 값이니 바로 반응한다** — 1분 값조차 지난 1분의 평균이다. 부하가 사라져도 15분 값은 한참 뒤에야 내려온다.

## 📝 정리

**"줄에 몇이 서 있었나를 세 가지 길이로 평균 낸 수"** 라고 읽으면 된다. 비율이 아니라 개수라 코어 수와 견주어야 뜻이 생기고, 리눅스에서는 디스크를 기다리는 것까지 세어진다. 셋을 나란히 읽으면 지금 오르는 중인지 내려가는 중인지가 보인다.

## 🧒 열 살에게

마트에서 계산대 앞에 몇 명이 서 있나 세어 본다고 해 봐. 그 수만 봐서는 모르고 계산대가 몇 개인지 같이 봐야 줄이 진짜 긴 건지 알 수 있어. 게다가 지금 센 수가 아니라 아까부터 지금까지 센 수를 평균 낸 거라, 줄이 다 빠지고도 한참은 크게 나와.

## ❓ 이해했는지

- 코어 둘짜리와 여덟짜리에서 같은 4.0 이 다르게 읽히는 까닭은 무엇인가 → 흔한 오해
- CPU 는 거의 놀고 있는데 이 값만 높을 때 무엇을 의심해야 하나 → 실제 사례
- 부하가 이미 사라졌는데도 값이 한동안 높게 남는 까닭은 무엇인가 → 작동 원리
