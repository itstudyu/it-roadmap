# Prometheus (프로메테우스)

## 📝 정의

Prometheus는 **지표를 주기마다 긁어와 시각을 붙여 쌓는 감시 도구**다.

SoundCloud 에서 만들어진 오픈소스 감시·알림 도구다. 재는 값을 시계열로 보관한다 — 기록한 시각을 함께 적고, 라벨이라 부르는 키·값 짝을 곁들여 저장한다.

### 비유
한 시간마다 체온을 재서 칸에 적어 두는 기록지. 지금 몇 도인지만이 아니라 언제부터 올랐는지가 남는다.

### 예
상태 페이지에서 "지난 24시간 응답 시간" 그래프를 본 적이 있을 것이다. 그 선을 이루는 점 하나하나가 주기마다 긁어온 값이다.

## 🖼️ 그림으로 보기

```도해
흐름: 지표 하나가 Prometheus 안에서 무엇이 되나
대상 :: `/metrics` 주소에 지금 값을 내걸어 둔다
수집 :: 정해진 주기로 그 주소를 긁어온다
시계열 :: 이름·라벨·시각·값 한 점으로 쌓인다
PromQL :: 쌓인 점을 골라 계산해서 본다
알림 규칙 :: 계산 결과가 조건에 걸리면 알린다
= 값을 밀어 올리는 게 아니라 주기마다 긁어오고, 긁어온 값은 시각이 붙은 점으로 남는다
```

## ⚠️ 해결하는 문제

```도해
대조: 지표를 쌓아 두지 않으면 무엇을 못 하나
쌓지 않으면 || Prometheus 로
장애 직전 :: 그때 값이 없다 || 되감아 본다
느려진 곳 :: 짐작으로 찾는다 || 라벨로 좁힌다
알림 기준 :: 눈으로 지켜본다 || 식으로 적는다
= 숫자에 시각과 라벨이 붙어야 되감고, 좁히고, 기계가 대신 지켜볼 수 있다
```

지금 값만 보여주는 화면은 "언제부터 이랬나" 에 답하지 못한다. 장애가 끝나고 나면 원인을 짚을 근거도 함께 사라진다. 어느 갈래가 문제인지도 알 수 없다 — 느린 것이 전체인지 `POST` 요청만인지 구분할 방법이 없기 때문이다.

Prometheus 는 **모든 값을 시계열로 저장**해서 이 셋을 한꺼번에 없앤다. 값마다 기록 시각이 붙으니 되감을 수 있고, 라벨이 붙으니 갈래별로 쪼개 볼 수 있고, 같은 값을 식으로 물을 수 있으니 사람이 지켜보지 않아도 조건에 걸릴 때 알림을 낼 수 있다.

## 🧱 구성

```도해
층: 시계열 한 점은 무엇으로 이루어져 있나
지표 이름 :: `http_requests_total`. 무엇을 재는가
라벨 :: `method="POST"`. 어느 갈래인가
타임스탬프 :: 밀리초 단위의 기록 시각
값 :: float64 숫자 하나
= 위의 둘이 "어느 시계열인가" 를 정하고, 아래 둘이 "그 순간 얼마였나" 를 적는다
```

## ⚙️ 작동 원리

수집은 **끌어오는 방식**이다. 공식 문서는 시계열 수집을 "HTTP 를 통한 pull 모델" 로 적는다. 감시 대상이 값을 보내는 것이 아니라, Prometheus 가 대상의 주소를 주기마다 찾아가 그 순간의 값을 읽어 온다. 기본 설정값으로 `scrape_interval` 은 1분, `scrape_timeout` 은 10초, 읽으러 가는 경로 `metrics_path` 는 `/metrics` 다.

값을 스스로 내걸 수 없는 대상은 exporter 가 대신 내건다. 반대로 주기적으로 긁힐 만큼 오래 살지 않는 짧은 작업은 push gateway 에 값을 맡겨 두고 끝난다. 이 둘이 pull 모델의 빈틈을 메운다.

쌓인 값은 PromQL 로 묻는다. 지표 이름과 라벨로 시계열을 고르고, 여러 시계열을 묶어 계산한다. 같은 식을 알림 규칙에 적어 두면 Prometheus 가 `evaluation_interval` (기본 1분)마다 그 식을 따져 보고, 조건에 걸린 알림을 Alertmanager 로 넘긴다. 규칙을 따지는 일과 그 알림을 사람에게 보내는 일은 이렇게 서로 다른 곳이 맡는다.

## 💡 실제 사례

- **원인 되감기** — 장애가 끝난 뒤에도 그 시각의 지연·오류율·자원 사용량이 그대로 남아 있어, 무엇이 먼저 무너졌는지 순서를 짚을 수 있다.
- **갈래별 좁히기** — 라벨을 붙여 둔 덕에 "느리다" 를 경로별·메서드별·인스턴스별로 쪼개 본다. 한 대만 느린 것과 전부 느린 것은 대응이 다르다.
- **알림 기준 세우기** — 사람이 지켜볼 화면 대신 식을 적는다. 알림 규칙에 쓴 PromQL 은 대시보드에서 쓰던 식 그대로다.

## 🚫 흔한 오해

- **앱이 지표를 Prometheus 로 보내는 것이다** — 방향이 반대다. 공식 문서는 수집을 "HTTP 를 통한 pull 모델" 로 적는다. 앱은 `/metrics` 에 지금 값을 내걸어 둘 뿐이고, 가지러 오는 쪽은 Prometheus 다.
- **라벨은 많이 붙일수록 좋다** — 라벨 값 하나가 달라지면 그것이 곧 새 시계열이다. 공식 문서는 "라벨셋 하나하나가 RAM·CPU·디스크·네트워크 비용이 붙는 추가 시계열" 이라며 지표 하나의 카디널리티를 10 아래로 두라고 권한다. 사용자 ID 처럼 값이 무한정 늘 수 있는 것을 라벨로 넣으면 안 되는 이유가 이것이다.
- **감시는 Prometheus 하나로 다 덮으면 된다** — 공식 문서부터 100% 정확도가 필요한 일, 예컨대 건당 과금에는 좋은 선택이 아니라고 적는다. 모아 둔 값이 그만큼 자세하지도, 빠짐없지도 않기 때문이다.

## 📝 정리

**"주기마다 긁어와 시각을 붙여 쌓아 두는 곳"** 이라고 읽으면 된다. 값을 받는 게 아니라 가지러 가고, 쌓인 한 점은 이름·라벨·시각·값으로 되어 있어서 되감기와 갈래 나누기가 둘 다 된다. 다만 빠짐없는 기록이 필요한 일에는 쓰지 않는다.

## 🧒 열 살에게

보건실 선생님이 한 시간마다 우리 반에 와서 열이 있나 재 보고, 잰 숫자를 시간이랑 같이 종이에 적어 두시지? 그래서 며칠 뒤에도 "어제 세 시부터 열이 올랐네" 하고 되짚을 수 있어. 우리가 찾아가서 말하지 않아도 선생님이 먼저 와서 재 가.

## ❓ 이해했는지

- 앱이 아무 데도 값을 보내지 않는데 그래프가 그려지는 이유는 무엇인가 → 그림
- 라벨 값 하나를 새로 붙이면 시계열은 어떻게 되나 → 구성
- 건당 과금 정산을 이 숫자로 하면 안 되는 이유는 무엇인가 → 흔한 오해
