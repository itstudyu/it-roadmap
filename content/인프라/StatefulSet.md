# StatefulSet (스테이트풀셋)

## 📝 정의

StatefulSet은 **파드마다 제 이름과 제 디스크를 붙여 두는 것**이다.

쿠버네티스 문서는 이걸 "각 파드에 끈적한 정체성을 유지시킨다" 고 적고, 네 가지를 보장한다고 나열한다 — 고정된 이름, 고정된 저장소, 정해진 순서로 뜨고 지기, 정해진 순서로 갈아 끼우기. Deployment 의 파드가 서로 갈아 껴도 되는 것들이라면, 여기 파드는 서로 못 바꾸는 것들이다.

### 이름
State :: 들고 있는 상태
-ful :: 가득한
Set :: 한 벌
= 붙여 읽으면 "상태를 들고 있는 한 벌". 파드마다 제 것이 따로 붙어 다닌다

### 비유
기숙사 방 배정과 같다 — 3호에 든 학생은 잠깐 나갔다 와도 늘 3호로 돌아오고 그 방 사물함도 그대로다.

### 예
DB 를 클러스터에 올렸다가 파드가 한 번 다시 뜨자 저장해 둔 것이 통째로 사라져 있던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: `web-1` 이 죽었다 살아나면 무엇이 그대로 돌아오나
파드 죽음 :: `web-1` 이 사라진다. 다른 노드로 옮길 수도 있다
같은 이름 :: 다시 뜨는 파드도 이름이 `web-1` 이다
같은 디스크 :: 쓰던 `www-web-1` 볼륨이 그대로 다시 붙는다
같은 주소 :: `web-1.nginx` 라는 DNS 이름도 그대로다
= 이름·디스크·주소 셋이 순번에 묶여 있어서 파드를 갈아도 따라온다
```

## ⚠️ 해결하는 문제

```도해
대조: 상태를 들고 있는 앱을 Deployment 로 띄우면 무엇이 깨지나
Deployment 로 || StatefulSet 으로
다시 뜬 뒤 :: 남의 디스크를 잡음 || 제 디스크로 돌아옴
서로 부르기 :: 누가 누군지 모름 || 이름으로 콕 집음
차례로 켜기 :: 순서가 없음 || 0번부터 차례대로
= 갈아 껴도 되는 파드와 제 자리를 지켜야 하는 파드는 다르게 다뤄야 한다
```

DB 나 큐처럼 스스로 데이터를 들고 있는 앱은 파드가 서로 대체 가능하지 않다. 복제본 세 개 중 어느 것이 원본이고 어느 것이 따라오는 쪽인지가 정해져 있고, 저마다 다른 파일을 들고 있다. Deployment 로 띄우면 파드 이름이 매번 달라지므로 서로를 지목할 방법이 없고, 볼륨도 아무거나 붙는다.

StatefulSet 은 **파드에 번호를 매겨 그 번호에 이름·저장소·DNS 주소를 못 박는다.** `web-0`, `web-1`, `web-2` 는 파드가 몇 번을 죽어도 그대로고, `volumeClaimTemplates` 로 만든 볼륨은 번호를 따라간다. 그래서 "3번 노드가 죽었으니 3번을 다른 기계에서 다시 띄우자" 가 성립한다.

## ⚙️ 작동 원리

이름은 `<StatefulSet 이름>-<순번>` 으로 정해진다. `replicas: 3` 이면 `web-0`·`web-1`·`web-2` 이고 그 사이에 빈 번호는 없다. 기본값인 `OrderedReady` 로 굴리면 `web-0` 이 Ready 가 될 때까지 `web-1` 은 안 뜬다. 줄일 때는 반대로 큰 번호부터 지운다.

저장소는 `volumeClaimTemplates` 가 맡는다. 이건 볼륨 하나가 아니라 틀이라, 파드마다 PVC 를 하나씩 새로 찍어 낸다. 이름은 `<틀 이름>-<파드 이름>` 이 되어 `www-web-0`, `www-web-1` 처럼 붙고, 파드가 다른 노드로 옮겨 가도 같은 PVC 가 따라간다.

DNS 이름을 만들어 주는 것은 StatefulSet 이 아니라 짝으로 둔 머리 없는 Service 다. `spec.serviceName` 에 적은 이름의 Service 를 **직접 만들어야** 하고, GKE 문서는 그 Service 의 `metadata.name` 이 `serviceName` 과 같아야 각 복제본이 고유한 주소로 불릴 수 있다고 적는다. 이걸 빼먹으면 파드는 뜨는데 서로를 못 찾는다.

## 💡 실제 사례

- **클러스터 안에 DB 를 둘 때** — `web-0` 이 어느 노드로 옮겨 가도 같은 PVC 가 따라붙는다. 그래서 파드를 다시 띄워도 저장한 것이 남는다.
- **서로를 이름으로 찾는 무리** — Kafka·ZooKeeper 처럼 구성원끼리 서로를 알아야 하는 앱은 `web-0.nginx` 같은 고정 이름으로 짝을 맞춘다.
- **줄이고 나서 남는 디스크** — `kubectl scale statefulset web --replicas=1` 로 줄여도 `www-web-1`·`www-web-2` 는 남는다. 데이터 안전을 위해 일부러 안 지운다고 문서가 적는다.

## 🚫 흔한 오해

- **StatefulSet 을 쓰면 데이터가 안 사라진다** — 데이터를 들고 있는 것은 PVC 와 그 뒤의 볼륨이다. PVC 를 지우거나 StorageClass 의 회수 정책이 `Delete` 면 볼륨은 그대로 없어진다.
- **머리 없는 Service 도 알아서 만들어 준다** — 안 만들어 준다. 문서가 한계 항목에 "직접 만들어야 한다" 고 적어 뒀고, 없으면 파드 DNS 이름이 아예 안 생긴다.
- **상태가 조금이라도 있으면 StatefulSet 이다** — 대개는 그 상태를 클러스터 밖(관리형 DB·오브젝트 저장소)에 두는 편이 낫다. 순서대로 뜨고 순서대로 지는 성질은 배포를 눈에 띄게 느리게 만들고, 볼륨 정리를 사람 몫으로 남긴다.

## 🚨 주의사항

- **지우기 전에 0 으로 줄여라.** 문서는 StatefulSet 삭제가 파드를 순서대로 내려준다고 보장하지 않으니, 순서 있는 종료가 필요하면 먼저 0 으로 줄이라고 적는다.
- **`OrderedReady` 로 굴리다 하나가 안 뜨면 거기서 멈춘다.** 앞 파드가 Ready 가 될 때까지 다음으로 안 가기 때문에, 잘못된 판을 올리면 손으로 풀어야 하는 상태에 빠질 수 있다고 문서가 경고한다.
- **PVC 는 자동으로 안 지워진다.** 클러스터를 정리할 때 남은 볼륨을 따로 찾아 지운다. 안 그러면 요금만 계속 나간다.

## 📝 정리

**"제 이름과 제 디스크를 달고 다니는 파드들"** 이라고 읽으면 된다. `web-0` 은 어디로 옮겨 가도 `web-0` 이고 쓰던 볼륨이 따라붙기 때문에, 서로를 이름으로 불러야 하거나 저장한 것이 남아야 하는 앱이 여기 붙는다.

## 🧒 열 살에게

기숙사에서 네 방 번호가 3호면, 잠깐 나갔다 돌아와도 다시 3호로 가고 사물함 안 물건도 그대로 있지? 친구들도 "3호 걔" 라고만 하면 네가 누군지 바로 알아.

- 파드 개수를 줄였는데 디스크가 그대로 남는 것은 왜인가 → 주의사항
