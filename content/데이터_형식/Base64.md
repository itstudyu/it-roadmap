# Base64 (베이스64)

## 📝 정의

Base64 는 **이진 데이터를 글자 64개로 바꿔 적는 방법**이다.

메일 본문이나 주소창처럼 글자만 지나갈 수 있는 자리가 아직 많다. RFC 4648 은 이런 표기법이 "옛 사정 때문에 US-ASCII 자료만 다루도록 제한된 환경에서 자료를 저장하거나 옮길 때" 쓰인다고 적는다. MDN 은 이것을 이진을 글자로 옮기는 표기 방식이라고 부른다.

### 이름
Base :: 몇 진법인가
64 :: 쓰는 글자 수
= 붙여 읽으면 "64진법". 탈 없이 지나가는 글자 64개만으로 다시 적는다는 뜻이다

### 비유
전화로 불러 주는 색칠 그림. 그림 자체는 전화선을 못 타니 칸마다 색 이름을 말로 읽어 주면, 듣는 쪽이 그대로 칠해 같은 그림을 만든다.

### 예
이메일에 사진을 첨부해 보낸 그 순간이다. 메일 본문은 글자만 실어 나르므로 사진은 글자 뭉치로 바뀌어 실린다.

### 직접
웹페이지에서 페이지 소스 보기를 누르고 `base64,` 를 찾아보라. 걸리는 페이지에서는 그림 한 장이 통째로 글자 줄로 박혀 있다.

## 🖼️ 그림으로 보기

```도해
흐름: 사진 한 장이 글자만 지나는 길을 어떻게 통과하나
사진 :: 아무 값이나 들어 있는 바이트 뭉치
3바이트씩 :: 24비트를 6비트짜리 넷으로 자른다
글자표 :: 6비트마다 정해진 글자 하나를 고른다
글자 줄 :: 영문 대소문자와 숫자, 기호 둘로만 된 줄
받는 쪽 :: 표를 거꾸로 보아 원래 바이트로 되돌린다
= 내용이 바뀌는 게 아니라 같은 것을 글자 64개로 다시 적는 것이다
```

## ⚠️ 해결하는 문제

```도해
대조: 글자만 지나는 자리에 이진을 그대로 넣으면 어떻게 되나
그대로 넣으면 || Base64 로
메일 본문 :: 중간에 깨진다 || 글자로만 실린다
주소창 :: 못 쓰는 글자 || 정해진 글자만
XML 안 :: 태그와 뒤엉킨다 || 그대로 박힌다
= 아직 글자만 지나는 길이 많다. 그 길로 이진을 보내려면 글자로 다시 적는 수밖에 없다
```

이진은 0부터 255까지 아무 값이나 들어 있는 바이트의 줄이다. 그 안에는 줄바꿈으로 읽히는 값도 있고, 그 자리에서 특별한 뜻을 가진 글자로 읽히는 값도 있다. 글자만 다루도록 만들어진 자리에 그대로 넣으면 중간에서 잘리거나 다른 것으로 바뀐다.

Base64 는 그런 자리를 위해, 어디서나 탈 없이 지나가는 글자 64개만 골라 그 글자들로만 다시 적는다. 이 폴더의 CSV·JSON·XML 은 무엇을 어떤 모양으로 적을지 정해 둔 형식이고, Base64 는 그 형식들이 글자밖에 담지 못해서 필요해지는 한 층 아래의 일이다.

## ⚙️ 작동 원리

셈은 단순하다. 바이트는 8비트씩이고 Base64 글자 하나는 6비트를 담는다. 8과 6이 맞아떨어지는 자리가 24라서, 3바이트를 한 묶음으로 잘라 6비트짜리 넷으로 나눈 뒤 글자 넷으로 적는다.

3의 배수로 안 떨어지면 마지막 묶음이 모자란다. 그 남는 자리를 `=` 로 채운다. RFC 4648 은 8비트가 남으면 `=` 둘을, 16비트가 남으면 `=` 하나를 붙이라고 정한다. 그래서 줄 끝의 `=` 는 뜻이 담긴 기호가 아니라 마지막 묶음이 덜 찼다는 표시다.

글자표는 하나가 아니다. 기본 표는 62번과 63번 자리에 `+` 와 `/` 를 쓰는데, 이 둘은 주소나 파일 이름에서 다른 뜻을 갖는다. 그래서 RFC 4648 은 그 자리에 `-` 와 `_` 를 쓰는 변형을 따로 정해 뒀다. 주소창에 들어가는 값이 `-` 와 `_` 로 되어 있으면 그 변형이다.

3바이트가 4글자가 되므로 결과는 원본보다 커진다. MDN 은 Base64 로 바꾼 결과가 대개 원본보다 3분의 1쯤 크다고 적는다.

## 💡 실제 사례

- **메일 첨부** — 메일 본문은 글자만 나르므로 사진과 문서를 Base64 로 바꿔 실어 보낸다.
- **페이지 안에 박은 그림** — 작은 아이콘을 파일로 따로 두지 않고 `data:` 로 시작하는 글자 줄로 페이지에 박아 넣는다.
- **글자만 담는 형식 안에 이진 넣기** — XML 이나 JSON 안에 사진이나 서명 값을 글자 줄로 바꿔 끼워 넣는다.

## 🚫 흔한 오해

- **Base64 로 바꿔 두면 남이 못 읽는다** — 암호가 아니다. RFC 4648 은 이 표기가 비밀번호 같은 것을 눈에 덜 띄게 할 뿐 계산상의 비밀은 전혀 주지 않는다고 적는다. 표를 거꾸로 보면 누구나 되돌린다.
- **이진을 다룰 일이 있으면 일단 Base64 로 감싸면 된다** — 그대로 실어 나를 수 있는 길이면 감쌀 이유가 없다. 3바이트가 4글자가 되어 크기가 3분의 1쯤 늘고, 양쪽에서 바꾸고 되돌리는 일이 더 붙는다.
- **Base64 는 UTF-8 같은 문자 인코딩이다** — 방향이 반대다. 문자 인코딩은 글자를 바이트로 바꾸고, Base64 는 바이트를 글자로 바꾼다. MDN 도 Base64 를 문자 쪽이 아니라 이진 쪽 표기라고 못 박는다.

## 📝 정리

**"바이트를 안전한 글자 64개로 다시 적은 것"** 이라고 읽으면 된다. 숨기는 것이 아니라 옮겨 적는 것이라 표만 있으면 누구나 되돌린다. 3바이트가 4글자가 되므로 결과는 원본보다 3분의 1쯤 커진다.

## 🧒 열 살에게

그림을 전화로 보낼 수는 없지? 그래서 칸마다 무슨 색인지 하나하나 말로 읽어 주면 친구가 그대로 칠해서 똑같은 그림을 만들어. 대신 말로 읽으면 그림을 그냥 건네줄 때보다 시간이 더 걸려.

## ❓ 이해했는지

- 사진을 메일에 붙였을 뿐인데 오가는 양이 늘어나는 이유는 무엇인가 → 흔한 오해
- 줄 끝에 `=` 가 하나 붙어 있으면 마지막 묶음에 몇 비트가 남았던 것인가 → 작동 원리
- 이진을 그대로 넣으면 안 되는 자리가 아직 남아 있는 이유는 → 해결하는 문제
