# JSON Schema (JSON 스키마)

## 📝 정의

JSON Schema는 **JSON 이 어떤 모양이어야 하는지 적어둔 JSON**이다.

규칙을 코드가 아니라 데이터로 적어두기 때문에 사람이 읽고, 기계가 검사하고, 다른 언어의 도구가 같은 파일을 그대로 가져다 쓴다. 스키마 자체도 JSON 문서이고, 가장 최근 판은 2020-12 다.

### 비유
서류 양식에 인쇄된 기입 안내. 어느 칸이 필수이고 무엇을 적어야 하는지가 양식 안에 같이 적혀 있다.

### 예
요청을 보냈더니 `'무료' is not of type 'number'` 같은 답이 돌아오는 그 순간이 이 검사에 걸린 것이다.

## 🖼️ 그림으로 보기

```도해
흐름: 스키마 한 장은 들어온 JSON 을 어떻게 판정하나
스키마 :: 필수 열쇠와 형식을 JSON 으로 적어둔다
인스턴스 :: 검사받을 JSON 한 덩이가 들어온다
키워드 :: type · required 같은 규칙을 하나씩 맞춰본다
결과 :: 참이냐 거짓이냐 하나로 떨어진다
= 규칙도 JSON 이고 검사받는 것도 JSON 이다
```

## ⚠️ 해결하는 문제

```도해
대조: 주고받을 모양을 문서로만 적어두면 무엇이 어긋나나
말로 약속 || 스키마로
어긋난 값 :: 터진 뒤에 안다 || 받는 즉시 안다
문서와 코드 :: 따로 늙는다 || 한 장을 같이 본다
언어가 다르면 :: 각자 다시 짠다 || 같은 파일을 쓴다
= 지킬 규칙을 데이터로 적어두면 사람과 기계가 같은 것을 본다
```

두 서비스가 JSON 을 주고받기로 하면 모양에 대한 약속이 생긴다. 그 약속이 위키 문서나 주석에만 있으면 한쪽이 필드를 바꿔도 다른 쪽은 모르고, 어긋난 값은 코드 깊숙한 곳에서 엉뚱한 오류로 나타난다.

스키마는 그 약속을 실행 가능한 파일로 만든다. 규칙이 특정 언어에 매여 있지 않아서 보내는 쪽이 자바스크립트고 받는 쪽이 파이썬이어도 같은 파일 하나로 같은 판정을 받는다.

## ⚙️ 작동 원리

키워드는 하는 일에 따라 갈린다. 참·거짓을 내는 **단언**(type, required), 값에 설명을 붙이는 **주석**(title, description, format), 아래쪽 스키마를 다시 적용하는 **적용자**(properties, items), 스키마 자신을 가리키는 **식별자**($id, $schema) 따위다. 검사기는 이 중 단언만 모아 마지막에 참·거짓 하나로 답한다.

여기서 나오는 성질 하나가 중요하다. **인스턴스는 스키마에 적힌 단언만 어길 수 있다.** 적어두지 않은 항목은 검사 대상이 아니라 무조건 통과다. `maxLength` 는 문자열만 재기 때문에 숫자가 들어오면 그냥 통과하고, 그래서 `type` 을 따로 걸어야 한다.

`$schema` 는 이 스키마가 어느 판(dialect)의 규칙으로 쓰였는지를 URI 로 밝히는 자리다. 키워드 묶음을 어휘(vocabulary)라 부르고, 어휘를 모아 한 판을 이룬다. 이 구조 덕분에 새 키워드를 더해도 옛 검사기가 그것을 주석으로 흘려보낼 수 있다.

## 📊 비교: 자주 쓰는 키워드

| 키워드 | 무엇을 재나 | 적어두는 값 |
|---|---|---|
| **type** | 값의 종류 | `"number"` 또는 `["string", "null"]` |
| **required** | 객체에 그 열쇠가 있나 | 열쇠 이름의 배열 |
| **properties** | 열쇠마다 그 아래 스키마를 적용 | 열쇠 → 스키마 |
| **enum** | 정해둔 값 중 하나인가 | 허용할 값의 배열 |
| **minimum** | 숫자의 하한 (그 값 포함) | 숫자 하나 |
| **format** | 뜻까지 맞는가 | `"email"` 같은 이름. 기본은 주석이다 |

## 💡 실제 사례

- **들어온 요청 거르기** — 본문을 스키마에 걸어 형식이 어긋난 것을 업무 코드에 닿기 전에 되돌린다.
- **설정 파일 점검** — `check-jsonschema` 같은 명령줄 도구로 배포 전에 설정이 스키마를 지키는지 본다.
- **언어를 넘긴 재사용** — 같은 스키마 파일을 파이썬 구현에 그대로 물리면 같은 판정이 나온다.

## 🚫 흔한 오해

- **스키마를 통과했으니 안전한 데이터다** — 스키마에 안 적은 것은 검사되지 않는다. 규칙이 없는 자리는 무엇이 들어와도 통과다.
- **`format: "email"` 이라고 적으면 이메일인지 봐준다** — 기본은 값에 이름표를 붙이는 주석일 뿐이다. 검사로 쓰려면 구현에서 그 어휘를 따로 켜야 한다.
- **스키마를 붙였으니 검증 코드는 필요 없다** — 재는 것은 모양까지다. "이 사용자가 이 값을 쓸 수 있나" 같은 업무 규칙은 여전히 코드가 판단해야 한다.

## 📝 정리

JSON Schema 는 JSON 의 모양에 대한 약속을 JSON 으로 적어두는 형식이다. 적어둔 단언만 검사되고 결과는 참·거짓 하나로 떨어지므로, 무엇을 적지 않았는지가 곧 무엇을 검사하지 않는지가 된다. 규칙이 언어에 매여 있지 않다는 점이 이 형식이 살아남은 이유다.

## ❓ 이해했는지

- 스키마를 통과했는데도 엉뚱한 값이 들어오는 일이 왜 생기나 → 흔한 오해
- 보내는 쪽과 받는 쪽의 언어가 달라도 같은 규칙을 쓸 수 있는 이유는 → 해결하는 문제
- `"type": ["string", "null"]` 은 무엇까지 허용한다는 뜻인가 → 비교
