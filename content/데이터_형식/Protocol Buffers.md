# Protocol Buffers (프로토콜 버퍼)

## 📝 정의

Protocol Buffers 는 **주고받을 모양을 먼저 적어두고 값을 이진으로 펴는 방식**이다.

구글이 만들었고, 공식 문서는 이것을 "구조화된 자료를 직렬화하는, 언어와 플랫폼을 가리지 않는 확장 가능한 방식" 이라고 적는다. 메시지의 모양을 `.proto` 파일에 적어두면 protoc 라는 컴파일러가 언어마다 읽고 쓰는 코드를 만들어 준다. 공식 문서는 "JSON 과 비슷한데 더 작고 빠르고, 각 언어에서 바로 쓰는 코드를 만들어 준다" 고 말한다.

### 이름
Protocol :: 주고받는 약속
Buffer :: 담아 두는 그릇
= 붙여 읽으면 "약속대로 담아 두는 그릇". 무엇을 몇 번으로 담을지 미리 적어둔다

### 비유
조립 가구의 부품 봉지. 봉지에는 이름이 없고 번호만 붙어 있어서, 같이 온 설명서가 있어야 어느 부품인지 알 수 있다.

### 예
개발자 도구로 응답을 열었는데 JSON 같은 글자가 아니라 알아볼 수 없는 바이트만 보이던 그 순간이다.

## 🖼️ 그림으로 보기

```도해
흐름: 값 하나가 어떻게 이진 한 줄이 되어 건너가나
정의 파일 :: 필드마다 이름과 번호를 짝지어 적어 둔다
보내는 쪽 :: 이름 대신 번호를 붙여 바이트로 편다
오간 줄 :: 이름도 자료형도 없이 번호와 값만 실린다
받는 쪽 :: 같은 정의 파일을 보고 번호를 이름으로 되돌린다
= 이름표를 뗀 자리에 번호만 남는다. 그래서 작지만 정의 파일 없이는 못 읽는다
```

## ⚠️ 해결하는 문제

```도해
대조: 주고받을 모양을 미리 못 박지 않으면 무엇이 어긋나나
정하지 않으면 || 정의 파일로
이름표 :: 매번 같이 실린다 || 번호만 실린다
읽는 코드 :: 언어마다 손으로 || 컴파일러가 만든다
새 필드 :: 약속을 다시 한다 || 모르면 건너뛴다
= 모양을 파일 하나에 못 박아 두면 그 파일 하나에서 각 언어의 코드가 나온다
```

글자로 적는 형식은 값마다 이름을 같이 싣는다. 숫자 하나를 보내려고 그 값의 이름까지 매번 함께 보내는 셈이다. 한 건은 사소하지만 같은 메시지를 수없이 주고받는 자리에서는 그만큼이 계속 쌓인다. 읽는 쪽 코드도 언어마다 따로 만들어야 하고, 한쪽이 필드를 바꾸면 다른 쪽에서는 실행 중에야 드러난다.

Protocol Buffers 는 주고받을 모양을 `.proto` 파일 하나에 못 박는다. 필드마다 번호를 붙여 두고, 이진으로 펼 때는 이름 대신 그 번호를 키로 쓴다. 공식 문서는 이진 메시지를 "필드 번호를 키로 쓰는 키-값 짝의 연속" 이라고 적는다. 새 필드를 넣어도 그 번호를 모르는 옛 코드는 그 자리를 건너뛰고 지나가므로, 공식 문서는 몇 가지만 지키면 옛 코드가 새 메시지를 문제없이 읽고 새 코드도 옛 메시지를 그대로 읽는다고 적는다.

## 🧱 구성

```도해
층: Protocol Buffers 는 무엇 무엇으로 되어 있나
정의 언어 :: `.proto` 파일에 메시지와 필드 번호를 적는 문법
만들어진 코드 :: 컴파일러 protoc 가 그 파일에서 뽑아낸 언어별 코드
런타임 :: 만들어진 코드가 읽고 쓸 때 부르는 언어별 꾸러미
직렬화 형식 :: 필드 번호와 값을 바이트로 적는 규칙
오간 바이트 :: 그 규칙대로 파일에 남거나 선을 타는 실물
= 위는 사람이 손으로 쓰는 것이고, 아래로 갈수록 기계만 보는 것이다
```

## ⚙️ 작동 원리

`.proto` 를 protoc 에 넣으면 언어별 코드가 나온다. 그 코드가 값을 바이트로 펼 때는 필드를 하나씩 돌면서, 필드마다 앞에 열쇠 한 덩이를 놓고 그 뒤에 값을 잇는다. 열쇠에는 필드 번호와 값을 담는 꼴(wire type)이 함께 들어 있다 — 숫자를 그대로 적는 꼴인지, 길이를 먼저 적고 그만큼 이어 붙이는 꼴인지 같은 것이다.

받는 쪽은 열쇠를 읽어 번호를 보고, 자기 정의에 있는 번호면 그 필드 자리에 값을 넣는다. 모르는 번호가 나오면 같이 적힌 담는 꼴만 보고 그 값이 몇 바이트인지 알아내 그만큼 건너뛴다. 값이 무엇인지는 몰라도 얼마나 긴지는 알 수 있다는 것 — 옛 코드가 새 필드를 만나고도 멀쩡히 도는 이유가 이 한 가지다.

값이 없는 필드는 아예 실리지 않는다. 받는 쪽은 실려 온 열쇠만 보고 무엇이 왔는지 알고, 안 온 필드는 정의에 적힌 기본값으로 채운다. 이름이 한 글자도 실리지 않고 자주 쓰는 필드에 작은 번호를 주면 열쇠까지 짧아지는 것이, 같은 내용이 JSON 보다 작아지는 자리다.

## 📊 비교: JSON 과 무엇이 다른가

| | JSON | Protocol Buffers |
|---|---|---|
| **적는 모양** | 사람이 읽는 글자 | 사람이 못 읽는 바이트 |
| **이름표** | 키 이름이 매번 실린다 | 필드 번호만 실린다 |
| **미리 할 일** | 없다 | `.proto` 를 쓰고 컴파일한다 |
| **읽는 코드** | 언어의 표준 기능 | protoc 가 만들어 준다 |
| **열어 보기** | 그대로 읽힌다 | 정의 파일이 있어야 읽힌다 |

## 💡 실제 사례

- **gRPC 통신** — gRPC 는 이 방식을 창구의 모양을 적는 언어이자 메시지 형식으로 쓴다. `.proto` 하나에서 양쪽 코드가 같이 나온다.
- **언어가 섞인 팀** — 같은 `.proto` 를 각 언어로 컴파일하면, 손으로 맞추던 필드 이름과 자료형이 파일 하나에서 나온다.
- **작은 메시지를 자주 주고받는 자리** — 이름표가 빠지는 만큼 한 건이 작아져서, 같은 것을 수없이 보내는 자리에서 차이가 쌓인다.

## 🚫 흔한 오해

- **JSON 보다 빠르니 이쪽으로 다 바꾸면 된다** — 공식 문서도 JSON 과 비슷한데 더 작고 빠르다고만 말한다. 사람이 열어볼 수 없고 정의 파일과 컴파일 단계가 따라붙으니, 사람이 읽고 고쳐야 하는 설정 파일 같은 자리에는 맞지 않는다.
- **바이트만 받아도 뜻을 알 수 있다** — 공식 문서는 대응하는 `.proto` 파일 없이는 메시지를 온전히 해석할 수 없다고 적는다. 스스로를 설명하지 않는 형식이다.
- **필드 이름을 바꾸면 통신이 깨진다** — 이진으로 오가는 것은 번호다. 번호를 그대로 두면 이름은 바꿔도 그대로 읽힌다. 반대로 번호를 바꾸면 그때 어긋난다.

## 📝 정리

**"모양을 파일에 먼저 못 박고 이름 대신 번호로 부치는 방식"** 이라고 읽으면 된다. 이름표가 빠진 만큼 작아지지만, 같은 정의 파일을 양쪽이 들고 있어야 읽힌다. 그 파일 하나에서 각 언어의 코드가 나오는 것이 글자 형식과 갈리는 자리다.

## 🧒 열 살에게

조립 장난감 상자를 열면 부품마다 이름 대신 번호만 붙어 있지? 그래서 같이 든 설명서를 봐야 어느 게 뭔지 알아. 대신 이름을 다 안 적으니까 짐이 훨씬 가벼워져.

## ❓ 이해했는지

- 새 필드를 넣어 보냈는데 옛 프로그램이 멀쩡히 도는 이유는 무엇인가 → 해결하는 문제
